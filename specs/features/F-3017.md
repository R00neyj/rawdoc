## 2. 서버

### 2.1 경로 판정 — 누가 권위인가

- **"본문에 있는 경로" 의 원본은 D1 `docs.content` 다**: `path ∈ repoImagePaths(docs.content, github_links.path)`. 첨부 열람(`extractAttachmentRefs(docs.content)`)과 같은 출처라 같은 늦음(r8)을 갖는다. **대응표(`github_images`)는 권한 근거가 아니다** — 행은 본문 확인 없이 쓰이고(2.4) 본문에서 빠져도 다음 정리까지 남는다
- 요청의 `path` 는 클라이언트가 이미 푼 저장소 경로다. 서버는 다시 풀지 않고 **위 집합과 글자 그대로 같은지**만 본다. 집합 원소는 모두 F-3015 2장 공통 꼴이라 `..`·앞 `/`·`\`·제어 문자·스킴이 들어갈 수 없다. 그래도 공통 꼴이 아니면(`isRepoDir(path) && path !== ''` 가 거짓) 집합을 계산하기 전에 404
- 저장소·브랜치는 늘 그 문서 `github_links` 행의 `repo`·`branch` 로 고정된다. 요청에 저장소를 넣을 자리가 없다
- `repoImagePaths` 는 **선형**이어야 한다(r1): HTML 쪽은 r2 방식(정규식 하나로 `<img…src` 를 찾지 않는다), 같은 url 글자는 `resolveRepoPath` 를 한 번만 부른다. 결과 집합은 F-3015 A2 그대로

### 2.3 그림 출처 찾기 — `image-sources` (F-3013 3.7 의 `pull` 응답 `imageSources` 를 대신함, Q1)

- 몸통 상한 262,144 B(`readJsonLimited`). `paths`: 문자열 배열 1~500개, 각각 공통 꼴(아니면 400 `{ error: 'invalid', field: 'paths' }`). 클라이언트가 **합친 뒤 본문**으로 `repoImagePaths` 를 계산해 보낸다. 서버는 본문에 있는지 보지 않는다 — 주인이 자기 토큰으로 자기 저장소를 읽을 뿐이고, D1 은 늦다(r8)
- 경로의 폴더(맨 위는 `''`)를 처음 나온 순서로 모아 **앞 20개**만 `GET /repos/{repo}/contents/{dir}?ref={branch}`(F-3015 2장 인코딩, `dir` 이 빈 글자면 `/contents`). 20개를 넘으면 `truncated: true`
- 응답 배열에서 `type === 'file'` 이고 `path` 가 요청 경로와 같은 항목만 `{ path, sha, size }`. 확장자로 거르지 않는다(형식은 클라이언트 시그니처 판정, F-3013 3.7)
- 폴더 하나가 `github_not_found` 면 그 폴더만 건너뛴다. 그 밖 `GithubFailure` 는 첫 폴더면 `githubFailureResponse` 그대로, 아니면 거기서 멈추고 모은 것 + `truncated: true`. 하위 요청: GitHub 20 + 갱신 1 + 401 재시도 1 + 토큰 끝점 1 < 50(F-3013 w1)

### 2.4 받기·대응 기록 — `raw`, `images` PUT

- **raw**: `path` 공통 꼴(아니면 400). `githubFetch(…, '/repos/{repo}/contents/{path}?ref={branch}', { headers: { Accept: 'application/vnd.github.raw+json' } })`. `GithubFailure` 는 그대로. `Content-Length` 가 `GITHUB_RAW_MAX_BYTES` 를 넘거나, 읽다가 넘으면 413 `{ error: 'too_large', limit }`. 본문 확인 없음(위 2.3 과 같은 이유)
  - 머리: `Content-Type: application/octet-stream`, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: no-store`. 저장소 파일이 HTML 이어도 우리 출처에서 문서로 열리지 않게 한다 — 주인을 남의 저장소에 잇게 꾄 뒤 이 주소로 보내는 경로를 막는다
- **images PUT**: 몸통 상한 4,096 B. `path` 공통 꼴, `blobSha` 40자 소문자 16진수, `attachment` 가 `{16hex}.{png|jpg|gif|webp}`(각각 400 `field`). 그 첨부가 `attachments` 에 `owner_id = 나`, `e2ee = 0`, 같은 `ext` 로 있어야 한다(없으면 404 `not_found`)
  - 한 batch: `INSERT … ON CONFLICT (doc_id, path) DO UPDATE SET attachment_id, ext, blob_sha, created_at = now` (`owner_id` = 나) + `dayUsageStatement`
  - 문서당 대응 행 1,000개 상한 — 새 경로인데 이미 1,000개면 409 `{ error: 'too_many', limit: 1000 }`
  - 본문에 그 경로가 있는지는 보지 않는다(r8). 남는 행은 3.3 이 지운다. 갈아 끼워진 옛 첨부는 참조가 끊겨 다음 정리가 지운다

### 2.5 프록시 — `img`·공개 셋 (F-3013 3.8 계약을 아래로 확정)

검사 순서 (어느 단계든 실패는 몸통 `{ error: 'not_found' }` 404 — 연결 없음·본문에 없음·GitHub 오류를 구분해 주지 않는다):

1. `path` 공통 꼴
2. 문서 권한 — 로그인: `getDocAccess`(보기·막힘 포함). 공개: 해당 공개 첨부 핸들러와 **같은 검사 순서**(토큰 모양 → `findPublicLink` → 대상 종류 → 링크 주인 문서 → 묶음은 `isDocInLinkSet`, 폴더는 `folderTreeIds`)
3. 연결 행: `github_links WHERE doc_id = ? AND owner_id = {문서 주인}`
4. `path ∈ repoImagePaths(docs.content, link.path)` (2.1)
5. 대응 행이 있고 그 첨부(주인 = 문서 주인, `e2ee = 0`)가 R2 에 있으면 `attachmentResponse` + 아래 머리, `Cache-Control: private, max-age=300`. 끝
6. `loadEnabledGithub` 가 null 이면 404 — **Cache API 를 보기 전**(F-3018 넘김)
7. 문서 주인의 `github_accounts` 행이 있고 `refresh_expires_at > now` — 아니면 404. 역시 캐시 앞
8. `caches.default.match(열쇠)` — 있으면 머리를 아래 값으로 다시 써서 낸다
9. 주인 토큰으로 raw 받기(2.4 와 같은 호출). `Content-Length` 또는 읽은 길이가 `GITHUB_PROXY_MAX_BYTES` 를 넘으면 404
10. 형식 판정: `sniffImage` 가 맞으면 `IMAGE_MIME[ext]`(픽셀 상한 넘음 포함 null 이면 다음). 아니면 경로가 `.svg`(대소문자 무시)로 끝나고 앞 4,096 바이트(latin1)에 `<svg`(대소문자 무시)가 있을 때만 `image/svg+xml`. 그 밖 404
11. 응답 + `ctx.waitUntil(caches.default.put(열쇠, 사본))`

**머리** (5·8·11 모두, 계약):

```
Content-Type: {서버 판정}
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src data:; sandbox
Cross-Origin-Resource-Policy: same-origin
Content-Disposition: inline
Cache-Control: private, max-age=300
Referrer-Policy: no-referrer
```

- `sandbox`(허용 토큰 없음)는 SVG 를 주소로 바로 열어도 스크립트·폼·같은 출처 권한이 없게 한다. `<img>` 로 그린 SVG 는 원래 스크립트를 돌리지 않는다. `img-src data:`·`font-src data:` 는 그림 편집기가 내보낸 SVG 의 내장 그림·글꼴을 살리려는 것 — 바깥 주소는 여전히 못 부른다
- 클라이언트 `Content-Type`·GitHub 가 준 `Content-Type` 은 쓰지 않는다. SVG 는 확장자와 내용 둘 다 맞아야 한다 — `.png` 이름의 HTML 은 10번에서 404
- **캐시 열쇠**: `{요청 origin}/api/github-cache/{repo_id}/{encodeURIComponent(branch)}/{encodePathSegments(path)}`. `/api/*` 는 `run_worker_first` 라 이 주소로 들어온 요청이 CDN 캐시에서 바로 나가지 않는다(r11). 이름 있는 캐시(`caches.open`)를 쓰지 않는다 — 저장소 식별자에 이름을 붙이지 않는 불변식과 부딪칠 자리를 만들지 않는다
  - 넣는 사본은 `Cache-Control: public, max-age=300` 으로 바꿔 넣는다(`private` 은 Cache API 가 저장하지 않을 수 있다 — 7장 2). 내보낼 때는 늘 위 머리
  - GitHub 에서 받은 200 만 넣는다. 404·형식 실패는 넣지 않는다. R2 대응(5번)은 넣지 않는다
  - 열쇠에 문서·주인이 없다: 같은 저장소를 잇는 주인 둘이 사본을 나눈다. 연결 PUT 이 `push` 권한을 GitHub 에서 확인했으므로(F-3015 Q1) 둘 다 그 저장소를 읽을 수 있던 사람이다 (Q2)
- `typeof caches === 'undefined'`(node 테스트)면 캐시 단계를 건너뛴다

## 3. 첨부 쪽

### 3.1 열람 판정 — `isDocAttachmentRef` (F-3013 3.8 ②)

```ts
export function isDocAttachmentRef(env: Env, doc: { id: string; content: string }, attachmentId: string): Promise<boolean>
```

- `extractAttachmentRefs(doc.content).has(id)` 면 바로 참(D1 읽기 0 — 지금 경로가 느려지지 않는다). 아니면 `github_images g JOIN github_links l ON l.doc_id = g.doc_id WHERE g.doc_id = ? AND g.attachment_id = ?` 행 중 `g.path ∈ repoImagePaths(doc.content, l.path)` 가 있으면 참
- r6 의 네 자리가 이것으로 바뀐다. 그 뒤 `isDocAttachmentOwner`·`e2ee = 0` 검사는 그대로. F-3013 3.8 ② 의 이름 `docAttachmentRefs`(집합)는 쓰지 않는다 — 한 id 만 물으면 대응 질의를 그 id 로 좁힐 수 있다

### 3.2 지우기 판정 — `isAttachmentInUse`·`handleDeleteAttachment`

- `isAttachmentInUse` 끝에 한 갈래: `github_images g JOIN github_links l … JOIN docs d ON d.id = g.doc_id WHERE g.owner_id = {나} AND g.attachment_id = ?` 중 `g.path ∈ repoImagePaths(d.content, l.path)` 가 하나라도 있으면 409 `in_use`. 대응 행은 늘 문서 주인 것이라 편집 초대 갈래는 필요 없다
- 지우기가 성공하면 같은 batch 에 `DELETE FROM github_images WHERE owner_id = ? AND attachment_id = ?` — 없는 첨부를 가리키는 대응을 남기지 않는다

### 3.3 매일 정리 — `cleanupServerAttachments` (F-3013 3.8 ①)

순서 (기존 (A)(B) 뒤에 (C), 지우기 뒤에 (D)):

- **(C) 대응 참조**: 대응 행이 있는 문서를 id 순으로 200개씩(`docs.id > ? … LIMIT 200`, 기존 쪽 나누기 방식) 읽고 그 문서들의 대응 행·연결 `path` 를 읽는다. **지금 있는 대응 행의 `attachment_id` 는 모두 `refs` 에 넣는다.** 그중 정리할 행 = 연결이 없거나, `path ∉ repoImagePaths(content, link.path)` 이면서 `created_at < now − GRACE_MS`
- 기존 지우기 (R2 → `attachments`)
- **(D)** 정리할 행을 `DELETE FROM github_images WHERE doc_id = ? AND path = ?` 로, 실행당 500행까지
- 결과: 본문에서 빠진 그림의 첨부는 **(D) 다음 실행**에 처음으로 참조 없음이 되고, 그때 첨부 `created_at` 기준 24시간 유예(F-219)를 그대로 거친다. 즉 줄을 지운 뒤 최소 하루 + 대응 행 24시간 유예를 지나야 지워진다. 대응 행의 24시간 유예는 D1 늦음(r8)·막 올린 대응을 지키려는 것
- 로그 `attachment gc: deleted={n} failed={n} github_rows={n}`
- 클라이언트 정리(`cleanupUnusedAttachments`)는 `idb` 만이라 손대지 않는다(F-3013 c2)

## 7. 확인 못 한 것 (H1·H2 로 확인)
1. workerd CPU — r1~r4 는 Node 수치. 프록시 한 번 = D1 4~6번 + `repoImagePaths`(1MB 그림 1,000개 2.5ms) + 받기. 10MB 를 `arrayBuffer()` 로 읽는 CPU 는 재지 않았다
2. Cache API 가 `Cache-Control: private` 사본을 저장하지 않는다는 것은 Cloudflare 문서를 이번에 받아 읽지 않은 기억이다. 넣을 때 `public` 으로 바꾸므로 어느 쪽이든 동작은 같다
3. Contents `raw` 응답에 `Content-Length` 가 늘 오는지 — 안 오면 읽으면서 상한을 센다(2.4·2.5 규칙 그대로)
4. 받은 SVG 의 `img-src data:` 가 `<img>` 로 그릴 때도 이 CSP 의 지배를 받는지는 브라우저마다 다를 수 있다 — H1

## 9. 열린 질문

### Q1. 그림 출처를 어디서 주나 — **기본값: 따로 `POST …/github/image-sources { paths }` (클라이언트가 합친 본문으로 경로 계산)**
- 이유: ① 서버가 `pull` 안에서 base64 를 풀어 훑으면 r4 2.5ms + r3 최대 2.5ms 가 F-3015 r6 의 9.77ms(Node) 위에 얹혀 CPU 10ms 를 넘기 쉽다 ② 필요한 그림은 원격 본문이 아니라 **합친 뒤 본문**의 것이다 ③ 가져오기(`file`)도 같은 길로 된다 — `pull` 에 붙이면 `file` 에도 붙여야 한다 ④ 받아 넣기에 실패한 그림을 나중에 다시 해도 월 횟수가 들지 않는다
- 다른 안(F-3013 원안): `pull`·`file` 응답에 `imageSources`. 왕복이 하나 줄지만 위 ①③ 을 지고, F-3015 의 `githubRepos.ts`·`githubLinks.ts` 를 이 명세가 고쳐야 한다

### Q2. 프록시 캐시 열쇠에 주인을 넣나 — **기본값: 넣지 않는다 (`repo_id`·`branch`·`path`)**
- 이유: F-3013 3.8 그대로. 같은 저장소를 잇는 주인은 모두 연결 때 쓰기 권한을 GitHub 에서 확인받았다(F-3015 Q1). 인기 공개 저장소를 여럿이 이으면 GitHub 호출을 나눈다
- 다른 안: 열쇠에 `owner_id` — 한 주인이 저장소 권한을 잃은 뒤 다른 주인이 받아 둔 사본을 300초 동안 내보낼 틈이 없어진다. 대신 주인마다 따로 받는다

### Q3. SVG 를 `inline` 으로 내나 — **기본값: `inline` + `sandbox` CSP**
- 이유: `<img>` 는 `Content-Disposition` 을 보지 않고, 주소로 바로 열었을 때 그림이 보이는 편이 "이미지 새 탭에서 열기" 와 맞다. 스크립트는 `sandbox`·`default-src 'none'` 이 막는다
- 다른 안: SVG 만 `attachment` — 주소로 바로 열면 내려받기가 된다. 브라우저 CSP 구현 차이(7장 4)에 기대지 않는 한 겹 더
