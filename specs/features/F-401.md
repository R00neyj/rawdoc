## 2. 마이그레이션 `migrations/0011_e2ee.sql` (계약)

```sql
-- F-401 금고(종단간 암호화) 열·키 묶음 표 (specs/features/F-400.md 3.1, F-401.md 2장)
ALTER TABLE docs ADD COLUMN e2ee_key TEXT;                          -- 금고 문서의 감싼 문서 키(base64). NULL 이면 일반 문서
ALTER TABLE docs ADD COLUMN attachment_refs TEXT;                   -- 금고 문서만. 본문이 쓰는 첨부 id(16진 16자) JSON 배열, 평문
ALTER TABLE folders ADD COLUMN e2ee INTEGER NOT NULL DEFAULT 0;     -- 1 이면 금고 폴더
ALTER TABLE attachments ADD COLUMN e2ee INTEGER NOT NULL DEFAULT 0; -- 1 이면 암호 첨부 (F-402 가 쓴다)
CREATE TABLE e2ee_keys (                                            -- 계정 금고 키 묶음, 계정마다 한 줄
  user_id TEXT PRIMARY KEY REFERENCES users(id),
  bundle TEXT NOT NULL,                                             -- E2eeKeyBundle JSON (F-400 2.3). 서버는 크기만 본다
  rev INTEGER NOT NULL,                                             -- 1 부터. 바꿀 때마다 +1, 조건부 UPDATE
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

- **기존 행 기본값**: 문서 `e2ee_key` NULL·`attachment_refs` NULL, 폴더 `e2ee` 0, 첨부 `e2ee` 0 — 모두 일반. 채우는 `UPDATE` 는 없다(r1)
- **금고 문서 행의 불변식**: `e2ee_key IS NOT NULL` ⇔ 금고 문서. 금고 문서의 `attachment_refs` 는 늘 JSON 배열 문자열(빈 배열 `'[]'` 포함), 일반 문서는 늘 NULL. 서버의 모든 쓰기가 이것을 지킨다(3장)
- 색인은 더하지 않는다. 새 조회(`owner_id = ? AND e2ee_key IS NOT NULL` 등)는 모두 `owner_id` 로 먼저 좁혀져 기존 `docs_owner_updated`·`folders_owner` 색인을 탄다
- **옛 Worker 와 함께 살 수 있다** — 옛 코드는 `INSERT` 에 열 이름을 적고(`docs.ts` `handleCreateDoc`, `folders.ts` `handleCreateFolder`) `SELECT *` 는 필드를 골라 옮기므로(`rowToDoc`·`rowToFolder`) 새 열이 있어도 동작이 같다. 그래서 원격 적용은 배포 직전 아무 때나 된다(CLAUDE.md "Remote D1 migrations are not automated")
- `worker/testD1.ts` `openTestDb()` 가 `migrations/*.sql` 을 번호 순서로 전부 적용하므로 `testD1` 을 쓰는 테스트(`docs.test.ts`·`usageRoutes.test.ts`·`writeGate.test.ts`·`accountBlock.test.ts`·`usage.test.ts`·`publicPage.test.ts` 등)에는 새 열이 저절로 들어간다

## 3. 새 라우트와 바뀌는 문서 라우트

### 3.1 키 묶음 — `worker/e2eeKeys.ts`

| 라우트 | 요청 | 성공 | 실패 | 쓰기 관문 |
| --- | --- | --- | --- | --- |
| `GET /api/e2ee/keys` | — | 200 `{ bundle: string, rev: number }` | 401 · 404 `{ error: 'no_vault' }` | 아님 |
| `PUT /api/e2ee/keys` | `{ bundle: string, baseRev: number }` | 200 `{ rev: number }` | 401 · 403 `account_blocked`(관문) · 429(관문) · 400 `{ error: 'invalid', field: 'bundle' \| 'baseRev' }` · 409 `{ error: 'conflict', rev: number }` · 413 `{ error: 'too_large', limit: 4096 }` | 걸린다 |
| `DELETE /api/e2ee/keys` | — | 204 | 401 · 403 · 429 · 409 `{ error: 'vault_not_empty', docs: number, folders: number }` | 걸린다 |

규칙:

- 본인 것만 읽고 쓴다(`requireUser` 의 `user.id`). 남의 묶음에 닿는 경로가 없다
- `PUT` 몸통은 `readJsonLimited(request, 16_384)` 로 읽는다 — 묶음 JSON 이 JSON 문자열 안에 들어가 따옴표가 이스케이프되면 최대 두 배 가까이 늘어서다. 몸통이 16,384 B 를 넘거나 `bundle` 의 UTF-8 바이트가 `E2EE_BUNDLE_MAX_BYTES`(4,096)를 넘으면 413 `{ error: 'too_large', limit: 4096 }`. `badBody` 는 `limit: MAX_CONTENT_BYTES` 를 싣기 때문에 여기서는 쓰지 않는다
- `bundle` 은 길이 1 이상 문자열이면 된다. **서버는 JSON 으로 풀어 보지 않는다**(F-400 2.3 "크기만 본다"). `baseRev` 는 0 이상 정수
- `baseRev` 판정 — 먼저 지금 행을 읽는다(`SELECT rev FROM e2ee_keys WHERE user_id = ?`):
  - 행이 없고 `baseRev` 0 → 새로 만든다. `rev` 1
  - 행이 있고 `baseRev` = 지금 `rev` → 바꾼다. `rev` +1
  - 그 밖 → 409 `{ error: 'conflict', rev: 지금 rev }` (행이 없으면 `rev: 0`). **batch 전에 끝나므로 하루 카운터가 오르지 않는다**(F-2025 6장 규칙 "409 사전 검사는 사용량 줄 없음")
  - 쓰기는 조건부다 — 새로 만들기는 `INSERT … ON CONFLICT(user_id) DO NOTHING`, 바꾸기는 `UPDATE … WHERE user_id = ? AND rev = ?`. batch `[쓰기 문장, dayUsageStatement(user.id)]`. 첫 문장이 0행이면(두 기기 동시 암호 바꾸기) 다시 읽어 409 `conflict` — 이때 하루는 이미 +1 이다(r3, 지금 `updateDocRow` 경합과 같다)
- `DELETE` — 행이 없으면 D1 에 쓰지 않고 204(다시 불러도 안전). 금고 문서(`docs.owner_id = ? AND e2ee_key IS NOT NULL`)나 금고 폴더(`folders.owner_id = ? AND e2ee = 1`)가 하나라도 있으면 409 `vault_not_empty` 에 두 개수. 없으면 batch `[조건부 DELETE(같은 두 NOT EXISTS 를 문장 안에 둔다 — r5), dayUsageStatement]` → 204. 조건부 DELETE 가 0행이면(그 사이 금고 문서가 생김) 다시 세어 409
- 응답은 모두 `jsonResponse` — `Cache-Control: no-store` 가 이미 붙는다(`worker/http.ts` `JSON_HEADERS`)

### 3.2 문서 만들기 `POST /api/docs` — 금고 필드

몸통에 선택 필드 둘을 더한다(F-400 3.8):

```ts
// POST /api/docs 몸통에 더하는 것. 둘 다 없으면 지금과 똑같다
e2eeKey?: string          // 감싼 문서 키 base64. 있으면 금고 문서
attachmentRefs?: string[] // e2eeKey 가 있을 때만. 없으면 []
```

판정 순서(지금 순서 사이에 끼운다 — 번호가 계약이다):

1. 지금의 `id`·`lineEnding`·`folderId`·`createdAt`·`updatedAt`·`pinnedAt` 검사 그대로
2. `e2eeKey` 가 있으면 `isValidWrappedKey` — 아니면 400 `field: 'e2eeKey'`
3. 제목·본문: `e2eeKey` 가 있으면 제목 `isBase64Text(title, E2EE_MAX_TITLE_CHARS)`(아니면 400 `field: 'title'`), 본문 `isBase64Text(content, Infinity)`(아니면 400 `field: 'content'`) 뒤 `isContentTooLarge` 413. 없으면 지금 규칙(`isValidTitle`, 문자열, 413)
4. `attachmentRefs`: `e2eeKey` 가 없는데 있으면 400 `field: 'attachmentRefs'`. 있으면 `isValidAttachmentRefs`(아니면 400)
5. 같은 `id` 가 이미 있으면 지금 분기 그대로(내 것이면 200 그 행, 남의 것이면 409 `id_taken`) — 재시도가 안전해야 하므로 아래 409 들보다 앞이다
6. `folderId` 가 있으면 `getOwnedFolder(env, folderId, user)` 로 폴더를 읽는다. 폴더가 금고인데 `e2eeKey` 가 없으면 409 `{ error: 'e2ee_folder' }`. 폴더가 없거나 남의 것이면 **지금처럼 통과**(지금도 `folderId` 존재를 확인하지 않는다 — 새 400 을 만들면 오프라인에서 폴더보다 문서가 먼저 올라가는 경우가 깨질 수 있어 바꾸지 않는다)
7. `e2eeKey` 가 있으면 `e2ee_keys` 에 내 행이 있는지 본다. 없으면 409 `{ error: 'no_vault' }`
8. 지금의 `checkDocCreate` 413 → batch `[INSERT(두 열 포함), ...docUsageStatements(+content 바이트, +1)]`

- 6·7 은 batch **전** 사전 검사다 — 하루 카운터가 오르지 않는다
- 7 은 사전 검사만 한다. 같은 순간 다른 탭이 `DELETE /api/e2ee/keys` 를 부르는 경합은 받아들인다(11장 Q2)
- 금고 문서는 일반 폴더에도 만들 수 있다(F-400 3.6 "금고 문서는 일반 폴더에도 있을 수 있다")
- 저장: `e2ee_key` = 받은 값, `attachment_refs` = `JSON.stringify(attachmentRefs ?? [])`. 일반 문서는 둘 다 NULL
- 응답 201 은 `rowToDoc` — 금고면 `e2eeKey`·`attachmentRefs` 가 실린다(3.5)

### 3.3 문서 쓰기 `PUT /api/docs/:id` — `e2ee: true` 표지

```ts
// PUT /api/docs/:id 몸통에 더하는 것
e2ee?: boolean            // 금고 문서에 쓸 때 true 필수
attachmentRefs?: string[] // e2ee 가 true 일 때만. 없으면 저장된 값 그대로
```

판정 순서(번호가 계약이다 — 지금 `handleUpdateDoc` 순서에 끼운다):

1. 몸통 읽기(1,100,000 B 넘으면 413) · 객체 아님 400
2. `e2ee` 가 있는데 불리언이 아니면 400 `field: 'e2ee'`. `false` 는 없는 것과 같다
3. 제목·본문: `e2ee === true` 면 3.2 의 3번 금고 규칙, 아니면 지금 규칙
4. `attachmentRefs`: `e2ee !== true` 인데 있으면 400, 있으면 `isValidAttachmentRefs`
5. `baseVersion` 정수 아님 400
6. `getDocAccess` → 404 · `blocked` 403 `account_blocked` · edit 미만 403 `forbidden` (지금 그대로. 금고 문서의 비소유자는 여기서 404 — 6.1)
7. **표지 대조**: 행이 금고(`e2ee_key` 있음)인데 `e2ee !== true` → 409 `{ error: 'e2ee_doc' }`. 행이 일반인데 `e2ee === true` → 409 `{ error: 'not_e2ee' }`
8. 일반 문서만: 지금의 편집 잠금 423 검사. **금고 문서는 `getActiveLock` 을 부르지 않고 `X-Lock-Session` 도 보지 않는다**(F-400 3.4 "편집 잠금을 잡지 않는다")
9. 버전 틀림 → 409 `{ error: 'conflict', doc }` (지금 그대로. 금고면 `doc` 에 `e2eeKey`·`attachmentRefs`)
10. 늘어나면 `checkDocGrow` 413 (지금 그대로 — 금고 봉투 길이의 증감)
11. 쓰기: 일반 문서는 지금의 `updateDocRow` **그대로**. 금고 문서는 새 조건부 쓰기 — 제목·본문·`attachment_refs`(받았을 때만 바꿈)·버전·`updated_at` 을 `id`·`owner_id`·`version` 과 `e2ee_key IS NOT NULL` 조건으로 바꾸고, 같은 batch 에 `docUsageStatements`(증감, 문서 수 0). 0행이면 지금처럼 다시 읽어 409 `conflict`
12. 200 `rowToDoc`

- 7번이 버전 검사(9번)보다 앞인 이유: 옛 탭은 버전이 맞아도 봉투를 평문으로 덮을 수 있다 — 표지가 먼저 막아야 한다
- 7·8·9 는 batch 전 사전 검사라 하루 카운터가 오르지 않는다
- **왜 `updateDocRow` 를 고치지 않나**: 일반 → 금고 전환(3.4)은 늘 `version` 을 올리므로, 전환 전에 읽은 행으로 하는 일반 쓰기는 `AND version = ?` 에서 0행이 된다. `worker/docWrite.test.ts` 50·80행이 그 문장을 글자까지 보므로 바꾸면 회귀만 는다
- 금고 쓰기 함수 이름은 구현 재량(`updateE2eeDocRow` 를 권함). 반환 모양은 `updateDocRow` 와 같게 한다

### 3.4 옮기기·빼기 `PUT /api/docs/:id/e2ee` — `worker/e2eeDocs.ts`

```ts
// 몸통 (F-400 3.8)
type SetDocE2eeBody = {
  e2eeKey: string | null          // 문자열 = 금고로 옮기기, null = 금고에서 빼기
  title: string                   // 옮기기: 제목 봉투 base64 / 빼기: 평문 제목
  content: string                 // 옮기기: 본문 봉투 base64 / 빼기: 평문 본문(저장 문자열, lineEnding 그대로)
  attachmentRefs: string[] | null // 옮기기: 배열(빈 배열 가능) / 빼기: null 또는 없음
  baseVersion: number
}
```

| 응답 | 언제 |
| --- | --- |
| 200 `rowToDoc(새 행)` + `purged: boolean` | 성공 (`purged` 는 아래 batch 뒤 규칙) |
| 400 `{ error: 'invalid', field }` | `e2eeKey` 가 문자열도 null 도 아님·`isValidWrappedKey` 아님 / 옮기기인데 제목·본문이 base64 아님·제목 2,040자 넘음·`attachmentRefs` 가 배열 아님 / 빼기인데 제목 500자 넘음·`attachmentRefs` 가 null·없음이 아님 / `baseVersion` 정수 아님 |
| 404 `not_found` | 문서 없음, **소유자가 아님**(초대받은 편집자여도) |
| 403 `account_blocked` | 막힌 계정 (`getDocAccess` 의 `blocked`) |
| 409 `{ error: 'e2ee_doc' }` | 옮기기인데 이미 금고 문서 |
| 409 `{ error: 'not_e2ee' }` | 빼기인데 일반 문서 |
| 409 `{ error: 'e2ee_folder' }` | 빼기인데 문서가 금고 폴더 안 — 폴더를 먼저 꺼야 한다(F-400 4.3 "폴더는 `e2ee` 를 먼저 끄고") |
| 409 `{ error: 'no_vault' }` | 옮기기인데 `e2ee_keys` 에 내 행이 없음 |
| 409 `{ error: 'conflict', doc }` | 버전 틀림(사전 검사) 또는 batch 첫 문장 0행 |
| 413 `{ error: 'too_large', limit: 1000000 }` | 본문 1,000,000 B 초과, 몸통 1,100,000 B 초과 |
| 413 `doc_quota_exceeded` | 증감(새 본문 바이트 − 옛 본문 바이트) > 0 이고 `checkDocGrow` 가 걸림 |

판정 순서는 표의 위에서 아래(400 → 404 → 403 → 409 `e2ee_doc`·`not_e2ee` → `e2ee_folder` → `no_vault` → `conflict` → 413 총량). 모두 batch 전이라 하루 카운터가 오르지 않는다

batch (순서가 계약이다 — 사용량 줄의 `changes()` 가 **바로 앞 문장**을 본다, F-2025 5.1):

1. `UPDATE docs SET title, content, e2ee_key, attachment_refs, version = baseVersion + 1, updated_at = now WHERE id AND owner_id AND version = baseVersion` — 옮기기면 `attachment_refs` = JSON 배열, 빼기면 NULL
2. `docUsageStatements(actor = owner = user.id, deltaBytes, deltaDocs 0)`
3. 옮기기만: 그 문서의 살아 있는 공유 링크 끊기(`share_links` `revoked_at = now`, `target_type = 'doc'`)
4. 옮기기만: `share_link_docs` 에서 `doc_id` = 이 문서인 행 전부 지우기 — **남의 묶음에 끼어 있던 것도**(묶음 링크의 주인은 이 문서의 주인뿐이지만 시작 문서가 다른 링크일 수 있다)
5. 옮기기만: `grants` 에서 이 문서(`target_type = 'doc'`) 행 전부 지우기

- 3·4·5 에는 **"1번이 실제로 바뀌었을 때만"** 조건을 문장 안에 둔다 — `AND EXISTS (SELECT 1 FROM docs WHERE id = ? AND e2ee_key = ?)`(새 감싼 키를 바인딩). 경합으로 1번이 0행이면 링크·초대가 그대로 남아야 한다. 새 감싼 키는 무작위라 이 조건은 이번 요청이 쓴 행만 맞는다
- 빼기에서 3·4·5 가 없는 이유: 금고 문서에는 링크·묶음·초대가 생길 수 없다(6장)
- `doc_locks` 행은 건드리지 않는다 — F-309 가 표를 지우면 문장이 실패한다. 금고 쓰기는 잠금을 보지 않는다(3.3 8번)
- batch 뒤 1번이 1행이면 **양쪽 모두** DO 저장소를 지운다 — 옮기기는 DO 저장소의 평문 Yjs 이력을 지우고 열린 연결을 `4404 deleted` 로 닫는다. 빼기는 남아 있을지 모르는 옛 저장소를 지워 다음 실시간 열기가 D1 의 평문에서 새로 시작하게 한다. 1번이 0행이면 다시 읽어 없으면 404, 있으면 409 `conflict` 그 행
- **지우기는 응답 전에 기다린다 (11장 Q4, 사용자 결정 대안 A).** `notifyPurge` 의 `waitUntil`(응답 뒤 실행) 대신 `purgeRoom` RPC 를 직접 기다리고, 던지면 **한 번 더**(모두 최대 2번) 부른다. 두 번 다 던지면 `console.error('e2ee_purge_failed', id)` 한 줄을 남기고 응답은 그대로 200 이다 — D1 batch 는 이미 커밋됐으므로 되돌리지 않는다. `DOC_ROOM` 바인딩이 없는 환경(`docRoomRpc.ts` `roomStub` 이 `null`)은 성공으로 친다. 기다리는 도우미는 `worker/docRoomRpc.ts` 에 두지 않고 `worker/e2eeDocs.ts` 안에 둔다(소유 표 밖 파일을 늘리지 않는다 — `roomStub` 과 같은 방식으로 `env.DOC_ROOM.getByName(id)` 를 부른다)
- 응답 200 몸통 = `rowToDoc(새 행)` 에 필드 하나:

```ts
purged: boolean // DO 저장소 지우기가 성공했으면 true. false 면 F-407 이 알림을 띄운다
```
- 대상 폴더 규칙: 옮기기는 어느 폴더에 있어도 된다. 빼기는 금고 폴더 안이면 409(위 표)
- 이 라우트는 `/api/docs/:id/e2ee` 로 `index.ts` 라우트 표에 들어가고, 비-GET `/api/` 라 쓰기 관문에 저절로 걸린다

## 4. 검사 상수·함수 — `worker/validate.ts` (계약)

**상수는 한 곳이다 (main 결정, 2026-09-25).** 금고 크기 상수와 일반 문서의 서버 상한은 F-403 이 만든 `src/lib/e2eeLimits.ts` 에 이미 있다. worker 는 거기서 import 하고 **같은 값을 새로 적지 않는다.** `worker/tsconfig.json` `include` 에 `../src/lib/e2eeLimits.ts` 를 더한다(그 파일은 DOM 타입을 쓰지 않는다 — 파일 머리 주석)

| worker 이름 (그대로 둔다 — 부르는 곳이 많다) | 받는 값 (`src/lib/e2eeLimits.ts`) | 값 (2026-09-25 두 파일에서 확인) |
| --- | --- | --- |
| `validate.ts` `MAX_CONTENT_BYTES` | `E2EE_SERVER_MAX_CONTENT_BYTES` | 1,000,000 = 지금 1,000,000 |
| `validate.ts` `MAX_TITLE_CHARS` | `E2EE_MAX_PLAIN_TITLE_CHARS` | 500 = 지금 500 |
| `attachments.ts` `MAX_ATTACHMENT_BYTES` | `E2EE_SERVER_MAX_ATTACHMENT_BYTES` | 5,242,880 = 지금 5,242,880 |
| (새로 쓰는 곳에서 직접 import) | `E2EE_MAX_TITLE_CHARS` · `E2EE_MAX_ATTACHMENT_REFS` · `E2EE_BUNDLE_MAX_BYTES` | 2,040 · 1,000 · 4,096 |

- worker 쪽 세 이름은 `export const MAX_CONTENT_BYTES = E2EE_SERVER_MAX_CONTENT_BYTES` 처럼 **받아서 다시 내보낸다** — `docs.ts`·`v1.ts`·`docRoomCore.ts`·테스트가 부르는 이름을 바꾸지 않기 위해서다. 값이 같으므로 동작은 그대로다
- `MAX_BODY_BYTES`(1,100,000)·`MAX_FOLDER_NAME_CHARS`(200)는 서버 전용이라 `validate.ts` 에 그대로 둔다

```ts
// worker/validate.ts — 서버 전용 상수와 검사 함수
export const E2EE_WRAPPED_KEY_MAX_CHARS = 128

// 표준 base64(알파벳 A-Z a-z 0-9 + /, 패딩 = 는 끝 두 자 안에서만), 길이 % 4 === 0, 길이 ≤ maxChars. 빈 문자열은 참
export function isBase64Text(value: unknown, maxChars: number): value is string
// isBase64Text 이고 길이 4 이상 E2EE_WRAPPED_KEY_MAX_CHARS 이하
export function isValidWrappedKey(value: unknown): value is string
// 배열, 원소 수 ≤ E2EE_MAX_ATTACHMENT_REFS, 원소마다 /^[0-9a-f]{16}$/. 중복은 허용하고 받은 그대로 저장
export function isValidAttachmentRefs(value: unknown): value is string[]
```

- **본문도 base64 인지 본다**(11장 Q1). 서버가 봉투가 진짜 암호문인지는 알 수 없지만, 평문 Markdown 은 거의 늘 공백·줄바꿈을 담아 이 검사에 걸린다 — 클라이언트 버그로 **평문이 금고 표지를 달고** 저장되는 사고를 막는 그물이다
- 비용: 1,000,000자에 허용 밖 글자를 찾는 방식은 0.87ms, 끝까지 맞추는 정규식은 3.9ms(r8, node). 구현은 **허용 밖 글자 찾기 + 길이·패딩 위치 확인**으로 한다 — 같은 요청의 `JSON.parse`(0.86ms)와 같은 크기로 묶어 두려는 것이다. 무료 플랜 CPU 한도(10ms 로 알고 있으나 이 명세에서 확인하지 않았다)에 여유를 남긴다
- 감싼 키를 56자로 못박지 않고 4~128자로 둔 이유: 봉투 첫 바이트가 판(`0x01`)이라(F-400 3.2) 나중 판의 감싼 키 길이가 달라져도 서버를 고치지 않게 하려는 것이다
- 상수를 import 하므로 서버·클라이언트 값이 어긋날 수 없다 — 11장 Q6 은 이것으로 닫힌다

## 5. 폴더 — `worker/folders.ts`

### 5.1 응답과 몸통

```ts
// GET /api/folders·/v1/folders 원소, POST·PUT 응답. 금고 폴더일 때만 싣는다
e2ee?: true
// POST /api/folders·PUT /api/folders/:id 몸통에 더하는 것
e2ee?: boolean
```

- F-400 3.8 은 "`e2ee: boolean`" 이라 적었지만 **금고일 때만 `true` 로 싣는다** — F-400 4.2 의 `Folder.e2ee?: true` 와 맞고, 일반 폴더 응답이 지금과 키까지 같아 목록을 `toEqual` 로 보는 테스트가 안 깨진다(11장 Q5)
- `e2ee` 가 있는데 불리언이 아니면 400 `field: 'e2ee'`

### 5.2 규칙 (서버가 지킨다)

| 요청 | 조건 | 응답 |
| --- | --- | --- |
| `POST /api/folders` | 부모가 금고인데 `e2ee !== true` | 409 `{ error: 'e2ee_folder' }` |
| `POST /api/folders` | `e2ee: true` — 부모가 없거나 일반이어도 | 201, 행 `e2ee = 1` |
| `PUT /api/folders/:id` `parentId` | 새 부모가 금고인데 이 폴더의 결과 `e2ee`(몸통 값, 없으면 지금 값)가 거짓 | 409 `e2ee_folder` |
| `PUT /api/folders/:id` `e2ee: true` (지금 일반) | 바로 아래 문서 중 일반(`e2ee_key IS NULL`)이 있거나 바로 아래 폴더 중 일반(`e2ee = 0`)이 있음 | 409 `{ error: 'e2ee_folder_not_ready', docs: number, folders: number }` — 두 수는 바로 아래의 **일반** 문서·폴더 개수 |

| `DELETE /api/folders/:id` `delete-all` | — | 바꿀 것 없음 |

- **켜기는 조건부 한 문장**이다 — `UPDATE folders SET e2ee = 1 … WHERE id AND owner_id AND NOT EXISTS (일반 자식 문서) AND NOT EXISTS (일반 자식 폴더)`(r4). 사전 검사로 409 몸통의 두 수를 만들고, batch 의 조건이 그 사이 끼어든 평문 만들기를 막는다. 링크 끊기·초대 지우기 문장에는 `AND EXISTS (SELECT 1 FROM folders WHERE id = ? AND e2ee = 1)` 조건을 둔다 — 켜기가 0행이면 그대로 남는다. 켜기가 0행이면 다시 세어 409 `e2ee_folder_not_ready`
- **"금고 폴더 아래는 늘 금고" 가 만들기·옮기기·끄기 모두에서 지켜진다**(11장 Q3). 그래서 금고 폴더를 빼는 것(F-407)은 **가장 바깥 금고 폴더부터** 끄고 안쪽으로 내려가야 한다 — 안쪽부터 끄면 409 다. F-400 4.3 은 순서를 적지 않았다(13장 갱신 대상)
- 이 규칙이 지켜지므로 `DELETE` `move-up` 행(아래)의 "부모가 금고" 경우에 올라가는 폴더는 이미 금고다 — 올라가는 **일반 문서**만 막으면 된다. 검사는 그래도 문서·폴더 둘 다 본다(규칙 이전에 만든 행이 없더라도 같은 문장으로 둔다)
- 부모 폴더를 읽을 때는 `getOwnedFolder`(`SELECT * FROM folders WHERE id = ?`)를 쓴다 — `worker/folders.test.ts` 32행·`worker/v1.test.ts` 가짜 D1 이 이미 이 문장을 받는다. 없거나 남의 부모는 지금처럼 `canCreateFolder`·`canMoveFolder` 가 400 으로 막는다
- 하루 카운터: 지금처럼 성공한 batch 에 `dayUsageStatement` 하나. 409 는 사전 검사라 오르지 않는다(켜기 경합 0행만 예외 — r3 과 같은 이유로 +1)

### 6.1 `resolveDocAccess` 계약

```ts
export interface DocRowLike {
  id: string
  owner_id: string
  folder_id: string | null
  e2ee_key?: string | null // 없으면(undefined) 일반 문서로 본다. getDocAccess 는 늘 읽어 넘긴다
}
```

- 선택 필드로 두는 이유: `worker/access.test.ts` 가 `resolveDocAccess` 에 `{ id, owner_id, folder_id }` 글자를 열 군데 넘기고, `worker/tsconfig.json` 이 테스트까지 타입 검사한다. 필수로 바꾸면 타입 오류만 는다
- 대신 `resolveDocAccess` 에 행을 **직접** 넘기는 곳은 셋뿐이다 — `getDocAccess`(X2), `grants.ts` `checkOwnedTarget`(X3), `docRoomCore.ts` `revalidateConnections`(X16 으로 금고 행이 애초에 안 온다). 셋 모두 이 명세가 막는다. 새로 부르는 곳을 만들 때는 `e2ee_key` 를 함께 읽어야 한다 — 코드 주석으로 남긴다
- 소유자의 막힘(`blocked`)은 금고 문서에서도 지금 규칙 그대로(F-2028 4.2)

### 6.2 `/pub` 폴더 트리를 자르는 방식 (X11)

- 트리 거르기를 `ownerFolders` 한 곳에서 하므로 그 함수를 쓰는 넷 — `folderTreeIds`(공개 폴더 문서·**`attachments.ts` 의 공개 폴더 첨부**), `handleGetDocShareSet`·`handlePublicGetDocSet` 의 위키링크 해석기, `handlePublicGetFolder` — 이 모두 금고 폴더를 모른다
- 결과: 링크 폴더 자체가 금고면 `rootFolder` 를 못 찾아 404(정상 경로로는 폴더를 켤 때 링크가 끊겨 오지 않는다). 금고 폴더 아래 가지 전체가 빠진다 — 5.2 규칙상 그 가지는 모두 금고다
- 위키링크 해석기가 금고 폴더를 모르면 `[[금고폴더/…]]` 경로가 끊긴 링크가 된다 — 대상이 어차피 공개 묶음에 없으므로 결과가 같다
- `handlePublicGetDocSet` 의 소유자 문서 목록(320행 `SELECT id, title, folder_id FROM docs WHERE owner_id = ? ORDER BY updated_at DESC`)은 **거르지 않는다.** 해석기는 제목 → id 표만 만들고 `buildWikiLinkTable` 이 묶음 id(`allowed`)만 남기므로 금고 문서가 응답에 나가지 않는다. 봉투 base64 제목이 사용자가 쓴 `[[…]]` 와 우연히 같을 일도 없다. 거르면 `worker/links.test.ts` 68행이 깨지기만 한다 — F-400 7장이 이 줄을 깨질 곳으로 적었으나 필요 없다

## 11. 열린 질문 — 전부 닫힘 (2026-09-25)

Q3·Q4 는 사용자 답, Q6 은 main 의 상수 위치 결정으로 닫혔다. 나머지는 기본값으로 확정. "다른 안" 은 기록으로만 남긴다

### Q1. 금고 본문이 base64 인지 서버가 볼까 — **확정(기본값): 본다(4장)**

- 이유: 클라이언트가 평문을 실수로 금고 표지와 함께 보내는 사고를 서버에서 한 번 더 막는다. F-400 1.1 "서버가 보는 것은 암호문뿐" 을 서버 쪽에서 지킬 수 있는 유일한 검사다
- 비용: 1MB 에 약 0.9ms(r8, node — workerd 값은 모름)
- 다른 안: 제목만 본다. 본문 검사 비용이 사라지지만 평문 사고를 서버가 모른다. 바뀌는 것 — 3.2 3번의 본문 부분, D3 첫 칸, V1 은 그대로

### Q2. 금고 문서 만들기·옮기기가 키 묶음을 요구할까 — **확정(기본값): 요구한다, 사전 검사만(3.2 7번·3.4)**

- 이유: 묶음이 없는데 금고 문서가 생기면 아무도 못 연다. `DELETE /api/e2ee/keys` 가 금고 문서가 없을 때만 되므로 "금고 문서가 있으면 묶음도 있다" 가 서버에서 성립한다
- 받아들이는 틈: 같은 순간 다른 탭이 금고 초기화(`DELETE`)를 부르면 둘 다 통과할 수 있다. `INSERT … WHERE EXISTS (e2ee_keys)` 로 문장 안에 넣으면 막히지만(r3 로 돌아가는 것은 확인) 0행 뒤 응답 분기와 하루 카운터(+1)가 생긴다. 금고 초기화는 "모두 지우고 새로 시작" 이므로 그 틈의 문서도 버려질 문서다
- 다른 안: 요구하지 않는다. D2·C2 가 사라지고 `no_vault` 409 가 없어진다

### Q3. 금고 폴더 안 폴더 하나를 끄는 것도 받을까 — **답(2026-09-25 사용자): 막는다. 부모가 금고면 끄기 409 `e2ee_folder`**

- 결과: "금고 폴더 아래는 늘 금고" 가 만들기·옮기기·끄기 모두에서 지켜진다(5.2). F-407 의 폴더 빼기는 **가장 바깥 금고 폴더부터** 끈다
- 고르지 않은 안: 끄기를 늘 받는다(F-400 3.6 글자 그대로). 금고 폴더 아래 일반 폴더가 생겨 그 안에 평문 문서를 만들 수 있었다

### Q4. 옮기기 뒤 DO 저장소 지우기가 실패하면 — **답(2026-09-25 사용자): 대안 A. 응답 전에 `purgeRoom` 을 최대 2번 기다리고, 실패하면 200 에 `purged: false`(3.4)**

- 왜 문제인가: 실시간으로 편집했던 문서의 **옮기기 전 평문 Yjs 이력**이 DO SQLite 에 남는다. X15·X16 때문에 그 DO 는 다시 깨어나지 않는다 — 깨어나면 `load` 가 `roomGone` 으로 저장소를 비우지만(X16), 깨울 길이 없다. 그래서 **30일 뒤 사라지는 백업(F-400 m10)과 달리 기한 없이 남는다**
- 실패율은 재지 않았다. `purged: false` 가 오면 F-407 이 알림을 띄운다(13장 갱신 대상)
- 고르지 않은 안: 지금 도우미 그대로(응답 뒤 `waitUntil`, 로그만) / 다시 부를 수 있는 지우기 전용 라우트(`POST /api/docs/:id/purge`)

### Q5. 폴더 응답의 `e2ee` 를 늘 싣을까 — **확정(기본값): 금고일 때만 `e2ee: true`(5.1)**

## 12. F-309 와의 관계 (F-400 5.2)

- **이 명세가 남기는 것**: `PUT /api/docs/:id` 의 `baseVersion` 비교와 409 `{ error: 'conflict', doc }`(3.3 9번). 금고 분기는 `getActiveLock`·`X-Lock-Session` 을 부르지 않으므로(3.3 8번) F-309 가 `worker/locks.ts`·`doc_locks`·423 을 지울 때 **일반 분기의 8번만** 걷으면 된다
- **F-309 가 먼저 오면**: `handleUpdateDoc` 에서 잠금 검사가 이미 없다 → 3.3 8번은 "일반 문서만: (없음)" 이 된다. F-309 가 일반 문서의 `/api` PUT 을 막는 방향으로 좁히더라도 `e2ee_key IS NOT NULL` 행은 3.3 의 금고 분기로 보내야 한다 — F-309 명세가 이 절과 F-400 5.2 를 읽어야 한다(13장 갱신 대상). 마이그레이션 번호는 먼저 커밋한 쪽이 `0011` 을 쓰고 다른 쪽이 다음 번호로 민다(1장)
- **이 명세가 먼저 오면**: F-309 는 `handleUpdateDoc` 의 일반 분기와 `handleUpdateDocV1` 의 423 줄만 걷는다. 3.4 옮기기가 `doc_locks` 를 건드리지 않으므로 표를 지워도 이 명세 코드가 깨지지 않는다
- **outbox·충돌 사본**은 클라이언트라 F-405. 다만 서버가 돌려주는 409 몸통이 셋으로 갈린다는 것을 F-405 가 알아야 한다 — 아래
- **발견: 지금 클라이언트는 `e2ee_doc` 409 를 버전 충돌로 읽는다.** `src/storage/docsApi.ts` `updateDoc` 이 409 를 모두 `ApiError('conflict', { doc: data?.doc })` 로 바꾸고, `serverStore.ts` `handleConflict` 가 `doc` 없이도 **기기 캐시의 내용으로 `(충돌 사본)` 일반 문서를 새로 만든다.** 금고로 옮긴 뒤 옛 탭(F-405 전 코드)이 그 문서에 남은 편집을 보내면 옮기기 전 평문 + 편집이 **새 일반 문서로 서버에 다시 올라간다.** 내용을 잃지는 않지만 D-9 문구 "저장되지 않은 내용은 사라질 수 있습니다"(F-400 5.1)와 다르고, 평문이 다시 서버에 생긴다. 모든 조각을 한 번에 배포하므로(F-400 Q10) 배포 순간 열려 있던 탭에서만 일어난다. `createDoc`·`createFolder` 의 409 는 `id_taken` 으로 읽혀 "번호가 겹쳐 …" 알림이 뜬다(`e2ee_folder`·`no_vault` 도 같은 길)
- **CLI**(`cli/src/client.ts`): 403 은 `forbidden`(종료 코드 4 — F-400 1.3 과 같다). 409 `e2ee_folder` 는 `conflict` 로 읽혀 버전 충돌처럼 보인다 — F-400 1.3 이 CLI 새 판을 내지 않기로 했으므로 받아들인다
