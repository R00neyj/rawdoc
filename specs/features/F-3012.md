## 2. 무엇을 하나

- **언제**: `PUT /api/{docs|folders}/:id/grants/:email` 이 **새 초대 행을 만들었을 때만**. 판정은 푸시와 같다(F-3001 3.5 — upsert 의 `created_at` 이 이번 `now`). 역할만 바꾼 `PUT` 은 행을 만들지도, 옛 행의 역할을 고치지도 않는다(행은 "그때 받은 초대" 의 기록)
- **누구에게**: 초대 이메일(소문자) 그대로 `recipient_email`. **아직 가입 안 한 이메일에도 만든다** — 초대 자체가 이메일로 기다렸다가 가입하면 열리므로(`handleGetShared` 가 `user.email` 로 읽는다), 첫 로그인 때 `공유받음` 에 왜 문서가 있는지 알림함이 설명한다. 90일 정리·300개 상한이 그대로 걸리고, 새로 저장하는 개인정보는 없다(이메일은 `grants` 에 이미 있다). 열린 질문 Q3
- **금고**: 초대가 409(`checkOwnedTarget`)라 batch 에 닿지 않는다 → 행 없음
- **겹침**: 알림함은 **새 초대마다 한 행**. 10분 겹침 막기는 푸시에만 남는다(열린 질문 Q1)
- **푸시와의 관계**: 행 넣기는 **응답 전 같은 batch**(초대 upsert 와 한 트랜잭션), 푸시는 지금처럼 그 뒤 `pushInBackground`(`waitUntil`). 푸시 판정·겹침 질의·`sharePushPayload` 는 그대로. VAPID 비밀이 없어도 행은 생긴다. 행 넣기는 `waitUntil` 의 CPU 를 쓰지 않는다 — 요청 본체 batch 에 문장 3개가 늘 뿐이고 D1 왕복 수는 같다(1번)
- `share` 행은 `push_due_at` 이 항상 NULL(6장 CHECK) — DocRoom 알람·`runDocPush` 가 보지 않는다

## 3. 서버 문장 — `worker/shareNotifications.ts`

```ts
export type ShareTarget = { targetType: 'doc' | 'folder'; targetId: string; email: string }
export function shareNotificationInsertStatements(
  db: D1Database,
  p: ShareTarget & { id: string; actorEmail: string; name: string; role: 'view' | 'edit'; now: number },
): D1PreparedStatement[]
export function shareNotificationDeleteStatements(db: D1Database, p: ShareTarget): D1PreparedStatement[]
```

### 3.1 넣기 (초대 `PUT` batch, 초대 upsert **뒤**, `dayUsageStatement` 와 순서 무관)

세 문장, 모두 같은 조건 "`grants` 에 (`targetType`, `targetId`, `email`) 행이 있고 `created_at = now`" 를 `WHERE EXISTS` 로 건다 — batch 가 트랜잭션이라 앞 upsert 결과를 본다. RETURNING 값을 Worker 로 받아 두 번째 batch 를 보내지 않는다.

1. `INSERT INTO notifications` — `id` 는 `crypto.randomUUID()`(읽음 API 가 UUID 만 받는다), `kind='share'`, 문서면 `doc_id=targetId`·`folder_id` NULL, 폴더면 반대, `comment_id`·`thread_id`·`push_due_at` NULL, `actor_email` = 초대한 사람 `user.email`, `doc_title` = `checkOwnedTarget` 이 이미 읽은 문서 제목 또는 폴더 이름(자르지 않는다 — 제목 500자·폴더 200자 검사가 이미 있다), `excerpt` = `''`, `created_at = now`, `role`
2. 받는 사람 리비전 +1 — `UPDATE users SET notif_rev = notif_rev + 1 WHERE email = ?`. 미가입이면 0행
3. 300개 상한 — 기존 `TRIM_NOTIFICATIONS_SQL` 에 `[email]`. 조건 없이 돌려도 300 이하면 0행

### 3.2 `handlePutGrant` 에서

`id` 를 만들고 3.1 문장을 기존 batch 배열 끝에 붙인다. `inserted` 를 읽는 자리(배열 첫 결과)와 푸시 판정은 바뀌지 않는다.

### 3.3 지우기 (초대를 지울 때)

- 두 문장: `notifRevBeforeDeleteSql(where)` 로 리비전 → `DELETE FROM notifications WHERE` 같은 where. where = `recipient_email = ? AND kind = 'share' AND`(문서면 `doc_id = ?`, 폴더면 `folder_id = ?`). **읽은 행도 지운다**
- `handleDeleteGrant`(주인이 초대 빼기) batch 에 붙인다. 지워진 초대가 없어도(이미 없음) 0행으로 끝난다
- **F-3011 에 넘기는 조건**: 받는 쪽 나가기도 같은 batch 에 이 함수를 붙인다
- 이유: 남은 행을 누르면 열 수 없는 문서·폴더로 간다. "넣었다 뺐다" 를 반복하면 매번 새 행이 생기지만(F-3007 Q1 과 같은 성질) 받는 사람이 읽을 행은 항상 살아 있는 초대 하나에 하나다

### 3.4 다른 지우는 자리

| 자리 | 문서 행 | 폴더 행 |
| --- | --- | --- |
| 문서 삭제 `docCommentDeleteStatements` | 기존 `doc_id = ?` 가 잡는다 | — |
| 금고로 옮기기 `e2eeCommentDeleteStatements` | 기존 `doc_id = ?1 AND …` 가 잡는다 | — |
| 폴더 삭제 `folderCommentDeleteStatements` | 기존(폴더 안 문서) | `FOLDER_NOTIFICATIONS_WHERE` 에 `OR folder_id IN (SELECT value FROM json_each(?2))` |
| 폴더 삭제 `contents=move-up`(`deleteFolderContents`) | 해당 없음(문서가 남는다) | 이 경로엔 알림 문장이 없다 — `targetShareCleanupStatements` 가 초대를 지우므로 매일 정리가 24시간 안에 잡는다. `worker/folders.ts` 는 손대지 않는다 |
| 계정 삭제 `accountCommentDeleteStatements` | 기존(`OWNER_DOCS`, 받는 사람) | `ACCOUNT_NOTIFICATIONS_WHERE` 에 `OR folder_id IN (SELECT id FROM folders WHERE owner_id = ?1)`. `folders` 를 지우기 전이라 성립(근거 4번째) |
| 매일 정리 `ORPHAN_WHERE` | 바뀜 ↓ | 바뀜 ↓ |

- `ORPHAN_WHERE` = `(kind <> 'share' AND {지금 NO_DOC 조건}) OR (kind = 'share' AND {받는 사람·대상의 grants 행 없음})`. 대상 종류는 `folder_id IS NULL` 이면 문서. 초대가 사라진 모든 경로(`move-up`, 빈 폴더를 금고로 — 둘 다 `worker/folders.ts` 가 `grants` 만 지운다)의 안전망
- 리비전은 기존처럼 `notifRevBeforeDeleteSql(ORPHAN_WHERE)` 가 같은 where 로 올린다

## 4. 응답 JSON (계약 — F-2116 이 읽는다)

`src/lib/docComments.ts` 에 더한다:

```ts
export const INBOX_NOTIFICATION_KINDS = ['mention', 'reply', 'comment', 'share'] as const
export type InboxNotificationKind = (typeof INBOX_NOTIFICATION_KINDS)[number]
export type ShareNotificationItem = {
  id: string
  kind: 'share'
  target: 'doc' | 'folder'
  targetId: string
  name: string            // 만들 때의 문서 제목 또는 폴더 이름. 빈 문자열일 수 있다
  role: 'view' | 'edit'
```

- `share` 항목 키는 **정확히 이 9개**. 댓글 종류 항목은 지금 키 10개 그대로 — `docId` 등을 `share` 에 섞지 않는다
- `target`·`targetId`·`name`·`role`·`actorEmail` 은 `PushShare`(`src/lib/pushText.ts`)와 같은 이름 — F-2116 이 문구를 `sharePushPayload` 와 맞출 때 그대로 넘길 수 있다
- 기존 `NotificationKind`·`NOTIFICATION_KINDS` 를 넓히지 않는 이유: 넓히면 지금 클라이언트가 `share` 를 불러 키 9개 항목에서 응답 전체를 버리고(근거 3번째), `COMMENT_TITLE` 등이 타입 오류가 난다. F-2116 이 `fetchNotifications` 를 `INBOX_NOTIFICATION_KINDS` 로 바꾸는 순간 `share` 가 켜진다

## 5. 목록 API — `worker/notifications.ts`

- `?kinds=` 검사·정규화 순서를 `INBOX_NOTIFICATION_KINDS` 로. `share` 가 끝이라 기존 조합의 정규화 결과·ETag 는 글자까지 같다(`-mention.reply.comment` 그대로). 새 꼬리 예: `?kinds=mention,reply,comment,share` → `W/"n1-{userId}-{rev}-{limit}-mention.reply.comment.share"`, `?kinds=share` → `…-share`
- `?kinds=` 없음 → `NOTIFICATIONS_DEFAULT_KINDS`(`mention`·`reply`) 그대로. **`share` 를 기본 종류에 넣지 않는다**(열린 질문 Q4) — "기본 켜짐" 은 4장 끝 문장으로 이룬다: 끄는 설정이 없고 클라이언트가 아는 종류를 전부 부른다
- 목록 질의에 `folder_id`, `role` 두 열. 항목 만들기는 `kind === 'share'` 면 4장 모양(`target` = `folder_id` 가 있으면 `'folder'`, `targetId` = `doc_id ?? folder_id`, `name` = `doc_title`), 아니면 지금 `toItem` 그대로. 응답 타입은 `InboxNotificationsResponse`
- `unread` 는 지금처럼 요청한 종류만 센다 → 지금 클라이언트의 배지에 `share` 가 안 들어간다
- 읽음 `POST /api/notifications/read` 는 바뀌지 않는다. `{ all: true }` 는 종류 무관이라 지금 클라이언트의 `모두 읽음` 이 보이지 않던 `share` 도 읽음으로 만든다(F-3005 Q3 과 같은 성질)
- 지금 클라이언트는 `share` 행이 생길 때 리비전이 올라 304 대신 200 을 한 번 받는다(F-3005 5.3 과 같은 비용)

## 6. 마이그레이션 `migrations/0021_notifications_share.sql` (계약)

0018 과 같은 순서(새 표 → 옮기기 → 옛 표 지우기 → 이름 바꾸기 → 색인). 새 표:

```sql
CREATE TABLE notifications_new (
  id TEXT PRIMARY KEY,
  recipient_email TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('mention','reply','comment','share')),
  doc_id TEXT,
  comment_id TEXT,
  thread_id TEXT,
  actor_email TEXT NOT NULL,
  doc_title TEXT NOT NULL,           -- share: 문서 제목 또는 폴더 이름
  excerpt TEXT NOT NULL,             -- share: ''
  created_at INTEGER NOT NULL,
  read_at INTEGER,
  push_due_at INTEGER,
  folder_id TEXT,                    -- share 폴더 대상만
  role TEXT CHECK (role IN ('view','edit')),
  CHECK (CASE WHEN kind = 'share'
    THEN comment_id IS NULL AND thread_id IS NULL AND push_due_at IS NULL AND role IS NOT NULL AND (doc_id IS NULL) <> (folder_id IS NULL)
    ELSE doc_id IS NOT NULL AND comment_id IS NOT NULL AND thread_id IS NOT NULL AND folder_id IS NULL AND role IS NULL END),
  UNIQUE (recipient_email, comment_id, kind)
);
```

- 옮기기는 기존 12열 그대로(`folder_id`·`role` NULL). 색인: 기존 `notifications_recipient_order`·`notifications_doc` 같은 정의, 새 `CREATE INDEX notifications_folder ON notifications(folder_id) WHERE folder_id IS NOT NULL`
- `UNIQUE` 는 `share` 의 `comment_id` 가 NULL 이라 걸리지 않는다(SQLite 는 NULL 끼리 다르다 — 재초대 행이 들어감을 잼)
- **배포 순서**: 원격 D1 에 0021 을 코드보다 먼저(CLAUDE.md). 옛 코드는 새 표에서 그대로 돈다 — 댓글 행 넣기는 두 새 열이 NULL 이라 CHECK 를 통과하고, 옛 매일 정리가 지울 `share` 행은 새 코드 전엔 없다

## 11. 열린 질문

### Q1. 같은 주인이 짧은 사이 여러 개를 초대할 때 알림함 행을 하나로 줄이나 — **기본값: 줄이지 않는다(초대마다 한 행)**

- 이유: 알림함은 울리지 않는 목록이고, 행마다 이동할 대상이 다르다. 줄이면 둘째 이후 대상은 알림함에서 찾을 길이 없다. 쏟아짐은 300개 상한·쓰기 제한(F-2026)이 막는다
- 다른 안(푸시처럼 10분 겹침이면 생략): 3.1 조건에 F-3007 `SHARE_OVERLAP_SQL` 의 "없음" 을 더한다. S7 이 행 1 로 바뀌고, F-2116 은 "외 N개" 를 보여 줄 수 없다(몇 개인지 저장 안 함)

### Q2. 초대를 지우면 알림 행도 지우나 — **기본값: 지운다(읽은 행 포함, 3.3)**

- 다른 안(남긴다): 3.3·S8 이 빠지고 F-3011 이 부를 함수도 없다. 대신 F-2116 이 "열 수 없는 대상" 행을 눌렀을 때의 처리를 정해야 하고, 매일 정리의 "초대 없음" 규칙(3.4)도 빼야 앞뒤가 맞는다

### Q3. 가입 안 한 이메일에도 행을 만드나 — **기본값: 만든다(2장)**

- 다른 안(만들지 않음): 3.1 조건에 `EXISTS (SELECT 1 FROM users WHERE email = ?)` 를 더하고 S5 를 뒤집는다. 가입 뒤 `공유받음` 에만 보이고 누가 언제 줬는지는 사이드바 `ownerEmail` 로만 안다

### Q4. `NOTIFICATIONS_DEFAULT_KINDS` 에 `share` 를 넣나 — **기본값: 넣지 않는다(5장)**

- 메인 지시는 "기본 종류에 기본 켜짐으로" 였다. 코드상 그 상수는 사용자 기본값이 아니라 "`?kinds=` 를 안 보내는 옛 클라이언트에게 줄 것" 이고(F-3005), 끄는 설정은 없다. 넣으면 그런 클라이언트가 키 9개 항목 하나에 알림함 전체를 잃고, 기본 ETag 모양(꼬리 없음)의 뜻도 바뀐다
- "기본 켜짐" 은 F-2116 이 `INBOX_NOTIFICATION_KINDS` 를 부르면 이뤄진다
- 다른 안(넣음): `NOTIFICATIONS_DEFAULT_KINDS = ['mention','reply','share']`, S10 의 `kinds` 없음 경우가 `share` 를 담도록 바뀌고 F-3005 N1 테스트 값이 바뀐다
