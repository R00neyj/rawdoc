## 2. 동작

### 2.1 요청 (계약)

- `fetchNotifications` 는 **`/api/notifications?kinds=mention,reply,comment`** 를 부른다. 값은 `NOTIFICATION_KINDS` 를 `,` 로 이은 것(`src/lib/docComments.ts` import) — 종류가 늘면 저절로 따라간다. 쉼표는 인코딩하지 않는다
- 다른 요청 옵션(`credentials`·`cache: 'no-store'`·`If-None-Match`)과 결과 판정은 그대로. 400(서버가 `kinds` 를 거절)은 지금처럼 `reason: 'invalid'`
- `markNotificationsRead` 는 바꾸지 않는다 — `{ all: true }` 는 종류와 상관없이 전부 읽음(F-3005 Q3)

### 2.2 응답 검사·문구

- `isNotificationItem`: `kind` 가 `NOTIFICATION_KINDS` 중 하나면 통과. 그 밖(`'like'` 등)은 지금처럼 false → 응답 전체 `null`
- `notificationText`: `kind` 로 셋을 가른다. `comment` 문구는 3장. 제목 자르기·빈 제목 규칙(`formatNotificationTitle`)은 셋 모두 같다
- 알림함 목록·배지·사이드바 점(F-510)·항목 눌러 이동(F-507 4.5)은 종류를 보지 않으므로 코드 변경 없이 `comment` 에도 그대로 선다. `comment` 행의 `threadId` 는 그 댓글이 속한 스레드(F-3005 4.1)라 이동 규칙도 같다

### 2.3 가짜 서버 (`e2e/fixtures/fakeServer.js`)

- 알림 GET 라우트를 **정규식 `/\/api\/notifications(\?[^#]*)?$/`** 로 바꾼다 — 근거 표의 셋째 줄. 쿼리 없는 주소와 `/read` 판정이 지금과 같다
- `kinds` 를 서버처럼 거른다: 쿼리에 `kinds` 가 없으면 `mention`·`reply` 만, 있으면 쉼표로 가른 종류만 `items`·`unread` 에 넣는다. 그래야 클라이언트가 `kinds` 를 빠뜨렸을 때 E1 이 빨개진다. 값 검사(400)는 흉내 내지 않는다 — node 테스트(F-3005 N3) 몫
- ETag(`W/"fake-{rev}"`)는 그대로 — 클라이언트가 늘 같은 `kinds` 를 보내므로 종류 꼬리가 필요 없다
- 요청 기록의 `search` 는 이미 남는다(`logNotificationRequest`)
