## 2. 계약 — `src/lib/folderTree.ts` 새 내보내기

다른 파일(Sidebar·MoveDocDialog·publicDoc·sidebarSelection·worker)과 테스트가 이 이름에 기대므로 여기서 정한다

```ts
// folderId 자신부터 위로 올라가며 id 를 모은다(가까운 것부터).
// 없는 폴더를 만나거나 이미 모은 id 를 다시 만나면 멈춘다. folderId 가 null 이거나 없는 폴더면 빈 배열
export function folderAncestors(folders: FolderLike[], folderId: string | null): string[]

// 폴더를 트리 순서(부모 다음 자식, 형제는 이름 ko 순)로 한 줄로 편다. depth 는 최상위가 0.
// 부모 판정은 buildTree 와 같다(3.3) — 없는 부모·순환에 든 폴더는 최상위
export function flattenFolderTree<T extends FolderLike>(folders: T[]): Array<T & { depth: number }>
```

- 기존 내보내기(`buildTree`·`canCreateFolder`·`canMoveFolder`·`ancestorsOfDoc`·`descendantFolderIds`·`pinnedDocs`·`resolveTargetFolderId`)의 **이름·인자·반환 모양은 그대로**다
- `folderAncestors` 는 **저장된 부모 사슬 그대로**다(순환이면 순환의 한 바퀴까지 담는다). 서버 권한·공개 범위 판정이 이것을 쓴다. 화면 트리의 부모 판정(3.3)과 다른 이유: 권한은 데이터가 말하는 대로 판정해야 하고, 화면은 모든 폴더를 한 번씩 보여야 해서다

## 3. 클라이언트 규칙 (`src/lib/folderTree.ts`)

### 3.1 만들기 — `canCreateFolder`

- 부모가 `null`·`undefined` 면 참. 부모가 **존재하는 폴더**면 참. 그 밖은 거짓
- 부모의 깊이는 보지 않는다

### 3.2 옮기기 — `canMoveFolder`

**판정(집합으로 정의)**: `parentId` 가 `null`·`undefined` 면 참. 아니면 대상 폴더가 존재하고, **대상이 `id` 자신이거나 `id` 의 자손이 아닐 때만** 참. `id` 의 자손 = `descendantFolderIds(folders, id)` 에서 `id` 를 뺀 것

- 자식이 있는 폴더도 다른 폴더 안으로 갈 수 있다. 대상이 몇 단계에 있든 상관없다
- **계산은 대상에서 위로 올라간다.** "대상의 저장된 조상 사슬(`folderAncestors(folders, parentId)`, 대상 자신 포함)에 `id` 가 있으면 거짓" 은 순환이 없는 데이터에서 위 집합 정의와 같은 답이다(1장 머리 (d), 200쌍 일치). 이유: `Sidebar.tsx` `canDropOn` 이 **`dragover` 마다** 이 함수를 부르고, 자손 집합 방식은 깊은 사슬에서 깊이의 제곱으로 느려진다(깊이 3,000 에서 238ms). 올라가기는 사슬 길이만큼만 본다
- 순환이 저장된 데이터(3.3)에서: 순환에 든 폴더를 최상위(`null`)로 옮기는 것은 늘 참이다 — **사용자가 순환을 푸는 길**이다. 순환에 든 폴더를 순환에 든 다른 폴더 안으로 옮기는 것은 거짓(그 대상의 사슬에 자신이 있다). 판정은 반드시 끝난다

### 3.3 순환 데이터 — 화면 부모 판정

**순환에 든 폴더** = 저장된 `parentId` 를 따라(존재하는 폴더로만) 올라가다 자기 자신에게 돌아오는 폴더. 자기 자신을 부모로 가리키는 폴더(자기 순환)도 포함한다

화면 트리에서 폴더의 부모는 다음과 같이 정한다. `buildTree`·`ancestorsOfDoc`·`flattenFolderTree` 가 **모두 이 한 규칙**을 쓴다

| 저장된 `parentId` | 화면 부모 |
| --- | --- |
| `null` | 최상위 |
| 없는 폴더를 가리킴 | 최상위 (지금 규칙 그대로) |
| 그 폴더가 **순환에 듦** | 최상위 — 순환의 모든 폴더가 최상위에 따로 보인다 |
| 순환으로 들어가는 사슬에 있지만 자신은 순환 밖 | 저장된 부모 그대로 (예: C→A, A↔B 면 C 는 A 아래) |
| 그 밖 | 저장된 부모 |

- 결과: 모든 폴더가 트리에 **정확히 한 번** 나온다. 지금 `buildTree` 는 순환에 든 폴더를 루트에서 닿지 못해 **사이드바에서 사라지게 한다**(코드 확인)
- `ancestorsOfDoc` 은 위 화면 부모로 올라간다. 순환 A↔B 의 A 안 문서면 `['A']`. 지금은 `while` 에 방문 기록이 없어 **무한 루프**다(코드 확인). 순환 안에 없는 폴더에서는 결과가 지금과 같다
- 순환이 생기는 길 — 이번에 코드로 찾은 것 둘(재현은 하지 않았다)
  1. **서버 경합**: `worker/folders.ts` `handleUpdateFolder` 는 소유자 폴더를 `SELECT` 해 `canMoveFolder` 로 검사한 뒤 **따로** `UPDATE` 한다. D1 은 문장 하나하나를 따로 처리하므로(가정 G1) 두 기기가 거의 동시에 A→B, B→A 를 보내면 둘 다 검사를 통과해 순환이 저장될 수 있다
  2. **클라이언트 병합(지금 코드에도 있다)**: 기기 1 이 오프라인에서 A→B 를 옮겨 outbox 에 둔 사이, 기기 2 가 B→A 를 서버에 반영했다. 기기 1 이 다시 켜질 때 `serverStore.listFolders` 는 **보내지 않은 항목이 있는 폴더(A)는 캐시 값을, 나머지(B)는 서버 값을** 쓴다 — 목록 응답이 A→B 요청보다 먼저 오면 캐시에 A.parent=B·B.parent=A 가 함께 남는다. 뒤이은 A→B 요청은 서버가 400 으로 거절하고 outbox 에서 버려지지만, 다음 `listFolders` 전까지 캐시는 순환 그대로다. **옛 2단계 규칙에서도 두 폴더가 최상위·자식 없음이면 똑같이 생긴다** — 지금 앱이 그 상태로 켜지면 `ancestorsOfDoc`(부팅 중 `addOpenFolders` 호출)에서 탭이 멈춘다
  3. 저장소 3종의 `removeFolder(…, 'move-up')` 이 순환 A↔B 의 A 를 지우면 B 의 부모가 B 자신이 된다(자기 순환). 위 규칙이 그대로 막는다

### 3.4 `buildTree` 비용

- 부모별 폴더·문서 묶음을 **호출마다 한 번** 만들고 거기서 자식을 꺼낸다. 폴더마다 전체 배열을 훑지 않는다. 정렬 규칙(폴더 이름 ko 순 먼저, 문서 `updatedAt` 내림차순)과 반환 모양은 그대로
- 이유: 1장 머리 (e). 깊이 제한이 풀리면 볼트 가져오기(F-2019)로 폴더 수백 개가 흔해진다. 사이드바는 렌더마다(끌기 중 `dropTargetKey` 가 바뀔 때마다 포함) `buildTree` 를 부른다
- `Sidebar.tsx` 에서 `useMemo` 로 감싸는 일은 하지 않는다 — 묶기만으로 1,000/5,000 에서 1.5ms 라 충분하고, 호출부를 바꾸지 않는 편이 겹침이 적다

### 3.5 `dedupeDescendants` (`src/app/sidebarSelection.ts`)

- 선택 항목의 조상을 올라가는 `hasSelectedAncestor` 가 방문 기록 없이 `while` 을 돈다 — 순환 데이터에서 **무한 루프**다(코드 확인). 여러 항목 끌어놓기·`폴더로 옮기기` 가 이 함수를 부른다
- 올라가기를 `folderAncestors` 로 바꾼다(순환에서 멈춘다). 결과 규칙("선택 안에 조상 폴더가 있으면 뺀다")은 그대로

## 4. 서버 (`worker/`)

### 4.1 규칙

- `handleCreateFolder`·`handleUpdateFolder` 는 이미 `src/lib/folderTree` 의 `canCreateFolder`·`canMoveFolder` 를 부른다 — **3.1·3.2 로 함께 바뀐다.** 응답 모양·상태 코드는 그대로(거부는 `400 {"error":"invalid","field":"parentId"}`)
- 자기 자손 안으로 옮기기, 없는 부모, 자기 자신은 400. 3단계 이상 만들기·자식 있는 폴더 옮기기는 201·200
- **트리에서 나온 폴더 id 목록을 SQL `IN (…)` 바인딩으로 보내지 않는다.** 서브트리 크기에 상한이 없어서다. D1 한 질의의 바인딩 인자 한도(가정 G2)를 넘으면 질의가 실패한다. 이 명세가 새로 쓰는 질의는 소유자 id 로 읽고 메모리에서 거른다. 문서 초대 id 목록처럼 트리와 무관한 목록은 `worker/folders.ts` `BATCH_ID_LIMIT`(100)처럼 100개씩 나눈다(F-242 3.1 선례)

### 4.2 공개 폴더 — `folderTreeIds`·`handlePublicGetFolder` (`worker/links.ts`)

**결론: 소유자 폴더를 한 번 읽고 메모리에서 자손을 모은다. 재귀 CTE 로 내려가지 않는다**

| 방식 | 질의 수 | 방문 행 (1장 머리 (a)) | 순환 | 단위 테스트 |
| --- | --- | --- | --- | --- |
| **소유자 폴더 전부 + `descendantFolderIds`** (채택) | 1 | 소유자 폴더 수 F | `descendantFolderIds` 가 집합이라 끝난다 | 순수 함수라 가짜 DB 로 된다 |
| 아래로 재귀 CTE | 1 | F × 서브트리 크기 (5,000 폴더에서 460만) | `UNION` 이면 끝난다 | 가짜 DB 는 SQL 을 실행하지 않아 로직이 시험되지 않는다 |
| `parent_id` 색인 추가 + 재귀 CTE | 1 | 서브트리 크기 | 같음 | 같음. 마이그레이션이 필요하다 — 개요 2.1 "마이그레이션 없음" 과 어긋난다 |

- 지금 `folderTreeIds` 의 `WHERE parent_id = ? AND owner_id = ?` 도 색인이 `owner_id` 뿐이라 소유자 폴더 F 개를 훑는다(측정: 방문 행에 F 가 그대로 잡힌다). **채택안은 방문 행이 지금과 같다**
- `folderTreeIds(env, folderId, ownerId)` 는 이름·인자·반환을 그대로 두고 **링크 폴더와 모든 자손 id**(링크 폴더가 맨 앞)를 돌려준다. 쓰는 곳 셋(`handlePublicGetFolder`·`handlePublicGetFolderDoc`·`worker/attachments.ts` `handlePublicGetFolderAttachment`)이 같이 풀린다. 뒤의 둘은 결과를 `includes` 로만 쓰므로 코드가 바뀌지 않는다
- `handlePublicGetFolder`
  - 응답 모양은 그대로 `{ name, folders: [{id,name,parentId}], docs: [{id,title,folderId,updatedAt}] }`. `folders` 에 **링크 폴더를 뺀 모든 자손**을 담는다(지금은 직속만). 순서는 정하지 않는다 — 화면이 정렬한다(5.3)
  - 문서는 `folder_id IN (…)` 대신 소유자 문서 메타를 `updated_at DESC` 로 읽고(`docs_owner_updated` 색인) 서브트리 폴더 집합으로 거른다. 지금 질의도 같은 색인으로 소유자 문서를 전부 훑으므로 방문 행이 같다. 바인딩 한도를 피하려는 것이다
  - 소유자 폴더 목록은 요청당 한 번만 읽는다(`folderTreeIds` 와 폴더 이름용으로 두 번 읽지 않는다). 그러려면 `handlePublicGetFolder` 가 폴더 목록을 직접 읽고 `descendantFolderIds` 를 부른다 — `folderTreeIds` 는 나머지 두 곳용으로 남는다
- 링크 폴더가 순환에 들었으면(A↔B, 링크는 A) 자손은 {A, B} 다. B 의 문서가 공개된다 — 저장된 데이터대로다

### 4.3 권한 사슬 — `folderChainRole` (`worker/access.ts`) — **개요와 다르게 정한다 (Q1)**

지금: 사슬 한 칸마다 `grants` 조회 1번 + `folders` 부모 조회 1번 → 질의 2 × 깊이. 개요 2.2 는 "소유자 폴더를 한 번 읽어 메모리에서" 로 정했다

**이 명세의 결론: 질의 2번 이하, 방문 행 ≈ 깊이**

1. `folderId` 가 `null` 이면 질의 없이 없음(지금과 같다)
2. 이 이메일이 **이 소유자에게서 받은 폴더 초대**를 한 번 읽는다(`grants` 의 `grantee_email`·`target_type = 'folder'`·`owner_id` — `grants_grantee` 색인. `owner_id` 는 `handlePutGrant` 가 폴더 소유자로 넣는다, 코드 확인). **하나도 없으면 여기서 없음** — 폴더를 읽지 않는다
3. 있으면 `folderId` 에서 **위로 올라가는 재귀 CTE 한 번**으로 사슬 행을 읽는다. 기본키로 찾고, 각 단계에 `owner_id` 조건, `UNION`(중복 제거)으로 순환에서 끝난다(1장 머리 (b), 로컬 D1 확인)
4. 메모리에서 `folderAncestors(사슬 행, folderId)` 를 돌며 2 의 초대와 겹치는 것 중 가장 높은 역할

- 호출 모양: 소유자 id 가 필요하므로 `folderChainRole` 이 소유자 id 를 받는다. `resolveDocAccess`·`isDocAttachmentOwner` 는 `doc.owner_id` 를 넘긴다. 내보내지 않는 함수라 다른 파일은 바뀌지 않는다
- **왜 개요안(소유자 폴더 전부)이 아닌가**: 이 판정은 초대받은 사람이 문서를 **저장할 때마다**(`worker/docs.ts` `getDocAccess` 5곳) 그리고 **잠금 연장 20초마다**(`useDocLock.ts` `EXTEND_INTERVAL_MS`, `worker/locks.ts`) 돈다. 개요안은 매번 소유자 폴더 수 F 행을 읽는다 — 폴더 1,000개 소유자의 문서를 한 시간 편집하면 수십만 행이다. D1 무료 플랜의 하루 읽기 한도(가정 G3)에 닿을 수 있다. 이 명세안은 매번 깊이만큼(보통 10행 미만)이다
- 대가: 3 의 SQL 은 단위 테스트의 가짜 DB 가 실행하지 않는다. 가짜 DB 는 `WITH RECURSIVE` 로 시작하는 질의에 **그 소유자의 폴더 전부**(사슬의 상위 집합)를 돌려주고, 사슬 걷기·역할 계산은 4 의 순수 함수가 맡아 시험된다. SQL 자체는 로컬 D1 스모크(14.4 L1)와 1장 머리 (b)로 확인한다

### 4.4 공유받음 목록 — `handleGetShared` (`worker/grants.ts`)

지금: 초대 폴더의 직속 문서 + 직속 하위 폴더의 문서만 모은다(주석 "폴더는 2단계까지"). `viaFolder` 는 자신·부모 두 칸만 본다. 모은 문서마다 `resolveDocAccess`(질의 1 + 2 × 깊이)를 부른다. 초대 폴더 문서를 찾는 질의가 소유자 조건 없이 `SCAN docs` 다(1장 머리 (c))

**바뀌는 것**

- 대상 문서 = (문서 초대를 받은 문서) ∪ (**저장된 조상 사슬에 폴더 초대가 하나라도 있는 폴더**의 문서). 내 소유 문서는 뺀다(지금과 같다)
- 역할 = 문서 초대 역할과 사슬의 모든 폴더 초대 역할 중 가장 높은 것 — `folderChainRole` 과 같은 규칙
- `viaFolder` = 문서가 든 폴더에서 위로 올라가며 **처음 만나는 초대 폴더**(가장 가까운 조상, 자신 포함)의 `{id, name}`. 사슬에 초대 폴더가 없으면 없음. 문서 초대가 같이 있어도 폴더 초대가 사슬에 있으면 넣는다(지금과 같다)
- 질의 방식
  - 내 초대를 한 번 읽을 때 `owner_id` 도 같이 읽는다
  - 폴더 초대를 준 **소유자마다** 폴더 전부 1번 + 문서 메타 1번(`docs_owner_updated` 색인). 사슬은 `folderAncestors` 로 메모리에서
  - 문서 초대만 있는 문서(그 소유자가 폴더 초대를 주지 않음)는 id 목록으로 100개씩 나눠 읽는다. 그 문서의 폴더 역할은 없다 — 그 소유자의 폴더 초대가 없으니까
  - 문서마다 `resolveDocAccess` 를 부르지 않는다
  - 소유자 이메일은 지금처럼 소유자당 한 번
- 질의 수 = 1 + 2 × (폴더 초대를 준 소유자 수) + ⌈문서 초대만인 문서 수 / 100⌉ + 소유자 수. **폴더 깊이·문서 수와 무관하다.** 방문 행은 폴더 초대를 준 소유자의 폴더·문서 수 합 — 지금의 전체 문서 표 훑기보다 적다
- 응답 모양(`id`·`title`·`lineEnding`·`folderId`·`pinnedAt`·`version`·`createdAt`·`updatedAt`·`role`·`ownerEmail`·`viaFolder?`)은 그대로. 순서는 지금처럼 정하지 않는다(클라이언트 `sortByUpdatedAtDesc`)

### 4.5 서버 경합 — 판단

- **동시 이동 두 개가 순환을 만들 수 있다**(3.3 의 1). D1 에서 `prepare().first()`·`run()` 은 한 문장씩 따로 처리되고, 한 요청 안의 `SELECT` 와 `UPDATE` 사이에 다른 요청의 문장이 끼어들 수 있다. `batch()` 는 한 트랜잭션이지만 앞 `SELECT` 결과로 갈라질 수 없다(가정 G1)
- 막으려면 `UPDATE` 한 문장 안에 "새 부모의 위 사슬에 자신이 없을 때만" 조건을 재귀 CTE 로 넣고 바뀐 행 수가 0 이면 400 을 주면 된다(한 문장이라 원자적). **하지 않는다** — 개요 2.3 이 사용자 승인을 받은 결정이고, 클라이언트 병합 경로(3.3 의 2)는 서버를 막아도 남으므로 3.3 의 방어가 어차피 필요하다. Q3
- 순환이 저장돼도 서버는 멈추지 않는다: `descendantFolderIds`(집합), 재귀 CTE(`UNION`), `folderAncestors`(방문 기록), `serverStore.sortFoldersParentFirst`(`seen`) 모두 끝난다

```ts
export type PublicFolderGroup = {

export function publicFolderGroups(folder: PublicFolder): PublicFolderGroup[]
```

- 순서: `flattenFolderTree(folder.folders)`(형제는 이름 ko 순, 부모 다음 자식). 링크 폴더는 `folders` 에 없으므로 그 직속 하위가 `depth` 0 이 된다
- **빈 폴더 숨기기**: 자신과 모든 자손에 문서가 하나도 없으면 묶음을 만들지 않는다. 자신은 문서가 없어도 자손에 문서가 있으면 제목 줄만 나온다 — 손자 문서로 가는 길이 보여야 해서다. 지금 규칙("자기 문서가 없으면 숨김")은 한 단계일 때만 맞다
- 화면: 링크 폴더 문서 목록(지금 그대로) → 묶음마다 `.public-folder-list-group`(`--depth` 실제 값) 안에 제목과 문서 목록. 제목 요소는 `depth` 0 이 `h3`, 1 이 `h4`, 2 가 `h5`, 3 이상이 `h6` — 클래스는 모두 `.public-folder-list-subtitle`. 묶음은 **중첩하지 않고 차례로** 늘어놓는다(들여쓰기가 CSS 상한에서 멈추려면 부모 여백이 쌓이지 않아야 한다)
- `firstFolderDocId` = 링크 폴더 문서 중 첫 문서, 없으면 `publicFolderGroups` 순서로 처음 나오는 문서. 기존 테스트 3건은 그대로 통과한다
- **달라지는 것**: 하위 폴더 순서가 서버가 준 순서(정렬 없음 — `handlePublicGetFolder` 질의에 `ORDER BY` 가 없다)에서 이름순으로 바뀐다. Q5
- 위키링크 연결을 하지 않는 것(F-211 2.3)은 그대로

### 5.4 들여쓰기 상한 (`src/styles/app.css`)

| 선택자 | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| `.tree-row` 왼쪽 여백 | `--depth` × 14px | `min(--depth, 5)` × 14px — 최대 70px |
| `.tree-group::before` `left` | `--depth` × 14px + 11px | **`min(--depth, 4)`** × 14px + 11px (Q2) |

| `.public-folder-list-group` 왼쪽 여백 | 없음 | `min(--depth, 5)` × 14px (신규 규칙) |

- 상한 숫자는 CSS 에만 있다. JS 는 실제 깊이를 넘긴다
- **가이드 선은 한 단계 낮게(4) 멈춘다 — 개요 2.4 "같은 값으로 멈춘다" 를 이렇게 읽는다.** `--depth` d 인 그룹의 선은 d × 14 + 11px 에 있어 **부모 폴더 토글의 가운데**를 지나고, 자식 행(d+1)의 토글은 그보다 14px 오른쪽이다. 선도 5 에서 멈추면 5단계 그룹(선 81px)의 자식 행이 상한에 걸려 70px 에 그려지고 토글 가운데가 81px — **선이 자식 토글 아이콘 한가운데를 지난다**(`.tree-group::before` 는 `z-index: 1` 로 행 위에 그려진다). 4 에서 멈추면 5단계 이하 그룹의 선은 4단계 그룹의 선(67px)과 정확히 겹치고, `--muted` 가 불투명 색(`tokens.css` 확인)이라 겹쳐도 진해지지 않는다. 6단계 이하 행의 토글(70~92px)과 선(67px)의 관계가 다른 단계(선이 자식 토글 왼쪽 끝 3px 앞)와 같다
- `min()` 은 `calc()` 안에서 쓴다. 대상 브라우저(데스크톱 Chrome·Edge·Firefox·Safari 최신)가 모두 지원한다

## 6. 가져오기 (`src/app/importWorkspace.ts`)

- **workspace(`manifest.json` 있음)**: `buildWorkspaceFolderPlan` 의 3단계 이상 합치기(`depthOf`·`flattenedIds`·`existingDepth`)를 없앤다. 폴더는 manifest 의 부모 그대로(끊긴 부모는 최상위, `scope: 'folder'` 에서 `rootFolderId` 가 내게 있으면 그 안 — 지금 규칙). 경고 `2단계로 합친 폴더 {N}개` 를 없앤다
- **manifest 순환**: manifest 폴더끼리 부모 사슬이 순환이면 **그 순환에 든 폴더의 부모를 `null`**(`scope: 'folder'` 이고 루트가 붙는 경우엔 그 루트)로 본다 — 3.3 과 같은 규칙. 지금은 합치기 루프(`guard < 10`)가 순환을 이상하게 옮겼다. 부모가 자식보다 먼저 오는 정렬은 지금 방식 그대로(방문 기록이 있어 끝난다)
- **일반 zip(`manifest.json` 없음)**: `buildPlainFolders` 의 `dirSegs.length > 2` 자르기를 없앤다. `A/B/C/D/문서.md` → 폴더 `A`→`B`→`C`→`D` 안의 문서. 경고 `2단계로 합친 폴더 {N}개` 를 없앤다. 이 경로의 나머지(볼트 가져오기로 바뀌는 것)는 F-2019 다
- `applyImportPlan` 은 바꾸지 않는다. 폴더를 부모 먼저 만들고 `createFolder` 가 3.1 로 깊은 부모를 받아들인다

## 16. 열린 질문 / 사람 결정 필요

### Q1. 권한 사슬을 어떻게 읽나 — **기본값: 초대 먼저 읽고, 있으면 위로 올라가는 재귀 CTE 한 번 (4.3)** — 개요 2.2 와 다르다

- 개요안(소유자 폴더를 한 번 다 읽고 메모리에서): 판정마다 소유자 폴더 수만큼 행을 읽는다. 이 판정은 초대받은 사람의 저장·잠금 연장(20초)마다 돈다 — 폴더 1,000개 소유자면 한 시간 편집에 수십만 행. SQL 이 단순한 `SELECT` 라 가짜 DB 로 전부 시험된다
- 기본값안: 판정마다 초대 행 + 깊이만큼. 폴더 초대가 없으면 폴더를 아예 안 읽는다. 대신 `WITH RECURSIVE` SQL 자체는 단위 테스트가 실행하지 않는다 — 로컬 D1(1장 머리 (b), L1)로 확인한다
- 개요안을 고르면: 4.3 의 3 이 "소유자 폴더 전부 읽기" 로 바뀌고 S1 의 "사슬 질의를 보내지 않는다" 단언이 "폴더 질의를 보내지 않는다" 로 바뀐다. 나머지는 같다

### Q2. 가이드 선 상한 — **기본값: 4 (행은 5) (5.4)**

- 5(개요 문장 그대로): 6단계 이하 행의 토글 아이콘 한가운데를 5단계 그룹의 선이 지난다
- 4: 5단계 이하 그룹의 선이 4단계 선과 겹쳐 하나로 보인다. 6단계 이하 행과 선의 관계가 다른 단계와 같다
- 5 를 고르면 5.4 표 한 칸과 H1 의 "선이 토글을 지나지 않는지" 만 바뀐다

### Q3. 서버 이동을 한 문장으로 원자화하나 — **기본값: 하지 않는다 (4.5)**

- 개요 2.3 의 승인된 결정을 따른다. 하면 서버 쪽 순환은 사라지지만 클라이언트 병합 경로(3.3 의 2)는 남는다. 조건부 `UPDATE` 의 SQL 은 가짜 DB 로 시험되지 않는다
- 하기로 하면: `worker/folders.ts` 가 소유 표에 들고, `handleUpdateFolder` 의 `UPDATE` 에 조건을 붙여 바뀐 행이 0 이면 400. S4 에 "경합 흉내" 는 가짜 DB 로 만들 수 없어 L1 에 동시 요청 스모크를 더한다

### Q4. `buildTree` 묶기를 이 명세에 넣나 — **기본값: 넣는다 (3.4)**

- 깊이와 직접 관계는 없고 폴더 **수** 문제다. 그러나 순환 방어로 `buildTree` 를 어차피 다시 쓰고, 볼트 가져오기(F-2019)가 폴더 수를 늘린다. 빼면 폴더 500·문서 3,000 에서 사이드바 렌더마다 약 40ms 가 든다(끌기 중 `dragover` 로 다시 그릴 때 포함)

### Q5. 공개 폴더 목록의 하위 폴더 순서 — **기본값: 이름순 (5.3)**

- 지금은 서버가 준 순서(정렬 없음, 사실상 만든 순서)다. 트리가 깊어지면 부모 다음 자식 순서를 만들어야 하고, 그때 형제 순서를 사이드바와 같이 이름순으로 둔다
- 만든 순서로 두려면 서버가 `created_at` 을 내려줘야 한다(응답 모양 변경). 권하지 않는다

### Q6. 폴더로 이동 대화상자에서 단계를 화면 읽기 도구에 알리나 — **기본값: 알리지 않는다 (9장)**
