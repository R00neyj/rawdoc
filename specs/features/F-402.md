## 2. 범위

### 한다
- 암호 첨부 올리기 — 형식 판정 없이 평문 메타(`ext`·`w`·`h`)를 믿고, 봉투 모양만 최소로 본다(3.1)
- 받기 — 소유자에게는 `octet-stream`, 그 밖의 모든 길(초대·공개·묶음·공개 폴더)에서는 암호 첨부가 없는 것과 같게(3.2)
- 지우기 — 소유자만, 쓰는 중이면 409(3.3)
- 정리 Cron 이 금고 문서 참조를 보게(4장)

### 하지 않는다
- 첨부 바이트 **바꿔 올리기**(같은 id 에 새 봉투). 금고 키 교체는 F-400 1.3 범위 밖이고, 로그인 이관(F-408)은 로컬 첨부를 처음 올리는 것이라 필요 없다. 같은 `(owner, id)` 에 다시 올리면 지금처럼 기존 행을 돌려준다(3.1 5번)
- 평문 첨부의 형식 판정 규칙(F-209 2.2) 바꾸기
- `/v1` 암호 첨부
- 지운 첨부를 클라이언트 캐시에서 거두기(F-406)

## 3. 라우트

### 3.1 올리기 `PUT /api/attachments/:idext` — `?e2ee=1`

쿼리(계약):

| 이름 | 값 | 없으면 |
| --- | --- | --- |
| `e2ee` | `1` 만 | 평문 올리기 — **지금 경로 그대로**(나머지 쿼리는 보지 않는다) |
| `w` | 10진 정수 1 이상, 앞에 0 없음(`/^[1-9][0-9]{0,7}$/`) | `e2ee=1` 이면 400 |
| `h` | 같음 | 같음 |

판정 순서 (번호가 계약이다. 쓰기 관문 401 → 403 `account_blocked` → 429 는 이보다 앞 — F-2026)

1. `requireUser`
2. `parseIdExt` 실패 → 404 `not_found` (지금 그대로)
3. `Content-Length` 가 없거나 5,242,880 초과 → 413 `{ error: 'too_large', limit: 5242880 }` (지금 그대로 — 본문을 읽기 전)
4. 쿼리 검사. `e2ee` 가 있는데 `'1'` 이 아니면 400 `{ error: 'invalid', field: 'e2ee' }`. `e2ee=1` 이면 `w` → `h` 순서로 위 규칙이 아니면 400 `{ error: 'invalid', field: 'w' | 'h' }`, `w × h` 가 `MAX_PIXELS`(40,000,000)를 넘으면 400 `{ error: 'unsupported' }` (평문 경로에서 `sniffImage` 가 같은 이유로 `null` → `unsupported` 인 것과 같은 응답)
5. 같은 `(owner, id)` 행이 이미 있으면: 행의 `e2ee` 가 요청과 같으면 200 기존 값(지금 그대로 — 재시도 안전), **다르면 409 `{ error: 'e2ee_mismatch' }`**. 평문 요청이 금고 행을 만날 때도 409 다(지금은 200 이었지만 금고 행은 이 명세 전에는 없다)
6. 본문 읽기, 5,242,880 초과 → 413 (지금 그대로)
7. 금고만 — **봉투 모양 검사**: 길이가 `E2EE_ATTACHMENT_OVERHEAD`(69) 미만이거나 0번 바이트가 `E2EE_FORMAT_VERSION`(1)이 아니면 400 `{ error: 'invalid', field: 'body' }`. 평문만 — 지금의 `sniffImage`·`type_mismatch`
8. 계정 한도: 지금 합계(봉투 포함 `SUM(size)`) + 본문 길이 > 314,572,800 → 507 `{ error: 'quota_exceeded', used, limit }` (지금 그대로)
9. 금고만 — R2 `put(att/{owner}/{id}.{ext})`, `httpMetadata.contentType = 'application/octet-stream'` → batch `[INSERT attachments(… , e2ee = 1), dayUsageStatement(owner)]` → 201

- 1~8 은 batch 전이라 하루 카운터가 오르지 않는다. 5번 200 도 지금처럼 오르지 않는다
- 금고 행의 저장 값: `ext` = 경로의 `ext`, `mime` = `ext` 의 이미지 mime(`png`→`image/png`, `jpg`→`image/jpeg`, `gif`→`image/gif`, `webp`→`image/webp` — `imageSniff.ts` 의 표를 export 해 쓴다. 값을 다시 적지 않는다), `size` = 봉투 바이트 길이, `width`·`height` = `w`·`h`, `e2ee` = 1
- **7번이 서버가 하는 유일한 내용 검사**다. 이유: 클라이언트 버그로 **평문 이미지가 금고 표지를 달고** 올라가는 사고를 막는다(F-401 11장 Q1 이 본문 base64 검사를 둔 것과 같은 이유). 평문 이미지 네 형식의 첫 바이트는 1 이 아니다(r8). 봉투가 진짜 암호문인지는 서버가 알 수 없다 — 이것은 그물이지 증명이 아니다
- 평문 올리기의 동작·응답은 5번의 새 409 하나 말고는 바뀌지 않는다. 평문 INSERT 문장도 그대로 둔다(`e2ee` 열은 기본값 0)

응답 몸통 (계약):

```ts
// 201·200 몸통 — 지금 여섯 필드에, 금고 첨부일 때만 하나를 더한다. 평문 첨부 응답은 키까지 지금과 같다
{ id: string; ext: 'png' | 'jpg' | 'gif' | 'webp'; mime: string; size: number; width: number; height: number; e2ee?: true }
```

- `mime` 은 금고 첨부에서도 이미지 mime 이다 — 클라이언트(F-406)가 복호화한 뒤 `Blob` 형식으로 쓸 값이다. 받기 응답의 `Content-Type` 과는 다르다(3.2)

`imageSniff.ts` 에서 export 하는 이름 (계약 — F-402 테스트가 import 한다):

```ts
export const MAX_PIXELS = 40_000_000
export const IMAGE_MIME: Record<ImageExt, string> // 지금의 MIME 표 그대로, 이름만 바꿔 내보낸다
```

### 3.2 받기 `GET /api/attachments/:idext` 과 공개 셋

| 누가 · 어느 길 | 첨부가 금고(`e2ee = 1`) | 첨부가 평문 |
| --- | --- | --- |
| 소유자 · `GET /api/attachments/:idext` (`?doc=` 는 무시) | **200**, `Content-Type: application/octet-stream`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Content-Disposition: inline`, `Cache-Control: private, max-age=31536000, immutable` — `attachmentResponse` 에 mime 만 바꿔 넘긴다 | 지금 그대로(행 `mime`) |
| 초대받은 사람 · `GET /api/attachments/:idext?doc={금고 문서}` | 404 — F-401 X1·X2 로 `getDocAccess` 가 `null` | — (금고 문서 본문은 봉투라 참조가 없다) |
| 초대받은 사람 · `?doc={일반 문서}` 인데 그 본문이 금고 첨부 id 를 참조 | **404 (새로 막는다)** | 지금 그대로 |
| 로그인 없음 · `/pub/docs/:token/attachments/:idext`, `/pub/docs/:token/docs/:docId/attachments/:idext`, `/pub/folders/:token/docs/:docId/attachments/:idext` | **404 (새로 막는다)** | 지금 그대로 |
| `?doc=` 없이 남의 첨부 | 404 (지금 그대로) | 404 |

- **새로 막는 방법**: 남·공개 받기 넷(`handleGetAttachment` 의 `?doc=` 갈래, `handlePublicGetAttachment`·`handlePublicGetDocSetAttachment`·`handlePublicGetFolderAttachment`)이 후보 첨부를 고르는 `SELECT * FROM attachments WHERE id = ? AND ext = ?` 끝에 `AND e2ee = 0` 을 붙인다. 앞부분 글자가 그대로라 `startsWith` 로 가르는 가짜 D1 이 깨지지 않는다
- **왜 새로 막나 — F-400 3.5 와 F-401 X26 이 놓친 길**: 두 명세는 "금고 문서는 링크·초대가 없으므로 코드 변경 없이 404" 라고 봤다. 그런데 **일반 문서 본문이 금고 첨부를 참조**할 수 있다 — 사용자가 열린 금고 문서의 `![](attachments/{id}.png)` 줄을 복사해 공유 중인 일반 문서에 붙여 넣으면 된다. 그러면 지금 코드는 그 일반 문서의 공개 링크·초대로 봉투 바이트를 **행의 `mime`(`image/png`)으로** 내보낸다. 평문은 새지 않지만 결정 6(금고는 공유·공개에서 빠진다)을 어기고, 봉투 크기·존재가 로그인 없이 드러난다
- 그 일반 문서의 소유자 자신은 소유자 길로 봉투를 받는다(평문 이미지가 아니므로 편집기에서 깨진 이미지로 보인다). 클라이언트가 이것을 어떻게 보일지는 F-406 이 정한다(11장 갱신 대상)
- 받기는 `GET` 이라 쓰기 관문 밖이다. 하루 카운터와 무관하다

### 3.3 지우기 `DELETE /api/attachments/:idext` — 신규

| 응답 | 언제 |
| --- | --- |
| 401 `unauthenticated` · 403 `account_blocked` · 429 `rate_limited` | 쓰기 관문(F-2026), 핸들러 전 |
| 403 `forbidden_origin` | `Origin` 검사(`worker/index.ts` 의 `/api/` 비-GET 공통), 관문 전 |
| 404 `{ error: 'not_found' }` | `idext` 모양이 틀림 / 내 `(owner, id)` 행이 없음(남의 첨부 포함) / 행의 `ext` 가 경로와 다름 |
| 409 `{ error: 'in_use' }` | 아래 "쓰는 중" |
| 204 (몸통 없음) | R2 `delete` → batch `[DELETE FROM attachments WHERE owner_id = ? AND id = ?, dayUsageStatement(owner)]` |
| 500 `internal` | R2 `delete` 가 던짐 — D1 행은 남는다. 다시 부르면 된다 |

판정 순서: 관문 → `requireUser` → `idext` → 내 행 → 쓰는 중 → R2 → D1 batch

- 평문·금고 첨부 모두 같은 규칙이다 — 옮기기(F-400 4.3 ⑤)는 평문 첨부를, 빼기는 금고 첨부를 지운다
- 404·409 는 batch 전이라 하루 카운터가 오르지 않는다. 204 는 +1
- **R2 가 먼저, D1 이 나중**인 이유: `attachmentGc.ts` 와 같은 순서다. R2 가 실패하면 행이 남아 다시 부를 수 있다. D1 이 실패하면 행이 없는 객체를 가리키게 되는데, 받기는 `BUCKET.get` 이 `null` 이라 404 이고, 다시 부르면 R2 `delete`(없는 키도 성공)와 D1 삭제가 다시 돈다
- 다시 부르기(이미 지움)는 404 다 — 소유자 행이 없는 것과 남의 첨부를 서버가 가르지 않는다. F-407 은 404 를 "지울 것 없음" 으로 읽는다(10장 Q5)
- 모든 D1 쓰기는 `batch` — F-2025 A13 의 `.run()` 정적 검사 결과가 늘지 않는다

**"쓰는 중" 판정 (계약 — 참이면 409)**. 지울 첨부 id 가 아래 어느 하나에 들어 있으면 쓰는 중이다

1. **일반 문서 본문**(`e2ee_key IS NULL`) 가운데 소유자가 ① 나 이거나 ② **나에게 편집 초대(`grants.role = 'edit'`, 문서·폴더 어느 것이든)를 준 사람**인 문서의 `extractAttachmentRefs(content)` (10장 Q1)
2. **내 금고 문서**(`owner_id = 나 AND e2ee_key IS NOT NULL`)의 `attachment_refs` 배열

- 1번의 판정 기준은 정리 Cron(F-219)과 같은 `extractAttachmentRefs` 다. SQL 로 먼저 좁히는 것은 권한다 — `instr(content, 'attachments/{id}.') > 0` 인 행만 `content` 를 받아 `extractAttachmentRefs` 로 확인. 좁히기 없이 본문을 다 받아 오면 1MB 문서 수천 개를 Worker 로 옮기게 된다. 문장 모양은 구현 재량(r2 가 잰 문장은 스크래치 `d1m/w.js` 의 `plainMissGrant`)
- 2번은 `json_each(docs.attachment_refs)` 로 문장 안에서 찾는다(F-401 r7 이 된다고 확인, r3 에서 행 수를 쟀다)
- 1번 ② 를 넣는 이유: 남의 일반 문서에 편집자로 넣은 이미지는 **첨부 소유자 = 편집자(나)** 다(`access.ts` `isDocAttachmentOwner`, F-219 2.1 "공유 편집자가 올린 첨부"). 같은 마크다운을 내 문서에도 두었다가 그 문서를 금고로 옮기면(F-407 ⑤) 내 문서만 보는 판정은 409 를 내지 않고, **남의 문서 이미지가 되살릴 길 없이 사라진다**(R2 는 백업이 없다 — F-400 m11). 초대가 편집에서 보기로 내려간 뒤에는 그 이미지가 남에게 보이지 않으므로(`isDocAttachmentOwner` 가 `edit` 만 참) 편집 초대만 본다. 초대를 준 사람의 문서 **전체**를 훑는 것은 초대 범위보다 넓다 — 넓게 잡아 409 가 더 나오는 쪽이 안전하다
- **읽기 비용**(r2·r3): 한 번에 약 (내 문서 수 + 편집 초대를 준 사람들의 문서 수) + 내 금고 첨부 참조 수. 초대가 없는 사용자는 내 문서 수만큼. 쓰는 곳은 옮기기·빼기(F-407)뿐이다. 예: 문서 2,000개인 사용자가 이미지 200장이 든 폴더를 옮기면 약 40~60만 행 — D1 하루 읽기 500만 행(F-2024 3.1)의 약 10%. **누가 일부러 올리기·지우기를 되풀이하면** 하루 쓰기 5,000 안에서 2,500쌍 × 문서 10,000 = 2,500만 행까지 갈 수 있다. F-2024 3.1 이 "쓰기마다 그 사람 문서 수만큼 읽기" 를 같은 이유로 버렸다는 것을 알고 받아들인다 — 이 라우트는 늘 쓰는 저장 경로가 아니고, 남용은 F-2028(계정 막기)로 다룬다. 10장 Q1 의 다른 안이 이 비용을 줄인다
- **받아들이는 틈**: 판정과 삭제 사이에 다른 탭이 같은 id 를 참조하는 저장을 하면 참조가 남은 채 지워진다. 정리 Cron 에는 24시간 유예가 있지만 이 라우트에는 없다. 옮기기 중 다른 탭이 같은 이미지를 새로 붙여 넣는 경우만 해당해 받아들인다

## 4. 정리 Cron — `worker/attachmentGc.ts`

참조 집합 = **(A) 일반 문서 본문 참조 ∪ (B) 금고 문서 `attachment_refs`**. 소유자별로 나누지 않는다(F-219 2.1 그대로). 유예 24시간·한 번 최대 500개·R2 먼저 지우기·실패는 로그만 — 전부 그대로

(A) 일반 문서 본문 — 문장 (계약, 앞부분은 가짜 D1 이 본다):

```sql
SELECT id, content FROM docs WHERE e2ee_key IS NULL AND id > ? ORDER BY id LIMIT ?
```

- 첫 쪽은 `id > ''`, 다음 쪽은 앞 쪽 마지막 `id`. 한 쪽 200행(`PAGE_SIZE` 그대로), 200 미만이면 끝
- `e2ee_key IS NULL` 을 넣는 이유: 금고 문서 본문은 봉투 base64 라 `extractAttachmentRefs` 가 늘 빈 집합이다(base64 글자에 `.` 이 없어 `attachments/{16진}.` 이 나올 수 없다). 빼지 않으면 금고 문서마다 최대 1MB 를 헛되이 옮긴다
- **`OFFSET` 을 키 기준 쪽 나누기로 바꾼다**(10장 Q2). 지금 방식은 쪽마다 앞을 다시 세어 문서 N 개에 약 N²/400행을 읽는다(r4 — N=10,000 이면 하루 약 255,000행). 키 기준은 N 행(r5). 같은 함수를 고치는 김에 바꾼다 — 결과(참조 집합)는 같다

(B) 금고 문서 참조 — 문장 (계약):

```sql
SELECT id, owner_id, attachment_refs FROM docs WHERE e2ee_key IS NOT NULL AND id > ? ORDER BY id LIMIT ?
```

- 쪽 나누기는 (A) 와 같다. 한 번 도는 데 문서 수 N 행(r5)
- 행마다 `attachment_refs` 를 `JSON.parse` 해 배열 안의 16진 16자 문자열만 참조 집합에 넣는다
- **풀지 못하는 행**(JSON 이 아님, 배열이 아님, `NULL`)이 있으면 그 행의 `owner_id` 를 "보호 소유자" 로 적고, **이번 실행에서 그 소유자의 첨부는 하나도 지우지 않는다.** `console.error('e2ee_refs_unreadable', 문서 id)` 한 줄. 서버는 F-401 검사를 거친 배열만 쓰므로 일어나지 않아야 하지만, 일어나면 그 사람의 금고 이미지가 하루 뒤 전부 지워진다 — 지우지 않는 쪽으로 넘어진다
- 한 문장 `json_each` (r6, 6,900행으로 가장 싸다)를 쓰지 않는 이유: JSON 하나가 깨지면 문장 전체가 던져 **모든 사람**의 정리가 멈춘다. 행마다 풀면 깨진 사람만 멈춘다

지울 대상 = `created_at < now − 24시간` 이고 id 가 참조 집합에 없고 **소유자가 보호 소유자가 아닌** 행 (최대 500개). 평문·금고 첨부를 가르지 않는다

- 금고 첨부의 삭제 판정 기준은 `attachment_refs`(결정 7)이지만, 금고 첨부 id 가 일반 문서 본문에 붙여 넣어져 있으면(3.2 "새로 막는 방법" 의 경우) (A) 로도 남는다. 남기는 쪽이라 문제없다
- **받아들이는 틈 (지금과 같다)**: 금고 첨부를 올린 뒤 그 참조를 담은 문서 저장이 24시간 넘게 서버에 닿지 않으면(탭을 닫고 하루 넘게 다시 열지 않음) 첨부가 지워진다. 일반 문서에도 지금 있는 틈이다(F-219). 금고 문서는 서버 보내기 간격이 10초(F-400 3.4)라 탭이 열려 있는 한 닿는다

## 10. 열린 질문 — 전부 닫힘 (2026-09-25 main, 모두 추천안)

### Q1. `DELETE` "쓰는 중" 판정에 편집 초대를 준 사람의 문서까지 넣을까 — **기본값: 넣는다 (3.3 1번 ②)**

| 안 | 좋은 점 | 드는 것 |
| --- | --- | --- |
| **내 문서 + 나에게 편집 초대를 준 사람의 문서 (기본)** | 남의 공유 문서에 편집자로 넣은 이미지가 옮기기(F-407)로 사라지지 않는다 — R2 는 되살릴 길이 없다 | 읽기 행이 초대를 준 사람들의 문서 수만큼 는다(r2: 2,301 → 5,304) |
| 내 문서만 (F-400 3.5 글자 그대로) | 읽기 행이 내 문서 수만큼. SQL 이 단순하다 | 위 경우 남의 문서 이미지가 지워진다. 일어나려면 "남의 문서에 이미지를 넣은 편집자가 같은 이미지 줄을 자기 문서에 복사한 뒤 그 문서를 금고로 옮김" 이 모두 맞아야 해 드물다 |

- 다른 안을 고르면: 3.3 1번 ② 와 X5 가 빠지고, X5 첫 경우가 204 로 바뀐다. F-400 3.5 는 고칠 것이 없다
- 셋째 안(기록만): `DELETE` 가 바로 지우지 않고 행을 "지금 정리 대상" 으로 표시해 다음 Cron 이 전체 참조로 판정. 요청마다 읽기가 0 이지만 평문이 최대 하루 남고 F-400 3.5 의 "204 로 지운다" 가 바뀐다 — 권하지 않는다

### Q2. 정리 Cron 의 일반 문서 읽기를 `OFFSET` 에서 키 기준으로 바꿀까 — **기본값: 바꾼다 (4장)**

- 이유: 같은 함수에 새 문장을 더하면서 가짜 D1 을 어차피 고쳐야 하고, 읽기가 N²/400 → N 으로 준다(r4·r5). 문서 10,000개면 하루 약 255,000행 → 10,000행
- 다른 안: (A) 는 `OFFSET` 그대로 두고 `WHERE e2ee_key IS NULL` 만 더한다. 그러면 `attachmentGc.test.ts` 가짜의 바인딩 읽기(`[limit, offset]`)는 그대로고 F2 가 빠진다. (B) 는 어느 쪽이든 키 기준이다(`OFFSET` 이면 쪽마다 전체를 훑는다 — r5)

### Q3. 금고 올리기에서 봉투 첫 바이트를 볼까 — **기본값: 본다, 1 이어야 한다 (3.1 7번)**

- 이유: 평문 이미지를 금고 표지로 올리는 클라이언트 버그를 서버가 거른다(r8). 비용은 한 바이트
- 드는 것: 첨부 봉투 판이 2 가 되면 서버도 고쳐야 한다(F-401 은 감싼 키 길이를 4~128 로 열어 둔 것과 반대 선택). 판 올림은 금고 키 교체와 함께 F-400 1.3 범위 밖이라 받아들인다
- 다른 안: 길이 ≥ 69 만 본다. U6 셋째가 201 로 바뀐다. 또 다른 안 — "`sniffImage` 가 이미지로 알아보면 거절" 은 판과 무관하지만 F-400 3.5 "`sniffImage` 를 건너뛴다" 와 글자가 어긋나 고르지 않았다

### Q4. 일반 문서 본문이 참조하는 금고 첨부를 남·공개에게 내줄까 — **기본값: 내주지 않는다 (3.2, `AND e2ee = 0`)**

- F-400 3.5 셋째 문단·F-401 X26 은 "코드 변경 없이 404" 로 보았으나 3.2 의 복사·붙여넣기 경우를 놓쳤다. 이 명세가 고친다(11장 갱신 대상)
- 다른 안: 지금 그대로 둔다. 봉투가 이미지 mime 으로 공개 링크에 나간다(평문은 아니다). R3~R6 의 첫 칸이 200 으로 바뀐다

### Q5. 이미 지운 첨부의 `DELETE` 를 204 로 할까 — **기본값: 404 (3.3)**

- 이유: 소유자 행이 없으면 "이미 지움" 과 "남의 것" 을 서버가 가르지 않는다. 204 를 주면 남의 첨부 id 를 넣은 요청에도 성공처럼 답하게 된다. F-407 은 404 를 "지울 것 없음" 으로 읽으면 된다
- 다른 안: 행이 없으면 204(F-401 `DELETE /api/e2ee/keys` 처럼). X2 첫 칸이 204 로 바뀌고, F-407 의 분기 하나가 준다

10. `json_each` 한 문장 대신 행마다 풀기 — 4장
