## 2. 결론 넷 (프롬프트가 결론을 요구한 것)

### 2.1 편집기와 "단일 `Y.Text` 원본" 불변식

- **금고 문서는 원격 링크를 붙이지 않는다.** 서버 문서라도 경로 판정이 `e2ee` 로 끝나면(6.3) 소켓을 열지 않고(`useLiveDoc` 에 문서 id 를 주지 않는다), 편집기에 `live` 를 주지 않는다. 편집기는 `createYBinding(text)` 로 만든 **자기 `Y.Doc` 의 `Y.Text` 하나**를 원본으로 쓴다(c1)
- 불변식의 두 번째 경우 "링크가 없으면 편집기 `Y.Doc` 이 원본" 에 그대로 들어맞는다. 봉투(D1 `docs.content`·`md-remote` 캐시·`md-docs` 행)는 그 `Y.Text` → `getText(lineEnding)` → 암호화로 만든 **한 방향 값**이다. 봉투를 복호화해 여는 `Y.Doc` 에 다시 밀어 넣는 일은 **문서를 새로 열 때(편집기를 새로 만들 때)뿐**이다 — 열린 편집기에 저장소 값을 되쓰지 않는다. 지금 `local`·`pending` 경로가 `store.get` 한 번으로 편집기를 여는 것과 같다
- 원격 업데이트가 없으므로 IME 게이트가 보류할 것이 없다. 서버의 `/ws/doc/:id` 도 금고 문서에 `4403` 으로 닫는다(F-401 6장) — 클라이언트가 실수로 열어도 평문은 흐르지 않는다
- `md-yjs` 에 금고 문서 기록을 쓰지 않는다 — 경로가 `realtime` 이 아니면 `useLiveDoc` 이 영속을 열지 않는다(App `docSession.persist` 는 `realtime` 판정 때만 채워진다)

### 2.2 저장 경로와 잠길 때 멈추는 순서

```
편집기 Y.Text ─(입력 700ms 멈춤, useDocSaver)─► withE2ee.update(평문)
   └─ 크기 판정(749,971 B) → 문서 키로 봉투 → 아래 저장소 update(봉투, attachmentRefs)
        ├─ idb   : md-docs 행에 봉투 (로컬 금고, 끝)
        └─ server: md-remote 캐시에 봉투 → outbox updateDoc{e2ee:true} (즉시 resolve)
                     └─ 보내기: 그 문서의 직전 응답 뒤 10,000ms 가 지나야 PUT {…, e2ee:true}
                          ├─ 200 → 캐시 version 갱신
                          └─ 409 → 금고 충돌 사본(새 id·새 문서 키로 다시 암호화). MK 없으면 항목을 두고 그 문서만 멈춤
```

- 기기 캐시는 지금처럼 700ms(`SAVE_DEBOUNCE_MS`)에 쓴다. 서버 간격 10초는 **outbox 보내기에서만** 건다(5.2) — 봉투를 캐시에 늦게 쓰면 탭이 닫힐 때 편집이 사라진다
- **잠길 때**(F-404 4.1 틀에 이 명세가 두 단계를 끼운다):

| 단계 | 이 명세가 등록하는 일 | 실패하면 |
| --- | --- | --- |
| `flush` | 지금 문서가 금고 문서이고 열려 있으면 `docSaver.flush()` 와 진행 중인 제목 저장을 기다린다. 둘 중 하나라도 실패(`false`·거부)면 **던진다** → 키링이 `'aborted'`, 알림 E14(F-404) | 잠그지 않는다 |
| `unmount` | 지금 문서가 금고 문서면 편집기를 내리고(`openDoc` 을 비움) 보기 모드 HTML 을 비운다. 목록 상태 `docs` 의 금고 문서를 `lockDocMetas` 로 잠긴 모양(제목 빈 글자·`e2ee: 'locked'`)으로 바꾼다. P1 이 그 자리에 뜬다 | 기록만 |
| `indexes` | (F-404 가 이미 검색·지도 캐시 비우기를 등록했다) 여기에 `e2eeStore.clearPlainCache()` 하나를 더한다 — 복호화 기억(4.4)과 문서 키 기억을 버린다 | 기록만 |
| `blobs` | 이 명세는 없다 — F-406 | — |

- `flush` 단계가 저장하는 봉투는 **캐시까지**다. 서버로 가는 PUT 은 10초 간격에 묶여 잠근 뒤에 나갈 수 있다 — 봉투만 보내므로 키가 필요 없다
- 잠긴 동안에도 outbox 는 멈추지 않는다. 멈추는 것은 **409 충돌을 받은 금고 문서 하나**뿐이다(5.3) — 사본을 만들려면 제목에 꼬리를 붙이고 새 id 로 다시 암호화해야 하는데 MK 가 없다(F-400 3.4)
- 조합 중 잠그기는 F-404 가 미룬다. `compositionend` 한 틱 뒤 잠그기가 다시 돌 때 `flush` 가 조합한 글자를 저장한다(F-404 4.2) — 이 명세가 따로 할 일은 없다
- `flush` 실패가 계속되는 경우(예: 편집기 내용이 750KB 를 넘어 E7 로 저장이 안 됨) 자동 잠금도 계속 `'aborted'` 다. F-404 11장 Q5(저장 못 한 편집을 잃지 않는 쪽) 의 결과로 받아들인다 — E14 는 한 번 열린 동안 한 번만 뜬다(F-404 4.1)

### 2.3 로컬(로그인 없음) 금고 문서의 저장 위치와 모양

- 저장소 `md-docs`(v5 그대로) 의 **기존 `docs` 스토어**, 같은 키(`id`)다. 새 스토어를 만들지 않는다
- 행 모양 (일반 문서 행에 필드 둘):

```ts
// md-docs docs 스토어의 금고 문서 행 — 일반 문서 행은 지금과 키까지 같다
{
  id: string
  title: string            // 제목 봉투 base64 (AAD "{id}:title")
  content: string          // 본문 봉투 base64 (AAD "{id}:content") — 평문은 fromEditorText 로 lineEnding 을 이은 저장 문자열
  lineEnding: 'crlf' | 'lf'
  createdAt: number; updatedAt: number
  folderId: string | null
  pinnedAt: number | null
  e2eeKey: string          // 감싼 문서 키 base64 56자 (MK = 로컬 금고 키, 묶음 행 id 'local')
  attachmentRefs: string[] // 본문이 쓰는 첨부 id(16진 16자), 정렬·중복 없음 (4.3)
}
// md-docs folders 스토어의 금고 폴더 행 — 일반 폴더 행에 e2ee: true 만 더한다
{ id, name, parentId, createdAt, updatedAt, e2ee: true }
```

- 로컬 금고 키 묶음은 F-404 가 만든 `md-docs` `e2ee` 스토어 행 `local` 이다. 로컬 금고 문서의 MK 는 그 묶음으로 푼 것이다
- 서버 캐시(`md-remote` `docs`)의 금고 문서 행도 같은 모양에 `userId`·`version` 이 붙는다 — 서버 응답을 그대로 넣기 때문이다(c3)

### 2.4 사이드바 잠긴 표시와 잠긴 폴더에 새 문서

- **잠긴 금고 문서**: 제목 자리에 `잠긴 문서`, 행에 자물쇠 아이콘(접근 이름 `금고`). **열린 금고 문서**: 복호화한 제목 + 같은 아이콘. **금고 폴더**: 이름(평문) + 같은 아이콘. 자세한 규칙 6.1
- **잠긴 금고 폴더에 `새 문서`**(폴더 `⋯` 메뉴, 사이드바 위 `새 문서` 가 지금 문서의 폴더를 고를 때, 없는 위키링크로 새 문서, 파일 가져오기):
  1. 대상 폴더가 금고 폴더인지 본다(`folders` 의 `e2ee`)
  2. 금고가 열려 있지 않으면 `requestOpen()`(F-404 6장) — `locked` 면 D-11 금고 열기, `none` 이면 D-8 금고 만들기
  3. 사용자가 닫으면(`false`) **아무것도 만들지 않고 알림도 없다**. 금고 정보를 못 읽으면(`requestOpen` 이 대화상자 없이 `false` — 상태 `unavailable`) 알림 E25
  4. 열리면 지금처럼 `store.create` — `withE2ee` 가 폴더를 보고 금고 문서로 만든다(4.2). 만든 문서가 열리고 제목 입력에 초점(지금과 같다)
- 문구 초안은 8장

| --- | --- | --- | --- | --- |

### 3.3 저장소 행·outbox

- `idbStore`: `create` 가 받은 `e2eeKey`·`attachmentRefs` 를 행에 싣는다(있을 때만). `applyPatch` 는 `attachmentRefs` 도 바꾼다(있을 때만). `createFolder` 는 `e2ee: true` 를 싣는다(있을 때만). `moveDoc`·`setPinned`·`removeFolder(move-up)` 은 지금처럼 행을 펼쳐 쓰므로 필드가 남는다
- `remoteCache.ts` `OutboxItem`:

```ts
| { type: 'createDoc'; /* 지금 필드 */ e2eeKey?: string; attachmentRefs?: string[] }
| { type: 'updateDoc'; docId: string; patch: { title?: string; content?: string; attachmentRefs?: string[] }; e2ee?: true }
| { type: 'createFolder'; /* 지금 필드 */ e2ee?: true }
```

- `updateDoc.e2ee` 는 **넣을 때** 정한다 — `serverStore.update` 가 캐시 행에 `e2eeKey` 가 있으면 `true`. 합치기(`enqueueUpdateDoc`)는 표지를 유지한다. 표지 없는 옛 항목은 일반 문서로 보낸다
- `DB_VERSION` 둘 다 그대로(c2). 이 명세 이전에 쌓인 outbox 항목은 새 필드가 없어 일반 항목으로 읽힌다 — 이 명세 이전에는 금고 문서가 없었으므로 맞다

### 4.1 읽기 — `list`·`get`·`refreshDocFromServer`·그 밖에 `Doc` 을 돌려주는 모든 메서드

- 아래 저장소의 문서에 `e2eeKey` 가 없으면 **그대로** 돌려준다(일반 문서, 필드 추가 없음)
- 있으면: MK 가 있으면 문서 키를 풀고 제목·본문을 복호화해 `e2ee: 'open'`, 없으면 `title: ''`·`content: ''`·`e2ee: 'locked'`. 두 경우 모두 `e2eeKey` 를 빼고 `attachmentRefs` 는 둔다(없으면 `[]`)
- **복호화 실패**(`decrypt-failed`·`bad-envelope`·`unsupported-version`, 서버가 봉투를 바꿔치기했거나 다른 금고 키로 만든 문서) — 그 문서만 `e2ee: 'locked'` 모양으로 돌려주고 `console.error('e2ee_decrypt_failed', id)` 를 문서마다 페이지 수명에 한 번 남긴다. 목록 전체를 실패시키지 않는다. 화면은 6.2 의 "손상" 문구로 구분한다
- 문서를 돌려주는 메서드 전부가 이 변환을 거친다 — `list`·`get`·`create`·`update`·`moveDoc`·`setPinned`, 서버 저장소의 `refreshDocFromServer`. 순서 규칙(정렬)은 아래 저장소 그대로

### 4.2 쓰기 — `create`·`update`

- **`create` 가 금고 문서가 되는 조건**: 입력 `e2ee === true`, 또는 `folderId` 가 금고 폴더(아래 저장소 `listFolders()` 의 `e2ee`). 조건이 맞는데 MK 가 없으면 `E2eeStoreError('locked')` 를 던지고 아무것도 쓰지 않는다
  - 순서: 평문 본문 크기 판정(`isPlainContentTooLarge` → `'too-large'`) → 첨부 id 목록(`attachmentRefsOf`, 1,000개 넘으면 `'too-many-refs'`) → 새 문서 id 를 **여기서** 정한다(입력 `id` 가 있으면 그것, 없으면 `crypto.randomUUID()`) — AAD 에 id 가 들어가므로 아래 저장소가 id 를 정하게 두면 안 된다 → `createDocKey(MK)` → 제목·본문 봉투 → 아래 `create({ …, id, title: 봉투, content: 봉투, e2eeKey, attachmentRefs })`
  - 반환: 평문으로 된 앱 층 `Doc`(`e2ee: 'open'`)
- **`update`**: 아래 저장소에서 행을 읽어(`get`) `e2eeKey` 가 없으면 그대로 넘긴다. 있으면 MK 가 없을 때 `'locked'`. `content` 가 있으면 크기·첨부 id 판정 뒤 그 문서의 **기존 문서 키**로 봉투(문서 키를 새로 만들지 않는다 — `e2eeKey` 가 바뀌지 않는다), `attachmentRefs` 를 함께 보낸다. `title` 이 있으면 제목 봉투. 앱이 준 `attachmentRefs` 는 버리고 본문에서 다시 만든다
- 크기 판정은 **암호화 전 평문**으로 한다(F-400 3.3). 경계: UTF-8 749,971 B 는 통과, 749,972 B 는 `'too-large'`. 판정에 걸리면 아래 저장소에 아무것도 쓰지 않는다 — 편집기 안의 내용은 그대로다
- 금고 문서의 평문 제목 상한은 일반 문서와 같은 500자(`E2EE_MAX_PLAIN_TITLE_CHARS`) — 이 한 겹이 따로 검사하지 않는다(제목 입력칸이 지금처럼 막는다). 서버의 2,040자 검사는 이 상한에서 나온 값이다(F-400 3.3)

### 4.3 첨부 id 목록 — 이 명세가 채운다

- 금고 문서를 쓸 때마다 `attachmentRefs = attachmentRefsOf(평문 본문)` 을 함께 보낸다. **F-400 6장은 이 일을 F-406 에 두었지만 F-405 로 당긴다** — 이 명세만으로도 금고 문서 본문이 평문 첨부(`attachments/{id}.png`)를 참조할 수 있고, `attachment_refs` 가 비어 있으면 F-402 정리 Cron 이 그 첨부를 지운다(`collectReferencedIds` = 일반 문서 본문 ∪ 금고 `attachment_refs`). F-406 은 첨부를 **암호화하는 일**만 남는다(11장)
- 정렬·중복 없음. 빈 본문이면 `[]`

### 4.4 기억(메모) — 같은 봉투를 다시 풀지 않는다

- 문서마다 마지막으로 푼 `{ e2eeKey, 제목 봉투, 본문 봉투 } → { 제목, 본문 }` 한 벌, 문서 키는 `e2eeKey` 마다 하나를 메모리에 둔다. 봉투가 글자까지 같을 때만 쓴다
- 이유: `list()` 는 탭 신호·저장·잠금 해제마다 불리고(App `resyncFromStore`), 검색·지도도 `store.list()` 의 본문을 쓴다. Node 에서 1,000개×5KB 가 148ms(c6) — 매번 다시 풀 값이 아니다
- `clearPlainCache()` 가 둘 다 비운다. 또 `getMasterKey()` 가 전에 쓴 MK 와 다른 객체(또는 `null`)를 돌려주면 읽기 전에 비운다 — 잠근 뒤 새 MK 로 다시 연 경우(복구로 새 암호를 정해도 MK 는 같은 값이지만 객체가 다르다) 옛 문서 키를 쓰지 않게
- 평문 기억은 **메모리에만** 둔다. IndexedDB·localStorage·`sessionStorage` 에 넣지 않는다(A6)

### 4.5 폴더·옮기기 규칙 (서버 규칙 F-401 5.2 를 기기에서 먼저 지킨다)

| 메서드 | 조건 | 결과 |
| --- | --- | --- |
| `createFolder` | 부모가 금고 폴더 | 아래에 `e2ee: true` 로 만든다 (키 필요 없음) |
| `moveDoc` | 일반 문서를 금고 폴더로 | `E2eeStoreError('e2ee-folder')`, 아무것도 안 바뀜 |
| `moveDoc` | 금고 문서를 어디로든 | 그대로 넘긴다 |
| `moveFolder` | 일반 폴더를 금고 폴더 아래로 | `'e2ee-folder'` |
| `moveFolder` | 금고 폴더를 어디로든 | 그대로 |
| `removeFolder(move-up)` | 부모가 금고 폴더인데 이 폴더 바로 아래에 일반 문서·폴더가 있음 | `'e2ee-folder'` (서버 409 와 같은 조건. "금고 아래는 늘 금고" 가 지켜지면 일어나지 않는다) |
| `renameFolder`·`remove`·`setPinned`·`removeFolder(delete-all)` | — | 그대로 (키 필요 없음) |

- 폴더를 금고로 켜고 끄는 일(`PUT /api/folders/:id` `e2ee`)은 F-407 이다. 이 명세는 이미 금고인 폴더를 다룬다

### 4.6 순수 도우미

- `lockDocMetas`: `e2ee === 'open'` 인 항목을 `{ …, title: '', e2ee: 'locked' }` 로, 나머지는 같은 객체 그대로. 잠그기 `unmount` 단계가 쓴다 — 그 단계에서는 MK 가 아직 있어 `list()` 를 다시 불러도 평문이 나온다(c7)
- `planE2eeReset`: 금고 폴더 중 **부모가 금고 폴더가 아닌 것**(맨 바깥)을 `folderIds` 로, 금고 문서 중 그 폴더들의 자손 폴더에 들지 않는 것을 `docIds` 로. 금고 초기화 단계(7.9)가 `folderIds` 를 `removeFolder(id, 'delete-all')`, `docIds` 를 `remove(id)` 로 지운다
- `makeE2eeConflictCopy`: 5.4

### 5.2 금고 문서 보내기 간격 — 10초

```ts
// serverStore.ts
export const E2EE_SERVER_SAVE_INTERVAL_MS = 10_000
```

- 규칙: **금고 문서 하나에 대한 `createDoc`·`updateDoc` 의 응답(성공이든 409 든)을 받은 뒤 `E2EE_SERVER_SAVE_INTERVAL_MS` 가 지나기 전에는 그 문서의 `updateDoc{e2ee}` 를 보내지 않는다.** 금고 문서의 첫 `updateDoc` (이 페이지에서 그 문서의 응답을 아직 받지 않음)은 곧바로 나간다
- 판정은 `findSendable` 에 더한다 — 지금의 413 붙잡기와 같은 모양: 붙잡힌 항목과 **같은 문서의 뒤 항목**을 건너뛰고(순서 보존), 다른 문서 항목은 보낸다. 시각은 `handlers.now`(테스트 주입)를 쓴다
- 붙잡힌 금고 항목이 있으면, 가장 이른 풀림 시각에 보내기를 한 번 다시 시작하는 타이머 하나를 둔다(브라우저에서만 — 429 재개와 같은 방식). 타이머가 없어도 30초 재시도(`RETRY_INTERVAL_MS`)가 이어받는다
- 붙잡힌 동안 들어온 편집은 `enqueueUpdateDoc` 이 **한 항목으로 합친다**(지금 그대로) — 그래서 10초마다 최대 한 번 보낸다
- 마지막 응답 시각은 페이지 메모리에만 둔다. 새로고침 뒤 첫 보내기는 곧바로 나간다
- 근거: F-400 3.4·10장 Q6. 분당 120·하루 5,000(F-2024)에 문서 하나가 시간당 최대 360번

### 5.3 금고 충돌 사본과 잠긴 동안 멈춤

`sendOne` 오류 갈래에 더한다(표의 위에서 아래 — 지금 갈래보다 앞):

| 항목 | 받은 오류 | 처리 | 알림 |
| --- | --- | --- | --- |
| `updateDoc` (`e2ee`) | `conflict` | 금고 충돌 사본(아래). 사본을 만들었으면 지금처럼 원본 캐시를 409 몸통의 `doc` 으로 바꾸고 항목을 뺀다 | 지금 문구(App `handleServerConflict`) |
| `updateDoc` (`e2ee`) | `not_e2ee` | 다른 곳에서 금고에서 뺀 문서다. `api.getDoc` 으로 서버 값을 받아 **`conflict` 와 같이** 금고 충돌 사본을 만든다(423 갈래가 서버 값을 따로 받는 것과 같다). 편집은 암호문으로 남는다 | 지금 문구 |
| `updateDoc` (일반) | `e2ee_doc` | 다른 곳에서 금고로 옮긴 문서에 옛 평문 편집이 남았다. **평문 사본을 만들지 않는다** — 이 항목과 그 문서의 나머지 outbox 항목을 지우고, `api.getDoc` 으로 서버 값(봉투)을 캐시에 넣는다 | E22 |
| `createDoc` | `e2ee_folder` | 다른 곳에서 금고로 바뀐 폴더에 만든 일반 문서다. 캐시 행과 항목의 `folderId` 를 `null` 로 바꿔 **다시 보낸다**(`true`) | E23 (한 보내기 회차에 한 번) |
| `createDoc` | `no_vault` | 금고가 다른 곳에서 초기화됐다. 캐시 행과 그 문서의 outbox 항목을 지운다 — 새 금고로는 풀 수 없는 문서다 | E24 |
| `createFolder` | `e2ee_folder` | `parentId` 를 `null` 로 바꿔 다시 보낸다 | E23 |
| `moveDoc` | `e2ee_folder` | 항목을 빼고 `api.getDoc` 으로 서버 값을 캐시에 넣는다(폴더가 되돌아간다) | E19 |
| `moveFolder`·`renameFolder` | `e2ee_folder` | 항목을 뺀다. 다음 `listFolders()` 가 캐시를 서버 값으로 맞춘다 | E19 |

**금고 충돌 사본** (F-400 3.4):

1. 사본 id 를 새로 만든다(`crypto.randomUUID()`)
2. 주입된 사본 함수(5.4)에 내 캐시 행(봉투)과 사본 id 를 준다. 함수는 MK 가 없으면 `null`
3. `null` 이면: **항목을 outbox 에 그대로 두고**, 그 문서 id 를 "금고 충돌 대기" 집합에 넣는다. `findSendable` 은 그 문서의 항목을 모두 건너뛴다(다른 문서는 계속 나간다). 알림 E21 을 문서마다 페이지 수명에 한 번. 원본 캐시는 바꾸지 않는다(다시 보냈을 때 같은 409 를 받아야 한다)
4. 값을 받으면: 지금 `handleConflict` 와 같은 순서 — 사본 캐시 행(`title`·`content` = 받은 봉투, `e2eeKey`·`attachmentRefs` = 받은 값, `version: 0`, 그 밖은 원본 캐시 행의 `lineEnding`·`folderId`)을 넣고, outbox 에 `createDoc`(같은 필드)을 넣고, 서버 값이 있으면 원본 캐시를 바꾸고, `handlers.onConflict({ docId, copyId })`
- **풀림**: `resumeE2eeConflicts()` 가 대기 집합을 비우고 보내기를 시작한다. 다시 보낸 항목은 409 를 다시 받고(버전이 그대로다) 이번에는 사본 함수가 값을 준다. `withE2ee.resumeAfterUnlock()` 이 이것을 부른다
- 사본의 폴더: 원본과 같은 폴더. 원본이 금고 폴더 안이면 사본도 금고 문서라 서버 규칙에 맞는다
- 일반 문서의 `conflict`·`locked`(423) 처리는 **바꾸지 않는다**

```ts

export type E2eeCopyResult = { title: string; content: string; e2eeKey: string; attachmentRefs: string[] }

export type ServerStore = Store & {
  // … 지금 그대로
  setE2eeCopyMaker(maker: E2eeCopyMaker | null): void // withE2ee 가 만들 때 한 번 부른다. 없으면 금고 충돌은 늘 대기
  resumeE2eeConflicts(): void
  // 지금 진행 중인 보내기 회차가 끝나기를 기다린 뒤 한 회차를 더 돌린다. 보낼 것이 없거나 회차가 멈추면(오프라인·429·차단) 끝난다

```

- `openStore.ts` 에 새 핸들러를 더하지 않는 이유: 사본 함수는 MK 를 읽어야 하는데 MK 는 부팅 뒤 `useE2ee` 가 만든 열쇠고리에 있다. 부팅의 `openStore` 때는 아직 없다. `withE2ee` 가 만들어질 때 `inner.setE2eeCopyMaker` 가 있으면 부른다
- `flushOutbox` 는 금고 초기화(7.9)만 쓴다 — 지운 금고 문서의 `removeDoc` 이 서버에 닿은 뒤에 `DELETE /api/e2ee/keys` 를 보내야 409 `vault_not_empty` 를 피한다
- `makeE2eeConflictCopy(mk, source, copyId)`: `openDocKey(mk, source.e2eeKey)` → 원본 id AAD 로 제목·본문 복호화 → 제목 뒤에 ` (충돌 사본)`(지금 `handleConflict` 와 같은 꼬리) → `createDocKey(mk)` → **사본 id** AAD 로 봉투 둘 → `attachmentRefs = attachmentRefsOf(본문)`. 복호화가 실패하면 던진다 — 서버 저장소는 던짐을 `null` 과 같이 대기로 둔다

### 6.3 경로 판정 — `docPath.ts`


- `e2ee` 경로는 `pending`·`fallback` 이 아니므로 편집 잠금(`useDocLock`)을 잡지 않고, `realtime` 이 아니므로 `useLiveDoc` 이 열리지 않고 `useDocSaver` 가 막히지 않는다

## 7. App 배선 — `App.tsx` (규칙)

### 7.1 저장소 감싸기

- 부팅에서 저장소가 `idb`·`server` 면 `withTabBroadcast(withE2ee(resolvedStore, { getMasterKey }), …)` 순서로 감싼다 — 탭 신호가 암호화 뒤의 쓰기에도 그대로 붙는다. `getMasterKey` 는 `e2eeRef.current?.keyring.getMasterKey() ?? null`(열쇠고리는 부팅 뒤에 생긴다 — F-404 6장과 같은 늦은 연결). 메모리 저장소는 감싸지 않는다
- `handleServerConflict` 는 원본·사본을 **감싼 저장소**에서 읽는다(지금은 `resolvedStore.get` — 금고 사본의 제목이 봉투로 보인다)
- `e2eeStore` 참조를 `ref` 로 들고 7.2·7.4·7.9 가 쓴다

### 7.2 잠그기·초기화 단계 등록

- 열쇠고리가 생기면(그리고 바뀌면) 등록하고, 해제 함수로 정리한다: `flush`(2.2 표), `unmount`(2.2 표), `indexes`(`clearPlainCache`), 초기화 단계(7.9)
- `flush` 단계의 "진행 중인 제목 저장": `commitTitle` 이 부르는 `store.update(…{ title })` 의 약속을 `ref` 에 두고 기다린다. 거부되면 던진다

### 7.3 목록 상태

- `DocMeta` 에 `e2ee`, `stripContent` 가 `e2ee` 를 옮긴다. 사이드바에 `ownedDocs`·`folders` 를 지금처럼 넘기면 6.1 의 필드가 따라간다

### 7.4 금고 상태가 바뀔 때

- `open` 이 되면: `e2eeStore.resumeAfterUnlock()` → `resyncFromStore()`(제목이 풀린다) → 지금 문서가 금고 문서면 본문 읽기(`openLoad` 효과)를 **다시 돌린다** — 효과의 의존 값에 금고 상태를 더하는 식으로. 편집기가 새로 생기며 초점
- `locked`·`none` 이 되면: `resyncFromStore()`(이미 `unmount` 가 바꾼 목록을 저장소 값으로 한 번 더 맞춘다)
- 본문 읽기 효과는 받은 문서가 `e2ee: 'locked'` 면 `setOpenDoc` 을 부르지 않는다 — 편집기가 빈 본문으로 뜨면 사용자가 입력해 빈 글이 저장된다(`update` 는 `'locked'` 로 막히지만 화면이 거짓말을 한다)

### 7.5 경로와 편집권

- 문서 열기 세션의 두 판정(렌더 중 빠른 판정, 효과 안 판정) 모두 `e2ee: 문서가 금고 문서인가` 를 넘긴다. 빠른 판정은 `currentDoc?.e2ee`, 효과 안 판정은 `store.get(id)` 로 한 번 더 본다 — 목록에 아직 없는 문서(해시로 바로 연 문서)가 `realtime` 으로 잘못 판정돼 소켓을 여는 일을 막는다. 빠른 판정이 `e2ee` 면 경로를 곧바로 정한다(지금 `local`·`view` 와 같이)
- **편집권 클레임**: `claimDocId` 조건을 "`store.kind === 'idb'` **또는 경로가 `e2ee`**" 로 넓힌다(c4, F-400 3.4 "지금의 편집권 클레임을 그대로 쓴다"). 두 번째 탭은 지금처럼 읽기 전용 + 편집권 알림

### 7.6 새 문서가 금고 폴더로 갈 때

- `createNewDoc`·`openWikiLinkTarget`(새 문서 갈래)·`runImportFiles` 는 `store.create` 전에 대상 폴더가 금고 폴더면 2.4 의 2~3번(`requestOpen`)을 한다. 여러 파일 가져오기는 한 번만 묻는다
- `saveCurrentAsNewDoc`: 지금 문서가 금고 문서면 `create` 에 `e2ee: true` 를 준다(최상위). 금고가 열려 있지 않으면 먼저 `requestOpen`, 닫으면 아무것도 안 한다. 편집기가 없으면(잠겨서 내려감) 지금처럼 빈 글이 아니라 **아무것도 만들지 않는다**
- `create` 가 `E2eeStoreError` 를 던지면: `'locked'` → E25 와 같은 뜻의 알림 E20, `'too-large'` → E6 문구(F-400), `'too-many-refs'` → E26. 그 밖은 지금의 `새 문서를 만들지 못했습니다. 다시 시도하세요.`

### 7.7 옮기기·폴더 만들기

- `handleMoveDoc`·`handleMoveFolder`(끌어 옮기기·D-3 폴더로 이동·여러 항목 이동이 모두 지난다)의 `catch` 가 `isE2eeStoreError(err, 'e2ee-folder')` 면 E19. 여러 항목 이동에서는 E19 를 한 번만 띄운다
- `handleCreateFolder` 는 바꿀 것 없음(4.5 가 `e2ee: true` 를 붙인다). 새 폴더 목록 항목에 `e2ee` 가 실려 사이드바가 자물쇠를 보인다

### 7.8 저장 실패 알림

- `onSaveError(error)`: `'too-large'` → E7(F-400 문구), `'too-many-refs'` → E26, `'locked'` → E20, 그 밖 → 지금 문구 `저장하지 못했습니다. 중요한 내용은 .md 내보내기로 백업하십시오.`
- E7·E26 은 **문서마다 저장이 한 번 성공할 때까지 한 번만** 띄운다(700ms 마다 같은 알림이 뜨지 않게). 성공(`onSaved`)하면 다시 띄울 수 있다

### 7.9 금고 초기화 단계 (F-404 `registerResetStep`)

1. `store.list()`·`store.listFolders()` → `planE2eeReset`
2. 지금 문서가 계획에 들어 있으면 먼저 홈으로(`setCurrentDocId(null)`, 해시 비움) — 다른 탭에서 지워짐 알림(F-296 7.3)이 뜨지 않게
3. `folderIds` 마다 `removeFolder(id, 'delete-all')`, `docIds` 마다 `remove(id)`
4. 서버 저장소면 `flushOutbox()` 를 기다린다
5. `resyncFromStore()`
- 실패는 던진다 — 열쇠고리가 기록만 하고 `source.remove()` 로 간다. 서버가 아직 문서를 갖고 있으면 409 `vault_not_empty` 로 D-13 에 개수 문구가 뜬다(F-404 7.4)

### 9.3 가짜 서버 — `e2e/fixtures/fakeServer.js`

- `POST /api/docs`: `e2eeKey`·`attachmentRefs` 를 저장하고 응답·목록에 싣는다(금고일 때만). `e2eeKey` 가 있는데 키 묶음이 없으면 409 `no_vault`, `e2eeKey` 없이 `e2ee` 폴더에 만들면 409 `e2ee_folder`

- `/api/folders`: `POST` 의 `e2ee: true` 저장, 부모가 `e2ee` 인데 `e2ee !== true` → 409 `e2ee_folder`. 목록·응답에 금고일 때만 `e2ee: true`
- `DELETE /api/e2ee/keys`: 금고 문서·금고 폴더가 남으면 409 `{ error: 'vault_not_empty', docs, folders }`(F-404 10.3 이 미룬 것)

## 14. 사람 확인 (specs/human-checks.md 에 더할 것)

1. 실제 한글 IME 로 금고 문서 본문을 조합하는 도중 자동 잠금 시간이 지나면 조합이 끝난 뒤 저장되고 나서 잠기는지, 다시 열었을 때 마지막 글자가 남아 있는지
2. 사이드바 자물쇠 아이콘의 자리·크기·색이 제목과 겹치지 않는지, 좁은 사이드바(최소 폭)에서 잠긴 문서 제목 `잠긴 문서` 가 잘리는 모양
3. P1 패널이 편집 영역 가운데에 자연스럽게 놓이는지, 어두운 테마에서 읽히는지
4. 느린 PC 에서 금고 문서 1,000개 계정의 사이드바가 열린 직후 멈칫하는 시간(c6 은 Node 값만 있다)
5. 원격 D1 에서 금고 문서 행의 `title`·`content` 가 봉투뿐인지 `wrangler d1 execute` 로 한 번 보기(F-400 9장 human-checks ③ 과 같은 항목)
6. 두 기기에서 같은 금고 문서를 번갈아 고칠 때 10초 간격 때문에 충돌 사본이 생기는 빈도가 견딜 만한지

## 15. 확인한 것과 가정

### 15.1 코드를 읽거나 돌려 확인한 것
- 머리 표 c1~c12
- `App.tsx` 에서 저장 막기(`useDocSaver` 의 `blocked`)는 `isDeletedElsewhere || claimReadOnly || isRealtime || isOfflineView` — `e2ee` 경로는 어느 것에도 들지 않아 저장이 돈다. 편집 잠금은 `docPath === 'pending' || 'fallback'` 일 때만 문서 id 를 받는다
- 실시간 편집기 옵션 `liveEditorOption` 은 `isRealtime && liveSnapshot.ready` 일 때만 만들어진다
- `worker/docs.ts` `handleCreateDoc` 은 `e2eeKey` 가 있을 때 금고 폴더 검사를 건너뛰고(금고 문서는 어느 폴더에나), 키 묶음이 없으면 409 `no_vault`. `handleUpdateDoc` 은 표지 대조(409 `e2ee_doc`·`not_e2ee`)를 버전 검사보다 먼저 한다. `handleMoveDocFolder` 는 금고 폴더로 가는 일반 문서에 409 `e2ee_folder`. `folders.ts` 는 금고 폴더 응답에만 `e2ee: true` 를 싣는다
- `serverStore.ts` `handleConflict` 는 사본 제목에 ` (충돌 사본)` 을 붙이고 `version: 0` 캐시 행 + `createDoc` 항목을 넣은 뒤 `onConflict` 를 부른다. App `handleServerConflict` 는 그 뒤 `resolvedStore.get` 으로 원본·사본을 읽는다
- `withTabBroadcast` 는 `{ ...store, … }` 로 감싸므로 `withE2ee` 의 추가 메서드·`ServerStore` 메서드가 펼침으로 살아남는다(단 `syncState` 게터는 펼치는 순간 값이 된다 — 지금도 같다)

### 15.2 가정으로 남긴 것
- **c6 은 Node 값이다.** 브라우저의 복호화 비용은 F-400 m3·m6(Chrome)만 인용했다. 4.4 기억이 필요하다는 판단은 Node 값만으로도 선다
- 같은 브라우저 두 탭이 같은 `md-remote` outbox 를 각자 보내는 지금 구조에서, 편집권이 없는 탭의 30초 재시도가 금고 항목을 10초보다 먼저 보낼 수 있다(10초 기록이 탭마다 따로다). 빈도는 재지 않았다 — 한도(분당 120)에 닿을 만큼은 아니라고 본다
- E10 의 760,000 B 붙여넣기가 CM6 에서 몇 초 걸리는지 재지 않았다. 느리면 구현이 줄 수를 줄이지 말고 줄 길이를 늘려 같은 바이트를 맞춘다
- `page.clock.install()` 이 서버 저장소의 재개 타이머까지 당긴다는 것은 F-404 E8 이 도는 것(같은 `setTimeout`·`Date.now`)에 기댄다 — 이 명세가 따로 확인하지 않았다
- 금고 폴더를 만드는 화면이 없어 e2e 가 IndexedDB·가짜 서버에 직접 `e2ee: true` 를 넣는다. 실제 흐름(F-407 옮기기)으로 만든 폴더와 행 모양이 같다는 것은 F-401 5.1 응답 모양에 기댄다
