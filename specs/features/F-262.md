# F-262 화면 분할 — 설계 개요

작성일: 2026-09-19
상태: 사용자 요청("2분할로 문서 두개 띄우기"). `specs/product.md` 4.5 를 이 명세와 함께 고쳐 범위에 넣음(기존 "분할 보기(원문|미리보기)" 제외 항목과는 다른 기능임을 구분)
근거: `App.tsx` 구조 조사(2026-09-19, fork 로 진행) — `currentDocId` 하나에 자동저장·문서 잠금(F-213)·공유(F-130)·폴더 이동(F-126)·우클릭 메뉴(F-170)·URL 해시 라우팅(`hashRoute.ts`)까지 10개 이상의 state/ref/자유 함수가 사슬로 엮여 있어, 한 개의 작은 명세로 구현할 규모가 아니다

**이 파일은 "작은 명세"(구현 단위 1개)가 아니라 설계 개요다.** `specs/architecture.md` 급 결정(데이터 모델·리팩토링 경계)을 담고, 실제 구현은 아래 3장의 F-263~F-268 로 나눠 순서대로(각각 사람 승인 후) 작성한다. 지금은 F-262 자체와 3장의 로드맵만 승인 대상이고, F-263 이후는 이 설계가 승인된 뒤 하나씩 상세 명세를 쓴다

착수 시점(2026-09-20 사용자 "양쪽 모두 수정이어야함, 나중에 개발할거야 yjs구현쯔음에"): **M3 실시간 협업(Yjs) 구현 무렵으로 미룬다.** 오른쪽 pane 읽기 전용안은 기각. 같은 문서를 양쪽에 여는 경우의 처리(한 문서에 `EditorState` 두 개 — 불변조건 충돌)가 아직 이 설계에 없으니 착수 때 Yjs 문서 공유 방식과 함께 정한다

사용자 확인 결과(2026-09-19):
- 오른쪽(보조) pane 은 왼쪽과 **완전 동등한 기능**(공유·폴더이동·우클릭 메뉴 등 전부)
- 진입점: 상단바 분할 토글 버튼 + 사이드바 문서 우클릭 메뉴(F-255) "오른쪽에 열기" 항목
- 새로고침 후 오른쪽 pane 에 열려 있던 문서는 **복원하지 않는다**(닫히고 왼쪽 문서만 남는다)

## 1. 범위와 제외

- 대상: 문서 편집 화면(S-2, 왼쪽 pane 은 지금 URL(`#/d/{id}`)이 가리키는 문서 그대로, 오른쪽 pane 은 화면 분할로 새로 여는 두 번째 문서)
- 제외(이번 라운드): 3분할 이상, 세로 분할(가로만), 상하 분할 미해결, 폭 조절 값 저장(사람 확인으로 넘길 수 있음), 새로고침 후 오른쪽 pane 복원, 좁은 창(모바일)에서 분할 진입(1023px 미만은 버튼을 숨긴다 — `App.tsx` 의 기존 `narrow` 판정 재사용)
- 도움말(S-7)·공유 관리(S-6)·공개 보기(S-5) 같은 전용 화면은 분할과 무관 — 분할은 일반 문서 편집 화면에서만 켤 수 있고, 켜진 상태에서 도움말 등으로 이동하면 분할이 꺼진다(왼쪽 자리에 그 화면이 뜬다)

## 2. 데이터 모델 (F-263 에서 구현)

- `panes: PaneState[]`(길이 1 또는 2, 0번이 왼쪽·1번이 오른쪽)로 지금의 `currentDocId`·`openDoc`·`editorRef`·`titleReadOnly`·`isReadOnlyByRole`·잠금 상태 등을 감싼다. 정확한 필드는 F-263 에서 정한다
- **왼쪽 pane 만 URL(`hashRoute.ts` `#/d/{id}`)과 동기화한다.** 오른쪽 pane 문서 id 는 React state 로만 둔다 — 새로고침하면 사라진다(사용자 확인 결과). `hashRoute.ts` 자체는 고치지 않는다
- `md.viewMode`(라이브\|원문\|보기, `architecture.md` 4장) 같은 전역 설정은 지금처럼 **왼쪽 pane 값만** localStorage 에 남긴다. 오른쪽 pane 은 분할을 열 때 왼쪽 값을 초깃값으로 복사해 시작하되, 이후 독립적으로 바뀔 수 있다(완전 동등 기능이므로) — 오른쪽에서 바꾼 값은 저장하지 않는다(F-263 에서 세부 확정)
- 자동저장(`useDocSaver`)·문서 잠금(`useDocLock`, F-213)은 pane 마다 독립 인스턴스가 필요하다 — 지금은 훅 호출이 하나뿐이다. 저장 유실 위험이 커서 별도 명세(F-265)로 집중 검증한다

## 3. 구현 로드맵 (작은 명세 F-263~F-268, 순서대로 승인 후 작성)

| # | 제목 | 요약 | 왜 이 경계인가 |
| --- | --- | --- | --- |
| F-263 | pane 상태 골격 | `currentDocId` 등 10여 개 state 를 `panes: PaneState[]`(길이 1 고정, 분할 없음) 로 감싸는 순수 리팩토링. 화면·동작은 지금과 완전히 같아야 한다(회귀 없음이 수용 기준) | 가장 위험한 단계(기존 동작 전체가 걸림)를 눈에 보이는 새 기능 없이 단독으로 검증 |
| F-264 | 오른쪽 pane 표시 + 분할 토글 | 상단바에 분할 토글 버튼, 켜면 `panes` 길이 2 로 늘려 빈 오른쪽 Editor/Viewer 를 그린다. 이 단계에서 오른쪽에 문서를 여는 방법은 아직 없어도 된다(다음 단계) | F-263 위에 눈에 보이는 첫 결과물 하나만 얹는다 |
| F-265 | 자동저장·잠금 pane 별 분리 | `useDocSaver`·`useDocLock` 을 pane 마다 독립 인스턴스로. 두 pane 에 다른 문서를 열고 동시에 편집해도 저장이 섞이지 않는지가 핵심 | 저장 유실은 되돌릴 수 없는 사용자 피해라 별도 명세로 집중 테스트 |
| F-266 | 사이드바 "오른쪽에 열기" | `Sidebar.tsx` 우클릭 메뉴(F-255)에 항목 추가, `onOpenInPane(id, 'right')` 콜백 | Sidebar 는 비교적 독립적이라 F-264 이후 아무 때나 가능 |
| F-267 | 부가 UI 의 pane 인자화 | `getShareDoc`·`requestInviteCurrentDoc`·`requestMoveDoc`·우클릭 컨텍스트 메뉴 등 지금 `currentDoc`/`editorRef.current` 를 직접 읽는 자유 함수들이 "어느 pane 에서 열렸는지"를 받게 고친다 | "완전 동등 기능" 요구사항의 나머지를 마무리하는 단계. 함수 하나하나가 좁고 독립적이라 이 시점에 몰아서 처리 |
| F-268 | 분할 폭 조절·좁은 창 대응 | 가운데 경계 드래그로 폭 조절(저장 여부는 사람 확인), `narrow` 조건에서 분할 버튼 숨김 확인, 시각 다듬기 | 순수 시각·상호작용 다듬기라 마지막 |

F-263~F-268 각각은 완료 시 `CLAUDE.md` 규칙대로 바로 커밋한다. 순서를 건너뛰지 않는다(F-265 전에 두 pane 을 자유롭게 쓰게 하면 저장 유실을 실사용자가 겪을 수 있다 — F-264 완료 시점엔 "오른쪽에 문서를 여는 진입점이 아직 없음"으로 위험을 막는다)

## 4. 이번 F-262 자체의 수용 기준

F-262 는 코드 변경이 없는 설계 문서다. "구현"의 수용 기준은 없고, 승인 기준만 있다
