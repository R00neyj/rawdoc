## 2. 로그인 — 바뀌지 않는 것을 확인

**결론: 로그인 버튼은 지금처럼 `/api/login?return={encodeURIComponent(해시)}` 로 간다. 앱은 `/login` 으로 직접 가지 않는다.**

| 부르는 곳 | 해시 | 지금 코드 | 이 명세 |
| --- | --- | --- | --- |
| 계정 메뉴 `로그인`(`AccountMenu` `handleLogin`) | `location.hash` 그대로 | 저장 대기 입력 저장 → `location.href = loginUrl(location.hash)` | 그대로 |
| 공유 관리 S-6 로그인 안내(`App` `loginFromShares`) | `#/shares` 고정 | `location.href = loginUrl('#/shares')` | 그대로 |
| 터미널 로그인 S-9(`CliLoginPage`) | `location.hash` 그대로 | `<a href={loginUrl(location.hash)}>` | 그대로(이 명세 소유 밖) |

- 이유: F-2032 1.1·3.1 이 `/api/login` 을 **유지**로 정했다. `GET /api/login` 은 세션이 있으면 곧장 복귀 주소로, 없으면 `/login?return={같은 값}` 으로 302 한다(F-2032 3.1 표 첫 행). 앱이 `/login` 으로 바로 가도 결과는 같지만 기존 e2e 세 곳(F-205 A6, F-2021 E3, F-2023 E6)이 `/api/login` 주소를 본다 — 바꿀 이득이 한 번의 302 뿐이다
- **복귀 주소 규칙은 서버가 정한다**(F-2032 3.2). 앱은 해시를 자르거나 거르지 않고 그대로 보낸다. 서버 쪽 규칙을 여기 옮겨 적으면(한 곳이 바뀔 때 다른 곳이 낡는다) 안 되므로 앱에서 다시 판정하지 않는다. 결과만 적으면:
  - `#/` 로 시작하고 512자 이하 → 로그인 뒤 `/` + 그 해시로 돌아온다
  - 해시가 비었거나(`loginUrl('')` = `/api/login?return=`), `#/` 로 시작하지 않거나, 512자를 넘으면 → `/?app=1` 로 돌아온다. 앱의 해시는 모두 `#/` 로 시작하고 가장 긴 것은 S-9 해시 약 107자(F-2023)라 보통은 넘지 않는다. 긴 제목 앵커가 붙은 문서 해시가 512자를 넘으면 문서 대신 홈으로 돌아온다 — 받아들인다
- 로그인 흐름 뒤쪽(`/login` 페이지, 제공자, 콜백)은 전부 F-2033 이다. e2e 는 가짜 서버라 `/api/login` 요청이 **나갔는지와 그 `return` 값**만 본다(F-205 A6 그대로)

## 3. 계약

### 3.1 `src/app/account.ts`

```ts
// 로그아웃 뒤 가는 곳 — 해시를 버린다(F-2032 3.6)
export const AFTER_LOGOUT_URL = '/?app=1'
export const LOGOUT_FAILED_MESSAGE = '로그아웃하지 못했습니다. 연결을 확인한 뒤 다시 시도해 주세요.'

// true = 서버가 세션을 끝냈다(2xx). false = 그 밖 전부
export async function logout(): Promise<boolean>
```

규칙:

- 요청은 `fetch('/api/auth/sign-out', { method: 'POST', credentials: 'same-origin', redirect: 'manual' })` 한 번. 본문·`Content-Type` 은 싣지 않는다(측정: 본문 없이 200). 같은 출처 `fetch` 라 브라우저가 `Origin` 을 싣는다 — F-2033 의 `Origin` 관문(F-2032 4.2)을 통과한다
- `redirect: 'manual'` 인 이유: `fetchAccount` 와 같게, 어딘가(예: 배포 사이에 남은 Access)가 302 로 가로채면 따라가지 않고 `opaqueredirect` 로 받아 **실패**로 본다. 따라가면 다른 출처 로그인 화면에 닿아 CORS 오류가 나거나, 같은 출처 HTML 을 200 으로 받아 성공으로 잘못 볼 수 있다
- **성공 = `response.ok`(200~299).** 응답 본문은 읽지 않는다 — `{"success":true}` 가 아닌 2xx 도 성공이다(본문 모양에 기대지 않는다. 멱등이라 본문이 판정에 필요 없다)
- 성공이면 **돌려주기 전에** `setPref('md.account', '')` — `fetchAccount` 가 `out` 일 때와 같은 방식이다. 이동(`location.replace`)은 이 함수가 하지 않는다: node 단위 테스트에 `location` 이 없고, 이동은 화면(AccountMenu)의 일이다
- 실패(예외, `opaqueredirect`, 2xx 가 아닌 상태 전부 — 401·403·404·5xx 포함)면 `false`. **`md.account` 를 건드리지 않는다** — 서버 세션이 살아 있을 수 있으므로 로그인 상태 표시를 유지한다
- 시간 제한을 두지 않는다(10장 Q2)
- `logoutUrl` 은 지운다. 남기면 `/cdn-cgi/access` 참조가 남는다(9장)

## 4. 로그아웃 동작

### 4.1 순서 (`AccountMenu` `handleLogout`)

1. 메뉴를 닫는다(`setOpen(false)`) — 지금과 같다. `runAndClose` 가 이미 포커스를 `계정` 버튼으로 돌려놓는다
2. `await onBeforeNavigate()` — 저장 대기 입력 저장. **지금과 같은 자리**이고, 로그아웃 요청보다 **먼저**다. 세션을 끝낸 뒤 저장하면 서버 저장소 쓰기가 401 로 실패한다
3. `await logout()`
4. `true` → `location.replace(AFTER_LOGOUT_URL)`
5. `false` → `onNotice({ type: 'error', message: LOGOUT_FAILED_MESSAGE })`. 이동하지 않는다

### 4.2 성공했을 때 화면

- 주소가 `/?app=1` 로 바뀌며 페이지를 새로 읽는다. 해시는 없다. `replace` 라 뒤로 가기로 로그인 상태의 문서 주소에 돌아가지 않는다
- 새로 읽은 앱은 `/api/me` 401 → `out` → 로컬 저장소로 부팅한다(F-205 2.4 그대로). 계정 메뉴는 `로그인` 한 항목만 보인다
- 서버 문서 해시(`#/d/{id}`)를 버리는 이유: 로컬 저장소에 없는 문서라 그대로 두면 부팅 뒤 `문서를 찾을 수 없습니다.` 알림이 뜬다(F-2032 3.6)
- 이미 열린 실시간 연결은 먼저 끊지 않는다. 페이지가 바뀌면서 닫힌다(F-2032 3.6, F-304 4.3)
- `md-remote`·`md-yjs` 는 남는다(1.2 결정). 같은 계정으로 다시 로그인하면 캐시를 그대로 쓴다

### 4.3 실패했을 때 화면

| 원인 | 앱이 보는 것 | 화면 |
| --- | --- | --- |
| 오프라인·DNS·연결 끊김 | `fetch` 예외 | N-1 error `로그아웃하지 못했습니다. 연결을 확인한 뒤 다시 시도해 주세요.` |
| 서버 5xx(비밀 없음 500 등, F-2032 4.1) | `status >= 500` | 같음 |
| `Origin` 관문 403, better-auth `INVALID_ORIGIN` 403 | 403 | 같음 |
| 서버가 아직 옛 판(`/api/auth/sign-out` 없음) | 404 | 같음 |
| 리다이렉트로 가로채임 | `opaqueredirect` | 같음 |

- 원인별로 문구를 나누지 않는다. 사용자가 할 수 있는 일이 "연결을 확인하고 다시 시도" 하나라서다. 403·404 는 운영에서 생기면 배포 사고이고 사용자가 고칠 수 없다 — 문구가 원인을 말하지 않는 것을 받아들인다
- 상태: 주소·해시·열린 문서·계정 메뉴 모두 그대로. 계정 메뉴를 다시 열면 이메일과 `로그아웃` 이 그대로 있다(`md.account` 를 안 지웠다). 실시간 연결도 그대로
- 알림은 error 라 `알림 닫기`(×)를 누를 때까지 남고, 정보성 알림에 밀리지 않는다(`pushNotice`, ia.md 4.2). NoticeBar 가 error 에 `role="alert"` 를 달아 화면 읽기 프로그램이 읽는다 — 이 명세가 따로 할 일은 없다
- 다시 시도: 계정 메뉴 → `로그아웃` 을 다시 누른다. 따로 `다시 시도` 버튼을 알림에 달지 않는다(10장 Q3)
- 이미 N4(`로그인이 만료되어 …`) 같은 error 알림이 떠 있으면 새 error 가 그것을 대체한다(`pushNotice` 기본 규칙). 로그아웃을 누른 사람에게는 로그아웃 결과가 더 급하다고 본다

### 4.4 진행 중 표시와 중복

- 요청이 나가 있는 동안 따로 표시하지 않는다. 측정상 로그아웃은 D1 쓰기 1 · 읽기 6 한 번이고, 메뉴는 이미 닫혀 있다
- 요청 중에 메뉴를 다시 열어 `로그아웃` 을 또 누르면 요청이 두 번 나간다. **막지 않는다** — 서버 쪽이 멱등이다(측정: 지운 세션 쿠키로 다시 보내도 200). 먼저 성공한 쪽이 `location.replace` 를 부르고, 두 번째 결과는 페이지가 바뀌며 버려진다
- 배포 사이 옛 서버(F-2033 전)에서는 404 → 늘 실패 알림이다. 이 명세를 F-2033 없이 배포하지 않는 이유 중 하나다(머리말)

## 5. 오프라인·로그아웃 상태에서의 메뉴

## 7. 가짜 서버 (`e2e/fixtures/fakeServer.js`)

반환 객체에 더하는 것(계약 — 다른 e2e 가 부를 수 있다):

```js
// 로그아웃 응답을 바꾼다. null = 정상(200), 'network' = 연결 실패, 숫자 = 그 상태로 응답
setSignOutFailure(mode) // mode: null | 'network' | number
// 지금까지 받은 POST /api/auth/sign-out 횟수
signOutCount() // → number
```

동작 규칙:

- `fakeServer` 안에 로그인 상태 플래그를 둔다. 처음은 로그인됨
- `**/api/me`: 로그인됨이면 지금처럼 200 `{id, email}`, 로그아웃됨이면 401 `{"error":"unauthenticated"}`(`e2e/account.spec.js` "로그아웃 상태" 테스트가 쓰는 본문과 같다)
- `**/api/auth/sign-out`: `POST` 가 아니면 `route.fallback()`. `POST` 면 횟수를 하나 올린 뒤 — `offline` 플래그가 켜져 있으면 `route.abort('internetdisconnected')`(다른 경로와 같다), `setSignOutFailure('network')` 면 `route.abort('failed')`, 숫자면 그 상태 + `{"error":"internal"}`, 아니면 로그인 상태를 로그아웃됨으로 바꾸고 200 `{"success":true}`
- `page.route` 는 페이지 이동 뒤에도 남으므로 `location.replace('/?app=1')` 뒤 새로 읽은 앱의 `/api/me` 가 401 을 받는다
- 기존 호출(e2e 25개 파일)은 로그아웃을 부르지 않으므로 결과가 같다 — 기본값이 "로그인됨, 정상 응답" 이다

### Q2. 로그아웃 요청에 시간 제한을 두나 — **기본값: 두지 않는다**

- 두지 않는 이유: 요청이 멈춰 있어도 앱은 그대로 쓸 수 있고(메뉴는 닫혔고 화면이 잠기지 않는다), 다시 누르면 새 요청이 나간다(멱등). 브라우저가 연결 실패를 알리면 4.3 알림이 뜬다
- 두는 쪽(예: 10초 뒤 `AbortSignal.timeout(10_000)` → 실패 알림)을 고르면: 3.1 에 "10초 넘으면 `false`" 규칙, 8.1 에 가짜 타이머 테스트 한 줄이 더해진다. 늦게 온 성공 응답은 버려지므로 **서버는 로그아웃했는데 앱은 실패 알림**인 경우가 생긴다 — 그래서 기본값은 두지 않는다

### Q3. 실패 알림에 `다시 시도` 버튼을 다나 — **기본값: 달지 않는다**

- 이유: F-2032 3.6 이 알림 문구만 정했다. 다시 시도는 계정 메뉴에서 한 번 더 누르면 되고, 로그아웃 실패는 드물다(측정: 서버 쪽은 D1 오류에도 200)
- 다는 쪽을 고르면: `NoticeWithAction` 의 `action`(`{ label: '다시 시도', onClick }`)을 쓰므로 `onNotice` 타입이 `(notice: NoticeWithAction) => void` 로 넓어지고(`NoticeBar.tsx` 에서 import), ia.md 6장에 `다시 시도` 낱말 행이 필요하다. A9 에 버튼 단언이 더해진다
