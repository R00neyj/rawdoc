## 3. 데이터

### 3.1 마이그레이션 (계약 — F-3001 2.1 그대로)

`migrations/0017_push_subscriptions.sql`:

```sql
CREATE TABLE push_subscriptions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  session_id TEXT,
  endpoint TEXT NOT NULL UNIQUE,
  p256dh TEXT NOT NULL,
  auth TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  last_ok_at INTEGER,
  fail_count INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX push_subscriptions_user ON push_subscriptions(user_id);
```

- 열 뜻은 F-3001 2.1 주석 그대로(파일 첫 줄 주석 한 줄에 `F-3001 2.1` 을 적는다). 외래 키를 걸지 않는다 — 계정 삭제 batch 가 지운다(6.3)
- **`created_at` 은 "마지막으로 등록된 때" 다.** 같은 `endpoint` 로 다시 `PUT` 하면 새로 등록한 것으로 본다(Q5): `user_id`·`session_id`·`p256dh`·`auth` 를 새 값으로, `created_at` = 지금, `last_ok_at` = NULL, `fail_count` = 0. **`id` 는 그대로**(m2)
- 표 이름·열에 제품명 없음(불변조건)

### 3.2 번호와 원격 적용 순서

- 번호 **`0017`**(Q1). 이 명세를 구현하는 커밋 때 `migrations/` 에 이미 `0017_*` 가 있으면(F-3010 이 먼저 들어간 경우) **그 다음 빈 번호**를 쓰고 보고에 적는다. 계약은 파일 이름의 뒷부분 `push_subscriptions` 와 3.1 DDL 이다 — 번호는 적용 순서일 뿐이고 이 표는 다른 마이그레이션에 기대지 않는다
- 원격 적용은 **코드 배포보다 먼저**(`deploy` 스킬 "원격 D1 마이그레이션은 읽는 코드보다 먼저"). 이 명세의 코드는 비밀 값이 없어도 **계정 삭제 batch 가 이 표를 지운다**(6.3) — 표 없이 코드가 먼저 나가면 계정 삭제가 500 이 된다. 순서:
  1. `npx wrangler d1 migrations apply md-editor-db --remote` (`0017` 하나)
  2. `deploy` 브랜치로 코드
  3. 비밀 값은 아무 때나(1번 전·3번 뒤 모두 된다 — 없으면 푸시 경로만 꺼져 있다): `node scripts/make-vapid-key.mjs` 로 만든 한 줄을 `npx wrangler secret put VAPID_PRIVATE_JWK` 에 붙여 넣는다. 이 값을 잃거나 바꾸면 모든 기기가 다시 구독해야 한다(F-3001 3.8) — 비밀번호 관리자에 따로 보관
- 쓰기 비용: 빈 표 만들기라 `0017` 자체의 행 쓰기는 없다(F-3001 6장의 `0018` 표 다시 만들기와 다르다)

## 4. `worker/pushServer.ts` (계약)

이 파일을 `pushApi.ts` 와 나누는 이유: F-3006 은 `DocRoom`(DO) 안에서, F-3007 은 초대 핸들러에서 구독을 읽고 결과를 반영한다. 핸들러 파일은 `./auth`(→ better-auth)를 끌어오고 `docRoomCore` 테스트들은 auth 를 모른다. 구독 표 문장을 이 파일 한 곳에 두면 F-3006·F-3007 이 같은 SQL 을 다시 쓰지 않는다

```ts
export type PushVapid = { keys: VapidKeys; subject: string }            // VapidKeys 는 webPush.ts
export type LivePushSubscription = {
  id: string; email: string; endpoint: string; p256dh: string; auth: string
  lastOkAt: number | null; failCount: number
}

export function loadVapid(env: Env): Promise<PushVapid | null>
export function listLivePushSubscriptions(db: D1Database, emails: readonly string[], nowMs: number): Promise<LivePushSubscription[]>
export function findLivePushSubscription(db: D1Database, userId: string, endpoint: string, nowMs: number): Promise<LivePushSubscription | null>
export function pushResultStatements(db: D1Database, sub: Pick<LivePushSubscription, 'id' | 'lastOkAt' | 'failCount'>, outcome: PushOutcome, nowMs: number): D1PreparedStatement[]
export function cleanupPushSubscriptions(env: Env, nowMs: number): Promise<{ dead: number }>

export const PUSH_FAIL_MAX = 3                     // 이어진 rejected 3번이면 지운다 (F-3001 2.1)
export const PUSH_LAST_OK_REFRESH_MS = 86_400_000  // last_ok_at 은 하루에 한 번만 고쳐 쓴다 (F-3001 2.1)
```

- 두 상수는 F-3001 2.5 표에 없던 것이라 `src/lib/pushPayload.ts`(F-3002, 고치지 않음)가 아니라 여기 둔다. 서버만 쓴다

### 4.1 `loadVapid` — "푸시 켜짐" 판정 한 곳

- `readVar(env, 'VAPID_PRIVATE_JWK')` 를 `importVapidKey` 에 넘긴다. `null` 이면 `null`
- `subject` = `new URL(readVar(env, 'BETTER_AUTH_URL')).origin`(F-3002 3.3). 값이 없거나 URL 이 아니면 `null`
- 던지지 않는다. 이 명세의 네 라우트 중 셋과 매일 정리는 이 값이 `null` 이면 D1 을 한 번도 부르지 않는다(5장·6.4). F-3006·F-3007 도 이 함수로 켜짐을 판정한다
- 요청마다 새로 부른다(가져오기 0.079 ms, F-3001 p3). 캐시는 두지 않는다 — DO 쪽 캐시는 F-3006

### 4.2 산 구독 — `listLivePushSubscriptions`, `findLivePushSubscription`

**"산 구독"** = 행이 있고, `users` 에 그 `user_id` 가 있고, `session_id` 가 NULL(개발 우회)이거나 **그 id 의 `auth_sessions` 행이 있고 `expires_at` 이 `new Date(nowMs).toISOString()` 보다 큰 것**(m4, `cleanupExpiredAuth` 와 같은 문자열 비교). 로그아웃(세션 행 삭제)·세션 만료 뒤에는 클라이언트가 아무것도 안 해도 빠진다(F-3001 2.1, 11장 A9)

- `listLivePushSubscriptions(db, emails, nowMs)` — 받는 사람 이메일(소문자) 목록의 산 구독 전부. `email` 은 `users.email`. 이메일 목록은 **바인딩 하나로**(`json_each`, `usage.ts` `DELETE_FOLDERS_SQL` 선례) — D1 문장당 바인딩 수 상한에 걸리지 않게. 빈 목록이면 D1 을 부르지 않고 `[]`. 순서는 `email` 오름차순, 같은 사람 안에서 `created_at` 내림차순(테스트가 순서를 기대할 수 있게)
- `findLivePushSubscription(db, userId, endpoint, nowMs)` — 그 사용자·그 `endpoint` 의 산 구독 하나 또는 `null`. `POST /api/push/test` 가 쓴다
- 문장 하나씩, 행 쓰기 없음

### 4.3 보낸 결과 반영 — `pushResultStatements`

F-3002 `PushOutcome` 네 값을 F-3001 3.7·3.8 규칙대로 문장 0~1개로 바꾼다. 실행은 부르는 쪽이 자기 batch 에 넣어 한다(F-3006 은 알림 행 처리와 한 batch).

| `outcome` | 문장 |
| --- | --- |
| `sent` | `fail_count` 가 0 이 아니거나 `lastOkAt` 이 NULL 이거나 `nowMs − lastOkAt ≥ PUSH_LAST_OK_REFRESH_MS` 이면 `UPDATE` 하나 — `fail_count = 0`, `last_ok_at` 은 하루가 지났거나 NULL 일 때만 `nowMs`(아니면 그대로). **셋 다 아니면 문장 없음**(행 쓰기 0 — F-3001 3.1 "하루에 한 번") |
| `gone` | 그 `id` 의 행 `DELETE` |
| `rejected` | `failCount + 1 ≥ PUSH_FAIL_MAX` 면 `DELETE`, 아니면 `fail_count = fail_count + 1` |
| `transient` | 없음 |

- 대상은 `id` 로만 고른다. 사이에 같은 `endpoint` 가 다른 계정으로 옮겨 가도(`id` 그대로, m2) `gone` 은 어차피 죽은 주소라 지워도 맞다
- 이 함수가 F-3003 에 있는 이유: `POST /api/push/test` 가 같은 규칙이 필요하고 F-3003 이 F-3006·F-3007 보다 먼저 간다. F-3001 3.7 표는 404·410·4xx 처리를 F-3006 몫으로 적었다 — F-3006 은 이 함수를 **부르기만** 한다(10장 갱신)

### 4.4 매일 정리 — `cleanupPushSubscriptions`

- `DELETE` 한 문장: `session_id` 가 NULL 이 아니면서 4.2 의 "세션이 살아 있음" 이 아닌 행, **또는** `users` 에 `user_id` 가 없는 행. `session_id` 가 NULL 인 행(개발 우회)은 사용자가 있으면 남긴다
- 결과 `{ dead: meta.changes }`, `console.log` 한 줄 `push gc: dead={n}`(`cleanupComments` 의 `comment gc: …` 와 같은 모양)
- 비용: 표 전체를 한 번 훑고 행마다 `auth_sessions` PK 조회(m4). 지운 행만큼 쓰기. 푸시를 켠 사람이 없으면 0행

## 5. 라우트 (계약)

### 5.1 `src/lib/pushApi.ts` — 몸통·응답 타입

```ts
export const PUSH_API_MAX_BODY_BYTES = 2048

export type PushKeyResponse = { publicKey: string }                                   // base64url 87자 (F-3002 3.2)
export type PushSubscribeBody = { endpoint: string; keys: { p256dh: string; auth: string } }
export type PushEndpointBody = { endpoint: string }
export type PushApiError =
  | { error: 'push_unavailable' }
  | { error: 'invalid'; field?: 'endpoint' | 'keys' }
  | { error: 'unsupported_push_service' }
  | { error: 'too_large'; limit: 2048 }
  | { error: 'not_found' }
  | { error: 'push_failed'; status: number | null }
```

- 2,048 B 인 이유: `endpoint` 최대 1,024자(`PUSH_ENDPOINT_MAX_CHARS`) + `p256dh` 87자 + `auth` 22자 + `PushSubscription.toJSON()` 의 `expirationTime` 과 JSON 틀 — 넉넉히 두 배
- 이 파일은 아무것도 import 하지 않는다(타입과 상수 하나). 앱·Worker 둘 다 import 한다 — `specs/architecture.md` 6장 "Worker 는 `src/lib/**` 만" 방향 그대로

### 5.2 표

모든 라우트는 로그인이 있어야 한다(`/api` 라 쿠키 세션 또는 개발 우회만, 토큰 아님). 성공 응답은 몸통 없는 204(`Cache-Control: no-store`, `account.ts` 선례) 또는 `jsonResponse`. 검사 순서는 **표의 행 순서** — 앞에서 걸리면 뒤는 보지 않는다.

**`GET /api/push/key`** — 쓰기 관문 없음(`GET`)

| 순서 | 조건 | 응답 |
| --- | --- | --- |
| 1 | 로그인 없음 | 401 `unauthenticated`(`requireUser`) |
| 2 | `loadVapid` 가 `null` | 503 `{ error: 'push_unavailable' }` |
| 3 | 그 밖 | 200 `{ publicKey }` = `loadVapid` 의 `keys.publicKey` |

D1: 인증 몫만. 이 라우트 자체의 질의 없음.

**`PUT /api/push/subscription`** — 쓰기 관문 탐(401 → 403 `account_blocked` → 429 day → 429 minute, `WRITE_LIMITER`)

| 순서 | 조건 | 응답 |
| --- | --- | --- |
| 1 | `loadVapid` 가 `null` | 503 `push_unavailable` |
| 2 | 몸통이 2,048 B 초과 | 413 `{ error: 'too_large', limit: 2048 }`(`readJsonLimited`. `badBody` 는 `limit` 이 문서 상한이라 쓰지 않는다) |
| 3 | JSON 아님, 또는 일반 객체 아님 | 400 `{ error: 'invalid' }` |
| 4 | `endpoint` 가 문자열이 아니거나, 길이 0 또는 1,024 초과, 또는 `new URL` 이 던짐 | 400 `{ error: 'invalid', field: 'endpoint' }` |
| 5 | `isAllowedPushEndpoint(endpoint)` 거짓(`http:`·포트·사용자 정보·목록 밖 호스트 모두) | 400 `{ error: 'unsupported_push_service' }` |
| 6 | `keys` 가 객체가 아니거나 `p256dh`·`auth` 가 문자열이 아니거나 `readPushKeys(p256dh, auth)` 가 `null` | 400 `{ error: 'invalid', field: 'keys' }` |
| 7 | 그 밖 | 한 batch(아래) 뒤 204 |

- `endpoint`·`keys` 밖의 키(`expirationTime` 등)는 **무시한다** — 클라이언트가 `toJSON()` 을 그대로 보내도 된다
- 저장하는 `p256dh`·`auth` 는 **받은 문자열 그대로**(패딩 `=` 가 있으면 그대로 — 보낼 때 `readPushKeys` 가 다시 푼다)
- batch 세 문장, 이 순서:
  1. 넣기 또는 옮기기 — 새 `id` 는 `crypto.randomUUID()`, `session_id` = `user.sessionId ?? null`, 충돌(`endpoint`)이면 3.1 의 "새로 등록" 규칙
  2. 5개 상한 — 이 사용자의 행 중 **방금 넣은 `endpoint` 를 뺀** 것을 `COALESCE(last_ok_at, created_at)` 내림차순(같으면 `id` 내림차순)으로 세워 앞 4개만 남기고 지운다(`PUSH_SUBSCRIPTIONS_PER_USER_MAX − 1`, m3). 방금 넣은 것은 늘 남는다
  3. `dayUsageStatement` — `write_count` +1(F-2025 R1 규칙: `/api` 쓰기는 모두 센다)
- 같은 기기를 다른 계정으로 켜면 1번이 행을 옮긴다. 옛 계정 쪽 상한은 따로 맞출 것이 없다(행이 줄 뿐)

**`DELETE /api/push/subscription`** — **쓰기 관문 없음**(Q2 기본값). `Origin` 검사는 탄다(`/api` 의 `GET` 아닌 요청 전부)

| 순서 | 조건 | 응답 |
| --- | --- | --- |
| 1 | 로그인 없음 | 401 `unauthenticated` |
| 2 | 몸통 2,048 B 초과 | 413 `too_large` |
| 3 | JSON·객체 아님 | 400 `invalid` |
| 4 | `endpoint` 가 문자열이 아니거나 길이 0 또는 1,024 초과 | 400 `invalid`, `field: 'endpoint'` |
| 5 | 그 밖 | `user_id` 가 나이고 `endpoint` 가 같은 행을 지운다(없어도, 남의 것이어도 0행) → 204 |

- 비밀 값이 없어도 된다 — 끄기는 늘 되어야 한다(서버가 보내지 않는 상태여도 행은 치운다)
- `write_count` 를 세지 않는다(관문 밖 — `/api/account` 와 같다)

**`POST /api/push/test`** — 쓰기 관문 탐

| 순서 | 조건 | 응답 |
| --- | --- | --- |
| 1 | `loadVapid` 가 `null` | 503 `push_unavailable` |
| 2 | 몸통 2,048 B 초과 | 413 `too_large` |
| 3 | JSON·객체 아님 | 400 `invalid` |
| 4 | `endpoint` 가 문자열이 아니거나 길이 0 또는 1,024 초과 | 400 `invalid`, `field: 'endpoint'` |
| 5 | `findLivePushSubscription(db, user.id, endpoint, now)` 가 `null` — 남의 구독, 없는 구독, **세션이 죽은 내 구독**(Q4) | 404 `{ error: 'not_found' }` |
| 6 | `sendPush(target, testPushPayload(), createVapidAuth(keys, subject), now)` — `topic` 없음. 결과로 `pushResultStatements` + `dayUsageStatement` 를 한 batch | `sent` → 204 / 그 밖 → 502 `{ error: 'push_failed', status }`(`status` 는 `PushSendResult.status` — 네트워크 오류·시간 초과·요청을 못 만든 경우 `null`) |

- 응답을 기다려 돌려준다(`waitUntil` 아님) — 버튼이 결과를 알려야 한다(F-3001 5.2 P1·P2). 푸시 서비스가 멎어도 `PUSH_SEND_TIMEOUT_MS`(10초) 안에 끝난다(F-3002 3.6)
- `write_count` 는 5번까지 통과해 보냈을 때만 +1(`sent` 든 아니든). 404 는 세지 않는다(batch 전)
- 남에게는 못 보낸다 — 5번이 `user_id` 로 거른다

### 5.3 `WRITE_LIMITER` 와 막힌 계정

- `PUT`·`POST /api/push/test` 는 관문의 분당 120(`MINUTE_WRITE_LIMIT`)·하루 5,000·막힌 계정 403 을 그대로 탄다 — 막힌 계정은 새로 켜지도, 테스트하지도 못한다(F-3001 3.7)
- `DELETE` 는 관문 밖이라 막힌 계정·한도에 닿은 계정도 끌 수 있다(Q2). 남용 비용은 `GET` 라우트와 같다(인증 읽기 + 0행 `DELETE`)
- 이미 켠 구독으로 **받는 것**은 막지 않는다(F-3001 3.7) — 이 명세의 판정(4.2)은 계정 막힘을 보지 않는다

## 6. 기존 파일 바꾸기

### 6.1 `AuthUser.sessionId` (`worker/auth.ts`)

- `AuthUser` 에 `sessionId?: string` — `auth_sessions.id`
- **`getUser` 의 better-auth 세션 경로만** 채운다: `result.session.id`. 개발 우회·`/v1` 토큰·`vi.mock('./auth')` 테스트는 비운다. `getUserRefreshing`(`GET /api/me` 전용)·`getUserWithSessionStart`(계정 삭제)는 채우지 않는다 — 쓰는 곳이 없다
- 관문이 `rememberUser` 로 기억한 사용자가 핸들러까지 가므로 `PUT` 은 `sessionId` 를 그대로 받는다
- 세션 연장은 id 를 바꾸지 않는다(F-3001 p12). 새로 로그인하면 새 id 다 — 그 기기의 행은 다음 `PUT` 때까지 옛 세션에 묶여 있다(10장 F-2110 행)

### 6.2 `readVar` (`worker/origin.ts`)

이름 합에 `'VAPID_PRIVATE_JWK'` 를 더한다. 다른 동작 없음. 이 이름은 `wrangler.jsonc` 어디에도 적지 않는다(정해진 것 3)

### 6.3 계정 삭제 (`worker/account.ts`)

- `deleteAccountStatements` 에 `push_subscriptions` 의 `user_id = ?1` 행 지우기 한 문장을 **`auth_sessions` 지우기 바로 앞**에(F-3001 3.7 표). 외래 키가 없으니 순서가 필수는 아니지만 "사용자에 딸린 것 → 세션 → 계정 → 사용자" 순서를 지킨다
- 비밀 값 유무와 상관없이 늘 넣는다 — 키를 뺀 뒤 계정을 지워도 구독 주소가 남지 않게
- 동기 경로 D1 문장 20 → 21(m1), "F-2038 W8" 상한 22 안

### 6.4 `worker/index.ts`

- 라우트 표에 네 줄: `GET /api/push/key`, `PUT /api/push/subscription`, `DELETE /api/push/subscription`, `POST /api/push/test`
- `scheduled` 의 매일 분기(`PURGE_CRON` 이 아닌 쪽): **`loadVapid(env)` 가 `null` 이 아닐 때만** `cleanupPushSubscriptions` 를 네 번째 `waitUntil`(`runQuietly` 로 감쌈)로 더한다. `null` 이면 지금처럼 셋 — 그래서 `{ DB }` 만 넘기는 기존 테스트 셋(근거 절)이 **고치지 않고** 통과한다. `PURGE_CRON` 분기는 그대로 하나
  - 비밀 값을 뺀 동안 남은 행은 계정 삭제로만 지워진다. 키를 다시 넣으면 다음 매일 정리가 치운다. 행이 남아 있어도 보낼 경로가 꺼져 있어 해가 없다

### 6.5 `scripts/make-vapid-key.mjs`

- `node scripts/make-vapid-key.mjs` — 인자 없음, 새 의존성 없음(전역 `crypto.subtle`)
- ECDSA P-256 키 쌍을 새로 만들어 비밀 키를 JWK 로 내보내고 **`kty`·`crv`·`d`·`x`·`y` 다섯 키만** 담은 JSON 한 줄을 **stdout** 에 쓴다(그 밖의 출력은 stdout 에 없다 — 복사·파이프가 그대로 되게). F-3002 `importVapidKey` 가 이 모양을 받는다(F-3002 m3)
- **stderr** 에 세 줄: 공개 키(base64url 87자 — `0x04‖x‖y`), `npx wrangler secret put VAPID_PRIVATE_JWK 에 위 한 줄을 붙여 넣으세요.`, `이 값을 잃거나 바꾸면 모든 기기가 다시 구독해야 합니다. 저장소에 커밋하지 마세요.`
- 파일을 쓰지 않는다. 부를 때마다 새 키다
- 스크립트 출력 문구는 개발자용이라 `ia.md` 문구 표 대상이 아니다

## 11. 열린 질문

### Q1. 마이그레이션 번호 — **기본값: F-3003 이 `0017`, F-3010 이 다음 빈 번호**

- 두 승인된 개요가 모두 `0017` 을 예정했다(근거 절). 먼저 명세를 쓴 쪽(F-3003)이 쓰고, F-3010 은 자기 명세·구현 때 빈 번호를 고른다. F-3003 구현 때 이미 `0017_*` 가 있으면 다음 빈 번호(3.2) — 둘 다 새 표를 만들 뿐 서로 기대지 않아 순서는 상관없다
- 다른 안: F-3003 이 `0020` 처럼 F-3001 의 `0018`·`0019` 뒤로 비켜 간다 — F-3001 2.1·6장 문장과 F-3005·F-3008 번호를 모두 고쳐야 하고 얻는 것이 없다

### Q2. `DELETE /api/push/subscription` 을 쓰기 관문 밖에 — **기본값: 밖(F-3001 3.7 과 다름)**

- F-3001 3.7 은 "넷 다 쓰기 관문" 이라 적었다. 그러면 **막힌 계정(F-2028)·하루 5,000 에 닿은 계정은 푸시를 끄지 못하는데 푸시는 계속 받는다**(F-3001 3.7 "받는 것은 막지 않는다"). F-2110 은 `DELETE` 가 실패하면 꺼지지 않은 채 error 로 둔다(F-3001 4.2). 계정 삭제(`/api/account`)가 같은 이유로 관문 밖이다(F-2038 3.4)
- 비용: 분당 한도 밖이 된다 — 남용해도 인증 읽기 + 0행 `DELETE` 로 `GET` 라우트와 같다. `write_count` 를 세지 않는다
- 다른 안(개요 그대로): 관문 안. `writeGate.ts`·`writeGate.test.ts` 의 예외 줄이 빠지고 A6 의 막힌 계정 행이 403 을 기대한다. 막힌 사람은 로그아웃(세션 삭제 → 산 구독 아님)이나 브라우저 알림 권한 끄기로만 멈출 수 있다

### Q3. 로컬 `npm run dev:worker` 의 푸시 — **기본값: 로컬에서는 꺼진다(503), 확인은 배포 주소에서**

- m5 — `secrets.required` 가 있는 한 `.dev.vars` 의 `VAPID_PRIVATE_JWK` 는 로컬에 들어가지 않는다. F-3001 6장의 "로컬은 `.dev.vars`" 는 틀렸다
- 기본값의 이유: F-3001 3.8 "`secrets.required` 에 넣지 않는다 — 없으면 푸시만 꺼지고 배포는 막히지 않는다" 를 지킨다. 서비스 워커는 어차피 `npm run dev` 에서 돌지 않아(F-3001 4.1) 로컬 푸시 확인은 원래 번거롭다. 서버 판정은 모두 node 단위 테스트가 본다(7장)
- 다른 안 A: `secrets.required` 에 넣는다 → 로컬 `.dev.vars` 가 된다. 대신 **비밀 값 없이는 배포가 실패**하고(m6 `addRequiredSecretsInheritBindings`), `authServer.test.ts` U12 기대 목록과 `worker-configuration.d.ts`(`npm run cf:types`)가 바뀐다. F-3001 3.8 결정을 뒤집는다
- 다른 안 B: 로컬에서 시험할 때만 `wrangler.jsonc` 를 잠시 고친다 — U12 가 커밋을 막아 주지만 절차가 사람 기억에 기댄다. 문서화하지 않는다

### Q4. 테스트 푸시도 세션이 산 구독에만 — **기본값: 그렇다(죽은 세션 → 404)**

- 이유: 실제 푸시(F-3006·F-3007)는 산 구독에만 간다. 테스트만 죽은 행으로 성공하면 "테스트는 되는데 알림은 안 온다" 가 된다. 404 를 받으면 F-2110 은 다시 `PUT` 할 근거가 생긴다(10장 로그아웃 뒤 재로그인 행)
- 다른 안: `user_id`·`endpoint` 만 맞으면 보낸다 — A9 의 둘째 경우가 204 가 된다

### Q5. 같은 `endpoint` 로 다시 `PUT` 하면 새 등록으로 — **기본값: `created_at` = 지금, `last_ok_at` NULL, `fail_count` 0**

- 이유: 다시 `PUT` 은 "이 기기가 살아서 서버에 알렸다"(F-3001 4.3, 7일마다) 는 뜻이다 — 5개 상한에서 살아 있는 기기가 뒤로 밀려 지워지지 않는다. 키를 바꾼 뒤 다시 구독한 기기의 실패 수도 0 부터. 대가는 `last_ok_at` 을 다음 성공 때 한 번 더 쓰는 것(7일에 한 번, 쓰기 1행)
- 다른 안: `created_at`·`last_ok_at` 은 그대로 두고 키·세션·실패 수만 바꾼다 — 상한 순서가 "처음 켠 때" 기준이 되어 오래 쓴 기기가 먼저 지워질 수 있다

### Q6. `pushServer.ts` 를 따로 — **기본값: 나눈다(F-3001 6장은 `pushApi.ts` 하나)**

- 이유는 4장 머리 — F-3006(DO)·F-3007 이 auth 를 끌어오지 않고 같은 문장을 쓴다. 다른 안: `pushApi.ts` 한 파일 — F-3006 이 `docRoomCore` 쪽에서 import 하면 `better-auth` 가 DO 테스트 import 그래프에 들어온다(돌려 보지 않았다 — 무거워질 뿐 깨지는지는 모른다)

### Q7. 푸시 라우트의 `write_count` — **기본값: `PUT`·`POST test` 는 +1, `DELETE` 는 세지 않음**

- 이유: `/api` 쓰기는 모두 센다(F-2025 R1) — 하루 5,000 으로 테스트 푸시 남용을 묶는다. `DELETE` 는 관문 밖이라(Q2) 세지 않는다. 기기 하나가 평소 쓰는 것은 7일에 `PUT` 하나(F-3001 4.3)라 한도에 닿지 않는다
- 다른 안: 셋 다 세지 않는다 — 테스트 푸시의 상한이 분당 120 뿐이 된다
