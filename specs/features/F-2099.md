## 2. 계정 슬롯 (`md.userCssAccount`)

- 모양은 개요 4.2 + **`etag`**(서버가 준 `ETag` 그대로). 클라이언트가 `"c1-…"` 를 조립하지 않는다 — 태그 모양은 서버 것(F-3010 3.1)
- **`readAccountSlot`**: `userId`·`snippets` 규칙은 F-2095 6장 그대로(어긋나면 `null`, `readUserCssSources().account` 와 늘 같은 답). 나머지는 칸마다 기본값으로 — `rev` 0 이상 안전 정수 아니면 0, `pending` 은 16진 16자 문자열만 남기고 모양이 틀리면 빈 것, `mergedLocal` 불리언 아니면 거짓, `fetchedAt` 수 아니면 0, `etag` 문자열 아니면 `''`. `rev` 가 0 으로 떨어지면 다음 보내기가 409 → 다시 얹기로 복구된다
- **`writeAccountSlot`**: `trySetPref` 실패면 `false`(아무것도 안 바뀜). 성공하면 같은 호출에서 `writeUserCssBoot(readUserCssSources())`(실패면 부팅 값 `''`, F-2095 6장과 같은 규칙) → `notifyUserCssChanged(origin)`
- **`editableSnippets(id)`**: `null` → 로컬 슬롯. 아니면 슬롯 `userId === id` 일 때 그 `snippets`, 아니면 `[]`
- **`saveUserCssSnippets(id, next)`**: `null` → `saveLocalSnippets(next)` 그대로. 아니면 한도·검증은 `saveLocalSnippets` 와 같은 순서·같은 결과 코드, 그다음 지금 슬롯(`userId` 가 다르거나 없으면 빈 새 슬롯 `{ rev: 0, snippets: [], pending: 빈 것, mergedLocal: false, fetchedAt: 0, etag: '' }`)에 `snippets = next`, `pending = diffPending(슬롯.snippets, next, 슬롯.pending)` 를 넣어 `writeAccountSlot(…, 'self')`. 실패 → `quota`
- 로그아웃은 슬롯을 지우지 않는다(개요 4.5). 계정 삭제는 지운다(결정 8)

## 3. 순수 함수 (`userCssSync.ts`)

- **`diffPending(prev, next, pending)`** — `next` 의 원소 중 `prev` 에 없거나 다섯 값 중 하나라도 다른 id 를 `upserts` 에, `prev` 에 있고 `next` 에 없는 id 를 `deletes` 에 더한다. 기존 순서 유지 후 새 것은 `next` 순서로 뒤에. 한 id 는 두 목록에 동시에 있지 않다 — 지운 id 는 `upserts` 에서 빠지고, 다시 나타난 id 는 `deletes` 에서 빠진다
- **`rebaseUserCss(server, local, pending)`** (개요 4.4) — 서버 순서대로 걸으며 `deletes` 의 id 는 빼고, `upserts` 의 id 는 `local` 의 같은 id 로 바꾼다. 서버에 없는 `upserts` id 는 `local` 순서대로 끝에 붙인다. `local` 에 없는 `upserts` id 는 무시. `pending` 이 비면 결과 = `server`. 다른 기기가 지운 스니펫을 이 기기가 고쳤으면 다시 살아난다("이 기기가 건드린 것이 이긴다", 개요 4.4)
- **`mergeLocalIntoAccount(account, local, newId, now)`** (개요 4.5) — `local` 을 차례로 보며 `account` 에 **이름과 원문이 둘 다 같은** 것이 있으면 건너뛴다. 아니면 새 id·`updatedAt = now`·`enabled` 그대로로 끝에 붙인다. 그때까지의 목록에 같은 이름이 있으면 이름을 `{이름} (이 브라우저)` 로 — 60자(UTF-16, F-2094 5.1)를 넘으면 `{이름}` 쪽 뒤를 잘라 전체 60자, 자른 끝의 공백은 지우고 서로게이트 쌍 가운데서 자르지 않는다. 붙이면 50개 또는 262,144 바이트를 넘는 스니펫은 건너뛰고 다음 것을 본다(로컬 슬롯에 남으므로 잃지 않는다). `added` = 붙인 새 id, 붙인 순서
- **`settlePending(sent, sentPending, current)`** — PUT 이 성공한 뒤 남길 `pending`. `current.pending.upserts` 중 `sentPending.upserts` 에 없거나, 지금 슬롯의 그 스니펫이 보낸 목록의 같은 id 와 다른 것만 남긴다. `deletes` 는 `sentPending.deletes` 에 없는 것만. 보내는 동안 사용자가 고친 것을 잃지 않게 한다

## 4. 동기화 엔진

**상태는 늘 `localStorage` 에서 다시 읽는다.** 엔진은 슬롯의 메모리 사본을 두지 않는다 — 같은 브라우저의 다른 탭이 먼저 보내 `pending` 을 비웠으면 이 탭은 보낼 것이 없다. 한 탭 안에서 받기·보내기는 한 줄로 이어 달린다(겹치지 않음). 탭 사이는 잠그지 않는다 — 둘이 같은 `pending` 을 보내면 하나가 409 → 다시 얹기로 같은 내용이 되고, `rev` 가 하나 더 오를 뿐이다.

엔진은 `fetch`·시계·타이머·id 생성을 주입받아 node 에서 판정한다. 계기(`start(id)`·`onOnline`·`onVisible`·`onSelfChange`·`pull`·`flush`)를 함수로 내놓고, `useUserCssSync` 는 이벤트를 잇기만 한다. `useUserCss.ts` 가 `useUserCssSync({ accountId: !isPublic && account.state === 'in' ? account.id : null, blocked: account.state === 'in' && account.blocked })` 로 부른다. 안전 모드에서도 돈다 — 안전 모드 창에서 고친 CSS 가 계정에 올라가야 한다(적용만 막힌다, F-2095 5장).

### 4.1 받기

| 계기 | 조건 |
| --- | --- |
| `accountId` 가 `null` 에서 id 로, 또는 다른 id 로 | 늘 |
| `visibilitychange` 로 보임 | 마지막 받기(`fetchedAt`) 뒤 600,000ms 이상 |
| `requestUserCssPull()` (설정 탭을 열 때) | 늘 — 304 라 싸다 |

1. 슬롯 `userId` 가 이 id 가 아니면 **빈 새 슬롯으로 바꿔 쓴다**(앞 계정의 스니펫·`pending` 을 버린다, 개요 4.5)
2. `GET /api/user-css`, `credentials: 'same-origin'`, `cache: 'no-store'`, `etag` 가 있으면 `If-None-Match`. 304 는 `!res.ok` 판정보다 먼저 가른다(`fetchNotifications` 선례)
3. 304 → `fetchedAt` 만 고친다. 200 → 몸통이 `{ snippets, rev }` 이고 `validateUserCssSnippets` 통과·`rev` 0 이상 정수일 때만 `snippets = rebaseUserCss(서버, 슬롯.snippets, 슬롯.pending)`, `rev`·`etag`(응답 헤더, 없으면 `''`)·`fetchedAt` 갱신. 그 밖의 응답·네트워크 실패 → 슬롯 그대로, **오류 줄 없음**(받기 실패는 다음 계기에 다시 한다)
4. `mergedLocal` 이 거짓이면 `mergeLocalIntoAccount(snippets, 로컬 슬롯)` → `added` 를 `pending.upserts` 끝에, `mergedLocal = true`
5. 3·4 를 **`writeAccountSlot(…, 'remote')` 한 번**에 쓴다(1번은 GET 전에 따로 쓴다 — 앞 계정 CSS 를 곧바로 내린다) → 적용은 F-2095 가 조합 끝까지 미룬다
6. `pending` 이 비어 있지 않으면 바로 보내기

### 4.2 보내기

| 계기 | 시점 |
| --- | --- |
| 이 탭의 `'self'` 변경(탭·D-16 저장)이고 슬롯에 `pending` 이 있음 | 마지막 변경 2,000ms 뒤(다시 바뀌면 다시 잰다) |
| `flushUserCssPush()` (D-16 닫기) | 바로, 걸린 2,000ms 타이머는 지운다 |
| `online` 이벤트, 받기 6번 | 바로 |

1. 슬롯을 다시 읽는다. `userId` 가 이 id 가 아니거나 `pending` 이 비었으면 끝. `blocked` 면 끝(오류 줄 없음 — 차단 알림이 이미 말한다, F-2030)
2. `checkUserCssLimits(slot.snippets)` 가 `count`/`bytes` → 그 오류, 보내지 않음(다시 얹기·병합이 상한을 넘긴 경우)
3. `PUT` `{ snippets: slot.snippets, baseRev: slot.rev }`
4. 200 `{ rev }` → 슬롯을 **다시 읽어** `userId` 가 같을 때만 `rev` 갱신, `etag = ''`, `pending = settlePending(보낸 것, 보낸 pending, 지금 슬롯)`, `writeAccountSlot(…, 'remote')`. 오류 지움
5. 409 → `If-None-Match` 없이 받아 다시 얹고 쓴 뒤(4.1 의 3·5) 3번부터 다시. **한 번의 보내기에서 PUT 은 최대 세 번** — 세 번째도 409 면 `conflict` 로 멈춘다. `pending` 은 남아 다음 계기에 새로 센다
6. 그 밖: 413 → `bytes`, 400 → `invalid`, 401 → 멈춤(오류 줄 없음 — 계정 상태가 `out` 으로 바뀐다), 네트워크 실패·403·429·5xx·몸통 모양 틀림 → `offline`

오류는 엔진 모듈 상태 하나(`getUserCssSyncError`)이고 저장하지 않는다. 다음 성공한 PUT·`accountId` 바뀜에서 `''` 로. 새로 읽은 페이지는 `pending` 이 남아 있으면 받기 6번에서 다시 보내 다시 판정한다.

## 5. 설정 탭·D-16 (로그인 상태)

- **노출:** 앱(공개 보기 아님)이면 로그인 여부와 무관하게 `사용자 CSS` 탭을 준다 — `SettingsDialog` 의 `css: userCss !== undefined`. `PublicView` 는 여전히 `userCss` 를 안 준다. 로그인 상태 탭은 6개, 좁은 창에서는 F-2096 3.4 로 옆으로 밀린다
- **목록·저장:** F-2096 3.3 의 모든 조작(켜기·새 스니펫·템플릿·삭제)과 D-16 의 읽기(`readInitial`)·저장(`flush`)이 `editableSnippets(accountId)`·`saveUserCssSnippets(accountId, …)` 를 쓴다. 읽고-고치고-쓰기를 한 틱에(F-2096 결정 7) 그대로. `accountId` 가 바뀌면 탭을 다시 만든다(`key`)
- **저장 위치 줄:** `accountId === null` → 지금 문구, 아니면 `계정에 저장해 로그인한 기기 모두에 적용합니다.`(개요 5.8)
- **오류 줄** `p.user-css-error[role=alert]` 하나: 이 탭의 마지막 저장 실패 문구가 있으면 그것, 없으면 `accountId !== null` 일 때 `userCssSyncMessage(getUserCssSyncError())`(`subscribeUserCssSyncError` 로 다시 그림)
- **다시 읽기:** `storage` 키에 `md.userCssAccount` 를 더한다. 탭이 열릴 때 `requestUserCssPull()`
- D-16 을 닫으면 저장(`flush`) 뒤 `flushUserCssPush()`

| 오류 | 문구 |
| --- | --- |
| `offline` | `계정에 저장하지 못했습니다. 연결되면 다시 보냅니다.` (개요 5.8) |
| `conflict` | `다른 기기에서 바뀐 내용과 합치지 못했습니다. 다시 열어 확인해 주세요.` (개요 5.8) |
| `count`·`bytes`·`invalid` | `userCssSaveMessage` 와 같은 문구(F-2096 5.2) |

## 6. 결정

1. **슬롯 없이 로그인한 첫 순간** — F-2095 Q1 그대로 아무것도 적용하지 않고, `in` 직후 받기 한 번(4.1)으로 슬롯을 만든다. 로그인은 OAuth 왕복이라 첫 로그인 직후는 사실상 늘 온라인이다. 대가: 첫 로그인 때 한 번 "로컬 CSS → 없음 → 병합된 CSS" 로 바뀐다(사람 확인)
2. **`mergedLocal` 은 병합 결과를 슬롯에 쓰는 그 쓰기에서 참으로** — 개요 4.5 는 "PUT 성공 뒤". 병합한 스니펫은 `pending.upserts` 에 들어가 PUT 이 실패해도 다음에 보내지므로 잃지 않는다. PUT 성공까지 거짓으로 두면 그사이 새로 고침에서 다시 병합하고, `(이 브라우저)` 로 이름이 바뀐 스니펫은 "이름·원문 둘 다 같음" 에 걸리지 않아 **두 번 붙는다**
3. **`etag` 를 슬롯에 둔다** — 서버 태그 모양을 클라이언트가 알 필요가 없다. PUT 성공 때 비워 다음 받기는 200(내용 같음) 한 번
4. **받기 실패는 조용히, 보내기 실패만 오류 줄** — 받기는 계기가 잦고(탭 열기·화면 복귀) 실패해도 잃는 것이 없다
5. **엔진은 `in` 일 때만 네트워크를 쓴다.** `offline`(저장 계정 id)일 때도 탭은 그 계정 슬롯을 고치고 `pending` 에 쌓는다 — 그 id 가 다음 `in` 과 같으면 보내고, 다르면 1번에서 버린다(개요 4.5)
6. **409 세 번의 셈은 보내기 한 번 안에서** — 계기(편집·`online`·새로 고침)마다 새로 센다. 멈춘 뒤 자동 재시도 타이머는 두지 않는다
7. **로컬 슬롯과 부팅 값의 `local` 은 건드리지 않는다** — 로그아웃하면 다시 쓴다(개요 4.5)
8. **계정 삭제 때 `md.userCssAccount`·`md.userCssBoot` 를 `''` 로** — `cleanUpAfterAccountDelete` 의 `md.account` 비우기 바로 뒤, 같은 `setPref` 경로로. 서버 행이 지워진(F-3010 4장) 계정의 CSS 가 이 브라우저에 남지 않게 한다(원격 문서 캐시를 지우는 것과 같은 까닭). 부팅 값을 비운 대가는 삭제 직후 첫 화면 한 번 늦게 칠함(F-2095 결정 1). 개요 4.7 에 없던 것 → 10장
