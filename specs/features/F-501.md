### 1.1 파일 이름 — `comments.ts` 에 섞지 않고 `docComments.ts` 로 (개요와 다른 곳, 11장 Q1)

개요 2.1·2.5·3.9·6장은 댓글 코어를 `src/lib/comments.ts` 에 둔다고 적었다. 그 파일은 이미 다른 일을 한다:

- `comments.ts` 는 `stripComments` 하나만 내보낸다 — 마크다운 주석 문법(`%% … %%`, `<!-- … -->`)을 공유·공개 화면에서 지우는 함수(F-214 2.1). importer 는 앱 넷(`SharedView.tsx`·`ShareMenu.tsx`·`toHtmlDoc.ts`·`toPlainText.ts`)과 worker 셋(`links.ts`·`publicPage.ts`·`shareSet.test.ts`)
- 화면 말로 이 파일은 `주석` 이고(우클릭 `주석`, 개요 c10), 새 코어는 `댓글` 이다. 개요 5.1 개념어 표가 "`주석` 은 HTML `<!-- -->` 다" 라고 둘을 갈라 놓았다. 한 파일에 두면 `stripComments` 가 "댓글을 지운다" 로 읽힌다
- 공유 화면(`SharedView.tsx`)·공개 페이지(`publicPage.ts`)가 `comments.ts` 를 import 한다. 여기에 `yjs` 를 부르는 코드를 섞으면 이 경로들이 쓰지 않는 의존이 딸려 들어올 수 있다(트리 셰이킹에 기대야 한다)

### 2.2 타입 (계약)

```ts
import type { RelativePositionJSON } from './docRoomProtocol'

export type CommentAuthor = { id: string; email: string } | { id: null; email: null }
export type CommentAnchor = { start: RelativePositionJSON; end: RelativePositionJSON }
export type AnchorRange = { from: number; to: number }        // Y.Text 인덱스(UTF-16), from < to

export type CommentEntry = {
  v: 1
  parent: string | null
  anchor: CommentAnchor | null
  quote: string
  body: string
  mentions: string[]
  author: CommentAuthor
  createdAt: number
  resolved: { by: CommentAuthor; at: number } | null
}

export type CommentRecord = {
  id: string
  parent: string | null
  body: string
  mentions: string[]
  authorId: string | null          // 추가 (Q2)
  authorEmail: string | null
  createdAt: number
  resolvedAt: number | null
  resolvedById: string | null      // 추가 (Q2)
  resolvedBy: string | null        // 이메일
  quote: string
  prefix: string
  suffix: string
  anchorFrom: number | null
  anchorLength: number | null      // 추가 (Q2)
}

export type CommentThread = {
  id: string                                   // 첫 댓글 id
  root: CommentEntry
  replies: { id: string; entry: CommentEntry }[]
}
```

- `CommentEntry` 는 개요 2.1 과 필드가 같다. `anchor` 의 인라인 타입에 `CommentAnchor` 라는 이름만 붙였다
- **첫 댓글도 `anchor: null` 일 수 있다** — 되살릴 때 자리를 못 찾은 고아(개요 3.4 ③ "`anchor: null`, `quote` 는 그대로"). 첫 댓글과 답글은 `anchor` 가 아니라 `parent` 로 가린다
- 모든 위치(`AnchorRange`, `anchorFrom`, `anchorLength`)는 **`content` `Y.Text` 의 UTF-16 인덱스**다. 편집기 `Y.Text` 는 씨앗이 `toEditorText` 로 LF 가 되고(`yBinding.ts` `createYBinding`), CM6 위치와 1:1 이다. 개요 3.3 `anchor_from` 주석 "DO 본문(LF) 기준 UTF-16" 과 같은 뜻
- `CommentRecord` 의 **추가 필드 셋**과 이유는 2.4

### 2.3 `CommentEntry` 모양 검사 — `validateCommentEntry`

```ts
export type CommentShapeError =
  | 'not_object' | 'unknown_field' | 'bad_version' | 'bad_parent' | 'bad_anchor' | 'bad_quote'
  | 'bad_body' | 'empty_body' | 'body_too_long'
  | 'bad_mentions' | 'too_many_mentions' | 'bad_author' | 'bad_created_at' | 'bad_resolved'

export function validateCommentEntry(value: unknown):
  | { ok: true; entry: CommentEntry }
  | { ok: false; error: CommentShapeError }
export function isCommentId(value: unknown): value is string
export function readCommentAnchor(value: unknown): CommentAnchor | null
export function normalizeCommentBody(raw: string): string
export function checkCommentBody(body: string): 'bad_body' | 'empty_body' | 'body_too_long' | null
```

**검사 순서가 계약이다** — 여럿이 틀리면 표에서 먼저 나오는 사유 하나를 돌려준다(테스트가 사유 문자열로 판정한다):

| 순서 | 사유 | 틀린 것 |
| --- | --- | --- |
| 1 | `not_object` | 평범한 객체가 아님(`null`·배열 포함) |
| 2 | `unknown_field` | 키가 정확히 `v`·`parent`·`anchor`·`quote`·`body`·`mentions`·`author`·`createdAt`·`resolved` 아홉이 아님(빠지거나 더 있음) |
| 3 | `bad_version` | `v !== 1` |
| 4 | `bad_parent` | `null` 도 아니고 `isCommentId` 도 아님 |
| 5 | `bad_anchor` | 답글(`parent` 가 문자열)인데 `anchor !== null`. 첫 댓글인데 `anchor` 가 `null` 도 아니고 `readCommentAnchor` 가 `null` |
| 6 | `bad_quote` | 문자열이 아님. 답글인데 `''` 가 아님. 첫 댓글인데 길이가 1~`COMMENT_QUOTE_MAX` 밖 |
| 7 | `bad_body` · `empty_body` · `body_too_long` | `checkCommentBody` 의 결과 |
| 8 | `too_many_mentions` · `bad_mentions` | 배열이 아니면 `bad_mentions`. 길이 > `MENTIONS_PER_COMMENT_MAX` 면 `too_many_mentions`. 그 밖에 항목이 문자열이 아님·소문자가 아님(`s !== s.toLowerCase()`)·6.1 이메일 모양이 아님·`COMMENT_EMAIL_MAX` 초과·중복·**`parseMentions(body)` 에 없음**·`author.id === null` 인데 빈 배열이 아님 → `bad_mentions` |
| 9 | `bad_author` | 키가 정확히 `id`·`email` 둘이 아님. 둘 다 `null` 이거나, `id` 가 1~`COMMENT_AUTHOR_ID_MAX` 자 문자열이고 `email` 이 1~`COMMENT_EMAIL_MAX` 자 문자열이어야 한다 — 한쪽만 `null` 은 틀림 |
| 10 | `bad_created_at` | `Number.isSafeInteger` 가 아니거나 음수 |
| 11 | `bad_resolved` | `null` 도 아니고 키가 정확히 `by`·`at` 이 아님. `by` 가 9번 규칙에 안 맞음. `at` 이 10번 규칙에 안 맞음. **답글인데 `null` 이 아님**. `by.id === null` 과 `author.id === null` 이 서로 다름(로컬 항목은 로컬이 해결하고, 서버 항목은 서버 사용자가 해결한다) |

- **키 집합을 닫는다(2번).** 알 수 없는 필드를 허용하면 edit 권한자가 필드 하나에 큰 값을 넣어 방 Doc 을 부풀릴 수 있다. 닫아 두면 항목 하나의 크기가 위 한도로 묶인다(최대 4,731 B, r10)
- `ok: true` 일 때 `entry` 는 **새 객체**다(입력 참조를 그대로 돌려주지 않는다) — 호출자가 고쳐도 `Y.Map` 이 쥔 값이 바뀌지 않게
- 작성자 이메일은 소문자를 요구하지 않는다 — 서버가 세션에서 찍은 값 그대로다(개요 2.2). 멘션만 소문자다

**`isCommentId`**: 문자열이고 1~`COMMENT_ID_MAX` 자이며 글자가 모두 `A–Z a–z 0–9 _ -` 인 것

**`readCommentAnchor`** — yjs 에 넘기기 전의 닫힌 모양 검사(r5 가 이유). 통과하면 입력과 같은 값의 새 객체, 아니면 `null`:

- 값이 평범한 객체이고 키가 정확히 `start`·`end` 둘
- `start`·`end` 각각 키가 정확히 `tname`·`item`·`assoc` 셋이고, `tname === Y_CONTENT_NAME`, `item` 은 키가 정확히 `client`·`clock` 둘인 객체이며 둘 다 음이 아닌 `Number.isSafeInteger`
- `start.assoc === 0`, `end.assoc === -1` (개요 2.1)
- `item: null`(타입 기준 위치)은 받지 않는다 — `from < to` 로 만든 앵커는 늘 `item` 이 있다(r2). 받으면 `{tname:'content'}` 처럼 문서 끝으로 풀려(r5) 엉뚱한 범위가 생긴다
- F-307 `readPeerCursor` 는 이보다 느슨하다(객체인지만 본다). 커서는 화면에만 쓰이고 앵커는 저장되므로 이 명세는 더 좁힌 함수를 따로 둔다. 개요 2.1 "검사 함수를 같이 쓴다" 와 다른 점 — 11장 Q4

**`normalizeCommentBody`**: `\r\n`·`\r` 을 `\n` 으로 바꾼 뒤 `String.prototype.trim()`. 화면(F-505·F-507)은 보내기 직전에 이것을 부르고, 그 결과를 저장한다

**`checkCommentBody`**: 문자열이 아니거나 `body !== normalizeCommentBody(body)` → `bad_body`. 길이 0 → `empty_body`. 길이 > `COMMENT_BODY_MAX` → `body_too_long`. 그 밖 `null`. 길이는 UTF-16 `.length` 다(개요 2.5 "UTF-16, 앞뒤 공백 뺀 길이" — 저장 값이 이미 정규화돼 있으므로 같다)

### 2.4 `CommentRecord` — 필드 셋을 더한 이유 (개요와 다른 곳, 11장 Q2)

개요 3.9 의 `CommentRecord` 로는 되살리기가 원래 항목을 다시 만들지 못한다. 세 군데가 비었다:

| 더한 필드 | 없으면 생기는 일 | D1 열 (F-502 마이그레이션) |
| --- | --- | --- |
| `authorId` | DO 가 D1 에서 되살린 댓글(개요 3.4)의 `author` 가 `{ id: null, email: null }`(로컬 작성자)이 된다. 2.4 삭제 권한은 작성자 id 로 가리므로 **작성자가 자기 댓글을 못 지운다** | 이미 있음: `author_id` |
| `resolvedById` | 되살린 해결 표시의 `by` 가 `CommentAuthor` 합 타입(둘 다 문자열 또는 둘 다 `null`)을 채우지 못한다 | **새 열 `resolved_by_id TEXT`** |
| `anchorLength` | 인용문은 200자에서 잘린다(`199자 + '…'`, 개요 2.1). 앵커가 200자보다 길면 기록만으로는 **범위의 끝을 알 수 없다** — 어디서 시작하는지는 찾아도 몇 자인지 모른다 | **새 열 `anchor_length INTEGER`** |

- 이관(개요 4.6)에서는 클라이언트가 보낸 `authorId`·`authorEmail`·`resolvedById`·`resolvedBy`·`mentions` 를 **쓰지 않는다** — 서버가 이관하는 사용자로 덮는다(4.4 `restoreCommentEntries` 의 `importer`). 로컬 기록은 늘 `null` 이다
- 다른 방법(열을 더하지 않기)은 11장 Q2

### 2.5 `CommentRecord` 검사 — `parseCommentRecords`

```ts
export function parseCommentRecords(value: unknown):
  | { ok: true; records: CommentRecord[] }
  | { ok: false; reason: 'invalid' | 'too_many' }
```

이관 몸통 `{ records }`(F-503 `POST …/comments/import`)과 로컬 기록 읽기(F-508)가 부른다. 신뢰하지 않는 입력으로 다룬다

- 배열이 아니면 `invalid`. 길이 > `COMMENTS_PER_DOC_MAX` → `too_many`(F-503 이 413 `too_many` 로 옮긴다)
- 항목마다: 키가 정확히 2.2 의 열다섯, `isCommentId(id)`, `id` 중복 없음, `parent` 는 `null` 이거나 **같은 배열 안 첫 댓글**의 id(답글의 답글·자기 자신·없는 id 는 `invalid`)
- `body` 는 `checkCommentBody` 통과. `mentions` 는 2.3 8번과 같은 규칙(`authorId === null` 이면 빈 배열)
- `authorId`·`authorEmail` 은 둘 다 `null` 이거나 2.3 9번 길이 규칙의 문자열 둘. `createdAt` 은 2.3 10번
- `resolvedAt === null` 이면 `resolvedById`·`resolvedBy` 도 `null`. `resolvedAt` 이 수면 둘 다 `null` 이거나 둘 다 문자열이고, `authorId === null` 여부와 `resolvedById === null` 여부가 같다. 답글은 `resolvedAt === null`
- 앵커 필드 — 세 모양 중 하나여야 한다:

| 종류 | `quote` | `prefix`·`suffix` | `anchorFrom` | `anchorLength` |
| --- | --- | --- | --- | --- |
| 답글 | `''` | `''` | `null` | `null` |
| 자리가 있는 첫 댓글 | `anchorLength ≤ 200` 이면 길이가 정확히 `anchorLength`. `> 200` 이면 `'…'` 로 끝나고 길이 199 또는 200 (7.2 의 자르기 결과) | 각 0~`ANCHOR_CONTEXT_CHARS` 자 | 음이 아닌 안전 정수 | 1 이상 안전 정수 |
| 고아 첫 댓글 | 1~200자 | `''` | `null` | `null` |

- 스레드마다 답글 수 ≤ `REPLIES_PER_THREAD_MAX`, 넘으면 `too_many`
- 모두 통과하면 입력 순서 그대로 새 객체 배열

```ts
import * as Y from 'yjs'

export function resolveCommentAnchor(ytext: Y.Text, anchor: CommentAnchor | null): AnchorRange | null
export function resolveCommentAnchors(
```

### 3.1 만들기 — `createCommentAnchor`

- `0 ≤ from < to ≤ ytext.length` 이고 둘 다 정수일 때만 만든다. 아니면 `null`(화면은 C1 `댓글을 달 부분을 먼저 선택하세요.` 를 띄운다 — F-505)
- 시작은 `createRelativePositionFromTypeIndex(ytext, from, 0)`, 끝은 `(ytext, to, -1)` 을 `relativePositionToJSON` 한 것. 결과는 늘 `readCommentAnchor` 를 통과한다(A1 이 단언)
- **직렬화는 JSON 객체 그대로 `Y.Map` 값 안에 둔다.** 바이트 인코딩 + base64 로 바꾸지 않는다 — 개요 10장 "기본값으로 정한 것" 2 가 JSON 모양으로 정했다. 비용: 앵커 하나 155자 대 바이너리 16 B(base64 약 24자), 댓글 500개면 약 65KB 차이(r1). 한도 끝 500개 2.37MB(r10)에 견주면 3% 남짓이라 바꾸지 않는다 — 11장 Q4

### 3.2 풀기와 고아 판정 — `resolveCommentAnchor`

돌려주는 값이 `null` 이면 **고아**다(개요 2.3). 다음 중 하나면 `null`:

1. `anchor === null` (되살릴 때 자리를 못 찾은 첫 댓글, 또는 답글)
2. `readCommentAnchor(anchor) === null` — yjs 에 넘기지 않는다(r5: 넘기면 던지거나 문서 끝으로 풀린다)
3. 시작·끝 중 하나라도 `createAbsolutePositionFromRelativePosition` 이 `null`(없는 항목, c7·r5)
4. 풀린 위치의 `type` 이 인자로 받은 `ytext` 와 다름(`title` 등, c7·r5)
5. `toAnchorRange(start.index, end.index) === null` — 시작 ≥ 끝(통째로 지워짐·잘라 붙임, c1·r3)

- 풀기는 `createAbsolutePositionFromRelativePosition(rpos, doc)` 를 **세 번째 인자 없이**(`followUndoneDeletions` 기본 `true`) 부른다. 그래야 되돌리기로 살아난 글에 앵커가 돌아온다(c1·r3)
- 1~5 밖의 이유로 yjs 가 던지면(모양 검사를 통과했는데도) 잡아서 `null`. 이 함수는 **던지지 않는다** — 서버(F-502·F-503)가 남이 보낸 값으로 부른다
- `docComments.ts` 에 `toAnchorRange(from: number | null, to: number | null): AnchorRange | null` 를 둔다 — 둘 중 하나가 `null` 이거나 `from >= to` 면 `null`. F-504 가 CM6 매핑으로 따라간 위치에도 **같은 고아 규칙**을 쓰도록(개요 2.3 "순수 함수 하나가 정하고 편집기·서버·레일이 같이 쓴다")

### 3.3 한꺼번에 풀기 — `resolveCommentAnchors`

- `entries` 중 **첫 댓글(`parent === null`)만** 결과 `Map` 에 넣는다(키 = 첫 댓글 id, 값 = `resolveCommentAnchor` 결과). 답글은 넣지 않는다
- **공개 API 만 쓴다.** 앵커마다 `resolveCommentAnchor` 를 부르는 것과 결과가 같아야 한다(A14)
- 비용(r6): 비용은 Y.Text 항목 수를 따른다. 새로 심은 Doc(로컬 문서 마운트·DO 씨앗 직후)은 1MB·500개도 0.11ms. 오래 편집해 항목 8,000개쯤으로 쪼개진 Doc 은 500개 약 175~181ms
- 이 비용을 어디서 치르나 — 이 함수를 부르는 자리는 개요가 이미 줄여 두었다: F-504 는 문서를 열 때·`comments` 가 바뀔 때(**바뀐 키만** 풀면 된다 — 한꺼번에 풀기는 열 때 한 번)·빈 범위가 된 앵커만(개요 4.2), F-502 는 방이 빌 때·알람 flush 때(개요 3.3). 편집 트랜잭션마다 부르는 자리는 없다
- 한 번 걸어 항목 → 위치 표를 만드는 방식(개요 c4 1.48ms, `Y.Text._start`·`Item.right` 를 걷는다)은 **쓰지 않는다**. 되돌리기로 살아난 항목을 따라가는 규칙(`followRedone`)까지 똑같이 옮겨야 결과가 공개 API 와 같아지고, 밑줄 필드는 yjs 판이 바뀌면 깨질 수 있다. F-502 가 방이 빌 때의 비용을 재서 줄여야 하면 그 명세가 이 함수의 내부만 바꾼다(시그니처·결과는 그대로, A14 가 같음을 지킨다)

## 4. 기록과 다시 붙이기 — `src/lib/commentAnchor.ts`

```ts
export function toCommentRecord(id: string, entry: CommentEntry, text: string, range: AnchorRange | null): CommentRecord
export function reanchor(text: string, record: CommentRecord): AnchorRange | null
export function restoreCommentEntries(
  ytext: Y.Text,
  records: readonly CommentRecord[],
  importer?: { id: string; email: string },
): { entries: [string, CommentEntry][]; orphaned: number }
```

### 4.1 `toCommentRecord` — 앵커 → 인용문·앞뒤 문맥·위치

`text` 는 `ytext.toString()`, `range` 는 호출자가 이미 가진 범위다(`resolveCommentAnchor` 결과, 또는 F-504 가 CM6 매핑으로 따라간 위치). **이 함수는 yjs 를 부르지 않는다** — L2 로컬 저장(F-508)은 본문을 저장할 때마다 기록을 만드는데, 그때마다 앵커를 공개 API 로 풀면 쪼개진 Doc 에서 수백 ms 가 든다(r6). 편집기가 이미 아는 위치를 넘겨받는다

| 항목 | `quote` | `prefix` | `suffix` | `anchorFrom` | `anchorLength` |
| --- | --- | --- | --- | --- | --- |
| 답글 | `''` | `''` | `''` | `null` | `null` |
| 첫 댓글, `range` 있음 | `commentQuote(text.slice(from, to))` (7.2) | `from` 앞 최대 32자 | `to` 뒤 최대 32자 | `from` | `to − from` |
| 첫 댓글, `range === null`(고아) | `entry.quote` 그대로 | `''` | `''` | `null` | `null` |

- `prefix` 는 `text.slice(max(0, from − 32), from)`, `suffix` 는 `text.slice(to, to + 32)`. **서로게이트 짝을 자르지 않는다**: `prefix` 의 첫 글자가 낮은 서로게이트(U+DC00–DFFF)면 한 자 빼고, `suffix` 의 마지막 글자가 높은 서로게이트(U+D800–DBFF)면 한 자 뺀다. 짝 없는 서로게이트는 D1 텍스트(UTF-8)에 들어가면 다른 글자로 바뀌어 되살릴 때 맞지 않는다
- 나머지 필드: `authorId`/`authorEmail` ← `entry.author`, `resolvedAt`/`resolvedById`/`resolvedBy` ← `entry.resolved`(없으면 셋 다 `null`), `body`·`mentions`·`createdAt`·`parent` 그대로
- 결과는 늘 `parseCommentRecords([…])` 를 통과한다(범위가 문서 안이고 `entry` 가 `validateCommentEntry` 를 통과했다면. A7 이 단언)
- 자리가 있는 첫 댓글의 기록 `quote` 는 **지금 본문**에서 다시 자른 값이다. 달 때의 `entry.quote` 와 다를 수 있다(그 사이 범위 안을 고쳤다면). 되살린 항목의 `quote` 는 기록의 값이 된다(4.4) — 레일의 고아 표시가 "마지막으로 기록할 때의 글" 을 보여 준다

### 4.2 `reanchor` — 다시 찾기 (개요 3.4 의 세 단계를 닫는다)

순수 문자열 함수. yjs 를 부르지 않는다. 결과 `null` 은 고아

**먼저 `null` 로 끝내는 경우**: `parent !== null`(답글), 또는 `anchorFrom`·`anchorLength` 중 하나라도 `null`(이미 고아였던 기록). 고아 기록은 **찾으러 가지 않는다** — 지워진 글과 같은 글이 다른 곳에 있으면 엉뚱한 곳에 붙고, 로컬 문서는 마운트마다 이 함수를 부르므로 한번 고아가 된 댓글이 다시 마운트할 때 저절로 되살아나는 일이 생긴다

**비교 대상(`head`)과 후보**:

- `anchorLength ≤ COMMENT_QUOTE_MAX` 이면 `head = quote`. `anchorLength > COMMENT_QUOTE_MAX` 이면 `head = quote` 에서 끝의 `'…'` 를 뗀 것(인용문 앞부분)
- 후보 = `text.startsWith(head, p)` 이고 `p + anchorLength ≤ text.length` 인 위치 `p`. 되찾은 범위는 `{ from: p, to: p + anchorLength }`
- `h = min(max(anchorFrom, 0), text.length)` (힌트)

**고르는 규칙**:

1. `h` 가 후보면 **바로 `h`**. 앞뒤 문맥은 보지 않는다(개요 3.4 ①). L2 로컬 마운트·이관은 본문과 기록이 같은 시점이라 여기서 끝난다(r7 "힌트가 맞을 때")
2. 아니면 후보를 **`|p − h|` 가 작은 순**으로 본다. 거리가 같으면 `p` 가 작은 쪽이 먼저. 후보마다 점수 = (`p` 바로 앞에서 거꾸로 `prefix` 끝과 같은 글자 수) + (`p + anchorLength` 부터 `suffix` 앞과 같은 글자 수). **점수가 가장 높은 후보**를 고르고, 점수가 같으면 먼저 본 후보(= 가까운 쪽)를 둔다
   - 점수가 `prefix.length + suffix.length`(더 맞을 수 없음)에 이르면 거기서 멈춘다. 가까운 순으로 보므로 멈춘 자리가 규칙대로의 답이다
   - 후보를 `REANCHOR_CANDIDATES_MAX`(1,000)개 본 뒤에는 멈추고 그때까지의 최고를 고른다 — **힌트에 가까운 1,000개** 안에서 고른다. 개요 3.4 의 "최대 1,000번 찾아" 를 이렇게 읽는다(앞에서부터 1,000개를 보면 힌트에서 먼 쪽만 볼 수 있다)
3. 후보가 없으면 `null`

- 되찾은 범위가 원래 `quote` 를 끝까지 확인하지는 않는다 — 200자를 넘는 앵커는 앞 199자(또는 198자)와 길이만 맞춘다. 앞뒤 문맥 점수가 나머지를 거든다
- 가까운 순으로 보는 방법(앞으로 `indexOf`·뒤로 `lastIndexOf` 를 번갈아, 뒤쪽은 앞쪽 후보까지의 거리 안에서만 찾기 등)은 구현이 정한다. **판정은 결과로만 한다**(A8~A12)

**비용** (r7·r8, node, 7회 중앙값): 힌트가 맞으면 1MB·500개 0.1ms 이하. 힌트가 어긋나도 1MB·500개 0.2ms. 가장 무거운 경우는 **인용문이 본문에 하나도 없어 모두 고아**일 때로, 앞뒤로 본문 전체를 한 번씩 훑어 1MB·500개 약 117~123ms, 100KB·500개 12ms. 후보 상한까지 도는 되풀이 글은 1MB·500개 31ms

**결론 — 개요 2.5 한도(본문 1MB·문서당 500개) 안에서 문제없다.** 부르는 자리는 셋이고 모두 드물다: DO 씨앗 가지(저장소를 잃었을 때, 개요 3.4), 이관(한 문서 한 번, 개요 4.6), 로컬 문서 마운트(힌트가 맞아 0.1ms 이하). 최악 123ms 는 "DO 저장소를 잃은 1MB 문서에서 댓글 500개가 모두 지워진 글에 달려 있던" 경우다. 편집 중에 부르는 자리는 없다

### 4.3 `restoreCommentEntries` — 기록에서 `CommentEntry` 되살리기

F-502(DO 씨앗 가지 복원), F-503(이관 `importComments`), F-508(로컬 마운트)이 같이 부른다. **`Y.Map` 에 쓰지 않는다** — 돌려준 `entries` 를 호출자가 자기 트랜잭션·origin 으로 `getMap(Y_COMMENTS_NAME)` 에 넣는다(origin 은 개요 3.4·3.1 이 호출자마다 정했다)

- `records` 는 `parseCommentRecords` 를 통과했거나 D1 복사본에서 읽은 것이라고 본다. 다만 부모가 `records` 안에 없는 답글은 **건너뛴다**(`entries` 에 넣지 않고 `orphaned` 에도 세지 않는다)
- 본문은 `ytext.toString()` 한 번
- 첫 댓글: `range = reanchor(text, record)` → `range` 가 있으면 `anchor = createCommentAnchor(ytext, range.from, range.to)`, 없으면 `anchor = null` 이고 `orphaned += 1`. `quote = record.quote`
- 답글: `anchor = null`, `quote = ''`
- `importer` 가 **있으면**(이관): `author = importer`, `resolved` 가 있으면 `by = importer`, `mentions = []`
- `importer` 가 **없으면**(복원·로컬): `author` 는 `authorId`·`authorEmail` 이 둘 다 문자열이면 그 둘, 아니면 `{ id: null, email: null }`. `resolved.by` 도 `resolvedById`·`resolvedBy` 로 같은 규칙. `mentions` 는 기록 그대로
- `v: 1`, `body`·`createdAt`·`parent` 그대로, `resolved.at = resolvedAt`
- 돌려주는 `entries` 는 `records` 순서, 키는 기록의 `id`. 모든 항목이 `validateCommentEntry` 를 통과한다(A13 이 단언)

## 5. 권한 — `commentAllowed` (`docComments.ts`)

```ts
export type CommentActor =
  | { kind: 'server'; userId: string; role: 'owner' | 'edit' | 'view'; blocked: boolean }
  | { kind: 'local'; canEdit: boolean }
export type CommentAction = 'add' | 'reply' | 'resolve' | 'delete'
export function commentAllowed(actor: CommentActor, action: CommentAction, target?: CommentEntry): boolean
```

- `role` 은 이 문서에 대한 역할(`resolveDocAccess` 결과, 소유자는 `'owner'`). `blocked` 는 F-2028 이 쓰기를 막은 계정. `local.canEdit` 은 그 탭이 편집권(F-296 `tabSync` 클레임)을 가졌는지
- "내 것" = `target.author.id !== null && target.author.id === actor.userId`. **이메일로 비교하지 않는다**(이메일은 바뀔 수 있다)

| 행위자 | `add` | `reply` | `resolve` | `delete` 내 것 | `delete` 남의 것 | `delete` `target` 없음 |
| --- | --- | --- | --- | --- | --- | --- |
| server `owner`, 막히지 않음 | 참 | 참 | 참 | 참 | 참 | 거짓 |
| server `edit`, 막히지 않음 | 참 | 참 | 참 | 참 | 거짓 | 거짓 |
| server `view`, 막히지 않음 | 참 | 참 | 참 | 참 | 거짓 | 거짓 |
| server, `blocked: true` (역할 무관) | 거짓 | 거짓 | 거짓 | 거짓 | 거짓 | 거짓 |
| local, `canEdit: true` | 참 | 참 | 참 | 참 (작성자 `나`) | 참 | 거짓 |
| local, `canEdit: false` | 거짓 | 거짓 | 거짓 | 거짓 | 거짓 | 거짓 |

- `add`·`reply`·`resolve` 는 `target` 을 보지 않는다(해결은 어느 스레드든 — 개요 2.4·10장 Q7)
- `delete` 는 답글이든 스레드(첫 댓글)든 규칙이 같다 — "그 항목의 작성자, 문서 소유자"(개요 2.4). 스레드를 지울 때 답글이 함께 지워지는 것은 호출자가 한다
- local 행위자가 `author.id` 가 문자열인 항목(서버 항목)을 지우려 하는 경우는 생기지 않는다(로컬 문서의 항목은 모두 로컬 작성자) — 그래도 표대로 `canEdit` 이면 참
- 서버 사후 검사(개요 3.2)의 "`resolved` 밖 필드가 바뀜 → 되돌림"·"작성자 다시 도장" 은 권한이 아니라 F-502 의 비교 규칙이다. 이 함수는 "그 동작을 할 수 있는 사람인가" 만 답한다

## 6. 스레드·멘션·한도 (`docComments.ts`)

### 6.1 멘션 파싱

```ts
export function parseMentions(body: string): string[]
export function finalizeMentions(body: string, picked: readonly string[]): string[]
```

**멘션 한 개의 모양**: `@` + 이메일. 이메일 = 로컬 부분 `[A-Za-z0-9._%+-]` 1자 이상 + `@` + 도메인 라벨 `[A-Za-z0-9-]` 1자 이상을 `.` 으로 둘 이상 이은 것(점 하나 이상 필수). 전체 이메일 길이 ≤ `COMMENT_EMAIL_MAX`

| 경계 | 규칙 | 예 → `parseMentions` |
| --- | --- | --- |
| 앞 | 첫 `@` 는 문자열 처음이거나, 바로 앞 글자가 `[A-Za-z0-9._%+\-@]` 가 **아니어야** 한다 | `a@kim@x.com` → `[]` (보통 이메일 뒤에 붙은 것), `(@kim@x.com)` → `['kim@x.com']`, `메일@kim@x.com` → `['kim@x.com']` |
| 뒤 | 도메인은 가능한 한 길게 먹되 `.` 뒤에 라벨 글자가 없으면 그 `.` 은 넣지 않는다. 이메일 바로 뒤 글자가 `[A-Za-z0-9_%+\-@]` 면 멘션이 아니다 | `@kim@x.com.` → `['kim@x.com']`, `@kim@x.com님` → `['kim@x.com']`, `@kim@x.com,@lee@y.org` → 둘, `@kim@x.com_z` → `[]`, `@kim@x` → `[]` (점 없음) |
| 대소문자 | 결과는 소문자로. 중복은 처음 나온 것 하나 | `@Kim@X.com @kim@x.com` → `['kim@x.com']` |
| 겹친 `@` | `@@kim@x.com` → `[]` (둘째 `@` 는 앞이 `@`) | |
| 코드 표기 | **가리지 않는다.** `` `@kim@x.com` `` 도 멘션이다 | 11장 Q3 |
| 줄 | 줄바꿈은 그냥 경계 글자다 | `\n@kim@x.com` → 하나 |

- 결과 순서 = 본문에 처음 나온 순서. 개수 제한 없이 다 돌려준다
- 코드 표기를 가리지 않는 이유: 댓글 본문은 **평문**이다(개요 1.2 "마크다운 렌더링 없음, 줄바꿈만"). 역따옴표가 코드를 만들지 않는다. 그리고 멘션은 후보 목록에서 **고른 것만** `mentions` 에 들어가므로(`finalizeMentions`), 역따옴표 안에 이메일을 적었다고 알림이 가지는 않는다
- 로컬 부분에 RFC 가 허용하는 `'`·`!`·`#` 같은 글자가 든 이메일은 멘션으로 잡히지 않는다(후보에서 골라도 `finalizeMentions` 가 뺀다 — 알림 없이 평문으로 남는다). Google·GitHub 로그인 이메일에서 드문 모양이라 좁은 글자 집합을 둔다

**`finalizeMentions(body, picked)`** — 보낼 때 화면(F-505·F-507)이 부른다. `picked` 를 소문자로 바꾼 것 중 `parseMentions(body)` 에 있는 것만, **본문에 처음 나온 순서**로, 앞에서 `MENTIONS_PER_COMMENT_MAX`(10)개까지. 10개를 넘는 멘션은 조용히 뺀다(평문 `@…` 로 남는다). 후보 목록에서 10개 넘게 고르지 못하게 하는 것은 F-507 의 화면 몫이다

- `validateCommentEntry` 8번이 "`mentions` ⊆ `parseMentions(body)`" 를 요구하므로, 서버(F-502 알림)는 `entry.mentions` 를 그대로 믿고 다시 파싱하지 않아도 된다

### 6.2 스레드 묶기·정렬

```ts
export function groupCommentThreads(entries: Iterable<readonly [string, unknown]>): {
  threads: CommentThread[]
  strays: string[]
  invalid: string[]
}
export function sortThreadsByPosition(
  threads: readonly CommentThread[],
  ranges: ReadonlyMap<string, AnchorRange | null>,
): { anchored: CommentThread[]; orphans: CommentThread[] }
export function toAnchorRange(from: number | null, to: number | null): AnchorRange | null
```

- `groupCommentThreads` 는 `Y.Map` 의 `entries()` 를 그대로 받는다(값이 `unknown`). 서버 사후 검사(F-502)와 레일(F-505)이 같은 판정을 쓴다
  - `invalid`: 키가 `isCommentId` 가 아니거나 값이 `validateCommentEntry` 를 통과하지 못한 키
  - `strays`: 올바른 답글인데 `parent` 가 유효한 첫 댓글이 아닌 것 — 부모 없음, 부모가 `invalid`, 부모가 답글(답글의 답글), `parent === 자기 id`. 서버는 이것들을 지운다(개요 3.2 "부모 없는 답글"·"답글의 답글"), 화면은 보이지 않는다
  - `threads`: 첫 댓글마다 하나. 스레드 순서와 스레드 안 답글 순서는 둘 다 `createdAt` 오름차순, 같으면 id 사전순(`<` 비교)
  - `invalid`·`strays` 는 키 사전순
- `sortThreadsByPosition`: `ranges` 는 첫 댓글 id → 범위. 값이 범위면 `anchored`, `null` 이거나 키가 없으면 `orphans`(개요 2.3 "본문이 지워진 댓글" 묶음). `anchored` 는 `from` 오름차순 → `to` 오름차순 → `createdAt` → id. `orphans` 는 `createdAt` → id
- 해결 여부로 가르거나 거르지 않는다 — `해결된 댓글 보기`(개요 4.3)는 F-505 가 결과에서 거른다

### 6.3 한도 — `checkCommentCapacity`

```ts
export type CommentCapacityError = 'doc_full' | 'thread_full'
export type CommentRejectReason = 'invalid' | 'too_long' | 'too_many'
export function checkCommentCapacity(threads: readonly CommentThread[], parent: string | null): CommentCapacityError | null
export function commentRejectReason(error: CommentShapeError | CommentCapacityError): CommentRejectReason
```

- `threads` 는 **새 항목을 넣기 전** 상태(`groupCommentThreads` 결과). 지금 개수 = 스레드 수 + 모든 답글 수(`invalid`·`strays` 는 세지 않는다)
- 지금 개수 + 1 > `COMMENTS_PER_DOC_MAX` → `doc_full` (먼저 본다)
- `parent` 가 있고 그 스레드의 답글 수 + 1 > `REPLIES_PER_THREAD_MAX` → `thread_full`
- `parent` 가 `threads` 에 없으면 `null` — "부모 없음" 은 한도가 아니라 F-503 의 `not_found` 다
- 서버 사후 검사(F-502)는 새 항목을 뺀 상태로 묶어서 부른다
- `commentRejectReason` 은 개요 3.1 `CommentOpReply` 의 `reason` 중 모양·한도 몫을 옮긴다: `body_too_long` → `too_long`, `doc_full`·`thread_full` → `too_many`, 나머지 전부 → `invalid`. `forbidden`·`not_found`·`rate_limited` 는 F-503 이 직접 정한다. 화면 문구는 `too_long` → C2, `too_many` → C3 (개요 5.1)

## 7. 인용문·짧은 해시 (`docComments.ts`)

### 7.1 짧은 해시 — `shortHash`

```ts
export function shortHash(input: string): string
export function commentSig(entry: CommentEntry): string
export function recordAnchorSig(record: CommentRecord): string
```

**결정: 동기 순수 함수, FNV-1a 64비트, 입력은 `TextEncoder` 로 만든 UTF-8 바이트, 출력은 소문자 16진수 16자(앞 0 채움).** `crypto.subtle` 은 쓰지 않는다

| 안 | 판단 |
| --- | --- |
| **FNV-1a 64 (UTF-8)** | **채택.** 표준 알고리즘이라 공개 시험값으로 세 환경이 같은지 판정할 수 있다. `TextEncoder` 는 Workers·브라우저·Node 모두 동기로 있다. 16비트 칸 구현으로 한글 1,000자 기록 500개 6.7ms(r9) |
| FNV-1a 32 (`peers.ts` `peerColorIndex` 와 같은 것) | 안 씀. 8자로 짧지만 충돌 확률이 비교마다 약 2⁻³², 64비트는 2⁻⁶⁴. `sig` 가 우연히 같으면 **D1 복사본이 그 변경을 영영 놓친다**(다음 변경 전까지) — 길이 8자를 아낄 이유가 없다 |
| `crypto.subtle.digest('SHA-256')` | 안 씀. 비동기라 `commentSig` 를 부르는 스냅숏 파생·기록 만들기가 모두 `await` 를 타야 한다. 위조 방지가 목적이 아니다(비교 대상은 서버 자신이 전에 쓴 값) |
| `BigInt` 로 FNV-1a 64 | 결과는 같지만 13배 느리다(r9 85.7ms) — 구현이 고를 일이지만 A 기준 시험값은 같다 |

- **시험값(계약)** — 세 환경이 같은지 이것으로 판정한다(r9 에서 `BigInt` 참조 구현과 16비트 칸 구현이 모두 같은 값을 냈다):

| 입력 | 출력 |
| --- | --- |
| `''` | `cbf29ce484222325` |
| `'a'` | `af63dc4c8601ec8c` |
| `'foobar'` | `85944171f73967e8` |
| `'댓글'` | `c8f9ec798637a89b` |

- 짝 없는 서로게이트는 `TextEncoder` 가 U+FFFD 로 바꾸므로 서로 다른 짝 없는 서로게이트가 같은 해시가 된다. 댓글 필드는 정상 문자열이라 문제 삼지 않는다
- 쓰는 곳: D1 `doc_comments.sig`·`anchor_sig`(개요 3.3) — 변경 감지용. **알림 중복은 이 해시로 가리지 않는다** — 개요 3.5 대로 `notifications` 의 `UNIQUE (recipient_email, comment_id, kind)` 가 막는다

**`commentSig(entry)`** = `shortHash(JSON.stringify([v, parent, body, mentions, author.id, author.email, createdAt, resolved?.at ?? null, resolved?.by.id ?? null, resolved?.by.email ?? null]))` — 배열의 순서가 계약이다. `anchor`·`quote` 는 넣지 않는다(개요 3.3 "앵커 밖 필드")

**`recordAnchorSig(record)`** = `shortHash(JSON.stringify([quote, prefix, suffix, anchorLength]))` — `anchorFrom` 은 넣지 않는다(개요 3.3 "위치 제외" — 위쪽을 한 글자 칠 때마다 아래 행이 다시 쓰이지 않게). `anchorLength` 는 2.4 에서 새로 든 필드라 넣는다

### 7.2 인용문 자르기 — `commentQuote`

```ts
export function commentQuote(text: string): string
```

- 길이 ≤ `COMMENT_QUOTE_MAX` 이면 그대로
- 넘으면 앞 199자 + `'…'`(U+2026). 199번째 글자(인덱스 198)가 높은 서로게이트면 앞 198자 + `'…'`(짝을 자르지 않는다) — 결과 길이 200 또는 199
- 줄바꿈·공백은 바꾸지 않는다(한 줄로 보이는 것은 화면 CSS 몫)
- `createCommentAnchor` 로 새 댓글을 달 때 `entry.quote` 도 이 함수로 만든다(F-505). 서버가 `comment-add` 에서 `quote` 를 자를 때도 같다(개요 3.1 ④, F-503)

## 11. 열린 질문 / 사람 결정 필요

### Q1. 파일 이름 — **사람 결정 필요 (승인된 개요와 다름). 기본값: 새 파일 `src/lib/docComments.ts` + `commentAnchor.ts`, `comments.ts` 는 그대로**

- 이유는 1.1: 기존 `comments.ts` 는 `주석` 문법 제거(`stripComments`, importer 7곳, 공유·공개 경로)이고 개요 5.1 이 `주석` 과 `댓글` 을 갈라 두었다. `yjs` 가 공유 경로에 딸려 들어갈 여지를 없앤다. F-2019 구현과 겹치지 않는다
- **다른 안 A — 개요대로 `comments.ts` 에 섞기**: 파일 하나가 두 뜻을 갖는다. 10장의 F-500 갱신 첫 두 줄이 없어진다. `comments.ts` 에 `yjs` 를 import 하지 않도록 앵커 쪽은 어차피 `commentAnchor.ts` 로 가야 한다
- **다른 안 B — 기존 것을 `markdownComments.ts` 로 옮기고 `comments.ts` 를 댓글에**: importer 7곳을 고친다(worker 둘 포함). F-2019 가 읽는 파일이 옮겨진다. 이 명세의 소유 표가 7곳으로 커진다

### Q2. `CommentRecord` 필드 셋·D1 열 둘 추가 — **사람 결정 필요 (승인된 계약을 넓힘). 기본값: 더한다**

- 2.4 표: `authorId` 가 없으면 복원한 댓글의 작성자가 자기 댓글을 못 지운다. `resolvedById` 가 없으면 해결 표시가 타입을 채우지 못한다. `anchorLength` 가 없으면 200자 넘는 앵커를 되살릴 때 끝을 모른다
- F-502 는 아직 쓰지 않았고 `0012` 마이그레이션도 없다 — 지금 더하면 바꿀 코드가 없다
- **다른 안 — 열을 더하지 않기**: `authorId` 는 D1 `author_id` 가 이미 있어 F-502 가 행에서 직접 채울 수 있다(기록 타입만 다름). `resolvedById` 대신 되살린 `resolved.by` 를 `{ id: null, email: null }` 로 두면 화면에 `해결함`(해결한 사람 이메일 없이)으로 보인다. `anchorLength` 대신 **앵커 범위를 200자 이하로 제한**하면(더 긴 선택은 앞 200자에만 댓글) 인용문이 곧 범위다 — 대신 긴 문단 전체에 다는 댓글이 앞부분만 칠해진다(F-504·F-505 규칙이 는다)

### Q3. 멘션이 역따옴표 안에서도 잡힘 — **기본값: 가리지 않는다**

- 6.1: 댓글 본문은 평문이고, 멘션은 후보에서 고른 것만 남는다. 역따옴표 안이라도 고르지 않았으면 알림이 없다
- 다른 안: `` `…` `` 안을 빼면 `parseMentions` 가 역따옴표 짝 규칙을 가져야 하고(`stripComments` 의 `findBacktickClose` 같은 것), 사용자가 역따옴표 안에서 후보를 골랐는데 알림이 안 가는 일이 생긴다

### Q4. 앵커 JSON 검사를 `readPeerCursor` 와 나눔 — **기본값: 나눈다(`readCommentAnchor` 가 더 좁다)**

- 개요 2.1 은 "F-307 커서와 같은 형식이라 검사 함수를 같이 쓴다" 고 적었다. 형식은 같다(둘 다 `relativePositionToJSON`). 다만 `readPeerCursor` 는 "객체인지" 만 보고, 그 값을 yjs 에 넘기면 던지거나(`{}`) 문서 끝으로 풀린다(`{tname:'content'}`) — r5. 커서는 화면에만 쓰여 괜찮지만 앵커는 서버가 저장하고 남의 값을 푼다
- 다른 안: `readPeerCursor` 를 좁히면 F-307 코드·테스트가 이 명세 소유로 들어온다. 이 명세는 커서를 건드리지 않는다
- 인코딩(JSON 대 바이트 + base64)은 개요 10장 기본값 2 가 정했고 바꾸지 않는다 — 500개에 약 65KB 차이(3.1)

### Q5. 댓글 500개 최악 크기가 개요 추정보다 큼 — **기본값: 한도는 그대로, 개요 근거 칸만 고친다**

- 개요 2.5 는 댓글 하나 3.3KB·500개 1.65MB 로 잡았다. 인용문 200자·멘션 10개까지 채우면 하나 4,731 B, 500개 약 2.37MB 다(r10). 문서를 열 때 모든 접속자가 받는 양이다
- 한도(개요 10장 Q8, 사용자 승인 범위)를 바꾸지 않는 이유: 이 값은 모든 필드를 한꺼번에 끝까지 채운 경우다. 개요 c5 의 보통 댓글(한글 200자)은 약 892 B 로 500개 약 450KB 다
- 다른 안: 문서당 한도를 350개로 내리면 최악이 약 1.66MB 로 개요의 추정과 맞는다. C3 문구의 숫자·상수가 바뀐다

### Q6. `resolveCommentAnchors` 를 공개 API 로만 — **기본값: 공개 API**

- 3.3: 쪼개진 1MB 문서 500개 약 175ms(r6)는 문서를 열 때·방이 빌 때 한 번 치른다. 내부 필드를 걷는 방식(1.48ms)은 yjs 판 올림과 `followRedone` 규칙 재현 위험이 있다
- 다른 안: F-501 에서 걷는 방식으로 구현하고 A9 로 결과가 같음을 지킨다. F-504 의 열 때 비용이 거의 0 이 된다. yjs 를 올릴 때마다 이 함수를 다시 봐야 한다
