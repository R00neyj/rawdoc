## 2. 결론 다섯 (프롬프트가 결론을 요구한 것)

### 2.1 폴더 옮기기의 단계와 "이어 옮기기" 상태

**단계** (서버 저장소. 로컬은 4.4 의 차이만)

1. **계획 세우기** — 저장소의 지금 목록(`list()`·`listFolders()`)으로 `planE2eeConvert` 가 단계 목록을 만든다(3.3). 대상 폴더 아래 전부(자신 포함)에서
   - 일반 폴더를 **깊이가 깊은 것부터** 차례로 놓고, 폴더마다 ① 그 폴더 **바로 아래** 일반 문서들의 `doc` 단계(사이드바 순서 — `updatedAt` 내림차순) ② 그 폴더의 `folder-on` 단계
   - 이미 금고인 문서·폴더는 계획에 넣지 않는다
2. **실행** — 단계를 하나씩, 앞 단계가 끝나야 다음으로. `doc` 단계 하나는 4.1 순서(첨부 암호 올리기 → 본문 id 바꾸기 → `PUT /api/docs/:id/e2ee` → 옛 첨부 `DELETE` → `md-yjs`·평문 캐시 첨부 지우기), `folder-on` 은 `PUT /api/folders/:id { e2ee: true }` 한 번
3. **끝** — 남은 첨부 지우기를 한 번 더 시도하고(4.1 ⑦) 끝 알림

**"이어 옮기기" 상태 — 따로 저장하지 않는다. 서버의 표지가 곧 진행 기록이다** (12장 Q1)

| 무엇 | 어디 | 모양 | 수명 |
| --- | --- | --- | --- |
| 어디까지 옮겼나 | **서버(와 그 캐시)의 표지 자체** — 문서 `e2eeKey`, 폴더 `e2ee` | 새 저장 없음. 다시 누르면 1번이 지금 목록으로 계획을 새로 세우고, 이미 금고인 것은 빠진다 | 영구(서버) |
| 올려 둔 암호 첨부 짝 | 페이지 메모리 — App 이 `ref` 로 든 `E2eeConvertMemory`(3.3) | `uploaded: Map<string, { id: string; ext: AttachmentExt }>` — 키 `"{방향}:{옛 첨부 id}"`, 값 새 첨부 | 페이지 수명. 같은 페이지에서 다시 누르면 다시 올리지 않고 쓴다 |
| 아직 못 지운 옛 첨부 | 같은 메모리 | `pendingDeletes: Array<{ id: string; ext: AttachmentExt }>` — `DELETE` 가 409 `in_use`·네트워크 실패·429 로 남긴 것 | 페이지 수명. 다음 실행의 처음과 끝에 다시 시도 |

- **왜 따로 저장하지 않나**: ① 다른 기기·다른 탭이 그 사이 같은 폴더를 옮기거나 뺄 수 있다 — 기기에 적어 둔 계획은 낡는다. 서버 표지는 낡지 않는다. "원본 하나를 두고 손으로 맞추는 사본을 두지 않는다" 는 불변조건의 태도와 같다 ② 서버의 폴더 규칙(금고 폴더는 바로 아래가 모두 금고일 때만 켜진다, F-401 5.2)이 계획을 다시 세워도 같은 순서를 강제한다 ③ 새로고침으로 잃는 것은 메모리 두 줄뿐이고, 그 결과는 서버 정리 Cron 이 치운다 — 아래
- **새로고침·탭 닫기로 메모리를 잃으면**: (가) 문서 `PUT` 이 성공한 뒤 옛 평문 첨부 `DELETE` 전에 끊겼다 → 그 평문 첨부는 이제 아무 문서도 참조하지 않으므로 F-402 정리 Cron(매일 18:00 UTC, 만든 지 24시간 지난 것)이 다음 실행에 지운다. 첨부는 보통 오래전에 만들어졌으므로 **최대 약 24시간**, 옮기기 직전 24시간 안에 올린 첨부면 최대 약 48시간 평문이 R2 에 더 남는다 (나) 첨부를 암호로 올린 뒤 `PUT` 전에 끊겼다 → 새 암호 첨부는 참조가 없어 Cron 이 24시간 뒤 지운다. 그 사이 300MB 한도에 봉투 크기만큼 잡힌다
- 한 페이지 안에서 멈춤 뒤 다시 누르면 (가)·(나) 둘 다 생기지 않는다 — 메모리가 살아 있다
- **진행 표시 `{n}/{total}`**: `total` 은 그 실행의 계획에 든 `doc` 단계 수, `n` 은 그 실행에서 끝낸 수. 이어 옮기기는 남은 것으로 새로 센다(앞 실행에서 옮긴 수를 더하지 않는다) — 기록을 두지 않는 결과다

### 2.2 429 를 받을 때 — 미리 늦추고, 받으면 기다린다

**미리 늦춘다: 서버로 가는 쓰기 요청 사이 최소 600ms** (12장 Q2)

```ts
// src/e2ee/convert.ts
export const E2EE_CONVERT_WRITE_GAP_MS = 600
export const E2EE_CONVERT_MAX_RATE_RETRIES = 5
```

- 규칙: 옮기기·빼기가 보내는 **쓰기 요청**(`PUT /api/docs/:id/e2ee`, `PUT /api/folders/:id`, `PUT /api/attachments/:idext`, `DELETE /api/attachments/:idext`)은 앞 쓰기 요청을 **보낸 시각**에서 600ms 가 지나기 전에 보내지 않는다. 읽기(`GET` — 첨부 받기, 문서 새로 읽기)는 늦추지 않는다. 로컬 금고(`idb`)는 서버가 없으므로 늦추지 않는다
- 600ms = 분당 100번. 한도 120 에서 **20을 남긴다** — 옮기는 동안에도 열린 금고 문서의 저장(문서당 10초 간격 = 분당 최대 6, F-405 5.2)·다른 탭의 저장이 429 를 맞지 않게
- 근거(c3): 고정 창 모형에서 1,000개(쓰기 1,010번)를 "429 받으면 60초 쉬기" 로만 하면 요청 지연 0.2~0.3초에서 429 를 5~6번 맞고 시간은 9.4~10.1분, 600ms 간격이면 **10.1분에 429 0번**. 시간은 거의 같고, 429 를 맞으면 같은 순간 outbox 의 보통 저장도 429 를 맞아 알림 `요청이 많아 잠시 쉬었다가 이어서 저장합니다.`(F-2030 L1)가 뜬다 — 늦추는 쪽이 사용자에게 조용하다

**받으면 기다린다** — 원격 한도는 위치별 근사라(c2) 늦춰도 429 가 올 수 있다

| 받은 것 | 처리 | 진행 표시 |
| --- | --- | --- |
| 429 `scope: 'minute'` (`ApiError`·`AttachmentApiError` 의 `kind 'rate_limited'`) | `retryAfter` 초(`parseRetryAfter` 가 이미 1~86,400 으로 자른 값)를 기다린 뒤 **같은 요청을 다시** 보낸다. 같은 요청이 429 를 연달아 `E2EE_CONVERT_MAX_RATE_RETRIES`(5)번 받으면 멈춘다(이유 `rate-limited`) | 진행 알림을 E35 로 바꾸고 1초마다 남은 초를 줄인다. 다시 보내면 E8 로 |
| 429 `scope: 'day'` | 기다리지 않고 **멈춘다**(이유 `day-limit`). 다시 열 수 있는 시각 = `nextUtcMidnight(now)` | 멈춤 알림 E8 + 이유 문장 R2 |

- 기다리는 동안 `멈추기`(진행 알림의 버튼)를 누르면 곧바로 멈춘다 — 기다림은 취소 신호를 보는 `sleep` 이다
- 기다림·늦춤의 시계와 `sleep` 은 실행기 의존으로 주입한다(단위 테스트가 실제로 60초를 기다리지 않게 — `serverStore` 의 `handlers.now` 와 같은 방식)
- 옮기기 도중 outbox 가 따로 429 를 맞는 것은 지금 규칙(F-2030 4.2) 그대로다. 옮기기는 outbox 를 거치지 않는다(5.2)

### 2.5 문서 1,000개 폴더를 옮기는 예상 시간

쓰기 수 `W = 문서 수 + 켤 폴더 수 + 2 × 바꿀 평문 첨부 수` (첨부마다 암호 올리기 1 + 옛 것 지우기 1). 읽기(`GET`)는 한도에 세지 않는다(`isWriteRoute` 가 `GET` 을 뺀다)

| 경우 (문서 1,000·폴더 10) | W | 600ms 간격, 요청 지연 ≤ 0.6초 | 요청 지연 1초 | 하루 5,000 |
| --- | --- | --- | --- | --- |
| 이미지 없음 | 1,010 | **약 10.1분** | 약 16.8분 | 안 닿음 |
| 이미지 평균 1장(서로 다름) | 3,010 | 약 30.1분 | 약 50.2분 | 안 닿음(그날 다른 쓰기가 1,990번 넘으면 닿음) |
| 이미지 평균 2장 | 5,010 | — | — | **닿는다** — 그날 쓰기가 0 이어도 약 4,990번째에서 멈춘다. 다음 UTC 자정(한국 시각 오전 9시) 뒤 다시 누르면 이어 간다 |

- 계산: `W × 0.6초`(c3 모형과 같다). 요청 지연이 0.6초를 넘으면 `W × 지연`. 암호화 비용(c1, 1,000개 약 0.4초)과 캐시에 없는 첨부 받기(`GET`, 이미지당 한 번)는 넣지 않았다 — 앞은 작고, 뒤는 이미지 크기·회선에 따라 다르다
- **실제 요청 지연은 재지 못했다.** `PUT /api/docs/:id/e2ee` 는 D1 batch + DO `purgeRoom` 을 응답 전에 기다리므로(c4) 보통 쓰기보다 느릴 수 있다. 그래서 0.6초·1초 두 줄로 적었다(15.2)
- 빼기도 같은 식이다(첨부마다 평문 올리기 1 + 암호 지우기 1)
- D-9·D-10 는 옮기기 전에 이 `W` 로 하루 남은 쓰기를 비교해 모자라면 한 줄 알린다(7.2 N3) — 막지는 않는다(12장 Q3)

## 4. 옮기기 순서 (규칙)

### 4.1 문서 하나를 금고로 — `doc` 단계 (`to-e2ee`)

실행기에 들어오기 **전**(App, 7.3): ⓐ 온라인(서버 저장소만 — 아니면 E5) ⓑ 크기(`planE2eeConvert` 의 `blocked` — 문서면 E6·E26, 폴더면 E33) ⓒ D-9 ⓓ `requestOpen()`(없으면 D-8, 잠겨 있으면 D-11. 닫으면 아무것도 안 한다) ⓔ 실행

`doc` 단계 하나 (번호가 계약이다):

1. **준비** — `noteActivity()`. 금고가 닫혔으면 멈춤(`locked`). 온라인이 아니면 멈춤(`offline`). `prepareDoc(id)` 가 `'blocked'` 면 멈춤(`pending-sync`). 서버 저장소면 `hasUnsyncedYjs(id)` 가 참이면 멈춤(`pending-sync`) — 이 기기에서 오프라인으로 편집해 아직 방에 못 올린 기록이 있다. 지금 옮기면 그 편집이 사라진다(c10)
2. **읽기** — 4.3 읽기 규칙. 이미 금고 문서면(다른 탭·기기가 먼저 옮김) 이 단계를 **끝난 것으로 치고** 다음으로(`n` 은 올린다)
3. **크기 다시 보기** — 읽은 평문이 `isPlainContentTooLarge` 면 멈춤(`too-large`), 첨부 줄이 1,000개 넘으면 멈춤(`too-large`). 계획 때는 캐시 본문으로 봤고 여기서는 새로 읽은 본문으로 본다
4. **첨부 바꾸기** — `attachmentLinksOf(본문)` 의 첨부마다, 메모리 `uploaded` 에 `"to-e2ee:{옛 id}"` 가 있으면 그것을 쓴다. 없으면
   1. `store.getAttachment(id, { ext })` — 없으면(`null`) **바꾸지 않고 둔다**(원래 없는 이미지. 본문 줄은 그대로)
   2. 받은 것이 이미 금고 첨부(`e2ee: true`)면 바꾸지 않는다(금고 이미지 줄을 복사해 넣은 경우 — F-402 3.2)
   3. 평문 바이트가 `isPlainAttachmentTooLarge`(5,242,811 B 초과)면 멈춤(`attachment-too-large`) — 봉투가 서버 상한 5,242,880 B 를 넘는다(F-406 k3)
   4. `store.putAttachmentNow({ blob, mime, ext, width, height, e2ee: true })` — 새 id·같은 확장자. 실패는 6장 표
   5. 메모리 `uploaded` 에 짝을 적는다
5. **본문 바꾸기** — `rewriteAttachmentLinks(본문, 짝)`. 제목은 바꾸지 않는다
6. **옮기기** — `store.setDocE2ee(id, { e2ee: true, title, content: 바꾼 본문 })`. `withE2ee` 가 새 문서 키·AAD `{id}` 로 봉투를 만들고 `attachmentRefs` 를 본문에서 만든다(5.1)
   - 409 `e2ee_doc` → 이미 금고(다른 곳에서 먼저) — 끝난 것으로 친다
   - 409 `conflict` → 6장 "충돌"
   - 그 밖 실패는 6장 표
   - 성공 응답의 `purged` 가 거짓이면 `purgeFailed` 를 1 올린다
7. **옛 첨부 지우기** — 4번에서 바꾼 옛 평문 첨부마다 `store.discardAttachment(id, ext)`(쓰기 간격 규칙을 지킨다). `deleted`·`not_found` 는 끝, `in_use` 와 네트워크·429 실패는 메모리 `pendingDeletes` 에 넣고 **멈추지 않는다** — 옮긴 문서는 이미 안전하고, 남은 평문은 정리 Cron 이 뒷받침한다(2.1)
8. **기기 흔적 지우기** — 서버 저장소면 `removeYjsRecord(id)`(실패는 기록만). 평문 캐시 첨부는 7번의 `discardAttachment` 가 `deleted`·`not_found` 일 때 함께 지운다(5.2)
9. `finishDoc(id, true)` → `n` +1 → 진행 알림

### 4.5 금고에서 빼기 — `doc` 단계 (`from-e2ee`)

4.1 과 같은 틀에 다음만 다르다

- 2번: 일반 문서면(다른 곳에서 먼저 뺌) 끝난 것으로 친다. 잠긴 모양(`e2ee: 'locked'`)이면 금고가 닫힌 것 — 멈춤(`locked`). 복호화 실패(F-405 4.1 손상)도 `locked` 모양으로 오므로, **금고가 열려 있는데 `locked` 모양이면 멈춤(`failed`)** — 풀 수 없는 문서를 평문으로 되돌릴 수 없다
- 3번 크기: 평문 상한은 일반 문서 1,000,000 B 라 금고 문서(≤ 749,971 B)는 늘 들어간다 — 보지 않는다
- 4번 첨부: 금고 첨부만 바꾼다(`e2ee: true` 인 것). `getAttachment(id, { ext })` 가 복호화한 평문을 `putAttachmentNow({ blob, mime, ext, width, height })`(`e2ee` 없음)로 새 id 에 올린다. 평문 첨부는 그대로 둔다. 메모리 키 `"from-e2ee:{옛 id}"`. 받지 못하면(`null` — 잠김·손상·없음) 금고가 열려 있으면 **바꾸지 않고 둔다**(깨진 이미지 줄로 남는다), 닫혀 있으면 멈춤(`locked`)
- 6번: `setDocE2ee(id, { e2ee: false, title, content })`. 409 `not_e2ee` → 끝난 것, 409 `e2ee_folder` → 멈춤(`failed` — 폴더 끄기가 앞 단계에서 됐어야 한다)
- 7번: 옛 **암호** 첨부를 지운다. `in_use` 는 다른 금고 문서의 `attachment_refs` 에 있는 것 — 남기는 것이 맞다
- 8번 없음

## 5. 저장소 층 규칙

### 5.1 `withE2ee` (`src/e2ee/e2eeStore.ts`)

| 메서드 | 규칙 |
| --- | --- |
| `setDocE2ee(id, { e2ee: true, title, content })` | MK 가 없으면 `E2eeStoreError('locked')`. 평문 본문 `isPlainContentTooLarge` → `'too-large'`, 첨부 id 1,000개 초과 → `'too-many-refs'`(F-405 4.2 와 같은 판정). `createDocKey(MK)` → **이 `id`** 를 AAD 로 제목·본문 봉투 → 아래 `setDocE2ee(id, { e2ee: true, title: 봉투, content: 봉투, e2eeKey, attachmentRefs: attachmentRefsOf(본문) })`. 반환 `doc` 은 F-405 4.1 읽기 변환을 거친 앱 층 `Doc`(`e2ee: 'open'`, 평문). 앱이 준 `e2eeKey`·`attachmentRefs` 는 버린다 |

| `setFolderE2ee`·`discardAttachment` | 그대로 넘긴다 |

### 5.2 서버 저장소 (`src/storage/serverStore.ts`)

**`setDocE2ee(id, input)`** (번호가 계약이다)

1. `navigator.onLine` 이 거짓이면 `ApiError('network')` 를 던진다
2. outbox 에 이 문서의 `createDoc`·`removeDoc` 이 있으면 `flushOutbox()` 한 번. 그래도 남았으면 `PendingSyncError` 를 던진다 — 서버에 아직 없는 문서는 옮길 수 없고, 지울 문서는 옮길 이유가 없다
3. 이 문서를 "옮기는 중" 집합에 넣는다 → `findSendable` 은 그 문서의 항목을 건너뛴다(금고 충돌 대기와 같은 방식, F-405 5.3). 진행 중인 보내기 회차가 있으면 끝나기를 기다린다 — 같은 문서의 `updateDoc` 이 옮기기와 겹쳐 나가지 않게
4. 캐시 행의 `version` 을 `baseVersion` 으로 `api.setDocE2ee(id, { e2eeKey, title, content, attachmentRefs, baseVersion })`
5. 성공: 캐시 행 = 응답(`purged` 를 뺀 것). 이 문서의 outbox `updateDoc` 항목을 **모두 지운다** — 그 내용은 방금 보낸 글에 이미 들어 있다(4.3 읽기 규칙이 캐시를 읽었다). 금고로 옮겼으면 그 문서의 마지막 응답 시각(F-405 5.2 10초 간격)을 지금으로 적는다. `{ doc: toDoc(응답), purged }` 를 돌려준다
6. 실패: 캐시를 바꾸지 않고 던진다(`ApiError` 그대로)
7. 끝(성공·실패 모두): "옮기는 중" 에서 빼고 보내기를 깨운다

```ts
// serverStore.ts — 옮기기 전에 서버로 보내야 할 것이 남았다
export class PendingSyncError extends Error {} // name 'pending_sync'
```

**`setFolderE2ee(id, on)`**: 온라인 확인 → 이 폴더의 outbox `createFolder` 가 남았으면 `flushOutbox()` 한 번, 그래도 남았으면 `PendingSyncError` → `api.updateFolder(id, { e2ee: on })` → 성공하면 캐시 폴더 행 = 응답. 실패는 던진다

**`putAttachmentNow(input)`**: 캐시에 같은 id 가 있으면 그것을 돌려준다(다시 올리기 안전). 없으면 id 를 정하고(주면 그것) 한도 사전 검사(`fetchUsage`, 지금 `putAttachment` 와 같은 식 — 넘으면 `QuotaExceededError`) → **`uploadAttachment(id, ext, blob, e2ee ? { width, height } : undefined)` 를 곧바로 부른다** → 성공하면 캐시 행(`uploaded: true`, `e2ee` 있으면 `e2ee: true`)을 쓰고 `{ id, ext }`. 실패하면 캐시에 쓰지 않고 `AttachmentApiError` 를 던진다. outbox `upload` 를 만들지 않는다. WebP 변환 없음

**`discardAttachment(id, ext)`**: `deleteAttachment(id, ext)`(F-406) → `deleted`·`not_found` 면 캐시 행도 지우고 그 값, `in_use` 면 캐시를 두고 `in_use`. 이 첨부의 outbox `upload` 가 남아 있으면 먼저 그 항목을 지운다 — 안 그러면 지운 뒤에 평문이 다시 올라간다. 던짐은 그대로

- `hasPendingChanges`·`refreshDocFromServer`·`flushOutbox` 는 지금 그대로 쓴다

### 5.3 로컬 저장소 (`src/storage/idbStore.ts`)

- `setDocE2ee(id, input)`: 행을 한 트랜잭션에서 읽어 `title`·`content` 를 받은 값으로, 옮기기면 `e2eeKey`·`attachmentRefs` 를 싣고 빼기면 **두 키를 행에서 없앤다**(일반 행은 키까지 지금과 같다 — F-405 3.1). `updatedAt` = 지금. 반환 `{ doc, purged: true }`. 행이 없으면 던진다
- `setFolderE2ee(id, on)`: 켜기는 바로 아래 문서가 모두 `e2eeKey` 를 갖고 바로 아래 폴더가 모두 `e2ee` 일 때만(아니면 `Error('e2ee_folder_not_ready')` — 실행기는 서버 409 와 같게 다룬다), 끄기는 부모 폴더가 `e2ee` 면 `Error('e2ee_folder')`. 켜면 `e2ee: true`, 끄면 키를 없앤다
- `putAttachmentNow`: `putAttachment` 와 같다(`idb` 는 원래 변환하지 않는다 — F-406 2.2). `e2ee: true` 면 행에 싣는다
- `discardAttachment(id, ext)`: 행이 없으면 `not_found`. 다른 문서 행 중 본문 `extractAttachmentRefs` 또는 `attachmentRefs` 에 id 가 있으면 `in_use`. 아니면 지우고 `deleted`

### 5.4 탭 신호 (`src/app/tabSync.ts`)

- `withTabBroadcast` 가 `setDocE2ee`·`setFolderE2ee` 를 **저장소에 있을 때만** 지금과 같은 `wrap` 으로 감싼다(성공하면 `docs-changed` 한 번). 없으면 키도 만들지 않는다 — `makeFakeStore` 로 도는 기존 U1~U5 가 그대로 통과한다
- `putAttachmentNow`·`discardAttachment` 는 감싸지 않는다(지금 첨부 메서드와 같다 — U4)
- 다른 탭은 `docs-changed` 로 목록을 다시 읽고, 지금 문서의 금고 여부가 바뀌었으면 7.5 규칙으로 다시 연다

- **충돌**: 이 탭의 지금 문서를 편집기 글로 옮기는 중(4.3 첫 줄)이거나 그 문서의 outbox 항목이 없으면 → `refreshDocFromServer(id)` 로 판을 새로 받고 **같은 글로** 다시 옮긴다(편집기 글은 그대로, 캐시에서 읽은 글이면 새로 읽은 글로). 한 문서에서 최대 3번. 넘거나 outbox 항목이 있던 문서면 멈춤(`conflict`) — 그 항목은 옮기는 중 표시가 풀리면 지금 규칙(F-207 충돌 사본)대로 나간다
  - 편집기 글로 옮기는 경우의 충돌은 대개 **이 탭이 실시간 세션을 닫자 DO 가 D1 에 쓴 것**이다(c8 `roomEmptied`) — 그 글은 편집기 글에 이미 들어 있다
- **`n`** 은 `doc` 단계가 끝날 때만(끝난 것으로 친 경우 포함) 올린다
- **끝 처리**(`done`·`stopped` 모두): 메모리 `pendingDeletes` 를 한 번씩 다시 `discardAttachment`(쓰기 간격 지킴, 429·실패는 그대로 남김). 멈춘 경우에도 한다 — 단 멈춤 이유가 `offline`·`day-limit`·`account-blocked`·`cancelled` 면 하지 않는다. 남은 `in_use` 수가 `keptAttachments`
- 실행 **처음**에도 `pendingDeletes` 를 한 번 시도한다(앞 실행에서 남긴 것)
- 쓰기 간격(2.2)은 이 표의 모든 쓰기 요청에 걸린다 — 다시 보내기·끝 처리 포함

**진행 표시** — 알림 띠(F-400 4.3 "진행은 알림 E8")

- 실행 동안 알림 하나를 **같은 자리에서 바꿔 가며** 둔다: 시작 때 E8/E34 `…중… 0/{total}`, `doc` 단계가 끝날 때마다 `n` 을 바꾸고, 기다리는 동안 E35 로 1초마다. 종류 `info` 지만 **4초 뒤 사라지지 않는다**(App 이 이 알림에만 자동 숨김을 끈다 — 7.3). 버튼 `멈추기`
- 다른 `warn`·`error` 알림이 자리를 차지하면 진행 알림은 그 동안 보이지 않는다(`pushNotice` 규칙 그대로 — c13). 옮기기는 계속된다. 다음 갱신이 `info` 라 `warn`·`error` 를 덮지 못하므로 사용자가 그 알림을 닫으면 다음 갱신 때 다시 보인다
- 끝나면 진행 알림을 걷고 끝 알림(E37·E38, 덧붙임 E39·E40) 또는 멈춤 알림(E8·E36 + 이유 문장)
- 문서 하나 옮기기도 같은 알림을 쓴다(`0/1` → 끝 알림). 로컬 문서 하나는 대개 한 순간에 끝나 진행 알림이 곧바로 끝 알림으로 바뀐다

- 금고 기능이 있을 때만(App 이 `SidebarProps.e2eeConvert` 를 줄 때 — 저장소가 `idb`·`server` 이고 `useE2ee` 가 `null` 이 아님) 항목을 만든다. 없으면 메뉴는 지금과 한 글자도 같다

```ts
// SidebarProps 에 더한다
e2eeConvert?: {
  online: boolean              // 서버 저장소의 온라인 여부. 로컬 저장소는 늘 true 로 준다
  busy: boolean                // 이 탭에서 옮기기·빼기가 진행 중
  onRequest(direction: E2eeConvertDirection, target: E2eeConvertTarget, name: string): void
  onUnavailable(reason: 'offline' | 'busy' | 'inside-e2ee-folder'): void
}
```

| 행 | 항목 (자리) | 보이는 조건 (`e2eeMenuForDoc`·`e2eeMenuForFolder`) |
| --- | --- | --- |
| 문서(트리·고정됨 묶음) | `금고로 옮기기…` (`IconLock`) — `폴더로 이동…` 다음, `삭제` 앞 | 일반 문서 |
| 〃 | `금고에서 빼기…` (`IconLockOpen`) — 같은 자리 | 금고 문서이고 폴더가 없거나 일반 폴더 안 → `enabled`. 금고 폴더 안 → `inside-e2ee-folder`(비활성, 누르면 E42) |
| 폴더 | `금고로 옮기기…` — `옵시디언 볼트로 내보내기` 다음, `삭제` 앞 | 폴더가 일반 폴더 |
| 〃 | `금고에서 빼기…` — 같은 자리(둘 다 보이면 `옮기기` 가 위) | 폴더가 금고이고 부모가 일반(또는 없음) — **가장 바깥 금고 폴더만**. 또는 폴더가 일반인데 아래(자손 전부)에 금고 문서·금고 폴더가 하나라도 있음(빼다 멈춘 폴더 이어 빼기, 2.3). 금고 폴더인데 부모도 금고면 **보이지 않는다** — 바깥 폴더에서 한다 |

- 여러 항목 선택 메뉴에는 넣지 않는다(10장)
- 비활성(`disabled: true`) — 각 항목을 이 순서로 판정: `busy` → E41, 서버인데 `online` 거짓 → E5, `inside-e2ee-folder` → E42. 눌리면 `onUnavailable(이유)` → App 이 알림
- 이름(`name`): 문서는 표시 제목(F-405 6.1 — 잠겼으면 `잠긴 문서`, 빈 제목이면 `제목 없음`), 폴더는 이름

### 7.3 App 흐름 (`App.tsx`)

1. 사이드바 `onRequest(방향, 대상, 이름)`
2. 진행 중이면 E41. 서버 저장소이고 오프라인이면 E5
3. 계획: `planE2eeConvert({ 방향, 대상, docs: store.list(), folders: store.listFolders() })`. 옮기기면 `blocked` 를 본다 — 문서 대상이 `tooLarge` 면 E6, `tooManyRefs` 면 E26(F-405), 폴더 대상에 하나라도 있으면 E33. 계획의 `docCount` 와 폴더 단계가 모두 0 이면(이미 다 옮겨짐) 끝 알림만
4. 빼기면 `requestOpen()` 먼저(2.3 1번) — 닫으면 끝. 연 뒤 계획을 다시 세운다(열리면 제목이 풀린다)
5. D-9/D-10. 취소면 끝. 옮기기이고 백업 안내를 보였으면 `setPref('md.e2eeBackupNotice', '1')`
6. 옮기기면 `requestOpen()`(D-8·D-11) — 닫으면 끝
7. 실행: 진행 알림을 띄우고(자동 숨김 없음, 버튼 `멈추기` → `AbortController.abort()`), `runE2eeConvert(계획, 의존, 진행 콜백)`. 의존의 `memory` 는 App `ref` 하나(페이지 수명), `noteActivity`·`isOpen` 은 `e2ee.keyring`, `hasUnsyncedYjs`·`removeYjsRecord` 는 서버 저장소일 때 `yjsStoreRef`(`unsyncedDocIds().includes(id)`·`removeDoc(id)`), `prepareDoc`·`finishDoc` 은 7.4
8. 끝: 진행 알림을 걷고 결과 알림, `resyncFromStore()`

- 실행 중에도 사이드바·편집은 된다(지금 옮기는 문서만 7.4 대로 잠깐 읽기 전용)
- 실행 중 탭을 닫거나 새로고침해도 막지 않는다(`beforeunload` 없음) — 서버 상태는 늘 "옮긴 문서는 금고, 못 옮긴 것은 일반" 이라 안전하고, 다시 누르면 이어 간다(2.1)

### 7.4 지금 문서 준비·다시 열기 (`prepareDoc`·`finishDoc`)

`prepareDoc(docId)` — `docId` 가 지금 열린 문서가 아니면 `null`. 맞으면:

1. 그 문서를 **읽기 전용**으로(옮기는 동안의 편집이 옮긴 글에 빠지지 않게). 편집권 알림 같은 새 알림은 띄우지 않는다
2. 대기 저장을 끝낸다 — `docSaver.flush()` 가 거짓이면 `'blocked'`(저장이 실패한 편집을 두고 옮기지 않는다)
3. 경로가 실시간이고 첫 동기화가 끝났으면: 편집기 글을 `{ text }` 로 잡고, **그 문서의 실시간 세션을 끝낸다**(소켓 닫기). 세션이 끝나면서 생기는 정지(`deleted`·`not-found`)에 `LIVE_NOTICE.gone` 을 띄우지 않는다(c9). 실시간인데 첫 동기화 전이면 `'blocked'`
4. 그 밖 경로면 `{}`(저장소에서 읽는다)

`finishDoc(docId, changed)`:

- 읽기 전용을 풀고, `changed` 면 **문서 열기 세션을 새로 시작**한다 — 경로 판정(F-405 6.3)이 새 금고 여부로 `e2ee` 또는 실시간을 고르고 편집기가 새 글로 뜬다. `changed` 가 거짓이면(멈춤) 세션을 새로 시작해 원래 경로로 돌아간다

**다른 탭·다른 문서**: `docs-changed`(5.4) 뒤 `resyncFromStore()` 가 받은 지금 문서의 금고 여부(`Doc.e2ee` 있음/없음)가 열린 세션의 경로와 맞지 않으면 문서 열기 세션을 새로 시작한다 — 다른 탭에서 옮긴 문서가 옛 실시간 세션(서버가 `4404` 로 닫음)에 머물지 않게. 이때도 `LIVE_NOTICE.gone` 을 띄우지 않는다

### 9.3 가짜 서버 — `e2e/fixtures/fakeServer.js`

- `PUT /api/docs/:id/e2ee`: F-401 3.4 판정을 옮긴다 — 옮기기인데 이미 금고 409 `e2ee_doc`, 빼기인데 일반 409 `not_e2ee`, 빼기인데 금고 폴더 안 409 `e2ee_folder`, 옮기기인데 키 묶음 없음 409 `no_vault`, 판 틀림 409 `{ error: 'conflict', doc }`. 성공하면 행을 바꾸고 `version` +1, 응답에 `purged: true`(조종 함수 `setPurgeFails(true)` 면 `false`). 그 문서의 공유 링크를 끊는다(`shareLinks` 에서 그 문서 링크 `revokedAt`). 요청은 `recordWrite` 를 지난다(`failWrites` 가 걸린다)
- `PUT /api/folders/:id`: 몸통 `e2ee` 를 받는다 — 켜기는 바로 아래 일반 문서·폴더 수를 세어 있으면 409 `{ error: 'e2ee_folder_not_ready', docs, folders }`, 끄기는 부모가 금고면 409 `e2ee_folder`. 응답은 금고일 때만 `e2ee: true`
- 조종 함수: `setPurgeFails(on)`. 기존 조종 함수·일반 동작은 바꾸지 않는다
- `DELETE /api/attachments` 는 F-406 7.3 그대로 쓴다

## 15. 확인한 것과 가정

### 15.1 코드를 읽거나 돌려 확인한 것
- 머리 표 c1~c17
- `worker/e2eeDocs.ts` 는 빼기에도 `purgeBeforeResponse` 를 부르고, 옮기기 batch 에서만 링크·묶음·초대를 지운다
- `worker/folders.ts` `handleUpdateFolder` 는 켜기 사전 검사(`plainChildren`) 뒤 조건부 문장(`TURN_ON_SQL`)으로 끼어든 평문을 막고, 0행이면 409 `e2ee_folder_not_ready` 를 다시 센다
- `src/storage/docsApi.ts`(작업 트리) `rateLimitedError` 는 `Retry-After` 머리를 먼저, 없으면 몸통 `retryAfter` 를 `parseRetryAfter` 로 읽는다(1~86,400초)
- `src/storage/serverStore.ts`(작업 트리) `applyRateLimitStop` 은 outbox 전체를 `retryAfter` 동안 멈추고 `scope` 에 따라 L1(`info`)·하루 문구(`error`)를 띄운다
- `src/app/FolderMenu.tsx` 는 `items` 뒤에 링크·초대 항목을 붙이고, 방향키는 `allItems` 전부를 돈다
- `@material-symbols/svg-400/outlined/lock_open.svg` 가 설치돼 있다
- `F-404` 8.2 도움말 `## 금고` 마지막 문단이 이미 `금고로 옮기기…` 를 안내한다(`src/app/helpDoc.ts` 에 들어가 있다)

### 15.2 가정으로 남긴 것
- **원격 요청 지연은 재지 않았다.** 2.5 표는 지연 ≤ 0.6초와 1초 두 줄이다. `PUT /api/docs/:id/e2ee` 가 DO `purgeRoom` 을 기다리므로 더 느릴 수 있다
