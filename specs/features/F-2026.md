## 2. 범위

### 2.1 한다

- `worker/index.ts` 라우트 표의 쓰기 라우트 26개(3장)를 핸들러 앞에서 한 관문으로 판정
- 관문 ① 사용자 판정 401, ② **보낸 사람 자신이** 막힌 계정이면 403 `account_blocked`, ③ 보낸 사람의 오늘 쓰기가 5,000 이상이면 429 `day`, ④ Rate Limiting 바인딩이 거절하면 429 `minute`
- `WRITE_LIMITER` 바인딩 설정과 타입 생성
- 관문과 핸들러가 인증을 **한 번만** 하게(6장) — F-2024 2.1 의 "추가 D1 읽기 0" 을 지키려면 필요하다

### 2.2 하지 않는다

- **남이 소유한 문서가 막힌 소유자 것일 때의 403**(F-2024 4.2 표 "막힌 계정 소유 문서의 다른 사람" 열), `/api/me`·`/v1/me` 의 `blocked`·`warned`, 공개 경로 404, `/ws` `4403`, 재검증, `/v1` PUT 소유자 차단, 가입 관문 — **F-2028.** 이 명세의 ② 는 요청을 보낸 사람의 `blockedAt` 만 본다. F-2024 6장 F-2026 행 제목의 "차단 403" 이 이것이고, F-2028 행 내용에 관문 ② 가 없으므로 이렇게 나눈다
- DO 스냅숏의 하루 카운터·느린 저장 — F-2027. 실시간 편집(`/ws`)은 Worker 요청이 아니라 분당에 안 잡힌다(F-2024 1.2)
- 하루 카운터 **올리기** — F-2025 가 핸들러 batch 에서 이미 한다. 관문은 읽기만 한다(D1 쓰기 0)
- 읽기(`GET`) 속도 제한, 로그인 반복 제한 — F-2024 5.3·Q8
- WAF 규칙 — F-2024 2.2 의 대안 갈래는 Q1 시험 결과로 닫혔다
- `observability`(Workers Logs 보관) 설정 — 로그는 `wrangler tail` 로 본다(5.3)

## 4. 관문 — `worker/writeGate.ts`

### 4.1 계약

```ts
// worker/writeGate.ts
export const MINUTE_WRITE_LIMIT = 120        // wrangler.jsonc WRITE_LIMITER 의 simple.limit 과 같은 값 (G10)
export const MINUTE_RETRY_AFTER = 60         // 초. 바인딩이 남은 시간을 주지 않는다 (RateLimitOutcome 은 success 하나)

// F-2024 3.4 그대로
export type RateLimitedBody = { error: 'rate_limited'; scope: 'minute' | 'day'; limit: number; retryAfter: number }
export type BlockedBody = { error: 'account_blocked' }

export function isWriteRoute(method: string, routePath: string): boolean     // 3장 규칙
export async function runWriteGate(request: Request, env: Env): Promise<Response | null>   // null = 통과
```

- `index.ts` 는 `found` 를 찾은 뒤 `isWriteRoute(request.method, found.route.path)` 가 참일 때만 `runWriteGate` 를 부르고, `Response` 가 오면 그것을 돌려주고 핸들러를 부르지 않는다. 호출은 지금의 `try` **안**이다 — `getUser` 가 던지는 설정 오류(`AuthConfigError`)·D1 오류는 지금처럼 `catch` 가 500 으로 바꾼다
- `routePath` 는 요청 경로가 아니라 **라우트 표의 패턴**(`found.route.path`)이다 — `:id` 에 무엇이 들어와도 판정이 같다
- 이름을 바꾸면 F-2028(관문에 판정을 더할 때)·7장 테스트가 어긋난다 — 계약이다

### 4.2 판정 순서와 규칙

| 순서 | 판정 | 걸리면 | 부르는 것 |
| --- | --- | --- | --- |
| ① | `getUser(request, env)` 가 `null` | **401** `{ "error": "unauthenticated" }` — `requireUser` 가 던지는 것과 같은 몸통 | `worker/auth.ts` `getUser` (ctx 없이 — 핸들러의 `requireUser(request, env)` 와 같은 호출) |
| — | 통과하면 `rememberUser(request, user)` (6장) | | |
| ② | 사용량(`usageOf(env, user)`)의 `blockedAt !== null` | **403** `{ "error": "account_blocked" }` | `worker/usage.ts` `usageOf` — `user.usage` 가 있으면 D1 을 읽지 않는다 |
| ③ | `isDailyLimitReached(usage, now)` | **429** `{ "error": "rate_limited", "scope": "day", "limit": 5000, "retryAfter": s }` + 헤더 `Retry-After: s`. `s` = `secondsUntilUtcMidnight(now)`, `limit` = `DAILY_WRITE_LIMIT` | `worker/usage.ts` |
| ④ | `env.WRITE_LIMITER.limit({ key: user.id })` 결과의 `success === false` | **429** `{ "error": "rate_limited", "scope": "minute", "limit": 120, "retryAfter": 60 }` + 헤더 `Retry-After: 60` | 바인딩 (5장) |
| — | 모두 통과 | `null` → 핸들러 | |

- `now` 는 관문에 들어온 순간의 `Date.now()` 하나. ③ 의 판정과 `retryAfter` 가 같은 값을 쓴다
- 응답 모양: `worker/http.ts` `jsonResponse(body, status)` — 지금 API 응답과 같은 헤더(`Content-Type`·`Cache-Control: no-store`·`X-Content-Type-Options`) — 에 429 만 `Retry-After` 를 더한다. `Retry-After` 값은 `retryAfter` 와 같은 정수의 10진 문자열
- ② 가 ③ 보다 먼저인 이유: 막힌 사람에게는 "내일 풀린다" 가 아니라 "막혔다" 가 맞는 답이다(F-2030 L5 가 이 403 을 보고 뜬다). ③ 이 ④ 보다 먼저인 이유: 이미 막힌 요청이 분당 몫을 쓰지 않게, 비싼 바인딩 호출을 마지막에(F-2024 2.1)
- ③ 은 **요청이 시작될 때**의 카운터로 본다(F-2025 4.3 "`usage` 는 요청이 시작될 때 값"). 동시 요청은 5,000 을 몇 건 넘길 수 있다 — F-2024 2.1 이 받아들였다
- ③ 은 보낸 사람의 카운터다. 편집 권한자가 남의 문서에 쓸 때 소유자 카운터는 보지 않는다(F-2025 Q1 — 하루 +1 도 보낸 사람에게 붙는다)
- 관문은 **요청 본문을 읽지 않는다**(헤더만). 막힌 1.1MB 본문이 끝까지 읽히지 않는다(F-2024 2.1). `request.body` 를 소비하지 않으므로 핸들러가 그대로 읽는다
- 관문은 D1 에 **쓰지 않는다.** 걸린 요청은 하루 카운터에 안 잡힌다(F-2024 1.2 "하루는 D1 쓰기를 센다")

## 5. 분당 — Rate Limiting 바인딩

### 5.1 `wrangler.jsonc` (계약 — F-2024 2.2 그대로)

```jsonc
"ratelimits": [
  { "name": "WRITE_LIMITER", "namespace_id": "1001", "simple": { "limit": 120, "period": 60 } }
]
```

- 자리: `triggers` 앞이든 뒤든 최상위 키 하나. 이 파일에 **주석을 넣지 않는다** — G10 이 `JSON.parse` 로 읽는다(측정 g)
- `namespace_id` `"1001"`: 이 계정에서 Rate Limiting 을 쓰는 곳은 이 Worker 하나다. 시험 Worker 는 `"9101"` 이었고 지워졌다(측정 h). 같은 `namespace_id` 를 쓰는 Worker 끼리 몫을 나눠 쓰므로(스키마 설명 "The namespace ID for this rate limiter" — 공유 규칙은 Cloudflare 문서 기준, 이 명세에서 원격으로 확인하지 않았다) 다른 Worker 에 `1001` 을 쓰지 않는다
- `period` 는 `10` 또는 `60` 만 된다(스키마 `enum`). 60
- `npm run cf:types` → `Env` 에 `WRITE_LIMITER: RateLimit`. 타입은 **필수**로 나오지만 테스트 `env` 에는 없을 수 있다 — 5.3

### 5.2 키와 근사

- 키는 `user.id` 그대로(접두사 없음). `namespace_id` 가 이미 다른 용도와 가른다. 토큰(`/v1`)과 브라우저(`/api`)가 같은 몫을 나눠 쓴다 — 토큰 10개를 만들어도 몫이 늘지 않는다(F-2024 2.2)
- 원격은 **위치(POP)별 근사**다(측정 h: 한도 3 에 4번 통과, 연달아 오는 요청에서는 더). 120 은 "대략 이쯤에서 멈춘다" 로만 믿는다. 정확한 판정이 필요한 곳은 하루 5,000(D1)이 맡는다
- 관문은 요청 하나에 `limit()` 을 **정확히 한 번** 부른다(④ 에 닿은 요청만)

### 5.3 실패와 없음 — 통과시킨다 (fail open)

| 경우 | 판정 | 로그 |
| --- | --- | --- |
| `env.WRITE_LIMITER` 가 없거나 `limit` 이 함수가 아님 | 통과 | `console.warn('write_limiter_missing')` — **격리(isolate)당 한 번**(모듈 변수로 한 번만). 요청마다 찍으면 바인딩이 없는 테스트 `env` 가 로그로 뒤덮인다 |
| `limit()` 이 던지거나 거부(reject)됨 | 통과 | `console.error('write_limiter_failed', err)` — **매번.** 원격에서 던지는 일은 드물다고 보고, 드물지 않다면 그것 자체가 알아야 할 일이다 |
| 결과의 `success` 가 `false` 가 아닌 모든 값(`true`, 필드 없음, 객체 아님) | 통과 | 없음 |
| `success === false` | 429 `minute` | 없음 |

- 통과시키는 이유: 분당 제한이 망가져 모든 저장이 막히는 쪽이 더 나쁘다. 하루 5,000 은 D1 로 따로 돈다(F-2024 2.2)
- **하루 판정(③)과 ② 는 fail open 이 아니다.** `usageOf` 가 D1 을 읽다 던지면(흉내 낸 `AuthUser` 에 `usage` 가 없을 때만 읽는다 — 운영에서는 인증이 이미 읽었다) 지금의 `catch` 가 500. D1 이 죽었으면 핸들러도 어차피 쓰지 못한다
- 바인딩 호출에 시간 제한은 두지 않는다. 원격 호출이 멈춰 매달리는 경우는 재지 않았다(가정 — 12장)
- 로그 문자열 `write_limiter_missing`·`write_limiter_failed` 는 `wrangler tail` 에서 찾는 이름이라 이 글자 그대로 쓴다

### 5.4 로컬에서는 어떻게 도나 (측정 a~e)

- `npm run dev:worker`(wrangler dev)와 `getPlatformProxy` 는 같은 miniflare 구현을 쓴다. `getPlatformProxy` 로 확인했다 — `wrangler dev` 자체로는 돌려 보지 않았다(같은 코드 경로라 같다고 본다 — 12장 가정)
- 로컬은 **정확**하다: 같은 키 121번째부터 거절, 동시 요청도 정확히 120. 창은 **벽시계 분에 맞춘 고정 창**이라 분이 바뀌는 순간 0 으로 돌아간다 — 130번을 보내도 분 경계를 넘기면 429 가 안 날 수 있다. H426(`rawdoc mkdir` 130번)은 분이 바뀐 직후에 시작하거나 250번을 보낸다(9장)
- 로컬에서 한도를 낮춰 보려면(H438) `wrangler.jsonc` 의 `simple.limit` 을 잠시 3 으로 바꿔 `dev:worker` 를 띄운다 — **커밋하지 않는다.** 이때 429 몸통의 `limit` 은 상수 120 그대로다(웹 L1 은 숫자를 쓰지 않아 화면에는 차이가 없다). G10 이 커밋 전에 잡는다
- 로컬 저장은 `.wrangler/state` 아래 miniflare DO SQLite(`_mf_ratelimit_buckets`)다 — 원격 몫과 섞이지 않는다
- 단위 테스트(node)는 바인딩이 없다 → 5.3 "없음" 으로 통과. 관문의 ④ 는 가짜 `{ limit }` 로 판정한다(F-2024 6장 "판정 나눔")

## 6. 인증은 요청당 한 번 — `rememberUser`

**문제.** 지금 모든 쓰기 핸들러는 첫 줄에서 `requireUser(request, env)` 를 부른다(`docs.ts`·`folders.ts`·`links.ts`·`grants.ts`·`locks.ts`·`apiTokens.ts`·`attachments.ts`·`v1.ts` — grep 확인). 관문이 ① 에서 `getUser` 를 부르고 핸들러가 또 부르면 **인증이 두 번**이다 — 세션이면 better-auth `getSession` 이 두 번(세션 1 + 사용자 1 읽기씩, F-2032 2.5), 토큰이면 `api_tokens`·`users` 읽기 두 번, 개발 우회면 `INSERT … ON CONFLICT DO NOTHING` + `SELECT` 두 번. F-2024 2.1 의 "인증이 읽은 행에서 판정 — 추가 D1 읽기 0" 이 깨진다

**계약** (`worker/auth.ts`):

```ts
export function rememberUser(request: Request, user: AuthUser): void
```

- `auth.ts` 안의 `WeakMap<Request, AuthUser>` 에 둔다. `getUser` 는 **맨 먼저** 이 표를 보고, 있으면 그 사용자를 돌려준다(`/v1/` 분기보다 앞). `requireUser` 는 `getUser` 를 부르므로 저절로 따른다
- 채우는 곳은 관문 ① 하나뿐이다. `getUser` 가 스스로 채우지 **않는다** — `auth.test.ts` 가 같은 `Request` 로 `getUser` 를 두 번 부르며 사이에 D1 을 고치는 경우(F-2025 AU1 "고친 뒤 다시")가 있어도 지금 동작이 바뀌지 않게
- `getUserRefreshing`(`GET /api/me`)은 보지 않는다 — 관문을 지나지 않는 경로다
- 열쇠가 `Request` **객체**라 핸들러가 새 `Request` 를 만들어 다른 핸들러를 부르면 거기서는 다시 인증한다. 그런 곳이 둘 있다: `handleCreateDocV1` → `handleCreateDoc(jsonRequest(…))`, `handleUpdateDocV1` 폴백 → `handleUpdateDoc(jsonRequest(…))`. **지금도 두 번 인증하는 곳**이고 관문 뒤에도 두 번이다(관문 1 + 안쪽 1, 바깥 `requireUser` 는 기억된 값) — 늘지도 줄지도 않는다. 고치려면 `v1.ts` 를 건드려야 해서 이 명세 밖이다(10장 Q2)
- `WeakMap` 이라 요청이 끝나면 함께 사라진다. 격리 사이에 새지 않는다
- `vi.mock('./auth')` 를 쓰는 테스트 10개 파일 중 `v1.test.ts` 를 뺀 9개는 `worker/index.ts` 를 import 하지 않는다(grep: `index` 를 import 하는 테스트는 `usageRoutes`·`loginRoutes`·`v1` 셋이고 모두 `vi.doUnmock('./auth')`) — 흉내 낸 모듈에 `rememberUser` 가 없어도 깨지지 않는다

## 12. 기존 명세·코드와 부딪치는 것, 그리고 가정

**부딪치는 것**

- **F-2024 6장 F-2026 주요 파일에 `worker/auth.ts` 가 없다** — 6장·Q1 로 더했다
- **F-2024 2.1 "필드가 없으면 관문은 `users` 를 id 로 한 번 읽는다"** — `usageOf` 가 그대로 한다. 다만 관문을 지나는 요청은 모두 실제 인증(세 경로 모두 `usage` 를 채움)이라 운영에서 이 읽기는 일어나지 않고, 흉내 낸 `AuthUser` 는 관문을 지나지 않는다(8장). 사실상 쓰이지 않는 갈래다
- **`specs/architecture.md` 6장이 아직 Access 시절 문장**(`/api/*` 는 Access 가 보호, `/ws/*` 는 `CF_Authorization` 쿠키)이다 — 이 명세 전부터의 어긋남. 11장에 적기만 했다
- **F-2024 1.2 표의 `/v1` 행과 R1** — 같다(26개). 어긋남 없음

**가정 (확인하지 않았다)**

- 원격 `limit()` 의 지연(로컬은 호출당 약 4ms), 원격에서 막힌 호출도 몫을 쓰는지, 원격 창이 고정인지
- 원격 `limit()` 이 매달려(끝나지 않아) 요청이 멈추는 경우 — 시간 제한을 두지 않았다
- `wrangler dev` 가 `getPlatformProxy` 와 같은 miniflare 바인딩을 쓴다는 것 — 같은 구현 파일이라 같다고 봤고, `dev:worker` 로 직접 돌려 보지는 않았다
- `namespace_id` 를 같은 계정의 다른 Worker 와 공유하면 몫을 나눠 쓴다는 것 — Cloudflare 문서 서술을 따른 것이고 원격으로 시험하지 않았다. 이 계정에서 `1001` 을 쓰는 다른 Worker 는 없다(시험 Worker 는 `9101`, 지워짐)
- 계정 플랜이 무료인지 — 측정 h 가 확인한 것은 "이 계정에서 된다" 까지다(`specs/notes.md`)
