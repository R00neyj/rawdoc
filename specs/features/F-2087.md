## 4. 칠하는 방법 (반드시 결론 1) — **CSS Custom Highlight API**

| | CSS Custom Highlight API (채택) | 글자 노드를 `<mark>` 로 감싸기 |
| --- | --- | --- |
| DOM | 그대로. `Range` 만 등록 | 글자 노드를 쪼개고 요소를 끼운다 |
| React `dangerouslySetInnerHTML` 과 | 무관 | React 가 모르는 DOM 변경. `html` 이 바뀌면 통째로 날아가고, 같은 `html` 이면 남는다(`useMemo`) — 닫을 때 직접 되돌려야 한다 |
| 다른 코드가 DOM 을 읽는 곳 | 영향 없음 | 선택 복사(서식 있는 복사에 `<mark>` 가 섞임), 우클릭 메뉴 선택 판정, `Outline`·스크롤 기억(F-295)의 `data-source-line` 탐색, 코드 복사 버튼의 `code.textContent` 는 괜찮지만 쪼개진 노드를 전제로 하지 않은 곳이 생긴다 |
| 지원 | Chrome·Chrome Android 105+, Safari·iOS 17.2+, Firefox 140+ (근거 표) | 전부 |
| 속도(5,000줄, 1,000개) | 현재 매치 바꾸기 한 프레임 16.6ms(4배 느리게 19.9~25.3ms) | 재지 않음 |

- 채택 이유: **DOM 을 바꾸지 않는다.** 불변식 "장식은 문서 내용을 바꾸지 않는다" 는 원문(`Y.Text`)에 대한 것이라 `<mark>` 로 감싸도 어기지는 않지만, Viewer DOM 을 React 밖에서 바꾸면 위 표의 부작용을 모두 되돌려야 한다. Highlight API 는 표시만 바꾸므로 그 불변식의 뜻과 가장 잘 맞는다
- 지원 범위: 제품 기준은 데스크톱 Chrome(product.md Q7)이고 휴대폰은 Chrome Android 다. 둘 다 105 부터라 문제없다. iOS·Safari 는 범위 밖(product.md 8장)이지만 17.2 부터는 된다
- `CSS.highlights` 가 없는 브라우저: **칠하지 않고** 개수·다음·이전·스크롤만 한다. 따로 대체 칠하기를 만들지 않는다
- `::highlight()` 가 받는 속성은 색·바탕색·글자 장식·그림자 등뿐이라 편집 카드의 **현재 매치 둘레 링(`box-shadow`)은 못 쓴다.** 현재 매치는 더 진한 바탕으로 가른다(8.2)

## 5. 찾기 규칙 (반드시 결론 2)

### 5.1 무엇을 찾나 — 보이는 본문 글자

- 뿌리는 **`.viewer > .markdown-body` 하나.** 제목 `h1.doc-title-view`·폴더 경로는 넣지 않는다 — 편집 모드 찾기도 제목(별도 위젯)을 찾지 않는다(Q6)
- 원문이 아니라 **그려진 글자**를 찾는다. `**사과**를` 은 `사과를` 로 찾히고, `**` 는 찾히지 않는다. 편집 모드와 결과 수가 다를 수 있다 — 이것은 의도다
- 빼는 곳(조상에 있으면 그 아래 글자 노드를 건너뛴다): `.katex`(수식 — 보이는 글리프는 입력한 TeX 와 달라 반쪽 매치가 된다, 숨은 MathML 에 TeX 원문이 있다), `.md-mermaid`(다이어그램), `.md-image`(이미지·자리 표시 글), `.markdown-callout-icon`, `.md-code-head`(코드 복사를 켠 화면의 언어 이름·버튼), `div.md-math-error`(오류 메시지). 인라인 수식 오류 `span.md-math-error` 는 원문 `$…$` 가 보이므로 넣는다
- 넣는 곳 예: 문단·목록·인용·콜아웃 제목과 본문·표 칸·코드블록(`pre`)·인라인 코드·링크·위키링크 글자·프론트매터 표
- **블록을 넘는 매치는 없다.** 글자 노드마다 가장 가까운 블록 조상 — `p, li, h1, h2, h3, h4, h5, h6, td, th, pre, blockquote, div, dt, dd, table, thead, tbody, tr, ul, ol`, 없으면 `.markdown-body` — 이 같은 노드끼리만 이어 붙인다. 그래서 `굵게` 가 `<strong>굵</strong>게` 처럼 인라인 요소를 넘어도 찾히고, 한 문단 끝과 다음 문단 첫머리를 잇는 가짜 매치는 없다
- 블록 글자 정리(`normalizeBlockText`): `pre` 밖에서는 `\n`·`\t` 를 공백 한 칸으로 **1:1** 바꾼다(길이 불변 — 오프셋이 그대로 글자 노드에 맞는다). 문단 안 소프트 줄바꿈이 화면에서 공백으로 보이기 때문이다. `pre` 안은 그대로 둔다
- 한글 NFC/NFD 정규화는 하지 않는다 — 편집 모드(`@codemirror/search`)도 하지 않는다

### 5.2 옵션 — 편집 모드와 같은 셋, 같은 뜻

기본은 모두 꺼짐(편집 카드와 같다). 점 세 개 `옵션 더 보기` 안에 둔다.

| 옵션 | 규칙 (편집 모드 `@codemirror/search` 6.7.2 와 맞춘 것) |
| --- | --- |
| 꺼짐(기본) | 문자열 찾기. `\n`·`\r`·`\t`·`\\` 를 풀어 읽는다(`literal: false` 와 같다). 대소문자 무시는 글자(코드 포인트)마다 `toLowerCase` 하되, **소문자로 바꾸면 길이가 달라지는 글자(`İ` 등)는 원래 글자 그대로 비교**한다 — 오프셋이 원문과 1:1 이어야 해서다(편집 모드와 이 드문 글자에서만 다를 수 있다). 겹치지 않게 왼쪽부터(`aa` 는 `aaaa` 에서 2개) |
| `대소문자 구분` | 위에서 소문자 바꾸기만 뺀다 |
| `정규식` | `new RegExp(search, 'gmu' + (대소문자 구분 아니면 'i'))` 를 블록 글자마다 돌린다. **잘못된 정규식은 매치 0개**(오류 문구 없음 — 편집 모드와 같다). 길이 0 매치는 버린다 |
| `단어 단위` | 매치 앞뒤 경계를 편집 모드 `stringWordTest`·`regexpWordTest` 와 **같은 식**으로 본다(근거 참고). 단어 글자는 `/[\p{Alphabetic}\p{Number}_]/u`, 블록 처음·끝은 단어 글자가 아닌 것으로 친다. 앞뒤 "한 글자" 는 코드 포인트 하나다(CM 은 자소 묶음 — 결합 문자에서만 다를 수 있다). 결과: `사과` 는 `사과를` 에서 안 찾히고 `사과 를` 에서 찾힌다 |

### 5.3 언제 다시 찾나

- 입력칸 `input` 이벤트마다 곧바로(지연 없음 — 편집 카드도 `keyup` 마다 곧바로다). **한글 조합 중에도 찾는다** — 조합 중인 글자도 입력칸 값에 들어 있다. 이 입력칸은 편집기가 아니라 IME 불변식(원격 갱신 보류·재계산 따라잡기)의 대상이 아니다
- 옵션을 바꿀 때마다
- 카드가 열린 채 `html` 이 바뀌면(보기 모드 변환이 다시 돌 때 — `useEditorSync` 의 보기 모드 effect 가 `docs` 변화에도 돈다) 색인을 다시 만들고 다시 찾는다. 현재 번호는 `min(이전 번호, 새 개수)` 로 두고 **스크롤하지 않는다**
- 색인은 열 때 한 번, `html` 이 바뀔 때 한 번 만든다. 글자를 칠 때마다 다시 만들지 않는다(근거 측정 — 색인이 한 번 찾기보다 2~3배 비싸다)

### 5.4 빈 입력

- 매치 없음, 칠하기 없음, 개수 칸 빈칸. `다음`·`이전` 은 아무 일도 하지 않는다(흐리게 하지 않는다 — 편집 카드도 늘 눌린다)

### 5.5 한도

- 매치는 문서 순서로 **1,000개(`VIEW_FIND_LIMIT`)** 까지만 모은다. 넘으면 `truncated` 가 참이고 개수 문구 뒤에 `+` 를 붙인다(6.4). 다음·이전은 그 1,000개 안에서 돈다
- 이유: 등록된 매치가 많을수록 현재 매치를 바꾸는 한 프레임이 길어진다(근거 표 — 4배 느린 CPU 에서 1,000개 19.9~25.3ms, 10,000개 68.1~80.4ms). 1,000 은 편집 모드 `모두 선택` 한도와 같다. 다른 값은 Q7

## 6. 이동·스크롤·개수 (반드시 결론 3)

### 6.1 현재 매치 고르기

- 검색어·옵션이 바뀌면: **보이는 영역 맨 위(`.viewer` 윗변 + 떠 있는 알약 가림 높이) 아래에 윗변이 있는 첫 매치**, 없으면 첫 매치(`pickStartIndex` — 매치 윗변 배열에서 `visibleTop` 이상인 첫 번호, 없으면 0). Chrome 찾기처럼 치는 동안 바로 옮겨 간다. 편집 모드는 치는 동안 선택을 옮기지 않지만, 보기 모드에는 커서가 없어 "어디서부터" 가 화면 위치밖에 없다
- `Enter`·`다음 찾기`·`F3`·`Ctrl+G`(맥 `Cmd+G`): 다음 번호, 끝에서 처음으로 돈다
- `Shift+Enter`·`이전 찾기`·`Shift+F3`·`Shift+Ctrl+G`: 이전 번호, 처음에서 끝으로 돈다
- **한글 조합 중 `Enter`(`isComposing` 참 또는 `keyCode` 229)는 무시한다** — 조합을 끝내는 `Enter` 가 다음 매치로 뛰면 안 된다

### 6.2 키 범위

| 키 | 언제 받나 | 브라우저 기본 동작 |
| --- | --- | --- |
| Ctrl/Cmd+F | `available` 이면 어디서나(3.6). 열려 있으면 입력칸 포커스 + 전체 선택 | 막는다 |
| `Enter`/`Shift+Enter` | 입력칸 포커스 | 막는다 |
| `F3`/`Shift+F3`, Ctrl/Cmd+G/Shift+Ctrl/Cmd+G | 카드가 열려 있고 포커스가 카드 안 또는 `.viewer` 안, 또는 포커스가 `body` 일 때 | 막는다(편집 모드 키맵도 `preventDefault: true`) |
| `Esc` | 카드가 열려 있고 포커스가 카드 안 또는 `.viewer` 안 | 막지 않는다. 위키링크 미리보기가 떠 있으면 그 창만 닫힌다(캡처 단계 `stopPropagation`, 손대지 않음) |

### 6.3 스크롤

- 매치 사각형이 보이는 영역(`.viewer` 윗변 + `floatCoverFor(.viewer)` ~ 아랫변) 안에 **다 들어 있으면 스크롤하지 않는다.** 아니면 매치 세로 가운데가 보이는 영역 가운데에 오도록 `.viewer.scrollTop` 을 정한다(`scrollTopToReveal`, 결과는 0 ~ 최대값으로 자른다). Chrome 찾기와 같은 동작이다
- 가로: 매치가 가로 스크롤 조상(`pre`, 표, 그 밖에 계산된 `overflow-x` 가 `auto`/`scroll` 인 조상) 안에서 보이는 폭 밖이면 그 조상의 `scrollLeft` 를 매치 왼쪽이 조상 왼쪽 + 32px 에 오게 한다
- **즉시 옮긴다**(`behavior: 'instant'`). `.viewer` 의 `scroll-behavior: smooth` 는 목차 이동용이다 — `Enter` 를 빠르게 누를 때 부드러운 스크롤이 겹쳐 밀린다
- 스크롤은 6.1 의 번호가 바뀔 때만. 모드 전환으로 이어받아 열 때(7장)와 `html` 이 바뀔 때(5.3)는 하지 않는다 — F-295 스크롤 기억과 다투지 않게

### 6.4 개수 문구 (`formatFindCount`)

| 상태 | 문구 |
| --- | --- |
| 빈 입력 | (빈칸) |
| 매치 0개(잘못된 정규식 포함) | `결과 없음` |
| 매치 있음 | `{현재}/{전체}` 예: `3/12` |
| 1,000개에서 잘림 | `{현재}/1000+` |

### 6.5 열기·닫기·포커스

- 열 때: 입력칸 포커스 + 전체 선택. `.viewer` 안에 100자 이하의 선택이 있으면 그 글(`\n` → 공백)을 검색어로 넣는다 — 편집 모드 `openSearchPanel` 의 `defaultQuery`(선택 100자 이하)와 같다. 선택이 없으면 **같은 문서에서 마지막으로 쓴 검색어·옵션**을 다시 넣는다(편집 모드 `searchState` 도 남는다)
- 닫기: `Esc`, `닫기` 버튼. 칠하기를 지우고, 포커스가 카드 안이었으면 `.viewer` 로 돌린다. 스크롤 위치는 그대로
- `다음`·`이전`·옵션 버튼을 눌러도 포커스는 입력칸에 남긴다(누를 때 포커스를 가져가지 않는다 — `댓글 달기` 버튼과 같은 방법). 휴대폰에서 누를 때마다 자판이 닫혔다 열리지 않게 하려는 것
- 문서를 바꾸면 닫히고 검색어도 버린다(편집 모드도 문서마다 편집기가 새로 생긴다). 공유 링크·공유 관리·도움말·지도로 가면(`available` 거짓) 닫는다
- 칠하기는 카드가 열려 있고 `available` 일 때만 있다. 닫힘·모드 전환·문서 전환·언마운트 때 두 하이라이트 이름을 모두 지운다

## 7. 편집 ↔ 보기 전환 때 이어받기 (반드시 결론 4) — **이어받는다**

- **들어가는 쪽 찾기가 떠나는 쪽 찾기의 열림 여부·검색어·옵션 셋(대소문자·정규식·단어 단위)을 그대로 받는다.** 편집·원문 → 보기: CM6 패널이 열려 있으면(`readSearchPanel`) 보기 카드를 그 검색어로 열고, 닫혀 있으면 보기 카드도 닫힌 채. 보기 → 편집·원문: 보기 카드가 열려 있으면 `syncSearchPanel(view, 질의)`, 닫혀 있으면 `syncSearchPanel(view, null)`
- 보기로 들어간 뒤 CM6 패널은 닫는다(`syncSearchPanel(view, null)`) — 숨은 편집기 안에 열린 패널이 남으면 편집 모드로 돌아올 때 옛 검색어로 다시 보인다(근거의 지금 동작)
- 이어받을 때 **포커스는 옮기지 않는다**(모드 전환 기본 동작 그대로) — 보기 카드는 입력칸에 포커스를 주지 않고, CM6 패널도 선택·스크롤·포커스를 옮기지 않는다. 현재 매치는 6.1 규칙으로 고르되 스크롤하지 않는다(6.3)
- 이유: "보기에서 찾은 곳을 편집으로 가서 고친다" 가 가장 흔한 흐름이다. 같은 문서 안 찾기가 모드마다 따로 놀면 모드를 바꿀 때마다 다시 쳐야 한다. 편집 ↔ 원문은 같은 편집기라 지금도 이어진다
- 원문 ↔ 편집 전환은 손대지 않는다(같은 편집기)
- 다른 선택은 Q1

## 8. 모양 (반드시 결론 5 — 값은 초안, 사람 확인)

### 8.1 카드

- `searchPanel.css` 의 카드 규칙 앞머리 `.cm-host .cm-panel.cm-search` 를 모두 `:is(.cm-host .cm-panel.cm-search, .view-find)` 로 바꾼다. `:is()` 의 구체성은 가장 구체적인 인자를 따르므로 편집 카드 규칙의 구체성은 그대로다. 매치 색 두 규칙(`.cm-host .cm-editor .cm-searchMatch…`)은 대상이 아니다
- `viewFind.css` 에만 있는 것:
  - 자리: `.content-area` 기준 `position: absolute; top: 10px; right: 10px; z-index: 20` — 편집 카드와 같은 자리·같은 층. 휴대폰 폭(≤600px)은 `top: calc(var(--float-cover) + 10px)`. F-2086 이 편집 카드 자리를 옮기면 이 규칙도 따라 옮긴다
  - 개수 칸: `span.view-find-field` 는 `position: relative`, 개수는 입력칸 안 오른쪽 끝(`right: 8px`, 세로 가운데), 글자 `--muted`·12px, 누르기 통과(`pointer-events: none`). 입력칸은 오른쪽 안쪽 여백을 개수 폭만큼(초안 56px) 늘린다. 입력칸 폭 140px 는 그대로 — 카드 폭이 편집 카드와 같다
  - 옵션 팝오버에 `모두 선택` 이 없어 편집 카드보다 좁다. 그대로 둔다
- 목차 팝업(`.outline-popup`, 같은 층 20, 오른쪽 위)과의 겹침은 편집 모드와 같게 둔다 — 사람 확인 H4

- 이유: 보기에서 찾고 편집에서 고치는 흐름. 편집 ↔ 원문은 지금도 이어진다
- 다른 선택(따로 둔다): 7장·`readSearchPanel`·`syncSearchPanel`·U13·U14·E2 가 빠진다. 대신 **보기로 갈 때 CM6 패널을 닫는 한 줄은 남겨야 한다**(숨은 패널 문제). `showSearchMatches.ts` 에는 닫기만 더한다

### Q2. S-4 공유 화면·S-7 도움말·S-5 공개 보기에도 넣나 — **기본값: 넣지 않는다(S-1 보기 모드만)**
- 이유: 사용자가 정한 범위는 "보기 모드". S-5 는 Ctrl+F 가 이미 브라우저 찾기로 잘 된다(2026-09-28 F-2062 Q1 수정). S-4·S-7 은 창 하나짜리 읽기 화면이라 브라우저 찾기로도 된다 — 다만 Q3 을 보라
- 다른 선택(넣는다): `useViewFind` 가 `viewerRef` 대신 "지금 보이는 본문 Viewer" 를 받게 넓히고, `available` 조건에 화면별 갈래가 생긴다. S-5 는 `useGlobalShortcuts` 가 공개 보기에서 effect 를 안 거는 규칙(F-2062 C3)을 바꿔야 하고 C3 기대값이 뒤집힌다. 카드 자리 규칙(`.content-area` 기준)이 S-4·S-5 머리 줄 아래로 바뀐다. e2e 가 늘어 3개 한도를 넘으므로 이유를 적어야 한다

### Q3. S-4 공유 화면·S-8 지도에서 Ctrl+F 가 막히고 숨은 패널만 열리는 지금 동작 — **기본값: 이 명세에서 고치지 않는다**
- 근거: 3.6 의 지금 동작 그대로 — `.content-area--doc` 가 `hidden` 이어도 편집기 `view` 가 있어 `preventDefault` 뒤 `openSearchPanel` 을 부른다(코드 읽기, 실행 확인 아님)
- 다른 선택(같이 고친다): Ctrl+F effect 에 "편집기가 화면에 보이지 않으면 막지 않는다" 한 갈래를 더한다. 11장에 S-4 Ctrl+F 가 안 막히는지 보는 단언 하나를 더해야 한다(E 한도 안에 넣으려면 E1 에 곁들인다). 사용자가 2026-09-28 공개 보기의 같은 증상을 "버그" 로 판정한 전례가 있어 **같이 고치는 쪽을 추천**하지만, 과제 범위 밖이라 결정을 사람에게 넘긴다

### Q4. 검색 결과(F-294)로 보기 모드 문서를 열 때 보기 카드에 검색어를 넣나 — **기본값: 넣지 않는다**
- 이유: F-294 는 "보기 모드에서는 열리지 않는다" 를 수용 기준(A7)과 `ia.md` 3.28 에 적었다. 그 결정을 뒤집는 것은 이 명세의 과제가 아니다
- 다른 선택(넣는다): F-294 의 `pendingEditorSearch` effect 에 보기 모드 갈래를 더하고(`useEditorSync.ts` 가 소유표에 들어온다), 첫 매치로 스크롤한다. `docSearch.spec.js` F-294 A7 의 기대값이 뒤집히고 `ia.md` 3.28 6번을 고친다

### Q5. 편집 모드 카드에도 개수(`3/12`)를 넣나 — **기본값: 이 명세에서는 넣지 않는다**
- 이유: 편집 카드는 `@codemirror/search` 패널이라 개수를 더하려면 `searchMoreToggle` 식 DOM 덧대기와 매치 세기(`SearchQuery.getCursor`)가 필요하다 — 별도 작은 명세 감이다. 이 명세 뒤 두 카드가 개수 칸 하나만 다르다
- 다른 선택(넣는다): `createEditor.ts` 가 소유표에 들어오고, 개수 계산이 편집 매치에서 매번 돈다(편집 모드 성능 측정이 따로 필요)

### Q6. 제목(`h1.doc-title-view`)도 찾나 — **기본값: 찾지 않는다(본문만)**
- 이유: 편집 모드 찾기가 제목을 찾지 않는다. 모드를 오갈 때 개수가 달라지는 원인을 하나 줄인다
- 다른 선택(찾는다): 뿌리를 `.viewer` 로 넓히고 폴더 경로 `span.doc-title-label` 만 뺀다. U 는 그대로, E1 개수가 바뀔 수 있다

### Q7. 매치 한도 — **기본값: 1,000개**
- 이유: 근거 표. 편집 `모두 선택` 과 같은 수
- 다른 선택: 2,000(4배 느리게 한 프레임 27.7~39.8ms)이나 한도 없음(글자마다 매치면 4배 느리게 525.6ms). 한도 없음이면 `truncated`·`+` 문구가 빠진다
