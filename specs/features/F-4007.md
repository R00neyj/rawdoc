# F-4007 조각 링크용 요청 토큰

작성일: 2026-10-12
상태: 승인 2026-10-12(사용자 "S-4 도 지원"·"추천안대로" — 상시 지시로 승인). S-4(`#/s/{조각}`)에서도 권한을 요청한다. 링크로 원본이 드러나는 것은 받아들였다. 이 명세는 서버 쪽(토큰 표·발급·요청 대상 판정·정리)만 다룬다. 조각 형식·복사·S-4 화면은 F-2137. 구현 담당 `feature-implementer`. 전부 node 단위(`testD1` + 실제 핸들러), e2e 없음

## 근거 (2026-10-12 HEAD, 이름으로 찾는다)
- `src/lib/shareCodec.ts` 조각은 `{ v:1, t, c, e }` 이고, `decodeShare` 는 모르는 키를 무시한다 → 키를 하나 더해도 옛 앱이 새 링크를 그대로 연다
- `src/app/shareCopy.ts` `copyShareLink` 는 지금 서버를 부르지 않는다(오프라인에서도 복사된다)
- 문서 id 는 이미 밖에 나가 있다: `/pub/folders/:token`·`/pub/docs/:token/set` 응답, 받은 사람의 `/#/d/{id}` 주소, 알림
- `worker/token.ts` `generateToken` = 32바이트 난수, base64url 43자. `isValidToken` 이 형식을 본다

## 1. 결정 — 조각에 넣는 것은 문서 id 가 아니라 요청 전용 토큰
| | 문서 id | 요청 토큰(채택) |
| --- | --- | --- |
| 요청 통로 | id 를 아는 누구나 — 공개 폴더 응답·주소창으로 퍼진 id 까지. 조각 링크를 만든 적 없는 문서도 요청을 받는다 | 소유자가 그 문서의 조각 링크를 만든 뒤에만 |
| 끊기 | 문서를 지우기 전엔 못 끊는다 | 서버에서 끊을 수 있다(문서 삭제·금고와 함께 끊고, 나중에 끄는 화면을 붙일 수 있다) |
| 존재 확인 | 상태 조회가 아무 id 의 존재를 알려 준다 | 토큰을 아는 사람만 |
| 비용 | 없음 | 문서당 첫 복사 때 D1 쓰기 1번, 복사에 왕복 1번(F-2137 이 메모리에 둔다) |

- `share_links` 를 다시 쓰지 않는 이유: 그 토큰은 `/pub` 으로 **지금 본문**을 읽게 한다. 조각 링크는 그때의 스냅숏만 건넨 것이라, 받은 사람이 살아 있는 문서를 읽게 되면 공유 범위가 넓어진다. 그래서 `/pub` 이 보지 않는 따로 된 표를 쓴다
- 문서당 살아 있는 토큰 하나. 같은 문서를 다시 복사하면 같은 토큰을 받는다(`findActiveLink` 와 같은 모양)

## 3. 표 (계약)
```sql
CREATE TABLE request_tokens (
  token TEXT PRIMARY KEY,                 -- generateToken 43자
  owner_id TEXT NOT NULL REFERENCES users(id),
  doc_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  revoked_at INTEGER
);
CREATE UNIQUE INDEX request_tokens_doc_live ON request_tokens(doc_id) WHERE revoked_at IS NULL;
```

## 4. 라우트와 판정
| 메서드·경로 | 성공 | 실패 |
| --- | --- | --- |
| `POST /api/docs/:id/request-token` | 200 `{ token }`(이미 있음, D1 쓰기 0) / 201 `{ token }`(새로, 소유자 `dayUsageStatement`) | 401, 404·403(`checkOwnedTarget` 과 같은 구분), 409 `e2ee_doc` |

- 소유자만 만든다 — 받은 사람이 복사한 조각에는 토큰이 없다(요청 통로는 주인이 연다)
- **F-4005 대상 찾기**: 토큰이 살아 있는 `share_links` 에 없으면 `request_tokens`(`revoked_at IS NULL`, 주인이 막히지 않음)를 본다. 찾으면 대상은 그 문서, `docId` 는 무시. 문서가 주인 것이고 금고 아님 — 아니면 404. 라우트·응답·상한·만들기 순서는 F-4005 그대로(`target` 은 늘 `'doc'`)
- **`LIVE_REQUEST_SQL`**: 링크 갈래에 `OR EXISTS (같은 token 의 살아 있는 request_tokens 행, 같은 owner_id·doc_id = r.target_id)` 를 더한다. 목록·승인·Cron 이 그대로 따라온다
- 두 표의 토큰이 겹칠 확률은 256비트 난수라 따지지 않는다. 겹쳐도 `share_links` 가 먼저다
- **끊기**: 문서 삭제·금고로 옮기기 때 `UPDATE request_tokens SET revoked_at = ?` + 그 토큰의 요청은 F-4006 4장 대상 조건이 이미 지운다. 계정 삭제는 행을 지운다. 끄는 화면은 없다(F-4004 8장 남은 갈림길)
