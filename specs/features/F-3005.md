Q2~Q7 기본값). 승인 대기. 개요 `F-3001`(2026-09-30 승인) 6장 로드맵의 F-3005 행 — 2.2 `notifications` 표 다시 만들기, 3.4 1·2·5번(종류 정하기·넣을 때 `push_due_at`·읽음이 푸시를 끔), 4.5 서버 쪽(`?kinds=`·ETag). **서버·API 계약까지만 한다.** 알림함이 `comment` 를 보여 주는 것(`isNotificationItem`·`notificationText`·`?kinds=` 붙여 부르기·도움말)은 F-2111, 모아 보내기·알람·"가장 이른 `push_due_at`" 문장은 F-3006 몫(2.3)

## 정해진 것 (바꾸지 않는다)

1. F-3001 1~5장 결정 전부와 10장 답 — **Q1: `comment`(내 문서의 새 댓글)만 알림함에도 넣는다.** 공유·저장 공간 경고는 알림 행을 만들지 않는다(푸시만, F-3007·F-3008)
2. 묶기 3분(`PUSH_BATCH_MS`)과 보내기 자체는 F-3006
3. `kind` 를 늘리려면 표를 다시 만든다(SQLite 는 `CHECK` 를 `ALTER` 로 못 바꾼다). `push_due_at` 에는 색인을 걸지 않는다(F-3001 2.2 — D1 무료 쓰기가 읽기보다 50배 빡빡)

5. 새 npm 의존성 없음. 새 UI 문자열 없음

## 3. 데이터

### 3.1 마이그레이션 (계약)

`migrations/0018_notifications_push.sql`. SQLite 공식 "다른 종류의 표 바꾸기" 절차(새 표 → 복사 → 옛 표 지우기 → 이름 바꾸기 → 색인)를 따른다. 파일 첫 줄은 주석 한 줄(`F-3005` 와 "CHECK 를 ALTER 로 못 바꿔 표를 다시 만든다"):

```sql
CREATE TABLE notifications_new (
  id TEXT PRIMARY KEY,
  recipient_email TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('mention','reply','comment')),
  doc_id TEXT NOT NULL,
  comment_id TEXT NOT NULL,
  thread_id TEXT NOT NULL,
  actor_email TEXT NOT NULL,
  doc_title TEXT NOT NULL,
  excerpt TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  read_at INTEGER,
  push_due_at INTEGER,               -- 이 행을 푸시로 보낼 차례가 되는 때(ms). NULL = 보낼 것 없음
  UNIQUE (recipient_email, comment_id, kind)
);
INSERT INTO notifications_new (id, recipient_email, kind, doc_id, comment_id, thread_id, actor_email, doc_title, excerpt, created_at, read_at, push_due_at)
  SELECT id, recipient_email, kind, doc_id, comment_id, thread_id, actor_email, doc_title, excerpt, created_at, read_at, NULL FROM notifications;
DROP TABLE notifications;
ALTER TABLE notifications_new RENAME TO notifications;
CREATE INDEX notifications_recipient_order ON notifications(recipient_email, created_at DESC, id DESC);
CREATE INDEX notifications_doc ON notifications(doc_id);
```

- 열 순서·이름·NULL 허용은 `0012` 그대로에 `push_due_at` 하나를 끝에 더했다. **`push_due_at` 에는 색인을 걸지 않는다**(정해진 것 3)
- 옛 행은 모두 `push_due_at` NULL — 마이그레이션 전에 생긴 알림은 푸시로 가지 않는다
- 색인 이름 `notifications_recipient_order`·`notifications_doc` 은 F-2075 테스트(`F-2075 A4 색인`)와 코드가 이름으로 기댄다 — 바꾸지 않는다. `UNIQUE`·PK 의 자동 색인은 이름 바꾸기가 따라 옮긴다(m1)
- 외래 키·트리거·뷰가 없어 `PRAGMA foreign_keys`·`defer_foreign_keys` 가 필요 없다(근거)
- 표·열 이름에 제품명 없음(불변조건)

### 3.2 번호와 원격 적용 순서

- 번호 **`0018`**. 구현 커밋 때 `migrations/` 에 이미 `0018_*` 가 있으면(F-3010 이 먼저 들어간 경우) **그 다음 빈 번호**를 쓰고 보고에 적는다 — F-3003 3.2 와 같은 규칙. 계약은 뒷부분 `notifications_push` 와 3.1 SQL 이다. 이 파일은 `0012`·`0015` 뒤이기만 하면 된다(`push_subscriptions` 는 SQL 이 아니라 넣기 문장이 읽는다)
- **F-3010(F-2092)** 은 `0017` 을 쓸 수 없다. 자기 명세를 쓸 때 그때의 다음 빈 번호를 고른다(10장)
- **원격 적용은 코드 배포보다 반드시 먼저.** 새 코드의 넣기 문장은 `push_due_at` 열과 `'comment'` 값을 쓴다 — 표가 옛 모양이면 **스냅숏 batch 전체가 실패**하고, 같은 batch 에 든 본문 `UPDATE docs` 도 D1 에 닿지 못한 채 다시 시도만 되풀이한다(F-502 4.2 한 batch). 반대 순서(표 먼저, 옛 코드)는 해가 없다 — 옛 코드는 열 이름을 적어 넣고 읽으며 `push_due_at` 은 NULL 허용, CHECK 는 넓어지기만 했다
- 순서:
  1. 원격에서 `SELECT COUNT(*) AS n FROM notifications` 를 본다. **쓰기 행 ≈ n × 5**(새 표 행 + 자동 색인 둘 + 색인 둘, F-3001 p10. **추정 — 원격 `rows_written` 은 재지 않았다**, m2). 그 값이 그날 남은 D1 쓰기(무료 10만/일)의 절반을 넘으면 UTC 자정 직후에 돌린다
  2. `npx wrangler d1 migrations apply md-editor-db --remote`
  3. `deploy` 브랜치로 코드
- 옛 표의 행을 지우는 `DROP TABLE` 이 쓰기 행으로 더 세어지는지, 원격 마이그레이션이 파일 하나를 트랜잭션으로 감싸는지는 **확인하지 않았다**. 적용이 도중에 실패하면 `notifications_new` 가 남을 수 있다 — 그때는 `DROP TABLE IF EXISTS notifications_new` 뒤 다시 적용한다(사람 확인 9장 ①)

## 4. 알림 행 만들기

### 4.1 `comment` 받는 사람 — `notificationTargets` (계약·규칙)

```ts
export type NotificationDraft = { recipient: string; kind: NotificationKind; commentId: string; threadId: string; actor: string; excerpt: string }
export function notificationTargets(
  item: { id: string; entry: CommentEntry },
  thread: CommentThread | null,
  people: ReadonlySet<string>,
  owner: string | null,     // 문서 주인 이메일(소문자). null = comment 행 없음
): NotificationDraft[]
```

- 지금 규칙(멘션 → 답글, 작성자 자신과 `people` 밖 제외, F-502 6.2)을 그대로 돈 **뒤**, 아래가 모두 참이면 `{ recipient: owner, kind: 'comment', …같은 base }` 를 **끝에 하나** 더한다:
  1. `owner` 가 null 이 아니다
  2. 작성자 이메일(소문자)이 `owner` 가 아니다 — 주인이 자기 문서에 쓴 댓글은 알리지 않는다
  3. `owner` 가 이 항목에서 아직 행을 받지 않았다 — **한 항목에서 한 사람은 행 하나, 우선순위 멘션 > 답글 > `comment`**. 주인이 멘션됐으면 `mention` 하나, 주인이 그 스레드에 먼저 썼으면 `reply` 하나
  4. `owner` 가 `people` 에 있다 — `loadDocPeople` 은 늘 주인을 넣으므로 실제로는 늘 참이다. 다른 경로로 불렀을 때 접근 없는 사람에게 제목·발췌가 가지 않게 같은 문을 둔다
- 첫 댓글·답글 모두 대상이다(F-3001 3.4 1번 "내 문서의 새 댓글"). 멘션이 없어도 된다
- 작성자 이메일이 없으면 지금처럼 `[]`(로컬 작성자 — 서버 문서에서는 사후 검사가 도장하므로 생기지 않는다, F-502 6.1)
- "새 항목" 의 뜻은 F-502 6.1 그대로 — D1 에 처음 들어가는 항목만. 고친 댓글·되살린 댓글(D9)·해결은 행을 만들지 않는다. 이관(F-503 5장)은 작성자가 주인이라 `comment` 행이 없다(근거)
- 한 batch 상한 `NOTIFICATIONS_PER_BATCH_MAX = 2_000` 에 `comment` 행도 들어간다. 항목마다 늘어나는 것은 최대 하나다

### 4.2 `push_due_at` — 넣을 때 (규칙)

`notificationStatements` 의 인자에 `pushDueAt?: number | null` 을 더한다(없으면 null). 넣기 문장은 행마다:

- `pushDueAt` 이 null 이 아니고, **받는 사람 이메일의 `users` 행에 딸린 `push_subscriptions` 행이 하나라도 있으면** `push_due_at = pushDueAt`
- 그 밖(`pushDueAt` null, 구독 없음, 가입하지 않은 이메일)은 NULL
- 구독 확인은 같은 넣기 문장 안의 `EXISTS` 하나로 한다 — 문장 수가 늘지 않는다(`notificationStatements` 는 지금처럼 넣기 조각 + TRIM + 리비전). `pushDueAt` 이 null 이면 `EXISTS` 를 평가하지 않도록 조건을 앞에 둔다(`CASE WHEN ? IS NOT NULL AND EXISTS …`) — 푸시가 꺼진 동안 읽기가 0행 늘어난다
- **세션이 살아 있는지는 보지 않는다**(Q2). 죽은 세션의 구독은 매일 정리(F-3003 `cleanupPushSubscriptions`)가 하루 안에 지우고, 보낼 때 F-3006 이 산 구독만 다시 읽는다. 틀려도 대가는 그 문서의 알람 한 번(DO 요청 1)이 "보낼 기기 없음" 으로 끝나 행을 NULL 로 만드는 것
- 넣기 문장은 계속 **`INSERT OR IGNORE INTO notifications`** 로 시작한다(`docRoomComments.test.ts` `label()` 이 이 접두사로 알아본다)
- 비용(m3): 푸시가 켜져 있을 때 받는 사람 행마다 D1 읽기 색인 조회 둘(`users` 이메일 → `push_subscriptions_user`). 쓰기는 같은 행의 열이라 0

### 4.3 `DocRoomCore` 배선 (규칙)

- **푸시 켜짐**: `loadVapid(host.env)` 가 null 이 아니면 켜짐. 방 인스턴스 수명 동안 **한 번만** 부르고 결과를 보관한다(비밀 값은 배포 단위로 바뀌고, 바뀌면 인스턴스가 새로 뜬다). 처음 부르는 때는 알림 초안이 하나라도 생긴 스냅숏이다 — 초안이 없으면 부르지 않는다. F-3006 이 같은 보관 값을 VAPID 키로 쓴다
- **`pushDueAt`**: 푸시가 켜져 있고 초안이 있으면 `now + PUSH_BATCH_MS`(`now` = 그 batch 의 `now`, 알림 `created_at` 과 같은 값), 아니면 null. `CommentPlan` 에 담아 `commentBundleStatements` → `notificationStatements` 로 넘긴다. 그래서 한 batch 에 넣은 행은 모두 같은 `push_due_at` 이다
- **접근 집합을 읽는 조건**: 지금("새 항목 중 멘션이 있거나 답글인 것") **또는 "작성자 id 가 있고 `ownerId` 와 다른 새 항목"** 이 하나라도 있을 때. 주인 혼자 쓰는 문서(가장 흔한 경우)는 지금처럼 `loadDocPeople` 을 부르지 않는다. 작성자 비교는 이메일이 아니라 **id** 로 한다(사후 검사가 도장한 값, 대소문자 문제 없음)
- **주인 이메일**: `docPeople` 보관에 이메일 집합과 함께 `role === 'owner'` 인 항목의 이메일을 둔다(60초 보관 규칙 그대로). `loadDocPeople` 이 null(없는 문서·금고)이면 초안 없음 — 지금 그대로
- 스냅숏 batch 의 문장 수·순서, `snapshot`·`scheduleAlarm`·`alarm` 은 바꾸지 않는다. `loadDocPeople` 이 던지면 스냅숏 전체가 실패하는 규칙(F-502 6.3)도 그대로 — 이제 주인이 아닌 사람의 댓글 하나로도 그 경로를 탄다

### 4.4 보내는 쪽이 아직 없을 때 (F-3006 전)

- `push_due_at` 이 채워진 행이 쌓이지만 읽는 문장이 없다. 표 전체를 훑는 질의가 이 열을 보지 않으므로 비용이 0이다
- F-3006 이 들어가면 첫 알람이 그 문서의 `push_due_at IS NOT NULL` 행을 읽어 `PUSH_STALE_MS`(1시간)보다 오래된 묶음을 보내지 않고 NULL 로 만든다(F-3001 3.4 ③⑤) — 쌓인 행은 그때 치워진다. **F-3006 에 넘길 조건**: 스냅숏 끝 "가장 이른 `push_due_at`" 은 `PUSH_STALE_MS` 보다 오래된 행을 빼고 구해야 한다. 안 빼면 오래 남은 행 때문에 알람이 곧바로 울려 새 댓글이 3분 묶음 없이 나간다(10장)

## 5. API — `GET /api/notifications`·`POST /api/notifications/read`

### 5.1 `?kinds=` (계약)

| 값 | 결과 |
| --- | --- |
| 없음 | `NOTIFICATIONS_DEFAULT_KINDS`(`mention`·`reply`) — **지금과 응답·ETag 가 글자까지 같다** |
| `mention,reply,comment` 처럼 쉼표로 이은 종류 | 그 종류만 목록·`unread` 에. 순서는 상관없고 겹친 것은 하나로 |
| 빈 문자열(`?kinds=`), 빈 조각(`mention,,reply`), 모르는 이름(`like`), 대소문자 다름(`Mention`), 공백 붙음(`mention, reply`), 길이 64자 초과 | 400 `{ "error": "invalid", "field": "kinds" }` |

- 판정 순서: 인증 → `limit`(지금 그대로) → `kinds` → ETag/304 → 질의. 400 은 D1 을 부르지 않는다(인증이 이미 읽은 것 말고)
- `kinds` 를 여러 번 주면(`?kinds=a&kinds=b`) 첫 값만 본다(`URLSearchParams.get`, `limit` 과 같다)
- 목록과 `unread` 둘 다 같은 종류 조건을 쓴다. 목록은 계속 `notifications_recipient_order` 색인을 탄다(m3)

### 5.2 응답 모양

- `NotificationsResponse` 그대로. 항목의 `kind` 가 `NotificationKind` 가 된다(2.1). 새 필드 없음 — `push_due_at` 은 내보내지 않는다

### 5.3 ETag (계약)

- `notificationsEtag({ userId, rev, limit, kinds? })`. 종류를 `NOTIFICATION_KINDS` 순서로 정규화해 **`NOTIFICATIONS_DEFAULT_KINDS` 와 같으면(또는 `kinds` 가 없으면) 지금 모양** `W/"n1-{userId}-{rev}-{limit}"`, 다르면 **꼬리 `-{종류를 . 으로 이음}`**:
  - `?kinds=comment,mention,reply` → `W/"n1-{userId}-{rev}-{limit}-mention.reply.comment"`
  - `?kinds=reply,mention` → `W/"n1-{userId}-{rev}-{limit}"`(기본과 같다)
- 이유: 같은 리비전이어도 종류에 따라 응답이 다르다(F-3001 4.5). 판 `n1` 은 그대로 — 꼬리가 없으면 옛 모양과 같다
- 리비전(`notif_rev`)은 지금처럼 **받는 사람 전원**에게 오른다. `comment` 행이 생기면 주인의 리비전이 올라, 옛 클라이언트는 목록이 같은데도 304 대신 200 을 한 번 받는다 — 60초 가져오기 한 번의 응답 크기뿐이라 두지 않는다

### 5.4 읽음 요청

- `READ_ALL_SQL`(그리고 그것을 잇는 `READ_IDS_SQL`)이 `read_at` 을 채울 때 **같은 문장에서 `push_due_at = NULL`** — 이미 읽은 행은 지금처럼 건드리지 않는다(`read_at IS NULL` 조건). 쓰는 행이 늘지 않는다(같은 행, 색인 없는 열)
- `{ all: true }` 는 종류와 상관없이 그 사람의 안 읽은 행 전부(Q3). 옛 클라이언트의 `모두 읽음` 은 보이지 않던 `comment` 행도 읽음으로 만든다
- 리비전·`write_count` 규칙 그대로(`changes()` 는 같다, 근거)

## 6. 금고(E2EE)

- 금고 문서에서는 `comment` 행도 0행이다 — 넣기 문장의 `DOC_WRITABLE` 과 `loadDocPeople` 의 `e2ee_key IS NULL` 이 그대로다(F-3001 3.9). 금고로 옮기면 그 문서 알림 행을 지우는 규칙(F-502 8장)도 그대로라 `comment` 행도 함께 지워진다
- 새 열 `push_due_at` 은 시각만 담는다

## 11. 열린 질문

### Q1. 매일 Cron 의 `push_due_at` 정리 — **사람 결정 필요. 기본값: 하지 않는다(F-3001 3.1·3.7·6장과 다름)**

- 승인된 개요는 "매일 Cron 이 `push_due_at` 이 1일보다 오래된 행을 NULL 로" 를 이 명세에 배정했다. 그 문장은 `push_due_at` 에 색인이 없어 **표 전체를 훑는다**(m3 `SCAN notifications`) — D1 읽기는 행 수만큼 매일 든다. F-3001 3.1 가정(1만 명, 알림 행 하루 10,800, 보관 90일, 받는 사람당 300 상한)이면 표가 수십만~약 100만 행이라 **하루 읽기 한도(500만)의 최대 약 20%** 를 이 한 문장이 쓴다(계산 — 잰 것 아님)
- 치우지 않아도 되는 이유: 남은 행을 읽는 곳은 F-3006 의 그 문서 알람뿐이고, 알람은 읽은 행을 **보냈든 뺐든 모두 NULL** 로 만들며 1시간(`PUSH_STALE_MS`)보다 오래된 묶음은 보내지 않는다(F-3001 3.4 ③⑤). 다음 알람이 오지 않는 문서의 행은 아무 질의도 읽지 않아 비용이 없다. 남는 위험은 "가장 이른 시각" 계산이 오래된 행을 집는 것 하나이고, F-3006 이 그 `MIN` 에서 오래된 행을 빼면 막힌다(4.4)
- 다른 안(개요 그대로): `cleanupComments` batch **끝**에 `UPDATE notifications SET push_due_at = NULL WHERE push_due_at IS NOT NULL AND push_due_at < ?`(`now − 1일`) 한 문장. 바뀌는 것: 1장 소유에 `worker/commentGc.ts`·`tests/worker/commentGc.test.ts`(결과 순서에 자리 하나, 로그 줄에 필드 하나), 7장에 그 테스트 한 행, 매일 읽기 = 알림 표 행 수 한 번 더. 기존 매일 정리가 이미 표를 여러 번 훑으므로(`created_at < ?` 지우기·고아 지우기, m3) 늘어나는 몫은 그 일부다
- 푸시가 꺼져 있을 때(비밀 값 없음)는 어느 안이든 `push_due_at` 이 채워지지 않는다(4.2)

### Q2. `push_due_at` 을 채울 때 구독의 세션까지 보나 — **기본값: 보지 않는다(구독 행이 있기만 하면)**

- 이유는 4.2. 보려면 넣기 문장에 지금 시각 ISO 바인딩 하나와 `auth_sessions` PK 조회가 받는 사람마다 더 든다. 틀린 경우의 대가(알람 한 번)가 작고, 보낼 때 F-3006 이 산 구독(F-3003 `listLivePushSubscriptions`)만 다시 읽는다
- 다른 안: F-3003 의 "산 구독" 조건(`session_id` NULL 이거나 `expires_at` > 지금)을 `EXISTS` 에 넣는다 — 로그아웃한 기기만 가진 사람의 행이 NULL 로 들어가 그 문서 알람이 덜 울린다. T2 에 "죽은 세션 구독만 있으면 NULL" 한 줄

### Q3. `{ all: true }` 가 `comment` 행까지 읽음으로 — **기본값: 그렇다(종류와 상관없이)**

- 이유: `모두 읽음` 의 뜻이 "내 알림 전부" 다. 몸통 계약(F-503 6.6 "정확히 `{ all: true }`")을 늘리지 않는다. 옛 클라이언트 사용자가 보이지 않던 `comment` 행을 함께 읽음으로 만드는 것은 새로고침 전 잠깐의 일이다
- 다른 안: 몸통에 `kinds` 를 더해 그 종류만 — `readTarget` 의 키 검사·F-503 6.6·N5 가 바뀌고, F-2111 이 몸통에 종류를 실어야 한다

### Q4. `NotificationItem.kind` 를 이 명세가 넓힌다 — **기본값: 그렇다(F-3001 6장은 F-2111 에 두었다)**

- 이유: 이 명세의 서버가 `?kinds=…comment` 에 `comment` 항목을 **돌려준다** — 응답 타입(`NotificationsResponse`)이 그것을 담아야 `worker/notifications.ts` 가 타입 검사를 통과한다. 클라이언트는 `isNotificationItem` 이 여전히 `comment` 를 거르므로(F-2111 전) 동작이 바뀌지 않는다
- 다른 안: 서버 쪽 행 타입만 넓히고 `NotificationItem` 은 F-2111 이 — 그 사이 `toItem` 이 `satisfies NotificationsResponse` 를 지키려면 형 변환이 하나 필요하다(타입이 거짓말을 한다)

### Q5. `comment` 행도 받는 사람당 300개 상한 안에 — **기본값: 그렇다(종류와 상관없이 하나의 상한)**
