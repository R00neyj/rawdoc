## 2. 풀어야 하는 구멍 — 낡은 역할 (Q1 의 근거)

- F-503 뒤 서버는 view 를 **닫지 않고** 읽기 전용 연결로 받는다(F-503 2.2). 읽기 전용 연결이 보낸 Yjs 갱신은 y-partyserver 가 **말없이 버린다**(F-503 t1) — 클라이언트에게 알리는 것이 없다
- 클라이언트가 문서를 여는 순간의 역할은 목록을 마지막으로 읽은 때의 값이다(k7). 그래서 아래 둘에서 **클라이언트는 편집 세션, 서버는 읽기 전용 연결** 이 된다:
  1. 목록을 읽은 뒤 소유자가 나를 edit → view 로 낮췄고, 그 뒤 이 문서를 연다
  2. 편집 세션이 끊긴 동안(네트워크·잠자기) 낮아졌고, 제어기가 다시 붙는다 — 서버 점검(F-503 3장)은 **연결 상태가 edit 인 연결** 만 닫으므로, 새로 붙은 view 연결은 닫히지 않는다
- 이때 사용자가 치는 글은 화면·`md-yjs` 에는 남고 서버에는 가지 않는다. 상태바는 `저장됨` 이다. **밀린 편집 러너(`yjsFlush`)도 `synced` 를 받아 그 기록을 "올렸음" 으로 표시한다** — 기록이 조용히 사라진다
- F-503 이전에는 서버가 view 를 `4403 forbidden` 으로 닫아 이 경우가 없었다. F-500 6장 "옛 클라이언트는 view 로 소켓을 열지 않는다" 는 옛 클라이언트의 **목록 역할이 맞을 때** 만 참이다
- 막는 방법 — 12장 Q1:
  - **(기본) 서버가 읽기 전용 연결에 `read-only` 메시지를 step 1 앞에 보낸다.** k1 에 따라 이 메시지는 `synced` 보다 반드시 먼저 온다 — 편집 세션은 `live` 가 되기 전에 안다
  - 다른 안: 클라이언트가 (다시) 붙을 때마다 역할을 서버에서 다시 읽는다. `GET /api/docs/:id` 에 역할이 없으므로(k7) `GET /api/shared` 를 통째로 읽어야 하고, 읽은 뒤 소켓이 열리기까지의 틈은 남는다

## 3. 경로 판정

### 3.1 `decideDocPath` (계약)

```ts
// src/app/docPath.ts — InitialDocPath 의 realtime 갈래
| { kind: 'realtime'; resume: boolean; startOffline: boolean; readOnly?: true }
```

위에서부터 처음 맞는 줄. `DocPathInput` 은 그대로다

| # | 조건 | 결과 | 지금과 비교 |
| --- | --- | --- | --- |
| 1 | 저장소가 `server` 가 아님, 공유 링크 화면 | `local` | 같음 |
| 2 | `e2ee` | `e2ee` | 같음 (F-405) |
| 3 | `forbidden` | `view` | 같음 |
| 4 | `role === 'view'` 이고 `online` | `{ kind: 'realtime', resume: false, startOffline: false, readOnly: true }` | **새로.** 지금은 `view` |
| 5 | `role === 'view'` 이고 오프라인 | `view` | 같음 |
| 6 | `hasPendingChanges` | `pending` | 같음 |
| 7 | 오프라인이고 기록 없음 | `offline-view` | 같음 |
| 8 | 그 밖 | `realtime`(`resume`·`startOffline` 지금 규칙) | 같음 |

- `readOnly` 키는 4번에만 넣는다 — 나머지 `realtime` 결과 객체에는 키가 없다(기존 `toEqual` 단언이 그대로 통과한다)
- 4번이 6·7번보다 앞인 이유: view 는 올릴 것이 없다. outbox 에 이 문서 항목이 남아 있어도(edit 였다가 낮아진 경우) 서버가 받지 않으므로 `pending` 경로의 잠금·PUT 은 뜻이 없다. `md-yjs` 기록도 쓰지 않는다(4장)
- 5번 — 개요 Q5(오프라인 view 는 댓글 안 보임) 그대로. 오프라인에서 여는 view 문서는 지금처럼 저장소 본문을 읽기 전용으로 띄운다

### 3.2 App 의 두 판정 자리

- **렌더 중 빠른 판정**(문서·저장소가 바뀐 렌더)과 **판정 effect**(outbox·기록·금고 여부를 기다린 뒤) 두 곳이 `decideDocPath` 를 부른다. 지금 effect 는 `role: undefined`·`forbidden: accountBlocked` 를 넘긴다 — view 는 빠른 판정이 이미 `view` 로 끝냈기 때문이다. 이 명세 뒤에는 빠른 판정이 view 를 `realtime` 으로 내므로(`online: true` 가정) **effect 판정이 view 를 다시 가려야 한다**
- 규칙: 두 자리에 **같은 `role`·`forbidden`** 을 넘긴다 — `role` 은 `currentDoc?.role`, `forbidden` 은 `forbiddenDocIds.has(id) || accountBlocked`. effect 는 `online` 에 `navigator.onLine` 을 넘긴다(지금 그대로). 세션을 만든 때의 값을 `DocSession` 에 담을지 ref 로 읽을지는 구현이 고른다
- `DocSession` 에 `readOnly: boolean` 을 더한다. 4번 결과면 참, 그 밖은 거짓. **읽기 전용 세션은 `persist: null`, `resume: false`, `startOffline: false`** — `md-yjs` 를 쓰지 않는다(개요 4.1, Q5)
- 빠른 판정의 결과를 곧바로 경로로 쓰는 것은 지금처럼 `local`·`view`·`e2ee` 셋뿐이다. view 온라인은 effect 를 기다린다 — 온라인 여부를 effect 에서 읽기 때문이다

### 3.3 view 문서를 여는 경로 표 (반드시 결론 1)

- **첫 동기화 전 `4403` 에서 N1 을 띄우지 않는 이유**: N1 `편집 권한이 없어 읽기만 할 수 있습니다.` 는 "편집하려 했는데 보기만 된다" 는 뜻이다. view 는 처음부터 보기만 했고, 문서를 열 때 `보기 권한만 있는 문서입니다.` 를 이미 본다. 달라지는 것은 실시간 반영·댓글이 없다는 것뿐이고, 그것은 레일의 C8 이 말한다
- **폴백을 모두 `view` 로 보내는 이유**: `fallback` 경로는 잠금 + 본문 PUT 으로 **한 명씩 편집** 하는 길이다(F-305 7.2). view 는 쓸 것이 없으므로 그 길이 뜻이 없다. 개요 4.1 "첫 동기화 전 실패(`fallback` 이 될 자리)면 지금의 `view` 로 연다"
- **`4404` 를 `view` 로 보내지 않는 이유**: 지금 편집 세션의 첫 동기화 전 `4404` 처리(저장소 본문 + N3 + 사이드바 새로 읽기, 금고로 바뀌었으면 조용히 다시 시작 — F-407 7.4)가 view 에도 그대로 맞다. 새 분기를 만들지 않는다

### 3.4 오프라인 view 가 온라인이 되면

- 지금은 `offline-view` 경로만 `online` 이벤트에 세션을 새로 시작한다(F-306 5.2 — App 의 `isOfflineView` effect). 이 조건을 **"`offline-view` 이거나, `view` 이면서 `fallbackReason === 'offline'`"** 으로 넓힌다
- 그래서 오프라인에서 연 view 문서는 연결되면 저절로 읽기 전용 실시간 세션이 되고 레일의 C8(`… 실시간 연결이 되면 보입니다.`)이 말한 대로 댓글이 보인다
- 다른 사유의 `view`(시간 제한·안 열림·`4403`·막힌 계정)는 저절로 다시 붙지 않는다 — 다시 해도 대개 같다(F-305 22장 Q2 와 같은 판단). 사용자가 문서를 다시 열면 새로 판정한다

## 5. 연결 제어기 — `src/app/liveDoc.ts`

### 5.1 계약

```ts
export type StopReason = 'signed-out' | 'forbidden' | 'not-found' | 'revoked' | 'deleted' | 'read-only'

// LiveDocDeps 에 더한다
readOnly?: boolean      // 읽기 전용 세션. 기본 false

// LiveDocController 에 더한다
send(text: string): boolean                                   // 단계가 live 이고 소켓이 있을 때만 보낸다. 보냈으면 true
subscribeCustom(listener: (text: string) => void): () => void // DocRoomMessage 가 아닌 문자열 메시지를 받는다
```

- `'read-only'` 는 **편집 세션**이 첫 동기화(재개 세션은 `ready`) 전에 서버의 `read-only` 메시지를 받았을 때만 나오는 멈춤 사유다(5.3)
- 읽기 전용 세션의 닫기 분류·시간 제한·`goOffline`·재연결·keepalive 는 **비재개 편집 세션과 한 글자도 다르지 않다.** 결과를 어느 경로로 보낼지는 App 이 정한다(3.3·8.2)
- `send` 가 `live` 에서만 보내는 이유: 명령은 오프라인 대기열이 없다(개요 3.1 "view 는 연결돼 있을 때만 댓글을 단다"). 첫 동기화 전에는 앵커를 만들 편집기도 없다
- `subscribeCustom`: 지금 `onCustom` 은 `parseDocRoomMessage` 로 `too-large`·`size-ok` 만 본다. 그 파서가 `null` 을 돌려준 문자열을 구독자들에게 넘긴다(F-503 4.1 "클라이언트는 받은 문자열을 두 파서에 차례로 넘긴다"). 명령 응답은 명령 클라이언트가 `parseCommentOpReply` 로 읽는다
- `liveStatusOf`: `stopped` + `'read-only'` → `'revoked'`. 이 상태는 App 이 곧바로 세션을 다시 시작하므로(8.2) 거의 보이지 않는다

### 5.2 알림 띠 — 읽기 전용 세션의 문구

지금 N2~N6 은 편집하는 사람에게 쓴 글이다(`편집 권한이 없어져`, `지금 화면의 내용은 새 문서로 저장할 수 있습니다`, `편집은 이 브라우저에 저장되고`). 읽기 전용 세션에서는 아래로 바꾼다. 형식은 `specs/ia.md` 4.2 표

| 밀린 편집 러너(`yjsFlush`) | 첫 메시지 | `ready` 전이라 `'read-only'` | `outcomeOf` 가 `stopped` 의 나머지 사유를 `'forbidden'` 으로 본다 — **`synced` 로 보지 않으므로 기록을 "올렸음" 으로 표시하지 않는다**. `yjsFlush.ts` 는 고치지 않는다 |

- 비재개 편집 세션에서 목록 역할을 고치고 곧바로 다시 여는 이유: 편집기가 아직 없어 잃을 글이 없다. 사용자에게는 "잠깐 `불러오는 중…` 이 길어졌다가 읽기 전용으로 열림" 으로 보인다
- 재개·동기화 뒤에 목록 역할을 고치지 않는 이유: 편집기에 서버에 못 올린 글이 있을 수 있다. 다시 시작하면 그 편집기가 사라진다. N2 의 `새 문서로 저장` 이 그 글을 건지는 길이다
- 이 표의 메시지는 `synced` 보다 먼저 온다(k1) — 편집 세션이 `live` 인 채 치는 틈이 없다

### 5.4 본문 편집을 막는 것 (반드시 결론 3)

겹겹으로 막는다. 새 코드는 3번과 4번의 입력뿐이다

1. **편집기 읽기 전용** — `isReadOnlyDoc` 에 `isRealtime && docSession.readOnly` 를 더한다(지금도 `isReadOnlyByRole` 이 `role === 'view'` 로 참이지만, 판정 입력과 같은 값을 직접 보게). 편집기는 `setReadOnly(true)` → `EditorState.readOnly` + `EditorView.editable(false)`(`createEditor.ts` `readOnlyExtensionsFor`). 기본 명령·입력·붙여넣기·끌어넣기·되돌리기(`yBinding.ts` `stackCommand` 가 `state.readOnly` 면 거절)가 막힌다
2. **제목** — `titleReadOnly` 가 `isReadOnlyDoc` 을 따른다(지금 그대로)
3. **awareness** — 내 상태 `null`(4장). 커서를 보내지 않는다
4. **서버** — 편집기 읽기 전용이 못 막는 프로그램 편집이 편집기 Doc 에 생겨도, 게이트 → 방 Doc → provider 로 나간 갱신을 y-partyserver 가 적용하지 않고 버린다(F-503 Y1). 그런 편집은 **이 화면에만** 남는다 — 지금 view 경로에서 편집기에만 남는 것과 같은 성질이다
- 댓글은 편집기 Doc 에 직접 쓰지 않는다 — 명령 쓰기 수단만 쓴다(7.1)

## 6. 명령 채널 (반드시 결론 2)

### 6.1 `LiveSocket.send` — `src/storage/liveSocket.ts`

```ts

  ping(): void
  close(): void
  send(text: string): boolean   // __YPS: 를 붙여 보낸다. 소켓이 OPEN 이 아니거나 끝났으면 보내지 않고 false
```

- `provider.sendMessage` 는 소켓 상태를 보지 않는다(k2). `ping()` 처럼 `ws.readyState === ws.OPEN` 일 때만 보낸다 — 던지지 않는다

### 6.2 제어기의 두 입구 — 5.1

- `send(text)`: 단계가 `live` 이고 지금 시도의 소켓이 있으면 `socket.send(text)` 의 결과, 아니면 거짓

### 6.3 세션 잇기 — `useLiveDoc`

- 읽기 전용 세션이면 명령 클라이언트(6.4)를 만들어 `send` 에 제어기의 `send` 를, 제어기의 `subscribeCustom` 에 클라이언트의 `receive` 를 잇는다
- **연결을 잃음**: 스냅숏 단계가 `live` 에서 다른 것으로 바뀔 때마다 `connectionLost()` 를 부른다. 동기화 뒤 소켓이 닫히면 제어기는 늘 `live` → `reconnecting`(또는 `stopped`) 으로 간다 — 한 소켓에서 보낸 명령이 다음 소켓의 응답을 기다리는 일이 없다
- 세션이 끝나면(문서 전환·정리) `dispose()` — 남은 명령은 `offline` 으로 끝난다

### 6.4 명령 클라이언트 — `src/app/commentOps.ts` (계약)

```ts
import type { CommentOp, CommentOpRejectReason } from '../lib/docRoomProtocol'

export const COMMENT_OP_TIMEOUT_MS = 10_000          // 보낸 뒤 응답을 기다리는 시간
export const COMMENT_OP_CLIENT_WINDOW_MS = 61_000    // 클라이언트 속도 창 — 이 안에서 COMMENT_OPS_PER_MINUTE(30)개까지 보낸다

export type CommentOpOutcome =
  | { ok: true }
  | { ok: false; reason: CommentOpRejectReason | 'offline' | 'no_response' }

export type CommentCommandClient = {
  request(op: CommentOp, isApplied: () => boolean): Promise<CommentOpOutcome>
  receive(text: string): void    // 명령 응답이 아니면 무시
  recheck(): void                // 기다리는 명령 중 isApplied() 가 참인 것을 곧바로 성공으로 끝낸다
  connectionLost(): void
  dispose(): void
}

export function createCommentCommandClient(deps: {
  send(text: string): boolean
  now(): number
  setTimeout(fn: () => void, ms: number): unknown
  clearTimeout(handle: unknown): void
}): CommentCommandClient
```

- `isApplied` = "이 명령이 바라는 결과가 이미 편집기 Doc `comments` 에 있는가". 명령 쓰기 수단(6.6)이 명령마다 만든다

### 6.5 명령 하나의 생애 — 규칙

**보내기** (`request`)

1. **속도 먼저**: 이 클라이언트가 지난 `COMMENT_OP_CLIENT_WINDOW_MS` 안에 보낸 명령이 30개면 **보내지 않고** `rate_limited`. 보낸 것만 센다(보내지 못한 것·로컬 검사에서 걸린 것은 세지 않는다)
2. `deps.send(encodeCommentOp(op))` 가 거짓이면 곧바로 `offline`
3. 보냈으면 기다림 목록 끝에 넣고 `COMMENT_OP_TIMEOUT_MS` 타이머를 건다

**끝내기** — 먼저 오는 하나로 끝나고, 끝난 명령은 목록에서 빠진다

| 무엇이 | 결과 |
| --- | --- |
| `comment-ack`(같은 `id`) | 성공 |
| `comment-reject`(같은 `id`) | `{ ok: false, reason }` — 서버 사유 그대로 |
| `recheck()` 때 `isApplied()` 참 | 성공 (ack 를 기다리지 않는다 — 개요 4.4 "ack 가 오기 전이라도 Yjs 로 항목이 먼저 보이면 그 카드를 쓴다") |
| 시간 제한 | `isApplied()` 참이면 성공, 아니면 `no_response` |
| `connectionLost()` | `isApplied()` 참이면 성공, 아니면 `offline` |
| `dispose()` | 위와 같다 |

- **응답 짝짓기**: 같은 `id` 로 기다리는 명령이 여럿이면(같은 스레드를 해결했다가 곧바로 다시 열기) 응답은 **먼저 보낸 것부터** 짝짓는다 — 서버는 한 연결의 명령을 받은 차례대로 끝내고 응답도 그 차례로 보낸다(F-503 4.2). 기다리는 것이 없는 응답(이미 `recheck` 로 끝난 명령의 늦은 ack, 앞 소켓의 응답)은 버린다
- **다시 보내지 않는다.** 연결을 잃은 명령은 다음 소켓으로 옮기지 않는다 — 재연결 사이에 같은 스레드를 남이 지웠거나 해결했을 수 있어, 사람이 다시 누르는 편이 맞다(F-500 6장 "재연결 때 대기 명령 버리기")
- **응답이 없는 두 경우**(F-503 4.4 0·1번 — 방이 사라졌거나 불러오지 못함, 읽을 수 없는 명령)는 시간 제한이 끝낸다
- `COMMENT_OP_TIMEOUT_MS = 10,000` 의 근거: 서버 처리는 명령 하나 1.3~1.6ms(F-503 t5, node). 남는 것은 왕복과 잠든 DO 를 깨워 불러오는 시간인데 **재지 않았다**. 첫 동기화 시간 제한(`FIRST_SYNC_TIMEOUT_MS`)과 같은 값으로 둔다 — 같은 서버가 같은 방을 깨워 답하는 일이다
- `COMMENT_OP_CLIENT_WINDOW_MS = 61,000` 의 근거(k5): 60,000 이면 도착 지연 200ms 에서 서버 거절이 생겼고, 61,000 은 지연 1초까지 0이었다. 창을 1초 넓혀 정직한 클라이언트가 서버 `rate_limited` 를 보지 않게 한다(개요 2.5 "정직한 클라이언트는 서버 거절을 보지 않는다"). 서버 거절이 와도 같은 C5 로 보인다

### 6.7 같은 댓글을 두 번 만들지 않기 — `id` 다시 쓰기

- 문제: `comment-add` 가 서버에 닿아 쓰였는데 갱신·ack 가 오기 전에 소켓이 끊기면, 클라이언트는 `offline`(C4)을 보이고 입력 글을 남긴다. 다시 붙으면 동기화로 그 항목이 온다. 사용자가 남은 글을 다시 보내면 **같은 댓글이 둘** 된다
- 규칙: 쓰기 수단은 `add`·`reply` 가 **`offline` 또는 `no_response`** 로 끝났을 때 그 명령(종류·`id`·정규화한 본문·`add` 면 앵커 JSON, `reply` 면 부모)을 **한 건** 기억한다. 다음 `add`·`reply` 가 종류·본문·(앵커 JSON 또는 부모)이 모두 같으면 **그 `id` 를 다시 쓴다**. 서버는 같은 키에 올바른 값이 있고 작성자가 보낸 사람이면 쓰지 않고 ack 한다(F-503 4.4 add 6번) — 곧 이미 쓰였으면 둘이 되지 않고, 안 쓰였으면 새로 쓰인다
- 기억은 다른 결과(성공·다른 실패)가 나거나 입력이 달라지면 버린다. 앵커 JSON 이 같으려면 같은 후보여야 한다 — 7.3 의 보관한 후보가 그것을 보장한다
- **알려진 한계**: 사용자가 C4 를 보고 글을 **고쳐서** 다시 보내면 새 댓글이 된다. 처음 것이 서버에 쓰였다면 둘이 남는다. 앞의 것은 사용자가 지울 수 있다(자기 댓글)

### 6.8 서버 `read-only` 메시지 (Q1 — 계약)

```ts
// src/lib/docRoomProtocol.ts
export type DocRoomMessage =
  | { type: 'too-large'; limit: number; bytes: number }
  | { type: 'size-ok' }
  | { type: 'read-only' }      // 이 연결은 읽기 전용이다 (F-506). 키가 type 하나
```

- 서버: `DocRoomCore.connect` 가 "문서 없음 → `4404`" 판정을 지난 뒤, **`sendSyncStep1` 을 부르기 전에** 연결 상태가 읽기 전용(`isReadOnlyState`)이면 `host.sendCustom(conn, encodeDocRoomMessage({ type: 'read-only' }))` 를 한 번 보낸다. edit·소유자 연결에는 보내지 않는다
- step 1 앞에 두는 이유: k1 로 순서는 어느 자리든 `synced` 보다 앞이지만, 첫 메시지로 두면 클라이언트가 방 Doc 에 서버 상태를 적용하기 전에 멈출 수 있다
- `parseDocRoomMessage` 는 `{ type: 'read-only' }` 를 돌려준다. 다른 키가 더 있어도 `type` 만 본다(지금 `size-ok` 와 같은 관대함)
- **옛 클라이언트와의 호환**: 옛 `parseDocRoomMessage` 는 모르는 `type` 에 `null` 이라 무시한다. 배포는 F-501~F-509 를 한 번에 한다(F-500 6장)
- 이 메시지는 명령 계약(`CommentOp`·`CommentOpReply`)을 바꾸지 않는다. `parseCommentOpReply` 는 이 문자열에 `null` 이다(키 집합이 다르다)

## 7. 댓글 화면에 더하는 것 (F-505 파일)

### 7.1 `CommentAccess` 명령 갈래 — `commentRail.ts`

```ts

| { kind: 'write'; via: 'command'; actor: CommentActor; author: CommentAuthor; connected: boolean }

// CommentAccessInput 에 더하는 필드
```

- F-505 3.1 의 판정 순서에서 **3번(`local`) 다음, 4번 앞** 에 한 줄: `docPath === 'realtime'` 이고 `liveReadOnly` 면 —

### 7.2 입력칸·버튼 — `CommentComposer.tsx`·`CommentThread.tsx`

| 상태 | 새 댓글 입력 카드 | 답글 입력칸 | `해결`/`다시 열기` | `⋯` → `삭제`(D-11 `삭제`) |
| --- | --- | --- | --- | --- |
| 명령, 연결됨, 쉬는 중 | F-505 그대로 | 그대로 | 그대로 | 그대로 |

## 12. 열린 질문 / 사람 결정 필요

### Q1. 서버가 view 연결에 `read-only` 메시지를 보내나 — **사람 결정 필요. 기본값: 보낸다(6.8)**

- 사용자는 "F-503 의 서버 계약은 커밋된 그대로 따른다" 고 했다. 이 안은 F-503 계약을 바꾸지 않고 **서버 → 클라이언트 메시지 한 종류를 더한다**(`DocRoomMessage` 갈래 하나, `connect` 한 줄). 그래도 커밋된 서버 파일을 고치므로 묻는다
- 기본값의 이유(2장): 낡은 역할로 편집 세션을 연 사람의 글이 **말없이** 서버에 가지 않고, 밀린 편집 러너가 그 기록을 "올렸음" 으로 지운다. F-503 이전에는 생기지 않던 일이고, F-503 이 view 를 받아 주면서 생겼다. 메시지는 `synced` 보다 먼저 오므로(k1) 편집 세션이 `live` 인 채 치는 틈이 없다
- **다른 안 A — 클라이언트가 붙을 때마다 역할을 다시 읽는다**: 공유 문서의 편집 세션이 소켓을 열기 전에 `GET /api/shared` 를 읽어 그 문서의 역할을 본다. 서버를 고치지 않는다. 대신 재연결마다 요청 하나(목록 전체)가 늘고, 읽은 뒤 소켓이 열리기까지의 틈에 낮아지면 여전히 샌다. 소유 표에서 `docRoomProtocol.ts`·`worker/docRoomCore.ts` 와 두 테스트가 빠지고 `liveDoc.ts`·`useLiveDoc.ts` 에 역할 확인 단계가 생긴다. 5.3 표는 "역할 확인에서 view" 로 바뀌고 E11·E12 의 방 쪽 준비가 `/api/shared` 응답 바꾸기로 바뀐다
- **다른 안 B — 이 명세에서 막지 않는다**: 2장의 구멍을 알려진 한계로 두고 따로 명세로 연다. M5 배포 전에 막지 않으면 F-503 이 나가는 순간부터 생긴다 — 권하지 않는다

### Q2. 첫 동기화 전 `4403` 의 view — **기본값: 조용히 `view`, N1 없음(3.3)**

- 다른 안: N1 을 그대로 띄운다. 얻는 것: 소유자가 막혀 실시간이 안 되는 것을 알 수 있다. 치르는 것: `편집 권한이 없어` 는 view 에게 틀린 말이라 새 문구가 필요하다. E8 의 기대가 바뀐다

### Q3. 연결 중 승격(view → edit) — **기본값: 다시 붙지 않는다(3.3 마지막 줄)**

- F-503 3장대로 그 연결은 끝까지 읽기 전용이다. 클라이언트는 승격을 알 길이 없다(Q1 메시지는 view 연결에만 간다). 목록을 새로 읽은 뒤(새로고침 등) 문서를 열면 편집 세션이 된다
- 다른 안: 서버가 모든 연결에 역할을 알린다(`{ type: 'role', role }`) — 읽기 전용 세션이 edit 를 받으면 다시 붙는다. Q1 메시지를 넓히는 것이고, 연결 중 승격은 여전히 알리지 않으므로(서버는 승격된 연결을 닫지 않는다) 얻는 것이 "다시 붙을 때" 뿐이다
