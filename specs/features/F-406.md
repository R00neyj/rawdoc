## 2. 올리기 — 판정 순서·저장 모양

### 2.1 계약 — `src/types.ts`

```ts
export type Attachment = {
  // … 지금 필드 그대로
  // 저장소 층: blob 이 봉투(바이너리 그대로)다 / 앱 층(withE2ee 가 돌려준 것): 금고 첨부를 복호화한 평문이다
  e2ee?: true
}

putAttachment(input: {
  // … 지금 필드 그대로 (blob·mime·ext·width·height·id)
  // 앱 층: "이 이미지를 금고 첨부로 암호화해 넣어라" / 저장소 층: "blob 은 이미 봉투다"
  e2ee?: true
}): Promise<{ id: string; ext: AttachmentExt }>

// 둘째 인자: 캐시·원문에서 확장자를 못 찾을 때 서버 저장소가 쓸 확장자. idb·메모리 저장소는 무시한다
getAttachment(id: string, hint?: { ext: AttachmentExt }): Promise<Attachment | null>
```

- 일반 첨부는 **키까지 지금과 같다** — `e2ee` 는 값이 있을 때만 싣는다(행·캐시·응답 모두). F-405 3.1 과 같은 이유다(`toEqual` 로 행을 보는 기존 테스트)
- `e2ee` 한 이름이 두 층에서 뜻이 다른 것은 F-405 `create({ e2ee })` 와 같은 방식이다. `withE2ee` 가 앱 층 뜻을 받아 저장소 층 뜻으로 바꿔 내려보낸다

### 2.2 판정 순서 (번호가 계약이다 — 모두 **암호화 전 평문**으로)

금고 문서에 붙여넣기·끌어놓기 (`App.handleImageFiles` → `attachImages(files, { store, source, e2ee: true })`):

1. **`attachImages`** — 지금 순서 그대로: 파일 20MB 이하 → 형식(`inspectImageBytes`) → 가로·세로 10,000px·면적 40,000,000 이하 → `shrinkImage`(긴 변 2,000px 초과면 줄여 WebP, 아니면 WebP 가 더 작을 때만 WebP)
2. **`attachImages`** — 결과 크기 상한이 **금고면 `E2EE_MAX_PLAIN_ATTACHMENT_BYTES`(5,242,811 B)**, 아니면 지금의 5,242,880 B. 넘으면 지금 문구(`GIF 는 한 장에 5MB 까지 넣을 수 있습니다.` / `이미지는 줄인 뒤에도 5MB 를 넘어 넣지 못했습니다.`) — 69 B 차이라 문구는 바꾸지 않는다
3. **`attachImages`** — 금고면 `width`·`height` 가 1 이상 정수가 아니면 형식 문구 `PNG·JPEG·GIF·WebP 이미지만 넣을 수 있습니다.` (서버가 `w`·`h` 를 1 이상 정수로만 받는다 — F-402 3.1. 올리기에서 400 을 받아 이미지가 사라지는 것보다 넣을 때 막는 쪽)
4. `store.putAttachment({ blob, mime, ext, width, height, e2ee: true })` → **`withE2ee.putAttachment`**:
   1. MK 가 없으면 `E2eeStoreError('locked')`, 아무것도 쓰지 않는다
   2. 아래 저장소가 `server` 이고 `ext` 가 `png`·`jpg` 면 `toWebp(blob)` — 서버 저장소 평문 경로와 같은 규칙(k10). 결과가 원본과 다르면 `ext 'webp'`·`mime 'image/webp'`. 가로세로는 그대로(같은 비트맵). `idb` 는 지금처럼 바꾸지 않는다
   3. 평문 바이트가 `isPlainAttachmentTooLarge` 면 `E2eeStoreError('too-large')` (2번이 이미 막으므로 방어용이다 — 4.2 변환 뒤 크기는 늘지 않는다, k10)
   4. 첨부 id 를 **여기서** 정한다(16진 소문자 16자, `crypto.getRandomValues`). 아래 저장소 `getAttachment(id)` 가 값을 돌려주면 다시 뽑는다 — AAD 에 id 가 들어가므로 아래 저장소가 id 를 정하게 두면 안 된다(F-405 4.2 문서 id 와 같은 이유)
   5. `encryptAttachment(MK, id, 평문)` → 봉투
   6. 아래 `putAttachment({ blob: 봉투 Blob(형식 application/octet-stream), mime: 이미지 mime, ext, width, height, id, e2ee: true })`
   7. `{ id, ext }` 를 돌려준다 — 원문에 들어가는 줄은 지금과 같은 `attachments/{id}.{ext}` 다
5. **서버 저장소** — `id` 를 받았으므로 변환을 건너뛴다(지금 그대로). 한도 사전 검사(F-221)는 봉투 크기로. 캐시 행 `e2ee: true`, outbox `upload`(모양 그대로)
6. **보내기** — `upload` 항목의 캐시 행이 `e2ee` 면 `PUT /api/attachments/{id}.{ext}?e2ee=1&w={width}&h={height}`. `w`·`h` 는 캐시 행의 값 = 1번 `shrinkImage` 결과의 가로세로(2번 `toWebp` 는 가로세로를 바꾸지 않는다)

- 금고가 아닌 문서의 붙여넣기는 **한 글자도 바뀌지 않는다**(`e2ee` 를 넘기지 않으면 `attachImages`·`withE2ee` 모두 지금 경로)
- `attachImages` 가 `putAttachment` 의 던짐을 문구로 바꾸는 규칙에 한 줄: `isE2eeStoreError(err, 'locked')` → F-405 E20 `금고가 잠겨 있어 저장하지 못했습니다. 금고를 연 뒤 다시 해 주세요.`, `'too-large'` → 2번 문구. 그 밖(한도 초과 `quota_exceeded` 이름, 그 외)은 지금 그대로
- 잠긴 금고 문서에는 편집기가 없어(F-405 6.2) 붙여넣기 자체가 일어나지 않는다. 붙여넣는 도중 잠기면: 단계 동안 MK 가 남아 있어(F-405 c7) 암호화·저장은 끝난다 — 봉투만 쓰므로 새는 것이 없다

### 2.3 저장 모양 — 로컬(로그인 없음) 금고 첨부

- 저장소 `md-docs`(F-404 가 올린 v5 그대로)의 **기존 `attachments` 스토어**, 키 `id`. 새 스토어를 만들지 않는다. 금고 문서 행과 같은 DB 라 한쪽만 지워지는 일이 없다(F-400 4.1)

```ts
// md-docs attachments 스토어의 금고 첨부 행 — 일반 첨부 행에 e2ee 만 더한다
{
  id: string          // 16진 소문자 16자 (AAD "att:{id}")
  mime: string        // 평문 이미지 mime — 'image/webp' 등. 복호화한 Blob 의 형식
  ext: 'png' | 'jpg' | 'gif' | 'webp'
  size: number        // 봉투 바이트 = 평문 + 69 (idbStore 가 blob.size 로 채운다 — 서버 행과 같은 뜻, F-402 3.1)
  width: number       // 평문 이미지 가로 (2.2 1번 결과)
  height: number
  createdAt: number
  blob: Blob          // 봉투, 형식 'application/octet-stream'
  e2ee: true
}
```

- 서버 캐시(`md-remote` `attachments`)의 금고 첨부 행도 같은 모양에 `userId`·`uploaded` 가 붙는다. **다른 기기에서 받아 넣은 행**(4.3)은 `width`·`height` 가 `0` 이다 — 봉투로는 잴 수 없고, `withE2ee` 가 복호화한 뒤 평문 머리에서 잰다(3.3)
- 로컬 금고도 평문 상한 5,242,811 B 를 지킨다 — 로그인 이관(F-408)이 그대로 올릴 수 있어야 한다
- **버전을 올리지 않는다**: 새 필드는 기존 행의 값이고 IndexedDB 는 값 모양을 검사하지 않는다(F-405 c2 와 같은 판단). 이 명세 이전의 행은 `e2ee` 가 없어 일반 첨부로 읽힌다 — 이 명세 전에는 금고 첨부가 없었으므로 맞다

## 3. 표시 — 복호화한 `blob:` 과 그 수명

### 3.1 편집기 이미지 장식이 금고 첨부를 그리는 길 (불변식 "장식은 문서 내용을 바꾸지 않는다")

- **원문은 그대로다.** 금고 문서 본문의 이미지 줄은 지금과 같은 `![…](attachments/{id}.{ext})` 3줄 블록이고, 편집기 `Y.Text` 에도 저장 평문에도 그 글자 그대로 있다. `blob:` 주소는 **장식(`ImageWidget`)이 그린 `<img>` 의 `src` 에만** 있다 — 지금 일반 첨부가 IndexedDB 의 `Blob` 을 `blob:` 으로 그리는 것과 같은 길이다(F-157 2.2)
- 흐름: `ImageWidget.toDOM` → `loadAttachment` → App `resolveAttachment(id)` → 감싼 저장소 `store.getAttachment(id)` → **`withE2ee.getAttachment`** 가 봉투를 복호화한 평문 `Blob` 을 돌려준다(3.3) → 위젯이 `createAttachmentUrl` 로 주소를 만든다(3.2)
- 장식·편집기·`imageBlock.ts` 의 해석 규칙은 바꾸지 않는다. 위젯이 받는 `AttachmentRecord` 에 `e2ee?: true` 한 필드가 더해질 뿐이다
- **금고 첨부는 금고 문서에서만 그린다** (12장 Q1): App `resolveAttachment` 는 **그 편집기·보기 화면이 보여 주는 문서**가 금고 문서가 아니면(`e2ee` 없음) `e2ee` 가 붙은 첨부를 `null` 로 돌려준다 → 위젯이 지금 자리 표시 `이미지를 찾을 수 없습니다` 를 그린다. 이유:
  1. 일반 문서는 잠가도 편집기가 내려가지 않는다. 거기에 복호화한 그림이 그려져 있으면 주소를 거둬도 이미 그린 `<img>` 는 화면에 남는다
  2. 일반 문서에 금고 이미지 줄을 복사해 넣은 경우(F-402 3.2) 서버는 초대·공개로 그 이미지를 내주지 않는다 — 소유자 화면만 보이면 "공유해도 보인다" 로 오해한다. 모두에게 같게 안 보인다
- 판정 기준은 호출 시점의 "지금 문서" 가 아니라 **그 편집기·보기 화면이 만들어질 때의 문서**다 — 문서를 바꾸는 순간 이전 편집기에서 늦게 풀린 요청이 새 문서 기준으로 판정되지 않게. 구현 방법(문서마다 콜백을 만들기, 위젯 쪽에 문서 id 를 넘기기 등)은 재량
- 인쇄(`printDoc` 에 넘기는 `resolveAttachment`)도 같은 함수라 같은 규칙이다

  2. 편집기 파괴 뒤에 풀린 `loadAttachment` 가 만든 주소는 지금 코드에서 영영 거둬지지 않는다(k5). 목록은 그것도 잡는다
- `printDoc.ts` 는 `fillAttachmentImages` 가 돌려준 주소를 인쇄 뒤 `URL.revokeObjectURL` 로 거둔다 — 고치지 않는다. 그 주소는 목록에 남은 채 이미 거둬진 상태가 되고, 다음 잠그기가 다시 거두는 것은 해가 없다(없는 주소 거두기는 아무 일도 안 한다). 글자열 몇 개가 남는 것뿐이라 받아들인다

### 3.3 `withE2ee.getAttachment` 규칙

1. **확장자 힌트**(4.2): 기억(F-405 4.4) 속 금고 문서 평문에서 `attachments/{id}.{ext}` 를 찾아 얻은 `ext`. 못 찾으면 힌트 없이
2. 아래 `getAttachment(id, 힌트)` → 레코드. `null` 이거나 `e2ee` 가 없으면 **그대로** 돌려준다(일반 첨부 — 금고 문서가 참조하는 평문 첨부도 여기)
3. `e2ee` 이면: 시작할 때의 MK 와 세대 값을 적는다. MK 가 없으면 `null`
4. 봉투 바이트 → `decryptAttachment(MK, id, 봉투)` → 평문. 실패(`decrypt-failed`·`bad-envelope`·`unsupported-version`)면 `null` + `console.error('e2ee_attachment_decrypt_failed', id)` 를 첨부 id 마다 페이지 수명에 한 번
5. 평문 머리를 `inspectImageBytes` 로 읽어 가로·세로를 얻는다. 못 읽으면(이미지가 아님) 4번 실패와 같게
6. **끝날 때 다시 본다**: 세대 값이 바뀌었거나 `getMasterKey()` 가 3번의 MK 와 다른 객체(또는 `null`)면 평문을 버리고 `null`
7. 돌려주는 값: 레코드를 펼치고 `blob` = 평문 `Blob`(형식 = `ext` 의 이미지 mime — `png`→`image/png`, `jpg`→`image/jpeg`, `gif`→`image/gif`, `webp`→`image/webp`, F-402 11장 ③), `size` = 평문 바이트, `width`·`height` = 5번 값, `e2ee: true`

- **세대 값**: `withE2ee` 안의 정수 하나. `clearPlainCache()`(잠그기 `indexes` 단계, F-405 7.2)가 1 올린다. `indexes` 는 `blobs` 보다 앞이고 단계 동안 MK 가 남아 있으므로(F-405 c7), **`indexes` 뒤에 끝난 복호화는 결과를 버린다** → `blobs` 단계 뒤에 새 금고 주소가 생기지 않는다
- **복호화 결과를 기억하지 않는다**(12장 Q2). 같은 첨부를 다시 부르면 다시 복호화한다 — 5MB 한 장이 Chrome 18.8ms(4배 감속 59.1ms, k2). 기억을 두면 추적해야 할 평문 사본이 하나 더 생긴다. 편집기는 이미 위젯 기억(편집기마다 id 당 한 번)이 있어 스크롤로 다시 부르지 않는다
- 평문 `Blob`·평문 바이트는 **IndexedDB·localStorage·`postMessage` 로 가지 않는다**(A4). 아래 저장소에는 봉투만 들어간다

### 3.4 수명 — 언제 거두나

| 때 | 누가 거두나 | 근거 |
| --- | --- | --- |
| 문서를 바꾸거나 홈으로 감 | 편집기 파괴 → `destroyImageCache` → `revokeAttachmentUrl`. 보기 화면 언마운트 정리 | k5·k6 — `<Editor key>`·`<Viewer key>` 가 문서 id |
| 보기 화면에서 `html` 이 바뀜 | `Viewer` 효과가 앞 주소를 모두 거둔다 | k6 |
| 원문 모드로 바꿈 | tracker `destroy` → `destroyImageCache` (지금 그대로) | `blocks.ts` |
| **잠그기** | `blobs` 단계: `useE2ee` 가 `keyring.registerLockStep('blobs', () => revokeE2eeAttachmentUrls())` 로 등록한다. 목록 전부를 거둔다 | F-400 2.5 ⑤, F-404 4.1 |
| 로그아웃·계정 바뀜 | 잠그기와 같다(F-404) | F-400 2.5 |
| 탭 닫기·새로고침 | 문서가 사라지며 모든 `blob:` 이 사라진다 | 브라우저 |

- 잠그기 순서 안에서: `unmount`(F-405 — 편집기를 내림, 잠긴 모양 목록) → `indexes`(세대 값 +1, 3.3) → `blobs`(목록 전부 거둠) → 키 버림. `blobs` 가 끝난 시점에 **금고 첨부 `blob:` 주소는 하나도 살아 있지 않다**(E3 가 `fetch` 로 판정)
- `blobs` 단계는 던지지 않는다. 던져도 F-404 규칙대로 기록만 하고 계속한다

### 3.5 메모리 상한

- **`withE2ee` 가 붙드는 평문: 0 B.** 복호화 결과를 돌려주면 끝이다(3.3). 복호화 한 번에 잠깐 드는 것은 봉투 읽기 + 잘라낸 암호문 사본 + 평문 + 평문 `Blob` — 첨부 하나당 봉투 크기의 약 4배, 최대 약 21MB
- **화면이 붙드는 평문**: 지금 열린 금고 문서의 편집기(위젯 기억)와 보기 화면이 그린 이미지뿐이다. 문서를 바꾸면 거둔다(3.4). 한 문서 안의 상한은 계산상 이미지 참조 1,000개(`E2EE_MAX_ATTACHMENT_REFS`) × 5,242,811 B 이지만, 위젯은 그려질 때만 첨부를 부른다(`toDOM` 에서 `_loadImage`)
- 따로 상한(오래된 주소부터 거두기 등)을 두지 않는다(12장 Q3). 일반 문서의 위젯 기억도 지금 상한이 없고, 금고라서 더 많이 붙드는 것은 없다
- 다른 금고 문서의 이미지는 그 문서를 열 때까지 복호화하지 않는다. 목록·검색·지도는 첨부를 읽지 않는다

```ts
  // … 지금 값 그대로
  | 'invalid'        // 400 { error: 'invalid', field } (F-402 3.1 4·7번)
  | 'e2ee_mismatch'  // 409 { error: 'e2ee_mismatch' } (F-402 3.1 5번)

// e2ee 를 주면 ?e2ee=1&w={width}&h={height} 를 붙인다
export function uploadAttachment(
  id: string,
  ext: AttachmentExt,
  blob: Blob,
  e2ee?: { width: number; height: number },
): Promise<UploadedAttachment>

// UploadedAttachment 에 e2ee?: true (서버가 금고일 때만 싣는다, F-402 3.1)

// F-407 이 옮기기·빼기에서 쓴다. 204 → 'deleted', 404 → 'not_found', 409 { error: 'in_use' } → 'in_use'.
// 그 밖은 uploadAttachment 과 같은 분류로 AttachmentApiError 를 던진다 (network·unauthorized·server_error·rate_limited·account_blocked·other)
export function deleteAttachment(id: string, ext: AttachmentExt): Promise<'deleted' | 'not_found' | 'in_use'>
```

- 400 분류: 몸통 `error` 가 `'type_mismatch'` → `type_mismatch`(지금), `'invalid'` → `invalid`, 그 밖(`'unsupported'` 포함, JSON 아님) → `unsupported`(지금). 409 분류: `'e2ee_mismatch'` → `e2ee_mismatch`, 그 밖 → `other`(지금)
- 판정 순서는 지금 그대로(507 → 401·5xx → 429 → 403 → 413 → 400) 뒤에 409 를 더한다
- `deleteAttachment` 를 이 명세에 두는 이유(12장 Q4): F-400 6장이 `attachmentsApi.ts` 를 F-406 에 두었고 F-407 행에는 없다. F-402 8장도 가짜 서버 `DELETE` 를 F-406 에 두었다

### 4.2 `putAttachment` · 보내기 — `serverStore.ts`

- `putAttachment` 가 `e2ee: true` 를 받으면(늘 `id` 와 함께 온다 — 2.2): 변환 없음(지금 `id` 규칙), 한도 사전 검사는 봉투 크기, 캐시 행에 `e2ee: true`. 그 밖은 지금 그대로
- `sendOne` 의 `upload` 갈래: 캐시 행이 `e2ee` 면 `uploadAttachment(id, ext, blob, { width, height })`. outbox 항목 모양은 바꾸지 않는다 — 금고 여부·가로세로는 보낼 때 캐시 행에서 읽는다
- `AttachmentApiError` 갈래: `invalid`·`e2ee_mismatch` 는 지금의 `too_large`·`unsupported`·`type_mismatch` 와 같게 — 항목을 빼고 알림 `이미지를 서버에 올리지 못했습니다.`(지금 문구). 둘 다 클라이언트가 막았어야 하는 경우라 다시 보내도 같은 답이다
- `cachedToAttachment` 가 `e2ee` 를 옮긴다(있을 때만)

### 4.3 `getAttachment(id, hint)` — 다른 기기에서 올린 금고 이미지 받기

- 캐시에 있으면 지금 그대로(행에 `e2ee` 가 있으면 함께)
- 없으면 확장자와 문서를 찾는다: ① 지금의 `findExtInDocs`(캐시 문서 본문) — 찾으면 지금처럼 `?doc=` 까지 ② 못 찾고 `hint` 가 있으면 `hint.ext`, `?doc=` 없이(소유자 받기 — 금고 첨부는 소유자만 받는다, F-402 3.2) ③ 둘 다 없으면 `null`(지금 그대로)
- 받은 응답의 형식이 **`application/octet-stream` 이면 봉투**다(F-402 3.2 — 평문 첨부는 늘 이미지 mime). 캐시 행: `e2ee: true`, `mime` = `ext` 의 이미지 mime, `width`·`height` `0`(`decodeDims` 를 부르지 않는다 — 봉투는 이미지가 아니다), `uploaded: true`. 이미지 mime 이면 지금 그대로
- 힌트를 두는 이유: 금고 문서의 캐시 본문은 봉투라 `findExtInDocs` 가 못 찾는다(k8). `attachmentRefs` 는 id 만 있고 확장자가 없다(F-401 계약 — 16진 16자). 평문 원문을 가진 것은 `withE2ee` 뿐이라 거기서 힌트를 만들어 내려보낸다(3.3 1번)
- 네 확장자를 차례로 받아 보기(404 를 세 번 맞기)는 쓰지 않는다 — 요청이 늘고 `?doc=` 없는 404 가 남의 첨부 id 를 캐는 것처럼 보인다

### 4.4 로그인 이관·옮기기와의 경계

- `migrateLocalAttachments`(F-208)는 캐시 문서 **본문**의 참조만 옮긴다 — 금고 문서 본문은 봉투라 금고 첨부를 옮기지 않는다. 로컬 금고 문서는 F-405 5.5 로 일반 이관에서 빠지고, 그 첨부 이관(감싼 키 바꿔 다시 올리기)은 F-408 이다. **이 명세는 바꾸지 않는다**
- 평문 첨부를 암호 첨부로 바꾸기·지우기는 F-407 이다. F-407 은 `withE2ee.putAttachment({ …, e2ee: true })` 와 `deleteAttachment` 를 쓴다

- 첨부 라우트의 경로 정규식이 **쿼리를 허용**하게 한다(지금은 `\.(png|jpg|gif|webp)$` 라 `?e2ee=1…` 가 붙으면 안 걸린다). 판정은 경로 부분으로
- `PUT` + `e2ee=1`: `w`·`h` 가 `/^[1-9][0-9]{0,7}$/` 가 아니면 400 `{ error: 'invalid', field }`, 몸통 길이 < 69 이거나 0번이 1 이 아니면 400 `{ error: 'invalid', field: 'body' }`, 같은 키가 있고 `e2ee` 가 다르면 409 `{ error: 'e2ee_mismatch' }`. 기록 `{ mime: ext 의 mime, bytes, width: w, height: h, e2ee: true }`, 응답 201 에 `e2ee: true`. 평문 `PUT` 은 지금 그대로(같은 키가 금고 기록이면 409)
- `GET`: 기록이 `e2ee` 면 `contentType: 'application/octet-stream'`
- `DELETE`: 기록이 없으면 404 `not_found`. 가짜 문서 중 본문에 `attachments/{id}.` 가 있거나 `attachmentRefs` 에 id 가 있으면 409 `in_use`. 아니면 지우고 204, `usage.used` 를 줄인다
- 기존 조종 함수·평문 동작은 바꾸지 않는다

## 14. 확인한 것과 가정

### 14.1 코드를 읽거나 돌려 확인한 것
- 머리 표 k1~k11
- `crypto.ts` `encryptAttachment(masterKey, attachmentId, bytes)` 는 id 를 `/^[0-9a-f]{16}$/` 로 검사하고 봉투 첫 바이트에 판 1 을 쓴다. `decryptAttachment` 는 길이 < 69 면 `bad-envelope`, 판이 다르면 `unsupported-version`, 키 풀기·복호화 실패는 `decrypt-failed`
- `keyring.ts` `E2eeLockPhase` 에 `blobs` 가 있고, `useE2ee.ts` 는 지금 `indexes` 에 검색·지도 캐시 비우기 둘만 등록한다 — `blobs` 에 등록한 곳이 없다
- `App.tsx` `resolveAttachment` 는 `store.getAttachment(id)` 에서 `{ blob, width, height }` 만 추려 편집기(`<Editor resolveAttachment>`)·보기 화면(`<Viewer resolveAttachment>`)·인쇄(`printDoc`)에 넘긴다. `handleImageFiles` 는 `attachImages(files, { store, source })` 한 곳
- `attachImages` 의 결과 상한 `MAX_RESULT_BYTES` 는 `5 * 1024 * 1024` = 5,242,880 이고, `putAttachment` 던짐은 `err.name === 'quota_exceeded'` 만 따로 가른다
- `serverStore.ts` `putAttachment` 의 `id` 갈래는 이미 있는 캐시 행을 그대로 돌려주고 변환을 건너뛴다. 평문 보내기 실패(`too_large`·`unsupported`·`type_mismatch`)는 항목을 빼고 `이미지를 서버에 올리지 못했습니다.`
- `e2e/fixtures/fakeServer.js` 첨부 라우트는 `page.route` 정규식 끝이 `$` 라 쿼리가 붙은 URL 을 받지 않는다. `serverStore.test.ts` 가짜는 `pathname` 으로 가른다

### 14.2 가정으로 남긴 것
