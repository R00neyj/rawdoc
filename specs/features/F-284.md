| # | 결정 |
| --- | --- |
| 1 | **검색은 전부 클라이언트에서 돈다.** 로그인·비로그인 모두 로컬에 있는 문서(IndexedDB / 원격 캐시)의 제목·본문을 훑는다. 서버 검색 API 도 D1 FTS5 도 만들지 않는다. 오프라인에서도 된다. 대가로 캐시에 없는 문서는 못 찾으므로, 검색 전에 목록을 한 번 당겨오는 보완을 둔다 (5.2) |

## 2. 진입점·화면·키보드

### 2.1 진입점 — 이미 있는 검색 버튼을 켠다

지금 검색 버튼은 **두 자리**에 있고 둘 다 `aria-disabled="true"` 다 (F-151, F-159, F-216).

> **2026-09-21 정정.** 원래 여기 있던 "펼친 사이드바 동작 버튼(`검색` + `준비 중`)" 행은 틀렸다 — 그 버튼은 2026-09-14 F-151(`003957b`)에서 이미 사라졌고 `SidebarButton` 의 `hint` prop 과 `.sidebar-btn-hint` CSS 는 죽은 코드로만 남아 있었다 (F-287 이 코드에서 확인, `git log -S "준비 중" -- src/app/Sidebar.tsx`). 그 행을 지우고 휴대폰 폭 자리를 대신 넣는다

| 자리 | 지금 모양 | 바뀌는 것 |
| --- | --- | --- |
| 사이드바 머리 줄 / 좁은 창 상단바 앞 묶음 (`SidebarHead.tsx`) | 아이콘, `aria-label`·툴팁 `검색 — 준비 중` | `aria-disabled` 제거, 문구 `검색`, 누르면 대화상자 |

### 2.2 화면 — 모달 대화상자

**사이드바 패널이 아니라 대화상자다.** 이유:

- 사이드바 폭은 200~480px(F-159)이라 발췌(스니펫)를 읽을 폭이 안 난다. 대화상자는 `Dialog.tsx` 의 `size="wide"` 를 쓴다
- `Dialog.tsx` 가 네이티브 `<dialog>` + `showModal()` 로 Esc·바깥 클릭·포커스 복귀를 이미 처리한다 (F-102 5.6). 새로 만들 것이 없다
- 결과에서 문서를 열면 곧바로 편집 화면으로 간다. 검색 패널을 열어 둔 채로 문서를 바꿔 가며 보는 흐름은 이번에 만들지 않는다 (5.4)

구성(위→아래):

1. 검색창 한 칸. `placeholder` = `검색어 또는 tag:값`. 열리면 여기에 포커스
2. 쿼리 해석 줄 — 필터가 있을 때만: `필터 tag=일기 · 검색어 "회고"`. 잘못 쓴 필터·못 읽은 문서 안내도 여기 (4.4)
3. 결과 목록. 행마다 **제목 · 폴더 경로 · 수정일 · 발췌 한 줄**
4. 꼬리 줄 — 결과 수, 상한에 걸렸으면 그 안내

- 해시 주소를 만들지 않는다. `#/shares`·`#/help` 같은 화면이 아니라 설정 대화상자(F-121)와 같은 급이다. 뒤로 가기로 닫히지 않는다
- `specs/design.md` 토큰만 쓴다. 색 hex·제품명 문자열을 직접 쓰지 않는다(불변조건)

## 3. 쿼리 문법

### 3.1 토큰 나누기

- 공백으로 쪼갠다. **큰따옴표(`"…"`) 안의 공백은 유지**한다. 닫는 따옴표가 없으면 줄 끝까지 한 토큰
- 작은따옴표는 따옴표로 보지 않는다 — 한국어 본문에 그대로 쓰이는 글자다
- 토큰이 `key:value` 모양이면 **필터**, 아니면 **본문 검색어**

### 3.2 `key:value` 판별 규칙

| 항목 | 규칙 | 예 |
| --- | --- | --- |
| 판별 | 첫 콜론 앞이 키, 뒤 전부가 값 | `tag:일기` → key `tag`, value `일기` |
| 키에 쓸 수 있는 글자 | `[A-Za-z0-9가-힣_-]+` 만. 그 밖(`/` `.` 공백 따옴표 등)이 섞이면 필터가 아니라 본문 검색어 | `my.key:1` → 본문 검색어 |
| 콜론으로 시작 | 키가 비어 있으므로 본문 검색어 | `:foo` → 본문 검색어 `:foo` |
| 값에 콜론 | 값은 첫 콜론 뒤 전부. 따옴표가 필요 없다 | `time:10:30` → value `10:30` |
| 값이 `//` 로 시작 | 필터가 아니라 본문 검색어 (URL 오인 방지. 유일한 예외) | `http://a.com` → 본문 검색어 |
| 값에 공백 | `tag:"주간 회고"` **하나만** 인정. 따옴표로 시작하는 토큰은 언제나 본문 검색어다 (아래 행과 짝) | `"tag:주간 회고"` → 본문 검색어 (2026-09-21 정정 — 원래 둘 다 인정한다고 적어 아래 행과 모순이었다. F-285 3.2) |
| 값이 빔 | **그 키를 가진 문서 전부**(존재 검사) | `tag:` |
| 필터를 본문 검색어로 쓰고 싶을 때 | 토큰 전체를 따옴표로 감싼다 | `"tag:일기"` → 본문에서 `tag:일기` 를 찾는다 |
| 대소문자 | **키·값 모두 구분하지 않는다** (`toLowerCase()` 후 비교). 한글은 대소문자가 없고 `Tag:`/`tag:` 를 구분하면 혼란만 는다 | `Tag:Diary` == `tag:diary` |
| 유니코드 정규화 | **키·값 모두 `.normalize('NFC')` 를 거친 뒤 비교**한다. 프론트매터에서 읽은 키·값도 같다. 자세한 것은 4.2 | NFD 로 저장된 `tag: 일기` 가 NFC 검색어 `tag:일기` 에 걸린다 |
| 값 일치 | **완전일치**(앞뒤 공백·대소문자 무시). 부분일치로 두면 `tag:회고` 가 `회고록` 까지 잡아 필터가 헐거워진다 | `tag:회고` 는 `회고록` 에 안 걸림 |
| 필터 여러 개 | **전부 AND**. 같은 키를 여러 번 써도 AND (`tags:a tags:b` = 둘 다 가진 문서) | |
| 필터 + 본문 검색어 | AND | `tag:일기 회고` = 태그가 일기이면서 본문에 `회고` |

### 3.3 프론트매터 쪽 한계 (실제 파서로 확인함)

`src/lib/frontmatter.ts` 의 `parseSimpleProperties` 를 그대로 떼어 돌려 본 결과(2026-09-20):

| 프론트매터 | 파서 결과 | 검색에서 |
| --- | --- | --- |
| `tags:` + 들여쓴 `  - a` `  - b` (블록 목록) | `{key:'tags', value:['a','b']}` | 배열. **항목 중 하나라도 완전일치하면 맞음** |
| `tags: [a, b]` (인라인 배열) | `{key:'tags', value:'[a, b]'}` — **배열로 안 읽힌다** | 그대로 두면 `tags:a` 가 안 걸린다 → 3.4 |
| `time: 10:30`, `url: https://x.com/a` | 값에 콜론이 남는다 | 정상 |
| `my key: v` | 키에 공백이 허용된다 | 쿼리 키 규칙(3.2)상 `my key:` 는 못 친다. 따옴표로도 안 된다 — 알려진 제약 |
| `tag: '일기'`, `t2: "메모"` | 감싼 따옴표 한 쌍이 벗겨진다 | 정상 |
| `# 주석` 줄 | 건너뛴다 | 정상 |
| `tag:` (값 없음) | `{key:'tag', value:''}` | `tag:` 존재 검사에 걸린다 |
| `author:` + 들여쓴 `  name: kim` (중첩 맵) | **`null`** (문서 전체 속성 없음) | 이 문서는 모든 필터에서 빠진다 |
| `desc: \|` + 들여쓴 여러 줄 (블록 스칼라) | **`null`** | 위와 같음 |

- **한 줄이라도 규칙 밖이면 그 문서의 속성 전체가 `null` 이 된다.** 그런 문서는 `key:value` 필터에 절대 안 걸린다. 본문 검색에는 정상으로 들어간다. ~~결과 아래에 `속성을 읽지 못한 문서 {N}개` 를 적어~~ **검색창 바로 아래 안내 줄에 `속성이 없거나 읽지 못한 문서 {N}개는 필터에서 빠졌습니다` 를 적어** 사용자가 왜 안 나오는지 알게 한다 (4.4)
  - 2026-09-21 F-288 이 두 가지를 고쳤다. (1) **자리** — 결과 아래가 아니라 검색창 바로 아래다. 결과 목록이 `max-height: 50vh` 로 잘려 있어 그 아래 글은 스크롤을 내려야 보이고, 결과가 0개일 때도 보여야 하는 문구다 (F-288 4.1). (2) **문장** — N 을 세는 `SearchOutcome.unreadableProperties` 는 프론트매터가 **아예 없는** 문서까지 센다(F-288 7.2 실측: 100개 중 90개). "읽지 못한" 만으로는 거짓이라 `속성이 없거나 읽지 못한` 으로 고쳤다 (F-288 13장 Q1, 사용자 확정)
- `findFrontmatter` 는 첫 줄이 `---` 이고 뒤에 `---`/`...` 닫는 줄이 있어야 범위를 돌려준다. 프론트매터가 없는 문서는 필터가 하나라도 있으면 결과에서 빠진다
- **`src/lib/frontmatter.ts` 를 고치지 않는다.** 그 파일은 F-133 소유이고 편집 화면·보기 화면의 속성 표가 같은 함수를 쓴다. 검색에 필요한 보정은 검색 쪽 순수 함수에서만 한다

### 3.4 인라인 배열 보정 (기본값 — 사람 확인 필요)

`tags: [a, b]` 는 흔한 표기인데 파서가 문자열로 준다. **검색 쪽에서만** 값이 `[` 로 시작해 `]` 로 끝나면 쉼표로 쪼개고 각 조각의 앞뒤 공백·따옴표를 떼어 배열처럼 본다. 원본 속성 표(F-133)의 표시는 바뀌지 않는다

- **쪼갠 원소와 원본 문자열을 모두 후보로 본다** — `tag:"[a, b]"` 처럼 원문 그대로 찾는 것도 걸려야 한다 (2026-09-21 F-285 6.3)
- 이 보정을 넣지 않으면 `tag:a` 가 `tags: [a, b]` 문서에 안 걸린다
- 기본값은 **넣는다**. 8장 Q2

#### 유니코드 정규화 (NFC) — 한글 검색이 실패하는 가장 흔한 원인

`한글` 은 눈에 같아 보여도 두 가지로 저장될 수 있다:

| 방식 | 코드포인트 | 길이 | 쓰는 곳 |
| --- | --- | --- | --- |
| NFC (완성형) | `U+D55C U+AE00` (`한`·`글`) | 2자 | Windows, Android, 대부분의 웹 |
| NFD (조합형) | `U+1112 U+1161 U+11AB U+1100 U+1173 U+11AF` (ㅎㅏㄴ + ㄱㅡㄹ) | 6자 | macOS 의 일부 — 특히 파일명, 일부 앱에서 복사한 텍스트 |

- NFD 의 자모는 낱자 `ㅎ`(U+314E, 호환 자모)가 아니라 **조합용 자모**(U+1112~)다. 눈으로 구분할 수 없다

- **화면에는 똑같이 보이는데 `indexOf` 는 못 찾는다.** macOS 에서 쓴 글을 동기화했거나 macOS 에서 만든 `.md` 를 가져온(F-282) 뒤 Windows 에서 검색하면 결과가 하나도 안 나오고, 사용자는 왜인지 알 방법이 없다
- **규칙: 인덱스를 만들 때와 검색어를 받을 때 양쪽 모두 `.normalize('NFC')` 를 한 번 거친다.** 제목·본문·프론트매터 키·값 전부 같다. 한쪽만 하면 아무 의미가 없다
- **원문 자체는 절대 정규화하지 않는다.** 정규화는 검색 인덱스와 검색어 안에서만 일어난다. 저장소에 쓰지 않고 `EditorState` 에도 돌려보내지 않는다 — 원문 보존이 이 제품의 불변조건이다 (`CLAUDE.md`)
- **NFD 를 검색어로 쳐도 된다.** macOS 사용자가 NFD 로 붙여넣은 검색어도 같은 정규화를 거치므로 NFC 본문에 걸린다. 방향이 한쪽만 되는 것이 아니다

**딸린 함정 — 위치가 어긋난다.** NFD→NFC 는 글자 수가 준다(6자 → 2자). 정규화한 문자열에서 찾은 인덱스를 원문에 그대로 쓰면 발췌가 엉뚱한 곳에서 잘린다

- **결정: 발췌(스니펫)도 정규화된 문자열에서 잘라 보여준다.** 원문으로 위치를 되돌리는 표(offset mapping)를 만들지 않는다
- 근거: **발췌는 표시용이라 원문과 바이트가 같을 필요가 없다.** 원문 보존 불변조건이 걸린 곳은 저장·내보내기이지 검색 결과 미리보기가 아니다. 위치 되돌림 표는 문서마다 만들어야 해서 인덱스 메모리와 만드는 시간이 둘 다 늘고, 버그가 나면 발췌가 조용히 어긋난다
- 대가: NFD 로 저장된 문서의 발췌는 원문과 코드포인트가 다르다. 보이는 글자는 같다. 문서를 열면 원문 그대로이므로 편집에 영향이 없다
- 4.3 의 `{ text, hit }` 조각 배열도 정규화된 문자열 기준으로 만든다

### 4.3 정렬·발췌·결과 행

- **정렬: 제목이 맞은 문서 묶음이 먼저, 본문만 맞은 문서 묶음이 뒤. 각 묶음 안은 `updatedAt` 내림차순** — 사이드바 목록과 같은 순서다
  - 점수 기반 랭킹을 만들지 않는다. 기준을 만들면 끝없이 튜닝하게 되고, 사용자는 목록 순서가 예측 가능할 때 찾기가 쉽다
- **발췌(스니펫)**: 본문 첫 매치 기준 앞 30자·뒤 70자. 줄바꿈·연속 공백은 공백 하나로 접고, 잘린 쪽에 `…`. **자르는 기준은 정규화된(NFC) 본문이다** — 4.2 "딸린 함정"
  - 발췌 계산은 **순수 함수가 `{ text, hit }` 조각 배열을 돌려주고** React 가 조각마다 `<span>` 을 그린다. `dangerouslySetInnerHTML` 을 쓰지 않는다 — DOM 없이 단위 테스트가 되고 XSS 도 없다
  - 제목 강조도 같은 함수를 쓴다
  - **문서당 발췌 1개**(첫 매치). 매치 개수를 세지 않는다 — 세려면 문서 전체를 끝까지 훑어야 한다
- **결과 행**: 제목 · 폴더 경로(`상위 / 하위`, `src/lib/folderTree.ts`) · 수정일(`YYYY-MM-DD`) · 발췌. 공유받은 문서(`Doc.role` 이 `edit` 또는 `view`)는 `공유받음` 표시 (2026-09-21 정정 — 원래 "`owner` 가 아님" 이었으나 로컬 저장소 문서는 `role` 이 `undefined` 라 전부 공유로 잡힌다. `memoryStore.ts` 28~30행 `normalizeDoc` 이 `role` 을 채우지 않는다. F-286 3.1)
- **결과 상한 200개**. 넘으면 ~~`결과가 많습니다 — 앞 200개만 보입니다`~~ **`결과 {총계}개 — 앞 {보이는 수}개만 보입니다`** (예: `결과 1,204개 — 앞 200개만 보입니다`). 가상 스크롤을 넣지 않는다
  - 2026-09-21 F-288 정정. 원래 문장은 총 개수를 모른다는 전제로 썼는데, `searchDocs` 가 자르기 **전에** `total = matched.length` 를 세어 이미 내보내고 있다(`src/lib/docSearch.ts` 251행). 총계를 적는 쪽이 "더 좁혀야 하나" 를 판단할 수 있다 (F-288 5.3·13장 Q3, 사용자 확정)
- **열기**: 클릭 또는 `Enter` → 대화상자를 닫고 `#/d/{id}` 로 이동(기존 문서 전환 흐름 그대로). ~~문서 안에서 검색어를 다시 찾아 주지는 않는다 (8장 Q3)~~ **열면 그 문서의 찾기 패널(F-261)에 검색어를 넣어 매치를 강조하고 첫 매치로 이동한다 (2026-09-21, F-294)**
  - 발췌·`bodyHit` 의 NFC 좌표를 쓰지 않는다는 4.2·5.4 의 사실은 그대로다 — F-294 는 좌표를 넘기지 않고 검색어 문자열만 넘겨 CM6 가 원문에서 직접 다시 찾는다

## 5. 성능·데이터·제외

### 5.1 인덱스와 성능

**저장하는 역색인을 만들지 않는다.** 메모리 인덱스만 쓰고, 탭을 닫거나 새로고침하면 사라진다 (재사용 규칙은 5.3)

인덱스 항목(문서마다): `id`, **NFC 정규화한 `title`**, **프론트매터를 뗀 뒤 NFC 정규화한 본문**, `parseSimpleProperties` 결과를 NFC 정규화한 것(또는 `null`), `folderId`, `updatedAt`, `role`

- 만드는 시점: 대화상자를 열 때. `store.list()`(본문 포함) + `store.listFolders()`. 두 번째부터는 바뀐 문서만 다시 만든다 (5.3)
- 검색 실행: 입력 **디바운스 150ms** 뒤 인덱스를 전부 훑는다. 검색어도 `.normalize('NFC')` 를 거친다 (4.2)
- **정규화한 본문만 담고 원문 본문은 담지 않는다.** 발췌를 정규화 문자열에서 자르기로 했으므로(4.2) 원문이 필요 없다 — 사본이 하나 더 생기지 않는다
- 소문자 사본을 미리 만들어 두지 않는다 — 메모리가 두 배가 되고, 발췌에는 원래 대소문자가 필요하다. 매 검색 때 `toLowerCase()` 한다

**실측 근거** (2026-09-20, 이 PC, Node. `src/lib/frontmatter.ts` 의 두 함수를 그대로 옮긴 스크립트로 합성 문서(CRLF, 프론트매터 5줄 + 한글 본문)를 만들어 쟀다):

| 문서 수 | 평균 길이 | 프론트매터 전부 파싱 | 본문 잘라내기 + 소문자화 + `indexOf` 전부 | 준비된 소문자 본문에서 `indexOf` 만 |
| --- | --- | --- | --- | --- |
| 100 | 2.1천자 | 2.1ms | 1.0ms | 0.0ms |
| 500 | 4.2천자 | 5.3ms | 4.1ms | 0.5ms |
| 1,000 | 4.2천자 | 7.2ms | 14.3ms | 1.7ms |
| 2,000 | 8.2천자 (16.3M자) | 32.3ms | 31.8ms | 3.4ms |
| 5,000 | 4.2천자 (20.8M자) | 40.2ms | 51.5ms | 6.5ms |

읽는 법:

- **인덱스 만드는 비용** ≈ 2열 + 3열의 "잘라내기" 부분. 1,000개에서 약 20ms, 5,000개에서 약 90ms. 대화상자를 열 때 한 번만 낸다
- **키 입력 한 번당 비용** ≈ 3열(소문자화 + `indexOf`)에서 잘라내기를 뺀 값이므로 위 표의 3열보다 작다. 5,000개 51ms 가 상한이고, 디바운스 150ms 안에 들어간다
- **`parseSimpleProperties` 를 문서마다 매번 도는 비용은 1,000개에서 7ms** 다. 그래도 인덱스에 결과를 담아 두고 필터마다 다시 돌리지 않는다
- **견디는 규모: 문서 5,000개 / 2천만 자까지.** 그 위(1만 개 이상)는 웹 워커나 저장하는 역색인이 필요하다 — 그 전까지 만들지 않는다. 계정 용량 상한 300MB(F-221)·D1 무료 500MB 를 생각하면 한 계정이 수천 개를 넘기기 어렵다

**정규화(NFC) 비용 실측** (2026-09-21, 이 PC, Node v24.12.0. 위와 같은 방식의 합성 문서를 만들어 `normalize('NFC')` 만 잰 **별도 스크립트**다. 문서 생성기가 달라 총 글자 수가 위 표와 조금 다르다 — 5,000개에서 23.1M자. 2회 실행의 중앙값):

| 문서 수 | 총 글자 | 원문이 이미 NFC 일 때 | 원문이 전부 NFD 일 때 |
| --- | --- | --- | --- |
| 100 | 0.2M자 | 0.1ms | 1.8ms |
| 500 | 2.3M자 | 1.6ms | 19.3ms |
| 1,000 | 4.6M자 | 3.0~3.4ms | 38~40ms |
| 2,000 | 18.0M자 | 13~18ms | 144~150ms |
| 5,000 | 23.1M자 | 19.4ms | 190~196ms |

- **거의 모든 문서는 이미 NFC 다**(Windows·Android·웹). 그 경우 5,000개에 20ms — 인덱스 만드는 비용(위 표로 약 90ms)에 20% 정도 얹힌다
- **최악(계정의 문서가 전부 NFD)은 5,000개에 190ms.** 인덱스 만드는 비용이 약 90ms → 약 280ms 로 는다. 대화상자를 열 때 한 번 내는 값이고, 5.3 재사용이 있으면 두 번째부터는 바뀐 문서만 낸다
- **NFD→NFC 로 글자 수가 절반 가까이 준다**(45.1M자 → 23.1M자). 정규화 문자열의 위치를 원문에 그대로 못 쓰는 이유가 이것이다 (4.2)
- **검색어 정규화는 잴 필요가 없다.** 5자 검색어를 1,000번 정규화하는 데 0.1ms
- 브라우저에서 재지 않았다 — 아래 F-286 게이트에서 같이 잰다

**측정하지 않은 것 — 이쪽이 더 오래 걸릴 수 있다**

위 표는 전부 **문자열 처리 시간만** 잰 것이다. 실제로 대화상자를 열면 그 전에 저장소에서 문서를 전부 읽어 와야 하고, **그 시간은 재지 않았다.** 구체적으로:

| 안 잰 것 | 왜 클 수 있나 |
| --- | --- |
| IndexedDB 에서 문서 전부 읽기 (`idbStore.list()` = `getAll`) | 수천 건·수십 MB 를 구조화 복제로 메인 스레드에 올린다. 문자열 처리보다 클 가능성이 있다 |
| 원격 캐시에서 읽기 + 빠진 본문 채우기 (`serverStore.list()`) | 캐시에 없거나 `version` 이 다른 문서마다 `api.getDoc` 이 **한 건씩** 나간다 (5.2). 네트워크가 들어간다 |
| React 가 결과 200행을 그리는 시간 | |
| 브라우저 환경 (V8 은 같지만 GC·메인 스레드 사정이 다르다) | |

**게이트 — F-286 에서 판정한다**

- **잰다**: `scripts/measure.mjs` 로 문서 1,000개를 넣은 상태에서 `Ctrl+Shift+F` 를 누른 뒤 (a) 검색창이 보이기까지, (b) 인덱스가 준비돼 첫 결과를 낼 수 있기까지 걸리는 시간
- **목표**: (a) **100ms 이내**, (b) **1,000ms 이내** (문서 1,000개, 로컬 저장소 또는 캐시가 채워진 상태)
- **(a) 는 문서 1,000개까지만 성립한다 (2026-09-21 F-287 7.1 실측).** 5,000개에서는 **검색과 무관한 설정 대화상자조차 294~478ms** 라 이 목표를 못 지킨다. 원인은 사이드바가 `memo` 가 아니라 App 상태가 바뀔 때마다 문서 행을 전부 다시 그리는 것(`Sidebar.tsx`)이고, 검색이 만든 문제가 아니다. 검색은 **설정 대화상자보다 30ms 넘게 느리지 않을 것**을 상대 기준으로 함께 본다
- **이 두 숫자는 이 프로젝트에서 실측해 정한 값이 아니다.** 응답 시간에 대해 널리 쓰이는 통념(0.1초 = 즉각 반응으로 느낀다, 1초 = 생각의 흐름이 안 끊기는 한계, 10초 = 주의가 끊긴다. Miller 1968 / Nielsen 1993 의 구분으로 알려져 있다)을 근거로 잡았다. **통념이라는 점을 밝혀 둔다**
- **목표를 넘으면 설계를 재검토한다.** 순서: (1) 5.3 인덱스 재사용으로 두 번째 이후를 줄인다 → (2) 캐시 스냅샷으로 먼저 그리고 `list()` 를 나중에 갈아 끼운다(5.2 에 이미 있는 방식) → (3) 인덱스 만들기를 청크로 쪼개 나눠 돈다 → (4) 웹 워커 → (5) 저장하는 역색인. **(4)·(5) 는 5.4 "하지 않는 것" 에 들어 있으므로 명세를 먼저 고치고 사람 승인을 받는다**

**메모리**: 5,000개 × 4천자 ≈ 2천만 자를 **한 번에 메모리에 올린다.** UTF-16(자바스크립트 문자열은 코드유닛당 2바이트) 기준 대략 **40MB**. 저장소가 돌려준 `Doc[]` 와 인덱스가 잠깐 함께 있으면 그 순간은 두 배까지 간다. 인덱스에는 정규화한 본문만 남기고 `Doc[]` 참조는 놓는다 — 다만 **그것으로 heap 이 줄지는 않는다.** `normalize('NFC')` 는 이미 NFC 인 문자열에 같은 객체를 돌려주므로 잘라낸 본문이 원문을 계속 붙잡는다 (2026-09-21 F-286 실측: 참조를 놓아도 53.2 → 53.2MB). "사본이 두 배로 늘지 않는다" 는 결론 자체는 맞다. 5.3 재사용 때문에 대화상자를 닫아도 인덱스는 남는다 — 버리는 때는 5.3

**저장되지 않은 입력**: 자동 저장은 입력이 멈추고 700ms 뒤다(`useDocSaver.ts` `SAVE_DEBOUNCE_MS = 700`). 검색 대화상자를 열기 **전에** `saver.flush()` 를 먼저 부른다 — `App` 이 문서 전환·새 버전 적용 전에 이미 쓰는 흐름과 같다. 안 그러면 방금 친 글자가 안 잡힌다

- 검색은 저장소 스냅샷을 읽기만 한다. 에디터 상태를 건드리지 않으므로 **"문서 상태의 원본은 CM6 `EditorState` 하나"** 불변조건과 충돌하지 않는다

### 5.2 로그인 사용자의 캐시 공백 (전제 1의 보완)

**코드에서 확인한 지금 동작** (`src/storage/serverStore.ts`):

- `list()` 는 `api.listDocs()`(=`ServerDocSummary`, **본문 없음**)를 받은 뒤, 캐시에 없거나 `version` 이 다른 문서마다 `api.getDoc(id)` 를 **한 건씩** 불러 본문까지 `remoteCache` 에 넣는다 (491~539행). 그리고 캐시 전체를 `Doc[]`(본문 포함)로 돌려준다
- → **내가 소유한 문서는 온라인에서 `list()` 를 한 번 부르면 본문이 전부 캐시에 들어온다.** 별도 "미리 당겨오기" 장치를 새로 만들 필요가 없다. **대화상자를 열 때 `store.list()` 를 부르는 것 자체가 그 보완**이다 (`App.tsx` 1685행·1781행이 이미 같은 방식으로 목록을 새로 읽는다)
- **진짜 공백은 공유받은 문서다.** 같은 함수 546~565행이 `api.getShared()` 결과를 **`content: ''` 로 채워** 돌려주고 캐시에 넣지 않는다 (F-207 이 일부러 캐시하지 않는다)

| 경우 | 이번 범위의 처리 |
| --- | --- |
| 내 문서 · 온라인 | 대화상자를 열 때 `list()` 가 빠진 본문을 채운다. 전부 검색 |
| 내 문서 · 오프라인 | `list()` 가 실패하면 캐시에 있는 것만. 머리에 `오프라인 —` 안내 (4.4) |
| **공유받은 문서** | **제목만 검색한다.** 본문은 대상에서 뺀다. ~~결과 아래에~~ **검색창 바로 아래 안내 줄에** `공유받은 문서 {N}개는 제목만 찾았습니다` (자리는 4.4 로 통일, F-288 4.1) |
| 로그인하지 않음 | IndexedDB `md-docs` 전부. 공백 없음 |

- 공유받은 문서 본문까지 하려면 문서마다 `api.getDoc` 요청이 한 건씩 나가고(검색 한 번에 수십 건) F-207 의 캐시 정책을 바꿔야 한다 → 별도 명세로 미룬다 (8장 Q4)
- 네트워크가 느리면 `list()` 가 오래 걸린다. ~~**대화상자는 캐시 결과로 먼저 그리고**, `list()` 가 끝나면 인덱스를 갈아 끼운다.~~ **지금은 `list()` 가 끝날 때까지 `목록을 새로 읽는 중…` 만 보여 준다. 2단계 그리기는 게이트를 넘길 때 검토한다 (5.1 재검토 순서 2번)**
  - 2026-09-21 정정. F-286 `buildSearchIndex` 는 `store.list()` 를 `await` 한 뒤에야 인덱스를 돌려주고(`src/app/searchIndex.ts` 119행) 중간 스냅샷이 없다. F-288 도 만들지 않는다 — 캐시본과 갱신본의 결과가 눈앞에서 바뀌는 쪽이 기다리는 것보다 낫다고 볼 근거가 아직 없다

### 5.3 인덱스 재사용 — 바뀐 문서만 다시 넣는다

대화상자를 열 때마다 인덱스를 처음부터 만들면 문서가 수천 개일 때 열 때마다 기다린다. **한 번 만든 인덱스를 재사용하고, 바뀐 문서만 다시 만든다**

**어디에 두나**

- `src/app/searchIndex.ts` 의 **모듈 수준 `Map<docId, IndexEntry>`**. React 상태가 아니다 — 대화상자를 닫아 컴포넌트가 사라져도 남아야 재사용이 되고, 이 값이 바뀐다고 화면을 다시 그릴 일도 없다
- **IndexedDB 에 영속시키지 않는다.** 새로고침하면 사라지고 다시 만든다 — 기존 결정 "저장하는 역색인 없음"(8장 기본값 7)을 그대로 둔다

**무엇이 "바뀌었다" 인가 — `updatedAt` + `title`**

| | 확인한 것 / 가정 |
| --- | --- |
| 앱이 쓸 수 있는 변경 표시는 `updatedAt` 뿐 | **확인.** `version` 은 `CachedDoc`(`remoteCache.ts` 9행)과 서버 `ServerDocSummary` 에만 있고, `serverStore.toDoc()`(80~83행)이 떼어 낸다. `src/types.ts` 의 `Doc` 에는 없다 |
| 제목·본문이 바뀌면 `updatedAt` 이 반드시 바뀐다 | **확인.** `idbStore.applyPatch`(30~37행)와 `serverStore.update`(607~619행)가 `updatedAt = Date.now()` 를 쓴다. 다른 기기에서 고친 것도 `worker/docs.ts` 245행이 `updated_at = now` 로 바꾸고, `list()` 가 그 값을 캐시에 넣는다 — **로컬·서버 양쪽에서 같은 판정이 된다** |
| `moveDoc`·`setPinned` 는 `updatedAt` 을 안 바꾼다 | **확인** (`idbStore.ts` 162·194행 주석, F-126·F-132 의 결정). 둘 다 제목·본문을 안 건드리므로 본문 인덱스는 그대로여도 맞다. **폴더 경로·고정·`role` 은 인덱스 캐시가 아니라 매번 `list()` 결과에서 읽는다** |
| 같은 밀리초 안에 두 번 저장되면 `updatedAt` 이 같아 갱신을 놓칠 수 있다 | **가정 — 실측하지 않았다.** 자동 저장이 700ms 디바운스라 실제로 일어나기 어렵다고 본다 |
| 기기 시계가 어긋나 서버 `updated_at` 이 캐시보다 과거일 수 있다 | **가정.** 그래서 `>` 가 아니라 **`!==` 로 판정**한다 — 값이 다르기만 하면 다시 만든다 |

- 판정 키는 `updatedAt` 과 `title` **둘 다**. `title` 을 같이 보는 것은 안전장치다(제목만 바뀌는 경로가 생겨도 놓치지 않는다)
- `list()` 결과에 없는 `id` 는 `Map` 에서 지운다. 문서 삭제·폴더 통째 삭제(F-247)가 여기서 반영된다
- 공유받은 문서는 본문이 `''` 라 제목만 들어간다(5.2). 판정은 같다

**통째로 버리는 때**

| 때 | 왜 |
| --- | --- |
| 로그인·로그아웃·계정 전환 | **남의 계정 문서 발췌가 보이면 안 된다.** `Map` 에 그 인덱스를 만든 저장소 표시(`store.kind` + 계정 id)를 같이 두고, 다르면 통째로 버리고 새로 만든다 |
| `store` 인스턴스가 바뀔 때 | `openStore()` 가 새 `Store` 를 돌려주는 시점이 계정 전환 시점과 같다. 같은 판정으로 걸린다 |

- 문서 삭제는 통째로 버릴 일이 아니다 — 위 "`list()` 에 없는 `id` 는 지운다" 로 처리된다
- 메모리는 대화상자를 닫아도 잡고 있다 (5.1 기준 최대 40MB 규모). 이것이 재사용의 대가다. 탭을 닫거나 새로고침하면 사라진다

**효과**: 두 번째 이후로는 **바뀐 문서 수만큼만** 프론트매터 떼기·속성 파싱·NFC 정규화를 다시 돈다. 문서 하나를 고치고 다시 열면 하나만. `store.list()` 호출 자체는 매번 한다 — 5.2 의 "캐시 공백 보완" 이 거기에 달려 있다

### 5.4 하지 않는 것

- 서버 검색 API, D1 FTS5, IndexedDB 에 저장하는 역색인 (사용자 전제 1). 5.3 의 재사용은 메모리 안에서만이다
- **원문을 정규화해서 저장하기.** NFC 정규화는 검색 인덱스와 검색어 안에서만 일어난다 (4.2, 불변조건)
- 정규화된 문자열의 위치를 원문 좌표로 되돌리는 표(offset mapping) — 발췌는 정규화 문자열에서 자른다 (4.2)
- 검색 라이브러리 도입 (FlexSearch·MiniSearch·Fuse.js) — 8장 Q1. **기본값은 의존성 없이 직접 구현**
- 정규식, 퍼지(오타 교정), 형태소 분석, 초성 검색, 동의어, 유사도 순 정렬
- 여러 문서 일괄 바꾸기
- 범위 지정 필터(`in:code`, `folder:…`, `is:pinned` 같은 것). 프론트매터 `key:value` 만
- 최근 검색어 저장, 저장한 검색, 검색 결과 URL 공유
- 첨부 이미지 파일명·이미지 안 글자(OCR)
- 공개 보기 화면(F-210·F-211)·공유 링크 화면의 검색
- 검색 결과를 열어 둔 채 문서를 바꿔 가며 보는 패널형 흐름
- 웹 워커 (5.1 규모 안에서는 필요 없다)

## 8. 열린 질문 / 사람 결정 필요

### Q1. 검색 라이브러리를 쓸 것인가 — **기본값: 쓰지 않는다 (직접 구현)**

| 방식 | 무게 | 한글 | 손이 가는 곳 | 판단 |
| --- | --- | --- | --- | --- |
| **직접 구현 (`indexOf`)** | 새 의존성 0 | 부분 문자열 매칭이라 형태소 없이 조사가 붙어도 걸린다 | 쿼리 파싱·발췌를 직접 짠다 (F-285, 대략 200줄) | **기본값** |
| MiniSearch | 작다 | 기본 토크나이저가 공백 기준이라 `회고를` 안의 `회고` 가 안 걸린다. `tokenize` 를 직접 줘야 하고 결국 n-gram 을 짜게 된다 | 색인 만들기·문서 바뀔 때 갱신 | 안 쓴다 |
| FlexSearch | 작다 | 위와 같음. CJK 는 모든 부분 문자열을 색인하는 옵션으로 풀 수 있으나 색인이 크게 부푼다 | 색인 메모리·옵션 튜닝 | 안 쓴다 |
| Fuse.js | 중간 | 퍼지 매칭이라 한글에서 엉뚱한 결과가 잘 나온다. 이번 요구(정확한 부분 문자열)와 안 맞는다 | 점수 임계값 튜닝 | 안 쓴다 |

- **무게(KB)와 토크나이저 성질은 일반적으로 알려진 내용이고 이 프로젝트에서 실측하지 않았다.** 도입을 결정하면 그때 실측한다
- 5.1 실측에서 5,000개까지 직접 구현으로 충분한 것이 확인됐다. 라이브러리를 넣을 이유가 지금은 없다

### Q2. 인라인 배열 `tags: [a, b]` 를 검색에서 쪼갤 것인가 — **기본값: 쪼갠다** (3.4)

쪼개지 않으면 흔한 표기에서 필터가 안 먹는다. 쪼개면 값에 쉼표가 들어간 문자열(`note: [1, 2] 참고`)을 배열로 오인할 수 있다

### Q3. 결과에서 문서를 열 때 F-261 패널에 검색어를 넣을 것인가 — ~~**기본값: 넣지 않는다**~~ **넣는다 (2026-09-21 사용자가 뒤집음, F-294)**

넣으면 긴 문서에서 매치 위치로 바로 갈 수 있어 편하다. 대신 `SearchDialog` 가 CM6 를 알아야 해서 `app → editor` 경계가 두꺼워지고, 필터만 있고 검색어가 없는 쿼리에서는 넣을 것이 없다

- **2026-09-21 사용자 결정으로 뒤집혔다.** 위가 걱정한 두 가지는 `specs/features/F-294.md` 가 이렇게 풀었다
  - `SearchDialog` 는 CM6 를 모른다 — 순수 함수가 본문에 실제로 들어 있는 검색어 **하나**를 고르고, App 이 그 문자열을 `src/editor/showSearchMatches.ts` 에 넘긴다 (F-294 4.1·5장)
  - 넣을 것이 없는 경우는 **아예 열지 않는다** — 필터만 친 쿼리, 제목만 맞은 문서(공유받은 문서 포함), 보기 모드 (F-294 4.2)

### Q4. 공유받은 문서 본문을 검색할 것인가 — **기본값: 이번엔 제목만** (5.2)

본문까지 하려면 공유받은 문서 수만큼 `api.getDoc` 요청이 나가고 F-207 캐시 정책을 바꿔야 한다. 별도 명세로 미룬다

### Q5. 단축키 `Ctrl+Shift+F` 로 확정할 것인가 — **확정 (2026-09-21)**

코드상 겹치는 바인딩이 없는 것은 확인했다(2.3). 남아 있던 "Chrome 자체가 이 조합을 쓰는지" 는 **F-287 7.2 에서 실측해 확정했다** — 실제 Chrome(channel `chrome`) 헤드리스·헤드풀 양쪽에서 페이지가 `keydown`(`key: 'F'`, ctrl+shift)을 그대로 받는다. `e.key` 가 **대문자 `'F'`** 로 오므로 비교할 때 `toLowerCase()` 가 필요하다. CM6 키맵이 이 조합을 잡지 않는 것도 `@codemirror/view` 소스에서 확인했다 (F-287 7.3)

### Q6. 값 일치를 완전일치로 둘 것인가 — **기본값: 완전일치** (3.2)

부분일치가 편할 때도 있지만(`tag:회` → `회고`) 필터가 헐거워진다. 부분일치가 필요하면 본문 검색어를 쓰면 된다

### Q7. 같은 키를 여러 번 쓸 때 AND 인가 OR 인가 — **기본값: AND** (3.2)

규칙이 하나라 설명하기 쉽다. `tags:a tags:b` = 둘 다 가진 문서. OR 이 필요하다는 의견이 나오면 그때 문법(`tags:a,b`)을 정한다

### 기본값으로 정한 것 (승인 시 확정)
