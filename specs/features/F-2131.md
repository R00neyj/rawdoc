## 2. 리졸버 — `githubImages.ts` (순수)

### 2.1 계약

```ts
// src/lib/imageMarkdown.ts
export type ImageTarget = { id: string; ext: ImageExt } | { repoPath: string; src: string }

// src/app/githubImages.ts
export type GithubImageScope =
  | { kind: 'doc'; docId: string }
  | { kind: 'pub'; token: string }
  | { kind: 'pubSet'; token: string; docId: string }
  | { kind: 'pubFolder'; token: string; docId: string }
export function githubProxySrc(scope: GithubImageScope, repoPath: string): string
export function parseGithubImageMap(raw: unknown): GithubImageMap | null
export function githubImageResolver(map: GithubImageMap, scope: GithubImageScope): ResolveImagePath
export function githubAttachmentOf(map: GithubImageMap, id: string): { ext: ImageExt } | null
```

- `ImageTarget` 에 `src` 를 넣는다(F-3013 3.8 ⑤ 는 `{ repoPath }` 만): 주소를 리졸버가 만들면 그리는 세 곳이 문서 id·공개 토큰을 따로 받지 않는다. `repoPath` 는 테스트 선택자·다시 시도용
- `githubProxySrc` 는 F-3017 4장 주소 넷 그대로, `path` 는 `encodeURIComponent`(`/` 도 `%2F`): `doc` → `/api/docs/{id}/github/img?path=`, `pub` → `/pub/docs/{token}/gh?path=`, `pubSet` → `/pub/docs/{token}/docs/{docId}/gh?path=`, `pubFolder` → `/pub/folders/{token}/docs/{docId}/gh?path=`. 토큰·id 도 `encodeURIComponent`
- `parseGithubImageMap`: `path` 가 `isRepoMdPath` 를 지나고 `images` 가 객체여야 한다(아니면 null). `images` 항목은 키가 문자열, 값이 `^[0-9a-f]{16}\.(png|jpg|gif|webp)$` 인 것만 남긴다
- `githubImageResolver(map, scope)(url)`: `resolveRepoPath(map.path, url)` 가 null 이면 null. `map.images[p]` 가 있으면 `{ id, ext }`, 없으면 `{ repoPath: p, src: githubProxySrc(scope, p) }`. **url 별 결과를 리졸버 안 `Map` 에 메모한다**(r7). 리졸버는 대응표가 바뀌면 새로 만든다
- `imageLineTarget` 은 그대로 — 외부 주소·`attachments/` 형식은 리졸버를 부르지 않는다(F-2127 2.2)

### 2.2 외부 요청 금지와의 관계 (F-2127 E2)
- 상대 경로가 요청되는 것은 **연결된 문서에서 대응표를 받은 뒤**뿐이고, 요청 주소는 늘 같은 출처의 첨부 주소나 2.1 프록시 주소다. 원문 url(`./img/a.png`)을 `src` 로 쓰는 일은 없다. 리졸버가 없는 화면(로그아웃 로컬 문서, 금고 문서, 연결 없는 문서, `SharedView`, 내보내기·인쇄)은 F-2127 그대로 글자·링크. F-2127 E2(로그아웃 문서)는 그대로 지난다

## 3. 그리기

### 3.1 편집기 다시 그리기 (F-3013 3.8 ④)

```ts
// src/editor/preview/imagePaths.ts
export const imagePathsChanged: StateEffectType<ResolveImagePath | null>
export const imagePathsField: StateField<ResolveImagePath | null>
// createEditor handle
setImagePaths(resolve: ResolveImagePath | null): void
```

- r2 선례 그대로: 필드는 효과 값으로 바뀐다. `createEditor` 는 필드를 **`previewCompartment` 밖** 최상위 확장에 `init(() => resolveImagePath ?? null)` 로 넣는다 — 모드·테마 전환 뒤에도 마지막 리졸버가 남는다. `blockPreview` 의 `build` 는 `state.field(imagePathsField, false) ?? resolveImagePath`(옵션 — `buildBlocks` 매개변수·기존 테스트 그대로)로 그린다
- StateField `update`: 트랜잭션에 `imagePathsChanged` 가 있으면 문서 변경과 같게 다룬다 — 조합 중(`isComposing`·`isCellComposing`·`isFrontmatterComposing`)이면 다시 그리지 않고 `stale: true` 로 두고, 아니면 `build`. 선택만 바뀐 갱신의 "열쇠가 같으면 건너뛰기" 에 걸리지 않는다. 조합 끝 `forceRecalc` 가 따라잡는다(불변식). 원격 Yjs 갱신이 아니라 게이트와 무관
- `Editor.tsx` 는 `resolveImagePath` prop 을 마운트 때 `createEditor` 에 넘기고, 이후 값은 `useEditorSync` 가 `setImagePaths` 로 민다(`setWikiContext` 와 같은 조건: `openDoc?.id === currentDocId`)

### 3.2 위젯 (`imageWidget.ts`, F-3013 3.8 ⑤)
- `buildBlocks` 의 이미지 줄 갈래는 저장소 갈래면 위젯에 `{ repoPath, src }` 를 넘긴다(`id`·`ext` 는 빈 글자). 같음 열쇠(`key`)에 `repoPath`·`src` 를 넣고, `updateDOM` 은 첨부↔저장소 갈래나 `src` 가 바뀌면 false — 대응이 늦게 오면 프록시 그림이 첨부 그림으로 바뀐다
- 저장소 갈래 `toDOM`: 바깥 `.md-image` 에 `data-img-repo="{repoPath}"`. `loadAttachment` 대신 `<img class="md-image-img" src="{src}">` 를 바로 넣고 `load` 때 `naturalWidth/Height` 로 `aspect-ratio`. `error` 면 자리 표시(`이미지를 찾을 수 없습니다`)를 그리고 **35,000ms 뒤 한 번** 같은 주소에 `&retry=1` 을 붙여 다시 시도(r10: D1 최대 30초 + 5초). 그때 위젯이 문서에서 빠졌으면 하지 않는다. blob URL 을 만들지 않으므로 캐시·해제 대상이 아니다
- 정렬·너비·삭제·더블클릭은 `form: 'markdown'` 경로 그대로 — alt 조각만 고치고 url 은 건드리지 않는다

### 3.3 보기 (`renderMarkdown.ts`, `Viewer.tsx`)
- `parseImageParagraph` 의 저장소 갈래 출력(계약):
  `<div class="md-image md-image--{align}"{lineAttr}{style}><img src="{src}" data-repo-path="{repoPath}" alt="{alt}"{widthAttr}></div>\n` — 첨부 갈래와 같은 틀에 `data-attachment` 대신 `src`·`data-repo-path`(둘 다 `escapeHtml`). 토큰 `meta` 는 `{ align, alt, width, repoPath, src }`. `meta` 를 읽는 `toPlainText`·`exportVault` 는 리졸버를 넘기지 않아 이 갈래를 만나지 않는다
- `Viewer` 채우기: `img[data-repo-path]` 는 이미 `src` 가 있어 읽지 않는다. `error` 에 `showPlaceholder` + 3.2 와 같은 35초 한 번 다시 시도. 보기 변환 두 곳(r5)은 `resolveImagePath` 를 넘기고, `useEditorSync` 효과의 deps 에 넣어 대응표가 늦게 오면 HTML 을 다시 만든다

### 3.4 공개 화면 (`PublicView.tsx`, `publicDoc.ts`)

## 4. 대응표 흐름 — `useGithubImages`

### 4.1 계약

```ts
export type GithubImagesHandle = {
  resolveImagePath: ResolveImagePath | null
  attachmentHint: (id: string) => { ext: ImageExt; docId?: string } | null
  setMap: (docId: string, map: GithubImageMap | null) => void
  addImage: (docId: string, path: string, attachment: string) => void
}
export function useGithubImages(o: { store: Store; currentDoc: DocMeta | null }): GithubImagesHandle
```

### 4.2 규칙
- **대상**: `store.kind === 'server'` 이고 지금 문서가 있고 `e2ee` 가 없을 때. 아니면 `resolveImagePath: null`, 요청 0
- **언제 받나 — 처음 필요할 때 한 번**: 상태는 문서별 `unknown | loading | none | ready(map) | failed(at)`, 메모리에만(저장소에 쓰지 않는다). `unknown`·`failed` 에서 리졸버는 null 을 돌려주고 **처음 불릴 때** `GET /api/docs/{id}/github/images` 를 예약한다(리졸버는 CM 갱신·렌더 안에서 불리므로 `queueMicrotask` 로 밖에서 시작, 같은 문서 동시 요청은 하나). 리졸버는 이미지 줄의 상대 경로에만 불리므로 그런 줄이 없는 문서는 요청 0
  - 200 → `parseGithubImageMap` → `ready`(틀리면 `none`). 404 → `none`. 그 밖·네트워크 → `failed(now)`, 60,000ms(`GITHUB_LINK_FRESH_MS`) 지난 뒤 다음 호출에서 다시
  - `ready` 는 그 문서를 다시 열어도 60,000ms 안이면 다시 받지 않는다. 계정 id 가 바뀌면 모두 비운다
- `ready(map)` → `githubImageResolver(map, { kind: 'doc', docId })`. 상태가 바뀔 때만 새 리졸버(같은 상태면 같은 함수)
- `setMap`: `useGithubFlow` 가 연결 캐시를 채우거나(`GithubLink` 의 `path`·`images`) 지울 때(`null` → `none`) 부른다 — 연결·가져오기·해제가 곧바로 화면에 반영된다
- `addImage`: 받아 넣기가 대응 하나를 기록할 때마다. 그 문서가 `ready` 면 `images` 에 더하고 새 리졸버 → 편집기 `setImagePaths`(3.1) → 그 줄이 첨부 그림으로 바뀐다

### 4.3 첨부 힌트 (r4)
- `Store.getAttachment(id, hint?: { ext: AttachmentExt; docId?: string })`. `serverStore` 는 캐시 본문에서 못 찾으면 `hint.docId` 를 `?doc=` 로 쓴다(지금은 `ext` 만). `idbStore`·`memoryStore` 는 힌트를 보지 않는다
- `useEditorSync` 의 `attachmentResolverFor` 는 `attachmentHint(id)` 를 **부를 때마다 ref 로 읽어** 넘긴다(편집기가 콜백을 마운트 때만 받으므로, r3). 힌트 = 지금 문서 대응표에서 그 id 의 `ext`, `docId` 는 내 문서가 아닐 때만(주인은 `?doc=` 판정이 D1 늦음 r10 을 타지 않게)

## 5. 받아 넣기 (F-3013 3.7 클라이언트 쪽)

### 5.1 언제 — 주인만
- **가져오기**: `useGithubFlow` `importFile` 의 `open(id, created)` 에서 `created` 가 있을 때(연결 PUT 이 성공한 뒤다) → `created.content`, `file.path`
- **당기기**: `useGithubPull` 이 부르는 `onSynced(docId, …)` 에서(합쳐 적용 뒤와 "같음" 둘 다, F-2129 4.3·4.4 의 204 뒤) 그 문서가 지금 문서면 편집기 `getText('lf')`, 아니면 건너뛴다. 연결 경로는 링크 캐시의 `path`
- 같은 문서에 이미 돌고 있으면 끝난 뒤 **한 번만** 마지막 본문으로 다시 돈다. 계정이 바뀌면 `AbortSignal` 로 멈춘다. 문서를 옮겨도 계속 돈다(대응은 문서별 서버 기록). 편집자·보기 권한은 받아 넣지 않는다(서버 라우트도 주인만). 금고 문서는 r11 로 생기지 않고, 클라이언트도 `githubDocRole` 이 null 이면 시작하지 않는다

### 5.2 순서 — `runGithubImageImport`

```ts
export const GITHUB_IMAGE_IMPORT_MAX = 50
export const GITHUB_IMAGE_IMPORT_CONCURRENCY = 2
export const GITHUB_IMAGE_IMPORT_MAX_BYTES = 5_242_880 // worker MAX_ATTACHMENT_BYTES
export function planGithubImageImport(sources: GithubImageSource[]): GithubImageSource[]
export function runGithubImageImport(input: { content: string; mdPath: string }, deps: GithubImageImportDeps):
  Promise<{ mapped: number; skipped: number; stopped: 'sources' | 'quota' | 'rate' | 'blocked' | 'too_many' | 'not_found' | 'aborted' | null }>
```

`deps` 는 `imageSources`·`raw`·`putImage`(5.3), `toWebp`, `upload(id, ext, blob)`(`uploadAttachment`, 실패는 `AttachmentApiError` 를 던짐), `newId()`(16자 소문자 16진수), `onMapped(path, attachment)`, `signal` — 테스트가 가짜를 넣는다

1. `paths` = `repoImagePaths(content, mdPath)` 의 앞 500개(`GITHUB_IMAGE_SOURCES_MAX_PATHS`). 비면 요청 0으로 끝
2. `image-sources` 1번. 실패 → `stopped: 'sources'`
3. `planGithubImageImport`: 응답 순서대로 `mapped` 아님(Q1) ∧ 경로가 `.svg` 로 끝나지 않음(대소문자 무시 — SVG 는 늘 프록시라 받지 않는다) ∧ `size ≤ 5,242,880` 인 것의 앞 50개
4. 동시 2개씩, 한 장마다: `raw` → `inspectImageBytes` 가 null 이면 건너뜀(프록시로 남음) → 그 `ext` 가 `gif`·`webp` 면 그대로, 아니면 `toWebp` 결과가 원본과 다르면 `webp` 아니면 원래 `ext` → `upload(newId(), ext, blob)` → `putImage({ path, blobSha: source.sha, attachment: '{id}.{ext}' })` 204 → `onMapped`
5. 멈춤(남은 것은 시작하지 않고 진행 중인 것은 끝낸다): 첨부 `quota_exceeded`·`rate_limited`·`account_blocked`, `putImage` 409 `too_many`·404, `signal`. 그 밖 실패(`raw` 413·404, 첨부 `too_large`·`unsupported`·`type_mismatch`·`network`, `putImage` 그 밖)는 그 장만 건너뛴다
- 올리고 대응 기록에 실패한 첨부는 참조가 없어 하루 뒤 정리된다(F-219)
- 동시 2: 한 장이 최대 5MB 원본 + 디코딩 비트맵(40,000,000 픽셀이면 약 160MB)이라 메모리를 묶는다. 50장 = 쓰기 101번(r8) < 분당 120
- 첨부 300MB 한도(F-221)에 든다 — `quota_exceeded` 면 멈춤

- **진행 표시 없음** (Q2): 그동안 그림은 프록시로 보이고(3.2) 하나 기록될 때마다 첨부 그림으로 바뀐다. 실패도 알리지 않는다 — 프록시로 남고 다음 당기기가 다시 시도한다

### 5.3 `githubApi.ts` 함수
`postDocGithubImageSources(id, body)` → `GithubImageSources`, `getDocGithubRaw(id, path)` → `Uint8Array`(`arrayBuffer()`, JSON 아님), `putDocGithubImage(id, body)` → `true`(204), `getDocGithubImages(id)` → `GithubImageMap`(`parseGithubImageMap`). 모두 `GithubResult`, 던지지 않는다. 받아 넣기는 `watch` 를 거친다(꺼짐·다시 연결 필요 → 상태 다시 읽기, F-2128 2장 ⑥)

### 5.4 Q1 서버 칸 — `image-sources` 응답
`GithubImageSource = { path: string; sha: string; size: number; mapped: boolean }`. `handleGithubImageSources` 가 응답 전 `SELECT path, blob_sha FROM github_images WHERE doc_id = ?` 1번(최대 1,000행) → `mapped` = 같은 `path` 행이 있고 `blob_sha === sha`. 그 밖은 F-3017 2.3 그대로

## 11. 열린 질문

### Q1. 바뀐 저장소 그림을 어떻게 아나 — **기본값: `image-sources` 응답에 `mapped` 칸 (5.4)**
- 이유: r1 — 클라이언트는 `blob_sha` 를 모른다. 서버는 대응 행과 GitHub sha 를 한 자리에서 비교할 수 있고 D1 읽기 1번이다. 저장소에서 그림을 바꾸면 다음 당기기에 새로 받는다
- 다른 안: 서버를 고치지 않고 "대응이 없는 경로만" 받는다 — `worker/`·계약이 그대로지만, 저장소에서 같은 경로의 그림을 바꿔도 연결을 끊었다 다시 잇기 전까지 옛 그림이 보인다. 5.2 3번의 `mapped` 조건이 "대응표에 없음" 으로, 5.4·그 단위 테스트·9장 첫 줄이 빠진다

### Q2. 받아 넣는 동안 알림 — **기본값: 없음 (5.2 끝)**
- 이유: 그림은 그동안 프록시로 보이고, 알림 띠 한 칸을 결과 문구와 다투지 않는다
- 다른 안: 끝나면 `저장소 그림 {n}개를 받아 넣었습니다`(받은 것이 있을 때만) 알림 — 당기기 결과 문구 바로 뒤에 덮어쓴다. `runGithubImageImport` 결과로 `useGithubFlow` 가 띄우고 `ia.md` 6장에 한 줄
