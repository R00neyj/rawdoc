## 2. `worker/pushSend.ts` — 보내기 한 벌 (계약)

**나누는 선**: `pushRun.ts` 는 "문서 알림 행을 모아 누구에게 무엇을 보낼지" 를 정하고, `pushSend.ts` 는 "정해진 기기들에 실제로 보내기" 만 한다. 보내기 루프는 `pushSend.ts` 한 곳에만 있다. `./auth` 를 import 하지 않는다(F-3003 4장 머리 — DO 인 `docRoomCore` 가 F-3008 에서 이 파일을 쓴다)

```ts
export const PUSH_SEND_CONCURRENCY = 6   // pushRun.ts 에서 옮김. pushRun.ts 는 같은 이름으로 다시 내보낸다

export type PushJob = { sub: LivePushSubscription; payload: PushPayload; topic?: string }
export type PushJobResult = { sub: LivePushSubscription; outcome: PushOutcome }

// 동시 최대 PUSH_SEND_CONCURRENCY. 던지지 않는다(sendPush 가 던지지 않는다). 결과 순서는 보장하지 않는다
export function sendPushJobs(jobs: readonly PushJob[], auth: VapidAuth, now: number, fetchImpl?: typeof fetch): Promise<PushJobResult[]>

// 산 구독 읽기 1 → 기기마다 보내기 → 결과 문장이 있으면 batch 1. 보낸 기기 수를 돌려준다. D1 예외는 그대로 던진다
export function pushToEmail(db: D1Database, auth: VapidAuth, email: string, payload: PushPayload, now: number, fetchImpl?: typeof fetch): Promise<number>

// Worker 요청용. VAPID 가 없으면 task 를 부르지 않고 끝(D1 0). 있으면 createVapidAuth 한 번 → task.
// ctx.waitUntil 이 있으면 거기 맡기고 곧바로 끝, 없으면 await. task 의 예외는 console.warn 한 줄로 삼킨다
export function pushInBackground(env: Env, ctx: ExecutionContext | undefined, label: string, task: (auth: VapidAuth) => Promise<void>): Promise<void>
```

- `loadVapid` 도 `waitUntil` 안에서 부른다 — 응답이 키 가져오기를 기다리지 않는다
- `pushToEmail` 의 하위 요청은 최대 **1 + 기기 수(≤ 5, `PUSH_SUBSCRIPTIONS_PER_USER_MAX`) + 1**. F-3008 은 이 수를 제 예산에 넣는다
- `runDocPush` 는 `sendPushJobs` 를 부르고 결과 batch(행 NULL·오래된 행·`pushResultStatements`)는 지금처럼 스스로 짠다 — 그 batch 는 알림 행 문장과 한 묶음이어야 해서 `pushToEmail` 을 쓰지 않는다
- **`waitUntil` 을 쓰는 이유**: 초대 응답이 푸시 서비스 왕복(최대 10초 시간 초과, `PUSH_SEND_TIMEOUT_MS`)을 기다리면 초대 대화상자가 멈춘다. F-3001 3.1 "푸시는 `waitUntil`" 그대로. `waitUntil` 작업도 같은 호출의 CPU 10 ms·하위 요청 50 에 들어간다(Cloudflare 일반 지식, **확인 안 함**) — 예산은 3.3

## 3. 초대 `PUT` 에서 보내기

### 3.1 새 초대 판정과 이름

- 초대 `INSERT` 끝에 `RETURNING created_at`. batch 결과 첫 항목의 `results[0].created_at === now` 일 때만 "새 초대". 결과가 없거나 다르면(역할만 바꿈·옛 `created_at`) 푸시 없음 — 문장이 하나도 늘지 않는다
- `checkOwnedTarget` 이 문서 `title`·폴더 `name` 을 같은 SELECT 에서 더 읽어 `{ ok: true, e2ee, name }` 으로 돌려준다(질의 수 그대로). SQL 모양(계약 — 6장 가짜 D1 이 접두사로 맞춘다):
  - `SELECT id, owner_id, folder_id, e2ee_key, title FROM docs WHERE id = ?`
  - `SELECT id, owner_id, e2ee, name FROM folders WHERE id = ?`
- 금고는 지금처럼 409 가 먼저라 제목 암호문이 푸시에 들 길이 없다(F-3001 3.9)

### 3.2 겹침 막기 (F-3001 3.5 + 경계 하나)

새 초대면 `pushInBackground(env, ctx, 'share', …)` 안에서 순서대로:

1. 한 문장(계약):

```sql
SELECT 1 FROM grants
 WHERE grantee_email = ?1 AND owner_id = ?2 AND created_at > ?3 AND created_at <= ?4
   AND NOT (target_type = ?5 AND target_id = ?6)
 LIMIT 1
-- ?3 = now − PUSH_SHARE_DEDUPE_MS, ?4 = now
```

   행이 있으면 끝. 대상 종류는 가리지 않는다(문서·폴더 초대가 섞여도 한 번)
2. `pushToEmail(env.DB, auth, grantee, sharePushPayload({ actorEmail: user.email, target, targetId, name, role }), now)`. 받는 사람 계정·구독이 없으면 구독 읽기 0행 → 끝

- **`created_at <= now` 인 이유**: 한 사람에게 두 초대가 동시에 들어오면 서로의 행을 보고 둘 다 건너뛸 수 있다. 이번 것보다 늦게 만든 행을 세지 않으면 가장 이른 초대 하나가 보낸다. 같은 ms 에 둘이면 둘 다 건너뛴다 — 받아들인다(알림함이 원본이 아니라 공유 목록에 이미 보인다)
- 10분 경계: 앞 초대가 정확히 `now − 600,000` 이면 세지 않는다(`>`)
- **알려진 한계**(Q1): 초대를 지우면 그 행이 사라지므로, 같은 대상에 "초대 → 지움 → 초대" 를 되풀이하면 매번 보낸다. 같은 `tag`(`share:{id}`)라 OS 가 바꿔 끼우고 `renotify` 거짓이라 **알림이 떠 있는 동안에는 다시 울리지 않는다**. 지운 뒤(사용자가 알림을 닫은 뒤)에는 다시 울린다. 속도는 `WRITE_LIMITER`(분당 120 쓰기, `wrangler.jsonc`)가 묶는다

### 3.3 예산

- 푸시가 더하는 하위 요청: 겹침 1 + 구독 1 + 기기 ≤ 5 + 결과 batch ≤ 1 = **최대 8**. 기존 초대 요청 몫(세션·소유 확인·batch·`notifyRevalidate` RPC)과 더해도 50 에 멀다
- CPU: 기기 5대 암호화 ≈ 3.4 ms(F-3001 p2, node 측정). 초대 요청 자체의 CPU 는 workerd 에서 재지 못했다 — 사람 확인 7장 ②(F-3001 9장 ⑦ 과 같은 항목)
- 겹침·구독 질의는 새 초대이고 VAPID 가 있을 때만 돈다. 역할만 바꾸는 `PUT`·`DELETE` 는 D1 호출이 지금과 같다

## 4. `testD1.ts` — batch 결과
