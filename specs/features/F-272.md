## 1. 범위

### 한다

- 저장소 `content/` 를 두고, **빌드 때** 그 안 `.md` 를 완결된 HTML 페이지로 바꿔 `dist/` 에 쓴다
- 사이트 공통 머리·꼬리와 그 CSS 를 한 모듈에 두고 **랜딩(`/`)도 같은 것을 쓴다**
- 없는 주소에 `404` 를 준다 (`dist/404.html` + `wrangler.jsonc`)
- `sitemap.xml`·`robots.txt` 를 빌드가 만든다
- 사이트 경로를 서비스 워커에서 뺀다 (`navigateFallbackDenylist`, precache 제외)
- 사이트 글에 쓸 수 있는 문법과 쓸 수 없는 문법을 **빌드 가드**로 못박는다 (9장)

### 하지 않는다 (F-273~F-276)

- `content/` 안의 **실제 글**. 체인지로그(F-273)·도움말(F-274)·법적 문서(F-275)·사용법 글과 `/guides` 목록(F-276)은 각자 자기 명세에서 파일을 더한다. 이 명세가 끝난 시점에 `content/` 는 비어 있고, 빌드는 `404.html`·`sitemap.xml`·`robots.txt` 세 개만 낸다
- 앱에서 사이트로 가는 링크 (F-276)
- 랜딩의 카피·섹션 구성·편집기 데모 (F-239·F-271 그대로 둔다. 이 명세가 바꾸는 것은 머리·꼬리뿐이다)
- 사이트 글의 목차·태그·검색·RSS·댓글·다국어 (F-270 5장)
- 분석·추적 스크립트, 쿠키 동의 배너 (F-270 5장)
- 사이트 페이지에 앱 자바스크립트를 싣는 일. 사이트 페이지는 **스크립트가 없다**

## 3. 빌드 단계

### 3.1 어디에 붙이나 — `vite build` 안의 플러그인

`npm run build` 를 `vite build && node …` 로 늘리지 않는다. **`vite.config.ts` 의 플러그인**으로 넣는다.

- `playwright.config.js` 의 webServer 는 `npm run build` 가 아니라 `npx vite build --outDir {dist}` 를 부른다. 스크립트를 늘리면 e2e·`npm run measure`(`dist-measure`)·`E2E_DIST` 슬롯이 사이트 파일 없는 `dist` 를 보게 된다
- Cloudflare Workers Builds 와 `npm run dev:worker` 는 `npm run build` 를 부르므로 어느 쪽이든 같다
- 출력 위치는 `config.build.outDir` 에서 받는다 — `--outDir dist-a` 슬롯이 그대로 동작한다

### 3.2 플러그인 (`vite.config.ts`, 파일 입출력만)

```ts
function sitePlugin(): Plugin   // plugins 배열에서 VitePWA(...) 뒤에 둔다
```

| 항목 | 값 |
| --- | --- |
| `enforce` | `'post'` |
| `apply` | `'build'` |
| `configResolved` | `outDir = path.resolve(config.root, config.build.outDir)` 를 기억한다 |
| 훅 | `closeBundle: { sequential: true, order: 'post', handler }` |

`handler` 가 하는 일은 넷뿐이다.

1. `content/**/*.md` 를 읽어 `{ 'legal/privacy.md': '원문', … }` 로 만든다 (`.md` 만. `.gitkeep` 등은 무시)
2. `dist/assets/index-*.css` 를 찾는다 (5.2). 0개거나 2개 이상이면 **빌드 실패**
3. `buildSite({ content, appCssHref, builtAt })` 를 부른다 (3.3)
4. 돌려받은 `{ 상대경로: 내용 }` 을 `outDir` 아래에 쓴다 (없는 폴더는 만든다)

`buildSite` 가 `Error` 를 던지면 잡지 않는다 — 빌드가 실패해야 한다 (9장 가드).

### 3.3 `site/` — 순수 모듈 (파일 입출력 없음)

```
site/
  build.ts     buildSite(input): Record<상대경로, 내용>  — 진입. sitemap.xml·robots.txt·404.html 도 여기서
  pages.ts     content 상대경로 → 사이트 주소 매핑, 주소 → dist 파일 경로
  guard.ts     사이트 글에 쓸 수 없는 문법 검사 (9장)
  helpPage.ts  도움말 가상 글 항목 — content/ 에 파일이 없다 (F-274)
  guidesIndex.ts  사용법 목록 가상 글 — content/ 에 파일이 없다 (F-276)
  render.ts    글 1개 → 완결된 HTML 문자열
  *.test.ts    위 네 모듈의 단위 테스트
```

```ts
// site/build.ts
export type SiteInput = {
  content: Record<string, string>   // 'legal/privacy.md' → 원문. 플러그인이 읽어서 넘긴다
  appCssHref: string                // '/assets/index-Dv2YhMQ7.css' (5.2)
  builtAt: Date                     // sitemap lastmod 기본값. 테스트는 고정값을 넘긴다
}
export function buildSite(input: SiteInput): Record<string, string>
```

- 파일 입출력을 `site/` 에 두지 않는 이유: 단위 테스트가 임시 폴더 없이 입력 객체 하나로 끝난다. `vite.config.ts` 의 test 환경이 `node` 라 `fs` 를 쓸 수는 있지만, 쓰지 않으면 테스트가 훨씬 짧다
- 의존 방향은 **`site → src`, `site → brand.config`** 한 방향이다. `src/` 는 `site/` 를 import 하지 않는다 (`specs/architecture.md` 1장 규칙에 한 줄 더하는 셈 — 10장 갱신 대상)
- `site/` 는 순수 문자열만 다룬다. DOM·React·`node:fs` 를 import 하지 않는다

### 3.4 보기 모드 변환기를 Node 에서 불러오는 방법

`site/build.ts` 는 `src/viewer/renderMarkdown.ts` 를 import 한다 (F-270 3장 "보기 모드와 같은 `markdown-it` 설정"). 그런데 그 파일은 `src/lib/calloutIcons.ts` → `@material-symbols/svg-400/…/warning.svg?raw` 로 이어진다. **`?raw` 는 Vite 전용이라 Node 가 그대로 못 읽는다.** `vite.config.ts` 를 esbuild 가 번들할 때도 node_modules 는 external 로 남아 같은 문제가 난다.

그래서 플러그인은 Vite 의 `runnerImport` 로 `site/build.ts` 를 불러온다.

```ts
import { runnerImport } from 'vite'
const { module } = await runnerImport<typeof import('./site/build')>(
  '/site/build.ts',
  { root: __dirname, configFile: false },   // configFile:false — 자기 설정을 다시 타면 되돌이가 된다
)
```

- 2026-09-20 실측(Vite 7.3.6, Node 24.12): `runnerImport('/src/viewer/renderMarkdown.ts', { root, configFile: false })` 가 158ms 에 성공했고, 콜아웃 아이콘 svg 가 HTML 에 그대로 들어갔다. `?raw` 는 Vite 코어 기능이라 `configFile: false` 여도 동작한다
- `runnerImport` 는 Vite 가 `@experimental` 로 표시한 API 다. Vite 를 올린 뒤 깨지면 대안은 Node 24 의 `module.registerHooks()` 로 `*.svg?raw` 만 가로채는 20줄짜리 로더다(새 의존성 없음). 지금 그것을 만들지는 않는다 — 11장 M2
- `runnerImport` 는 빌드마다 한 번만 부른다

### 3.5 서비스 워커보다 뒤에 쓴다

`vite-plugin-pwa` 는 `enforce: 'post'` + `closeBundle` 에서 **`dist/` 를 훑어** precache 목록을 만든다. `globPatterns` 가 `**/*.{js,css,html,…}` 라 사이트 HTML 이 그때 이미 있으면 전부 precache 에 들어간다 — 그러면 앱을 한 번 연 브라우저가 배포 뒤에도 옛 글을 본다.

`sitePlugin` 을 `plugins` 배열에서 `VitePWA(...)` **뒤에** 두고 훅에 `order: 'post'` 를 주면 PWA 의 `closeBundle` 다음에 돈다. `globPatterns`·`globIgnores` 는 **건드리지 않는다** — 목록을 늘리면 F-273~F-276 이 파일을 더할 때마다 같이 고쳐야 하고, 빠뜨려도 조용히 통과한다. 대신 순서가 지켜졌는지를 A9 로 판정한다.

### 3.6 `npm run dev` 에서는 사이트가 없다

`apply: 'build'` 라 dev 서버에는 사이트 페이지가 없다. `/changelog` 를 열면 앱이 뜬다. 사이트 확인은 `npm run build` 뒤 `npm run preview` 또는 `npm run dev:worker` 로 한다. dev 에서 사이트를 서빙하는 미들웨어는 만들지 않는다 — 쓸 일이 글 고칠 때뿐이고, 미들웨어를 두면 빌드 경로와 dev 경로 두 벌을 맞춰야 한다.

## 4. 보기 모드 변환기가 Node 에서 어디까지 도는가

F-270 3장이 "콜아웃·위키링크·Mermaid 처럼 브라우저가 필요한 확장이 Node 에서 도는지는 F-272 에서 확인" 으로 미뤄 둔 항목이다. **2026-09-20 `renderMarkdown.ts` 를 실제로 Node 에서 돌려 확인했다.**

| 문법 | Node 결과 | 사이트 글에서 |
| --- | --- | --- |
| 제목·문단·강조·목록·인용·표·수평선 | 그대로 나온다 | **쓴다** |
| 작업 목록 `- [ ]` | `<input type="checkbox" disabled>` | **쓴다** |
| 코드블록·인라인코드 | 그대로. 구문 강조는 원래 없다 | **쓴다** |
| 콜아웃 `> [!warning]` | `<div class="markdown-callout md-callout--warning">` + 아이콘 svg 원문까지 **완전히 나온다** | **쓴다** |
| 하이라이트 `==…==` | `<mark>` 로 나온다 (F-283 이후) | **쓴다** |
| 위키링크 `[[…]]` | `env.resolveWikiLink` 를 안 넘기면 `<span class="wikilink wikilink--plain">별칭</span>` — **글자로만** 보이고 눌리지 않는다 | **주소를 넘기지 않는다.** 문법을 소개할 때는 인라인코드(`` `[[제목]]` ``)로 감싼다 |
| Mermaid ` ```mermaid ` | `<div class="md-mermaid" data-mermaid-source="…">` **빈 자리표시만.** 실제 그림은 브라우저에서 mermaid 번들이 채우는데 사이트 페이지에는 스크립트가 없다 | **금지.** 빌드 가드가 막는다 (9장) |
| 이미지 `![alt](url)` | `md.renderer.rules.image` 가 `<a>이미지: alt</a>` **링크로 바꾼다**(F-123 오프라인 원칙) | **금지.** 빌드 가드가 막는다 (9장) |
| 이미지 블록 `<div class="md-image">` | `src` 없는 `<img data-attachment="…">` — 앱만 채운다 | **금지.** 같은 가드 |
| 프론트매터 | `renderMarkdown` 이 **표로 렌더한다** | 본문에 넣지 않는다 — 6.1 에서 떼고 본문만 넘긴다 |

그 밖에 확인한 두 가지:

- 제목에 `data-source-line="n"` 속성이 붙는다(F-144). 사이트 HTML 에도 남지만 보이지 않고 해가 없어 **그대로 둔다**
- 본문 링크에 `target="_blank" rel="noopener noreferrer"` 가 붙는다(F-123). 사이트 안 링크(`/help` 등)도 새 탭으로 열린다. 이번에는 **그대로 둔다** — 11장 M3

## 5. 공통 틀

### 5.1 `src/lib/siteChrome.ts` (신규, 순수)

랜딩(워커가 요청마다 만드는 HTML)과 사이트 페이지(빌드가 만드는 HTML) 둘 다 쓰므로 `src/lib/` 에 둔다. 워커는 `src/lib/**` 순수 함수만 import 한다(`specs/architecture.md` 6장, F-271 의 `appEntry.ts` 와 같은 자리).

```ts
export type SiteLink = { path: string; label: string }

// F-273~F-276 이 자기 페이지를 만들면서 한 줄씩 더한다. 이 명세는 둘 다 빈 배열로 둔다
export const SITE_NAV: SiteLink[] = []            // 머리 — 사용법·체인지로그·도움말
export const SITE_FOOTER_LINKS: SiteLink[] = []   // 꼬리 — 개인정보 처리방침·이용약관

export const SITE_CHROME_CSS: string

export function renderSiteHeader(args: {
  brandName: string
  brandIcon: string
  current?: string                  // 지금 페이지 주소. 같은 항목에 aria-current="page"
  appCta: 'link' | 'enter'          // 'enter' 는 랜딩용 — data-cta="enter" 를 붙인다 (5.4)
}): string

export function renderSiteFooter(args: { brandName: string }): string
```

- 제품명·아이콘·색을 **이 파일이 직접 적지 않는다.** 부르는 쪽(`worker/welcomePage.ts`·`site/render.ts`)이 `brand.config` 에서 읽어 넘긴다 (`CLAUDE.md` 불변조건)
- 머리: 로고(아이콘+제품명, `/` 링크) → `SITE_NAV` → `앱 열기`
- 꼬리: 제품명 → `SITE_FOOTER_LINKS`
- 운영자 표기·연락처는 꼬리에 넣지 않는다 (F-270 4장 — 나중에 정한다)
- 클래스 이름은 전부 `site-` 로 시작한다 (`.site-head`·`.site-brand`·`.site-nav`·`.site-app`·`.site-foot`). 랜딩 인라인 CSS 의 `.wrap`·`.bar`·`.brand` 와 부딪히지 않게 한다
- `SITE_CHROME_CSS` 는 색·서체를 토큰(`--ink`·`--ink-2`·`--muted`·`--rule`·`--paper`·`--panel`·`--accent`·`--font-display`·`--font-body`)으로만 쓴다. 사이트 페이지는 앱 CSS(5.2)에서, 랜딩은 자기 `:root` 블록에서 같은 이름을 얻는다. **폭 값은 자기 변수(`--site-page`·`--site-read`)로 정의한다** — `--page`·`--read-w` 는 랜딩에만 있고 `tokens.css` 에는 없다

### 5.2 사이트 페이지의 CSS — 앱 빌드 결과를 그대로 링크한다

사이트 페이지는 `<link rel="stylesheet" href="{appCssHref}">` 하나 + `SITE_CHROME_CSS` 를 담은 `<style>` 하나를 쓴다. `appCssHref` 는 플러그인이 찾은 `/assets/index-{해시}.css` 다.

- 그 파일 하나에 `tokens.css`·`markdown.css`·`callout.css`·`frontmatter.css`·`wikilink.css` 와 **서체 `@font-face`(해시 붙은 woff2 주소까지)** 가 전부 들어 있다. 본문 스타일·서체를 다시 적지 않는다 — 값을 흩어 쓰지 않는 것이 목적이다(`CLAUDE.md` 불변조건의 취지)
- 크기는 80KB(압축 전, 2026-09-20 `dist/assets/index-Dv2YhMQ7.css`). 앱과 같은 파일이라 사이트를 먼저 본 사람은 앱을 열 때 캐시를 다시 쓴다
- `--brand-accent` 는 `index.html` 에만 주입되므로 사이트 페이지가 `<style>:root{--brand-accent:{brand.accent}}</style>` 를 직접 넣는다 (랜딩이 하는 것과 같다)
- **본문 감싸개**: `markdown.css`·`callout.css`·`frontmatter.css` 의 선택자가 `:is(.app-shell, .public-view) .markdown-body` 로 잠겨 있다(65곳). 선택자를 고치는 대신 사이트 본문을 `<div class="site-article public-view"><article class="markdown-body">…` 로 감싸고, `SITE_CHROME_CSS` 가 `.public-view` 의 앱 전용 값 넷만 되돌린다

```css
/* app.css 의 .public-view(공개 보기 화면 S-5)는 화면 꽉 채우는 flex 열이다.
   사이트 글은 그 선택자만 빌려 쓰고 배치는 문서 흐름으로 되돌린다 (F-272 5.2) */
.site-article.public-view { display: block; height: auto; width: auto; background: none; }
```

- 테마는 `tokens.css` 기본값(화이트)이다. 사이트 페이지에는 `data-theme` 을 쓰는 스크립트가 없어 다크 모드 사용자도 밝은 화면을 본다 — 랜딩(`color-scheme: light`)과 같다. 12장 H4

- `<title>` 의 `{제목} · {brand.name}` 은 `worker/publicPage.ts` 가 쓰는 형식과 같다
- 제목·요약·주소 값은 `escapeHtml` 을 거친다. 본문은 `renderMarkdown` 이 이미 이스케이프한다(`html: false`)
- 스크립트 태그가 하나도 없다. 사이트 페이지는 자바스크립트 없이 완결된다

### 5.4 랜딩에 같은 머리·꼬리 붙이기 (`worker/welcomePage.ts`)

- 지금 `<header class="wrap bar">…</header>` 를 `renderSiteHeader({ …, appCta: 'enter' })` 로, `<footer class="wrap">{brand.name}</footer>` 를 `renderSiteFooter(...)` 로 바꾼다
- 랜딩의 `<style>` 안에 `SITE_CHROME_CSS` 를 이어 붙인다 (랜딩은 CSS 파일을 링크하지 않는 단일 HTML 이다 — F-239 §2)
- `appCta: 'enter'` 인 머리의 `앱 열기` 에는 `data-cta="enter"` 가 붙는다. 랜딩의 기존 CTA 스크립트(F-271 4.3)가 그대로 잡아 **두 값을 쓰고 `location.reload()`** 한다. 안 그러면 랜딩에서 `앱 열기` 를 눌러도 다시 랜딩이 나온다
- 사이트 페이지의 `앱 열기` 는 `appCta: 'link'` — 그냥 `<a href="/">` 다. 처음 온 사람은 `/` 에서 랜딩을 보고 거기서 시작한다(F-270 2장 흐름 그대로)
- 랜딩 본문·히어로·섹션·데모·`?app=1` 안내는 **손대지 않는다**
- `worker/welcomePage.ts` 의 `const siteUrl = 'https://rawdoc.app/'` 를 `src/lib/siteMeta.ts` 의 `SITE_URL` 로 바꾼다 (6.3)

## 6. 글 → 페이지

### 6.1 `content/` 규칙

- `content/**/*.md`. 파일 하나 = 페이지 하나
- 맨 앞에 프론트매터를 둔다. `src/lib/frontmatter.ts` 의 `findFrontmatter`·`textAfterFrontmatter`·`parseSimpleProperties` 를 그대로 쓴다(앱과 같은 해석)

| 키 | 필수 | 쓰임 |
| --- | --- | --- |
| `title` | **필수** | `<title>`·`og:title`. 없으면 빌드 실패 |
| `summary` | 선택 | `description`·`og:description`. 없으면 `SITE_DESCRIPTION` |
| `date` | 선택 | 글 목록 정렬(F-276) |
| `updated` | 선택 | `sitemap.xml` 의 `lastmod`. 없으면 `date`, 그것도 없으면 빌드 시각 |

- 프론트매터는 **떼고 본문만** `renderMarkdown` 에 넘긴다 (4장 표)
- 본문 첫 줄에 `# 제목` 을 다시 쓸지는 글 쪽 판단이다. 이 명세는 제목을 자동으로 넣지 않는다

### 6.2 주소 매핑 (`site/pages.ts`)

```ts
export function contentUrl(relPath: string): string | null
```

| `content/` 상대경로 | 주소 |
| --- | --- |
| `changelog.md` | `/changelog` |
| `help.md` | `/help` — **`content/` 에 실제 파일이 없다.** `site/build.ts` 가 `site/helpPage.ts` 의 가상 항목을 글 목록에 끼워 넣는다 (F-274) |
| `guides.md` | `/guides` — **`content/` 에 실제 파일이 없다.** `site/build.ts` 가 `site/guidesIndex.ts` 의 가상 항목을 글 목록에 끼워 넣는다 (F-276). 목록 본문은 `content/guides/*.md` 의 프론트매터에서 만든다 |
| `legal/privacy.md` | `/privacy` |
| `legal/terms.md` | `/terms` |


`legal/` 만 주소와 폴더가 다르다 — F-270 3장이 정한 원본 위치가 `legal/privacy.md` 이고 주소는 `/privacy` 다. 규칙으로 유도하지 않고 표에 적는다.

### 6.3 `src/lib/siteMeta.ts` 에 `SITE_URL` 추가

```ts
export const SITE_URL = 'https://rawdoc.app/'
```

지금 이 문자열이 `vite.config.ts`·`worker/welcomePage.ts` 두 곳에 따로 있다. canonical·`og:url`·`sitemap.xml`·`robots.txt` 가 모두 이 값을 쓰므로 한 군데로 모으고 세 곳이 여기서 읽는다. (제품 주소는 제품명 문자열이 아니라 배포 주소라 `brand.config.ts` 대상이 아니다 — `siteMeta.ts` 가 이미 같은 성격의 `SITE_DESCRIPTION` 을 갖고 있다.)

### 6.4 `sitemap.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url><loc>https://rawdoc.app/</loc></url>
  <url><loc>https://rawdoc.app/changelog</loc><lastmod>2026-09-20</lastmod></url>
  …
</urlset>
```

- `/` 와 **빌드가 실제로 낸 사이트 페이지 전부**. `404` 는 넣지 않는다
- 네임스페이스는 `http://www.sitemaps.org/schemas/sitemap/0.9` (`sitemaps`, 복수)
- `lastmod` 는 `YYYY-MM-DD` (6.1)
- `changefreq`·`priority` 는 넣지 않는다 (검색엔진이 무시한다)
- 주소 순서는 `SITE_PAGE_ORDER` 없이 **주소 문자열 오름차순** — 빌드마다 결과가 같아야 한다

### 6.5 `robots.txt`

```
User-agent: *
Disallow: /api/
Disallow: /v1/
Disallow: /pub/
Disallow: /p/

Sitemap: https://rawdoc.app/sitemap.xml
```

`/p/*` 는 이미 `X-Robots-Tag: noindex`(F-238)지만 크롤 자체를 줄이려고 함께 막는다.

### 6.6 `404.html`

- 머리·꼬리가 같다. 본문은 `<h1>찾는 페이지가 없습니다</h1>` + 안내 한 줄 + `앱 열기`(`/`) 링크
- `<meta name="robots" content="noindex">` 를 넣는다. canonical 은 넣지 않는다
- `sitemap.xml` 에 넣지 않는다

## 7. 없는 주소에 `404` — `not_found_handling`

F-270 3장은 "사이트 접두사를 `run_worker_first` 에 넣고 워커가 빌드 때 만든 목록에 없으면 404" 로 적었다. **그 방법은 쓰지 않는다.** 빌드가 만든 목록을 워커에 넘기려면 생성 파일을 워커 번들에 넣어야 하는데, 그러면 `npm run typecheck:worker`·CI·`wrangler deploy` 가 빌드 산출물 유무에 묶이고(커밋하면 금방 낡는다) 글이 늘 때마다 워커를 다시 배포해야 한다.

같은 결과를 설정 한 줄로 얻는다.

```jsonc
"assets": {
  "not_found_handling": "404-page",   // 지금 "single-page-application"
  …                                    // directory·binding·run_worker_first 는 그대로
}
```

Cloudflare 문서: `404-page` 는 자산에 없는 요청에 **가장 가까운 `404.html` 을 `404 Not Found` 로** 준다. 사이트 페이지는 실제 파일이라 그대로 나가고, 없는 주소는 검색엔진이 색인하지 않는다. `run_worker_first` 는 손대지 않으므로 사이트 페이지는 워커를 거치지 않는다(요청 수·CPU 를 쓰지 않는다).

### 7.1 SPA 폴백에 기대고 있던 두 곳을 먼저 고친다

`not_found_handling` 을 바꾸면 **`index.html` 을 200 으로 돌려받던 코드가 404.html 을 받는다.** 바꾸기 전에 둘을 고친다.

| 위치 | 지금 | 고친 뒤 |
| --- | --- | --- |
| `worker/publicPage.ts` 88행 | `env.ASSETS.fetch(request)` 로 받은 `index.html` 에 og 메타를 끼워 넣는다. `/p/{token}` 에는 자산이 없어 SPA 폴백에 기대고 있다 | `env.ASSETS.fetch(new URL('/', request.url))` — 루트 자산(`index.html`)을 명시적으로 받는다. `/index.html` 로 받으면 `html_handling` 이 `/` 로 301 하므로 **`/` 로 받아야 한다** |
| `worker/index.ts` `/p/` 분기 | `renderPublicPage` 가 `null`(토큰 형식 오류·폐기·없는 링크)이면 아래 `env.ASSETS.fetch(request)` 로 떨어져 앱이 뜨고, `PublicView` 가 `링크를 찾을 수 없습니다` 를 보여준다 | `/p/` 로 시작하고 `null` 이면 `env.ASSETS.fetch(new URL('/', url))` 로 앱을 준다. 지금 화면이 그대로 유지된다 |

- `/` 분기(F-271 2.1)는 그대로다. `html_handling: auto-trailing-slash` 가 `/` 를 `index.html` 로 풀어 주고, 이는 `not_found_handling` 과 무관하다 — A13 으로 판정한다
- 그 밖의 경로(`return env.ASSETS.fetch(request)`)는 **그대로 둔다.** 이제 없는 경로에 자산 서버가 404.html 을 준다
- 서비스 워커가 있는 브라우저는 `navigateFallback` 때문에 없는 경로에서도 앱을 본다. 이는 F-270 2장이 의도한 동작이고 크롤러에는 해당이 없다

## 8. 서비스 워커 제외 (`vite.config.ts`)

`workbox.navigateFallbackDenylist` 에 사이트 경로를 더한다. 안 더하면 앱을 한 번 연 사람이 `/changelog` 를 열 때 서비스 워커가 앱 `index.html` 을 준다(F-239 §0.2 와 같은 문제).

```js
navigateFallbackDenylist: [
  /^\/api\//, /^\/pub\//, /^\/v1\//, /^\/cdn-cgi\//, /^\/welcome$/,   // 지금 것
  /^\/guides(\/|$)/, /^\/changelog$/, /^\/help$/, /^\/privacy$/, /^\/terms$/,
  /^\/sitemap\.xml$/, /^\/robots\.txt$/, /^\/404(\.html)?$/,
],
```

- 아직 없는 주소까지 미리 넣는다 — F-273~F-276 이 `vite.config.ts` 를 다시 건드리지 않게 한다. 없는 주소를 denylist 에 넣어도 부작용은 없다(서비스 워커가 폴백하지 않고 네트워크로 나갈 뿐이다)
- `navigateFallback: 'index.html'`, `globPatterns`, `globIgnores`, `start_url`·`scope`·`file_handlers` 는 그대로다
- precache 제외는 3.5 의 실행 순서로 보장한다

### 9.1 자리표시 가드와 F-275 (F-270 6장 주석의 결정)

F-270 4장은 "자리표시 `{운영자}`·`{연락처}` 가 남아 있으면 빌드가 실패한다" 로, 6장은 "그러면 F-275 전에는 배포를 못 하니 꼬리 링크를 언제 켤지 F-272 명세 때 정한다" 로 남겨 두었다. 이렇게 정한다.

1. **자리표시 표기는 `{{운영자}}`·`{{연락처}}` 로 한다.** 중괄호 하나는 글 본문에 자연히 나올 수 있다(코드 예시 등)
2. 가드는 `content/**/*.md` **어디에든** `{{…}}` 가 있으면 실패시킨다 (G5)
3. **F-275 는 자리표시가 남은 초안을 `content/` 에 커밋하지 않는다.** 운영자·연락처가 정해진 뒤 채워서 커밋한다. 초안은 그때까지 F-275 명세 안에 둔다
4. **머리·꼬리 링크는 `SITE_NAV`·`SITE_FOOTER_LINKS` 에 적힌 것만 나온다**(5.1). 둘 다 이 명세에서는 빈 배열이고, F-273~F-276 이 자기 페이지를 만들면서 한 줄씩 더한다
5. `buildSite` 는 두 목록의 모든 `path` 가 **실제로 만들어진 페이지인지 검사하고**, 아니면 빌드를 실패시킨다 (`SITE_NAV 의 /changelog 페이지가 없습니다`)

결과: 없는 페이지로 가는 링크가 생길 수 없고, **F-272 이후 커밋의 배포가 F-275 에 막히지 않는다.** F-270 6장 주석이 걱정한 상황이 사라진다.
