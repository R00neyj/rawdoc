# F-3011 공유에서 나가기 — 받는 쪽 grant 자기 삭제 API

작성일: 2026-10-01
상태: 승인 (2026-10-01, 상시 지시 "명세 작성 후 사용자가 검토할 결정이 없으면 바로 구현" — 별도 검토 없이 승인 처리). 서버(`worker/`)만. 형제 명세 F-3012(초대 시 share 알림 행, 서버) · F-2115(사이드바 `⋯` 나가기 UI·확인·뒤처리 — 이 API 를 부른다) · F-2116(알림함 share 행·목록 갱신). UI·클라이언트 함수는 F-2115 몫이고, 여기서는 HTTP 계약만 정한다. 열린 질문 Q1 은 기본값이 있어 기본값이면 바로 구현해도 된다. **F-3012 가 먼저 구현돼 있어야 한다**(3.2 가 그 함수를 부른다)
구현 담당: `feature-implementer`

## 정해진 것 (사용자 결정, 바꾸지 않는다)

1. 나가기 = 받는 쪽이 **자기 grant 행을 삭제**. 숨기기 저장소·hidden 테이블 없음. 되돌리기는 소유자의 같은 이메일 재초대뿐 — `handlePutGrant` 의 `ON CONFLICT … DO UPDATE` upsert 가 행을 새로 만든다(새 `created_at` 이라 F-3007 공유 푸시도 다시 나간다)
2. 폴더 경유 문서(`viaFolder`, F-2058)는 문서 줄에서 나갈 수 없다(UI 가 막는다, F-2115). 폴더에서 나가면 하위가 한꺼번에 빠진다. 문서 단위 "제외" 저장 없음
3. 소유자에게 알림·푸시 없음
4. 실시간 연결: 문서 grant 는 `notifyRevalidate`, 폴더 grant 는 F-304 9.2 주기 점검 — 소유자 DELETE(`handleDeleteGrant`)와 같은 방식
5. 새 의존성·새 테이블·**마이그레이션 없음**. `grants` 표(`migrations/0005_grants.sql`, PK `(target_type, target_id, grantee_email)`, 색인 `grants_grantee`)만 쓴다

## 1. 파일 소유

| 파일 | 바뀌는 것 |
| --- | --- |
| `worker/grants.ts` | 새 핸들러 `handleLeaveDocShare`·`handleLeaveFolderShare` 추가. 기존 핸들러는 손대지 않는다 |
| `worker/index.ts` | 라우트 표에 `DELETE` 2줄 + import |
| `tests/worker/grantsLeave.test.ts` | 새 파일. 6장 L1~L10 |

- **F-3012 와 겹침**: F-3012 도 `worker/grants.ts`(`handlePutGrant`)를 고친다. 이 명세는 `handlePutGrant`·`checkOwnedTarget`·`handleDeleteGrant` 를 건드리지 않고 파일 끝 쪽에 새 함수만 더한다. 같은 파일이라 **동시에 구현하지 말고 차례로** 커밋한다(CLAUDE.md "파일이 겹치면 병렬 금지")
- `src/storage/docsApi.ts` 의 클라이언트 함수는 F-2115 소유. 3.4 오류 표를 그대로 옮기면 된다

## 2. 경로 결정 — 소유자 DELETE 를 넓히지 않고 새 경로

**`DELETE /api/shared/docs/:id`**, **`DELETE /api/shared/folders/:id`**. 요청 본문 없음.

기존 `DELETE /api/docs/:id/grants/:email` 을 "`:email` 이 내 이메일이면 받는 쪽 삭제" 로 넓히지 않는 이유:

- 그 라우트는 `checkOwnedTarget` 이 비소유자를 403 `forbidden` 으로 거른다(F-212 2.2 "권한은 있으나 동작이 막히면 403"). 받는 쪽 분기를 넣으면 같은 경로가 호출자에 따라 다른 행(`owner_id = 나` vs `grantee_email = 나`)을 지우게 되고, 403 계약 테스트(`tests/worker/grants*.test.ts`)의 의미가 흐려진다
- 받는 쪽은 자기 이메일을 URL 에 넣을 이유가 없다 — 서버가 세션의 `user.email` 로 정한다. 남의 이메일을 넣는 실수·위조가 구조적으로 불가능해진다
- `/api/shared` 는 이미 "나에게 공유된 것" 자원(`GET /api/shared`, `handleGetShared`)이라 그 아래 삭제가 자연스럽다. `matchPath`(`worker/index.ts`)는 마디 수가 달라 `GET /api/shared` 와 겹치지 않는다
- 복수형 `docs`·`folders` 는 `/api/docs`·`/api/folders` 와 맞춘다 — 클라이언트는 `grantsPath` 처럼 `` `/api/shared/${targetType}s/${id}` `` 로 만든다

`/v1`(CLI)에는 만들지 않는다 — 범위 밖.

## 3. 동작

### 3.1 지우는 행

`grants` 에서 `target_type = {doc|folder} AND target_id = :id AND grantee_email = 로그인 사용자 이메일(소문자)` **한 행**. `owner_id` 는 조건에 넣지 않는다.

- PK 가 `(target_type, target_id, grantee_email)` 이라 이 조건이 정확히 0 또는 1 행이다
- `owner_id` 를 빼는 이유: 받는 쪽은 소유자 id 를 모르고, 같은 id 가 다른 소유자에게 재사용돼 `owner_id` 가 어긋난 옛 행(리뷰 W2, `grantRole` 이 이미 무시하는 행)이라도 **내 이메일 행이면 내가 지워도 된다**. 선례: 계정 삭제가 `DELETE FROM grants WHERE grantee_email = ?1` 로 소유자 무관하게 지운다(`worker/account.ts`)
- 이메일은 `user.email.toLowerCase()` 로 묶는다 — `handlePutGrant` 가 소문자로 저장하고 `account.ts` 도 소문자로 지운다
- `docs`·`folders` 표는 읽지 않는다. 문서가 이미 지워졌어도 내 행이 남아 있으면 지운다

### 3.2 순서와 사용량

1. `requireUser`. 쓰기 관문은 라우트 표가 `isWriteRoute` 로 이미 건다(`/api/` + `DELETE`) — 401 → 403 `account_blocked` → 429 `day` → 429 `minute` 이 핸들러 전에 나간다. 예외 목록에 넣지 않는다(Q1)
2. 내 행이 있는지 `SELECT` 한 번. 없으면 **404 `not_found`, D1 쓰기·사용량 줄 없음** — F-2025 6장 규칙 "D1 에 쓰지 않고 끝나는 요청(404 …)은 사용량 줄도 없다"를 지키기 위해 batch 앞에서 끊는다
3. 있으면 `DELETE` + F-3012 의 `shareNotificationDeleteStatements(env.DB, { targetType, targetId, email })` + `dayUsageStatement(env.DB, user.id, now)` 를 **batch 하나**로(F-2025 6장 "쓰기 문장 전부와 사용량 줄을 batch 하나로"). 사용량은 받는 쪽 id 로 센다 — 행동한 사람이 받는 쪽이다
4. 204 응답을 만든 뒤, `doc` 이면 `notifyRevalidate(env, ctx, id, 소문자 이메일)`. `folder` 면 알리지 않는다(F-304 9.1 "폴더 초대 삭제" 행 그대로)

두 요청이 동시에 와서 둘 다 2단계를 통과하면 둘째 batch 의 `DELETE` 는 0행이고 사용량은 1 더 센다. 두 번 누르기 정도의 경합이라 받아들인다.

### 3.3 실시간 연결

- `notifyRevalidate` → `DocRoomCore.revalidateConnections(email)` 이 그 이메일의 연결 **전부**(다른 기기 포함)를 `resolveDocAccess` 로 다시 판정한다. 권한이 없어졌으면 `4403` `revoked` 로 닫힌다(F-304 9.3)
- 같은 문서를 폴더 경유로도 받았으면 판정이 폴더 권한으로 통과해 **연결이 남는다**. 폴더 role 이 `view` 인데 연결이 `edit` 였으면 `stillAllowed` 가 닫는다 — 기존 규칙 그대로, 이 명세가 바꾸지 않는다
- 폴더 나가기 뒤 그 아래 문서의 열린 연결은 다음 주기 점검에서 닫힌다(편집이 이어지면 최대 약 90초, F-304 9.2). 클라이언트는 나간 직후 열린 문서를 스스로 닫는 것으로 이 틈을 메운다 — F-2115 몫

### 3.4 응답 계약 (F-2115 가 그대로 소비)

| 상황 | 상태 | 본문 |
| --- | --- | --- |
| 내 행을 지움 | 204 | 없음 |
| 내 행 없음 — 초대받은 적 없음, 이미 나감, 소유자가 이미 삭제, **소유자 본인이 자기 문서에 호출**(자기 초대는 PUT 이 400 `invalid_self` 라 행이 없다), **금고 문서·폴더**(초대가 409 `e2ee_doc`/`e2ee_folder` 라 행이 없고, 폴더를 금고로 바꿀 때 `folders.ts` 가 그 폴더 grant 를 지운다), **폴더 경유로만 받은 문서를 문서 경로로 호출**, 없는 id | 404 | `{"error":"not_found"}` |
| 로그인 안 함 | 401 | `{"error":"unauthenticated"}` |
| 막힌 계정 | 403 | `{"error":"account_blocked"}` |
| 하루·분 한도 | 429 | `rate_limited` 본문 + `Retry-After` (F-2026 4장) |
| Origin 불일치 | 403 | `{"error":"forbidden_origin"}` |

- **404 를 고른 이유(204 멱등 대신)**: 서버가 "실제로 지웠는지"를 돌려줘야 폴더 경유 문서를 문서 경로로 부른 클라이언트 실수가 조용히 성공으로 보이지 않는다(목록에 그대로 남는데 204 면 원인을 찾기 어렵다). 다시 보내기·두 번 누르기는 클라이언트가 404 를 "이미 나감"으로 보고 목록을 새로 받으면 결과가 같다 — F-2115 에 넘기는 조건
- 404 본문은 사유를 나누지 않는다. 남의 문서 존재 여부를 드러내지 않는 F-212 2.2 "권한이 전혀 없으면 404" 와 같은 태도

### 3.5 그대로 두는 것 (정상 동작으로 명시)

- **직접 + 폴더 경유 둘 다** 받은 문서: 폴더에서 나가도 직접 grant 가 남아 `/api/shared` 에 `viaFolder` 없이 남는다. 문서에서 나가면 직접 행만 지워지고 폴더 경유로 남는다(`viaFolder` 가 붙고 role 은 폴더 role)
- 폴더 F 와 그 하위 폴더 G 를 **따로** 받았으면, F 에서 나가도 G 하위는 G grant 로 남는다(F-2058 하위 CTE 가 G 를 기점으로 다시 잡는다)
- 소유자의 초대 목록(`GET /api/{docs|folders}/:id/grants`)에서 그 이메일 행이 사라진다. 소유자에게 따로 알리지 않는다
- 나간 대상의 share 알림 행은 3.2 batch 에서 함께 지운다(읽은 행 포함, 받는 사람 `notif_rev` +1) — 소유자가 초대를 지울 때와 같다(F-3012 3.3)

### 3.6 목록 반영

나간 직후 `GET /api/shared` 는 그 항목을 돌려주지 않는다 — 캐시가 낄 자리가 없음을 확인했다.
- `handleGetShared` 는 매번 D1 을 읽고 ETag·조건부 응답이 없다. `jsonResponse` 는 `Cache-Control: no-store`(`worker/http.ts` `JSON_HEADERS`)
- 서비스 워커 `runtimeCaching` 은 `/assets/*.woff2` 하나뿐이다(`vite.config.ts`)
- 클라이언트 캐시에 공유받은 문서를 두지 않는다(F-212 2.4) — 목록을 언제 다시 받을지는 F-2115

## 9. 열린 질문

### Q1. 막힌 계정도 나갈 수 있게 쓰기 관문에서 뺄 것인가 — **기본값: 빼지 않는다(관문 적용)**

- 이유: 소유자 `DELETE` 와 같은 대우. 관문 예외(`isWriteRoute`)는 계정 삭제(F-2038 3.4)·푸시 끄기(F-3003 Q2)처럼 "막혔을 때 반드시 필요한 일"에만 있다. 나가기는 막힌 동안 미뤄도 손해가 없다
- 다른 쪽을 고르면: `worker/writeGate.ts` 의 `isWriteRoute` 에 `DELETE /api/shared/` 두 경로 예외를 더하고, 3.2 의 `dayUsageStatement` 를 빼야 한다(F-2038 3.4 처럼 관문 밖 쓰기는 세지 않는 쪽이 일관). 소유 표에 `worker/writeGate.ts`·`tests/worker/writeGate.test.ts` 가 붙고 L10 이 "204" 로 뒤집힌다

### Q2. 나갈 때 그 대상의 share 알림 행(F-3012)도 지울 것인가 — **결정: 지운다**

- 이유: F-3012 가 소유자의 초대 삭제에서 이미 지우도록 정했고(3.3), 나간 대상을 가리키는 알림 행은 눌러도 열리지 않는다. 같은 함수 `shareNotificationDeleteStatements` 를 부른다
- 결과: F-3012 완료가 선행 조건이라 `depends` 에 들어 있다. 구현은 F-3012 → F-3011 차례, 둘 다 `worker/grants.ts` 를 건드리므로 병렬 금지
