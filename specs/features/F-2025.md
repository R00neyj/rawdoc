## 2. 범위

### 한다

- 웹 표시 — F-2030. `/api/me`·`/v1/me` 응답은 **바뀌지 않는다**(`handleMe`·`handleApiMe` 가 `{ id, email }` 를 직접 만든다 — 확인)

## 3. `migrations/0010_usage.sql`

번호: `migrations/` 의 마지막이 `0009_auth.sql`(F-2033 `e73e722`) — **`0010` 확정**. 열·표 이름은 F-2024 2.3 계약 그대로

```sql
-- F-2025 사용량 열·가입 관문 표·누계 채우기 (specs/features/F-2024.md 2.3, F-2025.md 3장)
ALTER TABLE users ADD COLUMN write_day TEXT;                              -- 'YYYY-MM-DD' (UTC). NULL 이면 아직 쓰기 없음
ALTER TABLE users ADD COLUMN write_count INTEGER NOT NULL DEFAULT 0;      -- write_day 의 쓰기 수
ALTER TABLE users ADD COLUMN content_bytes INTEGER NOT NULL DEFAULT 0;    -- 소유 문서 본문 UTF-8 바이트 합
ALTER TABLE users ADD COLUMN doc_count INTEGER NOT NULL DEFAULT 0;        -- 소유 문서 수
ALTER TABLE users ADD COLUMN blocked_at INTEGER;                          -- NULL 이면 안 막힘 (F-2028)
ALTER TABLE users ADD COLUMN warned_at INTEGER;                           -- NULL 이면 주의 없음 (F-2028)

CREATE TABLE signup_gate (                                                -- 행 하나 (F-2028)
  id INTEGER PRIMARY KEY CHECK (id = 1),
  day TEXT NOT NULL,                                                      -- 'YYYY-MM-DD' (UTC)
  count INTEGER NOT NULL
);
INSERT INTO signup_gate (id, day, count) VALUES (1, '', 0);

-- 지금 있는 문서로 누계를 한 번 채운다 — 문서를 한 번씩 읽는다
UPDATE users SET (content_bytes, doc_count) = (
  SELECT COALESCE(SUM(length(CAST(docs.content AS BLOB))), 0), COUNT(*) FROM docs WHERE docs.owner_id = users.id
);
```

- 누계 채우기는 **행 값(row value) 한 문장**이다. 열마다 부분 질의를 따로 두는 모양보다 읽기가 절반이다 — 사용자 3·문서 2,010 에서 읽기 **2,014 행 vs 4,025 행**, 쓰기는 둘 다 3(측정 g). 두 판(로컬 D1·`node:sqlite`) 모두 행 값 `UPDATE` 를 받는다(측정 a·b)
- `content_bytes`·`doc_count` 에 `CHECK (… >= 0)` 을 두지 **않는다.** 누계가 어긋나 음수가 되는 순간 CHECK 가 사용량 줄을 실패시키고, 같은 batch 의 문서 쓰기까지 되돌려 저장이 막힌다. 음수는 저장을 막지 않고 `admin-recount` 가 바로잡는다(측정 g: CHECK 없이 음수가 들어간다)
- `users.updated_at` 은 건드리지 않는다(F-2024 2.3 끝)
- 기존 코드와의 호환: 새 열은 모두 NULL 허용이거나 `DEFAULT` 가 있어, `0010` 이 먼저 적용되고 Worker 가 옛 판인 동안에도 옛 `INSERT INTO users (id, email, created_at …)` 가 그대로 돈다(측정 a 의 씨앗이 그 모양)

### 3.1 원격 적용 순서 (사람, 배포 직전 — F-2033 11장 6번과 같은 자리)

| # | 언제 | 명령 | 확인 |
| --- | --- | --- | --- |
| 1 | 배포 직전 | `npx wrangler d1 migrations apply md-editor-db --remote` — `0009`(F-2033)·`0010` 이 번호 순서로 한 번에 | `npx wrangler d1 migrations list md-editor-db --remote` 에 남은 것 없음 |
| 2 | 1 바로 뒤 | `npx wrangler d1 execute md-editor-db --remote --command "SELECT (SELECT SUM(content_bytes) FROM users) AS a, (SELECT COALESCE(SUM(length(CAST(content AS BLOB))), 0) FROM docs) AS b, (SELECT SUM(doc_count) FROM users) AS c, (SELECT COUNT(*) FROM docs) AS d, (SELECT count FROM signup_gate) AS g"` | `a = b`, `c = d`, `g = 0` |
| 3 | 2 뒤 | `deploy` 브랜치 push (CLAUDE.md "Deployment") | Workers Builds 성공, 라이브 |
| 4 | 3 이 라이브로 확인된 뒤 | `node scripts/admin-recount.mjs --all --yes` (F-2029) | 출력의 바뀐 사용자 수 |

- **왜 1 이 3 보다 먼저인가.** 새 Worker 는 better-auth 세션 조회가 `write_day` 등을 읽는다(4.2) — 열이 없으면 세션 판정이 실패해 모두 로그아웃처럼 보인다. 반대로 옛 Worker 는 새 열이 있어도 돈다(3장 끝)
- **왜 4 가 있나.** 1 과 3 사이에 옛 Worker 가 쓴 문서 만들기·저장·삭제는 누계를 고치지 않는다. 그 몫을 한 번 다시 센다. 배포가 몇 분 안이면 어긋남은 그 몇 분의 쓰기뿐이다
- 비용: 1 의 누계 채우기는 쓰기 = 사용자 수, 읽기 ≈ 문서 수 + 사용자 수(측정 g). **원격 문서·사용자 수는 조회하지 않았다**
- **`wrangler d1 migrations apply` 가 파일 하나를 트랜잭션으로 묶는지는 확인하지 않았다.** 중간에 실패하면 `ALTER` 일부만 남아 다시 적용이 "duplicate column" 으로 막힐 수 있다 — 그때는 사람이 `PRAGMA table_info(users)` 로 남은 열을 보고 멈춘다(자동 복구 절차는 두지 않는다)

### 4.4 판정 규칙 (순수 함수)

- **날짜**: `utcDay` 는 ms 를 UTC 날짜 문자열로. 한국 시간 오전 8:59 는 UTC 전날이다. D1 무료 한도와 같은 경계(F-2024 2.3)
- **자정까지 초**: 다음 UTC 자정 − 지금을 초로 올림. 자정 정각이면 86,400, 자정 1ms 전이면 1. F-2026 의 `Retry-After`·`retryAfter` 에 그대로 쓴다(F-2024 3.4)
- **바이트**: `utf8Bytes` 는 `TextEncoder` 길이. SQLite `length(CAST(… AS BLOB))` 와 같다(측정 f — 짝 없는 서로게이트 포함)
- **만들기 413** (`checkDocCreate`): `docCount >= DOC_COUNT_QUOTA` 면 `resource: 'docs'`, `used` = `docCount`, `limit` = `DOC_COUNT_QUOTA`. 아니고 `contentBytes + 새 바이트 > DOC_BYTES_QUOTA` 면 `resource: 'bytes'`, `used` = `contentBytes`, `limit` = `DOC_BYTES_QUOTA`. 둘 다 넘으면 `docs` (F-2024 3.3 표 순서). 합이 한도와 **같으면 통과**
- **늘리는 PUT 413** (`checkDocGrow`): 증감이 0 이하면 늘 `null`(이미 넘은 상태여도 — F-2024 결정 6). 양수이고 `contentBytes + 증감 > DOC_BYTES_QUOTA` 면 `resource: 'bytes'`. 같으면 통과

## 5. 사용량 줄 — SQL 과 행 비용

### 5.1 문장 (계약 — 테스트가 글자까지 본다)

`usage.ts` 가 아래 다섯 문장을 **이 글자 그대로** 쓴다(상수 이름은 구현 재량, 문장 텍스트는 계약). 날짜 `?1` 은 JS 가 `utcDay(now)` 로 넘긴다 — SQLite `date('now')` 를 쓰지 않는 이유는 가짜 시계로 테스트하려고

| 쓰는 곳 | 문장 |
| --- | --- |
| 하루만 (`dayUsageStatement`) | `UPDATE users SET write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1 WHERE id = ?2` |
| 하루 + 누계 (`docUsageStatements`, 보낸 사람 = 소유자) | `UPDATE users SET write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1, content_bytes = content_bytes + CASE WHEN changes() = 1 THEN ?2 ELSE 0 END, doc_count = doc_count + CASE WHEN changes() = 1 THEN ?3 ELSE 0 END WHERE id = ?4` |
| 누계만 (`docUsageStatements`, 보낸 사람 ≠ 소유자의 첫 줄) | `UPDATE users SET content_bytes = content_bytes + CASE WHEN changes() = 1 THEN ?1 ELSE 0 END, doc_count = doc_count + CASE WHEN changes() = 1 THEN ?2 ELSE 0 END WHERE id = ?3` |
| 문서 하나 삭제 (`deleteDocUsageStatement`) | `UPDATE users SET write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1, (content_bytes, doc_count) = (SELECT users.content_bytes - COALESCE(SUM(length(CAST(content AS BLOB))), 0), users.doc_count - COUNT(*) FROM docs WHERE id = ?2 AND owner_id = ?3) WHERE id = ?3` |
| 폴더째 삭제 (`deleteFoldersUsageStatement`) | `UPDATE users SET write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1, (content_bytes, doc_count) = (SELECT users.content_bytes - COALESCE(SUM(length(CAST(content AS BLOB))), 0), users.doc_count - COUNT(*) FROM docs WHERE owner_id = ?2 AND folder_id IN (SELECT value FROM json_each(?3))) WHERE id = ?2` — `?3` 은 폴더 id 배열의 `JSON.stringify` |
| 사용량 읽기 (`readUsage`) | `SELECT write_day, write_count, content_bytes, doc_count, blocked_at, warned_at FROM users WHERE id = ?` |

- `changes()` 는 **바로 앞 문장**이 바꾼 행 수다. 그래서 `changes()` 를 쓰는 줄은 batch 에서 **문서 쓰기 바로 뒤**에 둔다. 보낸 사람 ≠ 소유자면 순서가 `[문서 쓰기, 누계만(소유자), 하루만(보낸 사람)]` — 하루만 줄은 `changes()` 를 보지 않으므로 마지막이어도 된다(측정 g "편집 권한자 PUT")
- 삭제는 `changes()` 가 아니라 **지우기 전에 D1 행을 직접 센다**(F-2024 3.2 3번을 문서 하나에도 적용). JS 가 앞서 읽은 본문으로 빼면, 읽은 뒤 지우기 전에 끼어든 PUT 만큼 누계가 영영 어긋난다. 그래서 빼는 줄이 batch **첫 문장**이고 `DELETE` 가 뒤다
- 폴더째 삭제는 D1 문장당 바인딩 한도(지금 `BATCH_ID_LIMIT` 100 으로 쪼개는 이유) 때문에 폴더 id 를 `json_each` 한 인자로 받는다 — 문장 하나로 모든 조각을 센다. 로컬 D1 에서 폴더 id 250개 한 인자로 돈다(측정 g). 삭제 문장은 지금처럼 100개씩 쪼갠 채 그 뒤에 온다

### 5.2 행 비용 — 로컬 D1 실측 (측정 g)

사용자 A 가 문서 2,000개를 가진 DB. `written`·`read` 는 batch 안 문장별 `meta.rows_written`·`meta.rows_read`

| 동작 | batch | 쓰기 행 | 읽기 행 | 결과 |

| 고정 | `UPDATE pinned_at` + 하루만 | 1 + 1 | 1 + 1 | |
| 잠금 처음 잡기 | 조건부 upsert + 하루만 | 2 + 1 | 0 + 1 | `results[0].meta.changes` 1 |
| 남이 잡은 잠금 | 같음 | 0 + 1 | 1 + 1 | `results[0].meta.changes` 0, `write_count` +1 |

- **원격 D1 의 행 계산이 같다는 것은 확인하지 않았다**(F-2024 2.4 끝과 같은 한계)

## 6. 핸들러 — 어디에 붙이나

**규칙.** 로그인한 사용자의 쓰기 요청(F-2024 1.2 표의 "예" 행)이 D1 에 쓰면, 그 요청의 D1 쓰기 문장 전부와 사용량 줄을 **batch 하나**로 보낸다. 요청 하나에 사용량 줄은 하나(보낸 사람 ≠ 소유자인 문서 쓰기만 둘 — 누계 줄 + 하루 줄). D1 에 쓰지 않고 끝나는 요청(400·403·404·409 사전 검사·413·같은 링크 다시 받기·세션 없는 잠금 놓기·같은 id 다시 만들기)은 사용량 줄도 없다(F-2024 1.2 "하루는 D1 쓰기를 센다")

### 6.1 `updateDocRow` (`worker/docWrite.ts`)

```ts
export async function updateDocRow(
  env: Env,
  existing: DocRow,
  patch: { title?: string; content?: string },
  actorId?: string,                 // 없으면 existing.owner_id — DO idle 경로가 이 모양으로 부른다
): Promise<{ ok: true; row: DocRow } | { ok: false }>
```

- 반환 모양·문서 `UPDATE` 문장(F-308 6.1)·바인딩 값은 **그대로**. `run` 한 번이던 것을 `env.DB.batch([문서 UPDATE, ...docUsageStatements(…)])` 로 바꾸고, 판정은 batch 결과 **첫 문장**의 `meta.changes === 1`
- 증감: `patch.content` 가 있으면 `utf8Bytes(patch.content) − utf8Bytes(existing.content)`, 없으면 0. `deltaDocs` 0. `ownerId` = `existing.owner_id`, `actorId` = 인자 또는 `existing.owner_id`
- 부르는 곳 셋(F-308 12장): `handleUpdateDoc` 은 `actorId` 로 `user.id` 를 넘긴다(`/api` PUT, `/v1` PUT 폴백 둘 다 이 함수). **DO idle 경로(`DocRoomCore.writeText`)는 그대로 둔다** — `actorId` 없이 불러 소유자에게 센다(11장 Q2). `docRoomCore.ts` 를 고치지 않는다
- 총량 검사는 이 함수 **밖**(호출하는 핸들러)에서 한다. DO idle 경로는 총량을 보지 않는다 — Worker `handleUpdateDocV1` 이 이미 봤다(F-308 12장)

### 6.2 `/api` 문서 (`worker/docs.ts`)

| 핸들러 | 순서 · batch |
| --- | --- |
| `handleCreateDoc` | 지금의 몸통 검사(400·413 `too_large`) → `existing` 분기(200·409, **카운터 없음·총량 검사 없음** — F-2024 3.3 끝) → `checkDocCreate(await usageOf(env, user), utf8Bytes(content))` 가 있으면 413 그 몸통 → batch `[INSERT docs, ...docUsageStatements({ actorId: user.id, ownerId: user.id, deltaBytes: 새 바이트, deltaDocs: 1 })]` |
| `handleUpdateDoc` | 지금 순서(400·413 `too_large` → 404·403 → 423 → 409) **뒤**, `updateDocRow` **앞**에: `content` 가 있고 증감(맞춘 뒤 아님 — `/api` 는 받은 그대로 저장한다) > 0 이면 소유자 사용량으로 `checkDocGrow`. 소유자 사용량 = `existing.owner_id === user.id` 면 `usageOf(env, user)`, 아니면 `readUsage(env, existing.owner_id)`(D1 읽기 1). 걸리면 413. 증감 ≤ 0 이면 사용량을 읽지 않는다 → `updateDocRow(env, existing, patch, user.id)` |
| `handleDeleteDoc` | 404·403 뒤 batch `[deleteDocUsageStatement(user.id, id), DELETE FROM docs …]` → `notifyPurge` 는 지금처럼 그 뒤 |
| `handleMoveDocFolder` · `handleSetPinned` | batch `[지금의 UPDATE, dayUsageStatement(user.id)]` |

- `/api` PUT 의 413 이 409·423 **뒤**인 이유: 버전이 틀린 요청은 어차피 쓰지 않으므로 413 보다 409 가 쓸모 있는 답이다(클라이언트가 최신 행을 받는다). `/v1` 은 F-308 12장이 정한 대로 409 **앞**이다(6.3) — `/v1` 의 빠른 409 는 DO 를 깨우지 않으려는 비용 줄이기라 순서가 달라도 결과 의미는 같다

### 6.3 `/v1` PUT (`worker/v1.ts` `handleUpdateDocV1`)

- 자리: F-308 4장 **5번(줄바꿈 맞춤·1MB) 뒤, 6번(빠른 409) 앞** (F-308 12장, F-2024 3.3 표)
- 증감 = `utf8Bytes(맞춘 content)` − `utf8Bytes(3번에서 읽은 행.content)`. `content` 가 없으면 검사 없음
- 소유자 사용량은 6.2 와 같은 규칙(`row.owner_id === user.id` 면 `usageOf`, 아니면 `readUsage`)
- 413 이면 `writeTextInRoom` 을 부르지 않는다(호출 0). 폴백(`writeTextInRoom` 이 `null`)은 `handleUpdateDoc` 을 부르므로 거기서 같은 검사를 한 번 더 한다 — 같은 행에서 같은 값이라 결과가 같다
- `handleCreateDocV1` 은 `handleCreateDoc` 을 부르므로 따로 할 일이 없다

### 7.1 F-2024 3.2 규칙과 이 명세의 문장

| F-2024 3.2 | 이 명세 |
| --- | --- |

| 2. 증감은 대체된 행에서 | `updateDocRow` 의 `existing.content` 바이트 |
| 3. 여러 문서를 지우는 쓰기는 지우기 **앞에** 같은 batch 에서 뺀다 | 폴더째 삭제 + **문서 하나 삭제도** (5.1 — 지우기 직전 D1 값을 센다) |

- 3.1 의 마이그레이션 ~ 배포 사이 옛 Worker 의 쓰기 — 3.1 4번이 한 번 다시 센다
- DO 스냅숏(F-2027 이 붙이기 전까지, 그리고 F-2024 3.2 끝의 "메모리 `base` 에서 거꾸로 계산" 문제)

### 7.3 다시 세는 SQL (F-2029 `admin-recount` 가 쓴다)

### 8.3 판정 나눔 — 왜 어댑터인가

- `changes()`·행 값 `UPDATE`·`json_each`·빼기 순서는 **SQL 의미**다. 지금 워커 테스트의 가짜 D1 은 SQL 앞부분 문자열로 분기해 흉내 내므로 이것을 판정하지 못한다 — 가짜가 맞게 흉내 내도록 짜면 테스트가 구현을 베낀다. F-2024 A8 을 "F-2025 단위 테스트로 판정" 한다고 적은 것을 지키려면 실제 SQLite 가 필요하다
- `worker/auth.test.ts`·`authServer.test.ts`·`loginRoutes.test.ts` 가 이미 `node:sqlite` 에 `migrations/` 를 적용해 쓴다(F-2033 측정 t). 다만 그것은 better-auth 에 **`DatabaseSync` 를 그대로** 넘기는 것이라 `env.DB.prepare().bind().first()` 를 부르는 우리 핸들러는 돌지 않는다. 그래서 D1 모양 어댑터 하나를 둔다

```ts
// worker/testD1.ts — 테스트 전용. 운영 코드는 import 하지 않는다
export function openTestDb(until?: string): DatabaseSync   // migrations/*.sql 을 번호 순서로. until('0009' 등) 이하만
export function asD1(db: DatabaseSync): D1Database          // prepare → bind → first·all·run, prepare 에서 바로 first·all·run, batch
```

- 어댑터 규칙: `run` 은 `{ success: true, meta: { changes } }`, `first` 는 행 또는 `null`, `all` 은 `{ results }`. `batch` 는 `BEGIN` → 문장 차례로 → `COMMIT`, 하나라도 던지면 `ROLLBACK` 하고 다시 던진다(D1 batch 가 실패 시 되돌리는 것은 F-2024 머리말 측정 "batch 둘째 문장이 오류"). `?1` 번호 바인딩은 `node:sqlite` 가 그대로 받는다(측정 h)
- 어댑터가 판정하지 못하는 것: 원격 D1 의 행 계산, 동시 요청. 그것은 5.2 측정과 사람 확인(10장)

### Q1. 편집 권한자가 남의 문서에 쓸 때 하루 카운터는 누구 것인가 — **기본값: 보낸 사람. 누계는 소유자** (확인 권장)

## 13. 기존 명세·코드와 부딪치는 것

- **F-2024 3.2 4번과 하루 카운터의 주인** — 개요는 누계만 적었다. 이 명세가 "보낸 사람" 으로 좁혔다(Q1). 개요의 다른 문장(관문이 보낸 사람을 봄)과는 맞는다
- **F-2024 3.2 3번의 범위** — 개요는 "여러 문서를 지우는 쓰기" 에만 "앞에 빼기" 를 적었다. 이 명세는 문서 하나 삭제에도 같게 했다(Q3)
- **F-308 A9 "run 한 번"** — 테스트가 `run` 을 적어 판정한다. batch 로 바뀌어 단언을 고친다(9장). 문서 `UPDATE` 문장 텍스트는 그대로
- **`links.ts` 의 문장별 `run`** — 지금 묶음 교체(`DELETE` 뒤 `INSERT` 여러 번)가 원자적이지 않다. 한 batch 로 바꾸며 원자적이 된다 — 동작이 달라지는 곳은 중간 실패 뿐(지금은 반쯤 바뀐 묶음이 남고, 뒤에는 그대로 남는다)
- **`specs/architecture.md` 6장 `migrations/` 줄**이 `0006` 에서 멈춰 있다(`0007`~`0009` 누락) — 이 명세 전부터의 어긋남. 12장에 함께 적었다
- **D1 batch 의 문장 수 한도** — 폴더째 삭제·묶음 링크가 문장을 많이 담는다. D1 "Worker 호출당 질의 수"(무료 50) 에 batch 안 문장이 몇 개로 세이는지는 **확인하지 않았다.** 지금도 `replaceShareLinkDocs` 는 문서마다 `run` 을 따로 하므로 batch 로 합쳐 늘어나지는 않는다
