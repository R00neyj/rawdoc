| --- | --- |

| 비용 | **무료 플랜으로 시작.** Hibernation API 필수. 한도 초과는 자동 과금이 아니라 에러로 실패한다 (9.3). 유료 전환($5/월)은 넘칠 때 |

## 1. 범위와 하지 않는 것

### 1.1 하는 것

- 문서 하나당 Durable Object 하나. `y-partyserver` 의 `YServer` 를 상속한 클래스가 Yjs 원본을 들고 WebSocket 으로 중계한다
- 클라이언트는 `y-codemirror.next` 의 `ySync` 로 `Y.Text` 를 CM6 에 잇는다. 되돌리기는 `yUndoManager`
- **편집 권한(`grants.role` 이 `edit`, 그리고 소유자)을 가진 사람 전원이 동시에 편집**한다. 같은 사람의 여러 탭·기기도 같은 경로를 쓴다
- 접속자 아바타와 원격 커서 (6장)
- 오프라인 편집은 브라우저 `Y.Doc` 영속에 쌓였다가 재연결 때 병합된다 (3.6)
- 편집 잠금(F-213)은 **WebSocket 에 한 번도 연결하지 못한 경우의 폴백**으로만 남는다 (8.2)

### 1.2 이번 범위에서 빼는 것

- **M4 댓글.** 앵커가 Yjs `RelativePosition` 기반이라 M3 이 선행 조건이지만(`product.md` 7장 M4), 댓글 자체는 M3 뒤
- **보기 권한자(`role: 'view'`)의 실시간 반영.** `/ws` 는 edit 이상만 연결한다. 보기 권한자·공유 링크(F-210/211)·공개 보기는 지금처럼 D1 스냅샷을 읽고, 새로고침해야 최신이 된다. 접속자 목록에도 보기 권한자는 나오지 않는다
- **변경 이력·버전 되돌리기.** `product.md` 8장 범위 밖 그대로. Yjs 업데이트 로그는 압축 대상이지 사용자에게 보여 주는 히스토리가 아니다 (3.4)
- **원격 MCP 서버.** 자동화 연결은 CLI(F-2021, npm `rawdoc`)로 대신했다(`product.md` 9장 Q44). `/v1` 을 DO 경유로 바꾸는 것까지만 하고(7장), 원격 MCP 는 터미널이 없는 클라이언트 수요가 생기면 그 뒤
- **GitHub 양방향 동기화**(`product.md` 7장 "M3 이후에 다시 본다")
- 다른 사람이 보고 있는 화면 따라가기(follow), 문서 단위 채팅, 편집 이력 하이라이트

## 2. 불변조건 재정의

### 2.1 `CLAUDE.md` 에 넣을 새 문장 초안

**이 개요는 `CLAUDE.md` 를 고치지 않는다.** 아래는 제안 문구이고, 실제 수정은 이 개요가 승인된 뒤 메인이 한다

지금 문장:

> - **문서 상태의 원본은 CM6 `EditorState` 하나다.** 별도 문자열 사본을 두고 동기화하지 않는다

바꿀 문장:

> - **열린 문서의 원본은 `Y.Doc` 의 `Y.Text` 하나다.** `EditorState` 는 그 투영이고, 둘은 `y-codemirror.next` 가 잇는다. 그 밖에 본문 문자열 사본을 두고 손으로 동기화하지 않는다. D1 `docs.content`·IndexedDB 캐시 본문은 `Y.Text` 에서 나오는 **단방향 파생**이고, 그 값을 열린 `Y.Doc` 에 되돌려 쓰지 않는다

지금 문장(유지, 뒤에 한 줄 덧붙임):

> - **IME 조합 중 재계산을 보류하면, 조합 종료 시 밀린 재계산을 반드시 따라잡는다.** 근거: `.workflow/tasks/T-004/verify.md` 6.5·7장

덧붙일 문장:

> - **원격 업데이트는 IME 조합 중에 적용하지 않는다.** 조합 중(표 칸 하위 에디터 조합 포함) 도착한 원격 Yjs 업데이트는 큐에 쌓고, `compositionend` 의 `forceRecalc` 와 같은 지점에서 한꺼번에 적용한다. Yjs 는 순서와 무관하게 병합되므로 지연 적용이 정합성을 깨지 않는다

바꾸지 않는 문장: "decoration 은 문서 내용을 바꾸지 않는다", "`src/` 는 `spike/` 를 import 하지 않는다", "저장소 식별자는 제품명과 무관하게 고정한다"(새 IndexedDB DB 이름은 `md-yjs` — 기존 `md-docs`·`md-remote` 와 같은 규칙), "제품명·색은 `brand.config.ts` 에서만"

### 2.2 그로 인해 바뀌는 코드 전제

| # | 지금 전제 | M3 에서 |
| --- | --- | --- |
| 1 | 저장소 → 에디터는 문서를 여는 시점 1회, 에디터 → 저장소는 단방향 스냅샷 (`specs/architecture.md` 3장) | 저장소 → `Y.Doc` 은 **DO 안에서 최초 1회 씨앗 심기**뿐(3.3). 브라우저는 절대 `Y.Doc` 에 본문을 밀어 넣지 않는다. 에디터 ↔ `Y.Text` 는 양방향 |
| 2 | 서버 값이 바뀌면 에디터를 다시 마운트해 반영한다 (F-207 2.4, F-213 2.3) | 본문은 다시 마운트하지 않는다 — `Y.Text` 가 스스로 바뀐다. 다시 마운트는 문서 전환·모드 전환 때만 |
| 3 | 조합 중 도착한 트랜잭션은 내가 친 글자다 (`preview/inline.ts`·`lines.ts`·`blocks.ts`·`wikiLinks.ts`·`frontmatter.ts`·`createEditor.ts` 목차 갱신) | 원격 트랜잭션이 섞인다. **보류 로직 자체는 그대로 두고**, 조합 중 원격 업데이트가 `EditorState` 에 닿지 않게 앞에서 막는다 (5장) |
| 4 | 되돌리기는 `@codemirror/commands` 의 `history()` | `yUndoManager` — 내 Ctrl+Z 가 남의 편집을 되돌리지 않게 (5.4) |
| 5 | 문서 본문 저장은 `useDocSaver` → `PUT /api/docs/:id` + `baseVersion` 낙관적 잠금 | 실시간 문서는 DO 가 D1 에 쓴다. 브라우저의 본문 PUT 은 폴백일 때만 (3.5·8.2) |
| 6 | 오프라인 본문 편집은 outbox `updateDoc{content}`, 충돌은 사본 (F-207 2.3·2.4) | 본문은 `Y.Doc` 영속. **실시간 경로에서** outbox `updateDoc{content}` 를 뺀다. `pending`·폴백 세션은 F-309 까지 outbox 를 그대로 쓴다(F-306 3.2 — 이 6번과 8.1 표가 부딪쳐 F-306 이 8.1 을 따르기로 확인했다). 실시간 문서의 본문 충돌 사본 없음 (3.6·3.7) |
| 7 | `docs.version` 은 낙관적 잠금용 비교값 | DO 가 유일한 필자라 비교 의미가 없어진다 — **단조 증가 카운터**로만 (3.5) |
| 8 | `readOnly` 는 권한(F-212)·잠금(F-213)이 정한다 | 여기에 "첫 동기화 전"·"연결된 적 없는 오프라인 문서" 가 더해진다 (3.6·8.2) |

**바뀌지 않는 것**: 라이브 프리뷰 decoration·블록 위젯·목차 코드는 원칙적으로 그대로다. decoration 은 `EditorState` 를 읽어 표시만 바꾸고(불변조건), 원격 편집은 `EditorState` 에 이미 들어온 뒤에 보이기 때문이다. 3번 항목만 예외다

## 3. 데이터·저장 구조

### 3.1 전체 그림

```
브라우저                        Durable Object (문서당 1개)        D1
┌──────────────┐               ┌────────────────────────┐      ┌──────────────┐
│ Y.Doc        │◄── WebSocket ─►│ Y.Doc (원본)           │      │ docs         │
│  ├ content   │   Yjs 업데이트 │  ├ content : Y.Text    │      │  content     │◄─ 디바운스
│  └ title     │   + awareness │  └ title   : Y.Text    │──────►│  title       │   파생 스냅샷
│      ▲       │               └───────┬────────────────┘      │  version     │   (3.5)
│      │ ySync │                       │ onLoad/onSave          │  line_ending │
│ EditorState  │                       ▼                        └──────┬───────┘
└──────────────┘               DO SQLite (업데이트 로그·스냅샷)         │
       │                                                               ▼
       ▼ (오프라인 영속)                                   공유 링크·`.md` 내보내기
IndexedDB `md-yjs`                                          `/v1` 읽기·문서 목록
```

- 화살표가 한 방향인 곳은 되돌아오지 않는다. D1 → `Y.Doc` 방향은 DO 의 최초 씨앗 심기(3.3) 한 번뿐이다

### 3.2 `Y.Doc` 안에 무엇을 두는가

| 이름 | 타입 | 내용 |
| --- | --- | --- |
| `content` | `Y.Text` | 본문. **LF 만 담는다** |
| `title` | `Y.Text` | 문서 제목 |

- `lineEnding`(`crlf`\|`lf`)은 `Y.Doc` 에 넣지 않고 D1 컬럼에 남긴다. CM6 는 `lineSeparator` 를 지정하지 않아 에디터 안이 항상 LF 이고(`src/lib/lineEnding.ts`), 저장·내보내기 때 `fromEditorText()` 로 잇는다 — **원문 바이트 보존이 지금과 똑같이 유지된다**
- **제목도 `Y.Doc` 에 넣는다.** 제목은 에디터 안 위젯(F-217 `docTitle.ts`)에서만 고치고 사이드바에는 이름 바꾸기 항목이 없다(2026-09-20 `src/app/Sidebar.tsx` 확인). 제목을 Yjs 밖에 두면 제목 수정 PUT 이 DO 가 올린 `version` 과 어긋나 409 → 충돌 사본을 만드는데, 본문 충돌 사본을 없애면서 제목 충돌 사본만 남기는 건 앞뒤가 안 맞는다. **이건 사용자 결정 표의 "본문" 범위를 메인이 넓힌 것이라 11장에 확인 항목으로 둔다**
- 폴더·고정·삭제·공유·초대는 `Y.Doc` 밖이다. 지금 API·outbox 를 그대로 쓴다

### 3.3 씨앗 심기 (기존 문서를 Yjs 로 옮기는 방법)

지금 있는 문서는 전부 D1 `docs.content` 에만 있다. 마이그레이션 스크립트를 따로 돌리지 않고 **문서를 처음 열 때 DO 안에서 한 번** 옮긴다

1. DO 의 `onLoad()` 가 DO SQLite 에서 저장된 Yjs 상태를 읽는다
2. 상태가 없으면 D1 에서 `content`·`title` 을 읽어 `Y.Text.insert(0, …)` 로 넣는다
3. 그 뒤로 D1 → `Y.Doc` 방향은 다시 일어나지 않는다. 예외: D1 이 DO 밖에서 쓰였으면 DO 가 흡수한다(F-304 7.2, 2026-09-24 승인)

- **브라우저는 어떤 경우에도 씨앗을 심지 않는다.** 두 탭이 동시에 열면 같은 본문이 두 번 들어간다. DO 는 문서당 하나이고 요청이 직렬화되므로 여기서만 하면 안전하다
- 씨앗 심기가 끝나기 전에는 클라이언트가 편집할 수 없다 — 첫 동기화(`synced`)까지 **에디터를 아예 띄우지 않는다**(읽기 전용으로 먼저 보이지 않는다, F-305 5.1). 상태바 `불러오는 중…`. 로컬에서 12ms(F-305 측정 d, 19.3 L2가 배포 환경 값을 잰다)

### 3.4 DO 안 영속과 업데이트 로그 압축

`y-partyserver` 는 **영속화 훅 `onLoad()`(`Y.applyUpdate`)·`onSave()`(`Y.encodeStateAsUpdate`)를 직접 짜야 한다. 안 짜면 모든 클라이언트가 나갔을 때 문서가 사라진다** (`y-partyserver` README, 확인일 2026-09-20). 기본 `callbackOptions` 은 debounceWait 2000ms, debounceMaxWait 10000ms, timeout 5000ms. F-304 는 5,000/30,000ms 로 바꾸고 방이 비면 곧바로 저장한다(F-304 6.2, 2026-09-24 승인)

DO SQLite 저장 규칙:

- **flush 마다 합친 업데이트를 1행으로 쓰고, 넘으면 1,500,000 B 로 조각낸다**(F-304 6.1, 2026-09-24 승인). DO SQLite 는 **string/BLOB 행 최대 2MB**(https://developers.cloudflare.com/durable-objects/platform/limits/ , 확인일 2026-09-20)라 하나의 큰 BLOB 로 두면 긴 문서에서 터진다
- 쌓인 로그가 **100행** 또는 **512KiB** 를 넘으면 그 flush 에서 **압축**한다: `Y.encodeStateAsUpdate(doc)` 결과를 2MB 미만 청크로 쪼개 쓰고 옛 로그 행을 지운다. 임계값은 F-304 6.3 실측으로 정해졌다(2026-09-24 승인)
- DO 1개당 SQLite 10GB, 계정 전체 무료 5GB. 문서당 스냅샷 수십~수백 KB 면 한참 남는다

### 3.5 D1 파생 스냅샷과 `version` 재정의

- **DO 가 `env.DB` 로 직접 쓴다.** 마지막 편집 후 5초 디바운스, 그리고 편집이 계속되면 최소 30초마다 1회. 값은 `Y.Text.toString()` 과 `title`
- `docs.version` 은 **DO 가 쓸 때마다 +1 하는 단조 증가 카운터**가 된다. DO 가 유일한 필자라 `baseVersion` 비교는 의미를 잃는다. `PUT /api/docs/:id` 의 409 판정 코드는 폴백 경로를 위해 그대로 두되, 실시간 문서에서는 그 경로를 타지 않는다
- DO 의 쓰기는 `WHERE version = 마지막으로 본 값` 조건부다. 0행이면(D1 이 DO 밖에서 바뀐 경우) D1 을 다시 읽어 흡수한 뒤 그 기준으로 한 번 더 쓴다(F-304 7.2·8.2, 2026-09-24 승인)
- **D1 읽기 경로는 하나도 바뀌지 않는다** — 공유 링크(F-210/211), `.md` 내보내기(F-112/F-158), 전체 내보내기(F-281), `/v1` 읽기(F-223), 문서 목록. 이 경로들은 WebSocket 을 열지 않는다. 대신 조용해지면 5초, 편집이 계속되면 최대 30초까지 낡은 값을 볼 수 있다(F-304 6.2, 2026-09-24 승인)
- **D1 쓰기 부하**: 문서·창 수와 무관하게 문서당 최대 12회/분(5초 디바운스, 30초 강제). 지금 F-213 잠금 연장이 창당 시간당 약 180행을 쓰고 있었으므로(F-213 2.5) 잠금을 폴백으로 좁히면 **순증이 아닐 수 있다**. D1 무료 하루 쓰기 10만 행은 DO SQLite 와 별개 한도다
- **문서 크기 상한(Q6, 지금 1,000,000 바이트 — F-206 2장)**: Yjs 는 이미 병합된 업데이트를 되돌릴 수 없으므로 "413 으로 거절" 이 성립하지 않는다. 결정 — DO 가 스냅샷을 쓰기 전에 UTF-8 바이트를 재고 상한을 넘으면 **D1 에 쓰지 않고** 연결된 클라이언트 전원에 경고 커스텀 메시지를 보낸다. 클라이언트는 error 알림 `문서가 1MB 를 넘어 서버에 저장되지 않습니다. 내용을 줄이거나 문서를 나눠 주세요`. 편집은 계속 되고 Yjs 원본은 DO 에 남는다. ### 3.6 브라우저 오프라인 영속 — `y-indexeddb` 를 쓰지 않는다

**결정: `y-indexeddb` 를 쓰지 않고 직접 짠다.** 근거:

1. `y-indexeddb` 는 9.0.12 가 마지막이고 **2023-11-02 이후 publish 가 없다**(npm registry 직접 확인, 2026-09-20). 아카이브 여부는 확인하지 못했다. `CLAUDE.md` "미도입 항목은 해당 명세가 생기기 전까지 의존성을 추가하지 않는다" 규칙상 새 의존성은 근거가 있어야 하는데, 3년 정지한 패키지를 **오프라인 편집이 날아가지 않아야 한다는 요구(F-207)의 유일한 보루**로 삼는 건 근거가 약하다
2. 이 패키지가 하는 일은 작다 — 업데이트 append, 주기적 압축, `whenSynced`. 우리는 이미 IndexedDB 계층(`src/storage/remoteCache.ts`, DB `md-remote`)을 직접 짜서 쓰고 있다
3. 직접 짜면 DO SQLite 쪽 압축 규칙(3.4)과 같은 모양을 쓸 수 있어 읽을 코드가 한 벌로 줄어든다

설계:

- IndexedDB DB 이름 **`md-yjs`**(제품명 쓰지 않음 — 불변조건). 스토어 `updates`(키 `[userId, docId, seq]`), `meta`(키 `[userId, docId]`)
- `Y.Doc` 의 `update` 이벤트마다 append. 로컬 원인·원격 원인 모두 담는다(재연결 없이 새로고침해도 원격분이 남게)
- 로그 행이 200개를 넘으면 `Y.encodeStateAsUpdate` 로 압축해 갈아치운다
- 문서를 열면 `md-yjs` 를 먼저 적용하고 그다음에 provider 를 붙인다. 이 순서라야 오프라인에서 새로고침해도 편집이 남는다
- **실측 항목(F-306)**: 1MB 문서에서 이어 칠 때 append 한 번의 소요 시간과 압축 한 번의 소요 시간. 압축이 입력을 눈에 띄게 끊으면 임계값을 올리거나 압축을 `requestIdleCallback` 으로 미룬다

**M3 갱신(F-306, 2026-09-24, 실측으로 확정)**:

- 키를 `[userId, docId, seq]` 에서 자동 증가 `key` + 색인 `byDoc = ['userId', 'docId']` 로 바꿨다 — 같은 브라우저 두 탭이 같은 문서를 열면 각자 seq 를 세어 키가 겹치고 서로의 행을 덮는다(F-306 4.1)
- `meta` 행에 `unsyncedLocal`(연결이 live 가 아닐 때 내 편집이 들어왔고 아직 `synced` 를 못 봤다)·`lastOpenedAt` 필드가 붙었다(F-306 4.1)
- 압축 임계값 "200개" → **500행, 마지막 업데이트 뒤 입력이 2,000ms 멈췄을 때만**, **이 세션이 아는 키만 지운다**(다른 탭이 쓴 행은 남긴다). 근거는 실측 (b) — 불러오기 비용은 문서 크기가 지배하고 행 수는 읽기에만 선형으로 붙는다(200 → 500행 +2ms, 이 PC). 느린 PC(CPU 4배 감속)에서 압축은 1MB 문서에 메인 스레드를 42.7~45.9ms 막아 입력 중이면 끊긴다 — `requestIdleCallback` 대신 "2초 조용함" 을 쓴다(입력 중에도 idle 틈이 생겨 콜백이 입력과 겹쳐 불릴 수 있고, 주입한 타이머로 node 테스트가 되기 때문. F-306 4.4)

**한계(회귀)**: 한 번도 온라인에서 열어 본 적 없는 서버 문서를 오프라인에서 열면 `md-yjs` 에 상태가 없어 편집할 수 없다(읽기 전용 + `연결되면 편집할 수 있습니다`). **F-306 이 이 경로를 `offline-view` 로 정했다** — 캐시 본문으로 읽기만 되고(방 Doc·`md-yjs` 로는 들어가지 않는다), 알림 띠 N7 `오프라인에서는 이 문서를 읽기만 할 수 있습니다. 연결되면 편집할 수 있습니다.` 가 뜨며, `online` 이 오면 그 문서 열기 세션을 새로 시작한다(F-306 5장). 지금은 캐시 본문으로 편집이 됐다. 11장 확인 항목

### 3.7 오프라인 병합을 사용자에게 어떻게 보이는가

본문 충돌 사본이 사라지므로 사용자가 "뭔가 합쳐졌다"를 알 수단이 필요하다. 결정:

- **연결이 끊긴 동안**: 상태바 `연결 끊김 · 다시 연결 중`(9.2). 편집은 그대로 된다
- **재연결 직후**: 내가 끊긴 동안 편집했고(로컬 `Y.Doc` 에 origin 이 로컬인 업데이트가 있었고) **동시에** 서버에서 받은 업데이트가 본문을 바꿨을 때만 info 알림 `연결이 끊긴 동안 한 편집을 합쳤습니다. 같은 곳을 다른 사람도 고쳤다면 문장이 섞였을 수 있습니다`
- 한쪽만 고쳤으면 알림을 띄우지 않는다 — 합쳐진 게 아니라 그냥 올라간 것이라서
- **되돌릴 사본은 만들지 않는다.** 사본을 만들면 사용자가 방금 없앤 "(충돌 사본)" 개념이 이름만 바꿔 돌아온다. 회복 수단은 `product.md` 8장 범위 밖인 버전 히스토리가 생겨야 제대로 생긴다 — 그때까지 회복 수단이 없다는 것을 그대로 적는다

### 4.2 WebSocket 을 `/api/*` 안에 두면 안 되는 이유

### 4.3 인증 방식 (1안) 과 실측 항목

`worker/auth.ts:146` 이 이미 `Cf-Access-Jwt-Assertion` **헤더 또는 `CF_Authorization` 쿠키**를 읽어 JWT 를 검증한다. 같은 출처(`rawdoc.app`)의 WebSocket 업그레이드에 그 쿠키가 실리면 `requireUser()` 가 그대로 동작한다. 브라우저 `WebSocket` API 는 커스텀 헤더를 못 넣지만 같은 출처 쿠키는 보낸다

- **확인 못 함 — 배포본에서 사람이 확인**: Cloudflare Workers 의 업그레이드 요청에 `CF_Authorization` 쿠키가 실제로 실리는지 문서로 확인하지 못했다. 로컬 `dev:worker` 는 `DEV_AUTH_EMAIL` 우회가 경로와 상관없이 먼저 걸려 로컬에서는 판정할 수 없다 — **F-304 15.4 S1(배포본)** 이 잰다(F-304 4.3, 2026-09-24 승인)

### 4.4 쿠키가 안 실릴 때의 2안 (티켓)

실측이 실패하면 아래로 간다. **F-304 4.4 가 구현 가능한 수준으로 적었다**(전환 조건: 15.4 S1 에서 연결이 `4401` 로 닫힘, 2026-09-24 승인). 아래 원래 문장 중 다음과 다른 부분은 F-304 4.4 가 우선한다 — 티켓은 `base64url(JSON) + "." + base64url(HMAC-SHA256(비밀, 앞부분))` 로 서명하고(Worker secret `WS_TICKET_SECRET`), 수명은 60,000ms, **한 번만 쓰기는 강제하지 않는다**(발급·사용마다 저장소 쓰기가 늘어서 — 문서 하나·사용자 하나·60초로 묶이는 것으로 충분하다고 본다)

1. `GET /api/ws-ticket?doc={id}` — Access 안 경로라 인증된다. 권한(edit 이상)을 확인하고 **60초짜리 티켓**을 돌려준다. 티켓은 DO 가 검증할 수 있게 서명한다
2. 클라이언트는 `wss://rawdoc.app/ws/doc/{id}?t={ticket}` 로 연결한다
3. 티켓은 URL 에 실려 로그에 남을 수 있으므로 단기로 둔다 — 이 Worker 는 요청 URL 을 로그로 남기지 않는다(`observability` 미설정)

### 4.5 권한 판정

- **F-304 로 바뀜 (2026-09-23 사용자 결정)**: 거절은 HTTP 403/404 가 아니라 소켓을 받은 뒤 닫기 코드 4401(로그인 필요)·4403(권한 없음·회수)·4404(문서 없음)로 한다 — 브라우저 `WebSocket` 은 업그레이드 실패의 HTTP 상태를 읽지 못한다. 폴더 단위 권한 회수·문서 이동은 즉시 알리지 않고 DO 가 60초마다 권한을 다시 본다(문서 단위 초대 삭제·권한 변경·문서 삭제는 즉시). 아래 원래 문장 중 이와 다른 부분은 F-304 4.2·9장이 우선
- Worker 가 업그레이드를 DO 로 넘기기 **전에** `getDocAccess(env, docId, user)` 로 `edit` 이상인지 본다(`worker/access.ts`). 아니면 업그레이드하지 않고 HTTP 403, 남의 문서면 404 — 기존 규칙 그대로
- 권한은 연결 시점에만 본다. 편집 중에 권한이 회수돼도 그 연결은 살아 있다. **결정**: 초대 삭제(F-225)·권한 변경 때 서버가 해당 DO 에 알려 그 사용자의 소켓을 닫는다. 닫힌 쪽은 읽기 전용으로 내려가고 알림을 받는다
- Access 세션은 168h. 세션이 만료된 뒤의 재연결은 인증에 실패한다 → 상태바 `다시 로그인 필요`(F-207 2.5 의 `signedOut` 과 같은 표시)

## 5. IME × 원격 업데이트 — 최대 위험

### 5.1 무엇이 문제인가

`src/editor/composition.ts` 가 신호(`forceRecalc`)와 판정(`isComposing`·`isForced`)을 정의하고, **여섯 곳 이상이 조합 중 재계산을 보류**한다. 전부 "조합 중 트랜잭션 = 내가 친 글자" 를 전제로 한다

| 파일 | 보류 지점 |
| --- | --- |
| `src/editor/preview/inline.ts:202-205` | 인라인 decoration 재계산 |
| `src/editor/preview/lines.ts:414-417, 478-481, 722-723` | 줄 단위 요소·목록 내어쓰기 측정 |
| `src/editor/preview/blocks.ts:439-445` | 표·코드블록·이미지 위젯. 조합 중이면 `value.map(tr.changes)` 로 위치만 따라감 |
| `src/editor/preview/wikiLinks.ts:191-196` | 위키링크 |
| `src/editor/frontmatter.ts:142,154` | 프론트매터 위젯 |
| `src/editor/createEditor.ts:427-430` | 목차(F-144) 갱신 |
| `autoPair.ts:306,320` · `commands.ts:103` · `preview/links.ts:116` · `preview/tableWidget.ts` | 조합 중 키·클릭 가로채기 금지 |

위험 네 가지(코드 근거에서 추론한 것이고 재현 실험은 하지 않았다):

1. **화면이 깨져 보이는 구간.** `ySync` 는 원격 변경을 `view.dispatch()` 로 적용한다. 원격 트랜잭션이 위 보류를 타면 decoration 위치가 어긋난다. 조합 종료 `forceRecalc` 로 회복은 되지만 그 사이 화면이 틀리다
2. **조합 자체가 깨진다.** `blocks.ts:406-410` 주석이 같은 함정을 이미 기록해 뒀다 — "조합 중 표 재계산이 그대로 일어나 편집 중인 하위 EditorView 의 DOM 을 파괴해 조합이 깨진다(updateDOM 의 '구조 바뀜' 분기 → endEdit → cellView.destroy())". 원격 업데이트가 조합 중 문서를 바꾸면 같은 경로가 열린다
3. **표 칸 하위 EditorView(F-125)는 별도 `EditorState` 이고 Yjs 밖이다.** 칸 조합 중에는 주 view 의 `composing` 이 false 라 `isCellComposing`(`preview/tableWidget.ts:93`) 으로 따로 본다. 칸 내용을 주 문서에 반영하는 타이밍(`tableWidget.ts` 의 "마이크로태스크로 미룬 쓰기", `trackPendingWrites`)과 Yjs 트랜잭션 경계가 어긋날 수 있다
4. **`history()` 가 남의 편집을 되돌린다.** 지금은 `@codemirror/commands` 의 `history()` 다 (`createEditor.ts:354, 421`)

### 5.2 완화안 — 조합 중 원격 업데이트 큐잉

보류 로직 여섯 곳을 고치지 않는다. **원격 업데이트가 `EditorState` 에 닿기 전에 막는다**

- ~~`Y.Doc` 의 `update` 이벤트를 받는 자리에 게이트를 둔다.~~ → **공유 `Y.Doc` 과 편집기 `Y.Doc` 사이에 게이트를 둔다 (F-303 3장, 2026-09-23 사용자 승인).** 원래 문장: `isComposing(view) || isCellComposing(view)` 이면 그 업데이트를 큐에 쌓고 `ySync` 로 흘려보내지 않는다

- 내가 친 글자(로컬 origin)는 막지 않는다. 막으면 IME 가 멈춘다

### 5.3 표 칸 하위 에디터

> **F-303 6.2 로 바뀜 (2026-09-23 사용자 결정).** 칸 편집 중(조합 아님) 원격은 곧바로 적용하고, 그 원격이 **편집 중인 칸**을 건드렸을 때만 칸 세션을 끝낸다. 칸 조합 중에는 5.2 보류 규칙을 따른다. 아래 원래 문장 중 "표 범위면 보류, 3초 뒤 `endEdit`" 는 폐기

- **이건 자동 테스트로 판정할 수 없다** — 실제 한글 IME 가 필요하다. 사람 확인 항목(5.5)

## 7. `/v1` PUT (F-223) 이 Yjs 밖 경로로 남는 문제

지금 `worker/v1.ts` 의 `handleUpdateDocV1` 은 `X-Lock-Session` 을 지우고 기존 핸들러로 넘긴다 — 그래서 **편집 잠금이 살아 있으면 항상 423** 이다(F-223 2.2). 잠금이 폴백으로 좁혀지면 이 보호가 사라지고, 스크립트가 D1 `docs.content` 를 직접 덮어 DO 안 Yjs 상태와 어긋난다. 그다음 DO 스냅샷이 D1 을 다시 덮으면 **스크립트가 쓴 내용이 조용히 사라진다**

**결정: `/v1` PUT 을 DO 경유로 바꾼다** (F-308)

1. Worker 가 문서 id 로 DO 를 잡고 RPC 로 "본문을 이 문자열로 바꿔라" 를 보낸다
2. DO 가 현재 `Y.Text` 와 새 문자열의 차이를 계산해 Yjs 트랜잭션 하나로 적용한다. 전체 삭제 후 삽입이 아니라 **차이만** 적용해야 접속 중인 편집자의 커서·선택이 문서 전체로 밀리지 않는다. 앞뒤 공통 접두·접미를 잘라 가운데만 바꾸는 수준이면 충분하다(글자 단위 최소 diff 를 요구하지 않는다). 방이 비고 불러오지 않았으면 DO 안에서 D1 만 쓰고 흡수에 맡긴다(F-308 5.2)
3. 적용 결과가 접속자 화면에 즉시 반영된다. D1 스냅샷은 평소 디바운스대로
4. `baseVersion` 은 **D1 `version` 기준으로 그대로 검사**한다. 스크립트가 낡은 버전을 들고 오면 지금처럼 409. 검사와 적용은 DO 안에서 한 번에 해야 경쟁이 없다. 검사 전에 DO 가 못 나간 편집을 먼저 D1 에 쓴다(F-308 7.1)
5. 실시간 편집자 임시 423 을 지운다. D1 잠금 423 은 F-309 에서(F-308 10.2). F-223 2.2 갱신 대상

- `POST /v1/docs`(새 문서)는 바꾸지 않는다 — DO 가 아직 없고 D1 에 만들면 나중에 씨앗 심기(3.3)가 집어간다
- `/v1` 읽기(`GET /v1/docs/:id`)는 D1 스냅샷을 그대로 읽는다. 최대 5초 낡을 수 있다는 것만 F-223 에 적는다
- **F-305 과 F-308 사이의 구멍**: 그사이에는 `/v1` PUT 이 잠금 없이 D1 을 덮을 수 있다. F-308 이 붙기 전까지 `/v1` PUT 은 **그 문서에 활성 DO 연결이 있으면 423** 을 유지한다(지금 잠금 검사 자리에 DO 접속자 수 확인을 넣는다). F-308 에서 이 임시 규칙을 지운다. **DO 가 잠든 동안의 `/v1` 쓰기는 F-304 흡수로 남는다** — 사라지지 않는다. 연결 중 겹치는 쓰기만 이 임시 423 이 막을 필요가 있다(F-304 7.2·11.3 8번, 2026-09-24 승인). F-308 에서 닫힘

## 8. 잠금·저장 경로의 경계

### 8.1 한 문서는 한 경로만 쓴다

가장 나쁜 경우는 같은 편집이 Yjs 로도 가고 PUT 으로도 가서 D1 을 서로 덮는 것이다. 이를 막는 규칙:

| 문서 상태 | 본문 저장 경로 | 잠금 |
| --- | --- | --- |
| 서버 문서 + WebSocket 연결 성공 | **Yjs 만.** `useDocSaver` 의 본문 저장을 끈다 | 잡지 않는다 |
| 서버 문서 + 한 번도 연결 못 함 | 기존 `PUT` + outbox (폴백) | 기존 F-213 잠금 |
| 서버 문서 + 연결됐다가 끊김 | **Yjs.** 폴백으로 내려가지 않는다 (8.2) | 잡지 않는다 |
| 서버 문서 + outbox 에 이 문서의 `createDoc`·`updateDoc` 이 남아 있음(`pending`) | 지금처럼 `store.get` → 편집기, 700ms 자동 저장 PUT (F-305 4.1 3번) | 기존 F-213 잠금 |
| 로그아웃 상태 로컬 문서 | 지금 그대로 IndexedDB | 해당 없음 |

- 판정은 **문서를 연 세션 단위**로 고정한다. 한 번 폴백으로 시작한 문서는 그 세션 동안 폴백이다 — 중간에 경로가 바뀌면 그 순간이 곧 이중 쓰기다
- 제목도 같은 규칙을 따른다 (3.2)

### 8.2 메인이 정한 "WS 실패 시 폴백" 을 좁힌 것 — 이견

메인 지시는 "WebSocket 연결 실패 시 폴백" 이다. 그대로 읽으면 **연결됐다가 끊겼을 때도** 폴백으로 내려간다는 뜻이 되는데, 그러면:

- 끊긴 동안 로컬 `Y.Doc` 에 쌓인 편집과, 폴백 PUT 이 D1 에 쓴 내용이 **둘 다 살아 있는 상태**가 된다
- 재연결하면 DO 의 Yjs 가 D1 을 다시 덮어 폴백으로 저장한 내용이 사라진다

그래서 **"한 번도 연결하지 못했을 때만 폴백"** 으로 좁혔다. 연결됐다가 끊긴 경우는 재연결만 기다리고, 그 사이 편집은 `md-yjs` 영속(3.6)이 지킨다. 11장 확인 항목

### 8.3 폴백이 열리는 경우

- DO 장애·배포 중 짧은 구간·무료 한도 소진(9.3)
- 기업 프록시가 WebSocket 을 막는 환경
- 인증 실패(Access 세션 만료) — 이 경우는 폴백이 아니라 `다시 로그인 필요`

폴백이면 상태바에 `실시간 연결 실패 · 한 명씩 편집` 을 띄우고 기존 잠금 알림 띠(F-213 2.3)를 그대로 쓴다

## 9. 운영

### 9.1 배포 때마다 연결이 전부 끊긴다

**코드를 배포하면 DO 가 재시작되고 기존 WebSocket 연결이 끊긴다** (https://developers.cloudflare.com/durable-objects/best-practices/websockets/ , 확인일 2026-09-20). 피할 수 없다 — 배포마다 접속자 전원이 한 번 끊긴다

- **확인 못 함 — 구현 전 실측**: `y-partyserver` 의 `YProvider` 가 자동 재연결하는지, 한다면 간격이 얼마인지. 안 하면 우리가 감싼다
- 배포 안내: `CLAUDE.md` "배포" 절차에 "올리기 전후로 사용자에게 알린다" 가 이미 있다. 편집자가 여럿이 되면 배포 전 공지 수단이 따로 필요해질 수 있다 — 지금은 범위 밖

### 9.2 재연결 전략

| 구간 | 동작 |
| --- | --- |
| 끊긴 직후 | 상태바 `연결 끊김 · 다시 연결 중`. 편집은 계속 된다 |
| 재시도 | 지수 백오프 1s → 2s → 4s → 8s → 16s → 30s(상한) — **값 확정**: `min(1,000 × 2^(n−1), 30,000) × (0.8~1.2 지터)`(F-305 7.3, 배포 직후 전원이 같은 순간에 몰리지 않게) |
| 10초 넘게 실패 | 알림 띠(warn) — **F-305 에서는 N5** `서버와 연결이 끊겼습니다. 다시 연결되면 이어서 저장됩니다. 그 전에 창을 닫으면 끊긴 뒤의 편집은 사라집니다`(F-306 전이라 브라우저에 저장되지 않는다). **F-306 이 오프라인 영속을 붙이면 이 절의 원래 문구**(`… 편집은 이 브라우저에 저장되고 다시 연결되면 합쳐집니다`)**로 되돌린다** — **F-306 이 들어와 N5 문구가 이 절 원래 문장(끝 마침표 없음)으로 실제로 되돌아갔다(F-306 11.2)** |
| 재연결 성공 | 알림 띠를 지우고, 병합이 실제로 일어났으면 3.7 의 알림 |
| 닫기 코드 4401·4403·4404(F-304 4.2) | 재시도를 멈추고 `다시 로그인 필요` 또는 `편집 권한이 없습니다` — 첫 동기화 전후로 갈리는 세부 동작은 F-305 8장 표 |

- `YProvider` 기본 재연결 간격은 `min(2^n × 100ms, 2,500ms)`, 지터 없음 — 위 표의 "지수 백오프 1s → 2s → 4s → … 최대 30s, 지터" 는 F-305 가 감싸야 나온다(F-304 4.2·11.3 5번, 2026-09-24 승인)
- 재연결해도 폴백으로 내려가지 않는다 (8.2)
- 탭이 백그라운드로 가도 연결을 끊지 않는다 — hibernation 은 서버 쪽에서 duration 을 안 물리므로(9.3) 연결 유지 비용이 거의 없다. 다만 브라우저가 백그라운드 탭의 타이머를 조이는 것은 통제 밖이라, 되돌아올 때 `visibilitychange` 에서 연결 상태를 한 번 확인한다

### 9.3 무료 한도 — 관측과 대응

Durable Objects 는 Workers Free 에서 **SQLite 백엔드로** 쓸 수 있다 (확인일 2026-09-20, https://developers.cloudflare.com/durable-objects/platform/pricing/ , https://developers.cloudflare.com/workers/platform/pricing/)

| 항목 | 무료 한도 |
| --- | --- |
| Requests | 100,000 / day (수신 WebSocket 메시지는 **20:1**, 송신 메시지는 과금 없음, 연결 수립 1건) |
| Duration | 13,000 GB-s / day (DO 1개는 실사용량과 무관하게 **128MB** 기준) |
| SQLite Storage | 5 GB (계정 전체), DO 1개당 10 GB |
| Rows Read / Written | 5,000,000 / 100,000 per day |
| DO 클래스 수 | 100 |

- **한도를 넘으면 자동 과금이 아니라 이후 작업이 에러로 실패한다.** 이게 이 설계의 가장 큰 운영 위험이다
- **Hibernation API 가 조건이다.** `ctx.acceptWebSocket()` + `webSocketMessage()`/`webSocketClose()`/`webSocketError()` 를 쓴다. 표준 `ws.accept()` + `addEventListener` 는 DO 를 메모리에 붙잡아 둔다. 문서 원문: "Billable Duration (GB-s) charges do not accrue during hibernation". 안 쓰면 **탭 1개를 8시간 열어두면 28,800초 × 0.125 GB = 3,600 GB-s 로 하루 한도의 28%** 를 먹는다(이 계산은 공식 수치에 대입한 것이고 문서에 적힌 값이 아니다)
- `setWebSocketAutoResponse()` 로 ping/pong 류를 **깨우지 않고** 응답한다(request·response 각 2,048자 상한). 연결별 상태는 `serializeAttachment()`(최대 16,384 bytes)

관측(사람 확인 항목으로 `specs/human-checks.md` 에 올린다):

| # | 언제 | 무엇 |
| --- | --- | --- |
| O1 | F-305 배포 후 **매일 1주일** | Cloudflare 대시보드 DO **Duration(GB-s)**, Requests, SQLite Rows Written |
| O2 | 하루 Duration 이 6,500 GB-s(한도의 50%)를 넘으면 | 먼저 hibernation 이 실제로 걸리는지 확인한다 — 접속자 0명인 문서의 DO 가 duration 을 계속 먹고 있으면 `ctx.acceptWebSocket()` 경로를 안 타는 것이다 |
| O3 | hibernation 이 정상인데도 넘으면 | Workers Paid **$5/월** 전환 (포함량 400,000 GB-s/월 + 1M requests/월) |
| O4 | D1 Rows Written | 스냅샷 디바운스(3.5)가 의도대로 도는지. F-213 잠금이 빠진 만큼과 비교 |

- **한도가 소진돼도 사용자 데이터는 남는다**: 클라이언트 로컬 `Y.Doc` + `md-yjs` 영속(3.6)에 편집이 있고, 한도가 리셋되면 재연결 때 병합된다. 이걸 근거로 "한도 초과 = 저장 실패로 데이터 유실" 은 아니다. 다만 **그 사이 다른 사람에게는 내 편집이 안 보인다**
- 유료 전환은 M3 의 선행 조건이 아니다

### 9.4 확인 못 한 운영 수치

- **DO 하나당 동시 WebSocket 연결 수 상한** — 공식 문서에 수치가 없다. best-practices 에 "connect thousands of clients per instance" 류 서술만 있다
- **Cloudflare Access 무료 좌석 수** — 2026-09-15 에 이어 2026-09-20 에도 1차 출처에서 찾지 못했다. 편집자 수가 늘면 먼저 막히는 곳이 여기일 수 있다
- `y-partyserver` 의 **hibernation 기본 켜짐 여부·켜는 옵션** — README 에 "works for both hibernate and non-hibernate modes" 주석은 있으나 켜는 방법을 확인하지 못했다. **F-304 가 확인함**: 기본값은 꺼짐(`{ hibernate: false }`)이고, `Server` 의 정적 속성 `options = { hibernate: true }` 로 켠다(F-304 5.1)

## 10. 테스트 방법

지금 e2e 구조로는 실시간 동작을 판정할 수 없다. 구현 에이전트가 헤매지 않게 방식을 여기서 정한다

### 10.1 왜 지금 구조로 안 되는가

- `playwright.config.js` 는 `vite preview`(정적 파일)만 띄운다. **Worker 가 없다.** 서버 API 는 `e2e/fixtures/fakeServer.js` 가 `page.route` 로 메모리에서 흉내낸다
- **`page.route` 는 WebSocket 을 가로채지 못한다**

### 10.2 정하는 방식

| 층 | 방법 |
| --- | --- |
| 조합 큐 어댑터(5.2), 스냅샷 디바운스(3.5), 로컬 영속 압축(3.6), diff 적용(7장 2번) | **Vitest 단위 테스트.** 전부 순수 함수로 뽑아낼 수 있다. `Y.Doc` 두 개를 만들어 `applyUpdate` 로 잇는 건 브라우저가 필요 없다 |
| DO 서버(`onLoad`/`onSave`, 권한, 씨앗 심기, 크기 초과) | **Vitest worker 테스트.** 지금 `worker/**/*.test.ts` 가 가짜 D1·R2 를 쓰는 것과 같은 방식으로 가짜 storage 를 넣는다 |
| 두 사람이 동시에 편집 (e2e) | **테스트 전용 in-page provider 주입 + `BroadcastChannel`** (아래) |
| 연결 실패 → 폴백 (e2e) | **`page.routeWebSocket()`** 으로 `/ws/*` 를 거절한다. Playwright 1.48+ 기능이고 설치된 것은 `@playwright/test ^1.63.0` 이라 쓸 수 있다 |
| IME × 원격 업데이트 | **자동 판정 불가.** 5.5 의 H1~H7 사람 확인 |
| 실제 DO·WebSocket 왕복 | **사람 확인.** `npm run dev:worker`(로컬 wrangler) 와 배포본에서 두 브라우저 |

**in-page provider 주입 방식**(구체)

1. 앱은 provider 를 직접 `new YProvider(...)` 하지 않고 **팩토리 하나를 거쳐** 만든다. 팩토리는 `window.__yProviderFactory` 가 있으면 그걸 쓰고, 없으면 진짜 `YProvider` 를 만든다. 테스트가 아닌 빌드에서도 이 분기 한 줄은 남는다 — 분기가 없으면 e2e 를 못 쓴다
2. e2e 는 `context.addInitScript` 로 `window.__yProviderFactory` 를 심는다. 이 가짜 provider 는 `Y.Doc` 의 업데이트를 **`BroadcastChannel`** 로 내보내고 받아서 `applyUpdate` 한다
3. **같은 브라우저 컨텍스트의 두 페이지는 같은 출처라 `BroadcastChannel` 로 이어진다.** 두 Playwright 페이지가 실제로 서로의 편집을 본다 — Yjs 바이너리 프로토콜을 테스트 코드에서 다룰 필요가 없다
4. awareness 도 같은 채널로 실어 접속자 아바타·원격 커서를 판정한다

이 방식이 **덮지 못하는 것**: DO 코드, WebSocket 프로토콜, hibernation, 인증. 그건 위 표의 worker 단위 테스트와 사람 확인이 맡는다. 이 경계를 각 작은 명세의 수용 기준에 그대로 적는다

- 시각값(아바타 색·커서 라벨 위치)은 e2e 로 고정하지 않는다 — `CLAUDE.md` "개발 방식". 열리고 닫히고 보이는지까지만
