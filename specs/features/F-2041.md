## 2. 불변조건 안에서 되는 것과 안 되는 것 — 결론

### 2.1 md-yjs 기록으로 방 Doc 을 먼저 세우는 것 — 된다

- `md-yjs` 행은 **그 방 Doc 자신의 Yjs 업데이트**다. `attach` 는 불러오기 origin(`YJS_LOAD_ORIGIN`)이 아닌 모든 업데이트 — 첫 동기화 step 2, 받은 원격 편집, 내 편집 중계 — 를 한 행씩 쓴다(`yjsStore.ts` `attach` 의 `onUpdate`, F-306 4.3). 그래서 기록 안의 항목 id 는 서버 Doc 의 항목 id 와 같은 역사다. 서버 동기화가 뒤에 와도 Yjs 는 이미 가진 항목을 다시 넣지 않는다(적용은 멱등)
- 이것은 "파생 값을 열린 Doc 에 되쓰기" 가 아니다 — F-306 4.3 이 이미 적은 그대로다. 달라지는 것은 **편집기를 붙이는 시점**뿐이다. 지금도 재개 세션은 기록을 먼저 적용한 뒤 소켓을 연다(`useLiveDoc` 의 `begin`, F-306 6.4). 오프라인 시작(`startOffline`)과 첫 동기화 시간 제한 뒤(`becomeReadyReconnecting`)에는 이미 동기화 전 방 Doc 으로 편집기를 띄운다. 이 명세는 그 상태를 **온라인 시작의 첫 순간부터** 쓴다
- F-301 3.3 "씨앗 심기가 끝나기 전에는 클라이언트가 편집할 수 없다" 의 근거는 "브라우저가 씨앗을 심으면 두 벌이 된다" 였다. 기록이 있다는 것은 **이 브라우저가 이미 DO 가 심은 씨앗을 받았다**는 뜻이라(기록의 첫 행은 첫 동기화 step 2) 이 근거에 걸리지 않는다. 기록이 있는 문서의 편집 허용은 F-306 이 오프라인 시작에서 이미 승인한 성질이다
- 남는 위험: DO 저장소가 초기화되면 기록과 새 씨앗이 두 벌로 합쳐진다(F-306 15장 L7). **지금도 똑같이 일어난다** — 지금도 기록을 먼저 적용하고 소켓을 열기 때문이다. 이 명세는 그 위험을 늘리지도 줄이지도 않는다. 사용자가 중복을 보는 시점이 "편집기가 뜬 뒤 1초쯤" 으로 옮겨질 뿐이다

### 2.2 `md-remote` 캐시 본문으로 방 Doc 을 심는 것 — 안 된다

- 캐시 본문은 문자열이다. 그것을 방 Doc 에 `insert` 하면 이 브라우저의 clientID 로 **새 항목**이 생긴다. 서버 Doc 의 같은 글자와 id 가 달라 Yjs 는 둘을 다른 글로 보고, 동기화하면 본문이 두 번 들어간다. 불변조건 "D1 `docs.content`·IndexedDB 캐시 본문은 `Y.Text` 의 한쪽 방향 파생 — 열린 `Y.Doc` 에 되쓰지 않는다" 가 막는 바로 그것이다(F-301 3.3 "브라우저는 어떤 경우에도 씨앗을 심지 않는다")
- 그래서 기록이 없는 문서에서 캐시 본문을 "먼저 보여 주는" 길은 **방 Doc 과 무관한 읽기 전용 화면**뿐이다. 그 화면을 둘지는 11장 Q1

## 3. 연결 제어기 — `readyAtStart` (`src/app/liveDoc.ts`)

### 3.1 계약

```ts
// LiveDocDeps 에 더한다
// 재개 가능 세션에서, 소켓을 여는 것과 동시에 ready 를 참으로 낸다. resumable 이 아니면 뜻이 없다
readyAtStart?: boolean     // 기본 false
```

- `useLiveDoc` 는 `readyAtStart: resumable` 을 넘긴다. 곧 **App 이 여는 재개 세션은 전부 이 규칙**을 쓴다
- 밀린 편집 러너(`yjsFlush.ts`, F-306 8장)는 넘기지 않는다 — 러너는 편집기를 띄우지 않으므로 `ready` 가 일찍 참이 될 이유가 없고, 러너의 판정 표(`reconnecting` → `failed`)가 지금 그대로 맞다. 옵션으로 가르는 이유가 이것이다: 재개 세션 전부를 바꾸면 러너가 "열린 뒤 닫힘" 한 번에 곧바로 `failed` 로 끝난다(지금은 30초 안에서 백오프로 다시 시도한다). 기존 단위 U19·U20 도 그대로 남는다(m5)
- `startOffline` 과 함께 오면 `startOffline` 이 이긴다(지금 F-306 6.2 그대로 — 소켓을 열지 않고 `reconnecting`)

### 3.2 시작

- `resumable && readyAtStart && !startOffline` 이면 `start()` 는 **소켓을 열기 전에** 스냅샷을 `{ phase: 'connecting', ready: true, everSynced: false }` 로 낸다. 구독자는 `start()` 가 돌아오기 전에 `ready: true` 를 받는다
- 첫 동기화 시간 제한 두 개(`FIRST_SYNC_TIMEOUT_MS`·`FIRST_SYNC_HARD_TIMEOUT_MS`)는 **지금처럼 건다.** 뜻만 바뀐다 — 이 세션에서 그 타이머는 편집기 표시가 아니라 "상태바를 `연결 중…` 에서 `연결 끊김 · 다시 연결 중` 으로 바꾸는 때" 를 정한다(3.4)
- 첫 `synced` → `live`, `everSynced: true`. 지금과 같다

### 3.3 닫기 분류

`readyAtStart` 세션은 첫 동기화 전 닫힘에 **F-306 6.3 표의 "`ready` 뒤" 열**을 쓴다. 지금 제어기의 `onClose` 가 `snap.ready` 를 "동기화 뒤" 로 보는 규칙 그대로다 — 새 분기를 만들지 않는다

| 닫기 | 지금(재개, `ready` 전) | **`readyAtStart`, 첫 동기화 전** |
| --- | --- | --- |
| `4401` | `stopped`/`signed-out`, `ready: true` | `stopped`/`signed-out` (같음) |
| `4403` | `stopped`/`forbidden`, `ready: false` → App 이 보기로 다시 연다(N1) | **`stopped`/`revoked`** → 방 Doc 편집기 그대로 읽기 전용 + N2 + `새 문서로 저장` |
| `4404` | `stopped`/`not-found`, `ready: true` | `stopped`/`deleted` (App 화면은 같다 — N3, 읽기 전용, `md-yjs` 기록 지움) |
| 그 밖, 열린 적 없음 | `reconnecting`, 백오프 | `reconnecting`, 백오프 (같음) |
| 그 밖, 열린 적 있음 | `connecting` 에 머물며 백오프 | **`reconnecting`**, N5 타이머, 백오프 |

- `4403` 을 `revoked` 로 보내는 이유: 편집기가 이미 떠 있고 사용자가 그 사이 쳤을 수 있다. `forbidden` 은 App 이 경로를 `view` 로 바꿔 편집기를 서버 본문으로 다시 만들므로 **친 글이 말없이 사라진다.** F-306 6.3 이 "`ready` 뒤" 열에 `revoked` 를 둔 근거와 같다. 11장 Q4
- "열린 적 있음" 을 `reconnecting` 으로 보내는 이유: 편집기가 떠서 쓰는 중인데 연결이 한 번 끊겼다 — 상태바가 그대로 알려야 한다. 동기화 뒤 끊김과 같은 표시다

### 3.4 첫 동기화 시간 제한·`goOffline`·`wake`

- 시간 제한이 울렸을 때 "이미 끝남" 은 `everSynced` 가 참이거나 단계가 `connecting` 이 아닌 것이다(`ready` 로 보지 않는다 — 이 세션은 처음부터 `ready` 다). 끝나지 않았으면 지금 `onFirstSyncTimeout` 규칙 그대로: 열린 소켓이 없으면 곧바로, 열린 소켓이 있으면 30초까지 기다린 뒤 `becomeReadyReconnecting`(단계 `reconnecting`, 소켓·재시도 타이머는 그대로, N5 타이머 시작). **폴백은 없다**
- `goOffline()` 이 `readyAtStart` 세션의 `connecting` 에서 오면: 소켓을 버리고 재시도 타이머를 끄고 `reconnecting`(N5 타이머 시작). 지금 재개 세션의 "`ready` 전 `goOffline`" 과 같은 결과다. 지금 코드의 분기 조건(`resumable && !snap.ready`)으로는 이 경우가 **아무 일도 하지 않고 지나간다** — 고쳐야 할 자리다
- `wake()` 는 지금 그대로(소켓이 없으면 연다)

### 3.5 비재개 세션 — 바뀌지 않는다

- `readyAtStart` 는 `resumable` 이 아니면 무시한다. 기록이 없는 문서의 흐름(첫 동기화까지 편집기 없음, 10초/30초 뒤 폴백)은 F-305·F-306 그대로다. 11장 Q1 이 ① 을 고르면 이 절이 바뀐다

## 4. 불러오기부터 편집기까지 — 순서

1. 판정 effect 가 `hasPendingChanges`·`hasState`·금고 여부를 함께 기다린다(지금 그대로). `realtime` + `resume: true`
2. `useLiveDoc` 가 빈 방 Doc 을 만들고 `attach` 를 기다린다. 기록이 모두 적용된 뒤에 제어기를 만든다(F-306 6.4 3번, 지금 그대로) — **`ready` 가 빈 방 Doc 에서 참이 되는 일은 여전히 없다**
3. 제어기 `start()` → `ready: true`(3.2). 같은 렌더에서 App 의 "첫 ready" 블록이 방 Doc 본문·제목으로 `openDoc`·사이드바 제목·글자 수를 맞추고, `liveEditorOption` 이 방 Doc 을 넘긴다. 편집기는 방 Doc 에서 편집기 Doc 을 복제하고 게이트를 세운다(F-305 9.1·9.2 — 한 동기 구간). **App 쪽 코드는 이 순서를 위해 바뀌지 않는다** — 이미 `ready` 를 보고 있다(F-306 9.1)
4. 소켓이 열리고 step 2 가 오면 방 Doc 에 원격분이 들어가고, 게이트가 편집기 Doc 으로 옮긴다. IME 조합 중이면 게이트가 보류했다가 `compositionend` 에 함께 적용한다(F-303, 불변조건). 새 코드 없음
5. `synced` → `live`. 병합 판정기(F-306 7장)가 `setLive(true)` 를 받는다

- 기록 불러오기 비용: 1MB 문서 기록 200~1,000행 적용 4.1~8.5ms(F-306 측정 b, 이 PC). 편집기 표시까지는 페이지 부팅이 지배한다(m3: 377~506ms 가 D=0 과 같은 구간)
- `attach` 가 실패하면 지금처럼 `onResumeFailed` → 비재개로 다시 판정(F-306 6.4 4번). 이때는 기다리는 흐름이다

### 5.1 편집 — 허용한다 (11장 Q2)

- 본문 PUT·편집 잠금은 없다 — 경로가 `realtime` 이라 F-305 10.1 표 그대로(`useDocSaver` `blocked`, `useDocLock` 에 `null`)
- 병합 알림 N8: 동기화 전에 내가 쳤고(`unsyncedLocal`) 첫 step 2 가 본문을 바꿨으면 뜬다(F-306 7.2 규칙 그대로, 새 코드 없음). 문구의 "연결이 끊긴 동안" 은 이 경우 "서버와 맞추기 전에" 가 더 정확하지만 문구는 바꾸지 않는다 — 합쳐진 사실과 "문장이 섞였을 수 있다" 는 경고가 같고, 동기화 전 1초 안팎에 치고 그사이 남도 같은 문서를 고친 경우에만 뜬다

### 5.2 본문 커서·스크롤 — 튀지 않는다 (코드와 측정으로 확인)

- 원격 변경은 `y-codemirror.next` 가 `view.dispatch({ changes, annotations })` 로 넣는다(`y-sync.js`). 선택은 CM6 가 그 변경으로 옮긴다 — `SelectionRange.map(change, assoc = -1)`(`@codemirror/state` 6.7.4). 커서 앞에 글이 들어오면 커서는 같은 글자 옆에 남는다. 문서를 열면 커서는 맨 앞(`ia.md` 3.4)이고, 맨 앞에 원격 글이 들어오면 `assoc = -1` 이라 새 글 **앞**에 남는다
- 스크롤: `.cm-scroller` 가 CM6 의 스크롤 요소다(`app.css` `.cm-host .cm-editor .cm-scroller`). CM6 6.43.11 `EditorView.measure` 는 변경 전 화면 위쪽 줄(`scrollAnchorAt`)을 기억했다가 변경 뒤 그 줄의 높이 차만큼 `scrollTop` 을 고친다. m7 에서 위쪽에 5줄이 들어와도 화면 위쪽 줄이 한 줄 안에서 버텼다
- 새 코드 없음. 보이는 느낌은 사람 확인(9.3 H-a)

### 5.3 사이드바 정렬 — 따라잡기로는 `updatedAt` 을 올리지 않는다 (App.tsx)

- 지금 App 은 `liveRoomDoc`(= `ready` 인 방 Doc)의 **모든** `update` 에 700ms 뒤 사이드바 `updatedAt` 을 지금 시각으로 바꾼다(`liveRoomDoc` effect, F-305 10.1). 지금은 첫 step 2 가 `ready` 전에 들어오므로 걸리지 않는다. 이 명세 뒤에는 첫 step 2 가 `ready` 뒤에 들어온다 — 그대로 두면 **남이 고친 문서를 열기만 해도 그 문서가 목록 맨 위로 뛴다**
- 규칙: **`everSynced` 가 거짓인 동안 들어온 업데이트는 origin 이 편집기 중계(`isEditorRelay`, `remoteGate.ts`)일 때만** `updatedAt` 을 올린다. `everSynced` 가 참이 된 뒤는 지금 그대로(원격·내 편집 모두)
- 재연결 뒤 따라잡기(`everSynced` 참)는 지금처럼 올린다 — 이 명세가 만든 문제가 아니고, 바꾸면 F-305 10.1 의 동작이 바뀐다
- `everSynced` 는 effect 안에서 최신 값을 읽어야 한다(업데이트 순간의 값). step 2 는 `synced` 보다 먼저 적용되므로(`y-partyserver` `dist/provider/index.js` 의 sync 메시지 처리기가 `readSyncMessage` 로 step 2 를 적용한 **다음 줄에서** `provider.synced = true`) 첫 step 2 는 거짓일 때 들어온다

### 5.4 제목 — 기록의 제목으로 떴다가 동기화에서 맞춘다

- "첫 ready" 블록은 사이드바 제목을 방 Doc `title` 로 맞춘다(지금 그대로). 이 순간 방 Doc 은 기록의 제목이라, 그 뒤 서버에서 제목이 바뀌었으면 **사이드바·제목 칸이 한 번 옛 제목을 보였다가** step 2 가 오면 `observeTitle` → `onRemoteTitle` 로 새 제목이 된다(F-305 9.3, 새 코드 없음)
- 받아들이는 이유: 목록 제목(`list()` 의 D1 값)을 그대로 두면 제목 칸 글자와 방 Doc `title` 이 달라진다. 그 상태에서 제목을 고치면 `writeLiveTitle` 이 방 Doc 값과의 차이를 쓰므로 의도하지 않은 글자가 들어간다. 한 번 바뀌어 보이는 쪽이 덜 나쁘다. 11장 Q6
- 제목 칸에 포커스가 있으면 원격 제목이 와도 칸 글자를 바꾸지 않는다(F-305 9.3 `docTitle.ts`, 지금 그대로)

### 5.5 금고로 옮기기 — 동기화 전에는 막는다 (App.tsx `prepareConvertDoc`)

- 지금 열린 실시간 문서를 금고로 옮길 때 App 은 **편집기 글**을 봉투에 담는다(F-407 7.4). 동기화 전에는 편집기 글에 그 사이 남이 고친 것이 없다 — 옮기면 그 편집이 금고 사본에서 빠진다
- 규칙: `prepareConvertDoc` 은 세션 스냅샷의 단계가 `live` 가 아니면 `'blocked'` 를 돌려준다(지금 조건 `ready` 대신). 실행기는 이것을 `pending-sync` 로 멈추고 지금 문구 `아직 서버에 올리지 못한 편집이 있는 문서가 있습니다. 저장이 끝난 뒤 다시 누르세요.` 를 띄운다(F-407 실행기 1번). 새 문구 없음
- 재연결 중(`reconnecting`) 세션도 같이 막힌다. 지금은 `ready` 라 통과했는데, 같은 이유(편집기 글이 서버보다 낡았을 수 있다)로 막는 것이 맞다. 이 명세가 만든 창만 막으려면 조건이 더 복잡해지고 얻는 것이 없다

### 5.6 알림 띠·읽기 전용 — 새 규칙 없음

- N2·N3·N4·N5·N6·N8 은 지금 effect 그대로 스냅샷을 따른다. 3.3 표의 결과만 달라진다
- `notFoundBeforeSync`(`!ready` 조건)는 `readyAtStart` 세션에서 참이 되지 않는다 — 비재개 세션에만 남는다(지금 재개 세션과 같다)
