# F-4017 공유 폴더에 편집 초대자가 만든 새 문서는 폴더 소유자 소유

상태: 승인됨(2026-10-24, 열린 질문이 모두 기본값이라 "결정 없으면 바로 진행" 상시 지시로 승인) — 사용자 버그 보고(2026-10-24) "내가 공유한 폴더에서 다른 사람이 위키링크로 새 문서 생성해도 나머지 사람들에겐 안보임". grill 결정표와 흐름도 [`specs/wireframes/shared-folder-new-doc-flow.html`](../wireframes/shared-folder-new-doc-flow.html)(확정) 그대로. 서버만 — 클라이언트(입구 A·B, 빈 공유 폴더 그리기, 알림 문구)는 이 계약 위에서 F-2166. 단위 테스트만, e2e 0개(브라우저로만 보이는 동작 없음)

## 근거 (2026-10-24 HEAD `8d40a36`, 이름으로 찾는다)
- **새 라우트로 뺀다(기존 `POST /api/docs` 는 그대로).** `src/storage/serverStore.ts` 충돌 사본 경로(`copyDoc`, `folderId = myDoc?.folderId ?? serverDoc?.folderId`)가 공유받은 문서의 소유자 폴더 id 를 단 `createDoc` 를 outbox 에 넣는다. 기존 경로를 바꾸면 이런 대기 항목·옛 PWA 가 보낸 요청이 사용자 의사와 무관하게 남의 소유가 된다. 온라인 전용(결정 3)·즉시 응답 계약도 outbox 경로와 맞지 않는다
- 권한은 `access.ts` `folderChainRole`(자신+상위 사슬 grant 최고값, grant `owner_id` 일치 — 리뷰 W2) 그대로 — 하위 트리 어느 폴더든(결정 9). 소유자 가정 grep(`owner_id` in `worker/`): `docRoomCore.ts` 는 D1 행의 `owner_id` 를 읽어 방 소유자로 삼고(`READ_ROW_SQL`), `attachments.ts` `attachment_docs.doc_owner_id` 도 `access.doc.owner_id` 에서 온다 → 행에 폴더 소유자를 넣으면 추가 변경 없음. 휴지통·고정·옮기기는 `owner_id === user.id` 판정이라 만든 사람은 못 함(결정 1 그대로). `folders` 에는 휴지통 열이 없다(`0027_trash.sql` 은 `docs` 만) → "휴지통 폴더" 는 "없는 폴더" 404
- 쓰기 관문 `writeGate.ts` `isWriteRoute` 는 `/api/` 비-GET 을 모두 쓰기로 본다 → 새 라우트도 401→403 `account_blocked`(보낸 사람)→429 하루→429 분(`WRITE_LIMITER` 키 = **보낸 사람 id**)을 자동으로 지난다. Origin 검사도 같다
- 옛 클라이언트: `docsApi.ts` `getShared` 는 응답을 배열로 단정하고 `serverStore.ts` `fetchShared` 가 `.map` 예외를 `null` 로 삼켜 공유 목록 갱신이 조용히 멈춘다 → 응답 모양은 opt-in 으로만 바꾼다(3.2)

## 2. 계약 (F-2166 이 그대로 받는다)
```ts
// POST /api/shared/folders/:id/docs — :id = 초대 폴더 또는 그 하위 트리의 폴더
type CreateSharedBody = { id?: string; title: string; content: string; lineEnding: 'crlf' | 'lf'; createdAt?: number; updatedAt?: number }
// 201(새로 만듦)·200(같은 id 재시도) 몸통 = GET /api/shared 의 문서 항목과 같은 모양
type SharedDocItem = { id: string; title: string; lineEnding: 'crlf' | 'lf'; folderId: string; pinnedAt: null; version: number
  createdAt: number; updatedAt: number; role: 'edit'; ownerEmail: string; viaFolder: { id: string; name: string } }
// GET /api/shared?folders=1 — 쿼리 없으면 지금 배열 그대로
type SharedWithFolders = { docs: SharedDocItem[]; folders: SharedFolderItem[] }
type SharedFolderItem = { id: string; name: string; role: 'edit' | 'view'; ownerEmail: string }
```
## 3. 동작
### 3.1 만들기 판정 순서 (번호가 계약)
0. 쓰기 관문(위 근거) — 401 / 403 `account_blocked` / 429
1. 본문: `badBody` 413 `too_large`·400 `invalid`. `folderId`·`pinnedAt`·`e2eeKey`·`attachmentRefs` 중 하나라도 있으면 400 `{ error:'invalid', field }` — 폴더는 경로로만, 고정은 소유자만, 금고 문서는 공유되지 않는다
2. `id`·`lineEnding`·`createdAt`·`updatedAt` 은 `handleCreateDoc` 와 같은 검사·같은 400 `field`. 제목·본문은 `checkTitleContent(…, e2ee=false, required=true)` → 400 `field` / 413 `too_large`
3. `:id` 가 uuid 가 아니거나 `folders` 행이 없음 → 404 `not_found`
4. 폴더 `owner_id === user.id` → 409 `{ error:'own_folder' }` (내 폴더는 `POST /api/docs`)
5. `folderChainRole(env, :id, folder.owner_id, user.email)` 이 `null` → 404 `not_found`, `'view'` → 403 `forbidden`. 문서 하나만 초대받은 사람은 폴더 grant 가 없으므로 404
6. 대상 폴더 또는 그 상위 사슬에 `e2ee = 1` 폴더가 있음 → 404 `not_found` (권한 판정 뒤라 초대 밖 사람은 금고 여부를 알 수 없다)
7. `isWriteBlocked(env, { owner_id: folder.owner_id, … }, user)` → 403 `account_blocked` (소유자 막힘 포함, `handleUpdateDoc` 와 같다)
8. 몸통 `id` 행이 이미 있음: `owner_id === folder.owner_id` · `deleted_at IS NULL` · `e2ee_key IS NULL` · `resolveDocAccess` 가 `edit` 이상이면 200 + 그 행의 `SharedDocItem`(재시도 안전). 그 밖은 모두 409 `id_taken` — 남의 행을 덮거나 존재를 알리지 않는다
9. `checkDocCreate(readUsage(env, folder.owner_id), 본문 UTF-8 바이트)` 가 막으면 413 `{ error:'owner_quota_exceeded', resource:'bytes'|'docs' }` — 소유자의 `used`·`limit` 은 싣지 않는다(남의 사용량 노출 방지). 기존 `doc_quota_exceeded` 와 코드가 달라 클라이언트가 `공유 폴더 주인의 저장 공간이 가득 찼습니다.` 로 가를 수 있다
10. batch `[INSERT docs(owner_id = folder.owner_id, folder_id = :id, pinned_at NULL, version 1, e2ee_key·attachment_refs NULL), ...docUsageStatements({ actorId: user.id, ownerId: folder.owner_id, deltaBytes, deltaDocs: 1 })]` → 소유자 누계 +바이트·+1, 보낸 사람 하루 +1(`TOTAL_ONLY` + `DAY_ONLY`). 이어 `quotaPushInBackground` 를 **소유자**에게(`handleUpdateDoc` 증가 갈래와 같다 — 결정 5 의 "알림 없음"은 새 문서 알림이고, 기존 용량 경고 푸시는 그대로) → 201

- `role` 은 5번 결과(`'edit'`). `viaFolder` 는 사슬에서 가장 가까운 초대 폴더 `{id, name}` — `handleGetShared` 의 `storedChain` 규칙과 같다. `ownerEmail` 은 `users.email`
- 3~8 은 batch 전 사전 검사 — 거절이면 D1 쓰기 없음(하루 카운터도 안 오름). 사전 검사와 INSERT 사이의 초대 회수·폴더 삭제 경합은 받아들인다(F-401 3.2 7번 선례). 폴더가 그사이 지워지면 문서는 소유자 최상위 고아 행 — 지금 `POST /api/docs` 와 같은 성질
- 소유자에게 알림함·푸시 새 항목 없음(결정 5). DocRoom 시드는 첫 연결 때 D1 행에서 — 따로 할 일 없음

### 3.2 `GET /api/shared?folders=1`
- 쿼리 값이 정확히 `1` 일 때만 `SharedWithFolders`. 없거나 다른 값이면 지금 배열 — 옛 앱·`/v1/shared`(`handleListSharedV1` 이 같은 함수를 쿼리 없이 부름)·MCP `list_shared` 는 그대로
- `docs` 는 지금 배열과 같은 내용. `folders` 는 내 폴더 grant 대상 중 `folders` 행이 있고 소유자가 내가 아닌 것 전부(빈 폴더 포함, 결정 8). 이미 읽는 `SHARED_FOLDERS_SQL` 결과에서 뽑아 **D1 질의를 늘리지 않는다**(`ownerEmail` 캐시 미스 소유자당 `users` 1회는 예외). `role` 은 그 폴더의 사슬 grant 최고값(`storedChain`+`higherRole`) — 중첩 초대(F view, F/G edit)면 F `view`, G `edit` 두 항목. 순서 보장 없음(클라이언트가 정렬)
- grant 가 하나도 없으면 `{ docs: [], folders: [] }`

## 4. 위협 — 새로 생기는 쓰기 길
| 시도 | 결과 |
| --- | --- |
| 보기 초대자·문서 하나만 초대받은 사람 | 403 `forbidden` / 404 |
| 초대 회수 직후, 초대 밖 형제 폴더 id, 다른 소유자의 같은 이름 폴더 | 404 — 폴더는 id 로만 찾고 grant 는 그 폴더 소유자 것만 센다 |
| 남의 기존 문서 id 를 몸통에 넣어 덮기 | 409 `id_taken`, 행 불변 |
| 고정·다른 폴더·금고 문서로 만들기 | 400 `field` |
| 금고 하위 폴더 | 404 |
| 소유자 공간 채우기 | 소유자 한도 413 + 보낸 사람 분 120·하루 5,000(`WRITE_LIMITER`·`DAILY_WRITE_LIMIT`). 편집 초대자가 소유자 용량을 쓰는 것 자체는 결정 1·4 가 받아들인 성질(지금도 본문 늘리기로 가능) |
