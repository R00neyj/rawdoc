## 2. 전체 그림

- `useNotifications` 가 들고 있는 `items`(대기 읽음을 얹은 값, 최대 30개)에서 `readAt === null` 인 항목의 `docId` 를 모은다. 그 집합에 든 문서의 사이드바 행에 점을 단다
- 폴더가 접혀 있으면 그 아래(깊이 무관) 문서 중 하나라도 집합에 있으면 폴더 행에 점. `공유받음` 묶음이 닫혀 있으면 그 머리에 점
- 사용자가 문서를 열면 그 순간 목록에 있던 그 문서의 안 읽은 알림을 서버에서 읽음으로 바꾼다(**Q1 기본값**) — 점·상단바 배지·알림함이 한 상태에서 나온다
- 새 요청은 없다. 가져오기 주기·실패 처리는 F-507 그대로라 점도 최대 약 2분 늦게 뜬다(F-500 3.5 서버 최대 60초 + F-507 폴링 60초)

## 3. 계약

### 3.1 `src/app/docNotifications.ts`

```ts
import type { NotificationItem } from '../lib/docComments'
import type { TreeNode } from '../lib/folderTree'

export function unreadNotificationDocIds(items: readonly NotificationItem[]): ReadonlySet<string>
export function unreadNotificationIdsForDoc(items: readonly NotificationItem[], docId: string): string[]
export function foldersWithUnreadDocs(tree: readonly TreeNode[], unreadDocIds: ReadonlySet<string>): ReadonlySet<string>
```

- `unreadNotificationDocIds`: `readAt === null` 인 항목의 `docId` 집합. 빈 목록이면 빈 집합
- `unreadNotificationIdsForDoc`: 그 문서의 `readAt === null` 항목 `id` 를 **목록 순서 그대로**(서버가 새것부터 준다), 최대 `NOTIFICATIONS_READ_IDS_MAX`(50)개. 이유: 서버 한도(r2). 목록이 30개라 실제로 잘리지는 않지만, 나중에 `limit` 을 올려도(Q3) 요청이 400 이 되지 않게 한다
- `foldersWithUnreadDocs`: 트리를 한 번 걸어, 자기 아래 어느 깊이에든 집합에 든 문서가 있는 폴더 id 를 모은다. `buildTree` 결과를 받으므로 화면 부모 규칙(없는 부모·순환 폴더는 최상위)이 그대로 따라온다. 폴더가 열렸는지는 보지 않는다 — 그리는 쪽(3.3)이 가린다. 비용은 r8

### 3.2 `useNotifications` 에 더하는 것

```ts
// UseNotificationsResult 에 더한다
markDocRead: (docId: string) => void
```

- 아무것도 하지 않는 때(위에서부터 처음 맞는 것): `blocked` / `navigator.onLine` 이 거짓 / 서버 값을 한 번도 받지 못함 / 보낼 id 가 0개
- 보낼 id: **부르는 순간의** 마지막 서버 값에 지금 대기 읽음을 얹은 값(F-507 `applyPendingReads`)에 `unreadNotificationIdsForDoc` 을 적용한 것. 렌더 사이 상태 `items` 가 아니라 훅 안 ref 값에서 계산한다 — 이유: 알림 항목을 누른 직후(`markRead` 가 대기를 더한 직후) 같은 틱에 불려도 그 id 를 두 번 보내지 않게(r3, 8.2 E10)
- 그 뒤는 `markRead` 와 같다: `ids` 대기 하나를 더하고 곧바로 화면에 얹은 뒤 `markNotificationsRead({ ids })` **한 번**. 성공이면 `settledAt`, 실패면 그 대기를 빼서 마지막 서버 값으로 되돌림. 알림 띠 없음(F-507 3.3)
- 오프라인에서 보내지 않는 것은 `markRead` 와 다르다. 이유: `markRead` 는 사용자가 항목을 직접 누른 것이라 실패가 곧 보이는 것이 맞지만, 문서 열기는 부수 효과라 오프라인에서 먼저 칠했다 곧바로 되돌아오는 깜빡임만 남는다

| 금고 문서 | 그 id 의 안 읽은 알림이 남아 있으면 보인다(보통은 서버가 옮길 때 지운다, F-502 3.7) | 예외를 두지 않는다 |
| 홈 화면 `최근 문서`·검색·지도 | 없음 — 사이드바만 | 사용자 요청 범위 |

### 4.2 문서를 열면 그 문서의 알림을 읽음으로 (Q1 기본값)

- **읽음이 되는 때** — 둘:
  1. **문서 화면에 보이는 문서가 바뀌어 X 가 될 때**, 그 순간 알림 상태가 `ready` 면 `markDocRead(X)`. "문서 화면" 은 `bootPhase === 'ready'` · `currentDocId !== null` · 공유 링크 화면·공유 관리·도움말·지도가 모두 없음. 다른 문서·홈·공유 관리·도움말·지도에서 X 로 오는 것이 모두 해당한다(사이드바·팔레트·검색·위키링크·뒤로 가기·알림 항목 이동 무엇이든)
  2. **사용자가 이미 보이는 X 를 다시 고를 때** — `selectDoc(X)` 가 r5 의 "아무 일 없음" 갈래로 갈 때 `markDocRead(X)` 만 부른다. 현재 문서 행에 점이 남는 경우(4.3) 그 행을 눌러 지울 수 있게 하기 위해서다
- **읽음이 되지 않는 때**:
  - 전환 순간 상태가 `ready` 가 아니었으면(부팅 직후 마지막 문서·해시 문서가 열린 경우 — r4) **나중에 `ready` 가 되어도 거슬러 읽지 않는다.** 이유: 사용자가 아직 점을 보지 못한 알림을 앱이 스스로 지우지 않게. 부팅 때 열린 문서의 행에는 점이 보이고, 누르면(2번) 읽음이 된다
  - 문서를 보는 **동안** 새로 도착한 알림(다음 폴링에서 온 것) — 전환이 아니므로 읽지 않는다. 점이 현재 문서 행에 생긴다(4.3). 이유: 보고 있는 문서라도 레일 밖 다른 스레드의 멘션일 수 있다
  - 막힌 계정·오프라인(3.2)
- 알림 항목을 눌러 이동할 때(F-507 4.5): 그 항목은 F-507 대로 `markRead` 로 먼저 읽음이 되고, 다른 문서로 옮겨 가면 1번이 **그 문서의 나머지** 안 읽은 알림을 읽는다(같은 id 는 다시 보내지 않는다, 3.2). 같은 문서 안 이동(F-507 E6 갈래)은 전환이 아니라 그 항목만 읽음
- 알림함을 열기만 해서는 여전히 읽음이 아니다(F-507 4.4 그대로)
- 요청 수: 문서를 열 때마다 그 문서에 안 읽은 알림이 있을 때만 `POST /api/notifications/read` 1번. 쓰기 한도(하루 5,000·분당 120, F-500 3.8)의 1이다. 점이 있는 문서를 여는 횟수만큼이라 한도에 가까워질 일은 없다고 본다

### 4.3 30개로 잘린 목록 — 표시가 틀리는 경우와 처리 (반드시 결론 1)

목록은 **읽음·안 읽음을 섞은 최근 30개**다(r1). `unread` 는 전체 수다. 그래서:

| 경우 | 사이드바 | 상단바 배지 | 처리 |
| --- | --- | --- | --- |
| 안 읽은 알림이 모두 최근 30개 안 | 맞다 | 맞다 | — |
| 어떤 문서의 안 읽은 알림이 **모두 30번째보다 오래됨** | 그 문서에 **점이 없다**(빠뜨림) | 그 수까지 센다 → 배지가 사이드바 점보다 많다 | 받아들인다. 사이드바 점은 "최근 30개 안의 안 읽은 알림" 이다. 없는 점을 지어내지는 않는다 — **틀리는 쪽은 늘 빠뜨림뿐이다**(목록의 `readAt` 은 서버 값이다) |
| 한 문서에 안 읽은 알림이 30개 안과 밖에 걸쳐 있음 | 점이 있다 | 맞다 | 그 문서를 열면 30개 안의 것만 읽음이 된다. 밖의 것은 서버에 안 읽음으로 남아 배지에만 남는다 — 알림함 `모두 읽음` 으로 지운다(F-507 4.3 "모두 읽음 은 보이지 않는 것까지") |
| 다른 탭·기기에서 읽음 | 다음 가져오기(최대 60초, 탭이 다시 보이면 곧바로)까지 점이 남는다 | 같음 | F-507 4.2 그대로 |
| 읽음 요청 실패 | 먼저 지운 점이 곧바로 되돌아온다 | 같음 | F-507 3.3 그대로, 알림 띠 없음 |

- 문서별 **개수**를 보이지 않는 이유(Q2)가 이 표다 — 30개 밖 알림 때문에 문서별 수는 서버 전체 수와 맞지 않을 수 있고, 맞는지 화면이 알 길이 없다. 점("있음")은 30개 안에서 판정이 정확하다
- `limit` 을 서버 최대 50 으로 올리는 안은 Q3

### 4.4 IME·편집기

## 10. 열린 질문

### Q1. 문서를 열면 그 문서의 알림을 읽음으로 할까 — **결정: A (사용자, 2026-09-27)**

| 안 | 동작 | 좋은 점 | 대가 |
| --- | --- | --- | --- |
| **A (기본값)** | 문서 화면이 그 문서로 바뀔 때(상태 `ready` 일 때만), 그 순간 목록의 그 문서 안 읽은 알림을 `POST …/read` 한 번으로 읽음 | 점·배지·알림함·다른 탭·다른 기기가 서버 한 상태에서 나온다. 사용자가 점을 보고 문서를 연 뒤 알림함에서 또 지울 일이 없다 | F-507 4.4 "읽음이 되는 것은 둘뿐" 에 세 번째 길을 더한다. 레일을 열지 않고 문서만 봐도 멘션이 읽음이 된다 — 그 문서의 `댓글` 배지(F-505)는 남는다 |
| B | 읽음으로 하지 않는다. 점은 알림함과 같이 남고, 알림함에서 항목을 누르거나 `모두 읽음` 해야 없어진다 | F-507 규칙을 바꾸지 않는다. 요청이 늘지 않는다 | 문서를 열어 댓글을 다 읽어도 점이 계속 남는다 — 알림함을 따로 비워야 한다 |
| C | 이 탭에서만 점을 숨긴다(서버 읽음 없음, 메모리) | F-507 규칙을 바꾸지 않는다 | 사이드바에는 없는데 배지·알림함에는 안 읽음으로 남아 둘이 어긋난다. 새로고침·다른 탭에서 다시 생긴다 |

- A 를 고르는 이유: 요청이 "문서 열기 전까지 모른다" 는 것이라, 연 뒤에는 표시의 할 일이 끝났다. 한 상태를 여러 곳이 보이는 편이 어긋날 곳이 없다
- A 안의 세부(기본값으로 정함): 부팅 때 열린 문서는 읽지 않는다, 보는 동안 새로 온 알림은 읽지 않는다, 현재 문서 행을 다시 누르면 읽는다, 막힌 계정·오프라인은 보내지 않는다(4.2)
- **B 를 고르면**: 3.2 `markDocRead`·4.2·5장 "문서 열기 읽음"·"같은 문서 다시 고르기" 줄이 빠진다. E5·E6 후반·E8·E9·E10 둘째 `POST`·E11 이 빠지고, 대신 "DOC 행을 눌러도 `POST` 없음, 점 그대로" 한 줄. 도움말 문장은 6장의 짧은 쪽. F-507·F-500 갱신 행(11장 첫 두 줄)이 없어진다
- **C 를 고르면**: `markDocRead` 대신 App 안 "이 탭에서 연 문서의 알림 id 집합" 을 두고 사이드바 집합에서 뺀다. E5 는 "`POST` 없음, 점 없음, 배지 그대로" 가 된다. 도움말 문장은 짧은 쪽

### Q2. 점인가 숫자인가 — **결정: 기본값(숫자 없는 점)**

- 문서별 수는 30개 목록 안에서만 셀 수 있어 서버의 실제 수와 다를 수 있다(4.3). 행에는 제목·자물쇠·`⋯`·(공유받음) 소유자 이메일 앞부분이 이미 있다
- 다른 안(숫자 배지, `commentBadgeText` 규칙): 3.3 의 점이 `.tree-unread-count` 글자가 되고 `.tree-unread-sr` 이 `, 안 읽은 알림 {N}개` 가 된다. E1 의 "숫자 글자 없음" 이 "`2`" 가 된다. 폴더 행 합계를 어떻게 셀지(같은 문서 중복 등) 규칙이 더 든다

### Q3. 목록 크기 30 을 50 으로 올릴까 — **결정: 기본값(그대로 30)**

- 서버가 이미 `limit` 최대 50 을 받는다(r1) — 서버 변경 없이 된다. 빠뜨림(4.3)이 줄어든다
- 두 질의 모두 받는 사람의 행 전부(최대 300)를 걷으므로(F-507 r3) D1 읽기 행 수는 거의 같다. 대신 응답이 약 5/3 로 커지고, 알림함에 보이는 항목도 50개가 된다 — F-507(승인) 4.3 "30개" 와 F-500 4.8 `limit=30` 을 바꾸는 일이다
- 다른 안을 고르면: `fetchNotifications` 가 `limit=50` 을 보내고(F-507 3.1 파일 — 이 명세 소유에 더함), E13 이 51개가 된다

### Q4. 목록에 없는 문서의 안 읽은 알림이 보이면 문서 목록을 다시 읽을까 — **결정: 기본값(아니다)**

- 부팅 뒤 초대받은 문서는 알림 항목을 누를 때 F-507 4.5 가 한 번 다시 읽어 찾는다. 사이드바는 그 전까지 그 문서를 모른다 — 이는 알림과 무관한 기존 한계다(`resyncFromStore` 는 부팅·다른 탭 신호 때만)
- 다른 안: 알림 목록에 모르는 `docId` 의 안 읽은 항목이 처음 보일 때 `resyncFromStore()` 를 문서 id 마다 한 번. 접근을 잃은 문서라면 한 번 헛읽기가 생긴다(요청 `GET /api/docs` + `GET /api/shared`). 고르면 5장에 한 줄, e2e 한 줄(E9 모양)이 는다

### Q5. 문서 목록이 안 보이는 때(레일·닫힌 좁은 창 사이드바)에 대신 표시할까 — **결정: 기본값(하지 않는다)**

- 두 경우 모두 상단바 `알림` 배지가 보인다(F-507 4.1 — 좁은 창에서도 상단바에 그대로)
- 다른 안: 레일 맨 위 또는 좁은 창 사이드바 토글에 점. 토글 버튼 읽기 이름·툴팁 문구가 늘고 `SidebarHead.tsx` 가 소유에 든다

### 기본값으로 정한 것 (승인 시 확정)

1. 표시 원천은 `useNotifications` 의 대기 얹은 `items` 하나 — 2장
2. 접힌 폴더·닫힌 `공유받음` 머리에 합쳐 표시, 열리면 아래로 옮김 — 3.3

4. 틀리는 쪽은 빠뜨림뿐임을 받아들이고 따로 표시하지 않음 — 4.3
5. 부팅 때 열린 문서·보는 동안 온 알림은 자동으로 읽지 않음 — 4.2
6. 오프라인·막힌 계정은 문서를 열어도 요청 없음 — 3.2
