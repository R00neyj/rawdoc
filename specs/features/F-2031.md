## 3. 새 오류 코드 — 종료 코드와 문구

### 3.1 표 (F-2021 4.5 에 더하는 행 — 계약)

| 종료 | `error` | 언제 | 표준 오류 문구 |
| --- | --- | --- | --- |
| **8** | `rate_limited` | 429, 분당(`scope` 가 `day` 가 아닌 모든 429 — 몸통 없음 포함) | `요청이 너무 많습니다. {retryAfter}초 뒤 다시 시도하세요.` |
| **8** | `rate_limited` | 429 `scope: 'day'`, `limit` 있음 | `오늘 쓰기 한도({limit}번)를 다 썼습니다. 약 {남은 시간} 뒤 풀립니다.` |
| **8** | `rate_limited` | 429 `scope: 'day'`, `limit` 없음 | `오늘 쓰기 한도를 다 썼습니다. 약 {남은 시간} 뒤 풀립니다.` |
| 7 | `doc_quota_exceeded` | 413 `error: 'doc_quota_exceeded'`, `resource` 가 `docs` 아님 | `계정의 문서 저장 공간이 부족합니다 ({used} / {limit} 바이트).` |
| 7 | `doc_quota_exceeded` | 413 `error: 'doc_quota_exceeded'`, `resource: 'docs'` | `문서 수가 한도에 이르렀습니다 ({used} / {limit}개).` |
| 4 | `account_blocked` | 403 `error: 'account_blocked'` | `이 계정은 운영자가 쓰기를 막았습니다. 읽기만 할 수 있습니다.` |

- 문구는 F-2024 5.2 표 그대로다. 이 명세가 더한 것은 **값이 빠졌을 때의 모양** 셋뿐이다: 하루 문구의 `limit` 없음(위 셋째 줄), `{남은 시간}` 의 모양(3.3), 413 두 줄에서 `used`·`limit` 가운데 하나라도 숫자가 아니면 괄호째 뺀다(`계정의 문서 저장 공간이 부족합니다.` / `문서 수가 한도에 이르렀습니다.`). 기존 `locked` 가 `email` 이 없으면 괄호째 빼는 것(F-2021 9장)과 같은 방식이다
- `{used}`·`{limit}` 은 숫자 그대로(천 단위 구분 없음) — 기존 `quota_exceeded` 문구(`이미지 저장 공간이 부족합니다 ({used} / {limit} 바이트).`)와 같다
- 기존 413 `too_large`(문서 하나 1MB·첨부 5MB)·507 `quota_exceeded`(이미지 300MB)·403 `forbidden` 은 그대로다. `error` 문자열로 가른다(F-2024 3.4 "기존 413 `too_large` 과 `error` 로 구분한다")
- 문구에 제품명을 쓰지 않는다 — `brandGuard.test.ts` 가 `client.ts`·`output.ts` 안의 `brand.cliName` 문자열을 막는다

### 3.2 응답 분류 규칙 (`client.ts` `handleResponse`)

1. **429 는 몸통을 해석하지 못해도 `rate_limited` 다.** 지금 코드는 비 2xx 몸통이 JSON 이 아니면 상태를 보기 전에 `bad_response` 로 끝낸다(0.1.0 실행 결과 "429 몸통 HTML"). WAF 로 가면 429 몸통이 우리 모양이 아니므로(F-2024 9장 Q1 끝) 429 판정은 JSON 해석 실패 분기보다 **먼저** 와야 한다. 429 에서 몸통이 JSON 객체가 아니면 빈 객체로 본다
2. 429 의 값 정하기
   - `scope`: 몸통 `scope` 가 문자열 `'day'` 면 `'day'`, 그 밖은 전부 `'minute'`
   - `retryAfter`(초): ① 몸통 `retryAfter` 가 0 이상의 유한한 수면 그 값을 올림 ② 아니면 `Retry-After` 헤더가 숫자만으로 된 문자열(`^\d+$`)이면 그 값 ③ 아니면 **60**. 마지막에 1 보다 작으면 1. HTTP 날짜 형식의 `Retry-After` 는 읽지 않는다(③ 으로 간다) — 우리 서버는 초를 보내고(F-2024 3.4), 날짜를 해석하면 CLI 가 시계에 기대게 된다
   - `limit`: 몸통 `limit` 이 수일 때만
3. 413: 몸통 `error` 가 `'doc_quota_exceeded'` 면 `doc_quota_exceeded`(`resource` 는 `'bytes'`·`'docs'` 일 때만 싣는다, `used`·`limit` 은 수일 때만). 그 밖은 지금처럼 `too_large`
4. 403: 몸통 `error` 가 `'account_blocked'` 면 `account_blocked`. 그 밖은 지금처럼 `forbidden`
5. 나머지 상태의 순서와 결과는 바꾸지 않는다. 413·403 의 몸통이 JSON 이 아니면 지금처럼 `bad_response` 다(1번 예외는 429 만)

### 3.3 하루 한도의 `{남은 시간}`

`retryAfter` 초에서 만든다. 시계를 읽지 않는다 — 서버가 "다음 UTC 자정까지 남은 초, 올림" 을 보낸다(F-2024 3.4). 순수 함수라 단위 테스트로 판정한다

규칙: 전체 분 = `retryAfter / 60` 올림(최소 1). 시 = 전체 분 ÷ 60 의 몫, 분 = 나머지

| 시 | 분 | 모양 |
| --- | --- | --- |
| > 0 | > 0 | `{시}시간 {분}분` |
| > 0 | 0 | `{시}시간` |

### 3.4 `CliErrorCode`·`CliErrorDetails` (계약 — `output.ts`)

```ts
export type CliErrorCode =
  | /* 기존 20개 그대로 */
  | 'rate_limited'        // 8
  | 'doc_quota_exceeded'  // 7
  | 'account_blocked'     // 4

export type CliErrorDetails = {
  /* 기존 필드 그대로 */
  scope?: 'minute' | 'day'
  retryAfter?: number
  resource?: 'bytes' | 'docs'
}
```

- 코드 이름은 서버 `error` 문자열과 같다(F-2024 3.4). F-2021 4.5 는 CLI 코드와 서버 코드를 같은 이름으로 둔다(`conflict`·`locked`·`too_large`·`quota_exceeded`)
- `EXIT_CODES` 는 `Record<CliErrorCode, number>` 라 세 줄을 빼먹으면 타입 검사가 실패한다(`npm run typecheck:cli`)

## 4. `--json` 오류 줄

`CliErrorJson` 에 세 필드를 더한다 (계약 — F-2021 4.4 에 더하는 것):

```ts
export type CliErrorJson = {
  /* 기존 필드 그대로: error, status, message, field?, limit?, used?, email?, expiresAt?, currentVersion? */
  scope?: 'minute' | 'day'   // 429
  retryAfter?: number        // 429 — 3.2 로 정한 초. 서버가 안 보냈어도 늘 있다(60)
  resource?: 'bytes' | 'docs' // 413 doc_quota_exceeded
}
```

- 규칙은 기존과 같다 — `details` 에 값이 있을 때만 싣는다. `rate_limited` 는 `scope`·`retryAfter` 가 늘 있고 `limit` 은 서버가 보냈을 때만. `doc_quota_exceeded` 는 `resource`·`used`·`limit` 이 서버가 보냈을 때만
- `account_blocked` 는 새 필드가 없다(`{ error, status: 403, message }`)
- `--json` 이어도 오류는 표준 오류로 간다(F-2021 4.4). 바꾸지 않는다

예 (단위 테스트의 기대값):

| 서버 응답 | `--json` 표준 오류 한 줄 |
| --- | --- |
| 429 `{ error: 'rate_limited', scope: 'minute', limit: 120, retryAfter: 60 }` | `{"error":"rate_limited","status":429,"message":"요청이 너무 많습니다. 60초 뒤 다시 시도하세요.","limit":120,"scope":"minute","retryAfter":60}` |
| 429 몸통 없음, 헤더 없음 | `{"error":"rate_limited","status":429,"message":"요청이 너무 많습니다. 60초 뒤 다시 시도하세요.","scope":"minute","retryAfter":60}` |
| 429 `{ …, scope: 'day', limit: 5000, retryAfter: 32400 }` | `{"error":"rate_limited","status":429,"message":"오늘 쓰기 한도(5000번)를 다 썼습니다. 약 9시간 뒤 풀립니다.","limit":5000,"scope":"day","retryAfter":32400}` |
| 413 `{ error: 'doc_quota_exceeded', resource: 'docs', used: 10000, limit: 10000 }` | `{"error":"doc_quota_exceeded","status":413,"message":"문서 수가 한도에 이르렀습니다 (10000 / 10000개).","limit":10000,"used":10000,"resource":"docs"}` |
| 403 `{ error: 'account_blocked' }` | `{"error":"account_blocked","status":403,"message":"이 계정은 운영자가 쓰기를 막았습니다. 읽기만 할 수 있습니다."}` |

- 키 순서는 판정하지 않는다(`toEqual`). 위 줄은 읽기 쉽게 적은 것이다

## 7. 요구사항 정리

- 새 응답을 받아도 **아무것도 다시 보내지 않는다.** 요청 수는 지금과 같다(`put --force` 는 2회, 나머지 1회)
- 새 분기는 `/v1` 경로와 메서드를 가리지 않는다. 읽기(`GET`)가 429 를 받는 일은 서버 규칙상 없지만(F-2024 1.2 — 쓰기만 센다), WAF 규칙이 IP 로 걸면 생길 수 있다 — 그때도 같은 종료 8
- `login`·`whoami` 가 `GET /v1/me` 에서 429 를 받아도 같은 분류다. `login` 은 이미 `emitError(deps, false, err)` 로 사람용 문구를 쓴다 — 바꾸지 않는다
- 새 분기는 `main.ts` 를 고치지 않고 흐른다 — `emitError` 가 `err.code` 로 종료 코드와 문구를 고른다

## 13. 확인한 것과 가정

### 13.1 코드를 읽거나 돌려 확인한 것

- 0.1.0 이 새 응답에 하는 것 — 머리말 표(0.1.0 태그 코드를 실제로 돌림)
- npm 공개 판 `0.1.0` 하나, 태그 `cli-v0.1.0` 하나 — `npm view`·`git tag`
- 0.1.0 과 HEAD 의 `client.ts`·`output.ts` 가 같다 — `git diff --stat cli-v0.1.0 HEAD -- cli/`
- F-2023 은 운영에 배포됨, F-308·F-2033 은 아님 — `git merge-base --is-ancestor … origin/deploy`
- 423 이 `/v1` PUT 에 아직 있다 — `worker/v1.ts` `handleUpdateDocV1` 의 `getActiveLock` 분기
- `forbidden_origin` 403 은 `/api/` 에만 — `worker/index.ts` 의 `url.pathname.startsWith('/api/') && needsOriginCheck(…)`. CLI 는 `/v1` 만 부르므로 이 403 을 받지 않는다
- `main.ts` `emitError` 가 코드 → 종료·문구를 `output.ts` 에 맡긴다 — `main.ts` 를 고칠 필요가 없다
- `client.test.ts` 에 413·429 단언이 없다 — `grep`

### 13.2 가정으로 남긴 것

- F-2024 3.4 의 몸통 모양(`scope`·`limit`·`retryAfter`·`resource`·`used`)이 F-2025·F-2026·F-2028 구현에서 그대로 나온다고 본다. 서버 코드는 아직 없다
- F-2024 9장 Q1 시험 결과(`specs/notes.md` "2026-09-24 — Rate Limiting 바인딩 시험", 커밋 `59de487`)는 "이 계정에서 바인딩이 배포·동작함" 이다. 그래서 WAF(몸통 없는 429)로 갈 가능성은 낮아졌지만 F-2026 명세는 아직 없다. 몸통 없는 429 분기(3.2 1번)는 WAF 가 아니어도 프록시·플랫폼이 내는 429 를 받기 위해 남긴다. 그런 429 에 `Retry-After` 가 붙는지는 모른다 — 없으면 60초로 떨어진다
- `put --force` 재실행 `5,5,5,5,0` 은 메인이 전한 F-308 구현 보고 값이다. 이 명세 작성 중 다시 돌리지 않았다
- 운영 웹에서 0.2.0 `login` 이 실제로 되는지는 돌려 보지 않았다 — 배포 여부만 git 으로 봤다(사람 확인 H381)
