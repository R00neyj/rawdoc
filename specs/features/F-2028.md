
- 바인딩: `?1` = `utcDay(Date.now())`(`worker/usage.ts`, UTC `YYYY-MM-DD`), `?2` = `SIGNUP_DAILY_LIMIT`. SQLite `date('now')` 를 쓰지 않는 이유는 F-2025 5.1 과 같다 — 가짜 시계로 시험하려고
- 실행: `env.DB.prepare(문장).bind(…).run()` 한 번. **batch 가 아니다** — 문장 하나라 원자적이다(측정 e)
- 판정: 결과 `meta.changes === 1` 이면 `undefined`(통과), 아니면 `{ error: 'signup_closed' }` — `errorDescription` 은 넣지 않는다. better-auth 가 `message` 로 `error` 값을 써서 `error_description=signup_closed` 가 붙는다(`validate-user-info.mjs`, 측정 a)
- 던지면(D1 오류) **잡지 않는다.** better-auth `assertValidUserInfo` 가 잡아 `validation_failed` 로 막는다 — 통과시키지 않는다(F-2024 4.1 3번, 측정 b). `/login` 은 표에 없는 코드라 마지막 줄 `로그인하지 못했습니다. 잠시 뒤 다시 시도해 주세요.` 를 보인다
- `validateUserInfo` 의 순서(이메일 인증 검사 → `create-user` 일 때만 `admitNewUser`)는 F-2033 이 이미 만들었다(`authOptions`). 이 명세는 `admitNewUser` 본문만 채운다. 그래서 인증 안 된 이메일·다시 로그인·둘째 제공자 연결은 자리를 쓰지 않는다

### 4.2 판정 자리 — `resolveDocAccess` 가 역할을 낮춘다

**계약** (`worker/access.ts`):

```ts
export interface DocAccess<T extends DocRowLike> {
  role: Role
  doc: T
  blocked?: true   // 막힘 때문에 role 이 'owner'·'edit' 에서 'view' 로 낮아졌을 때만 있다 (F-2028)
}
```

**규칙** (`resolveDocAccess(env, doc, user)` — 모양·인자는 그대로):

1. 지금 규칙대로 기본 역할을 정한다(소유자 / 문서·폴더 초대 중 높은 것 / 없음)
2. 기본 역할이 없음 → `null`, `view` → 그대로. **이 두 경우는 사용량을 읽지 않는다**
3. 기본 역할이 `owner`·`edit` 이면 막힘을 본다 — 먼저 **보낸 사람**: `usageOf(env, user).blockedAt !== null`(`user.usage` 가 있으면 D1 을 읽지 않는다). 막혔으면 곧바로 4 번. 아니고 `doc.owner_id !== user.id` 면 **소유자**: `readUsage(env, doc.owner_id).blockedAt !== null`
4. 둘 중 하나라도 막혔으면 `{ role: 'view', doc, blocked: true }`. 아니면 지금처럼 `{ role, doc }` — `blocked` 키를 두지 않는다
- 사용량 행이 없으면(`readUsage` 가 `EMPTY_USAGE`) 안 막힌 것으로 본다
- `usageOf`·`readUsage` 는 F-2025 `worker/usage.ts` 의 것 — **새 SQL 이 없다.** 읽는 문장은 F-2025 5.1 "사용량 읽기" 그대로(측정 g: 읽기 1행)

**왜 역할을 낮추나** (12장 Q1):

- **재검증이 저절로 따라온다.** `DocRoomCore.revalidateConnections` 는 `resolveDocAccess` 결과가 `edit` 미만이면 `4403 revoked` 로 닫는다(F-304 A18 "보기·권한 없음 연결만 4403 revoked"). F-2027 이 막 고친 `docRoomCore.ts` 를 건드리지 않고 7 번 경로가 닫힌다
- **`/ws` 연결도 저절로.** `resolveDocSocket` 이 `edit` 미만이면 `4403 forbidden` — 6 번이 코드 변경 없이 닫힌다
- **읽기는 그대로.** `view` 는 읽기에 충분하다 — `handleGetDoc`·`handleGetAttachment`(`?doc=`)·`checkOwnedTarget`(403/404 가름) 모두 `access` 가 `null` 인지만 보거나 `edit` 이상을 요구한다. `handleGetDoc` 응답에 `role` 은 없다(`rowToDoc`). F-2024 결정 10 "본인 읽기·내보내기 허용"·Q4 "남은 읽기 허용" 과 같은 뜻이다
- **`blocked` 표시가 있어야 403 몸통을 가른다.** 역할만 낮추면 1·2·4 번이 지금의 403 `forbidden` 을 준다. 웹은 `forbidden` 을 받으면 그 문서의 대기 편집을 **모두 버린다**(F-2030 2장 표 "403 `account_blocked` | `updateDoc` → `forbidden`" 행). `account_blocked` 를 받아야 F-2030 4.4 대로 항목을 남기고 `/api/me` 로 누구의 차단인지 확인한다
- `blocked` 는 **낮춘 경우에만** 붙는다. 원래 `view` 인 사람은 소유자가 막혀도 지금처럼 `forbidden` 을 받는다 — 쓸 수 없던 사람에게 소유자 차단을 알릴 까닭이 없다

**D1 읽기 비용** (측정 g: `readUsage` 한 번 = 읽기 1행)

| 부르는 곳 · 사용자 | 기본 역할 | 추가 읽기 |
| --- | --- | --- |
| HTTP 요청(`/api`·`/v1`)·`/ws` 연결 — 세 인증 경로가 `usage` 를 채운다(F-2025 4.3) | `owner` | **0** |
| 같음 | `edit` (남의 문서) | 1 (소유자) |
| 같음 | `view`·없음 | 0 |
| DO 재검증 — 연결 상태에 사용량이 없다(`{ id, email }`) | `owner` | 1 (본인 = 소유자) |

- 편집 권한자의 `GET /api/docs/:id`·`/v1/docs/:id`·`GET /api/attachments/:idext?doc=` 도 1행 는다 — 읽기인데도 판정이 한 자리라 그렇다. 공유받은 문서를 읽는 경로라 드물다
- 편집 권한자의 늘리는 PUT 은 F-2025 가 이미 소유자 `readUsage` 를 한 번 부른다(`handleUpdateDoc`·`handleUpdateDocV1` 의 총량 검사) — 같은 행을 한 번 더 읽는다(읽기 +1). 한 번으로 합치려면 `DocAccess` 에 소유자 사용량을 싣는 계약이 하나 더 는다. 하지 않는다
- 재검증은 편집이 이어지는 방에서 60초에 한 번이다(`REVALIDATE_INTERVAL_MS`). 연결 10개 방이면 1분에 최대 20행

## 5. 공개 경로 404 — 전수

### 5.1 한 함수로 모은다 — `worker/links.ts`

**계약:**

```ts
// worker/links.ts
export type PublicLinkRow = { token: string; owner_id: string; target_type: 'doc' | 'folder'; target_id: string; created_at: number; revoked_at: number | null }
export async function findPublicLink(env: Env, token: string): Promise<PublicLinkRow | null>
```

문장(글자까지 계약 — 테스트가 본다):

```sql
SELECT * FROM share_links WHERE token = ? AND revoked_at IS NULL AND NOT EXISTS (SELECT 1 FROM users WHERE users.id = share_links.owner_id AND users.blocked_at IS NOT NULL)
```

- **링크 소유자**(`share_links.owner_id`)가 막혔으면 "없는 링크" 와 같이 `null`. 링크 행·묶음(`share_link_docs`)은 지우지 않는다 — 풀면 같은 주소가 다시 열린다(F-2024 4.2 끝)
- `NOT EXISTS` 를 고른 이유: 소유자 사용자 행이 없는 링크(있을 수 없지만)도 지금처럼 보인다 — `readUsage` 가 행이 없으면 안 막힘으로 보는 것과 같은 규칙. `JOIN` 모양은 읽기가 같고(측정 f: 둘 다 2행) 행이 없으면 숨긴다
- 앞부분이 지금 문장 `SELECT * FROM share_links WHERE token = ? AND revoked_at IS NULL` 과 같다 — 앞부분으로 가르는 기존 가짜 D1(`links.test.ts`·`publicPage.test.ts`)이 그대로 맞는다(10장)
- 토큰 모양 검사(`isValidToken`)는 지금처럼 각 핸들러가 **먼저** 한다 — 모양이 틀리면 D1 을 읽지 않는다
- `target_type` 검사도 지금처럼 각 핸들러 몫이다

## 7. `/api/me`·`/v1/me` — `blocked`·`warned`

### 7.1 계약

```ts
// GET /api/me (handleApiMe), GET /v1/me (handleMe) — 200 몸통
type MeBody = { id: string; email: string; blocked: boolean; warned: boolean }

// worker/v1Contract.ts
export type V1Me = { id: string; email: string; blocked: boolean; warned: boolean }
// V1_EXAMPLES.me = { id: 'user-1', email: 'a@b.com', blocked: false, warned: false }
```

- `blocked` = 사용량의 `blockedAt !== null`, `warned` = `warnedAt !== null`. 사용량은 `usageOf(env, user)` — 세 인증 경로가 `usage` 를 채우므로 운영에서 추가 D1 읽기 0. 흉내 낸 사용자처럼 `usage` 가 없을 때만 1행
- **`warned` 는 원래 값 그대로다** — `blocked` 가 참이어도 `warned` 를 거짓으로 바꾸지 않는다. 둘 다 참이면 L5 만 띄우는 것은 웹 몫이다(F-2030 5.3 `planAccountNotices`, A3). 서버가 가리면 운영자가 `admin-unblock` 한 순간 L7 이 다시 보여야 하는데, 원래 값이면 그것이 저절로 된다
- `warned` 의 뜻: 운영자가 `admin-warn` 으로 이 계정에 주의를 보냈다. 쓰기를 막지 않는다. 사용자가 봤는지 서버는 기록하지 않는다(F-2024 4.4). `admin-warn --clear` 로만 거짓이 된다 — 시간이 지나 저절로 풀리지 않는다
- 401 몸통·연장 쿠키(`handleApiMe` 의 `Set-Cookie`)는 그대로
- 값은 늘 새 값이다: 세션 조회는 쿠키 캐시를 쓰지 않는다(`session.mjs` — `cookieCache.enabled === true` 일 때만, `authOptions` 에 없다). 토큰·개발 우회도 요청마다 `users` 를 읽는다. `admin-block` 뒤 다음 `/api/me` 가 `blocked: true`

## 8. `/v1` 안쪽 두 번 인증 — 이 명세가 받는다 (F-2026 Q2)

- **문제**(F-2026 6장 끝): `handleCreateDocV1` 은 `handleCreateDoc` 을, `handleUpdateDocV1` 폴백은 `handleUpdateDoc` 을 **새 `Request`**(`jsonRequest`)로 부른다. `rememberUser` 의 열쇠가 `Request` 객체라 안쪽 핸들러가 토큰 인증을 다시 한다 — `api_tokens` 1행 + `users` 1행 읽기
- **규칙:** 두 곳 모두, 바깥 핸들러가 `requireUser` 로 받은 사용자를 새 `Request` 에 `rememberUser` 로 옮긴 뒤 안쪽 핸들러를 부른다. `jsonRequest` 의 모양은 그대로
- 효과: `POST /v1/docs` 한 번의 토큰 조회 문장(`SELECT id, user_id, last_used_at FROM api_tokens …`)이 2 → **1**(관문 ① 한 번). 폴백 PUT 도 같다
- 이 명세에서 받는 이유: `v1.ts` 를 어차피 고친다(4.3). 한 호출씩 두 자리라 작다
- 대가: `v1.test.ts` 의 `vi.mock('./auth')` 가 `rememberUser` 를 내보내야 한다(10장)

### 10.2 테스트 전용 도우미 — `worker/testD1.ts` `asAuthDb`

```ts
// worker/testD1.ts — 테스트 전용
export function asAuthDb(db: DatabaseSync): DatabaseSync
```

- **받은 `DatabaseSync` 객체를 그대로 돌려준다**(같은 객체). 그 객체의 `prepare` 결과 문장에 D1 모양 `bind(...args)` 를 덧붙이고, `bind` 는 `first`·`all`·`run`(`asD1` 과 같은 결과 모양)을 가진 문장을 돌려준다. `batch` 는 두지 않는다
- 왜 이 모양인가: better-auth(kysely-adapter `createKyselyAdapter`)는 `DatabaseSync` 인스턴스면 node:sqlite 방언을 고르지만, 객체에 `batch`·`exec`·`prepare` 가 모두 있으면 D1 방언으로 **덮어쓴다**. `DatabaseSync` 에는 `exec` 가 이미 있으므로 `batch` 를 두면 안 된다. 그렇게 해서 better-auth 는 지금처럼 node:sqlite 로, 우리 코드(`admitNewUser`)는 D1 한 문장 모양으로 같은 DB 를 쓴다(측정 i)
- 두 번 불러도 한 번만 감싼다
- 운영 코드는 import 하지 않는다(`testD1.ts` 머리 규칙 그대로)
- 다른 안: 테스트마다 `authOptions(env, db, admit)` 로 better-auth 를 직접 만들어 `env.DB` 와 better-auth DB 를 가른다(측정 a 방식). `getAuth(env)` 를 지나는 `loginRoutes.test.ts`·`auth.test.ts` 에서는 쓸 수 없다 — `getAuth` 가 `env.DB` 하나를 둘 다에 넘긴다

## 14. 기존 명세·코드와 부딪치는 것, 그리고 가정

**부딪치는 것**

- **F-2024 4.2 "재검증 최대 60초"** — 재검증은 flush 끝에서만 돌아 실제로는 편집이 이어질 때 최대 약 90초다(6.2). 13장
- **F-2024 6장이 `worker/docSocket.ts` 를 주요 파일로 적었다** — 4.2 로 코드 변경이 필요 없다. 13장
- **F-2024 6장 F-2028 행에 없는 파일이 는다** — `docs.ts`·`locks.ts`(4.3), `v1Contract.ts`(7장), 테스트 여럿(10장). F-2024 는 "주요 파일" 이라 적었고 F-2025·F-2026 도 같은 이유로 늘렸다
- **F-2033 의 테스트들이 `env.DB` 에 `DatabaseSync` 를 넣는다** — 운영에서는 D1 하나를 better-auth 와 우리 코드가 함께 쓰지만, 테스트는 better-auth 가 받는 `DatabaseSync` 를 그대로 `env.DB` 에 두어 `admitNewUser` 가 채워지는 순간 새 사용자 테스트가 모두 깨진다(10.1). F-2033 이 `admitNewUser` 를 늘 `undefined` 로 둔 동안에는 드러나지 않았다
- **F-2027 은 `/v1` PUT 이 "Worker 관문(F-2028)을 지나 DO 에 닿으면" 을 가정했다**(F-2027 5.3 끝) — 이 명세의 자리는 관문(`writeGate.ts`)이 아니라 핸들러 `handleUpdateDocV1` 이다(4.3). 동작은 F-2027 의 가정과 같다(Worker 가 먼저 403, DO 를 부르지 않음)
- **F-2029 12장 "F-2028 이 초로 읽으면 어긋난다"** — 이 명세는 `NULL` 여부만 본다. 부딪침 없음

**가정 (확인하지 않았다)**

- 원격 D1 의 관문 문장 원자성과 행 계산 — 로컬 workerd D1 에서만 쟀다(측정 d·e·f·g)
- 원격 better-auth 콜백이 로컬 흉내와 같은 `Location` 을 준다는 것 — 소스(`callback.mjs` `redirectOnError`)와 node 흉내(측정 a·b)로만 확인했다
- 원격에서 `validateUserInfo` 가 던질 때 better-auth 로거가 남기는 줄의 모양 — 로컬은 `console.error` 1번
- 재검증 최대 약 90초는 코드 상수로 계산한 값이다. DO 를 원격에서 돌려 재지 않았다
- 11장 ① 의 로컬 OAuth App 이 이 PC 에 준비돼 있는지 — 확인하지 않았다(F-2032 2.6 절차)
