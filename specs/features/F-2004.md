### 2.1 이 커밋이 끝난 시점의 상태

1. **연결이 많은 문서가 눈에 띄게 크다.** 고립 문서(반지름 3.0)와 연결 1개(5.2)가 1.7배, 허브(최대 20.6)와는 6.9배다
2. **덩어리에 앞뒤가 생긴다.** 카메라에서 먼 노드일수록 바탕색 쪽으로 섞여 옅어지고, 회전하면 앞뒤가 실시간으로 뒤집힌다
3. **노드에 마우스를 올리면 그 문서와 이어진 문서들의 이름표가 뜬다.** 회전·이동·확대를 해도 이름표가 노드에 붙어 따라다닌다
4. 현재 문서는 `--accent`, 끊긴 링크는 `--muted`, 공유받아 본문을 못 읽은 문서는 `--ink-2` 다
5. 끊긴 링크 노드를 우클릭(터치는 길게 누르기)하면 `이 제목으로 새 문서` 한 항목짜리 메뉴가 뜬다

**쓸 만한가 — 판단.** 쓸 만하다. F-2003 이 "덩어리를 손으로 돌린다"를 만들었고 이 커밋이 그 덩어리에 **정보**를 넣는다. 남는 아쉬움은 노드를 끌 수 없는 것(F-2009)과 설정 패널이 없는 것(F-2005)뿐이다.

### 2.2 노드 끌기를 F-2009 로 빼는 이유 (2026-09-22 사용자 결정)

F-292 9장 로드맵의 F-2004 행에는 `노드 끌기 재가열` 이 들어 있었다. **뺀다.**

- **F-2003 이 좌클릭 끌기를 이동(pan)으로 가져갔다.** 그래서 노드 끌기는 `pointerdown` 시점의 레이캐스트로 "노드에서 시작했나"를 갈라야 하고, 화면에 평행한 평면 위의 world 좌표를 매 `pointermove` 마다 풀어야 하고, `fixNode`/`releaseNode`/`reheat` 로 시뮬레이션을 다시 깨워야 하고, 터치에서는 이미 `enableRotate = false` 로 잠가 둔 제스처(F-2003 5.2)와 겹친다. **그것만으로 한 덩어리다**
- F-2004 는 그것 없이도 `mapNodeStyle.ts`(순수·TDD) + `MapLabels.tsx`(새 DOM 레이어·호버 레이캐스트·매 프레임 투영) + 깊이 섞기로 F-2002 급이다
- **F-2009 를 F-292 9장 로드맵 표에 새 행으로 더한다** — F-2005~F-2008 뒤, 선행 F-2004, 누가 = 메인 (16장 갱신 대상)
- F-2003 6.3 이 F-2004 앞으로 남긴 쪽지("노드를 끌면 좌표가 바뀌므로 끄는 동안 `posDirty = true` 를 세워야 한다")도 **F-2009 몫**이다. 이 명세는 `posDirty` 규칙을 그대로 둔다

## 3. `src/lib/mapNodeStyle.ts` — 내보내는 것이 전부다

테스트 환경이 `node` 다(`vite.config.ts` 227행 `environment: 'node'`). **three 도 DOM 도 import 하지 않는 순수 모듈이어야 단위 테스트가 된다** — `mapCamera.ts`(F-2003 7.5)·`cssColor.ts`(F-2002)와 같은 규칙이다.

```ts
// 지도 노드 크기·깊이·이름표 판정 (specs/features/F-2004.md 3장)
// three 를 import 하지 않는 순수 모듈이다 — 테스트 환경이 node 라 이 규칙이 곧 테스트 가능성이다
import type { Rgba } from './cssColor'

export const MAP_NODE_BASE_RADIUS = 3
export const MAP_NODE_DEGREE_COEF = 2.2
export const MAP_NODE_DEGREE_CAP = 64
export const MAP_MISSING_RADIUS = 3
export const MAP_MAX_LABELS = 60
export const MAP_DEPTH_MIX_MAX = 0.65

export function nodeRadius(degree: number, missing: boolean, scale?: number): number

export function depthMix(distance: number, near: number, far: number, maxMix?: number): number

export function blendRgb(base: Rgba, target: Rgba, t: number, out: [number, number, number]): void

export function pickLabelNodes(
  pinned: readonly number[],
  candidates: readonly number[],
  degreeOf: (index: number) => number,
  max?: number,
): number[]

export type ScreenPoint = { x: number; y: number; visible: boolean }

export function ndcToScreen(
  ndcX: number, ndcY: number, ndcZ: number,
  cssWidth: number, cssHeight: number,
  out: ScreenPoint,
): ScreenPoint

export function screenRadius(worldRadius: number, distance: number, cssHeight: number, tanHalfVFov: number): number
```

| 함수 | 정의 | 왜 이 값인가 |
| --- | --- | --- |
| `nodeRadius` | `missing` 이면 `MAP_MISSING_RADIUS × scale`. 아니면 `d = clamp(degree, 0, 64)`(유한수가 아니면 0), `(3 + 2.2·√d) × scale`. `scale` 기본 `1` | F-292 6.1·결정 8. **끊긴 링크는 degree 와 무관하게 3.0 고정**이라 분기가 함수 안에 있어야 호출부가 두 번 판단하지 않는다 |
| `depthMix` | `span = far - near`; `span <= 0` 이면 `0`; 아니면 `clamp01((distance - near) / span) × maxMix`. `maxMix` 기본 `0.65` | F-292 6.1. **`span <= 0` 이 노드 하나짜리 그래프**다 — B5 가 요구하는 "원색" |
| `blendRgb` | `out[k] = base[k] + (target[k] - base[k]) × t` 를 세 채널. 알파는 버린다 | sRGB 좌표에서 섞는다. `tokens.css` 가 쓰는 `color-mix(in srgb, …)` 와 같은 공간이라 화면의 다른 색과 어긋나지 않는다 (`design.md` 3.2) |
| `pickLabelNodes` | `pinned` 를 순서대로 중복 없이 담고(`max` 까지), 남는 자리에 `candidates` 중 아직 안 담긴 것을 **`degreeOf` 내림차순, 같으면 인덱스 오름차순**으로 담는다 | F-292 6.2 "동시 최대 60개, 넘으면 `degree` 큰 순". `pinned` 는 호버한 노드다 — 이웃이 60개를 넘어도 **자기 이름표는 반드시 보인다**. **F-2005 가 `이름표 표시 거리` 안쪽 노드를 `candidates` 에 더하기만 하면 되도록** 두 배열로 갈랐다 |
| `ndcToScreen` | `x = (ndcX·0.5 + 0.5)·cssWidth`, `y = (-ndcY·0.5 + 0.5)·cssHeight`, `visible = ndcZ >= -1 && ndcZ <= 1 && 0 <= x <= cssWidth && 0 <= y <= cssHeight`. `out` 에 써서 돌려준다 | 7.6 이 실측으로 정한 판정이다. **`out` 을 받는 이유는 프레임마다 60개를 만들지 않기 위해서다** (F-2002 6.6 재사용 버퍼 규칙) |
| `screenRadius` | `distance <= 0` 이면 `0`; 아니면 `worldRadius · cssHeight / (2 · distance · tanHalfVFov)` | 이름표를 노드 **아래**에 붙이려면 그 노드가 화면에서 얼마나 큰지 알아야 한다 (7.4). 시야 축 위의 점에 대한 정확식이고 가장자리에서는 근사다 — 이름표 위치라 그 정도면 된다 |

- **내보내는 것은 위가 전부다.** 상수 6개 + 함수 6개 + 타입 1개
- `Rgba` 는 `import type` 이라 런타임 의존이 0이다 (`cssColor.ts` 4행)
- 단위 테스트는 14.1 U1~U8

## 4. 노드 크기

### 4.1 무엇을 갈아끼우나

`MapScene.tsx` 44~45행의 상수 둘이 사라진다.

```
- const NODE_RADIUS = 6.0
- const MISSING_RADIUS = 3.0
```

169행의 채우기가 공식으로 바뀐다. F-2002 6.6 이 `radii` 를 **배열로** 잡아 둔 덕에 한 줄이다.

```ts
for (let i = 0; i < nodeCount; i++) {
  const node = graph.nodes[i]
  radii[i] = nodeRadius(node.degree, node.missing, NODE_SCALE)
}
```

- `NODE_SCALE` 은 `1.0` 상수다. **F-2005 가 이것을 prop 으로 바꾼다** (2장)
- `graph.nodes[i].degree` 는 `buildWikiGraphFromEntries` 가 이미 채운다 (`wikiGraph.ts` 173~176행 — **나가는 간선과 들어오는 간선을 둘 다 센다**). 끊긴 링크 노드도 `degree` 를 갖지만 `nodeRadius` 가 무시한다
- `radii` 는 **열 때 한 번만** 채운다. `degree` 는 그래프가 다시 만들어질 때만 바뀌고 그러면 장면째 다시 만들어진다 (effect (a))

### 4.2 `maxNodeRadius` 가 커지는 것이 카메라 맞춤에 주는 영향 — 무시해도 된다

F-2003 7.2 가 `fit()` 의 `r` 을 `bounds.radius + maxNodeRadius` 로 정했고, `maxNodeRadius` 는 `radii` 의 최댓값이다(171~172행). 공식이 들어오면 이 값이 **6.0 고정에서 3.0~20.6 으로** 움직인다.

| 상황 | `bounds.radius` | `maxNodeRadius` | `r` | 비교 |
| --- | --- | --- | --- | --- |
| 첫 실행 (노드 1개, degree 0) | 0 | **6.0 → 3.0** | 6.0 → **3.0** | 카메라 거리가 절반이 된다. **화면 그림은 똑같다** — 11장이 계산한다 |
| 문서 수십 개 (허브 degree 4) | 약 200 | 6.0 → **7.4** | 206 → **207.4** | +0.7% |
| 노드 1,000 (허브 degree 64 이상) | 약 1,200 | 6.0 → **20.6** | 1,206 → **1,220.6** | +1.2% |

- **큰 그래프에서는 1% 안쪽이라 눈에 안 보인다.** `bounds.radius` 가 `linkDistance`(기본 120)에 끌려 수백~수천이라 노드 반지름 20.6 은 끼어들 자리가 없다
- **노드 하나짜리 그래프에서만 눈에 띄게 달라지는데, 그것도 화면에서는 같다** (11장). `mapCamera.ts` 는 한 줄도 안 고친다

### 4.3 왜 `degree` 에 상한을 두나

F-292 6.1 의 `min(degree, 64)` 를 그대로 쓴다. 64 를 넘는 노드는 이미 화면에서 가장 큰 점이고 더 키우면 주변 노드를 가린다. **상한을 `mapNodeStyle.ts` 안에 두는 것이 중요하다** — 호출부가 `Math.min` 을 잊으면 허브 하나가 화면을 덮는데 그건 눈으로만 잡힌다.

## 5. 깊이 섞기

### 5.1 무엇을 어떻게

F-292 6.1·결정 9 를 그대로 푼다.

1. 프레임마다 카메라와 **각 노드 중심** 사이의 거리를 잰다
2. 그 프레임의 **가장 가까움(`near`)·가장 멂(`far`)** 을 그 거리들의 최소·최대로 잡는다
3. `t = depthMix(d, near, far)` — 가장 가까운 노드는 `0`, 가장 먼 노드는 `0.65`
4. 그 노드의 **base 색**을 `--panel` 쪽으로 `t` 만큼 섞어 `setColorAt` 한다

- **경계구를 다시 계산하지 않는다.** F-292 6.1 은 "현재 그래프 경계구의 [가장 가까움, 가장 멂]"이라고 적었는데, **경계구 기준으로 잡으면 카메라가 덩어리 안에 들어갔을 때(`minDistance` 가 `맞춤` 거리의 0.05배라 들어갈 수 있다, F-2003 7.5) 뒤쪽 절반이 범위 밖으로 나간다.** 실제 노드 거리의 최소·최대를 쓰면 언제나 [0, 0.65] 를 꽉 채운다. 같은 뜻이고 더 안전한 구현이라 이렇게 적는다
- **`--panel` 과 섞는 이유**: 배경이 `--panel` 이다(`MapScene.tsx` 192행). 먼 노드가 배경으로 녹아드는 것이 곧 깊이다. 알파를 쓰지 않는 이유는 F-292 3.5(깊이 정렬 비용) 그대로
- **fog 를 쓰지 않는다** (F-292 결정 9)
- **그룹 색(F-2008)이 들어와도 이 설계는 그대로 선다.** 깊이 섞기는 노드마다 들고 있는 **base 색**을 섞을 뿐이고, 섞는 상대가 배경 하나라 그룹 사이 색상(hue) 차이는 유지된다 — fog 를 거부한 이유가 그대로 근거다

### 5.2 매 프레임 다시 쓴다 — 실측으로 정했다

깊이는 카메라 거리에 달려 있으므로 **회전할 때마다** 노드 1,000개의 `setColorAt` + `instanceColor` 업로드가 필요하다. F-2003 6.3 이 바로 그 종류의 매 프레임 업로드(`uploadPositions`)를 `posDirty` 로 끊어 G6 를 벌었으므로, 같은 걱정을 먼저 재고 결론을 냈다.

**2026-09-22 실측** — `three@0.186.0` 을 esbuild 로 묶어 설치된 Chrome(Playwright, 1600×900, `antialias: true`, `setPixelRatio` 2, RX 7600)에서 인스턴스 1,000개·간선 1,000개로 쟀다. `performance.now()` 가 0.1 ms 로 뭉개지므로 **200회 배치로 나눠** 재고 3회 중앙값을 적는다.

| 무엇을 | 중앙값 |
| --- | --- |
| **깊이 섞기 한 번**(최소·최대 훑기 + 1,000회 보간 + `setColorAt` + `needsUpdate`) | **0.0075 ~ 0.013 ms** |
| 노드 1,000개 `Vector3.project()` | 0.010 ~ 0.014 ms |
| `render()` 호출(CPU 쪽) | 0.003 ~ 0.006 ms |
| `render()` + `instanceColor.needsUpdate = true`(= 12 KB GPU 업로드) | 0.010 ~ 0.24 ms |
| 레이캐스트 한 번(`computeBoundingSphere()` 포함) | 0.10 ~ 0.17 ms |
| 그중 `computeBoundingSphere()` 만 | **0.049 ~ 0.072 ms** |

프레임 간격(rAF, 90프레임, 앞 3프레임 버림):

| 프레임마다 하는 일 | 평균 fps | 최악 프레임 |
| --- | --- | --- |
| 회전만 | 144~146 | 7.1~7.2 ms |
| 회전 + **깊이 섞기** | 144 | 7.1~7.4 ms |
| 회전 + 깊이 섞기 + 노드 1,000개 투영 | 144 | 7.1~7.2 ms |
| 회전 + 깊이 섞기 + 레이캐스트 | 144 | 7.1~7.3 ms |

- 이 기기는 144 Hz 라 **7.1 ms 는 vsync 간격 그 자체**다. 즉 네 조건이 전부 프레임 예산을 다 못 채운다
- **결론: 임계값을 두지 않고 그리는 프레임마다 다시 쓴다.** 0.0075~0.013 ms 는 F-2003 실측 최악 프레임 10~11 ms 가 33 ms 목표에 대해 남긴 **22 ms 여유의 0.06%** 다. "카메라가 일정 각도 이상 움직였을 때만" 같은 임계값은 **옅어짐이 계단으로 보이는 대가**를 치르면서 아무것도 못 번다
- `render + needsUpdate` 의 0.24 ms 는 vsync 없이 200회를 몰아칠 때만 나온 값이다(버퍼 교체 대기). 실제 프레임 루프에서는 위 표대로 회전만 할 때와 구분되지 않았다
- **`posDirty` 규칙은 그대로 둔다** (F-2003 6.3). 좌표 업로드는 `Matrix4.compose` 1,000회 + `Float32Array` 16,000개 쓰기로 색 업로드보다 훨씬 무겁고, 그것이 안 바뀐다는 판단은 여전히 맞다

### 5.3 프레임 루프의 정확한 자리

`MapScene.tsx` 296~331행의 `frame()` 에 **두 줄만** 끼운다.

```
frame():
  dirty = false
  … 기존 tick / fit / updateClip …
  controls.update()
  if (posDirty) { uploadPositions(); posDirty = false; boundsStale = true }
  applyDepth()                                   // ← 새로 넣는다 (5.1)
  placeLabels()                                  // ← 새로 넣는다 (7.5)
  renderer.render(scene, camera)
  if (layout.isSettled() && !dirty) { … 기존 정지 판정 … }
```

- **`posDirty` 블록 뒤여야 한다.** `applyDepth()`·`placeLabels()` 는 `posBuf` 를 읽는데 그 배열을 채우는 것이 `uploadPositions()` 다(`MapScene.tsx` 272행 `layout.readPositions(posBuf)`). 좌표가 바뀐 프레임에는 그 블록이 먼저 채워 주고, 안 바뀐 프레임에는 직전 값이 그대로 맞다
- **`controls.update()` 뒤여야 한다.** 그 전에는 `camera.position` 이 이 프레임 값이 아니다
- reduced-motion 경로에서 배치가 안 끝났으면 `frame()` 이 304행에서 먼저 `return` 한다 — 그릴 것이 없으니 깊이도 이름표도 계산하지 않는다. 그대로 둔다

## 6. 색 — 무엇을 무슨 색으로

### 6.1 base 색 표

`applyColors()` 가 **인스턴스 색을 직접 쓰지 않고 `baseColors`(`Float32Array(nodeCount × 3)`, sRGB 0~1)를 채운다.** 인스턴스에 쓰는 것은 `applyDepth()` 하나로 모은다.

| 대상 | base 색 | 판정 |
| --- | --- | --- |
| 끊긴 링크 | `--muted` | `node.missing` |
| **공유받아 본문을 못 읽은 문서** | **`--ink-2`** | `graph.unreadable` 에 그 `id` 가 있다 |
| 현재 문서 (`#/map/{id}` 의 그 문서) | `--accent` | `node.id === activeCenterId` |
| 그 밖 | `--ink` | |
| 간선 | `--rule` (지금 그대로) | 6.4 |

판정 순서는 **끊긴 링크 → 현재 문서 → 공유받음 → 기본** 이다. 현재 문서가 공유받은 문서일 수 있고 그때는 `--accent` 가 이긴다.

- `graph.unreadable` 은 문서 id 배열이다(`wikiGraph.ts` 103·178행). `truncateGraphByDegree` 가 자른 뒤에도 남은 노드 것만 걸러서 들고 온다(같은 파일 `induceSubgraph` 의 `unreadable` 필터). **`Set` 으로 한 번 만들어 `applyColors` 안에서 돌려 쓴다**
- `readTheme()` 이 읽는 토큰에 **`--ink-2` 를 더한다**(지금은 `--panel`·`--ink`·`--accent`·`--muted`·`--rule` 다섯, `MapScene.tsx` 91~99행). 프로브 방식은 F-2002 6.3 그대로

### 6.2 현재 문서는 깊이 섞기에서 뺀다

`applyDepth()` 에서 **현재 문서 노드만 `t = 0`** 으로 둔다(원색 `--accent` 유지).

- **이유 1 — 남은 표시가 그것뿐이다.** 6.3 이 바깥 링을 빼므로 현재 문서를 가리키는 표시가 색 하나다. 덩어리 뒤쪽에 있을 때 65% 씻기면 "먼 노드" 와 구분이 안 된다
- **이유 2 — 딱 한 노드다.** 나머지 999개가 깊이를 그대로 표현하므로 앞뒤 감각이 죽지 않는다
- **이유 3 — 뜻이 맞는다.** `#/map/{id}` 는 "이 문서를 보여 달라"는 주소다. 가장 진한 점이 그것인 편이 읽기 쉽다
- 반대쪽을 고르면 어떻게 되는지는 17장 Q2

### 6.3 바깥 링·테두리는 그리지 않는다 (2026-09-22 사용자 결정)

F-292 6.1 색 표는 현재 문서에 `--accent` **+ 바깥 링**, 공유받은 문서에 `--ink` **+ `--ink-2` 테두리**를 적었다. **색만 쓰고 링·테두리는 안 그린다.**

- 구체에 테두리를 두르려면 **조금 큰 구체를 뒤에 까는 두 번째 `InstancedMesh`** 가 필요하다 — 드로우 콜 +1, 인스턴스 2배, 깊이 정렬 문제. F-292 3.5 가 드로우 콜 1회를 설계의 근거로 삼았다
- 현재 문서는 이미 `--accent` 라 링 없이도 눈에 띄고(6.2 가 깊이 섞기에서까지 빼 준다), 공유받은 문서는 소수다
- **공유받은 문서는 `--ink` 대신 `--ink-2` 를 칠해 구분을 되살린다.** 화이트 테마에서 `--ink` 는 `#1c1b18`, `--ink-2` 는 `#4a4740` 이라 나란히 놓으면 보인다(`tokens.css` 19~20행). 꼬리 줄 `공유받은 문서 {N}개는 나가는 링크를 읽지 못했습니다.` 가 그 뜻을 말해 준다
- **정말 링·테두리가 필요한지는 사람 확인으로 판정한다** — 14.4 H-g

### 6.4 간선은 건드리지 않는다

지금 간선은 `LineBasicMaterial` 하나에 `--rule` 단색이다(`MapScene.tsx` 162·193행). F-292 6.1 의 `현재 문서에 닿는 간선은 --ink 30%` 는 **F-2005 로 미룬다**.

- 간선마다 색을 다르게 하려면 `vertexColors` 를 켜고 정점 색 버퍼를 하나 더 들어야 한다. 그런데 **F-2005 의 `표시 > 선 두께` 가 "WebGL `lineWidth` 가 무시되므로 간선 색의 진하기로 표현한다"**(F-292 6.6)라서 같은 재질을 다시 잡는다
- 한 커밋 안에서 두 번 고치지 않는다. 16장 갱신 대상에 올린다
- **간선에는 깊이 섞기도 넣지 않는다.** 같은 이유(단색 재질)이고, 노드에만 깊이가 있어도 앞뒤는 충분히 읽힌다 — 14.4 H-b 가 그것을 묻는다

## 7. 이름표 — `MapLabels.tsx`

### 7.1 무엇을 보이나 (F-292 6.2·결정 7)

- **평소 숨긴다**
- 노드에 마우스를 올리면 **그 노드와 직접 이어진 노드까지** 이름표를 띄운다. 이웃은 방향을 가리지 않는다(백링크도 이웃 — F-292 6.4 와 같은 규칙)
- 동시에 보이는 이름표는 **최대 60개**, 넘으면 호버한 노드 + `degree` 큰 순 (3장 `pickLabelNodes`)
- `이름표 표시 거리` 는 **0 고정**(호버할 때만). 슬라이더는 F-2005 몫
- 글꼴 `--font-sans`, 색 `--ink-2`, 크기 11px (F-292 6.2). 레이어 전체가 `aria-hidden="true"` (F-292 6.10)

### 7.2 React 에 무엇을 맡기고 무엇을 직접 쓰나 — 실측을 먼저 적는다

**2026-09-22 실측** — 절대 배치된 `<span>` 에 매 프레임 좌표를 넣을 때, (a) `el.style` 을 직접 쓰는 것과 (b) React 19 `useState` 로 배열을 통째로 갈아 끼우는 것을 나란히 쟀다(같은 Chrome, 120프레임, 3회).

| 이름표 수 | 직접 DOM (프레임 간격 / 그중 JS) | React state (프레임 간격) |
| --- | --- | --- |
| **60** | 144 fps · 최악 7.1~7.2 ms / JS 0~0.1 ms | 144 fps · 최악 7.1~7.2 ms |
| 600 | 144 fps · 최악 7.2~7.6 ms / JS 0.4~0.6 ms | 144 fps · **최악 8.9~10.9 ms** |

**정직하게 적는다: 상한인 60개에서는 두 방식의 프레임 간격이 구분되지 않았다.** 600개에서야 React 쪽 최악 프레임이 3~4 ms 길어진다. 그러니 **"React 가 느려서"가 아니라 아래 구조적인 이유로 직접 DOM 을 고른다.**

- **프레임 루프가 React 밖에 있다.** 그리기는 `buildScene()` 안의 명령형 클로저이고(`MapScene.tsx` 125~539행), 거기서 매 프레임 `setState` 를 부르면 **`MapScene` 컴포넌트가 프레임마다 다시 렌더된다.** 그러면 550행의 의존성 없는 effect 가 매 프레임 돌아 `inputs.current` 객체를 새로 만든다. F-2002 6.1 이 `inputs` ref 를 만든 이유가 정확히 "프레임 데이터를 React 밖에 둔다"였다
- **60 은 오늘의 상한이고 F-2005 가 `이름표 표시 거리` 로 그 상한을 늘 채우게 만든다.** 600 쪽 수치가 남의 일이 아니다

**그래서 이렇게 가른다.**

| 무엇 | 어디 | 언제 바뀌나 |
| --- | --- | --- |
| **보일 이름표 목록**(`{ id, title }[]`) | **React state** (`MapScene` 의 `useState`) | 호버한 노드가 바뀔 때만. 마우스를 노드 위에서 움직이는 동안에는 안 바뀐다 |
| **각 이름표의 화면 좌표와 보임 여부** | **ref 로 직접 DOM** (`el.style.translate`, `el.hidden`) | 프레임마다 |

### 7.3 `MapScene` 과 `MapLabels` 사이의 통로

```tsx
// MapLabels.tsx
export type MapLabelItem = { id: string; title: string }
export type MapLabelsHandle = { place(index: number, x: number, y: number, visible: boolean): void }
```

- `MapLabels` 는 `items` 를 받아 `<div class="map-labels" aria-hidden="true">` 안에 `<span class="map-label" hidden>` 을 그린다. **처음에는 전부 `hidden`** 이다 — 좌표가 들어오기 전에 왼쪽 위에 잠깐 뜨는 것을 막는다
- `useImperativeHandle` 로 `place` 하나만 내보낸다. `place(i, x, y, visible)` 는 `els[i]` 가 없으면 조용히 넘어가고, 있으면 `el.style.translate = \`${x}px ${y}px\`` 와 `el.hidden = !visible` 만 쓴다
- **`MapScene` 이 `MapLabels` 를 자기 자식으로 그린다.** `MapPage` 는 아무것도 모른다 — 이름표가 필요로 하는 것(그래프 인접 목록·카메라·레이캐스트)이 전부 `MapScene` 안에 있다

```tsx
// MapScene.tsx (컴포넌트 쪽)
const [labelItems, setLabelItems] = useState<MapLabelItem[]>([])
const labelsRef = useRef<MapLabelsHandle | null>(null)
…
<div className="map-scene" ref={wrapperRef}>
  <canvas … />
  <MapLabels ref={labelsRef} items={labelItems} />
  <span className="map-probe" aria-hidden="true" ref={probeRef} />
</div>
```

- `buildScene(...)` 에 **인자 둘을 더한다** — `labelsRef` 와 `setLabelItems`. `useState` 의 setter 는 **React 가 신원 유지를 보장**하고 `buildScene` 은 `[graph]` 가 바뀔 때만 도니 `inputs` ref 에 넣지 않고 그냥 넘긴다
- 장면 쪽은 `labelIndices: number[]` 를 클로저에 들고 있는다. `setLabelItems` 에 넘긴 배열과 **같은 순서**라 `place(i, …)` 의 `i` 가 그대로 맞는다
- **React 가 커밋하기 전 한 프레임은 `els[i]` 가 비어 있다.** 그 프레임은 아무것도 안 그리고 넘어간다. 그래서 **effect 를 하나 더 둔다** — `useEffect(() => { sceneRef.current?.requestDraw() }, [labelItems])`. 커밋 직후 한 프레임을 더 돌려 자리를 잡는다 (9.1 의 effect (e))
- 장면을 버릴 때(effect (a) 의 cleanup) `setLabelItems([])` 를 먼저 부른다

### 7.4 화면 좌표를 어떻게 내나

```
placeLabels():
  const handle = labelsRef.current
  if (!handle) return
  for (k = 0; k < labelIndices.length; k++) {
    const i = labelIndices[k]
    pv.set(posBuf[i*3], posBuf[i*3+1], posBuf[i*3+2])
    const d = pv.distanceTo(camera.position)              // 화면 반지름에 쓴다
    pv.project(camera)                                     // 월드 → NDC
    ndcToScreen(pv.x, pv.y, pv.z, cssW, cssH, screenPt)
    const r = screenRadius(radii[i], d, cssH, tanHalfVFov)
    handle.place(k, screenPt.x, screenPt.y + r, screenPt.visible)
  }
```

- **`cssW`·`cssH` 는 `resize()` 가 캐시한 값이다** (`wrapper.clientWidth/clientHeight`, `MapScene.tsx` 262~263행). `getBoundingClientRect()` 를 프레임마다 부르지 않는다
- **`setPixelRatio` 가 아니라 CSS 크기를 쓴다.** `renderer.setSize(w, h, false)`(266행)가 캔버스의 CSS 크기를 CSS 에 맡기고 그리기 버퍼만 픽셀비로 키운다. `project()` 가 돌려주는 NDC 는 픽셀비와 무관하고, 이름표는 CSS 픽셀 위에 놓이는 DOM 이다. **픽셀비를 곱하면 고DPI 화면에서 이름표가 두 배 어긋난다**
- `.map-scene` 이 `position: absolute; inset: 0` 이고 캔버스가 그 100%×100% 라(`map.css` 143~153행) **이름표 레이어의 좌표계가 곧 캔버스의 좌표계다.** 오프셋 계산이 없다
- **이름표는 노드 아래에 붙는다** — `y + screenRadius`. 그래서 노드가 커져도(허브) 이름표가 구체에 파묻히지 않는다
- 가로 가운데 맞춤과 여백은 **CSS 가 한다** — `.map-label { transform: translate(-50%, 0); padding-top: 4px }`. JS 는 `style.translate`(개별 속성)만 쓴다. **2026-09-22 Chrome 실측: `CSS.supports('translate','10px 10px')` 가 `true` 이고, `style.translate = '400px 300px'` + `transform: translate(-50%, 8px)` 를 건 span 의 상자가 정확히 `centerX = 400`, `top = 308` 로 나왔다.** 둘이 섞이지 않는다(개별 속성이 먼저, `transform` 이 나중)
- **`hidden` 으로 숨긴다.** 같은 실측에서 `el.hidden = true` 가 상자를 0 으로 만들었다. `.map-label[hidden] { display: none }` 을 CSS 에 명시해 다른 `display` 규칙에 덮이지 않게 한다

### 7.5 화면 밖·카메라 뒤 (실측으로 정했다)

**2026-09-22 Node 실측** — `PerspectiveCamera(50, 16/9, 0.1, 2000)` 을 `(0,0,100)` 에 두고 원점을 보게 한 뒤 `Vector3.project()`:

| 월드 z | NDC z | NDC x | 판정 |
| --- | --- | --- | --- |
| 0 (원점) | **0.9981** | 0 | 보인다 |
| 100.1 (카메라 바로 뒤) | **3.0002** | -120.6 (좌우가 뒤집혔다) | **z > 1 로 걸러진다** |
| 101 | 1.2001 | -12.06 | 걸러진다 |
| 1e6 (아주 멀리 뒤) | **1.0001** | -0.000 | 걸러진다 |
| 99.9999 (근평면 안쪽) | **-1999.1** | 120628 | **z < -1 로 걸러진다** |

- **카메라 뒤는 `z > 1`, 근평면 앞은 `z < -1` 이다. 한 점도 예외가 없었다** — `ndcToScreen` 의 `-1 <= ndcZ <= 1` 이 정확히 절두체 안쪽이다. 이 검사를 빠뜨리면 **카메라 뒤 노드의 이름표가 좌우 반대편 화면에 나타난다**(위 표의 `x` 열이 그 증거다)
- 원평면(`far`) 밖은 `z` 가 1.0001 쯤이라 같은 검사에 걸린다. 애초에 `clipPlanes()`(F-2003 7.5)가 `far = distance + radius×4` 로 그래프를 늘 감싸므로 생기지 않는다
- **화면 밖은 숨긴다.** 가장자리에 붙여 두지 않는다 — 호버한 노드와 그 이웃뿐이라 개수가 적고, 가장자리에 붙이면 어느 노드 것인지 알 수 없다 (17장 Q5)

### 7.6 호버 판정 — 기존 `pointermove` 리스너에 얹는다

**레이캐스트 비용을 먼저 쟀다** (5.2 표): 1,000 인스턴스에서 **한 번에 0.10~0.17 ms**, 그중 **`computeBoundingSphere()` 가 0.049~0.072 ms** 로 절반 가까이다. Chrome 은 `pointermove` 를 vsync 에 맞춰 보내므로 최악이 **프레임당 한 번**이다.

- **스로틀하지 않는다.** 0.17 ms 는 33 ms 예산의 0.5% 다. 스로틀을 넣으면 이름표가 마우스보다 늦게 뜨는 것만 얻는다
- **`computeBoundingSphere()` 는 좌표가 바뀐 뒤 한 번만 부른다.** 지금은 `hitAt()` 이 부를 때마다 다시 계산한다(`MapScene.tsx` 367행). 경계구는 **인스턴스 행렬에만** 달려 있고 카메라와 무관하므로, `boundsStale` 플래그를 두고 `uploadPositions()` 가 돌 때만 세운다(5.3 의 루프). 배치가 멈춘 뒤에는 한 번 계산하고 계속 쓴다 — **호버 레이캐스트가 0.05~0.11 ms 로 내려간다**
- **리스너를 새로 달지 않는다.** F-2003 4.1 이 등록 순서를 `pointerdown → pointermove → pointerup → pointercancel → touchend → contextmenu → OrbitControls` 로 못 박았고 그 순서는 바꾸면 안 된다. 호버는 **이미 있는 `onPointerMove`**(415~419행, 지금은 길게 누르기 판정 전용)에 얹는다
- **다만 `pointerleave` 하나는 새로 단다** — 커서가 캔버스를 벗어나면 이름표를 거둬야 한다. `contextmenu` **뒤, `OrbitControls` 생성 앞**에 단다(순서 규칙 안에 있다). `dispose()` 의 `removeEventListener` 가 **여섯에서 일곱**이 된다

```
onPointerMove(e):
  … 기존 길게 누르기 슬롭 판정 …
  if (e.pointerType === 'touch') return              // 터치에는 호버가 없다 (17장 Q3)
  if (inputs.current.menuOpen) return                // 메뉴가 떠 있는 동안은 잠겨 있다
  if (e.buttons !== 0) return                        // 끌고 있다 — 제스처 중에는 호버를 갱신하지 않는다 (17장 Q4)
  setHover(hitAt(e.clientX, e.clientY))

onPointerLeave(e):  setHover(null)

setHover(hit):
  const next = hit ? 노드 인덱스 : -1
  if (next === hoverIndex) return                    // 같은 노드 위에서 움직이는 동안은 아무 일도 없다
  hoverIndex = next
  labelIndices = next < 0 ? [] : pickLabelNodes([next], adjacency[next], (i) => graph.nodes[i].degree)
  setLabelItems(labelIndices.map((i) => ({ id: graph.nodes[i].id, title: graph.nodes[i].title })))
  requestDraw()
```

- **`adjacency` 는 `buildScene()` 에서 한 번 만든다** — `graph.edges` 를 훑어 양방향으로 담는 `number[][]`. 노드 1,000·간선 1,000 이면 O(E) 한 번이다
- `hitAt()` 은 끊긴 링크 노드도 맞힌다. **끊긴 링크 노드에도 이름표가 뜬다** — 그 제목이 곧 사용자가 쓴 `[[…]]` 문자열이라 오히려 쓸모가 있다
- 마우스를 노드 위에서 움직이는 동안 `setLabelItems` 가 다시 불리지 않는다(같은 인덱스면 즉시 `return`). **React 렌더는 호버가 바뀔 때만 한 번이다**

## 11. 기존 e2e 가 깨지는가 — 직접 계산했다

F-2003 A1~A13 은 **"첫 실행 상태에서 노드 하나의 화면 반지름이 캔버스 높이의 0.394배"** 에 기대고 있다(`e2e/map.spec.js` 247~250행의 `NODE_R = 0.394`). 노드 반지름이 **6.0 에서 3.0 으로** 바뀌므로 직접 따졌다.

**유도.** 노드 하나짜리 그래프에서 `bounds.radius = 0` 이므로 `fit()` 의 `r = 0 + maxNodeRadius = R`(그 노드의 world 반지름)이다. `fitDistance`(`mapCamera.ts` 4~9행)는

```
dist = r · 1.15 / sin(min(vFov, hFov) / 2)
```

이고, 화면 높이 `H` 에서 거리 `dist` 에 있는 반지름 `R` 짜리 구가 차지하는 화면 반지름은 `R·H / (2·dist·tan(vFov/2))` 다. `r = R` 이므로 **`R` 이 약분된다**:

```
화면 반지름 / H = R·sin(vFov/2) / (2 · R · 1.15 · tan(vFov/2)) = cos(vFov/2) / 2.3
```

`fov = 50°` 이므로 `cos 25° / 2.3 = 0.90631 / 2.3 = ` **`0.39405`**.

| 확인 | 결과 |
| --- | --- |

### 12.1 G6 — 이름표·깊이 섞기를 켠 채 회전 중 fps

F-2003 12.1 의 명령을 그대로 쓰되 **드래그 전에 `hover:` 를 하나 끼운다** — 그래야 이름표가 떠 있는 상태로 회전을 잰다. 7.6 대로 버튼이 눌려 있는 동안에는 호버를 갱신하지 않으므로, 끄는 내내 이름표 집합이 유지된 채 매 프레임 투영된다.

```
  --action "eval:document.querySelector('[aria-label=\"지도\"]').click()" \
  --action "wait:9000" \
  --action "hover:.map-canvas" \
  --action "wait:300" \

  --action "drag:.map-canvas:right:600:0:60" \

```

## 17. 열린 질문 / 사람 결정 필요

**사람이 꼭 골라야 하는 것은 없다.** 사용자가 2026-09-22 에 정한 둘(노드 끌기를 F-2009 로, 링·테두리 보류)은 이미 본문에 박았고, 아래는 전부 기본값이 서 있다. 다른 쪽을 골랐을 때 무엇이 달라지는지 적었다.

### Q1. 공유받은 문서를 `--ink-2` 로 칠하는 것 — **기본: 칠한다**

F-292 6.1 은 `--ink` + `--ink-2` 테두리였는데 테두리가 빠졌으므로(6.3), 색만 남기면 보통 문서와 구분이 아예 사라진다. 한 줄로 되살린다.
**다른 쪽을 고르면**: `--ink` 그대로 두고 구분을 꼬리 줄 `공유받은 문서 {N}개는 나가는 링크를 읽지 못했습니다.` 에만 맡긴다. `applyColors` 에서 `Set` 조회 한 줄이 빠지고 6.1 표가 한 행 줄어든다. **H-g 가 이것도 함께 묻는다.**

### Q2. 현재 문서를 깊이 섞기에서 빼는 것 — **기본: 뺀다**

6.2 의 이유 셋.
**다른 쪽을 고르면**: `applyDepth()` 의 `if (i === centerIndex) t = 0` 한 줄을 지운다. 깊이 표현이 완전히 균일해지는 대신, 현재 문서가 뒤쪽에 있을 때 **`--accent` 가 65% 씻겨 그냥 먼 노드처럼 보인다.** 링을 다시 넣기로 한다면(H-g) 이쪽이 맞는 선택이 된다.

### Q3. 터치에서도 호버 이름표를 띄우는가 — **기본: 안 띄운다**

터치에는 호버가 없고, 노드를 탭하면 문서가 열리며, 길게 누르면 메뉴가 뜬다(F-2003 5장). 이름표가 끼어들 자리가 없다.
**다른 쪽을 고르면**: 탭할 때 문서를 여는 대신 **한 번째 탭은 이름표, 두 번째 탭은 열기**로 만든다. F-2003 A12(짧게 누르면 그 문서가 열린다)가 깨지고 터치 조작 전체를 다시 설계해야 한다. 그러지 않는다.

### Q4. 끌고 있는 동안 호버를 갱신하지 않는 것 — **기본: 갱신하지 않는다**

회전·이동 중에는 이름표 집합이 그대로 얼어 있고 자리만 따라온다. 끄는 동안 이름표가 계속 바뀌면 읽을 수 없고, 레이캐스트를 프레임마다 한 번 더 돌게 된다.
**다른 쪽을 고르면**: `if (e.buttons !== 0) return` 한 줄을 지운다. 끄는 내내 커서 밑 노드가 바뀔 때마다 `setLabelItems` 가 불려 **React 렌더가 프레임마다 일어난다** — 7.2 가 피하려던 바로 그 상태다.

### Q5. 화면 밖 이름표를 가장자리에 붙이는가 — **기본: 숨긴다**

호버한 노드와 그 이웃뿐이라 개수가 적고, 가장자리에 모아 붙이면 어느 노드 것인지 알 수 없다.
**다른 쪽을 고르면**: `ndcToScreen` 이 `visible` 대신 잘린 좌표를 돌려주고 이름표에 방향 표시를 붙인다. U7 이 바뀌고 이름표 디자인이 하나 더 는다.

### Q6. 이름표를 노드 **아래**에 붙이는 것 — **기본: 아래**

`y + screenRadius`(7.4). 위에 붙이면 큰 허브에서 이름표가 화면 위로 밀려나고, 가운데에 두면 구체에 파묻힌다.
**다른 쪽을 고르면**: `padding-top` 을 `padding-bottom` 으로 바꾸고 `transform: translate(-50%, -100%)` 에 `y - screenRadius` 를 준다. 숫자 둘이다. 14.2 A6 의 "위로 2 px 씩 올라가며 찾는" 방향이 아래로 바뀐다.
