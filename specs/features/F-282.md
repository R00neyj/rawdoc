# F-282 가져오기

작성일: 2026-09-20

근거: `specs/features/F-277.md` 3장(가져오기 흐름·판정표·경고)·4장(설정 `데이터` 절)·5장(하지 않는 것)·6장 로드맵(F-282, 의존 F-281), `specs/features/F-281.md` 3.4(`manifest.json` 형식 확정)·3.2(`toFileName`·`toFolderName`)·3.5(스트리밍 zip), F-114 2.1~2.2(`decodeMarkdown`, BOM·줄바꿈), F-126 4장(폴더 2단계), F-156 2.1(`attachments/{id}.{ext}` 원문 형식), F-208 2.2(id·시각 유지 이관), F-209(첨부 저장·서버 재검사), F-213 2.3~2.4(잠금·충돌 사본·에디터 재마운트), F-221 2.1(계정 이미지 300MB), F-206 2.2(문서 1MB)

zip 파일 하나를 읽어 문서·폴더·첨부를 이 저장소로 들인다. F-281 이 만든 zip(왕복)과 `manifest.json` 이 없는 일반 `.md` zip 둘 다 받는다

**데이터를 덮는 기능이라 파괴적이다.** 덮기·건너뜀·사본·실패·취소 규칙을 3.7~3.10 에서 남김없이 정한다

## 1. 범위

### 한다

- 설정 대화상자 `데이터` 절에 `가져오기…` 버튼을 더한다 (F-281 이 만든 절, `전체 내보내기` 옆)
- zip 을 **두 번 훑어** 미리보기를 만들고(1차) 사용자가 확인하면 적용한다(2차). `fflate` 스트리밍 `Unzip` 으로 항목을 하나씩 읽어 메모리에 한 번에 올리지 않는다 (3.3)
- `manifest.json` 이 있으면 **왕복 가져오기**(3.6): 문서 id 를 유지해 새로 만들거나, `updatedAt` 이 더 늦으면 갱신한다. 갱신 전에 지금 내용을 사본으로 남긴다
- `manifest.json` 이 없으면 **일반 zip 가져오기**(3.7): `.md`·`.markdown` 만, 전부 새 문서
- 미리보기 대화상자(새로·갱신·건너뜀·이미지 개수와 경고 목록), 진행 표시, 취소, 결과·실패 목록 (3.9)
- 저장소 인터페이스에 **선택 필드**를 더한다 — `create({ id, createdAt, updatedAt, pinnedAt })`, `createFolder({ id })`, `putAttachment({ id })` (3.11)

### 하지 않는다

- 내보내기 쪽 — F-278~F-281. `src/app/exportWorkspace.ts`·`src/app/exportDoc.ts` 를 **고치지 않는다**
- `manifest.json` 형식 바꾸기. F-281 이 확정한 `format: 1` 을 읽기만 한다. 모르는 필드는 무시한다 (F-281 3.4)
- zip 끌어놓기(F-145 확장) — F-277 4장에서 범위 밖
- Obsidian `![[그림.png]]`, Notion·HackMD 전용 형식 해석 (F-277 5장). 그런 이미지 참조는 **원문을 그대로 두고** 개수만 알린다
- 가져올 항목 하나씩 고르기(체크박스), 되돌리기(undo), 가져오기 기록
- 공유받은 문서·남의 계정으로 가져오기 (F-277 5장)
- `serverStore` 의 `id_taken` 처리 방식 바꾸기 — 4장 Q1
- 새 의존성. `fflate` 0.8.3 은 F-281 이 이미 들여놨고 **압축 해제 API(`Unzip`·`UnzipInflate`·`UnzipPassThrough`·`unzipSync`)가 그 안에 있다** (3.3 실측)

## 3. 요구사항

### 3.1 진입점과 흐름

1. 설정 대화상자 `데이터` 절 → `가져오기…`
2. **설정 대화상자를 닫고** 파일 선택창을 연다. 대화상자를 겹쳐 열지 않는다 — 설정 위에 미리보기가 또 뜨면 포커스 되돌리기가 꼬인다
3. 파일 하나를 고르면 `await saver.flush()` 로 저장 대기 중인 입력을 먼저 저장한다 (F-281 3.1 Q5 와 같은 이유. 지금 열린 문서가 갱신 대상일 수 있다)
4. zip 을 1차로 훑어 **미리보기**를 만든다 (3.4~3.8). 거부 사유가 있으면 대화상자를 열지 않고 오류 알림만 낸다
5. 미리보기 대화상자 → `가져오기` / `취소`
6. `가져오기` → 진행 표시 → 결과 (3.9)

- 파일 입력: `<input type="file" accept=".zip,application/zip" data-import="zip" hidden>`. 기존 `.md` 입력(F-114)은 `data-import="md"` 를 붙여 구분한다
- 고른 파일이 zip 이 아니어도 확장자로 막지 않는다 — 읽어 보고 실패하면 3.5 의 거부 메시지를 낸다
- 여러 파일 선택은 받지 않는다(`multiple` 없음). 하나만 처리한다

### 3.2 로그인·오프라인

| 상태 | 동작 |
| --- | --- |
| 로그인하지 않음 | 이 브라우저(IndexedDB) 저장소로 들인다. 용량 상한 없음 |
| 로그인함 | 서버 저장소로 들인다. 문서 1MB·이미지 5MB·계정 300MB 상한이 걸린다 (3.10) |
| 로그인 + 오프라인 | **막지 않는다.** `serverStore` 는 캐시에 먼저 쓰고 outbox 로 보내므로 오프라인에서도 들일 수 있다. 보내기는 온라인 복귀 때 이어진다 |

- 내보내기(F-281 3.1)는 오프라인에서 막았다. 첨부를 **읽어야** 했기 때문이다. 가져오기는 **쓰기**뿐이라 막을 이유가 없다
- 다만 미리보기의 이미지 용량 경고(3.10)는 `fetchUsage()` 가 필요하므로 오프라인이면 조용히 건너뛴다

### 3.3 zip 읽기 (조사 결과)

설치된 `fflate` **0.8.3** 에 압축 해제 API 가 있다: `Unzip`(스트리밍, `onfile` 핸들러), `UnzipInflate`·`UnzipPassThrough`(압축 방식별 디코더, `register` 로 붙인다), `unzipSync`/`unzip`(한 번에). `node_modules/fflate/lib/index.d.ts` 1344~1539줄

실제로 돌려 확인한 것 (2026-09-20, Node 24, 프로젝트의 `fflate` 0.8.3):

| 확인 | 결과 |
| --- | --- |
| F-281 의 스트리밍 `Zip` + `ZipPassThrough` 출력 | 로컬 헤더의 general purpose flag 가 `8`(데이터 디스크립터), 로컬 헤더 압축 크기가 `0` 이다 |
| 그 zip 을 스트리밍 `Unzip` 으로 읽기 | 된다. 1KB 씩 밀어 넣어도 항목 이름·바이트가 정확히 나온다. 한글 경로·`폴더/attachments/{id}.png` 중첩 경로 그대로 |
| `ZipDeflate`(압축) + 데이터 디스크립터 | 스트리밍 `Unzip` 이 그대로 푼다 |
| 필요 없는 항목에서 `file.start()` 를 **부르지 않기** | 된다. 그 항목은 건너뛰고 다음 항목 파싱이 이어진다. 압축·무압축, 데이터 디스크립터 있음·없음 네 조합 모두 확인 |
| 스트리밍으로 만든 zip 의 `file.size`·`file.originalSize` | `undefined` 다(문서에 적힌 대로). 일반 zip(`zipSync`)에서는 값이 있다 |
| 파일명 디코딩 | fflate 는 UTF-8 플래그(bit 11)가 꺼져 있으면 이름을 **latin1 로 푼다**(`strFromU8(…, !(flag & 2048))`, `esm/browser.js` 1836·2462행). 즉 바이트가 문자열에 1:1 로 남는다 |
| `new TextDecoder('euc-kr')` | Node 24 에서 있다. `'cp949'` 라벨은 **없다**(예외) |

**이 명세의 방식**

```ts
// 항목을 하나씩 흘려 준다. bytes 가 null 이면 want() 가 false 라 읽지 않고 건너뛴 항목이다
export async function* readZipEntries(
  chunks: AsyncIterable<Uint8Array>,
  opts?: { want?: (name: string) => boolean },
): AsyncGenerator<{ name: string; bytes: Uint8Array | null }>
```

- 입력은 `AsyncIterable<Uint8Array>` 다. 브라우저에서는 `file.stream()`, 테스트에서는 배열을 그대로 준다 — **DOM 없이 단위 테스트가 된다**
- `Unzip` 콜백은 동기라 안에서 `await` 할 수 없다. 완성된 항목을 큐에 쌓아 두고 **조각을 하나 밀어 넣을 때마다 큐를 비워 yield** 한다. 최대 메모리는 "진행 중인 항목 1개 + 한 조각 안에서 끝난 작은 항목들"
- `zip.push` 가 던지면(깨진 zip) 잡아 3.5 의 거부로 바꾼다
- **같은 이름이 두 번 나오면 처음 것만 쓴다.** 뒤의 것은 조용히 버린다
- 두 번 훑는다. `File`/`Blob` 은 디스크에 있어 `stream()` 을 두 번 부를 수 있다
  - **1차(미리보기)**: `want` 가 `manifest.json` 만 `true`. 나머지는 이름만 모은다. 비용이 거의 없다
  - **2차(적용)**: 계획에 든 `.md`·첨부 항목만 `want` 가 `true`
- `unzipSync` 는 쓰지 않는다. zip 전체와 푼 내용이 동시에 메모리에 올라간다(300MB 계정이면 수백 MB)

### 3.4 파일명 인코딩 (UTF-8 vs CP949)

```ts
export function decodeZipName(raw: string): string
```

순수 함수. 규칙:

1. 코드포인트 중 `0xFF` 를 넘는 것이 하나라도 있으면 **그대로 돌려준다** — fflate 가 UTF-8 플래그를 보고 제대로 푼 이름이다
2. 전부 `0x7F` 이하(순수 ASCII)면 그대로 돌려준다
3. 그 밖(전부 `0xFF` 이하인데 `0x80` 이상이 섞임) → 코드포인트를 바이트로 되돌린 뒤
   1. `new TextDecoder('utf-8', { fatal: true })` 가 성공하면 그 결과 — UTF-8 로 적고도 플래그를 안 켜는 압축기(리눅스 `zip` 등) 대응
   2. 실패하면 `new TextDecoder('euc-kr', { fatal: true })` 가 성공할 때 그 결과 — Windows 탐색기가 만든 CP949 이름
   3. 둘 다 실패하거나 `euc-kr` 디코더를 만들 수 없으면(try/catch) 원래 문자열 그대로

- 1 이 먼저인 이유: fflate 가 UTF-8 로 제대로 푼 한글 이름은 코드포인트가 `0xFF` 를 넘어 3 에 들어가지 않는다. 역으로 들어가면 멀쩡한 이름을 깨뜨린다
- 서유럽 문자(`é` 등)만 든 CP949 아닌 legacy 이름은 3-1·3-2 를 둘 다 실패해 3-3 으로 원래 모습이 남는다. 이 경우는 고치지 않는다
- 경로 구분자 `\` 는 디코딩 뒤 `/` 로 바꾼다 (3.7 경로 정규화)

### 3.5 판별과 거부

1차 훑기가 끝나면:

| 조건 | 결과 |
| --- | --- |
| 루트 `manifest.json` 이 있고, UTF-8 JSON 으로 파싱되고, `format` 이 **숫자 `1`** 이고 `folders`·`docs` 가 **배열** | **workspace** — 3.6 |
| `manifest.json` 이 없음 | **plain** — 3.7 |
| `manifest.json` 이 있는데 `format` 이 숫자가 아니거나 `folders`·`docs` 가 배열이 아님 | **plain** — 우연히 이름이 같은 남의 파일로 본다. 거부하지 않는다 |
| `manifest.json` 이 있고 `format` 이 숫자인데 `1` 이 아님 | **거부.** `이 zip 은 모르는 형식(format {N})이라 가져올 수 없습니다.` |
| `manifest.json` 이 있고 `format`·`folders`·`docs` 가 다 맞는데 JSON 이 깨짐 | 위 세 조건에 걸리지 않으므로 plain 으로 떨어진다 |
| zip 자체를 읽지 못함(`Unzip` 이 던짐, 항목이 0개) | **거부.** `zip 파일을 읽지 못했습니다. 파일이 손상되었을 수 있습니다.` |

- `format` 판별 타입은 코드에서 `'workspace' | 'plain'` 으로 쓴다. **제품명을 쓰지 않는다** (CLAUDE.md 불변조건)
- 거부는 대화상자를 열지 않고 `error` 알림만 낸다

### 3.6 workspace zip 계획 (`manifest.json` 있음)

`manifest.folders`·`manifest.docs` 를 훑어 항목별 계획을 만든다. 전부 순수 함수다

```ts
export type ImportPlan = {
  kind: 'workspace' | 'plain'
  folders: PlanFolder[]   // 부모가 자식보다 먼저
  docs: PlanDoc[]
  attachments: PlanAttachment[]
  warnings: string[]
  counts: { created: number; updated: number; skipped: number; images: number }
}
```

**항목 검증** — `docs[]` 의 `id`(빈 문자열 아닌 문자열)·`path`(문자열)가 없거나 타입이 틀리면 그 항목만 버리고 경고에 개수를 센다. 나머지는 관대하게 채운다

| 필드 | 값이 이상할 때 |
| --- | --- |
| `title` | `path` 의 파일 이름에서 확장자를 뗀 것 |
| `lineEnding` | `'crlf'`·`'lf'` 가 아니면 **그 `.md` 바이트에서 판정**(`decodeMarkdown`) |
| `createdAt`·`updatedAt` | 양의 정수가 아니면 지금 시각 |
| `pinnedAt` | 양의 정수가 아니면 `null` |
| `folderId` | 문자열이 아니면 `null` |

**문서 판정** — 기존 목록은 `store.list()` 결과다

| 경우 | 결과 |
| --- | --- |
| 같은 id 가 **내 문서**(`role` 이 `'owner'` 이거나 없음)에 없음 | `create` — **id·`createdAt`·`updatedAt`·`pinnedAt` 을 유지**한다 |
| 같은 id 가 내 문서에 있고 zip 쪽 `updatedAt` **>** 기존 `updatedAt` | `update` — 덮기 전 사본 (3.9) |
| 같은 id 가 내 문서에 있고 zip 쪽이 같거나 더 이름 | `skip` |
| 같은 id 가 **공유받은 문서**(`role` 이 `'edit'`·`'view'`)임 | `create-new-id` — **새 id 로 새 문서**를 만든다. 남의 문서를 덮지 않는다. 경고 `공유받은 문서와 id 가 같아 새 문서로 만든 것 {N}개` |
| `path` 에 해당하는 zip 항목이 없음 | 계획에서 뺀다. 경고 `zip 에 없는 문서 {N}개` |

**폴더 판정**

| 경우 | 결과 |
| --- | --- |
| 같은 id 폴더가 있음 | **그 폴더를 쓴다.** 이름·위치를 바꾸지 않는다 (F-277 3.2) |
| 없음 | `id` 를 유지해 만든다. 이름은 `manifest.folders[].name` |
| `parentId` 가 `manifest.folders` 에도 내 폴더에도 없음 | 최상위(`null`)로 만든다 |
| ~~깊이가 3단계 이상~~ (2026-09-23, F-2017: 깊이 제한이 없어져 합치기 삭제, 이 행 해당 없음) | ~~2단계로 올린다(조부모의 자식으로). 경고 `2단계로 합친 폴더 {N}개`. F-281 은 2단계까지만 내보내므로 보통 나오지 않는다 — 손으로 고친 manifest 방어 (F-126 4장)~~ |
| `scope: "folder"` zip 에서 `rootFolderId` 가 가리키는 폴더가 **내게 있음** | zip 루트를 그 폴더 안으로 넣는다 |
| `scope: "folder"` zip 에서 그 폴더가 **없음** | zip 루트 = **최상위**. `manifest` 에 그 폴더의 이름이 없어 만들 수 없다 (F-281 3.4 — `folders[]` 에 루트 폴더 자신은 들어 있지 않다). 경고 없음 (4장 Q2) |

- 이름이 같은 폴더가 이미 있어도 **id 가 다르면 따로 만든다.** 앱이 폴더 이름 중복을 허용한다(`createFolder` 에 중복 검사가 없다)
- 문서 제목 중복도 그대로 둔다
- 폴더는 `manifest.folders` 순서(F-281 이 부모 먼저로 정렬했다)를 믿지 않고 `parentId` 로 다시 위상 정렬한다

**첨부** — `manifest` 에 첨부 목록이 없다(F-281 3.4). zip 항목 이름 중 `(…/)?attachments/{16자리 16진수}\.(png|jpg|gif|webp)` 에 맞는 것을 모아 **id 별로 하나씩만** 계획에 넣는다(같은 id 가 여러 폴더에 중복해 들어 있다 — F-281 3.3). 이미 `store.getAttachment(id)` 에 있으면 계획에서 뺀다

### 3.7 일반 zip 계획 (`manifest.json` 없음)

**경로 정규화** (이름 디코딩 3.4 뒤에)

1. `\` → `/`
2. 앞의 `./`·`/` 제거
3. 세그먼트에 `..` 가 있으면 **그 항목을 버린다**(zip slip 방어). 경고 `경로가 이상해 건너뛴 파일 {N}개`
4. 이름이 `/` 로 끝나면 디렉터리 항목이라 버린다(세지 않는다)

**잡음 항목** — 아래는 건너뛰고 **"건너뛴 파일" 수에 넣지 않는다**

- `__MACOSX/` 로 시작
- 세그먼트 중 하나가 `.` 로 시작(`.DS_Store`, `.obsidian/`, `.git/` 등)
- `Thumbs.db`, `desktop.ini` (대소문자 무시)

**공통 최상위 벗기기** — 잡음을 뺀 항목이 **모두 같은 첫 디렉터리 `X/` 아래**에 있고, 루트에 파일이 하나도 없으면 `X/` 를 벗긴다. 압축 프로그램이 한 겹 더 씌우는 것과 Obsidian 보관함 폴더째 압축을 같게 다룬다. `X` 폴더는 만들지 않는다 (4장 Q4)

**문서**

- 확장자가 `.md`·`.markdown`(대소문자 무시)인 것만 문서로 본다
- 그 밖의 파일은 건너뛰고 경고 `.md 가 아니라 건너뛴 파일 {N}개`. 단 아래 "이미지" 에 해당하는 것은 세지 않는다
- 제목: 파일 이름에서 확장자를 뗀 것. 비면 `제목 없는 문서`
- 내용: `decodeMarkdown(bytes)`(F-114 2.1) — BOM 제거, 줄바꿈 판정, 섞이면 CRLF 통일. UTF-8 이 아니면 그 문서는 실패 목록에 넣는다(적용 단계)
- **전부 새 문서다.** id·`createdAt`·`updatedAt` 은 저장소가 새로 정한다. `pinnedAt` 은 `null`. 같은 제목이 있어도 갱신하지 않는다 (F-277 "기본값으로 정한 것" 3)

**폴더**

- 경로의 디렉터리 부분을 그대로 폴더로 만든다. `A/문서.md` → 폴더 `A`. `A/B/문서.md` → `A` 안 `B`
- ~~**3단계 이상은 2단계에 합친다.** `A/B/C/D/문서.md` → `A/B` 안의 문서. 경고 `2단계로 합친 폴더 {N}개` (F-126 4장)~~ 합치기 삭제 — 깊이 제한 없음, 경로 그대로 폴더를 만든다 (2026-09-23, F-2017). 나머지는 F-2019 가 대체
- **같은 부모 안에 이름이 정확히 같은 폴더가 이미 있으면 그 폴더에 넣는다.** 대소문자는 구분한다(앱 폴더 이름은 파일 시스템이 아니다)
- 폴더 이름은 zip 경로 세그먼트 그대로다. `toFolderName` 을 쓰지 않는다 — 그건 내보낼 때 파일 시스템용으로 깎는 함수고, 들일 때는 원래 이름을 되살리는 쪽이 맞다

**이미지**

- 문서 원문에 `attachments/{16자리 16진수}.{ext}` 참조가 있고, **그 문서가 놓인 디렉터리 기준으로** 같은 이름의 zip 항목이 있을 때만 가져온다 (`A/B/문서.md` → `A/B/attachments/{id}.{ext}`)
- 참조는 있는데 zip 에 파일이 없으면 경고 `가져오지 못한 이미지 참조 {N}개`
- 그 형식이 아닌 이미지 참조(`![[그림.png]]`, `![](images/a.png)`)는 **원문을 그대로 두고** 경고 `이 앱 형식이 아니라 가져오지 못한 이미지 {N}개` (F-277 3.3 — 원문을 바꾸지 않는다)
- 어느 문서도 참조하지 않는 `attachments/` 파일은 가져오지 않는다(세지도 않는다)

### 3.8 미리보기 대화상자 (`ImportPreviewDialog`)

한 대화상자가 **미리보기 → 진행 → 결과** 세 단계를 돈다

| 단계 | 내용 | 버튼 |
| --- | --- | --- |
| 미리보기 | 제목 `가져오기`, 파일 이름 한 줄, 요약 `새로 {N}개 · 갱신 {N}개 · 건너뜀 {N}개 · 이미지 {N}개`, 경고가 있으면 `.import-list` 목록 | `취소`(초기 포커스) / `가져오기` |
| 진행 | `가져오는 중… {done}/{total}` | `취소` 하나 |
| 결과 | 요약 한 줄 + 실패 목록(`.import-list`) | `닫기` |

- 갱신이 1개 이상이면 미리보기에 `.dialog-note` 로 `덮이는 문서는 이전 내용을 "(가져오기 전)" 문서로 남깁니다.`
- `새로 + 갱신` 이 0 이면 `가져오기` 버튼을 `disabled` 로 두고 `.dialog-note` 에 `가져올 문서가 없습니다.`
- **실패가 하나도 없으면 결과 단계를 건너뛰고** 대화상자를 닫은 뒤 알림만 낸다. 실패가 있을 때만 결과 단계를 보여 준다 (4장 Q5)
- Esc·바깥 클릭으로 닫기: 미리보기 단계는 취소와 같다. **진행 단계에서는 닫히지 않는다**(`Dialog` 에 그 기능이 없으면 이번에 만들지 않고, 닫혀도 가져오기는 이어지게 둔다 — 4장 Q6)
- 대화상자가 열려 있는 동안 편집을 막지 않는다

### 3.9 적용 — 순서·원자성·취소

**순서**: 폴더(부모 먼저) → 문서(`create` → `update` 순, 각각 계획 순서) → 첨부

**원자성은 없다.** 되돌리지 않는다

- 이유: 저장소에 여러 종류를 묶는 트랜잭션 경계가 없고(`serverStore` 는 캐시 + outbox 비동기), 되돌리는 중 실패하면 더 나쁜 상태가 된다
- 항목 하나가 실패하면 **그 항목만** 실패 목록에 넣고 다음으로 간다
- 폴더 만들기가 실패하면 그 폴더에 들어갈 문서는 **최상위**로 넣는다(문서를 잃지 않는다). 실패 목록에 폴더 1건

**덮기 전 사본** (F-277 3.2 — 이 기능의 안전장치다)

- `update` 문서마다, 덮기 **직전에** `store.create({ title, content, lineEnding, folderId })` 로 지금 내용을 사본으로 남긴다. id·시각은 새로 만든다
- 제목은 `{기존 제목} (가져오기 전)`. 합쳐서 500자(서버 제목 상한, `worker/validate.ts` `MAX_TITLE_CHARS`)를 넘으면 **앞을 잘라** 맞춘다
- 폴더는 기존 문서와 같은 폴더
- **사본 만들기가 실패하면 그 문서를 갱신하지 않는다.** 실패 목록에 `{제목} — 사본을 만들지 못해 갱신하지 않았습니다`
- 사본은 갱신마다 새로 생긴다(중복 억제 없음)

**잠금 문서** — F-277 3.2 는 "다른 사람이 편집 중인 문서는 갱신하지 않고 실패 목록" 이라고 적었지만, 클라이언트가 잠금 상태를 미리 알 방법이 없다(`serverStore.update` 는 캐시에 쓰고 즉시 돌아온다). **미리 거르지 않는다.** 서버가 423 을 주면 기존 F-213 2.4 흐름이 그 편집을 충돌 사본으로 돌리고 알린다 — 데이터는 잃지 않는다 (4장 Q6)

**현재 열린 문서**

- 시작 전에 `await saver.flush()` (3.1)
- 열린 문서가 `update` 대상이었으면, 끝난 뒤 `editorRemountNonce` 를 올려 에디터를 다시 마운트한다 (F-213 2.3 과 같은 방식). 안 하면 에디터의 옛 `EditorState` 가 다음 저장 때 가져온 내용을 덮어쓴다
- 열린 문서가 대상이 아니면 아무것도 하지 않는다

**취소**

- 진행 중 `취소` → **지금 항목까지는 그대로 두고 다음 항목부터 멈춘다.** 되돌리지 않는다
- 알림 `가져오기를 멈췄습니다. 문서 {N}개를 들였습니다.` (`warn`)
- 항목 하나 안에서는 멈추지 않는다(쓰기 도중에 끊지 않는다)

**진행·결과 알림**

| 때 | 알림 |
| --- | --- |
| 진행 중 | 대화상자 안에서만 표시한다. 알림 띠를 쓰지 않는다 (내보내기와 다르다 — 여기는 대화상자가 이미 떠 있다) |
| 성공 | `info` `문서 {N}개를 가져왔습니다.` (갱신이 있으면 `문서 {N}개를 가져오고 {M}개를 갱신했습니다.`) |
| 실패 있음 | 결과 단계 + `warn` `{N}개를 가져오지 못했습니다.` |
| 전부 실패 | `error` `가져오지 못했습니다.` |

끝나면 사이드바 목록·폴더를 새로 읽는다(`store.list()`·`store.listFolders()`)

### 3.10 한도

| 한도 | 값 | 동작 |
| --- | --- | --- |
| 문서 1개 크기 | UTF-8 1,000,000 바이트 (`worker/validate.ts` `MAX_CONTENT_BYTES`) | `store.kind === 'server'` 일 때만 검사. 넘으면 그 문서를 건너뛰고 미리보기 경고 + 실패 목록. 로컬 저장소는 검사하지 않는다 |
| 이미지 1장 | 5,242,880 바이트 (`worker/attachments.ts` `MAX_ATTACHMENT_BYTES`) | 넘으면 그 이미지만 건너뛴다. 로컬 저장소도 같은 기준을 쓴다(나중에 로그인하면 못 올라간다) |
| 계정 이미지 총량 | 300MB (F-221 2.1) | `putAttachment` 가 `QuotaExceededError`(`name === 'quota_exceeded'`)를 던지면 **남은 이미지를 더 시도하지 않고** 전부 실패 목록에 넣는다. 알림 `이미지 저장 공간(300MB)이 가득 차 이미지 {N}개를 넣지 못했습니다.` |
| 이미지 형식 | `inspectImageBytes`(`src/lib/imageFile.ts`)가 PNG·JPEG·GIF·WebP 로 알아본 것만 | 아니면 그 이미지만 건너뛴다 |

- `MAX_CONTENT_BYTES`·`MAX_ATTACHMENT_BYTES` 는 `worker/` 에 있다. `src/` 가 `worker/` 를 import 하지 않도록 **`importWorkspace.ts` 안에 상수를 다시 적고 근거 주석을 단다**
- 미리보기 용량 경고: `store.kind === 'server'` 이고 계획에 이미지가 1장 이상이면 `fetchUsage()`(`src/storage/attachmentsApi.ts`)로 남은 공간을 보고, **고른 zip 파일 전체 크기**(`File.size`)가 남은 공간보다 크면 경고 한 줄 `이미지 저장 공간이 모자랄 수 있습니다(남은 공간 {N}MB).` 조회가 실패하면(오프라인 등) 경고를 내지 않는다
  - 이미지 실제 합계를 쓰지 않는 이유: F-281 이 만든 zip 은 로컬 헤더에 크기가 없어(3.3) 1차 훑기에서 바이트를 다 읽어야만 합계가 나온다. 느슨한 상한으로 대신한다 (4장 Q7)

### 3.11 저장소 인터페이스 확장

`src/types.ts` 의 `Store` 에 **선택 필드**만 더한다. 기존 호출부는 그대로 통과해야 한다

```ts
create(input: {
  title: string; content: string; lineEnding: LineEnding; folderId?: string | null
  // 가져오기(F-282)·이관이 원본 값을 유지할 때만 준다
  id?: string; createdAt?: number; updatedAt?: number; pinnedAt?: number | null
}): Promise<Doc>

createFolder(input: {
  name: string; parentId?: string | null
  id?: string; createdAt?: number; updatedAt?: number
}): Promise<Folder>

putAttachment(input: {
  blob: Blob; mime: string; ext: AttachmentExt; width: number; height: number
  // 주면 이 id 로 저장한다. 원문의 attachments/{id}.{ext} 를 고치지 않으려면 id 와 ext 가 그대로여야 한다
  id?: string
}): Promise<{ id: string; ext: AttachmentExt }>
```

규칙:

- `create({ id })` — 그 id 가 **이미 있으면 던진다**(덮지 않는다). 호출하는 쪽이 먼저 판정한다
- `createFolder({ id })` — 같음
- `putAttachment({ id })` — 그 id 가 이미 있으면 **덮지 않고 기존 것을 그대로 돌려준다**. `serverStore` 는 **WebP 변환을 건너뛴다** (`ext` 가 바뀌면 원문 `src` 와 어긋난다. F-209 의 "F-208 로 옮기는 기존 첨부는 변환하지 않는다" 와 같은 이유)
- `putAttachment` 의 계정 한도 사전 검사(`serverStore`, F-221 2.3)는 `id` 를 줄 때도 그대로 한다
- `createFolder` 의 `createdAt`·`updatedAt` 은 **로컬 저장소에서만 쓰인다** — 서버가 받지 않는다(3.12). `serverStore` 는 캐시에만 넣고 outbox 에는 싣지 않는다

### 3.12 서버 API 가 무엇을 받는가 (F-277 3장 미뤄둔 확인 — `worker/` 코드를 읽고 확인)

| 라우트 | 받는 것 | 결론 |
| --- | --- | --- |
| `POST /api/docs` (`worker/docs.ts` 127~196) | `id`·`title`·`content`·`lineEnding`·`folderId`·**`createdAt`**·**`updatedAt`**·**`pinnedAt`** | 새 문서는 **id·시각·고정을 모두 유지할 수 있다.** 검사는 `isValidTimestamp`(정수 ms, 0 초과, **지금+1일 이하**, `worker/validate.ts` 35~38) — 시계가 앞선 기기에서 나온 zip 은 400 이 날 수 있다 |
| 같은 라우트, id 가 이미 있을 때 | — | **내 것이면 200 으로 기존 문서를 그대로 돌려준다(덮지 않는다).** 남의 것이면 409 `id_taken` |
| `POST /api/folders` (`worker/folders.ts` 38~95) | `id`·`name`·`parentId` 만 | **폴더 시각은 유지할 수 없다** — 서버가 현재 시각으로 넣는다. `manifest.folders` 에 시각이 없어(F-281 3.4) 실제로 문제가 없다 |
| `PUT /api/docs/:id` (198~261) | `title`·`content`·`baseVersion` 만 | **갱신으로는 `updatedAt` 을 유지할 수 없다.** 서버가 `Date.now()` 로 덮는다 |
| `PUT /api/docs/:id/pin` (299~325) | `pinned` 불린만 | **`pinnedAt` 값을 지정할 수 없다.** F-277 3.2 의 "새로 만든 문서만 `pinnedAt` 을 따른다" 와 맞는다 |

**정리** — 새 문서는 `id`·`createdAt`·`updatedAt`·`pinnedAt` 을 전부 유지한다. **갱신 문서는 내용·제목만 바뀌고 `updatedAt` 은 가져온 시각이 된다.** 같은 zip 을 두 번 가져오면 두 번째는 전부 `skip` 이라 문제가 없다

### 3.14 `id_taken` 동기화 실패 문구 (2026-09-21 사람 승인)

재발급은 F-289 로 미루지만(Q1·4.1), **무엇이 잘못됐는지는 알려 준다.** 지금은 원인이 무엇이든 `동기화하지 못했습니다.` 한 줄만 떠서 사용자가 알 길이 없다

| 오류 | 문구 |
| --- | --- |

- 문서(`createDoc`)와 폴더(`createFolder`) 둘 다 같은 줄로 떨어지므로 문구 하나로 덮는다
- **버리는 동작은 그대로다** — `removeOutbox(entry.key)` 후 계속 진행. 재시도해도 성공하지 않는다

### 4.1 id 재발급을 F-289 로 떼는 근거 (2026-09-21 조사)

| A9 (단위) | 실패·취소 | ① 문서 하나에서 `store.create` 가 던진다 ② 사본 만들기가 던진다 ③ 폴더 만들기가 던진다 ④ 둘째 문서 뒤에 취소 신호를 준다 | ① 그 문서만 실패 목록, 나머지는 들어간다 ② **갱신하지 않고** 실패 목록 — 원래 내용이 남는다 ③ 그 폴더 문서는 최상위로 들어간다 ④ 셋째부터 `store` 호출이 없고 결과에 `cancelled: true`, 들인 수가 2 |
| A10 (단위) | 한도 | `kind:'server'` 가짜 저장소에 ① 1MB 넘는 `.md` ② 5MB 넘는 이미지 ③ 이미지 형식이 아닌 바이트 ④ 셋째 이미지에서 `QuotaExceededError` | ①②③ 은 그 항목만 건너뛰고 실패 목록·경고. ④ 뒤로는 `putAttachment` 를 더 부르지 않고 남은 이미지가 전부 실패 목록에 든다. `kind:'idb'` 면 ① 은 검사하지 않는다 |
| A11 (e2e, 스모크) | 대화상자 | 설정 → `가져오기…` → 파일 고르기 → 미리보기 → `취소` | 설정이 닫히고 미리보기가 열린다. 요약 줄이 보인다. `취소` 로 닫히고 문서 수가 그대로다 |
| A12 (e2e) | 왕복 | 최상위 문서 1 + 폴더 1(문서 1) + 하위 폴더 1(문서 1) 을 만들어 `전체 내보내기` → 문서·폴더를 전부 지움 → 그 zip 을 가져오기 | 문서 3개와 폴더 2개가 같은 구조·같은 제목으로 돌아온다. 저장된 원문 바이트가 내보내기 전과 같다 |
| A13 (e2e) | 갱신·사본 | 내보낸 뒤 그 문서를 고쳐 저장 → zip 의 `updatedAt` 이 더 늦도록 manifest 를 고쳐 가져오기 | 미리보기가 `갱신 1개`, 갱신 뒤 본문이 zip 내용이고 사이드바에 `{제목} (가져오기 전)` 문서가 생겼으며 그 내용이 고친 쪽이다 |
| A14 (e2e) | 일반 zip | `a.md`·`폴더/b.md`·`note.txt` 를 담은 zip 을 만들어 가져오기 | 문서 2개가 생기고 `폴더` 가 생긴다. 미리보기 경고에 `.md 가 아니라 건너뛴 파일 1개` 가 보인다 |
| A15 (e2e) | 거부 | `manifest.json` 이 `{"format":99,"folders":[],"docs":[]}` 인 zip 을 고른다 | 대화상자가 열리지 않고 `모르는 형식(format 99)` 오류 알림이 뜬다. 문서 수가 그대로다 |
| A16 | 빌드·타입·린트 | `npm run build`·`npm run typecheck`·바꾼 파일 eslint | 통과 |
| A17 | 소유 범위 | `npm run review -- F-282` | 2장 표 밖 변경이 없다. 특히 `src/app/exportWorkspace.ts`·`src/app/exportDoc.ts` 가 바뀌지 않았다 |
