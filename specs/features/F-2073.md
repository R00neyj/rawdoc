### 4.3 3.3 렌더 중 상태 조정

- **블록 e 를 `useE2eeMigrate` 로 옮긴다.** e 가 쓰는 상태는 `e2eeUnmountTrackedDocId`·`e2eeUnmountedDocId` 둘이다. 둘을 쓰는 곳은 블록 e 와 Ⓜ5 의 `unmount` 단계뿐이다(`grep -nw`). 둘 다 Ⓜ 에 들어온다. 그래서 F-2059 3.3 "쓰는 상태가 모두 같은 조각에 있을 때만" 을 만족한다. 읽는 `currentDocId` 는 옵션으로 받는다. App 은 `e2eeUnmountedDocId` 값만 JSX 에서 읽는다
- 옮긴 뒤 순서: a(≈567)·b·c(≈718)·d(≈721)는 App 이다. **e 는 `useE2eeMigrate` 호출(≈1107) 안이다.** f·g 는 `useNotificationsGlue` 호출(≈1360) 안이다. h(≈1436)는 App 이다. 결국 **a→b→c→d→e→f→g→h 로 지금과 같다**

### 4.5 3.5 공개 보기 조기 반환 · 3.8 훅 호출 자리

**`useE2eeMigrate` 호출 자리 = Ⓜ2 가 있던 자리다.** `useE2ee` 반환을 ref 에 잇는 `[e2ee]` effect 와 빈 줄 다음이고, `// 금고 상태가 바뀌면 목록을 다시 읽는다 …` 주석 앞이다. 이 자리여야 하는 이유는 세 가지다.
- Ⓜ2·Ⓜ5 두 effect 의 실행 자리가 한 줄도 움직이지 않는다(4.2)
- 블록 e 가 d 와 f 사이에 남는다(4.3)
- 인자 `e2ee` 가 `useE2ee` 반환값이라, 그보다 위로는 올라갈 수 없다

**`useE2eeConvert` 호출 자리 = 절 "금고로 옮기기·빼기" 머리가 있던 자리다.** `requestE2eeOpen` 닫는 괄호와 빈 줄 다음이고, `// 대상이 금고 폴더면 …`(`ensureE2eeOpenForFolder`) 앞이다. Ⓒ 에는 effect 가 없어서 자리는 TDZ 로만 정해진다. 옵션 `commentAccessValue`(≈1309)보다 아래이고, 반환값을 쓰는 JSX(≈3815~)보다 위면 된다. 절 자리가 이 조건을 만족한다.

- **두 훅의 호출 순서: `useE2eeMigrate`(≈1107) → `useE2eeConvert`(≈2491).** 두 훅 사이에 데이터가 오가지 않는다. 서로의 반환값을 인자로 받지 않는다
- **`convertingDocId` 순환이 TDZ 없이 도는 이유.** 상태 선언(≈528)과 `useLiveDoc` 호출(≈679)은 App 에 그대로 있다. `useE2eeConvert` 는 setter(`setConvertingDocId`)와 ref(`liveSessionRef`)만 받는다. `useLiveDoc` 가 읽는 값 중 이 훅이 만드는 것은 없다. 흐름은 다음과 같다: `prepareConvertDoc`(훅, 이벤트 뒤) → `setConvertingDocId(docId)` → App 다시 렌더 → `useLiveDoc(null)` → 세션 정리 → effect ③ 이 `liveSessionRef.current = null` → 훅의 기다림 고리가 빠져나간다. 호출 순서상 훅이 `useLiveDoc` 보다 한참 아래지만, 모든 연결이 setter·ref·effect 를 거쳐서 렌더 중 순서에 기대지 않는다. `useLiveDoc` 호출 자리는 옮기지 않는다(개요 4장)
- 두 호출 모두 조기 반환 `if (publicRoute) {`(≈3616)보다 위다. 공개 보기 렌더에서도 두 훅이 불린다. Ⓜ2 는 `bootPhase`·`store.kind` 판정으로, Ⓜ5 는 열쇠고리 유무로 지금처럼 돈다. 블록 e 도 지금처럼 돈다. 두 훅은 조기 반환 아래 값을 받지 않는다. 판정은 `publicView.spec.js` 다
- `useState`·`useRef` 호출이 App 안 다른 자리로 옮겨진다(Ⓜ1 은 ≈546 → ≈1107, Ⓒ1 은 ≈529~544 → ≈2491). React 에서 의미가 있는 것은 렌더마다 순서가 같은가뿐이다. 조건부 호출이 없으므로 같다

## 11. 열린 질문 (모두 기본값 — 기본값대로면 사람이 정할 갈림길 없음)

### Q1. 잠그기·초기화(Ⓜ4~Ⓜ6)를 어느 파일에 두나 — **기본값: `useE2eeMigrate.ts`**

- 이유
  - Ⓜ2~Ⓜ5 는 App 에서 이어진 한 덩어리다(≈1107~1268). 한 호출 자리로 옮기면 effect 두 개의 실행 자리와 블록 e 의 순서(d → e → f)가 한 줄도 움직이지 않는다(4.2·4.3)
  - 파일 이름은 개요 2.3 이 정한 계약이라 셋째 파일을 만들 수 없다. 개요 5.4 매핑은 다섯 구역을 두 파일에 묶어 두었고, 어느 쪽인지는 정하지 않았다
  - 이름이 "Migrate" 인데 잠그기·초기화가 들어가는 어색함은 머리 주석과 `architecture.md` 줄(10장)로 드러낸다
- 다른 쪽
  - **(b) 잠그기·초기화·블록 e 를 App 에 둔다**: 이름은 깔끔하다. 대신 App 감소가 약 55줄 준다(Ⓜ4·Ⓜ5·Ⓜ6 합 55줄에서 추정). 개요 5.4 행이 "잠그기·초기화" 를 이 조각에 두었으므로 그 행을 고쳐야 한다
  - **(c) `useE2eeConvert.ts` 에 둔다**: 한 훅은 한 자리에서만 불린다. Ⓒ 를 ≈1107 로 올리면 옵션 `commentAccessValue`(≈1309)가 TDZ 다. 잠그기를 ≈2491 로 내리면 블록 e 가 f·g·h 뒤로 가 3.3 을 어긴다. 피하려면 블록 e 와 두 상태를 App 에 두고 setter 를 넘기는 등 틀이 새로 생긴다
  - **(d) 셋째 파일 `useE2eeLock.ts`**: 이름이 가장 맞는다. 개요 2.3 계약을 먼저 고쳐야 한다(승인된 개요 수정 = 사용자 승인). 줄 감소는 같다

### Q2. `convertingDocId` 상태를 훅이 갖나 — **기본값: App 에 둔다, 훅은 setter 만 받는다**

- 이유: `useLiveDoc` 인자(≈679)와 `isConvertingDoc`(≈1295)가 렌더 중에 읽는다. 상태를 훅이 가지면 훅 호출이 ≈679 위로 가야 한다. 그러면 `commentAccessValue`·`resyncFromStore` 가 TDZ 다(4.1). 개요 4장 "`useLiveDoc` 호출 자리는 옮기지 않는다" 와도 맞는다
- 다른 쪽(훅이 갖는다): 두 옵션을 ref 로 우회해야 한다(3.1 셋째 항목). 이는 3.2 "클로저를 ref 로 바꾸지 않는다" 를 어기고, 새 최신값 대입이 생긴다

### Q3. `runE2eeReset` 을 옮기나 — **기본값: 옮긴다(Ⓜ6), effect ② 의 대입 줄은 그대로**

- 이유: 개요 5.4 행의 "초기화" 가 이 함수다. `useE2eeMigrate` 반환값이 effect ②(≈2362)보다 위에서 선언되므로, effect ② 는 한 글자도 안 바뀌고 TDZ 도 없다
- 다른 쪽(App 에 둔다): App 감소가 16줄 준다. 옵션에서 `setCurrentDocId`·`replaceHashUrl` 이 빠진다. 초기화 등록(Ⓜ5)과 본체가 두 파일에 갈라진다

### Q4. `e2eeResetStepRef` 선언을 옮기나 — **기본값: App 에 두고 `useE2eeMigrate` 호출 바로 위로 올린다**
