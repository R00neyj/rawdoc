# F-2120 로그인 상태 사이드바 목록 자동 갱신 — 보임·포커스 복귀·주기

작성일: 2026-10-03
상태: 승인됨(2026-10-03, 사람 승인 — Q1 은 사용자가 절충안 45초·270 ms/행으로 확정). 사용자 보고(2026-10-03) "cli로 넣은 문서(혹은 공동 소유 폴더 작업자가 만든 문서)가 새로고침 전까지 사이드바에 반영안됨". 클라이언트만 바꾼다(서버 파일 소유 없음). 사람 결정은 **Q1(주기·행당 계수)** 하나 — 무료 플랜 하루 한도에 직접 닿는 값이라 숫자 표를 붙였다. 비용 계산 때문에 작은 명세 목표(150줄)보다 길다
범위 확인: `specs/product.md` 8장(범위 밖)에 목록 자동 갱신이 없다

## 정해진 것 (사용자 결정, 바꾸지 않는다)

1. 클라이언트 갱신만. 서버 푸시는 10장 한 문단(후속 F-3NNN)
2. 갱신 시점은 ① 탭 숨김→보임 ② 창 포커스 복귀 ③ 보이는 동안 주기 — 셋 다. PC 는 사이드바가 늘 떠 있다
3. 대상은 로그인 상태 서버 저장소 목록(내 문서·폴더, 공유받은 문서·공유받은 폴더 안 문서). 로그아웃(`idb`)은 대상 아님
4. 열린 문서 본문은 건드리지 않는다. IME 조합 중에는 반영하지 않고 끝날 때 따라잡는다. 이름 바꾸기·끌어 놓기·다중 선택을 흐트러뜨리지 않는다

## 근거 (직접 읽거나 돌린 것, 2026-10-03 HEAD `3bfeb9c`)

- **목록을 서버에서 다시 읽는 길은 이미 하나로 모여 있다.** `App.tsx` `listRefresher`(`cachedList.ts` `createListRefresher`, 한 번에 하나) → `resyncFromStore('bootMerge')` → `store.listFolders()` + `store.list()`(= `GET /api/docs` + `GET /api/shared`) → `applyResyncResult`(`mergeResyncList`, `flushSync`). 지금 이것을 부르는 것은 검색·지도·탭 신호 뒤 TTL 검사(`isListStale`, `LIST_FRESH_TTL_MS` 600,000)뿐이라, 아무것도 안 하면 다른 곳 변경이 **영영** 안 붙는다
- `App.tsx` `visibilitychange`·`pagehide` 효과는 `docSaverFlushRef` 만 부른다. `window` `focus` 듣는 곳 없음
- **실시간 채널**: 클라이언트 웹소켓은 `src/storage/liveSocket.ts`(문서별 DO, `useLiveDoc`·`bootFlow`) 하나뿐이다. `useLiveNotices.ts` 는 알림 띠 UI 훅이고 소켓이 아니다. 알림은 60초 HTTP 폴링(`useNotifications.ts`, F-2057 ETag + `md-notifications` 채널로 한 탭만 가져오기)

ETag 는 `GET /api/notifications` 만(`worker/notifications.ts` `notificationsEtag`·`ifNoneMatchHits`). 목록 ETag(`users.list_rev`)는 F-2056 사용자 결정 3 이 "재측정 뒤" 로 미뤄 둔 것

## 2. 순수 모듈 `src/app/listAutoRefresh.ts`

```ts
export const LIST_REFRESH_MIN_MS = 45_000        // Q1 확정(사용자, 2026-10-03)
export const LIST_REFRESH_MS_PER_ROW = 270       // Q1 확정 — 탭 하나가 시간당 읽는 행을 약 13,300 으로 묶는다
export const LIST_REFRESH_MAX_MS = 1_800_000
export const LIST_REFRESH_IDLE_MAX_STREAK = 2    // 무변화 연속 상한 → 최대 4배
export const LIST_FOCUS_GAP_MIN_MS = 10_000

export type ListRefreshReason = 'interval' | 'visible' | 'focus' | 'online' | 'sidebar'

export function baseIntervalMs(rows: number, overrideMs?: number): number | null
export function nextIntervalMs(base: number, idleStreak: number): number
export function focusGapMs(base: number): number
export function shouldStartListRefresh(input: {
  reason: ListRefreshReason
  now: number
  lastServerListAt: number | null
  intervalMs: number
  focusGapMs: number
  visible: boolean
  sidebarVisible: boolean
  online: boolean
  signedOut: boolean
}): boolean
export function nextIdleStreak(prev: number, outcome: { failed: boolean; changed: boolean }): number
export function listFingerprint(
  docs: readonly { id: string; title: string; updatedAt: number; folderId?: string | null; pinnedAt?: number | null; role?: string; e2ee?: unknown }[],
  folders: readonly { id: string; name: string; parentId: string | null }[],
): string
```

규칙:
- `baseIntervalMs`: `overrideMs` 가 `0` 이하면 `null`(끔). 양수면 그 값을 그대로 쓴다(최소·최대 무시 — e2e 용, 4.3). 없으면 `clamp(rows × LIST_REFRESH_MS_PER_ROW, LIST_REFRESH_MIN_MS, LIST_REFRESH_MAX_MS)`. `rows` = 지금 사이드바 `docs.length + folders.length`(공유 문서 포함)
- `nextIntervalMs` = `min(base × 2^min(idleStreak, 2), max(base, LIST_REFRESH_MAX_MS))` — 기본 45초면 45·90·180초
- `focusGapMs` = `min(base, max(LIST_FOCUS_GAP_MIN_MS, base / 4))`
- `shouldStartListRefresh`: `visible`·`sidebarVisible`·`online` 중 하나라도 거짓이거나 `signedOut` 이면 거짓. `lastServerListAt` 가 `null` 이면 참. `now < lastServerListAt`(시계 역행)이면 거짓. 그 밖에 `'interval'` 은 경과 ≥ `intervalMs`, 나머지 넷은 경과 ≥ `focusGapMs`
- `nextIdleStreak`: `failed` 이거나 `!changed` 면 `min(prev + 1, 2)`, 아니면 `0`
- `listFingerprint`: 문서는 배열 순서대로 id·제목·`updatedAt`·`folderId`·`pinnedAt`·`role`·`e2ee` 를, 폴더는 id·이름·`parentId` 를 구분 문자로 이은 문자열. 내용이 같으면 다른 배열 객체여도 같다

**계수 뜻**: 문서가 많을수록 한 번이 비싸므로 주기를 늘려 탭 하나의 시간당 읽기를 `3600 / 0.27 ≈ 13,300` 행 근처로 묶는다(행 166 개 이하면 최소 45초가 이긴다)

## 3. 훅 `src/app/useListAutoRefresh.ts`

### 3.1 켜지는 조건
`store.kind === 'server'` 이고 `bootPhase === 'ready'` 이고 `account.state === 'in'` 일 때만. `baseIntervalMs` 가 `null` 이면(덮어쓰기 0) 아무것도 안 한다. 꺼지면 타이머·듣기를 모두 걷는다

### 3.2 시점
- **타이머**: 다음 판정 시각 = `(store.lastServerListAt() ?? 지금) + nextIntervalMs(base, idleStreak)`. 갱신이 끝날 때마다, 그리고 아래 사건마다 다시 건다. 기준이 `lastServerListAt` 이라 검색·지도·부팅이 서버 목록을 읽으면 다음 주기가 그만큼 밀린다
- **사건**: `document` `visibilitychange`(보임이 될 때 `'visible'`), `window` `focus`(`'focus'`), `window` `online`(`'online'`), 사이드바가 안 보이다 보이게 될 때(`'sidebar'`). 이 넷은 `idleStreak` 을 0 으로 되돌린 뒤 판정한다
- **멈춤**: 숨김·사이드바 안 보임·`navigator.onLine === false`·`syncState.signedOut` 이면 타이머를 걷는다(돌지 않는다). 사이드바 보임 = 좁은 화면이면 `sidebarOpen`, 아니면 `!sidebarCollapsed`
- 시작은 `listRefresher.run()` — 이미 진행 중(검색의 뒤 새로 읽기 등)이면 그것에 합류하므로 요청이 겹치지 않는다(`createListRefresher`, F-2056 5.4)
- DO 소켓 재연결 중인지는 보지 않는다 — 목록은 HTTP 이고 소켓과 무관하다

### 3.3 끝난 뒤
- 실패 = 갱신 전후 `store.lastServerListAt()` 이 그대로(`/api/docs` 네트워크 오류·5xx·401). 변화 = 갱신 전후 `listFingerprint(docsRef.current, foldersRef.current)` 가 다름. `nextIdleStreak` 으로 갱신
- 반영 보류(3.4)로 버린 회차는 `idleStreak` 을 바꾸지 않는다

### 3.4 반영 보류와 따라잡기 (불변조건·사용자 결정 4)
- **보류 조건** = 조합 중 ∨ 끌기 중 ∨ `document.activeElement` 가 `.tree-rename-input`
  - 조합 중: `window` 캡처 `compositionstart` 로 켜고 `compositionend` 또는 `window` 캡처 `blur` 로 끈다(포커스 잃은 조합은 끝난 것, CLAUDE.md 불변조건. 선례 `useE2ee.ts` 4.2 판정)
  - 끌기 중: `window` 캡처 `dragstart` 로 켜고 `dragend`·`drop` 으로 끈다
- `listRefresher` 의 `refresh`(App) 는 `resyncFromStore('bootMerge', gate)` 를 부른다. `resyncFromStore` 는 `shouldApplyListResult` 를 통과한 **직후, `setFolders`·`applyResyncResult` 전에** `gate.canApply()` 를 묻고, 거짓이면 반영하지 않고 `lastAppliedListSeqRef` 도 올리지 않은 채 `gate.markDeferred()` 를 부르고 끝낸다. 검색·지도가 시작한 뒤 새로 읽기도 같은 `refresh` 라 같이 보류된다(검색 결과는 캐시를 읽으므로 영향 없음)
- 서버 응답은 이미 `md-remote` 캐시와 `lastSharedList()` 에 들어가 있다(`runList`·`listFolders`). 그래서 **따라잡기는 서버를 다시 부르지 않고** 보류가 풀린 순간(`compositionend`·`blur`·`dragend`·`drop`·`.tree-rename-input` 의 `focusout`) `setTimeout 0` 뒤 보류 조건을 다시 보고 `resyncFromCache('bootMerge')` 를 한 번 부른다. 따라잡을 회차가 없으면 안 부른다
- 다중 선택은 보류하지 않는다 — 선택은 id 집합이고 사라진 id 만 빠진다. 새 줄이 끼어 순서가 바뀌는 것은 다른 탭 신호(F-296)와 같다
- 이 경로는 사이드바 state 만 바꾼다. 편집기·`Y.Doc` 에 원격 업데이트를 넣지 않는다

### 3.5 탭 여러 개 — 조율하지 않는다
보이는 탭마다 따로 돈다. 숨긴 탭은 멈추므로 겹치는 것은 창 여러 개를 나란히 띄운 경우뿐이다. 다른 안은 9장 Q2

### 3.6 상태·오류
새 UI 문구·새 화면 상태 없음. 갱신은 조용히 일어난다. 실패해도 알림 없음(다음 주기에 다시, 연속 실패면 최대 4배로 늘어남). 쓰는 기존 문구는 `이 문서가 다른 곳에서 삭제되었습니다. 지금 화면의 내용은 저장되지 않습니다.` 하나. 설정 항목도 두지 않는다(9장 Q3)

## 4. 배선

### 4.1 `App.tsx`
- `resyncFromStore(deletedSource, gate?)` — `gate?: { canApply: () => boolean; markDeferred: () => void }`. 기존 부르는 곳(다섯 훅·탭 신호·알림 열기)은 `gate` 를 안 넘기므로 지금 그대로. 반환 타입 `Promise<void>` 유지
- `resyncFromCache(deletedSource = 'tab')` — 인자 하나 추가. 탭 신호는 지금처럼 `'tab'`
- `listRefreshDepsRef` 에 훅이 돌려준 `gate` 를 더하고, `createListRefresher` 의 `refresh` 가 `resyncFromStore('bootMerge', deps.gate)` 를 부른다
- 훅 호출: `useListAutoRefresh({ enabled, store, listRefresher, resyncFromCache, docsRef, foldersRef, sidebarVisible })` 정도. 이름은 구현자 몫, 위 의존만 넘긴다

### 4.2 e2e 덮어쓰기 — `window.__listAutoRefreshMs`
- 훅이 판정마다 `window.__listAutoRefreshMs` 가 `number` 면 `baseIntervalMs(rows, 그 값)` 에 넘긴다(`declare global` 은 훅 파일에). 선례 `window.__yProviderFactory`(`remoteGate.ts`)
- 이유: 기존 e2e 46개 파일이 `fakeServer` 로 로그인 상태를 만들고, 일부는 `/api/docs` GET 수를 세거나(`listReuse.spec.js` A1·A2·M1 등) `page.clock.fastForward('10:01')` 로 시간을 건너뛴다. 30초 타이머가 끼면 수가 흔들린다

### 4.3 `e2e/fixtures/fakeServer.js`
- 옵션 `listAutoRefreshMs = 0` 을 더하고, 받은 `page`/`context` 에 `addInitScript` 로 `window.__listAutoRefreshMs` 를 그 값으로 둔다. 기본 0 이라 기존 e2e 는 주기 갱신이 꺼진 채 지금과 같다. 별도 `addInitScript` 를 하나 더 거는 대신 옵션으로 두는 까닭: 여러 init 스크립트의 실행 순서는 Playwright 가 보장하지 않는다

## 5. 비용 — 결론

| 계정 (N 문서, F 폴더) | 기본 주기 B | 시간당 행 (B / 무변화 4B) | 시간당 요청 (B / 4B) | 보이는 8시간 하루 행 (B / 4B) |
| --- | --- | --- | --- | --- |
| 24, 3 (보고 계정 규모) | 30초 | 4,320 / 1,080 | 360 / 90 | 34,560 / 8,640 |
| 500, 20 | 93.6초 | ≈ 20,300 / 5,100 | ≈ 115 / 29 | ≈ 163,000 / 41,000 |
| 1,000, 50 | 189초 | ≈ 20,200 / 5,000 | 57 / 14 | ≈ 161,000 / 40,000 |
| 10,000, 200 | 1,800초(상한) | ≈ 20,400 / 20,400 | 6 / 6 | ≈ 163,000 / 163,000 |

- 행 = 회차 × (N+F+9). 요청 = 회차 × 3. 본문 받기(바뀐 내 문서마다 요청 1)는 빼고 셌다
- **응답 크기**: 10,000개 계정은 30분에 2.26 MB(압축 전). 주기가 문서 수에 비례하므로 탭 하나가 받는 양은 계정 크기와 거의 무관하게 시간당 약 4.5 MB 이하다(`20,000행 × 225 B`). 작은 계정은 30초 × 5.4 KB = 시간당 약 0.65 MB
- **무료 한도에 견줌**: 작은 계정이 하루 8시간 계속 바뀌는 목록을 보면 요청 2,880 — Workers 100,000/일 ÷ 2,880 ≈ **34명**이 이 기능만으로 하루 요청을 다 쓴다(알림 폴링 하루 480 을 더하면 약 29명). 무변화로 4배가 되면 약 138명. 문서 500개 계정은 D1 하루 읽기 5,000,000 ÷ 163,000 ≈ **30명**. 두 숫자가 Q1 의 근거다
- 클라이언트 쪽: `runList` 는 요약마다 `cache.getDoc`, 끝에 `cache.getDocs`(본문 포함 전체)를 읽는다. 큰 계정에서 갱신 한 번의 IndexedDB 비용은 재지 않았다 → 사람 확인 H2
- 서버 지원으로만 줄일 수 있는 몫(목록 ETag 304 — 바뀐 것 없으면 인증 행만)은 10장 후속

## 9. 열린 질문

### Q1 주기 하한과 행당 계수 — **확정: 45초 · 270 ms/행** (사용자 결정 2026-10-03, 아래 표의 30초·60초 사이 절충)

확정값 기준 수치(30초 안의 2/3, 60초 안의 4/3 배로 환산): 작은 계정 하루 요청 1,920 / 480, 무료 한도를 채우는 작은 계정 수 ≈ 52 / 208, 500개 계정 하루 행 ≈ 108,000, D1 읽기 한도를 채우는 500개 계정 수 ≈ 46, CLI 로 만든 문서가 뜨기까지 최대 45초(무변화 뒤 3분). 위 상수와 U1~U3 기대값, 5장 표·본문의 30초 기준 수치는 구현이 이 값으로 다시 계산해 맞춘다(명세 본문은 안 고침 — 구현 보고에 적는다)

| 안 | 작은 계정 하루 요청(8시간, B / 4B) | 이 기능만으로 Workers 무료 한도를 채우는 작은 계정 수 | 500개 계정 하루 행(B) | D1 읽기 한도를 채우는 500개 계정 수 | CLI 로 만든 문서가 뜨기까지 최대 |
| --- | --- | --- | --- | --- | --- |
| **30초 · 180 ms (기본)** | 2,880 / 720 | ≈ 34 / 138 | ≈ 163,000 | ≈ 30 | 30초(무변화 뒤 2분) |
| 60초 · 360 ms | 1,440 / 360 | ≈ 69 / 277 | ≈ 81,000 | ≈ 61 | 60초(무변화 뒤 4분) |

- 기본 30초 까닭: 사용자가 기본값 후보로 든 값이고, 포커스 복귀(10초 간격)와 함께면 "터미널에서 `rawdoc new` 하고 돌아오면 바로" 가 된다
- 60초를 고르면: 상수 둘(`LIST_REFRESH_MIN_MS = 60_000`, `LIST_REFRESH_MS_PER_ROW = 360`)과 U1~U3 의 기대값만 바뀐다. e2e 는 덮어쓰기를 쓰므로 그대로
- 지금 실제 사용자 수는 이 명세가 모른다. 사용자가 수십 명 단위로 늘기 전에 10장 목록 ETag 가 필요하다는 신호로 읽는 것이 맞다

### Q2 탭 사이 조율 (기본: 안 한다 — 기본값대로 간다)
숨긴 탭은 멈추므로 이득은 "보이는 창 여러 개" 에만 있다. 하려면 F-2057 처럼 BroadcastChannel 로 "목록 읽음(시각)" 을 알리고 받은 탭은 `resyncFromCache` + 자기 타이머를 미는 방식이 된다. 다만 `lastSharedList()` 가 탭 메모리라(F-2056 3.1) 받은 탭의 공유 목록이 낡는 문제가 같이 온다 — 그 비용에 비해 이득이 작다

### Q3 설정에서 끄기 (기본: 두지 않는다 — 기본값대로 간다)
갱신은 조용하고 반영 보류가 입력을 지킨다. 끌 이유가 비용뿐인데 그것은 사용자가 아니라 운영이 정할 값이다

### Q4 주기 갱신에서 바뀐 본문 받기 (기본: 지금 `list()` 그대로 — 기본값대로 간다)
본문을 미루려면 `serverStore.list()` 에 옵션이 생기고 F-2042 `get()` 대기 규칙까지 손대야 한다. 다른 기기가 큰 문서를 계속 고치는 경우의 체감은 H2 로 본다

## 10. 후속 (이 명세 밖)

**서버 푸시·조건부 목록 (F-3NNN)**: 가장 싼 다음 단계는 목록 ETag — `users.list_rev` 를 문서·폴더·초대 쓰기 batch 에서 올리고(F-2057 `notif_rev` 와 같은 모양) `GET /api/docs`·`/api/folders`·`/api/shared` 가 `If-None-Match` 면 304. 무변화 회차가 인증 행(약 2~3)만 읽게 되어 5장 표의 B/4B 행 수가 대부분 사라진다. 다만 `/api/shared` 는 남의 쓰기(폴더 소유자의 새 문서)로도 바뀌므로 받는 쪽 리비전을 같이 올려야 한다. 그다음이 푸시 — 사용자별 DO(또는 알림 채널)로 "목록 바뀜" 신호를 보내 주기를 없앤다. 무료 플랜에서는 DO 요청 100,000/일·Hibernation 조건(product.md Q42)을 같이 따진다. 둘 다 서버 변경이라 사용자 결정 1 에 따라 여기서 하지 않는다
