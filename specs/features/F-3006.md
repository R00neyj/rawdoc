## 2. 알람 하나를 나눠 쓰기 (F-3001 3.3 규칙의 구체화)

### 2.1 걸기 — `scheduleAlarm(at)`

- 규칙: **걸린 알람이 있고, 그 시각이 지금보다 뒤이고, `at` 보다 늦지 않으면** 건너뛴다. 그 밖(없음·지났음·`at` 이 더 이름)은 `setAlarm(at)` 하고 기억한다. 지금 F-2027 동작(같은 창 안 되풀이 안 함)은 이 규칙의 한 경우라 C6·C8 의 `alarms` 가 그대로 한 번이다
- 걸린 시각을 모를 때(새 인스턴스 = 쫓겨난 뒤, 또는 `setAlarm` 이 던진 뒤) **한 번** `host.getAlarm()` 으로 읽는다. 호스트에 `getAlarm` 이 없으면(테스트 가짜) "없음". `alarm()` 이 시작하면 "없음" 으로 안다(런타임이 막 소비했다)

### 2.2 울렸을 때 — `alarm()` 순서

1. `gone`·`!loaded` 면 끝(지금 그대로 — C16)
2. **flush** — 지금의 `runFlush(false, true, true)` 에 하나 더: **이 flush 는 연결 점검(`revalidateConnections`)을 건너뛴다.** 이유는 4.3 의 하위 요청 예산(점검은 연결 수만큼 D1 을 부른다). 점검은 다음 보통 flush 와 권한 바뀜 RPC(`revalidateConnections(email)`)가 그대로 한다. flush 가 먼저인 이유: 방에만 있던 새 댓글이 알림 행이 되어 이번 묶음에 들고, 지운 댓글의 알림 행이 먼저 지워진다(F-502). 느린 저장이 미룬 것도 여기서 쓰이므로 느린 저장 몫의 다음 알람은 없다
3. **푸시** — VAPID 가 없으면(2.3) 여기서 끝. 있으면 `runDocPush`(4장). 결과에 따라 2.1 규칙으로 다시 건다: `next`(가장 이른 미래 행) / 1초 뒤(남은 사람·200행 넘침, 4.3) / 10분 뒤(재시도, 6장)
4. **`alarm()` 은 던지지 않는다.** 푸시 쪽 모든 예외를 잡아 6장으로 보낸다 — 알람 처리기가 던지면 런타임이 스스로 알람을 다시 부른다(Cloudflare 일반 지식, **이번에 확인하지 않음**) → 10분 한 번 규칙이 깨진다

### 2.3 VAPID 보관

- F-3005 의 `pushOn`(불리언)을 **`{ vapid: PushVapid; auth: VapidAuth } | null` 보관**으로 바꾼다. 처음 필요할 때 `loadVapid` 한 번, `auth = createVapidAuth(keys, subject)` 는 인스턴스 수명 동안 하나(출처별 JWT 캐시가 여기 산다 — F-3002 3.3). `buildCommentPlan` 의 켜짐 판정은 이 값이 null 이 아닌지로. 알람 3번에서 처음 부를 수도 있다. `loadVapid` 는 D1 을 부르지 않는다 → **비밀 값이 없으면 알람의 D1 호출은 지금과 같다**(A11)

## 3. 스냅숏 끝 MIN (F-3001 3.4 ② 뒷부분)

- 조건: 이번 batch 에 알림 초안이 있고 `pushDueAt` 이 null 이 아닐 때만(= 푸시 켜짐 + 넣는 행 있음). 그 밖에는 batch 가 지금과 글자까지 같다
- batch **맨 끝**에 한 문장(계약 — 테스트 `label()` 이 접두사로 알아본다):

```sql
SELECT MIN(push_due_at) AS due FROM notifications WHERE doc_id = ?1 AND push_due_at > ?2
-- ?2 = batch 의 now − PUSH_STALE_MS
```

- **`PUSH_STALE_MS` 보다 오래된 행을 뺀다**(F-3005 4.4 조건). 안 빼면 남은 옛 행 때문에 알람이 곧바로 울려 새 댓글이 3분 묶음 없이 나간다
- batch 가 돌아오면 마지막 결과의 `due` 가 숫자일 때 2.1 로 건다. `judgeUsage` 가 읽는 자리(`results[0|1]`)는 그대로다. batch 가 던지면 알람 없음(지금의 계획 되돌리기 그대로)
- 알려진 한계: 1시간 안에 남은 행(6장에서 두 번 실패하고 포기한 묶음)이 있으면 알람이 곧 울리고 새 행도 그 묶음에 들어 곧바로 나간다. D1 이 두 번 연달아 실패한 뒤에만 생긴다

## 4. 모아 보내기 — `worker/pushRun.ts`

### 4.1 공개 모양 (계약)

```ts
export const PUSH_READ_ROWS_MAX = 200
export const PUSH_FOLLOWUP_MS = 1_000
export const PUSH_RETRY_MS = 600_000
export const PUSH_SEND_CONCURRENCY = 6

export type PresenceConn = { email: string; connectedAt: number | null; lastPing: number | null }
export function presentEmails(conns: Iterable<PresenceConn>, now: number): Set<string>   // 소문자 이메일 (5장)

export type DocPushInput = {
  db: D1Database
  docId: string
  now: number
  auth: VapidAuth
  present: ReadonlySet<string>
  fetchImpl?: typeof fetch
}
export type DocPushResult =
  | { type: 'done'; next: number | null; followUp: boolean }   // next = 가장 이른 미래 행의 push_due_at
  | { type: 'failed' }                                          // D1 이 던졌다 — 재시도 판단은 부르는 쪽 (6장)
export async function runDocPush(input: DocPushInput): Promise<DocPushResult>
```

- 받는 사람 묶기·빼기·예산 자르기는 D1 없는 **순수 함수**로 떼어 둔다(이름은 구현이 정한다) — 8.1 의 대부분을 D1 없이 판정

### 4.2 모으기

한 문장(질의 1):

```sql
SELECT n.id, n.recipient_email, n.kind, n.thread_id, n.actor_email, n.doc_title, n.excerpt, n.created_at, n.read_at, n.push_due_at
FROM notifications n
WHERE n.doc_id = ?1 AND n.push_due_at > ?2
  AND EXISTS (SELECT 1 FROM docs d WHERE d.id = ?1 AND d.e2ee_key IS NULL)
ORDER BY n.push_due_at, n.id LIMIT 200
-- ?2 = now − PUSH_STALE_MS
```

- 0행이면 `{ type: 'done', next: null, followUp: false }` — batch 없음. `LIMIT` 값은 `PUSH_READ_ROWS_MAX`. **첫 행의 `push_due_at` 이 지금보다 뒤면 아직 차례가 아니다**(느린 저장 알람에 깨어난 경우 등) → 보내지 않고 `next` = 그 값
- 그 밖에는 읽은 **모든 행**이 한 묶음이다 — 아직 창이 안 끝난 뒤쪽 행까지(F-3001 3.4 ③ 그대로)
- 금고가 됐거나 없어진 문서는 `EXISTS` 로 0행(F-3001 3.9). 그 행들은 F-502 가 지운다

### 4.3 빼기와 하위 요청 예산

받는 사람(`recipient_email`, 이미 소문자 — `loadDocPeople`)별로:

| 경우 | 보내나 | 그 행 |
| --- | --- | --- |
| `read_at` 있음 | 그 행 빼기 | NULL |
| `present` 에 있음(5장) | 그 사람 전부 빼기 | 모두 NULL |
| 남은 행 0 | — | 모두 NULL |
| 산 구독 0(`listLivePushSubscriptions` — 로그아웃·만료 세션 빠짐, A9) | — | 모두 NULL |
| 그 밖 | 기기마다 `commentPushPayload(docId, 남은 행)` 한 건, `Topic` = `pushTopic(docId)` | 모두 NULL |

- 구독 질의는 보낼 사람이 남았을 때만(질의 1). **예산**: 한 알람 호출의 D1 은 최대 12 — 빈 방을 깨운 `onLoad` 2(`READ_ROW_SQL`·댓글 표지) + 2번 flush 최대 7(막힘 읽기 1, 접근 집합 3, batch·다시 읽기·batch 3 — 연결 점검은 2.2 로 뺐다) + 푸시 3(모으기·구독·결과 batch). 하위 요청 50(F-3001 p5)에서 12 와 여유 2 를 빼 **한 호출 보내기 최대 36** = `PUSH_SENDS_PER_RUN_MAX`(40 → 36, 갱신 대상). D1 호출이 하위 요청으로 세어진다는 것과 batch 하나가 1로 세어진다는 것은 F-3001 의 가정 그대로 — **확인하지 않았다**
- 이메일 오름차순으로 **사람 단위**로 담는다. 다음 사람의 기기 수를 더하면 36 을 넘으면 거기서 멈춘다(한 사람 최대 5대라 첫 사람은 늘 들어간다). 못 담은 사람의 행은 **건드리지 않고** `followUp: true`. 모으기가 200행을 꽉 채워 읽었을 때도 `followUp: true`
- 보내기는 동시에 최대 `PUSH_SEND_CONCURRENCY`(6) — Workers 동시 연결 6(일반 지식, 확인 안 함)에 맞춘다. 한 번에 다 던지면 줄 선 요청이 `sendPush` 의 10초 시간 초과를 먼저 먹을 수 있다. 최악 36건 ≈ 6묶음 × 10초 = 60초(DO 는 벽시계 제한이 이보다 넉넉하다고 알려져 있다 — 확인 안 함)

### 4.4 결과 batch (질의 1)

한 `db.batch` 로:
1. `UPDATE notifications SET push_due_at = NULL WHERE id IN (SELECT value FROM json_each(?1))` — 이번에 다룬 행 **모두**(보냈든 뺐든. 못 담은 사람 행만 제외)
2. `UPDATE notifications SET push_due_at = NULL WHERE doc_id = ?1 AND push_due_at <= ?2` — 1시간 넘은 행(F-3005 Q1 답: 매일 Cron 대신 여기서 치운다)
3. 보낸 기기마다 `pushResultStatements(db, sub, outcome, now)`(404·410 지움, 4xx 실패 수, 하루 지난 `last_ok_at` — F-3003 그대로. 보통은 0문장)

- **오래된 행은 행 단위로 뺀다**(F-3001 3.4 ③ 의 "가장 오래된 행이 오래된 묶음" 을 바꿈 — 갱신 대상). 묶음 단위면 옛 행 하나 때문에 같은 사람의 새 댓글 푸시까지 사라진다
- batch 가 던지면 `failed` — 이미 보낸 푸시가 있으면 재시도 때 한 번 더 간다(같은 `tag`·`Topic` 이라 OS·푸시 서비스가 바꿔 끼운다)
- `next`: 결과 batch 뒤에는 null(읽은 행을 모두 치웠다. 그 사이 새로 들어온 행은 그 스냅숏의 MIN 이 스스로 건다)

## 5. "열어 둠" 판정

- **연결 시각**: `DocRoom.onConnect` 가 신원과 같은 `setState` 에 `connectedAt: Date.now()` 를 더한다. 키 이름은 `docRoomCore.ts` 가 `CONNECTED_AT_KEY = 'connectedAt'` 로 내보낸다(`COMMENT_RATE_KEY` 와 같은 방식). 첨부라 hibernation 을 넘긴다. 이 배포 전에 열린 연결은 이 값이 없다 → null
- **마지막 ping**: `DocRoomHost` 에 선택 항목 `lastPing?(conn): number | null` — `DocRoom` 은 `ctx.getWebSocketAutoResponseTimestamp(conn)?.getTime() ?? null`. 자동 응답은 DO 를 깨우지 않고 런타임이 시각을 남긴다. 없으면(테스트 가짜) null
- `presentEmails`: 연결마다 `readConnState(state)?.email` 을 소문자로, `max(connectedAt, lastPing)` 이 `now − PUSH_PRESENCE_FRESH_MS`(90초) 이상이면 넣는다. 둘 다 null 이면 넣지 않는다. 역할은 보지 않는다(view 도 "열어 둠"). `alarm()` 이 `runDocPush` 직전에 `host.connections()` 로 한 번 만든다
- 숨은 탭도 열어 둠(F-3001 Q4 답). 휴대폰이 잠겨 ping 이 멈추면 90초 뒤부터 빠진다

## 6. 재시도 — 10분 한 번

- **조건**: `runDocPush` 가 `failed`(모으기·구독·결과 batch 중 D1 이 던짐). 푸시 서비스 429·5xx·시간 초과는 실패가 아니다 — 그 기기만 이번에 건너뛴다(F-3001 3.1 표)
- **표지**: DO SQLite `ydoc_meta` 의 키 **`push_retry`**(`YStore.getMeta`·`setMeta`). 값 = 재시도를 건 때(ms), `'0'` 또는 없음 = 표지 없음. 메모리에 두지 않는 이유: 10분 사이에 빈 방은 쫓겨난다
  - 실패 + 표지 없음 → 표지 = now, 2.1 로 `now + PUSH_RETRY_MS` 에 건다
  - 실패 + 표지 있음 → **포기**: 표지 `'0'`, `console.warn` 한 줄, 알람을 걸지 않는다
  - `done` + 표지 있음 → 표지 `'0'`
- **무한 반복이 없는 근거**: 푸시가 스스로 거는 알람은 셋뿐이다 — (a) 1초 뒤: 결과 batch 가 **커밋되어** 행을 줄인 뒤에만(행 수는 유한, 새 행은 스냅숏에서만 생긴다) (b) 10분 뒤: 표지가 없을 때만, 걸면서 표지를 세운다 → 실패가 이어져도 한 번 (c) `next`: 아직 차례가 아닌 미래 행이 있을 때만 — 그 시각에 울리면 차례다. 포기한 행은 사용자의 다음 댓글(스냅숏 MIN)이 다시 깨울 때까지 아무 알람도 걸지 않는다
- 표지 쓰기는 실패·회복 때만(DO 행 쓰기 1)

## 11. 열린 질문

### Q1. 한 호출 보내기 상한 — **기본값: 36 으로 줄인다(F-3001 2.5 의 40 과 다름)**

- 이유: 4.3 의 최악 D1 12 를 넣으면 40 은 하위 요청 50 을 넘는다(52). 36 이면 넘는 경우가 없다
- 다른 안: 40 유지 + "flush 가 D1 을 불렀으면 이번 호출은 보내지 않고 1초 뒤 알람으로 넘김". 상수는 그대로지만 알람이 늘고, 넘긴 알람이 또 flush 를 만나는 경우를 막을 메모리 표지가 필요하다. 바뀌는 것: 2.2 에 분기 하나, 8.2 에 한 행, `pushPayload.ts` 는 소유에서 빠진다

### Q2. 알람 flush 의 연결 점검 건너뛰기 — **기본값: 건너뛴다**

- 이유: 점검은 연결마다 D1 을 불러 예산을 못 정한다. 60초 점검은 보통 flush 와 권한 바뀜 RPC 가 계속 한다 — 편집이 없는 방은 지금도 점검이 돌지 않는다
- 다른 안: 점검을 두고 그 호출에서 보낸 연결 수만큼 보내기 상한을 줄인다(연결 × 최대 3). 연결이 12개를 넘으면 그 호출은 못 보내고 1초 뒤로 — 규칙이 하나 더 는다
