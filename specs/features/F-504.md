## 2. 전체 흐름 (한 문단씩)

- **읽는 곳**: 편집기 `Y.Doc` 의 `comments`(`Y_COMMENTS_NAME`)와 `content` `Y.Text`(`binding.ytext`). 방 Doc 은 보지 않는다. 원격 댓글은 본문과 같은 게이트(`remoteGate.ts`)를 지나 편집기 Doc 에 닿는다
- **가진 것**: CM 상태 필드 하나(이하 "댓글 필드")가 스레드마다 지금 범위(또는 고아), 열림·해결, 활성 스레드 id, 앵커 후보 범위, "경계가 지워져 다시 풀어야 할 스레드" 집합을 든다. 장식·거터·레일 좌표는 모두 이 필드에서 나온다
- **움직이는 길 셋**: 편집 트랜잭션(로컬·원격·되돌리기 모두 CM 트랜잭션이다) → 필드가 **매핑**한다. `comments` 가 바뀜 → 바뀐 키만 **다시 푼다**. 경계 글자가 지워짐 → 300ms 쉼 뒤 그 스레드만 **다시 푼다**(12장 Q1). 다시 푼 결과는 효과(`StateEffect`) 하나로 필드에 넣는다
- **조합 중**: 매핑은 계속한다. 장식의 모양·집합을 바꾸는 효과(다시 푼 결과·활성·후보·붙이기)는 보내지 않고 모았다가 `forceRecalc` 가 오면 한 번에 보낸다

### 3.1 `attach` / 떼기

- `attach` 는 한 번에 하나. 이미 붙어 있으면 먼저 뗀다(`attachRemoteCursors` 와 같게)
- 붙일 때: `comments` 관찰 시작(`map.observe` 로 바뀐 키 모으기 + `doc.on('afterTransaction')` 에서 넘기기, 5.2), ① 전부 풀기(5.1), 댓글 거터 켜기(4.3), 레일 좌표 한 번 보내기
- 뗄 때: 관찰·타이머 해제, 필드 비움(장식 0, 거터 표시 0), 거터 끄기. 문서·`Y.Doc` 은 건드리지 않는다
- 편집기 `destroy()` 는 떼기를 먼저 부른다(`detachRemoteCursors` 와 같은 자리)
- F-505 는 **댓글을 볼 수 있는 경로(F-500 4.1 표 "댓글 보기 = 됨")에서만** 붙인다. 금고 문서·보기 모드 전용 화면·공유 화면은 붙이지 않는다

### 3.2 `ranges()`

- 키 = 지금 `comments` 의 올바른 첫 댓글 id 전부(열림·해결). 값 = 지금 범위, 또는 고아면 `null`. 답글·`invalid`·`strays` 는 없다
- **다시 풀기를 기다리는 스레드(경계가 지워진 것)는 이 자리에서 `resolveCommentAnchor` 로 풀어 돌려준다** — 효과를 보내지 않는 읽기다. 그래서 F-508 이 이 값으로 `toCommentRecord` 를 만들면 Yjs 기준 위치가 기록된다. 필드(화면)는 300ms 뒤에 같은 값으로 따라온다
- 붙어 있지 않으면 빈 `Map`

### 3.3 `setActive` / `reveal`

- `setActive(id)`: 그 스레드의 앵커에 활성 클래스. `null` 이면 끈다. 없는 id·고아·해결된 스레드면 활성 클래스가 아무 데도 붙지 않는다(값은 기억한다 — 앵커가 되살아나면 붙는다). **활성 상태의 주인은 F-505** 다. F-504 는 클릭을 알리기만 하고(`onActivate`) 스스로 활성을 바꾸지 않는다
- `reveal(id)`: 앵커 시작을 편집 영역 **가운데**로 스크롤하고 `setActive(id)`. **커서·선택은 옮기지 않는다**(F-500 4.4 5번). 스크롤은 `scrollToHeading` 과 같은 두 단계(먼저 `EditorView.scrollIntoView(from, { y: 'center' })`, 그려진 뒤 rAF 2회에 실측으로 고침)를 따른다. 고아·없는 id·편집기가 숨겨짐(`scrollDOM.clientHeight === 0`)이면 아무것도 안 하고 `false`

### 3.4 후보 — `beginDraft` / `takeDraft` / `clearDraft` (선택 → 앵커 만들기 도우미)

F-500 4.4 1번 "카드를 연 순간의 범위를 쓴다, 그 사이 편집은 매핑으로 따라간다" 를 편집기 쪽에서 맡는다

- `beginDraft()`: 주 편집기의 **주 선택**(`selection.main`)이 비었거나, 조합 중이거나, 붙어 있지 않으면 `null`. 아니면 그 범위를 후보로 필드에 넣고(후보 장식 4.1) 범위를 돌려준다. 이미 후보가 있으면 바꾼다
- 후보는 앵커와 같은 규칙으로 매핑된다(시작 `assoc 1`, 끝 `assoc -1`)
- `takeDraft()`: 후보를 지우고, 매핑된 범위가 `toAnchorRange` 로 `null`(빈 범위)이면 `null`. 아니면 `{ anchor: createCommentAnchor(ytext, from, to), range, quote: commentQuote(slice) }`. `anchor` 가 `null` 이면(범위가 `Y.Text` 밖 — 생길 수 없지만) `null`
- `clearDraft()`: 후보를 지운다(취소)
- 표 칸 하위 편집기 안의 선택은 주 선택이 아니다 — 칸 안에서는 후보를 만들 수 없다(칸 편집 중 주 선택은 표 원문 시작의 빈 커서라 `null`). 주 편집기에서 표를 덮어 고른 선택은 된다
- 읽기 전용(`readOnly`·`editable: false`)이어도 동작한다 — 보기 권한자(F-506)가 쓴다. 읽기 전용에서 마우스 선택이 CM 선택으로 들어오는지는 F-506 e2e 가 판정한다(이 PC 에서 확인하지 않았다)
- `null` 일 때 띄울 문구는 F-505 가 정한다(기본 C1 `댓글을 달 부분을 먼저 선택하세요.`)

## 4. 화면 표시

### 4.1 앵커 장식 (mark 만)

| 대상 | 장식 | 클래스·속성 (계약) |
| --- | --- | --- |
| 열린 첫 댓글, 범위 있음 | `Decoration.mark` 하나 `[from, to)` | `class="cm-comment-anchor"`, `data-thread-id="{id}"` |
| 그중 활성 스레드 | 같은 mark 에 클래스 하나 더 | `cm-comment-anchor cm-comment-anchor-active` |
| 앵커 후보(3.4) | 별도 `Decoration.mark` | `class="cm-comment-anchor-draft"` (속성 없음) |
| 해결된 첫 댓글 | **없음** (F-500 4.2 "본문에 칠하지 않는다") | — |
| 고아 | 없음 | — |

- 위젯·치환(`Decoration.replace`·`widget`) 장식을 **쓰지 않는다**. 문서·`Y.Text` 가 바뀌지 않는 것은 A13 이 판정한다
- 겹치는 앵커는 각자 mark 하나 — CM 이 span 을 겹쳐 그린다. 배경이 반투명이라 겹친 곳이 진해진다(모양은 H1)
- 장식은 필드의 범위에서 만든다. 트랜잭션마다 새로 지어도 500개 0.17ms(n2), 실제 뷰에서 한 글자당 +0.1~0.2ms(n3)라 따로 줄이지 않는다
- **블록 위젯 안의 앵커**(표·코드블록·수식·이미지·mermaid — 편집 모드에서 `blocks.ts` 가 원문을 위젯으로 치환한 곳): mark 는 치환된 원문에 붙으므로 **보이지 않는다**. 커서가 들어가 원문이 펼쳐지면(코드블록 등) 보인다. 표는 늘 위젯이라(F-125) 표 안 앵커는 편집 모드에서 보이지 않는다 — 거터 표시(4.3)와 레일 카드(좌표 4.4)는 있다. 원문 모드에서는 모두 보인다
- 인라인으로 숨긴 표시(`**`·`[[` 등 `Decoration.replace({})`)는 mark 가 그 부분만 건너뛴다
- 이 제품에는 코드 접기(`foldService`·`foldGutter`)가 없다(`src` 에서 `grep` 0건) — "접힌 영역" 은 위 블록 위젯뿐이다

### 4.2 누르기 — 앵커 글자

- 주 편집기 `click`(왼쪽 버튼, 수정 키 없음, 조합 중 아님)에서, 누른 요소에서 가장 가까운 조상 `.cm-comment-anchor` 의 `data-thread-id` 로 `onActivate(id, 'anchor')`. 겹친 앵커면 **가장 안쪽 span** 이 이긴다
- 클릭 뒤 주 선택이 비어 있지 않으면(끌어서 고름) 부르지 않는다 — 댓글을 달려고 고르는 중일 수 있다
- 기본 동작(커서 놓기)은 막지 않는다
- 앵커 밖을 누르면 아무것도 부르지 않는다(활성을 끌지는 F-505 몫)
- 키보드로 앵커를 활성하는 길은 두지 않는다 — F-500 4.9 의 키보드 길은 레일이다

### 4.3 댓글 거터

- `gutter({ class: 'cm-comment-gutter', lineMarker, widgetMarker, lineMarkerChange, initialSpacer, domEventHandlers })` 하나. `markers` `RangeSet` 은 쓰지 않는다 — 블록 위젯이 가린 줄의 표시가 버려지기 때문이다(n9)
- **세는 규칙**: 열린 첫 댓글 중 범위가 있고 `from` 이 그 블록의 `[line.from, line.to]` 안인 것의 수. 텍스트 줄은 `lineMarker`, 블록 위젯 칸은 `widgetMarker` 에서 센다. `block.to === block.from` 인 점 위젯(맨 위 제목 `docTitle` 등)은 세지 않는다 — 위치 0 의 스레드가 두 번 세어지지 않게
- 줄바꿈(`lineWrapping`)된 긴 줄은 블록 하나라 표시도 하나다
- **표시 DOM (계약)**: `<div class="cm-comment-gutter-marker" data-count="{N}" title="댓글 {N}개">`. `N ≥ 2` 이면 글자 `{N}`, `N = 1` 이면 글자 없음(모양은 CSS). 1 이상일 때만 만든다. `aria-hidden="true"` — 키보드·화면 읽기 길은 레일이다(F-500 4.9)
- `initialSpacer` 로 표시 하나 폭을 늘 잡아 둔다 — 첫 댓글이 생길 때 본문이 옆으로 밀리지 않게
- **누르기**: 거터 `mousedown`(왼쪽 버튼) → 그 블록에서 세어진 스레드 중 `sortThreadsByPosition` 순서로 첫 것을 `onActivate(id, 'gutter')`. `true` 를 돌려 기본 동작을 막는다. 조합 중이면 부르지 않는다
- **어디에 두나 — 줄 번호 compartment 안, `lineNumbers()` 바로 뒤.** 그래서 줄 번호 오른쪽에 온다(CM 은 활성 거터를 확장 순서대로 놓는다). **줄 번호를 끄면 댓글 거터도 없다**(12장 Q2) — 붙어 있고(`attach`) 줄 번호가 켜져 있을 때만 확장이 들어간다. `setLineNumbers(on)` 과 `attach`/떼기가 같은 compartment 를 다시 구성한다
- 앵커 장식·레일·클릭은 줄 번호와 무관하게 동작한다

### 4.4 레일 좌표 — `onLayout`

- **좌표계**: `top` 은 `view.scrollDOM` 의 스크롤 콘텐츠 좌표 — `scrollDOM.scrollTop = top` 이면 그 줄 윗변이 스크롤 영역 윗변에 온다. 스크롤해도 값이 바뀌지 않는다. F-505 는 `scrollDOM` 의 `scroll` 을 스스로 들어 레일을 옮긴다
- **어느 높이**: 앵커 시작 글자가 든 **시각 줄의 윗변**. 시작이 화면에 그려진 텍스트 줄 안이면 `coordsAtPos(from, 1)` 실측, 블록 위젯 안이면 그 위젯 블록의 윗변, 그려지지 않은 곳이면 높이 지도 추정(`lineBlockAt(from).top`). 추정은 그 줄이 그려질 때 CM 이 고치고(`heightChanged`) 그때 다시 보낸다
- **보내는 때**: 다음 중 하나가 있은 업데이트 뒤, `view.requestMeasure` 의 읽기 단계에서 재고 쓰기 단계에서 부른다. 같은 키로 요청해 **한 프레임에 최대 한 번**
  - 필드가 바뀜(스레드·범위·열림/해결·다시 푼 결과), `docChanged`, `heightChanged`, `geometryChanged`(창 크기·폭 변화), `attach` 직후
  - **스크롤만으로는 보내지 않는다** — 좌표가 스크롤 콘텐츠 기준이라 바뀌지 않는다. 다만 스크롤로 새로 그려진 줄의 실제 높이가 추정과 달라 `heightChanged` 가 나면 보낸다
- **안 보내는 때**: 편집기가 숨겨짐(`scrollDOM.clientHeight === 0` — 보기 모드에서 `.editor-slot` 이 `hidden`). "밀림" 표시를 두고 다시 보이면(`geometryChanged`) 보낸다. 직전에 보낸 값과 모든 수가 같으면 보내지 않는다
- **비용**: 500개 읽기 0.2~0.4ms(n3). 입력 중에는 한 글자마다 프레임당 한 번 돈다
- 조합 중에도 보낸다 — 레일 이동은 편집기 DOM 을 건드리지 않는다. F-505 의 입력 카드(`textarea`)에서 조합 중일 때 레일이 움직여도 React 가 그 요소를 다시 만들지 않게 하는 것은 F-505 몫(키를 스레드 id 로)
- F-505 규칙(계약): `anchored`·`orphans` 어디에도 없는 스레드는 **아직 위치를 모르는 것**이다 — 레일에 잠깐 숨긴다. F-505 가 `comments` 를 직접 관찰해 새 항목을 먼저 보더라도, 그것을 고아 묶음에 넣지 말고 다음 `onLayout` 을 기다린다(5.2 의 순서 때문에 한 프레임 늦는다)

## 5. 위치를 따라가는 규칙 (반드시 결론 1·2)

### 5.1 ① 열 때 — `attach` / `start()`

- `groupCommentThreads(map.entries())`(n4: 500개 1.45ms) → 첫 댓글 전부에 `resolveCommentAnchors` → 효과 하나로 필드에 넣는다
- **동기로 한 번에 한다.** 비용(n1): 새로 심은 Doc(로컬 문서 마운트, F-508 이 되살린 직후) 1ms 미만. 실시간 경로의 편집기 Doc(방 상태를 옮겨 만듦) 항목 8,000개 약 25ms. 무작위 편집 20,000번으로 항목 39,000개까지 쪼갠 극단 약 230ms — 문서를 열 때 한 번이다. 나눠서 푸는 안은 12장 Q4

### 5.2 ② `comments` 가 바뀔 때 — `mapChanged(keys)`

- 붙어 있는 동안 `map.observe` 가 `event.keysChanged` 를 모으고, **`doc.on('afterTransaction')` 에서** 모은 키가 있으면 `mapChanged(keys)` 를 부르고 비운다. 이유(n8): 한 Yjs 트랜잭션에 본문과 댓글이 함께 들어오면(원격 갱신·게이트 비우기) 관찰자 순서가 정해져 있지 않다. `afterTransaction` 은 `y-sync` 가 CM 에 본문을 넣은 **뒤**라, 이때 푼 위치가 CM 문서 위치와 같다
- `afterTransaction` 은 입력 한 글자마다 불린다(`y-sync` 가 쓰는 트랜잭션). 모은 키가 없으면 곧바로 돌아온다
- `mapChanged`: `groupCommentThreads` 를 다시 돌려 스레드 집합·열림/해결을 새로 읽고, **바뀐 키 중 첫 댓글인 것만** `resolveCommentAnchor` 로 푼다(하나 0.16ms 이하, n1). 없어진 키는 필드에서 뺀다. 바뀌지 않은 스레드는 매핑된 범위를 그대로 둔다. 결과를 효과 하나로 보낸다
- **보내기 안전**: `dispatch` 는 `remoteCursors.ts` `requestRefresh` 처럼 먼저 바로 해 보고, CM 업데이트 도중이라 던지면 `queueMicrotask` 로 다시 한다. `comments` 쓰기가 CM 업데이트 안에서 일어나는 길은 지금 없다(F-505 의 쓰기는 React 처리기, 게이트 비우기는 소켓·타이머·`compositionend` 다음 틱)
- 조합 중이면 보내지 않고 모은다(6장)

### 5.3 편집 트랜잭션 — 매핑 (필드 `update`)

- `docChanged` 인 트랜잭션마다 스레드·후보의 범위를 `from = changes.mapPos(from, 1)`, `to = changes.mapPos(to, -1)` 로 옮긴다. 방향은 앵커의 시작 `assoc 0`(오른쪽 글자에 붙음)·끝 `assoc -1`(왼쪽 글자에 붙음)과 같다 — 경계 바로 앞·뒤에 친 글자가 범위에 들지 않는다(n5 "시작 바로 앞"·"끝 바로 뒤")
- 옮긴 결과는 `toAnchorRange(from, to)` 로 판정한다 — `null` 이면 그 순간부터 고아로 보인다(장식·거터 없음, `orphans` 에 들어감). F-501 3.2 "같은 고아 규칙" 그대로
- 로컬 입력·원격 갱신(`y-sync` 가 CM 트랜잭션으로 들여옴)·`Y.UndoManager` 되돌리기가 모두 이 길을 탄다. 이 명세는 CM 트랜잭션의 출처를 가리지 않는다
- 비용(n2·n3): 한 글자 0.022ms(매핑) + 장식 0.17ms, 실제 뷰에서 한 글자당 +0.1~0.2ms. 변경 1,000개짜리 트랜잭션 약 4.6ms

### 5.4 ③ 경계 글자가 지워진 앵커 — 300ms 쉼 뒤 그것만 다시 풀기

**이 명세의 기본값은 개요 4.2 ③ 을 넓힌다 — 12장 Q1, 사람 결정 필요**

- 필드 `update` 에서 매핑과 함께 **경계 판정**을 한다: `changes.mapPos(from, 1, MapMode.TrackAfter) === null`(시작의 첫 글자가 지워짐) 또는 `changes.mapPos(to, -1, MapMode.TrackBefore) === null`(끝의 마지막 글자가 지워짐)이면 그 스레드를 "다시 풀 것" 집합에 넣는다. 매핑으로 빈 범위가 된 앵커는 반드시 경계 글자가 지워졌으므로(범위 안 글자가 모두 지워져야 빈 범위다) 개요의 ③ 을 포함한다
- 근거(n5): 23가지 편집 중 매핑과 Yjs 가 갈린 4가지가 **모두** 경계 글자가 지워진 경우였고, 경계가 남은 경우는 9가지 모두 같았다(경계가 지워진 14가지 중 10가지는 우연히 같았다). 경계 글자가 지워지면 Yjs 는 지워진 항목의 목록 자리로 위치를 푸는데, 그 자리가 새로 넣은 글자의 앞인지 뒤인지는 CM 의 변경 모양으로 알 수 없다
- 집합이 비지 않으면 타이머를 건다. **그 뒤 집합에 새로 들어올 때마다 다시 건다**(마지막 경계 삭제 뒤 `COMMENT_RERESOLVE_MS` = 300ms). 울리면 조합 중이 아니면 집합의 스레드만 `resolveCommentAnchor` 로 풀어 효과 하나로 보내고 집합을 비운다
- 타이머가 울리기 전 화면은 매핑 값이다(되돌리기 직후 300ms 동안 고아로 보였다가 제자리로 온다 — 개요 2.3 "레일은 다음 위치 계산 때 제자리로")
- 비용: 푸는 수가 경계를 지운 앵커 수뿐이다. 한 개 0.16ms 이하(항목 8,000개, n1)
- 개요대로(빈 범위만) 좁히면 n5 의 갈림 셋이 남는다 — 12장 Q1

## 12. 열린 질문 / 사람 결정 필요

### Q1. 다시 풀기 ③ 을 "경계 글자가 지워진 앵커" 로 넓힘 — **사람 결정 필요 (승인된 개요 4.2 ③·기본값 13 과 다름). 기본값: 넓힌다**

- 개요는 ③ 을 "매핑으로 빈 범위가 된 앵커" 로 적었다(되돌리기로 돌아오는 경우, 개요 c1). 이번에 23가지 편집을 돌려 보니(n5) 빈 범위가 아닌데도 매핑과 Yjs 가 갈리는 경우가 셋 더 있었다: 범위를 통째로 골라 다시 침(매핑은 새 글자에 붙어 있고, Yjs 는 고아), 마지막 글자를 바꿈(매핑은 새 글자 포함, Yjs 는 제외), 시작 경계를 덮어 바꿈(반대로)
- 갈린 채로 두면: 같은 문서에서 **내 화면과 다른 사람 화면의 앵커가 다르다**(다른 사람은 문서를 열 때 Yjs 로 푼다). 그 스레드의 `comments` 가 바뀌거나 문서를 다시 열 때까지 이어진다. 로컬 문서(L2)는 기록이 매핑 값으로 저장돼, 다시 열면 매핑 쪽 뜻(새 글자에 붙음)이 굳는다 — 서버 문서와 뜻이 달라진다
- 넓힌 규칙은 갈린 경우를 모두 잡고(갈린 4가지 모두 경계 삭제), 경계가 남은 9가지는 건드리지 않았다. 비용은 경계를 지운 앵커 수 × 0.16ms 이하(n1), 300ms 쉼 뒤 한 번. 개요의 ③ 을 그대로 포함한다
- **좁게(개요대로)를 고르면**: 5.4 의 경계 판정을 "`toAnchorRange` 가 `null`" 로 바꾸고 A7 기대를 "빈 범위가 된 것만 같다" 로 고친다. 3.2 `ranges()` 의 "기다리는 스레드를 풀어 줌" 도 빈 범위만. 위의 불일치는 알려진 한계로 F-500 2.3 에 적는다

### Q2. 줄 번호를 끄면 댓글 거터도 없음 — **사람 결정 필요 (개요가 정하지 않은 빈칸). 기본값: 없다**

- 설정 `줄 번호` 는 F-147 에서 "거터 켜기·끄기" 다(`data-gutters='off'` 이면 `.cm-line` 왼쪽 패딩까지 0). 거터를 끈 사용자에게 댓글 때문에 거터가 다시 생기면 그 선택을 뒤집는다. 앵커 장식·레일은 그대로라 댓글을 못 보지는 않는다
- `e2e/lineNumbers.spec.js` 의 `.cm-gutters` 개수 단언 10곳이 그대로 통과한다(8장)
- **다른 안 — 붙어 있으면 늘 댓글 거터**: 줄 번호를 꺼도 거터에서 댓글 줄을 볼 수 있다. 대신 `lineNumbers.spec.js` 60·97·113·117·126·129행을 F-505 가 고치고, `data-gutters='off'` 에서 거터가 있는 경우의 패딩 규칙을 새로 정해야 한다(app.css, F-505). 설정 이름을 `줄 번호` 대로 두면 "줄 번호를 껐는데 거터가 있다" 가 된다

### Q3. 표 칸을 고치면 그 칸 안의 앵커가 고아 — **기본값: 알려진 한계로 둔다(도움말에 적음)**

- 다른 안: 칸 쓰기를 "앞뒤 같은 부분을 빼고 바뀐 곳만" 으로 바꾸는 별도 명세(표 위젯은 F-125·F-135·F-138 소유). 그러면 칸 안 앵커가 남는다. F-138 의 패딩 삽입 규칙·`advanceCellRange` 를 함께 봐야 하고, 칸마다 입력 한 번의 변경 모양이 바뀐다. M5 범위를 늘리므로 기본값은 두지 않는다

### Q4. 열 때 전부 풀기를 한 번에 — **기본값: 동기 한 번**

- 다른 안: 화면에 보이는 것부터 여러 프레임에 나눠 푼다. 극단에서 첫 화면이 빨라지지만, 그동안 레일은 "위치를 모르는 스레드" 를 숨기고(4.4) 장식이 조금씩 나타난다. 코드가 늘고 A11 이 여러 단계를 판정해야 한다
