## 2. 범위

### 한다

- `PUT /v1/docs/:id` 가 문서의 `DocRoom` 에 RPC `writeText` 로 쓴다. 방이 비어 있고 불러오지 않았으면 Yjs 를 깨우지 않고 **DO 안에서** D1 조건부 쓰기만 하고(idle 경로), 방이 살아 있으면 `Y.Text` 에 차이만 적용하고 곧바로 D1 에 스냅숏을 쓴다(실시간 경로) (5·6장)
- `baseVersion` 검사를 실시간 경로에서는 **DO 가 아직 D1 에 못 쓴 편집까지 반영한 값**으로 한다 (7장)
- `/v1` PUT 의 본문 줄바꿈을 문서 `lineEnding` 에 맞춘다 (8장, 19장 Q1)
- DO 호출이 던지면 지금 경로(`handleUpdateDoc`)로 쓴다 (9장)
- F-305 의 임시 423 과 그 부속(`refuseWhileLive`·`liveEditorOf`·`activeEditor`)을 지운다 (10장)

### 하지 않는다

- **`PUT /api/docs/:id` 는 바꾸지 않는다.** 폴백·`pending` 세션과 가져오기(F-282)가 쓰는 길이고, 잠금·outbox·충돌 사본(F-207·F-213)과 묶여 있다. F-305 15장 L5(가져오기로 열린 실시간 문서를 덮으면 DO 가 흡수할 때까지 화면에 안 온다)는 그대로 남는다 — 19장 Q6
- **D1 잠금(F-213) 423 은 `/v1` PUT 에 그대로 남는다.** 지우는 것은 F-309 (10.2)
- `POST /v1/docs`(F-301 7장 그대로 — DO 가 없고 나중에 씨앗 심기가 집어간다), `/v1` 읽기(D1 스냅숏 그대로)
- CLI 코드. 게시된 0.2.0 이 그대로 동작해야 한다 (11장)
- 사용량 카운터·문서 총량(F-2024 → F-2025·F-2027). 그 자리만 남긴다 (12장)
- 새 UI 문자열 없음

## 3. 전체 흐름

```
CLI ── PUT /v1/docs/:id ──► Worker handleUpdateDocV1
                             본문 400·413 → 접근 404·403 → D1 잠금 423 → 줄바꿈 맞춤·413 → 낡은 version 이면 409(DO 안 부름)
                             │
                             ▼ RPC writeText (docRoomRpc.writeTextInRoom)
                           DocRoom DO ── 불러오지 않았고 연결 0 ──► idle 경로: blockConcurrencyWhile 안에서 D1 조건부 UPDATE (Yjs·SQLite 안 건드림)
                             │
                             └─ 그 밖 ──► setName 으로 초기화(onLoad) → 실시간 경로:
                                          따라잡기 → flush(선) → 같은 값이면 200 → version 비교 → 차이 적용 → flush(후)
                             │
                             ▼ 결과 { ok | conflict | too_large | not_found | unavailable }
                           Worker 가 V1 응답으로 바꾼다. RPC 가 던지면 handleUpdateDoc 로 (9장)
```

- DO 가 한 번에 한 `writeText` 만 처리한다 (6.8)
- D1 → `Y.Doc` 방향은 늘지 않는다. idle 경로가 D1 에 쓴 값은 다음 불러오기의 흡수(F-304 7.2)가 가져간다 — F-301 3.3 의 예외 그대로

## 4. Worker — `handleUpdateDocV1` 판정 순서

위에서부터 보고 첫 실패에서 멈춘다. 1~4 는 지금 `handleUpdateDoc` 과 같은 순서·같은 응답이다

| # | 검사 | 실패하면 |
| --- | --- | --- |
| 1 | `requireUser` | 401 (지금 그대로) |
| 2 | 몸통 `readJsonLimited(MAX_BODY_BYTES)`, 객체, `title`(`isValidTitle`)·`content`(문자열)·받은 그대로의 `content` 크기·`baseVersion`(정수) | 400 `invalid`(`field`) · 413 `too_large` — 지금과 같은 순서·모양 |
| 3 | `getDocAccess(env, id, user)` — 열 목록 기본값 `*` 그대로 | 404 `not_found` · 보기 권한이면 403 `forbidden` |
| 4 | `getActiveLock` — 유효 잠금이 있으면(토큰 요청에는 잠금 세션이 없다, `X-Lock-Session` 은 지금처럼 지운다) | 423 `{"error":"locked","email","expiresAt"}` — 지금 그대로 (10.2) |
| 5 | `content` 가 있으면 **문서 `line_ending` 에 맞춘다**: `fromEditorText(toEditorText(content), 행.line_ending)`. 맞춘 값이 `MAX_CONTENT_BYTES` 를 넘으면 | 413 `{"error":"too_large","limit":1000000}` (8장) |
| 6 | `baseVersion !== 행.version` **이고** 요청한 값(맞춘 `content`, `title`)이 행과 하나라도 다르면 | 409 `{"error":"conflict","doc":<행>}` — **DO 를 부르지 않는다** (7.3) |
| 7 | `writeTextInRoom(env, ctx, id, 입력)` (5.4) | 결과를 아래 표로. `null` 이면 9장 |

결과 → 응답

| 결과 `type` | 응답 |
| --- | --- |
| `ok` | 200, V1 문서(`V1_EXAMPLES.doc` 과 같은 키) |
| `conflict` | 409 `{"error":"conflict","doc":<V1 문서>}` |
| `too_large` | 413 `{"error":"too_large","limit":1000000}` |
| `not_found` | 404 `{"error":"not_found"}` |
| `unavailable` | 503 `{"error":"unavailable"}` (6.7) |

- V1 문서는 DO 결과의 `title`·`content`·`version` 에 Worker 가 3번에서 읽은 행의 `id`·`line_ending`·`folder_id`·`pinned_at`·`created_at` 을 붙인다. `updatedAt` 은 결과의 값, 결과가 `null` 이면 행의 `updated_at`
- 3번에서 `*`(본문 포함)를 그대로 읽는 이유: 6번의 409 몸통에 본문이 들어가고(F-223 2.1 `409 conflict(doc)`), F-2025 가 PUT 의 총량 증감을 이 행에서 계산한다(F-2024 3.2 2번). `/v1` PUT 은 사람이 치는 명령이라 드물다
- 6번은 비용 줄이기다. 낡은 `baseVersion` 은 DO 안에서도 409 가 되므로(7.2) DO 를 깨우지 않고 끝낸다. "요청 값이 행과 같으면 넘긴다" 단서는 7.4 의 같은 값 규칙을 지키려고 있다

### 5.2 경로 고르기

- **idle 경로** = 이 인스턴스가 아직 불러오지 않았고(`load` 가 끝난 적 없음) **열린 연결이 0개**. 연결 목록은 초기화 없이 읽힌다(`ctx.getWebSockets()` — F-304 9.3, F-305 12.2 `activeEditor` 가 같은 방식으로 썼다)
- **실시간 경로** = 그 밖 전부 — 불러온 인스턴스(연결이 없어도), 또는 연결이 있는데 잠에서 막 깨어 아직 안 불러온 인스턴스(hibernation, F-304 5.2)
- 고르는 판단과 idle 경로의 시작(`exclusive` 호출) 사이에 `await` 가 없어야 한다 — 그 사이에 새 연결이 들어와 불러오기가 시작되면 안 된다

**왜 둘로 나누나** (19장 Q2). 아무도 안 연 문서까지 실시간 경로로 보내면 PUT 한 번마다 ① `onLoad`(1MB 문서 불러오기 6.7~14.9ms CPU, 측정 (b)(d), 그리고 DO SQLite 읽기·D1 본문 읽기) ② DO 저장소가 한 번도 없던 문서면 **씨앗 심기로 문서 크기만큼 DO SQLite 쓰기** ③ `y-partyserver` 가 `onStart` 에서 건 저장 디바운스(5,000ms, F-304 6.2)가 이 업데이트로 한 번 걸려 **DO 가 5초 더 깨어 있다** — 이 디바운스는 밖에서 끌 수 없다(머리말 소스 확인). F-304 10.1 계산으로 깨어 있는 15초 = 1.9 GB-s. 1분마다 도는 스크립트 하나가 한 문서에 쓰면 하루 1,440번 × 1.9 = 약 2,700 GB-s, **무료 하루 13,000 GB-s 의 21%** 다(런타임이 잠들기 전 기다리는 시간은 F-304 U4 대로 확인 못 함 — 값은 추정). idle 경로는 DO 요청 1건 + D1 쓰기로 끝난다 — F-305 가 이미 PUT 마다 쓰던 RPC 1건(`activeEditor`)과 같은 몫이다

### 5.3 호스트에 더하는 것

```ts
// worker/docRoomCore.ts — DocRoomHost 에 두 멤버
ensureLoaded(): Promise<void>                        // 초기화(onLoad)가 끝날 때까지. 이미 됐으면 곧바로
exclusive<T>(fn: () => Promise<T>): Promise<T>        // 그동안 이 DO 에 다른 이벤트(새 연결·메시지·RPC)가 들어오지 않는다
```

- `worker/docRoom.ts` 배선: `ensureLoaded` = `this.setName(this.name)`, `exclusive` = `this.ctx.blockConcurrencyWhile(fn)`
- `setName` 을 고른 이유: RPC 는 `#ensureInitialized` 를 지나지 않는데(머리말), `partyserver` 가 RPC 앞 초기화를 위해 스스로 쓰는 공개 메서드가 이것이다(`getServerByName` → `setName`). `getByName` 주소에서는 이름 확인이 늘 통과한다(`ctx.id.name === this.name`). `@deprecated` 표시는 "이름을 넘기는 용도로는 필요 없다" 는 뜻이고 초기화 동작은 그대로다. 다른 안은 19장 Q8
- `DocRoomHost` 가 바뀌므로 `docRoomCore.test.ts` 의 `makeRoom` 호스트에 두 멤버를 더한다(15장). 테스트 쪽 `ensureLoaded` 는 아직 안 불렀으면 `core.load()`, `exclusive` 는 `fn()` 을 그대로 부르고 부른 횟수를 센다

```ts

async writeText(input: RoomTextWrite): Promise<RoomTextWriteResult>

// worker/docRoomRpc.ts — 결과가 응답을 바꾸므로 기다린다
```

- `writeText` 껍데기는 `this.core.writeText(input)` 만 부른다. 규칙은 전부 core 에 있다(F-304 5.3 원칙)

### 5.5 idle 경로

`exclusive` 안에서 한 번에:

1. `SELECT * FROM docs WHERE id = ?` — 없으면 `not_found`
2. **같은 값이면 쓰지 않는다**: 요청한 필드(`title`·`content`)가 모두 행과 같으면 `ok`(행 그대로, `version` 안 오름) (7.4)
3. `baseVersion !== 행.version` → `conflict`(행)
4. `updateDocRow(env, 행, { title, content })`(6.1) — 1행 바뀜 → `ok`(새 행). 0행 → 행을 다시 읽어 없으면 `not_found`, 있으면 `conflict`(그 행)

- Yjs 문서·DO SQLite·저장 타이머를 **하나도 건드리지 않는다.** `doc` 에 업데이트가 생기지 않으므로 5.2 ③ 의 디바운스도 걸리지 않는다
- 이 DO 에 SQLite 상태가 있으면 다음 불러오기에서 `d1_version` ≠ D1 `version` 이라 흡수가 돈다(F-304 7.1 6번·7.2). 없으면 씨앗이 이 값으로 심긴다
- `exclusive` 가 필요한 이유: 쓰는 도중(D1 `UPDATE` 를 기다리는 동안) 새 연결이 들어오면 그 `onLoad` 가 쓰기 **전** D1 을 읽고, 쓰기가 끝난 뒤 그 연결의 첫 편집 flush 가 조건부 쓰기 0행 → 흡수를 탄다. 흡수는 겹치면 DO 가 이기므로(F-304 7.3) PUT 이 200 을 받고도 겹친 부분이 사라진다. `blockConcurrencyWhile` 동안에는 새 연결의 `fetch` 가 전달되지 않는다
- 알려진 손실(F-304 7.2 "알려진 손실" 과 같은 것, 받아들인다): 앞서 D1 쓰기가 실패한 채 DO 가 내려가 SQLite 에만 있는 편집이 있으면, 그 뒤 idle 경로가 쓴 D1 값을 다음 불러오기가 "지금 문서를 기준" 으로 흡수해 그 편집이 D1 값 쪽으로 바뀐다

## 6. 실시간 경로

`ensureLoaded()` 뒤에 아래 순서. 순서가 계약이다

| # | 단계 | 규칙 |
| --- | --- | --- |
| 1 | 불러오기·사라진 방 | `ensureLoaded()` 뒤에도 불러온 상태가 아니면 `unavailable`(18장 U2 — 초기화가 안 돌았는데 빈 `document` 에 쓰지 않게). `gone` 이면 `not_found` |
| 2 | 따라잡기 | `docVersion !== base.version` 이면 D1 한 줄을 다시 읽어, 줄이 없으면 사라진 방 처리 후 `not_found`, `version` 이 `base.version` 과 다르면 흡수(F-304 7.2). **`connect()` 의 따라잡기와 같은 동작** — 한 벌로 둔다 |
| 3 | flush(선) | `await flush()` — 아직 D1 에 못 나간 편집을 먼저 쓴다. 그 편집이 있었으면 여기서 `base.version` 이 오른다 (7.1) |
| 4 | 같은 값 | 요청한 필드가 지금 `document` 값(본문은 `toEditorText(content)` 와 `Y.Text`, 제목은 그대로)과 모두 같으면 `ok`(`base` 로 만든 상태) (7.4) |
| 5 | version | `baseVersion !== base.version` → `conflict`(`base`) |
| 6 | 편집 계산 | 본문 `rebaseExternal(base.content, toEditorText(content), 지금 본문)`, 제목 `rebaseExternal(base.title, title, 지금 제목)`. 하나라도 `'conflict'` → `conflict`(`base`) |
| 7 | 크기 | 본문 편집을 적용한 결과를 `fromEditorText(…, base.lineEnding)` 로 바꿔 UTF-8 로 잰 값이 `MAX_CONTENT_BYTES` 를 넘으면 `too_large`(`bytes`). 적용하지 않는다 |
| 8 | 적용 | 한 Yjs 트랜잭션에 본문·제목 편집(`delete` 뒤 `insert`). origin 은 core 안 상수(클라이언트와 공유하지 않음 — 흡수와 같은 원칙). 연결된 클라이언트에 곧바로 퍼진다 |
| 9 | flush(후) | `await flush()` |
| 10 | 결과 | 8번에서 편집이 없었거나, 9번 동안 `base.version` 이 8번 직전 값보다 커졌으면 `ok`(`base`). 그 밖이면 `unavailable` (6.7) |

- 4·6·7·8 번 사이에는 `await` 가 없다 — JavaScript 한 흐름 안이라 그사이 다른 편집이 끼지 않는다. **검사와 적용이 한 번에** 일어난다(F-301 7장 4번)
- 3번의 `await` 동안에는 연결된 편집자의 업데이트가 들어올 수 있다(D1 호출은 DO 의 입력 게이트를 닫지 않는다 — Cloudflare 문서 서술로 알고 있고 이번에 확인하지 않았다, 18장 U3). 그래서 6번은 `diffText(지금, X)` 가 아니라 `rebaseExternal` 이다: 평소(3번이 `base` 를 지금 본문과 같게 만든 경우) 결과는 `diffText(지금, X)` 와 같고, 끼어든 편집이 있으면 겹치지 않을 때만 둘 다 살리고 겹치면 409
- `exclusive` 를 실시간 경로에 쓰지 않는 이유: D1 두 번 왕복 동안 모든 편집자의 업데이트 중계가 멈추고, `blockConcurrencyWhile` 은 30초를 넘기면 DO 를 재시작해 연결이 전부 끊긴다(Cloudflare 문서 서술 — 확인하지 않았다). 위 규칙으로 막을 필요가 없다

### 6.1 `updateDocRow` — 문서 행 조건부 쓰기 한 벌

```ts
// worker/docWrite.ts
export type DocRow = { id: string; owner_id: string; title: string; content: string; line_ending: 'crlf' | 'lf'
  folder_id: string | null; pinned_at: number | null; version: number; created_at: number; updated_at: number }
export function rowToDoc(row: DocRow): V1Doc   // 지금 docs.ts 의 rowToDoc 을 옮긴다(모양 그대로)
export async function updateDocRow(
  env: Env, existing: DocRow, patch: { title?: string; content?: string },
): Promise<{ ok: true; row: DocRow } | { ok: false }>
```

- 문장은 지금 `handleUpdateDoc` 의 것 그대로: `UPDATE docs SET title = ?, content = ?, version = ?, updated_at = ? WHERE id = ? AND owner_id = ? AND version = ?`. 값: 없는 필드는 `existing` 값, `version` = `existing.version + 1`, `updated_at` = 지금 ms
- `handleUpdateDoc`(`/api`·`/v1` 폴백)과 DO idle 경로(5.5)가 이 함수 하나를 쓴다. **F-2025 가 사용량 줄을 붙일 자리가 이 한 곳이다**(12장)
- `rowToDoc` 의 반환 모양은 `V1Doc`(`worker/v1Contract.ts`)과 같다. 서버 핸들러는 `v1Contract.ts` 를 import 하지 않는다는 규칙(그 파일 머리 주석)을 지키려면 반환 타입을 따로 적지 않고 추론에 맡겨도 된다 — 어느 쪽이든 `F-2021 U15`(키 집합 테스트)가 지킨다

### 6.2 차이만 적용한다 — 커서가 밀리지 않는다

- 6번 편집은 `diffText` 수준(앞뒤 공통 부분을 잘라 가운데 하나, 서로게이트 쌍을 가르지 않음 — F-304 7.3)이다. F-301 7장 2번 "글자 단위 최소 diff 를 요구하지 않는다" 그대로
- 편집 범위 밖의 원격 커서·선택은 Yjs 상대 위치라 제자리에 남는다. 범위 **안**의 커서는 지워진 자리의 경계로 모인다 — 받아들인다
- 조합 중인 편집자에게는 이 업데이트도 원격 업데이트라 F-303 게이트가 조합이 끝날 때까지 미룬다. 클라이언트 쪽 작업 없음

### 6.3 서버에 저장된 모양

- `Y.Text` 에는 LF 만 들어간다(F-301 3.2). D1 에는 스냅숏 규칙(F-304 8.1)대로 `fromEditorText(…, base.lineEnding)` 이 들어간다. 4장 5번에서 이미 문서 줄바꿈으로 맞췄으므로 **200 응답의 `content` 는 Worker 가 맞춘 값과 같다**(다른 편집자가 끼어들지 않았다면 — 6장 둘째 줄)
- 제목은 D1 에 `MAX_TITLE_CHARS`(500)까지 (F-304 8.1)

### 6.4 비용 (실측 (a)(b)(d), node)

| 경우 | DO CPU(추정 — node 값) | 저장소 |
| --- | --- | --- |
| idle | 0(Yjs 안 씀) | D1 읽기 1 + `UPDATE` 1(0행이면 읽기 1 더) |
| 실시간, 작은 편집, 1MB | 따라잡기 없으면 `toString` + diff + 적용 약 3ms + 스냅숏 준비(바이트 세기 1.5ms·줄바꿈 0.2ms) | flush(선): 못 나간 편집이 있을 때만 SQLite + D1. flush(후): SQLite 1행 + D1 `UPDATE` 1 |
| 실시간, 전부 다시 씀, 1MB | 약 10ms(최대 12ms) | 위와 같고, SQLite 행이 약 1MB(1,500,000 B 조각 한 개 안) |
| 실시간, 잠에서 깬 인스턴스 | + 불러오기 1MB 6.7~14.9ms | + F-304 5.2 의 불러오기 읽기 |

- 1MB 몸통 `JSON.parse` 1.9ms 와 줄바꿈 맞춤 0.6ms 는 Worker 쪽이다
- 실시간 경로는 8번 업데이트 때문에 5.2 ③ 의 디바운스가 걸려 DO 가 5초 더 깨어 있다. 연결된 편집자가 있는 방은 어차피 깨어 있으므로 차이가 없다

### 6.5 크기 초과 상태의 방

방이 `tooLarge`(F-304 8.3 — DO 본문이 1MB 를 넘어 D1 이 멈춤)이면 3번이 D1 에 못 써 `base` 가 낡은 채 남는다. 6번은 `base`(D1 값)에서 요청 값으로 가는 편집과 `base` 에서 지금 DO 본문으로 가는 편집을 견주므로 겹치면 409 이고, 409 몸통은 D1 값이다. **CLI 로는 초과한 방을 줄일 수 없을 수 있다** — 브라우저 편집자가 줄여야 한다(편집자에게는 이미 경고가 떠 있다). 받아들인다

### 6.6 사라진 방

1번·2번에서 D1 줄이 없으면 `not_found`. 연결을 `4404`·`deleted` 로 닫는 것은 F-304 9.4 그대로

### 6.7 D1 쓰기에 실패하면 — 503

- 9번 flush(후)가 D1 에 못 쓰면(D1 오류 → F-304 8.4 재시도가 걸림, 또는 끼어든 편집으로 1MB 를 넘음) 편집은 이미 `Y.Doc`·DO SQLite 에 있고(flush 는 SQLite 가 먼저 — F-304 6.2) 재시도가 D1 에 옮긴다. 응답은 503 `{"error":"unavailable"}` — CLI 는 `server_error`(종료 1) `서버 오류가 났습니다 (503). 잠시 뒤 다시 시도하세요.` 를 낸다
- 200 을 주지 않는 이유: 200 몸통은 D1 에 있는 값·`version` 이어야 GET 과 맞는데(7.2), 그 값에는 이 편집이 없다
- **같은 명령을 다시 하면** 대개 200 이다: D1 이 아직 옛 `version` 이면 Worker 6번을 지나고 DO 3번이 D1 에 쓴 뒤 4번(같은 값)에서 `ok`. 재시도가 먼저 D1 에 닿았으면 D1 행이 이미 요청 값이라 Worker 6번의 단서로 DO 까지 가고 4번에서 `ok`
- 폴백(9장)으로 넘기지 않는다 — DO 가 이미 편집을 들고 있어 D1 을 한 번 더 쓰면 흡수가 두 번 얹는다

### 6.8 한 번에 하나

`writeText` 는 core 안에서 줄을 세워 하나씩 처리한다(앞 호출이 끝나야 다음 호출의 1번이 시작된다). 같은 `baseVersion` 을 든 PUT 두 개가 동시에 오면 첫째가 쓰고 둘째는 5번에서 409 — 지금 D1 조건부 쓰기와 같은 결과다. 이 줄은 `writeText` 끼리만 막고 편집자 업데이트·flush 는 막지 않는다

## 7. `baseVersion` 의 뜻과 응답 `version`

### 7.1 문자 그대로 읽으면 생기는 구멍 — flush(선)이 막는다

F-301 7장 4번은 "D1 `version` 기준으로 검사" 다. DO 는 편집을 5초(조용해지면)~30초(계속 치면) 뒤에야 D1 에 쓴다(F-304 6.2). 그래서 **D1 `version` 만 비교하고 `diffText(지금, X)` 를 적용하면**: CLI 가 `version` N 을 읽은 뒤 브라우저 편집자가 친 글자(아직 D1 에 안 나감, D1 은 여전히 N)가 CLI 의 X 에 없으므로 **지워진다** — 낙관적 잠금이 막아야 할 잃어버린 갱신이 최대 30초 창으로 생긴다

6장 3번이 먼저 D1 에 써서 `version` 을 올리므로 그런 편집이 있으면 5번에서 409 가 된다. 결과:

- **"PUT 이 200 이면 문서가 정확히 X 가 된다"** 는 지금 계약(F-223 2.2 "`/api` 와 같다")이 그대로다. 합쳐 주지 않는다 — 합치는 안은 19장 Q3
- F-2021 9장이 이미 예고한 동작이다: "누가 편집 중이면 `put --base-version` 이 409 를 자주 받는다. 예상된 동작이다"

### 7.2 응답 `version` 과 D1 이 맞는가 — 맞다

- `ok`·`conflict` 몸통은 **D1 에 지금 있는 값**이다: idle 은 방금 쓰거나 읽은 행, 실시간은 flush 뒤의 `base`(= DO 가 마지막으로 D1 에 쓴 값, F-304 7.1). 그래서 응답 직후 `GET /v1/docs/:id` 가 같은 `content`·`version` 을 준다(그사이 다른 편집이 없다면)
- 200 의 `version` 은 `baseVersion + 1` 이다(지금과 같다). 6장 3번 뒤 끼어든 편집이 있어도 9번 스냅숏 한 번에 같이 실리므로 `+1` 이다. 예외는 7.4(같은 값 — `version` 그대로)뿐이다
- 409 몸통의 `version` 이 곧 다음 `--base-version` 으로 쓸 값이다(CLI 문구 `… --base-version {currentVersion} 으로 올리세요`). 실시간 경로의 409 는 3번이 방금 쓴 값이라 **GET 없이 바로 다시 써도 된다**
- `version` 은 계속 단조 증가한다 — idle·폴백은 `handleUpdateDoc` 과 같은 조건부 `+1`, 실시간은 DO 스냅숏의 조건부 `+1`(F-304 8.2)

### 7.3 Worker 의 빠른 409

4장 6번은 D1 `version` 이 이미 `baseVersion` 과 다를 때다. D1 `version` 은 줄지 않고 DO 쪽 `base.version` 은 따라잡은 뒤 D1 이상이므로, 그 경우 DO 안에서도 5번이 409 다 — 부를 이유가 없다. 409 몸통은 Worker 가 읽은 행(지금과 같다)

### 7.4 같은 값이면 쓰지 않는다 — 지금과 다르다

- 요청한 필드가 문서의 지금 값과 모두 같으면 `baseVersion` 과 상관없이 **200 + 지금 값, 쓰기 없음, `version` 그대로**. 지금은 같은 값이어도 `version` 이 오르고 낡으면 409 다
- 이유: ① 실시간 경로는 바뀐 것이 없으면 D1 에 쓰지 않는다(F-304 8.2 1번) — 억지로 `version` 을 올리려면 같은 본문을 한 번 더 써야 한다 ② 6.7 의 다시 하기가 409 대신 200 이 된다 ③ D1 쓰기가 준다(F-2024 하루 카운터)
- 폴백 경로(9장, `handleUpdateDoc`)는 지금 동작 그대로다 — 드문 경로라 맞추지 않는다
- CLI 영향: `put` 출력 `{id}\t{version}` 의 `version` 이 오르지 않을 수 있다. 그 값은 여전히 지금 `version` 이라 다음 `--base-version` 으로 쓸 수 있다 (11장)

## 8. 줄바꿈 — 문서 `lineEnding` 에 맞춘다 (19장 Q1)

- `Y.Text` 는 LF 만 담고 `lineEnding` 은 D1 열에 남는다(F-301 3.2, 승인). 실시간 경로에서는 받은 CRLF·LF 가 그대로 남을 수 없다
- 결정: `/v1` PUT 은 **모든 경로에서** `content` 를 문서 `line_ending` 으로 맞춰 저장한다(4장 5번 — Worker 한 곳). 문서 `line_ending` 열은 바꾸지 않는다
- 경로마다 다르게 하지 않는 이유: idle·폴백은 받은 그대로 둘 수 있지만, 그러면 같은 명령이 "그 순간 누가 열고 있었나" 에 따라 다른 바이트를 남긴다
- 바이트가 같게 남는 경우: 문서와 같은 줄바꿈으로 보낼 때 — `get -o a.md` 로 받은 파일을 고쳐 `put` 하는 흐름(F-2021 4.6 "`get -o` → `put` 원문 같음", 그 테스트 U7 은 CLI 쪽이라 영향 없음), 편집기에서 연 파일을 그대로 올릴 때
- 바이트가 바뀌는 경우: 문서와 다른 줄바꿈 파일(예: LF 문서에 CRLF 파일), 섞인 줄바꿈(CLI 는 이미 CRLF 로 통일해 보낸다 — F-2021 4.6), 홀로 쓴 `\r`(줄바꿈으로 바뀐다 — `toEditorText`). **F-223 2.3 "받은 문자열 그대로 저장한다" 가 이 경우에 깨진다** — 17장 갱신 대상
- 지금도 브라우저가 그 문서를 한 번 열어 저장하면 열의 줄바꿈으로 바뀐다(`getText(lineEnding)`). 이 명세는 그 시점을 PUT 으로 당긴다

## 9. DO 호출이 실패하면 — 지금 경로로 쓴다

- `writeTextInRoom` 이 `null`(바인딩 없음·RPC 가 던짐)이면 `handleUpdateDoc`(`/api` 와 같은 D1 직접 쓰기)을 부른다. 요청 몸통은 4장 5번에서 맞춘 `content` 로 새로 만든다(`jsonRequest`, `X-Lock-Session` 지움 — 지금 `v1.ts` 모양). `handleUpdateDoc` 은 접근·잠금·`version` 을 다시 본다
- 이유 (F-305 22장 Q3 과 같은 방향):
  1. DO 장애가 CLI 쓰기 장애가 되지 않는다. 가장 큰 운영 위험인 **무료 한도 소진(F-301 9.3)은 UTC 자정까지 DO 호출을 실패시킨다** — 그 몇 시간 동안 CLI 가 멈춘다. D1 한도는 별개다
  2. 그 사이 D1 에 쓴 값은 다음 불러오기·연결·flush 가 흡수한다(F-304 7.2). 한도 소진이나 배포 재시작 중에는 실시간 편집도 끊겨 있어 겹칠 편집이 거의 없다
  3. 잃을 수 있는 경우: DO 는 살아 편집자가 치고 있는데 RPC 만 실패하고, CLI 편집이 아직 D1 에 안 나간 그 편집과 겹칠 때 — 흡수에서 DO 가 이겨 CLI 쪽 겹친 부분이 200 을 받고도 사라진다. F-308 전(F-305 구간)에 이미 받아들인 모양이 DO 실패 때로 좁혀진 것이다
- RPC 가 DO 쪽 적용 뒤에 던졌다면(응답 유실): D1 이 이미 `+1` 이면 폴백의 조건부 쓰기가 409(몸통에 CLI 의 편집이 들어 있다). 아니면 폴백이 X 를 쓰고, DO 의 다음 flush 가 0행 → 흡수에서 D1 쪽 편집(X)과 DO 쪽 편집(이미 X 를 적용함)이 겹쳐 DO 가 이기고 DO 본문(X)을 쓴다 — 두 번 얹히지 않는다
- 6.7 의 `unavailable` 은 RPC 실패가 아니다 — 폴백으로 넘기지 않는다
- 반대 안(503 으로 거절)은 19장 Q4
