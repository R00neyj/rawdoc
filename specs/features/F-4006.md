## 3. 승인 = 초대 경로
- `applyGrant(env, ctx, owner: AuthUser, t: { targetType; targetId; name }, email, role, extra: D1PreparedStatement[]): Promise<void>` — 지금 `handlePutGrant` 의 batch(초대 upsert `RETURNING`·사용량·`shareNotificationInsertStatements`) 끝에 `extra` 를 붙이고, 그 뒤 새 초대 푸시(F-3007)·`notifyRevalidate`/`notifyFolderRooms` 를 지금 조건 그대로. `handlePutGrant` 는 검증(금고 409·이메일·자기 자신·`role`) 뒤 이것을 부르고 `{ email, role }` 을 돌려준다 — 응답·문장·푸시가 글자 하나 안 바뀐다
- 승인 순서: `id`·`owner_id = 나`·대기·`LIVE_REQUEST_SQL` 인 행 → 없으면 404 → 요청자(`requester_id`·`requester_email`)의 지금 권한(F-4005 5장)이 요청 이상이면 요청만 지우고 200 `{ email, role: 지금 권한 }` → 아니면 대상 이름을 읽어 `applyGrant(…, requester_email, role, 요청 지우기(id))` → 200 `{ email, role }`
- **낮추지 않는다**: 문서 직접 보기 초대가 있는 사람의 편집 요청 → upsert 가 편집으로 올린다. 올림은 새 초대가 아니라 F-3012 행·F-3007 푸시가 없다(F-4004 1장에서 받아들임)
- 거절: 같은 행 확인 → `UPDATE … SET status = 'rejected', decided_at = now` + 그 id 의 알림함 행 지우기(`accessRequestDeleteStatements` 의 앞 두 문장만 — 요청 행은 쿨다운 동안 남긴다)

## 4. 정리 자리 (`accessRequestDeleteStatements` 의 where)
| 자리 | where |
| --- | --- |
| 승인 | `id = ?` |
| `targetShareCleanupStatements`(문서·폴더 삭제, `move-up` 포함) | `target_type = '{종류}' AND target_id IN (…)`, 같은 90개 묶음 |
| 금고로 옮기기 | 대상 + 그 파일 기존 성공 조건(`WROTE_KEY` / `EXISTS … e2ee = 1`) |
| 링크 끊기 | `token IN (SELECT token FROM share_links WHERE target_type = ? AND target_id = ? AND revoked_at IS NOT NULL)`, 끊기 `UPDATE` **뒤** |
| 초대 `PUT`(주인이 같은 사람을 직접 초대) | 대상 + `requester_email = ?`, 대기·거절 모두 — `applyGrant` 의 `extra` |
| 계정 삭제 | `owner_id = ?1 OR requester_id = ?1` — `share_link_docs` 지우기 **앞**(users 외래 키). 알림함 행은 이 문장들이 지운다 |
| 매일 Cron `purgeAccessRequests(env, now)` | `NOT LIVE` / 대기이고 `created_at < now − EXPIRE` / 거절이고 `decided_at < now − COOLDOWN` |

- 이유: 승인할 수 없는 요청이 목록·알림함에 남지 않게. 묶음에서 빠진 문서처럼 즉시 자리가 없는 경우는 목록·승인이 `LIVE_REQUEST_SQL` 로 거르고 Cron 이 24시간 안에 지운다
