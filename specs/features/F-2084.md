## 2. 범위

### 한다
- 폭 ≤600px(기존 `@media (max-width: 600px)`, F-216 과 같은 문턱)에서 서식 바 줄을 **앱 틀 맨 아래**로 옮기고, 편집기 포커스 중에만 보이게 한다
- 앱 틀(`.app-shell`)을 visualViewport 에 맞춰, 키보드가 뜨면 앱이 키보드 위 공간으로 줄어들게 한다 — 서식 바가 맨 아래에 있으니 결과적으로 키보드 바로 위에 붙는다. 같은 코드로 **iOS 에서 키보드가 뜰 때 상단 바가 밀려 올라가는 문제도 막는다** (3.3)
- 휴대폰 폭 서식 바 버튼을 눌러도 편집기 포커스(가상 키보드)가 유지되게 한다 (3.5)

### 하지 않는다
- 601px 이상 — F-233 3.1·3.6 배치 그대로(1024px 미만은 상단 바 밑 줄, 이상은 `topbar-spacer`). 단 meta 변경이 안드로이드 601px 이상에 주는 영향은 3.2
- 서식 바 **내용** 변경 — 되돌리기·다시 실행·탭 3개·가로 스크롤·탭 왼쪽 고정은 F-233 3.6·tweak 2026-09-23 그대로
- 상단 바 접기 — F-2083
- iOS 당김 바운스 — tweak 2026-09-29(`overscroll-behavior: none`) 로 이미 처리. 입력 칸 자동 확대·주소창 높이 변화 — 사용자가 겪지 않는다고 함
- 표 칸 하위 편집기 안에서 서식 바 — 숨긴다 (3.4, 열린 질문 Q2)
- 상태바 — 그대로 둔다 (열린 질문 Q3)
- `navigator.virtualKeyboard`(VirtualKeyboard API) — Chrome 전용이고 TypeScript `lib.dom.d.ts` 에 타입이 없다(`VirtualKeyboard` 0건 확인). iOS 에 없으므로 쓰지 않는다
- 공개 보기(`PublicView`)·공유 화면 — 서식 바가 원래 없다(F-233 3.1)

## 3. 요구사항

### 3.1 무엇이 보이는가 (≤600px)

| 상태 | 서식 바 |
| --- | --- |
| F-233 3.1 조건 불충족(설정 끔·홈·읽기 전용·보기 모드·지도·공유 화면) | 없음 (지금과 같음) |
| 조건 충족 + 편집기 포커스 중(3.4) | 앱 틀 맨 아래 한 줄. 키보드가 떠 있으면 키보드 바로 위 |
| 조건 충족 + 포커스 없음·제목 입력칸·표 칸·다른 입력(검색·댓글·대화상자) | 없음. **자리도 차지하지 않는다**(상단 바 밑 줄도 없다) |

- 나타남·사라짐에 전환 애니메이션을 두지 않는다 — 키보드가 올라오는 애니메이션과 겹쳐 위치가 두 번 움직여 보이지 않게
- 줄 안의 모양은 F-233 3.6 의 좁은 창 줄과 같다(`.editor-toolbar--narrow`: 탭 아이콘·왼쪽 고정·가로 스크롤). 다른 점은 테두리가 줄 **위쪽**(본문과 경계)에 있다는 것뿐
- 서식 바 줄 높이는 CSS 합산으로 41px(`.editor-toolbar-row` 위아래 padding 6+6, 버튼 28, 테두리 1). 나타날 때 편집 영역이 그만큼 줄어든다 — 겹쳐 덮지 않으므로 커서가 서식 바 밑에 가려지지 않는다
- 세로 순서: 상단 바 → 본문 → 상태바 → 서식 바 → (키보드)

### 3.2 위치 계산 — 한 코드 경로, 플랫폼별로 다른 입력

**결론: 안드로이드는 meta `interactive-widget=resizes-content` 로 브라우저가 레이아웃을 줄이게 하고, iOS 는 `visualViewport` 로 앱 틀을 직접 맞춘다. 두 경우를 가르는 분기 코드는 두지 않는다** — 3.3 의 판정은 안드로이드에서 저절로 "아무것도 안 함" 이 된다.

| 플랫폼 | 키보드가 뜨면 | `innerHeight` | `visualViewport.height` | 3.3 결과 |
| --- | --- | --- | --- | --- |
| 안드로이드 Chrome 108+ (meta 있음) | 레이아웃 뷰포트가 줄어든다 → `height: 100%` 인 앱 틀도 줄어든다 | 줄어듦 | = `innerHeight` | 높이 = 이미 줄어든 값, 위치 0 → CSS 기본값과 같음(사실상 무동작) |
| iOS Safari (meta 무시) | 레이아웃 뷰포트는 그대로, 보이는 영역(visual viewport)만 줄고 필요하면 페이지를 밀어 올린다(`offsetTop > 0`) | 그대로 | 줄어듦 | 앱 틀을 보이는 영역 위치·높이로 맞춘다 |
| 데스크톱 | 가상 키보드 없음 | 그대로 | = `innerHeight` | 무동작 |

- meta 최종 문자열: `width=device-width, initial-scale=1.0, interactive-widget=resizes-content`
- 이 방식을 고른 이유: 안드로이드는 브라우저가 키보드 애니메이션과 같은 프레임에 레이아웃을 줄여 JS 한 프레임 지연이 없다. iOS 는 `interactive-widget` 를 지원하지 않아 `visualViewport` 가 유일한 수단이다. 두 경로를 한 판정 함수로 묶으면 "안드로이드 전용 분기" 가 생기지 않는다
- **meta 변경의 영향**
  - 데스크톱: 없음. Chrome 154 에서 meta 유무 두 경우 모두 콘솔 경고 없음, `visualViewport.height === innerHeight`(1600×900·390×844 모바일 에뮬레이션 모두) 확인
  - 안드로이드 601px 이상(태블릿·가로 모드): 지금은 키보드가 앱 아래쪽을 **덮고**, 바꾼 뒤에는 앱이 키보드 위로 **줄어든다**. F-233 좁은 창 줄(상단 바 밑)은 그대로 위에 있다. Chrome 108 이전 기본 동작이 이것이었다. 받아들이지 않으면 열린 질문 Q1 의 B
  - 안드로이드에서 키보드가 열리고 닫힐 때 `window` `resize` 가 뜬다. 이미 `resize` 를 듣는 곳: `useContextMenu.ts`(우클릭 메뉴 닫기 — 터치 길게 누르기는 `isTouchContextMenu` 로 메뉴를 안 여니 영향 없음), `useSidebarLayout.ts`(`innerWidth` 만 읽음 — 폭이 안 바뀌어 다시 그리지 않음). 새로 막을 곳 없음

### 3.3 앱 틀 맞추기 (`viewportFit`·`useViewportFit`)

순수 함수 계약:

```ts
export type ViewportInput = { innerHeight: number; vvHeight: number; vvOffsetTop: number; vvScale: number }
export type ViewportFit = { height: number; top: number } | null
export function fitToVisualViewport(input: ViewportInput): ViewportFit
```

규칙:
- `vvScale` 이 1 이 아니면(|scale − 1| > 0.01, 사용자가 핀치 확대 중) `null` — 확대 중에 앱 틀을 따라 움직이면 확대가 무의미해진다
- `vvHeight <= 0`(문서가 활성 아님) 이면 `null`
- 그 밖에는 `height = min(vvHeight, innerHeight)`, `top = max(0, vvOffsetTop)`. 반올림하지 않는다(키보드 위 경계에 틈이 생기지 않게)

훅 규칙:
- `window.visualViewport` 가 없으면 아무것도 안 한다
- 폭 ≤600px(`matchMedia('(max-width: 600px)')`) 일 때만 동작. 폭이 601px 이상으로 바뀌면 변수를 지운다
- `visualViewport` 의 `resize`·`scroll` 둘 다 듣는다(iOS 는 키보드 연 뒤 페이지를 밀 때 `scroll` 만 뜬다). 한 프레임에 한 번만 쓴다(`requestAnimationFrame` 로 모음)
- 결과를 `document.documentElement.style` 에 CSS 변수로 쓴다 — 선례 `useAppearancePrefs.ts` 의 `CONTENT_WIDTH_VAR`. `null` 이면 두 변수를 지운다

| CSS 변수 | 값 | 없을 때 기본 |
| --- | --- | --- |
| `--vv-height` | `{height}px` | `100%` |
| `--vv-top` | `{top}px` | `0px` |

- CSS(≤600px): `.app-shell` 의 **위 끝 = 보이는 영역 위 끝(`--vv-top`), 높이 = `--vv-height`**. iOS 가 페이지를 밀어 올려도 앱 틀이 보이는 영역을 따라가므로 상단 바가 화면 밖으로 나가지 않는다 — **2장 "iOS 상단 바 밀림" 은 이 규칙으로 같이 막는다**(서식 바 위치와 같은 코드라 분리하지 않음)
- 이동에 `transform` 을 쓰지 않는다 — `transform` 이 걸린 조상은 `position: fixed` 자손(서식 바 툴팁·제목 목록, 우클릭 메뉴)의 기준 상자가 되어 그 좌표 계산(`getBoundingClientRect` 기준)이 모두 어긋난다
- iOS 가 스크롤해 버린 페이지를 `window.scrollTo(0, 0)` 으로 되돌리지 않는다 — 브라우저 스크롤과 싸우면 흔들린다. 앱 틀이 따라가기만 한다
- 이 훅은 편집기에 아무것도 dispatch 하지 않는다. 앱 틀 높이가 바뀌면 CM6 가 자기 `ResizeObserver` 로 다시 잰다
- 휴대폰 폭에서 편집기 밖 입력(검색·대화상자·댓글)에 포커스해도 같은 규칙이 적용된다 — iOS 밀림은 그쪽에서도 같은 문제라 막는 편이 낫다

### 3.4 "편집기 포커스 중" 판정 (`useToolbarDock`)

```ts
export function useToolbarDock(editorRef: RefObject<EditorHandle | null>): { docked: boolean; editorFocused: boolean }
```

- `docked` = 폭 ≤600px(`matchMedia('(max-width: 600px)')`, 변화 구독)
- `editorFocused` = 다음 중 하나
  1. `document.activeElement === 주 편집기 view.contentDOM` — CM6 `EditorView.hasFocus` 와 같은 기준(`@codemirror/view` 6.43.11 `get hasFocus()` 가 `root.activeElement == contentDOM` 으로 판정). `hasFocus` 자체는 쓰지 않는다 — `document.hasFocus()` 도 요구해 앱 전환 뒤 돌아올 때 한 번 거짓이 된다
  2. `document.activeElement` 가 `.editor-toolbar-row` 안 — 키보드로 서식 바에 들어갔거나(Tab), 조합 중 탭(3.5)으로 버튼이 포커스를 받은 경우
- 이 기준이 가르는 곳 (전부 코드로 확인):

| 포커스 위치 | `activeElement` | 판정 | 이유 |
| --- | --- | --- | --- |
| 본문 | 주 `contentDOM` | 보임 | |
| 제목 입력칸 | `textarea.doc-title` — 주 `contentDOM` 안의 블록 위젯(`docTitle.ts` `TitleWidget`) | 숨김 | 명령이 본문 선택에 걸려 제목 칸 입력과 무관하다 |
| 표 칸 하위 편집기 | 칸 `EditorView` 의 자기 `contentDOM`(`tableWidget.ts` `new EditorView({ parent: td })`) | 숨김 | 지금 `runToolbarCommand`(App.tsx) 는 늘 주 view 에 명령을 걸고 `view.focus()` 해 칸 편집을 끝낸다 — 칸 안에서 누르면 엉뚱한 곳(주 선택)에 서식이 들어간다. F-233 1장 "칸 안 동작 안 함" 과 같은 결론. 열린 질문 Q2 |
| 코드블록 언어·복사 버튼 등 본문 안 위젯 버튼, 표 범위 선택 요소(`md-table-cell-highlight`) | 그 요소 | 숨김 | 편집 중이 아니다 |
| 서식 바 안 | `.editor-toolbar-row` 안 요소 | 보임 | |

- 주 view 는 **판정할 때마다** `editorRef.current?.view` 로 새로 읽는다 — 편집기는 문서 전환·다시 마운트(`editorRemountNonce`)로 바뀐다
- 구독: `document` 에 `focusin`·`focusout` 을 캡처로 단다. `focusin` 은 곧바로 다시 판정, `focusout` 은 **다음 틱(`setTimeout(0)`) 에** `document.activeElement` 로 다시 판정 — 포커스가 한 순간 빠졌다 곧바로 돌아오는 경우(조합 중 탭 후 `runToolbarCommand` 의 `view.focus()`, 제목 목록 키보드 조작) 서식 바가 한 프레임 사라졌다 다시 나타나지 않게. 선례: `tableWidget.ts` 칸 편집기 `blur` 가 같은 이유로 `setTimeout(0)` 뒤 판정
- 안드로이드 뒤로 가기 키로 키보드만 내리면 포커스는 편집기에 남는다 → 서식 바는 화면 맨 아래에 남는다. 본문 밖을 누르거나 다른 곳에 포커스가 가면 사라진다 (열린 질문 Q5)
- `AppTopBar` 의 `showToolbar` 는 F-233 3.1 조건 **그리고** `(!docked || editorFocused)`. `docked` 면 `TopBar` 가 서식 바 줄에 `editor-toolbar-row--docked` 클래스를, `EditorToolbar` 에 `docked` 를 넘긴다

### 3.5 버튼이 포커스를 빼앗지 않게 (docked 때만)

- 지금 코드는 서식 바 버튼에 `mousedown` 처리가 없어, 누르면 버튼이 포커스를 가져가고(편집기 blur → 안드로이드 키보드 내려감) `runToolbarCommand` 의 `view.focus()` 가 다시 올린다. 휴대폰에서 버튼마다 키보드가 내려갔다 올라오는 원인
- **docked 줄 전체(`.editor-toolbar-row--docked`)에서 `mousedown` 의 기본 동작을 막는다** — 버튼뿐 아니라 줄의 빈 곳(padding·구분선)을 눌러도 포커스가 body 로 빠지지 않게. 선례: `ContextMenu.tsx` `keepFocus`, `tableWidget.ts` `buildAddButton`, `DocumentArea.tsx` 댓글 달기 버튼. 전부 `mousedown`
- 가로로 끌어 스크롤하는 터치는 `mousedown` 을 만들지 않으므로 스크롤은 그대로다
- **예외 — 한글 조합 중이면 버튼에서는 막지 않는다.** 판정은 `isComposing(주 view)`(`src/editor/composition.ts`). 막지 않으면 버튼이 포커스를 가져가며 브라우저가 조합을 확정(`compositionend`)하고, F-303 5.4 대로 포커스 잃은 조합은 끝난 것으로 보아 밀린 원격 업데이트도 비워진다. 그 뒤 `click` 에서 명령이 확정된 글자 위에 걸리고 `view.focus()` 로 돌아온다. 이 경우만 키보드가 한 번 내려갔다 올라올 수 있다 (열린 질문 Q4)
  - 막으면 조합이 살아 있는 채로 명령 트랜잭션이 들어간다 — CM6 가 조합 중 DOM 을 보호하는 구간에 문서 변경이 끼어 음절 중복·유실 위험. 이 명세는 그 위험을 지지 않는다
  - 줄의 빈 곳(버튼 밖)은 조합 중에도 막는다 — 조합을 이어 가는 편이 사용자 의도에 맞다
- 601px 이상(docked 아님)은 지금 동작 그대로 — 막지 않는다

### 3.6 제목 목록·툴팁 (docked 때만)

- 줄이 화면 맨 아래라 지금처럼 버튼 **아래**로 열면(`EditorToolbar.tsx` 제목 목록 `r.bottom + 2`, 툴팁 `r.bottom + 6`) 키보드 뒤나 화면 밖으로 나간다 → docked 면 **버튼 위로** 연다(목록 아래 끝 = 버튼 위 끝 − 2px, 툴팁 아래 끝 = 버튼 위 끝 − 6px). 가로 좌표 규칙은 그대로
- 제목 목록을 **손가락·마우스로 열 때는 첫 항목으로 포커스를 옮기지 않는다** — 옮기면 편집기 blur → 키보드가 내려가 줄 위치가 바뀌고 목록 좌표가 어긋난다. 키보드로 열 때(`click` 의 `detail === 0`)는 지금처럼 첫 항목에 포커스
- 목록이 열린 채 `visualViewport` `resize` 가 오면 목록을 닫는다 — 좌표가 낡는다. 선례: `useContextMenu.ts` 가 `resize` 로 우클릭 메뉴를 닫음
- 601px 이상은 지금 그대로

### 3.7 IME·불변식

- 이 명세는 편집기에 트랜잭션을 만들지 않는다(명령 실행은 기존 `runToolbarCommand` 그대로). 원격 업데이트 보류·비우기(F-301 2.1, F-303)와 조합 끝 재계산 따라잡기(`compositionCatchup`)에 새 경로를 만들지 않는다
- 서식 바가 **나타나고 사라지는 때는 포커스 변화 때뿐**이다. 포커스가 빠지면 조합은 이미 끝난 것(F-303 5.4)이라, 조합 도중에 서식 바가 생기거나 없어지는 일은 없다
- 조합 **도중에** 일어날 수 있는 레이아웃 변화는 키보드 높이 변화(추천 단어 줄이 생기고 사라짐 등) → 앱 틀 높이 변화 → CM6 스크롤러 크기 변화 하나뿐이다. 안드로이드 Chrome 108 이전 기본(`resizes-content`)이 바로 이 동작이었고, CM6 는 크기 변화에 줄 DOM 을 다시 그리지 않고 측정만 한다. 실기기 확인은 사람 확인 H5
- 조합 중 탭은 3.5 예외로 조합을 먼저 끝낸다
