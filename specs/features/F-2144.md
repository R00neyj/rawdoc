# F-2144 CLI 이미지 올리기를 WebP 로
상태: 승인 (2026-10-14, Q2 = jsquash, Q1 = 기본값). 사용자 요청 "cli로 이미지까지 업로드할때 webp 로 안올라가는거 같음". 정해진 것: wasm 인코더를 CLI 번들에 넣는다(런타임 의존성 0 유지, 서버 변환 없음), 규칙은 브라우저와 같다(커지거나 실패하면 원본). 구현 담당 `complex-implementer`(아무도 돌려 보지 않은 wasm 번들). `App.tsx` 변경 없음

## 근거 (2026-10-14 HEAD, 이름으로 찾는다)
- CLI 에서 이미지를 올리는 길은 `upload` 하나다: `main.ts` `case 'upload'` → `commands.ts` `upload` → `client.ts` `apiUploadAttachment`. `new`·`put` 은 첨부를 올리지 않는다(`grep attach cli/src`)
- 브라우저 규칙: `src/storage/toWebp.ts` quality 0.9, 결과가 작을 때만. 부르는 쪽은 모두 **png·jpg 만** 바꾼다 — `serverStore.ts` `putAttachment`(gif·webp·id 지정 제외), `importVault.ts` `applyVaultPlan`·`e2eeStore.ts`(png·jpg 만), `githubImages.ts`(gif·webp 제외). gif 는 움직임을 잃지 않게, webp 는 이미 webp 라서
- 서버는 형식만 판정한다(`worker/imageSniff.ts` `sniffImage`, 픽셀 40,000,000 초과 거부). 5MB 검사는 받은 바이트(=변환 뒤)에 한다(`worker/v1.ts`)

**직접 재거나 돌린 것** (스크래치, Node 22.23.3·24.13.0, 저장소 Vite 7.3.6·Vitest 5.0.0)
- (a) `@jsquash/*` 는 wasm 모듈을 넘기지 않으면 glue 가 `file://` 를 `fetch` 해 `TypeError: fetch failed`. `new WebAssembly.Module(바이트)` 를 각 `init` 에 넘기면 Node 22·24 둘 다 동작
- (b) `import x from '….wasm?inline'` 은 빌드 실패(`Unexpected character '\0'`). `?url&inline` 은 `data:application/wasm;base64,…` 문자열로 들어온다. `@jsquash/webp/encode.js` 는 simd·일반 glue 를 동적 import 해 `dist/assets/*.mjs` 두 파일이 더 생긴다 → `codec/enc/webp_enc_simd.js` + `utils.js` `initEmscriptenModule` 을 직접 import 하면 `inlineDynamicImports` 없이 파일 1개
- (c) 크기(지금 `cli/src/main.ts` + 변환 모듈을 같은 설정으로 묶음): `rawdoc.js` 129.70 kB → **1,163.58 kB**. `npm pack --dry-run` 묶음 36,228 B → **425,497 B**, 풀린 크기 130,211 B → 1,164,090 B. 비교로 지금 번들 + 날 `.wasm` 세 파일(glue 없음)은 묶음 314,376 B
- (d) `--version` 시작 5회: 66~78 ms → 74~86 ms. wasm 컴파일·초기화 첫 변환 때 21~50 ms
- (e) 변환(번들 실행, Node 22): `og-image.png` 131,032 → 63,406 B(363 ms), 4000×3000 JPEG 2,546,086 → 818,250 B(1.3 s), 1×1 PNG 70 B → webp 100 B·`toss-qr.png` 1,388 → 9,026 B(둘 다 원본 유지 대상)
- (f) `decodeJpeg(…, { preserveOrientation: true })` 는 EXIF Orientation 6 인 40×20 을 20×40 으로 돌린다(`false` 면 40×20). 16비트 PNG 는 8비트로 풀린다. 앞 절반 JPEG 는 회색으로 채워 풀리며 stderr 에 `Premature end of JPEG file` 을 쓴다 — `init(module, { printErr: () => {} })` 로 0 바이트. 깨진 PNG·헤더만 60000×60000 PNG 는 `unwrap_throw` 를 던진다
- (g) Vitest 가 `?url&inline` 을 그대로 풀어 실제 wasm 변환 테스트가 통과(저장소 설정이 아닌 최소 설정으로 확인)

## 2. 변환 — `cli/src/webp.ts`
```ts
export function toWebpBytes(bytes: Uint8Array): Promise<Uint8Array> // 바꾸지 않으면 받은 객체를 그대로 돌려준다
```
- `inspectImageBytes(bytes)`(`src/lib/imageFile.ts`)가 `null` 이거나 `ext` 가 `png`·`jpg` 가 아니면 원본 — 브라우저 호출처와 같다. gif·webp·그 밖은 지금처럼 서버가 판정한다
- `width × height > 40_000_000` 이면 풀지 않고 원본(`// worker/imageSniff.ts MAX_PIXELS`, `githubImages.ts` `GITHUB_IMAGE_IMPORT_MAX_BYTES` 주석 방식). 서버가 어차피 거부하고, 압축 폭탄을 wasm 메모리에 풀지 않게
- 풀기: png 는 `@jsquash/png` `decode`, jpg 는 `@jsquash/jpeg` `decode(…, { preserveOrientation: true })` — 변환하면 EXIF 가 사라지므로 방향을 픽셀에 굽는다. 브라우저 `createImageBitmap` 도 방향을 굽는다고 보지만 돌려 확인하지 않았다(H1)
- 굽기: `webp_enc_simd` 의 `encode` 에 `@jsquash/webp/meta.js` `defaultOptions` + `quality: 90`(브라우저 0.9). 그 밖 옵션은 기본값
- 결과 길이 `<` 원본 길이일 때만 결과, 같거나 크면 원본. 어디서든 던지면 원본. 크기 한도(5MB)는 미리 재지 않는다(F-2021 4.2 그대로) — 변환으로 5MB 아래가 되면 올라간다
- wasm 은 세 `.wasm` 을 `?url&inline` 으로 받아(측정 b) `WebAssembly.Module` 로 만들어 각 `init` 에 넘긴다. 첫 png·jpg 에서 한 번만 만들고 Promise 를 프로세스 동안 둔다 — 다른 명령은 컴파일 비용이 없다. simd 판본만 싣는다(Node 22 의 V8 은 wasm SIMD 를 늘 켠다)
- 코덱 출력은 어디에도 쓰지 않는다: emscripten 두 모듈에 `print`·`printErr` 를 빈 함수로(측정 f). 표준 출력은 결과 데이터만이라는 F-2021 4.1 규칙
- 변환했다는 안내는 하지 않는다. 사람용 출력은 서버가 준 `markdown` 그대로(`…/{id}.webp`), `--json` 의 `ext`·`mime`·`size` 가 결과를 보인다

## 3. 번들과 고지
- `cli/dist/` 는 `rawdoc.js` 하나와 `THIRD_PARTY_NOTICES.txt` 뿐. `rawdoc.js` 에 `node:` 아닌 import 가 없다(F-2021 3.3). wasm 을 `dist/` 에 따로 두면 묶음이 약 110 kB 작지만(측정 c) 한 파일 원칙이 깨지고 실행 위치에서 `.wasm` 을 찾는 코드가 든다 — base64 로 넣는다
- 고지: Apache-2.0(jsquash glue)·BSD(libwebp)·IJG/BSD(libjpeg-turbo)는 바이너리 재배포에 고지를 요구한다. 플러그인이 `generateBundle` 에서 `node_modules/@jsquash/{webp,png,jpeg}/LICENSE` 와 `codec/LICENSE.codec.md` 를 패키지 이름·버전 머리줄과 이어 붙여 낸다 — 버전을 올려도 손으로 고치지 않게
- `src/`·`worker/` 는 `@jsquash/` 를 import 하지 않는다(U7) — 앱 번들·precache 변화 0
