## 2. 범위

### 한다

- 에디터를 만들 때마다(= `Editor` 마운트마다) **그 에디터 전용 `Y.Doc`** 을 만들고, 저장소 본문을 LF 로 바꿔 `Y.Text` `content` 에 심고, `EditorState` 를 그 `Y.Text` 로 만든다. `ySync` 가 이후 모든 로컬 변경을 같은 update 안에서 `Y.Text` 로 옮긴다
- `history()` → `Y.UndoManager` + `y-codemirror.next` 의 `yUndoManager` 플러그인. **묶음 단위는 지금 `history()` 와 같게** 맞춘다(4장, U5 결론)
- 에디터를 버릴 때 `Y.Doc` 을 버린다
- 되돌리기 키맵과 표 칸의 되돌리기 위임을 새 명령으로 바꾼다

### 하지 않는다

- provider·WebSocket·awareness·원격 커서 — F-304·F-305·F-307
- 조합 중 원격 업데이트 큐 — F-303. F-302 에는 원격 업데이트가 없다
- `Y.Doc` 영속(IndexedDB `md-yjs`) — F-306
- **제목 `Y.Text`(`title`) — F-305.** F-301 3.2 는 제목도 `Y.Doc` 에 넣지만, F-302 단계에서는 그 값을 읽는 곳이 없다. 넣으면 App 의 `docs[].title`·제목 위젯과 손으로 맞춰야 하는 사본이 하나 더 생겨 불변조건(7장)에 어긋난다. provider 가 붙는 F-305 에서 제목 저장 경로와 함께 옮긴다
- 저장 경로·`useDocSaver`·outbox·`version` — 그대로
- `Y.Doc` 을 에디터 밖(App·훅)으로 꺼내는 것 — F-305 가 provider 와 함께 정한다(13장 Q6)

## 3. `Y.Doc` 수명과 원본

### 3.1 만들기

`createEditor(parent, { text, … })` 가 `EditorState` 를 만들기 **직전에** `createYBinding(text)` 를 한 번 부른다. 순서가 계약이다

1. `new Y.Doc()` — 옵션 없음(`guid` 무작위, `gc: true`). `guid` 는 F-305 가 provider 와 함께 정한다
2. `ydoc.getText('content')` 에 `toEditorText(text)` 를 **origin 없이** 한 번 넣는다(씨앗). `text` 가 빈 문자열이면 넣지 않는다
3. `new Y.UndoManager(ytext, { trackedOrigins: new Set(), captureTimeout: Number.POSITIVE_INFINITY })` — **씨앗 뒤에** 만든다. 4.3
4. `EditorState.create({ doc: ytext.toString(), extensions })` — 첫 문서는 `text` 가 아니라 `ytext.toString()` 에서 만든다. `EditorState` 가 처음부터 `Y.Text` 의 투영이 되게 하는 것이다

- `Y.Text` 이름 `content` 는 **F-304 이후 DO SQLite 에 영속되는 식별자**가 된다. 제품명과 무관하게 고정한다(`CLAUDE.md` "저장소 식별자" 규칙과 같은 이유). 상수 `Y_TEXT_NAME` 으로 둔다(5.1)
- 문서를 여는 경로는 지금과 같다 — `App` 의 `store.get(currentDocId)` → `setOpenDoc` → `<Editor text={openDoc.content}>` → 마운트 → `createEditor`. `Editor`·`App` 은 한 줄도 바뀌지 않는다
- **F-305 가 더한 짝 함수**: 실시간 경로(첫 동기화 뒤 방 Doc에서 편집기 Doc을 복제하는 경우)는 `createYBinding` 대신 `yBinding.ts` 의 `createYBindingFromState(state: Uint8Array)` 를 쓴다 — 씨앗(2번)을 넣지 않고 주어진 Yjs 상태를 그대로 적용한 뒤 `UndoManager` 를 그 **뒤에** 만드는 점은 같다(F-305 9.1)

### 3.2 버리기 — 문서 전환·다시 마운트·모드 전환

| 사건 | 지금 | F-302 |
| --- | --- | --- |
| 문서 전환 (`key` 의 `currentDocId` 가 바뀜) | `Editor` 언마운트 → `handle.destroy()` → 새 마운트. 실행 취소 기록이 사라진다(ia.md 126행) | 같다. `destroy()` 가 그 `Y.Doc` 을 버리고 새 마운트가 새 `Y.Doc` 을 만든다. 실행 취소 기록도 `Y.Doc` 과 같이 사라진다 |
| 다시 마운트 (`editorRemountNonce` — 편집 잠금 되찾음 F-213, 편집권 되찾음 F-296, 가져오기로 열린 문서 갱신 F-282) | 저장소 값으로 `openDoc` 을 바꾸고 새 마운트 | 같다. **열린 `Y.Doc` 에 저장소 값을 되돌려 쓰지 않는다** — 옛 `Y.Doc` 을 버리고 새 값으로 새 `Y.Doc` 을 만든다(7장) |

`destroy()` 순서: 기존 정리 → `view.destroy()`(`ySync` 가 `unobserve`, `yUndoManager` 가 리스너·tracked origin 을 뗀다) → `binding.destroy()`. `binding.destroy()` 는 `ydoc.destroy()` 하나면 된다 — `Y.UndoManager` 는 생성자에서 `doc.on('destroy', this.destroy)` 를 걸어 문서와 같이 죽는다(yjs `UndoManager.js` 확인). 두 번째 호출은 아무것도 안 한다(`ydoc.isDestroyed` 로 판정)

### 3.3 무엇이 원본이고 저장은 무엇을 읽는가

- **원본: 그 에디터의 `Y.Text`.** `EditorState` 는 투영이고, 로컬 변경은 `ySync` 의 `update()` 가 **같은 view update 안에서 동기로** `Y.Text` 에 옮긴다(`y-sync.js` `YSyncPluginValue.update` 가 `ytext.doc.transact(…, conf)`). `Y.Text` 를 바꾸는 다른 주체는 F-302 에 없다 — 되돌리기·다시 실행은 `Y.Text` 를 바꾸고 `ySync` 의 observer 가 곧바로 `view.dispatch` 로 `EditorState` 에 옮긴다. 따라서 **모든 트랜잭션 경계에서 `ytext.toString() === view.state.doc.toString()`** 이다
- **저장 경로는 바꾸지 않는다.** `useDocSaver` 는 `handle.getText(lineEnding)` 을 읽고, `getText` 는 지금처럼 `view.state.doc.sliceString(0, len, sep)` 이다. 공유(`getShareDoc`)·인쇄·보기 HTML·내보내기·`새 문서로 저장` 도 같은 `getText` 를 읽는다. 위 동치 때문에 이것은 `Y.Text` 에서 나온 **단방향 파생**이고, 사람이 손으로 맞추는 사본이 아니다(7장). `Y.Text` 에서 직접 읽는 안은 13장 Q1
- **저장소 → `Y.Doc` 방향은 씨앗 한 번뿐이다(3.1 2번).** 그 뒤로 저장소 값이 열린 `Y.Doc` 에 들어오는 길은 없다. 저장소 값이 바뀌어 화면에 반영해야 하는 경우(3.2 다시 마운트)는 새 `Y.Doc` 을 만든다

### 3.4 씨앗 심기 — F-301 3.3 "브라우저는 씨앗을 심지 않는다" 와의 관계

F-301 2.2 1번("브라우저는 절대 `Y.Doc` 에 본문을 밀어 넣지 않는다")·3.3("브라우저는 어떤 경우에도 씨앗을 심지 않는다")은 **DO 와 이어지는 공유 `Y.Doc`** 에 대한 규칙이다. 두 탭이 같은 공유 문서에 각자 씨앗을 심으면 본문이 두 번 들어가기 때문이다. 한편 F-301 5.4 는 로컬 저장소 문서·폴백 문서도 같은 `Y.Doc` 코드를 쓴다고 정했고, 그 문서들은 DO 가 없어 누군가 심지 않으면 비어 있다. 이 명세는 둘을 이렇게 가른다

- **provider 에 붙지 않는 `Y.Doc`**(로그아웃 로컬 문서, F-305 의 폴백 문서, 그리고 F-302 단계의 모든 문서): 브라우저가 에디터를 만들 때 한 번 심는다. 그 `Y.Doc` 은 그 에디터 하나만 쓰고, 영속되지 않고, 에디터와 함께 버려진다 — 두 곳이 같은 `Y.Doc` 에 심을 길이 없다
- **provider 에 붙는 `Y.Doc`**(F-305 이후 연결 성공한 서버 문서): 브라우저는 심지 않는다. F-301 3.3 그대로
- **경계 규칙(F-305 에 넘기는 계약): 브라우저가 씨앗을 심은 `Y.Doc` 은 어떤 provider 에도 붙이지 않는다.** 붙이면 DO 의 씨앗과 합쳐져 본문이 두 번 들어간다. F-301 8.1 "한 문서는 세션 동안 한 경로만" 과 같은 선이다. 운영 provider 는 `y-protocols` sync 순서상 입양으로도 이를 막을 수 없다 — 연결할 문서의 편집기 Doc 을 비운 채 만든다(F-304 11.3 1번)
- 개발용 연결(`?ysync`)·e2e 훅은 브라우저가 심은 Doc 을 이으므로 입양(F-303 8.3)으로 씨앗 두 벌을 막는다. 운영 provider 에는 여전히 붙이지 않는다

F-301 본문 문구를 이 구분에 맞게 다듬는 것은 12장 갱신 대상이다

- **씨앗은 실행 취소 대상이 아니다.** 씨앗은 origin 없는 트랜잭션이고, `UndoManager` 는 씨앗 **뒤에** 만들며 `trackedOrigins` 에 `null` 을 넣지 않는다. 둘 중 하나만 지켜도 첫 Ctrl+Z 가 본문을 지우지 않지만 둘 다 지킨다 — 기본값(`new Set([null])`)으로 씨앗 뒤에 만들면 실측 (c) 대로 Ctrl+Z 1회에 본문 전체가 사라진다
- `yUndoManager` 플러그인이 생성자에서 `addTrackedOrigin(YSyncConfig)` 를 하므로(`y-undomanager.js`), 결과적으로 추적되는 origin 은 **`ySync` 가 로컬 편집을 넣을 때 쓰는 `YSyncConfig` 하나**(+ `UndoManager` 자신)다. F-301 5.4 "로컬 origin 으로 한정" 이 이것이다

### 3.5 줄바꿈

- 씨앗은 `toEditorText(text)`(`src/lib/lineEnding.ts`, `\r\n`·`\r` → `\n`)를 거친다. **`Y.Text` 에 `\r` 이 들어가면 안 된다** — CM6 는 `lineSeparator` 를 지정하지 않아 `\r\n` 을 줄 구분 하나로 읽으므로 `Y.Text` 와 `EditorState` 의 길이가 줄마다 1씩 어긋나고, `ySync` 가 위치를 그대로 옮기므로 편집이 엉뚱한 자리에 들어간다(실측 (c))
- 이후 로컬 입력은 `ySync` 가 `insert.sliceString(0, insert.length, '\n')` 로 옮겨 LF 만 들어간다. 붙여넣기의 `\r\n` 은 CM6 가 입력 단계에서 이미 줄로 나눈다
- 저장·내보내기의 CRLF 복원은 지금처럼 `getText(lineEnding)` 이 한다. **원문 바이트 보존이 지금과 똑같다**(A13)

## 4. 되돌리기 — U5 결론

### 4.1 두 방식의 묶음 규칙 (코드로 확인)

| | CM6 `history()` (`@codemirror/commands` 6.11.0) | `Y.UndoManager` (yjs 13.6.32) |

| S4 | 표 칸 `a`(`input.table`) → 50ms 뒤 `<br>`(`input.table`) — F-162 A2 와 같은 열 | `\| 1a<br> \| 2 \|` → `\| 1a \| 2 \|` | **`\| 1 \| 2 \|`** | `\| 1a \| 2 \|` |

**결론: Yjs 기본 묶음은 지금과 다르다.** 빠르게 이어지는 서로 다른 동작(입력 뒤 붙여넣기·클릭 후 입력·표 칸 쓰기 뒤 줄바꿈 삽입)을 한 번에 되돌려 **사용자가 의도한 것보다 많이 지운다.** 조합은 반대로 더 잘게 나뉜다. 기존 e2e 중 `F-162 A2`·`F-140 A14` 가 이 차이로 실패할 열이다(10장)

### 4.3 결정 — CM6 규칙을 그대로 흉내 낸다

- `Y.UndoManager` 의 시간 묶음을 끈다(`captureTimeout: Number.POSITIVE_INFINITY`). 그러면 `stopCapturing()` 을 부르기 전까지 모든 로컬 변경이 한 묶음에 합쳐진다
- 로컬 트랜잭션마다 4.4 의 `nextUndoGroup` 이 "새 묶음" 이라고 판정하면, **`ySync` 가 그 변경을 `Y.Text` 에 넣기 전에** `undoManager.stopCapturing()` 을 부른다. 그러면 `Y.UndoManager` 가 그 변경부터 새 스택 항목을 연다
- 이 방식은 실측 (b) 에서 7가지 모두 `history()` 와 같았다. 4.1 표의 "합치는 조건" 을 한 글자도 바꾸지 않고 옮기는 것이 이 결정의 내용이다. 다른 안(Yjs 기본 500ms 를 받아들이기)은 13장 Q2

### 4.4 `src/editor/undoGroup.ts` — 계약

```ts
import type { ChangeSet, Transaction } from '@codemirror/state'

export const UNDO_GROUP_DELAY_MS = 500

export type UndoGroupState = {
  changes: ChangeSet      // 지금 묶음의 변경을 이어 붙인 것 (묶음 시작 문서 → 지금 문서)
  time: number            // 묶음의 마지막 변경 트랜잭션의 Transaction.time
  selectionMoved: boolean // 마지막 변경 뒤 선택만 바뀐 트랜잭션이 있었는가
} | null

export function nextUndoGroup(
  prev: UndoGroupState,
  tr: Transaction,
): { state: UndoGroupState; startNew: boolean }
```

규칙(4.1 CM6 열을 그대로):

1. `tr` 에 `ySyncAnnotation` 이 붙어 있으면(되돌리기·다시 실행의 결과, F-303 이후엔 원격 변경) `{ state: null, startNew: false }`. 다음 로컬 변경은 새 묶음이 된다 — CM6 가 되돌리기 뒤 첫 변경을 새 묶음으로 여는 것과 같다
2. 변경이 없고 선택이 있는 트랜잭션: `prev` 가 있으면 `selectionMoved: true` 로 바꿔 돌려주고, 없으면 `null`. `startNew: false`
3. 변경도 선택도 없는 트랜잭션(효과만 — `forceRecalc` 등): `prev` 그대로, `startNew: false`
4. 변경이 있는 트랜잭션: userEvent 는 `tr.annotation(Transaction.userEvent)`, 시각은 `tr.annotation(Transaction.time)`. 아래가 모두 참이면 **합친다**, 하나라도 거짓이면 **새 묶음**
   - `prev` 가 있다
   - userEvent 가 없거나 `/^(input\.type|delete)($|\.)/` 에 맞는다
   - (`selectionMoved` 가 거짓 **이고** `time - prev.time < UNDO_GROUP_DELAY_MS` **이고** 닿음) **또는** userEvent 가 정확히 `input.type.compose`
   - "닿음": `prev.changes` 의 바뀐 범위(뒤쪽 문서 좌표)와 `tr.changes` 의 바뀐 범위(앞쪽 문서 좌표) 중 한 쌍이라도 `t >= from && f <= to` — `@codemirror/commands` `isAdjacent` 와 같은 부등식(맞닿음 포함)
5. 합치면 `changes` 는 `prev.changes.compose(tr.changes)`, 새 묶음이면 `tr.changes`. 둘 다 `time` 은 이 트랜잭션 시각, `selectionMoved: false`

- 순수 함수다. DOM·`Y.Doc` 을 모른다. `ySyncAnnotation` 만 `y-codemirror.next` 에서 가져온다
- `UNDO_GROUP_DELAY_MS` 는 `history()` 의 `newGroupDelay` 기본값(500)과 같은 값이다. 바꾸지 않는다

### 4.5 명령·키맵 — `undoLocal`·`redoLocal`·`undoKeymap`

`y-codemirror.next` 0.3.6 의 공개 export 는 `yCollab`·`ySync`·`ySyncFacet`·`YSyncConfig`·`ySyncAnnotation`·`yRemoteSelections`·`yRemoteSelectionsTheme`·`YRange`·`yUndoManagerKeymap` 뿐이고(`dist/src/index.d.ts`), `package.json` `exports` 가 `.` 하나라 `y-undomanager.js` 를 직접 가져올 수 없다. `yUndoManager` 플러그인은 `yCollab(ytext, null, { undoManager })` 로만 얻는다. 그 키맵 `yUndoManagerKeymap` 의 명령은 읽기 전용을 보지 않으므로(4.1) **키맵은 우리 것을 쓴다**

- `undoLocal: StateCommand` — `state.readOnly` 면 false. 그 state 의 `UndoManager`(yBinding 안의 Facet 으로 찾는다)의 `undoStack` 이 비었으면 false. 아니면 `undoManager.undo()` 후 true. `redoLocal` 은 `redoStack`·`redo()` 로 같은 규칙. `@codemirror/commands` 의 `cmd()` 반환 규칙과 같다
- Facet 이 없는 state(yBinding 을 안 붙인 state)에서는 둘 다 false
- `undoKeymap` 바인딩(`preventDefault: true` 전부):

| key | mac | 명령 |
| --- | --- | --- |
| `Mod-z` | | `undoLocal` |
| `Mod-y` | `Mod-Shift-z` | `redoLocal` |
| `Mod-Shift-z` | | `redoLocal` |

- 지금 `historyKeymap` 과 다른 점: Windows `Ctrl+Shift+Z` 가 본문에서도 다시 실행이 된다(지금은 Linux 만. 표 칸 `cellKeydown` 은 이미 모든 OS 에서 그렇다), `Mod-u`·`Alt-u`(선택 되돌리기)가 없어진다. 13장 Q3·Q4
- 브라우저 편집 메뉴의 `historyUndo`·`historyRedo`(`beforeinput`)는 `yCollab` 이 넣는 핸들러가 받는다. CM6 는 `domEventHandlers` 핸들러가 true 를 돌려주면 `preventDefault()` 를 부르고(`@codemirror/view` `InputState.runHandlers`), 그 핸들러는 항상 true 라 브라우저 기본 되돌리기와 겹치지 않는다. 읽기 전용이면 `contentEditable=false` 라 `beforeinput` 이 오지 않는다. 따로 핸들러를 넣지 않는다

### 4.6 표 칸

`tableWidget.ts` `cellKeydown` 의 Mod-z·Mod-Shift-z·Mod-y 는 `endEdit(mainView)` 뒤 주 에디터의 되돌리기를 부른다. `import { redo, undo } from '@codemirror/commands'` 를 `undoLocal`·`redoLocal`(yBinding)로 바꾼다. 그대로 두면 주 에디터에 `historyField` 가 없어 **칸에서 Ctrl+Z 가 아무것도 안 한다.** `guardComposing` 은 그대로 감싼다(둘 다 `StateCommand`)

## 5. 조립

### 5.1 `src/editor/yBinding.ts` — 계약

```ts
import type * as Y from 'yjs'
import type { Extension, StateCommand } from '@codemirror/state'
import type { KeyBinding } from '@codemirror/view'

export const Y_TEXT_NAME = 'content'

export type YBinding = {
  ydoc: Y.Doc
  ytext: Y.Text
  undoManager: Y.UndoManager
  extension: Extension   // 묶음 판정 플러그인 + UndoManager Facet + yCollab(ytext, null, { undoManager })
  destroy(): void        // ydoc.destroy(). 두 번째 호출은 무시
}

export function createYBinding(text: string): YBinding
export const undoLocal: StateCommand
export const redoLocal: StateCommand
export const undoKeymap: readonly KeyBinding[]
```

- `createYBinding` 은 3.1 의 1~3번을 한다. DOM 을 건드리지 않는다 — node 단위 테스트에서 그대로 부른다(실측 (f))
- **묶음 판정 플러그인**(`ViewPlugin`): 상태 `UndoGroupState` 하나를 들고, update 의 트랜잭션을 순서대로 `nextUndoGroup` 에 넣는다. 하나라도 `startNew` 면 그 update 에서 `undoManager.stopCapturing()` 을 한 번 부른다. 한 update 에 트랜잭션이 여럿이면 `ySync` 가 그 변경 전체를 Yjs 트랜잭션 하나로 넣으므로 그 안을 더 나눌 수 없다 — CM6 는 여러 트랜잭션을 한 번에 dispatch 할 때만 이렇게 묶고 이 앱에는 그런 호출이 없다(`src/` 에서 `.dispatch(a, b)`·`dispatch(...)`·`dispatchTransactions`·`.update([` 형태 grep 0건, 2026-09-23)
- `awareness` 자리에는 `null` 을 넘긴다 — `yCollab` 이 `yRemoteSelections` 를 붙이지 않는다

### 5.2 `createEditor.ts` 조립 순서

- 확장 목록의 `history()` 자리에 `binding.extension` 을 둔다. **묶음 판정 플러그인은 `yCollab(...)` 보다 배열 앞**에 있어야 한다 — 같은 우선순위 안에서 `ViewPlugin.update` 는 조립 순서대로 돌고, `stopCapturing()` 이 `ySync.update` 의 `transact` 보다 먼저 불려야 한다. 뒤에 두면 경계가 한 트랜잭션씩 밀려 S4 가 `history()` 와 달라진다 — `F-162 A2` e2e 가 이걸 잡는다
- `yCollab` 이 넣는 순서(`ySync` 다음 `yUndoManager`)는 바꾸지 않는다. `yUndoManager` 의 선택 저장이 그 순서를 전제로 한다(`y-undomanager.js` `_onStackItemAdded`·`_storeSelection`)
- `binding.extension` 은 **어떤 compartment 에도 넣지 않는다**(3.2 — 재구성에 플러그인이 다시 만들어지면 묶음 상태·선택 저장이 끊긴다)
- `keymap.of([...defaultKeymap, ...historyKeymap, indentWithTab])` 의 `historyKeymap` 을 `undoKeymap` 으로 바꾼다. 위치·우선순위는 그대로
- `@codemirror/commands` import 에서 `history`·`historyKeymap` 을 뺀다(`defaultKeymap`·`indentWithTab` 은 남는다)
- `EditorState.create({ doc: binding.ytext.toString(), extensions })`. `text` 옵션은 `createYBinding(text)` 에만 넘긴다
- `destroy()` 끝에서 `view.destroy()` 다음에 `binding.destroy()`
- **handle(`EditorHandle`) 은 바뀌지 않는다.** `getText`·`setViewMode` 등 전부 그대로. `ydoc` 을 handle 로 내보내지 않는다(13장 Q6)

## 7. 불변조건

### 7.1 `CLAUDE.md` — 구현 시 메인이 고친다

F-301 2.1 의 승인된 문장을 **F-302 구현 커밋에서 메인이** `CLAUDE.md` "Invariants" 에 옮긴다. `CLAUDE.md` 는 영어가 원본이므로 아래 영어 문장을 넣는다. 영어는 승인된 한국어 문장의 번역이고 뜻을 더하거나 빼지 않았다

**바꿀 문장** — 지금:

> - **There is exactly one source of truth for document state: the CM6 `EditorState`.** Do not keep a separate string copy in sync with it

바꾼 뒤(승인 원문, F-301 2.1):

> - **열린 문서의 원본은 `Y.Doc` 의 `Y.Text` 하나다.** `EditorState` 는 그 투영이고, 둘은 `y-codemirror.next` 가 잇는다. 그 밖에 본문 문자열 사본을 두고 손으로 동기화하지 않는다. D1 `docs.content`·IndexedDB 캐시 본문은 `Y.Text` 에서 나오는 **단방향 파생**이고, 그 값을 열린 `Y.Doc` 에 되돌려 쓰지 않는다

`CLAUDE.md` 에 넣을 영어:

> - **The one source of truth for an open document is the `Y.Text` in its `Y.Doc`.** `EditorState` is a projection of it, and `y-codemirror.next` connects the two. Do not keep any other copy of the body text and sync it by hand. D1 `docs.content` and the IndexedDB cached body are **one-way derivations** of `Y.Text`; never write those values back into an open `Y.Doc`

**덧붙일 문장** — "IME 조합 중 재계산을 보류하면…"(영어: "If you defer recomputation during IME composition, you must catch up…") 바로 뒤에 한 줄. 승인 원문(F-301 2.1):

> - **원격 업데이트는 IME 조합 중에 적용하지 않는다.** 조합 중(표 칸 하위 에디터 조합 포함) 도착한 원격 Yjs 업데이트는 큐에 쌓고, `compositionend` 의 `forceRecalc` 와 같은 지점에서 한꺼번에 적용한다. Yjs 는 순서와 무관하게 병합되므로 지연 적용이 정합성을 깨지 않는다

`CLAUDE.md` 에 넣을 영어:

> - **Never apply remote updates during IME composition.** Remote Yjs updates that arrive during composition (including composition in a table-cell sub-editor) are queued and applied together at the same point as the `forceRecalc` on `compositionend`. Yjs merges regardless of order, so delayed application does not break consistency

- 나머지 불변조건 문장은 바꾸지 않는다(F-301 2.1 "바꾸지 않는 문장")
- `CLAUDE.ko.md` 는 스냅숏이라 자동으로 따라가지 않는다. 같이 고칠지는 메인 판단

### 7.2 F-302 에서 불변조건이 어떻게 지켜지나

| 불변조건 | F-302 에서 |
| --- | --- |
| 원본은 `Y.Text` 하나, `EditorState` 는 투영 | `EditorState` 의 첫 문서가 `ytext.toString()` 이고(3.1 4번), 이후 로컬 변경은 `ySync`, 되돌리기는 `Y.Text` → observer → `EditorState`. 손으로 맞추는 코드가 없다 |
