## 1. 범위

### 1.1 하는 것

- 편집 화면에서 **선택한 본문 범위**에 댓글을 달고, 한 단계 답글을 달고, 해결·다시 열기·삭제한다
- 앵커는 본문 **내용**에 붙는다(c1) — 위에 줄을 넣어도, 앞뒤를 고쳐도 같은 글자를 가리킨다. 범위가 통째로 지워지면 "본문이 지워진 댓글"(2.3)로 남는다
- 서버 문서: 실시간 경로에서 모든 접속자가 댓글을 실시간으로 본다. edit 이상은 오프라인에서도 달 수 있고(`md-yjs` 가 방 Doc 째 저장한다 — 댓글 `Y.Map` 도 그 안에 있다) 다시 붙으면 합쳐진다
- 로컬 문서: 댓글이 된다. 로그인하면 문서와 함께 계정으로 옮긴다(4.5·4.6)
- 서버 문서에서 @멘션과 답글이 앱 안 알림함에 알림을 만든다(3.5·4.8)
- **본문 바이트는 그대로다.** 댓글은 `Y.Text`(`content`) 밖의 `Y.Map`(`comments`)에만 있다. `.md` 내보내기·전체 내보내기·옵시디언 내보내기·인쇄·공유 링크·공개 보기·`/v1`·D1 `docs.content` 는 `Y.Text` 에서만 나오므로 댓글이 섞일 길이 없다(사용자 결정 9). 6장 로드맵의 수용 기준 하나가 이것을 바이트 비교로 판정한다

### 1.2 이번 범위에서 빼는 것

- 댓글 본문 **고치기**(지우고 다시 쓴다). 댓글 본문의 마크다운 렌더링(평문, 줄바꿈만 살린다), 이모지 반응, 첨부
- 메일·브라우저 푸시 알림(사용자 결정 5). 알림 설정(끄기·종류 고르기)
- 공유 링크·공개 보기·`/v1`·CLI 에서 댓글 보기(공유 링크 방문자는 댓글을 보지도 달지도 않는다)
- 보기 모드(F-123, 렌더링된 읽기 화면)에서의 댓글 표시 — 편집·원문 모드에서만 보인다(4.3)
- 검색(F-287)·지도(F-292)에 댓글 넣기
- 댓글 되돌리기(Ctrl+Z). 편집기 `Y.UndoManager` 는 `content` 만 추적한다(`yBinding.ts` `bind`) — 댓글 동작은 되돌리기 대상이 아니다
- 금고 문서의 댓글(사용자 결정 8)

## 2. 데이터 모델

### 2.1 `Y.Doc` 안의 자리 — 계약

| 이름 | 타입 | 내용 |
| --- | --- | --- |
| `content` | `Y.Text` | 본문 (그대로) |
| `title` | `Y.Text` | 제목 (그대로) |
| **`comments`** | **`Y.Map<CommentEntry>`** | **신규.** 키 = 댓글 id(`crypto.randomUUID()`), 값 = 아래 JSON. 첫 댓글과 답글이 같은 `Y.Map` 에 나란히 있다 |

- `comments` 는 **저장소 식별자**다(DO SQLite·`md-yjs` 에 영구히 남는다). 이름에 제품명이 없고, 한 번 정하면 바꾸지 않는다 — `Y_CONTENT_NAME` 처럼 `src/lib/docRoomProtocol.ts` 에 `Y_COMMENTS_NAME = 'comments'` 로 둔다
- 값은 **평범한 JSON 한 덩어리**(Yjs `ContentAny`)이고 중첩 `Y.Map` 을 쓰지 않는다. 바뀌는 필드는 첫 댓글의 `resolved` 하나뿐이라 동시에 고쳐도 잃는 것이 없다 — 답글은 따로 키를 가지므로 "A 가 해결, B 가 답글" 이 겹쳐도 둘 다 남는다. 해결을 두 사람이 동시에 누르면 Yjs 의 같은 키 규칙대로 한쪽 값이 이긴다(둘 다 해결이면 결과가 같다)

```ts
// src/lib/docComments.ts (F-501) — 서버·클라이언트가 같이 쓴다
type RelativePositionJSON = Record<string, unknown>   // docRoomProtocol.ts 의 것 그대로 (F-307)
type CommentAuthor = { id: string; email: string } | { id: null; email: null }  // 뒤쪽 = 로컬 문서
type CommentEntry = {
  v: 1
  parent: string | null                                          // 답글이면 첫 댓글 id. 한 단계만
  anchor: { start: RelativePositionJSON; end: RelativePositionJSON } | null  // 첫 댓글만. 답글은 null
  quote: string                                                  // 달 때 앵커 텍스트, 최대 200자(넘으면 199자 + '…'). 답글은 ''
  body: string
  mentions: string[]                                             // 소문자 이메일. 로컬 문서는 늘 []
  author: CommentAuthor
  createdAt: number                                              // ms
  resolved: { by: CommentAuthor; at: number } | null             // 첫 댓글만 뜻이 있다
}
```

- 앵커는 **시작 `assoc 0`, 끝 `assoc -1`** 로 만든다. 경계 바로 앞·뒤에 친 글자가 범위를 넓히지 않는다(c1)
- **앵커 JSON 은 `Y.relativePositionToJSON` 모양**이다 — F-307 원격 커서(`PeerCursor`)와 같은 형식이다. 검사는 `readPeerCursor` 보다 좁은 `readCommentAnchor` 로 한다(F-501 2.3)

### 2.2 작성자

| 문서 | `author` | 화면 |
| --- | --- | --- |
| 서버 문서 | `{ id, email }` — **서버가 확인한 값**(3.1·3.2). 클라이언트가 적어 보낸 값은 믿지 않는다 | 이메일 (F-307 접속자 표시와 같게) |
| 로컬 문서 | `{ id: null, email: null }` | `나` |
| 로컬 → 계정 이관 뒤 | 서버가 이관한 사용자로 채운다(4.6) | 이메일 |

### 2.3 고아 댓글 — "본문이 지워진 댓글"

- 판정: 앵커의 시작·끝을 풀었을 때 **시작 ≥ 끝**(빈 범위)이거나, 풀 수 없을 때(`null`, c7). 순수 함수 하나(F-501)가 정하고 편집기·서버·레일이 같이 쓴다
- **지우지 않는다.** 레일 맨 아래 `본문이 지워진 댓글` 묶음에 달 때의 `quote` 를 취소선으로 보여 준다. 거터 표시·앵커 장식이 없고 `본문으로 이동` 이 없다. 답글·해결·삭제는 된다
- **되돌아온다.** 지운 것을 되돌리기(Ctrl+Z)하면 Yjs 가 지워진 항목을 되살린 항목으로 이어 주므로 앵커가 원래 범위로 돌아온다(c1). 레일은 다음 위치 계산(4.2) 때 그 스레드를 제자리로 옮긴다
- 잘라서 다른 곳에 붙인 글은 따라가지 않는다(c1 — 새 항목이다). 고아가 된다
- 해결된 고아 스레드는 `해결된 댓글 보기` 를 켰을 때만 보인다(4.3)

## 3. 서버

### 3.1 보기 권한자의 댓글 쓰기 — 서버가 가려내는 방법 (반드시 정할 것 1)

지금 `/ws` 는 edit 이상만 받는다(`docSocket.ts` `resolveDocSocket` 이 view 를 4403 으로 닫고, `docRoomCore.ts` `readConnState` 가 `owner`·`edit` 만 인정한다). view 가 댓글을 보려면 방 Doc 이 있어야 한다 — 앵커가 `RelativePosition` 이라 D1 본문만으로는 위치를 풀 수 없다. 그래서 **view 도 소켓을 연다.** 남는 것은 view 가 보낸 것 중 본문 변경을 어떻게 막느냐다

| 안 | 갱신 하나당 비용 | 막는 힘 | 드는 것 | 판단 |
| --- | --- | --- | --- | --- |
| A. 임시 Doc 에 적용해 본문·제목 비교 | **14.7ms(100KB) / 34.5ms(1MB)**(c2) + 문서 한 벌 메모리 | 정확 | 코드는 짧다 | 안 씀 — 사람이 빨리 칠 때 초당 수십 건이면 DO CPU 를 그대로 먹는다 |
| B. 갱신을 풀어 뿌리 타입만 가리기(`decodeUpdate` + `getItem`·`findRootTypeKey`) | 0.004~0.014ms(c3) | 정확하게 짜기 어렵다 — 항목이 원점만 가질 때 부모를 서버 Doc·같은 갱신에서 찾아야 하고, 아직 없는 항목(pending)·지우기 집합의 범위마다 항목을 찾아야 한다. 하나라도 빠뜨리면 본문 쓰기가 샌다 | Yjs 내부 구조에 기대는 코드 | 안 씀 |
| **C. view 연결은 Yjs 로 쓰지 못하게(`isReadOnly`) + 댓글은 별도 명령 메시지로** | **Yjs 갱신: 0**(y-partyserver 가 decode 전에 버린다, c8). 명령 하나: JSON 파싱 + 앵커 두 개 풀기(0.003~0.22ms, c4) + `Y.Map` 한 번 쓰기 | **정확** — 막는 코드가 y-partyserver 의 이미 있는 분기다. 본문을 건드릴 수 있는 바이트가 서버 Doc 에 닿지 않는다 | 명령 5종의 검사 코드, 클라이언트 명령 보내기·응답 기다리기 | **채택** |
| D. 댓글만 `/api` RPC 로 받기 | 요청마다 Worker → DO RPC | 정확 | 오프라인 불가, 요청마다 쓰기 관문(F-2026) 1회 | C 와 같은 효과인데 소켓이 이미 열려 있다 — 안 씀 |

**결론 — C.**

- `DocRoom.isReadOnly(conn)` 이 연결 상태의 `role === 'view'` 일 때 참을 돌려준다. `readConnState` 는 `view` 를 받는다(`RoomRole` 에 `'view'`). 연결 상태는 hibernation 뒤에도 남는다(지금 `setState` 방식 그대로)
- view 연결의 **awareness 는 중계하지 않는다**(`relayAwareness` 앞에서 버린다) — F-307 의 `접속자` 는 "함께 편집 중인 다른 사람" 이다(ia.md 6장). 10장 Q4
- **명령 메시지** — 기존 문자열 채널(`__YPS:` + `encodeDocRoomMessage` 와 같은 JSON)을 쓴다. 계약(`src/lib/docRoomProtocol.ts`, F-503):

```ts
type CommentOp =
  | { type: 'comment-add'; id: string; start: RelativePositionJSON; end: RelativePositionJSON; body: string; mentions: string[] }
  | { type: 'comment-reply'; id: string; parent: string; body: string; mentions: string[] }
  | { type: 'comment-resolve'; id: string; resolved: boolean }
  | { type: 'comment-delete'; id: string }
type CommentOpReply =
  | { type: 'comment-ack'; id: string }
  | { type: 'comment-reject'; id: string; reason: 'forbidden' | 'invalid' | 'not_found' | 'too_long' | 'too_many' | 'rate_limited' }
```

- DO 가 명령을 받으면 순서대로: ① 보낸 연결이 `view` 인지(edit 이상은 3.2 의 직접 쓰기를 쓴다 — 명령이 와도 받아 준다) ② 분당 30번(메모리, 연결별) ③ 모양·한도(F-501 검사 함수) ④ `comment-add`: 앵커 둘을 서버 Doc 에서 풀어 **둘 다 `content` `Y.Text` 이고 시작 < 끝**인지(c7), `quote` 는 **서버가** 그 범위에서 잘라 만든다 ⑤ `comment-reply`: 부모가 있고 부모의 `parent` 가 `null`(한 단계) ⑥ `comment-delete`: 2.4 규칙 ⑦ 서버 origin(`COMMENT_SERVER_ORIGIN`)으로 `Y.Map` 에 쓴다. `author` 는 연결 상태의 `{ userId, email }`. 답글이면 같은 트랜잭션에서 첫 댓글의 `resolved` 를 `null` 로(4.4) ⑧ 보낸 연결에만 `comment-ack`. 어느 단계든 걸리면 `comment-reject` 하나
- 명령은 Yjs 가 아니므로 오프라인 대기열이 없다. **view 는 연결돼 있을 때만 댓글을 단다**(5.1 C4)
- 권한 다시 확인(`revalidateConnections`): 접근이 없어지면 지금처럼 4403 `revoked`. **edit 연결이 view 로 낮아졌으면 4403 `revoked`** 로 닫는다 — 클라이언트가 경로를 다시 판정해 view 로 다시 붙는다(4.1). view 가 edit 로 올라간 연결은 그대로 두고 다음 연결부터 edit 로 붙는다
- 막힌 계정: 지금처럼 `forbidden` 입력으로 소켓 없이 `view` 경로(F-2030 5.2). 댓글을 보지도 달지도 못한다

### 3.2 edit 이상의 직접 쓰기와 서버의 사후 검사

- edit 이상(소유자 포함)은 **편집기 `Y.Doc` 의 `comments` 에 직접 쓴다.** 본문과 같은 길(게이트 → 방 Doc → provider)을 타므로 오프라인·`md-yjs`·재연결 병합이 그대로 따라온다(사용자 결정 1 "오프라인이 Yjs 경로로 따라온다")
- 서버는 쓰기 **전에** 막지 않는다(막으려면 3.1 A·B 가 필요하다). 대신 DO 가 `comments` `Y.Map` 을 관찰해 **연결에서 온 트랜잭션**(origin 이 연결)을 검사하고, 어긋나면 **곧바로 서버 트랜잭션으로 고친다**:

| 무엇이 왔나 | DO 가 하는 것 |
| --- | --- |
| 새 항목의 `author` 가 보낸 연결의 사용자와 다름 | `author` 를 연결 사용자로 **다시 도장** |
| 새 항목의 모양·한도가 틀림(F-501 검사), 문서 500개·스레드 100개 초과, 부모가 없거나 답글의 답글 | 그 항목을 **지운다** |
| 있던 항목의 `resolved` 밖 필드가 바뀜 | 이벤트의 옛 값(`YMapEvent` `keys` 의 `oldValue`)으로 **되돌린다** |
| 지우기인데 2.4 삭제 규칙에 안 맞음 | 옛 값으로 **되살린다** |
| 첫 댓글이 지워져 부모 없는 답글이 남음 | 그 답글들을 **지운다** |

- 이 검사는 `comments` 를 바꾼 트랜잭션에서만 돈다. 본문만 바꾼 갱신에는 비용이 없다
- 고치기는 다른 접속자에게 원래 갱신이 먼저 퍼진 뒤에 따라간다 — 잠깐 보였다 바뀐다. **정직한 클라이언트는 이 규칙에 걸리지 않는다**(화면이 같은 규칙으로 먼저 막는다). edit 권한자는 이미 본문을 통째로 지울 수 있는 사람이므로, 사후 고치기로 충분하다고 본다
- **알려진 한계**: DO 저장소를 잃은 뒤(3.4) 누군가의 `md-yjs` 가 남의 옛 댓글을 다시 보내면 그 항목이 "보낸 사람" 으로 다시 도장된다. F-306 L7(저장소를 지우면 본문도 두 벌이 될 수 있다)과 같은 사고 때만 생긴다

### 3.3 D1 복사본 — 모양과 쓰는 때 (반드시 정할 것 2)

마이그레이션 `migrations/0012_comments.sql`(지금 마지막이 `0011_e2ee.sql`. F-502 를 쓸 때 다음 빈 번호). 계약 — 이름을 바꾸면 F-502~F-509 가 어긋난다:

```sql
CREATE TABLE doc_comments (          -- comments Y.Map 의 한쪽 방향 복사본. 원본은 DO
  doc_id TEXT NOT NULL,
  id TEXT NOT NULL,                  -- Y.Map 키
  parent_id TEXT,                    -- 답글이면 첫 댓글 id
  author_id TEXT,
  author_email TEXT,
  body TEXT NOT NULL,
  mentions TEXT NOT NULL DEFAULT '[]',   -- JSON 배열
  quote TEXT NOT NULL DEFAULT '',
  prefix TEXT NOT NULL DEFAULT '',   -- 앵커 앞 32자
  suffix TEXT NOT NULL DEFAULT '',   -- 앵커 뒤 32자
  anchor_from INTEGER,               -- DO 본문(LF) 기준 UTF-16 위치 힌트. NULL = 답글 또는 고아
  anchor_length INTEGER,             -- 앵커 길이. NULL = 답글 또는 고아 (F-501 Q2)
  resolved_at INTEGER,
  resolved_by TEXT,                  -- 이메일
  resolved_by_id TEXT,               -- 해결한 사람 id (F-501 Q2)
  created_at INTEGER NOT NULL,
  bytes INTEGER NOT NULL,            -- body·quote·prefix·suffix 의 UTF-8 바이트 합 (3.8)
  sig TEXT NOT NULL,                 -- 앵커 밖 필드의 짧은 해시
  anchor_sig TEXT NOT NULL,          -- quote·prefix·suffix·anchor_length 의 짧은 해시 (위치 제외, F-501 2.4·7.1)
  PRIMARY KEY (doc_id, id)
);
CREATE TABLE notifications (
  id TEXT PRIMARY KEY,
  recipient_email TEXT NOT NULL,     -- 초대가 이메일 기준이라 아직 가입 안 한 사람도 받는다
  kind TEXT NOT NULL CHECK (kind IN ('mention','reply')),
  doc_id TEXT NOT NULL,
  comment_id TEXT NOT NULL,
  thread_id TEXT NOT NULL,           -- 첫 댓글 id (이동에 쓴다)
  actor_email TEXT NOT NULL,
  doc_title TEXT NOT NULL,           -- 만들 때의 제목
  excerpt TEXT NOT NULL,             -- 댓글 본문 앞 120자
  created_at INTEGER NOT NULL,
  read_at INTEGER,
  UNIQUE (recipient_email, comment_id, kind)
);
CREATE INDEX notifications_recipient ON notifications(recipient_email, created_at DESC);
CREATE INDEX notifications_doc ON notifications(doc_id);
```

- 표 이름에 제품명이 없다(불변조건). `docs` 에 외래 키를 걸지 않는다 — 지금 `docs` 를 지우는 batch 들이 순서를 새로 맞춰야 해서다. 지우는 자리는 3.7 이 하나씩 적는다
- **쓰는 때 = DO 스냅숏(`DocRoomCore.snapshot`) batch 안.** 지금 문서 행 `UPDATE` + 사용량 줄 두 문장에 댓글 문장을 **변화가 있을 때만** 붙인다. 댓글 변화가 없으면 batch 는 지금과 똑같다(`docRoomCore.test.ts` "F-2027 C1" 이 그대로 통과한다)
  - 본문은 그대로이고 댓글만 바뀌었으면 문서 행 `UPDATE` 없이 댓글 문장 + 사용량 줄(하루 +1, F-2024 2.5 그대로)만. 댓글은 `docs.updated_at`·`version` 을 올리지 않는다 — 사이드바 순서가 댓글로 흔들리지 않는다
  - 문장 수: D1 무료는 호출당 질의 50개(c9). 행마다 `INSERT` 하면 500행이 넘친다. 그래서 **`json_each` 한 문장으로 여러 행**을 쓴다(지금 `DELETE_FOLDERS_SQL` 이 쓰는 방식). 바인딩 문자열은 2MB 까지(c9) — 1,000,000자마다 문장을 나눈다. 댓글 500개 최악도 upsert 2~3 + 지우기 1 + 알림 1 + 알림 정리 1 문장이다
- **무엇을 쓰나** — DO 는 불러올 때 `SELECT id, sig, anchor_sig FROM doc_comments WHERE doc_id = ?` 한 번으로 "D1 에 있는 것" 을 메모리에 든다. 스냅숏마다:
  - 새 항목·`sig` 가 달라진 항목 → upsert. 그 항목의 앵커(quote·prefix·suffix·위치)도 이때 푼다
  - `Y.Map` 에 없는 id → 지우고, 그 댓글의 알림도 지운다
  - **모든 항목의 앵커 다시 적기는 방이 빌 때(`roomEmptied`)와 알람 flush 에서만**, 그리고 `anchor_sig` 가 달라진 행만 쓴다. 이유: 위치 힌트를 매번 맞추면 위쪽을 한 글자 칠 때마다 아래 행 전부를 다시 써야 한다. 앵커를 모두 푸는 비용은 1MB·500개 최악 310ms(c4, 공개 API) — 편집 중 스냅숏마다가 아니라 방이 빌 때 한 번이다. 한 번 걸어 표를 만드는 방식(1.48ms)은 Yjs 내부 필드를 써서 기본으로 두지 않는다 — F-502 가 재 보고 고를 수 있다
- **복사본을 쓰는 곳**: 복원(3.4), 알림 만들기(3.5), 금고로 옮기기 전 개수(4.7), 운영·개인정보 요청 처리. **댓글 목록을 D1 에서 읽어 화면에 보이는 길은 두지 않는다** — 화면은 늘 `Y.Map` 을 읽는다

### 3.4 복원 경로와 불변조건 (반드시 정할 것 2 뒷부분)

**복원 = DO 가 빈 방에 씨앗을 심을 때 댓글도 같이 심는 것.**

- `DocRoomCore.load` 의 씨앗 가지(DO 저장소가 비어 D1 에서 본문을 심는 곳, `rows.length === 0`)에서, 본문을 심은 뒤 `doc_comments` 를 읽어 행이 있으면 `reanchor`(F-501)로 새 `Y.Text` 에 앵커를 다시 만들어 `comments` 에 넣는다. origin 은 서버의 흡수 origin(`ABSORB_ORIGIN` 과 같은 성격 — 클라이언트와 공유하지 않는 상수)
- `reanchor` 규칙(순수 함수, 계약): ① 본문의 `anchor_from` 자리에서 `quote` 로 시작하면 거기 ② 아니면 `quote` 가 나오는 곳을 최대 1,000번 찾아 `prefix`·`suffix` 가 가장 많이 맞는 곳, 같으면 `anchor_from` 에 가장 가까운 곳(1MB 되풀이 글 500행 21.7ms, c6). 후보는 힌트에 가까운 순으로 최대 1,000개, 앞뒤 문맥이 다 맞으면 멈춤, 고아 기록(`anchor_from` NULL)은 찾지 않음(F-501 4.2) ③ 없으면 고아(`anchor: null`, `quote` 는 그대로). 답글은 앵커가 없으니 그대로 넣는다
- 씨앗 가지가 도는 때는 셋이다: 처음 여는 문서(댓글 행이 있을 수 없다), **운영자가 DO 저장소를 지웠거나 잃었을 때**(복원이 필요한 경우), 금고로 옮긴 뒤 빼기(4.7 — 행을 이미 지웠다). 문서 삭제는 `roomGone` 이라 씨앗 가지에 오지 않는다
- 복원한 항목은 D1 에 이미 있으므로 새것으로 세지 않는다 — 알림이 다시 생기지 않는다(3.5)
- **알려진 한계**: 복원한 앵커는 원래 `RelativePosition` 이 아니다. 복사본의 인용문이 방이 빌 때 마지막으로 적힌 것이라, 그 뒤 앵커 둘레를 많이 고쳤으면 고아로 돌아올 수 있다

**불변조건과의 관계 — 결론: 위반이 아니다. 다만 문장을 고친다(9장 `CLAUDE.md`).**

- 지금 불변조건은 "D1 `docs.content`·IndexedDB 캐시 본문은 `Y.Text` 의 한쪽 방향 파생이고, **그 값을 열린 `Y.Doc` 에 되돌려 쓰지 않는다**" 이고, F-301 3.3 이 예외를 하나 둔다 — "D1 → `Y.Doc` 방향은 **DO 의 최초 씨앗 심기** 한 번뿐". 댓글 복원은 **정확히 그 자리**(같은 함수, 같은 조건, `blockConcurrencyWhile` 안이라 아직 아무 클라이언트도 붙지 않은 방)에서만 일어난다. 열린 `Y.Doc`(연결이 있는 방, 브라우저의 방 Doc·편집기 Doc)에 D1 댓글을 쓰는 길은 두지 않는다
- 브라우저는 D1 댓글을 읽지 않는다(3.3). 그래서 "복사본을 브라우저가 되돌려 쓰는" 길이 구조상 없다
- 로그인 이관(4.6)은 D1 이 아니라 **로컬 기록**을 DO 에 넣는 것이다 — view 명령(3.1)처럼 서버가 새 항목을 쓰는 것과 같은 종류다. 파생값 되돌리기가 아니다
- 로컬 문서의 댓글을 마운트 때 새 편집기 `Y.Doc` 에 다시 심는 것(4.5)은 지금 로컬 문서가 **본문을 마운트 때 심는 것**(architecture.md 3장 "저장소 → 에디터: 문서를 여는 시점 1회")과 같은 자리·같은 방향이다
- 고칠 문장(제안, 9장): 불변조건 둘째 줄 끝에 "D1 `doc_comments` 도 `comments` `Y.Map` 의 한쪽 방향 파생이다. D1 → `Y.Doc` 은 DO 가 빈 방에 씨앗을 심을 때 본문과 함께 한 번뿐이다" 를 덧붙인다

### 3.5 알림 — 만드는 때·중복·위조 (반드시 정할 것 4)

- **알아채는 곳은 DO 다.** 클라이언트가 "멘션했다" 를 따로 API 로 알리게 하면 그 호출을 위조·반복할 수 있고, 오프라인에서 단 댓글은 알림을 잃는다. DO 는 스냅숏마다 **D1 복사본에 없던 항목**(3.3 의 새 항목)을 이미 가려내므로, 같은 batch 안에서 알림 행을 만든다
  - "새것" 을 D1 에 있느냐로 정하므로 DO 가 쫓겨나도(eviction) 잃지 않는다 — batch 가 실패하면 다음 스냅숏에서도 여전히 새것이다
  - `UNIQUE (recipient_email, comment_id, kind)` + `INSERT OR IGNORE` 라 같은 batch 를 다시 돌려도 두 번 생기지 않는다
- **받는 사람**: `mention` — 항목의 `mentions` 중 3.6 에서 접근이 확인된 사람. `reply` — 답글이면 그 스레드의 첫 댓글 작성자와 앞선 답글 작성자들. 둘 다 해당하면 `mention` 하나만. **작성자 자신은 빼고**, 로컬 작성자(`id: null`)는 받지 않는다
- **위조 방지**: 알림의 보낸 사람(`actor_email`)은 항목의 `author` 에서 오는데, 그 값은 3.1(명령 — 서버가 적음)과 3.2(직접 쓰기 — 서버가 다시 도장)를 거친 것이다. 멘션 대상은 서버가 접근을 다시 확인한다(3.6). 클라이언트가 알림을 만드는 API 는 없다
- **시각**: 댓글이 서버에 닿고 스냅숏이 돈 뒤 — 조용해지면 5초, 계속 치면 최대 30초(`FLUSH_DEBOUNCE_MS`·`FLUSH_MAX_WAIT_MS`), 소유자가 하루 한도를 넘어 느린 저장이면 최대 60초(F-2027). 클라이언트가 60초마다 가져오므로(4.8) 최악 약 2분 뒤 보인다
- 댓글을 지우면 그 댓글의 알림도 같은 batch 에서 지운다. 스냅숏 전에 지워진 댓글은 알림이 생기지 않는다
- **정리**: 매일 Cron(`scheduled`, 지금 UTC 18시)이 90일 지난 알림, 받는 사람마다 최근 300개를 넘는 알림, 없는 문서의 알림을 지운다
- `doc_title` 은 만들 때의 제목이다 — 나중에 접근을 잃은 사람에게 바뀐 제목이 새지 않는다. 대신 제목을 바꾸면 옛 제목으로 보인다

### 3.6 멘션 후보와 서버 확인 (사용자 결정 6)

- "접근할 수 있는 사람" = 소유자 이메일 ∪ 문서 초대 ∪ 문서가 든 폴더와 상위 폴더들의 초대(`access.ts` 의 `grantRole`·`folderChainRole` 과 같은 규칙, 역할 무관). 한 함수(`worker/docPeople.ts`, F-502)가 **질의 3번 이하**로 만든다 — 소유자 이메일 1, 폴더 사슬 1(`FOLDER_CHAIN_SQL`), 그 소유자의 초대 1. DO 는 이 집합을 60초 들고 있다(3.1 의 권한 다시 확인 주기와 같다)
- 이메일마다 `resolveDocAccess` 를 부르면 멘션 10개에 질의 20~30개라 무료 한도 50(c9)에 가깝다 — 그래서 집합으로 한 번
- 서버 확인: 멘션 이메일이 집합에 없으면 **조용히 빼고**(알림 없음) 본문의 `@이메일` 글자는 그대로 둔다
- 후보 목록 API `GET /api/docs/:id/people` 도 같은 함수를 쓴다(3.9). **view 도 이 목록을 본다** — 이 문서를 볼 수 있는 사람의 이메일이 다른 접근자에게 보인다. 개인정보 처리방침에 적는다(9장)
- 막힌 계정도 후보에 남는다(읽기는 된다, F-2024 Q4)

## 4. 클라이언트

### 4.1 어느 경로에서 댓글이 되나

`decideDocPath` 의 경로(F-305 4.1, F-306 5.1)마다:

| 경로 | 댓글 보기 | 달기 | 쓰는 곳 |
| --- | --- | --- | --- |
| `local`(로그아웃 로컬 문서) | 됨 | 편집권 탭만 | 편집기 `Y.Doc` `comments` → 로컬 기록(4.5) |
| `realtime`, edit 이상 (재개·오프라인 재개 포함) | 됨 | 됨 (오프라인도) | 편집기 `Y.Doc` `comments` 직접(3.2) |
| **`realtime` 읽기 전용 — view (신규)** | 됨 | 연결돼 있을 때 | 명령 메시지(3.1) |
| `view`(막힌 계정·오프라인 view·view 실시간 연결 실패) | 안 됨 | 안 됨 | — 레일 자리에 C8 |
| `pending`·`fallback`·`offline-view` | 안 됨 | 안 됨 | — C8 |
| 금고(`e2ee`, F-405) | 없음 | 없음 | 댓글 UI 가 없다(4.7) |
| 공유 링크 화면·공개 보기 | 없음 | 없음 | — |

- **view 경로를 바꾼다.** 지금 view 는 소켓 없이 D1 본문을 읽기 전용으로 띄운다(F-301 12장 M5 "보기 권한자는 실시간 반영을 받지 않는다", F-305 E14). 댓글을 보려면 방 Doc 이 있어야 하므로 **온라인 view 는 읽기 전용 실시간 세션**이 된다 — 본문도 실시간으로 따라온다. `DocPathInput` 은 그대로, 결과의 `realtime` 갈래에 선택 필드 하나를 더한다(계약, F-506):

```ts
| { kind: 'realtime'; resume: boolean; startOffline: boolean; readOnly?: true }
```

  - 판정: `role === 'view'` 이고 `forbidden` 이 아니고 온라인이면 `{ kind: 'realtime', resume: false, startOffline: false, readOnly: true }`. 오프라인이거나 `forbidden` 이면 지금처럼 `view`. F-405 가 더하는 `e2ee` 갈래가 이보다 앞이다
  - 읽기 전용 세션은 `md-yjs` 를 붙이지 않는다(쓸 것이 없다. 오프라인 view 에서 댓글을 보이려면 10장 Q5)
  - 첫 동기화 전 실패(`fallback` 이 될 자리)면 지금의 `view` 로 연다 — `vite preview` 에서 소켓이 1006 으로 닫히는 기존 fakeServer e2e(보기 문서를 쓰는 `docTitle`·`invite`·`editorToolbar`·`homeScreen`)가 그대로 통과하게
- 편집기 쪽은 읽기 전용이 그대로라(`isReadOnlyByRole`) 본문을 칠 수 없다. provider 가 보낼 로컬 변경이 없다

### 4.2 편집기 표시 — 장식·거터·위치 (사용자 결정 7)

- **앵커 장식**: 열린(해결 안 된) 스레드의 범위에 `Decoration.mark` 하나. **mark 장식만 쓴다** — 위젯·치환 장식을 쓰지 않으므로 문서 내용·원문 바이트가 바뀌지 않는다(불변조건 "decorations never change document content"). 활성 스레드는 한 단계 진하게. 해결된 스레드는 `해결된 댓글 보기` 가 켜져 있어도 본문에 칠하지 않는다
- **거터 표시**: 열린 스레드의 **시작이 있는 줄**에 표시 하나(한 줄에 여럿이면 하나 + 개수). 줄 번호 거터 오른쪽의 별도 거터. 누르면 그 줄의 첫 스레드가 활성(좁은 창이면 판을 연다)
- 클래스·선택자 이름(계약, e2e 와 F-505 가 같이 쓴다): 앵커 `cm-comment-anchor`, 활성 앵커 `cm-comment-anchor-active`, 거터 표시 `cm-comment-gutter-marker`, 레일 `.comment-rail`, 카드 `.comment-thread`(속성 `data-thread-id`), 고아 묶음 `.comment-orphans`, 판 `.comment-sheet`
- **위치를 어떻게 따라가나** — 이 개요가 정하는 규칙:
  - 원본은 `RelativePosition` 이다. 하지만 편집 트랜잭션마다 모든 앵커를 다시 풀면 1MB·500개에서 310ms(c4)라 칠 때마다 멈춘다. 그래서 **편집 트랜잭션에서는 CM6 위치 매핑**(시작은 뒤쪽에 붙게, 끝은 앞쪽에 붙게 — c1 의 `assoc` 과 같은 방향)으로 따라가고, `RelativePosition` 으로 다시 푸는 것은 ① 문서를 열 때 ② `comments` 가 바뀔 때 ③ 경계 글자(시작의 첫 글자·끝의 마지막 글자)가 지워진 앵커 — 빈 범위가 된 것 포함 — 를, 마지막 그런 트랜잭션 뒤 300ms 쉼에 **그 앵커들만**(되돌리기로 살아나는 경우, c1. F-504 5.4 — 2026-09-26 사용자 승인으로 "빈 범위" 에서 넓힘) ④ 글자를 넣은 편집 트랜잭션 뒤 300ms 쉼에 **고아 스레드만**(늦은 되돌리기로 살아나는 경우 — F-504 구현 중 발견, 2026-09-26 사용자 승인으로 추가) — 넷이다. 줄 번호를 끄면 댓글 거터도 없다(F-504 Q2)
  - 원격 본문 편집도 `y-codemirror.next` 가 CM6 트랜잭션으로 들여오므로 같은 매핑을 탄다
- **IME**: 원격 댓글 변경도 본문과 **같은 게이트**를 지난다 — `remoteGate.ts` 는 방 Doc 의 `update` 를 통째로 붙잡았다가 `compositionend` 에 넘긴다(`comments` 도 같은 Doc 이다). 그래서 조합 중에는 댓글 표시가 바뀌지 않고, 조합이 끝나면 따라잡는다(불변조건 둘 다 지킴). 댓글 장식 재계산을 조합 중 미루는 코드를 새로 둔다면 조합 끝(`forceRecalc`)에서 따라잡아야 한다
- 내가 단 댓글은 편집기 `Y.Doc` 에 쓴다 — 앵커가 가리키는 항목이 바로 그 Doc 에 있고, 게이트가 방 Doc 으로 넘긴다(`onEditorUpdate`). 댓글 UI 는 **편집기 `Y.Doc` 의 `comments` 를 읽고 쓴다**(방 Doc 이 아니다) — 화면의 본문과 댓글 위치가 같은 시점을 본다

### 4.3 레일과 판

- **넓은 화면 — 오른쪽 레일**: 메인 열 너비가 **968px 이상**이면 편집 영역 오른쪽에 레일(폭 280px). 본문 최대 폭은 레일이 있는 동안 `min(800px, 메인 열 − 280 − 48)` 로 줄어든다(640px 미만으로는 줄지 않는다 — 그래서 968 = 640 + 280 + 48). 수치는 design.md 가 최종으로 정하고 e2e 로 고정하지 않는다
  - 카드는 **앵커 시작 줄의 높이**에 붙는다. 겹치면 아래로 밀고(간격 8px), 활성 카드는 제자리에 두고 나머지를 위아래로 민다. 레일은 편집 영역과 함께 스크롤한다
  - 순서: 문서 위치순. 고아 묶음은 맨 아래
  - 레일 머리: `댓글` + `해결된 댓글 보기`(체크). 해결된 스레드는 흐리게, 제자리(앵커가 살아 있으면) 또는 고아 묶음에
  - 레일이 있는 동안 오른쪽 목차(F-144)는 `목차` 버튼 모드(F-229, 좁은 여백 때의 모양)로 바뀐다 — 둘이 같은 오른쪽 여백을 다투지 않게
- **좁은 화면 — 아래에서 올라오는 판**: 메인 열 968px 미만. 판은 창 높이의 60%, 스레드를 문서 위치순 목록으로. 거터 표시·앵커를 누르거나 상단바 `댓글` 을 누르면 열리고, `닫기`·Esc·판 바깥 누르기로 닫힌다
- **열고 닫기**: 상단바 `댓글` 버튼(열린 스레드 수 배지)이 레일·판을 연다·닫는다. 이 기기 설정 `md.commentRail`(`open`\|`closed`, 없으면 열린 스레드가 있을 때 연다). 문서마다가 아니라 기기 하나에 하나
- **보기 모드(F-123)**: 레일·거터·장식이 없다. 상단바 `댓글` 을 누르면 편집 모드로 바꾸고 레일을 연다
- **빈 상태**: 스레드가 0개면 레일에 `이 문서에 댓글이 없습니다. 본문을 선택하고 댓글을 달아 보세요.` (댓글을 달 수 없는 경로면 C8)
- `댓글 달기` 떠 있는 버튼: 선택 영역이 있고 댓글을 달 수 있으면 레일의 선택 시작 높이에(좁은 화면은 선택 바로 아래 편집 영역 오른쪽 끝에) 뜬다

### 4.4 흐름

1. **달기**: 본문 선택 → `댓글 달기`(떠 있는 버튼·우클릭 메뉴·팔레트·`Ctrl+Alt+M`) → 레일(판)에 입력 카드가 선택 높이에 열린다. 선택이 비었으면 C1. 조합 중에는 단축키가 동작하지 않는다(F-109 `guardComposing` 과 같게) → `Ctrl+Enter` 또는 `댓글 달기` 로 보낸다 / `Esc`·`취소` 로 버리고 포커스를 편집기로. 입력 카드가 열린 동안 선택 범위는 앵커 후보 장식으로 칠해 둔다. 보낼 때의 선택이 아니라 **카드를 연 순간의 범위**를 쓴다(그 사이 편집은 매핑으로 따라간다)
   - edit 이상·로컬: 편집기 `Y.Doc` 에 한 트랜잭션. view: `comment-add` → ack 가 올 때까지 카드에 `보내는 중…`, ack 가 오기 전이라도 Yjs 로 항목이 먼저 보이면 그 카드를 쓴다. reject 면 입력을 남긴 채 C3~C6
2. **답글**: 카드의 `답글` 입력칸 → 같은 방식. 해결된 스레드에 답글을 달면 **다시 열린다**(한 트랜잭션)
3. **해결 / 다시 열기**: 카드 머리 버튼. 해결하면 레일에서 사라지고(해결 보기 꺼짐일 때) 장식·거터 표시가 없어진다
4. **삭제**: 카드 `⋯` → `삭제`. 확인 대화상자(D-11). 권한이 없으면 메뉴 항목이 없다(2.4)
5. **이동**: 카드를 누르거나(Enter) → 앵커를 편집 영역 가운데로 스크롤하고 활성으로. **커서는 옮기지 않는다**(F-144 목차와 같게). 본문의 앵커 글자를 누르면 그 스레드가 활성이 되고 레일이 그 카드로 스크롤한다
6. **주소로 이동**: `#/d/{docId}/c/{threadId}`(새 해시 형식, 계약) → 문서를 열고 댓글이 준비되면 그 스레드로 5번과 같이 이동한 뒤 주소를 `#/d/{docId}` 로 바꾼다(`history.replaceState`, 뒤로 가기 기록을 늘리지 않는다). 없으면 C9. `hashRoute.ts` 의 `#/d/(.+)` 가 지금 이 모양을 문서 id 로 먹으므로 **그보다 앞에** 새 패턴을 둔다
7. **알림 읽음**: 4.8

### 4.5 로컬 문서 — 댓글을 어디에 두나 (사용자 결정 3, **10장 Q1**)

사용자 결정 문장은 "로컬 `md-yjs`" 인데 **지금 로컬 문서는 `md-yjs` 를 쓰지 않는다**(c11). 로컬 문서의 편집기 `Y.Doc` 은 마운트마다(모드 전환 포함) 본문으로 새로 심으므로, `Y.Map` 에 넣은 댓글과 `RelativePosition` 은 다시 마운트하면 사라진다. 둘 중 하나를 골라야 한다

| 안 | 하는 것 | 드는 것 |
| --- | --- | --- |
| **L2 (기본). 세션 안에서는 `Y.Map`, 저장은 인용문 기록** | 열려 있는 동안은 편집기 `Y.Doc` 의 `comments`(서버 문서와 같은 코드·같은 UI). 저장할 때는 `CommentRecord`(3.9 — 인용문·앞뒤 문맥·위치)로 바꿔 `md-docs` 새 스토어 `comments`(keyPath `docId`)에 **본문과 같은 IndexedDB 트랜잭션**으로 쓴다. 마운트 때 `reanchor`(3.4)로 새 `Y.Doc` 에 다시 심는다 | 본문과 기록을 같은 시점의 편집기 상태에서 한 트랜잭션으로 쓰므로 위치 힌트가 늘 정확하다 → 다시 심기가 정확하다. `reanchor`·`CommentRecord` 는 D1 복사본(3.3)·이관(4.6)과 **같은 코드**. 로컬 문서 여는 길(본문 심기)은 그대로 |
| L1. 로컬 문서도 `md-yjs` 에 `Y.Doc` 상태를 저장 | 로컬 문서를 열 때 `md-yjs` 의 상태를 먼저 불러오고 본문 대신 그것으로 편집기를 띄운다 | 로컬 문서 여는 길을 바꾼다. `md-docs` 본문과 `md-yjs` 상태가 어긋날 때(가져오기 덮어쓰기·다른 탭) 어느 쪽을 믿을지 규칙이 새로 필요하다(DO 의 `d1_version`·`applyExternal` 과 같은 것을 브라우저에). 모드 전환 다시 마운트도 상태를 이어받게 바꿔야 한다. 이관 때 로컬 `Y.Doc` 상태의 항목 id 가 서버 방(D1 본문에서 새로 심음)과 달라 어차피 인용문으로 다시 붙여야 한다 |

- **기본값 L2** — 이유: 사용자 결정 3 이 원하는 결과("로컬 문서에도 댓글", "이관 때 같이 올라감")를 L1 보다 적은 변경으로 낸다. 결정 1 의 "`Y.Doc` 안의 `Y.Map`" 은 열려 있는 동안 그대로 지켜진다. 다른 점은 **로컬 문서의 댓글 기록이 `md-yjs` 가 아니라 `md-docs` 에 있다**는 것 하나다
- L1 을 고르면: F-508 이 `openYjsStore` 를 로컬용 고정 키(사용자 id 자리에 제품명 없는 상수)로도 열고, `App.tsx` 로컬 경로·`yBinding.ts` 심기·모드 전환 다시 마운트를 바꾼다. 로드맵에 로컬 `md-yjs` 명세 하나가 더 붙는다
- L2 세부: 로컬 문서 댓글을 바꾸면(달기·해결·삭제) 본문 저장과 같은 저장을 **곧바로** 한 번 돌린다(700ms 기다리지 않는다). 문서를 지우면 기록도 지운다. `md-docs` 버전은 F-404 가 올린 5 다음 번호(F-508 을 쓸 때 다음 빈 번호). 다른 탭은 지금 로컬 본문이 다른 탭에 반영되는 방식 그대로 다시 마운트 때 기록을 읽는다

### 4.6 로그인 이관 (F-208 확장)

- F-208 이 로컬 문서를 outbox `createDoc` 으로 넣을 때, 그 문서에 로컬 댓글 기록이 있으면 **바로 뒤에** outbox 항목 `importComments { docId, records }` 를 넣는다 — outbox 순서가 "문서가 서버에 먼저 있다" 를 보장한다
- 보내기: `POST /api/docs/:id/comments/import` → DO `importComments`: 방의 `comments` 가 **비어 있을 때만** 본문에 `reanchor` 해 넣는다. 작성자는 이관한 사용자(2.2), 해결 표시의 `by` 도 같다. 비어 있지 않으면 409 `comments_exist` — outbox 는 그 항목을 조용히 버린다(로컬 기록은 `md-docs` 에 남는다, F-208 "로컬 `md-docs` 는 지우지 않는다")
- 본문이 로컬과 같은 바이트로 올라가므로 위치 힌트가 그대로 맞는다 — 고아가 생기지 않는 것이 보통이다
- 503(방을 못 깨움)은 outbox 가 지금 규칙대로 다시 보낸다
- 멘션·알림은 없다(로컬 댓글은 `mentions: []`)
- 로컬 **금고** 문서는 댓글이 없으므로 옮길 것이 없다

### 4.7 금고 (사용자 결정 8, F-400·F-407 과 잇기)

- 금고 문서(`Doc.e2ee` 가 있음, F-405)에서는 상단바 `댓글` 버튼·레일·거터·우클릭 `댓글 달기`·팔레트 `댓글 달기` 가 **없다**. 서버는 이미 금고 문서의 소켓을 4403 으로 닫고(F-401) DO 가 없으므로 댓글이 생길 자리가 없다. 댓글 API 는 409 `e2ee_doc`
- **일반 문서를 금고로 옮길 때: 댓글을 지운다 — 경고 뒤.** 암호화 대상(제목·본문·첨부, F-400 결정 2)에 댓글이 없고, 금고 문서는 혼자 편집·DO 없음(결정 5·6)이라 댓글이 살 자리가 없다. 댓글을 금고 봉투에 함께 넣는 것은 1차 금고 범위 밖이다
  - 서버: `setDocE2eeStatements`(옮기기 batch)에 `doc_comments`·`notifications` 지우기와 사용량 빼기를 더한다(F-502). DO 는 이미 비운다(`purgeBeforeResponse`)
  - 화면: 금고로 옮기기 확인(F-400 D-9)에서 `GET /api/docs/:id/comments/count` 의 `total` 이 1 이상이면 본문에 한 문장 `댓글 {N}개도 함께 지워집니다.` 를 더한다. 폴더 옮기기는 옮길 문서들의 합(문서마다 한 번 묻는다 — 폴더 옮기기가 이미 문서마다 요청을 보낸다, F-400 4.3). 로컬 금고로 옮길 때는 `md-docs` 기록의 개수, 옮긴 뒤 그 기록을 지운다
  - **F-407 과의 순서**: F-407 은 M4 라 M5 보다 먼저 구현된다. 그때는 댓글이 없으므로 F-407 은 이 문장을 모른다. **M5 의 F-509 가 F-407 이 만든 화면·`convert.ts` 에 이 문장과 로컬 기록 지우기를 더한다.** F-407 명세를 쓸 때 D-9 본문 끝에 "추가 문장 자리" 를 두라고 9장에 적는다
- 금고에서 빼면 댓글이 없는 일반 문서로 시작한다(옛 댓글은 되살아나지 않는다 — 이미 지웠다)

### 4.8 알림함 (사용자 결정 5)

- 상단바 계정 메뉴 **왼쪽**에 `알림` 아이콘 버튼(로그인했을 때만). 안 읽은 수 배지 1~99, 넘으면 `99+`
- 가져오기: 부팅 뒤 한 번, 탭이 보이는 동안 **60초마다**, `visibilitychange` 로 다시 보일 때, 알림함을 열 때 — `GET /api/notifications?limit=30`. 오프라인이면 건너뛴다. GET 이라 쓰기 한도에 안 잡힌다
- 알림함(팝오버, 폭 360px. 좁은 창은 화면 너비): 새것부터. 안 읽은 것은 점 표시. 항목: 문구(5.1) + 발췌 한 줄 + 상대 시각. 머리에 `모두 읽음`. 비었으면 `새 알림이 없습니다.`
- 항목을 누르면: 그 항목만 읽음(`POST /api/notifications/read { ids: [id] }`) → `#/d/{docId}/c/{threadId}`(4.4 6번). 문서가 열리지 않으면(삭제·접근 잃음) 지금 문서 열기 실패 처리 그대로 + C9
- 읽음 표시는 먼저 화면에 반영하고 요청이 실패하면 다음 가져오기에서 서버 값으로 돌아온다

### 4.9 키보드·접근성

- `Ctrl+Alt+M`(맥 `Cmd+Option+M`): 편집기 포커스에서 선택 범위에 댓글 달기. CM6 기본 키맵들에 없다(c10). **브라우저·OS 가 먼저 먹는지는 확인하지 않았다** — 맥 `Cmd+Option+M` 은 여러 앱에서 "모든 창 최소화" 로 알려져 있다(확인하지 않음). 기준 브라우저는 Windows Chrome(product.md 2장)이다. 사람 확인 항목에 넣는다
- 입력 카드: `Ctrl+Enter` 보내기, `Esc` 취소(포커스 편집기로). 멘션 후보 목록이 열려 있으면 `↑`·`↓`·`Enter`·`Esc` 가 목록 먼저
- 레일은 `<aside aria-label="댓글">`, 카드는 `<article>`, 카드 머리에 작성자·시각. 포커스 순서: 편집기 → (Esc 다음 Tab, I3) 레일 카드들 → 상태바
- 멘션 후보: `@` 다음 글자로 이메일 부분 일치 거르기, 최대 8개, 내 이메일은 빼고. 고르면 본문에 `@{이메일} ` 을 넣고 `mentions` 에 더한다. 보낼 때 본문에 `@{이메일}` 이 남은 것만 `mentions` 에 남긴다. 후보는 문서를 열 때 `GET /api/docs/:id/people` 한 번(실패하면 후보 없이 평문 `@`)

## 10. 열린 질문 / 사람 결정 필요

### Q1. 로컬 문서의 댓글을 어디에 두나 — **사람 결정 필요. 기본값: L2(세션 안 `Y.Map` + `md-docs` 인용문 기록)**

- 사용자 결정 3 은 "로컬 `md-yjs`" 인데, 로컬 문서는 지금 `md-yjs` 를 쓰지 않고 마운트마다 `Y.Doc` 을 새로 만든다(c11)
- 두 안의 차이는 4.5 표. **기본값의 이유**: 같은 결과(로컬 댓글·이관)를 로컬 문서 여는 길을 건드리지 않고 낸다. 이관 때는 어느 안이든 인용문으로 다시 붙여야 한다(서버 방은 D1 본문에서 새로 심어 항목 id 가 다르다)
- **L1 을 고르면**: 로컬 문서가 `Y.Doc` 상태를 영구히 갖게 되어 나중에 로컬 문서의 다른 기능(되돌리기 기록 유지 등)에 쓸 수 있다. 대신 F-508 이 커지고(로컬 여는 길·다시 마운트·`md-docs`/`md-yjs` 어긋남 규칙), `md-yjs` 가 로그아웃 상태에서도 열린다. 로드맵에 명세 하나가 더 붙는다

### Q2. M5 착수 시점 — **사람 결정 필요. 기본값: M4(F-404~F-409) 가 끝난 뒤**

- `product.md` 3장 "단계는 순서대로 진행한다" 그대로
- **다른 안**: F-501(순수)·F-502·F-503(서버)·F-504(편집기)는 M4 남은 명세와 파일이 겹치지 않는다(M4 남은 것은 `src/app`·`src/storage`·`src/e2ee` 쪽). 앞당기면 M5 가 빨라지지만 `product.md` 3장 규칙에 예외 한 줄이 필요하다. F-505 부터는 F-405 를 기다린다

### Q3. edit 이상도 명령 메시지로만 쓰게 할까 — **기본값: 아니다, edit 이상은 `Y.Map` 에 직접 쓴다**

- 기본값의 이유: 오프라인에서 달기·재연결 병합이 Yjs 로 저절로 된다(사용자 결정 1). 서버는 사후에 고친다(3.2)
- 다른 안: 모두 명령으로 쓰면 서버가 쓰기 **전에** 모든 규칙을 막는다. 대신 edit 이상의 오프라인 댓글에 명령 대기열(outbox 같은 것)이 필요하고, edit 연결이 `comments` 를 직접 쓰는 것도 막아야 해서 결국 3.1 A·B 같은 검사가 edit 연결에 필요하다

### Q4. view 연결을 접속자로 보일까 — **기본값: 보이지 않는다(awareness 버림)**

- F-307 의 `접속자` 는 "함께 편집 중인 다른 사람"(ia.md 6장)이다. 보이게 하면 F-307 의 문구·아바타 규칙과 view 커서 표시 여부를 새로 정해야 한다

### Q5. 오프라인 view 에서 댓글을 보일까 — **기본값: 보이지 않는다(C8)**

- 보이게 하려면 읽기 전용 세션도 `md-yjs` 를 붙여야 한다. view 는 쓸 것이 없어 병합 문제는 없지만, `md-yjs` 가 view 문서까지 30일 보관(F-306 `RETAIN_MS`)하게 된다

### Q6. 알림 종류 — **기본값: 멘션 + 내 스레드에 달린 답글**

- 사용자 결정 4 는 "@멘션 + 알림". 답글 알림을 빼면 `kind` 가 `mention` 하나가 되고 3.5 의 "받는 사람" 둘째 줄이 없어진다. 문서 소유자에게 모든 새 댓글을 알리는 것은 넣지 않았다(시끄러움)

### Q7. 해결·다시 열기를 누구나 — **기본값: 댓글을 달 수 있는 사람 누구나(2.4)**

- 다른 안: 스레드 작성자 + edit 이상. 그러면 view 가 남의 해결된 스레드에 답글을 달 때 다시 열 수 없어 "답글 = 다시 열림"(4.4) 규칙에 예외가 생긴다

### Q8. 한도 수치 — **기본값: 2.5 표**

- 본문 1,000자·문서 500개·답글 100개·멘션 10명·알림 90일/300개. 문서당 500개를 늘리면 방 Doc 초기 동기화 양(최악 약 1.65MB)과 D1 행 수가 비례해 는다

### Q9. 용어 "멘션" — **기본값: `멘션`**

- ia.md 는 외래어를 우리말로 바꾸는 편(지도·검색)이지만 `템플릿` 처럼 굳은 말은 쓴다. `언급` 으로 바꾸면 5.1 의 문구 세 곳만 바뀐다
