## 2. 흐름과 호출 수

클라이언트(F-2130) 순서: `push-plan` → `blobs`(**`.md` 먼저**, 이어 `missing` 그림 한 장씩) → `push`. `.md` 를 `blobs` 로 보내는 것이 F-3013 3.4 와 다르다(Q1)

| 라우트 | GitHub 호출 (정상) | 최악 바깥 하위 요청 | 횟수 |
| --- | --- | --- | --- |
| `push-plan` | 브랜치 GET, `.md` Contents GET, `attachments` 폴더 Contents GET = **3** | 3 + 브랜치 404 때 ref GET 1 + 갱신 1 + 401 갱신·재시도 2 = 7 | — (한도 검사만) |
| `blobs` | blob POST **1** | 1 + 갱신 1 + 401 뒤 강제 갱신 1 = 3 | — |
| `push` | 브랜치 GET, `.md` Contents GET, tree POST, commit POST, ref PATCH = **5** | 5 + 422 뒤 브랜치 GET 1 + 갱신 1 + 401 갱신·재시도 2 = 9 | 1 (커밋을 만든 때만) |

- 그림 N 장 = Worker 호출 N+3 번(`push-plan`·`.md` blob·그림 N·`push`). **한 호출의 하위 요청은 N 과 무관**하게 9 이하라 외부 50(F-3013 w1)에 닿지 않는다. N 의 상한은 GitHub 내용 만들기 분당 80(d1) 이 정한다: 한 푸시의 쓰기 = blob N+1 + tree + commit + ref = N+4. **N ≤ 50**(F-3013 기본값) 이면 54. 같은 분에 50장 푸시를 두 번 하면 GitHub 가 한도로 막는다(503 `github_rate_limited`)
- `WRITE_LIMITER` 분당 120 안: 그림 50장 푸시 = 53 쓰기 요청
- D1 은 내부 하위 요청(1,000)이라 따지지 않는다

## 3. `POST /api/docs/:id/github/push-plan`

공통 앞부분 (세 라우트 같음): F-3015 3.1 순서 — `requireUser` → `loadEnabledGithub` null 이면 503 `github_disabled` → 입력 검사 → `getDocAccess` null 404 `not_found`, 주인 아님 403 `forbidden`, `e2ee_key` 있음 409 `e2ee`(F-3015 3.4 의 틈을 여기서 한 번 더 막는다 — 평문이 나가는 바로 그 길이다) → 연결 행 없음 404 `not_found` → (횟수 라우트) `checkGithubQuota`. 모든 응답 `Cache-Control: no-store`. GitHub 호출은 연결 행의 `repo`·`branch`·`path` 로만, 주소 인코딩은 F-3015 2장 마지막 줄 규칙

- 몸통 `GithubPushPlanBody`, 상한 32,768 B(`readJsonLimited`, 넘으면 413). `attachments` 는 배열, 1,000개 이하(`E2EE_MAX_ATTACHMENT_REFS`), 각 이름 c3 꼴. 아니면 400 `invalid` `field: 'attachments'`. 중복은 하나로
- `push` 가 쓸 수 없는 것을 미리 막으려고 `checkGithubQuota` 도 부른다(세지는 않는다)
- **원격 확인** (4장 ①②와 같은 함수):
  1. 브랜치 GET `/repos/{repo}/branches/{branch}` → 머리 `H` = `commit.sha`, 트리 `T` = `commit.commit.tree.sha`. 404 면 `GET /repos/{repo}/git/ref/heads/{branch}` 한 번 더: 409 → 409 `github_empty_repo`(d3), 그 밖 → 404 `github_not_found`. 응답 `name` ≠ 연결의 `branch`(이름 바뀐 브랜치로 넘겨짐) → 404 `github_not_found`
  2. `.md` Contents GET `{path}?ref={H}`, `Accept: application/vnd.github.object+json`(1MB 넘어도 sha 를 받으려고, d1·d5). 지금 sha `S` = 응답 `sha`, 404 면 `S = null`. `type !== 'file'`(폴더·심볼릭 링크) → 409 `github_conflict`, `remoteSha: null`
  3. **충돌 판정**: `S === remote_sha`(둘 다 null 포함)면 통과. 아니면 409 `{ error: 'github_conflict', remoteSha: S }`
- **첨부 판정**:
  - D1 `SELECT id, ext FROM attachments WHERE e2ee = 0 AND id IN (SELECT value FROM json_each(?))` — 행이 있고 `ext` 가 같은 이름만 올릴 수 있다. 나머지(행 없음·금고 첨부·확장자 다름)는 `skipped`. 주인 것인지는 보지 않는다 — 편집자가 넣은 그림도 같은 문서 그림이고 주인이 `?doc=` 로 읽는다
  - 원격 `{md 폴더}/attachments` Contents GET `?ref={H}`(object 형식, md 폴더가 맨 위면 `attachments`). `entries` 중 `type: 'file'` 의 `name` 집합. 404 = 빈 집합. 폴더가 아니고 파일이면 502 `github_unavailable` + `console.error('github_unexpected', 'push-plan', 'attachments_not_dir')`
  - 판정은 **이름만**: 첨부 id 는 난수이고 내용이 바뀌지 않는다. 폴더 항목이 1,000개를 넘어 못 본 이름은 `missing` 이 되어 다시 올라간다(같은 바이트라 git 차이 없음, blob 1번 낭비)
- 200 `GithubPushPlan`: `missing`·`skipped` 는 입력 순서(중복 제거 뒤)

## 4. `POST /api/docs/:id/github/blobs`

- **몸통을 읽지 않는다.** 클라이언트가 만든 `{"encoding":"base64","content":"…"}` 를 GitHub `POST /repos/{repo}/git/blobs` 로 그대로 흘려보낸다. 형식 검사는 GitHub 몫
- `Content-Length` 가 없거나 0 이상 정수가 아니면 411 `{ error: 'length_required' }`, `7_000_000`(`GITHUB_BLOB_MAX_BYTES`) 넘으면 413 `{ error: 'too_large', limit }`. 둘 다 GitHub 호출 0
- 보내는 길: `githubAccessToken` 으로 토큰 → `FixedLengthStream(Content-Length)` 에 `request.body` 를 잇고 그 `readable` 을 `fetch` 몸통으로(머리 `githubApiHeaders` + `Content-Type: application/json`). 길이를 속이면 스트림이 깨져 502. FixedLengthStream 을 쓰는 이유: 바깥 요청에 `Content-Length` 를 보장하고 바이트가 JS 를 거치지 않는다(workerd 기본 제공, `worker/worker-configuration.d.ts`). node 테스트는 `vi.stubGlobal` 로 대역을 둔다
- 응답 판정: 201 → 몸통 `sha`(40자 소문자 16진수, 아니면 502) → 200 `{ sha }`. 400·422 → 400 `invalid` `field: 'content'`. 409 → 409 `github_empty_repo`. 401 → `githubAccessToken(db, config, userId, usedRev)` 로 강제 갱신만 하고(실패면 그 실패, 대개 409 `github_reconnect`) **502 `github_unavailable`**. 그 밖은 `classifyGithubResponse`(한도 503·403·404·5xx), 남는 상태는 502 + `console.error('github_unexpected', 'blobs', status)`
- **재시도는 클라이언트가**: 같은 바이트의 blob 은 같은 sha 라 다시 보내도 안전하다. F-2130 은 `blobs` 502 를 한 번 다시 보낸다(401 뒤에는 이미 새 토큰이 있다)
- 횟수·한도 검사 없음(F-3013 3.4). D1 쓰기 없음

## 5. `POST /api/docs/:id/github/push`

- 몸통 `GithubPushBody`, 상한 16,384 B. 검사(실패는 400 `invalid` + `field`): `message` 문자열, `trim()` 이 빈 글자 아님, `length ≤ 1000`(F-3013 4.4), 그대로 쓴다(앞뒤 공백·줄바꿈 포함) / `mdSha` 40자 소문자 16진수 / `images` 배열 50개 이하, 각 `name` c3 꼴·`sha` 40자 16진수, 이름 중복 없음
- `remote_sha`·`expectedSha` 는 몸통으로 받지 않는다 — D1 연결 행이 원본이다(다른 탭이 당겨 `synced` 했으면 그 값이 맞다)
- 순서:
  1. 3장 원격 확인 ①~③ 그대로(`H`·`T`·`S`, 409 `github_conflict` + `remoteSha`)
  2. **바뀐 것 없음**: `S === mdSha` 이고 `images` 가 비면 GitHub 를 더 부르지 않고 200 `{ sha: mdSha, commitSha: null, commitUrl: null }`. 횟수 세지 않음, D1 쓰기 없음(`remote_sha` 가 이미 `mdSha`)
  3. tree POST `{ base_tree: T, tree: [...] }`: `{ path, mode: '100644', type: 'blob', sha: mdSha }` + 그림마다 `{md 폴더}/attachments/{name}`. 모드는 늘 `100644`(원격이 실행 파일 모드였으면 바뀐다 — `.md` 라 받아들임). 422 → 400 `invalid` `field: 'sha'`(없는 blob)
  4. commit POST `{ message, tree: T2, parents: [H] }`. **`author`·`committer` 를 보내지 않는다** — GitHub 가 토큰 주인(연결된 GitHub 사용자)과 지금 시각으로 채운다(d1). 앱 이름·제품 이름을 메시지에 붙이지 않는다
  5. ref PATCH `/repos/{repo}/git/refs/heads/{branch}` `{ sha: C, force: false }`. 200 → 성공. **422·409 → 브랜치 GET 한 번 더**: 머리가 `H` 가 아니면 409 `{ error: 'github_conflict' }`(`remoteSha` 없음 — 누가 그사이 푸시했다), 그대로 `H` 면 403 `github_forbidden`(브랜치 보호·규칙 — 영어 메시지를 읽지 않고 가른다). 403 은 `classifyGithubResponse` 대로 `github_forbidden`
  6. 성공 뒤 D1 한 batch: `UPDATE github_links SET remote_sha = mdSha, synced_at = now WHERE doc_id = ? AND owner_id = ? AND repo_id = ? AND branch = ? AND path = ?`(그사이 다시 연결됐으면 0행 — 옛 대상으로 간 푸시가 새 연결을 건드리지 않는다), `github_usage` +1(`countGithubUse` 와 같은 SQL), `dayUsageStatement`
  7. 200 `{ sha: mdSha, commitSha: C, commitUrl: 'https://github.com/{repo}/commit/{C}' }`
- 3·4번의 그 밖 비정상 상태는 502 + `console.error('github_unexpected', 'push', 단계, status)`

### 5.1 중간 실패의 결과

| 실패 지점 | GitHub 에 남는 것 | D1 | 다시 하면 |
| --- | --- | --- | --- |
| `push-plan`·`push` ①~③ | 없음 | 그대로 | 409 면 당겨 합친 뒤 처음부터 |
| `blobs` 일부만 성공 | 어디에도 안 걸린 blob(GitHub 가 치운다) | 그대로 | 처음부터. 같은 blob 은 같은 sha |
| tree·commit 성공, ref 실패 | 걸리지 않은 tree·commit | 그대로 | 409 → 당겨 합침, 403 → 브랜치 설정 문제 |
| ref 성공, D1 batch 실패 또는 응답 유실 | 새 커밋 | `remote_sha` 가 옛 값 | 다음 푸시가 409(`remoteSha` = 방금 올린 sha) → 당기기가 "같습니다" → `synced` 로 맞춰진다. 횟수 +1 이 빠질 수 있다(받아들임) |

- 서버는 스스로 다시 보내지 않는다(`githubFetch` 의 401 한 번 제외). F-2130 은 `push` 502 를 자동으로 다시 보내지 않는다 — 응답 유실이면 이미 올라갔다

## 10. 열린 질문

### Q1. `.md` 바이트를 어떻게 보내나 — **기본값: 그림처럼 `blobs` 로 흘려보내고 `push` 는 sha 만 받는다**
- 이유: `push` JSON 에 1MB `.md` 를 실으면 몸통 처리만 8.01ms(m1)이고 `.md` Contents 파싱 2.70ms(m2)를 더하면 Node 기준 10ms 를 넘는다. `blobs` 길은 바이트가 JS 를 거치지 않는다. 클라이언트가 base64 로 만들어 BOM·CRLF 가 바이트 그대로 간다(`utf-8` 인코딩의 해석 차이가 없다). 대가: 충돌로 막힐 푸시에도 `.md` blob 하나를 먼저 만든다(push-plan 이 충돌을 먼저 걸러 드물다)
- 다른 안(F-3013 원안, `push` 몸통 `content`): Worker 호출이 하나 줄지만, `MAX_CONTENT_BYTES` 근처 문서에서 CPU 10ms 를 넘을 수 있다. 그때 `push` 는 `content` 를 문자열로 받아 `encoding: 'utf-8'` blob 을 만들고 크기 검사를 `MAX_CONTENT_BYTES + 3` 으로 한다

### Q2. 빈 저장소 — **기본값: 막는다 (409 `github_empty_repo`)**
- 이유: Git Data API 는 빈 저장소에서 409 이고 ref 를 만들 수도 없다(d1·d3). 되게 하려면 Contents `PUT` 으로 첫 커밋을 따로 만들어야 하는데 파일 하나 = 커밋 하나라 그림을 같은 커밋에 못 넣고, 기본 브랜치를 우리가 만들게 된다(F-3013 1.2 "브랜치 만들기 안 함")
- 다른 안: 빈 저장소면 `.md` 만 Contents `PUT`(`branch` = 연결 브랜치)으로 첫 커밋, 그림은 다음 푸시로. 서버에 base64 만들기(`Buffer`, 5MB 1.3ms — F-3013 m3)와 분기 하나가 는다
