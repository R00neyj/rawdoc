# F-2116 알림함 공유 알림 표시·이동·공유받음 갱신

작성일: 2026-10-01
상태: 승인 (2026-10-01, 상시 지시 "명세 작성 후 사용자가 검토할 결정이 없으면 바로 구현" — 별도 검토 없이 승인 처리). 클라이언트 쪽 한 단위. 서버(`share` 행 만들기, 항목 JSON 확장, `INBOX_NOTIFICATION_KINDS`)는 형제 **F-3012**(작성됨, `depends` 에 넣음), 공유 나가기는 F-3011(API)·F-2115(사이드바 ⋯). **F-3012 구현 뒤에 착수한다.** 열린 질문 3개 모두 기본값 있음
구현 담당: `feature-implementer`

## 정해진 것 (사용자 결정, 바꾸지 않는다)

1. 알림함에 문서·폴더 공유 행이 뜬다. 문구는 F-3001 5.1 푸시 표의 "문서 공유"·"폴더 공유" 행과 같다. 역할 이름 `보기`·`편집`
2. 문서 행 → `#/d/{id}`. 폴더 행 → 홈(`#/`) + 사이드바 `공유받음` 이 열리고 그 폴더가 보인다. 이동은 `handleOpenNotification`(`useNotificationsGlue.ts`)을 넓힌다
3. 공유 목록 갱신은 **새 `share` 행이 알림 결과에 처음 나타날 때만** `resyncFromStore` 한 번. 탭 복귀용 장치는 따로 두지 않는다(알림 폴링이 `visible` 과 60초마다 이미 돈다). 목록 TTL 10분(F-2056)은 그대로
4. 첫 로드에 이미 있던 행은 새 행이 아니다. 304 는 부르지 않는다
5. 웹 푸시 클릭(서비스 워커)은 범위 밖. 새 의존성 없음

## 근거 (직접 읽은 것, HEAD `a1b973e`)

- **옛 클라이언트는 `share` 행을 받지 않는다.** `fetchNotifications` 는 `?kinds=` 에 `NOTIFICATION_KINDS` 를 붙이고, `worker/notifications.ts` `LIST_SQL`·`UNREAD_SQL` 이 `kind IN (json_each(kinds))` 로 목록과 안 읽은 수를 함께 거른다. 설치된 PWA 의 옛 JS 는 `mention,reply,comment` 만 보낸다
- **반대로 응답 검사는 아주 엄격하다.** `isNotificationItem` 은 `hasExactKeys`(키 10개 정확히)와 `kind ∈ NOTIFICATION_KINDS` 를 보고, 항목 하나라도 틀리면 `readNotificationsResponse` 가 응답 전체를 `null` → `reason: 'invalid'` → 알림함 `알림을 불러오지 못했습니다.`. BroadcastChannel 메시지(`notificationsShare.ts`)도 같은 검사를 거친다
- F-3012 는 `NOTIFICATION_KINDS` 를 넓히지 않고 `INBOX_NOTIFICATION_KINDS`·`InboxNotificationItem` 을 따로 둔다(F-3012 4장). 그래서 F-3012 커밋만 배포돼도 지금 클라이언트는 `share` 를 요청하지 않아 안전하고, 이 명세가 `fetchNotifications` 를 `INBOX_NOTIFICATION_KINDS` 로 바꾸는 순간 `share` 가 켜진다 → 3장 조건 K3
- 부팅 순서: `notificationsEnabled` 는 `bootPhase === 'ready'` 일 때만 켜진다. 기다리는 길은 `store.list()` 가 끝난 뒤 `finishBootRouting` → `setBootPhase('ready')`, 캐시 먼저 길은 `finishBootRouting` 바로 뒤에 서버 목록(`applyBootMerge`)을 띄운다(`bootFlow.ts`). 두 길 모두 첫 알림 요청과 서버 목록 읽기가 거의 같은 때다 → 첫 결과를 기준선으로 삼아도 놓치는 틈은 그 사이 몇백 ms
- 문구 원천: `src/lib/pushText.ts` `sharePushPayload(PushShare)` 가 이미 두 행의 제목·본문을 만든다(제목 40자 자르기, 빈 문서 제목 `제목 없는 문서`, 빈 폴더 이름 `이름 없는 폴더`, `ROLE_LABEL`). `formatFolderName` 은 모듈 밖에 안 보이므로 이 함수를 통째로 쓴다
- 사이드바 `공유받음`: `Sidebar.tsx` `SharedGroup` 의 열림이 **지역 `useState(true)`** 라 밖에서 열 길이 없고 저장도 안 된다. 폴더는 **접을 수 없다** — `viaFolder` 로 묶은 `span.shared-doc-folder-name` 아래 문서가 늘 보인다. 그래서 "폴더 펼침" = 묶음 열기 + 그 폴더로 스크롤이다. `addOpenFolders`(`md.openFolders`)는 내 트리 전용이라 쓰지 않는다. 문서 없는 폴더 공유는 사이드바에 나타나지 않는다(묶음이 문서에서 만들어진다). `viaFolder` 는 **가장 가까운** 초대 폴더다(`worker/grants.ts`)
- 기존 길: `useSidebarLayout.onNavigateFolder` 가 좁은 창이면 사이드바를 열고, 레일이면 펼쳐 `md.sidebar` 를 저장하고, 두 프레임 뒤 `scrollToFolderRow` 로 스크롤·강조(`tree-row--highlight-start/fading` — 클래스는 요소 종류를 가리지 않는다)
- 홈 해시: `parseHash` 가 `''`·`#`·`#/` 를 `home` 으로 본다. `useHashRouting` 은 홈이면 `setCurrentDocId(null)` 만 하고 포커스를 옮기지 않는다(`EmptyState.tsx` 에 `focus` 없음)
- App.tsx 순서: 글루 호출(`useNotificationsGlue`)이 `useSidebarLayout` 보다 위다. 글루 결과는 그 아래(`useDocNavigation` 인자 이후)에서만 쓰여 호출 자리를 `useSidebarLayout` 아래로 옮길 수 있다
- 알림함 종류 필터·설정 UI 는 **없다**(`grep kinds src/app` — 요청 주소뿐). 설정 `알림` 묶음은 푸시 스위치만이라 이 명세가 손댈 곳이 없다

### 2.2 항목 모양·검사·문구

- 이 명세가 `share` 항목에서 읽는 값: 대상 종류(문서·폴더), 대상 id, 이름(문서 제목·폴더 이름), 역할(`view`·`edit`), 보낸 사람 이메일, `id`·`createdAt`·`readAt`. 필드 이름은 **F-3012 가 `src/lib/docComments.ts` 에 정한 모양 그대로** 쓴다. `PushShare` 와 같은 이름(`target`·`targetId`·`name`·`role`·`actorEmail`)이면 `notificationLines` 가 `sharePushPayload` 에 그대로 넘긴다
- `isNotificationItem`: 기존 세 종류는 지금 검사(키 10개 정확히) 그대로. `share` 는 F-3012 모양의 키 집합을 정확히, 대상 종류·역할은 값 목록 안, 문자열·숫자는 지금과 같은 방식으로 본다. 하나라도 틀리면 지금처럼 응답 전체 `null` — 종류를 하나씩 버리지 않는 이유: 서버는 요청한 종류만 돌려주고 안 읽은 수도 그 종류로 세므로, 모르는 종류가 오는 것은 서버 버그다
- `notificationLines`:
  - `mention`·`reply`·`comment` → `{ text: notificationText(item), excerpt: notificationExcerptLine(item.excerpt) }` (지금 화면 그대로)
  - `share` → `sharePushPayload` 의 `title` 에 `.` 을 붙인 것이 `text`, `body` 가 `excerpt`

| 경우 | 첫 줄 (`notification-item-text`) | 둘째 줄 (`notification-item-excerpt`) |
| --- | --- | --- |
| 문서 공유 | `{보낸 사람}님이 문서를 공유했습니다.` | `"{문서 제목}" · {보기\|편집} 권한` |
| 폴더 공유 | `{보낸 사람}님이 폴더를 공유했습니다.` | `"{폴더 이름}" · {보기\|편집} 권한` |

  알림함 행이 푸시 제목 + `.` 인 것은 `comment` 행과 같은 규칙(F-3001 5.1 끝). 안 읽음 읽기 이름(` 안 읽음`)·시각 줄은 지금 그대로

### 2.3 새 공유 행 → 목록 다시 읽기 (`useShareResync`)

`useShareResync({ status, items, accountId, resync })` — 글루가 `notifications.status`·`notifications.items`·계정 id·`resyncFromStore` 를 넘긴다.

- `nextShareSeen` 규칙
  - `seen === null`(기준선 없음): `resync: false`, `seen` = 지금 `share` 항목 id 전부. 첫 결과에 있던 행은 읽음 여부와 상관없이 새 행이 아니다(정해진 것 4)
  - 그 밖: 지금 `share` 항목 중 `seen` 에 없는 id 가 하나라도 있으면 `resync: true`. `seen` 은 기존 ∪ 지금 id(목록에서 빠진 id 도 남긴다 — 다시 나타나도 새 행이 아니다). 읽음 여부는 보지 않는다(다른 탭이 먼저 읽었어도 이 탭 목록은 모른다). `share` 아닌 항목은 무시
- 훅 규칙
  - `status === 'ready'` 이고 `items` 가 바뀔 때마다 `nextShareSeen` 을 돌린다. 304·읽음 표시 다시 계산·다른 탭이 보낸 같은 결과로 `items` 배열이 새로 와도 새 id 가 없으면 아무것도 안 한다 — 304 를 따로 가를 필요가 없다
  - `status === 'idle'`(꺼짐·로그아웃)이거나 `accountId` 가 바뀌면 `seen = null`
  - `resync: true` 면 `resyncFromStore('bootMerge')` 를 한 번 부르고 기다리지 않는다. 실패는 삼키고 **다시 시도하지 않는다** — 그 id 는 이미 `seen` 이다. 남는 길: 행을 누를 때의 다시 읽기(2.4), TTL 뒤 새로 읽기. `'bootMerge'` 인 이유: 지금 연 공유 문서가 사라졌으면 "다른 탭" 이 아니라 "다른 곳" 문구가 맞다(`resyncFromStore` 주석, F-2056 3.2)
  - 다른 탭은 같은 결과를 BroadcastChannel 로 받아 각자 한 번 다시 읽는다(탭마다 목록 상태가 따로다)
- 알려진 한계: 오프라인으로 부팅해 첫 알림 결과가 한참 뒤에 오면 그 사이 공유는 기준선에 묻힌다. 행을 누르면 찾는다

### 2.4 행 누르기 (`handleOpenNotification`)

공통 앞부분은 지금 그대로: 알림함 닫기 → `markRead(item.id)`.

- **댓글 종류**: 지금 그대로
- **문서 공유**: 대상 문서가 `docsRef.current` 에 없고 온라인이면 `resyncFromStore()` 를 한 번 기다린다(실패 무시) → `location.hash = formatHash(docId)`. 이미 그 주소면 해시가 안 바뀌어 아무 일도 없다(이미 열려 있다). 다시 읽어도 없으면 기존 해시 처리의 `문서를 찾을 수 없습니다.`
- **폴더 공유**, 이 순서로
  1. `sharedFolderListed(docsRef.current, folderId)` 가 거짓이고 온라인이면 `resyncFromStore()` 를 한 번 기다린다(실패 무시)
  2. 그래도 거짓이면 알림 띠 info `공유받은 폴더를 찾을 수 없습니다.` 하고 끝(해시·사이드바 그대로, 열린 질문 Q2)
  3. `parseHash(location.hash).type !== 'home'` 일 때만 `location.hash = '#/'`(이미 홈이면 해시 변화 없음)
  4. `revealSharedFolder(folderId)` — 글루 옵션, App 이 `onNavigateSharedFolder` 를 넘긴다
- `onNavigateSharedFolder(folderId)`(`useSidebarLayout`): 좁은 창이면 사이드바를 열고, 레일이면 펼치고 `md.sidebar` 를 `expanded` 로(`onNavigateFolder` 와 같은 갈래), `sharedGroupOpen` 을 참으로. **늘 두 프레임 뒤에**(묶음이 닫혀 있었으면 그 안이 아직 DOM 에 없다) `[data-shared-folder-id="{id}"]` 를 찾아 이름 줄(`.shared-doc-folder-name`)을 `scrollIntoView({ block: 'nearest' })`·강조 클래스로 깜박이고, 그 폴더 첫 문서 링크(`a.doc-item-btn`)에 포커스. 못 찾으면 아무것도 안 한다
- 포커스를 사이드바로 옮기는 이유: 항목 버튼이 닫힌 팝오버와 함께 사라져 포커스가 `body` 로 떨어진다. 문서 행은 해시 처리가 편집기로 포커스를 준다

### 2.5 사이드바 안 읽은 점 (F-510)

- `notificationDocId`: 댓글 종류 → `item.docId`, 문서 공유 → 대상 문서 id, 폴더 공유 → `null`
- `unreadNotificationDocIds`·`unreadNotificationIdsForDoc` 이 `item.docId` 대신 이것을 쓴다. 결과: 안 읽은 문서 공유 행이 그 문서 행(`공유받음` 안)과 닫힌 `공유받음` 머리에 점을 켜고, 그 문서를 열면 F-510 4.2 대로 공유 행도 읽음이 된다(열린 질문 Q1)
- 폴더 공유는 점이 없다 — 폴더 이름 줄에는 점 자리가 없고, 문서마다 켜면 "그 문서의 알림" 이라는 점의 뜻(ia 3.34)과 어긋난다

### 2.6 `Sidebar` (계약 — e2e 가 쓴다)

- prop: `sharedGroupOpen: boolean`, `onToggleSharedGroup: () => void`. `SharedGroup` 의 지역 상태를 없앤다. 기본값 열림·저장하지 않음은 지금 그대로(`useSidebarLayout` 의 `useState(true)`)
- `.shared-group-toggle` 에 `aria-expanded`
- 폴더 묶음 `li.shared-doc-folder` 에 `data-shared-folder-id="{folderId}"`, React `key` 도 폴더 id(지금 `group.name` 이라 같은 이름 폴더 둘이 겹친다)

## 8. 열린 질문 (모두 기본값 있음)

### Q1. 안 읽은 문서 공유 행이 사이드바 점을 켜나 — 기본값: 켠다

- 이유: 새로 받은 문서가 `공유받음` 안에서 눈에 띄고, 그 문서를 열면 공유 행도 읽음이 되어(F-510 4.2) 점·배지·알림함이 한 상태에서 나온다는 F-510 원칙을 그대로 지킨다. 코드는 `notificationDocId` 한 곳
- 다른 안(켜지 않음): `notificationDocId` 가 공유를 모두 `null` 로. 문서를 열어도 공유 행은 알림함에서 누르거나 `모두 읽음` 할 때까지 남는다. U4 기대가 뒤집힌다

### Q2. 폴더를 못 찾을 때 — 기본값: 알림 띠만, 이동 없음

- 이유: 빈 폴더 공유·공유가 끝난 폴더·나간 폴더(F-2115)는 사이드바에 나타나지 않는다. 홈으로 가서 닫힌 듯 보이는 묶음만 열면 아무 일도 안 일어난 것처럼 보인다
- 다른 안: 알림 없이 홈 + 묶음 열기만. 새 문구가 없어지고 ia 4.2 행이 빠진다. 가장 가까운 초대 폴더가 하위 폴더인 경우(근거 `viaFolder`)에는 이쪽이 문서를 보여 준다는 장점이 있다

### Q3. 공유 행을 한 줄로 — 기본값: 두 줄(지금 항목 구조)

- 이유: 댓글 행이 이미 "누가 무엇을" 첫 줄 + 발췌 둘째 줄이고, 푸시 제목/본문 나눔과도 같다. 사용자 문장의 ` · ` 는 그 두 부분을 이은 것으로 읽었다
- 다른 안: `notificationLines` 의 `text` 를 `{제목} · {본문}` 으로 잇고 `excerpt` 를 빈 문자열(둘째 줄 숨김). U2 기대만 바뀐다
