## 1. 범위 — 무엇을 막고 무엇을 세나

### 1.1 막으려는 것

- 무료 플랜은 한도를 넘으면 과금이 아니라 **오류로 실패**한다(product.md 7장 M3). 한 사람이 D1 하루 쓰기 10만 행을 다 쓰면 **UTC 자정까지 모든 사용자의 저장이 실패**한다
- 지금 `worker/` 에는 속도 제한이 0건이다. 있는 한도는 문서 하나 1MB(`MAX_CONTENT_BYTES`), 제목 500자, 이미지 5MB·계정 300MB, 토큰 10개뿐이다. 문서 **수**와 본문 **합계**는 무제한이다
- CLI(F-2021)가 공개돼 `/v1` 반복 호출이 쉬워졌다. 분당 120 만으로는 하루를 못 막는다 — 120 × 1,440분 = **172,800 요청/일**로 D1 하루 쓰기 한도를 혼자 넘는다. 그래서 하루 5,000 이 따로 있다
- F-2032 뒤에는 가입 한 번이 D1 11행이다(F-2032 2.5). 가입 상한이 없으면 이메일이 다른 계정을 자동으로 만들어 가입만으로 쓰기 행을 쓸 수 있다 — 4.1

### 1.2 "쓰기"의 정의 — 어느 요청이 카운터를 올리나

**규칙: 로그인한 사용자가 부르는 `/api/*`·`/v1/*` 라우트 중 메서드가 `GET` 이 아닌 것은 전부 쓰기다.** 로그인 **전**에 부르는 인증 경로 둘(`POST /api/login`, `/api/auth/*`)만 뺀다 — 관문 ①(사용자 판정 401)이 먼저라 넣으면 로그인 시작·OAuth 콜백·로그아웃이 막힌다(F-2032 8장). 그 밖의 예외는 두지 않는다 — 예외 하나가 우회 경로가 된다(아래 잠금 참고)

| 곁가지 쓰기 — 가입(F-2032 2.5 11행 + 가입 관문 1행, 4.1 이 따로 막음), 다시 로그인 4행, 둘째 제공자 연결 8행, 세션 연장(`GET /api/me`, 세션마다 하루 최대 1행), 로그아웃 1행, 만료 세션 접근 1행, `api_tokens.last_used_at`(토큰마다 10분에 1회, 토큰 10개면 하루 최대 1,440행), Cron 첨부·만료 세션 정리 | 요청 단위 아님 | 안 셈 | 안 셈 |

- **잠금을 빼지 않는 이유.** 잠금 연장은 `pending`·`fallback` 세션에서만 20초마다 한 번이다(`useDocLock.ts` `EXTEND_INTERVAL_MS`, `App.tsx` `useDocLock` 의 `docId` 조건). 8시간 폴백 편집이 1,440번이라 하루 5,000 안에 든다. 빼면 `/api` 쿠키로 잠금만 분당 120번 두드려 하루 172,800행을 쓸 수 있다. 이 개요의 소명세는 F-309 **앞**에 구현되므로 잠금 라우트가 아직 살아 있다(F-2032 8장 F-2024 첫 행)
- **분당은 요청을 세고, 하루는 D1 쓰기를 센다.** 분당 제한은 관문(2.1)에서 요청마다 한 번 바인딩을 부른다 — 400·404·409·413 으로 끝난 요청도 분당에는 잡힌다. 하루 카운터는 핸들러가 **실제로 D1 쓰기 batch 를 실행할 때만** +1 한다(2.3). 검사에서 걸려 D1 에 닿지 않은 요청은 하루에 안 잡힌다. F-308 의 "같은 값 PUT 은 쓰지 않는다"(F-308 7.4)도 D1 에 닿지 않으므로 하루에 안 잡힌다
- 조건부 쓰기가 0행으로 끝나도(버전 충돌 409, 잠금 못 잡음 423) batch 는 실행됐으므로 하루 +1 이다 — 사용량 줄이 행 1개를 실제로 썼다(측정표 "버전 틀림")
- 로그인 반복으로 쓰기 행을 쓰는 구멍은 5.3 에 적었다(막지 않음)

## 2. 분당·하루 제한

### 2.1 쓰기 관문 — 한 곳에서, 핸들러보다 먼저

- `worker/index.ts` 의 라우트 표에서 쓰기 라우트(1.2)를 가려, **핸들러를 부르기 전에** 관문 하나를 지난다. 새 파일 `worker/writeGate.ts`(F-2026)
- 관문 앞에는 F-2033 의 `Origin` 검사가 있다(F-2032 4.2 — 라우트 표를 찾기 전에, 없거나 다르면 403 `forbidden_origin`). 관문은 그 뒤다
- 순서: ① 사용자 판정(401) → ② **차단 확인**(403 `account_blocked`, 4.2) → ③ **하루 확인**(429 `scope: "day"`) → ④ **분당 확인**(429 `scope: "minute"`) → 핸들러. 싼 검사를 먼저 하고, 바인딩 호출은 마지막에 한다 — 이미 막힌 요청이 분당 몫을 쓰지 않게
- 하루 확인은 **인증 때 이미 읽은 `users` 행**의 `write_day`·`write_count` 로 한다. 인증은 요청마다 `users` 를 한 줄 읽는다 — 세션이면 better-auth `getSession`(세션 1 + 사용자 1, F-2032 2.5), 토큰이면 `getTokenUser` 의 `SELECT … WHERE id = ?`, 로컬 개발 우회면 `findOrCreateUser` 의 `SELECT`. 읽는 열만 늘리면 **추가 D1 읽기가 0** 이다
  - better-auth 세션 조회는 **스키마에 선언된 필드만** 돌려준다(F-2032 2.4 끝, `factory.mjs` `transformSingleOutput`). 그래서 사용량 열을 `user.additionalFields` 로 선언한다(2.3 계약)
  - 사용량 값은 `AuthUser` 의 **선택 필드**로 싣는다(2.3 계약). F-2032 1.1 이 `getUser`·`requireUser` 의 모양을 지키는 이유(9개 테스트가 `{ id, email }` 로 흉내 냄)를 그대로 지키려고 필수로 두지 않는다. 필드가 없으면(흉내 낸 테스트) 관문은 `users` 를 id 로 한 번 읽는다 — 운영에서는 늘 채워져 있어 이 읽기가 일어나지 않는다
- 요청 본문은 관문 뒤에서 읽는다. 막힌 요청이 1.1MB 본문을 끝까지 읽히지 않게
- 동시 요청은 하루 5,000 을 몇 건 넘길 수 있다(같은 순간 들어온 요청들이 모두 4,999 를 본다). 넘치는 양은 동시에 보낸 요청 수만큼이라 받아들인다

### 2.2 분당 — Rate Limiting 바인딩 (9장 Q1 답: 먼저 시험, 안 되면 WAF)

`wrangler.jsonc` 에 추가할 바인딩(계약 — 이름을 바꾸면 F-2026·`npm run cf:types` 결과가 어긋난다):

```jsonc
"ratelimits": [
  { "name": "WRITE_LIMITER", "namespace_id": "1001", "simple": { "limit": 120, "period": 60 } }
]
```

- 키는 **`user.id`** 그대로. 토큰(`/v1`)과 브라우저(`/api`)가 같은 몫을 나눠 쓴다 — 스크립트가 토큰을 10개 만들어도 몫이 늘지 않는다
- 이 바인딩은 **Cloudflare 위치(POP)마다 따로 세는 근사치**다(사용자 조사, 공식 문서). 한 사람이 여러 위치에서 동시에 보내면 120 을 넘을 수 있다. 하루 5,000 이 그 구멍을 막는다
- 바인딩 호출이 예외를 던지면 **통과시킨다**(fail open). 분당 제한이 망가져 모든 저장이 막히는 쪽이 더 나쁘다. 하루 카운터는 그대로 돈다
- **무료 플랜 가용 여부는 F-2026 명세를 쓰기 전에 사람이 임시 Worker 로 시험한다**(9장 Q1 절차, 6장 사람 할 일). 안 되면 F-2026 은 바인딩·`WRITE_LIMITER` 를 빼고 관문 ④ 를 두지 않는다. 분당 보호는 대시보드의 WAF 무료 규칙 1개(IP 기준)가 맡고, 하루 카운터는 그대로다

### 2.3 하루 — `users` 행에 둔다

D1 마이그레이션(F-2025)이 `users` 에 열을 더한다. **번호는 F-2033 의 마이그레이션 뒤**다 — HEAD `9f3d84c` 에는 `0008` 까지 있고, F-308 은 마이그레이션이 없으며(F-308 1장 "건드리지 않는 파일" `migrations/`), F-2033 이 다음 빈 번호(`0009`)를 쓴다(F-2032 2.3). 그래서 F-2025 는 `0010` 이 될 것으로 본다 — F-2025 를 쓸 때 `migrations/` 를 다시 보고 다음 빈 번호로 정한다

아래 열 이름·표 이름이 계약이다(관문·DO·스크립트·better-auth 선언이 같은 이름을 쓴다):

```sql
ALTER TABLE users ADD COLUMN write_day TEXT;                              -- 'YYYY-MM-DD' (UTC)
ALTER TABLE users ADD COLUMN write_count INTEGER NOT NULL DEFAULT 0;      -- write_day 의 쓰기 수
ALTER TABLE users ADD COLUMN content_bytes INTEGER NOT NULL DEFAULT 0;    -- 3장
ALTER TABLE users ADD COLUMN doc_count INTEGER NOT NULL DEFAULT 0;        -- 3장
ALTER TABLE users ADD COLUMN blocked_at INTEGER;                          -- 4.2, NULL 이면 안 막힘
ALTER TABLE users ADD COLUMN warned_at INTEGER;                           -- 4.4, NULL 이면 주의 없음
CREATE TABLE signup_gate (                                                -- 4.1, 행 하나
  id INTEGER PRIMARY KEY CHECK (id = 1),
  day TEXT NOT NULL,                                                      -- 'YYYY-MM-DD' (UTC)
  count INTEGER NOT NULL
);
INSERT INTO signup_gate (id, day, count) VALUES (1, '', 0);
```

- 처음 판의 `CREATE INDEX users_created ON users(created_at)` 는 **뺀다.** 가입 상한을 `users` 를 세어 판단하지 않고 `signup_gate` 한 줄로 하므로(4.1) 색인이 필요 없다. 색인이 있으면 가입마다 쓰기 1행이 더 든다(처음 판 측정 "가입 1건 4행" 중 1행)
- 표 이름 `signup_gate` 에 제품명이 없다(불변조건)

better-auth 선언(F-2025 가 `worker/authServer.ts` 에 더한다 — 계약. 키 이름을 바꾸면 세션 조회 결과의 필드 이름이 바뀐다):

| `user.additionalFields` 키 | `type` | `fieldName` | `input` | `required` |
| --- | --- | --- | --- | --- |
| `writeDay` | `string` | `write_day` | `false` | `false` |
| `writeCount` | `number` | `write_count` | `false` | `false` |
| `contentBytes` | `number` | `content_bytes` | `false` | `false` |
| `docCount` | `number` | `doc_count` | `false` | `false` |
| `blockedAt` | `number` | `blocked_at` | `false` | `false` |
| `warnedAt` | `number` | `warned_at` | `false` | `false` |

- `defaultValue` 는 두지 않는다. better-auth 는 값이 없고 `defaultValue` 도 없는 필드를 `INSERT` 에서 뺀다(`factory.mjs` `transformInput`) — 새 사용자 행에는 DB `DEFAULT`(0·NULL)가 들어간다. `defaultValue` 를 두면 better-auth 가 값을 직접 넣는데 결과는 같고 선언만 늘어난다
- `input: false` — 사용자가 better-auth 입력(가입·`update-user`)으로 이 값을 넣지 못하게. `update-user` 경로는 F-2032 3.1 허용 목록에 없어 어차피 닫혀 있지만 선언으로도 막는다
- 이 필드를 선언하면 F-2033 의 스키마 검사 테스트(F-2032 6장 "판정 나눔")가 **F-2025 마이그레이션까지 적용한 DB** 로 돌아야 통과한다 — 7장 회귀

`AuthUser` 확장(계약, `worker/auth.ts`, F-2025):

```ts
export interface UserUsage {
  writeDay: string | null
  writeCount: number
  contentBytes: number
  docCount: number
  blockedAt: number | null
  warnedAt: number | null
}
export interface AuthUser {
  id: string
  email: string
  usage?: UserUsage   // getUser 세 경로(세션·토큰·개발 우회)가 이미 읽은 행에서 채운다. 흉내 낸 테스트는 비워 둔다
}
```

- **날짜 경계는 UTC 자정.** D1 무료 한도도 UTC 자정에 풀린다 — 같은 경계라야 "오늘 한도" 가 실제 위험과 맞는다. 한국 시간으로 오전 9시다
- 카운터 올리기 규칙: 쓰기 batch 끝에 사용량 줄 하나를 붙인다. `write_day` 가 오늘이면 `write_count + 1`, 아니면 `write_day` 를 오늘로 바꾸고 `1`. 날짜 바꿈을 따로 하는 작업(Cron 등)이 없다 — 첫 쓰기가 바꾼다
- 같은 줄이 총량(3장)도 함께 고친다. **쓰기 한 번에 `users` 행 한 번**이다
- 하루 초과 판정: `write_day` 가 오늘이고 `write_count >= 5000`
- 사용량 줄은 `users.updated_at` 을 건드리지 않는다. 그 열은 better-auth 가 쓰는 ISO 문자열(F-2032 2.3)이고 사용자 정보가 바뀐 시각이다

**`users` 열 vs 별도 일별 표** (9장 Q3 기본값 — `users` 열, 승인):

| | `users` 열 (기본값) | 별도 표 `usage_daily(user_id, day, writes)` |
| --- | --- | --- |
| 쓰기당 추가 행 | **1** (카운터·총량 한 줄) | 2 (일별 upsert 1 + 총량 줄 1) — 측정표 upsert 1행 + `users` 1행 |
| 관문 읽기 | 0 (인증이 읽는 행에 필드만 추가) | 요청마다 +1 행 |
| 기록 | 오늘 것만. 어제 누가 많이 썼는지는 모른다 | 날짜별로 남는다(표가 사용자×일 수만큼 자란다) |

### 2.4 쓰기 한 번에 드는 D1 행 — 전후 비교 (로컬 측정값)

| 동작 | 지금 | 뒤 | 배수 |
| --- | --- | --- | --- |
| 문서 만들기 | 3 | 4 | 1.33 |
| 문서 PUT / DO 스냅숏 / DO idle 쓰기 | 2 | 3 | 1.5 |
| 고정 · 삭제 | 1 | 2 | 2 |
| (별도 일별 표였다면) 문서 PUT | 2 | 4 | 2 |
| 가입 (F-2032 뒤) | 11 | 12 (가입 관문 1) | 1.09 |

- 사용자 전제의 "행 쓰기 비용 2배" 는 별도 표일 때의 값이다. `users` 열에 합치면 흔한 쓰기(PUT·스냅숏)가 **1.5배**다
- **하루 한도에 닿은 한 사람이 쓰는 몫:** 5,000 × 3~4행 = **15,000~20,000행 = D1 하루 쓰기 10만 행의 15~20%.** 한도에 닿은 사람이 5~6명이면 여전히 전체가 멈춘다. 이 개요는 **한 사람이 전체를 멈추는 것**을 막는다. 여러 사람이 함께 쓰는 것까지 막으려면 전체 상한이 필요하다(5.3, 하지 않음)
- **하루 가입 20명이면 240행**(12 × 20). 상한에 걸린 가입 시도는 0행이다 — 관문 줄이 `changes = 0` 이면 쓰기 0(측정)이고, 그 뒤 better-auth 는 사용자·계정·세션을 만들지 않는다(4.1)
- 로그인 쪽 곁가지(F-2032 2.5): 세션 연장은 활성 세션마다 하루 최대 1행, 활성 1,000명이면 약 1,000행(1%)
- **원격 D1 의 행 계산이 로컬과 같다는 것은 확인하지 않았다.** 원격 사용량도 조회하지 않았다(사용자 전제). 구현 뒤 대시보드의 D1 "Rows written" 으로 한 번 맞춰 본다(8장 human-checks)

### 2.5 실시간 방(DO) — 소유자 카운터에 더하고, 넘으면 느리게

- 붙이는 자리는 **`DocRoomCore.snapshot`** 하나다(F-308 12장 ②). F-308 뒤 DO 가 D1 문서 행을 쓰는 곳은 둘 — 실시간 경로의 `snapshot`(편집자 저장·`/v1` PUT 실시간 경로의 flush 모두 이것), idle 경로의 `updateDocRow`(F-308 5.5). 뒤쪽은 `updateDocRow` 자체에 붙는 사용량 줄(3.3)이 세므로 F-2027 은 `snapshot` 만 본다 — 두 번 세지 않는다
- 스냅숏의 D1 `UPDATE` 와 **같은 batch** 에 소유자 사용량 줄을 붙인다(F-2027). 줄이 새 `write_count` 를 돌려주게 해서(`RETURNING`) DO 가 **추가 읽기 없이** 초과를 안다
- 초과면 그 방은 **느린 저장**으로 바뀐다
  - `onSave`(5초 디바운스·30초 최대)는 그대로 불린다. y-partyserver 는 디바운스 간격을 onStart 에서 한 번 걸어서 **실행 중에 바꿀 수 없다**(`y-partyserver/dist/server/index.js` `onStart` 의 `debounce(…)`, F-308 머리말도 같은 확인). 그래서 간격을 바꾸는 대신 **`flush` 가 D1 스냅숏을 건너뛴다**
  - 건너뛰는 규칙: 마지막 D1 스냅숏에서 **60초**가 안 지났으면 D1 은 쓰지 않고 `persistPending`(DO SQLite `yStore`)만 한다. 편집은 버려지지 않는다
  - 미룬 스냅숏은 **DO 알람**으로 60초 시점에 한다. `roomEmptied`(마지막 연결이 닫힘)도 느린 저장 중에는 곧바로 쓰지 않고 알람에 맡긴다 — 곧바로 쓰면 연결·끊기를 되풀이해 60초를 우회할 수 있다. partyserver 의 `alarm()` 은 초기화(`onLoad` → `core.load()`)를 거친 뒤 `onAlarm()` 을 부르므로 깨어난 방에서도 동작한다(`partyserver/dist/index.js` `alarm`)
  - 느린 저장은 UTC 날짜가 바뀌면 풀린다. DO 가 쫓겨나면(eviction) 상태를 잊는다 — 다음 스냅숏 한 번이 다시 알려 준다. 쫓겨날 때마다 한 번 더 쓰는 셈이라 받아들인다
- **`/v1` PUT 의 실시간 경로와 느린 저장.** F-308 6장 9번 flush(후)는 PUT 응답 전에 D1 에 써야 200 을 준다(F-308 6.7 — 못 쓰면 503). 소유자가 하루 한도를 넘었으면 이 PUT 은 관문 ③(하루 확인)에서 **이미 429** 로 끝난다 — PUT 을 보낸 사람이 소유자일 때. 편집 권한자가 남의 문서에 PUT 하면 관문은 **보낸 사람**의 카운터를 보고, flush(후)는 **소유자**에게 센다. 그때 방이 느린 저장이면 flush(후)가 D1 을 건너뛰어 F-308 6장 10번이 `unavailable`(503)이 된다. F-2027 은 **`writeText` 가 부르는 flush 는 느린 저장이어도 D1 에 쓴다**로 정한다 — 사람이 친 명령 하나라 60초 규칙의 목적(자동 저장 폭주)과 다르고, 그 한 번도 소유자 카운터에 +1 된다
- **방마다 60초라 방이 여러 개면 느린 저장도 쌓인다.** 한도를 넘은 사람이 문서 10개를 동시에 열어 두면 하루 14,400번 × 3행 = 43,200행까지 쓸 수 있다. 결정 4("편집은 버리지 않음")를 지키는 한 막을 수 없는 구멍이다 — 9장 Q5(기본값: 그대로)
- 느린 저장은 **화면에 알리지 않는다**(9장 Q6 기본값). 편집은 DO 에 남고 다른 편집자에게는 실시간으로 보인다. 늦어지는 것은 D1 스냅숏을 읽는 경로(공유 링크·`/v1` GET·목록)뿐이고 최대 60초다

## 3. 문서 총량 — 100MB · 10,000개

### 3.1 계산 방법 — 매번 `SUM` 이 아니라 `users` 행에 누계

| | 매번 `SUM`·`COUNT` | **`users` 에 누계 (기본값)** |
| --- | --- | --- |
| 쓰기 행 | 0 | 쓰기마다 +1 — 하지만 2.3 의 카운터 줄과 **같은 줄**이라 실제 추가는 0 |
| 읽기 행 | 검사마다 **그 사람 문서 수만큼**(측정: 2,001개 → 2,001행). 문서 10,000개 × 하루 5,000 쓰기 = 5,000만 행 — D1 하루 읽기 500만 행의 **10배** | 0 (인증 때 읽은 행) |
| 정확성 | 늘 정확 | 어긋날 수 있다 — 아래 규칙으로 막고, 어긋나면 스크립트로 다시 센다 |

- 바이트는 **`length(CAST(content AS BLOB))`** 로 센다. `length(content)` 는 글자 수다(측정: `가나다` 3 vs 9)
- 대상은 `docs.content` 의 UTF-8 바이트뿐이다. 제목(최대 500자)·첨부(따로 300MB)는 넣지 않는다
- 한도 상수(계약): `DOC_BYTES_QUOTA = 104_857_600`(100MiB — 첨부 `ATTACHMENT_QUOTA_BYTES` 314,572,800 이 300MiB 인 것과 같은 단위), `DOC_COUNT_QUOTA = 10_000`

### 3.2 누계를 맞게 유지하는 규칙

1. **증감은 실제로 바뀐 행 기준.** 조건부 `UPDATE`(버전)가 0행이면 총량도 안 바뀐다 — 사용량 줄에서 `changes()` 로 앞 문장 결과를 본다(측정표 "버전 맞음/틀림")
2. **증감은 대체된 행에서 계산한다.** `updateDocRow(env, existing, patch)`(F-308 6.1)는 조건부 `UPDATE` 가 바꾸는 바로 그 버전의 행(`existing`)을 인자로 받는다. 새 바이트 − `existing.content` 의 바이트
3. **여러 문서를 지우는 쓰기**(폴더 삭제가 안의 문서를 지움, `handleDeleteFolder`)는 지우는 문장 **앞에** 같은 batch 에서 그 문서들의 바이트 합과 수를 빼는 줄을 둔다. 읽기 행은 지우는 문서 수만큼 — 한 번뿐이다
4. **소유자 기준.** 편집 권한으로 남의 문서를 고쳐도 늘어나는 것은 **문서 소유자**의 총량이다(DO 스냅숏도 소유자, 결정 4 와 같은 방향). `updateDocRow` 는 `existing.owner_id` 를 안다(F-308 12장)
- 그래도 어긋나는 곳: DO 스냅숏이 대체하는 행의 바이트를 메모리의 `base` 에서 거꾸로 계산하면 원래 줄바꿈이 섞였던 문서에서 몇 바이트 틀릴 수 있다. F-2027 이 D1 값에서 계산할지 정한다. `/v1` PUT 실시간 경로의 413 판정은 Worker 가 읽은 D1 행 기준이라 DO 보다 최대 30초 낡은 값에서 증감을 잰다(F-308 12장) — 근사다. 어긋남은 `admin-recount`(4.3)로 바로잡는다
- 마이그레이션(F-2025)이 지금 있는 문서로 누계를 한 번 채운다(모든 문서를 한 번 읽는다 — 원격 문서 수는 조회하지 않았다)

### 3.3 넘었을 때 — 늘리는 쓰기만 거절, 그리고 검사·카운터의 자리

| 요청 | 거절 조건 | 응답 | 검사하는 곳 |
| --- | --- | --- | --- |
| 문서 만들기 (`POST /api/docs`, `POST /v1/docs`) | `doc_count >= 10000` | 413 `resource: "docs"` | 핸들러 |
| 문서 만들기 | `content_bytes + 새 바이트 > 104857600` | 413 `resource: "bytes"` | 핸들러 |
| 문서 PUT `/api` | 증감 > 0 **이고** `content_bytes + 증감 > 104857600` | 413 `resource: "bytes"` | `handleUpdateDoc`, `updateDocRow` 부르기 전 |
| 문서 PUT `/v1` | 같음 | 같음 | **Worker `handleUpdateDocV1` 4장 5번(줄바꿈 맞춤) 뒤, 6번 앞** (F-308 12장). 증감 = 맞춘 `content` 바이트 − 4장 3번에서 읽은 행의 바이트. DO 는 총량을 보지 않는다 |
| 문서 PUT — 증감 ≤ 0 | 거절 안 함 (이미 넘은 상태여도) | 200 | — |
| 삭제·폴더 삭제 | 거절 안 함 | 204 | — |
| 실시간 편집(DO) | 검사 안 함 (결정 7). 문서 하나 1MB 만 | — | — |

- `id` 가 이미 있는 문서로 다시 만들기(멱등 재시도, `handleCreateDoc` 의 `existing` 분기)는 새 문서가 아니므로 수 검사를 하지 않는다
- 실시간 편집으로 100MB 를 넘길 수 있다. 넘은 뒤에는 새 문서와 늘리는 PUT 이 막힌다 — 결정 7 이 받아들인 대가다

**카운터·누계 줄을 붙이는 자리** (F-308 12장이 정한 것을 이어받는다):

| D1 문서 행을 쓰는 곳 | 누가 부르나 | 붙이는 소명세 |
| --- | --- | --- |
| `worker/docWrite.ts` `updateDocRow` | `/api` PUT(`handleUpdateDoc`), `/v1` PUT 폴백(F-308 9장), DO idle 경로(F-308 5.5) | **F-2025** — 함수 하나에 붙이면 세 경로가 모두 센다 |
| `DocRoomCore.snapshot` | 편집자 자동 저장, `/v1` PUT 실시간 경로의 flush(선·후) | **F-2027** |
| 그 밖의 쓰기 핸들러(만들기·삭제·고정·폴더·링크·초대·잠금·토큰·첨부) | 각 핸들러 | F-2025 |

- `updateDocRow` 는 F-308 이 만드는 함수라 **F-308 구현 뒤** 그 모양(`{ ok: true; row } | { ok: false }`)을 유지한 채 안의 문장을 batch 로 바꾼다. F-308 A9(문장 글자 그대로 검사)는 F-2025 가 고친다(7장)
- 느린 저장(2.5)의 판정도 `snapshot` 의 batch 결과(`RETURNING write_count`)를 쓴다. idle 경로는 느린 저장이 없다 — Yjs·저장 타이머를 건드리지 않는 한 번의 쓰기이고 하루 한도는 그 PUT 의 관문이 이미 봤다

### 3.4 응답 계약 (2장·3장·4장 공통)

상태 코드와 `error` 문자열은 계약이다 — 웹(F-2030)·CLI(F-2031)·`worker/v1Contract.ts` 가 이 모양에 댄다.

```ts
// 429 — 헤더 Retry-After: <초>
type RateLimitedBody = { error: 'rate_limited'; scope: 'minute' | 'day'; limit: number; retryAfter: number }
// 413 — 문서 하나가 1MB 를 넘는 기존 { error: 'too_large', limit } 과 error 로 구분한다
type DocQuotaBody = { error: 'doc_quota_exceeded'; resource: 'bytes' | 'docs'; used: number; limit: number }
// 403 — 쓰기 라우트에서 막힌 계정
type BlockedBody = { error: 'account_blocked' }
```

- 가입 마감은 HTTP 몸통이 아니라 **OAuth 오류 코드** `signup_closed` 다 — better-auth 가 `/login?return=…&error=signup_closed` 로 돌려보낸다(4.1). 처음 판의 `GET /api/me` 403 `SignupClosedBody` 는 **없앤다**: F-2032 뒤 사용자 행이 없으면 세션도 없어 `/api/me` 는 401 이다(F-2032 3.4 끝)
- `retryAfter`: 분당은 **60 고정**(바인딩이 남은 시간을 알려 주지 않는다 — `RateLimitOutcome` 은 `success` 하나뿐). 하루는 **다음 UTC 자정까지 남은 초, 올림**
- 413 에 새 `error` 를 쓰는 이유: 첨부 계정 한도는 507 `quota_exceeded` 인데(F-221), 사용자가 "413 계열" 로 정했다. 기존 413 `too_large` 와 섞이지 않게 `error` 로 가른다. 옛 CLI(0.2.0)는 413 을 상태 코드만 보고 `too_large` 종료 코드 7 로 끝낸다 — 종료 코드는 새 CLI 와 같다(5.2)
- `GET /api/me`·`GET /v1/me` 200 응답에 `blocked: boolean`·`warned: boolean` 을 더한다(4.2·4.4). `GET /api/usage` 200 응답은 기존 `{ used, limit }`(첨부)을 그대로 두고 아래를 더한다

```ts
type UsageBody = {
  used: number; limit: number                                               // 첨부 — 기존 그대로
  docs: { bytes: number; bytesLimit: number; count: number; countLimit: number }
  writes: { today: number; limit: number }
}
```

## 4. 가입 제한과 계정 차단

### 4.1 하루 신규 가입 20명 — better-auth `validateUserInfo` 안의 한 문장 관문

**가입 = better-auth 가 사용자 행을 만드는 것.** F-2032 뒤 사용자 행을 만드는 곳은 둘이다: ① OAuth 콜백에서 처음 보는 이메일 — better-auth `internalAdapter.createUser`, ② 로컬 개발 우회(`DEV_AUTH_EMAIL`, F-2032 2.4 2번)의 `findOrCreateUser`. `/v1` 은 이미 있는 사용자의 토큰만 받는다(`getTokenUser` 는 사용자를 만들지 않는다). ② 는 상한을 보지 않는다(로컬 전용 — 처음 판과 같음)

**판정 자리.** better-auth 옵션 `user.validateUserInfo`(F-2033 이 `worker/authServer.ts` 에 두는 것, F-2032 2.2) 안에서 **동작이 `create-user` 일 때만** 판정한다. 근거(소스): `createUser` 가 `validateUserInfo` 를 `action: "create-user"` 로 **사용자 `INSERT` 전에** 부르고(`internal-adapter.mjs` `createUser`), `{ error }` 를 돌려주면 `APIError("FORBIDDEN", { code })` 가 되어(`validate-user-info.mjs`) OAuth 콜백이 그 코드로 오류 주소에 보낸다(`callback.mjs` — `handleOAuthUserInfo` 의 `catch` 에서 `redirectOnError(e.body.code, …)`). `link-account`·`sign-in` 동작에서는 세지 않는다 — 이미 있는 사람이다

**규칙 (F-2032 9장 Q6 의 결론 — 비원자성을 받아들이지 않고 없앤다):**

1. 먼저 F-2032 의 이메일 인증 검사(`emailVerified !== true` → `email_not_verified`). 인증 안 된 이메일이 가입 자리를 쓰지 않게 **이 검사가 앞**이다
2. 그다음 **가입 관문 한 줄**: `signup_gate` 의 한 행을 조건부로 올린다 — "`day` 가 오늘(UTC)이 아니면 `day` = 오늘·`count` = 1, 오늘이면 `count < 20` 일 때만 `count + 1`". 문장 모양은 머리말 측정표 "가입 관문 한 줄" 이다. `changes = 1` 이면 통과, `0` 이면 `{ error: 'signup_closed' }`
3. D1 오류로 관문 줄이 던지면 **통과시키지 않는다** — `validateUserInfo` 가 던지면 better-auth 가 `validation_failed` 로 막는다(`assertValidUserInfo` 의 `catch`, "Fails closed"). 사용자는 `/login` 에서 "로그인하지 못했습니다. 잠시 뒤 다시 시도해 주세요." 를 본다(F-2032 3.4 마지막 줄)

**왜 이 방식인가 — 세 안 비교**

| 안 | 동시 가입이 몰릴 때 | 가입 1건 추가 비용 | 실패 뒤 남는 것 | 판단 |
| --- | --- | --- | --- | --- |
| **(A) `signup_gate` 한 줄 조건부 `UPDATE` (채택)** | 넘치지 않는다 — 한 문장. 로컬 측정: 동시 50번에 정확히 20 성공 | 쓰기 1 · 읽기 1 | 관문을 지난 뒤 사용자·계정 `INSERT` 가 실패하면(같은 사람이 두 제공자로 동시에 첫 로그인해 `users.email UNIQUE` 에 걸리는 경우 등) **자리 하나가 헛되이 쓰인다** — 그날 상한이 1 줄어드는 쪽이라 안전하다 | 채택 |
| (B) `validateUserInfo` 에서 `SELECT COUNT(*) FROM users WHERE created_at >= 오늘` 후 판단 (F-2032 8장이 적은 방식) | 동시 요청 수만큼 넘친다 | 쓰기 0 · 읽기 = 오늘 가입 수(측정 20명 → 20행) + `users_created` 색인 유지 비용(가입마다 쓰기 1) | 없음 | 비원자. 색인이 필요해 쓰기도 결국 1 |
| (C) `databaseHooks.user.create.before` 에서 사용자 행 조건부 삽입 흉내 | 넘치지 않을 수 있으나 better-auth 가 자기 `INSERT` 를 또 한다 | — | D1 은 대화형 트랜잭션이 없어(F-2032 9장 Q6, `D1SqliteDriver.beginTransaction` 이 던짐) 반쯤 만든 계정이 남을 수 있다. `before` 가 `false` 를 돌려주면 `createUser` 가 `null` → 뒤의 `createAccount` 가 깨져 `unable_to_create_user` 로 끝나 전용 문구를 쓸 수 없다(`with-hooks.mjs`·`link-account.mjs`) | 안 씀 |

- (A) 는 처음 판이 기댄 "한 문장 조건부 쓰기로 경쟁을 막는다"(`locks.ts` `acquireLock` 과 같은 방식)를 better-auth 밖의 작은 표로 옮긴 것이다. 사용자 행을 우리가 만들지 않아도 된다
- 헛된 자리는 되돌리지 않는다. 되돌리려면 better-auth 의 `create.after`·실패 경로에 훅을 더 걸어야 하고, 되돌리기 자체가 쓰기다. 운영자가 `admin-usage` 에서 오늘 가입 수(`signup_gate.count`)와 실제 오늘 만든 `users` 수가 다른 것을 볼 수 있다(4.3)
- 상수(계약): `SIGNUP_DAILY_LIMIT = 20`

**사용자가 보는 것.** 콜백이 `302 /login?return={같은 값}&error=signup_closed&error_description=signup_closed` 로 보낸다(F-2032 3.2 실패 주소 규칙). `/login` 오류 줄(F-2032 3.4 표)에 한 줄을 더한다 — 문구는 5.1 L6. 처음 판의 "`GET /api/login` 이 마감이면 302 `/?app=1`" 규칙과 "`GET /api/me` 403 `signup_closed`" 는 **없앤다**(F-2032 8장)

**가입 상한 밖의 계정 수.** 처음 판의 "Zero Trust 비활성 좌석 1개월 자동 해제" 는 Access 가 사라져 없어진다(결정 8). 앱에는 **전체 계정 수 상한이 없다** — 풀어 줄 좌석이 없으므로 "비활성 1개월 해제" 에 해당하는 앱 기능도 두지 않는다. 전체 계정 수를 막아야 하면 새 결정이다(5.3)

- 로그인을 막지 않는 이유: F-2032 뒤에는 앱이 로그인을 막을 수 **있다**(F-2032 8장 — `validateUserInfo` `sign-in` 또는 `databaseHooks.session.create.before`). 하지만 막으면 결정 10 의 "본인 읽기·내보내기" 를 할 길이 없다. 막힌 사람은 로그인한 뒤 L5 를 본다

- 막아도 공개 링크 행(`share_links`)·초대(`grants`)·토큰·세션은 지우지 않는다. 풀면(`admin-unblock`) 그대로 돌아온다

### 4.3 관리 스크립트 `scripts/admin-*.mjs`

- `npx wrangler d1 execute md-editor-db --remote --json --command "…"` 을 부르는 얇은 Node 스크립트. `scripts/` 규칙대로 JS(`.mjs`), 새 의존성 없음. `--local` 을 주면 원격 대신 로컬 D1
- **쓰는 스크립트는 `--yes` 없이는 실행하지 않고 대상과 SQL 을 출력만 한다.** `wrangler d1 execute` 는 바인딩 인자를 받지 않으므로 이메일은 **소문자로 바꾼 뒤 엄격한 형식 검사를 통과한 것만** SQL 에 넣는다. 자유 문장(사유 등)은 SQL 에 넣지 않는다

| 스크립트 | 하는 일 |
| --- | --- |
| `admin-usage.mjs [--top N]` | 오늘(UTC) 쓰기 많은 순 N명(기본 20): 이메일·`write_count`·`content_bytes`·`doc_count`·`blocked_at`·`warned_at`·가입일. 오늘 가입 수 두 값 — `signup_gate.count`(관문을 지난 수)와 오늘 `created_at` 인 `users` 수(실제로 만든 수). 전체 `content_bytes` 합(9장 Q2 — DB 하나의 크기 지켜보기). 읽기만 |
| `admin-block.mjs <email> [--yes]` | `blocked_at` 을 지금 시각으로 |
| `admin-unblock.mjs <email> [--yes]` | `blocked_at` 을 NULL 로 |
| `admin-warn.mjs <email> [--clear] [--yes]` | `warned_at` 을 지금 시각으로(4.4). `--clear` 면 NULL 로 |
| `admin-recount.mjs [<email> \| --all] [--yes]` | `content_bytes`·`doc_count` 를 `docs` 에서 다시 센다(3.2 어긋남 바로잡기). `--all` 은 모든 문서를 한 번 읽는다 |

### 4.4 제한 전 알림 — `users.warned_at` (9장 Q9 답)

사용자 답: **"중대한 위반은 즉시, 그 외는 앱 알림으로".** 서버는 메일을 보내지 않고 연락처도 없다(terms.md·privacy.md). 그래서 "앱 알림" 은 앱 화면의 알림 띠다

| 경우 | 운영자가 하는 일 | 사용자가 보는 것 |
| --- | --- | --- |
| 중대한 위반 | `admin-block` 곧바로 | 다음 `/api/me`·쓰기에서 L5 |
| 그 밖의 위반 | 먼저 `admin-warn` → 사용자가 앱을 연 뒤에도 계속되면 `admin-block` | 먼저 L7(주의), 그 뒤 L5 |

- `warned_at` 은 쓰기를 막지 않는다. `/api/me` 의 `warned: true` 로 앱이 L7 을 띄울 뿐이다
- "미리 알린 뒤" 가 성립하려면 사용자가 앱을 열어 L7 을 봐야 한다. **본 것을 서버가 확인하지는 않는다**(읽음 기록 없음). 얼마나 기다린 뒤 막을지는 운영자가 정한다 — 이 개요는 기간을 정하지 않는다
- "중대한 위반" 이 무엇인지는 약관 문장이다(8장 `terms.md` 행). 지금 제11조 둘째 문장("긴급하거나 법령 위반이 명백한 경우에는 먼저 제한하고 곧바로 알립니다")이 이미 즉시 제한의 근거다 — 사용자 답에 맞춰 "그 외는 앱 화면 알림으로 미리 알린다" 를 더하는 방향이다. 문장은 메인 초안 + 사용자 확인(F-270·F-2035 와 같은 방식)

### 5.1 웹 — 알림 띠(N-1), ia.md 4.2 형식

숫자는 하드코딩하지 않고 응답의 `limit` 에서 채운다(바이트는 `AccountMenu.tsx` `formatUsage` 와 같은 MB 표기). `{시각}` 은 다음 UTC 자정을 **브라우저 현지 시각**으로 적는다(한국이면 `오전 9:00`)

| # | 언제 | 종류 | 문구 | 버튼 |
| --- | --- | --- | --- | --- |
| L1 | outbox 가 429 `minute`(또는 몸통 없는 429)를 받음 — 멈출 때 한 번 | info | `요청이 많아 잠시 쉬었다가 이어서 저장합니다.` | — |
| L2 | outbox 가 429 `day` 를 받음 | error | `오늘 저장 한도(하루 {limit}번)를 넘었습니다. {시각}부터 다시 저장됩니다. 그때까지 바뀐 내용은 이 브라우저에 보관됩니다.` | — |

- L6 이 `{시각}` 을 쓰지 않는 이유: `/login` 은 스크립트가 없는 Worker 페이지라(F-2032 3.3) 브라우저 현지 시각을 계산할 수 없다. 사용자 대부분이 한국어 화면을 쓰므로 한국 시간과 UTC 를 함께 적는다
- L7 의 종류 `warn` 은 이미 있다(`src/app/notice.ts` `NoticeType = 'info' | 'error' | 'update' | 'warn'`). `warn` 은 `info` 에 대체되지 않는다(`pushNotice` 의 `PROTECTED_TYPES`)

outbox 동작 (F-207 2.3 에 더함, F-2030):

- **429** — 항목을 **버리지 않는다.** 이번 회차를 멈추고 `Retry-After` 초(없거나 숫자가 아니면 60) 동안 보내지 않는다. 30초 재시도(`RETRY_INTERVAL_MS`)·`online` 이벤트도 그 시각 전에는 보내지 않는다
- **413 `doc_quota_exceeded`** — 항목을 **버리지 않는다.** 이번 회차에서 그 항목과 **같은 문서의 뒤 항목**을 건너뛰고 나머지(삭제·줄이기 등)를 계속 보낸다 — 앞 항목에서 멈추면 공간을 비우는 삭제가 뒤에 막혀 영영 못 나간다. 건너뛴 항목은 다음 회차에 다시 보낸다
- **403 `account_blocked`** — 항목을 버리지 않고 보내기를 멈춘다. 서버 문서는 읽기 전용으로 연다(L5)
- **403 `forbidden_origin`**(F-2032 4.2) — 이 개요의 응답이 아니다. 같은 출처 `fetch` 는 늘 `Origin` 을 실어 정상 앱에서는 나지 않는다. F-2030 은 이것을 지금의 403(`forbidden`) 처리에 맡긴다
- 상태바(ia.md 4.1)에 새 문구는 없다. 쌓인 항목 수는 지금의 동기화 대기 표시가 보여 준다
- **지금 배포된 웹은 세 응답을 잘못 다룬다** — 429 는 `other` 로 떨어져 **항목을 버리고** `동기화하지 못했습니다.`, 413 `doc_quota_exceeded` 는 `too_large` 로 **버리고** `1MB 초과` 문구, 403 은 `forbidden` 으로 그 문서의 **대기 편집을 모두 버린다**(`serverStore.ts` `sendOne`). 그래서 F-2030 은 서버 관문(F-2026·F-2028)과 **같은 배포**로 나간다(6장 — 이제 모두 한 배포다). 새 버전 알림(F-117)을 누르지 않은 열린 탭은 옛 코드로 남는다 — 받아들인다

계정 메뉴:

- 계정 메뉴 이미지 줄(`.account-menu-usage`) 아래에 **새 줄** `.account-menu-usage-docs` — `문서 {n}MB / {limit} · {count}개`. 90% 이상이면 `-danger` 모양(이미지 줄과 같은 규칙). **기존 `.account-menu-usage` 선택자는 그대로 둔다**(`e2e/imageQuota.spec.js` 가 그 문구를 정확히 본다). 응답에 `docs` 가 없으면(옛 서버·가짜 서버) 줄을 그리지 않는다. 하루 쓰기 수는 보이지 않는다
- 처음 판의 "S-9(터미널 로그인)에서 `signup_closed` 면 전용 문장" 은 **없앤다.** S-9 의 `로그인` 링크는 `/api/login` → `/login` 을 거치므로(F-2032 3.5) 마감이면 `/login` 오류 줄(L6)에서 멈추고 S-9 로 돌아오지 않는다. `account.ts` `fetchAccount` 에 `closed` 상태를 더하지 않는다
- `helpDoc.ts` 의 한도 문단(이미지 300MB 문장)에 문서 100MB·10,000개·하루 5,000번을 더한다

### 5.3 하지 않는 것

- 관리자 화면·API, 사용자에게 보내는 메일(서버는 메일을 보내지 않는다), 차단 사유 저장, 자동 차단, 주의 읽음 기록
- 초과 시 과금·플랜
- 첨부 한도(300MB)의 계산 방식 변경 — 지금처럼 올릴 때마다 `SUM`. 이 개요는 건드리지 않는다

## 9. 열린 질문 / 사람 결정 필요

### Q1. Rate Limiting 바인딩을 무료 플랜에서 쓸 수 있나 — **답(2026-09-24 사용자): 임시 Worker 로 먼저 시험, 안 되면 WAF 규칙 1개 + 하루 카운터**

시험 절차(F-2026 명세를 쓰기 전, 사람):

1. 스크래치 폴더에 바인딩 하나(`limit: 5, period: 10`)만 있는 임시 Worker 를 만든다. 이름에 제품명을 넣지 않는다
2. `wrangler deploy` 가 되면 1초 간격으로 10번 불러 6번째부터 `success: false` 가 나오는지 본다
3. 확인 뒤 임시 Worker 를 지운다. 결과를 `specs/human-checks.md` 에 적는다

| 방식 | 분당 보호 | 드는 것 | 판단 |
| --- | --- | --- | --- |
| Rate Limiting 바인딩 | 사용자 id, 60초, 위치별 근사 | 무료 가용 미확인 | **시험해서 되면 이것** |
| D1 분 카운터 | 정확 | 쓰기 요청마다 **+1 행** — 지키려는 쓰기 행을 더 쓴다 | 안 쓴다 |
| WAF 무료 규칙 1개 | **IP** 기준, 10초 | 0. 같은 IP(회사·학교)를 나누는 사람이 함께 막힌다. 조건식에 메서드·경로를 얼마나 쓸 수 있는지 확인 못 함 | **바인딩이 안 되면 이것** |
| 하루 카운터만 | 분 단위 없음 | 0 | 어느 쪽이든 늘 있다 |

WAF 로 가면 429 몸통이 우리 모양이 아니다 — 그래서 5.1·5.2 가 **몸통 없는 429 도 `minute` 로, `Retry-After` 가 없으면 60초**로 다룬다. WAF 를 쓰면 5.3 "로그인 반복" 과 Q8 "읽기 남용" 에 쓸 규칙 자리가 없다(무료 1개)
