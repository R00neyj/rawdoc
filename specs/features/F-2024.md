## 1. 범위 — 무엇을 막고 무엇을 세나

### 1.1 막으려는 것

- 무료 플랜은 한도를 넘으면 과금이 아니라 **오류로 실패**한다(product.md 7장 M3). 한 사람이 D1 하루 쓰기 10만 행을 다 쓰면 **UTC 자정까지 모든 사용자의 저장이 실패**한다
- 지금 `worker/` 에는 속도 제한이 0건이다. 있는 한도는 문서 하나 1MB(`MAX_CONTENT_BYTES`), 제목 500자, 이미지 5MB·계정 300MB, 토큰 10개뿐이다. 문서 **수**와 본문 **합계**는 무제한이다
- CLI(F-2021)가 공개돼 `/v1` 반복 호출이 쉬워졌다. 분당 120 만으로는 하루를 못 막는다 — 120 × 1,440분 = **172,800 요청/일**로 D1 하루 쓰기 한도를 혼자 넘는다. 그래서 하루 5,000 이 따로 있다

### 1.2 "쓰기"의 정의 — 어느 요청이 카운터를 올리나

**규칙: `/api/*`·`/v1/*` 에서 메서드가 `GET` 이 아닌 라우트는 전부 쓰기다.** 예외 목록을 두지 않는다 — 예외 하나가 우회 경로가 된다(아래 잠금 참고)

| 경로 | 쓰기인가 | 분당 | 하루 |
| --- | --- | --- | --- |
| `/api`: `POST docs`, `PUT docs/:id`, `DELETE docs/:id`, `PUT docs/:id/folder`, `PUT docs/:id/pin` | 예 | 셈 | 셈 |
| `/api`: `POST`·`DELETE docs/:id/lock` (잠금 잡기·연장·놓기) | 예 | 셈 | 셈 |
| `/api`: `POST`·`DELETE docs/:id/link`, `POST`·`DELETE folders/:id/link` | 예 | 셈 | 셈 |
| `/api`: `POST folders`, `PUT`·`DELETE folders/:id` | 예 | 셈 | 셈 |
| `/api`: `PUT`·`DELETE docs/:id/grants/:email`, `PUT`·`DELETE folders/:id/grants/:email` | 예 | 셈 | 셈 |
| `/api`: `POST tokens`, `DELETE tokens/:id`, `PUT attachments/:idext` | 예 | 셈 | 셈 |
| `/v1`: `POST docs`, `PUT docs/:id`, `POST folders`, `POST attachments`, `POST docs/:id/link` | 예 | 셈 | 셈 |
| DO 스냅숏(`docRoomCore` `snapshot` 의 D1 `UPDATE`) | 요청이 아님 | **안 셈** (바인딩은 Worker 요청에만 건다) | **소유자에게 셈** (결정 4) |
| 모든 `GET` — `/api`·`/v1`·`/pub`, `GET /api/login`, `GET /api/me`, `GET /ws/doc/:id`(업그레이드) | 아니오 | 안 셈 | 안 셈 |
| 곁가지 쓰기 — 새 사용자 `INSERT`(가입, 4.1 이 따로 막음), `api_tokens.last_used_at`(토큰마다 10분에 1회, 토큰 10개면 하루 최대 1,440행), Cron 첨부 정리 | 요청 단위 아님 | 안 셈 | 안 셈 |

- **잠금을 빼지 않는 이유.** 잠금 연장은 `pending`·`fallback` 세션에서만 20초마다 한 번이다(`useDocLock.ts` `EXTEND_INTERVAL_MS`, `App.tsx` `useDocLock` 의 `docId` 조건). 8시간 폴백 편집이 1,440번이라 하루 5,000 안에 든다. 빼면 `/api` 쿠키로 잠금만 분당 120번 두드려 하루 172,800행을 쓸 수 있다
- **분당은 요청을 세고, 하루는 D1 쓰기를 센다.** 분당 제한은 관문(2.1)에서 요청마다 한 번 바인딩을 부른다 — 400·404·409·413 으로 끝난 요청도 분당에는 잡힌다. 하루 카운터는 핸들러가 **실제로 D1 쓰기 batch 를 실행할 때만** +1 한다(2.3). 검사에서 걸려 D1 에 닿지 않은 요청은 하루에 안 잡힌다
- 조건부 쓰기가 0행으로 끝나도(버전 충돌 409, 잠금 못 잡음 423) batch 는 실행됐으므로 하루 +1 이다 — 사용량 줄이 행 1개를 실제로 썼다(측정표 "버전 틀림")

## 2. 분당·하루 제한

### 2.1 쓰기 관문 — 한 곳에서, 핸들러보다 먼저

- `worker/index.ts` 의 라우트 표에서 쓰기 라우트(1.2)를 가려, **핸들러를 부르기 전에** 관문 하나를 지난다. 새 파일 `worker/writeGate.ts`(F-2026)
- 순서: ① 사용자 판정(401) → ② **차단 확인**(403 `account_blocked`, 4.2) → ③ **하루 확인**(429 `scope: "day"`) → ④ **분당 확인**(429 `scope: "minute"`) → 핸들러. 싼 검사를 먼저 하고, 바인딩 호출은 마지막에 한다 — 이미 막힌 요청이 분당 몫을 쓰지 않게
- 하루 확인은 **인증 때 이미 읽은 `users` 행**의 `write_day`·`write_count` 로 한다. 지금도 인증은 요청마다 `users` 를 한 줄 읽는다(`findOrCreateUser` 의 `SELECT`, `getTokenUser` 의 `SELECT … WHERE id = ?`) — 읽는 열만 늘리면 **추가 D1 읽기가 0** 이다
- 요청 본문은 관문 뒤에서 읽는다. 막힌 요청이 1.1MB 본문을 끝까지 읽히지 않게
- 동시 요청은 하루 5,000 을 몇 건 넘길 수 있다(같은 순간 들어온 요청들이 모두 4,999 를 본다). 넘치는 양은 동시에 보낸 요청 수만큼이라 받아들인다

### 2.2 분당 — Rate Limiting 바인딩

`wrangler.jsonc` 에 추가할 바인딩(계약 — 이름을 바꾸면 F-2026·`npm run cf:types` 결과가 어긋난다):

```jsonc
"ratelimits": [
  { "name": "WRITE_LIMITER", "namespace_id": "1001", "simple": { "limit": 120, "period": 60 } }
]
```

- 키는 **`user.id`** 그대로. 토큰(`/v1`)과 브라우저(`/api`)가 같은 몫을 나눠 쓴다 — 스크립트가 토큰을 10개 만들어도 몫이 늘지 않는다
- 이 바인딩은 **Cloudflare 위치(POP)마다 따로 세는 근사치**다(사용자 조사, 공식 문서). 한 사람이 여러 위치에서 동시에 보내면 120 을 넘을 수 있다. 하루 5,000 이 그 구멍을 막는다
- 바인딩 호출이 예외를 던지면 **통과시킨다**(fail open). 분당 제한이 망가져 모든 저장이 막히는 쪽이 더 나쁘다. 하루 카운터는 그대로 돈다
- **무료 플랜에서 쓸 수 있는지·과금되는지 확인하지 못했다.** 확인 절차와 안 될 때의 대안은 9장 Q1

### 2.3 하루 — `users` 행에 둔다

D1 마이그레이션 `0009`(F-2025)가 `users` 에 열을 더한다(계약 — 관문·DO·스크립트가 같은 열 이름을 쓴다):

```sql
ALTER TABLE users ADD COLUMN write_day TEXT;                              -- 'YYYY-MM-DD' (UTC)
ALTER TABLE users ADD COLUMN write_count INTEGER NOT NULL DEFAULT 0;      -- write_day 의 쓰기 수
ALTER TABLE users ADD COLUMN content_bytes INTEGER NOT NULL DEFAULT 0;    -- 3장
ALTER TABLE users ADD COLUMN doc_count INTEGER NOT NULL DEFAULT 0;        -- 3장
ALTER TABLE users ADD COLUMN blocked_at INTEGER;                          -- 4.2, NULL 이면 안 막힘
CREATE INDEX users_created ON users(created_at);                          -- 4.1
```

- **날짜 경계는 UTC 자정.** D1 무료 한도도 UTC 자정에 풀린다 — 같은 경계라야 "오늘 한도" 가 실제 위험과 맞는다. 한국 시간으로 오전 9시다
- 카운터 올리기 규칙: 쓰기 batch 끝에 사용량 줄 하나를 붙인다. `write_day` 가 오늘이면 `write_count + 1`, 아니면 `write_day` 를 오늘로 바꾸고 `1`. 날짜 바꿈을 따로 하는 작업(Cron 등)이 없다 — 첫 쓰기가 바꾼다
- 같은 줄이 총량(3장)도 함께 고친다. **쓰기 한 번에 `users` 행 한 번**이다
- 하루 초과 판정: `write_day` 가 오늘이고 `write_count >= 5000`

**`users` 열 vs 별도 일별 표** (사용자 표현 "사용량 행" 을 어떻게 둘지 — 기본값은 `users` 열, 9장 Q3):

| | `users` 열 (기본값) | 별도 표 `usage_daily(user_id, day, writes)` |
| --- | --- | --- |
| 쓰기당 추가 행 | **1** (카운터·총량 한 줄) | 2 (일별 upsert 1 + 총량 줄 1) — 측정표 upsert 1행 + `users` 1행 |
| 관문 읽기 | 0 (인증 `SELECT` 에 열만 추가) | 요청마다 +1 행 |
| 기록 | 오늘 것만. 어제 누가 많이 썼는지는 모른다 | 날짜별로 남는다(표가 사용자×일 수만큼 자란다) |

### 2.4 쓰기 한 번에 드는 D1 행 — 전후 비교 (로컬 측정값)

| 동작 | 지금 | 뒤 | 배수 |
| --- | --- | --- | --- |
| 문서 만들기 | 3 | 4 | 1.33 |
| 문서 PUT / DO 스냅숏 | 2 | 3 | 1.5 |
| 고정 · 삭제 | 1 | 2 | 2 |
| (별도 일별 표였다면) 문서 PUT | 2 | 4 | 2 |

- 사용자 전제의 "행 쓰기 비용 2배" 는 별도 표일 때의 값이다. `users` 열에 합치면 흔한 쓰기(PUT·스냅숏)가 **1.5배**다
- **하루 한도에 닿은 한 사람이 쓰는 몫:** 5,000 × 3~4행 = **15,000~20,000행 = D1 하루 쓰기 10만 행의 15~20%.** 한도에 닿은 사람이 5~6명이면 여전히 전체가 멈춘다. 이 개요는 **한 사람이 전체를 멈추는 것**을 막는다. 여러 사람이 함께 쓰는 것까지 막으려면 전체 상한이 필요하다(5.4, 하지 않음)
- 가입 1건은 `users_created` 색인까지 4행(측정 "상한 2 로 세 번"의 첫 두 번). 하루 20명이면 80행
- **원격 D1 의 행 계산이 로컬과 같다는 것은 확인하지 않았다.** 원격 사용량도 조회하지 않았다(사용자 전제). 구현 뒤 대시보드의 D1 "Rows written" 으로 한 번 맞춰 본다(8장 human-checks)

### 2.5 실시간 방(DO) — 소유자 카운터에 더하고, 넘으면 느리게

- 스냅숏의 D1 `UPDATE` 와 **같은 batch** 에 소유자 사용량 줄을 붙인다(F-2027). 줄이 새 `write_count` 를 돌려주게 해서(`RETURNING`) DO 가 **추가 읽기 없이** 초과를 안다
- 초과면 그 방은 **느린 저장**으로 바뀐다
  - `onSave`(5초 디바운스·30초 최대)는 그대로 불린다. y-partyserver 는 디바운스 간격을 onStart 에서 한 번 걸어서 **실행 중에 바꿀 수 없다**(`y-partyserver/dist/server/index.js` `onStart` 의 `debounce(…)`). 그래서 간격을 바꾸는 대신 **`flush` 가 D1 스냅숏을 건너뛴다**
  - 건너뛰는 규칙: 마지막 D1 스냅숏에서 **60초**가 안 지났으면 D1 은 쓰지 않고 `persistPending`(DO SQLite `yStore`)만 한다. 편집은 버려지지 않는다
  - 미룬 스냅숏은 **DO 알람**으로 60초 시점에 한다. `roomEmptied`(마지막 연결이 닫힘)도 느린 저장 중에는 곧바로 쓰지 않고 알람에 맡긴다 — 곧바로 쓰면 연결·끊기를 되풀이해 60초를 우회할 수 있다. partyserver 의 `alarm()` 은 초기화(`onLoad` → `core.load()`)를 거친 뒤 `onAlarm()` 을 부르므로 깨어난 방에서도 동작한다(`partyserver/dist/index.js` `alarm`)
  - 느린 저장은 UTC 날짜가 바뀌면 풀린다. DO 가 쫓겨나면(eviction) 상태를 잊는다 — 다음 스냅숏 한 번이 다시 알려 준다. 쫓겨날 때마다 한 번 더 쓰는 셈이라 받아들인다
- **방마다 60초라 방이 여러 개면 느린 저장도 쌓인다.** 한도를 넘은 사람이 문서 10개를 동시에 열어 두면 하루 14,400번 × 3행 = 43,200행까지 쓸 수 있다. 결정 4("편집은 버리지 않음")를 지키는 한 막을 수 없는 구멍이다 — 9장 Q5
- 느린 저장은 **화면에 알리지 않는다**(기본값, 9장 Q6). 편집은 DO 에 남고 다른 편집자에게는 실시간으로 보인다. 늦어지는 것은 D1 스냅숏을 읽는 경로(공유 링크·`/v1` GET·목록)뿐이고 최대 60초다

## 3. 문서 총량 — 100MB · 10,000개

### 3.1 계산 방법 — 매번 `SUM` 이 아니라 `users` 행에 누계

| | 매번 `SUM`·`COUNT` | **`users` 에 누계 (기본값)** |
| --- | --- | --- |
| 쓰기 행 | 0 | 쓰기마다 +1 — 하지만 2.3 의 카운터 줄과 **같은 줄**이라 실제 추가는 0 |
| 읽기 행 | 검사마다 **그 사람 문서 수만큼**(측정: 2,001개 → 2,001행). 문서 10,000개 × 하루 5,000 쓰기 = 5,000만 행 — D1 하루 읽기 500만 행의 **10배** | 0 (인증 때 읽은 행) |
| 정확성 | 늘 정확 | 어긋날 수 있다 — 아래 네 가지로 막고, 어긋나면 스크립트로 다시 센다 |

- 바이트는 **`length(CAST(content AS BLOB))`** 로 센다. `length(content)` 는 글자 수다(측정: `가나다` 3 vs 9)
- 대상은 `docs.content` 의 UTF-8 바이트뿐이다. 제목(최대 500자)·첨부(따로 300MB)는 넣지 않는다
- 한도 상수(계약): `DOC_BYTES_QUOTA = 104_857_600`(100MiB — 첨부 `ATTACHMENT_QUOTA_BYTES` 314,572,800 이 300MiB 인 것과 같은 단위), `DOC_COUNT_QUOTA = 10_000`

### 3.2 누계를 맞게 유지하는 규칙

1. **증감은 실제로 바뀐 행 기준.** 조건부 `UPDATE`(버전)가 0행이면 총량도 안 바뀐다 — 사용량 줄에서 `changes()` 로 앞 문장 결과를 본다(측정표 "버전 맞음/틀림")
2. **증감은 대체된 행에서 계산한다.** PUT 은 조건부 `UPDATE` 가 바꾸는 바로 그 버전의 행을 이미 읽어 두었다(`getDocAccess` 가 `SELECT *`). 새 바이트 − 그 행의 바이트
3. **여러 문서를 지우는 쓰기**(폴더 삭제가 안의 문서를 지움, `handleDeleteFolder`)는 지우는 문장 **앞에** 같은 batch 에서 그 문서들의 바이트 합과 수를 빼는 줄을 둔다. 읽기 행은 지우는 문서 수만큼 — 한 번뿐이다
4. **소유자 기준.** 편집 권한으로 남의 문서를 고쳐도 늘어나는 것은 **문서 소유자**의 총량이다(DO 스냅숏도 소유자, 결정 4 와 같은 방향)
- 그래도 어긋나는 곳: DO 가 대체하는 행의 바이트를 메모리의 `base` 에서 거꾸로 계산하면 원래 줄바꿈이 섞였던 문서에서 몇 바이트 틀릴 수 있다. F-2027 이 D1 값에서 계산할지 정한다. 어긋남은 `admin-recount`(4.3)로 바로잡는다
- 마이그레이션 `0009` 가 지금 있는 문서로 누계를 한 번 채운다(모든 문서를 한 번 읽는다 — 원격 문서 수는 조회하지 않았다)

### 3.3 넘었을 때 — 늘리는 쓰기만 거절

| 요청 | 거절 조건 | 응답 |
| --- | --- | --- |
| 문서 만들기 (`POST /api/docs`, `POST /v1/docs`) | `doc_count >= 10000` | 413 `resource: "docs"` |
| 문서 만들기 | `content_bytes + 새 바이트 > 104857600` | 413 `resource: "bytes"` |
| 문서 PUT (`/api`·`/v1`) | 증감 > 0 **이고** `content_bytes + 증감 > 104857600` | 413 `resource: "bytes"` |
| 문서 PUT — 증감 ≤ 0 | 거절 안 함 (이미 넘은 상태여도) | 200 |
| 삭제·폴더 삭제 | 거절 안 함 | 204 |
| 실시간 편집(DO) | 검사 안 함 (결정 7). 문서 하나 1MB 만 | — |

- `id` 가 이미 있는 문서로 다시 만들기(멱등 재시도, `handleCreateDoc` 의 `existing` 분기)는 새 문서가 아니므로 수 검사를 하지 않는다
- 실시간 편집으로 100MB 를 넘길 수 있다. 넘은 뒤에는 새 문서와 늘리는 PUT 이 막힌다 — 결정 7 이 받아들인 대가다

### 3.4 응답 계약 (2장·3장·4장 공통)

상태 코드와 `error` 문자열은 계약이다 — 웹(F-2030)·CLI(F-2031)·`worker/v1Contract.ts` 가 이 모양에 댄다.

```ts
// 429 — 헤더 Retry-After: <초>
type RateLimitedBody = { error: 'rate_limited'; scope: 'minute' | 'day'; limit: number; retryAfter: number }
// 413 — 문서 하나가 1MB 를 넘는 기존 { error: 'too_large', limit } 과 error 로 구분한다
type DocQuotaBody = { error: 'doc_quota_exceeded'; resource: 'bytes' | 'docs'; used: number; limit: number }
// 403 — 쓰기 라우트에서 막힌 계정
type BlockedBody = { error: 'account_blocked' }
// 403 — GET /api/me, 가입 상한에 걸린 새 이메일 (4.1)
type SignupClosedBody = { error: 'signup_closed'; retryAfter: number }
```

- `retryAfter`: 분당은 **60 고정**(바인딩이 남은 시간을 알려 주지 않는다 — `RateLimitOutcome` 은 `success` 하나뿐). 하루·가입 마감은 **다음 UTC 자정까지 남은 초, 올림**
- 413 에 새 `error` 를 쓰는 이유: 첨부 계정 한도는 507 `quota_exceeded` 인데(F-221), 사용자가 "413 계열" 로 정했다. 기존 413 `too_large` 와 섞이지 않게 `error` 로 가른다. 옛 CLI(0.2.0)는 413 을 상태 코드만 보고 `too_large` 종료 코드 7 로 끝낸다 — 종료 코드는 새 CLI 와 같다(5.3)
- `GET /api/me`·`GET /v1/me` 200 응답에 `blocked: boolean` 을 더한다. `GET /api/usage` 200 응답은 기존 `{ used, limit }`(첨부)을 그대로 두고 아래를 더한다

```ts
type UsageBody = {
  used: number; limit: number                                               // 첨부 — 기존 그대로
  docs: { bytes: number; bytesLimit: number; count: number; countLimit: number }
  writes: { today: number; limit: number }
}
```

## 4. 가입 제한과 계정 차단

### 4.1 하루 신규 가입 20명

- 사용자 행을 만드는 곳은 `worker/auth.ts` `findOrCreateUser` 하나다. `/api/*` 는 Access 가 막고(product.md 7장 M2, 앱 `md-editor-api` 는 `rawdoc.app/api`), `/ws/*` 는 같은 함수를 쿠키로 부르고, `/v1` 은 이미 있는 사용자의 토큰만 받는다(`getTokenUser` 는 사용자를 만들지 않는다). **가입 = 이 함수의 `INSERT`**
- 규칙: **한 문장 조건부 `INSERT`** — "오늘(UTC) 만든 사용자 수 < 20 일 때만 넣는다". 로컬 측정에서 상한을 넘지 않았다(측정표). 동시 가입이 몰려도 문장 하나라 21번째가 들어가지 않는다 (`locks.ts` `acquireLock` 이 한 문장 조건부 쓰기로 경쟁을 막는 것과 같은 방식)
- 이미 있는 사용자는 이 검사를 거치지 않는다. 지금처럼 요청마다 `INSERT` 를 먼저 부르면 요청마다 `COUNT` 가 돈다 — F-2028 은 **먼저 `SELECT` 하고 없을 때만 `INSERT`** 로 순서를 바꾼다(기존 사용자 요청의 읽기가 늘지 않게)
- 넣지 못했고 이메일로도 행이 없으면 **가입 마감**
  - `GET /api/me` → 403 `signup_closed`
  - `GET /api/login` → 지금은 사용자 판정이 실패하면 401 JSON 이다. 마감이면 **302 `/?app=1`** + 원래 `return` 해시로 보낸다 — `/?app=1` 은 첫 방문 랜딩을 건너뛰는 탈출구다(`rootRoute.ts` `rootTarget`). 앱이 뜨고 `/api/me` 가 마감을 알려 준다
  - 그 밖의 `/api/*`·`/ws/*` 는 지금처럼 401·4401
- `DEV_AUTH_EMAIL` 우회(로컬)는 상한을 보지 않는다
- **Zero Trust 좌석**: 비활성 좌석 1개월 자동 해제는 대시보드 설정이다(사람 할 일, 8장 human-checks). 좌석이 차면 Access 가 새 로그인을 막으므로 앱까지 오지 않는다 — 그때의 화면은 Access 것이라 이 개요가 정하지 않는다. 무료 좌석 수는 확인하지 못했다(product.md 7장 M2 "무료 좌석 수는 문서에서 확인하지 못했다")

### 4.2 막힌 계정 — `users.blocked_at`

| 대상 | 막힌 계정 본인 | 막힌 계정 소유 문서의 다른 사람 | 근거 |
| --- | --- | --- | --- |
| 쓰기 라우트(1.2) | 403 `account_blocked` (관문 ②) | 그 문서에 쓰는 요청도 403 `account_blocked` | 결정 10 "쓰기 전부 차단" |
| 읽기 `GET /api`·`/v1` (목록·문서·첨부·내보내기) | 허용 | 허용 (기본값, 9장 Q4) | 결정 10 "본인 읽기·내보내기 허용" |
| 공개 링크 `/pub/*`·`/p/*`·공개 첨부 | — | **404** — 링크 소유자(`share_links.owner_id`)가 막혔으면 없는 링크와 똑같이 | 결정 10 |
| 실시간 연결 `/ws/doc/:id` | `4403 forbidden` | 소유자가 막혔으면 `4403` | 쓰기 전부 차단 |
| 이미 열린 실시간 연결 | 다음 재검증(`revalidateConnections`, 편집이 있으면 최대 60초)에서 `4403` | 같음 | `docRoomCore` 재검증 경로 |
| DO 스냅숏 | — | 소유자가 막혔으면 D1 에 쓰지 않는다. 편집은 `yStore` 에 남는다 | "편집을 버리지 않음"(결정 4)과 같은 태도 |

- 공개 조회는 `share_links WHERE token = ? AND revoked_at IS NULL` 이 `links.ts`·`publicPage.ts`·`attachments.ts` 에 흩어져 있다. F-2028 은 **소유자 차단 조건을 모든 공개 조회에 빠짐없이** 붙인다 — 하나라도 빠지면 그 경로로 계속 보인다. 수용 기준에 공개 경로 전부를 한 줄씩 둔다
- 막아도 공개 링크 행(`share_links`)·초대(`grants`)·토큰은 지우지 않는다. 풀면(`admin-unblock`) 그대로 돌아온다
- 막힌 계정도 로그인은 된다(Access 는 모른다). 이메일을 Access 에서도 막고 싶으면 사람이 Zero Trust 정책에서 따로 한다 — 이 개요 범위 밖

### 4.3 관리 스크립트 `scripts/admin-*.mjs`

- `npx wrangler d1 execute md-editor-db --remote --json --command "…"` 을 부르는 얇은 Node 스크립트. `scripts/` 규칙대로 JS(`.mjs`), 새 의존성 없음. `--local` 을 주면 원격 대신 로컬 D1
- **쓰는 스크립트는 `--yes` 없이는 실행하지 않고 대상과 SQL 을 출력만 한다.** `wrangler d1 execute` 는 바인딩 인자를 받지 않으므로 이메일은 **소문자로 바꾼 뒤 엄격한 형식 검사를 통과한 것만** SQL 에 넣는다. 자유 문장(사유 등)은 SQL 에 넣지 않는다

| 스크립트 | 하는 일 |
| --- | --- |
| `admin-usage.mjs [--top N]` | 오늘(UTC) 쓰기 많은 순 N명(기본 20): 이메일·`write_count`·`content_bytes`·`doc_count`·`blocked_at`·가입일. 오늘 가입 수. 읽기만 |
| `admin-block.mjs <email> [--yes]` | `blocked_at` 을 지금 시각으로 |
| `admin-unblock.mjs <email> [--yes]` | `blocked_at` 을 NULL 로 |
| `admin-recount.mjs [<email> \| --all] [--yes]` | `content_bytes`·`doc_count` 를 `docs` 에서 다시 센다(3.2 어긋남 바로잡기). `--all` 은 모든 문서를 한 번 읽는다 |

| L2 | outbox 가 429 `day` 를 받음 | error | `오늘 저장 한도(하루 {limit}번)를 넘었습니다. {시각}부터 다시 저장됩니다. 그때까지 바뀐 내용은 이 브라우저에 보관됩니다.` | — |
| L3 | 413 `doc_quota_exceeded` `bytes` | error | `계정의 문서 저장 공간({limit})이 가득 찼습니다. 문서를 지우거나 줄이면 다시 저장됩니다.` | — |

outbox 동작 (F-207 2.3 에 더함, F-2030):

- **429** — 항목을 **버리지 않는다.** 이번 회차를 멈추고 `Retry-After` 초(없거나 숫자가 아니면 60) 동안 보내지 않는다. 30초 재시도(`RETRY_INTERVAL_MS`)·`online` 이벤트도 그 시각 전에는 보내지 않는다
- **413 `doc_quota_exceeded`** — 항목을 **버리지 않는다.** 이번 회차에서 그 항목과 **같은 문서의 뒤 항목**을 건너뛰고 나머지(삭제·줄이기 등)를 계속 보낸다 — 앞 항목에서 멈추면 공간을 비우는 삭제가 뒤에 막혀 영영 못 나간다. 건너뛴 항목은 다음 회차에 다시 보낸다
- **403 `account_blocked`** — 항목을 버리지 않고 보내기를 멈춘다. 서버 문서는 읽기 전용으로 연다(L5)
- 상태바(ia.md 4.1)에 새 문구는 없다. 쌓인 항목 수는 지금의 동기화 대기 표시가 보여 준다
- **지금 배포된 웹은 세 응답을 잘못 다룬다** — 429 는 `other` 로 떨어져 **항목을 버리고** `동기화하지 못했습니다.`, 413 `doc_quota_exceeded` 는 `too_large` 로 **버리고** `1MB 초과` 문구, 403 은 `forbidden` 으로 그 문서의 **대기 편집을 모두 버린다**(`serverStore.ts` `sendOne`). 그래서 F-2030 은 서버 관문(F-2026·F-2028)과 **같은 배포이거나 그보다 먼저** 나가야 한다(6장). 새 버전 알림(F-117)을 누르지 않은 열린 탭은 옛 코드로 남는다 — 먼저 내보낼수록 안전하다

계정 메뉴와 S-9:

- 계정 메뉴 이미지 줄(`.account-menu-usage`) 아래에 **새 줄** `.account-menu-usage-docs` — `문서 {n}MB / {limit} · {count}개`. 90% 이상이면 `-danger` 모양(이미지 줄과 같은 규칙). **기존 `.account-menu-usage` 선택자는 그대로 둔다**(`e2e/imageQuota.spec.js` 가 그 문구를 정확히 본다). 응답에 `docs` 가 없으면(옛 서버·가짜 서버) 줄을 그리지 않는다. 하루 쓰기 수는 보이지 않는다
- 터미널 로그인 화면(S-9)에서 `/api/me` 가 `signup_closed` 면 L6 과 같은 문장을 보이고 `로그인`·`승인` 버튼을 두지 않는다 — 지금은 403 을 `out` 으로 보고 `로그인` 링크를 내어 같은 자리로 되돌아오는 고리가 된다(`account.ts` `fetchAccount`)
- `helpDoc.ts` 의 한도 문단(이미지 300MB 문장)에 문서 100MB·10,000개·하루 5,000번을 더한다

## 9. 열린 질문 / 사람 결정 필요

### Q1. Rate Limiting 바인딩을 무료 플랜에서 쓸 수 있나 — **사람 확인 필요. 기본값: 쓴다(결정 2), 안 되면 대안**

확인하지 못한 것: 무료 플랜 가용 여부와 과금. 확인 절차(구현 전, 사람):

1. 스크래치 폴더에 바인딩 하나(`limit: 5, period: 10`)만 있는 임시 Worker 를 만든다. 이름에 제품명을 넣지 않는다
2. `wrangler deploy` 가 되면 1초 간격으로 10번 불러 6번째부터 `success: false` 가 나오는지 본다
3. 확인 뒤 임시 Worker 를 지운다. 결과를 `specs/human-checks.md` 에 적는다

안 될 때:

| 방식 | 분당 보호 | 드는 것 | 판단 |
| --- | --- | --- | --- |
| Rate Limiting 바인딩 | 사용자 id, 60초, 위치별 근사 | 무료 가용 미확인 | **기본값** |
| D1 분 카운터 | 정확 | 쓰기 요청마다 **+1 행** — 지키려는 쓰기 행을 더 쓴다 | 안 쓴다 |
| WAF 무료 규칙 1개 | **IP** 기준, 10초 | 0. 같은 IP(회사·학교)를 나누는 사람이 함께 막힌다. 조건식에 메서드·경로를 얼마나 쓸 수 있는지 확인 못 함 | 바인딩이 안 되면 이것 |
| 하루 카운터만 | 분 단위 없음 | 0 | 어느 쪽이든 늘 있다 |

WAF 로 가면 429 몸통이 우리 모양이 아니다 — 그래서 5.1·5.2 가 **몸통 없는 429 도 `minute` 로, `Retry-After` 가 없으면 60초**로 다룬다

### Q2. 계정당 100MB 와 D1 무료 DB 500MB — **사람 확인 필요. 기본값: 결정 5 그대로**

`specs/product.md` 7장 M2 는 "무료 DB 500MB" 라고 적었다(2026-09-15 문서 확인). 사용자 전제의 "저장 5GB" 는 계정 전체 합이다. DB 가 `md-editor-db` 하나이므로 **100MB 를 다 쓴 계정 5개면 DB 가 찬다.** 이 개요는 결정을 바꾸지 않는다. 다른 선택지: 계정당 한도를 낮춘다(예: 20MB → 25계정) / 그대로 두고 `admin-usage` 로 합계를 지켜본다. 이 문서 작성 중 D1 한도 문서를 다시 열어 보지는 않았다

### Q3. 사용량을 `users` 열에 둘 것인가 — **기본값: `users` 열** (2.3)

추가 행이 쓰기당 1(별도 표는 2), 관문 읽기가 0. 대신 날짜별 기록이 없다. 별도 표를 고르면: 2.4 의 PUT 이 3행 → 4행(2배), 관문이 요청마다 한 줄 더 읽고, `admin-usage` 가 지난 날짜도 보여 줄 수 있다

### Q4. 막힌 소유자 문서를 초대받은 사람이 읽을 수 있나 — **기본값: 읽기 허용, 쓰기 거절** (4.2)

결정 10 이 공개 경로만 404 로 정했다. 초대받은 사람까지 404 로 하면 그 사람의 사이드바에서 문서가 사라진다(남용이 초대 목록을 통한 배포라면 그쪽이 맞다). 다른 쪽을 고르면: `access.ts` 판정에 소유자 차단을 넣어 읽기도 404, F-2028 에 초대 목록 경로 수용 기준이 는다

### Q5. 느린 저장의 "방 여러 개" 구멍 — **기본값: 결정 4 그대로(60초만)** (2.5)

막으려면: 하루 두 배(10,000)를 넘으면 D1 스냅숏을 **멈춘다**(편집은 `yStore` 에 남고 다음 날 처음 스냅숏에서 D1 에 반영). 결정 4 의 "편집은 버리지 않음" 은 지켜지지만 "간격만 늘림" 과 다르므로 사용자가 정한다

### Q6. 느린 저장을 알릴 것인가 — **기본값: 알리지 않는다** (2.5)

알리면 DO 가 사용자 정의 메시지를 하나 더 보내고 ia.md 4.2 에 줄이 는다. 알리지 않아도 편집은 잃지 않는다

### Q7. 하루 한도를 넘은 뒤 삭제도 막나 — **기본값: 막는다** (1.2)

삭제도 D1 쓰기라 결정 3 에 든다. 삭제만 풀어 주면 "삭제 → 만들기(413 아님, 하루 한도에 걸림)" 는 여전히 막히므로 우회는 없다. 대신 규칙이 하나 는다. 결정 6 의 "줄이는 편집·삭제 허용" 은 총량(3장)에 대한 것으로 읽었다

### Q8. 읽기 남용 — **기본값: 이번 범위 밖** (5.3)

결정 1 이 쓰기만 골랐다. 막으려면 Q1 의 WAF 규칙을 `/v1/*` 전체에 건다(바인딩을 쓰면 WAF 규칙 1개가 비어 있다)

### Q9. 이용약관 제11조 "미리 알린 뒤" 와 알릴 수단 — **사람 결정 필요**

제11조는 "이용자가 제7조를 어기면 운영자는 **미리 알린 뒤** 서비스 이용을 제한할 수 있습니다" 다. 서버는 메일을 보내지 않고 연락처도 아직 없다(terms.md·privacy.md "연락처: 아직 정해지지 않았습니다"). 차단 도구(4.3)는 알림 없이 막는다. 화면의 L5 가 "곧바로 알림" 역할은 하지만 "미리" 는 아니다. 약관 문장을 고칠지, 차단 전에 알릴 경로를 정할지 사람이 정한다. 이 개요는 약관을 고치지 않는다

### 기본값으로 정한 것 (승인 시 확정)

1. 쓰기 = `/api`·`/v1` 의 `GET` 이 아닌 라우트 전부. 잠금 포함, 예외 없음 — 1.2

5. 누계를 `users` 행에 두고 카운터와 같은 줄에서 고친다 — 2.3·3.1
6. 413 은 `error: "doc_quota_exceeded"` 로 기존 `too_large` 와 가른다 — 3.4
7. 가입 상한은 한 문장 조건부 `INSERT`, 마감이면 `/api/login` 이 `/?app=1` 로 — 4.1
8. 막힌 계정의 공유·초대·토큰은 지우지 않는다 — 4.2
9. 관리 스크립트는 `--yes` 없이 쓰지 않는다 — 4.3
10. 웹 outbox 는 429·413·403 에서 항목을 버리지 않는다. 413 은 같은 문서만 건너뛰고 나머지를 보낸다 — 5.1
11. 계정 메뉴에 문서 줄을 새 클래스로. 하루 쓰기 수는 안 보인다 — 5.1
