## 2. 공용 계약 — `src/lib/accountDeletion.ts`

이름과 값이 다른 명세·테스트와 맞물리는 계약이다. 서버(`worker/account.ts`)와 앱(`src/app/accountDelete.ts`) 둘 다 여기서 import 한다(architecture.md 6장 "Worker 는 `src/lib/**` 순수 함수와 `src/types.ts` 만 import").

```ts
export const ACCOUNT_DELETE_FRESH_MS = 10 * 60 * 1000   // 4.1, 11장 Q1
export const ACCOUNT_DELETE_CONFIRM_WORD = '삭제'        // 6.3, 11장 Q2

// GET /api/account 200 본문
export type AccountDeletePreview = {

  docs: number            // 내가 가진 서버 문서. 금고 문서 포함

  sharedDocs: number      // 그중 다른 사람이 지금 열 수 있는 문서 (3.2)
  folders: number
```

## 3. 서버 API

### 3.1 경로 — 계약

| 메서드·경로 | 성공 | 실패 (본문은 `{ error }`, 3.3) |
| --- | --- | --- |
| `GET /api/account` | 200 `AccountDeletePreview` | 401 `unauthenticated`, 500 `internal` |
| `DELETE /api/account` | **204, 본문 없음** | 401 `unauthenticated`, 403 `forbidden_origin`(`index.ts` 관문, 지금 그대로), 403 `reauth_required`(+ `freshMinutes: 10`), 500 `internal` |

- `/v1/*` 에는 두지 않는다. 명령줄 도구로 계정을 지우는 길은 없다
- `GET` 은 세션을 연장하지 않는다(`getUser` 와 같은 `disableRefresh`). 연장은 지금처럼 `GET /api/me` 만(F-2033 3.3)
- `DELETE` 응답에 쿠키를 지우는 `Set-Cookie` 를 싣지 않아도 된다. 앱이 곧바로 `/?app=1` 로 새로 읽고, 첫 `GET /api/me` 가 없는 세션에 쿠키 지우는 줄을 싣는다(m8). 실어도 틀리지 않다 — 구현자가 better-auth `api.signOut` 을 재사용해 싣기로 하면 W3 에 단언을 더한다

### 3.2 미리 보기 개수 — 규칙

- 모두 `owner_id = 나`(토큰은 `user_id`) 로 센다. 질의는 **개수 한 번 + 공유 중 문서 한 번 = 2번**(m4, 0.6ms + 3.6ms). 문서 1,000개 규모에서도 같은 두 번이다
- `sharedDocs` = 내 문서 중 다음 하나라도 맞는 것의 **중복 없는** 개수:
  1. 문서 초대가 있다(`grants`, `target_type = 'doc'`)
  2. 초대가 걸린 폴더 **또는 그 하위 폴더**에 있다
  3. 살아있는(끊지 않은) 문서 공유 링크의 시작 문서다
  4. 살아있는 문서 공유 링크의 묶음(`share_link_docs`)에 들어 있다
  5. 살아있는 폴더 공유 링크가 걸린 폴더 또는 그 하위 폴더에 있다
- 금고 문서는 초대·링크가 붙을 수 없으므로(F-401) 저절로 빠진다. 규칙에 따로 적지 않는다
- 하위 폴더 추적은 D1 재귀 CTE 한 질의로 한다(m4 에서 확인한 모양). JS 에서 폴더 나무를 따로 읽어 풀면 질의가 2~3번 늘고 무료 CPU 10ms 를 더 쓴다

### 3.3 오류 문자열 — 계약

| `error` | 언제 |
| --- | --- |
| `unauthenticated` | 세션이 없거나 만료 |
| `reauth_required` | 세션은 있지만 만든 지 10분 이상(4.1). 본문 `{ "error": "reauth_required", "freshMinutes": 10 }` |
| `forbidden_origin` | 비`GET` 의 `Origin` 이 틀림 — 지금 `index.ts` 관문이 그대로 낸다 |
| `internal` | batch 실패 등. 지우기는 한 트랜잭션이라 **아무것도 지워지지 않은 상태**(5.2) |

### 3.4 쓰기 관문·분당 제한 — 적용하지 않는다

- `isWriteRoute` 는 `/api/account` 에 **거짓**(두 메서드 다). 이유: 관문은 막힌 계정(403 `account_blocked`)·하루 한도(429)·분당 한도(429)를 거른다. 계정 삭제는 **막힌 계정도, 한도를 넘긴 계정도 할 수 있어야 한다** — 방침 9절 "언제든지 … 지우고" 와 약관 제11조 3항(막힌 계정도 자기 문서를 보고 내보낼 수 있다)의 뜻. 되풀이해 부를 수 없는 한 번짜리 동작이라 분당 제한도 필요 없다
- `Origin` 검사는 그대로 받는다(`index.ts` 가 라우트 표 앞에서 모든 비`GET` `/api/*` 에 건다)
- 막힌 계정의 삭제 뒤 기록을 남기느냐는 11장 Q4

## 4. 본인 확인 — 최근 로그인

### 4.1 기준 — 10분

- `DELETE` 는 **지금 요청의 세션을 만든 시각(`auth_sessions.created_at`)부터 10분(`ACCOUNT_DELETE_FRESH_MS`) 안** 이어야 한다. 경계: `now − createdAt < 10분` 이면 통과, 같거나 크면 `reauth_required`(better-auth 가 `>=` 로 거절하는 것과 같은 방향, m6)
- 10분인 이유: 다시 로그인 → 앱으로 돌아옴 → D-15 가 다시 열림 → `삭제` 입력까지 1분 안팎이다. 지켜 줄 상황은 "로그인된 채 자리를 비운 기기" 인데, better-auth 기본값 1일은 그 기기에서 거의 늘 통과한다. 다른 값의 효과는 11장 Q1
- 세션 연장(`GET /api/me`, 24시간마다)은 `createdAt` 을 바꾸지 않으므로(m6) 오래 켜 둔 탭은 늘 다시 로그인이 필요하다 — 의도한 동작이다
- 개발 우회(`isDevBypass`, 로컬 `http:` + `@example.com`)는 세션이 없다 → **통과로 본다**, `freshUntil: null`. 운영에서는 켜지지 않는다(`origin.ts` `isDevBypass` 조건)

### 4.2 판정 자리

- **better-auth 옵션(`freshAge`)도 `deleteUser` 도 쓰지 않는다.** `freshAge` 는 better-auth 자기 경로(`/list-sessions`, `deleteUser` 등)에만 걸리는데 그 경로들은 `AUTH_ROUTES` 허용 목록에 없어 404 다. `deleteUser` 는 m7 대로 못 쓴다. 판정 방식(세션 `createdAt` 과 기준 초)만 그대로 가져온다
- `worker/auth.ts` 에 함수 하나를 더한다 — `getUser` 와 같은 순서(개발 우회 → better-auth `getSession`, `disableRefresh`)로 사용자를 찾고, **세션 만든 시각(ms)을 같이 돌려준다.** 개발 우회면 시각은 `null`. `/v1/` 토큰 경로는 이 함수가 다루지 않는다(`/api/account` 는 `/api/` 뿐)
- 판정 식 자체는 `worker/account.ts` 의 순수 함수로 둔다 — 단위 테스트(W6)가 시각만 넣어 경계를 본다

### 4.3 다시 로그인 흐름

```
D-15 가 reauth 상태 → `다시 로그인…`
  → (앱) 저장 대기 입력 먼저 저장(로그인 버튼과 같은 `onBeforeNavigate`)
  → (앱) sessionStorage `md.accountDelete` 에 {"step":"resume","userId":…,"at":…} (6.5)
  → location.href = `/login?return={지금 해시}&reauth=1`
  → (/login) 세션이 있어도 페이지를 그린다, 안내 줄 한 줄 (4.4)
  → 사용자가 Google / GitHub 고름 → POST /api/login → 제공자 → 콜백: 새 세션(createdAt = 지금, m6)
  → `/{해시}` 로 돌아옴 → 앱 부팅 → `/api/me` in → 표지 확인 → D-15 가 저절로 열림 (6.5)
```

- 해시를 쓰지 않고 sessionStorage 표지를 쓰는 이유: 돌아온 뒤에도 **보던 문서 주소가 그대로**다. 새 해시(`#/delete-account` 류)를 두면 `hashRoute.ts`·`bootPaint.ts`·`App.tsx` 라우팅 분기가 늘고, 닫은 뒤 원래 주소를 되살릴 방법이 없다
- 앱 안 대화상자에 제공자 버튼을 직접 그리지 않고 `/login` 으로 보내는 이유: Google·GitHub 공식 로고는 `worker/providerLogos.ts` 에만 둔다(`CLAUDE.md` 불변조건 예외, F-2032 3.3.1). 앱에 로고 없는 글자 버튼을 두면 제공자 표기 규칙을 새로 따져야 한다
- **다른 계정으로 로그인해 돌아온 경우**: 표지의 `userId` 와 지금 계정 id 가 다르면 D-15 를 열지 않고 N-1 `warn` 한 줄(6.6). 다른 계정의 미리 보기를 띄워 엉뚱한 계정을 지우는 일을 막는다
- 로그인이 실패·취소되면 better-auth 는 `failureUrl`(`/login?return=…&error=…`)로 보낸다. 여기에는 `reauth=1` 이 없어서 **세션이 아직 살아 있으면** `handleLoginPage` 가 곧바로 앱으로 돌려보낸다(m13) — 표지가 남아 있으므로 D-15 가 다시 열리고, 서버가 여전히 `fresh: false` 라 reauth 상태가 다시 보인다. 오류 문구(`로그인을 취소했습니다.` 등)는 보이지 않는다. 받아들인다 — `loginReturn`·`handleLoginStart` 에 `reauth` 를 실어 나르는 변경은 이 명세의 이득에 비해 로그인 경로를 많이 건드린다(11장 Q8)

### 4.4 `/login?reauth=1`

- `handleLoginPage`: 쿼리 `reauth` 가 정확히 `'1'` 이면 **세션이 있어도 302 하지 않고** 페이지를 그린다. 그 밖의 값·없음이면 지금 동작 그대로
- `renderLoginPage` 입력에 선택 필드 `reauth: boolean`. 참이면 제목 아래 안내 줄을 오류 줄보다 먼저 하나 더 그린다:
  - `<p class="login-reauth">계정 삭제를 계속하려면 다시 로그인하세요. 삭제할 계정의 Google 또는 GitHub 로 로그인해야 합니다.</p>`
  - 스크립트는 여전히 없다. 폼·숨은 `return` 은 그대로
- `.login-reauth` 한 규칙 — 색은 `pageTokens.ts` 변수만(`--ink` 등). 모양은 사람 확인
- `GET /api/login`(`loginUrl`)은 바꾸지 않는다. 앱은 다시 로그인 때만 `/login?…&reauth=1` 로 직접 간다

### 5.2 D1 batch — 한 트랜잭션, 순서가 계약

`DELETE /api/account` 는 최근 로그인 판정 뒤 **D1 batch 하나**로 5.1 의 D1 행을 전부 지운다. batch 는 한 트랜잭션이라(하나가 실패하면 전부 되돌린다) "계정은 지웠는데 문서가 남은" 중간 상태가 없다. 그래서 `deleting` 같은 표지 열이 필요 없다.

- **삭제와 겹친 다른 요청**: 판정을 이미 지난 내 다른 기기의 쓰기(`POST /api/docs`·첨부 올리기 등)가 batch 뒤에 D1 에 닿으면 `users` 행이 없어 외래 키 오류 → 500. 첨부 올리기는 R2 에 먼저 쓰므로 객체 하나가 남을 수 있다 — `r2_prefix` 작업을 1시간 동안 끝내지 않는 이유(5.4)

### 5.3 `purge_jobs` 표 — 계약

```sql
CREATE TABLE purge_jobs (
  kind TEXT NOT NULL CHECK (kind IN ('room', 'r2_prefix')),
  target TEXT NOT NULL,              -- room: 문서 id, r2_prefix: 'att/{userId}/'
  priority INTEGER NOT NULL,         -- 클수록 먼저. room 은 docs.updated_at, r2_prefix 는 0
  created_at INTEGER NOT NULL,       -- ms
  attempts INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (kind, target)
);
CREATE INDEX purge_jobs_order ON purge_jobs(kind, priority DESC);
```

- 표 이름에 제품명이 없다(불변조건). `users` 에 외래 키를 걸지 않는다 — 사용자 행이 지워진 뒤에도 남아야 하는 행이다
- 계정 삭제 전용 이름이 아니다. 지금 폴더 `전부 삭제`(`handleDeleteFolder` `delete-all`)가 지운 문서의 DO 를 비우지 않는 문제(12장 X2)를 나중에 같은 표로 고칠 수 있게 일반 이름으로 둔다. **이 명세는 그 경로를 고치지 않는다**

### 5.4 DO·R2 정리 — 곧바로 시작해 차례로

한 요청에서 다 끝낼 수 없다. 무료 플랜 한 호출의 하위 요청이 50개(m5)이고, 문서 1,000개면 방 비우기 RPC 만 1,000번이다. 그래서 **요청은 D1 을 곧바로 지우고, 방·R2 는 `purge_jobs` 에 적어 두고 비운다.**

비우는 함수(`worker/purgeJobs.ts`) 하나를 두 곳이 부른다:

| 부르는 곳 | 호출 예산(`maxCalls`) | 언제 |
| --- | --- | --- |
| `DELETE /api/account` 의 `ctx.waitUntil` | **15** | 204 응답 뒤. 요청 동기 경로가 이미 쓴 D1 20개 안팎 + 15 + 정리 D1 4 ≤ 50 |
| `scheduled` — 새 Cron `*/10 * * * *` | **40** | 10분마다. 정리 D1 4 + 40 ≤ 50 |

규칙:

- **호출 하나** = 방 비우기 RPC 한 번, R2 `list` 한 번, R2 `delete`(키 1,000개까지 한 번) 한 번. D1 은 예산과 따로 **4문장 이하**: 방 작업 읽기 1, R2 작업 읽기 1, 끝난 작업 지우기 1, 실패 `attempts` 올리기 1(끝난 것·실패한 것은 id 목록을 JSON 한 인자로 넘겨 한 문장씩 — 지금 `DELETE_FOLDERS_SQL` 이 쓰는 `json_each` 방식)
- 예산 안에서 **방 작업을 먼저**, `priority` 큰 것(최근 고친 문서)부터. 이유: 다른 사람이 **지금 열어 둔** 방일 가능성이 가장 높다. 방은 편집이 있으면 스스로 닫히지만(m10) 편집 없이 열어만 둔 방은 이 작업이 닫는다. 방 작업이 없거나 예산이 남으면 R2
- 방 비우기: 지금 `purgeRoom` RPC 를 그대로 부르되 **성공·실패를 돌려받는** 함수로(`notifyPurge` 는 실패를 삼키므로 못 쓴다). 성공 → 작업 행 지움. 던짐 → `attempts + 1`, 행을 남긴다. `DOC_ROOM` 바인딩이 없으면(테스트·로컬 일부) 비울 것이 없는 것으로 보고 성공 처리 — `notifyPurge` 의 "stub 없으면 아무것도 안 함" 과 같다. 동시에 최대 **6개**(Workers 요청당 동시 연결 6, m5 표의 "Simultaneous outgoing connections")
- 방 비우기를 한 번도 연 적 없는 문서에 불러도 된다 — DO 가 새로 생겨 빈 저장소를 지우고 끝난다. 어느 문서에 DO 저장소가 있는지 D1 이 모르므로 전부 부른다
- R2: `list({ prefix, limit: 1000 })` → 객체가 있으면 그 키들로 `delete` 한 번 → 예산이 남으면 되풀이. `list` 가 0개를 돌려주면: 작업을 만든 지 **1시간 이상**이면 행을 지우고, 아니면 남긴다(5.2 끝의 겹친 올리기 때문). R2 호출이 던지면 `attempts + 1`
- `attempts` 가 **144**(10분 Cron 으로 하루)에 닿는 순간 한 번 `console.error('purge_job_stuck', kind)` — 대상 id·접두사는 로그에 넣지 않는다. 행은 지우지 않고 계속 시도한다
- 두 곳이 동시에 같은 작업을 집어도 괜찮다 — 방 비우기와 R2 지우기는 두 번 해도 결과가 같다

**1,000문서·5,000첨부 계정의 계산** (호출 수는 위 규칙 그대로 센 것, 걸리는 시간은 Cron 간격에서 나온 것. 원격에서 재지 않았다):

| 단계 | 방 호출 | R2 호출 | 남은 방 |
| --- | --- | --- | --- |
| 삭제 요청 `waitUntil` | 15 | 0 | 985 |
| Cron 1~24회 (10분 간격) | 24 × 40 = 960 | 0 (방이 예산을 다 씀) | 25 |
| Cron 25회 (삭제 후 약 4시간 10분) | 25 | `list` 5 + `delete` 5 = 10 (1,000개씩 5번, 예산 남은 15 안) | 0 |
| Cron 26회 (약 4시간 20분) | 0 | 빈 `list` 1 — 작업을 만든 지 1시간이 넘었으므로 행 지움 | — |
| **끝** | | | 삭제 후 약 **4시간 20분** |

- 문서가 10개인 보통 계정은 요청 `waitUntil` 에서 방을 다 비우고, R2 는 첫 Cron 에서 지운 뒤 1시간 유예 후 작업 행까지 사라진다
- 유료 플랜이면 예산을 올려 몇 분으로 줄일 수 있다(상수 두 개). 올리는 판단은 사람 — 11장 Q5
- **D1 에서 이미 지운 문서의 방은 새 연결을 받지 못한다** — `/ws` 는 D1 로 접근을 먼저 본다(`docSocket.ts` `not_found` → 4404). 그래서 정리가 끝나기 전의 방은 "남은 저장소" 일 뿐 다시 열 수 있는 문서가 아니다

### 5.5 Cron 가르기

- `wrangler.jsonc` `triggers.crons` 를 `["0 18 * * *", "*/10 * * * *"]` 로. 이 Worker 의 Cron 은 2개가 된다. 무료 계정 한도 5개(m5) — **같은 Cloudflare 계정의 다른 Worker 가 Cron 을 몇 개 쓰는지는 확인하지 않았다**(9.4 H6)
- `scheduled` 는 `event.cron` 이 정확히 `'*/10 * * * *'` 이면 정리만 `waitUntil` 한 번. **그 밖의 값(매일 Cron, 테스트가 넘기는 빈 객체 포함)이면 지금처럼 첨부 정리·세션 정리 두 개만** — 정리 작업은 넣지 않는다. 그래서 `worker/loginRoutes.test.ts` "F-2033 scheduled 정리" 의 `pending.length === 2` 가 그대로 통과한다(8장)
- 두 문자열은 `worker/index.ts` 상수로 둔다. `wrangler.jsonc` 문자열과 글자까지 같아야 한다 — 다르면 정리가 영영 돌지 않는다(P5 가 두 값을 대조한다: 테스트가 `wrangler.jsonc` 를 읽어 `crons` 배열에 상수가 있는지 본다)
- 비어 있을 때 10분 Cron 한 번 = D1 읽기 2문장(방 작업·R2 작업 각 0행). 하루 144번

| `DELETE` 500·그 밖 | `계정을 삭제하지 못했습니다. 잠시 뒤 다시 시도해 주세요.` |

- 숫자는 `formatCount`(천 단위 쉼표)로 쓴다. `formatMegabytes` 는 계정 메뉴 사용량 줄과 같은 함수
- 초점: 열 때 `취소`(D-1 과 같이 안전한 쪽). `confirm` 이 되면 입력칸. 닫으면 `계정 삭제…` 버튼으로 되돌린다. 6.5 로 저절로 열린 경우(설정 없이 열림) 닫으면 `document.body`
- 막힌 계정(`blocked`)이어도 똑같이 열리고 지울 수 있다(3.4)

### 6.4 "안 올린 변경" 판정

- App 이 D-15 를 열 때 한 번 계산해 넘긴다: 이 계정의 `md-remote` outbox 개수 > 0 **또는** `md-yjs` 의 안 보낸 문서(`unsyncedDocIds`)가 1개 이상. 둘 중 하나를 읽지 못하면(저장소 열기 실패) 안내를 **보인다** — 모르는 채 조용히 사라지는 쪽보다 안내가 한 줄 많은 쪽이 낫다
- 삭제 전에 올리려고 시도하지 않는다(`onBeforeNavigate` 를 부르지 않는다). 곧 지울 서버에 올리는 것은 쓰기 한도만 쓴다

### 6.5 다시 열기 표지 — sessionStorage `md.accountDelete`

| 값 (JSON 문자열) | 누가 쓰나 | 뜻 |
| --- | --- | --- |
| `{"step":"resume","userId":"…","at":1790000000000}` | D-15 `다시 로그인…` 직전 | 돌아오면 D-15 를 다시 연다 |
| `{"step":"done"}` | 삭제 성공, 주소 이동 직전 | 새로 읽은 뒤 N-1 `계정을 삭제했습니다.` |

- sessionStorage 인 이유: 같은 탭에서만 이어져야 한다. OAuth 로 다른 사이트를 다녀와도 같은 탭이면 남는다. 키 이름에 제품명이 없다(불변조건). `prefs.ts` 는 localStorage 전용이라 거치지 않는다 — `lockSession.ts` 가 sessionStorage 를 직접 쓰는 것과 같은 방식
- 부팅 판정(순수 함수로, C2): 계정 상태가 처음 `in` 으로 정해진 뒤 한 번 읽고 **읽은 즉시 지운다.**
  - `resume` + 같은 `userId` + `now − at < 10분`(`ACCOUNT_DELETE_FRESH_MS`) → D-15 를 설정 없이 연다
  - `resume` + 다른 `userId` → 열지 않고 6.6 경고
  - `resume` + 10분 이상 지남 → 아무것도 안 함
  - `done` → N-1 info `계정을 삭제했습니다.` (계정 상태와 무관 — 삭제 뒤엔 `out` 이다)
  - JSON 이 아니거나 모양이 틀림 → 아무것도 안 함
- 계정 상태가 `offline` 이면 `resume` 을 지우지 않고 다음 `in` 까지 기다린다 — 연결이 돌아오면 이어진다. `out` 이면(다시 로그인이 실패하고 세션도 없던 경우) 지운다

### 6.6 N-1 문구

| 때 | 종류 | 문구 |
| --- | --- | --- |
| 삭제 후 새로 읽음 | `info` | `계정을 삭제했습니다.` |
| 다른 계정으로 다시 로그인해 돌아옴 | `warn` | `다른 계정으로 로그인해 계정 삭제 창을 열지 않았습니다. 지우려던 계정으로 다시 로그인하세요.` |

## 7. 이 기기 정리 — `DELETE` 204 뒤

### 7.1 무엇을

| 저장소 | 지우는 것 | 남기는 것 | 함수 |
| --- | --- | --- | --- |
| IndexedDB `md-remote` | `docs`·`folders`·`outbox`·`attachments` 에서 `userId = 나` 인 행 전부 | 다른 계정의 행 | `remoteCache.ts` 새 독립 함수 |
| IndexedDB `md-yjs` | `updates`(`byDoc` 첫 칸 = 나)·`meta`(`byUser` = 나) 행 전부 | 다른 계정의 행 | `yjsStore.ts` 새 독립 함수 |
| IndexedDB `md-docs` `e2ee` 스토어 | 행 `account:{나}` | 행 `local`(로컬 금고), 문서·폴더·첨부 스토어 전부 | 있는 `deleteE2eeRow` |
| localStorage | `md.account` → `''`, `md.lastDocId` → `''` | 그 밖의 `md.*`(화면 설정·`md.localMigrated` 등) | `setPref` |
| 이 탭의 메모리 금고 | 로그아웃과 같은 잠금 신호(`onAccountLoggedOut` → `broadcastLogoutLock`) | — | 있는 것 |

- `md.lastDocId` 를 비우는 이유: 로그아웃 상태 부팅이 지운 서버 문서 id 를 찾다 빈 결과로 떨어지는 대신 곧바로 홈으로 간다
- `md.localMigrated` 는 그대로 둔다. 같은 이메일로 다시 가입하면 새 계정 id 라서 로컬 문서 이관(F-208)이 다시 돈다 — 새 계정이 받는 동작과 같다
- IndexedDB 두 DB 를 통째로 지우지 않는 이유: 한 브라우저에 여러 계정이 로그인한 적이 있으면 다른 계정의 캐시가 같이 사라진다(결정 4 "계정에 딸린")

### 7.2 순서와 실패

1. `DELETE` 204 를 받는다
2. 이 탭의 금고 잠금 신호
3. 7.1 의 IndexedDB 세 가지를 **함께** 시작하고, 모두 끝나거나 **3,000ms** 가 지나면 다음으로. 하나가 던져도 나머지는 계속한다(`console.error` 한 줄씩)
4. localStorage 두 값
5. sessionStorage `md.accountDelete` = `{"step":"done"}`
6. `location.replace('/?app=1')` (로그아웃 뒤 주소 `AFTER_LOGOUT_URL` 과 같은 값)

- 서버는 이미 지웠으므로 3번이 실패하거나 시간을 넘겨도 되돌리지 않는다. 남은 행은 지운 계정 id 에 묶여 앱이 다시 읽을 길이 없는 찌꺼기다
- 3,000ms 인 이유: 다른 탭이 같은 DB 를 오래 붙잡으면 기다림이 끝나지 않을 수 있다. 사용자는 이미 서버 삭제가 끝난 화면에 머물러 있다
- **같은 브라우저의 다른 탭**은 알리지 않는다 — 로그아웃도 알리지 않는다(금고 잠금만 전한다). 그 탭은 다음 서버 요청에서 401 을 받고 지금 401 처리를 따른다. 그 탭이 그 사이 `md-remote` 에 다시 쓰는 행은 위 찌꺼기와 같다
- **다른 기기**의 `md-remote`·`md-yjs` 는 지울 수 없다. 그 기기가 다음에 `/api/me` 를 부르면 401 → 로그아웃 상태가 되고, 캐시는 지운 계정 id 에 묶인 채 남는다. D-15 안내 4 와 방침 10절(10장)에 적는다

## 11. 열린 질문 / 사람 결정 필요

### Q1. 최근 로그인 기준 — **사람 결정 필요. 기본값: 10분**

| 안 | 효과 |
| --- | --- |
| **10분 (기본)** | 자리를 비운 기기에서 거의 늘 다시 로그인이 필요하다. 다시 로그인 → 확인까지 1분 안팎이라 불편은 한 번의 왕복 |
| 5분 | 더 엄격. 돌아와서 안내를 읽다가 넘기면 한 번 더 왕복 |
| 1시간 | 로그인 직후 한동안은 바로 지울 수 있다. 공용 PC 에서 로그인해 둔 채 떠난 경우를 덜 막는다 |
| 1일 (better-auth 기본) | 매일 쓰는 사람은 거의 늘 통과 — 사실상 확인이 없다 |

바꾸면: `ACCOUNT_DELETE_FRESH_MS` 한 값, reauth 문구의 `10분`, 표지 유효 시간(같은 상수), W6·C2 의 경계값

### Q2. 확인 입력 — **기본값: `삭제` 를 입력해야 버튼이 켜진다**

사용자는 이메일 입력을 요구하지 않았다. 기본값은 D-13(금고 초기화)과 같은 "낱말 입력" 이다 — 실수로 누르는 것을 막을 뿐 본인 확인은 아니다(본인 확인은 Q1). 다른 안: ① 입력 없음 — 버튼 한 번. 되돌릴 수 없는 동작에 한 번 누름뿐이라 권하지 않는다 ② 이메일 전체 입력 — 긴 이메일은 치기 번거롭고 본인 확인 효과는 Q1 과 겹친다. 바꾸면 `ACCOUNT_DELETE_CONFIRM_WORD`·입력 라벨·E3 만 바뀐다

### Q3. 다른 사람에게 **받은** 초대 행 — **사람 결정 필요. 기본값: 지운다**

초대 행(`grants.grantee_email`)은 초대한 사람이 만든 기록이다(방침 5절 "초대 기록 — 사용자가 그 사람의 권한을 지울 때까지" 는 초대한 쪽 기준).
- **지움(기본)**: 내 다른 기기의 열린 소켓이 60초 점검에서 닫힌다. 같은 이메일로 다시 가입해도 옛 초대가 살아나지 않는다. 대신 초대한 사람의 공유 목록에서 내 이메일이 말없이 빠진다
- 남김: 초대한 사람의 설정을 건드리지 않는다. 대신 ① 내 다른 기기에서 그 사람 문서를 열어 둔 소켓이 끊기지 않는다 — 소켓은 연결할 때만 세션을 보고, 60초 점검은 이메일 초대만 본다(`revalidateConnections`). 이를 막으려면 점검에 "사용자 행이 있는가" 를 더해야 한다(`docRoomCore.ts` 변경, 이 명세 소유 밖) ② 다시 가입하면 옛 초대로 그 문서가 다시 열린다
바꾸면: 5.2 7번 문장을 빼고, D-15 안내 1·방침 초안에서 "받은 초대도 끊깁니다" 를 뺀다. ①을 막는 변경이 따로 필요하다

### Q4. 막힌 계정의 삭제와 기록 — **사람 결정 필요. 기본값: 막힌 계정도 지울 수 있고, 기록을 남기지 않는다**

- **기본**: 막힌 계정이 지우고 같은 이메일로 다시 가입하면 막히지 않은 새 계정이 된다. 받아들이는 이유 — 막힘을 피하려는 사람은 새 이메일(새 Google 계정)로도 같은 일을 한다. 이메일로 묶는 기록은 그 우회를 막지 못하고, 하루 가입 20명 관문(F-2028)이 대량 재가입을 따로 막는다. 방침 81행 "계정 삭제 요청을 처리할 때까지" 와도 맞는다
- 다른 안 ① 막힌 계정은 삭제 버튼을 막고 연락처로만 — 방침 9절 "언제든지 … 지우고" 와 부딪친다 ② 지우되 `이메일 해시·막힌 시각` 을 N일 남기고 재가입 때 다시 막는다 — 표 하나·가입 관문 변경(`authServer.ts` `validateUserInfo`)이 더해지고, 방침 3·5절에 "삭제 뒤에도 남는 항목" 을 새로 적어야 한다
바꾸면: ①은 3.4·6.3·W4 가, ②는 5.1 `users` 행·새 마이그레이션·방침 문장이 바뀐다

### Q5. 정리 속도 — **기본값: 10분 Cron, 호출 예산 요청 15·Cron 40**

무료 플랜 호출당 50개(m5) 안에 들게 잡은 값이다. 1,000문서·5,000첨부 계정이 끝까지 지워지는 데 약 4시간 20분(5.4 표). 다른 안: ① 매일 Cron 에만 붙이기 — Cron 수는 그대로지만 같은 계정이 25일 넘게 걸린다 ② Workers 유료($5/월) — 호출당 하위 요청 10,000·CPU 30초라 예산을 수백으로 올려 몇 분 안에 끝난다. 비용 결정은 사람(product.md Q42). 방침 초안의 "보통 몇 시간 안에" 는 기본값 기준이다

### Q6. 방침 시행일 — **사람 결정 필요. 기본값: 기능 배포일에 고친 방침을 올리고, 시행일은 그날 + 7일**

방침 14절은 "고칠 때 시행일 7일 전부터 알린다" 이다. 이 변경은 사용자에게 유리한 쪽(삭제 수단이 늘어남)이라 30일 규정은 해당하지 않는다고 본다. 그 7일 동안 방침 본문(옛 83행 "화면에서 지우는 기능이 없습니다")과 실제 앱이 어긋난다. 다른 안: ① 방침을 먼저 올려 7일 뒤를 시행일로 잡고, 기능은 그 시행일에 배포 ② 새 판을 곧바로 시행 — 14절 문장과 어긋난다. 어느 쪽이든 체인지로그에 적는다

### Q7. 진입점 — 기본값: 설정 `계정` 탭만

main 전달이 "설정 계정 탭" 이라 그대로 따랐다. 계정 메뉴(상단바)에 `계정 삭제…` 를 두면 한 번에 닿지만, 로그아웃 옆에 되돌릴 수 없는 동작이 놓인다. 바꾸면 `AccountMenu.tsx` 가 소유에 들어오고 `e2e/account.spec.js` 메뉴 항목 목록 단언을 고친다

### Q8. 다시 로그인 실패 뒤 안내 — 기본값: 오류 문구를 잃어도 받아들인다 (4.3 끝)

실패·취소하면 `/login?…&error=…` 이 되는데, 세션이 살아 있으면 곧바로 앱으로 돌아가 D-15 reauth 상태가 다시 보인다. 오류 문구를 보이려면 `loginReturn`·`handleLoginStart`·폼 숨은 필드에 `reauth` 를 실어 `failureUrl` 까지 이어야 한다 — 로그인 경로 세 곳 변경. 사용자가 원하면 이 명세에 넣는다

### 기본값으로 정한 것 (한 줄씩)

- better-auth `deleteUser`·`freshAge` 옵션을 쓰지 않는다(m7, 4.2)
- 삭제는 D1 batch 하나(15문장), 표지 열 없음(5.2)
- DO·R2 는 일반 이름 `purge_jobs` 표로 정리(5.3)
- 방 먼저, 최근 고친 문서부터(5.4)
- 쓰기 관문을 걸지 않는다(3.4)
- 돌아오는 길은 sessionStorage 표지, 새 해시 없음(4.3)
- 다른 계정으로 돌아오면 D-15 를 열지 않는다(4.3)
- IndexedDB 는 계정별 행만, DB 통째 삭제 없음(7.1)
- `md.localMigrated` 는 남긴다(7.1)
- 같은 브라우저 다른 탭에 알리지 않는다(7.2)
