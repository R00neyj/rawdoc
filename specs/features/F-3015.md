## 2. 경로 규칙 — `src/lib/githubPath.ts`

```ts
export const REPO_PATH_MAX = 1024
export function resolveRepoPath(mdPath: string, url: string): string | null
export function repoImagePaths(content: string, mdPath: string): Set<string>
export function isRepoMdPath(path: unknown): path is string
export function isRepoDir(dir: unknown): dir is string
export function isRepoFullName(repo: unknown): repo is string
export function isBranchName(branch: unknown): branch is string
export function githubBlobUrl(repo: string, branch: string, path: string): string
```

**저장소 경로의 공통 꼴**: `/` 로 나눈 세그먼트가 하나 이상, 빈 세그먼트·`.`·`..` 없음, `\`·제어 문자(U+0000–U+001F, U+007F) 없음, 앞뒤 `/` 없음, 길이 `REPO_PATH_MAX` 이하

- `resolveRepoPath`: F-3013 3.5 그대로, 순서를 고정한다 — ① 첫 `?`·`#` 부터 뗀다 ② `decodeURIComponent` 한 번(던지면 null) ③ 빈 글자, 스킴(`^[A-Za-z][A-Za-z0-9+.-]*:`), `//` 시작, `\`·제어 문자 → null ④ `/` 로 시작하면 저장소 맨 위, 아니면 `mdPath` 의 폴더가 기준 ⑤ 세그먼트를 차례로 — `.` 은 버리고 `..` 은 하나 올라가며, 맨 위보다 위로 가면 null. 빈 세그먼트(`a//b`, 끝의 `/`)는 null ⑥ 결과가 공통 꼴이 아니면 null
- `repoImagePaths`: 본문 전체에서 마크다운 `![…](url …)`(url 은 `<…>` 또는 공백·괄호 없는 글자, `parseImageLine` 의 url 꼴과 같음)와 HTML `<img … src=…>`(큰따옴표·작은따옴표·따옴표 없음, 대소문자 무시)를 줄 위치와 상관없이 훑는다. `attachments/{16hex}.{png|jpg|gif|webp}` 와 정확히 같은 url 은 넣지 않는다 — 리졸버가 불리지 않는 꼴이다(r10). 나머지는 `resolveRepoPath(mdPath, url)` 가 null 이 아닌 것만
- `isRepoMdPath`: 공통 꼴 + 끝이 `.md`·`.markdown`(대소문자 무시)
- `isRepoDir`: 빈 글자(저장소 맨 위) 또는 공통 꼴
- `isRepoFullName`: `^[A-Za-z0-9][A-Za-z0-9-]{0,38}/[A-Za-z0-9._-]{1,100}$` 이고 이름이 `.`·`..` 가 아님
- `isBranchName`: 1–255자, 공백·제어 문자·`~^:?*[\` 없음, `..`·`@{`·`//` 없음, `/`·`.` 로 시작하거나 끝나지 않음, `.lock` 으로 끝나지 않음
- `githubBlobUrl`: `https://github.com/{repo}/blob/{branch}/{path}`, branch·path 는 세그먼트마다 `encodeURIComponent` 하고 `/` 는 그대로
- GitHub API 주소를 만들 때(서버)도 같은 규칙: 경로는 세그먼트마다 `encodeURIComponent`, 브랜치는 `?ref=` 에 `encodeURIComponent`. 사용자 글자가 주소의 다른 자리로 새지 않게 한다

## 3. 서버

### 3.1 공통 순서

```ts
// worker/githubSettings.ts — 설정 행이 켜져 있고 loadGithubConfig 가 null 이 아닐 때만
export function loadEnabledGithub(env: Env): Promise<{ config: GithubConfig; settings: GithubSettings } | null>
```

모든 라우트: `requireUser`(401) → `loadEnabledGithub` 가 null 이면 503 `{ error: 'github_disabled' }`(F-3013 3.9) → 입력 검사 400 `{ error: 'invalid', field }` → (문서 라우트) 권한 → (횟수 라우트) `checkGithubQuota` 429 → GitHub 호출 → 성공한 뒤에만 `countGithubUse`

- `GithubFailure` 는 `githubFailureResponse` 로 그대로 낸다(409 `github_reconnect`·503 `github_rate_limited`·403 `github_forbidden`·404 `github_not_found`·502 `github_unavailable`). `githubFetch` 가 넘긴 그 밖 4xx `Response` 와 모양이 틀린 2xx 몸통(필드 없음·타입 다름)은 502 `github_unavailable` + `console.error('github_unexpected', 라우트 이름, status)`
- 모든 응답 `Cache-Control: no-store`

### 3.2 고르기·파일 — `worker/githubRepos.ts`

| 라우트 | 입력 | GitHub 호출 | 응답 | 횟수 |
| --- | --- | --- | --- | --- |
| `GET /api/github/repos` | — | `GET /user/installations?per_page=100` 1번, 이어 설치마다 `GET /user/installations/{id}/repositories?per_page=100&page=n` | `GithubRepoList` | — |
| `GET /api/github/branches?repo=` | `isRepoFullName` | `GET /repos/{repo}/branches?per_page=100` 1번 | `GithubBranchList` | — |
| `GET /api/github/tree?repo=&branch=&dir=` | 셋 다 검사, `dir` 없으면 `''` | `GET /repos/{repo}/contents/{dir}?ref={branch}` 1번 (`dir` 이 빈 글자면 `/contents`) | `GithubTree` | — |
| `POST /api/github/file` | `{ repo, branch, path }`, `isRepoMdPath`. 몸통 상한 4,096 B(`readJsonLimited`) | `GET /repos/{repo}/contents/{path}?ref={branch}` 1번 | `GithubFile` | 1 |

- **repos**: 저장소 항목은 `id`·`full_name`·`default_branch`·`private`·`archived`·`permissions.push` 에서 만든다. `canWrite` = `permissions.push === true && archived !== true`. 같은 `id` 는 하나만. 모은 뒤 `fullName` 의 소문자 사전순으로 정렬. 저장소 목록 호출은 **최대 10번**, 모은 저장소가 **300개**면 멈춘다. 다음 쪽은 응답 `Link` 머리에 `rel="next"` 가 있을 때만 부른다. 설치가 100개를 넘거나(설치 응답에 `rel="next"`), 10번·300개에서 멈췄는데 남은 쪽·설치가 있으면 `truncated: true`. 설치가 0개면 `{ repos: [], truncated: false }`
  - 하위 요청 상한(w1 외부 50): GitHub 호출 최대 11번. `githubFetch` 한 번이 토큰 갱신·401 재시도로 최대 4번 바깥으로 나가지만, 갱신 뒤 다시 401 이면 `github_reconnect` 로 끝나므로 한 요청의 바깥 호출은 11 + 갱신 2 + 재시도 1 이하
- **branches**: 이름만. `rel="next"` 가 있으면 `truncated: true`. 기본 브랜치가 첫 100개에 없을 수 있다 — 화면(F-2128)이 `defaultBranch` 를 목록 앞에 끼운다
- **tree**: 응답이 배열이 아니면(그 경로가 파일) 404 `github_not_found`. `type` 이 `dir` 인 것과, `type` 이 `file` 이고 이름이 `.md`·`.markdown`(대소문자 무시)으로 끝나는 것만. `symlink`·`submodule` 은 뺀다. 정렬: 폴더 먼저, 그 안에서 `name` 의 코드 단위 순. 폴더 `size` 는 0. GitHub 배열 길이가 1,000 이상이면 `truncated: true` (Contents API 의 폴더 1,000개 상한 — 7장 확인 못 한 것 1)
- **file**:
  - 응답이 객체가 아니거나 `type !== 'file'` → 404 `github_not_found`
  - `size > MAX_CONTENT_BYTES + 3`(BOM 몫) → 413 `{ error: 'too_large', limit: MAX_CONTENT_BYTES }` (`badBody` 와 같은 모양)
  - `encoding !== 'base64'` 이면(GitHub 가 큰 파일 내용을 싣지 않은 경우) 같은 413. **raw 형식으로 다시 받지 않는다** — 받으면 Worker 가 base64 를 만들어야 하고(F-3013 m3), 1,000,003 B 이하인데 GitHub 가 내용을 빼는 경우는 BOM 붙은 상한 근처 몇 바이트뿐이라 다시 받을 값이 없다
  - `content` 는 GitHub 글자를 **그대로**(60자마다 `\n` 포함) 넘긴다. 받는 쪽은 공백을 지우고 base64 를 푼다. 지우기를 서버에서 하지 않는 것은 CPU 를 아끼기 위함이다(r6)
  - `linkedDocId`: `github_links` 에서 `owner_id = 나`, `repo`·`branch`·`path` 가 같은 행의 `doc_id`, 없으면 null. F-2128 이 새 문서를 만들기 전에 "이미 연결된 문서" 로 보낼 수 있게. D1 읽기 1번
  - 이 응답은 GitHub `sha`(40자 16진수가 아니면 502)와 `size` 만 쓴다. GitHub 응답의 `download_url`(비공개 저장소면 임시 토큰이 붙는다)은 브라우저로 넘기지 않는다

### 3.3 연결 — `worker/githubLinks.ts`

| 라우트 | 누가 | 몸통 → 응답 | GitHub 호출 | 횟수 |
| --- | --- | --- | --- | --- |
| `GET /api/docs/:id/github` | 주인·편집자 | → `GithubLink` / 연결 없으면 404 `not_found` | 0 | — |
| `PUT /api/docs/:id/github` | 주인 | `GithubLinkPut` → 200 `GithubLink` | `GET /repos/{repo}` 1번 | — |
| `DELETE /api/docs/:id/github` | 주인 | → 204 (연결이 없어도 204) | 0 | — |
| `POST /api/docs/:id/github/pull` | 주인 | → `GithubPulled` / 연결 없으면 404 `not_found` | Contents 1번 (3.2 file 과 같은 판정) | 1 |
| `POST /api/docs/:id/github/synced` | 주인 | `GithubSyncedBody` → 204 / 연결 없으면 404 `not_found` | 0 | — |

- **권한**: `getDocAccess` 가 null → 404 `not_found`. 주인 라우트는 `access.doc.owner_id !== user.id` → 403 `forbidden`(`handleSetDocE2ee` 처럼 행의 주인으로 본다 — 막힌 주인은 이미 쓰기 관문이 403). GET 은 `access.role` 이 `view` 이고 `blocked` 가 아니면 403 `forbidden`(F-3013 Q6)
- **PUT** 순서: 몸통(상한 4,096 B) `repo`(`isRepoFullName`)·`branch`(`isBranchName`)·`path`(`isRepoMdPath`)·`sha`(null 또는 40자 소문자 16진수)·`bom`(boolean) → 권한 → 금고(`e2ee_key` 있음) 409 `{ error: 'e2ee' }` → `GET /repos/{repo}` → `permissions.push !== true` 또는 `archived` 면 403 `github_forbidden` → 다른 문서가 같은 `(owner_id, repo_id, branch, path)` 면 409 `github_target_taken` → 쓰기
  - **`repo_id`·`repo` 는 GitHub 응답의 `id`·`full_name` 으로 저장한다.** 클라이언트가 보낸 `repoId` 를 믿지 않는다 — F-3017 프록시 캐시 열쇠가 `repo_id` 라, 남의 저장소 id 를 적은 연결로 그 캐시를 더럽힐 수 있다(F-3013 3.4 계약 변경, Q1)
  - 쓰기는 한 batch: ① 대상(`repo_id`·`branch`·`path`) 이 바뀌는 다시 연결이면 그 문서 `github_images` 삭제 ② r5 의 조건부 UPSERT — `remote_sha = sha`, `remote_bom = bom`, `synced_at = sha ? now : null`, `created_at` 은 처음 값 유지 ③ `dayUsageStatement`. ②가 0행이면 행을 다시 읽어 금고면 409 `e2ee`, 문서가 없으면 404. UNIQUE 오류도 409 `github_target_taken`(`githubAuth.ts` 의 `/UNIQUE/i` 선례)
  - `sha`·`bom` 은 믿는다(F-3013 3.4). 브랜치·경로가 GitHub 에 있는지는 확인하지 않는다 — 없으면 당기기가 404, 푸시가 처음 만든다
- **DELETE**: 한 batch 로 `github_images` → `github_links`(그 문서) → `dayUsageStatement`. F-3013 Q4 그대로
- **pull**: 연결 행의 `repo`·`branch`·`path` 로만 부른다(몸통 무시). 응답은 3.2 file 과 같은 판정·같은 413, `linkedDocId` 없음. 연결 행을 바꾸지 않는다 — `remote_sha` 는 합치기를 적용한 뒤 `synced` 가 바꾼다. `imageSources` 는 F-3017 이 이 응답에 더한다
- **synced**: `sha`(40자 소문자 16진수)·`bom`(boolean) → `UPDATE github_links SET remote_sha, remote_bom, synced_at = now WHERE doc_id = ? AND owner_id = ?` + `dayUsageStatement`. 0행이면 404
- **`remote_sha` 가 바뀌는 때 (전부)**: PUT(보낸 `sha`), `synced`(합치기 적용 뒤·"같습니다" 뒤), F-3016 푸시 성공. 그 밖에는 바뀌지 않는다
- 꺼짐(503)은 GET·DELETE 에도 적용된다(F-3013 3.9). 화면은 `status.enabled` 가 false 면 이 라우트들을 부르지 않는다(F-3013 4.1)

### 3.4 금고 두 방향 (F-3013 3.6)

- 연결 쪽: PUT 의 금고 검사(409 `e2ee`)와 조건부 UPSERT(r5). 검사 뒤 UPSERT 전에 금고로 옮겨져도 0행이 되어 409 `e2ee`
- 금고 쪽: `handleSetDocE2ee` 에서 `moving` 이고 `e2ee_doc` 검사 바로 뒤(r9 순서의 첫 409 다음, `no_vault` 앞)에 `SELECT 1 FROM github_links WHERE doc_id = ?` 가 있으면 409 `{ error: 'github_linked' }`. batch 전이라 하루 카운터가 오르지 않는다. 금고에서 빼기(`e2eeKey === null`)에는 검사가 없다
- 남는 틈: 금고 쪽 검사를 지난 뒤 batch 전에 연결 PUT 이 끝나면 연결된 금고 문서가 생긴다. 같은 주인이 두 탭에서 몇 ms 안에 두 동작을 해야 한다. 받아들인다(Q2)

## 4. 문서 삭제와 FK (r3·r4)

- `deleteDocRows`: `DELETE FROM github_images WHERE doc_id = ?`, `DELETE FROM github_links WHERE doc_id = ?` 를 `DELETE FROM docs` **앞**에(`share_link_docs` 줄 옆)
- `deleteFolderContents`(`contents === 'delete-all'`): 지울 문서 id 묶음(`BATCH_ID_LIMIT`)마다 `DELETE FROM github_images WHERE doc_id IN (…)`, `DELETE FROM github_links WHERE doc_id IN (…)` 를 `share_link_docs` 묶음 줄과 같은 자리에 — `DELETE FROM docs` 앞
- 계정 삭제는 F-3014 7장이 이미 했다(`github_images`·`github_links` → … → `docs`). 고치지 않는다
- 연결된 문서를 지워도 원격 파일은 그대로(F-3013 1.2 "지우기의 원격 반영" 안 함)

## 7. 확인 못 한 것 (구현 때 H1 로 확인)
1. Contents API 폴더 목록 상한 1,000개 — GitHub 문서에서 기억한 값이고 이번에 받아 읽지 않았다. 틀려도 `truncated` 판정만 덜 맞을 뿐 동작은 같다
2. GitHub 가 내용을 JSON 에 싣는 상한("1MB")이 1,000,000 B 인지 1,048,576 B 인지. 어느 쪽이든 3.2 의 `encoding` 검사가 413 으로 받는다
3. 사용자 토큰의 `GET /repos/{repo}` 응답 `permissions.push` 가 앱 설치 범위까지 반영하는지. 설치 안 된 공개 저장소면 `push: true` 로 연결될 수 있고, 그때는 F-3016 푸시가 403·404 로 막힌다(보안 문제는 아님 — 토큰이 설치 범위를 넘지 못한다)
4. r6 은 Node 수치. workerd CPU 10ms 안에 드는지는 H1 에서 1MB 파일로 확인

## 10. 열린 질문

### Q1. PUT 이 저장소를 GitHub 에서 확인하나 — **기본값: 확인한다 (`GET /repos/{repo}` 1번, 클라이언트 `repoId` 무시)**
- 이유: `repo_id` 는 연결 대상 유일성과 F-3017 프록시 캐시 열쇠다. 클라이언트 값을 믿으면 주인이 남의 저장소 id 와 자기 저장소 이름을 섞어 남의 공개 문서 그림 캐시를 바꿔 칠 수 있다. 쓰기 권한(`canWrite`)도 서버가 한 번 더 본다
- 다른 안(F-3013 원안, 믿는다): GitHub 호출 0, PUT 이 빨라진다. 대신 F-3017 캐시 열쇠를 `repo` 글자로 바꾸거나 프록시가 매번 저장소를 확인해야 한다

### Q2. 금고 옮기기와 연결 PUT 의 틈 — **기본값: 받아들인다 (금고 쪽은 검사만)**
- 이유: 같은 주인이 두 탭에서 몇 ms 안에 해야 생기고, 생겨도 주인 자신의 저장소로 주인이 푸시할 때만 평문이 나간다. 막으려면 `setDocE2eeStatements` 의 첫 문장(F-401·F-502·F-2057 이 문장 순서·`changes()` 에 기대는 batch)에 조건을 넣어야 한다
- 다른 안: `MOVE_ROW_SQL` 에 `AND NOT EXISTS (SELECT 1 FROM github_links WHERE doc_id = ?)` 를 붙이고, 0행일 때 연결이 있으면 409 `github_linked`, 없으면 지금처럼 `conflict`. `e2eeDocs.test` C9·C10 의 바인딩 기대가 바뀐다
