# F-4018 심사 전용 비밀번호 로그인

작성일: 2026-11-04
상태: 승인됨(2026-11-04 사용자, Q1·Q2 9장). F-4008 11장 Q3 의 후속. 2026-11-04 OpenAI 심사 반려(시험 GitHub 계정이 새 기기 이메일 확인에 막힘, 2FA 없이는 끌 수 없다 — [GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/verifying-new-devices-when-signing-in)). 사용자 결정 7가지(이메일 1개·접힌 영역·병기·켜 둠·OAuth 이어가기·시드 안 함·흐름도)는 그대로. 새 의존 없음

## 근거 (better-auth 1.7.10·`@better-auth/oauth-provider` 1.7.10, 이름으로 찾는다)
- `signInEmail`(`api/routes/sign-in.mjs`)은 `provider_id='credential'`·`account_id = user.id`·`password` 가 빈 값이 아닌 `auth_accounts` 행을 요구하고 `ctx.context.password.verify` 로 비교한다. `validateUserInfo` 는 부르지 않는다 → `emailVerified` 검사·가입 관문(F-2024)은 이 길에 걸리지 않는다. `internalAdapter.createUser` 는 엔드포인트 문맥 밖이면 `validation_context_missing` 으로 던진다
- 플러그인 before 훅은 본문에 `oauth_query` 가 있으면 어느 엔드포인트든 검증해 담고, after 훅은 응답이 세션 쿠키를 심으면 authorize 를 다시 돌린다. `Sec-Fetch-Mode: navigate` 가 아니면 `{redirect:true,url}` JSON(`handleRedirect`), 동의 전이면 url = 상대 경로 `/oauth/consent?{서명 질의}`(`redirectWithPromptCode`). `dispatch.mjs` 는 after 훅 반환값으로 응답을 바꾼다 — F-4010 `handleConsentSubmit` 의 안쪽 `Request` 와 같은 길
- `emailAndPassword` 를 켜면 생기는 `sign-in/email`·`sign-up/email`·`request-password-reset`·`reset-password`·`change-password`·`verify-password`·`change-email` 은 모두 `worker/index.ts` `AUTH_ROUTES` 밖이라 밖에서 404. `disableSignUp` 은 `sign-up/email` 을 안쪽에서도 막는다
- `isAllowedOrigin` 이 Origin 없는·다른 출처 `/api/` POST 를 403. `/login` CSP `form-action 'self' …`(지금 report-only)가 같은 출처 POST 를 덮는다. 단, 이미 동의한 앱이면 303 이 앱 `redirect_uri` 로 바로 간다(F-4010 A4) → `/login` OAuth 갈래에도 동의 화면의 `formTarget` 이 필요하다
- `ctx.context.password` 를 쓰는 곳은 코어 이메일·비밀번호 라우트와 우리가 쓰지 않는 플러그인(admin·username·phone-number·email-otp·two-factor)뿐 — `@better-auth/oauth-provider` 는 쓰지 않는다(grep)

## 2. 결정
- **경로: better-auth `emailAndPassword` + 우리 핸들러가 안쪽 `Request` 로 부름.** 세션 쿠키와 OAuth 이어가기(after 훅)를 플러그인이 그대로 해 준다. 버린 안: 자체 세션 생성 — `createSession`·`setSessionCookie` 를 엔드포인트 밖에서 부르고 authorize 이어가기(`prompt=login` 제거 등)를 우리가 다시 짜야 한다
- 옵션: `emailAndPassword: { enabled: true, disableSignUp: true, password: { hash, verify } }`. `verify({hash, password})` 는 `hash === 'worker-secret'` 이고 `verifyReviewPassword(env, password)` 일 때만 참(다른 행은 늘 거짓), `hash` 는 SHA-256 hex. **자격 증명의 원본은 Worker 비밀뿐**, D1 `password` 열에는 표지 `'worker-secret'` 만 둔다(비밀을 바꿔도 D1 은 따라갈 것이 없다)
- **비밀**(선택, `secrets.required` 밖, `openaiChallenge.ts` 의 `'X' in env` 처럼 읽음): `REVIEW_LOGIN_EMAIL`, `REVIEW_LOGIN_PASSWORD_HASH`. `reviewLoginConfig` 는 이메일이 trim 뒤 비지 않고 해시가 `/^[0-9a-f]{64}$/` 일 때만 값을 주고, 아니면 null = 기능 꺼짐(형식만 틀리면 `console.error('review_login_misconfigured')`)
- **해시: 평문이 아닌 SHA-256 hex.** 비밀번호는 사람이 고르지 않고 32바이트 난수(base64url 43자)라 느린 KDF 가 필요 없다(`apiTokens.ts` `sha256Hex` 선례). 비교는 `constantTimeEqual`(길이가 같은 바이트 XOR 누적, node 테스트에서도 돈다). 만드는 명령(평문은 비밀번호 관리자에, 해시만 비밀에):
  `node -e "const c=require('crypto'),p=c.randomBytes(32).toString('base64url');console.log(p);console.log(c.createHash('sha256').update(p).digest('hex'))"`
- **`POST /api/login/password`** 순서(Origin 관문은 라우터가 먼저):
  1. 기능 꺼짐 → 404 `not_found`
  2. `handleLoginStart` 와 같은 4,096B·form-urlencoded 검사, 어긋나면 303 `…error=bad_request`. `oauth_query` 가 있고 `isLiveOAuthQuery` 거짓 → 303 `/oauth/error?error=request_expired`
  3. `LOGIN_LIMITER.limit({ key: 'login-pw:' + (CF-Connecting-IP ?? 'unknown') })` 실패·바인딩 없음·던짐 → 303 `…error=too_many_attempts`(닫힌 쪽으로 실패 — 쓰기 관문과 반대)
  4. **모든 요청에서** 비밀번호 해시를 비교하고, 이메일(trim·소문자)과 비밀번호가 둘 다 맞을 때만 다음으로. 아니면 303 `…error=invalid_credentials` — 두 실패가 D1 을 거치지 않는 같은 길이라 응답도 시간도 같다
  5. `ensureReviewAccount` → 안쪽 `Request`(`{BETTER_AUTH_URL}/api/auth/sign-in/email`, JSON `{email, password, oauth_query?}`, `Origin` = `BETTER_AUTH_URL` 출처, `Accept: application/json`, 쿠키 없음)를 `getAuth(env).handler` 로. better-auth `verify` 는 같은 확인을 한 번 더 한다
  6. 200 이면 그 `Set-Cookie` 를 실어 303 — OAuth 갈래는 `url` 이 `consentRedirectAllowed` 일 때 그 주소, 웹은 `loginReturn(return).successUrl`. 그 밖 응답은 `console.error` + OAuth 303 `/oauth/error?error=server_error`, 웹 `…error=internal_server_error`
- 실패 주소: 웹은 `loginReturn(return).failureUrl`, OAuth 는 `/login?{q}`(850자 상한은 소셜 상태 쿠키 때문이라 여기 없다) 뒤에 `error=`
- 제한 키는 IP 하나: 이메일 키는 아무나 그 계정을 잠글 수 있고, 256비트 비밀번호라 IP 를 돌리는 대입도 의미가 없다. 바인딩은 호출 수를 세니 실패가 아닌 **시도마다** 센다. 새 바인딩인 이유: `WRITE_LIMITER` 의 120/60초는 설정이 바인딩 하나에 하나뿐이라 로그인에 쓰기엔 느슨하다
- **`ensureReviewAccount`**: SQL 두 문장 batch — `users`(uuid, 소문자 이메일 — `findUserByEmail` 이 소문자로 찾는다, `created_at` ms, `name ''`, `email_verified 1`, `updated_at` ISO) `ON CONFLICT(email) DO NOTHING`, 그 id 로 `auth_accounts` credential 행 `ON CONFLICT DO NOTHING`. 그 이메일 사용자에게 credential 밖 계정 행(google·github)이 이미 있으면 만들지 않고 `console.error('review_email_taken')` + `invalid_credentials`(실제 사용자 계정에 비밀번호 길을 붙이지 않는다). 가입 관문은 세지 않는다 — 이메일이 고정이라 행은 평생 하나
- **계정 경계**: `validateUserInfo` 첫 줄 — 기능이 켜져 있고 `isReviewEmail(env, data.user.email)` 이면 `{ error: 'reserved_email' }`(OAuth 가입·로그인·연결 셋 다 이 훅을 지난다). 그래서 심사 계정에 Google·GitHub 가 붙지 않는다. 문구는 대체 문구. 심사용 주소는 **메일함이 없어도 된다**(메일을 보내는 길이 없다 — `sendVerificationEmail`·`sendResetPassword` 없음)
- 심사자가 이 계정을 지우면(F-2038, 비밀번호 로그인 직후라 세션이 새것) 다음 로그인에 빈 계정이 다시 생긴다. 샘플은 사람이 다시 넣는다
- 안드로이드 앱 로그인(F-4015·F-4016)에 관한 결정은 하지 않는다
