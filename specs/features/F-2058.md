### 3.1 마이그레이션

파일 이름 `migrations/00NN_shared_indexes.sql`. 내용은 두 줄(+ 첫 줄 주석)이다.

```sql
CREATE INDEX docs_owner_folder ON docs(owner_id, folder_id);
CREATE INDEX folders_owner_parent ON folders(owner_id, parent_id);
```

- **번호 규칙: 구현 시점 `migrations/` 의 마지막 번호 + 1.** 오늘(2026-09-28) 마지막은 `0013_purge_jobs.sql` 이다. F-2057 이 이 명세보다 먼저 구현되면 그것이 `0014` 를 가지므로 이 명세는 `0015`, 이 명세가 먼저면 `0014`. 구현자는 커밋 직전 `ls migrations` 로 다시 본다
- 색인 이름 `docs_owner_folder`·`folders_owner_parent` 는 계약이다 — 9장 A3 이 계획 문자열에서 이 이름을 찾는다
- `docs_owner_updated`(0002)는 지우지 않는다. 목록은 `ORDER BY updated_at DESC` 라 그 색인이 계속 필요하고, 새 색인이 그 자리를 가져가지 않는다(머리 (k))
- `IF NOT EXISTS` 를 쓰지 않는다 — 기존 마이그레이션 13개와 같은 모양
- **배포 순서: 원격 마이그레이션을 먼저 적용하고 워커를 올린다.** 색인 없이 3.3 질의가 돌면 `CROSS JOIN` 이라도 하위 폴더마다 `docs_owner_updated` 로 소유자 문서 전부를 훑는다(머리 (b)의 문서 쪽 — S1 에서 문서 CTE 만 40,713행, 지금보다 20배). `deploy` 스킬의 "새 `migrations/000N` 이 있으면 배포 전에 `d1 migrations apply --remote`" 규칙이 이미 그 순서다. 구현 커밋 본문과 배포 보고에 이 줄을 적는다

### 3.2 폴더 CTE — `SHARED_FOLDERS_SQL`

`worker/grants.ts` 에서 내보내는 문자열 상수. `access.ts` 의 `FOLDER_CHAIN_SQL` 과 같은 방식(테스트가 계획을 볼 수 있게 내보낸다).

```sql
WITH RECURSIVE sub(id, owner_id) AS (
  SELECT f.id, f.owner_id FROM grants g JOIN folders f ON f.id = g.target_id AND f.owner_id = g.owner_id
   WHERE g.grantee_email = ?1 AND g.target_type = 'folder' AND g.owner_id <> ?2
  UNION
  SELECT f.id, f.owner_id FROM folders f JOIN sub s ON f.parent_id = s.id AND f.owner_id = s.owner_id
)
SELECT f.id, f.name, f.parent_id, f.owner_id FROM sub s CROSS JOIN folders f ON f.id = s.id
```

- 바인딩: `?1` = 내 이메일, `?2` = 내 사용자 id. **두 개뿐** — 초대 폴더 id 를 바인딩으로 넘기지 않고 `grants` 에서 바로 기점을 잡으므로 100개 한도와 무관하다(머리 (g))
- 기점의 `f.owner_id = g.owner_id` = 리뷰 W2·W4 조건. 초대 행을 준 소유자의 폴더만 기점이 된다(머리 (h)). 지금 코드가 `folders WHERE owner_id = 초대의 owner_id` 로 읽던 것과 같은 효과
- 재귀 단계의 `f.owner_id = s.owner_id` — 남의 폴더가 같은 `parent_id` 를 가져도 따라가지 않는다. `folders_owner_parent` 를 타는 조건이다
- `g.owner_id <> ?2` — 지금 코드의 "내 소유자 몫은 건너뜀"(`if (ownerId === user.id) continue`)
- `UNION`(중복 제거)이라 순환에서 끝난다(머리 (g)). SQLite 재귀 CTE 에는 깊이 제한이 없고, 결과 행 수는 하위 폴더 수로 묶인다
- 소유자가 여럿이어도 **한 번**에 모두 읽는다. 결과 `owner_id` 로 소유자별로 나눈다
- 금고 폴더(`e2ee = 1`)를 거르지 않는다 — 지금 코드도 폴더는 거르지 않고 문서만 `e2ee_key IS NULL` 로 거른다

### 3.3 문서 CTE — `SHARED_DOCS_SQL`

같은 `sub` 정의(3.2 와 한 글자도 다르지 않게 — 두 상수가 앞부분을 공유하도록 만들어도 된다) 뒤에:

```sql
SELECT d.id, d.title, d.line_ending, d.folder_id, d.pinned_at, d.version, d.created_at, d.updated_at, d.owner_id
  FROM sub s CROSS JOIN docs d ON d.owner_id = s.owner_id AND d.folder_id = s.id
 WHERE d.e2ee_key IS NULL
```

- **`CROSS JOIN` 은 계약이다.** 그냥 `JOIN` 이면 계획기가 `docs` 를 바깥에 두고 100배 가까이 읽는다(머리 (e)). SQLite 에서 `CROSS JOIN` 은 결과는 `JOIN` 과 같고 고리 순서만 고정한다. 3.2 의 바깥 `CROSS JOIN` 도 같은 이유로 맞춰 둔다(지금 계획은 `JOIN` 이어도 같지만 통계가 생기면 바뀔 수 있다)
- **`ORDER BY` 를 붙이지 않는다.** 정렬 행이 읽기로 한 번 더 세진다(머리 (f)). 응답 순서는 지금도 계약이 아니다(4장)
- 열 목록은 지금 `SHARED_DOC_COLUMNS` 와 같은 9개
- `d.owner_id = s.owner_id` — 폴더 소유자의 문서만. 지금 코드의 `docs WHERE owner_id = ?`(소유자 문서만 읽고 그 폴더 표로 사슬을 걷던 것)와 같은 범위

### 3.4 `handleGetShared` 의 흐름 (규칙으로)

1. 내 초대를 읽는다 — 지금 질의 그대로(`grants WHERE grantee_email = ?`). 없으면 `[]`
2. 문서 초대 표(`id → {role, ownerId}`)와 소유자별 폴더 초대 표를 만든다 — 지금 그대로
3. **폴더 초대가 하나라도 있으면** `SHARED_FOLDERS_SQL` 과 `SHARED_DOCS_SQL` 을 한 번씩 부른다. 없으면 부르지 않는다(질의 0번 — 문서 초대만 받은 사람은 지금과 같은 질의 수)
4. 폴더 행을 소유자별 `id → {name, parent_id}` 표로 만든다. 문서마다 그 소유자 표로 `storedChain` 을 걸어 지금과 **같은 규칙**으로 폴더 역할(사슬 최고값)과 `viaFolder`(가장 가까운 초대 폴더)를 구하고, 문서 초대 역할(`docGrantRole` — 초대 owner 가 문서 owner 와 같을 때만)과 `higherRole` 로 합친다. 결과를 문서 id 로 기억한다
5. **문서 초대 중 4 에서 이미 뽑힌 문서 id 를 뺀 나머지 전부**를 지금의 `id IN (…)` 질의로 100개씩(`BATCH_ID_LIMIT`) 읽고 `docGrantRole` 로 역할을 정한다. `viaFolder` 는 없다
   - **지금과 다른 점**: 지금은 "폴더 초대를 준 소유자" 의 문서 초대를 4 의 소유자 문서 전부 읽기에서 함께 처리하고 5 에서는 뺐다(`!folderGrantsByOwner.has(g.owner_id)`). 이제 4 는 하위 문서만 읽으므로 **같은 소유자의 하위 밖 문서 초대**는 5 에서 읽어야 한다. 이 필터 조건을 "4 에서 뽑히지 않은 것" 으로 바꾸는 것이 이 명세의 핵심 변경 둘 중 하나다(다른 하나는 3.2·3.3 질의)
6. 내 소유 문서를 빼고 소유자 이메일을 붙인다 — 지금 그대로

- 질의 수 = 1(초대) + [폴더 초대가 있으면 2] + ⌈5 의 id 수 / 100⌉ + 소유자 수. **폴더 깊이·문서 수와 무관하다**(F-2017 4.4 의 성질 유지, 지금 테스트 "폴더 깊이 3 과 30 에서 보낸 질의 수가 같다" 가 그대로 통과해야 한다). 폴더 초대를 준 소유자 수와도 무관해진다(지금은 소유자당 2번)
- 읽는 행 ≈ 초대 수 + 3 × 하위 폴더 수 + 하위 문서 수 + 하위 밖 문서 초대 수 + 소유자 수(머리 (d))

### 3.5 가능했던 다른 모양 — 쓰지 않는다

- **문서를 폴더 id 목록 `json_each` 로 읽기**(폴더 CTE 결과 id 를 JSON 한 개로 넘겨 `folder_id IN (SELECT value FROM json_each(?))` — `commentRows.ts` `FOLDER_DOCS` 선례): 재귀를 한 번만 돌려 S1 에서 약 66행 덜 읽지만 소유자가 여럿이면 소유자마다 한 번씩 불러야 한다. 차이가 작고 질의 수가 소유자 수를 따라가게 되어 쓰지 않는다
- **폴더 CTE 없이 소유자 폴더를 전부 읽고 `descendantFolderIds` 로 자손을 모으기**: Q1 의 다른 선택지다(9장 Q1)

## 4. 응답·권한 — 바뀌지 않는 것

- 응답은 지금과 같은 배열, 원소 모양 `id`·`title`·`lineEnding`·`folderId`·`pinnedAt`·`version`·`createdAt`·`updatedAt`·`role`·`ownerEmail`·`viaFolder?`(F-212 2.3·F-2017 4.4). 같은 입력에 대해 **원소 집합과 각 원소의 모든 필드가 같다**
- 순서는 계약이 아니다 — F-2017 4.4 가 "정하지 않는다" 로 정했고, 소비처 둘이 모두 다시 정렬한다(`serverStore.list()` 의 `sortByUpdatedAtDesc`, `handleListSharedV1` 의 `updatedAt` 내림차순·`id` 오름차순). 지금은 폴더 갈래가 소유자별 `updated_at` 내림차순, 문서 초대 갈래는 정하지 않은 순서였고, 이제 폴더 갈래도 정하지 않은 순서가 된다
- 상태 코드·인증(`requireUser`)·빈 목록 `[]`·금고 문서 제외(`e2ee_key IS NULL`)·내 문서 제외는 그대로

## 5. 같은 결과인가 — 따진 것

지금 코드는 소유자의 **모든** 폴더 표로 `storedChain` 을 걷는다. 새 코드는 **하위 폴더만** 든 표로 걷는다. 두 결과가 같은 이유:

- 문서 폴더 `a0` 에서 부모를 따라 올라가는 사슬 `a0, a1, …` 에 초대 폴더 `ak` 가 있으면, `a0 … ak` 는 모두 `ak` 의 자손(또는 자신)이라 하위 폴더 집합에 든다. 하위 표로 걷는 사슬은 전체 사슬의 **앞부분**이고(표에 없는 폴더에서 멈춘다), 초대 폴더는 모두 그 앞부분 안에 있다. 그래서 역할(사슬 최고값)과 `viaFolder`(처음 만나는 초대 폴더)가 같다
- 거꾸로 하위 문서 CTE 가 돌려준 문서는 폴더가 어떤 초대 폴더의 자손이므로 사슬에 초대 폴더가 반드시 있다 — 역할이 `null` 인 문서가 새로 끼지 않는다
- 하위 밖 문서는 지금도 폴더 역할이 `null` 이므로 문서 초대만 본다 — 3.4 의 5 가 같은 판정을 한다
- 순환: 지금 `storedChain` 은 방문 기록으로, 새 CTE 는 `UNION` 으로 멈춘다. 하위 표 걷기도 같은 `storedChain` 이다
- 초대가 가리키는 폴더가 지워졌거나 남의 것이면: 지금은 폴더 표에 없어 아무 문서도 덮지 않는다. 새 CTE 는 기점에서 빠진다(머리 (h)) — 같다
- 지운 문서 id 를 남이 다시 만든 경우(리뷰 W2): 두 갈래 모두 `docGrantRole` 이 초대 owner 와 문서 owner 를 대조한다 — 같다

## 12. 확인한 것과 가정

확인한 것은 머리의 "직접 재거나 돌린 것" (a)~(l) 과 근거 줄이다.

- G1 **원격 D1 의 `rows_read` 계산이 로컬 workerd 와 같다** — 확인하지 않음. 조사 보고와 같은 가정. 원격 D1 의 SQLite 버전·계획기도 로컬과 같다고 가정했다(로컬 D1 은 `sqlite_version()` 을 막아 버전을 읽지 못했다). `CROSS JOIN` 이 고리 순서를 고정하는 것은 SQLite 의 문서화된 동작이라 버전 차이에 강하다
- G2 원격 `docs`·`folders` 의 행 수 — 재지 않음. 마이그레이션 한 번 비용은 머리 (j) 의 비율(읽기 약 2N·쓰기 약 N)로만 적었다
- G3 실사용에서 초대 하위가 소유자 전체보다 작다는 것 — 표본 S1~S3 은 요청받은 모양(문서 2,000 소유자·하위 폴더 20)을 따른 것이다. 하위가 소유자 전체와 같으면(최상위 폴더 하나에 모든 것을 넣고 그것을 초대) 이 명세의 이득은 "폴더 표 전부 읽기" 차이 정도로 줄어든다(S2 가 그 쪽에 가깝다)
