## 2. 범위

### 한다
- `users.notif_rev` 열. 알림 목록 응답이 바뀔 수 있는 모든 D1 쓰기가 같은 batch 안에서 받는 사람의 리비전을 올린다(3.5)
- `GET /api/notifications` 가 `ETag` 를 싣고, 같은 `If-None-Match` 면 D1 질의 없이 304
- 클라이언트가 마지막 ETag 와 그 응답을 쥐고 조건부로 묻는다
- 같은 브라우저·같은 계정의 탭끼리 가져온 결과를 채널로 나누고, 가장 최근에 가져온 보이는 탭 하나만 60초마다 가져온다

### 하지 않는다
- 알림 문구·화면·배지·사이드바 점(F-507·F-510) — 그대로
- 폴링 주기 60초, 5초 최소 간격, 401 에 멈춤(F-507 4.2) — 그대로
- 부분 색인 `read_at IS NULL`, 폴링 180초(조사 후보 F ②④ — 미채택)
- 읽음 대기(`PendingRead`)의 탭 사이 공유 — 지금처럼 탭마다. 한 탭에서 읽은 것은 다음 가져오기(누가 가져오든)에 반영된다(F-507 Q4 그대로)
- 알림 `TRIM` 문장 고치기(m13) — 12장 Q6 으로 알리기만
- `/api/docs` ETag(조사 후보 D, 보류)

## 3. 서버

### 3.1 마이그레이션

```sql
-- F-2057 알림 리비전 (specs/features/F-2057.md 3장)
ALTER TABLE users ADD COLUMN notif_rev INTEGER NOT NULL DEFAULT 0;   -- 받은 알림 목록이 바뀔 때마다 +1. ETag 에만 쓴다
```

- 채우기 문장 없음. 모든 사람이 0 에서 시작한다 — 배포 전에 쥐고 있던 ETag 는 없으므로(서버가 처음 싣는다) 0 이 잘못 맞을 일이 없다
- **배포 순서(구현 커밋 본문과 배포 때 반드시)**: 원격 D1 에 이 마이그레이션을 **먼저** 적용하고 그다음 코드를 올린다. 3.2 로 better-auth 가 `notif_rev` 열을 읽게 되므로, 열이 없는 D1 에 새 코드가 올라가면 `getSession` 이 실패해 **모든 `/api` 가 401** 이 된다(F-2025 `0010` 과 같은 위험). 반대 순서(열만 먼저)는 옛 코드가 열을 무시하므로 안전하다
- 되돌리기: 코드를 되돌려도 열은 남겨 둔다(해 없음)

### 3.2 인증이 이미 읽는 행에서 리비전 싣기 — 추가 읽기 0

- `USER_ADDITIONAL_FIELDS` 에 `notifRev: { type: 'number', fieldName: 'notif_rev', input: false, required: false }`. 사용량 열(F-2025 4.2)과 같은 모양이라 better-auth `getSession` 이 같은 `users` 한 행에서 함께 가져온다(F-2025 측정 g: 열을 늘려도 읽기 1행)
- `AuthUser` 에 선택 필드 하나:

```ts
export interface AuthUser {
  id: string
  email: string
  usage?: UserUsage
  notifRev?: number // 세션·개발 우회 경로가 채운다. /v1 토큰 경로와 vi.mock('./auth') 테스트는 비워 둔다
}
```

- `toAuthUser` 는 `user.notifRev` 가 숫자일 때만 `notifRev` 키를 싣는다(숫자가 아니면 키 자체가 없다 — `usage.test.ts` U7 "키가 id·email 둘뿐" 이 그대로 통과해야 한다)
- `findOrCreateDevUser` 의 `SELECT id, email, ${USAGE_COLUMNS}` 에 `notif_rev` 를 더한다(같은 행)
- `getTokenUser`(`/v1`) 는 건드리지 않는다 — `/v1` 에는 알림 경로가 없다

### 3.3 ETag 값

```
W/"n1-{userId}-{notifRev}-{limit}"
```

| 부분 | 왜 |
| --- | --- |
| `W/` | 약한 검증자. Cloudflare 가 압축하면서 강한 ETag 를 약하게 바꾸거나 떼는 경우가 있다 — 처음부터 약하게 낸다 |
| `n1` | 응답 모양의 판. 응답 모양(`NotificationsResponse`)이 바뀌는 배포에서 `n2` 로 올리면 옛 탭이 쥔 값이 전부 빗나간다 |
| `userId` | **계정이 바뀌면 반드시 빗나가게.** 리비전만 쓰면 두 계정이 둘 다 `0` 일 때 로그아웃 → 다른 계정 로그인 뒤 옛 값이 맞아 남의 목록이 남는다. 같은 이메일로 지웠다 다시 가입해도 id 가 다르다 |
| `notifRev` | 3.5 가 올린다 |
| `limit` | 같은 사람이라도 `?limit=` 이 다르면 목록이 다르다. 지금 클라이언트는 `limit` 을 보내지 않아 늘 `30` |

- 두 함수 모두 `worker/notifications.ts` 에 두고 내보낸다(단위 테스트가 부른다): `notificationsEtag(p: { userId: string; rev: number; limit: number }): string`, `ifNoneMatchHits(header: string | null, etag: string): boolean`
- `ifNoneMatchHits` 규칙: 헤더를 `,` 로 나눠 앞뒤 공백을 떼고, 각 값과 `etag` 에서 앞의 `W/` 를 뗀 나머지가 글자까지 같은 것이 하나라도 있으면 참. `*` 는 **맞지 않는 것**으로 본다(이 경로에서 `*` 를 보낼 까닭이 없다). 헤더가 없거나 빈 문자열이면 거짓

### 3.4 `GET /api/notifications`

순서가 결정이다:

1. `requireUser` (지금 그대로 — 인증 2행)
2. `limit` 검사 (지금 그대로 — 틀리면 400)
3. `user.notifRev` 가 숫자가 아니면 → 지금과 똑같이 목록·개수를 읽어 200, **`ETag` 없음**
4. 숫자면 ETag 를 만들고, `ifNoneMatchHits(요청 If-None-Match, ETag)` 가 참이면 **304**, D1 질의 없음. 헤더는 `ETag`·`Cache-Control: no-store` 둘, 본문 없음
5. 아니면 지금처럼 `LIST_SQL`·`UNREAD_SQL` 로 200. 헤더는 `jsonResponse` 의 세 헤더 + `ETag`

- **리비전을 목록보다 먼저 읽는다(인증 때).** 그 사이에 알림이 새로 생기면 응답에는 새 알림이 있는데 ETag 는 옛 리비전이다 — 다음 요청은 옛 값을 보내고, 리비전은 이미 올랐으므로 빗나가 200 을 한 번 더 받는다. 손해는 요청 하나의 216행이고 **틀린 304 는 생기지 않는다**. 반대 방향(목록이 리비전보다 옛것)은 순서상 일어나지 않는다
- 막힌 계정도 지금처럼 본다(F-503 6.5)

### 3.5 리비전을 올리는 모든 쓰기 자리

규칙: **알림 행을 넣거나 `read_at` 을 바꾸거나 지우는 D1 문장이 있는 batch 에는, 그 영향을 받는 받는 사람의 `notif_rev` 를 1 올리는 문장이 같은 batch 에 있다.** 원자성 때문에 같은 batch 여야 한다 — 따로 보내다 실패하면 목록은 바뀌었는데 ETag 는 그대로라 영영 304 가 나온다.

지우는 자리의 공통 모양: **지우는 문장 바로 앞에**, 그 `DELETE` 와 **같은 `WHERE`·같은 바인딩**으로 받는 사람을 고른다(지운 뒤에는 누가 받는 사람이었는지 알 수 없다).

```sql
UPDATE users SET notif_rev = notif_rev + 1 WHERE email IN (SELECT recipient_email FROM notifications WHERE {그 DELETE 의 WHERE})
```

| # | 자리 (함수) | 더하는 문장 | 쓰기 증가 | 읽기 증가 (m2~m5) |
| --- | --- | --- | --- | --- |
| ① | 알림 넣기 — `notificationStatements`(DO 스냅숏 batch, `commentBundleStatements` 가 부름) | `TRIM` 뒤에 한 문장: `UPDATE users SET notif_rev = notif_rev + 1 WHERE email IN (SELECT value FROM json_each(?1)) AND EXISTS (SELECT 1 FROM docs WHERE id = ?2 AND e2ee_key IS NULL)` — `?1` 은 `TRIM` 에 넘기는 받는 사람 JSON 그대로, `?2` 는 문서 id. 넣기 문장의 `DOC_WRITABLE` 과 같은 조건이라 금고 문서면 0행 | 스냅숏마다 **가입한 받는 사람 수 R** | 약 5 × R |
| ② | 읽음 표시 — `handleReadNotifications` | 지금의 `dayUsageStatement` 자리를 **한 문장으로 바꾼다**: `UPDATE users SET notif_rev = notif_rev + CASE WHEN changes() > 0 THEN 1 ELSE 0 END, write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1 WHERE id = ?2`. 읽음 `UPDATE` 바로 뒤에 있어야 `changes()` 가 그 문장을 본다. `usage.ts` 에 `DAY_ONLY_SQL` 옆에 두고 `dayUsageStatement` 와 같은 바인딩 모양의 함수로 낸다 | **0** (같은 `users` 행을 어차피 쓴다) | **0** |
| ③ | 댓글 지우기 — `commentBundleStatements` 의 `DELETE_ROW_NOTIFICATIONS_SQL` 앞 | 공통 모양, `WHERE doc_id = ?1 AND comment_id IN (SELECT value FROM json_each(?2))` | 지운 알림의 받는 사람 수 | 그 문서 알림 행 수 + 약 5 × 받는 사람 |
| ④ | 문서 삭제 — `docCommentDeleteStatements` | 공통 모양, `WHERE doc_id = ?` | 같음 | 같음 |
| ⑤ | 폴더 삭제 — `folderCommentDeleteStatements` / 금고로 옮기기 — `e2eeCommentDeleteStatements` | 공통 모양, 각 `DELETE FROM notifications` 의 `WHERE` 그대로 | 같음 | 같음 |
| ⑥ | 계정 삭제 — `accountCommentDeleteStatements` | 공통 모양, `WHERE doc_id IN (SELECT id FROM docs WHERE owner_id = ?1) OR recipient_email = ?2`. 지우는 본인 행도 오르지만 같은 batch 끝에서 행째 지워진다 | 같음 | 같음 |
| ⑦ | 매일 정리 — `cleanupComments` | `OLD_NOTIFICATIONS_SQL`·`ORPHAN_NOTIFICATIONS_SQL` **각각 바로 앞**에 공통 모양. `OVERFLOW_SQL` 앞에는 두지 않는다(아래) | 지운 알림의 받는 사람 수 | 하루 1번, 알림 전체 행 수 × 2 |

- 호출하는 쪽(`docs.ts`·`folders.ts`·`e2eeDocs.ts`·`account.ts`·`docRoomCore.ts`)은 고치지 않는다 — 문장 묶음 함수가 돌려주는 배열에 들어가므로 저절로 같은 batch 에 실린다. `cleanupComments` 는 batch 결과 배열의 자리가 밀리므로 결과를 꺼내는 자리만 맞춘다(돌려주는 객체 모양은 그대로)
- **⑦ `OVERFLOW_SQL` 을 빼는 까닭**: 받는 사람별 300개 넘침은 ①의 `TRIM` 이 넣을 때마다 이미 자르고, ①이 같은 batch 에서 그 사람의 리비전을 올린다. 매일 정리의 넘침 문장은 안전망이라 평소 0행이고, 앞에 붙일 부질의가 `TRIM` 과 같은 상관 부질의라 비싸다(m13)
- ② 에서 `changes() > 0` 으로 거르는 까닭: 이미 읽은 알림을 다시 읽음 표시하거나(두 탭이 같은 항목을 누름) 안 읽은 것이 없을 때 `모두 읽음` 은 목록을 바꾸지 않는다 — 리비전을 올리면 모든 탭이 쓸데없이 216행짜리 200 을 한 번 더 받는다
- ① 은 `INSERT OR IGNORE` 가 중복으로 0행을 넣어도 리비전을 올린다. 손해는 200 한 번이고, 막으려면 `changes()` 를 봐야 하는데 바로 앞 문장이 `TRIM` 이라 넣기 문장의 값을 볼 수 없다
- **트리거는 쓰지 않는다**(m6): SQLite 트리거는 행마다 돌아 `모두 읽음` 75행에 `users` 쓰기가 75 더 붙는다. 명시 문장은 받는 사람마다 1
- 문장 수: 스냅숏 batch 는 알림을 넣을 때 +1, 댓글을 지울 때 +1(최대 +2). 계정 삭제 batch +1, 문서·폴더 삭제·금고 전환 batch 각 +1, 매일 정리 batch +2. D1 호출당 질의 상한(F-500 c9: 무료 50)에 대한 여유는 각 batch 에서 지금 문장 수 + 이 수로 넘지 않는다 — 가장 긴 계정 삭제 batch 가 지금 17문장이다(`deleteAccountStatements`)

## 4. 클라이언트

### 4.1 `fetchNotifications(etag)` — `src/app/notificationsApi.ts`

```ts
export type NotificationsFetchResult =
  | { ok: true; data: NotificationsResponse; etag: string | null }
  | { ok: true; notModified: true }
  | { ok: false; reason: 'network' | 'unauthorized' | 'server' | 'invalid' }

export async function fetchNotifications(etag: string | null): Promise<NotificationsFetchResult>
```

- `etag` 가 있으면 `If-None-Match: {etag}` 를 싣는다. 요청 옵션에 `cache: 'no-store'` 를 준다(브라우저 HTTP 캐시가 끼지 않게 — m7 에서 있어도 없어도 304 가 스크립트에 왔지만 명시한다)
- 상태 판정 순서: 304 → `{ ok: true, notModified: true }` (지금 코드는 `!res.ok` 를 `invalid` 로 보므로 **304 를 그 앞에서** 가른다) → 401 → 5xx → 그 밖 비 2xx `invalid` → 200 은 지금처럼 JSON 모양 검사(`readNotificationsResponse`)
- 200 의 `etag` = 응답 `ETag` 헤더. 없거나 200자를 넘으면 `null`(다음 요청을 조건부로 하지 않는다). 가짜 서버·옛 서버가 `ETag` 를 안 보내도 지금과 똑같이 돈다
- 보낸 `etag` 가 `null` 인데 304 가 오면 `{ ok: false, reason: 'invalid' }`

### 4.2 탭 사이 채널 — `src/app/notificationsShare.ts`

**새 채널을 둔다. `md-tabs` 를 재사용하지 않는다.** `md-tabs` 의 `TabMessage` 합집합은 `reduceClaim`(편집권)과 `useTabSync` 의 목록 다시 읽기가 모든 메시지를 훑는다 — 종류를 더하면 두 곳을 고쳐야 하고(F-296 소유), 알림은 편집권과 상관이 없다. 채널 이름은 저장소 식별자와 같은 규칙으로 제품명을 쓰지 않는다.

```ts
export const NOTIFICATIONS_CHANNEL_NAME = 'md-notifications'
export const NOTIFICATIONS_FOLLOWER_DELAY_MS = 10_000

export type NotificationsShareMessage = {
  kind: 'notifications-result'
  v: 1
  tabId: string
  accountId: string
  startedAt: number // 그 결과를 가져온 요청을 시작한 시각(ms)
  etag: string | null
  data: NotificationsResponse // 서버 값 그대로 — 보낸 탭의 읽음 대기를 얹지 않는다
}

export function readNotificationsShare(raw: unknown): NotificationsShareMessage | null
export function isNewerStart(a: { startedAt: number; tabId: string }, b: { startedAt: number; tabId: string }): boolean
```

- `readNotificationsShare`: 키 7개가 정확히 이것뿐이고 `kind`·`v` 가 맞고, `tabId`·`accountId` 는 빈 문자열이 아닌 문자열, `startedAt` 은 유한한 수, `etag` 는 `null` 또는 문자열, `data` 는 `readNotificationsResponse` 를 통과해야 한다. 아니면 `null`(다른 판의 탭이 보낸 메시지를 버린다)
- `isNewerStart(a, b)`: `a.startedAt > b.startedAt`, 같으면 `a.tabId > b.tabId`(사전순). 같은 밀리초에 두 탭이 가져와도 한쪽만 "더 새것" 이 된다
- 탭 id 는 `src/lib/tabChannel.ts` 의 `newTabId()` 를 쓴다

### 4.3 누가 가져오나 — 선출 없이 "마지막에 가져온 보이는 탭"

명시적 리더 선출은 두지 않는다. 각 탭이 **마지막으로 적용한 결과의 (시작 시각, 탭 id)** 를 쥐고, 그보다 새 결과만 적용한다. 60초 타이머는 **자기가 가져왔으면 60초, 남의 결과를 받았으면 받은 때부터 70초(60 + `NOTIFICATIONS_FOLLOWER_DELAY_MS`)** 로 건다. 그러면 마지막에 가져온 탭의 타이머가 늘 먼저 울리고, 다른 탭은 그 결과를 받아 타이머를 다시 미룬다 — 가져오는 탭이 하나로 수렴한다.

| 일 | 그 탭이 하는 것 |
| --- | --- |
| 자기 요청 시작 | 지금처럼 `lastStartedAt = now`, 60초 타이머 |
| 자기 응답 200·304 | 그 결과의 `(startedAt, 내 tabId)` 가 지금까지 적용한 것보다 새것이면 적용(4.4)하고 **채널로 보낸다**. 아니면(그 사이 남의 더 새 결과를 적용함) 버리고 보내지 않는다 |
| 자기 응답 실패 | 지금처럼(401 멈춤, 첫 실패면 `failed`). 채널로 보내지 않는다 |
| 채널 메시지 받음 | `readNotificationsShare` 통과 + `accountId` 가 내 계정 + 내가 켜져 있음(`enabled`) + 적용한 것보다 새것일 때만: 적용(4.4), `lastStartedAt = max(내 값, msg.startedAt)`, 타이머를 **지금부터 70초**로 다시 건다. 보이지 않는 탭도 받아 적용한다 |
| 타이머 울림 | 지금 `shouldFetchNotifications('interval')` 그대로 — 보이는 탭이고 `now - lastStartedAt ≥ 60초`. `lastStartedAt` 에 남의 시작 시각도 들어가므로 뒤따르는 탭은 방금 누가 가져왔으면 건너뛴다 |
| `visible`·`online`·`open` | 지금 규칙 그대로(5초 최소 간격) — 다만 `lastStartedAt` 이 **어느 탭이든 마지막 시작**이다. 다른 탭이 3초 전에 가져왔으면 알림함을 열어도 요청하지 않고 받은 값을 보인다 |
| `enable`(부팅·로그인) | 지금 그대로 늘 가져온다(ETag 없이 — 새 탭은 쥔 값이 없다) |

- **가져오는 탭이 닫히거나 숨으면**: 그 탭은 더 보내지 않는다(닫힘) 또는 `interval` 이 안 보여서 건너뛴다(숨음). 남은 보이는 탭의 70초 타이머가 울려 그 탭이 가져오고, 이제 그 탭이 마지막에 가져온 탭이 된다. **최악 간격은 60초 → 70초 한 번.** 보이는 탭이 하나도 없으면 아무도 가져오지 않는다 — 지금과 같다
- **두 탭이 거의 동시에 가져오면**(뒤따르는 두 탭의 70초 타이머, `online` 이 모든 탭에 동시에): 한 번은 둘 다 요청한다. 서로의 결과를 받으면 `isNewerStart` 에서 진 쪽이 뒤따르는 탭(70초)이 되고 이긴 쪽은 60초 타이머를 유지 — 다음 주기부터 하나다
- **보이게 될 때와의 관계**: 숨은 탭도 결과를 받아 두므로 보이게 되는 순간 화면은 최대 60~70초 전 값이다. 그래도 `visible` 재조회는 지금처럼 한다(5초 간격) — 304 면 2행이라 싸고, 사용자가 돌아온 탭이 최신이라는 F-507 4.2 행동을 바꾸지 않는다. 그 탭이 가져왔으므로 이제 그 탭이 가져오는 탭이 된다
- **알림함을 연 탭**: `open` 은 5초 안에 어느 탭이든 가져왔으면 그 값, 아니면 그 탭이 곧바로(조건부로) 가져오고 결과를 다른 탭에 보낸다
- `BroadcastChannel` 이 없으면(`typeof BroadcastChannel === 'undefined'`) 채널 없이 지금처럼 탭마다 가져온다. ETag 는 그래도 쓴다
- 배포 직후 옛 코드의 탭은 채널에 없으므로 따로 가져온다 — 섞여 있어도 틀리지 않고 절약만 줄어든다

### 4.4 결과 적용 — 200·304·받은 메시지가 같은 길

- 200: 서버 값과 ETag 를 **짝으로** 바꾼다(ETag 는 그 값과 함께 온 것만 쥔다)
- 304: 쥔 서버 값·ETag 를 그대로 둔다. 서버 값이 없는데 304 면 4.1 이 이미 `invalid` 로 바꾼다
- 받은 메시지: 메시지의 `data`·`etag` 로 바꾼다
- 셋 다 이어서: `pendingRef = dropSettledReads(pending, 그 결과의 startedAt)` → `recomputeFromServer()` → `status = 'ready'`, 한 번 받음 표시. 받은 메시지는 **보낸 탭의 `startedAt`** 으로 떨군다 — 내 읽음 요청이 끝난 뒤에 시작한 가져오기라면(누가 가져왔든) 서버 값에 이미 들어 있다. 304 에서도 떨궈도 된다: 읽음이 실제로 행을 바꿨으면 3.5 ② 가 리비전을 올려 304 가 나올 수 없다
- 채널로 보낼 때 `data` 는 서버 값(`lastServerRef`)이다 — 읽음 대기를 얹은 화면 값이 아니다. 대기는 탭마다다(2장)

### 4.5 계정·로그아웃

- 훅 입력에 `accountId: string | null` 을 더한다. 채널은 `enabled && accountId !== null` 일 때만 연다
- `enabled` 가 꺼지면(로그아웃·서버 저장소 아님) 지금 정리에 더해 **쥔 ETag 를 버리고 채널을 닫는다**. 다음에 켜지면 ETag 없이 시작한다
- `accountId` 가 바뀌면 채널을 닫았다 다시 열고 ETag·서버 값·`lastStartedAt` 을 버린다(정상 흐름에서는 로그인이 페이지를 다시 읽어 일어나지 않지만, 일어나도 남의 값이 남지 않게)
- 다른 계정의 메시지는 버린다(4.3). 서버 쪽에서도 ETag 에 `userId` 가 있어 다른 계정 세션에 옛 ETag 가 맞지 않는다(3.3)
- **ETag 는 메모리에만.** localStorage·IndexedDB 에 두지 않는다 — 새 탭·새로고침은 ETag 없는 요청 하나로 시작한다. 저장 키가 늘지 않는다

### 4.6 `useNotifications` 가 드러내는 것

`UseNotificationsResult` 모양은 바꾸지 않는다(`status`·`items`·`unread`·`refresh`·`markRead`·`markAllRead`·`markDocRead`). `NotificationsMenu.tsx`·사이드바 점(F-510)은 고치지 않는다.

### 4.7 `App.tsx`

`useNotifications({ enabled: notificationsEnabled, blocked: …, accountId: account.state === 'in' ? account.id : null })` — 인자 하나만 더한다. F-2059(App.tsx 분할)와 겹치는 줄은 이 호출 한 줄뿐이다.

| 뒤 — 두 탭 모두 보임 | 60 + 20 + 2 = 82 | 부팅 2 + 리비전 바뀜 8 = 10 | 72 | 10 × 216 + 72 × 2 + 넣기 쪽 5 × 5 = **약 2,330** | +5 (스냅숏) |
| 뒤 — 한 탭만 보임 | 82 | 10 | 72 | **약 2,330** | +5 |

- 두 탭 모두 보일 때 **약 92%**, 한 탭만 보일 때 **약 87%** 줄어든다. 200 의 수는 요청 수가 아니라 **리비전이 바뀐 횟수**에 묶인다 — 알림이 조용한 사람은 한 시간 내내 2행씩이다
- 보고서 시나리오(알림이 적어 요청당 약 62행, 80회)면 지금 약 5,000 → 뒤 약 60 × 2 + 10 × 62 ≈ 750
- 쓰기: 읽음 표시 0, 알림 넣기 스냅숏마다 +R, 지우기는 지운 알림의 받는 사람 수 — 드문 동작이다

### 5.1 측정 방법

1. **자동(구현 때)**: U2 가 304 경로에서 `notifications` 표를 건드리는 문장이 0개임을 센다(= 인증 2행만). E2·E3 이 두 탭에서 분 단위 요청 수를 센다
2. **로컬 행 수(구현 뒤 한 번, 구현자가 보고에 붙인다)**: 이 명세의 m1~m5 스크립트와 같은 방식 — `getPlatformProxy` 로컬 D1 에 새 마이그레이션까지 적용하고 ①~⑦ 문장의 `meta.rows_read`·`rows_written` 을 찍어 3.5 표의 값과 같은 자리수인지 확인한다(스크립트는 스크래치패드에만)
3. **운영(배포 전후, 사람)**: `npx wrangler d1 insights md-editor-db --time-period 1d --sort-by reads --limit 20 --json` 을 배포 직전과 배포 24시간 뒤에 받아, `LIST_SQL`·`UNREAD_SQL` 두 질의의 `count`·읽은 행 합을 비교한다. 기대: 두 질의의 실행 수가 배포 전의 **20% 이하**(알림이 드문 사용자 기준). 9.4 H1

### 이 명세 밖 — 따로 알림

- **Q6 알림 넣기의 `TRIM` 문장이 비싸다(m13).** `TRIM_NOTIFICATIONS_SQL` 은 받는 사람의 행마다 상관 부질의(`LIMIT 300`)를 돌려, 받은 알림 152개인 사람 한 명에게 알림을 하나 넣는 스냅숏이 **읽기 46,667** 을 쓴다(행이 늘면 제곱에 가깝게 는다). 같은 판정을 받는 사람별 "300번째 행보다 오래된 것만" 문장으로 바꾸면 305. 알림 폴링 전체(5장 "지금" 약 30,700/시간)와 맞먹거나 넘는 크기라 **별도 소명세를 권한다**(F-502 소유 문장, 매일 정리 `OVERFLOW_SQL` 도 같은 조건을 쓴다). 이 명세의 ① 은 `TRIM` 을 건드리지 않고 그 뒤에 붙기만 하므로 둘은 따로 갈 수 있다

## 13. 확인한 것과 가정

### 13.1 코드를 읽거나 돌려 확인한 것
- 머리말 m1~m13 전부
- 알림 행을 넣는 곳은 `notificationStatements` 하나(`docRoomCore.ts` 스냅숏이 `commentBundleStatements` 로 부름). `read_at` 을 바꾸는 곳은 `handleReadNotifications` 하나. 지우는 곳은 `commentRows.ts` 의 다섯 자리(`DELETE_ROW_NOTIFICATIONS_SQL`·`DOC_NOTIFICATIONS_DELETE_SQL`·폴더·금고·계정)와 `commentGc.ts` 세 문장 — `grep -rn "notifications" worker/*.ts` 로 전부 봤다. `grants.ts`(초대 취소)는 알림을 지우지 않는다
- 인증 세 경로 중 세션·개발 우회는 `users` 행을 읽고, better-auth 추가 필드가 `getSession` 결과에 실린다(F-2025 `toAuthUser` 가 이미 그렇게 씀)
- `jsonResponse` 헤더 셋에 `ETag` 가 없고, `index.ts` 는 `/api` 응답 헤더를 고치지 않는다
- 클라이언트는 `limit` 을 보내지 않는다(`fetchNotifications` 가 `/api/notifications` 그대로)
- 가짜 서버의 읽음 실패(`recordWrite`)는 알림 상태를 바꾸기 전에 돌아간다

### 13.2 가정으로 남긴 것
- **원격 D1 이 로컬 workerd 와 같은 행 수를 센다** — 조사 보고와 같은 가정. H1 로 확인
- **Cloudflare 가 Worker 응답의 약한 `ETag` 와 요청 `If-None-Match` 를 그대로 통과시킨다** — 문서로만 알고 재지 않았다. H2 로 확인. 통과시키지 않으면 늘 200 이 되어 지금과 같아질 뿐 틀리지는 않는다
- better-auth 가 `additionalFields` 하나를 더해도 `getSession` 이 읽기 2행 그대로 — F-2025 측정 g(열 2개 → 8개에도 1행)에서 미루어 봤고 이번에 따로 재지 않았다
- 2026-09-15 이전(F-205 전)에 대문자가 섞인 이메일로 만든 `users` 행은 없다 — m10 은 코드 경로만 확인했고 운영 데이터는 보지 않았다. 있다면 그 사람은 ①·③~⑦ 이 리비전을 못 올려 304 가 이어진다(읽음 ②는 id 로 찾으므로 된다). 확인 문장: `SELECT COUNT(*) FROM users WHERE email <> lower(email)` — 배포 전 메인이 원격에서 한 번
- 5장 시나리오의 사건 수(스냅숏 5·읽음 3·보임/열기 20)는 가정이다

### 13.3 기존 명세·코드와 부딪힌 것
- F-500 4.8 은 `GET /api/notifications?limit=30` 이라 적었지만 코드는 `limit` 을 보내지 않는다(서버 기본 30 과 같아 결과는 같다). 이 명세는 코드대로 ETag 끝이 `-30`
