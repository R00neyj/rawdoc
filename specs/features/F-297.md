## 2. 문제

### 2.1 지금 코드에서 벌어지는 일

1. `src/storage/docsApi.ts` 62행 `export const lockSessionId: string = resolveLockSessionId()` — 모듈이 평가될 때 한 번 정해진다
2. 46~58행 `resolveLockSessionId()` 는 `sessionStorage['md.lockSession']` 에 값이 있으면 **그것을 그대로 쓴다** (F-250 3.1)
3. 크롬 `탭 복제` 는 `sessionStorage` 를 통째로 복사한다 → 두 탭의 `lockSessionId` 가 같아진다
4. `worker/locks.ts` 37행 잡기 조건 `... OR doc_locks.session_id = ?` 가 맞아떨어져 **두 탭 다 `200`** 을 받는다. `worker/docs.ts` 231행 `PUT` 의 `activeLock.session_id !== X-Lock-Session` 도 안 걸린다
5. 그래서 두 탭 다 편집 가능하고, 둘 다 저장한다

### 2.2 버전 검사(409)도 못 막는다 — 조용히 덮인다

"둘 다 저장해도 `baseVersion` 이 안 맞아 409 가 나니 충돌 사본이 생기지 않느냐" 는 성립하지 않는다.

`src/storage/serverStore.ts` 241~244행이 `baseVersion` 을 **IndexedDB 캐시에서 읽는다**:

```ts
const cachedDoc = await cache.getDoc(userId, entry.docId)
const baseVersion = cachedDoc?.version ?? 0
```

그 캐시는 같은 브라우저·같은 사용자면 **두 탭이 공유한다**(`createRemoteCache`, userId 로 구분). 탭 B 가 저장해 캐시 버전이 4가 되면, 탭 A 가 뒤이어 보낼 때도 캐시에서 4를 읽어 보낸다 → `409` 가 안 난다 → **탭 A 의 본문이 탭 B 의 저장을 통째로 덮는다.** 알림도, 충돌 사본도, 흔적도 없다.

즉 **두 탭을 갈라 주는 장치는 편집 잠금 하나뿐**이고, 세션 id 가 같아지는 순간 그 하나가 없어진다.

### 2.3 재현 절차 (사람이 손으로)

서버 문서여야 한다(로컬 IndexedDB 문서는 잠금 자체가 없고, 그쪽은 F-296 6.4 가 맡는다).

1. 로그인 상태로 앱을 연다 — 배포본(`https://rawdoc.app/`) 또는 `npm run dev:worker` 에 `.dev.vars` 의 `DEV_AUTH_EMAIL` 을 넣은 로컬
2. 서버 문서를 하나 열고 본문에 `AAA` 를 친 뒤 상태바가 `저장됨` 이 될 때까지 기다린다
3. 그 탭의 **탭 제목을 우클릭 → `탭 복제`**
4. 복제된 탭에 같은 문서가 열린다. **여기서 `다른 창에서 편집 중입니다. 읽기만 할 수 있습니다.` 가 뜨지 않고 그냥 편집된다** ← 구멍
   (비교: 같은 문서를 `Ctrl+T` 로 연 **새 탭**에서 열면 이 안내가 뜬다. `e2e/docLock.spec.js` 200~219행 F-250 A6 이 그 동작을 지킨다)
5. 복제 탭에서 `BBB` 를 치고 `저장됨` 을 기다린다
6. 원래 탭으로 가서 `CCC` 를 치고 `저장됨` 을 기다린다
7. 아무 탭이나 **새로고침**한다 → 본문에 `BBB` 가 없다. 나중에 저장한 쪽이 앞의 편집을 통째로 덮었고, 경고는 한 번도 없었다

고친 뒤에는 4번에서 안내가 뜨고 복제 탭이 읽기 전용이 된다(4.3).

## 3. 범위

### 3.1 한다

- 부팅 때 `md.lockSession` 값이 **다른 살아 있는 탭에서 이미 쓰이고 있는지** `BroadcastChannel` 로 물어본다
- 쓰이고 있으면 **물어본 탭이** 새 UUID 를 만들어 `sessionStorage` 에 쓰고 그 값을 쓴다 (회전)
- 세션 id 를 싣는 요청 3개(`PUT /api/docs/:id`, `POST …/lock`, `DELETE …/lock`)는 회전 여부가 정해지기 전에 나가지 않게 막는다
- `lockSessionId` 모듈 상수를 없애고 `getLockSessionId()` 로 바꾼다 (4.1)

### 3.2 하지 않는다

- **부팅을 늦추지 않는다** — 4.2
- **새 UI 를 만들지 않는다.** 회전한 탭은 F-213 의 기존 읽기 전용 흐름을 그대로 탄다 (4.3). 새 알림 문구·설정 키·아이콘이 없다
- `sessionStorage` 를 버리고 메모리 값으로 되돌리기 — F-250 을 되돌리는 것이다(사용자 결정 1)
- 서버(`worker/**`)·D1 스키마 변경 — 1장
- 로컬(IndexedDB) 문서의 탭 사이 편집권 — **F-296 6.4 가 맡는다.** 이 명세는 서버 문서 잠금만 본다
- **공유 outbox 경합** — 두 탭이 같은 IndexedDB outbox 를 함께 비우는 문제(`serverStore.ts` 455~456행이 만들어지자마자 `kickSend()` 를 부른다)는 세션 id 와 별개로 **지금도 있다.** 세션 id 가 갈라지면 뒤늦은 탭의 `PUT` 이 `423` 을 받아 F-207 2.4 충돌 사본 경로로 들어가므로, **평범한 두 탭에서 이미 벌어지는 것과 같은 상태로 수렴한다.** 새로 나빠지는 것은 없다. 별도 판단이 필요하면 11장 Q5
- `BroadcastChannel` 이 없는 브라우저를 위한 폴백 — F-296 5.4 와 같은 판단(4.4)

## 4. 결론 — 미루지 않고 여기서 정한 것

### 4.1 모듈 상수 `lockSessionId` 를 어떻게 바꾸는가 — **읽는 자리가 셋뿐이라 전부 함수 호출로 바꾼다**

`grep -rn "lockSessionId"` 로 저장소 전체를 훑었다. `src/`·`worker/`·`e2e/` 를 통틀어 읽는 자리는 **아래가 전부**다.

| 파일:행 | 지금 | 뒤 |
| --- | --- | --- |
| `src/storage/docsApi.ts:62` | `export const lockSessionId: string = resolveLockSessionId()` | **삭제.** 41~59행(`LOCK_SESSION_STORAGE_KEY`·`newLockSessionId`·`resolveLockSessionId`)과 함께 `src/storage/lockSession.ts` 로 옮긴다 |
| `src/storage/docsApi.ts:134` | `headers: { …, 'X-Lock-Session': lockSessionId }` | `'X-Lock-Session': getLockSessionId()` — **요청을 만드는 시점에** 읽는다 |
| `src/app/useDocLock.ts:3, :170` | `import { …, lockSessionId, … }` → `createDocLockController(docId, lockSessionId, …)` | **import 를 지운다.** 세션 id 는 컨트롤러가 모르고 `docsApi.lockDoc`/`unlockDoc` 이 안에서 읽는다 (아래) |
| `src/storage/docsApi.test.ts:40, :49, :60` | `const { lockSessionId } = await import('./docsApi')` | `lockSession.test.ts` 로 옮기며 `getLockSessionId()` 로 (9장) |

**고른 방식: 가변 모듈 상태 + getter, 그리고 세션 id 를 `docsApi` 밖으로 내보내지 않는다.**

- `src/storage/lockSession.ts` 안에 `let currentSessionId` 를 두고 `getLockSessionId(): string` 으로만 낸다. 값을 export 하지 않으므로 **import 한 쪽이 옛 값을 들고 있을 수 없다**
- `lockDoc(id, sessionId)` → **`lockDoc(id)`**, `unlockDoc(id, sessionId, opts)` → **`unlockDoc(id, opts)`** 로 좁힌다. 세션 id 는 `X-Lock-Session` 과 똑같이 API 계층의 구현 세부사항이 된다 — 지금도 `updateDoc`(128~152행)은 세션 id 를 인자로 받지 않는다. **세 함수의 모양이 같아진다**
- 그래서 `createDocLockController(docId, sessionId, myEmail, api, callbacks)` 에서 두 번째 매개변수가 빠진다. 컨트롤러는 잠금 수명 동안 세션 id 를 들고 있지 않는다

**다른 두 안을 안 고른 이유:**

| 안 | 왜 안 쓰나 |
| --- | --- |
| `lockSessionId` 를 그대로 두고 회전을 `docsApi` import 보다 먼저 끝낸다 | **불가능하다.** `import` 는 동기이고 회전 판정은 `BroadcastChannel` 왕복(비동기)이 필요하다. 회전을 먼저 끝내려면 동기 대기가 있어야 하는데 브라우저에 그런 수단이 없다 |
| 컨트롤러에 `getSessionId: () => string` 을 넘겨 매번 읽게 한다 | `start()` 가 게이트(4.2)를 안 거치고 곧바로 `lockDoc` 을 부르므로 **회전 전 id 로 잠금을 잡을 수 있다.** 그러면 서버가 두 탭을 같은 세션으로 보아 `200` 을 주고, 최대 20초(연장 주기)까지 "편집할 수 있는 것처럼" 보인다. 지금 버그와 같은 상태가 20초 남는다 |

### 4.2 회전을 기다리는 동안 첫 요청이 나가면 — **부팅이 아니라 요청 3개만 막는다**

**결정: `App.tsx` `boot()` 을 건드리지 않는다. `docsApi` 의 세션 id 를 싣는 함수 안에서만 기다린다.**

근거 — 부팅 순서를 실제로 따라가 보면:

1. `boot()` 581행 `await fetchAccount()` 는 `/api/me` 를 부르는데 **세션 id 를 싣지 않는다**(`src/app/account.ts` 14행). `list()`·`listFolders()`·`/api/shared` 도 마찬가지다. `X-Lock-Session` 을 붙이는 자리는 저장소 전체에서 `docsApi.ts` 134행 하나뿐이다(grep 확인)
2. **그런데 `openStore()` 안에서 이미 세션 id 를 싣는 요청이 나갈 수 있다.** `serverStore.ts` 455~456행이 저장소를 만들자마자 `refreshPending(); kickSend()` 를 부르고, outbox 에 지난 세션이 남긴 `updateDoc` 이 있으면 곧바로 `PUT`(134행 헤더 포함)이 나간다. 그러므로 **"부팅이 끝난 뒤에 기다리면 된다" 는 틀렸다.** `App.tsx` 620행 `setStore` 뒤에 게이트를 두는 설계는 이 경로를 못 막는다
3. 따라서 게이트는 `docsApi` 안에 있어야 하고, 그러면 `App.tsx` 는 한 줄도 안 바뀐다

**부팅을 늦추지 않는 이유:** 150ms 는 화면이 뜨는 시간에 더해질 값이 아니다. 늦춰야 하는 것은 "세션 id 를 싣는 요청" 뿐이고, 그것은 전부 배경 요청이다 — `POST lock` 은 결과가 늦어도 사용자가 보는 것이 없고(실패해야 읽기 전용 안내가 뜬다), `PUT` 은 어차피 `useDocSaver` 700ms 디바운스 뒤에 나간다.

**최대로 늦어지는 양: 150ms, 그리고 그나마도 탭 수명의 첫 150ms 안에 나가는 요청에만 붙는다.** 그 뒤로는 `isLockSessionSettled()` 가 `true` 라 `await` 자체를 건너뛴다.

**게이트를 `if (!isLockSessionSettled()) await lockSessionReady()` 형태로 쓴다(그냥 `await lockSessionReady()` 로 쓰지 않는다).** `unlockDoc` 이 `pagehide` 에서 `keepalive: true` 로 불리기 때문이다(`useDocLock.ts` 111행). 이미 끝난 약속이라도 `await` 하면 `fetch` 호출이 마이크로태스크 하나 뒤로 밀리는데, 페이지가 헐리는 중에는 그 한 틱도 아껴야 한다. 조건문으로 감싸면 **정착 뒤에는 `fetch` 까지가 완전히 동기**다.

**회전 판정이 아예 필요 없는 경우가 있다 — 그때는 기다리지도 않는다.** `sessionStorage` 에 값이 **없어서 이번에 새로 만든** id 는 복제될 수가 없다(복제 탭은 저장된 값을 물려받은 탭이다). 그래서:

| 시작 상태 | 질의 | `settled` | 뜻 |
| --- | --- | --- | --- |
| 저장된 값이 없다 → 새로 만듦 | **안 보낸다** | 처음부터 `true` | 평범한 첫 방문·새 탭. **대기 0ms** |
| 저장된 값이 있다 → 그대로 씀 | 보낸다 | 답이 오면 즉시 / 없으면 150ms 뒤 | 새로고침이거나 복제 탭 |

즉 **150ms 대기는 새로고침·탭 복제에서만 생긴다.** 새로고침 뒤 `POST lock` 이 150ms 늦는 것은 F-250 A4 e2e(`e2e/docLock.spec.js` 177~198행, 500ms 기다린 뒤 판정)에 영향이 없다.

### 4.3 겹친 것을 발견한 뒤 무엇을 보여주는가 — **새 UI 가 없다. F-213 의 기존 흐름 그대로**

**결정: 회전한 탭은 "다른 세션" 이 되고, 그다음은 F-213 이 원래 하던 대로 한다.**

- 원래 탭이 그 문서의 잠금을 쥐고 있으면 → 회전한 탭의 `POST lock` 이 `423` → `useDocLock.ts` 101~104행이 읽기 전용 + `다른 창에서 편집 중입니다. 읽기만 할 수 있습니다.`(21~24행, 같은 계정이라 이 문구가 나온다) + 15초마다 재시도. 원래 탭이 문서를 떠나거나 닫히면 `이제 편집할 수 있습니다.`(74행)와 함께 되잡는다
- 원래 탭이 **그 문서를 열고 있지 않으면** → 회전한 탭이 잠금을 정상으로 잡는다. **읽기 전용이 되지 않는다.** 회전이 곧 읽기 전용이라는 뜻이 아니다 (7장 A7 이 이것을 지킨다)

**"이미 겹친 채로 저장이 나간 뒤" 라는 상태는 이 설계에서 생기지 않는다.** 세션 id 를 싣는 요청 세 개가 전부 게이트 뒤에 있기 때문이다(4.2). 그래서 사후 복구 UI(`새 문서로 저장` 같은 것)를 두지 않는다. 남는 구멍은 둘뿐이고 둘 다 감지 자체가 불가능한 경우다:

| 남는 경우 | 결과 |
| --- | --- |
| `BroadcastChannel` 이 없는 브라우저 | 지금과 같다 — 구멍이 그대로 남는다 (4.4) |
| 배포 중이라 한쪽 탭이 **옛 번들**이라 응답자가 없다 | 그 조합에서만 지금과 같다. 양쪽이 새 번들이 되면 사라진다 |

**회전한 쪽이 "원래 탭" 일 수도 있다 — 그래도 그대로 둔다.** 복제 탭 B 가 있는 상태에서 원래 탭 A 가 새로고침하면, 질의를 보낸 쪽은 A 이므로 **A 가 회전한다.** A 는 자기 잠금을 되잡지 못하고 최대 60초(`worker/locks.ts` 8행 `LOCK_DURATION_MS`) 읽기 전용이 된다 — F-250 이 없애려던 그 60초다. 다만 (ㄱ) 그 상황은 복제 탭이 있을 때만 생기고, (ㄴ) 그때 화면에 뜨는 `다른 창에서 편집 중입니다` 는 **사실 맞는 말**이며, (ㄷ) B 가 그 문서를 열고 있지 않으면 잠금이 60초 안에 만료해 15초 재시도가 되찾는다. 누가 서버 잠금을 쥐고 있는지까지 물어 정하는 안은 11장 Q2.

### 4.4 `sessionStorage` 를 못 쓰는 환경

F-250 3.1 이 정한 대로 `sessionStorage` 접근이 던지면 메모리 값으로 간다(`docsApi.ts` 55~58행). 그 환경에서는:

- **페이지 로드마다 새 id** 가 만들어진다 → 저장된 값이 없는 것과 같아 **질의를 보내지 않고 곧바로 `settled`** 다 (4.2 표 1행). 대기 0ms
- 탭을 복제해도 **복사될 저장값이 없으므로** 겹치지 않는다. 이 환경에는 애초에 구멍이 없다
- 대신 F-250 이 고친 "새로고침해도 같은 id" 도 원래부터 없다. **이 명세가 그것을 더 나쁘게 하지 않는다**
- 회전이 일어났을 때 `sessionStorage` 에 새 값을 쓰는 것도 `try/catch` 로 감싼다. 못 써도 이번 탭 수명 동안은 메모리 값으로 맞게 동작한다
- **응답자는 이 환경에서도 켠다.** 자기 id 를 물어보는 탭이 있으면 답해야 한다

### 4.5 같은 증상을 내는 다른 경로

먼저 **앱 안에는 그런 경로가 없다.** `grep -rn "window\.open" src/` 결과는 `src/editor/preview/links.ts` 135행 하나이고 `'noopener,noreferrer'` 를 넘긴다. F-296 4.1 이 새로 넣는 `window.open(…, '_blank', 'noopener')` 도 안전하다(F-296 5.2·8.2, 6.2 에서 재확인함).

브라우저 쪽 경로:

| 경로 | 겹치나 | 근거 |
| --- | --- | --- |
| 크롬 `탭 복제` | **겹친다** — 이 명세의 출발점 | 실제 메뉴는 Playwright 로 못 누른다. 같은 방식으로 새 최상위 브라우징 컨텍스트를 만드는 `window.open(url, '_blank')`(noopener 없음)에서 `sessionStorage` 가 복사되는 것을 6.2 에서 실측했다. **실제 메뉴 확인은 10장 H1** |
| `window.open(url, '_blank')` — `noopener` 없음 | **겹친다** | 6.2 실측 (`SESSION-A` 가 그대로 보였다) |
| `window.open(url, '_blank', 'noopener')` | 안 겹친다 | 6.2 실측 (`null`) |
| `<a target="_blank">` / 가운데클릭 | 안 겹친다 | 크롬이 `noopener` 를 기본 적용한다 (F-296 8.2) |
| 주소창에 붙여넣은 새 탭, `Ctrl+T` | 안 겹친다 | 6.2 — 같은 컨텍스트의 평범한 새 페이지도 `md.lockSession` 이 `null` 이었다 |
| `Ctrl+Shift+T`(닫은 탭 복원), 브라우저 재시작 세션 복원 | **겹치지 않는다** | 복원은 **닫힌 탭**을 되살리는 것이라 원본이 살아 있지 않다. 다만 크롬이 복원 시 `sessionStorage` 를 되살리는지는 자동화로 확인하지 못했다 — **10장 H2** |
| 탭을 창 밖으로 끌어내기(`새 창으로 이동`) | 안 겹친다 | 복사가 아니라 이동이다 |
| 시크릿 창·다른 프로필 | 안 겹친다 | 저장소가 통째로 따로다 |

**열거에 기대지 않는다.** 이 설계가 잡는 것은 "**새로 뜬 탭이 이미 살아 있는 탭의 id 를 들고 시작하는 것**" 이고, 복사가 어떤 메뉴로 일어났는지는 상관이 없다. 위 표에 없는 경로가 나중에 생겨도 같은 방식으로 걸린다.

## 5. 설계

### 5.1 F-296 것을 어떻게 재사용하나 — **채널 이름·대기 시간은 공유, 채널 객체는 따로**

F-296 은 `src/app/tabSync.ts` 6.1 에 `TAB_CHANNEL_NAME = 'md-tabs'`, `CLAIM_WAIT_MS = 150`, 탭 id 생성 함수를 둔다. 그 셋을 **`src/lib/tabChannel.ts`** 로 옮기고 `tabSync.ts` 는 거기서 가져와 그대로 다시 내보낸다.

```ts
// src/lib/tabChannel.ts (신규)
export const TAB_CHANNEL_NAME = 'md-tabs'   // 저장소 식별자에 제품명을 쓰지 않는다 (CLAUDE.md 불변조건)
export const CLAIM_WAIT_MS = 150
export function newTabId(): string { /* crypto.randomUUID(), 없으면 Date.now()+random */ }
```

```ts
// src/app/tabSync.ts (F-296) — 두 줄만 바뀐다
export { TAB_CHANNEL_NAME, CLAIM_WAIT_MS, newTabId } from '../lib/tabChannel'
```

- **왜 옮기나**: `src/storage/lockSession.ts` 가 이 값들을 써야 하는데, `specs/architecture.md` 71행이 의존 방향을 `app → storage` 로 못박았다. `storage → app` import 는 금지이고 `storage → lib` 는 허용이다. `lib/` 는 "순수 함수, DOM·React·CM6 없음"(43행)인데 이 파일은 상수와 uuid 생성뿐이라 조건을 지킨다
- **re-export 로 두는 이유**: `src/app/useTabSync.ts`·`src/app/App.tsx` 의 import 문이 안 바뀐다. F-296 구현이 끝난 직후에 들어가므로 충돌면을 최소로 한다
- **F-296 구현이 이름을 다르게 두었으면 그 이름을 따른다.** 옮기는 대상은 이름이 아니라 "채널 이름 상수 · 클레임 대기 시간 상수 · 탭 id 생성 함수" 셋이다

**채널 객체는 따로 만든다.** F-296 의 채널은 `useTabSync` 가 `bootPhase === 'ready'` 에 열고 언마운트에 닫는다(F-296 6.3). F-297 의 채널은 **모듈 평가 때** 열려야 하고 탭이 죽을 때까지 닫지 않는다 — 수명이 다르다. 같은 탭 안에 `md-tabs` 채널 객체가 둘 생기는데, 6.3 에서 실측한 대로 **같은 탭의 다른 채널 객체는 서로의 메시지를 받는다.** 그래서:

- F-296 의 리듀서는 `session-query`·`session-hold` 를 **무시해야 한다**(kind 로 갈라지므로 구조상 그렇지만, 8장 U15 로 못 박는다)
- F-297 의 리듀서는 `docs-changed`·`claim-*` 및 객체가 아닌 값을 **무시해야 한다** (U8)
- 두 프로토콜의 `tabId` 는 서로 달라도 된다. 각자 자기 것만 견주므로 섞이지 않는다

### 5.2 메시지 (2종)

```ts
// src/storage/lockSession.ts
export type LockSessionMessage =
  | { kind: 'session-query'; tabId: string; sessionId: string }   // "이 id 를 내가 쓴다. 쓰는 탭 있나"
  | { kind: 'session-hold';  tabId: string; sessionId: string }   // "내가 쓰고 있다"
```

- `release` 가 없다. 세션 id 는 탭이 죽으면 같이 사라지고, 살아 있는 동안만 겹침이 뜻을 가진다
- 문서 id·본문·이메일을 싣지 않는다. 다른 탭에 나가는 값은 **임의의 uuid 두 개**뿐이다

### 5.3 순수 리듀서와 구동부

```ts
// 순수 — DOM·채널·타이머를 모른다. node 단위 테스트가 이것만으로 8장 U4~U8 을 판정한다
export type LockSessionAction = { type: 'none' } | { type: 'reply-hold' } | { type: 'rotate' }

export function reduceLockSessionMessage(
  state: { tabId: string; sessionId: string; waiting: boolean },
  msg: unknown,
): LockSessionAction
```

| 받은 것 | 결과 |
| --- | --- |
| 객체가 아니거나 `kind` 가 두 종이 아니다 | `none` (F-296 메시지가 같은 채널로 들어온다) |
| `msg.tabId === state.tabId` | `none` (자기 무시 — F-296 6.1 과 같은 규칙) |
| `msg.sessionId !== state.sessionId` | `none` |
| `session-query` | `reply-hold` — **`waiting` 여부와 상관없이 답한다** |
| `session-hold`, `waiting === true` | `rotate` |
| `session-hold`, `waiting === false` | `none` — 정착한 탭은 남의 답에 흔들리지 않는다 |

**둘 다 `waiting` 인 드문 경우**(복제를 연달아 두 번 했거나, 원래 탭이 새로고침하는 동안 복제 탭이 떠 있는 경우)에는 서로의 질의에 서로 답해 **둘 다 회전한다.** 옛 id 는 아무도 안 쓰게 되고 두 탭은 서로 다른 새 id 를 갖는다 — 겹침이 없어지므로 목적은 달성된다. 굳이 한쪽만 남기려고 `since` 비교(F-296 6.4 `claimWins`)를 들이지 않는다. 세션 id 는 문서 편집권과 달리 **누가 갖느냐가 아니라 겹치지 않느냐만 중요**하기 때문이다.

구동부(채널·타이머를 주입받는다. 이것도 node 에서 돈다):

```ts
export function startLockSessionGuard(deps: {
  tabId: string
  post: (m: LockSessionMessage) => void
  wait: (ms: number, fn: () => void) => void
  read: () => string | null        // sessionStorage 읽기 (try/catch 안쪽)
  write: (v: string) => void       // sessionStorage 쓰기 (try/catch 안쪽)
}): { handle: (msg: unknown) => void; ready: Promise<void>; settled: () => boolean; current: () => string }
```

- 저장된 값이 있으면 `waiting = true`, `post({ kind:'session-query', … })`, `wait(CLAIM_WAIT_MS, …)`
- `rotate`: 새 uuid 를 만들어 `write` 하고 `waiting = false`, `ready` 를 **즉시** resolve. 타이머는 무시한다
- 타이머가 먼저 끝나면 id 를 그대로 두고 `waiting = false`, `ready` resolve
- 정착 뒤에도 `handle` 은 계속 돈다 — 나중에 나를 복제한 탭에 답해야 한다 (U12). 회전했다면 **새 id 기준**으로 답한다 (U13)

### 5.4 모듈 배선

```ts
// src/storage/lockSession.ts — 모듈 평가 때 한 번
export function getLockSessionId(): string
export function isLockSessionSettled(): boolean
export function lockSessionReady(): Promise<void>
```

- `typeof window === 'undefined' || typeof BroadcastChannel === 'undefined'` 면 채널을 만들지 않고 `settled = true` 로 시작한다. **테스트 환경(`vite.config.ts` 227행 `environment: 'node'`)이 여기로 떨어져** 단위 테스트가 실제 채널을 열지 않는다
- 아니면 `new BroadcastChannel(TAB_CHANNEL_NAME)` 을 열고 `onmessage` 를 `handle` 에 잇는다. **닫지 않는다** — 탭이 죽을 때 같이 사라진다
- `docsApi.ts` 의 세 함수는 이렇게 시작한다

```ts
if (!isLockSessionSettled()) await lockSessionReady()
```

| 함수 | 세션 id 를 어디에 쓰나 |
| --- | --- |
| `updateDoc(id, body)` (128행) | `headers['X-Lock-Session'] = getLockSessionId()` |
| `lockDoc(id)` (155행, 인자에서 `sessionId` 제거) | `jsonInit({ sessionId: getLockSessionId() }, 'POST')` |
| `unlockDoc(id, opts)` (170행, 인자에서 `sessionId` 제거) | `?session=${encodeURIComponent(getLockSessionId())}` |

### 5.5 `useDocLock` 이 바뀌는 곳 (3줄)

| 행 | 지금 | 뒤 |

## 6. 실측 (이 PC, 2026-09-21. 추정이 아니라 직접 돌려 얻은 값)

Playwright `channel: 'chrome'` 헤드리스, `HeadlessChrome/153.0.0.0`, Windows 11. 스크립트는 스크래치패드에 두었고 저장소에 남기지 않는다.

### 6.1 Playwright 로 `탭 복제` 를 흉내 낼 수 있는가 — **된다**

한 컨텍스트에서 같은 원본을 연 페이지들로 실험했다.

| 실험 | 결과 |
| --- | --- |
| `context.newPage()` 로 연 평범한 페이지가 보는 `sessionStorage['md.lockSession']` | **`null`** — 같은 컨텍스트라도 `sessionStorage` 는 **공유되지 않는다**. 그냥 새 페이지로는 복제를 흉내 낼 수 없다 |
| `page.addInitScript(sid => sessionStorage.setItem('md.lockSession', sid))` 뒤 `goto` | 페이지 첫 스크립트가 **`SESSION-A` 를 본다** → 복제 탭과 같은 출발 상태다. **이 방법을 7장 e2e 가 쓴다** |
| 위 페이지에서 값을 `ROTATED` 로 바꾸고 `reload()` | 다시 **`SESSION-A`** 가 된다 — `addInitScript` 는 새로고침 때도 다시 돈다. **복제 탭을 새로고침하는 테스트는 쓰지 않는다** (회전 결과가 덮인다) |

### 6.2 `sessionStorage` 가 복제되는 경로 (4.5·2.1 의 근거)

원래 탭에 `sessionStorage['md.lockSession'] = 'SESSION-A'` 를 넣고 열었다.

| 여는 방법 | 새 탭이 보는 값 |
| --- | --- |
| **`window.open(url, '_blank')`** (noopener 없음) | **`SESSION-A`** — 복제된다 |
| `window.open(url, '_blank', 'noopener')` | `null` |
| `context.newPage()` + `goto` (= `Ctrl+T` 로 새로 여는 것) | `null` |

F-296 8.2 와 같은 결론이다(그 명세는 `<a target="_blank">` 까지 쟀다). **크롬 `탭 복제` 메뉴 자체는 자동화로 누를 수 없어 재지 못했다 — 10장 H1.**

### 6.3 같은 탭 안의 두 `BroadcastChannel` (5.1 의 근거)

한 페이지에서 `md-tabs` 채널 객체 두 개(`a`, `b`)를 열고 각각 하나씩 보냈다.

| 보낸 쪽 | 받은 쪽 |
| --- | --- |
| `a` 가 `session-query` | **`b` 가 받았다.** `a` 자신은 못 받았다 |
| `b` 가 `docs-changed` | **`a` 가 받았다.** `b` 자신은 못 받았다 |

→ F-296 의 채널이 F-297 메시지를 **반드시 받는다.** 양쪽 리듀서가 모르는 `kind` 를 무시해야 한다는 요구(5.1)가 실제로 필요하다.

### 6.4 질의 → 응답 왕복 시간 (`CLAIM_WAIT_MS` 150ms 의 근거)

복제 탭이 `session-query` 를 보내고 원래 탭의 `session-hold` 가 돌아오기까지. 원래 탭은 **배경**에 두고 20회.

| | 값 |
| --- | --- |
| 중앙값 | **0.30ms** |
| 최대 | **0.60ms** |
| 최소 | 0.20ms |

→ **150ms 는 실측 최대의 250배**다. F-296 8.5 가 잰 값(중앙값 0.20ms / 최대 2.40ms, 응답 탭 3개 배경)과 같은 자릿수다. 더 줄일 이유도, 늘릴 이유도 없어 F-296 의 상수를 그대로 쓴다.

또 **아무도 그 id 를 안 쓰고 있을 때는 300ms 를 기다려도 답이 오지 않는 것**을 확인했다(거짓 회전이 없다).

`src/storage/` 가 `src/app/` 을 import 할 수 없다는 `specs/architecture.md` 71행 때문이다. re-export 로 두면 F-296 의 다른 파일은 안 바뀐다.
→ **안 옮기기로 하면**: F-297 이 `'md-lock-session'` 같은 **자기 채널 이름**을 `src/storage/lockSession.ts` 안에 따로 둔다. F-296 파일을 한 줄도 안 건드려도 되고(1장에서 `src/app/tabSync.ts`·`tabSync.test.ts` 두 줄이 빠진다), 같은 탭 안 채널 교차(6.3)도 없어져 U8·U15 가 필요 없어진다. 대신 `md-tabs` 와 `md-lock-session` 두 이름이 생기고, "탭 사이 신호는 `md-tabs` 하나" 라는 규칙이 깨진다. **사용자 지시가 "F-296 이 만든 것을 재사용" 이라 기본값을 옮기는 쪽으로 뒀다.**

### Q2. 겹쳤을 때 **누가** 회전할까 — **기본값: 물어본 쪽(나중에 뜬 탭)이 회전한다**

보통은 물어본 쪽이 복제 탭이라 맞다. 어긋나는 경우는 하나다 — **복제 탭이 떠 있는 상태에서 원래 탭이 새로고침하면 원래 탭이 회전해** 최대 60초 읽기 전용이 된다 (4.3).
→ **바꾸려면**: `session-hold` 에 "내가 지금 이 세션으로 서버 잠금을 쥐고 있나"(또는 `since`)를 실어 보내 잠금을 쥔 쪽이 id 를 지키게 한다. 메시지에 필드가 늘고, "쥐고 있다" 를 클라이언트가 어떻게 아는지(마지막 `POST lock` 성공 시각?)를 또 정해야 한다. **겹침 자체가 드문 상황이라 기본값을 권한다.**

### Q3. 회전했다는 것을 사용자에게 알릴까 — **기본값: 알리지 않는다** (4.3)

회전은 내부 사정이고, 사용자가 보는 결과(읽기 전용 안내 또는 정상 편집)는 F-213 이 이미 말해 준다. 세션 id 라는 말을 화면에 꺼낼 이유가 없다.
→ **알리기로 하면**: `specs/ia.md` 6장 UI 문구표에 줄이 하나 늘고(예: `이 탭은 복제된 탭이라 편집 세션을 새로 시작했습니다.`), 알림 띠가 뜨는 시점이 부팅 직후라 다른 알림(저장소 경고 등)과 자리를 다툰다. **안 알리는 쪽을 권한다.**

### Q4. `CLAIM_WAIT_MS` 150ms 를 그대로 쓸까 — **기본값: 그대로 쓴다** (6.4)

실측 왕복 최대 0.60ms 의 250배다. 더 줄이면(예: 30ms) 대기가 짧아지지만, 대기가 붙는 경우 자체가 새로고침·복제뿐이고 그 요청은 전부 배경 요청이라 줄여서 얻을 것이 없다.
→ **바꾸면**: F-296 과 상수를 공유하지 못해 `src/lib/tabChannel.ts` 에 값이 둘 생긴다.

### Q5. 두 탭이 같은 outbox 를 함께 비우는 것 — **이번 범위 밖. 기록만 한다** (3.2)

`serverStore.ts` 455~456행이 저장소를 만들자마자 `kickSend()` 를 부르고, outbox 는 같은 사용자면 탭끼리 공유한다. 탭 B 가 탭 A 가 넣어 둔 `updateDoc` 을 대신 보낼 수 있다. 세션 id 가 갈라진 뒤에는 그 `PUT` 이 `423` 을 받아 F-207 2.4 충돌 사본이 생긴다 — **평범한 두 탭에서 지금도 벌어지는 일**이라 F-297 이 새로 만드는 문제가 아니다.
→ **다루기로 하면**: outbox 소유권을 탭 하나에 주는(F-296 6.4 편집권과 같은 모양) 별도 명세가 필요하다. M3(F-306)이 outbox 의 `updateDoc` 자체를 걷어내므로 **그때 함께 사라질 가능성이 크다.**
