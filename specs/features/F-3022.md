# F-3022 휴지통 열과 조회 거르기
작성일: 2026-10-16
상태: 승인 2026-10-16(사용자 "ㄱㄱ" — F-3021 개요·흐름 [`trash-flow.html`](../wireframes/trash-flow.html)과 함께). F-3021 6장 첫 자식: 마이그레이션, 2장 필터·가드, `deleted` 본문, `docRoomCore` 갈래. 휴지통 행을 만드는 길이 아직 없어 **운영 동작은 바뀌지 않는다**. 전부 node 단위(`testD1` + 실제 핸들러, 테스트가 `deleted_at` 을 직접 채운다), e2e 없음(브라우저로 휴지통 행을 만들 수 없다). 구현 담당 `feature-implementer`. 열린 질문 없음 — F-3021 Q1·Q2 는 기본안으로 승인됐고, 나머지 갈래는 F-3021 결정 4·5장에서 바로 따라 나온다

## 근거 (2026-10-16 작업 트리, 직접 셈)
- `worker/*.ts`(`.d.ts` 제외, 하위 폴더 없음)의 F-3021 정규식은 줄 79곳 = **문자열 조각 78개**(`account.ts` `COUNTS_SQL` 은 두 줄 템플릿 하나). TypeScript AST 로 주인 이름까지 뽑아 아래 3장 표를 만들었다: 막음 48 · 허용 30
- 가짜 D1 테스트 대부분이 `sql.startsWith(...)` 로 맞춘다 → 조건은 **WHERE 맨 끝(ORDER BY·LIMIT 앞)에 붙인다**. 그러면 접두가 그대로라 8장 말고는 깨지지 않는다. `DocRoomHost` 선택 메서드 선례 `getAlarm?`·`lastPing?`

## 2. 마이그레이션
`0027` 번호는 F-4009(OAuth 표 `0028`)와 맞췄다. 기존 행은 셋 다 `NULL` = 살아 있음. 행 읽는 코드는 **`deleted_at` 이 숫자일 때만** 휴지통으로 본다(열을 안 주는 가짜 D1 이 `undefined` 를 돌려도 살아 있음)

## 3. 거르기 (F-3021 2장 표를 주인 이름으로 확정)

## 4. 가드 `tests/worker/trashFilter.test.ts` (계약 — F-3023·이후 명세가 고친다)
- `typescript`(이미 devDependency)로 `worker/*.ts`(`.d.ts` 제외)를 파싱해 문자열·템플릿 조각마다 정규식 `/(FROM|JOIN|UPDATE|INTO) docs\b|docs d\b/` 를 본다. 조각에 `deleted_at` 이 있으면 통과
- 없으면 **주인** = 가장 가까운 함수·메서드 선언 이름, 없으면 그 조각을 품은 최상위 `const` 이름. (파일, 주인)별 개수가 `ALLOW: { file: string; owner: string; count: number; reason: string }[]` 와 **정확히** 같아야 한다 — 허용된 함수에 질의가 하나 늘어도 걸린다. 목록에 있는데 0개인 항목도 실패(죽은 허용)
- 실패 메시지에 파일·주인·줄·조각 앞 80자. 개수가 지금 78/48/30 인지는 단언하지 않는다(새 질의마다 깨지지 않게)

## 5. `deleted` 본문 (F-3021 2장 끝)
```ts
// worker/access.ts — 404 갈래에서만 부른다. ownerId 를 주면 그 소유자 행만
export async function findTrashedDoc(env: Env, docId: string, ownerId?: string): Promise<DocRowLike | null>
```
- `getDocAccess` 는 `WHERE id = ? AND deleted_at IS NULL`. 휴지통 판정은 이 404 갈래로만 하므로 정상 경로 질의 수는 그대로
- `GET /api/docs/:id`(`handleGetDoc`): `getDocAccess` 가 `null` 이면 `findTrashedDoc(id)` → 행이 있고 `resolveDocAccess` 가 `null` 이 아니면 404 `{ "error": "deleted" }`, 아니면 지금처럼 `not_found`. 금고 문서는 `resolveDocAccess` 가 소유자만 통과시킨다
- `/pub` (`pubResponse`, 모두 링크 주인 `findTrashedDoc(id, link.owner_id)` 이고 `e2ee_key` 없음일 때): `handlePublicGetDoc` 시작 문서 · `handlePublicGetDocSet` 시작 문서가 결과에 없을 때(묶음 전체가 `deleted`) · `handlePublicGetDocSetDoc` 묶음 안 문서 · `handlePublicGetFolderDoc` 행의 `folder_id` 가 트리 안일 때. 묶음 목록·폴더 목록에서는 휴지통 문서가 그냥 빠진다
- `handleCreateDoc` id 검사: 행이 내 것이고 휴지통이면 404 `{ "error": "deleted" }`(남의 행은 지금처럼 409 `id_taken`). `/v1` 응답·`commentsApi`·`docSocket` 은 `getDocAccess` 를 따라 `not_found` 그대로

## 6. `docRoomCore` 갈래 (F-3021 5장, 경계는 F-3023 과 맞춤)
- `DocRoomHost` 에 `retire?(): void` — 이 인스턴스를 곧 버린다. `docRoom.ts` 는 `setTimeout(() => ctx.abort('trashed'), PURGE_CLOSE_GRACE_MS)`(`purgeRoom` 과 같은 이유로 미룸)
- 새 private `roomTrashed()`: `closeAll(SOCKET_CLOSE.notFound, 'deleted')` → `markGone()` → `host.retire?.()`. **`store.clear()` 는 하지 않는다**. 버리는 이유: `gone` 인 인스턴스가 남으면 복원 뒤 새 연결도 4404 를 받아 클라이언트가 `md-yjs` 를 지운다
- `readRow`·`ACCESS_ROW_SQL` 결과: 행 없음 → `roomGone()`(지금), `deleted_at` 이 숫자 → `roomTrashed()`. 부르는 곳(`load`·`catchUp`·스냅숏 충돌 뒤 다시 읽기·`revalidateConnections`)의 돌려주는 값은 `roomGone` 갈래와 같다. `writeIdle` 은 `FULL_ROW_SQL` 거르기로 `not_found`
- F-3023 `closeTrashed()` 는 마지막 스냅숏 뒤 `roomTrashed()` 만 부른다. 폴더째 보낼 때 21번째 이후 방은 이 갈래가 다음 D1 확인(접속·편집 충돌·60초 `revalidateConnections`) 때 닫는다(F-3021 Q1, 승인)

## 8. 기존 테스트 회귀 (grep, 돌리지 않음)
- `access.test.ts` 60행 `sql.endsWith(' FROM docs WHERE id = ?')` → `deleted_at IS NULL` 로 끝나는 문장도 받게, 422행 기대 문자열 끝에 ` AND deleted_at IS NULL`
- `docRoomCore.test.ts` 81행 `hidden` 의 `endsWith(' AND e2ee_key IS NULL')` → `includes`, 82·90행 접두(열 끝 `, deleted_at`), 744행 `FULL_ROW_SQL` 기대 문자열, 1434행 접두. 가짜 행은 `deleted_at` 이 없어도 된다(2장)
- `links.test.ts` 75행 `... WHERE owner_id = ? ORDER BY updated_at DESC` 접두 → 조건이 ORDER BY 앞에 끼므로 고친다
- 위 셋 밖의 `startsWith` 가짜는 그대로. 새 `findTrashedDoc` 질의(404 갈래만)를 가짜가 모르면 `unhandled sql` 로 던진다 — 그 갈래를 타는 가짜 테스트는 grep 으로 못 찾았다. 나오면 `null` 갈래를 더한다
