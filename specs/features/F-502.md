## 2. 마이그레이션 — 최종 DDL (계약)

번호: 지금 마지막이 `0011_e2ee.sql` 이라 **`0012_comments.sql`**. F-2038 의 `0012_purge_jobs.sql` 이 먼저 커밋돼 있으면 **`0013_comments.sql`**(F-2038 1장이 같은 규칙을 적었다). 개요 3.3 에 F-501 Q2 의 두 열을 더한 그대로다. 열 순서·이름·기본값이 계약이다

```sql
-- F-502 댓글 복사본·알림 (specs/features/F-500.md 3.3, F-502.md 2장)
CREATE TABLE doc_comments (          -- comments Y.Map 의 한쪽 방향 복사본. 원본은 DO
  doc_id TEXT NOT NULL,
  id TEXT NOT NULL,                  -- Y.Map 키
  parent_id TEXT,                    -- 답글이면 첫 댓글 id
  author_id TEXT,
  author_email TEXT,
  body TEXT NOT NULL,
  mentions TEXT NOT NULL DEFAULT '[]',   -- JSON 배열 (항목의 mentions 그대로)
  quote TEXT NOT NULL DEFAULT '',
  prefix TEXT NOT NULL DEFAULT '',   -- 앵커 앞 최대 32자
  suffix TEXT NOT NULL DEFAULT '',   -- 앵커 뒤 최대 32자
  anchor_from INTEGER,               -- DO 본문(LF) 기준 UTF-16 위치 힌트. NULL = 답글 또는 고아
  anchor_length INTEGER,             -- 앵커 길이. NULL = 답글 또는 고아
  resolved_at INTEGER,
  resolved_by TEXT,                  -- 해결한 사람 이메일
  resolved_by_id TEXT,               -- 해결한 사람 id
  created_at INTEGER NOT NULL,
  bytes INTEGER NOT NULL,            -- body·quote·prefix·suffix 의 UTF-8 바이트 합. 쓰는 문장이 SQL 안에서 계산한다
  sig TEXT NOT NULL,                 -- commentSig (F-501 7.1)
  anchor_sig TEXT NOT NULL,          -- recordAnchorSig (F-501 7.1)
  PRIMARY KEY (doc_id, id)
);
CREATE TABLE notifications (
  id TEXT PRIMARY KEY,               -- crypto.randomUUID()
  recipient_email TEXT NOT NULL,     -- 소문자
  kind TEXT NOT NULL CHECK (kind IN ('mention','reply')),
  doc_id TEXT NOT NULL,
  comment_id TEXT NOT NULL,
  thread_id TEXT NOT NULL,           -- 첫 댓글 id
  actor_email TEXT NOT NULL,
  doc_title TEXT NOT NULL,           -- 만들 때의 제목(최대 500자)
  excerpt TEXT NOT NULL,             -- 댓글 본문 앞 120자 (6.5)
  created_at INTEGER NOT NULL,       -- 서버 시각 ms
  read_at INTEGER,
  UNIQUE (recipient_email, comment_id, kind)
);
CREATE INDEX notifications_recipient ON notifications(recipient_email, created_at DESC);
CREATE INDEX notifications_doc ON notifications(doc_id);
```

- 개요 3.3 과 다른 곳은 주석뿐이다(`bytes` 를 SQL 이 계산한다, `recipient_email` 은 소문자, `created_at` 은 서버 시각)
- `doc_comments` 에 따로 색인을 두지 않는다. DO 의 모든 질의가 `doc_id = ?` 로 시작해 기본키 앞머리를 탄다(s6). Cron 의 "없는 문서" 질의만 표 전체를 읽는다(10장)
- 표 이름에 제품명이 없다(불변조건). `docs` 에 외래 키를 걸지 않는다(개요 3.3)
- 원격 적용은 배포 직전 한 번(F-500 6장 "배포", `deploy` 스킬). 이 명세의 코드만 먼저 배포돼도 표가 없으면 DO 불러오기의 복사본 읽기가 던진다 → **마이그레이션이 코드보다 먼저다**(14장 H1)

## 3. 사후 검사 — edit 이상의 직접 쓰기 (개요 3.2)

### 3.1 어디서, 어떤 트랜잭션에

- `DocRoomCore.load` 가 끝난 뒤(지금 `doc.on('update')` 를 거는 자리와 같은 때) `comments` `Y.Map` 에 `observe` 를 하나 건다. 불러오기 중 저장소 행을 적용하는 트랜잭션·씨앗 심기·복원은 관찰되지 않는다
- 관찰은 **모든 origin** 에서 두 가지를 한다: 바뀐 키를 "D1 에 알릴 키"(4.2 `dirty`)에 더하고, 앵커 다시 적기 표지(4.5 `anchorsDirty`)를 켠다
- **검사·고치기는 연결에서 온 트랜잭션에서만** 한다. 판정:
  - origin 이 서버 origin 집합(`SERVER_ORIGINS`: `ABSORB_ORIGIN`·`WRITE_ORIGIN`·새 `COMMENT_FIX_ORIGIN`. F-503 이 자기 origin 을 여기에 더한다 — 11.1)에 있으면 검사하지 않는다
  - 그 밖이면 연결로 본다. y-partyserver 2.2.0 은 받은 갱신을 그 `Connection` 을 origin 으로 적용한다(`handleMessage` → `readSyncMessage(…, connection, …)`). 행위자 = `readConnState(origin.state)`. 읽을 수 없으면(`null`) **행위자 없음** — 그 트랜잭션의 댓글 변경을 모두 되돌린다(3.3 규칙 0)
- 본문만 바꾼 트랜잭션에서는 `comments` 관찰이 불리지 않는다 — 비용 0(개요 3.2)
- 고치기는 관찰 콜백 안에서 **`COMMENT_FIX_ORIGIN` 트랜잭션 하나**로 쓴다. 그 트랜잭션의 관찰은 서버 origin 이라 검사하지 않고 끝난다 → **무한 루프가 없다**(s1: 연결 갱신 3번에 관찰 5번으로 끝남). 고치기 갱신은 원래 갱신 뒤에 따로 나가 모든 연결(보낸 연결 포함)에 퍼지고, `pending` 에 쌓여 DO SQLite 에 남는다(지금 `doc.on('update')` 그대로)

### 3.2 순수 판정 — `planCommentFixes` (계약)

```ts
// worker/commentGuard.ts
import type { CommentEntry } from '../src/lib/docComments'
export type CommentChange = { key: string; action: 'add' | 'update' | 'delete'; oldValue: unknown }
export type CommentFixActor = { userId: string; email: string; role: 'owner' | 'edit' | 'view' }
export type CommentFix = { op: 'set'; key: string; value: CommentEntry } | { op: 'delete'; key: string }
export function planCommentFixes(
  after: ReadonlyMap<string, unknown>,       // 트랜잭션 뒤 comments 전체 (Y.Map 의 entries 를 Map 으로)
  changes: readonly CommentChange[],          // YMapEvent.changes.keys 를 옮긴 것
  actor: CommentFixActor | null,              // null = 행위자 없음
): CommentFix[]
```

- DO 는 결과를 순서대로 `Y.Map` 에 적용한다(`set` → `map.set`, `delete` → `map.delete`). 결과가 비면 트랜잭션을 열지 않는다
- 권한은 F-501 `commentAllowed({ kind: 'server', userId, role, blocked: false }, …)` 로 판정한다. `blocked` 가 늘 `false` 인 이유: 연결은 막힌 계정이면 붙지 못하고(F-2030), 붙은 뒤 막히면 60초 점검이 닫는다. 그 사이의 댓글은 본문 편집과 같이 받아 준다
- 모양은 `isCommentId`·`validateCommentEntry`, 묶기는 `groupCommentThreads`, 한도는 `COMMENTS_PER_DOC_MAX`·`REPLIES_PER_THREAD_MAX` — 모두 F-501 의 커밋된 export 를 그대로 부른다

### 3.3 규칙 — 순서가 계약이다

| 단계 | 대상 | 판정 | 고치기 |
| --- | --- | --- | --- |
| 0 | 행위자 없음 | 모든 변경 | `add` → `delete`. `update`·`delete` → 옛 값이 `validateCommentEntry` 를 통과하면 `set` 옛 값, 아니면 `update` 는 `delete`, `delete` 는 그대로 둔다. 여기서 끝(1~5 를 하지 않는다) |
| 1 | `delete` — 옛 값이 올바르지 않음 | 허용 | 없음 |
| 1 | `delete` — 옛 값이 첫 댓글 | `commentAllowed(…, 'delete', 옛 값)` | 거짓이면 `set` 옛 값(되살림) |
| 1 | `delete` — 옛 값이 답글 | `commentAllowed(…, 'delete', 옛 값)` **또는** 같은 트랜잭션에서 그 부모 첫 댓글의 지우기가 허용됨(스레드 삭제는 남의 답글도 함께 지운다, 개요 2.4) | 둘 다 거짓이면 `set` 옛 값 |
| 2 | `update` — 옛 값이 올바르지 않음 | `add` 로 본다(3단계) | — |
| 2 | `update` — 옛 값이 올바름 | 새 값이 `validateCommentEntry` 를 통과하고, 첫 댓글이고, **`resolved` 밖 여덟 필드가 옛 값과 같고**(깊은 비교), `commentAllowed(…, 'resolve')` | 거짓이면 `set` 옛 값. 참이고 새 `resolved` 가 `null` 이 아닌데 `resolved.by` 가 행위자와 다르면 `by` 를 행위자 `{ id: userId, email }` 로 바꿔 `set` |
| 3 | `add` | 키가 `isCommentId` 가 아니거나 값이 `validateCommentEntry` 를 통과하지 못함 | `delete` |
| 3 | `add` | 통과 | `author` 가 행위자와 다르면 행위자로, `resolved` 가 있으면 그 `by` 도 행위자로 바꿔 `set`(다시 도장). 같으면 없음 |
| 4 | 1~3 을 적용한 뒤의 전체 | `groupCommentThreads` 의 `invalid`·`strays` | 전부 `delete` — 부모가 지워져 남은 답글, 답글의 답글, 모양이 틀린 옛 값까지 이번에 치운다 |
| 5 | 4 뒤의 전체 | 개수(스레드 + 답글) > 500, 스레드 답글 > 100 | **이번 트랜잭션에 `add` 된 키 중에서만** `createdAt` 이 늦은 것부터(같으면 id 사전순으로 뒤쪽부터) 넘친 수만큼 `delete`. 스레드 한도를 먼저, 문서 한도를 나중에. 있던 항목은 한도로 지우지 않는다 |

- 같은 키에 여러 고치기가 나오면 마지막 것 하나만 돌려준다
- 3단계 다시 도장의 이유: 로컬 작성자(`{ id: null, email: null }`) 모양으로 온 항목은 `mentions` 가 비어 있어야 통과하므로 도장만 바꾸면 계속 올바르다. `resolved.by` 를 같이 바꾸지 않으면 `validateCommentEntry` 11번("`by.id === null` 과 `author.id === null` 이 같아야")에 걸린다
- 2단계 "`resolved` 밖 여덟 필드" = `v`·`parent`·`anchor`·`quote`·`body`·`mentions`·`author`·`createdAt`. 앵커도 바꿀 수 없다(개요 2.4 "남의 댓글 본문·앵커·작성자 바꾸기 — 아무도")
- **정직한 클라이언트는 어느 규칙에도 걸리지 않는다** — 결과가 빈 배열이다(G1). F-505 가 같은 권한·한도를 화면에서 먼저 막는다
- **알려진 한계** (개요 3.2 그대로 + 하나): ① DO 저장소를 잃은 뒤 누군가의 `md-yjs` 가 남의 옛 댓글을 다시 보내면 보낸 사람으로 다시 도장된다 ② 고치기는 원래 갱신이 다른 접속자에게 먼저 퍼진 뒤 따라간다 — 잠깐 보였다 바뀐다 ③ 받은 갱신이 앞선 갱신을 기다리던(pending) 구조를 함께 풀면, 풀린 구조도 뒤 갱신을 보낸 연결의 것으로 검사된다. 같은 방의 클라이언트는 서버를 거쳐서만 서로의 항목을 보므로 ①과 같은 사고(저장소 손실) 밖에서는 생기지 않는다

## 4. D1 파생 — 스냅숏 batch 의 댓글 묶음 (개요 3.3)

### 4.1 DO 가 들고 있는 것

| 이름 | 내용 | 채우는 때 |
| --- | --- | --- |
| `known` | `Map<id, { sig, anchorSig }>` — "D1 에 있는 것" | 불러올 때 `SELECT id, sig, anchor_sig FROM doc_comments WHERE doc_id = ?`(씨앗 가지는 5장의 전체 행 읽기로 대신). batch 가 던지지 않고 돌아온 뒤 그 batch 의 upsert·지우기대로 고친다 |
| `dirty` | D1 과 대조할 키 집합 | 3.1 관찰(모든 origin). **불러올 때 `Y.Map` 의 모든 키 + `known` 의 모든 키**(DO 가 D1 쓰기 전에 내려갔던 경우를 맞춘다) |
| `anchorsDirty` | 마지막 전체 다시 적기 뒤 본문이나 댓글이 바뀌었나 | `doc.on('update')`(지금 `pending` 에 넣는 처리기)에서 켠다. 복원·`applyExternal` 도 여기서 켜진다 |
| 접근 집합 보관 | `{ at, people }` | 6.3 |

- 불러온 뒤 `Y.Map` 이나 `known` 에 항목이 하나라도 있으면, 본문이 D1 과 다를 때와 **같은 `LOAD_FLUSH_DELAY_MS` 타이머**를 건다(이미 걸렸으면 하나로). 연결이 편집 없이 머물러도 대조가 한 번 돈다
- `roomGone`·`purge` 는 셋을 모두 비운다

### 4.2 스냅숏마다 — 무엇을 쓰나

`snapshot()` 은 지금 "본문이 같으면 곧바로 `'ok'`" 로 끝난다. 이것을 **본문 쪽과 댓글 쪽을 따로 판정**하도록 바꾼다

- **댓글 쪽 판정**: `groupCommentThreads(map.entries())` 한 번(500개 1.3ms, s5)으로 "살아 있는 항목"(스레드의 첫 댓글 + 답글, `invalid`·`strays` 제외)을 정한다
  - 보통 스냅숏: `dirty` 의 키만 본다. 살아 있으면 `commentSig` 를 `known` 과 비교해 다르거나 없으면 upsert 대상. 살아 있지 않은데 `known` 에 있으면 지우기 대상
  - 전체 다시 적기(4.5): 위에 더해 살아 있는 모든 첫 댓글의 기록을 만들어 `recordAnchorSig` 가 `known.anchorSig` 와 다른 것을 upsert 대상에 더한다
  - upsert 대상 행 = `toCommentRecord(id, entry, content.toString(), range)` 에 `sig`·`anchorSig` 를 더한 객체. `range` 는 첫 댓글이면 `resolveCommentAnchor`(보통 스냅숏, 대상마다) 또는 `resolveCommentAnchors` 결과(전체 다시 적기, 한 번), 답글이면 `null`
  - `known` 에 없는 upsert 대상 = **새 항목** → 알림 후보(6장)
- **본문 쪽 판정**은 지금 그대로(같음·크기 초과·`mayWrite`·조건부 UPDATE·흡수 뒤 한 번 더)
- `mayWrite`(막힌 소유자·느린 저장, F-2027)는 **batch 전체**에 건다 — 걸리면 댓글도 쓰지 않고 `dirty` 를 남긴다
- 두 쪽 다 쓸 것이 없으면 batch 가 없다. **댓글 변화가 없으면 batch 는 지금과 글자까지 같다**(D3, `docRoomCore.test.ts` "F-2027 C1" 이 그대로 통과)

### 4.3 batch 모양 — 순서가 계약이다

| 경우 | 문장 순서 |
| --- | --- |
| A. 본문이 바뀜 (+ 댓글) | ① `UPDATE_SQL`(지금) ② `snapshotUsageStatement(…, bytes − base.rowBytes)`(지금) ③~ 댓글 묶음(있으면) |
| B. 본문 문장이 없음(본문이 같음·크기 초과), 댓글만 | ① `snapshotUsageStatement(…, 0)` — 하루 +1(F-500 3.8), `RETURNING` 으로 `judgeUsage` ② ~ 댓글 묶음 |

**댓글 묶음** (있는 문장만, 이 순서):

| # | 문장 | 조건 |
| --- | --- | --- |
| c1 | 댓글 바이트 빼기 — 소유자 `content_bytes` 에서 이 문서의 `doc_comments.bytes` 합을 뺀다 | 늘 |
| c2 | upsert — `json_each` 로 여러 행, `INSERT … ON CONFLICT (doc_id, id) DO UPDATE` 로 `doc_id`·`id` 밖 모든 열을 새 값으로. `bytes` 는 SQL 이 `length(CAST(… AS BLOB))` 넷의 합으로 계산. **`WHERE EXISTS (SELECT 1 FROM docs WHERE id = ? AND e2ee_key IS NULL)`** — 지워졌거나 금고가 된 문서에는 한 행도 쓰지 않는다 | upsert 대상이 있을 때. 4.4 대로 나눔 |
| c3 | 지우기 — `doc_comments` 에서 이 문서의 id 목록(`json_each`) | 지우기 대상이 있을 때 |
| c4 | 그 댓글들의 알림 지우기 — `notifications` 에서 이 문서의 같은 id 목록 | c3 과 같이 |
| c5 | 알림 넣기 — `INSERT OR IGNORE`, `json_each`, c2 와 같은 `EXISTS` 조건 | 알림 행이 있을 때. 4.4 대로 나눔 |
| c6 | 받는 사람별 최근 300개만 — c5 의 받는 사람 목록(`json_each`)에 한해, 받는 사람마다 `created_at DESC, id DESC` 로 300개 밖을 지운다(상관 부질의 `ORDER BY … LIMIT`, s6) | c5 와 같이 |
| c7 | 댓글 바이트 더하기 — c1 의 반대 | 늘 |

- **c1·c7 로 누계를 맞추는 이유**: 합을 DO 메모리로 계산하면 "batch 는 커밋됐는데 응답이 실패" 해 다시 보낼 때 두 번 더해진다. 같은 트랜잭션 안에서 앞뒤 합을 빼고 더하면 몇 번을 다시 돌려도 결과가 같고, 어긋난 누계도 그 문서 몫은 저절로 바로잡힌다(s6 에서 되풀이 확인). 문서당 합계는 기본키 색인을 탄다(s6)
- **기존 문장을 고치지 않는다.** `SNAPSHOT_USAGE_SQL` 의 `changes()` 는 바로 앞 문장(①)을 보므로 ①·② 순서는 지금 그대로다. B 에서 첫 문장으로 쓸 때는 두 증감이 0 이라 `changes()` 가 무엇이든 누계가 바뀌지 않는다
- **성공 판정**: batch 가 던지지 않고 돌아오면 댓글 묶음은 커밋된 것이다 — `UPDATE_SQL` 이 0행이어도(흡수 뒤 두 번째 시도로 가는 경우) `known` 을 고치고 처리한 `dirty` 키를 뺀다. 던지면 `known`·`dirty` 를 그대로 두고 지금의 다시 시도(`scheduleRetry`)를 탄다. 두 번째 시도에는 댓글 묶음이 새로 생긴 것만 실린다
- 처리 중에 다시 바뀐 키는 `dirty` 에 남는다 — batch 를 만들기 직전에 이번에 다룰 키를 떼어 두고, 실패하면 되돌려 넣는다
- 댓글은 `docs.updated_at`·`version` 을 올리지 않는다(개요 3.3). B 에는 `UPDATE_SQL` 이 없다

### 4.4 D1 호출당 문장 수 — 결론: 최악 16문장, 한도 50 안

**JSON 나누기**: c2·c5 의 바인딩 JSON 은 **UTF-8 1,000,000 B 이하**로 나눈다(`COMMENT_JSON_CHUNK_BYTES = 1_000_000`). 행 단위로 채우다가 다음 행을 더하면 넘을 때 새 문장을 연다. 근거: D1 바인딩 문자열 한도 2MB(개요 c9), 지금 코드가 한 문장에 묶는 가장 큰 값이 본문 1,000,000 B(s8). 개요 3.3 의 "1,000,000자" 는 한글이면 3MB 라 쓰지 않는다

| 경우 (댓글 500개 = 문서 한도) | 본문 | c1 | c2 | c3·c4 | c5 | c6 | c7 | 합 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 보통 — 새 댓글 1개(멘션 있음) + 본문 편집 | 2 | 1 | 1 | 0 | 1 | 1 | 1 | **7** |
| 댓글만 — 해결 1번 | 1 | 1 | 1 | 0 | 0 | 0 | 1 | **4** |
| 방이 빔, 500개 모두 앵커가 바뀜, 한글로 모든 칸을 끝까지(행 7,509 B, s7) | 2 | 1 | 4 | 0 | 0 | 0 | 1 | **8** |
| 최악 — 제어 문자로 채운 500개 upsert(행 11,298 B, s7) + 지우기 + 알림 2,000행(행 1,486 B, 6.4) | 2 | 1 | 6 | 2 | 3 | 1 | 1 | **16** |

- 개요의 "upsert 2~3" 은 한 행 3.3KB 로 잡은 값이다. 한도 끝까지 채운 행으로 다시 세면 4(한글)~6(제어 문자)이다
- 같은 호출에서 더 도는 질의: 불러오기의 복사본 읽기 1(깨어날 때), 접근 집합 3(60초에 한 번, 알림이 필요할 때만, 7장), 지금의 60초 권한 점검. **DO 호출 하나가 D1 "Worker 호출당 50" 에 그대로 걸리는지는 확인하지 않았다** — 걸린다고 보고 셌다
- 행 쓰기 양: 보통 스냅숏은 바뀐 행만 쓴다. 전체 다시 적기는 `anchor_sig` 가 바뀐 행만(위치 힌트만 움직인 행은 안 쓴다, 개요 3.3)

### 4.5 전체 다시 적기 — 언제

- `roomEmptied()` 의 flush 한 번과 `alarm()` 의 flush 한 번에서만. 방식은 지금 `bypassNext` 와 같은 "다음 한 번" 표지(`fullAnchorsNext`)다 — 도는 flush 에 합쳐지면 뒤이은 한 번에 실린다
- **`anchorsDirty` 가 꺼져 있으면 건너뛴다** — 마지막 전체 다시 적기 뒤 본문도 댓글도 안 바뀌었으면 풀 것이 없다. batch 를 만들기 직전에 끄고, batch 가 실패하면 다시 켠다
- 보통 스냅숏(5초 쉼·30초 최대)에서는 하지 않는다. 그래서 편집 중 D1 의 `anchor_from` 은 새 댓글·바뀐 댓글 말고는 움직이지 않는다(의도, 개요 3.3)
- **알려진 한계**: 방이 며칠씩 비지 않으면 그동안 D1 의 인용문·앞뒤 문맥이 옛 값이다. 복원(5장)은 힌트가 어긋나도 앞뒤 문맥으로 찾는다(F-501 r7, 1MB·500개 0.2ms). 방이 비지 않은 채 DO 저장소를 잃을 때만 문제가 된다 — 16장 Q2

### 4.6 전체 다시 적기의 비용 — DO CPU 판단

| 문서 | 전체 다시 적기(500개) | 비교: 지금 깨어날 때 상태 적용 |
| --- | --- | --- |
| 새로 심은 Doc(항목 1개), 933KB | 12.4ms | 12.8~13.5ms |
| 오래 편집한 Doc(항목 7,978개), 933KB | **214~242ms** (풀기 219ms) | 24.6~31.4ms |

(s2·s3. Node, 이 PC. workerd 에서 재지 않았다)

- **결론: 공개 API 그대로 간다**(F-500 3.3·F-501 3.3 기본값). 한 번 치르는 곳이 "마지막 사람이 나간 순간" 과 "느린 저장 알람" 뿐이고, 본문·댓글이 안 바뀌었으면 건너뛴다. 댓글 50개면 1/10(F-501 r6: 쪼갠 1MB 50개 17.9ms)
- **확인하지 못한 것**: DO 호출 하나의 CPU 한도. F-2038 m5 는 Workers 무료 플랜 요청당 CPU 10ms 를 적었는데 DO 에도 같은 수가 걸리는지는 이 세션에서 확인하지 않았다. 다만 **지금 코드가 쪼갠 1MB 문서를 깨울 때 이미 25~31ms 를 쓴다**(s3). 10ms 가 DO 에 그대로 걸린다면 댓글과 무관하게 이미 넘고 있다. 배포 뒤 대시보드로 본다(14장 H3). 넘치면 16장 Q2 의 안(내부 필드로 한 번 걷기, 1.48ms)으로 `resolveCommentAnchors` 내부만 바꾼다 — F-501 A9 가 결과가 같은지 지킨다

### 4.7 `shortHash` 를 빠르게 (F-501 파일, 내부만)

- 커밋된 `shortHash` 는 `BigInt` 로 곱한다. 500개 대조에 85~92ms(s4) — 불러올 때 모든 키를 대조하고(4.1), 전체 다시 적기마다 `recordAnchorSig` 500번을 부르므로 매번 이만큼 든다
- **16비트 칸 넷으로 곱하는 구현으로 바꾼다.** 같은 FNV-1a 64, 같은 UTF-8 입력, 같은 16진수 16자 출력. 500개 6.8ms(s4). F-501 7.1 표가 두 구현을 "구현이 고를 일" 로 두었고 시험값 넷(B15)이 같음을 지킨다. 이 명세는 긴 입력 둘(한글 1,000자, 제어 문자 섞인 글)에서 BigInt 참조 구현과 같음을 더 단언한다(H1)
- 시그니처·출력·다른 함수는 바꾸지 않는다. 16장 Q1

## 5. 복원 — 씨앗 가지 (개요 3.4)

- `load` 의 씨앗 가지(`rows.length === 0`)에서 본문·제목을 심는 트랜잭션 **뒤, `writeBase` 앞**에 한다:
  1. `SELECT * FROM doc_comments WHERE doc_id = ? ORDER BY created_at, id`
  2. 행이 있으면 행마다 `rowToCommentRecord`(`commentRows.ts`) — 열 → `CommentRecord` 필드. `mentions` 는 `JSON.parse`, 배열이 아니면 `[]`
  3. `restoreCommentEntries(content, records)`(F-501, `importer` 없음) → `entries`
  4. `ABSORB_ORIGIN` 트랜잭션 하나로 `comments` 에 `set`
  5. `known` = 읽은 행의 `id`·`sig`·`anchor_sig`
- 그 뒤 지금처럼 `writeBase(encodeStateAsUpdate(doc))` — 복원한 댓글이 기준 행에 함께 들어간다
- **알림이 다시 생기지 않는다** — 되살린 항목의 필드(`v`·`parent`·`body`·`mentions`·작성자·`createdAt`·해결)가 행과 같아 `commentSig` 가 `known` 의 `sig` 와 같다. 새 항목이 아니다(D9)
- 되살린 앵커 자리의 인용문·앞뒤 문맥은 지금 본문에서 다시 자른 값이라 `anchor_sig` 가 바뀔 수 있다. `anchorsDirty` 가 켜져 있으므로 다음 전체 다시 적기에서 그 행만 쓴다
- 자리를 못 찾은 첫 댓글은 `anchor: null` 로 들어온다(고아). 그 행은 다음 전체 다시 적기에서 `anchor_from`·`anchor_length` 가 `NULL` 이 되고, 이후 다시 찾지 않는다(F-501 4.2)
- 씨앗 가지가 아닌 불러오기(`d1_version` 이 다르거나 같음)에서는 D1 댓글을 `Y.Doc` 에 **쓰지 않는다**. 읽는 것은 `id, sig, anchor_sig` 뿐이다
- 불변조건: 이 자리는 F-301 3.3 이 허락한 "DO 의 최초 씨앗 심기" 와 같은 함수·같은 조건·`blockConcurrencyWhile` 안이다(개요 3.4). 문장 덧붙임은 15장

## 6. 알림 (개요 3.5)

### 6.1 무엇이 새 항목인가

- 4.2 의 "`known` 에 없는 upsert 대상". 같은 batch 가 그 항목의 행을 쓰므로, batch 가 커밋되면 다음 스냅숏부터는 새것이 아니다. batch 가 실패하면 다음 스냅숏에서도 새것이다 — DO 가 내려가도 잃지 않는다(`known` 은 D1 에서 다시 읽는다)
- 작성자 이메일이 `null` 인 항목(로컬 작성자)은 알림을 만들지 않는다. 서버 문서에서는 사후 검사가 다시 도장하므로 생기지 않는다

### 6.2 받는 사람 — `notificationTargets` (`commentRows.ts`, 순수)

```ts
export type NotificationDraft = { recipient: string; kind: 'mention' | 'reply'; commentId: string; threadId: string; actor: string; excerpt: string }
export function notificationTargets(
  item: { id: string; entry: CommentEntry },
  thread: CommentThread | null,          // 답글이면 그 스레드(groupCommentThreads 결과), 첫 댓글이면 null
  people: ReadonlySet<string>,           // 7장 접근 집합의 소문자 이메일
): NotificationDraft[]
```

- 작성자 이메일 `A`(소문자로 비교). `A` 가 없으면 `[]`
- `mention`: `entry.mentions` 중 `people` 에 있고 `A` 가 아닌 것. 순서는 `mentions` 순서
- `reply`(답글일 때만): 그 스레드 첫 댓글 작성자 + 그 답글보다 앞선 답글들(스레드 순서 = `createdAt` → id, F-501 6.2)의 작성자. 소문자, 중복 없음, `A` 제외, `mention` 받는 사람 제외, **`people` 에 있는 것만**. 순서는 첫 댓글 작성자 → 앞선 답글 순
- **`reply` 도 접근 집합으로 거르는 이유**(개요 3.5 는 `mention` 에만 적었다): 스레드에 전에 쓴 사람이 그 뒤 접근을 잃었을 수 있다. 알림에는 문서 제목과 본문 발췌가 들어가므로 접근을 잃은 사람에게 가면 안 된다. 개요 3.5 "나중에 접근을 잃은 사람에게 바뀐 제목이 새지 않는다" 와 같은 뜻이다 — 16장 Q3
- `threadId` = 첫 댓글이면 자기 id, 답글이면 `parent`. `actor` = 작성자 이메일(항목 값 그대로 — 서버가 확인한 값, 개요 3.5 위조 방지). `excerpt` = 6.5

### 6.3 접근 집합 — 언제 읽나

- 새 항목 중 **`mentions` 가 비어 있지 않거나 답글인 것**이 하나라도 있을 때만 `loadDocPeople`(7장)을 부른다. 60초(`REVALIDATE_INTERVAL_MS` 와 같은 값) 안에 읽은 것이 있으면 그것을 쓴다
- `loadDocPeople` 이 던지면 **스냅숏 전체가 실패**한다 → 지금의 다시 시도. 알림 없이 행만 쓰면 그 항목이 "새것" 이 아니게 되어 알림을 영영 잃기 때문이다
- `null`(문서가 없거나 금고)이면 알림 없음. 그 경우 c2·c5 의 `EXISTS` 조건도 아무것도 쓰지 않는다

### 6.4 한 batch 의 알림 상한

- **`NOTIFICATIONS_PER_BATCH_MAX = 2_000`**. 새 항목을 `createdAt` → id 순으로, 각 항목의 `NotificationDraft` 를 6.2 순서로 이어 붙여 앞 2,000개만 쓴다. 넘으면 `console.warn('docRoom: notifications capped (' + docId + ')')` 한 번
- 이유: 받는 사람은 항목당 멘션 10 + 스레드의 앞선 작성자(최대 101)라 이론상 500항목 × 111명까지 갈 수 있다. 문장 수(4.4)를 묶으려면 상한이 필요하다. 2,000 = 행 1,486 B 최악으로 3문장. 실제로 넘으려면 한 스냅숏(최대 30초) 안에 접근 있는 사람 수십 명이 얽힌 새 댓글 수백 개가 있어야 한다 — 16장 Q4

### 6.5 알림 행의 값

| 열 | 값 |
| --- | --- |
| `id` | `crypto.randomUUID()` (다시 돌리면 다른 값이지만 `UNIQUE (recipient_email, comment_id, kind)` 가 막는다, s6) |
| `recipient_email` | 소문자 |
| `doc_title` | 스냅숏 때 `clippedTitle()` (최대 500자). 빈 문자열이면 빈 그대로 — 화면이 `제목 없는 문서`(개요 5.1) |
| `excerpt` | 본문 앞 120 UTF-16 단위. 120번째 단위가 높은 서로게이트면 119. 말줄임표를 붙이지 않고 줄바꿈도 그대로 — 한 줄로 보이는 것은 화면 몫(F-507). 함수 `notificationExcerpt(body)` |
| `created_at` | batch 를 만들 때의 서버 `Date.now()` — 항목의 `createdAt`(클라이언트 시계)이 아니다 |
| `read_at` | `NULL` |

- 댓글을 지우면 c4 가 그 댓글의 알림을 같은 batch 에서 지운다. 스냅숏 전에 지워진 댓글은 행도 알림도 생기지 않는다(개요 3.5)

## 7. 접근 집합 — `loadDocPeople` (개요 3.6)

```ts
// worker/docPeople.ts
export type DocPerson = { email: string; role: 'owner' | 'edit' | 'view' }
export async function loadDocPeople(env: Env, docId: string): Promise<DocPerson[] | null>
```

- **질의 3번 이하**:
  1. 문서와 소유자 이메일 — `docs` 와 `users` 를 소유자 id 로 이은 한 행, `docs.e2ee_key IS NULL` 조건. 없으면 `null`
  2. 폴더 사슬 — `folder_id` 가 있을 때만. `access.ts` 의 `FOLDER_CHAIN_SQL` 을 그대로(그래서 `export` 한 단어를 더한다, 1장). 같은 SQL 을 두 곳에 두지 않는다
  3. 초대 — 그 소유자의 초대 중 (문서 초대 AND 이 문서) 또는 (폴더 초대 AND 사슬의 폴더 id 목록 — `json_each`)
- 역할: 소유자는 `'owner'`. 나머지는 이메일마다 문서 초대와 사슬 폴더 초대 중 높은 것(`higherRole` 과 같은 규칙, `access.ts` 의 `grantRole`·`folderChainRole` 과 같은 판정). 소유자 이메일과 같은 초대는 무시한다
- 이메일은 모두 소문자. 순서: 소유자 먼저, 나머지는 이메일 사전순
- 막힌 계정도 들어 있다(개요 3.6, F-2024 Q4). 아직 가입하지 않은 초대 이메일도 들어 있다(초대가 이메일 기준)
- F-503 의 `GET /api/docs/:id/people` 이 같은 함수를 쓴다(개요 3.9). DO 는 이메일만 쓴다

## 8. 지우는 자리 (개요 3.7)

모두 **이미 있는 batch 에 문장을 더한다**. 새 요청·새 트랜잭션을 만들지 않는다. 문장 만들기는 `commentRows.ts` 에 두고 핸들러는 부르기만 한다

### 8.1 문서 삭제 — `handleDeleteDoc` (**F-2038 과 겹침**)

지금 `[deleteDocUsageStatement, DELETE FROM docs …]` 뒤에 셋: ① 댓글 바이트 빼기(4.3 c1 과 같은 문장) ② 그 문서의 `doc_comments` 지우기 ③ 그 문서의 `notifications` 지우기. ①은 ② 앞이어야 한다. 기존 두 문장의 순서·글자는 그대로다

### 8.2 폴더 삭제 `contents=delete-all` — `handleDeleteFolder` (**F-2038 과 겹침**)

`deleteFoldersUsageStatement` 바로 뒤, 문서 `DELETE` 묶음 **앞**에 셋: 폴더 id 목록(`json_each`, `DELETE_FOLDERS_SQL` 과 같은 방식) 안 문서들의 ① 댓글 바이트 빼기 ② `doc_comments` 지우기 ③ `notifications` 지우기. 문서 행이 있어야 폴더로 문서를 찾을 수 있으므로 문서 지우기 앞이다. 폴더 수와 무관하게 3문장. `move-up` 은 문서를 지우지 않으므로 더하지 않는다

### 8.3 금고로 옮기기 — `setDocE2eeStatements` (`e2eeKey` 가 있을 때)

지금 5문장(`MOVE_ROW` · 사용량 · 링크 끊기 · 묶음 행 · 초대) 뒤에 셋: ① 댓글 바이트 빼기 ② `doc_comments` 지우기 ③ `notifications` 지우기 — **셋 다 `WROTE_KEY` 조건**(이 요청이 감싼 키를 실제로 썼을 때만, 지금 3·4·5번과 같은 방식). 1번이 0행이면 아무것도 바뀌지 않는다(X4). 금고에서 빼기(`e2eeKey === null`)에는 더하지 않는다 — 옮길 때 이미 지웠다. DO 는 지금처럼 `purgeBeforeResponse` 로 비운다

### 8.4 계정 삭제 — `worker/account.ts` (F-2038 5.2, **F-2038 과 겹침**)

F-2038 5.2 "F-502 가 댓글 표를 만들면 이 batch 의 11번(`docs`) 앞에 두 문장을 더한다" 를 받는다. 두 문장: ① 내 문서(`owner_id = 나`)의 `doc_comments` 지우기 ② 내 문서의 `notifications` + **받는 사람이 내 이메일(소문자)인** `notifications` 지우기. 사용량 문장은 없다(`users` 행을 지운다)

- **구현 시점에 `worker/account.ts` 가 있으면** 이 명세가 더한다(1장 조건부 행). **없으면** 문장 만들기만 `commentRows.ts` 에 두고(`accountCommentDeleteStatements(db, userId, email)`), F-2038 구현이 11번 앞에서 부른다 — 이 경우 F-2038 에 한 줄 알림이 필요하다(15장)
- 남의 문서에 내가 단 댓글은 남긴다(F-2038 5.1 표 — 그 문서 `Y.Doc` 에 있어 D1 만 지워도 다음 스냅숏에서 되살아난다)

### 8.5 지우지 않는 곳

- 초대 지우기(`DELETE …/grants/:email`) — 지우지 않는다(개요 3.7)
- 금고에서 빼기 — 위 8.3

- 계정 100MiB 초과여도 댓글을 막지 않는다(개요 3.8 — DO 스냅숏은 본문도 한도로 막지 않는다)

### 9.2 소유자

- 댓글 바이트는 **문서 소유자**에게 센다(개요 3.8). DO 는 불러올 때 읽은 `owner_id`(`this.ownerId`)를 쓴다

### 9.3 recount (`scripts/lib/admin.mjs`)

- `RECOUNT_S` 의 바이트 합과 `recountPreview` 의 `real_bytes` 에 **그 사용자 문서들의 `doc_comments.bytes` 합**을 더한다. 문서 수는 그대로
- 댓글 행이 없으면 값이 같다 — 기존 S8 이 그대로 통과한다
- Cron 안전망(10장)이 지운 행은 누계에서 빼지 않는다 — recount 가 바로잡는 몫이다

## 16. 열린 질문 / 사람 결정 필요

### Q1. F-501 파일의 `shortHash` 내부를 이 명세가 바꾸나 — **기본값: 바꾼다**

- 이유: 커밋된 BigInt 구현은 500개 85~92ms, 16비트 칸은 6.8ms(s4). 불러올 때마다·전체 다시 적기마다 치른다. 출력이 같고(시험값 넷 + 긴 입력 둘) F-501 7.1 이 두 구현을 "구현이 고를 일" 로 두었다
- **다른 안 — 그대로 둔다**: 소유 표에서 `src/lib/docComments.ts`·`test` 두 줄이 빠진다. 불러오기 대조가 댓글 500개 문서에서 약 85ms 더 든다. 4.1 의 "불러올 때 전부 대조" 를 "불러온 뒤 첫 스냅숏에서" 로 옮겨도 비용은 같다

### Q2. 앵커 풀기를 공개 API 로만 — **기본값: 공개 API**

- 4.6: 쪼갠 1MB·500개 214~242ms 를 마지막 사람이 나갈 때 한 번. 지금 깨어날 때 이미 25~31ms 를 쓴다. DO CPU 한도는 확인하지 못했다 → 배포 뒤 H3
- **다른 안 A — 내부 필드로 한 번 걷기**(`Y.Text._start`·`Item.right`, 개요 c4 1.48ms): `resolveCommentAnchors` 내부만 바꾸고 F-501 A9 가 결과를 지킨다. 되돌리기로 살아난 항목을 따라가는 규칙(`followRedone`)까지 옮겨야 하고, yjs 를 올릴 때마다 다시 봐야 한다(F-501 3.3)
- **다른 안 B — 방이 비지 않아도 1시간마다 한 번**: 4.5 알려진 한계(방이 며칠씩 비지 않는 문서)를 줄인다. 대신 그 비용을 1시간마다 치른다

### Q3. 답글 알림도 접근 집합으로 거르나 — **기본값: 거른다**

- 6.2: 접근을 잃은 사람에게 제목·발췌가 가지 않게. 개요 3.5 는 `mention` 에만 적었다
- **다른 안 — 개요 문장 그대로(`reply` 는 거르지 않음)**: 답글만 있는 새 항목에서는 `loadDocPeople` 을 부르지 않아 질의가 준다. 접근을 잃은 옛 참여자도 알림을 받고, 누르면 문서가 열리지 않는다(개요 C9)

### Q4. 한 스냅숏의 알림 2,000개 상한 — **기본값: 둔다**

- 6.4: 문장 수를 16 안으로 묶는다. 넘친 알림은 버리고 로그 한 줄
- **다른 안 — 상한 없음**: 이론상 500 × 111 행이 한 batch 에 실려 D1 호출당 50문장을 넘을 수 있다(행 1,486 B 최악이면 약 83문장). 그러면 batch 가 계속 실패해 댓글 복사본까지 멈춘다
- **다른 안 — 넘친 새 항목을 다음 스냅숏으로 미룸**: 버리는 알림은 없지만 "새것" 판정을 항목 단위로 나눠야 해 4.2 가 복잡해진다
