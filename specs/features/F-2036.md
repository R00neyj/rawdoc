### 2.1 현재 절 강조 — 실측

스크래치패드에서 Playwright 가 쓰는 설치된 Chrome 채널(버전 **153.0.8010.53**)로 확인했다.

- `CSS.supports('scroll-target-group: auto')` → `true`, `CSS.supports('selector(:target-current)')` → `true`
- 목차 `ol` 에 `scroll-target-group: auto` 를 주면, 링크를 누른 뒤 그 링크가 `:target-current` 에 걸리고, 휠로 더 내리면 지나간 절의 링크로 옮겨 간다(40절 문서에서 확인)
- 같은 페이지에서 `scroll-target-group: none` 이면 아무 링크도 걸리지 않는다
- Tab 순서는 바뀌지 않는다(`auto`/`none` 모두 링크 하나씩 차례로 간다)
- **목차 칸이 스스로 스크롤해 따라가지는 않는다.** 목차가 칸보다 길 때(도움말) 현재 항목이 칸 밖에 있을 수 있다. 받아들인다
- Firefox·Safari 지원 여부는 **확인하지 않았다**. 지원하지 않으면 속성이 무시되어 강조만 없고 나머지는 같다

## 3. 제목 `id` — 어디서 붙이나

### 3.1 결론: 사이트 빌드가 렌더 결과에 후처리로 붙인다

| 안 | 내용 | 판단 |
| --- | --- | --- |
| (가) `renderMarkdown` 이 늘 `id` 를 붙인다 | 앱 보기 모드·공개 보기(S-5)·HTML 내보내기·앱 도움말에도 `id` 가 생긴다. 사용자 문서의 제목 `root` 가 `id="root"` 가 되어 React 마운트 노드와 겹치는 등 앱 DOM 과 부딪힐 수 있다. 앱 목차는 `data-source-line` 으로 제목을 찾으므로(`findViewerHeadingEl`) 얻는 것이 없다 | 안 쓴다 |
| (나) `renderMarkdown` 에 선택 인자 `headingIds` 를 더한다(기본 꺼짐) | 앱은 안 달라진다. 그러나 `id` 계산이 `heading_open` 규칙 안과 사이트 목차 두 곳에 생기고, 한 곳에서 계산하려면 `renderMarkdown.ts` → `headingTarget.ts` → `renderMarkdown.ts` 순환 import 가 생긴다(`headingTarget.ts` 가 이미 `parseMarkdownTokens` 를 import 한다) | 안 쓴다 |
| **(다) 사이트가 렌더 결과에 `id` 를 끼운다** | `renderMarkdown` 은 h1~h3 에 **늘** `data-source-line` 을 붙인다(`heading_open` 규칙, `sourceLines` 옵션과 무관). `listDocHeadings` 는 그와 같은 줄 번호를 내도록 만든 함수다(F-2018 7.1). 사이트는 `listDocHeadings(본문)` 으로 제목·줄을 얻고, `<hN data-source-line="L">` 를 `<hN id="…" data-source-line="L">` 로 바꾼다. 계산은 한 곳(`siteHeadings`), 앱 코드 변경 없음 | **쓴다** |

실측(스크래치패드, 지금 `content/` 전부 + 도움말 + 사용법 목록 11 페이지): 모든 페이지에서 `listDocHeadings(본문)` 의 h1~h3 각각에 대해 `renderMarkdown(본문)` 안의 `<h{단계} data-source-line="{줄}">` 가 **정확히 한 번** 나온다(어긋남 0). 모든 페이지가 `<h1` 로 시작한다. 지금 페이지 HTML 에 `id="` 는 하나도 없다.

### 3.2 `id` 규칙

`headingSlug(text)`:

1. 유니코드 글자(`\p{L}`)·결합 부호(`\p{M}`)·숫자(`\p{N}`)·공백·`-`·`_` 가 **아닌** 글자를 지운다
2. 앞뒤 공백을 떼고 소문자로 바꾼다(`toLowerCase`, 한글은 그대로)
3. 이어진 공백을 `-` 하나로 바꾼다. 이어진 `-` 는 줄이지 않는다
4. 결과가 빈 문자열이면 `절`

순서가 결정이다 — 지우기를 먼저 해야 `**  **` 같은 제목이 `-` 하나로 남지 않고 `절` 이 된다(1 → 공백만 남음 → 2 에서 빈 문자열).

중복: 문서 순서로 매긴다. 이미 쓴 `id` 이면 `{기본}-1`, `{기본}-2` … 중 **아직 안 쓴 첫 번째**. 그래서 `## 가` / `## 가 1` / `## 가` 는 `가` / `가-1` / `가-2` 가 된다.

| 제목 | `id` |
| --- | --- |
| `이 앱은` | `이-앱은` |
| `내보내기·가져오기` | `내보내기가져오기` |
| `1. 한 문서에 한 생각` | `1-한-문서에-한-생각` |
| `2026-09-24` | `2026-09-24` |
| `Hello World!` | `hello-world` |
| `A_B-c` | `a_b-c` |
| `…` | `절` |
| `(제목 없음)` (빈 제목) | `제목-없음` |

실측(도움말 35개 제목의 결과): `도움말 이-앱은 화면 글쓰기 문서-관리 저장 이미지 위키링크 공유 내보내기가져오기 설치와-오프라인 단축키 마크다운-문법 제목 제목-1 제목-2 제목-3 강조 굵게 기울임 취소선 인라인코드 목록 글머리-목록 번호-목록 체크박스 인용 링크 위키링크-1 표 코드블록 이미지-1 콜아웃 구분선 프론트매터`. `이미지`·`위키링크` 가 두 번씩 나와(앱 사용법 절과 문법 절) 중복 처리가 실제로 필요하다. `제목 1` 은 문법 예시 결과가 만든 진짜 h1 이다 — 에디터 목차에도 똑같이 나온다.

- 페이지 틀(머리·꼬리·문서 목록·목차·접는 목차)은 **`id` 속성을 하나도 쓰지 않는다.** 제목 `id` 와 부딪힐 수 없게 하려는 것이다(A6)
- 링크는 `href="#{id}"` 로 한글을 그대로 쓴다. 실측: Chrome 153 에서 `href="#내보내기가져오기"` 를 누르면 주소가 `#%EB%82%B4…` 로 인코딩되고 `:target` 이 그 h2 에 걸린다

### 3.3 `siteHeadings(body)` — 목차에 넣는 제목

- `listDocHeadings(body)` 결과 중 **단계 1~3** 만. `listDocHeadings` 는 최상위 블록 제목만 낸다 — 인용·콜아웃·목록 안의 제목은 목차에도 없고 `id` 도 안 붙는다. 에디터(`extractHeadings`)는 그것들도 넣는다. 지금 사이트 글에는 그런 제목이 없다
- 글자가 비면 `(제목 없음)`(에디터와 같은 문자열), `id` 는 그 글자로 3.2 규칙. 실측: `#`·`# ` 만 있는 줄과 `` # `  ` ``·`# [](x)` 는 `listDocHeadings` 글자가 빈 문자열이다. **`# **  **` 는 다르다** — markdown-it 이 공백만 감싼 `**` 를 강조로 보지 않아 글자가 `**  **` 그대로 나온다(에디터는 정규식으로 떼어 `(제목 없음)`). 보이는 제목도 `**  **` 이므로 목차가 본문과 같은 글자를 보이는 쪽을 따른다
- `body` 는 `renderSitePage` 가 `renderMarkdown` 에 넘기는 것과 **같은 문자열**(프론트매터를 뗀 본문)이다. 줄 번호 기준이 같아야 해서다
- 목차 표시 조건: 결과 중 단계 2·3 이 하나 이상. 아니면 목차 `nav` 와 접는 목차의 `이 페이지` 부분을 내지 않는다

실측 목차 항목 수(h1~h3): 체인지로그 11, `cli` 7, `command-palette-templates` 6, `markdown-portability` 8, `wiki-links` 8, `wiki-map` 6, `zettelkasten` 8, 처리방침 15, 이용약관 16, 도움말 35, `/guides` 1(→ 목차 없음).

### 3.4 `F-274 A2` 를 어떻게 고치나

지금: "사이트 페이지 HTML 이 `renderMarkdown(HELP_DOC_CONTENT)` 를 그대로 포함한다(`toContain`)". 제목에 `id` 가 끼고 제목 뒤에 접는 목차가 들어가므로 이 단언은 깨진다.

새 문장: **"사이트 페이지의 `<article class="markdown-body">` 안쪽에서 접는 목차(`<details class="site-fold">…</details>`)를 들어내고 ` id="…"` 속성을 모두 지우면 `renderMarkdown(HELP_DOC_CONTENT)` 와 정확히 같다(`toBe`). 프론트매터 표(`markdown-frontmatter`)가 본문에 없다."**

- 뜻은 그대로다 — "앱과 한 원본, 렌더 결과까지 같다". 다른 것은 사이트가 **더한** `id` 와 접는 목차뿐이라는 것을 바이트로 못박는다
- `renderMarkdown` 은 `html: false` 라 본문 글자에서 ` id="` 가 생길 수 없다(`"` 가 `&quot;` 로 나간다). 지우기가 본문을 건드리지 않는다

## 4. 왼쪽 문서 목록

### 4.1 구성과 순서

머리 메뉴(`SITE_NAV`) 순서를 그대로 따르고, 사용법 글은 `사용법` 아래에 한 단계 들여 둔다. 법적 문서 둘은 꼬리(`SITE_FOOTER_LINKS`) 순서로 아래에 따로 묶는다.

```
사용법                              /guides
  {사용법 글 — sortGuideEntries 순서}   /guides/{slug}
체인지로그                           /changelog
도움말                              /help
──
개인정보 처리방침                    /privacy
이용약관                            /terms
```

지금 `content/` 기준 사용법 글은 6편이라 항목은 모두 11개다.

- 글자: `SITE_NAV`·`SITE_FOOTER_LINKS` 의 `label`, 사용법 글은 프론트매터 `title`(`guideEntry` 가 읽은 값). 머리·꼬리와 같은 원본이라 이름이 어긋나지 않는다
- 사용법 글은 `SITE_NAV` 에서 `path === GUIDES_PATH` 인 항목 **아래에만** 붙는다. 그 항목이 없으면(단위 테스트가 `SITE_NAV` 를 비울 때) 사용법 글은 목록에 없다
- 법적 문서를 목록에 넣는 것은 기본값이다 — 10장 Q4

### 4.2 지금 페이지 표시

- 페이지 주소와 `url` 이 **정확히 같은** 항목 하나에만 `aria-current="page"`. `/guides/wiki-links` 에서 부모 `사용법` 은 표시하지 않는다 — 머리 메뉴(`renderSiteHeader`)도 정확히 같을 때만 표시한다
- 모양은 머리 메뉴의 현재 표시와 같게 `--accent` 글자색(`.site-nav a[aria-current='page']` 와 같은 값). 사람 확인 H6

### 4.3 빌드가 목록을 만드는 자리

`buildSite` 는 루프 **전에** 이미 `guideEntries` 를 갖고 있고(`fileEntries.flatMap(… guideEntry …)`), 나머지 항목은 상수(`SITE_NAV`·`SITE_FOOTER_LINKS`)다. 그래서 루프 전에 `buildDocNav(guideEntries)` 를 **한 번** 부르고, 루프 안 모든 `renderSitePage` 호출에 같은 값을 넘긴다. 페이지를 두 번 렌더할 필요가 없다.

계약(이름과 모양이 결정이다):

```ts
// site/pageNav.ts
export type SiteHeading = { level: 1 | 2 | 3; text: string; id: string; line: number }
export function headingSlug(text: string): string
export function siteHeadings(body: string): SiteHeading[]
export function addHeadingIds(html: string, headings: readonly SiteHeading[]): string

export type DocNavLink = { url: string; label: string; children?: DocNavLink[] }
export type DocNav = { main: DocNavLink[]; legal: DocNavLink[] }
export function buildDocNav(guides: readonly GuideEntry[]): DocNav

// site/render.ts — 입력에 docNav 한 칸이 는다
renderSitePage(input: { url: string; raw: string; appCssHref: string; docNav?: DocNav })
```

- `docNav` 를 생략하면 문서 목록(넓은 칸·접는 목차 안 둘 다)을 내지 않는다. 기존 단위 테스트(`render.test.ts`·`helpPage.test.ts`)가 인자 없이 부르는 것을 그대로 두기 위해서다. `buildSite` 는 **늘** 넘긴다
- `addHeadingIds` 는 제목마다 `<h{level} data-source-line="{line}">` 가 **정확히 한 번** 나오지 않으면 `Error` 를 던진다. 메시지에 줄 번호가 들어간다(예: `제목 12행에 id 를 붙일 자리를 찾지 못했습니다`). 렌더러의 제목 모양이 바뀌면 빌드가 조용히 `id` 없는 페이지를 내지 않고 멈추게 하려는 것이다
- 링크 대상 검사는 새로 두지 않는다. `SITE_NAV`·`SITE_FOOTER_LINKS` 는 `buildSite` 의 기존 링크 목록 검사가 이미 보고, 사용법 글 주소는 빌드가 만든 것이다

## 5. 칸 배치

### 5.1 1060 틀 안에 세 칸이 들어가나 — 계산

지금 틀: `--site-page` 1060px, 좌우 안쪽 여백 32px → 쓸 수 있는 폭 **996px**. 본문 `--site-read` 40rem = 640px.

원문 기호를 걸 여백(실측, 스크래치패드에서 `dist-tweak/help.html` 계산값): 제목 `#` 56px 글자 30.8px + 오른쪽 여백 22.4px = **53.2px**, `##` 24px 글자 26.4px + 9.6px = 36.0px, `###` 20px 글자 33.0px + 8px = 41.0px, 목록 `-` 는 `left: -16px`. 그래서 문서 목록과 본문 사이에 **56px 이상**이 있어야 기호가 목록에 닿지 않는다.

| 배치 | 필요한 폭 | 996px 에 |
| --- | --- | --- |
| 목록 200 + 기호 여백 64 + 본문 640 + 사이 48 + 목차 224 | 1176 | **안 들어간다** (180px 넘침) |
| 목록 168 + 기호 여백 56 + 본문 **544(34rem)** + 사이 ≥40 + 목차 184 | 992 | **들어간다** (4px 남음) |

본문을 640px 로 두려면 틀을 1240px 이상으로 넓혀야 한다. **기본값은 틀을 그대로 두고 세 칸일 때만 본문을 34rem 으로 줄이는 것이다** — 머리·꼬리·랜딩의 틀이 그대로라 랜딩 ↔ 글 페이지를 오갈 때 로고가 움직이지 않는다. 다른 안(글 페이지만 1280 틀)은 10장 Q1.

### 5.2 기본값의 수치와 경계

| 창 폭 | 배치 | 원문 기호 |
| --- | --- | --- |
| **1056px 이상** | 세 칸. 문서 목록 168px · 기호 여백 56px · 본문 최대 34rem(폭이 모자라면 줄어든다) · 사이 최소 40px(남는 폭을 여기서 받는다) · 목차 184px. 목차의 오른쪽 끝이 머리 `앱 열기` 버튼 오른쪽 끝과 같은 선 | 문서 목록과 본문 사이 56px 여백에 건다 |
| 1055px 이하 | 한 칸(지금과 같다). 두 옆칸은 숨고 제목 아래 접는 `목차` 가 보인다. 본문 최대 40rem | 글줄 안으로 들인다 |

- **1120px 규칙의 경계를 1055px 로 옮긴다.** 지금 `@media (max-width: 1120px)` 는 "여백이 기호를 받기에 좁으면 글줄 안으로" 다. 1056~1120px 는 이제 세 칸이고 기호는 틀 안 56px 여백에 걸리므로, 기호를 들이는 경계는 한 칸으로 바뀌는 1055px 와 같아진다. 1055px 이하에서는 틀이 창 폭과 같아 왼쪽 여백이 32px 뿐이라 53.2px 짜리 기호가 들어가지 않는다
- 1056px 은 "쓸 수 있는 폭 992px" 에서 나온 경계다(992 + 32 × 2). 세로 스크롤바가 폭을 먹으면(앱 스크롤바 10px) 본문 칸이 그만큼 줄어든다 — 본문을 `최대 34rem` 으로 둔 이유다. 가로 스크롤은 생기지 않아야 한다(A18)
- 세 칸일 때 첫 제목(h1)의 폭은 **본문 칸 폭**이다. 지금 tweak 은 제목을 틀 끝까지 넓히는데(`width: min(100vw - 64px, --site-page - 64px)`), 세 칸에서는 목차 칸을 덮는다. 한 칸(1055px 이하)에서는 지금 규칙 그대로
- 실측(스크래치패드, 헤드리스 Chrome 153 으로 `dist-tweak/help.html` 에 위 수치를 끼워 봄): 창 1056 / 1280 / 1440 / 1600 에서 가로 넘침 없음(`scrollWidth` = `clientWidth`), 본문 544px, 목차 오른쪽 끝 = `앱 열기` 오른쪽 끝(1024 / 1138 / 1218 / 1298), 제목 `#` 왼쪽 끝과 문서 목록 오른쪽 끝 사이 8px(1056) — 닿지 않는다. 34rem 에서 제목 `한 번 쓴 글을 다른 도구로 옮기기` 는 두 줄, `도움말` 은 한 줄

### 5.3 붙어 있기(sticky)와 긴 목차

- 문서 목록·목차 두 칸은 `position: sticky`, 위에서 24px 에 붙는다. 처음 위치는 첫 제목(h1)의 윗선과 맞춘다(h1 `margin-top` 56px). 사람 확인 H1
- 두 칸 모두 높이 상한 `100vh - 48px`, 넘치면 **그 칸 안에서** 세로 스크롤. 페이지 스크롤이 칸 끝에서 페이지로 넘어가지 않게 `overscroll-behavior: contain`
- 실측: 도움말 목차 35항목 × 32.8px = **1148px**. 창 높이 800px 에서 칸 752px, 900px 에서 852px — 도움말은 칸 안 스크롤이 생긴다. 다른 페이지는 가장 긴 이용약관 16항목(약 525px)이라 들어간다
- 제목(h1~h3)에 `scroll-margin-top: 16px`(2장). 머리(`.site-head`)는 붙어 있지 않으므로 더할 값이 없다
- 부드러운 스크롤은 쓰지 않는다(브라우저 기본 즉시 이동) — `prefers-reduced-motion` 을 따로 다룰 일이 없다

## 6. 표시 구조

### 6.1 markup 계약

선택자·클래스·`aria-label` 이 계약이다. 다른 명세·테스트가 이 이름을 쓴다.

```html
<main class="site-main site-doc">
  <nav class="site-docnav" aria-label="문서">
    <ul class="site-docnav-list">
      <li><a class="site-docnav-item" href="/guides">사용법</a>
        <ul class="site-docnav-list">
          <li><a class="site-docnav-item" href="/guides/wiki-links">위키링크로 문서 잇기</a></li>
        </ul>
      </li>
      <li><a class="site-docnav-item" href="/help" aria-current="page">도움말</a></li>
    </ul>
    <ul class="site-docnav-list site-docnav-legal">…</ul>
  </nav>
  <div class="site-article public-view">
    <article class="markdown-body">
      <h1 id="도움말" data-source-line="1">도움말</h1>
      <details class="site-fold">
        <summary>목차</summary>
        <p class="site-fold-label" aria-hidden="true">문서</p>
        <nav aria-label="문서">{문서 목록과 같은 ul}</nav>
        <p class="site-fold-label" aria-hidden="true">이 페이지</p>
        <nav aria-label="이 페이지">{목차와 같은 ol}</nav>
      </details>
      …본문…
    </article>
  </div>
  <nav class="site-toc" aria-label="목차">
    <ol class="site-toc-list">
      <li data-level="1"><a class="outline-item" href="#도움말">도움말</a></li>
      <li data-level="2"><a class="outline-item" href="#이-앱은">이 앱은</a></li>
    </ol>
  </nav>
</main>
```

- 순서: 문서 목록 → 본문 → 목차. 보이는 순서와 DOM 순서가 같아 Tab 순서도 왼쪽 → 가운데 → 오른쪽이다
- **틀 쪽 목록 태그는 전부 `class` 를 단다.** 맨 `<ul>`·`<ol>` 은 본문에만 나온다. `site/build.test.ts` `F-276 A6` 이 `/<ul>[\s\S]*?<\/ul>/` 로 본문 목록을 찾기 때문이다(9장, A10)
- 목차 `ol` 과 접는 목차 안 `ol` 은 같은 클래스(`site-toc-list`)라 둘 다 `scroll-target-group: auto` 가 걸린다
- 목차가 없는 페이지(3.3)는 `nav.site-toc` 를 통째로 빼고, 접는 목차 안의 `이 페이지` 라벨과 `nav` 도 뺀다. 세 칸 격자의 오른쪽 칸은 비어 있다
- `docNav` 가 없으면(4.3) `nav.site-docnav` 와 접는 목차 안 `문서` 라벨·`nav` 를 뺀다. 둘 다 없으면 `<details>` 도 내지 않는다
- 제목 아래 접는 목차는 **본문 안**에 들어간다 — 제목(h1)이 `renderMarkdown` 결과의 일부라 그 사이에 끼울 다른 방법이 없다. 끼우는 자리: 렌더 결과가 `<h1` 로 시작하면 첫 `</h1>` 과 그 뒤 줄바꿈 바로 다음, 아니면 본문 맨 앞. 지금 페이지는 모두 `<h1` 로 시작한다(3.1 실측)
- 링크 글자·`href` 는 `escapeHtml` 을 거친다

### 6.2 접는 목차의 동작

- 1055px 이하에서만 보인다. 1056px 이상에서는 `display: none`(접근성 트리에서도 빠진다)
- 처음엔 닫혀 있다(`open` 속성 없음). `목차` 를 누르거나 초점을 두고 Enter·Space 로 연다 — 브라우저 기본 `<details>` 동작이다
- 스크립트가 없으므로 항목을 눌러 이동해도 열린 채 남는다. 닫으려면 `목차` 를 다시 누른다. Esc·바깥 클릭으로 닫히지 않는다 — 에디터(F-229 2.4)와 다른 점이고 스크립트 금지의 결과다
- 요약 줄은 글자 `목차` 와 브라우저 기본 펼침 표시(▶/▼)다. 아이콘은 두지 않는다
- 본문 안에 들어가므로 본문 CSS(`:is(.app-shell, .public-view) .markdown-body` 의 `ul`·`li`·`a` 규칙)가 접는 목차 안 목록에 새지 않게 `SITE_CHROME_CSS` 가 되돌린다 — 글머리 기호·밑줄·목록 들여쓰기가 넓은 칸의 목록과 같아야 한다. 사람 확인 H4
- 지금 tweak 의 "첫 문단 안내문" 규칙(`h1:first-child + p`)과 "첫 문단이 아니면 위 여백 44px" 규칙(`h1:first-child + :not(p)`)은 접는 목차가 사이에 끼면 **틀어진다**(앞 규칙은 안 걸리고, 뒤 규칙은 접는 목차 자체에 걸린다). 두 규칙이 **접는 목차를 건너뛴 다음 요소**에 걸리도록 고친다. 넓은 창에서 접는 목차가 `display: none` 이어도 DOM 형제라 똑같이 고쳐야 한다

### 6.3 달지 않는 곳

- **랜딩**(`/`, `worker/welcomePage.ts`): `renderSitePage` 를 쓰지 않고 `renderSiteHeader`·`renderSiteFooter`·`SITE_CHROME_CSS` 만 쓴다(코드 확인). 새 CSS 규칙은 모두 `.site-doc`·`.site-docnav`·`.site-toc`·`.site-fold` 아래에만 걸고, 랜딩에는 그 클래스가 없다(`grep` 확인) — 랜딩은 바뀌지 않는다
- **404**(`render404` in `site/build.ts`): `<main class="site-main">` 에 `site-doc` 이 없고 `renderSitePage` 를 쓰지 않는다 — 바뀌지 않는다
- 앱 안 도움말(S-7, `src/app/HelpPage.tsx`)·공개 보기(S-5)·공유 화면: 사이트가 아니므로 바뀌지 않는다

### 가정 (확인 안 함)

- Firefox·Safari 의 `scroll-target-group`·`:target-current` 지원 여부 — 모른다. 지원하지 않으면 강조만 없다는 것은 CSS 의 "모르는 속성·선택자는 무시" 규칙에서 나온 추론이다. **단, `:target-current` 를 다른 선택자와 쉼표로 묶으면 그 규칙 전체가 버려지므로 따로 적어야 한다**
- 세로 스크롤바가 있는 실제 창의 1056px 부근 — 헤드리스 시제품에는 스크롤바가 없었다. 본문 칸이 스크롤바 폭만큼 줄어든다는 것은 계산이다
- 페이지 HTML 크기 증가 — 재지 않았다. 목차가 넓은 칸·접는 목차에 두 번 들어가므로 도움말이 가장 크게 는다
