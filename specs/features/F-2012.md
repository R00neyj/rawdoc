### 2.1 이 커밋이 끝난 시점의 상태

1. **장력 슬라이더를 끝에서 끝까지 끌어도 노드가 커지거나 작아지지 않는다.** 덩어리가 제자리에서 오므라들고 벌어진다. 손을 떼도 카메라는 그대로다
2. `맞춤` 을 누르면 카메라가 **240 ms 동안 부드럽게** 제자리로 돌아온다. 180° 돌려 놓은 상태에서도 덩어리를 **가로지르지 않고 돌아서** 간다
3. `여기로 이동`·`Ctrl`+클릭도 같은 전환으로 그 노드를 화면 가운데로 데려온다
4. 전환 중에 마우스를 대거나 휠을 굴리면 **전환이 즉시 끊기고 손이 이긴다**
5. `prefers-reduced-motion` 이면 셋 다 예전처럼 즉시다
6. 지도를 처음 열 때 배치가 자라나며 카메라가 따라가는 그림은 **하나도 안 바뀐다**

**쓸 만한가 — 판단.** 쓸 만하다. 신고 두 건이 모두 사라지고, 잃는 것은 "장력을 크게 바꾸면 덩어리가 화면 밖으로 나갈 수 있다" 하나인데 그것은 사용자가 결정 2 로 이미 받아들였고 `맞춤` 한 번이면 끝난다.

## 3. 신고 1 — 장력을 바꾸면 노드가 커 보인다

### 3.1 원인 — 코드로 특정했다. 노드는 커지지 않는다, 카메라가 다가온다

노드의 월드 반지름은 장력과 **무관하게 고정**이다 — `fillRadii()`(`MapScene.tsx` 200~209행)가 `nodeRadius(degree, missing, NODE_SCALE × nodeScale)` 로 열 때 한 번 채우고, `장력` 슬라이더는 그 함수를 부르지 않는다(`setView`, 798~813행은 `nodeScale` 이 바뀔 때만 `fillRadii` 를 부른다).

화면 반지름은 `screenRadius(r_world, d, cssH, tanHalfVFov)` 이므로 **카메라 거리 `d` 에 반비례**한다. 그런데 `fit()`(428~447행)과 `refit()`(449~469행)이 둘 다 `fitDistance(graphRadius(bounds.radius), …)` 로 거리를 잡는다. 곧:

> **화면 반지름 ∝ 노드 월드 반지름 ÷ 그래프 반지름.** 장력을 키우면 덩어리가 오므라들어 그래프 반지름이 줄고, 카메라가 그만큼 다가와서 점이 커 보인다.

**F-2006 4.2 가 이미 같은 것을 봤다.** `반발력` 을 0→1 로 훑어도 `최근접거리 ÷ 최대반경` 이 0.113~0.115 로 고정이고, 화면에서 바뀌는 것은 **점 지름 8.9 px → 1.1 px 뿐**이었다. 그때는 "쓸모 있는 슬라이더" 로 읽었는데, 사용자가 실제로 써 보니 **"노드 크기가 변한다" 로 읽혔다.** 사용자 결정 1 이 그 판정을 뒤집는다.

### 3.2 처방 — `holdFit` 인 동안에는 맞춤을 통째로 건너뛴다

**`followFit` 만 떼면 안 된다.** `frame()` 566행에 `if (!userMoved && settling) fit()` 이 따로 있어서, 카메라를 한 번도 안 건드린 사용자는 여전히 **매 프레임 `fit()` 을 맞는다** — 지도를 열자마자 패널을 열어 슬라이더를 끄는 것이 정확히 그 경우다.

`frame()` 565~572행을 이렇게 바꾼다.

```
const settling = ticked || !layout.isSettled()
if (tween) stepTween(performance.now())          // 전환이 최우선 (7.1)
else if (holdFit) updateClip()                   // 장력 재계산 중에는 맞추지 않는다 (사용자 결정 1)
else if (!userMoved && settling) fit()
else updateClip()
if (!settling) { liveRecalc = false; holdFit = false }
```

- **`followFit` 줄(567행)과 `followFit = false`(570행)가 사라진다**
- **지금의 `forceDriven` 이 둘로 갈린다** (16장 Q1, 사람 결정 2026-09-22). `liveRecalc` 은 **reduced-motion 예외**만 맡고(F-2006 9장), `holdFit` 이 **자동 맞춤 중단**만 맡는다. 장력 슬라이더는 둘 다 켜고, **`F-2009` 의 노드 끌기는 `liveRecalc` 만 켠다** — 그래야 F-2009 7.2 가 일부러 고른 "배치가 도는 중에 노드를 끌면 자동 맞춤을 그대로 둔다" 가 산다. 내리는 조건이 `!settling` 로 같아 한 줄이 두 줄이 될 뿐이다
- **`updateClip()` 은 반드시 돈다.** 덩어리가 퍼지는 동안 `camera.far` 를 그대로 두면 뒤쪽이 잘린다 (F-2003 7.3). 여기에 **확대 한계 넓히기 한 줄을 더한다** — 8.2
- **`tween` 이 `holdFit` 보다 앞이다.** 장력 재계산 중에도 사용자가 `맞춤` 을 누르면 그 한 번은 들어준다. 다만 **따라가기는 안 한다** — 전환이 끝나면 다시 `holdFit` 가지로 떨어진다. 결정 1·2 와 정확히 맞는다

## 5. 전환 — 무엇을 어떻게 보간하나

### 5.1 240 ms · 튕김 없는 곡선. `design.md` 4장에 예외를 둔다

`specs/design.md` 4장 `전환` 행은 이렇게 적혀 있다.

> 곡선: 색·바탕·테두리·그림자·투명도는 `--ease-out`, **크기·위치(`transform`)만 탄성 `--ease-spring`**, 그중 툴팁·메뉴·대화상자 나타남은 더 튀는 `--ease-pop` 240ms

**카메라는 그 규칙의 예외다. 근거 둘:**

1. **그 문장은 DOM `transform` 기준이다.** 화면의 한 조각이 튀어 들어오는 것과, **시야 전체가 튀는 것**은 다른 일이다. 카메라가 오버슛하면 덩어리 전체가 한 번 지나쳤다 돌아오고, 그건 멀미다 (사용자 결정 3)
2. **`--ease-spring`(`cubic-bezier(0.51, 0.08, 0.5, 1.23)`)과 `--ease-pop`(`0.32, 1.9, 0.5, 1`)은 둘 다 y 가 1 을 넘는다.** 값이 1 을 넘는다는 것은 카메라가 목표 위치를 지나쳐 **덩어리 반대편까지 갔다 돌아온다**는 뜻이다. `맞춤` 의 목표가 "전체가 보이게" 인데 그 도중에 전체가 안 보인다

**길이 240 ms 는 토큰이 아니라 `MapScene.tsx` 의 상수다.**

```ts
// 카메라 전환 길이. 툴팁·메뉴·대화상자 나타남과 같은 240 ms 다 (design.md 4장 `전환`, F-2012 5.1)
const CAMERA_TWEEN_MS = 240
```

- `--transition-pop`(240ms)과 길이가 같지만 곡선이 달라서 그 토큰을 못 쓴다. 길이만 뽑아 쓰는 토큰은 저장소에 없다
- `DAMPING_FACTOR`(68행)·`LONG_PRESS_MS`(64행)와 같은 자리에 같은 모양으로 둔다. **색 hex 와 달리 시간 상수는 불변조건의 대상이 아니다**

### 5.2 곡선을 JS 에서 — **토큰을 실행 시점에 읽어서 푼다** (실측)

CSS `cubic-bezier` 는 `x(t)=진행도` 를 풀어 `y(t)` 를 내야 하고 닫힌 식이 없다. 세 갈래를 봤다.

| 안 | 문제 |
| --- | --- |
| 제어점 `(0, 0, 0.2, 1)` 을 JS 에 그대로 적는다 | **디자인 값이 두 곳에 갈라진다.** `tokens.css` 를 고쳐도 카메라만 옛 곡선으로 남는다 (`CLAUDE.md` "Two copies drift apart") |
| `1-(1-t)³` 같은 닫힌 식으로 대신한다 | 곡선이 다르다. **직접 쟀다 — 500 px 이동에서 최대 18.0 px, t=126 ms 에서 어긋난다** |
| **`--ease-out` 을 프로브로 읽어 푼다 (채택)** | 파싱 20줄 + 풀이 20줄. `tokens.css` 가 유일한 원본으로 남는다 |

**설치된 Chrome 에서 직접 확인했다** (2026-09-22, Playwright `channel: 'chrome'`).

| 확인 | 결과 |
| --- | --- |
| `getComputedStyle(span).getPropertyValue('--ease-out')` | **`"cubic-bezier(0, 0, 0.2, 1)"`** — 치환된 문자열이 그대로 나온다 |
| 같은 방법의 `--ease-spring` | `"cubic-bezier(0.51, 0.08, 0.5, 1.23)"` |
| 브라우저가 실제로 푸는 값 (WAAPI `animate` + `pause` + `currentTime`) | t=0.1 → **0.303848**, 0.2 → **0.500000**, 0.24 → **0.562931**, 0.3 → **0.644990**, 0.4 → **0.755263**, 0.5 → **0.839245**, 0.6 → **0.902111**, 0.8 → **0.977559** |
| 뉴턴 8회 + 이분 40회 풀이를 그 10점에 대 본 오차 | **최대 4.2×10⁻⁷** |

- **읽는 자리는 이미 있는 프로브다.** `MapScene` 은 `.map-probe` `<span>` 으로 색 토큰을 읽고 있다(`readToken`, 98~102행). `--ease-out` 은 `:root`(`tokens.css` 15행)에 있고 커스텀 속성은 상속되므로 같은 프로브에서 읽힌다
- **`buildScene()` 에서 한 번만 읽는다.** 테마가 바뀌어도 곡선 토큰은 안 바뀐다 — `MutationObserver` 가 부르는 `applyColors()` 에 넣지 않는다
- **파싱에 실패하면 선형(`e = t`)으로 떨어진다.** 제어점을 코드에 적어 두면 갈라짐이 되살아나므로 **대체값으로도 안 적는다.** 선형이어도 단조이고 오버슛이 없어 결정 3 을 깨지 않는다

### 5.3 무엇을 보간하나 — **위치를 직선으로 이으면 덩어리를 가로지른다**

`맞춤` 의 끝 위치는 `center + (0, 0, dist)` 로 **각도까지 정면으로 되돌린다**(`fit()` 437행). 시작 위치를 끝 위치까지 직선으로 이으면 어떻게 되는지는 산수로 나온다.

카메라 오프셋을 `o = position − target` 이라 하면, `position` 과 `target` 을 각각 선형 보간할 때 `o(e) = lerp(o₀, o₁, e)` 다. **`o₀` 와 `o₁` 이 마주 볼 때(180° 돌려 본 상태에서 `맞춤`) `e = 0.5` 에서 `o = 0`** — 카메라가 그래프 중심을 정확히 관통한다. 게다가 `OrbitControls.update()` 는 **매 호출 거리를 `[minDistance, maxDistance]` 로 자르므로**(`_clampDistance`, 1083행 · update 785행에서 호출 — 소스 직접 확인) 중간에 튕기기까지 한다.

> **방향은 구면 보간, 거리는 등비 보간, target 은 선형 보간.**

```
dir  = slerp(dir₀, dir₁, e)          // 단위벡터
dist = dist₀ · (dist₁ / dist₀)^e      // 등비
target = lerp(target₀, target₁, e)
position = target + dir · dist
```

- **거리를 등비로 잇는 이유**: `OrbitControls` 의 휠 확대가 곱셈이다 — 한 칸에 ×0.95(`_getZoomScale`, F-2003 3.2). 같은 어법이라야 "일정한 속도로 줌" 으로 보인다. 덤으로 **거리가 절대 0 이나 음수가 되지 않는다**
- **180° 마주 보는 경우의 회전축**은 임의다. `dot < −0.9999` 면 `dir₀` 에 수직인 축 하나를 골라(X 축과의 외적, 그것이 0 이면 Y 축) `π·e` 만큼 돈다 (9.3)
- 이 선택이 맞는지는 **단위 테스트 U5 가 못 박고**(중간점에서 거리가 안 죽고 방향이 양끝에 수직), **느낌은 사람 확인 H-b** 다

### 5.4 `맞춤` 과 `여기로 이동` 은 **한 함수로 묶는다**

`여기로 이동` 은 각도와 거리를 유지하므로(`lookAtNode`, 479~494행) 끝 자세가 `dir₁ = dir₀`, `dist₁ = dist₀` 다. 그러면 위 식에서 구면 보간과 등비 보간이 **둘 다 항등**이 되고 `target` 선형 보간만 남는다 — 정확히 원하는 동작이다.

> **모드는 `'fit'` 과 `'look'` 둘뿐이고, 다른 것은 끝 자세를 무엇으로 잡느냐 한 곳이다.**

| 모드 | 끝 `target` | 끝 `dir` | 끝 `dist` |
| --- | --- | --- | --- |
| `'fit'` | `layout.bounds().center` | `(0, 0, 1)` | `fitDistance(graphRadius(radius), fov, aspect)` |
| `'look'` | 그 노드의 최신 좌표 | `dir₀` (시작 각도) | `dist₀` (시작 거리) |

두 함수로 가르면 시작 자세 얼리기·취소·정지 판정·확대 한계가 전부 두 벌이 된다. **하나로 묶는다.**

### 5.5 끝점은 **매 프레임 다시 잡는다**

시작 자세만 얼리고 끝 자세는 프레임마다 `layout.bounds()`(`'fit'`)·`layout.readPositions()`(`'look'`)로 다시 읽는다.

- **배치가 도는 중에 `맞춤` 을 눌러도 240 ms 뒤에 어긋나 있지 않다.** 얼려 두면 그 사이 덩어리가 자라 끝나는 순간 한 번 튄다
- **전환이 끝나는 순간과 그 다음 프레임의 자동 맞춤(`fit()`)이 정확히 같은 자세다** → 이어지는 지점에 끊김이 없다 (7.3)
- **창 크기가 바뀌어도 새 `aspect` 가 다음 프레임에 저절로 들어온다** (4장 표 6번)
- **비용은 0 에 가깝다.** `layout.bounds()` 한 번이 노드 1,000 에서 **0.0423 ms**(F-2006 6.2 실측)이고, 이 자리는 원래 `updateClip()` 이 `bounds()` 를 부르던 자리다

### 6.1 지금 루프는 배치가 멈추면 꺼진다

(`MapScene.tsx` 542~599행)

### 6.2 전환은 `requestDraw()` 로 시작하고 `dirty` 로 이어 간다 — **새 표시가 필요 없다**

- **시작**: `beginTween()` 끝에서 `requestDraw()`. 루프가 꺼져 있었으면 켜진다
- **이어 감**: `stepTween()` 이 마지막 줄에서 **`dirty = true`**. `frame()` 이 맨 앞(544행)에서 `dirty = false` 를 내리므로, 카메라 분기가 그 뒤에 다시 세우면 그 프레임 끝의 정지 판정을 통과하지 못한다 → 다음 프레임이 돈다
- **멈춤**: `t ≥ 1` 인 프레임에서 `endTween()` 이 `tween = null` 로 만든다. **그 프레임에는 `dirty = true` 가 이미 서 있으므로 한 프레임을 더 돌고**, 그 다음 프레임은 `tween` 이 없어 `dirty` 가 `false` 로 남아 **배치가 멈춰 있으면 루프가 꺼진다.** 끝나는 자리가 결정적이다

> **`controls` 의 `change` 에 기대지 않는다.** 전환 중에는 `change` 가 사실상 매 프레임 오지만(`_lastTargetPosition` 비교, OrbitControls 918~923행), **마지막 한두 프레임은 이동량이 `_EPS`(1e-6) 아래라 안 올 수 있다.** 명시적으로 `dirty = true` 를 세우는 편이 안전하고 읽기 쉽다.

- **시각은 `performance.now()` 를 쓴다.** `setAnimationLoop` 의 콜백 인자에 기대지 않는다 — 지금 `frame()` 이 인자를 안 받고 있고, 받게 바꾸면 그 하나 때문에 시그니처가 바뀐다
- **루프가 영영 안 꺼지는 경우가 없다.** `t` 는 실시간 기반이라 240 ms 가 지나면 반드시 1 에 닿는다. 탭이 백그라운드로 가 rAF 가 멈추면 전환도 멈췄다가, 돌아오면 `t` 가 이미 1 이라 **한 프레임에 끝난다** (16장 Q3)
- **`dispose()` 에서 `cancelTween()` 을 부른다.** 상태를 지우는 것이라기보다 `enableDamping` 복구를 빠뜨리지 않으려는 것이다 (번들이 통째로 버려지므로 실질 효과는 없다)

## 7. 전환 중의 `userMoved`·`selfDriven`·취소

### 7.1 `frame()` 안에서 전환이 최우선이다

3.2 의 분기 그대로다. 전환이 도는 동안에는 자동 맞춤(`fit()`)도 `updateClip()` 도 따로 안 돈다 — `stepTween()` 이 그 안에서 `updateClip()` 을 부른다 (8.1).

### 7.2 취소는 `start` 이벤트 하나로 잡는다 — **소스로 확인했다**

`selfDriven` 을 240 ms 내내 켜 두면 **그 사이의 진짜 사용자 조작이 `userMoved` 를 못 세운다.** 그래서 전환을 **취소**한다.

> `controls.addEventListener('start', cancelTween)`

- **`start` 는 사용자 조작에서만 나온다.** `onPointerDown`(1738행)·`onMouseWheel`(1782행)·`onTouchStart`(1876행) 세 곳뿐이고, **`update()` 는 `start` 를 쏘지 않는다**(`update()` 안의 dispatch 는 `change` 하나, 918행). 직접 읽어 확인했다
- **`change` 로는 못 가른다.** 우리가 전환으로 일으킨 `change` 와 사용자 것이 섞인다. 그래서 F-2003 7.3 이 `selfDriven` 을 만든 것이고, 여기서는 그 반대 방향의 표시가 필요하다
- **취소는 `enableDamping = true` 와 `selfDriven = false` 로 되돌리고 끝이다.** `userMoved` 는 건드리지 않는다 — **곧 오는 `change` 가 스스로 `true` 로 세운다** (607~610행)
- **순서가 안전하다.** `start` 는 `pointerdown` 처리 안에서 상태를 세운 직후에 나오고, 실제 카메라 이동은 그 다음 `pointermove` 부터다. 휠은 `start` → `_handleMouseWheel` → `end` 순이라 취소가 먼저 돈다
- **`enabled === false`(노드 메뉴가 떠 있는 동안, F-2003 4.4)면 `start` 자체가 안 나온다** — 메뉴를 여는 우클릭이 전환을 끊지 않는다. 맞는 동작이다

### 7.3 `userMoved` 를 언제 뒤집나

| 모드 | 언제 | 왜 |
| --- | --- | --- |
| `'fit'` | **전환이 끝나는 순간 `false`** | 시작할 때 끄면 `!userMoved && settling` 자동 맞춤이 전환과 겹쳐 같은 프레임에 두 번 카메라를 쓴다. F-2003 17장 Q1("`맞춤` 은 자동 맞춤을 다시 켠다")은 그대로 지켜진다 — **켜지는 시점이 240 ms 늦어질 뿐이다** |
| `'fit'` 인데 **취소됐다** | 그대로 `true` | 사용자가 도중에 손을 댔으니 자동 맞춤을 되살리면 안 된다 |
| `'look'` | **시작하는 순간 `true`** | 지금 `lookAtNode()` 493행이 하는 일 그대로다. 취소되든 말든 결과가 같다 |

**전환이 끝난 뒤 배치가 아직 돌고 있으면** 다음 프레임부터 자동 맞춤(`fit()`)이 매 프레임 돈다. 5.5 덕분에 전환의 마지막 자세와 그 `fit()` 의 자세가 같아서 **이어지는 자리에 튐이 없다.**

### 7.4 `selfDriven` 은 전환 내내 켜 둔다

`beginTween()` 에서 켜고 `endTween()`·`cancelTween()` 에서 끈다. 그 사이의 `change` 는 전부 우리가 일으킨 것이고, **사용자 것은 `start` 가 먼저 와서 전환을 끊으므로 `selfDriven` 이 이미 꺼져 있다.**

## 8. 전환 중 절단면과 확대 한계

### 8.1 절단면은 **매 프레임** 다시 잡는다 — `updateClip()` 을 그대로 부른다

카메라가 움직이는 내내 `near`·`far` 가 안 따라오면 덩어리 앞뒤가 잘린다. `stepTween()` 은 자세를 쓴 **뒤에** 기존 `updateClip()`(472~476행)을 그대로 부른다 — 그 함수가 이미 "지금 카메라 위치에서 중심까지의 거리" 로 계산하므로 `'fit'`·`'look'` 두 모드를 한 줄로 덮는다.

### 8.2 확대 한계는 **넓히기만 한다** — 안 그러면 `update()` 가 전환 거리를 잘라낸다

**`OrbitControls.update()` 는 매 호출 `_spherical.radius` 를 `[minDistance, maxDistance]` 로 자른다**(785행 → `_clampDistance` 1083행. 소스 직접 확인). 두 값은 지금 `fit()`·`refit()` 에서만 갱신되므로, **덩어리가 크게 줄어든 뒤 `맞춤` 을 누르면 전환 중간 거리가 옛 `minDistance` 에 걸려 튕긴다.** 장력 네 축을 끝에서 끝까지 쓰면 그래프 반지름이 100배 가까이 움직이므로 실제로 걸린다.

```
function applyZoomLimits(fitDist) {
  const lim = zoomLimits(fitDist)
  const d = camera.position.distanceTo(controls.target)   // 지금 거리
  controls.minDistance = Math.min(lim.min, d)
  controls.maxDistance = Math.max(lim.max, d)
}
```

- **지금 거리를 포함하도록 넓히기만 하므로 `update()` 가 카메라를 밀어내는 일이 없다.** 좁히면 그 자체가 카메라 이동이 된다
- **부르는 곳 둘.** (1) `stepTween()` 이 자세를 쓴 직후 — 인자는 그 프레임의 `fitDistance`, (2) **장력 재계산 중의 `updateClip()` 가지** — 그래야 덩어리가 커져 화면 밖으로 나가도 **휠로 물러나 되찾을 수 있다** (사용자 결정 2 의 "맞춤으로 되돌린다" 에 길을 하나 더 준다). 16장 Q2
- **`fit()` 은 안 고친다.** 그 자리에서는 카메라가 정확히 `dist` 에 있어 `zoomLimits(dist)` 가 언제나 `dist` 를 품는다 — 결과가 같고, F-2003 소유 줄을 건드리지 않는 편이 낫다
- **`stepTween()` 은 `controls.update()` 를 직접 부르지 않는다.** `frame()` 572행이 바로 다음 줄에서 부르고, 거기까지 오면 한계가 이미 넓혀져 있어 잘리지 않는다. 두 번 부르면 `change` 판정이 두 번 돌 뿐 이득이 없다

## 9. `src/lib/mapCamera.ts` 에 더하는 것

### 9.1 내보내는 것 셋

```ts
export type CubicBezier = readonly [number, number, number, number]

/** CSS `cubic-bezier(x1, y1, x2, y2)` 문자열을 제어점 넷으로. 모양이 아니면 null */
export function parseCubicBezier(text: string): CubicBezier | null

/** 진행도 t(0~1) → 곡선 위의 값. curve 가 null 이면 선형 */
export function easeAt(curve: CubicBezier | null, t: number): number

export type CameraPose = { target: number[]; dir: number[]; dist: number }

/** 두 자세 사이 e(0~1) 지점의 target·position 을 out 배열에 쓴다. 방향은 구면, 거리는 등비, target 은 선형 */
export function tweenPose(from: CameraPose, to: CameraPose, e: number, outTarget: number[], outPosition: number[]): void
```

- **`CameraPose` 를 `readonly` 가 아닌 `number[]` 로 두는 것은 의도다.** `MapScene` 이 자세 객체 둘과 출력 배열 둘을 만들어 **프레임마다 돌려쓴다** — F-2002 6.6 의 "프레임마다 할당하지 않는다" 규칙이다
- **`three` 를 import 하지 않는다** (F-2003 7.5). 그래서 `Quaternion.setFromUnitVectors` 를 못 쓰고 9.3 을 직접 푼다

### 9.2 `parseCubicBezier`·`easeAt`

- 파싱: 앞뒤 공백을 떼고 `/^cubic-bezier\(\s*([-\d.eE+]+)\s*,\s*…\)$/` 로 넷을 꺼낸다. 하나라도 유한수가 아니면 `null`. **`x1`·`x2` 를 `[0, 1]` 로 자른다** — CSS 명세가 x 만 그 범위를 요구한다(y 는 넘어도 된다). 자르지 않으면 `x(t)` 가 단조가 아니라 풀이가 발산할 수 있다
- 풀이: `x(t)` 에 **뉴턴 8회**, 오차가 1e-7 안에 안 들어오면 **이분 40회**로 보정하고 `y(t)` 를 돌려준다. `t ≤ 0` → 0, `t ≥ 1` → 1
- **5.2 실측대로 Chrome 과 4.2×10⁻⁷ 안에서 같다.** 그 10점이 그대로 U2 의 기대값이다

### 9.3 `tweenPose` — 구면 보간을 직접 푼다

```
d0 = normalize(from.dir) (길이 0 이면 (0,0,1))
d1 = normalize(to.dir)   (길이 0 이면 d0)
c  = clamp(dot(d0, d1), -1, 1)
if (c > 0.9999)            dir = normalize(lerp(d0, d1, e))      // 거의 같은 방향 — 선형으로 충분하고 sin θ 가 0 에 수렴해 불안정하다
else if (c < -0.9999)      축 = normalize(d0 × X);  (길이 0 이면 normalize(d0 × Y))
                           dir = d0 를 그 축 둘레로 π·e 만큼 돌린 것 (로드리게스)
else                       θ = acos(c);  dir = (sin((1-e)θ)·d0 + sin(eθ)·d1) / sin θ
dist   = from.dist · (to.dist / from.dist)^e        // from.dist ≤ 0 이면 선형으로 떨어진다
target = from.target + (to.target − from.target)·e
position = target + dir·dist
```

- **로드리게스 회전도 세 줄이다** — `v·cosφ + (k×v)·sinφ`(`k·v = 0` 이라 세 번째 항이 사라진다)
- `e` 는 `[0, 1]` 로 자른다. `e = 0`·`e = 1` 에서 **정확히** 양 끝이 나와야 한다 (U4)

## 10. `MapScene.tsx` 에 생기는 모양

```ts
type CameraTween = { startedAt: number; mode: 'fit' | 'look'; nodeIndex: number }
let tween: CameraTween | null = null
const poseFrom: CameraPose = { target: [0, 0, 0], dir: [0, 0, 1], dist: 1 }
const poseTo: CameraPose = { target: [0, 0, 0], dir: [0, 0, 1], dist: 1 }
const tweenTarget = [0, 0, 0]
const tweenPosition = [0, 0, 0]
// `--ease-out` 을 프로브로 한 번 읽는다. 못 읽으면 선형이다 (5.2)
const easeCurve = parseCubicBezier(getComputedStyle(probe).getPropertyValue('--ease-out'))

function beginTween(mode: 'fit' | 'look', nodeIndex = -1) {
  if (reduced) { if (mode === 'fit') fit(); else lookAtIndex(nodeIndex); return }   // 결정 5
  cancelTween()
  selfDriven = true
  controls.enableDamping = false
  controls.update()                       // 남은 관성을 전부 적용하고 누적값을 비운다 (F-2003 3.4)
  offset.copy(camera.position).sub(controls.target)
  if (offset.lengthSq() === 0) offset.set(0, 0, 1)
  poseFrom.dist = offset.length()
  offset.normalize()
  poseFrom.dir[0] = offset.x; … ; poseFrom.target[0] = controls.target.x; …
  tween = { startedAt: performance.now(), mode, nodeIndex }
  if (mode === 'look') userMoved = true   // 7.3
  requestDraw()
}

function stepTween(now: number) {
  const t = Math.min(Math.max((now - tween.startedAt) / CAMERA_TWEEN_MS, 0), 1)
  const e = easeAt(easeCurve, t)
  const { center, radius } = layout.bounds()
  const fitDist = fitDistance(graphRadius(radius), camera.fov, camera.aspect)
  if (tween.mode === 'fit') { poseTo.target ← center; poseTo.dir ← [0,0,1]; poseTo.dist = fitDist }
  else { const pos = layout.readPositions(posBuf); poseTo.target ← pos[i*3 …]; poseTo.dir ← poseFrom.dir; poseTo.dist = poseFrom.dist }
  tweenPose(poseFrom, poseTo, e, tweenTarget, tweenPosition)
  controls.target.set(...tweenTarget)
  camera.position.set(...tweenPosition)
  applyZoomLimits(fitDist)                // 8.2 — 자세를 쓴 뒤여야 지금 거리가 맞다
  updateClip()                            // 8.1
  dirty = true                            // 6.2
  if (t >= 1) endTween()
}

function endTween()  { const wasFit = tween?.mode === 'fit'; tween = null; controls.enableDamping = true; selfDriven = false; if (wasFit) userMoved = false }
function cancelTween(){ if (!tween) return; tween = null; controls.enableDamping = true; selfDriven = false }   // userMoved 는 안 건드린다

function requestFit() { beginTween('fit') }
function requestLook(id: string) { const i = graph.nodes.findIndex((n) => n.id === id); if (i < 0) return; beginTween('look', i) }
```

- **기존 `fit()`(428~447행)은 한 줄도 안 고친다.** 첫 열림·자동 맞춤·`ResizeObserver` 가 그대로 쓴다
- **기존 `lookAtNode(id)` 는 `lookAtIndex(i)` 로 인자만 바꾼다.** `findIndex` 를 `requestLook` 이 이미 했고 `stepTween` 도 인덱스를 쓰기 때문이다. 본문의 나머지 열두 줄은 그대로다
- **`SceneBundle` 의 바깥 이름은 안 바꾼다** — `fit: requestFit`, `lookAtNode: requestLook`. 효과 (b)·(c)(891~912행)는 한 글자도 안 고친다
- `ResizeObserver`(769~773행) 맨 앞에 `if (tween) { requestDraw(); return }` 한 줄 (4장 표 6번)
- `dispose()`(821행 부근)에 `cancelTween()` 한 줄

## 16. 열린 질문 / 사람 결정 필요

**사람이 꼭 골라야 하는 것은 Q1 하나다.** 나머지 넷은 코드·실측으로 기본값이 서 있고, 다른 쪽을 골랐을 때 무엇이 달라지는지 적었다.

### Q1. `forceDriven` 한 플래그에 두 뜻을 겹치는 것 — **정해졌다: 가른다 (2026-09-22)**

처음 설계는 `forceDriven` 을 **(a) reduced-motion 예외**(F-2006 9장)에 더해 **(b) 자동 맞춤 중단**(3.2)으로도 쓰는 것이었다. 3.4 대로 수명은 정확히 맞았지만, **`F-2009`(노드 끌기) 7.3 이 같은 플래그를 (a) 때문에 켜는데** F-2009 7.2 는 **"배치가 도는 중에 노드를 끌면 자동 맞춤을 그대로 둔다"** 를 일부러 골랐다. 겹쳐 두면 그 선택이 (b) 때문에 조용히 깨진다.

**그래서 둘로 가른다.** `liveRecalc`(= 옛 `forceDriven`, reduced-motion 예외. 장력·끌기 둘 다 켠다)과 `holdFit`(= 자동 맞춤 중단. **장력만** 켠다). 내리는 조건이 둘 다 `!settling` 로 같아서 `MapScene.tsx` 에 `let` 한 줄과 `frame()` 한 줄이 늘 뿐이다.

### Q2. 장력 재계산 중에 확대 한계를 넓히는 것 — **기본: 넓힌다**

8.2. 덩어리가 100배 커지면 옛 `maxDistance`(옛 맞춤 거리의 4배)에 막혀 **휠로 물러나도 전체가 안 보인다.** 넓혀 두면 사용자 결정 2 의 "맞춤으로 되돌린다" 말고 **휠로도 되찾을 수 있는 길**이 하나 더 생긴다. 넓히기만 하므로 카메라가 밀리지 않는다.

**다른 쪽을 고르면**: `updateClip()` 가지를 지금 그대로 둔다(절단면만). 코드가 세 줄 줄고 `F-2012 A7` 이 없어진다. 대신 장력을 크게 바꾼 뒤 **휠이 중간에서 멈추는** 상태가 된다 — 사용자가 "확대가 고장 났다" 로 읽을 수 있다. 전환 중의 넓히기(8.2 의 (1))는 **어느 쪽을 고르든 반드시 남긴다** — 없으면 `맞춤` 이 스스로 튕긴다.

### Q3. 전환의 끝점을 매 프레임 다시 잡는 것 — **기본: 다시 잡는다**

5.5. 얼려 두면 배치가 도는 중에 `맞춤` 을 눌렀을 때 240 ms 뒤에 한 번 튀고, 창 크기가 바뀌면 틀린 `aspect` 로 끝난다. 비용은 `layout.bounds()` 한 번(노드 1,000 에서 0.0423 ms)인데 **원래 `updateClip()` 이 같은 자리에서 부르던 것**이라 순증이 0 이다.

**다른 쪽을 고르면**: `beginTween()` 에서 끝 자세도 얼린다. `stepTween()` 이 다섯 줄 짧아지고 `poseTo` 가 한 번만 채워진다. 대신 위 두 경우에 튐이 생기고, **전환이 끝나는 자세와 다음 프레임의 자동 맞춤 자세가 어긋나** 이어지는 자리에 한 번 더 튄다 (7.3).

### Q4. 전환 길이를 설정으로 빼는 것 — **기본: 안 뺀다**

`md.mapView` 에 축을 더하면 `mapPrefs.ts`(F-2005 소유)·패널·저장 검증이 전부 늘어난다. **240 ms 는 `design.md` 4장이 툴팁·메뉴·대화상자에 이미 쓰는 값**이고, 움직임을 줄이고 싶은 사람에게는 OS 설정(`prefers-reduced-motion`)이라는 표준 통로가 이미 있다.

**다른 쪽을 고르면**: `표시` 묶음에 `전환 길이` 슬라이더가 하나 늘고 F-2005 소유 파일을 열어야 한다. **이 명세의 범위를 넘는다** — 필요해지면 별도 번호로.

### Q5. 거리를 등비로 잇는 것 — **기본: 등비**

5.3. `OrbitControls` 의 휠 확대가 곱셈이라 같은 어법이고, 거리가 0 이나 음수가 될 수 없다.
