# F-4004 공유 링크에서 보기·편집 권한 요청

작성일: 2026-10-12
상태: 개요, 승인 2026-10-12(사용자 "추천안대로"). 사용자 요청(2026-10-12) "로그인 한 사람이고, 링크 공유 받은 상태일때, 편집 수정 보기 권한 요청하는 버튼있었으면 좋겠음". 접근 권한을 바꾸는 일이라 보안(`F-4NNN`). 구현 단위는 7장 자식 일곱이다. 열린 질문 Q1~Q4 는 사용자가 기본값으로 확정했다(2026-10-12, 8장). 8장 남은 갈림길(요청 토큰 끄는 화면)은 기본값 "없음"

## 정해진 것 (사용자, 바꾸지 않는다)
1. 요청자는 `보기`(공유받은 문서로 내 목록에 둔다) 또는 `편집` 중 하나를 골라 요청한다
2. 소유자는 공유 관리(S-6 `#/shares`)의 대기 목록에서 승인·거절한다. 알림함 행·안 읽은 배지(F-507·F-2116 경로)와 웹 푸시(F-3007 경로)로 알린다
3. 요청 메시지는 없다. 소유자가 보는 것은 요청자 이름·이메일과 고른 권한뿐
4. **S-4(`#/s/{조각}`)와 S-5(`#/p/…`) 둘 다** 요청을 받는다. 조각 링크가 원본 문서와 이어진다는 점(링크로 원본이 드러남)은 받아들였다

## 근거 (2026-10-12 HEAD, 이름으로 찾는다)
- S-4: `src/lib/shareCodec.ts` 조각 JSON 은 `{ v, t, c, e }` 뿐이고 조각은 서버로 가지 않는다 → 지금 링크로는 원본을 알 수 없다. `decodeShare` 는 모르는 키를 버린다 → 키를 더해도 옛 앱이 연다
- S-5: 서버 `share_links` 행이 있고 `findPublicLink` 가 소유자·대상을 안다. `handlePublicGetDoc` 응답에 문서 id 가 없다 → 요청은 **토큰**으로 대상을 찾는다
- 권한 = `grants`(`migrations/0005_grants.sql`). 추가는 `worker/grants.ts` `handlePutGrant` 한 곳 — 금고 409, 자기 자신 400, 새 초대면 F-3012 `share` 행과 F-3007 푸시
- S-5 는 부팅·`/api/me` 를 타지 않는다 → 로그인 여부를 S-5 가 직접 묻는다. S-4 는 앱 안이라 `account` 가 있다
- 쓰기 관문(`isWriteRoute`)은 GET 이 아닌 `/api/*` 를 모두 센다
- `users.name`(0009)은 있지만 어느 화면도 아직 보이지 않는다

## 1. 결정
- **버튼은 S-4·S-5.** S-5 는 링크 토큰으로, S-4 는 소유자가 서버 문서를 복사할 때 조각에 넣는 **요청 전용 토큰**으로 원본을 찾는다(id 가 아닌 이유는 F-4007 1장 — 요청 통로를 소유자가 연 문서로 한정, 서버에서 끊기 가능, 존재 확인 막기). 옛 조각·로컬 문서·받은 문서·금고 문서의 조각에는 토큰이 없어 버튼도 없다
- 두 토큰은 같은 요청 라우트(`/api/access-requests/link/:token`)를 쓴다. 서버가 `share_links` 다음 `request_tokens` 를 본다
- **대상**: S-5 문서 링크 → 지금 보는 문서(F-252 묶음 소속은 서버가 다시 확인). 폴더 링크 → 그 폴더. S-4 → 토큰의 문서
- **승인 = 초대 경로 그대로.** `handlePutGrant` 본문을 `applyGrant` 로 꺼내 초대 `PUT` 과 승인이 같이 부른다. 새 권한 모델·새 role 없음. 소유자는 요청한 권한으로만 승인한다(바꾸려면 승인 뒤 초대 대화상자)
- **권한을 낮추지 않는다.** 이미 요청한 권한 이상이면 승인은 요청만 지운다
- **상태**: 서버 행은 `pending`·`rejected`. 승인하면 행을 지우고 초대가 남는다. 소유자가 같은 사람을 직접 초대해도 요청은 지운다
- **요청자에게 알리기**: 승인 — 새 초대면 기존 F-3012 행·F-3007 푸시. 보기 → 편집 올림은 기존 규칙상 알림이 없다(받아들인다). 거절 — 알림 없음, 그 링크 화면에서만 보인다
- **이메일 노출**: 요청 대화상자에 `소유자에게 내 이름과 이메일이 보입니다.` 를 늘 보인다. 요청자는 승인 전에 소유자 이메일을 보지 못한다. 이름은 요청 때의 `users.name` 복사, 비었으면 이메일만

## 2. 버튼이 보이는 조건 (S-4·S-5 같은 규칙)
| 보는 사람 | 보이는 것 (S-5 아이콘 버튼 / S-4 아이콘 + 글자) |

| 로그아웃·오프라인·조회 실패·토큰 없는 조각 | 아무것도 없음(지금 화면 그대로) |
| 소유자 / 편집 권한(문서·폴더 사슬) | `앱에서 열기`(S-4 `원본 문서 열기`) |

| 대기 중 | `권한 요청 보냄` — 누르면 내용과 `요청 취소` |
| 거절 후 7일 안 | 거절 안내와 다시 요청할 수 있는 날 |

## 3. 남용 막기
- 요청자·대상당 행 하나. 대기 중 다시 보내면 권한만 바뀌고 새 알림·푸시 없음
- 거절 뒤 **7일** 안 다시 요청 → 409. 대기 요청은 **30일** 뒤 매일 Cron 이 지운다
- 요청자 한 명의 대기 **20개**, 소유자 한 명이 받은 대기 **100개**(409). 그 위는 F-2026 관문·하루 사용량
- 푸시는 소유자당 10분에 한 번. 알림함 행은 요청마다
- 막힌 소유자 → 링크·토큰이 없는 것과 같다, 막힌 요청자 → 관문 403

## 4. 정리
요청 행 id = 알림함 행 id. "살아 있는 요청" = 토큰(링크 또는 요청 토큰)이 살아 있고 대상이 같은 소유자에게 있으며 금고 아님. 목록·승인·상태가 이 조건으로 거른다. 즉시 지우는 곳: 승인·거절(알림만)·취소·문서·폴더 삭제·금고로 옮기기·링크 끊기·직접 초대·계정 삭제. 문서 삭제·금고는 요청 토큰도 끊는다. 매일 Cron 이 나머지와 만료를 지운다

## 5. 데이터·API 개요 (계약은 자식)
- 마이그레이션 `0025_access_requests.sql`(요청 표 + `notifications` 다시 만들기), `0026_request_tokens.sql`
- 요청자 `GET`·`POST`·`DELETE /api/access-requests/link/:token`, 소유자 `POST /api/access-requests/:id/approve`·`/reject`, `GET /api/shares` 의 `requests`, 토큰 발급 `POST /api/docs/:id/request-token`
- 알림함 종류 `access_request`(`share` 와 같은 9키), 푸시 `tag` 는 `share:{대상 id}` 재사용

## 6. 하지 않는 것
요청 메시지, 승인 때 권한 바꾸기, 앱 안 문서 화면의 요청, 로그아웃 방문자의 로그인 유도, 이메일 발송, 거절 푸시, CLI·`/v1`
