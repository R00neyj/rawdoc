## 2. 범위

### 2.1 한다

- 사이드바 문서 행·홈 화면 `최근 문서` 항목을 `#/d/{id}` **링크**로 만들어 **가운데클릭**으로 새 탭에서 열리게 한다
- 사이드바 문서 우클릭 메뉴(F-255)에 **`새 탭에서 열기`** 항목을 넣는다
- 탭 사이에 `BroadcastChannel` 로 "저장소가 바뀌었다" 신호를 보내, 받은 탭이 **문서·폴더 목록을 다시 읽는다** (5.1)
- 같은 문서를 두 탭에서 열면 **나중 탭이 읽기 전용**이 된다. 로컬(IndexedDB) 문서에도 F-213 과 같은 모양의 편집권을 준다 (5.2·6.4)
- 지금 편집 중인 문서가 다른 탭에서 지워지면 **읽기 전용 + 알림 + `새 문서로 저장`** (5.3·7.3)

### 2.2 하지 않는다

- **앱 안 화면 분할** — F-262 로드맵 전체(F-263 pane 골격 ~ F-268 폭 조절)를 버린다. 무엇을 잃는지는 3장에 솔직히 적었다
- 열린 문서의 **본문을 탭 사이에 실시간 반영** — 불변조건(`CLAUDE.md`: 문서 상태의 원본은 CM6 `EditorState` 하나)을 지킨다. 다른 탭의 본문 변경을 열려 있는 `EditorState` 에 밀어 넣지 않는다. 실시간 동시 편집은 M3(F-301)이다
- **설정 18개 키(`src/app/prefs.ts` 27~46행)를 탭 사이에 맞추기** — 5.5
- 공개 보기(S-5 `#/p/`)·공유 화면(S-4 `#/s/`)·공유 관리(S-6 `#/shares`)·검색 대화상자(D-6)에 새 탭 진입점 주기 — 4.6, 13장 Q2
- `Ctrl`/`Cmd`+클릭으로 새 탭 열기 — 사이드바에서 그 조합은 F-255 여러 선택이 쓰고 있다 (4.2, 13장 Q1)
- 새 탭이 열리는 **위치**(오른쪽 끝 / 원래 탭 옆) 조절, 창 배치 자동화 — 브라우저가 정한다
- 탭 개수 제한, 이미 열린 탭 찾아가기 — 13장 Q4
- 서버 저장소의 탭 간 동기화 강화 — 서버 저장소는 F-207 `subscribeSync`(App.tsx 562~565행)와 F-213 잠금이 이미 맡는다. 이번 신호는 **로컬 저장소와 서버 저장소의 로컬 캐시 양쪽에 똑같이** 보내되, 편집권(6.4)만 `store.kind === 'idb'` 로 좁힌다 (5.2)

| **사이드바가 양쪽에 중복으로 떠 가로 공간을 먹는다** | 창 두 개는 각자 사이드바를 그린다. 기본 폭 300px(`md.sidebarWidth` 기본값, ia.md 3.27) × 2 = 600px 이 목록에 간다. F-262 는 사이드바 하나에 편집 영역 둘이었다. 완화 수단은 있다 — 한쪽 사이드바를 접으면(F-143 `md.sidebar: collapsed`) 레일만 남는다. **다만 `md.sidebar` 는 localStorage 라 두 탭이 서로 덮어쓴다** (5.5, 13장 Q5) |
| **좁은 화면에서는 뜻이 없다** | 1024px 미만에서 창을 둘로 쪼개면 각각 512px 이라 둘 다 겹침 사이드바(ia.md 3.11)가 된다. F-262 도 1023px 미만에서 분할 버튼을 숨겼으니(F-262 1장) 결과는 같다 |
| **pane 사이 끌어놓기** | F-262 였으면 왼쪽 문서의 텍스트·이미지를 오른쪽 pane 으로 끌어 놓는 길이 열렸다(로드맵엔 없었지만 가능했다). 탭 두 개 사이에는 브라우저 기본 텍스트 드래그밖에 없고, 그것도 창을 나란히 놓아야 된다 |
| **한 화면에서 두 문서를 같이 스크롤·비교** | 탭으로도 창을 나란히 두면 되지만, 두 pane 의 스크롤을 묶는 식의 기능은 영영 없다 |
| **"오른쪽에 열기" 라는 명확한 뜻** | F-262 21행이 정했던 사이드바 메뉴 `오른쪽에 열기` 가 `새 탭에서 열기` 로 바뀐다. 새 탭이 어디 생기는지는 브라우저가 정하므로 "오른쪽" 을 약속할 수 없다 |

**새 탭으로도 되는 것**(F-262 가 하려던 것 중 살아남는 것): 서로 다른 두 문서를 동시에 보기, 양쪽 모두 완전히 편집 가능(F-262 20행의 "완전 동등한 기능" — 새 탭은 앱 전체가 그대로라 자동으로 만족한다), 양쪽에서 공유·폴더 이동·우클릭 메뉴 전부 사용, 새로고침해도 각 탭이 자기 문서를 복원(F-262 22행은 오른쪽 pane 을 **복원하지 않기로** 했는데 새 탭은 `#/d/{id}` 라 복원된다 — **개선**), 3개 이상 동시에 열기(F-262 는 2분할만, 1장 제외 항목 — **개선**).

**F-262 가 미해결로 남겼던 것**(17행 "같은 문서를 양쪽에 여는 경우의 처리 — 한 문서에 `EditorState` 두 개, 불변조건 충돌")은 이 명세 6.4 가 **읽기 전용으로** 푼다. 불변조건은 "한 문서에 `EditorState` 하나" 가 아니라 "**열려 있는 문서 상태의 원본은 CM6 `EditorState` 하나**" 이므로, 탭마다 `EditorState` 가 있는 것 자체는 위반이 아니다(탭마다 앱 인스턴스가 따로다). 위반이 되는 것은 **둘이 같은 저장소 레코드에 동시에 쓰는 것**이고, 그것을 편집권 하나로 막는다.

### 4.1 사이드바 문서 우클릭 메뉴 (F-255)

`Sidebar.tsx` `DocRow` 260~275행·`PinnedRow` 318~333행의 `ownItems` 맨 앞에 넣는다

- `SharedDocRow`(363~381행)에는 `⋯` 메뉴 자체가 없다(F-212 2.4). **메뉴 항목을 주지 않는다.** 링크(4.2)만 준다

- `window.open(..., 'noopener')` 로 여는 이유는 5.2 — **`noopener` 가 없으면 sessionStorage 가 복제돼 F-213 편집 잠금이 깨진다**(8장에서 실측)

### 4.2 문서 라벨을 링크로 — 가운데클릭

`DocRow`(291~298행)·`PinnedRow`(342~348행)·`SharedDocRow`(369~375행)의 `<button className="tree-label doc-item-btn">` 을 이렇게 바꾼다

```tsx
<a
  className="tree-label doc-item-btn"
  href={formatHash(node.id)}
  draggable={false}
  aria-current={node.id === ctx.currentDocId ? 'page' : undefined}
  onClick={(e) => { e.preventDefault(); ctx.onItemClick(e, item, () => ctx.onSelectDoc(node.id)) }}
>
  {node.title}
</a>
```

| 조작 | 결과 | 왜 |
| --- | --- | --- |
| 일반 클릭 | 지금 그대로 — 이 탭에서 문서를 연다 | `onClick` 의 `preventDefault()` 로 브라우저 이동을 막고 기존 `handleItemClick`(764~775행)을 그대로 탄다. `selectDoc` 이 `beforeLeaveDoc()`(저장 flush)·`pushHashUrl` 을 한다 — 브라우저 기본 이동은 그걸 건너뛰므로 막아야 한다 |
| `Ctrl`/`Cmd`+클릭 | 지금 그대로 — **여러 선택 더하기·빼기** (F-255 2장). 새 탭은 열리지 않는다 | `click` 에서 `preventDefault()` 하면 Chrome 이 새 탭을 열지 않는다 — 8.3 에서 실측 |
| `Shift`+클릭 | 지금 그대로 — 범위 선택 (F-255 3.1). 새 창은 열리지 않는다 | 위와 같다 |
| **가운데클릭** | **배경 새 탭**에서 그 문서가 열린다. 앱 코드는 한 줄도 돌지 않는다 | 브라우저 기본 동작. `click` 이 아니라 `auxclick` 이고 `preventDefault()` 의 영향을 받지 않는다 — 8.3 에서 실측 |
| 드래그 | 지금 그대로 — 행(`.tree-row`)의 `draggable` 이 받는다 | `<a href>` 는 기본이 `draggable=true` 라 그대로 두면 링크 URL 드래그가 시작돼 F-255 끌어놓기를 가로챈다. **`draggable={false}` 가 필수다** |

- **`<button>` 을 유지하고 `auxclick` 을 듣는 방법은 쓰지 않는다.** 스크롤되는 영역(`.sidebar-scroll`) 안의 `<button>` 을 가운데클릭하면 Chrome 이 자동 스크롤 모드로 들어가 **`auxclick` 이 아예 오지 않는다** — 8.3 실측. `mousedown` 을 `preventDefault()` 해 자동 스크롤을 막는 우회가 필요한데, 그러면 드래그 시작까지 망가진다. `<a href>` 는 그 문제가 없다
- `onItemClick` 의 타입(Sidebar.tsx 97행)을 `ReactMouseEvent<HTMLButtonElement>` → `ReactMouseEvent<HTMLElement>` 로 넓힌다. 폴더 라벨(223행)은 `<button>` 그대로다
- `SharedDocRow` 는 메뉴가 없으므로 `onClick={(e) => { e.preventDefault(); ctx.onSelectDoc(doc.id) }}` 로만 고친다

## 5. 결론 — 미루지 않고 여기서 정한 것

### 5.1 BroadcastChannel 로 무엇을 보내는가 — **"바뀌었다" 신호만 보낸다**

**결정: 변경 내용을 통째로 보내지 않는다. `{ kind: 'docs-changed' }` 신호만 보내고 받는 탭이 저장소를 다시 읽는다.**

근거 셋:

1. **다시 읽는 비용이 충분히 싸다 — 실측(8.1).** 문서 1,000개(문서당 4KB)에서 `list()` 전체 재읽기 + `stripContent` + 정렬이 **23ms**, 5,000개에서 **105ms**. 사람이 알아채는 문턱(100ms)에 5,000개에서야 닿는다. 그마저도 250ms 디바운스로 묶여 연속 변경에서는 한 번만 돈다
2. **이미 그렇게 하고 있다.** `App.tsx` 1778·1997~2000·2093~2096행 세 곳이 **폴더 삭제·이동 뒤에 이미 `store.list()` 전체를 다시 읽는다.** 새로운 종류의 비용이 아니다
3. **내용을 보내면 코드 경로가 둘이 된다.** 보내는 쪽이 만든 `Doc` 을 받는 쪽이 React state 에 합치려면 `setDocs` 의 합치기 규칙(App.tsx 397~401·1155·1365·1944~1949·2059·2130행 등 10곳 이상)을 두 번째로 구현해야 한다. 두 경로는 반드시 어긋난다. 게다가 본문(`content`)을 실어 보내면 열린 `EditorState` 에 밀어 넣고 싶은 유혹이 생기는데 그건 불변조건 위반이다

**보내는 메시지는 4종뿐이다** (6.1). 본문(`content`)은 **어떤 메시지에도 넣지 않는다**.

`doc-deleted` 같은 전용 메시지도 두지 않는다 — 다시 읽은 목록에 `currentDocId` 가 없으면 지워진 것이다 (7.3).

### 5.2 같은 문서를 두 탭에 여는 경우 — **허용하되 나중 탭이 읽기 전용**

**결정: 막지 않는다. 기존 탭으로 보내지도 않는다. 두 번째 탭은 읽기 전용이 되고, 먼저 연 탭이 그 문서를 놓으면 되찾는다.** F-213 서버 잠금과 **똑같은 모양**이다.

`md.lockSession` 이 sessionStorage 라는 사실(`src/storage/docsApi.ts` 40·46~58·61행)을 실제로 따져 보면 이렇다 — 8.2 에서 실측:

| 여는 방법 | sessionStorage 복제 | `lockSessionId` | 서버 문서에서 벌어지는 일 |
| --- | --- | --- | --- |
| `<a target="_blank" rel="noopener">` | **안 됨** | 새 값 | 두 번째 탭이 `423 locked` → 읽기 전용 + `다른 창에서 편집 중입니다.` **F-213 설계대로 맞게 동작한다** |
| `<a target="_blank">` (rel 없음) | **안 됨** (Chrome 153 은 `target=_blank` 에 `noopener` 를 기본 적용) | 새 값 | 위와 같다 |
| `window.open(url, '_blank', 'noopener')` | **안 됨** | 새 값 | 위와 같다 |
| **`window.open(url, '_blank')`** (noopener 없음) | **복제됨** | **같은 값** | 서버가 두 탭을 **같은 세션으로 보고 둘 다 `200`** 을 준다. 둘 다 편집 가능 → 나중 PUT 이 앞 PUT 을 덮는다. **저장 유실** |
| 가운데클릭 (링크) | 안 됨 | 새 값 | 맞게 동작한다 |
| Chrome `탭 복제` | **복제됨** | **같은 값** | ~~같은 유실~~ **F-297 이 부팅 때 새 id 를 발급해 막는다** (2026-09-21) |

→ **그래서 4.1 의 `window.open` 은 세 번째 인자 `'noopener'` 가 필수다.** 이 문자열 하나가 빠지면 서버 문서에서 저장이 유실된다. 4.2 의 링크 경로는 Chrome 이 알아서 `noopener` 라 안전하다.

**`src/app/useDocLock.ts`·`src/storage/docsApi.ts` 에 요구하는 것: 없다 (한 줄도 고치지 않는다).**

- `docsApi.ts` 46~58행 `resolveLockSessionId()` — 새 탭은 sessionStorage 가 비어 있으므로 새 UUID 를 만든다. **F-213 2.2 "같은 사람의 다른 창도 다른 세션이다" 가 그대로 성립한다**
- `useDocLock.ts` 145행 `applicable = isServerStore && Boolean(docId) && role !== 'view' && online` — 서버 문서에서만 켜진다. 그대로 둔다
- `useDocLock.ts` 21~24행 `lockedMessage` — 자기 자신의 다른 창이면 이미 `다른 창에서 편집 중입니다. 읽기만 할 수 있습니다.` 를 준다. 새 탭도 이 문구를 받는다. **고치지 않는다**
- 실제로 이 동작을 검증하는 e2e 가 이미 있다 — `e2e/docLock.spec.js` 200~217행 `F-250 A6 같은 문서를 다른 탭에서 열면 그 탭은 읽기 전용이다`. `context.newPage()` 로 두 번째 탭을 만들고 `#/d/{id}` 로 간다. **F-296 이 만드는 흐름과 같다**

**구멍은 로컬(IndexedDB) 문서다.** 로컬에는 잠금이 없다. `useDocSaver` 는 700ms 디바운스로 `store.update(id, { content })` 를 쏘고(`useDocSaver.ts` 5·68행), `idbStore.update` 는 읽고-합쳐-쓴다(`idbStore.ts` 152~165행, 30~36행 `applyPatch`). 두 탭이 같은 문서를 열면 **나중에 저장한 쪽이 이깁니다. 경고도 흔적도 없다.** 그래서 로컬 문서에도 편집권을 준다 — 6.4.

**다른 선택지를 안 고른 이유:**

| 안 | 왜 안 쓰나 |
| --- | --- |
| 같은 문서면 메뉴 항목을 감춘다 | 사이드바에서 다른 문서를 눌러 도달하는 경로, 주소창에 붙여 넣는 경로를 못 막는다. 겉만 가린다 |

### 5.4 BroadcastChannel 미지원 환경 — **폴백을 두지 않는다**

**결정: `storage` 이벤트 폴백을 두지 않는다. `typeof BroadcastChannel === 'undefined'` 면 탭 동기화 기능 전체를 조용히 끈다(앱은 지금과 똑같이 동작한다).**

- 지원 범위(`node_modules/caniuse-lite/data/features/broadcastchannel.js`, 1.0.30001810): **Chrome 54+, Edge 79+, Firefox 38+, iOS Safari 15.4+**
- 판정 기준 브라우저는 **데스크톱 Chrome** 하나다 (`specs/product.md` 9장 Q7). Edge 도 Chromium 79+ 라 전부 지원

- 기능이 꺼지면 무엇이 안 되나: 다른 탭의 변경이 자동으로 안 보인다(새로고침하면 보인다), 같은 문서를 두 탭에서 열어도 로컬 문서에 경고가 없다(= 지금과 같다). **없던 기능이 없는 것이지 회귀가 아니다**

## 6. 설계

### 6.1 메시지 (4종)

```ts
// src/app/tabSync.ts
// 2026-09-21 F-297: TAB_CHANNEL_NAME·CLAIM_WAIT_MS·newTabId 는 src/lib/tabChannel.ts 로
// 옮기고 이 파일이 그대로 다시 내보낸다(re-export). 부르는 쪽은 안 바뀐다
export const TAB_CHANNEL_NAME = 'md-tabs'   // 저장소 식별자에 제품명을 쓰지 않는다 (CLAUDE.md 불변조건)
export const RESYNC_DEBOUNCE_MS = 250
export const CLAIM_WAIT_MS = 150
export const CLAIM_RETRY_MS = 15_000        // useDocLock.ts 6행 RETRY_INTERVAL_MS 와 같은 값

export type TabMessage =
  | { kind: 'docs-changed'; tabId: string }
  | { kind: 'claim-query';   tabId: string; docId: string }
  | { kind: 'claim-hold';    tabId: string; docId: string; since: number }
  | { kind: 'claim-release'; tabId: string; docId: string }
```

- `tabId` 는 탭마다 `crypto.randomUUID()` 로 한 번 만들고 **메모리에만** 둔다. sessionStorage 에 넣지 않는다 — 새로고침하면 새 탭으로 쳐도 된다(편집권은 어차피 다시 잡는다)
- **받은 메시지의 `tabId` 가 내 것이면 전부 무시한다.** `BroadcastChannel` 객체는 자기가 보낸 것을 자기에게 주지 않지만, **같은 탭 안의 다른 채널 객체에는 준다**(8.5 실측). `src/main.tsx` 가 `StrictMode` 라 개발 중 effect 가 두 번 돌아 채널이 잠깐 둘이 될 수 있다. 한 줄 방어로 막는다
- **본문(`content`)을 싣는 메시지는 없다**

### 6.2 보내기 — 저장소를 감싼다 (`withTabBroadcast`)

보내는 자리를 사람이 일일이 찾아 넣으면 반드시 빠뜨린다(`App.tsx` 안에 저장소를 바꾸는 자리가 15곳이 넘는다). **저장소를 한 번 감싸서 한 곳에서 보낸다.**

```ts
// src/app/tabSync.ts
export function withTabBroadcast(store: Store, post: (m: TabMessage) => void, tabId: string): Store
```

- 감싸는 메서드: `create`·`update`·`remove`·`moveDoc`·`setPinned`·`createFolder`·`renameFolder`·`moveFolder`·`removeFolder`. 각각 **성공(resolve)한 뒤에만** `post({ kind: 'docs-changed', tabId })`
- 첨부(`putAttachment`·`removeAttachment`)는 보내지 않는다 — 사이드바 목록에 안 나온다
- 읽기(`list`·`get`·`listFolders`·`listAttachments`·`getAttachment`)는 보내지 않는다
- **나머지 속성은 그대로 통과시킨다** — `kind`, `subscribeSync`(F-207), `importLocal`·`refreshDocFromServer`(서버 저장소만). `{ ...store, create: ..., update: ... }` 로 충분하다. 세 저장소 모두 평범한 객체 리터럴에 클로저를 담아 돌려주므로(`idbStore.ts` 113행, `memoryStore.ts`, `serverStore.ts` 483행) 펼쳐도 `this` 가 깨지지 않는다 — 확인함
- **`App.tsx` 의 `setStore(resolvedStore)`(620행) 한 곳만** `setStore(withTabBroadcast(resolvedStore, post, tabId))` 로 바꾼다. 그러면 `App.tsx` 안 모든 저장 경로가 자동으로 신호를 보낸다

### 6.3 받기 — `useTabSync`

```ts
// src/app/useTabSync.ts
export function useTabSync({
  enabled,        // bootPhase === 'ready'
  tabId,
  claimDocId,     // 편집권이 필요한 문서 id. store.kind !== 'idb' 이거나 문서가 없으면 null
  onDocsChanged,  // 디바운스된 뒤 1회 — App 의 resyncFromStore

  onClaimRegained, // 편집권을 되찾았을 때 — 저장소에서 다시 읽어 에디터를 다시 마운트
```

- 채널은 `useRef` 에 **탭당 하나**. `typeof BroadcastChannel === 'undefined'` 면 `post` 는 아무것도 안 하고 `claimReadOnly` 는 항상 `false`
- `docs-changed` 를 받으면 `RESYNC_DEBOUNCE_MS`(250ms) 뒤에 `onDocsChanged()` 를 **한 번** 부른다. 그 사이 더 오면 타이머를 다시 건다
- 언마운트·`pagehide` 에 `claim-release` 를 보내고 채널을 닫는다

### 6.4 편집권 (로컬 문서 전용)

**켜지는 조건: `store.kind === 'idb'` 이고 문서가 열려 있을 때만.** 서버 저장소는 F-213 이 맡고(5.2), 메모리 저장소는 탭마다 저장소가 따로라 겹칠 일이 없다.

개발 빌드 `?ysync`(F-303 9.4)에서는 편집권을 잡지 않는다.

낙관적으로 시작한다 — **문서를 열면 곧바로 편집 가능**하고, 다른 탭이 잡고 있다고 답하면 그때 읽기 전용으로 내린다. `useDocLock`(App.tsx 408~416행)이 `423` 을 받고 내리는 것과 같은 모양이다.

| 상황 | 동작 |
| --- | --- |
| 문서를 연다 | `since = Date.now()`, `held = true`(편집 가능). `claim-query` 를 보낸다 |
| 남의 `claim-query` 가 왔고 내가 그 문서를 `held` | `claim-hold { docId, since }` 로 답한다 |
| 남의 `claim-hold` 가 왔고 내가 그 문서를 `held` | `claimWins(남, 나)` 면 내가 내려온다(`held = false`). 아니면 그대로 |
| 읽기 전용이 됐다 | 알림(info) `다른 탭에서 편집 중입니다. 읽기만 할 수 있습니다.` + 에디터·제목 읽기 전용 + **대기 중인 자동 저장 폐기**(7.4) + `CLAIM_RETRY_MS`(15초)마다 `claim-query` 재시도 |
| 남의 `claim-release` 가 내 문서로 왔고 내가 읽기 전용 | 15초를 기다리지 않고 **즉시** `claim-query` 를 다시 보낸다 |
| `claim-query` 를 보내고 `CLAIM_WAIT_MS`(150ms) 안에 `claim-hold` 가 안 왔다 | 편집권을 가진다. `held = true`, `since = Date.now()`. 읽기 전용이었다면 알림(info) `이제 편집할 수 있습니다.` (`useDocLock.ts` 74행과 **같은 문자열**) + **저장소에서 문서를 다시 읽어 에디터를 다시 마운트**(`onClaimRegained`) |
| 문서를 떠난다 / `pagehide` / 언마운트 | `claim-release` 를 보낸다 |

```ts
// 둘 다 열려 있을 때 정확히 한 쪽만 내려오게 하는 규칙
export function claimWins(a: { since: number; tabId: string }, b: { since: number; tabId: string }): boolean {
  return a.since < b.since || (a.since === b.since && a.tabId < b.tabId)
}
```

- **먼저 연 쪽이 이긴다.** `since` 가 같은 드문 경우는 `tabId` 사전순으로 가른다. 이 규칙이 없으면 두 탭이 동시에 열렸을 때 서로 `claim-hold` 를 받고 **둘 다 읽기 전용**이 된다
- **죽은 탭은 자동으로 정리된다.** 임대·만료가 아니라 "물어보고 답 없으면 가진다" 방식이라, 탭이 크래시하거나 `claim-release` 를 못 보내고 사라져도 다음 재시도(15초)에 풀린다. 만료 시각을 어디에도 저장하지 않는다
- 읽기 전용으로 내려오기까지의 틈은 실측 **왕복 0.2ms(중앙값)·2.4ms(최대)** 다(8.5). 자동 저장 디바운스가 700ms(`useDocSaver.ts` 5행)라 **그 틈에 저장이 나갈 수 없다.** 그래도 7.4 의 `blocked` 로 한 겹 더 막는다

| 1,000 | 20KB | 81.7ms | 0.3ms | **82.0ms** |
| 5,000 | 20KB | 322.1ms | 1.4ms | **323.5ms** |

- 커서로 돌며 `content` 를 버리는 방식도 같이 쟀다 — **더 빠르지 않다**(1,000개 20.9~27.7ms, 5,000개 111.4~117.6ms). 레코드는 어차피 통째로 역직렬화된다. **그래서 목록 전용 인덱스·필드 분리 같은 최적화를 이번에 하지 않는다**
- 5,000개 × 20KB(= 문서만 100MB)는 극단이다. 그 구간에서 320ms 는 눈에 띄지만, 이번 신호로 **새로 생기는** 비용이 아니다 — 폴더를 지우기만 해도 지금 이미 그만큼 든다(App.tsx 1997행)

### 8.2 새 탭을 여는 방법별 sessionStorage 복제 (5.2 의 근거)

원래 탭에 `sessionStorage['md.lockSession'] = 'SESSION-A'`, `localStorage['md.viewMode'] = 'raw'` 를 넣고 열어 본 결과

| 여는 방법 | 새 탭의 `md.lockSession` | `window.opener` | 새 탭의 `localStorage` |
| --- | --- | --- | --- |
| `<a target="_blank" rel="noopener">` | `null` | 없음 | `raw` (공유됨) |
| `<a target="_blank">` (rel 없음) | `null` | 없음 | `raw` |
| `window.open(url, '_blank', 'noopener')` | `null` | 없음 | — |
| **`window.open(url, '_blank')`** | **`SESSION-A`** | **있음** | — |

### 8.3 가운데클릭·수정자 클릭 (4.2 의 근거)

| 실험 | 결과 |
| --- | --- |
| `<a href>` 가운데클릭 | **새 탭이 열린다** (`context.waitForEvent('page')` 로 확인) |
| `<a href>` 가운데클릭 + `click` 에 `preventDefault()` | **그래도 새 탭이 열린다** (가운데클릭은 `click` 이 아니라 `auxclick`) |
| `<a href>` 가운데클릭 + `mousedown` 에 `preventDefault()` | **그래도 새 탭이 열린다** |
| `<a href>` Ctrl+클릭, `click` 에 `preventDefault()` | **새 탭이 안 열린다**, `click` 핸들러는 `ctrlKey=true` 로 불린다 |
| `<a href>` Shift+클릭, `click` 에 `preventDefault()` | **새 창이 안 열린다**, 핸들러는 `shiftKey=true` 로 불린다 |
| `<button>` 가운데클릭, **스크롤 없는** 페이지 | `pointerdown`→`mousedown`→**`auxclick` 온다** |
| **`<button>` 가운데클릭, 스크롤되는 페이지(body 3000px)** | `pointerdown`→`mousedown` 까지만. **`auxclick` 이 안 온다** (Chrome 자동 스크롤이 먹는다) |

→ 사이드바는 스크롤되는 영역이다. **`<button>` + `auxclick` 은 못 쓴다.**

### 8.4 해시만 적힌 주소로 새 탭 (4.5 의 근거)

`http://measure.local/#/d/aaa` 에서 `window.open('#/d/ccc', '_blank', 'noopener')` → 새 탭 주소 `http://measure.local/#/d/ccc`, `sessionStorage['md.lockSession']` 은 `null`, 원래 탭 주소는 `#/d/aaa` 그대로.

### 8.5 BroadcastChannel (5.4·6.1·6.4 의 근거)

| 실험 | 결과 |
| --- | --- |
| 탭 A 가 보낸 메시지 | 같은 컨텍스트의 **다른 탭 전부**가 받는다 |
| **같은 탭 안의 다른 채널 객체** | **받는다** → 6.1 의 `tabId` 자기 무시 규칙이 필요한 이유 |
| 왕복 시간 (응답 탭 3개가 배경일 때, 20회) | **중앙값 0.20ms / 최대 2.40ms** |
| 왕복 시간 (요청 탭이 배경일 때, 20회) | **중앙값 0.20ms / 최대 0.50ms** |
| `localStorage.setItem` 의 `storage` 이벤트 | 다른 탭에만 온다(자기 탭에는 안 온다). 폴백 후보로 동작은 하지만 5.4 의 이유로 안 쓴다 |
| 한 Playwright 컨텍스트에 페이지 여러 개 | IndexedDB·localStorage·BroadcastChannel 전부 공유된다 → **9장 e2e 가 성립한다** |

→ `CLAIM_WAIT_MS = 150ms` 는 실측 최대(2.4ms)의 약 60배다.

## 13. 열린 질문 / 사람 결정 필요

### Q1. `Ctrl`/`Cmd`+클릭으로도 새 탭을 열까 — **기본값: 열지 않는다**

사이드바에서 `Ctrl`+클릭은 **F-255 가 여러 항목 선택에 쓰고 있다**(`Sidebar.tsx` 765~768행, `F-255.md` 2장). 둘 다 줄 수 없다. `Alt`+클릭은 Chrome 에서 링크 **다운로드**라 못 쓴다. 홈 화면 `최근 문서` 에는 충돌이 없지만, **두 목록에서 규칙이 다른 편이 더 나쁘다**고 봤다.
→ **다른 쪽을 고르면**: `F-255.md` 2장의 `Ctrl`/`Cmd`+클릭 규칙을 고쳐 다시 승인받아야 하고, 사이드바에서 **항목을 하나씩 더하고 빼는 수단이 사라진다**(범위 선택 `Shift`+클릭만 남는다). F-255 수용 기준 D4·D5 와 `e2e/sidebarSelect.spec.js` 86~101행을 지워야 한다.

### Q2. 공개 보기(S-5)·검색 대화상자(D-6)에도 줄까 — **기본값: 주지 않는다**

S-5 는 저장소를 열지 않아 탭 동기화가 무의미하고 `PublicFolderList` 라는 별도 컴포넌트다. D-6 은 결과를 새 탭에서 열 때 대화상자를 닫을지·포커스를 어디로 보낼지가 따로 정해져야 한다(F-287 3.28 6번과 충돌한다).
→ **주기로 하면**: S-5 는 `e2e/publicView.spec.js` 163·205행이 `getByRole('button', { name: '문서3' })` 을 쓰므로 그 두 줄이 깨진다. D-6 은 F-287·F-294 의 "열면 대화상자가 닫히고 포커스는 에디터로" 규칙에 예외가 생겨 두 명세를 고쳐야 한다. **별도 작은 명세로 빼는 편을 권한다.**

### Q3. 메뉴 항목이 **앞 탭**을 여는 것을 그대로 둘까 — **기본값: 그대로 둔다**

`window.open` 은 항상 앞 탭(포커스 이동)이고, 가운데클릭은 배경 탭이다. 브라우저가 정하는 것이라 앱이 고를 수 없다. 사용자가 메뉴에서 **골라서** 누른 경우엔 그 탭으로 가고 싶은 게 보통이라고 봤다.
→ **바꾸려면**: 앞 탭으로 가는 것이 싫다면 메뉴 항목 문구를 `새 탭에서 열고 이동` 으로 바꾸는 정도가 전부다. 배경 탭으로 여는 방법은 없다.

### Q4. 이미 다른 탭에 열려 있는 문서를 또 열려 할 때 알려줄까 — **기본값: 알리지 않는다**

지금 설계는 두 번째 탭이 열린 **뒤에** 읽기 전용 알림을 받는다. "이미 다른 탭에 열려 있습니다" 를 **열기 전에** 알리려면 메뉴를 그리는 시점에 편집권 상태를 물어봐야 하고(비동기 150ms), 메뉴가 늦게 뜬다.
→ **알리기로 하면**: 6.1 에 `claim-list` 같은 질의를 더하고, 사이드바가 "다른 탭에서 열림" 표시를 행에 그려야 한다(`specs/design.md` 토큰이 필요하다).

### Q5. 설정 18개 키를 탭 사이에 맞출까 — **기본값: 맞추지 않는다** (5.5)

3장에서 적었듯, 사이드바를 한쪽만 접어 공간을 버는 것이 탭마다 따로 놀지 않는다(`md.sidebar` 를 서로 덮어쓴다). 화면은 각자 자기 메모리 값을 쓰므로 **새로고침 전까지 눈에 보이는 고장은 없다.**
→ **맞추기로 하면**: 어느 키를 맞출지 하나씩 정하고(테마·서체는 `document.documentElement.dataset` 까지, `src/main.tsx` 24~32행), 각 키의 React state 되돌리기를 다 써야 한다. **별도 작은 명세 하나 분량이다.** 반대로 **탭마다 달라야 자연스러운 키**(`md.viewMode`·`md.sidebar`)도 있어서, 전부 맞추는 것이 답이 아닐 수 있다.

### Q6. Chrome `탭 복제` 로 생기는 서버 문서 저장 유실 — **이번 범위 밖. 사람 결정 필요**

8.2 에서 확인했다. `탭 복제`(또는 `noopener` 없는 `window.open`)는 sessionStorage 를 복제해 `md.lockSession` 이 같아지고, 서버가 두 탭을 한 세션으로 보아 **둘 다 편집 가능**해진다. 나중 저장이 앞 저장을 덮는다. **F-296 이 만드는 길이 아니라 F-250 3.1 이 sessionStorage 를 쓰기로 하면서 생긴 구멍이다.**
→ 고치려면 `docsApi.ts` 가 세션 id 에 **탭 고유 값**(6.1 의 `tabId` 같은, 메모리에만 있는 값)을 섞어야 하는데, 그러면 F-250 이 얻으려던 "새로고침해도 같은 세션" 이 깨진다. **별도 명세로 판단하기를 권한다.**

### Q7. F-262 를 정말 접는가 — **사용자 확인 필요**

3장의 "버리는 것" 여섯 가지를 읽고 그래도 새 탭으로 가는지. 특히 **창 배치를 사람이 직접 해야 한다**와 **사이드바가 양쪽에 중복으로 뜬다** 둘.
→ **접지 않기로 하면**: F-262 를 `overview` 로 되돌리고 F-263 부터 순서대로 쓴다. 그 경우에도 이 명세의 **5.1 탭 간 신호·6.4 편집권**은 쓸모가 남는다(분할이 있어도 탭 두 개를 쓰는 사람은 있다) — 그 두 가지만 남긴 축소판으로 다시 쓰면 된다.
