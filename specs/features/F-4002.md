## 2. A — 공유 링크 묶음 상한

### 2.1 쓰기 (`POST /api/docs/:id/link`, `/v1` 같은 핸들러)

```ts
// worker/links.ts
export const LINK_DOC_IDS_MAX = 100
export const LINK_BODY_MAX_BYTES = 8_192
```

- `readDocIds` 는 `readJsonLimited(request, LINK_BODY_MAX_BYTES)` 로 읽는다. `too_large` 면 `'bad_request'`. 8,192 는 UUID 100개 본문(r5, 3,912 B)의 두 배 남짓 — 공백·들여쓰기가 있어도 든다. `MAX_BODY_BYTES`(1,100,000)는 본문 업로드용이라 쓰지 않는다. `badBody` 도 쓰지 않는다(413 + 본문 크기 `limit` 이 이 라우트와 맞지 않는다)
- `invalid_json`·본문 없음·객체 아님·`docIds` 필드 없음 → 지금처럼 `undefined`(묶음 정보 없음). 단순 링크 복사·CLI 가 이 경로다 — 동작을 바꾸지 않는다
- `docIds` 가 배열이 아니거나 문자열 아닌 원소가 있거나 **원소 수 > 100** 이면 `'bad_request'`. 개수는 중복 제거·시작 문서 제외 **전** 원본 길이로 센다 — D1 을 부르기 전에 끝내는 것이 목적이다
- 소유 검사는 **질의 1개**로: `SELECT id, e2ee_key FROM docs WHERE owner_id = ?1 AND id IN (SELECT value FROM json_each(?2))`. 돌아오지 않은 id 가 하나라도 있으면 400(지금 규칙), 금고 문서는 조용히 뺀다(F-401 X8 그대로). 문서 수와 무관하게 질의 수가 같다(r4)
- `share_link_docs` 다시 쓰기는 `DELETE` 1문 + `INSERT INTO share_link_docs (token, doc_id) SELECT ?1, value FROM json_each(?2)` 1문. 사용량 줄과 한 batch(F-2025 6.4 그대로)
- 응답 형태·상태 코드·토큰 유지 규칙(F-259 2장)은 그대로

### 2.2 읽기 — 이미 100개를 넘는 묶음

- `handlePublicGetDocSet` 의 `SELECT id, title … WHERE id IN (…)` 과 `SELECT id, content, folder_id … WHERE id IN (…)` 을 `id IN (SELECT value FROM json_each(?))` 로 바꾼다. 순서는 지금처럼 메모리에서 `orderedIds` 로 맞춘다
- 결과: 묶음 크기와 무관하게 바인딩이 문당 2개라 **99개 이상 묶음이 지금 깨지던 것(r3)도 고쳐진다.** 이미 D1 에 100개를 넘는 묶음이 있어도 잘라내거나 지우지 않고 그대로 보여 준다 — 마이그레이션 없음. 그런 묶음은 소유자가 D-6 에서 다시 저장하면(앱은 50개 이하만 보낸다) 그때 줄어든다
- 자르지 않는 이유: 공개 독자가 이미 받은 주소에서 문서가 사라지면 소유자는 원인을 알 수 없다. 큰 묶음 한 번 읽기의 비용은 소유자 문서 메타 전체 읽기(`ownerDocs`)가 이미 지배한다
- `handlePublicGetDocSetDoc`·`isDocInLinkSet` 는 문서 하나씩이라 바꾸지 않는다

## 3. B — 권한 회수 뒤 열린 방 재검증

### 3.1 경로별 처리

"즉시" = 응답을 만든 뒤 `ctx.waitUntil` 로 RPC 를 보낸다(F-304 9.3 도우미 규칙). 회수 전에 도착한 편집은 이미 적용·중계되어 되돌릴 수 없다 — 즉시 재검증은 창을 RPC 지연으로 줄일 뿐이다

| 경로 | 처리 | 이메일 거르기 |
| --- | --- | --- |
| 문서 초대 삭제·`view` 로·문서 나가기 | 지금 그대로(`notifyRevalidate`) | 그 이메일 |
| **폴더 초대 삭제** `DELETE /api/folders/:id/grants/:email` | **즉시** — 그 폴더 하위(재귀) 문서 방 | 그 이메일 |
| **폴더 초대 `view` PUT, 기존 행을 바꿀 때** | **즉시** — 같음. 새로 만든 초대(`RETURNING created_at` 이 `now`)는 잃은 권한이 없어 보내지 않는다. `edit` PUT 은 보내지 않는다 | 그 이메일 |
| **폴더 이동** `PUT /api/folders/:id` 의 `parentId` 변경 | 잃은 상위 폴더(3.2)에 폴더 초대가 있을 때만 **즉시** — 옮긴 폴더 하위 문서 방 | 거르지 않음(누가 잃었는지 묻지 않는다) |
| **문서 이동** `PUT /api/docs/:id/folder`, `PUT /v1/docs/:id/folder` | `folder_id` 가 실제로 바뀌고 금고 문서가 아니면 **즉시** — 그 문서 방 1개 | 거르지 않음 |
| **폴더 지우기 `move-up`**(`/api`·`/v1` 공용 `deleteFolderContents`) | 지운 폴더에 폴더 초대가 있었을 때만 **즉시** — 지우기 batch **전에** 그 폴더 하위 문서를 구하고, batch 뒤에 보낸다 | 거르지 않음 |
| 폴더 지우기 `delete-all`, 문서 지우기 | 지금 그대로(`notifyPurge`) | — |
| 폴더를 금고로 켜기 | 없음 — 켜기는 일반 하위 문서·폴더가 0개일 때만 된다(`TURN_ON_SQL`). 방이 있는 문서가 없다 | — |
| 폴더 나가기(받은 사람) | **지연 허용**(최대 약 90초). 본인이 스스로 버린 권한이라 막을 제3자가 없고, 클라이언트가 나간 직후 열린 문서를 닫는다(F-3011 3.3, F-2115). 하위 문서가 많으면 최대 20번 RPC 를 쓸 이유가 없다 | — |
| 계정 삭제 — 소유 문서 | 바꾸지 않는다. `docs` 행이 지워져 다음 스냅숏이 `roomGone` 으로 끝나고 D1 에 쓰지 않는다(r10). 방 비우기는 `purge_jobs`(F-2038) | — |
| 계정 삭제 — 받은 초대 | **지연 허용**. 지운 사람이 본인이고, 그 사람의 열린 연결은 직전까지 정당한 권한이었다. 받은 문서 목록을 지우기 전에 모으려면 소유자 여럿에 걸친 팬아웃이 든다 | — |
| 관리자 차단(`blocked_at`) | **지연 허용**. Worker 경로가 없다(r9) — 알리려면 새 라우트가 필요하고 정해진 것 4번이 막는다. 소유자가 막힌 방은 첫 스냅숏 뒤 `mayWrite` 가 D1 쓰기를 멈춘다. 막힌 사람이 남의 문서를 편집하는 창은 최대 약 90초(F-2028 6.2 결정 그대로) | — |

### 3.2 대상 문서 구하기 (`worker/revalidateTargets.ts`)

```ts
export type RoomTargets = { ids: string[]; capped: boolean }
export async function subtreeRoomDocIds(env: Env, folderId: string, ownerId: string): Promise<RoomTargets>
export function lostAncestorIds(folders: FolderLike[], oldParentId: string | null, newParentId: string | null): string[]
export async function anyFolderGrant(env: Env, ownerId: string, folderIds: readonly string[]): Promise<boolean>
```

- **`subtreeRoomDocIds`** — 질의 1개. 그 폴더(소유자 것)와 하위 폴더 전부를 재귀 CTE 로 내려가 `docs` 와 잇고, `e2ee_key IS NULL`(금고 문서는 방이 없다 — `docRoomCore.ts` `ACCESS_ROW_SQL`), `ORDER BY updated_at DESC LIMIT REVALIDATE_FANOUT_MAX + 1`. 한 개 더 읽어 `capped` 를 정하고 `ids` 는 앞 20개
  - **재귀 단계는 `owner_id` 를 `sub` 행에서 이어받는다**(`grants.ts` `SHARED_SUBTREE_CTE` 와 같은 모양, `folders_owner_parent` 색인을 `(owner_id, parent_id)` 로 쓴다). 바인딩 상수로 쓰면 33배 더 읽는다(r8)
  - `FOLDER_CHAIN_SQL`(위로 올라감)·`getDocAccess`(문서 하나)는 아래로 내려가는 이 질문에 맞지 않아 재사용하지 않는다. `links.ts` `ownerFolders` + `descendantFolderIds` 방식은 소유자 폴더·문서 전부를 읽어(r8 같은 데이터에서 3,501행) 작은 하위 트리에서 손해다
  - `updated_at` 내림차순인 이유: 편집 중인 방은 스냅숏마다 `updated_at` 이 오른다(r11). 상한에 걸려 빠진 문서는 최근 편집이 없는 쪽이다
- **`lostAncestorIds`** — 순수. `folderAncestors(folders, oldParentId)` 에서 `folderAncestors(folders, newParentId)` 에 없는 것. 옮긴 폴더 자신과 그 하위의 초대는 같이 움직이므로 잃지 않는다. 이동 전 폴더 표(`handleUpdateFolder` 가 이미 읽은 `ownFolders`)로 계산한다
- **`anyFolderGrant`** — `SELECT 1 FROM grants WHERE owner_id = ?1 AND target_type = 'folder' AND target_id IN (SELECT value FROM json_each(?2)) LIMIT 1`. 빈 목록이면 질의 없이 `false`
- 폴더 이동은 `lostAncestorIds` 가 비면 `anyFolderGrant` 도 부르지 않는다 — 최상위에서 옮기는 흔한 경우에 D1 질의가 늘지 않는다

### 3.3 비용 상한

- **한 요청에서 방 RPC 는 최대 20개**(`REVALIDATE_FANOUT_MAX`). 넘는 문서는 기존 주기 점검(최대 약 90초, r7)에 맡기고 `console.warn` 한 줄(`room revalidate capped`, 폴더 id)
- 20 의 근거: 무료 플랜 호출당 하위 요청 50(r4). F-2038 이 같은 예산에서 계정 삭제 요청의 방 RPC 를 15(`PURGE_CALLS_ON_DELETE`)로 잡은 것과 같은 보수적 계산 — `waitUntil` 작업도 같은 호출의 하위 요청으로 센다고 본다(가정 G1). 이 경로의 D1 질의는 인증·대상 확인·batch·대상 질의로 한 자릿수라 D1 50 한도와 겹치지 않는다
- 연결이 없는 방에 보낸 RPC 는 `revalidateConnections` 가 `targets.length === 0` 에서 D1 없이 끝난다(F-304 9.3) — 비용은 DO 요청 1건
- 대상 질의는 응답 전에 `await` 한다(1문). RPC 는 `dispatch` 처럼 문서마다 `waitUntil` 에 맡겨 응답을 늦추지 않는다

### 3.4 계약 (`worker/docRoomRpc.ts`, `worker/docs.ts`)

```ts
export const REVALIDATE_FANOUT_MAX = 20
export function notifyRevalidateDocs(env: Env, ctx: ExecutionContext | undefined, docIds: readonly string[], email?: string): Promise<void>

export async function writeMoveDocFolder(env: Env, ctx: ExecutionContext | undefined, existing: DocRow, folderId: string | null): Promise<DocRow>
```

- `notifyRevalidateDocs` 는 앞 `REVALIDATE_FANOUT_MAX` 개만 보낸다(부르는 쪽이 이미 잘랐어도 한 번 더 지킨다). 문서마다 `revalidateConnections(email)` — `email` 이 없으면 모든 연결을 본다. 도우미 규칙(`DOC_ROOM` 없음 → 아무것도 안 함, 던지면 삼킴)은 `notifyRevalidate` 그대로
- 기존 `notifyRevalidate` 시그니처는 바꾸지 않는다(문서 초대 경로·테스트 그대로)

## 8. 열린 질문

### Q1. 상한을 넘는 하위 문서를 어떻게 하나 — **기본값: 20개만 보내고 나머지는 주기 점검(최대 약 90초)**
- 이유: 새 표·마이그레이션 없이 끝나고, 상한에서 빠지는 것은 최근 스냅숏이 없는 방(r11)이다. 폴더 하나에 열린 편집 방이 20개를 넘는 일은 지금 규모에서 드물다고 본다(가정 G2)
- 다른 안: `purge_jobs` 처럼 남은 문서를 D1 표에 적고 10분 Cron 이 비운다 — 마이그레이션 1개, `purgeJobs.ts` 에 `kind = 'revalidate'` 추가, 이 명세 소유 표에 `migrations/`·`worker/purgeJobs.ts` 가 붙는다. Cron 주기가 10분이라 90초 점검보다 늦어 이득이 없다. 또 다른 안: Workers 유료로 상한을 올림(product.md Q42 비용 결정)
