## 1. 범위 — 무엇이 바뀌고 무엇이 그대로인가

### 1.1 바뀌는 접점은 하나

- 바뀌는 것은 **"요청 → `AuthUser { id, email }`"** 한 곳이다. `worker/auth.ts` 의 `getUser(request, env, ctx?)` 와 `requireUser(…)` 의 **시그니처와 반환 모양은 그대로** 두고 속만 바꾼다
  - 이유: `worker/` 의 테스트 9개(`apiTokens`·`attachments`·`docRoomRpc`·`docSocket`·`folders`·`grants`·`links`·`shares`·`v1`)가 `vi.mock('./auth')` 로 이 두 함수를 흉내 낸다. 모양을 지키면 그 테스트들이 손대지 않고 통과한다
- 권한(`worker/access.ts`)·공유·초대(`grants`)·공개 링크·DO 재검증(`revalidateConnections` 가 `{ userId, email }` 로 `resolveDocAccess`)은 **이메일·사용자 id 만 보므로 바뀌지 않는다**
- 앱 쪽 로그인 **진입 주소 `loginUrl(hash)` = `/api/login?return=…` 도 그대로 둔다**(3.1). 바뀌는 것은 그 주소가 Access 대신 `/login` 으로 보낸다는 것과 로그아웃 방식(3.6)뿐이다

### 1.2 그대로 두는 것

| 대상 | 이유 |
| --- | --- |
| `/v1/*` — `Authorization: Bearer rd_…` 만, 쿠키를 보지 않음(`getUser` 의 `/v1/` 분기 → `getTokenUser`) | 결정 9. CLI 무변경 |
| `/pub/*`·`/p/*` 공개 경로 | 로그인과 무관 |
| DO(`worker/docRoom.ts`) | 인증은 DO 로 넘기기 **전에** Worker 가 한다(`docSocket.ts` `resolveDocSocket` → `getUser`). DO 는 `X-WS-*` 헤더만 읽는다. **DO 쪽 코드 변경 없음** |
| `md.account` localStorage 키, `fetchAccount()` 의 `in`·`out`·`offline` 판정 | `/api/me` 의 200·401 계약이 그대로다 |
| IndexedDB `md-remote` 캐시 | 로그아웃해도 지우지 않는다(`remoteCache.ts` 머리 주석, F-207 2.1). 세션이 만료돼도 같다 — 기본값 "로컬 캐시 유지" 는 지금 동작 그대로다 |
| 닫기 코드 `4401` → 상태바 `다시 로그인 필요`·N4 (F-305) | 세션이 만료된 뒤 재연결하면 `getUser` 가 null → `4401`. 문구·흐름 그대로 |

## 2. 서버 — better-auth 구성

### 2.1 의존성

| 패키지 | 판 | 넣는 곳 | 크기(측정) | 비고 |
| --- | --- | --- | --- | --- |
| `better-auth` | **`1.7.5` 정확히 고정**(`^` 없음. `three` 를 `0.186.0` 으로 고정한 선례) | `dependencies` | Worker gzip +330 KiB(압축 안 함) / +223 KiB(minify) — 머리말 표 | MIT. 따라오는 것: `@better-auth/core`·`kysely-adapter` 등 1.7.5, `kysely` 0.29.6, `zod` 4.6.5, `jose` 6.2.12, `better-call` 1.4.0, `@noble/ciphers`·`@noble/hashes` 2.4.0, `nanostores` 1.5.3, `defu` 6.1.7, `@better-fetch/fetch` 1.3.2 (전부 MIT) |
| `kysely-d1` | **넣지 않는다** | — | — | `database: env.DB` 를 그대로 넘기면 better-auth 가 `batch`·`exec`·`prepare` 를 보고 **내장 `D1SqliteDialect`** 를 고른다(`@better-auth/kysely-adapter` `index.mjs`). 로컬 D1 로 로그인 전 과정을 돌려 확인했다 |

- 고정 이유: 이 개요는 better-auth **내부 동작**(연결 조건, `validateUserInfo` 호출 위치, 날짜 저장 방식, 스키마 필드)에 기대 결정을 내렸다. 판을 올릴 때는 F-2033 의 스키마 검사 테스트(6장 "판정 나눔")와 연결 규칙 테스트를 다시 돌린 뒤 올린다
- 웹앱 번들(`src/`)은 이 패키지를 import 하지 않는다. 앱 쪽 로그인·로그아웃은 `fetch` 두 줄이라 `better-auth/react` 클라이언트도 쓰지 않는다
- 지금 Worker 의 gzip 은 약 102 KiB(메인 전달값, 이 개요에서 다시 재지 않음). 더하면 약 430 KiB 다. Workers 번들 한도는 2026-09-04 부터 64 MiB 비압축(메인 조사)이라 한도 문제는 없다. 남는 위험은 **시작 시간·CPU**(2.7)

### 2.2 better-auth 설정 — 계약

인스턴스는 새 파일 `worker/authServer.ts`(F-2033) 한 곳에서 만든다. 아래 표의 키와 값은 계약이다 — 표 이름·쿠키 이름·오류 코드가 여기서 정해지고 3장·4장·F-2024 가 거기에 댄다

| 옵션 | 값 | 이유 |
| --- | --- | --- |
| `baseURL` | `env.BETTER_AUTH_URL` (운영 `https://rawdoc.app`) | OAuth `redirect_uri` 와 쿠키 `Secure`·`__Secure-` 접두사가 여기서 정해진다 |

- **인스턴스는 isolate 하나에 한 번만 만든다**(첫 사용 때 만들어 모듈 변수에 둔다). 생성이 첫 요청에서 약 11ms(Node 근사) 걸리는데 요청마다 만들면 그 비용을 매번 낸다. `import { env } from 'cloudflare:workers'` 로 모듈 최상위에서 만들지 **않는다** — `worker/v1.test.ts` `freshWorker` 가 node 환경에서 `worker/index.ts` 를 import 하고, 거기서는 `cloudflare:workers` 가 없다
- `nodejs_compat` 호환 플래그를 **켠다**(`wrangler.jsonc` `compatibility_flags`). better-auth 는 `workerd` 조건에서 `node:crypto` 판을 고르고(`@better-auth/utils` `exports["./password"].workerd`), `node:async_hooks` 의 `AsyncLocalStorage` 가 없으면 `validateUserInfo` 가 `validation_context_missing` 으로 실패한다(`internal-adapter.mjs` `createUser`). 로컬 workerd 는 플래그 없이도 둘을 불러왔지만 운영도 그런지 확인하지 않았다 — 켜도 번들 크기가 같았으므로(측정) 명시적으로 켠다

### 2.3 D1 마이그레이션 — 계약

번호는 F-2033 을 구현할 때 **다음 빈 번호**(HEAD `3aca17c` 기준 `0009`)다. F-308 이 먼저 마이그레이션을 더하면 그다음 번호가 된다. F-2024 의 F-2025 는 이것 **뒤** 번호로 밀린다(8장). 아래는 초안이고, 열 이름·표 이름·열 타입이 계약이다(2.2 매핑과 F-2033 의 스키마 검사 테스트가 이 모양에 댄다)

```sql
-- users: better-auth 가 요구하는 열을 더한다. id·email·created_at 은 그대로
ALTER TABLE users ADD COLUMN name TEXT NOT NULL DEFAULT '';
ALTER TABLE users ADD COLUMN email_verified INTEGER NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN image TEXT;
ALTER TABLE users ADD COLUMN updated_at TEXT;               -- better-auth 가 ISO 문자열로 쓴다
UPDATE users SET email_verified = 1,
                 updated_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now');

CREATE TABLE auth_sessions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token TEXT NOT NULL UNIQUE,
  expires_at TEXT NOT NULL,                                  -- ISO
  ip_address TEXT,
  user_agent TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX auth_sessions_user ON auth_sessions(user_id);

CREATE TABLE auth_accounts (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  account_id TEXT NOT NULL,                                  -- 제공자 쪽 사용자 id (Google sub, GitHub id)
  provider_id TEXT NOT NULL,                                 -- 'google' | 'github'
  access_token TEXT,
  refresh_token TEXT,
  id_token TEXT,
  access_token_expires_at TEXT,
  refresh_token_expires_at TEXT,
  scope TEXT,
  password TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (provider_id, account_id)
);
CREATE INDEX auth_accounts_user ON auth_accounts(user_id);

CREATE TABLE auth_verifications (                            -- 쓰지 않지만 better-auth 스키마 검사가 요구한다(측정)
  id TEXT PRIMARY KEY,
  identifier TEXT NOT NULL,
  value TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX auth_verifications_identifier ON auth_verifications(identifier);
```

- **`UPDATE users SET email_verified = 1` 을 빼면 안 된다.** 지금 원격 `users` 의 행은 Access 가 이메일을 확인한(일회용 코드 또는 Google) 사람들이다. 이 줄이 없으면 그 사람이 Google·GitHub 로 로그인할 때 연결 조건 "기존 행 `email_verified = 1`" 에 걸려 `account_not_linked` 로 **자기 계정에 못 들어간다**(측정). 결정 3 "기존 사용자 없음" 이어도 운영자 본인의 행과 문서는 있다 — 원격 행 수는 조회하지 않았다
- `created_at` 은 INTEGER ms 그대로 둔다(2.2 훅). `updated_at`·세 새 표의 날짜는 better-auth 가 쓰는 ISO 문자열(`2026-09-24T01:37:58.085Z` 모양)이다 — 한 표 안에서 두 형식이 섞이는 것은 `users` 의 `created_at`(ms)·`updated_at`(ISO) 뿐이다
- `password` 열은 이메일·비밀번호 로그인을 켜지 않아 늘 NULL 이지만 better-auth 계정 스키마의 필드라 둔다
- `ON DELETE CASCADE` 는 D1 의 외래 키 강제 여부와 상관없이 뜻을 적어 두는 용도다. 계정 삭제 기능은 없다(개인정보 처리방침 5절)

### 2.4 요청에서 사용자를 찾는 규칙 (`getUser`)

순서(먼저 걸리는 것을 쓴다):

1. 경로가 `/v1/` 이면 `getTokenUser` — **지금 그대로**
2. **로컬 개발 우회**(2.6 조건)면 `DEV_AUTH_EMAIL` 로 사용자를 찾거나 만든다. 이 경로는 better-auth 를 거치지 않고 지금의 `findOrCreateUser` 한 문장 `INSERT … ON CONFLICT(email) DO NOTHING` + `SELECT` 를 쓴다. 넣을 때 `email_verified = 1`
3. 그 밖: better-auth 세션 조회 `getSession({ headers: request.headers, query: { disableRefresh: true } })`. 결과가 있으면 `{ id: user.id, email: user.email }`, 없거나 예외면 null
- **세션 연장은 `GET /api/me` 에서만 한다.** 그 핸들러만 `disableRefresh` 없이 부르고, 연장이 일어나 better-auth 가 돌려준 `Set-Cookie` 를 응답에 그대로 싣는다. 다른 경로는 읽기만 한다(D1 쓰기 0)
  - 이유: 연장 쿠키를 모든 `/api/*` 응답에 실으려면 `getUser` 가 응답 헤더를 들고 나가야 해서 시그니처가 바뀐다(1.1 의 9개 테스트). 앱은 `/api/me` 를 **부팅 때 1회·`online` 이벤트 때** 부른다(`App.tsx` `boot`·`online` 리스너). S-9 도 부른다(`CliLoginPage` `fetchAccount`). 하루에 한 번이라도 앱을 열면 30일이 다시 시작된다
  - 다른 선택은 9장 Q2
- `Cf-Access-Jwt-Assertion`·`CF_Authorization`·JWKS 캐시·`verifyAccessJwt`·`base64Url*` 는 **모두 지운다**(결정 5). `wrangler.jsonc` 의 `ACCESS_TEAM_DOMAIN`·`ACCESS_AUD` 도 지운다
- 세션 조회는 `users` 행을 **스키마에 선언된 필드만** 돌려준다(`factory.mjs` `transformSingleOutput` 은 스키마 필드만 돈다). F-2024 가 인증 때 함께 읽으려는 `write_day`·`write_count` 등은 `user.additionalFields`(`input: false`)로 선언해야 결과에 실린다 — 8장 F-2024 갱신

### 2.5 D1 행 비용 — 무엇이 쓰기를 만드나

| 동작 | 쓰기 | 읽기 | 언제 |
| --- | --- | --- | --- |
| 로그인 시작(`POST /api/login`) | 0 | 0 | 버튼 누를 때 |
| 가입(첫 로그인) | 11 | 3 | 사람마다 한 번 |
| 둘째 제공자 연결 | 8 | 4 | 사람마다 최대 한 번 |
| 다시 로그인 | 4 | 3 | 로그아웃했거나 30일 지났을 때 |
| 인증된 요청 하나(`/api/*`·`/ws` 업그레이드) | **0** | **2** | 요청마다 — 지금은 `INSERT … DO NOTHING`(0·0) + `SELECT`(읽기 1), 즉 **읽기가 요청당 1 → 2** |
| 세션 연장 | 1 | 4 | 세션마다 하루 최대 1회(`GET /api/me`) |
| 만료 세션 접근 | 1 | 4 | 만료 뒤 첫 요청 |
| 로그아웃 | 1 | 6 | 누를 때 |
| 매일 Cron 정리(3.7) | 지운 행 수 | 만료 행 수 | 하루 1회 |

- **요청마다 쓰기가 생기지 않는다.** `updateAge` 1일이면 활성 사용자 1,000명이 하루 약 1,000행(연장) — D1 무료 하루 쓰기 10만 행의 1%. `updateAge: 0` 이면 연장이 요청마다라 F-2024 의 하루 한도 계산(2.4)이 무너진다
- 읽기는 요청당 1행 늘어난다. F-2024 5.3 이 읽기 남용을 범위 밖으로 뒀으므로 이 개요도 줄이지 않는다(쿠키 캐시는 2.2 이유로 안 씀)
- F-2024 1.2 의 "곁가지 쓰기 — 새 사용자 `INSERT`(가입) 3행" 은 이제 11행이다(8장)

### 2.6 비밀·설정 값과 로컬 개발

운영 값(계약 — 이름을 바꾸면 `authServer.ts`·`wrangler.jsonc`·human-checks 가 어긋난다):

| 이름 | 종류 | 운영 값 | 설정 방법 |
| --- | --- | --- | --- |
| `BETTER_AUTH_URL` | `wrangler.jsonc` `vars` | `https://rawdoc.app` | 커밋 |
| `BETTER_AUTH_SECRET` | 비밀 | 32바이트 난수의 base64 (예: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`) | `npx wrangler secret put BETTER_AUTH_SECRET` (사람) |
| `GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` | 비밀 | Google Cloud OAuth 클라이언트(웹 애플리케이션) | `npx wrangler secret put …` (사람) |
| `GITHUB_CLIENT_ID` · `GITHUB_CLIENT_SECRET` | 비밀 | GitHub OAuth App(운영용) | `npx wrangler secret put …` (사람) |

- `wrangler.jsonc` 에 `"secrets": { "required": ["BETTER_AUTH_SECRET", "GOOGLE_CLIENT_ID", "GOOGLE_CLIENT_SECRET", "GITHUB_CLIENT_ID", "GITHUB_CLIENT_SECRET"] }` 를 둔다. 스키마 설명(`node_modules/wrangler/config-schema.json`)대로 이 키가 있으면 `npm run cf:types` 가 `.dev.vars` 를 뒤지지 않고 이 목록으로 `Env` 타입을 만든다 — 두 PC 의 `.dev.vars` 차이로 `worker-configuration.d.ts` 가 달라지지 않는다. 로컬 dev 에서 빠진 비밀은 경고만 한다고 적혀 있다(배포를 막는지는 확인하지 않았다)
- 클라이언트 id 도 비밀로 둔다 — GitHub OAuth App 은 콜백 주소를 **하나만** 받아서 운영·로컬 앱이 따로고, id 가 환경마다 다르다
- `wrangler secret put` 은 `.env` 의 `CLOUDFLARE_API_TOKEN` 으로 된다(CLAUDE.md "Deployment"). 그 토큰에 Workers Scripts 편집 권한이 있다(2026-09-18 재발급 기록) — 비밀 쓰기가 그 권한으로 되는지는 확인하지 않았다

로컬(`npm run dev:worker`, 8790) — `.dev.vars` 키(계약):

| 키 | 필수 | 값 |
| --- | --- | --- |
| `BETTER_AUTH_URL` | 예 | `http://localhost:8790` |
| `BETTER_AUTH_SECRET` | 예 | 32자 이상 아무 문자열 |
| `DEV_AUTH_EMAIL` | 아니오 | `dev@example.com` — 있으면 OAuth 없이 그 이메일로 로그인된 것으로 본다(지금처럼) |
| `GOOGLE_*` · `GITHUB_*` | 아니오 | 로컬에서 **실제** OAuth 를 시험할 때만. GitHub 은 로컬용 OAuth App 을 따로 만든다 |

- **로컬 인증 모드** = `BETTER_AUTH_URL` 이 `http:` 이고 호스트가 `localhost` 또는 `127.0.0.1`. 운영 값은 `https://rawdoc.app` 이라 이 분기에 들어가지 않는다
- **개발 우회** = 로컬 인증 모드 **그리고** `DEV_AUTH_EMAIL` 이 `@example.com` 으로 끝남. 지금 조건의 "`ACCESS_AUD` 가 비었음" 자리를 "로컬 인증 모드" 가 대신한다. 이 판정 함수 하나를 `auth.ts` 에서 내보내고 `docSocket.ts` 의 복사본(`isDevBypass`)을 지운다
- 로컬 출처 허용(4.2·`/ws`)은 **로컬 인증 모드**를 조건으로 한다 — `DEV_AUTH_EMAIL` 없이 실제 OAuth 를 로컬에서 시험할 때도 `/ws` 가 열려야 한다
- 에이전트 병렬 슬롯(8791~)은 실제 OAuth 콜백 주소가 없어 우회로만 쓴다

### 2.7 시작 시간·CPU — 확인 못 한 위험

- Workers 무료 플랜의 요청당 CPU 한도(10ms)에 대해: 인스턴스 **첫** 생성이 Node 에서 11.0ms 였다. isolate 의 첫 요청 하나가 한도에 닿을 수 있다. 그 뒤 `getSession` 은 0.5ms 안팎이다. **workerd 에서 재지 않았다**
- 묶은 모듈을 불러오는 데 Node 에서 60ms. 지금 Worker 와 비교하지 않았다
- 확인은 배포 뒤 Workers 대시보드의 CPU 시간·"exceeded CPU" 오류를 1주 본다(8장 human-checks). 넘치면 F-2033 이 인스턴스 생성을 `/api/auth/*`·로그인·세션이 필요한 경로에서만 하도록 좁힌다 — 지금도 `/pub/*`·정적 자산·`/v1/*` 는 만들지 않는다(2.2)

## 3. 로그인 흐름과 `/login` 페이지

### 3.1 주소

| 요청 | 누가 처리 | 응답 |
| --- | --- | --- |
| `GET /api/login?return={해시}` | Worker(지금 `handleLogin`) | 세션 있음 → `302 Location: {복귀 주소}`. 없음 → `302 Location: /login?return={같은 값}` |
| `GET /login?return={해시}&error={코드}` | Worker(새 `worker/loginPage.ts`, 스크립트 없는 완결 HTML) | 세션 있음 → `302 {복귀 주소}`. 없음 → 200 로그인 페이지(3.3) |
| `POST /api/login` (폼: `provider`, `return`) | Worker(새 핸들러) | `Origin` 검사(4.2) → `provider` 가 `google`·`github` 가 아니면 `303 /login?return=…&error=bad_request` → better-auth `signInSocial` 을 서버에서 불러 `303 Location: {제공자 인증 주소}` + `oauth_state` `Set-Cookie` |
| `GET /api/auth/callback/google` · `/github` | better-auth `handler` | 성공 `302 {복귀 주소}` + 세션 쿠키. 실패 `302 /login?return=…&error={코드}` |
| `POST /api/auth/sign-out` | better-auth `handler` | 200 `{"success":true}` + 쿠키 지움, 세션 행 삭제 |
| `/api/auth/` 아래 그 밖의 모든 경로 | Worker | **404** `{"error":"not_found"}` — better-auth 에 넘기지 않는다 |
| `GET /api/me` | Worker | 지금 그대로 `200 {id,email}` / `401`. 세션 연장 `Set-Cookie` 를 실을 수 있다(2.4) |

- **`/api/auth/*` 는 허용 목록만 넘긴다.** better-auth 는 기본으로 `update-user`·`list-sessions`·`revoke-sessions`·`link-social`·`unlink-account`·`get-session`·`sign-in/social` 등을 연다. 쓰지 않는 경로는 공격면이다. 필요한 것은 콜백 둘과 로그아웃뿐이다
- **로그인 시작을 `/api/auth/sign-in/social` 로 직접 보내지 않는 이유**: `/login` 은 스크립트가 없어 HTML 폼만 쓸 수 있는데, 그 경로는 JSON 만 받는다(측정: 폼 인코딩 → 415). 그래서 폼은 우리 `POST /api/login` 으로 오고, Worker 가 `signInSocial` 을 서버에서 부른다(측정: `url` + 상태 쿠키를 돌려준다)
- **GET 링크가 아니라 POST 폼인 이유**: 링크면 미리 가져오기·크롤러가 제공자 인증을 시작하게 되고, `Origin` 검사(4.2)를 한 규칙으로 둘 수 없다. 버튼이 폼 제출이라 스크립트도 필요 없다
- `/login` 은 `wrangler.jsonc` `assets.run_worker_first` 에 넣고, 서비스 워커 `navigateFallbackDenylist` 에 `/^\/login$/` 을 넣는다 — 안 넣으면 설치된 PWA 가 `/login` 이동을 `index.html` 로 가로챈다(지금 `/guides`·`/privacy` 를 막는 것과 같은 이유)
- `/login` 응답 헤더: `Cache-Control: private, no-store`, `<meta name="robots" content="noindex">`. `sitemap.xml` 에 넣지 않는다. `robots.txt` 는 고치지 않는다

### 3.2 복귀 주소 규칙 (`return`)

- `return` 은 `#/` 로 시작하고 **512자 이하**일 때만 쓴다. 아니면 빈 값으로 본다(열린 리다이렉트 방지는 지금 `handleLogin` 규칙 그대로)
- 512자인 이유: `return` 이 암호화된 `oauth_state` 쿠키에 **두 번**(성공 주소·실패 주소) 들어간다. 1,024자면 쿠키가 4,804바이트로 브라우저 쿠키 한도 4,096바이트를 넘어 버려지고, 콜백이 `state_mismatch` 로 실패한다(측정). 512자는 2,756바이트. 지금 가장 긴 앱 해시는 CLI v2 로그인 해시로 약 107자다(F-2023)
- 복귀 주소: `return` 이 있으면 `/` + `return`(예 `/#/d/abc` — 지금 `handleLogin` 과 같다. `/` 가 랜딩을 줘도 랜딩의 조기 판정 스크립트가 `#/` 해시를 보고 앱으로 넘긴다, F-271 4.2). 빈 값이면 `/?app=1`(첫 방문 랜딩을 건너뛰는 탈출구, `rootRoute.ts`)
- 실패 주소: `/login?return={encodeURIComponent(return)}`. better-auth 가 뒤에 `&error=…` 를 붙인다(측정)
- 세 곳(`GET /api/login`·`GET /login`·`POST /api/login`)이 같은 순수 함수 하나로 판정한다 — 단위 테스트 대상

### 3.3 `/login` 페이지 — 내용과 문구

- 틀: 사이트 머리·꼬리(`renderSiteHeader({ appCta: 'link' })`·`renderSiteFooter`), `SITE_CHROME_CSS`, 페이지 전용 `<style>` 을 한 파일에 담는다(랜딩 `welcomePage.ts` 와 같은 방식 — Worker 는 해시가 붙은 앱 CSS 이름을 모른다). **`<script` 가 하나도 없다**(F-272 규칙, F-276 A12 와 같은 판정)
- 색은 `brand.config.ts` 값과 `color-mix()` 로만(불변조건). **예외는 제공자 로고 두 개뿐**이다 — 3.3.1
- 버튼은 로고(20px, 글자 왼쪽) + 글자. 로고는 장식이라 `aria-hidden="true"`, 버튼의 접근 이름은 글자(`Google로 계속`)다

#### 3.3.1 제공자 로고 (9장 Q4 — 공식 로고를 넣는다, 2026-09-24 사용자)

| 로고 | 모양 | 원래 색 | 출처(사람이 받아 올 곳) |

- SVG 는 **받은 그대로**(경로·색·비율을 고치지 않는다). 파일 머리 주석에 받은 URL·받은 날짜를 적는다
- **라이선스·사용 조건: 확인 못 함.** 이 개요 작성 환경에 웹을 여는 도구가 없어 위 두 페이지를 읽지 못했다. 사람이 로고를 받을 때 확인할 것(8장 human-checks): ① 로그인 버튼에 쓰는 것이 허용되는지 ② Google 은 버튼 모양(배경색·테두리·글꼴·로고 크기·여백)을 정해 둔 것으로 알려져 있다 — 그 규칙과 3.3 버튼 모양이 맞는지 ③ 로고 옆 문구로 `Google로 계속`·`GitHub로 계속` 이 허용되는지. 규칙과 어긋나면 F-2033 이 버튼 모양만 규칙에 맞춘다(문구·폼 동작은 그대로)
- **다크 테마**: `/login` 은 다른 사이트 페이지처럼 `data-theme` 을 쓰는 스크립트가 없어 **늘 밝은 화면**이다(F-272 "다크 모드 사용자도 밝은 화면", H4). 그래서 검정 GitHub 마크와 Google 색 G 를 밝은 버튼 바탕에 그대로 둔다. 어두운 판(흰 GitHub 마크)은 넣지 않는다 — 사이트 페이지가 다크 모드를 갖게 되면 그때 GitHub 이 주는 흰 판을 같은 파일에 더한다
- 불변조건 예외 문장은 8장 `CLAUDE.md` 행에 초안이 있다(메인이 반영)

| 자리 | 문구 |

| `<title>` | `로그인 · {제품명}` |
| h1 | `로그인` |
| 안내(h1 아래) | `Google 또는 GitHub 계정으로 로그인하면 문서가 서버에 저장되고 다른 기기에서 이어서 쓸 수 있습니다.` |
| 버튼 1 (`<button type="submit" name="provider" value="google">`) | `Google로 계속` |

| 동의 안내 | `계속하면 이용약관과 개인정보 처리방침에 동의하는 것으로 봅니다.` — `이용약관` 은 `/terms`, `개인정보 처리방침` 은 `/privacy` 링크 |

- 첫 포커스는 따로 옮기지 않는다(스크립트 없음). 탭 순서: 머리 링크 → 오류 줄(초점 없음) → `Google로 계속` → `GitHub로 계속` → 약관 링크 → 꼬리 링크
- 오프라인이면 이 페이지는 열리지 않는다(서비스 워커가 가로채지 않으므로 브라우저 오류 화면). 로그인은 제공자와 통신해야 하므로 오프라인 대체 화면을 두지 않는다

### 3.4 오류 코드 → 문구

`error` 값을 화면에 그대로 찍지 않는다. 아래 표에 없는 값은 모두 마지막 줄이다

| `error` | 문구 |
| --- | --- |
| `email_not_verified`, `account_not_linked`, `email_not_found` | `이메일 주소가 인증되지 않은 계정이라 로그인하지 못했습니다. Google 또는 GitHub 계정 설정에서 이메일을 인증한 뒤 다시 시도해 주세요.` |
| `access_denied` (제공자 화면에서 취소) | `로그인을 취소했습니다.` |
| `state_mismatch`, `state_not_found`, `state_invalid`, `state_security_mismatch` | `로그인 시간이 지났거나 다른 창에서 시작한 로그인입니다. 다시 시도해 주세요.` |
| 그 밖(`invalid_code`, `unable_to_get_user_info`, `bad_request`, `internal_server_error` 등) | `로그인하지 못했습니다. 잠시 뒤 다시 시도해 주세요.` |

- `account_not_linked` 를 "인증 안 됨" 과 같게 보는 이유: 2.3 의 `UPDATE` 로 모든 기존 행이 `email_verified = 1` 이고 새 행은 `validateUserInfo` 가 인증된 것만 만든다. 그래서 이 코드가 나는 경우는 "제공자가 이 이메일을 인증 안 됨이라 함" 하나다(연결 조건, `link-account.mjs`)
- GitHub 은 **공개 프로필 이메일, 없으면 기본(primary) 이메일**을 쓰고 그 주소의 `verified` 를 본다(`github.mjs` `getUserInfo`). GitHub 의 보조 이메일로는 들어올 수 없다 — F-2035 가 도움말·약관 문장에서 다룬다
- F-2024 의 가입 마감(`signup_closed`)도 같은 경로로 이 페이지에 온다 — 문구는 F-2024 L6 을 여기에 더한다(8장)

### 3.5 흐름 한 번 — 계정 메뉴에서 로그인

1. 계정 메뉴 `로그인` → 저장 대기 입력 저장 → `location.href = /api/login?return=%23%2Fd%2Fabc` (지금 그대로)
2. Worker: 세션 없음 → `302 /login?return=%23%2Fd%2Fabc`
3. `/login` → `Google로 계속` → 폼 `POST /api/login` → `303 https://accounts.google.com/o/oauth2/v2/auth?…` + `oauth_state` 쿠키
4. Google 에서 로그인·동의 → `GET /api/auth/callback/google?code&state` → better-auth: 상태 쿠키 확인 → 토큰 교환 → `validateUserInfo` → 사용자 찾기·만들기·연결 → 세션 행 → `302 /#/d/abc` + `__Secure-better-auth.session_token`(30일)
5. 앱 부팅 → `/api/me` 200 → `in` → 서버 저장소

S-9(터미널 로그인)의 `로그인` 링크도 같은 `/api/login?return=` 이라 4번 뒤 S-9 화면으로 돌아와 `승인` 을 누를 수 있다(F-2023 흐름 그대로, `POST /api/tokens` 는 4.2 검사를 통과한다 — 같은 출처 `fetch` 는 `Origin` 을 싣는다)

### 3.6 로그아웃

- 계정 메뉴 `로그아웃` → 저장 대기 입력 저장 → `fetch('/api/auth/sign-out', { method: 'POST', credentials: 'same-origin' })`
  - 200: `md.account` 를 지우고 `location.replace('/?app=1')`. 서버 문서 해시(`#/d/{id}`)에 그대로 머물면 로컬 저장소에 없는 문서라 "찾을 수 없음" 알림이 뜨므로 해시를 버린다
  - 네트워크 오류·그 밖의 상태: 이동하지 않고 N-1 error `로그아웃하지 못했습니다. 연결을 확인한 뒤 다시 시도해 주세요.`
- `logoutUrl()`(`/cdn-cgi/access/logout`)은 지운다. better-auth 는 세션 **행을 지운다**(측정 쓰기 1) — Access 로그아웃과 달리 서버에서 세션이 끝난다(결정 8 "세션 폐기")
- 이미 열린 실시간 연결은 끊지 않는다(F-304 4.3 "쿠키는 연결 시점에만 본다" 그대로). `location.replace` 로 페이지가 바뀌면서 연결도 닫힌다
- 옛 탭(새 버전 알림을 안 누른 탭)의 `로그아웃` 은 `/cdn-cgi/access/logout` 으로 간다. Access 앱을 지운 뒤 그 주소가 무엇을 주는지는 확인하지 않았다. 세션 쿠키는 남는다 — 새로 고치면 로그인 상태다

### 3.7 만료 행 정리

- 이미 있는 매일 Cron(`scheduled`, UTC 18시)에 더한다: `auth_sessions` 중 `expires_at` 이 지금보다 이른 행, `auth_verifications` 중 `expires_at` 이 이른 행을 지운다. ISO 문자열은 모두 같은 `…Z` 모양이라 문자열 비교가 시각 비교와 같다
- 이유: better-auth 는 만료 세션을 **그 세션으로 다시 요청이 올 때만** 지운다(`getSession`). 버려진 기기의 세션은 영원히 남는다

## 4. 보안

### 4.1 비밀 값이 없을 때

- better-auth 는 비밀이 없으면 `NODE_ENV === "production"` 일 때만 멈추고, 아니면 **알려진 기본 비밀로 서명하고 경고만** 한다(`isProduction` 판정, `@better-auth/core` `env-impl.mjs`). Workers 에서는 `NODE_ENV` 를 두지 않는다
- 그래서 `authServer.ts` 가 직접 막는다: `BETTER_AUTH_SECRET` 이 없거나 32자 미만이면 인스턴스를 만들지 않고, 인증이 필요한 요청은 500 `{"error":"internal"}` + `console.error`. 세션 없이 도는 경로(`/pub/*`·정적·`/v1/*`)는 영향 없다

### 4.2 CSRF — `Origin` 검사

| 경로 | 무엇이 막나 |
| --- | --- |
| `/api/auth/*` 의 `POST`(로그아웃) | better-auth 가 쿠키 있는 비-GET 요청의 `Origin`(없으면 `Referer`)을 `baseURL`·`trustedOrigins` 와 비교해 403 `INVALID_ORIGIN`(측정). `callbackURL`·`errorCallbackURL` 도 같은 기준으로 검사(측정) |
| 우리 `/api/*` 의 `GET`·`HEAD`·`OPTIONS` 가 아닌 요청 전부(`POST /api/login`·`/api/auth/*` 포함) | **새 규칙**: 라우트 표를 찾기 전에 `Origin` 을 본다. `new URL(SITE_URL).origin`(`src/lib/siteMeta.ts`)과 같으면 통과. 로컬 인증 모드면 `http://localhost:*`·`http://127.0.0.1:*`·요청 주소의 출처도 통과. **`Origin` 이 없거나 다르면 403 `{"error":"forbidden_origin"}`**, 핸들러·D1 에 닿지 않는다 |
| `/v1/*` | 검사하지 않는다. `Authorization: Bearer` 만 보고 쿠키를 읽지 않으므로(`getUser` 첫 분기) 다른 사이트가 사용자의 권한을 빌릴 수 없다 |
| `/ws/*` | 지금 그대로 `docSocket.ts` `isAllowedOrigin`(F-304 4.5). 로컬 조건만 2.6 대로 바뀐다 |
| `/pub/*` | `GET` 만 있다 |

- 세션 쿠키는 `SameSite=Lax`(측정)라 다른 사이트의 `fetch`·폼 `POST` 에는 실리지 않는다. 이것이 1차 방어이고 `Origin` 검사는 2차다. 둘 다 두는 이유: 앞으로 쿠키 속성이 바뀌거나 같은 사이트(하위 도메인)에서 오는 요청을 막으려면 `Origin` 이 있어야 한다
- 브라우저는 `GET`·`HEAD` 가 아닌 요청에 `Origin` 을 싣는다(Fetch 표준). 참조 정책이 `no-referrer` 면 `"null"` 이 될 수 있는데, 앱은 참조 정책을 두지 않는다(`index.html` 에 `referrer` 없음 — 확인). 잠금 해제의 `keepalive` `DELETE`(`useDocLock` `unlockDoc`)도 같은 출처 `fetch` 라 `Origin` 이 실린다
- 판정 함수는 `docSocket.ts` 의 `isAllowedOrigin` 을 새 파일 `worker/origin.ts` 로 옮겨 둘이 함께 쓴다
- e2e 는 가짜 서버(`page.route`)라 Worker 의 이 검사를 거치지 않는다. 판정은 단위 테스트다

### 4.3 이메일 인증과 계정 연결

- 거부는 better-auth 두 곳에서 일어난다: 새 사용자·다시 로그인은 `validateUserInfo`(쓰기 0 으로 거부, 측정), 기존 이메일에 새 제공자를 연결할 때는 연결 조건(`account_not_linked`, 쓰기 0, 측정)
- 연결은 **이메일이 소문자로 같을 때만** 일어난다(better-auth 가 저장·비교 모두 소문자). 지금 `users.email` 도 소문자다(F-205 2.1)
- Google 은 `id_token` 의 `email_verified`, GitHub 은 `/user/emails` 의 `verified` 를 쓴다. Google `id_token` 은 토큰 교환 응답에서 바로 디코드하고 서명을 다시 검증하지 않는다(`google.mjs` `getUserInfo` `decodeJwt`) — 클라이언트 비밀로 Google 에 TLS 로 직접 받은 값이라 받아들인다

### 4.4 저장하지 않는 것 (개인정보 줄이기)

| 값 | 기본 동작 | 이 설계 |

## 9. 열린 질문 / 사람 결정 필요

### Q1. Access 앱을 언제 지우나 — **결정됨(2026-09-24 사용자): 배포 직전** (추천안)

결정 5 는 처음에 "배포 뒤 삭제" 였고 이 결정으로 "배포 직전" 이 됐다. 이유: Access 는 `rawdoc.app/api` 경로 전체를 막는다(product.md 7장 M2). 새 코드가 나간 뒤에도 앱이 살아 있으면 `/api/login`·`/api/auth/callback/*`·`/api/me` 가 **Access 를 먼저 거친다** — Access 쿠키가 없는 사람은 로그인 버튼을 누르면 Access 일회용 코드 화면을 보게 되고, Access 쿠키가 있는 사람만 새 로그인을 끝낼 수 있다

| 순서 | 사이 동안 일어나는 일 | 판단 |
| --- | --- | --- |
| **배포 직전 삭제 (채택)** | 삭제~배포 몇 분 동안 옛 Worker 가 돈다. 옛 `getUser` 는 JWT 를 **직접** 검증하므로(F-205 2.2) 이미 로그인한 사람은 그대로 쓰고, 새로 로그인하는 사람만 그 몇 분 동안 못 한다. 옛 코드가 새 사용자 행을 만들 길도 없다(새 JWT 를 받을 곳이 없다) — 2.3 의 `email_verified = 1` 뒤에 `0` 인 행이 끼어들지 않는다 | 권장 |
| 배포 뒤 삭제 (처음 결정 5 문장) | 배포~삭제 사이 새 로그인이 Access 화면에 걸린다. 운영자 본인은 Access 쿠키가 있어 끝까지 갈 수 있다 | 채택하지 않음 |

### Q2. 세션 연장을 어디서 하나 — **기본값: `GET /api/me` 에서만** (2.4)

다른 쪽(인증된 모든 `/api/*` 요청에서 연장): `getUser` 가 연장 `Set-Cookie` 를 들고 나가야 해서 `worker/index.ts` 가 응답에 붙이는 길(요청별 보관소)이 생기고, 1.1 의 9개 테스트가 흉내 내는 함수 모양은 지키되 `index.ts` 에 공통 후처리가 는다. 얻는 것: 앱을 새로 고치지 않고 30일 넘게 열어 둔 탭도 로그인이 유지된다. D1 쓰기는 둘 다 세션당 하루 1행으로 같다

### Q3. 스키마 검사를 운영에서 끄나 — **기본값: 끈다(`validateSchema: false`)** (2.2)

켜면 isolate 가 뜰 때마다 D1 에 스키마 조회(`sqlite_master` + 표마다 `PRAGMA`)가 가고, 어긋나면 **모든 인증 요청이 실패한다**(옵션 설명). 끄면 어긋남은 CI 의 스키마 테스트가 잡는다. 켜는 쪽을 고르면: 원격 마이그레이션을 빠뜨리고 배포한 경우 로그인이 곧바로 실패해 빨리 드러난다. 대신 cold start 마다 읽기 행이 늘고 한 번 더 기다린다(행 수는 재지 않았다)

### Q4. `/login` 버튼에 제공자 로고를 넣나 — **결정됨(2026-09-24 사용자): 공식 로고를 넣는다** (추천안 "넣지 않는다" 와 반대)

추천안이 넣지 않으려던 이유는 Google 로고가 색이 박힌 SVG 라 "색 hex 는 `tokens.css`·`brand.config.ts` 에만" 불변조건과 부딪친다는 것이었다. 사용자가 넣기로 해서 이 개요가 정한 것:

- 불변조건 예외 한 줄 — 8장 `CLAUDE.md` Invariants 행(문장 초안)
- 로고 파일 위치 `worker/providerLogos.ts` 한 곳, 인라인 SVG, 받은 그대로 — 3.3.1
- 출처 URL 두 개. **라이선스·사용 조건과 Google 버튼 모양 규칙은 확인 못 함** — 구현 전 사람 확인(6장 사람 할 일 0번, human-checks ⑭)
- 다크 테마 처리 없음(`/login` 은 늘 밝은 화면) — 3.3.1

### Q5. 세션 토큰 평문 저장을 받아들이나 — **기본값: 받아들인다** (4.4)

better-auth 는 `auth_sessions.token` 을 평문으로 둔다. 바꾸려면 better-auth 의 세션 조회를 우회하는 사용자 정의 계층이 필요해 "라이브러리 최대한 활용"(결정 8)과 멀어진다. D1 접근은 Cloudflare 계정과 `.env` 토큰으로만 된다

### Q6. 가입 상한의 원자성 — **F-2024 로 넘김** (8장)

F-2024 4.1 은 "한 문장 조건부 `INSERT` 로 21번째가 절대 안 들어간다" 였다. better-auth 가 사용자를 만들면 그 문장을 쓸 수 없고, `validateUserInfo` 에서 세고 판단하므로 동시 가입 수만큼 넘칠 수 있다. 이 개요는 F-2024 결정 8 의 숫자(하루 20명)를 바꾸지 않는다 — F-2028 이 받아들일지 정한다. 막으려면 `databaseHooks.user.create.before` 에서 조건부 삽입을 흉내 내야 하는데, better-auth 가 사용자·계정·세션을 한 트랜잭션처럼 다루지 않아(D1 은 대화형 트랜잭션 불가 — `D1SqliteDriver.beginTransaction` 이 던진다) 반쯤 만들어진 계정이 남을 수 있다

### 기본값으로 정한 것 (승인 시 확정)

1. `getUser`·`requireUser` 시그니처 유지, 앱의 `loginUrl` 주소 유지 — 1.1
