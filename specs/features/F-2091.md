# F-2091 휴대폰 폭 하단 알약·서식 바를 가상 키보드 열림으로 판정

작성일: 2026-09-30
상태: 승인 (2026-09-30 — 열린 질문(10장)은 모두 기본값대로. 별도 검토 없이 "결정할 것 없으면 바로 구현" 상시 지시로 승인. 알약·서식 바 둘 다 키보드 기준은 사용자가 정함)
사용자(2026-09-30): "모바일 하단 네비바는 포커스를 기준으로 하는게 아니라 키보드가 열린지 아닌지로 판별해야할듯 / 한번 문서 수정하기 시작하면 네비바를 볼 방법이 뷰전환 뿐임"
**이 명세는 F-2084 Q5(키보드만 내려가도 서식 바는 남긴다)와 F-2086 12장 Q3(키보드만 내려가도 알약은 숨은 채)을 뒤집는다.** 두 질문 모두 "키보드 유무를 가를 믿을 만한 값이 없다" 를 이유로 들었다 — 이 명세 3장이 그 값을 정한다
구현 담당: `feature-implementer`. 파일이 겹치는 진행 중 명세 없음

## 정해진 것 (2026-09-30 사용자, 바꾸지 않는다)

1. 하단 알약(F-2086 `.phone-nav`)은 가상 키보드가 열려 있으면 숨고, 닫혀 있으면 보인다 — 포커스가 편집기·입력칸에 남아 있어도 키보드가 닫혔으면 보인다
2. 서식 바(F-2084 `.editor-toolbar-row--docked`)도 같은 키보드 기준 — 키보드가 열렸고 편집기 포커스일 때만 보인다. 키보드를 내리면 서식 바는 숨고 알약이 나온다. 한 자리에 둘이 겹치지 않는다
3. F-2086 5장의 다른 숨김 조건(사이드바·댓글 판·단축키 판 열림 — CSS, 모달 안 포커스 예외)은 그대로. 바뀌는 건 "텍스트 입력 중" 판정뿐

## 3. 요구사항

### 3.1 `src/app/softKeyboard.ts` — 순수 판정 (반드시 결론 1)

```ts
export const KEYBOARD_MIN_PX = 150

export type KeyboardSample = {
  width: number    // window.innerWidth
  height: number   // visualViewport.height
  scale: number    // visualViewport.scale
}
export type KeyboardTrack = {
  baselines: Readonly<Record<string, number>>  // 폭(반올림한 정수의 문자열) → 그 폭에서 본 가장 큰 height
  open: boolean
}
export const INITIAL_KEYBOARD_TRACK: KeyboardTrack   // { baselines: {}, open: false }

export function trackKeyboard(prev: KeyboardTrack, sample: KeyboardSample): KeyboardTrack

export type KeyboardState = 'open' | 'closed' | 'unknown'
export function keyboardState(track: KeyboardTrack, env: { coarse: boolean; supported: boolean }): KeyboardState

export function typingSurface(focused: boolean, keyboard: KeyboardState): boolean
```

`trackKeyboard` 규칙 (이 순서):
1. `|scale − 1| > 0.01`(핀치 확대 중 — `viewportFit.ts` 와 같은 문턱) 이거나 `height <= 0` 이거나 `width <= 0` → `prev` 를 **그대로(같은 객체)** 돌려준다. 확대 중에는 판정을 얼린다 — 확대하면 `visualViewport.height` 가 배율만큼 줄어 키보드로 오판한다
2. 키 = `String(Math.round(width))`. 기준값 = `max(prev.baselines[키] ?? 0, height)`
3. `open = 기준값 − height >= KEYBOARD_MIN_PX`
4. 기준값·`open` 이 둘 다 `prev` 와 같으면 `prev` 를, 아니면 새 객체를 돌려준다

- **기준값은 "이 폭에서 지금까지 본 가장 큰 보이는 높이"** 다. 키보드가 닫힌 높이가 곧 최대값이라, 앱이 뜬 뒤 한 번이라도 키보드 없이 잰 폭이면 맞다. 앱은 키보드 없이 뜬다(새로고침·새 탭에서 키보드는 닫혀 있다)
- 폭별로 따로 두는 이유: 화면 회전. 세로 390 에서 쌓은 기준값이 가로 844 로 돌렸다 오면 그대로 남는다. ≤600px 휴대폰의 가로 폭은 600 을 넘어 이 규칙이 쓰이지 않지만, 되돌아왔을 때 세로 기준값이 살아 있어야 한다
- 문턱 150px 이유: 세로 가상 키보드(추정 250~350)보다 충분히 작고, 주소창·탭 막대 접힘(추정 60 안팎)·추천 단어 줄(추정 40 안팎)보다 충분히 크다. 두 추정 모두 실기기로 재지 않았다 — H1·H2 가 확인하고, 어긋나면 이 상수 하나만 바꾼다(10장 Q1)
- 기준값은 줄지 않는다. 받아들이는 어긋남:
  - 안드로이드 분할 화면에서 위아래 나눔선을 끌어 높이만 150px 이상 줄이면, 그 폭의 기준값이 전체 높이로 남아 "열림" 으로 본다. 이때는 3.3·3.4 의 결합 때문에 **포커스가 없으면 아무 영향이 없고**, 포커스가 있으면 지금(F-2084·F-2086) 동작과 같아진다 — 새 동작이 옛 동작으로 물러날 뿐 둘 다 사라지거나 겹치지는 않는다
  - 키보드가 열린 채 처음 보는 폭으로 회전하면(가로로 앱을 연 뒤 세로로 돌림) 그 폭의 첫 기준값이 키보드 열린 높이라 "닫힘" 으로 본다. 키보드를 한 번 내리면 기준값이 올라가 그 뒤로 맞다
  - 떠 있는 키보드(Gboard floating)·블루투스 물리 키보드: `visualViewport.height` 가 거의 줄지 않아 "닫힘" — 알약이 보이고 서식 바는 숨는다(정해진 것 1·2 의 문자 그대로. 10장 Q5)

`keyboardState`: `!env.supported`(`window.visualViewport` 없음) 이거나 `!env.coarse` → `'unknown'`. 아니면 `track.open ? 'open' : 'closed'`

`typingSurface(focused, keyboard)` = `focused && keyboard !== 'closed'`
- `'unknown'`(마우스 창·`visualViewport` 없는 브라우저)은 포커스만 본다 — F-2084·F-2086 의 지금 규칙이 그대로 남는다
- 알약·서식 바 둘 다 이 함수 하나로 판정한다(3.3·3.4). 한 곳에서 판정해야 "알약과 서식 바가 동시에 보이거나 동시에 없어지는" 경우가 생기지 않는다(3.6)

### 3.2 `src/app/useSoftKeyboard.ts` — 모듈 저장소

```ts
export const COARSE_QUERY = '(pointer: coarse)'
export function useSoftKeyboard(): KeyboardState
```

- 모듈 안에 `KeyboardTrack` 하나(시작 `INITIAL_KEYBOARD_TRACK`). `useSyncExternalStore(subscribe, getSnapshot)` 로 읽는다 — 선례 `historyEntries.ts`
- `getSnapshot` 은 `keyboardState(track, { coarse: matchMedia(COARSE_QUERY).matches, supported: 'visualViewport' 있음 })`. 문자열이라 값이 같으면 같은 스냅숏이다. **처음 불릴 때 표본을 한 번 뜬다**(구독 전 첫 렌더도 맞는 값을 받게)
- 첫 구독자가 붙을 때 듣개를 단다, 마지막이 떨어지면 뗀다(참조 수). 모듈 `track` 은 떼도 남긴다(다시 붙으면 기준값을 이어 쓴다)
  - `visualViewport` `resize` → 표본(`{ width: innerWidth, height: vv.height, scale: vv.scale }`)을 떠 `trackKeyboard` 로 갱신, 스냅숏이 바뀌면 구독자에게 알린다. **`requestAnimationFrame` 으로 미루지 않는다** — 계산이 가볍고, 미루면 한 프레임 동안 알약과 서식 바의 판정이 어긋날 수 있다
  - `matchMedia(COARSE_QUERY)` `change` → 구독자에게 알린다(2-in-1 기기에서 포인터가 바뀜)
- `visualViewport` `scroll` 은 듣지 않는다 — 높이가 바뀌지 않는다
- 폭 조건(≤600px)은 이 저장소가 보지 않는다. 쓰는 쪽(`useToolbarDock` 의 `docked`, `PhoneNav` 의 `usePhoneWidth`)이 이미 폭으로 거른다
- 이 훅은 편집기에 아무것도 dispatch 하지 않는다

### 3.3 서식 바 — `useToolbarDock` (반드시 결론 2)

```ts
export function useToolbarDock(editorRef: RefObject<EditorHandle | null>): { docked: boolean; dockVisible: boolean }
```

- `dockVisible = typingSurface(편집기 포커스, useSoftKeyboard())`. "편집기 포커스" 판정(주 `contentDOM` 이거나 `.editor-toolbar-row` 안)과 `focusin`/`focusout` 시점 규칙은 F-2084 3.4 그대로
- **결합: 편집기 포커스 그리고 키보드 열림.** 키보드만 보면 분할 화면 높이 변화·(열린 채) 다른 입력칸 포커스에서 서식 바가 뜬다 — 서식 바는 주 편집기에 명령을 거는 도구라 편집기 포커스가 필요 조건이다(F-2084 3.4 표 그대로: 제목·표 칸·찾기 입력칸에서는 키보드가 열려도 없음)
- `useSoftKeyboard()` 는 `docked` 와 무관하게 늘 부른다(훅 순서)
- `AppTopBar` `showToolbar` 마지막 조건 `(!toolbarDocked || dockVisible)`. `keepEditorFocusOnToolbar` 는 그대로

### 3.4 하단 알약 — `PhoneNav` (반드시 결론 2)

- 숨김 = `typingSurface(focusHidesPhoneNav(focusInfoOf(activeElement)), useSoftKeyboard())`. `focusHidesPhoneNav`·`focusInfoOf`·`focusin`/`focusout` 시점은 그대로
- **결합: 텍스트 입력 포커스 그리고 키보드 열림.** 이유:
  - 포커스 없이 가상 키보드가 열리는 경우는 없다 — 결합해도 사용자 결정 1 의 결과는 같다
  - 결합하지 않으면 키보드가 아닌 높이 변화(안드로이드 분할 화면 나눔선, 3.1)에서 포커스 없이 알약이 사라진다. 결합하면 그 경우 알약은 보인다
  - 모달 안 입력(`inModal`)은 `focusHidesPhoneNav` 가 거짓이라 키보드가 열려도 숨지 않는다 — 정해진 것 3(모달이 알약을 덮고, 닫힐 때 포커스가 알약 버튼으로 돌아와야 한다)
- 훅은 모두 조건 없이 부른 뒤 `!phone || hidden` 이면 `null`(지금과 같은 자리)
- 숨는 방식은 그대로 — 그리지 않는다, 전환 없음

### 3.5 `navigator.virtualKeyboard` 를 쓰지 않는 이유

| 안 | iOS Safari | 안드로이드 Chrome | 비용 |
| --- | --- | --- | --- |
| **A. `visualViewport.height` 와 폭별 최대값 차이 (채택)** | 됨 — `visualViewport.height` 가 준다 | 됨 — meta 로 `innerHeight` 와 같이 주지만 최대값과 비교하므로 잡힌다 | 순수 함수 하나, 듣개 하나 |
| B. `innerHeight − visualViewport.height` | 됨 | **안 됨** — 둘이 같이 줄어 차이가 늘 0(근거 절) | — |
| C. `navigator.virtualKeyboard` `geometrychange` | **없음** | Chrome 94+ 에만. W3C 초안상 키보드 사각형은 `overlaysContent = true` 일 때만 채워지고, 그러면 키보드가 앱을 덮는 방식으로 바뀌어 F-2084 Q1-A(`resizes-content` 로 앱이 줄어듦)와 앱 틀 규칙을 다시 짜야 한다(초안 문구 기준, 기기로 확인 안 함) | TS 타입 0건 — 전역 선언을 직접 써야 함. 두 경로 |
| D. 포커스 순간의 높이와 비교 | 됨 | 됨 | 키보드가 열린 채 다른 입력칸으로 옮기면 그 순간 높이가 이미 줄어 있어 "닫힘" 으로 오판 |
| E. `screen.height`·`screen.availHeight` 와 비교 | 탭 막대·PWA 여부마다 차이가 달라 기준을 못 정한다 | 상태바·주소창·PWA 여부마다 다르다 | — |

## 10. 열린 질문 (모두 기본값 있음)

### Q1. 키보드 문턱 — **기본값: 150px 고정**
- 이유: 3.1. 주소창·추천 단어 줄 변화와 키보드 사이 가운데쯤. 상수 하나라 실기기에서 어긋나면 바꾸기 쉽다
- 다른 쪽(기준값 대비 비율, 예 `height < 0.8 × 기준값`): 키가 작은 휴대폰(보이는 높이 약 550)에서 110px, 큰 휴대폰(약 930)에서 186px 로 문턱이 달라진다. `KEYBOARD_MIN_PX` 가 `KEYBOARD_MIN_RATIO` 가 되고 U1 d~f 의 경계 값이 바뀐다

### Q2. 알약 숨김에 포커스를 결합하는가 — **기본값: 결합(텍스트 입력 포커스 그리고 키보드 열림)**
- 이유: 3.4. 포커스 없는 키보드는 없으니 사용자 결정의 결과는 같고, 분할 화면 높이 변화에서 알약이 사라지지 않는다
- 다른 쪽(키보드 열림만): `PhoneNav` 가 `focusHidesPhoneNav` 를 부르지 않게 되고 `useFocusHidesNav` 가 빠진다. 대신 모달 안 입력(팔레트)에서 알약이 숨어 **대화상자를 닫을 때 포커스를 돌려줄 알약 버튼이 없어진다**(F-2086 3.1 `inModal` 의 이유) — 모달 예외를 따로 남겨야 한다. E1 5번 기대가 "알약 0개" 로 바뀐다

### Q3. 마우스 창(≤600px, 고운 포인터) — **기본값: 포커스만(지금 그대로)**
- 이유: 가상 키보드가 없는 곳에서 "키보드 닫힘" 으로 보면 데스크톱 좁은 창에서 서식 바가 영영 안 뜬다
- 다른 쪽(포인터와 무관하게 키보드 판정): `keyboardState` 의 `coarse` 조건이 빠진다. 데스크톱 600px 창에서 편집 중에도 서식 바가 없고 알약이 보인다. E2 기대가 뒤집힌다

### Q4. F-2086 6장 자동 포커스 끄기 — **기본값: 유지 (5장)**
- 다른 쪽(푼다): `DocumentArea.tsx` 의 `&& !phone` 를 지우고 소유표에 든다. 휴대폰에서 문서를 열면 커서가 본문에 있고, iOS 는 키보드 없이(알약 보임·서식 바 없음), 안드로이드는 확인 안 된 채로 키보드가 올라올 수 있다. F-2086 E1 2번 "blur 없이 알약이 보인다" 는 iOS 형 에뮬레이션(키보드 없음)이라 여전히 통과한다. 사람 확인 H715 기대가 바뀐다

### Q5. 물리 키보드·떠 있는 키보드 — **기본값: "닫힘" 그대로 받아들임**
- 이유: 정해진 것 1·2 를 문자 그대로 따른 결과. 휴대폰에 물리 키보드를 붙여 쓰는 경우가 드물고, 이때도 알약은 쓸 수 있다
- 다른 쪽(편집기 포커스가 N 초 이상 이어지면 서식 바를 띄움 같은 보조 규칙): 새 추정 규칙이라 실기기 측정이 먼저 필요하다. 이 명세에서는 다루지 않는다
