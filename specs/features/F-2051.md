## 2. `/welcome` — 언제나 랜딩

### 2.1 주소와 응답

| 요청 | 조건 | 응답 |
| --- | --- | --- |
| `GET /welcome` | 항상(쿠키·질의 문자열 상관없음) | 랜딩 HTML `200`. `/welcome` 판(2.2) |
| `GET /` | 지금 그대로(F-271 2장) | 쿠키 있으면 앱, 없으면 랜딩 `/` 판 |
| `GET /welcome/`(끝 빗금) | — | **지금 그대로.** `run_worker_first` 의 `"/welcome"` 은 정확히 그 경로만 받으므로 정적 자산 → `404.html`. 이 명세가 다루지 않는다 |

### 2.2 경로별 차이 — 렌더 인자로 준다

같은 랜딩 HTML 을 두 경로가 쓴다. 경로별 차이는 **워커가 `renderWelcomePage` 에 인자로 넘기고, HTML 문자열 자체가 달라진다.** 인라인 스크립트가 `location.pathname` 을 읽어 가르는 방식은 쓰지 않는다(11장 Q6).

계약:

```ts
// worker/welcomePage.ts
export type LandingPath = '/' | '/welcome'
export function renderWelcomePage(options?: { path?: LandingPath }): Response   // 기본 '/'

// src/lib/siteChrome.ts
export const WELCOME_PATH = '/welcome'
```

- 인자를 안 주면 `'/'` 판이다. 기존 호출(`worker/index.ts` 의 `/` 분기, `e2e/helpers.js` `mockLanding`, `worker/loginPage.test.ts` U25, `worker/rootRoute.test.ts` A3, `e2e/landing.spec.js` F-2049 E2)은 고치지 않아도 지금과 같은 판을 받는다
- `/welcome` 문자열은 `WELCOME_PATH` 하나에서 읽는다. 사이드바·머리글·워커 분기가 같은 상수를 본다(F-276 의 `GUIDES_PATH` 와 같은 방식)

| 부분 | `'/'` 판 | `'/welcome'` 판 | 이유 |
| --- | --- | --- | --- |
| `<head>` 조기 판정 스크립트(`earlyScript`) | 있음(지금 그대로) | **없음.** 문자열에서 통째로 뺀다 | 2번 결정 — 기존 사용자 키가 있어도 앱으로 보내지 않는다. `md.landingReloaded` 가드도 이 판에서는 쓰일 일이 없다 |
| `[data-cta="enter"]` 클릭(히어로 `로그인 없이 사용`·하단 CTA·머리글 `앱 열기`) | 두 값 쓰기 → `location.reload()`(지금 그대로) | 두 값 쓰기 → **`/` 로 이동** | c9 — `/welcome` 을 다시 받으면 또 랜딩이다. `/` 로 가면 쿠키가 있으니 워커가 앱을 주고, 서비스 워커가 있으면 캐시된 `index.html` 이 뜬다 |
| `[data-cta="login"]` 클릭 | 두 값 쓰기 → `/api/login?return=` | 같음 | 로그인 뒤 돌아가는 곳이 `/` 라 경로와 무관하다 |
| `.cookie-escape` 문단 | 있음 | 있음(그대로 둔다) | 보이게 하는 `data-cookie-escape` 는 조기 판정 스크립트만 붙인다. `/welcome` 판에서는 보일 길이 없다. 뺄지 말지로 분기를 늘리지 않는다 |
| 머리글 | `renderSiteHeader({ …, appCta: 'enter', current: WELCOME_PATH })` | 같음 | 두 판 모두 "소개" 페이지다. 머리글의 `소개` 에 `aria-current="page"` 가 붙는다(3.2) |
| `<link rel="canonical">`·`og:url` | `https://rawdoc.app/` | **`https://rawdoc.app/`(같음)** | 2.4 |
| 본문·스토리·데모 번들 | 같음 | 같음 | 내용은 하나다 |

- `/` 로 이동은 새 기록을 남기는 이동이다(뒤로 가기로 `/welcome` 에 돌아올 수 있다). `location.replace` 를 쓰지 않는 이유: 사용자가 일부러 연 소개 페이지이므로 뒤로 가기 대상이 되는 것이 자연스럽다
- 쿠키가 막힌 브라우저에서 `/welcome` → `로그인 없이 사용` 을 누르면 `/` 가 랜딩(`/` 판)을 주고, 거기서 F-271 4.2 의 1회 가드·`?app=1` 탈출구가 그대로 동작한다. 새 처리 없음
- 로그인한 사용자가 `/welcome` 을 보면 `로그인 없이 사용`·`로그인` 문구가 그대로 보인다. 누르면 `/` → 앱(로그인 상태 유지)으로 간다. 문구를 바꾸려면 로그인 여부를 알아야 하는데 랜딩은 세션을 읽지 않는다(F-239·F-271) — 이번에 바꾸지 않는다

### 2.3 응답 헤더 — `worker/rootRoute.ts`

```ts
// 삭제
welcomeRedirect(): Response
// 추가
withWelcomeHeaders(response: Response): Response
```

`withWelcomeHeaders` 가 붙이는 것:

- `Cache-Control: no-cache` — 응답이 쿠키와 무관하므로 `/` 의 `private, no-store` 가 필요 없다. 다만 배포마다 HTML 이 바뀌므로 매번 확인하게 한다(`public/_headers` 의 `/`·`/index.html` 과 같은 값)
- `Vary` 는 붙이지 않는다. `X-Robots-Tag` 도 붙이지 않는다(2.4)

`worker/index.ts` 폴백 분기의 `/welcome` 줄은 `withWelcomeHeaders(renderWelcomePage({ path: WELCOME_PATH }))` 를 돌려준다. 분기 순서(`/p/` → `/login` → `/welcome` → `/` → 폴백)는 그대로다.

### 2.4 검색엔진

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| canonical·`og:url` | 두 판 모두 `https://rawdoc.app/` | 같은 내용이다. 대표 주소는 크롤러가 쿠키 없이 받는 `/` 하나로 둔다(F-271 4.1) |
| `X-Robots-Tag`·`<meta name="robots">` | 붙이지 않는다 | `noindex` 와 다른 주소를 가리키는 canonical 을 함께 쓰면 신호가 엇갈린다. canonical 하나로 중복을 알린다 — 11장 Q7 |
| `sitemap.xml` | 넣지 않는다 | `site/build.ts` 는 `'/'` 와 `content/` 글 주소만 넣는다(`renderSitemap(['/', ...urls])`). `/welcome` 은 자동으로 빠진다. 코드 변경 없음 |
| `robots.txt` | 고치지 않는다(`Disallow` 안 함) | 막으면 크롤러가 canonical 을 읽지 못한다 |
| `llms.txt` | 고치지 않는다 | 랜딩은 거기 없다 |

- 머리글(3장)이 모든 사이트 페이지에서 `/welcome` 으로 링크한다. 내부 링크가 canonical 이 아닌 주소를 가리키는 것은 약한 엇갈림이다. 그래도 `/` 로 링크하면 기존 사용자에게 앱이 뜨므로(이 명세가 푸는 문제) 받아들인다

### 2.5 서비스 워커

**고칠 것 없음.** c4 — `/welcome` 은 이미 `navigateFallbackDenylist` 에 있어 설치된 서비스 워커도 가로채지 않고, `run_worker_first` 에도 있다. `vite.config.ts` 는 주석만 고친다(1장).

- 오프라인: 서비스 워커가 가로채지 않으므로 브라우저 기본 오프라인 화면이 뜬다. 랜딩 번들도 precache 에 없다(c5). 앱 안 링크(4장)를 오프라인이라고 숨기거나 막지 않는다 — `사용법` 링크(F-276)와 같은 처리다

## 3. 공개 사이트 머리글 — `소개`

### 3.1 모양

```html
<header class="site-head">
  <a class="site-brand" href="/welcome">…{제품명}</a>
  <nav class="site-nav">
    <a class="site-nav-intro" href="/welcome">소개</a>
    <a href="/guides">사용법</a><a href="/changelog">체인지로그</a><a href="/help">도움말</a>
  </nav>
  <a class="site-app" href="/">앱 열기</a>
</header>
```

- `소개` 는 **`SITE_NAV` 배열에 넣지 않고** `renderSiteHeader` 가 `<nav>` 맨 앞에 직접 그린다. c8 — 넣으면 빌드 검사가 throw 하고 글 페이지 왼쪽 문서 목록에 섞인다
- 클래스 `site-nav-intro` 는 계약이다(3.3 규칙과 e2e 가 쓴다)
- 로고 `.site-brand` 의 주소를 `/` 에서 `WELCOME_PATH` 로 바꾼다 — 11장 Q2(기본값). 사이트의 "첫 화면" 은 랜딩이고, `/` 는 기존 사용자에게 앱이다. 앱으로 가는 길은 `앱 열기` 가 따로 있다
- `앱 열기` 는 그대로 `/`. 랜딩(`appCta:'enter'`)에서는 2.2 의 `enter` 동작을 탄다
- 머리글의 링크는 전부 같은 탭이다(지금 `SITE_NAV` 와 같다)
- 404 본문의 `앱 열기`(`/`), 공개 보기 화면(S-5)의 `PublicBrand`(`/`, `{제품명} 열기`)는 앱으로 가는 링크라 **바꾸지 않는다**

### 3.2 `current`

`renderSiteHeader` 의 `current` 가 `WELCOME_PATH` 이면 `소개` 링크에 `aria-current="page"` 를 붙인다. 랜딩 두 판이 `current: WELCOME_PATH` 를 넘긴다(2.2). 로고에는 붙이지 않는다.

### 3.3 좁은 창

c11 — `소개` 하나로 390·360px 에서 머리글이 가로로 넘친다. **폭 600px 이하에서 `.site-nav-intro` 를 숨긴다**(`display: none`). 그 폭에서는 로고가 같은 주소로 간다.

- 600 은 `specs/ia.md` 가 쓰는 휴대폰 폭 경계(≤600px, F-216)와 맞춘 값이다. 잰 값으로는 430px 도 넘치지 않지만, 사이트 글 페이지는 앱 CSS 의 서체를 쓰고 c11 은 시스템 글꼴로 쟀으므로 여유를 둔다
- 숨김은 CSS 규칙 한 줄이다. 마크업은 폭과 무관하게 같다(크롤러·스크린 리더에게는 링크가 있다 — `display:none` 은 접근성 트리에서도 빠지므로 좁은 창 스크린 리더 사용자는 로고로 간다)
- 이 규칙은 `SITE_CHROME_CSS` 에 둔다. 폭 값은 계약이 아니다(시각값 — 사람 확인 H3). 다만 **390px 에서 가로 넘침이 없어야 한다**는 것은 F-2049 E3 이 자동으로 지킨다

### 3.4 쓰는 곳

`renderSiteHeader` 를 부르는 네 곳(c7) 모두 바뀐다: 랜딩(두 판), 로그인 페이지(`/login`), 404, 사이트 글 페이지 전부. 부르는 쪽 코드는 랜딩의 `current` 말고는 고치지 않는다.

## 4. 앱 안 — 사이드바 `소개`

### 4.1 자리와 개수

**사이드바 아래 묶음에 한 줄, 한 곳만.** 순서는 `앱 설치`(조건부) → `도움말` → `사용법` → **`소개`** → `설정`.

- 로그인 여부·저장소 종류와 무관하게 **항상 보인다.** 로그인 안 한 사용자가 닿는 곳이어야 한다(요구) — 사이드바는 로그인 상태와 무관하게 늘 있고, 좁은 창에서는 서랍으로 열린다
- `사용법` 뒤에 둔다 — 둘 다 창을 떠나는 링크다. F-276 4.1 의 "떠나는 항목을 뒤에" 규칙을 따른다
- 계정 메뉴에는 두지 않는다 — 계정 전용 메뉴이고(c6), 로그인 안 한 사용자에게는 `로그인` 하나뿐이라 찾기 어렵다
- 명령 팔레트에는 두지 않는다 — 지금 팔레트에 사이트로 나가는 명령이 하나도 없다(c6). 하나만 넣으면 `도움말`·`사용법` 과 어긋난다 — 11장 Q5
- 도움말 화면(`#/help`)에도 두지 않는다 — 도움말 원본(`helpDoc.ts`)은 공개 `/help` 와 같은 원본이라(F-274) 사이트 페이지에 "소개로 가기" 가 한 번 더 생긴다

### 4.2 링크 동작

`사용법`(F-276 4.2·4.3)과 똑같이 **`SidebarButton`·`RailButton` 의 `href` 통로**를 쓴다. 새 컴포넌트를 만들지 않는다.

- `href={WELCOME_PATH}` — 새 탭(`target="_blank" rel="noopener noreferrer"`), 컴포넌트가 붙인다
- 펼친 사이드바: 아이콘 + `소개` + 바깥 링크 표시(`.sidebar-btn-ext`). 접힌 레일: 아이콘만, `aria-label`·툴팁 `소개`
- 새 탭인 이유: 편집 중인 앱을 떠나지 않게 한다. 랜딩의 `앱 열기`·`로그인 없이 사용` 은 새 탭에서 `/` → 앱으로 간다(두 번째 탭). F-296 탭 편집권이 있어 같은 문서를 두 탭에서 열어도 한쪽만 편집한다 — 새 문제 아님
- 오프라인: 따로 막지 않는다(2.5). 새 탭에 브라우저 오프라인 화면이 뜬다
- 설치한 PWA 창: 새 탭 링크가 어디서 열리는지(브라우저 창 또는 앱 창)는 브라우저가 정한다. 확인하지 않았다 — 사람 확인 H2

### 4.3 아이콘

`src/app/icons.tsx` 에 `IconIntro` 를 더한다. 원본은 `@material-symbols/svg-400/outlined/web.svg`(설치본에 있음을 확인). 이름은 계약이 아니고 아이콘 모양은 사람 확인(H4) — `info` 는 바로 위 `도움말`(`help`, 원 안 물음표)과 모양이 비슷해 기본값에서 뺐다. 다른 아이콘으로 바꾸는 것은 tweak 로 한다.

## 11. 열린 질문 (모두 기본값이 있다)

### Q1 링크 문구 — 기본값 `소개`

- 이유: 사이드바 아래 묶음(`도움말`·`사용법`·`설정`)과 사이트 머리글(`사용법`·`체인지로그`·`도움말`)이 모두 두세 글자 한 낱말이다. 제품명이 이미 로고로 옆에 있다
- 다른 쪽 `{제품명} 소개`(사용자가 말한 "Rawdoc 소개" 류)를 고르면: 사이드바와 머리글 문구가 `brand.name` 을 읽어 만든 문자열이 된다(제품명 불변조건). 머리글은 c11 기준 폭이 더 늘어 3.3 의 숨김 경계를 다시 재야 한다. 5장 문구 표·A5·A11~A13 의 기대 문자열이 바뀐다

### Q2 로고 주소 — 기본값 `/welcome` 으로 바꾼다

- 이유: 지금 로고가 `/` 라 기존 사용자에게는 사이트 로고를 누르면 앱이 뜬다. 사이트의 첫 화면은 랜딩이고 앱은 `앱 열기` 가 맡는다. 좁은 창에서 `소개` 를 숨길 수 있는 것도 로고가 같은 곳으로 가기 때문이다(3.3)
- 다른 쪽(로고 `/` 유지)을 고르면: 3.3 의 좁은 창 숨김을 쓸 수 없다(숨기면 휴대폰에서 소개로 갈 길이 없다). 대신 600px 이하에서 `.site-nav` 를 가로 스크롤(`overflow-x: auto`)로 두거나 nav 간격을 줄여야 하고, 그 값은 다시 재야 한다(c11 기준 390px 에서 8px, 360px 에서 38px 넘침). A5·A13 의 로고 기대값이 빠진다

### Q3 좁은 창에서 `소개` 숨김 경계 — 기본값 600px

- 이유는 3.3. 다른 값(예: 480px)을 고르면 481~600px 사이에서도 `소개` 가 보인다. c11 로는 430px 도 넘치지 않지만 사이트 글 페이지 서체로는 재지 않았다

### Q4 이미 301 을 캐시한 브라우저 — 기본값 대응하지 않는다

- 이유: 영향받는 것은 2026-09-20 뒤 운영 `/welcome` 을 연 브라우저뿐이다. `/welcome` 이 랜딩 주소였던 기간은 명세 날짜로 F-239(2026-09-17)부터 F-271(2026-09-20)까지다(배포 날짜는 확인하지 않았다). 사이트 데이터를 지우면 풀린다
- 다른 쪽을 고르면: 앱·머리글 링크를 `/welcome` 이 아닌 주소(예: 질의 문자열을 붙인 `/welcome?from=app`)로 걸어 캐시 키를 피한다. 크롤러가 보는 내부 링크에 질의 문자열이 붙고, 링크 주소가 `WELCOME_PATH` 와 달라져 A5·A11~A13 기대값이 바뀐다. 질의 문자열로 캐시를 피하는지는 재지 않았다

### Q5 명령 팔레트 명령 — 기본값 넣지 않는다

- 이유는 4.1. 넣으려면 `도움말`·`사용법` 도 같이 넣는 편이 맞고, 그것은 이 명세 범위 밖이다
- 넣으면: `src/app/paletteCommands.ts` 에 명령 한 줄(`window.open(WELCOME_PATH, '_blank', 'noopener')`)과 `paletteCommands.test.ts`·`paletteContract.test.ts` 기대 목록이 바뀐다. 1장 소유 표에 두 파일이 는다

### Q6 경로 차이를 어디서 주나 — 기본값 렌더 인자

- 이유: 단위 테스트(node, DOM 없음)로 "`/welcome` 판에 조기 판정이 없다" 를 문자열로 판정할 수 있다(A1). 스크립트가 없으니 `/welcome` 에서 깜빡임·되돌이 가능성 자체가 없다
- 다른 쪽(한 HTML + 스크립트 안 `location.pathname === '/welcome'` 분기)을 고르면: `renderWelcomePage` 시그니처가 그대로이고 `e2e/helpers.js` 는 `mockLanding` 하나로 두 경로를 물릴 수 있다. 대신 A1~A3 은 단위로 판정할 수 없어 e2e(A8·A9)만 남는다

### Q7 `/welcome` 색인 신호 — 기본값 canonical 만

- 이유는 2.4. 다른 쪽(`X-Robots-Tag: noindex` 추가)을 고르면 `withWelcomeHeaders` 가 그 헤더를 붙이고 A4 기대값이 바뀐다. canonical 과 `noindex` 가 함께 있으면 검색엔진이 어느 쪽을 따를지 정해져 있지 않다

### Q8 앱 링크 새 탭 — 기본값 새 탭

- 이유는 4.2(F-276 과 같다). 같은 탭을 고르면 `SidebarButton`·`RailButton` 의 `href` 통로를 쓸 수 없다(그 통로는 새 탭을 컴포넌트가 강제한다, F-276 4.3). 새 분기를 더해야 하고, 편집 중인 앱이 그 탭에서 사라진다

## 13. 확인하지 않은 것 (가정)

- 설치한 PWA 창에서 `target="_blank"` 같은 출처 링크가 브라우저 탭으로 열리는지 앱 창으로 열리는지(H2)
- c11 의 폭은 이 PC 시스템 글꼴 기준이다. 사이트 글 페이지(앱 CSS 서체)·다른 OS 에서는 재지 않았다. 3.3 의 600px 는 그 여유를 둔 값이다
- 검색엔진이 `/welcome` 의 canonical 을 `/` 로 받아들이는지(H6). 예전 301 로 모인 신호가 유지되는지도 확인하지 않았다
- Q4 대안(질의 문자열)이 캐시된 301 을 피하는지 재지 않았다. c10 은 같은 주소를 다시 여는 경우만 쟀다
- 운영에서 예전 `/welcome` 301 을 받은 브라우저가 실제로 몇이나 되는지 알 수 없다(분석 스크립트 없음, F-270 5장)
