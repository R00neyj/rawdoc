## 2. 데이터와 공통 함수 (계약)

### 2.1 마이그레이션

`migrations/0019_push_quota.sql`: F-3001 2.3 한 줄 그대로(`ALTER TABLE users ADD COLUMN push_quota_at INTEGER;`) + 머리 주석 한 줄. 색인 없음(`id` 로만 찾는다)

### 2.2 `worker/usage.ts`

```ts
// 각 항목 used / limit >= PUSH_QUOTA_RATIO 인 것만 남긴다. 하나도 없으면 null. D1 없음
export function quotaOver(candidates: PushQuota): PushQuota | null

// 되풀이 막기. 이번에 보낼 차례면 그 사용자 이메일, 아니면 null (문장 하나)
export function claimQuotaPush(db: D1Database, userId: string, now: number): Promise<string | null>

// claim → 이메일이 있으면 pushToEmail(db, auth, email, quotaPushPayload(quota), now). 보낸 기기 수
export function sendQuotaPush(db: D1Database, auth: VapidAuth, userId: string, quota: PushQuota, now: number, fetchImpl?: typeof fetch): Promise<number>

// Worker 요청용. quotaOver 가 null 이면 곧바로 끝(waitUntil·D1 0). 아니면 pushInBackground(env, ctx, 'quota', auth => sendQuotaPush(…))
export function quotaPushInBackground(env: Env, ctx: ExecutionContext | undefined, userId: string, candidates: PushQuota, now: number): Promise<void>
```

되풀이 막기 문장(계약):

```sql
UPDATE users SET push_quota_at = ?1
 WHERE id = ?2 AND (push_quota_at IS NULL OR push_quota_at < ?1 - ?3)
 RETURNING email
-- ?1 = now, ?3 = PUSH_QUOTA_REPEAT_MS
```

- F-3001 3.6 의 문장에 `RETURNING email` 만 더했다: "바뀐 행이 1" 판정과 받는 사람 이메일을 한 문장으로 얻는다. DO 에는 소유자 이메일이 없고(`ownerId` 만), 본문 `PUT` 은 남의 문서일 수 있다. `pushToEmail` 이 이메일을 받는다(F-3007)
- 경계: 정확히 7일(`now − push_quota_at = PUSH_QUOTA_REPEAT_MS`)이면 **아직 안 보낸다**(`<`, 개요 그대로)
- **순서는 claim 먼저, 구독 읽기 나중**(개요 그대로). 구독이 없는 사람도 7일 표지가 찍힌다 — 쓰기 1행/7일/사람. 그 7일 안에 푸시를 켜면 다음 경고는 7일 뒤
- 모든 D1(claim·구독·결과 batch)은 VAPID 가 있을 때 task 안에서만 돈다 → 비밀 값이 없으면 이 명세가 더하는 D1 은 0

## 3. Worker 쪽 — 알아채는 네 자리

받는 사람은 늘 **소유자**(F-3001 3.6). 판정 값은 **이번 요청이 바꾼 쪽만** 넣는다 — 이미지 요청은 `images` 만, 문서 요청은 `docBytes`·`docCount` 만. 이유: 다른 쪽 값은 질의를 더 해야 한다(개요 "값이 이미 손에 있는 곳만"). 모두 쓰기가 **성공한 뒤**에만 부른다(413·507·409 뒤에는 없음)

| 자리 | 넘기는 값 (`used`) |
| --- | --- |
| `storeAttachment`(평문 — `/api` 올리기와 `/v1/attachments` 둘 다 이 함수) 성공 뒤 | `images` = 읽은 합 + 이번 크기 |
| `handleUploadAttachment` 금고 분기 성공 뒤 | 같음 |
| `handleCreateDoc`(`/api`·`/v1` 둘 다) 성공 뒤 | `docBytes` = 요청 시작 사용량 `contentBytes` + `newBytes`, `docCount` = `docCount` + 1 |
| `handleUpdateDoc` 에서 `deltaBytes > 0` 이고 쓰기 성공 뒤(Q1) | `docBytes` = `ownerUsage.contentBytes` + `deltaBytes`, `docCount` = `ownerUsage.docCount`. `userId` = `existing.owner_id` |

- 인자: `storeAttachment` 끝에 `ctx?: ExecutionContext`, `handleCreateDoc`·`handleCreateDocV1`·`handleCreateAttachmentV1` 셋째 인자 `ctx?: ExecutionContext`. `/v1` 둘은 받은 `ctx` 를 그대로 넘긴다. 응답 모양·상태 코드는 바뀌지 않는다
- 요청 시작 사용량은 동시 요청이 있으면 조금 낡았다 — 받아들인다(계정 메뉴도 같은 값을 읽는다. 다음 쓰기가 다시 판정한다)
- 예산: 푸시가 더하는 하위 요청은 claim 1 + 구독 1 + 기기 ≤ 5 + 결과 batch ≤ 1 = **최대 8**, 90% 를 넘은 요청에서만(보내지 않는 6일 23시간 동안은 claim 1). CPU 는 F-3007 3.3 과 같은 모양 — 기기 5대 약 3.4 ms, 요청 자체는 재지 못했다(7장 ②)

## 4. DO 쪽 — 스냅숏 뒤

- 판정 값: 이번 flush 에서 **마지막으로 성공한 스냅숏 batch 의 사용량 행**(`judgeUsage` 가 받는 그 행). `docBytes` = `content_bytes`, `docCount` = `doc_count`. 행이 없으면 없음
- 자리: `flushOnce` 에서 스냅숏이 끝난 뒤, **`skipCheck` 가 아닐 때만**(= 알람이 부른 flush 는 건너뛴다). `quotaOver` → `pushKeys()`(null 이면 끝, D1 0) → `sendQuotaPush(db, auth, ownerId, …)`. 예외는 `console.warn` 한 줄로 삼키고 스냅숏 결과·재시도·연결 점검에 영향이 없다
- **알람을 뺀 이유 — F-3006 예산**: 알람 한 호출은 D1 최대 12 + 보내기 36 + 여유 2 = 50(F-3006 4.3). 여기에 이 경로의 최대 8 이 얹히면 58 로 넘는다. 알람 flush 에서 넘긴 판정은 다음 보통 flush(편집·마지막 연결 닫힘·RPC 쓰기)가 한다. 그래서 **F-3006 의 12 는 그대로다**
- **인스턴스당 한 번**: 이 인스턴스에서 `claimQuotaPush` 를 한 번 불렀으면(결과·예외와 상관없이) 다시 부르지 않는다. 이유: 90% 넘은 소유자가 편집하면 스냅숏마다(5~30초) claim 이 한 번씩 돈다 — 대부분 0행인 질의만 는다. 인스턴스가 쫓겨났다 다시 뜨면 다시 한 번. 보통 flush 호출이 더하는 하위 요청은 인스턴스 수명에 한 번, 최대 8
- **기다린다**(`await`): flush 는 겹쳐 돌지 않으므로 이 푸시가 끝날 때까지 다음 flush 가 기다린다 — 최악 `sendPush` 시간 초과 10초, 7일에 한 번. `waitUntil` 없이 떼어 보내면 인스턴스가 쫓겨날 때 claim 만 찍히고 푸시를 잃고 테스트가 결정적이지 않다
- 금고 문서는 방이 없다(`READ_ROW_SQL` `e2ee_key IS NULL`) — 금고 본문의 증가는 3장 `PUT` 이 맡는다

1. `npm run dev:worker`(`.dev.vars` 에 `VAPID_PRIVATE_JWK`), 푸시를 켠 기기에서 로컬 D1 로 `UPDATE users SET content_bytes = 95000000 WHERE email = …` 뒤 새 문서 → `저장 공간이 거의 찼습니다` / `문서 91MB / 100MB` 류, 누르면 앱 첫 화면. 한 번 더 만들면 오지 않음
