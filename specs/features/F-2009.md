# F-2009 노드 끌기 — 옮기고 놓으면 고정 해제·재가열

작성일: 2026-09-22
상태: **사람 승인 대기.** 사람이 꼭 골라야 하는 갈림길은 16장 Q1~Q7 이고 **전부 기본값이 서 있다.** F-292 를 뒤집는 곳은 없다 — 297행이 이미 "끌 수 있다 / 놓는 순간 고정이 풀린다 / F-2009 몫" 이라고 적어 둔 것을 글자대로 푼다. **F-2003·F-2004 의 기존 e2e 두 건이 깨지고**(14장), 그 둘을 고치면서 `specs/features/F-2004.md` 14.2 A3 의 문장도 함께 고쳐야 한다(15장).

> | **F-2009** | 노드 끌기 | 좌클릭 끌기로 노드를 옮기고 놓으면 고정 해제·재가열. 화면 평행 평면 좌표 풀기, 이동(pan)과 가르기, 터치 | F-2004 | **메인** |

**구현은 메인이 직접 한다** (F-292 9장 `누가` 열).

### 2.1 이 커밋이 끝난 시점의 상태

1. **노드에 마우스를 올려 왼쪽 버튼으로 끌면 그 노드가 커서를 따라온다.** 커서는 `grabbing`
2. **끄는 동안 이웃 노드가 따라온다.** 간선이 늘어나고 주변이 밀린다
3. **놓으면 고정이 풀려 힘이 다시 잡는다.** 제자리 쪽으로 돌아오거나 새 균형으로 굳는다
4. **끄는 동안 그 노드와 이웃의 이름표가 붙어 따라다닌다**(F-2004), **호버 강조도 유지된다**(F-2010)
5. 배경을 끌면 지금처럼 이동, 우클릭이면 회전. **노드 끌기 때문에 달라지는 것이 하나도 없다**
6. 터치는 노드 위 한 손가락 끌기가 노드 끌기, 두 손가락은 그대로 확대·이동, 움직이지 않고 누르고 있으면 그대로 메뉴
7. `장력` 슬라이더를 움직인 뒤 노드를 끌어 놓으면 **그 힘 값이 실제로 무엇을 하는지 손으로 보인다**

**쓸 만한가 — 판단.** 쓸 만하다. F-292 결정 1(재미·인상)에서 F-2003 이 "덩어리를 손으로 돌린다"를, F-2004 가 "덩어리에 정보가 있다"를 만들었고, 이 커밋이 **"덩어리를 손으로 흐트러뜨릴 수 있다"** 를 더한다. 옵시디언 그래프뷰와 조작이 같아지는 마지막 한 칸이다.

## 3. 화면 평행 평면 좌표 풀기

### 3.1 어느 평면인가 — 끌기 시작에 한 번 정하고 끝까지 안 바꾼다

> **카메라 시선에 수직이고, 끌기를 시작한 순간의 그 노드를 지나는 평면.**

- **깊이(`depth`)를 `pointerdown` 때 한 번 재서 끌기 내내 그대로 쓴다.** 그래야 평면이 고정되고, 노드가 커서를 따라오는 배율도 일정하다. 매 `pointermove` 마다 다시 재면 노드가 이미 그 평면 위에 있으므로 같은 값이 나오지만, 시뮬레이션이 그 노드를 못 움직이는 것은 `fx` 뿐이고 `forceCenter` 가 **모두를 평행이동**하므로(F-292 441행) 깊이가 프레임마다 조금씩 흔들린다. **한 번만 잰다**
- **끄는 동안 카메라는 움직이지 않는다.** 마우스는 `controls.enabled = false`(4.4), 터치는 `enableRotate = false`(5.2), 자동 맞춤은 7.2 가 끈다. 그래도 창 크기 변경(`ResizeObserver` → `aspect` 변경)은 끌기 중에도 올 수 있으므로 **기저와 `aspect` 는 `pointermove` 마다 다시 읽는다** — 비용이 0.0915 µs 다 (3.4)
- 깊이가 0 이하면(노드가 카메라 뒤) 식이 뒤집힌다. **`Math.max(depth, camera.near)` 로 바닥을 깐다.** 레이캐스트로 맞힌 노드는 언제나 앞에 있으므로 실제로는 안 걸리는 방어다

### 3.2 식 — `src/lib/mapCamera.ts` 에 순수 함수 둘을 더한다

테스트 환경이 `node` 다(`vite.config.ts` 227행 `environment: 'node'`). **three 도 DOM 도 import 하지 않아야 단위 테스트가 된다** — `mapCamera.ts`(F-2003 7.5)·`mapNodeStyle.ts`(F-2004 3장)와 같은 규칙이다. 그래서 `Raycaster`·`Plane` 을 쓰지 않고 식을 직접 쓴다.

```ts
// 지도 카메라 — 화면 평행 평면 좌표 풀기 (specs/features/F-2009.md 3장)

/** 3원소 좌표. three 를 안 쓰려고 튜플로 받는다 */
export type MapVec3 = readonly [number, number, number]

/** 카메라에서 점까지의 '보는 방향' 깊이. fwd 는 카메라가 보는 방향의 단위벡터다 */
export function viewDepth(point: MapVec3, camPos: MapVec3, fwd: MapVec3): number

/**
 * NDC(−1~1) 좌표를, 카메라 시선에 수직이고 카메라에서 depth 만큼 떨어진 평면 위의 world 좌표로 푼다.
 * out 에 써서 돌려준다 — 프레임마다 할당하지 않으려는 것이다 (F-2002 6.6)
 */
export function unprojectToViewPlane(
  ndcX: number,
  ndcY: number,
  depth: number,
  camPos: MapVec3,
  right: MapVec3,
  up: MapVec3,
  fwd: MapVec3,
  tanHalfVFov: number,
  aspect: number,
  out: [number, number, number],
): [number, number, number]
```

| 함수 | 정의 |
| --- | --- |
| `viewDepth` | `(point − camPos) · fwd` |
| `unprojectToViewPlane` | `sx = ndcX · aspect · tanHalfVFov · depth`; `sy = ndcY · tanHalfVFov · depth`; `out = camPos + fwd·depth + right·sx + up·sy` |

**왜 이 식인가** — three 의 원근 투영 행렬은 `m[0][0] = 1/(aspect·tan(fov/2))`, `m[1][1] = 1/tan(fov/2)` 이고 `w_clip = −z_cam` 이다. 그래서 `ndcX = x_cam / (aspect·tan(fov/2)·depth)` 이고, 이것을 `x_cam` 에 대해 푼 것이 위의 `sx` 다. **원근이라 깊이에 비례해 배율이 커지는 것이 `· depth` 한 항으로 전부 들어간다** — 가까운 노드는 커서를 조금만 따라오고 먼 노드는 많이 따라온다.

### 3.3 three 와 대 봤다 — 오차가 부동소수 한계다 (실측 (a))

카메라를 `position (37, −91, 210)`, `lookAt (5, 3, −2)`, `fov 50`, `aspect 1600/900` 으로 세우고:

| 확인 | 결과 |
| --- | --- |
| 임의의 점 2,000개를 `Vector3.project()` 로 NDC 로 만든 뒤 위 식으로 되돌리기 | **최대 오차 3.5×10⁻¹³** |
| 같은 카메라에서 `Raycaster.setFromCamera()` + `Ray.intersectPlane(Plane)` 결과와 비교 (NDC 500점) | **최대 차이 9.6×10⁻¹²** |
| `camera.getWorldDirection(v)` 와 `matrixWorld.extractBasis()` 의 −Z 기저 | **거리 0. 정확히 같다** |

**그래서 `Plane`·`Raycaster` 를 새로 가져오지 않는다.** 답이 같고, 순수 함수로 떼면 단위 테스트가 되며, `MapScene.tsx` 의 import 집합이 안 는다.

### 3.4 카메라 기저를 어떻게 읽나 — `matrixWorld.extractBasis()`

```ts
camera.updateMatrixWorld()
camera.matrixWorld.extractBasis(dragRight, dragUp, dragBack)   // Vector3 셋. 돌려쓴다
// fwd = −dragBack (카메라는 자기 −Z 를 본다)
```

- **`updateMatrixWorld()` 를 반드시 먼저 부른다.** `Object3D.updateMatrixWorld()`(`src/core/Object3D.js` 1176~1178행)는 `matrixAutoUpdate` 가 켜져 있으면 언제나 `updateMatrix()` 로 다시 합성한다. `controls.update()` 는 `camera.position`·`quaternion` 만 바꾸고 `matrixWorld` 를 즉시 갱신하지 않으므로, 이 줄이 없으면 **한 프레임 낡은 기저**를 쓴다
- **카메라는 `scene` 에 안 들어 있다**(`MapScene.tsx` 176행이 만들기만 한다). 그래서 `scene.updateMatrixWorld()` 가 건드리지 않는다 — 더더욱 우리가 불러야 한다
- `Matrix4.extractBasis`(`src/math/Matrix4.js` 239행)는 열 셋을 그대로 꺼낸다. 카메라 scale 이 1 이라 단위벡터다
- **비용: `updateMatrixWorld()` + `extractBasis()` 1회에 0.0915 µs** (실측 (e), 20만 회 평균). `pointermove` 가 프레임당 최대 1건(6.5)이므로 **16.7 ms 예산의 0.0005%** 다

### 3.5 화면 좌표 → NDC 는 `hitAt()` 이 이미 한다

`MapScene.tsx` 552~568행 `hitAt()` 의 앞 네 줄이 그것이다. **그 부분을 `toNdc(clientX, clientY): boolean` 한 함수로 떼어 `hitAt()` 과 끌기가 같이 쓴다.**

```ts
function toNdc(clientX: number, clientY: number): boolean {
  const rect = canvas.getBoundingClientRect()
  if (rect.width === 0 || rect.height === 0) return false
  ndc.set(((clientX - rect.left) / rect.width) * 2 - 1, -(((clientY - rect.top) / rect.height) * 2 - 1))
  return true
}
```

`hitAt()` 은 `if (nodeCount === 0) return null; if (!toNdc(x, y)) return null` 로 시작하게 바뀐다. **동작은 한 톨도 안 바뀐다.**

## 4. 마우스 — 이동(pan)과 가르기

### 4.1 이벤트 분기표 (F-2003 4.3 을 노드 끌기가 들어간 형태로 다시 그린다)

`pointerdown` 에서 **왼쪽 버튼이면 언제나 레이캐스트를 한 번 한다.** 비용은 노드 1,000 에서 0.05~0.17 ms 이고(F-2004 5.2 실측) 누를 때 한 번뿐이다.

| 이벤트 | 조건 | 무슨 일이 일어나나 | `OrbitControls` 는 |
| --- | --- | --- | --- |
| `pointerdown` | 버튼 0 · 레이캐스트 **적중** · 메뉴 닫힘 · **마우스** | 끌기 후보 기록(`pendingDrag`), **`controls.enabled = false`** | 자기 `onPointerDown` 이 1555행에서 즉시 빠져나간다 — `setPointerCapture`(1559행)도 안 한다 |
| `pointerdown` | 버튼 0 · 적중 · 메뉴 닫힘 · **터치** | 끌기 후보 기록 + **기존 길게 누르기 준비**(`enableRotate = false`) | `enabled` 는 그대로 `true` — 두 손가락 확대가 살아 있어야 한다 (5.2) |
| `pointerdown` | 버튼 0 · 적중 · **메뉴 열림** | 아무 것도 안 한다. 그 클릭은 메뉴를 닫기만 한다 (F-2003 4.5) | `enabled` 가 이미 `false` |
| `pointerdown` | 버튼 0 · **배경** | 지금 그대로 | 이동(pan) 시작 |
| `pointerdown` | 버튼 2 (우클릭) | 아무 것도 안 한다 | 회전 시작 |
| `pointermove` | 끌기 후보 + **문턱 초과** (마우스 `CLICK_SLOP` 4 px / 터치 `LONG_PRESS_SLOP` 10 px) | **끌기 시작**(`beginDrag`) → 그 자리로 `moveDrag` | 마우스는 이미 꺼져 있다 |
| `pointermove` | 끌고 있는 중 | `fixNode` + `reheat` + `requestDraw` (6장). **호버·이름표는 안 건드린다** | — |
| `pointermove` | 그 밖 | 지금 그대로 (길게 누르기 슬롭 판정 → 호버) | — |
| `pointerup` | 끌고 있었다 | **`endDrag()`** — `releaseNode` + `reheat` + 잠금 해제. 그 뒤 기존 클릭 판정은 `> CLICK_SLOP` 에서 걸려 **문서를 열지 않는다** | 마우스는 `enabled` 복구 |
| `pointerup` | 끌기 후보였지만 문턱을 못 넘었다 | 끌기가 시작된 적이 없다 → **평소대로 문서를 연다** | `enabled` 복구 |
| `pointercancel` | 끌고 있었다 | `endDrag()` | 같다 |
| `contextmenu` | 왼쪽 버튼이 눌려 있다 | 지금 그대로 — `(e.buttons & 1) !== 0` 이라 메뉴를 안 연다 (F-2003 4.3) | — |

### 4.2 문턱 — 기존 상수를 그대로 쓴다

| 입력 | 끌기가 시작되는 문턱 | 왜 |
| --- | --- | --- |
| 마우스 | `CLICK_SLOP` = **4 px** (`MapScene.tsx` 59행) | `onPointerUp` 이 같은 값으로 "클릭이냐"를 가른다(652행). 같은 상수를 쓰면 **클릭과 끌기가 정확히 상호배타**가 된다 — `≤ 4` 면 문서를 열고 `> 4` 면 끌기다. 사이에 아무 일도 안 일어나는 구간이나 둘 다 일어나는 구간이 없다 |
| 터치 | `LONG_PRESS_SLOP` = **10 px** (62행) | `onPointerMove` 가 이미 같은 값에서 길게 누르기를 취소한다(622행). **한 이벤트에서 "길게 누르기가 죽고 끌기가 산다"** 가 되어 두 제스처의 경계가 하나로 모인다. 손가락 떨림 때문에 4 px 로 두면 탭이 끌기가 된다 |

**새 상수를 만들지 않는다.** 16장 Q3 이 다른 쪽을 적어 둔다.

### 4.3 `fixNode` 는 문턱을 넘고 나서 시작한다

`pointerdown` 에서 바로 `fixNode` 하지 않는다. 그랬다가는 **노드를 그냥 클릭하기만 해도** 놓을 때 `releaseNode` + `reheat` 가 돌아 덩어리가 한 번 출렁인다. `Ctrl`+클릭(`여기로 이동`)처럼 지도를 닫지 않는 경로에서 그게 그대로 보인다.

- `pointerdown` 에서 하는 일은 **레이캐스트와 플래그 기록, `controls.enabled = false` 뿐**이다
- 문턱을 넘은 첫 `pointermove` 에서 비로소 `beginDrag()` 가 `fixNode` 를 시작한다

### 4.4 `OrbitControls` 를 어떻게 막나 — `pointerdown` 에서 `enabled = false`

**F-2003 4.4 가 메뉴에 쓴 방법과 같은 스위치를, 켜는 시점만 다르게 쓴다.**

- **왜 `pointerdown` 인가.** 문턱(4 px)을 넘을 때까지 미루면 그 사이에 `OrbitControls` 가 이미 `setPointerCapture`(1559행) + `state = PAN` 으로 들어가 **카메라가 4 px 만큼 밀린 채로 남는다.** `pointerdown` 에서 끄면 1555행에서 바로 빠져나가 캡처도 상태 전이도 없다 (F-2003 4.2 가 "`enabled = false` 에서는 `change` 0건·`start` 0건, 그동안에도 우리 리스너는 그대로 불린다"를 실측했다)
- **F-2003 이 우클릭에 대해 이 방법을 물리친 이유는 여기 해당하지 않는다.** 거기서는 노드 위 우클릭 드래그가 "회전도 메뉴도 아닌 죽은 제스처"가 되는 것이 문제였다. 여기서는 **죽는 제스처가 없다** — 노드 위에서 시작한 좌클릭 끌기는 노드 끌기가 되고, 4 px 안에서 끝나면 클릭이 된다
- **대가: 노드가 덮은 픽셀에서는 이동(pan)을 시작할 수 없다.** 사용자 결정 2 가 그렇게 정했다. 첫 실행처럼 노드 하나가 화면 높이의 78.8% 를 덮는 경우(F-2003 7.2)에는 화면 대부분에서 이동을 시작할 수 없는데, **그 상태에서 사용자가 하고 싶은 것은 이동이 아니라 그 노드를 끄는 것**이다. 조금만 비켜서 누르면 이동이 된다
- **되돌리는 곳은 하나다.** 메뉴와 섞이지 않게 로컬 플래그 하나를 둔다.

```ts
let menuOpen = false          // bundle.setMenuOpen() 이 쓴다
let dragLock = false          // 우리가 controls.enabled 를 껐나

function lockControls() { dragLock = true; controls.enabled = false }
function unlockControls() { if (!dragLock) return; dragLock = false; controls.enabled = !menuOpen }
```

`setMenuOpen(open)` 은 `menuOpen = open; controls.enabled = !open && !dragLock` 이 된다. **메뉴와 끌기가 동시에 성립하는 경우는 없지만**(메뉴가 떠 있으면 끌기 후보를 안 만든다) 두 스위치가 한 변수를 나눠 쓰므로 이렇게 모은다.

### 4.5 캔버스 밖으로 끌고 나가도 따라오게 — 우리가 캡처한다

`controls.enabled = false` 라 `OrbitControls` 가 캡처를 안 하므로, **`beginDrag()` 에서 `canvas.setPointerCapture(pointerId)` 를 우리가 부른다.**

- **실측 (d)**: 캡처를 잡은 캔버스에서 바깥(캔버스 밖 좌표)으로 끌었을 때 `pointermove` 가 정상으로 들어왔고, `pointerup` 뒤 `lostpointercapture` 가 한 번 왔다. 캡처 없이 끌면 캔버스를 벗어나는 순간 이벤트가 끊긴다
- 캡처는 `pointerup`·`pointercancel` 에서 브라우저가 스스로 놓는다. 따로 `releasePointerCapture` 를 부르지 않는다
- **터치에서는 우리가 캡처하지 않는다.** `controls.enabled` 가 `true` 라 `OrbitControls` 가 이미 같은 캔버스에 캡처를 잡아 두었고(1559행), 캡처 대상이 같은 요소라 우리 리스너에 그대로 들어온다
- `pointerleave` 는 캡처 중에 눌려 있다가 놓을 때 밀려 온다 — F-2010 8.1 이 이미 확인하고 받아들인 동작이다. 끌기가 끝난 뒤 커서가 캔버스 밖이면 이름표가 거둬진다. 맞는 동작이다

## 5. 터치

### 5.1 F-2003 이 비워 둔 자리에 그대로 들어간다

> **노드 위에서 시작한 한 손가락 드래그는 그 제스처 동안 회전하지 않는다. (…) F-2004 가 그 제스처를 노드 끌기로 가져갈 자리이기도 하다** — F-2003 5.2 (그 몫이 F-2004 2.2 에서 F-2009 로 옮겨 왔다)

지금 그 제스처는 **아무 일도 안 한다.** 손가락을 노드에 대고 움직이면 회전도 안 되고 메뉴도 안 뜬다. 그 죽은 제스처가 노드 끌기가 된다.

### 5.2 순서

```
pointerdown (터치, 첫 손가락, 노드 적중, 메뉴 닫힘):
  controls.enableRotate = false          // 기존 (F-2003 5.2)
  longPress = { … , timer: 500 ms }      // 기존
  pendingDrag = { id, touch: true, index }   // 신규

pointermove (같은 pointerId, 이동 > 10 px):
  beginDrag()                            // 신규. longPress 보다 먼저 판정한다
  endLongPress()                         // 기존. 아래 한 줄이 바뀐다

endLongPress():
  타이머를 지우고 longPress = null
  controls.enableRotate = drag === null  // ← 끌고 있으면 잠근 채로 둔다 (기존은 무조건 true)

pointerup / pointercancel:
  endDrag()                              // 신규. endLongPress 보다 먼저
  activeTouches -= 1, endLongPress()     // 기존 — 여기서 enableRotate 가 true 로 돌아온다

두 번째 손가락이 닿으면 (activeTouches > 1):
  endDrag()                              // 신규 — 끌던 노드를 놓은 것으로 친다
  endLongPress()                         // 기존
```

- **`controls.enabled` 는 터치에서 안 끈다.** F-2003 5.1 이 실측한 대로 `enableRotate = false` 만으로 한 손가락 회전이 완전히 막히고(`onTouchStart` 1806~1812행), **두 손가락 `DOLLY_PAN` 가지는 `enableRotate` 를 보지 않아**(1838~1848행) 확대·이동이 그대로 산다. `enabled` 를 끄면 두 번째 손가락의 `pointerdown` 까지 1555행에서 잘려 확대가 죽는다
- **두 번째 손가락이 끌기를 끝낸다.** 한 손가락 끌기 도중에 손가락을 더 얹으면 노드를 놓고 확대·이동으로 넘어간다. 끌면서 동시에 확대하는 제스처는 두지 않는다 — `OrbitControls` 가 그 프레임에 카메라를 움직이면 3.1 이 고정한 평면이 틀어져 노드가 튄다
- **길게 누르기 메뉴는 그대로다.** 10 px 안에서 500 ms 를 버티면 메뉴, 10 px 를 넘기면 끌기. 한쪽이 서면 다른 쪽은 안 선다
- **터치에는 호버가 없으므로 끄는 동안 이름표가 안 뜬다** (F-2004 17장 Q3 그대로). 8.2

### 5.3 안 바뀌는 것

배경 위 한 손가락 회전, 두 손가락 확대·이동, `touchend` 의 `preventDefault` 처방(F-2003 5.3), 짧은 탭으로 문서 열기 — **한 줄도 안 바뀐다.**

## 6. 시뮬레이션

### 6.1 `MapLayout` 은 이미 다 갖고 있다 — 코드로 확인했다

| 부르는 것 | `mapLayout3d.ts` | 계약 (F-2001 5.4) |
| --- | --- | --- |
| `fixNode(i, x, y, z)` | 292~299행 | `fx/fy/fz` 대입. 다음 tick 부터 좌표가 그 값으로 못 박히고 속도가 0 |
| `releaseNode(i)` | 301~308행 | `fx/fy/fz` 를 `null` 로. **재가열은 하지 않는다 — 호출자가 이어 부른다** |
| `reheat(alpha)` | 282~285행 | `simulation.alpha(alpha)`. `restart()` 를 안 부른다 |
| `nodes` | 235행 | 시뮬레이션이 들고 있는 노드 배열. 좌표를 복사 없이 읽는다 |
| `setAlphaTarget(t)` | 287~290행 | **쓰지 않는다** (6.3) |

**이미 단위 테스트도 있다** — `src/lib/mapLayout3d.test.ts` 203~220행(`fixNode` 로 못박고 `releaseNode` + `reheat` 로 다시 움직인다), 305~315행(고정 좌표로 경계구 계산). **F-2009 는 그 파일을 안 건드린다.**

### 6.2 끄는 동안 — 입력마다 `reheat(MAP_REHEAT_ALPHA)`

```
moveDrag(e):
  기저·깊이로 world 좌표를 푼다 (3장)
  layout.fixNode(dragIndex, x, y, z)
  layout.reheat(MAP_REHEAT_ALPHA)        // 0.6. MapScene.tsx 66행에 이미 있는 상수
  requestDraw()
```

- **안 돌리면 재미가 죽는다.** 배치가 멈춘 상태에서 `fx` 만 바꾸면 `alpha` 가 `alphaMin` 아래라 이웃에 걸리는 힘이 사실상 0 이다. 끌던 노드만 혼자 움직이고 간선이 고무줄처럼 늘어나기만 한다
- **`posDirty` 를 직접 세우지 않는다.** `reheat` 가 `isSettled()` 를 false 로 만들면 `frame()` 493~498행이 `layout.tick(1)` 을 돌면서 스스로 세운다. 그리고 d3 의 tick 은 힘 단계를 지난 뒤 `node.fx != null` 이면 `node.x = node.fx` 로 덮으므로(`d3-force-3d/src/simulation.js`), **tick 이 한 번이라도 돌아야 `fx` 가 화면에 반영된다.** 즉 재가열이 곧 반영 경로다 — **F-2003 6.3 이 "F-2009 에게" 남긴 쪽지의 답이 이것이다.** 별도의 `posDirty = true` 한 줄은 필요 없다
- **끌다가 손을 멈추면** `pointermove` 가 안 와서 `alpha` 가 잦아들고 278 tick 뒤 루프가 멈춘다. 다시 움직이면 `reheat` + `requestDraw` 가 되살린다. **맞는 동작이다** — 그릴 것이 없는 동안 배터리를 안 태운다

### 6.3 `setAlphaTarget` 을 쓰지 않는다 — F-2006 5.3 과 같은 경로

d3 의 관용적 끌기 패턴은 `alphaTarget(0.3).restart()` 로 끄는 내내 미지근하게 돌리고 놓을 때 `alphaTarget(0)` 이다. **`MapLayout.setAlphaTarget` 도 있다. 그래도 안 쓴다. F-2006 5.3 이 슬라이더에 대해 내린 결론이 끌기에도 글자 그대로 적용된다.**

- **놓는 신호를 놓치면 영영 안 멈춘다.** `alphaTarget` 이 남으면 `isSettled()` 가 영원히 false 이고 `frame()` 518~521행이 rAF 루프를 못 멈춘다. 끌기는 `pointerup`·`pointercancel`·두 번째 손가락·`dispose` 네 갈래로 끝나는데, 그중 하나라도 새면 노트북 배터리를 계속 태운다
- **입력마다 `reheat(0.6)` 이면 수치적으로 같으면서 그 위험이 없다.** `pointermove` 가 프레임당 최대 1건이므로(6.5) 매 프레임 `alpha` 가 0.6 으로 다시 세워진다 — `alphaTarget(0.6)` 과 같다. 입력이 끊기면 그냥 278 tick 뒤에 멈춘다
- **F-2006 과 같은 상수·같은 함수를 쓴다.** `MAP_REHEAT_ALPHA`(`MapScene.tsx` 66행, 값 0.6)를 그대로 부른다. **끌기 재가열과 슬라이더 재가열은 같은 경로다** — 새 상수도 새 분기도 만들지 않는다
- **`restart()` 는 부르지 않는다** (F-2001 3.3).

### 6.4 `alpha` 0.6 이 놓았을 때 어떤 그림을 주나 — 쟀다 (실측 (b)·(c))

`mapLayout3d.ts` 216~231행의 힘 구성을 그대로 복제해서, 배치를 정지시킨 뒤 0번 노드를 **60프레임에 걸쳐** 원래 반지름 밖으로 끌고(프레임마다 `alpha` 를 A 로 세우고 1 tick) 놓아서 멈출 때까지 돌렸다.

| 문서 수 | `alpha` | 놓은 자리(원래에서) | 멈춘 뒤 원래에서 | 이웃 최대 이동 | tick |
| --- | --- | --- | --- | --- | --- |
| 30 | 0.3 | 568.1 | **295.4** (52% 남음) | 214.2 | 248 |
| 30 | **0.6** | 568.1 | **262.7** (46% 남음) | 364.1 | 278 |
| 30 | 1.0 | 568.1 | **223.6** (39% 남음) | 516.1 | 300 |
| 1,000 | 0.3 | 2,135.7 | **929.9** (44%) | 1,189.3 | 248 |
| 1,000 | **0.6** | 2,135.7 | **632.2** (30%) | 1,896.7 | 278 |
| 1,000 | 1.0 | 2,135.7 | **519.6** (24%) | 2,490.1 | 300 |

**읽는 법 두 가지.**

1. **어느 값에서도 노드는 "원래 자리로 정확히 돌아오지" 않는다.** 힘 마당에 균형점이 여럿이라 놓은 자리 근처의 새 균형으로 굳는다. `alpha` 가 클수록 보폭이 커서 더 멀리(=원래 쪽으로) 간다. **이것이 맞는 동작이다** — 사용자 결정 1 이 원한 것은 "제자리로 스냅" 이 아니라 "힘이 다시 잡는다" 이고, 옵시디언도 그렇다
2. **`alpha` 를 키우면 돌아오는 대신 이웃이 더 밀린다.** 0.6 은 그 사이의 값이고, **F-2006 5.2 가 슬라이더에 대해 고른 값과 같다.** 두 경로가 같은 상수를 쓰는 것이 자연스럽다

**이웃이 실제로 따라오는가 — 두 문서 그래프에서 쟀다 (실측 (c)).** 정지 상태에서 0번을 60프레임 동안 world 600 만큼 끌었을 때 **이웃(1번)이 515.4 따라왔다**(15/30/45/60 프레임에 119.5 / 251.0 / 383.1 / 515.4 로 매끄럽게 늘었다). 이 중 상당 부분은 `forceCenter` 가 무게중심을 원점으로 되돌리는 몫이다(F-292 441행) — `forceCenter` 는 `strength` 가 1 로 고정이고 사용자가 못 만지므로, **이웃이 따라오는 것은 `장력` 슬라이더를 어떻게 두어도 성립한다.** 13.2 A6 이 이 성질을 자동 판정에 쓴다.

**노드 하나짜리 그래프**(첫 실행 상태)는 다르다. `forceCenter` 가 그 노드 하나를 무게중심으로 보므로 **놓은 다음 1 tick 만에 정확히 `[0, 0, 0]` 으로 돌아온다**(실측 (c): 끈 뒤 `[500,0,0]` → 놓고 1 tick `[0,0,0]`). 13.2 A2 가 그 확정성을 쓴다.

### 6.5 `pointermove` 는 프레임당 몇 건인가 — 쟀다 (실측 (d))

설치된 Chrome 에서 캡처를 잡은 캔버스에 끌기를 태웠다.

| 조건 | `pointermove` | rAF 프레임 |
| --- | --- | --- |
| 120걸음을 Playwright 최대 속도(약 7 ms 간격)로 | **120건** | 121 |
| 300걸음을 한꺼번에 밀어 넣고, 프레임마다 20 ms 를 태워 일부러 느리게 | **3건** | 20 |

**둘 다 "프레임당 1건 이하" 다.** Chrome 이 원시 마우스 이동을 vsync 에 맞춰 합치기 때문이고, 그래서 6.2 의 "입력마다 `reheat`" 가 프레임당 최대 한 번이다. F-2006 6.4 가 슬라이더 `input` 에 대해 잰 것과 같은 성질이다.

## 7. 카메라와 그리기 루프

### 7.1 끌기는 카메라를 건드리지 않는다

`controls.target`·`camera.position` 을 한 줄도 안 쓴다. `fit()`·`refit()`·`lookAtNode()` 도 안 부른다. **`selfDriven` 을 쓸 일이 없다.**

### 7.2 자동 맞춤은 꺼야 한다 — 안 그러면 끌기가 안 보인다

`frame()` 501행이 **`!userMoved && settling` 인 동안 프레임마다 `fit()`** 을 부른다. `fit()` 은 `layout.bounds()` 의 중심에 카메라 target 을 놓는다. 그래서 **자동 맞춤이 켜진 채로 노드를 끌면 카메라가 그 노드를 쫓아가 화면에서 아무것도 안 움직이는 것처럼 보인다.** 첫 실행(노드 하나)에서는 bounds 중심이 곧 그 노드라 **완전히 안 움직인다.**

> **끌기를 시작할 때 배치가 이미 멈춰 있었으면 `userMoved = true` 로 세운다.**

```
beginDrag():
  …
  if (layout.isSettled()) userMoved = true
```

- **선례가 있다.** `lookAtNode()`(430행)도 카메라를 사용자가 직접 움직인 것이 아닌데 `userMoved = true` 로 세운다 — 이 플래그의 뜻은 "사용자가 화면을 자기 뜻대로 정했으니 자동 맞춤을 그만둔다" 다 (F-2003 7.3)
- **`isSettled()` 로 거르는 이유**: 지도를 연 직후 배치가 퍼지는 3~5초 사이에 노드를 끌면, 자동 맞춤을 꺼 버리는 순간 자라나는 덩어리가 틀을 벗어난다. 그 구간에서는 자동 맞춤을 그대로 두고 카메라가 따라가게 둔다. 끌기 자체는 그대로 동작한다(노드는 다른 노드들에 대해 움직인다)
- **되살리는 길은 `맞춤` 하나다** — F-2003 7.3 과 같다
- **`followFit`(F-2006 6.3)은 안 켠다.** 끄는 동안 카메라가 거리를 다시 잡으면 노드가 커서에서 미끄러진다. 놓은 뒤에도 안 켠다 — 16장 Q5

### 7.3 `reduced-motion` — 끄는 동안에는 예외로 둔다

`frame()` 481행은 `reduced && !forceDriven` 이면 **배치가 끝날 때까지 한 프레임도 안 그린다**(485행 `return`). 그대로 두면 끌기가 F-2006 9장이 적은 슬라이더와 똑같이 된다 — **캔버스가 얼어붙고, 손을 뗀 뒤 278 tick 을 다 돈 다음에야 한 번 그린다.**

> **`beginDrag()` 에서 `forceDriven = true` 로 세운다.** 473행의 주석을 "장력 슬라이더가 일으킨" → **"사용자 조작(장력 슬라이더·노드 끌기)이 일으킨"** 으로 넓힌다.

- `frame()` 504~507행이 `!settling` 일 때 스스로 내리므로 따로 끄지 않는다. 끄는 동안에는 프레임마다 `reheat` 가 들어가 `settling` 이 유지되고, 놓은 뒤 278 tick 이 지나면 내려간다
- 근거는 F-2006 9장이 인용한 F-292 결정 13 그대로다 — **"회전은 사용자가 직접 일으키는 조작이라 그대로 둔다."** 노드 끌기는 그보다 더 직접적이다
- **새 플래그를 만들지 않는다.** 두 조작의 뜻이 같고(사용자가 일으킨 재계산), 내리는 조건도 같다

### 7.4 그 밖에 안 바뀌는 것

`dirty`·`posDirty`·`boundsStale`·`selfDriven`·`followFit`·정지 판정식(`layout.isSettled() && !dirty`)·`updateClip()` — **한 줄도 안 바꾼다.**

## 8. 이름표·호버·커서

### 8.1 이름표와 호버 강조는 **지금 코드가 그대로 해 준다** — 새 줄이 0개다

- `onPointerMove` 628행이 `if (e.buttons !== 0) return` 으로 **끄는 동안 호버를 갱신하지 않는다**(F-2004 7.6, F-2010 8.2 가 그 줄을 유지하기로 이미 정했다). 누르기 직전의 `hoverIndex` 가 곧 끌고 있는 노드이므로 **그 노드와 이웃의 이름표가 끄는 내내 떠 있고**, F-2010 의 호버 강조도 그 노드에 그대로 남는다
- `placeLabels()`(338~350행)가 프레임마다 `posBuf` 의 최신 좌표로 이름표를 다시 놓는다. **노드가 움직이면 이름표가 따라간다**
- `refreshLabels()`(313행)는 `hoverIndex` 가 안 바뀌므로 불릴 일이 없다. **끄는 동안 React 렌더가 0회다**
- `setHover()` 를 끌기 중에 부르지 않는다 — 부르면 이름표 집합이 바뀌어 깜빡인다 (2026-09-22 버그의 재발)

### 8.2 터치는 끄는 동안 이름표가 없다

`onPointerMove` 626행이 `e.pointerType === 'touch'` 에서 바로 빠져나간다. F-2004 17장 Q3 이 정한 "터치에는 호버가 없다" 그대로다. **이 명세가 뒤집지 않는다** — 손가락이 노드를 가리고 있어 그 아래 이름표를 띄워도 안 보인다. 사람 확인 H-e 가 묻는다.

### 8.3 커서 — 끄는 동안 `grabbing`

| 상태 | 커서 | 어디서 |
| --- | --- | --- |
| 노드 위 (안 끌고 있음) | `pointer` | 지금 그대로 (`setHover()` 576행) |
| 배경 | `''`(= `auto`) | 지금 그대로 |
| **끌고 있음** | **`grabbing`** | `beginDrag()` 가 `canvas.style.cursor = 'grabbing'` |
| 끌기가 끝난 직후 | `hoverIndex >= 0 ? 'pointer' : ''` | `endDrag()` 가 직접 쓴다 |

- **`endDrag()` 가 직접 써야 하는 이유**: `setHover()` 는 `next === hoverIndex` 면 즉시 `return` 한다(573행). 끌기 전후로 `hoverIndex` 가 안 바뀌므로 `setHover()` 를 불러도 커서가 안 돌아온다
- **F-2004 가 `controls.cursorStyle = 'grab'` 을 되돌린 결정과 부딪히지 않는다.** 그 결정은 **호버 커서**에 관한 것이었다 — "손 모양에는 팁이 없어 어느 노드를 가리키는지 안 보인다"(사용자 지시 2026-09-22). 끌고 있는 동안에는 무엇을 잡았는지가 이미 확정이라 팁이 필요 없다. `OrbitControls` 는 `_cursorStyle` 이 `'grab'` 일 때만 커서를 건드리는데(1584·1625행) 우리는 `'auto'` 로 두었으므로 부딪히지 않는다
- **CSS 로 하지 않는다.** 캔버스는 요소 하나라 선택자로 노드 위와 배경, 끄는 중과 아닌 중을 가를 수 없다 (F-2003 8.4)
- 16장 Q4 가 다른 쪽을 적어 둔다

## 9. `src/app/MapScene.tsx` 구조

행 번호는 **`9a44280`**(F-2006 구현 직후) 기준이다. **F-2010 이 같은 파일을 먼저 연다** — 구현할 때 다시 확인한다.

### 9.1 새로 생기는 값

```ts
// 217행 근처 (돌려쓰는 Vector3 들 옆)
const dragRight = new Vector3()
const dragUp = new Vector3()
const dragBack = new Vector3()
const dragFwd = new Vector3()
const dragOut: [number, number, number] = [0, 0, 0]

// 546행 근처 (downAt·menuWasOpen 옆)
let pendingDrag: { id: number; touch: boolean; index: number; x: number; y: number } | null = null
let drag: { id: number; touch: boolean; index: number } | null = null
let dragDepth = 0
// 누른 자리와 노드 중심의 차 — 노드가 커서로 튀지 않게 한다
const dragGrab: [number, number, number] = [0, 0, 0]
let menuOpen = false
let dragLock = false
```

**새 `useEffect` 가 0개, 새 prop 이 0개, 새 리스너가 0개다.** 기존 일곱 리스너(685~691행)에 얹기만 한다.

### 9.2 새 함수 넷

```
readBasis():                                  // 3.4
  camera.updateMatrixWorld()
  camera.matrixWorld.extractBasis(dragRight, dragUp, dragBack)
  dragFwd.copy(dragBack).negate()

beginDrag(pd, e):                             // 문턱을 넘은 첫 pointermove
  drag = { id: pd.id, touch: pd.touch, index: pd.index }
  pendingDrag = null
  const n = layout.nodes[pd.index]            // 복사 없이 읽는다 (F-2001 5.4)
  readBasis()
  dragDepth = Math.max(viewDepth([n.x, n.y, n.z], camPosTuple(), fwdTuple()), camera.near)
  // 누른 자리를 같은 평면으로 풀어 노드 중심과의 차를 기억한다
  if (toNdc(pd.x, pd.y)) {
    unprojectToViewPlane(ndc.x, ndc.y, dragDepth, …, dragOut)
    dragGrab[0] = n.x - dragOut[0]; dragGrab[1] = n.y - dragOut[1]; dragGrab[2] = n.z - dragOut[2]
  } else { dragGrab[0] = dragGrab[1] = dragGrab[2] = 0 }
  if (layout.isSettled()) userMoved = true    // 7.2
  forceDriven = true                          // 7.3
  if (!drag.touch) canvas.setPointerCapture(pd.id)   // 4.5. enabled 는 pointerdown 에서 이미 껐다
  canvas.style.cursor = 'grabbing'            // 8.3
  moveDrag(e)

moveDrag(e):
  if (!drag) return
  readBasis()
  if (!toNdc(e.clientX, e.clientY)) return
  unprojectToViewPlane(ndc.x, ndc.y, dragDepth, …, dragOut)
  layout.fixNode(drag.index, dragOut[0] + dragGrab[0], dragOut[1] + dragGrab[1], dragOut[2] + dragGrab[2])
  layout.reheat(MAP_REHEAT_ALPHA)             // 6.2
  requestDraw()

endDrag():
  if (!drag) return
  layout.releaseNode(drag.index)
  layout.reheat(MAP_REHEAT_ALPHA)             // F-2001 5.4 계약: releaseNode 는 스스로 재가열하지 않는다
  drag = null
  canvas.style.cursor = hoverIndex >= 0 ? 'pointer' : ''
  requestDraw()
```

- `camPosTuple()`·`fwdTuple()` 은 매번 배열을 만들지 않도록 **모듈 안에서 돌려쓰는 `[number,number,number]` 둘**에 `camera.position`·`dragFwd` 값을 채워 넣는 두 줄짜리 헬퍼다 (F-2002 6.6 의 규칙)
- `unlockControls()` 는 `endDrag()` 가 아니라 **`pointerup`·`pointercancel`** 에서 부른다 — 문턱을 못 넘고 끝난 클릭에서도 잠금을 풀어야 하기 때문이다

### 9.3 기존 함수에 손대는 곳 — 여섯 군데뿐이다

| 함수 | 행 | 무엇을 |
| --- | --- | --- |
| `hitAt` | 552~568 | 앞 네 줄을 `toNdc()` 로 뺀다 (3.5). **동작 변화 0** |
| `endLongPress` | 581~588 | 마지막 줄을 `controls.enableRotate = drag === null` 로 (5.2) |
| `onPointerDown` | 600~618 | 왼쪽 버튼이면 레이캐스트를 **한 번만** 하고 마우스·터치가 나눠 쓴다. 적중 + 메뉴 닫힘이면 `pendingDrag` 기록, 마우스면 `lockControls()`. **터치 길게 누르기 흐름은 그대로** (4.1) |
| `onPointerMove` | 620~630 | 맨 앞에 **끌기 시작 판정 → 끌기 이동** 두 블록. 그 뒤 기존 길게 누르기 슬롭·호버 판정 (4.1) |
| `onPointerUp` | 637~655 | 맨 앞에 `endDrag()` + `unlockControls()`. 그 아래 기존 클릭 판정은 안 고친다 — `> CLICK_SLOP` 이 알아서 거른다 |
| `onPointerCancel` | 657~662 | 맨 앞에 `endDrag()` + `unlockControls()` |

`setMenuOpen`(721~723행)은 4.4 의 두 줄로 바뀐다. `dispose()`(749행)는 **안 고친다** — `layout.destroy()` 가 시뮬레이션을 멈추고, 포인터 캡처는 캔버스가 떨어져 나가면서 사라진다.

## 11. 게이트 — G7 에 얹는다

**새 게이트를 세우되 목표치는 G7 과 같다.** 끄는 동안의 상태는 F-2006 12.3 의 G7 과 **정확히 같은 상태**(노드 1,000, 시뮬레이션이 프레임마다 1 tick)이고, F-2009 가 프레임에 더하는 일은 **`pointermove` 당 `readBasis`(0.0915 µs) + 좌표 풀기(산술 열댓 번) + `fixNode`·`reheat`(대입 넷)** 이 전부다. `pointermove` 가 프레임당 최대 1건이므로(6.5) **프레임당 0.001 ms 미만**이다. 목표를 따로 낮출 근거가 없다.

| # | 무엇을 | 목표 |
| --- | --- | --- |
| **G7c** | **노드 1,000**, 배치가 멈춘 뒤 **노드를 끄는 동안**의 프레임 간격 | **평균 45 fps 이상(프레임 간격 22.2 ms 이하), 최악 프레임 50 ms 이하** (3회 중앙값) — G7·G7b 와 같은 수 |

  --action "hover:.map-canvas" \

- **`wait:9000` 으로 먼저 배치를 끝낸다.** 그래야 재는 것이 "여는 중" 이 아니라 "끌기가 일으킨 재가열" 이다

- 앞 두 프레임은 버린다(`slice(2)`)
- **못 맞추면 이 순서대로** (F-2006 12.3 의 목록 중 끌기에 실제로 듣는 것만): (1) `readBasis()` 가 `pointermove` 마다가 아니라 프레임마다 한 번만 돌게 옮긴다, (2) 구체 분할 수를 `8 × 6` → `6 × 4` (F-292 7장 (4)), (3) 그래도 못 맞추면 **멈추고 보고한다**
- **번들 게이트는 두지 않는다.** 새 의존성 0개·새 파일 0개이고 `mapCamera.ts` 에 붙는 함수 둘은 산술 스무 줄이다. 구현 뒤 `dist/assets/MapPage-*.js` 의 gzip 이 **직전 커밋 대비 +1 KB 이내**인 것만 한 줄로 확인한다
- **G4(첫 열기 412 ms)·G5(reduced-motion 배치 5,521 ms)는 건드리지 않는다** — 사람 결정 대기 중이다

## 16. 열린 질문 / 사람 결정 필요

**사람이 꼭 골라야 하는 것은 없다. 전부 기본값이 서 있고, 다른 쪽을 골랐을 때 무엇이 달라지는지 적었다.**

### Q1. 노드 위에서 `pointerdown` 하는 순간 `controls.enabled` 를 끄는 것 — **기본: 끈다**

4.4 의 이유. 문턱까지 미루면 `OrbitControls` 가 캡처를 잡고 카메라를 최대 4 px 밀어 놓은 뒤 멈춘다.
**다른 쪽을 고르면**: `beginDrag()` 에서 끈다. 코드가 한 줄 줄고 "노드 위에서도 이동(pan)을 시작할 수 있다"가 살아나지만, **끌기를 시작할 때마다 카메라가 4 px 씩 틀어지고 `userMoved` 가 켜진다.** 그리고 `OrbitControls` 의 캡처와 우리 캡처가 같은 요소에 겹친다. 무엇보다 사용자 결정 2("노드 위에서 시작한 좌클릭 끌기만 노드 끌기다")와 어긋난다.

### Q2. 재가열 `alpha` 를 `MAP_REHEAT_ALPHA`(0.6) 로 — **기본: 슬라이더와 같은 상수를 쓴다**

6.3·6.4 의 이유와 실측표.
**다른 쪽을 고르면**: 끌기 전용 상수를 따로 둔다. `0.3` 이면 놓았을 때 덜 돌아오고 이웃이 덜 밀린다(문서 30 에서 52% 남음 / 이웃 214). `1.0` 이면 더 돌아오지만 이웃이 크게 튄다(39% / 516). **숫자 하나이고 `MAP_REHEAT_ALPHA` 옆에 상수 한 줄을 더하면 된다.** 사람 확인 H-b 가 이것을 묻는다.

### Q3. 문턱을 기존 상수(`CLICK_SLOP` 4 / `LONG_PRESS_SLOP` 10)로 — **기본: 기존 상수**

4.2 의 이유 — 클릭 판정·길게 누르기 취소와 경계가 정확히 맞물린다.
**다른 쪽을 고르면**: `DRAG_SLOP` 을 따로 두고 6~8 px 쯤으로 올린다. 손 떨림에 덜 민감해지는 대신, **4~8 px 구간이 "끌기도 아니고 클릭도 아닌" 죽은 구간**이 된다(`onPointerUp` 이 `> 4` 에서 클릭을 막으므로). 그 구간까지 없애려면 `onPointerUp` 의 `CLICK_SLOP` 도 같이 올려야 하고, 그러면 F-2002 6.8 이 정한 클릭 판정이 바뀐다.

### Q4. 끄는 동안 커서를 `grabbing` 으로 — **기본: 바꾼다**

8.3 의 이유. F-2004 가 되돌린 것은 **호버** 커서였다.
**다른 쪽을 고르면**: `pointer` 로 둔다. `beginDrag`·`endDrag` 에서 각 한 줄이 빠지고 커서 상태가 둘로 줄지만, 끌고 있다는 피드백이 노드의 움직임뿐이 된다.

### Q5. 놓았을 때 카메라를 다시 맞추는가(`followFit`) — **기본: 안 맞춘다**

7.2 의 마지막 글머리. 끌기는 사용자가 화면 구도를 직접 정한 조작이라, 놓자마자 카메라가 움직이면 방금 만든 배치를 다시 못 보게 된다. 덩어리가 틀을 벗어나면 `맞춤` 이 있다.
**다른 쪽을 고르면**: `endDrag()` 끝에서 `followFit = true` 한 줄. F-2006 6.3 이 슬라이더에 대해 고른 것과 같아지고, 노드를 멀리 던져 놓아도 전체가 화면 안에 남는다. 대신 **놓을 때마다 카메라가 줌아웃해 노드가 작아진다** — 여러 개를 차례로 끌 때 거슬린다.

### Q6. 끌다가 창이 blur 되는 경우를 막는가 — **기본: 안 막는다**

10장. `window` 에 `blur`·`pointerup` 리스너를 새로 달지 않는 것은 F-2003 4.4 가 메뉴에 대해 내린 것과 같은 기준이다.
**다른 쪽을 고르면**: `canvas` 에 `lostpointercapture` 를 하나 더 달아 `endDrag()` 를 부른다. 리스너가 일곱에서 여덟이 되고 `dispose()` 의 `removeEventListener` 도 하나 는다. 안전하지만 아직 일어난 적 없는 상황에 대한 보험이다.

### Q7. 여러 노드를 한꺼번에 끌 수 있게 하는가 — **기본: 안 한다**

명세 어디에도 없고, 고를 방법(사각형 선택 등)부터 새로 설계해야 한다.
**다른 쪽을 고르면**: 새 소명세가 필요하다. 이 명세의 범위 밖이다.
