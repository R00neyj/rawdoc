## 사용자가 이미 정한 것 (2026-09-23. **바꾸지 않는다**)

1. **모양은 스켈레톤이다.** 사이드바 목록 자리와 편집 영역 자리에 흐린 줄(자리표시 막대)을 그린다. 가운데 로고+스피너, 상단 진행 막대는 기각됐다. 이유는 S-3 이 이미 레이아웃 뼈대를 그리고 있어 이어 붙이기 쉽고, 문서가 뜰 때 화면이 튀지 않아서다

## 2. 범위

### 한다

- 앱 HTML(`index.html`)을 받는 모든 앱 경로에서 첫 페인트부터 `ready` 까지 스켈레톤을 보인다
- 첫 페인트 전에 저장된 테마(`md.theme` + 시스템 다크 설정), 사이드바 너비(`md.sidebarWidth`), 사이드바 접힘(`md.sidebar`)을 반영해 스켈레톤을 실제 화면과 같은 틀로 그린다
- 공개 보기(S-5) 경로에서는 스켈레톤을 그리지 않는다
- 부팅 중 `.app-shell` 을 `aria-busy`·`inert` 로 둔다
- F-136 3.3 의 막힘 문구가 뜨면 스켈레톤을 걷고 그 문구를 보인다

### 하지 않는다

- **`ready` 뒤 문서 본문 로딩**(`store.get` → `Editor` 마운트)을 가리는 일. 사용자 결정 2 의 경계를 따른다. 실측한 틈과 다른 선택지는 16장 Q1
- 공개 보기(`PublicView`)·공유 관리·도움말·지도 화면 **안의** 자체 로딩 표시(`불러오는 중…`, `연결을 읽는 중…`)를 바꾸는 일
- 랜딩(`worker/welcomePage.ts`)·공개 사이트(`site/`)·`404.html`. 이 셋은 `index.html` 을 쓰지 않는 따로 된 HTML 이라 스켈레톤이 생길 자리가 없다 (7장)
- JS 번들 크기 줄이기. 첫 방문 JS 는 gzip 669KB 이고(3.1), 스켈레톤이 그 시간을 가릴 뿐 줄이지는 않는다
- 부팅이 끝나지 않는 오류(JS 로드 실패, `boot()` 예외)에 제한 시간을 두는 일 (11장)
- 서체를 첫 페인트 전에 반영하는 일. 스켈레톤에 글자가 없어서 필요 없다

## 3. 지금 — 코드와 실측

### 3.1 첫 화면이 그려지는 순서

- `index.html` 은 `<div id="root"></div>` 와 `/src/main.tsx` 모듈 하나뿐이다. 빌드하면 `<head>` 에 `index-*.js`(모듈), `createEditor-*.js`(modulepreload — 메인이 정적으로 import 한다), `createEditor-*.css`·`index-*.css`(스타일시트 링크)가 들어간다
- 크기(2026-09-23 작업 트리 빌드): `index-*.js` 619,013B(gzip 205,575B), `createEditor-*.js` 1,599,138B(gzip 463,816B), `index-*.css` 88,762B(gzip 15,238B), `createEditor-*.css` 17,524B(gzip 3,482B). **첫 방문에는 CSS 19KB 가 먼저 오고 JS 669KB 를 받는 동안 화면이 `--paper` 한 색이다.** 사용자가 말한 "흰 화면" 이 이 구간이다
- `data-theme` 은 `src/main.tsx` 가 **번들 실행 뒤에** 넣는다. 그래서 다크 사용자는 JS 가 뜨기 전까지 화이트 `--paper` 를 본다. 첫 페인트 전에 테마를 읽는 인라인 스크립트는 **지금 없다**
- CSP 는 없다. `worker/**/*.ts` 에 `Content-Security-Policy` 를 붙이는 곳이 없고, `public/_headers` 는 `Cache-Control` 만, `wrangler.jsonc` 에는 헤더 설정이 없다. `index.html` 에 `<meta http-equiv>` 도 없다. 인라인 스크립트의 선례는 `worker/welcomePage.ts` 의 조기 판정 스크립트다
- PWA: `workbox.globPatterns` 에 `html` 이 있어 `index.html` 이 precache 되고 `navigateFallback: 'index.html'` 이다. 인라인 내용이 바뀌면 revision 만 바뀐다. 서비스 워커가 내주는 오프라인 부팅에도 스켈레톤이 따라간다

### 3.2 부팅 구간 실측

`vite preview` 에서 첫 로드와 다시 읽기 두 번을 쟀다. `mount` = `#root` 에 첫 자식이 생긴 때, `ready` = `.app-shell` 이 있고 `[data-editor-slot]` 이 사라진 때, `content` = `md.startScreen='last'` 일 때 `.cm-line` 이 처음 보인 때. 단위는 ms, 탐색 시작 기준이다

| 조건 | FP | mount | ready | content |
| --- | --- | --- | --- | --- |
| 감속 없음, 첫 로드 | 148~176 | 219~230 | 302~323 | 383 |
| 감속 없음, 다시 읽기 | 20~40 | 43~76 | 63~112 | 95~130 |
| CPU 4배 감속, 첫 로드 | 140~156 | 705~747 | 1,139~1,255 | 1,629 |
| CPU 4배 감속, 다시 읽기 | 76~220 | 227~375 | 369~555 | 534~684 |
| `/api/me` 400ms 지연 | 36~152 | 92~192 | 509~614 | — |

- 로컬 프리뷰에는 워커가 없다. `/api/me` 가 `index.html` 을 200 으로 돌려주고, JSON 파싱이 실패해 `offline` 으로 곧바로 끝난다. **운영에서는 `/api/me` 한 번이 연결 재사용 기준 139~158ms 더 든다**(curl 측정). 로그인 사용자는 여기에 `list()` 의 `/api/docs` 등이 더해진다
- **ready → 본문(`content`) 틈**: 감속 없음 25~81ms, CPU 4배 148~374ms. 이 틈에서는 편집 영역이 비어 있다. 이 명세 범위 밖이다 (16장 Q1)

### 3.3 부팅 중 React 가 그리는 것

- `bootPhase === 'booting'` 인 동안에도 `.app-shell` 전체(사이드바 머리 줄·버튼들, 상단바, 빈 목록)가 그려진다. `.content-area[data-editor-slot]` 은 비어 있고, 막혔을 때만 `.boot-blocked-notice` 가 뜬다
- 부팅 중 `store` 는 `createMemoryStore()` 임시값이다. 사이드바 `새 문서` 버튼은 부팅 중에도 눌리고, 누르면 이 임시 저장소에 쓴다(`boot()` 가 저장소를 바꾸면 사라진다). `openSearch` 는 `bootPhase !== 'ready'` 면 돌아가고 인쇄도 `printDisabledRef` 로 막혀 있지만, 사이드바 버튼에는 이런 막음이 없다
- 공개 보기는 `publicRoute` 초기값(`parsePathRoute(location.pathname)` 이 먼저, 없으면 `parseHash(location.hash)`)으로 첫 렌더부터 `PublicView` 를 조기 반환한다

## 4. 결정 1 — 색과 테마를 첫 페인트에 어떻게 맞추나

### 4.1 결론

- 스켈레톤 CSS 는 **번들 CSS**(`src/styles/boot.css`, `main.tsx` 가 import)에 둔다. 색은 `tokens.css` 의 `var(--paper)`·`var(--panel)`·`var(--rule)`·`var(--ink)` 와 `color-mix(in srgb, …)` 로만 만든다. **HTML 에도 CSS 에도 hex 를 쓰지 않는다.** 토큰을 추출해 주입하는 빌드 단계는 두지 않는다
- 테마는 **`<head>` 인라인 스크립트** 하나가 첫 페인트 전에 `<html data-theme>` 을 넣는다. 그러면 `tokens.css` 의 `:root[data-theme='sepia'|'dark']` 블록이 스켈레톤에도 그대로 걸린다

### 4.2 왜 인라인 `<style>` 이나 토큰 주입이 아닌가

- 빌드된 `index.html` 은 `<head>` 에 `<link rel="stylesheet">` 가 있다. 이 링크는 렌더 차단이다. **실측 (a)**: CSS 를 1,500ms 붙잡자 first-paint 가 1,644ms 로 밀렸다. 즉 첫 페인트 시점에는 번들 CSS 가 **이미 적용돼 있다.** 인라인 `<style>` 로 옮겨도 더 일찍 그려지지 않는다
- 인라인 `<style>` 로 가려면 `vite.config.ts` 가 `tokens.css` 에서 테마 3종 값을 뽑아 주입해야 한다(`readTokenColor` 선례). 얻는 것은 없고, 토큰 값이 HTML 과 번들 두 곳에 실리는 것만 늘어난다
- 예외는 개발 서버(`npm run dev`)다. 거기서는 CSS 가 JS 로 주입돼 JS 전에는 스켈레톤에 스타일이 없다. 마크업에 글자 노드가 없고 빈 `div` 뿐이라 **아무것도 보이지 않는다**(지금 개발 서버와 같다). 개발 서버의 첫 페인트는 이 명세의 판정 대상이 아니다

### 4.3 머리 인라인 스크립트 `BOOT_PAINT_SCRIPT`

위치와 모양

- `index.html` 의 `<meta name="viewport">` 바로 다음 줄 자리표시 `%BOOT_PAINT_SCRIPT%` 를 `bootPaintPlugin()` 이 `<script>…</script>` 로 바꾼다(`%BRAND_NAME%` 치환과 같은 방식). **`type="module"`·`src` 없는 클래식 스크립트**이고, 모든 `<link rel="stylesheet">` 보다 앞에 온다
- `head-prepend` 로 넣지 않는 이유가 있다. 스크립트가 `<meta charset>` 앞에 오면 charset 선언이 문서 앞 1,024바이트 밖으로 밀릴 수 있다. `vite preview` 는 `Content-Type: text/html` 을 charset 없이 준다(curl 확인). 그런데 스켈레톤 마크업에는 한국어 `aria-label` 이 있다
- 개발 서버에서도 같은 플러그인이 치환한다(`brandHtmlPlugin` 이 개발 서버에서도 도는 것과 같다)

하는 일 — 결과는 `<html>` 에만 쓴다

| 쓰는 것 | 값 | 규칙 |
| --- | --- | --- |
| `data-theme` 속성 | `white` \| `sepia` \| `dark` | `resolveTheme(md.theme, matchMedia('(prefers-color-scheme: dark)').matches)` 와 **같은 결과**. 저장값이 없거나 모르는 값이면 시스템 설정을 따른다 |
| `--boot-sidebar-w` 사용자 속성(`style`) | `{정수}px` | `clampSidebarWidth(resolveStoredSidebarWidth(md.sidebarWidth), innerWidth)` 와 **같은 결과** |
| `data-boot-sidebar` 속성 | `collapsed` 또는 없음 | `md.sidebar === 'collapsed'` 일 때만 넣는다 |
| `data-boot-view` 속성 | `doc` \| `home` \| `blank` \| `off` | 6.3 표 |

지킬 것

- 쓰는 전역 이름은 **`document`·`localStorage`·`matchMedia`·`location`·`innerWidth` 다섯 개뿐이다.** `window.` 접두사를 붙이지 않는다. 단위 테스트가 이 다섯 이름을 가짜로 덮어 스크립트를 실행하기 때문이다(14.1). 다른 전역을 쓰면 테스트에서 `ReferenceError` 로 드러난다
- `localStorage` 읽기는 **하나씩 따로** 감싼다. 한 읽기가 던지면(시크릿 창·차단) 그 값만 기본값으로 둔다(`prefs.ts` 의 `getPref` 와 같은 뜻). 스크립트 전체도 감싼다. 어떤 경우에도 예외가 밖으로 나가지 않는다
- 키 문자열(`md.theme`·`md.sidebar`·`md.sidebarWidth`·`md.startScreen`)과 너비 상수(`MIN_SIDEBAR_WIDTH`·`MAX_SIDEBAR_WIDTH_CAP`·`MAX_SIDEBAR_WIDTH_MARGIN`·`DEFAULT_SIDEBAR_WIDTH`)는 스크립트 문자열에 손으로 다시 적지 않는다. `sidebarWidth.ts` 에서 import 한 값을 `JSON.stringify` 로 끼워 넣는다(`worker/welcomePage.ts` 가 `EARLY_APP_KEYS` 를 끼워 넣는 선례). 판정 **논리**(`resolveTheme`·`clampSidebarWidth`·`parseHash` 의 공개·문서 패턴)는 스크립트 안에 따로 적을 수밖에 없다. 대신 U1~U4 가 원래 함수와 결과가 같은지 표로 묶는다
- 문법은 ES2017 이하로 쓴다. 번들을 거치지 않으므로 선택적 체이닝 같은 문법이 그대로 나간다
- `src/main.tsx` 가 번들 실행 때 `data-theme` 을 다시 넣는 줄은 **그대로 둔다.** 같은 값을 다시 넣을 뿐이고, 스크립트가 실패했을 때의 안전망이다

## 5. 결정 2 — 인라인 → React 인계

### 5.1 결론 — 같은 DOM 노드가 그대로 남고, React 는 걷기만 한다

- 스켈레톤은 `#root` **바깥**(`<body>` 안, `#root` 바로 앞 형제)의 `#boot-skeleton` 한 덩어리다. `position: fixed; inset: 0` 으로 창 전체를 덮는다
- React(`createRoot(#root)`)는 이 노드를 만들지도 그리지도 않는다. 부팅 중 React 는 **지금처럼** `.app-shell` 을 그 아래 그린다. 스켈레톤이 위를 덮는다
- `ready` 가 되면 App 이 이 노드를 **DOM 에서 지운다.** ready 화면이 이미 아래에 그려져 있으므로 그 커밋이 화면에 나가는 순간 스켈레톤 → 실제 화면이 한 프레임에 바뀐다

### 5.2 왜 이 방식인가 — 버린 쪽과 비교

| | A. 겹침 노드 유지, React 가 걷기만 (채택) | B. `#root` 안에 인라인, React 가 같은 모양을 다시 그림 |
| --- | --- | --- |
| 인계 순간 | 노드가 바뀌지 않는다. **실측 (b)**: React 마운트 전후로 같은 노드(심어 둔 `data-mark` 유지) | React 첫 커밋이 `#root` 안 내용을 비우고 자기 트리로 바꾼다. 같은 프레임이긴 하지만 두 벌이 픽셀까지 같아야 깜빡이지 않는다 |
| 모양의 원본 | `index.html` 한 벌 | `index.html` + React 컴포넌트 두 벌. 어긋나면 사용자 결정 2 위반 |
| App 변경 | 레이아웃 효과 하나 + 속성 두 개 | 부팅 중 렌더를 `.app-shell` 대신 스켈레톤 컴포넌트로 바꿔야 한다. 그러면 부팅 중에는 `appShellRef`·`sidebarRef`·`toggleButtonRef` 가 비어, 마운트 때 한 번 구독하는 효과들이 빈 ref 를 잡을 위험이 생긴다 |
| 막힘 문구(F-136) | 스켈레톤을 걷으면 지금 자리에 그대로 보인다 | 스켈레톤 컴포넌트 안에 문구 자리를 새로 만들어야 한다 |

### 5.3 걷는 때와 방법

- `removeBootSkeleton(doc)` 이 하는 일: `#boot-skeleton` 을 지우고, `<html>` 의 `data-boot-view`·`data-boot-sidebar` 속성과 `--boot-sidebar-w` 사용자 속성을 지운다. **`data-theme` 은 지우지 않는다**(그 뒤로는 `main.tsx`·App 의 테마 효과가 주인이다). 노드가 없어도 던지지 않고, 두 번 불러도 된다(StrictMode 이중 실행)
- 부르는 조건은 아래 셋 중 하나라도 참일 때다
  - `bootPhase === 'ready'`
  - `publicRoute !== null` — 공개 보기. CSS 로 이미 숨어 있지만 DOM 에서도 지운다 (7장)
  - `dbBlockedMessage !== null` — F-136 막힘. 기다리는 동안 흐린 줄이 "진행 중" 처럼 보이면 사용자가 다른 창을 닫아야 한다는 사실이 가려진다. 걷고 지금처럼 문구를 보인다. 막힘이 풀려 부팅이 이어져도 **스켈레톤은 다시 그리지 않는다**
- **때: 그 조건을 만든 커밋이 화면에 그려지기 전**(레이아웃 효과 시점)이다. 수동 효과(`useEffect`)는 페인트 뒤에 돌 수 있어 한 프레임 동안 둘이 겹칠 수 있다. 스켈레톤이 위에 있으니 깜빡임은 아니지만, 그 프레임 동안 ready 화면의 클릭을 가로챈다
- 효과는 `if (publicRoute)` 조기 반환 **위에** 선언한다. 훅 순서 규칙이고, 공개 보기에서도 돌아야 하기 때문이다
- 걷을 때 흐려지며 사라지는 전환은 두지 않는다 (16장 Q6)

`src/app/bootPaint.ts` 가 내보내는 것

```ts
export const BOOT_PAINT_SCRIPT: string
export function removeBootSkeleton(doc: Pick<Document, 'getElementById' | 'documentElement'>): void
```

## 6. 결정 3 — 좁은 창·접힌 사이드바·너비, 그리고 편집 영역 변형

첫 페인트 때는 React 상태가 없다. 그래서 React 가 상태로 정하는 네 가지를 각각 아래처럼 맞춘다

### 6.1 좁은 창 — CSS 미디어 쿼리 하나

- App 의 `narrow` 는 `matchMedia('(max-width: 1023px)')`(`NARROW_QUERY`)다. `boot.css` 가 **같은 조건** `@media (max-width: 1023px)` 로 스켈레톤 사이드바 열을 숨긴다. JS 가 필요 없다
- 좁은 창의 실제 화면은 이렇다. 겹침 사이드바는 처음에 닫혀 있고(`sidebarOpen` 초기값 `false`), 상단바가 창 전체 폭 맨 위에 있고, 그 아래가 편집 영역이다. 스켈레톤은 사이드바 열을 빼고 상단바(`.boot-skeleton-topbar`)를 창 전체 폭으로, 그 아래 편집 영역을 둔다
- 실측(창 800×900): `.topbar` 는 x=0, 폭 800, 높이 52다. 겹침 `.sidebar` 는 화면 밖(x=-300)이다

### 6.2 넓은 창 — 너비와 접힘

- 너비: 스켈레톤 사이드바 열 폭 = `var(--boot-sidebar-w, var(--sidebar-w))`. 머리 스크립트가 App 과 같은 계산으로 넣은 값이다(4.3)
- 접힘: `html[data-boot-sidebar="collapsed"]` 면 열 폭 = `var(--sidebar-rail-w)`(48px)이고 막대를 그리지 않는다. 좁은 창에서는 이 속성이 있어도 사이드바 열을 숨긴다(App 의 `isRail = collapsed && !narrow` 와 같다)
- 실측(1600×900): 저장값 없음 → `.sidebar` 폭 300, `md.sidebarWidth=360` → 360, `md.sidebar=collapsed` → 48
- 부팅 중 창 크기를 바꾸면 너비는 머리 스크립트 때 값으로 남는다(좁은 창 전환은 미디어 쿼리라 따라간다). ready 에서 실제 값으로 맞춰진다. 부팅 구간이 짧아 따로 다루지 않는다

### 6.3 편집 영역 변형 — `data-boot-view`

ready 뒤 편집 영역이 무엇이 되느냐에 따라 막대 모양을 고른다. 홈 화면(가운데 정렬, `EmptyState`) 사용자에게 문서 모양 막대를 보이면 ready 때 모양이 튄다. 기본 시작 화면이 홈(`md.startScreen` 기본 `home`, F-232)이라 그런 사용자가 대부분이다

| 조건 (위에서부터 처음 맞는 것) | 값 | 편집 영역 막대 |
| --- | --- | --- |
| `parsePathRoute(location.pathname)` 또는 `parseHash(location.hash)` 의 `type` 이 `public`·`publicFolder` | `off` | 스켈레톤 전체를 숨긴다 (7장) |
| `parseHash` 의 `type` 이 `doc` | `doc` | 문서 모양 (9.3) |
| `parseHash` 의 `type` 이 `share`·`shares`·`help`·`map` | `blank` | 막대 없음. 사이드바·상단바 틀만 |
| 그 밖(`#/`·해시 없음·모르는 해시)이고 `md.startScreen === 'last'` | `doc` | 문서 모양 |
| 그 밖 | `home` | 홈 모양 (9.4) |
| 스크립트가 속성을 못 넣었을 때(속성 없음) | — | `blank` 와 같게 그린다 |

- `startScreen === 'last'` 이면 `lastDocId` 가 없어도 `doc` 이다. App 의 `resolveInitialDoc` 은 마지막 문서가 없으면 목록 첫 문서를 연다. 문서가 0개라 홈이 되는 경우는 머리 스크립트가 알 수 없다. 그때는 문서 모양 → 홈으로 바뀐다
- e2e `openApp()` 은 `md.startScreen='last'` 를 넣으므로 `doc`, `openAppHome()` 은 `home` 이다

### 6.4 마크업 계약 — 이름

| 선택자 | 무엇 | 쓰는 곳 |
| --- | --- | --- |
| `#boot-skeleton.boot-skeleton` | 겹침 뿌리. `role="status"`, `aria-label="불러오는 중…"` | `boot.css`, `removeBootSkeleton`, e2e |
| `.boot-skeleton-sidebar` | 사이드바 열 (머리 줄 막대 1 + 목록 막대 6). `aria-hidden="true"` | `boot.css`, e2e A5·A6 |
| `.boot-skeleton-main` | 오른쪽 열. `aria-hidden="true"` | `boot.css` |
| `.boot-skeleton-topbar` | 상단바 자리 (좁은 창에서만 막대 1) | `boot.css`, e2e A7 |
| `.boot-skeleton-content` | 편집 영역 자리 | `boot.css` |
| `.boot-skeleton-doc` | 문서 모양 묶음 (제목 막대 1 + 본문 막대 7) | `boot.css`, e2e A8 |
| `.boot-skeleton-home` | 홈 모양 묶음 (문장 막대 1 + 버튼 자리 2) | `boot.css`, e2e A8 |

- 마크업은 `index.html` 에 정적으로 한 벌만 둔다. `doc`·`home` 두 묶음을 다 두고 CSS 가 `data-boot-view` 로 하나만 보인다
- **글자 노드를 두지 않는다.** 이름은 `aria-label` 로만 준다. 개발 서버처럼 스타일이 오기 전 상태에서도 글자가 새어 보이지 않게 하기 위해서다
- 쌓임 순서: `.boot-skeleton` 의 `z-index` 는 `100` 이다. 지금 `src/styles/*.css` 의 최댓값이 `50` 이다(2026-09-23 grep). 대화상자는 최상위 레이어라 비교 대상이 아니다. 부팅 중에는 대화상자가 열리지 않는다

## 8. 결정 5 — 너무 짧게 지나가 번쩍이는 문제

**결론: 표시 지연도, 최소 표시 시간도 두지 않는다. 대신 깜빡임 움직임만 400ms 늦게 시작한다**

- 스켈레톤은 **실제 화면과 같은 틀**(사이드바 폭, 상단바 높이, 열 바탕색)을 그린다. 짧게 지나가도 바뀌는 것은 "막대 → 글자" 뿐이다. 스피너처럼 번쩍이지 않는다. 지금은 첫 페인트가 창 전체 `--paper` 한 색이고, 그다음 틀, 그다음 내용이 온다. 오히려 지금보다 바뀌는 단계가 하나 준다
- 표시 지연(예: 200ms 뒤 나타남)을 두면 그 동안 지금의 빈 화면이 그대로 보인다. 3.2 표에서 운영 부팅은 `/api/me` 만으로 139ms 이상이다. 그러니 많은 부팅에서 빈 화면 → 스켈레톤 → 화면 세 단계가 되어 번쩍임이 오히려 는다. 사용자 결정 2("첫 페인트부터")와도 어긋난다
- 최소 표시 시간(예: 300ms)은 **모든 부팅을 그만큼 늦춘다.** 다시 읽기 부팅(63~112ms)이 3~5배 느려진다
- 움직임: 막대가 옅어졌다 돌아오는 깜빡임(9.5)은 **400ms 뒤에 시작한다.** 짧은 부팅(감속 없는 다시 읽기 ~112ms, 운영 로컬 사용자 추정 ~300ms)은 움직임 없이 지나간다. 오래 걸리는 부팅(CPU 감속, 로그인 사용자 목록 읽기)만 "아직 진행 중" 을 알린다. 시작할 때 값이 정지 상태와 같아서, 움직임이 시작되는 순간 튀지 않는다

## 10. 접근성

- `#boot-skeleton`: `role="status"`, `aria-label="불러오는 중…"`. 안의 두 열은 `aria-hidden="true"` 다. 문구는 기존 로딩 문구(`PublicView.tsx`·`SharesPage.tsx` 의 `불러오는 중…`)와 같다
- `.app-shell`: `bootPhase === 'booting'` 인 동안 `aria-busy="true"` 와 `inert` 를 둔다. ready 커밋에서 둘 다 없어진다(속성 자체가 사라진다. `"false"` 로 남기지 않는다)
  - **왜 `inert` 인가.** 겹침이 마우스는 막지만 키보드 `Tab` 은 아래 사이드바 버튼으로 간다. 그러면 초점 테두리가 스켈레톤에 가려 안 보이고(WCAG 2.4.7), `Enter` 로 `새 문서` 를 누르면 임시 memoryStore 에 써서 사라진다(3.3)
  - 막힘(F-136)으로 스켈레톤을 걷은 뒤에도 부팅 중이면 `inert` 는 남는다. 같은 이유다. 막힘 문구는 글자라 `inert` 여도 보인다
  - 전역 단축키 중 부팅 중에 무언가를 여는 것은 없다. `Ctrl+Shift+F` 는 `openSearch` 가, `Ctrl+P` 는 `printDisabledRef` 가 이미 막는다. 그래서 `inert` 안에 대화상자가 열려 갇히는 경우는 없다
- Playwright 1.63 은 `inert` 요소도 `getByRole` 로 찾는다(`e2e/*` 의 `.item-menu-list:not([inert])` 선례가 증거다). 대신 클릭 가능성 검사에서 가려진 것으로 보고 기다린다. 부팅 직후 누르는 테스트는 ready 까지 저절로 기다린다

## 16. 열린 질문 / 사람 결정 필요

### Q1. ready 뒤 편집 영역이 비는 틈 — **기본: 사용자 결정대로 ready 에서 걷는다** (사람이 봐 주면 좋다)

- 사실(3.2): `doc` 화면에서 ready → 첫 `.cm-line` 까지 감속 없이 25~81ms, CPU 4배 148~374ms 동안 편집 영역이 빈다. 문서 모양 막대 → 빈 칸 → 글자 순서가 된다. 사용자 말 "문서 가져와지기 전에" 를 넓게 읽으면 이 틈도 가려야 한다
- 기본값의 이유: 사용자가 경계를 "`ready` 가 되면 사라진다" 로 못박았다. 틈도 보통 한두 프레임이다
- 다른 쪽을 고르면: 편집 영역 부분(`.boot-skeleton-content`)만 에디터 첫 그림까지 남긴다. 걷는 일이 두 단계가 된다. ready 때 사이드바·상단바 겹침을 먼저 걷고, `openDoc` 이 도착해 `Editor` 가 첫 줄을 그린 뒤(보기 모드면 `viewerHtml` 이 채워진 뒤) 편집 영역 겹침을 걷는다. 그러려면 5.3 의 조건, `removeBootSkeleton` 의 계약(부분 제거), 겹침 배치(편집 영역만 덮는 위치 계산), e2e A3·A11 이 바뀐다. `Editor` 에서 "첫 그림" 신호를 받아야 해 `src/editor/Editor.tsx` 가 파일 소유에 들어온다

### Q2. 표시 지연·최소 표시 시간 — **기본: 둘 다 없다** (8장)

- 다른 쪽을 고르면: 표시 지연 200ms 면 빠른 부팅에서는 지금의 빈 화면이 그대로 남아 사용자 요청과 어긋난다. 최소 300ms 면 모든 부팅이 그만큼 늦는다. 어느 쪽이든 `boot.css`(지연은 CSS `animation-delay` 로 된다)나 `App.tsx`(최소 시간은 걷는 때를 미룬다)가 바뀌고 e2e A3 의 기다림이 늘어난다

### Q3. 움직임 — **기본: 400ms 뒤 시작하는 불투명도 깜빡임**

- 다른 쪽을 고르면: 움직임 없음이면 `boot.css` 에서 애니메이션만 빠지고, A10 은 "늘 `none`" 으로 바뀐다. 오래 걸리는 부팅에서 멈춘 화면처럼 보일 수 있다. 빛이 지나가는 shimmer 로 하면 그라디언트 배경 위치를 움직인다. 막대마다 칠이 달라져 8% 흐린 줄 인상이 옅어지고, `color-mix` 두 벌이 더 든다

### Q4. 편집 영역 변형 셋(`doc`·`home`·`blank`) — **기본: 셋**

- 다른 쪽을 고르면: 문서 모양 하나로 합치면 머리 스크립트에서 `startScreen`·해시 판정이 빠지고 U3 가 줄어든다. 대신 기본 설정 사용자(홈)가 매번 문서 막대 → 가운데 홈 화면으로 튀는 것을 본다. 사용자 결정 1 의 이유("문서가 뜰 때 화면이 튀지 않음")와 어긋난다

### Q5. 부팅 중 `.app-shell` 의 `inert` — **기본: 둔다** (10장)

- 다른 쪽을 고르면: `aria-busy` 만 둔다. 키보드 `Tab` 이 스켈레톤 아래 버튼으로 가 초점이 안 보이고, `Enter` 로 만든 새 문서가 임시 저장소와 함께 사라지는 지금 문제가 남는다. A2·A3·A9 의 `inert` 단정이 빠진다

### Q6. 걷을 때 흐려지며 사라지기 — **기본: 없음, 바로 지운다**

- 다른 쪽을 고르면: 150ms 정도 불투명도 전환을 두면 그동안 겹침이 준비된 화면의 클릭을 가로채므로 `pointer-events: none` 을 함께 줘야 한다. `removeBootSkeleton` 은 전환이 끝난 뒤 지워야 한다. A3 은 "0개" 가 되기까지 기다림이 늘어난다. 틀이 같아 전환 없이도 튀지 않으니 얻는 것이 적다
