## 2. 읽기 전용 연결 (개요 3.1)

### 2.1 무엇이 바뀌나

| 자리 | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| `/ws/doc/:id` 판정 | view → `4403` `forbidden` | view → **넘긴다**(`X-WS-Role: view`). 막힌 view 는 `4403` `forbidden`(2.2) |

| `onCustomMessage` | 빈 몸 | `core.handleCommentOp(conn, message)` (4장) |

### 2.2 `/ws/doc/:id` 판정 — `resolveDocSocket`

지금 순서(메서드·Upgrade → Origin → UUID → 사용자 → 접근 → 금고)는 그대로 두고, 마지막 "`edit` 미만이면 `4403`" 한 줄을 아래로 바꾼다:

1. `access.blocked` 가 참(edit·소유자였는데 본인 또는 소유자가 막힘) → `4403` `forbidden`. **지금 결과와 같다**(DS1·DS2)
2. `access.role === 'view'` 이고 `isWriteBlocked(env, access.doc, user)` 가 참 → `4403` `forbidden`
3. 그 밖 → 넘기기. `X-WS-Role` 에 `access.role` 그대로(`owner`·`edit`·`view`)

- 2번이 필요한 이유(t8): `resolveDocAccess` 는 view 에 막힘을 보지 않는다. 개요 2.4 는 댓글 달기에서 **막힌 계정을 뺀다**. 소켓을 받아 준 뒤 명령마다 막힘을 D1 로 보지 않으려고 입구에서 막는다
- **소유자가 막힌 문서의 view 초대자도 막는다** — 개요 2.4 는 "막힌 계정" 만 적었다. 이유: 지금 소유자가 막히면 그 문서의 edit 초대자도 `4403` 이다(F-2024 4.2 "실시간 연결", DS2). 소유자가 막힌 문서는 DO 스냅숏도 멈춘다(F-2027 `mayWrite`). view 만 열어 두면 막힌 문서에 댓글이 쌓이고 D1 복사본·알림은 풀릴 때까지 밀린다. 같은 판정 함수(`isWriteBlocked`: 본인 → 소유자 순)를 쓰므로 새 규칙이 아니다
- `isWriteBlocked` 는 `worker/access.ts` 의 지금 함수를 **그대로 내보낸다**(`export` 한 단어). 질의: 본인 사용량(세션에 `usage` 가 실려 오면 0번, 아니면 1번) + 소유자가 남이면 소유자 사용량 1번
- 금고 문서의 view 초대자는 지금처럼 `resolveDocAccess` 가 `null` → `4404` `not_found`(F-401 X1)
- 권한 판정 SQL 의 열 목록은 그대로(`content`·`*` 없음, F-304 A22)

### 2.3 읽기 전용 판정 — `isReadOnlyState` (계약)

```ts
// worker/docRoomCore.ts
export type RoomRole = 'owner' | 'edit' | 'view'
export type RoomConnState = { userId: string; email: string; role: RoomRole }
export function readConnState(state: unknown): RoomConnState | null   // 'view' 도 받는다
export function isReadOnlyState(state: unknown): boolean               // role 이 'owner'·'edit' 가 아니면 참
export function mayRelayAwareness(state: unknown): boolean             // role 이 'owner'·'edit' 일 때만 참
```

- **닫힌 쪽으로 판정한다** — 상태를 읽을 수 없는 연결도 읽기 전용이다. `onConnect` 가 신원을 못 읽으면 곧바로 닫으므로 보통은 생기지 않지만, 그 사이에 온 sync 메시지가 적용되지 않게
- `DocRoom.isReadOnly(conn)` 은 `isReadOnlyState(conn.state)` 한 줄이다. **메모리에 아무것도 들지 않는다** — 연결 상태는 WebSocket 첨부(attachment)에 있어 hibernation 을 넘긴다(t4). 깨어난 DO 가 다시 만든 `DocRoomCore` 도 같은 답을 낸다
- 효과(t1·t2): view 연결이 보낸 sync step 2·update 는 y-partyserver 가 `Y.Doc` 에 닿기 전에 버린다. **본문·제목·`comments` 어느 것도 view 연결의 Yjs 로는 바뀌지 않는다.** step 1(내 상태 달라)은 답한다 — view 도 방 Doc 을 받는다
- view 연결은 Yjs 로 쓰지 못하므로 F-502 사후 검사(`comments.observe`)에 view 연결 origin 의 트랜잭션이 오지 않는다(F-502 11.1)

### 2.4 view 연결의 awareness — 버린다 (개요 Q4)

- `DocRoom.onMessage` 가 awareness 바이트(첫 바이트 `1`)를 가로채는 지금 자리에서, `mayRelayAwareness(conn.state)` 가 거짓이면 **아무것도 하지 않고 돌아간다** — `relayAwareness` 도 `super.onMessage` 도 부르지 않는다. 그래서 view 는 `clientID` 를 소유하지 않고 clock 기록도 생기지 않는다(F-307 4.2)
- 받는 쪽은 바꾸지 않는다 — 방이 중계하는 awareness 와 `onConnect` 의 첫 awareness 는 view 연결에도 간다. 편집자 커서를 view 화면에 그릴지는 F-506 이 정한다
- `onClose` 의 `forgetAwareness` 는 그대로 — view 연결은 기록이 비어 있어 보낼 것이 없다

### 2.5 연결 뒤의 나머지

- `DocRoom.onConnect` 는 그대로 — `readForwardedIdentity` 결과를 `setState` 로 병합하고 `core.connect` 를 부른다. view 연결도 `catchUp`·step 1·`too-large` 알림을 똑같이 받는다
- 마지막 view 연결이 닫혀도 지금처럼 `roomEmptied()`(F-502 의 앵커 전체 다시 적기 포함)가 돈다
- DO 이용 시간: view 연결도 방을 깨워 둔다. hibernation 이 켜져 있어(`static options = { hibernate: true }`) 메시지가 없으면 잠든다 — 지금 edit 연결과 같다

## 3. 권한 다시 확인 — `revalidateConnections` (개요 3.1)

지금 규칙(연결마다 `resolveDocAccess` → 없거나 `edit` 미만이면 `4403` `revoked`)을 **연결 상태의 역할에 따라** 둘로 가른다. D1 행 한 줄 읽기·`email` 거르기·문서 없음 → `roomGone`·`lastRevalidate` 는 그대로다

| 연결 상태 `role` | 판정 결과 | 하는 것 |
| --- | --- | --- |
| `owner`·`edit` | 접근 없음 | `4403` `revoked` (지금 그대로) |
| `owner`·`edit` | `role` 이 `view` (강등, 또는 막혀서 `blocked: true`) | `4403` `revoked` (지금 그대로) — 클라이언트가 경로를 다시 판정해 view 로 다시 붙는다(F-506) |
| `owner`·`edit` | `edit`·`owner` | 그대로 |
| `view` | 접근 없음 | `4403` `revoked` |
| `view` | `blocked: true` | `4403` `revoked` |
| `view` | `role === 'view'` 이고 `isWriteBlocked` 참 | `4403` `revoked` |
| `view` | `role === 'view'` 이고 막히지 않음 | 그대로 |
| `view` | `edit`·`owner`(승격) | **그대로 둔다. 연결 상태도 `view` 로 둔다** — 개요 3.1 "다음 연결부터 edit 로 붙는다". 이 연결은 끝까지 읽기 전용이다 |
| 상태를 읽을 수 없음 | — | `4403` `revoked` (지금 그대로 — `state` 가 없으면 접근 없음) |

- `isWriteBlocked` 를 부르는 것은 **view 연결이면서 판정이 `view` 인 경우뿐**이다. edit·소유자 판정은 `resolveDocAccess` 가 이미 막힘을 본다
- **D1 질의 수** (코드 읽기로 셈): 연결 하나당 `resolveDocAccess` 가 초대 1 + 폴더 사슬 최대 2 + (edit·소유자면) 막힘 최대 2, view 연결이면 막힘 최대 2 를 더해 **어느 쪽이든 최대 5**. 점검 한 번 = 1 + 5 × 연결 수. **알려진 한계**: 연결 10개면 51 로, D1 "Worker 호출당 50"(개요 c9)이 DO 호출에도 걸린다면 넘는다. **걸리는지는 확인하지 않았다**(F-502 4.4 도 같은 가정). 지금 edit 연결 10개에서도 같은 수가 나오는 기존 한계이고, view 가 소켓을 열게 되면서 연결 수가 는다 — 12장 Q3
- 점검은 지금처럼 flush 끝(60초에 한 번)과 `notifyRevalidate` RPC(초대 바뀜)에서 돈다. view 만 있는 방은 편집이 없어 flush 가 드물지만, 명령이 `comments` 를 쓰면 그 갱신이 flush 를 부르므로 **명령을 보내는 연결은 늦어도 다음 flush 의 점검에서** 걸린다. 막힌 뒤·초대를 잃은 뒤 그 사이에 온 명령은 받아 준다 — edit 연결의 편집을 받아 주는 것과 같다(F-304 9.2, F-2028 6.2)

## 4. 명령 채널 (개요 3.1)

### 4.1 계약 — `src/lib/docRoomProtocol.ts`

```ts
export const COMMENT_OP_MAX_CHARS = 16_384   // __YPS: 를 뗀 문자열 길이(UTF-16). 넘으면 읽지 않는다

export type CommentOp =
  | { type: 'comment-add'; id: string; start: RelativePositionJSON; end: RelativePositionJSON; body: string; mentions: string[] }
  | { type: 'comment-reply'; id: string; parent: string; body: string; mentions: string[] }
  | { type: 'comment-resolve'; id: string; resolved: boolean }
  | { type: 'comment-delete'; id: string }

export type CommentOpRejectReason = 'forbidden' | 'invalid' | 'not_found' | 'too_long' | 'too_many' | 'rate_limited'
export type CommentOpReply =
  | { type: 'comment-ack'; id: string }
  | { type: 'comment-reject'; id: string; reason: CommentOpRejectReason }

export function encodeCommentOp(op: CommentOp): string
export function parseCommentOp(text: string): { ok: true; op: CommentOp } | { ok: false; id: string | null }
export function encodeCommentOpReply(reply: CommentOpReply): string
export function parseCommentOpReply(text: string): CommentOpReply | null
```

- 모양은 개요 3.1 그대로다. 이 명세가 더한 것은 길이 상한·파싱 함수 넷·`CommentOpRejectReason` 이라는 이름뿐이다
- **`id` 의 뜻**: `comment-add`·`comment-reply` 는 **새 항목의 `Y.Map` 키**(클라이언트가 `crypto.randomUUID()` 로 만든다). `comment-resolve`·`comment-delete` 는 **대상 항목의 키**. 응답의 `id` 는 받은 명령의 `id` 그대로
- 인코딩은 `JSON.stringify` 한 줄. 바깥 전송은 지금 문자열 채널(`__YPS:` 접두사, t1). 서버 → 클라이언트 쪽 기존 `DocRoomMessage`(`too-large`·`size-ok`)와 `parseDocRoomMessage` 는 **바꾸지 않는다** — `parseDocRoomMessage` 는 응답 문자열에 `null` 을 돌려준다. 클라이언트(F-506)는 받은 문자열을 두 파서에 차례로 넘긴다
- `createdAt`·`author`·`quote`·`resolved.at`·`resolved.by` 는 명령에 **없다** — 서버가 연결 상태와 서버 시각·서버 본문으로 채운다(개요 2.2·3.1 ④)
- `COMMENT_OP_MAX_CHARS = 16,384` 의 근거(t6): 정직한 명령의 최악이 6,285자. 화면이 1,000자에서 막지 못해 본문이 조금 넘친 명령도 `too_long` 응답을 받도록 두 배 남짓 여유를 둔다

**`parseCommentOp` 규칙** — 신뢰하지 않는 입력. 던지지 않는다:

| 경우 | 결과 |
| --- | --- |
| `text.length > COMMENT_OP_MAX_CHARS`, JSON 이 아님, 평범한 객체가 아님, `id` 가 `isCommentId`(F-501) 가 아님 | `{ ok: false, id: null }` — **응답을 보낼 수 없다** |
| `id` 는 올바른데 `type` 이 넷 밖이거나, 키 집합이 그 `type` 의 것과 정확히 같지 않거나(빠짐·더 있음), 필드 타입이 틀림 | `{ ok: false, id }` |
| 통과 | `{ ok: true, op }` — 새 객체 |

- 필드 타입: `start`·`end` 는 평범한 객체(안쪽 모양은 4.4 의 앵커 단계가 `readCommentAnchor` 로 본다), `body` 문자열, `mentions` 문자열 배열, `parent` 는 `isCommentId`, `resolved` 불리언. 본문 길이·멘션 규칙은 여기서 보지 않는다(4.4 의 항목 검사가 사유를 가른다)
- `parseCommentOpReply`: 키 집합이 정확히 `{type,id}`(ack) 또는 `{type,id,reason}`(reject), `id` 가 `isCommentId`, `reason` 이 여섯 중 하나. 아니면 `null`

### 4.2 DO 쪽 입구 (계약)

```ts
// worker/docRoomCore.ts
export const COMMENT_SERVER_ORIGIN = { commentServer: true }   // 명령·이관이 쓰는 트랜잭션 origin. 클라이언트와 공유하지 않는다
export const COMMENT_RATE_KEY = 'commentRate'                 // 연결 상태 안의 칸 이름
export type CommentRateState = { start: number; count: number }
export type StatefulConnection = RoomConnection & { setState(update: (prev: unknown) => unknown): unknown }
// class DocRoomCore
handleCommentOp(conn: C & StatefulConnection, text: string): void
```

- **동기 함수다.** 안에 `await` 가 없다 — D1 을 읽지 않는다(권한은 연결 상태, 막힘은 2.2·3장). 그래서 한 연결의 명령들은 받은 순서대로 끝나고, 응답도 **보낸 순서대로** 간다(소켓 하나, DO 는 메시지를 차례로 부른다). 클라이언트는 같은 `id` 의 응답을 보낸 순서(FIFO)로 짝지으면 된다
- `COMMENT_SERVER_ORIGIN` 을 F-502 의 `SERVER_ORIGINS` 초기값에 더한다(F-502 11.1). **안 더하면 F-502 사후 검사가 명령으로 쓴 항목을 "행위자 없음" 으로 보고 지운다** — O11 이 지킨다
- 이관(5장)도 같은 origin 을 쓴다. 두 origin 을 가를 필요가 없다 — 둘 다 "서버가 검사를 끝내고 쓴 것" 이다
- `RoomConnection` 에 `setState` 를 더하지 않고 이 메서드만 `StatefulConnection` 을 받는다 — `docRoomCore.test.ts`·F-502 `docRoomComments.test.ts` 의 가짜 연결을 고치지 않으려고. partyserver `Connection` 은 `setState` 를 갖는다

### 4.3 속도 한도 — 연결 상태에 둔다

- **어디에**: 연결 상태의 `commentRate` 칸(`{ start, count }`) — `setState` 로 병합해 쓴다. WebSocket 첨부라 **hibernation 을 넘긴다**(t4). DO 메모리에 두면 방이 잠들 때마다(연결이 조용하면 잠든다) 창이 비어, "30개 보내고 잠들 때까지 기다리기" 를 되풀이해 한도를 우회할 수 있다
- **방식: 고정 창.** `start` 부터 60,000ms 가 지났으면 `start = now`, `count = 0` 으로 새로 연다. `count` 를 1 올린 뒤 `COMMENT_OPS_PER_MINUTE`(30, F-501) 을 넘으면 `rate_limited`. 거절된 메시지도 센다
- 미끄러지는 창(최근 30개 시각 목록)을 쓰지 않는 이유: 첨부에 숫자 30개(약 450 B)를 싣게 된다. 첨부 크기 상한은 **이 세션에서 확인하지 않았다** — 칸을 두 숫자(약 40 B)로 둔다
- **알려진 한계**: 창 경계를 끼면 2초 안에 최대 60개가 들어간다. 연결을 새로 열면 새 창이다(연결은 Worker 입구에서 세션·권한을 다시 보므로 공짜가 아니다)
- **edit·소유자 연결의 명령에도 같은 한도**를 건다 — 명령을 쓰는 연결이 누구든 같은 입구다. 정직한 edit 클라이언트는 명령을 쓰지 않는다(개요 Q3)
- `/api` 분당 120(F-2026)과 하루 5,000(F-2024)은 소켓 메시지에 걸리지 않는다. 명령이 쓴 항목은 F-502 스냅숏 batch 의 하루 +1 에 묻어 간다(개요 3.8)

- 스레드 삭제가 남의 답글을 함께 지우는 것은 개요 2.4 그대로다(F-502 3.3 1단계와 같은 판정)

- `mentions` 를 접근 집합으로 거르지 않는다 — 알림을 만들 때 F-502 가 거른다(F-502 6.2). 본문의 `@이메일` 은 그대로 남는다(개요 3.6)
- **쓰기와 응답의 순서**: `doc.transact` 가 끝나는 순간 y-partyserver 의 `update` 처리기가 모든 연결에 갱신을 보낸다(동기). 응답은 그 뒤에 보낸다. 그래서 **보낸 연결은 ack 를 받기 전에 그 항목을 Yjs 로 이미 받았다**(O1 이 차례를 단언). 개요 4.4 "ack 가 오기 전이라도 Yjs 로 항목이 먼저 보이면 그 카드를 쓴다" 와 맞는다
- 응답은 보낸 연결에만 `host.sendCustom(conn, encodeCommentOpReply(…))` 로 간다

### 4.5 비용 (t5)

- 명령 한 건 1.3~1.6ms(댓글 499개, 60만 자, node). 대부분이 `groupCommentThreads`(500개 약 1ms)다. 연결 하나당 분당 30건이면 분당 최대 약 50ms. 한 번 걸어 표를 만드는 식의 최적화는 하지 않는다
- **workerd 에서 재지 않았다.** DO CPU 는 F-502 14장 H3 과 같이 배포 뒤 대시보드로 본다

### 4.6 F-502 와의 관계

- 명령이 쓴 항목도 F-502 의 `comments` 관찰이 `dirty` 에 넣는다 → F-502 스냅숏이 D1 `doc_comments` 행과 알림을 만든다. **이 명세는 D1 에 직접 쓰지 않는다**(F-502 11.1)
- 서버 origin 이라 F-502 사후 검사는 이 항목을 검사하지 않는다 — 명령 경로가 같은 규칙(모양·한도·권한·작성자)을 **쓰기 전에** 지켰기 때문이다
- 명령이 쓴 항목의 `author` 는 연결 상태(Worker 가 세션에서 찍은 값)라, F-502 의 알림 "보낸 사람" 이 서버가 확인한 값이 된다(개요 3.5 위조 방지)

## 5. DO RPC `importComments` (개요 4.6)

```ts
// worker/docRoomCore.ts
export type RoomCommentImport = { records: CommentRecord[]; user: { id: string; email: string }; docVersion: number }
export type RoomCommentImportResult =
  | { type: 'ok'; imported: number; orphaned: number }
  | { type: 'exists' }
  | { type: 'not_found' }
  | { type: 'unavailable' }
// class DocRoomCore
importComments(input: RoomCommentImport): Promise<RoomCommentImportResult>
// worker/docRoom.ts — class DocRoom
async importComments(input: RoomCommentImport): Promise<RoomCommentImportResult>   // core 로 넘기기만
// worker/docRoomRpc.ts
export async function importCommentsInRoom(env: Env, docId: string, input: RoomCommentImport): Promise<RoomCommentImportResult | null>  // 던지면 null
```

- 개요 3.9 의 결과 셋에 **`not_found` 를 더했다** — `writeText`(F-308)처럼 DO 가 불러오다 문서가 사라졌음을 알면(`roomGone`) API 가 404 로 답해야 한다. outbox(F-508)는 404 를 "그 항목 버림" 으로 다룬다

**순서** — `writeLive` 와 같은 틀이다:

1. `await host.ensureLoaded()` (RPC 는 partyserver 초기화를 거치지 않는다 — F-308 5.3)
2. `gone` → `not_found`. `!loaded` → `unavailable`
3. `await catchUp(docVersion)` 이 거짓 → `not_found` (Worker 가 본 D1 version 이 방과 다르면 따라잡는다 — 이관 본문은 방금 올린 D1 본문과 같다)
4. **`comments` `Y.Map` 의 크기가 0 이 아니면 `exists`** — D1 이 아니라 `Y.Map` 을 본다(F-502 11.1). 올바르지 않은 값만 남아 있어도 0 이 아니다
5. `restoreCommentEntries(content, records, { id: user.id, email: user.email })`(F-501 4.3) → `COMMENT_SERVER_ORIGIN` 트랜잭션 하나로 모두 `set`
6. `await runFlush(false, true)` — DO SQLite 에 갱신을 남기고(`flushOnce` 가 먼저 `persistPending`) D1 스냅숏을 한 번 돌린다. 느린 저장 검사를 건너뛰는 이유는 `writeLive` 와 같다(이 요청은 이미 쓰기 관문을 지났다). **스냅숏이 실패해도 결과는 `ok`** — 갱신은 DO 저장소에 남았고 F-502 의 다시 시도·다음 스냅숏이 D1 을 맞춘다
7. `{ type: 'ok', imported: entries.length, orphaned }` (`orphaned` 는 5번의 자리를 못 찾은 첫 댓글 수, 부모 없는 답글은 어디에도 세지 않는다 — F-501 4.3)

- **4번과 5번 사이에 `await` 가 없다.** 같은 문서에 이관이 두 번 겹쳐 와도(outbox 다시 보내기) 뒤의 것은 4번에서 `exists` 다
- 작성자·해결한 사람은 이관한 사용자, `mentions` 는 `[]` 가 된다(F-501 `importer`). 그래서 F-502 알림이 생기지 않는다 — 답글 알림의 받는 사람이 모두 작성자 자신이라 빠진다(F-502 6.2). O14 가 단언한다
- 이관 본문은 로컬(LF, 편집기 본문)과 같은 바이트로 올라가고 DO 본문도 LF(`toEditorText`)라 위치 힌트가 그대로 맞는다 — `reanchor` 1단계에서 끝난다(F-501 r7 "힌트가 맞을 때" 1MB·500개 0.1ms 이하)

### 6.3 `GET /api/docs/:id/comments/count` — `worker/commentsApi.ts`

- 1~3번은 6.2 와 같다
- 200 `{ total, open }` — D1 복사본(`doc_comments`) 기준: `total` = 그 문서의 **모든 행**(첫 댓글 + 답글), `open` = `parent_id` 가 `NULL` 이고 `resolved_at` 이 `NULL` 인 행(열린 스레드 수). 행이 없으면 `{ total: 0, open: 0 }`. 질의 한 번
- 쓰는 곳: 금고로 옮기기 확인의 `댓글 {N}개도 함께 지워집니다.`(F-509, `N = total`)

## 8. 경계 — 다른 명세가 이어받는 것

### 8.1 F-502 (이 명세 앞)

- F-502 가 둔 것을 **바꾸지 않는다**: 사후 검사 규칙, `known`·`dirty`·`anchorsDirty`, 스냅숏 batch 모양, 복원, 알림 만들기, `loadDocPeople`
- 이 명세가 더하는 것: `SERVER_ORIGINS` 에 `COMMENT_SERVER_ORIGIN` 한 개, `readConnState` 가 `'view'` 를 받음. F-502 사후 검사의 `CommentFixActor.role` 은 이미 `'view'` 를 포함한다(F-502 3.2) — view 연결은 Yjs 로 쓰지 못해 그 자리에 오지 않는다
- F-502 의 테스트 중 **상태 `role: 'view'` 를 "행위자 없음"(`null`)으로 기대하는 것**이 있으면 이 명세 뒤 깨진다. 2026-09-26 작업 트리의 `worker/docRoomComments.test.ts` 에는 없었다(`grep`, 가짜 `conn` 은 `'owner' | 'edit' | null`). 구현 때 한 번 더 `grep` 한다

### 8.2 F-506 (이 명세 뒤 — 명령 클라이언트)

F-506 이 알아야 할 서버 동작:
- view 소켓이 **첫 동기화 전에 `4403` `forbidden`** 으로 닫힐 수 있다 — 본인이 막혔거나 **소유자가 막혔을 때**(2.2). 클라이언트는 본인 막힘만 안다(F-2030 `accountBlocked`). 이때 읽기 전용 세션을 조용히 지금의 `view` 로 여는지는 F-506 이 정한다(개요 4.1 "첫 동기화 전 실패면 지금의 `view`")
- 연결 중 `4403` `revoked` — view 연결은 초대를 잃었거나 막혔을 때, edit 연결은 view 로 내려갔을 때(3장)
- 응답이 **없는** 명령이 있다(4.4 0·1번) — 기다림에 끝이 있어야 한다
- 같은 연결의 응답은 보낸 순서대로 온다. ack 는 그 항목의 Yjs 갱신 뒤에 온다(4.4)
- `comment-add`·`comment-reply` 를 같은 `id` 로 다시 보내면 `comment-ack`(쓰기 없음), `comment-delete` 의 없는 대상도 `comment-ack`
- 받은 문자열은 `parseDocRoomMessage` 와 `parseCommentOpReply` 둘 다에 넘긴다(4.1)
- 승격된 view 연결은 다시 붙기 전까지 읽기 전용이다(3장). 초대가 바뀐 것을 화면이 알면 다시 붙을지는 F-506 이 정한다

### Q1. A8 을 실제 y-partyserver 로 판정하려고 `vite.config.ts` 에 한 줄 — **기본값: 더한다**

- 이유: 읽기 전용의 막는 힘은 우리 코드가 아니라 y-partyserver 의 `readSyncMessage` 분기다(t1). 패키지를 올렸을 때 그 분기가 바뀌면 view 가 본문을 쓸 수 있게 된다 — 진짜 패키지로 도는 테스트(Y1)가 그것을 잡는다. 지금은 `partyserver` 가 `cloudflare:workers` 를 불러 node 에서 풀리지 않고, y-partyserver 가 외부화돼 있으면 `vi.mock('partyserver')` 가 먹지 않는다(t2). `server.deps.inline: ['y-partyserver']` 를 두면 된다. 기존 worker 테스트 588개가 그대로 통과했다(t3)
- **다른 안 — 설정을 두지 않는다**: Y1 을 빼고 R1(`isReadOnly` 가 view 에 참)만 판정한다. 소유 표에서 `vite.config.ts`·`docRoomReadOnly.test.ts` 가 빠진다. y-partyserver 를 올릴 때 `readSyncMessage` 를 사람이 다시 읽어야 한다 — 그 확인을 `specs/human-checks.md` 에 "y-partyserver 올릴 때" 항목으로 둔다

### Q2. 소유자가 막힌 문서의 view 초대자도 소켓을 막나 — **기본값: 막는다(`4403`)**

- 2.2: 지금 edit 초대자가 같은 경우 `4403` 이다. 막힌 문서는 DO 스냅숏이 멈추고 D1 복사본·알림이 밀린다
- **다른 안 — view 는 소유자 막힘을 보지 않는다**: 막힌 문서에서도 view 가 실시간 본문·댓글을 본다. 대신 그 사이 단 댓글은 D1 에 풀릴 때까지 안 들어가고 알림도 늦는다. 2.2 의 2번이 "본인 막힘만" 이 되어 `isWriteBlocked` 대신 `usageOf` 만 부른다. 3장 표의 한 줄이 바뀐다

### Q3. 점검 한 번의 D1 질의 수 — **기본값: 이 명세에서는 바꾸지 않는다**

- 3장: 연결 하나당 최대 5, 연결 10개면 51. D1 "호출당 50" 이 DO 호출에 걸리는지는 확인하지 않았다. 지금 edit 연결 10개에서도 같다
- **다른 안 — 점검 한 번에 연결 8개까지만 보고 나머지는 다음 주기로**: 질의가 41 이하로 묶인다. 대신 연결이 많은 방은 권한 회수가 주기 몇 번만큼 늦는다. `revalidateConnections(email)`(초대 바뀜 알림)은 한 사람 것이라 그대로 둔다. 초대가 많은 문서가 실제로 생기면 F-502 H3·이 명세 H4 의 대시보드를 보고 따로 명세로 연다

### Q4. 명령 속도를 edit·소유자 연결에도 거나 — **기본값: 건다**

- 4.3: 입구가 하나다. 정직한 edit 클라이언트는 명령을 쓰지 않으므로 영향이 없다
- **다른 안 — view 에만**: 4.4 3번에 "view 일 때만" 조건이 붙는다. edit 연결이 명령으로 분당 수천 건을 보내도 막지 않는다(그 사람은 이미 Yjs 로 무엇이든 쓸 수 있어 막는 이득이 작다)

### 기본값으로 정한 것 (승인 시 확정)

1. view 는 `X-WS-Role: view` 로 넘기고, `isReadOnlyState` 로 y-partyserver 가 Yjs 쓰기를 버린다. 상태를 못 읽으면 읽기 전용 — 2.2·2.3
2. 막힌 view(본인·소유자)는 입구에서 `4403 forbidden`, 연결 중이면 점검에서 `revoked` — 2.2·3장
3. view awareness 는 받기만, 보내는 것은 버림 — 2.4
4. 점검 규칙 표, 승격된 view 는 그대로 읽기 전용 — 3장
5. 명령 계약과 파서 넷, 16,384자 상한, 응답 없는 두 경우 — 4.1·4.4
6. 명령 처리는 동기 함수, 응답은 Yjs 갱신 뒤·보낸 순서대로 — 4.2·4.4
7. 속도 한도는 연결 상태의 고정 창(`commentRate`), 거절도 셈, 모든 연결 — 4.3
8. 검사 순서 표와 사유, 같은 `id` 다시 보내기·없는 대상 지우기는 ack — 4.4
9. 명령·이관 origin 은 `COMMENT_SERVER_ORIGIN` 하나, `SERVER_ORIGINS` 에 더함 — 4.2
10. `importComments` 순서, `Y.Map` 이 비었을 때만, 끝에 flush, 결과에 `not_found` — 5장
11. API 계약 타입은 `docComments.ts` 에, 다섯 경로의 판정 순서·오류 문자열, 이관 몸통 5,000,000 B, 읽음 몸통 8,192 B — 6장
