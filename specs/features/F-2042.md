# F-2042 부팅 목록 읽기 — 병렬화와 캐시 먼저 셸

작성일: 2026-09-26
상태: **사람 승인 — 받음 (2026-09-26). 사용자 답: Q1 = 캐시 먼저 셸도 같이 한다. Q2~Q7 기본값.** 사용자가 "부팅 API 병렬화" 진행을 정했다(2026-09-26 "ㄱㄱ", main 전달). 병렬화(3장)는 그대로 가는 결정이고, **사람이 정할 갈림길은 11장 Q1(캐시 먼저 셸을 이번에 같이 하나)** 하나다. 나머지 Q2~Q7 은 기본값이 있다
범위 확인: `specs/product.md` 8장(범위 밖)에 부팅 속도·목록 읽기가 없다. 비기능 표(234행 `성능`)는 "수치 기준 없음" 이라 막지 않는다
단위 판단: 작은 명세 하나. 저장소(`serverStore.list`·`get`)와 부팅(`App.tsx` `boot()`)이 함께 바뀌어야 뜻이 있다 — 저장소만 바꾸면 셸이 여전히 본문을 다 받을 때까지 기다리고, 부팅만 바꾸면 3.5 의 낡은 본문 문제가 열린 채 나간다. 구현은 `complex-implementer` 를 권한다(IndexedDB·네트워크 경쟁 조건, 측정 기준)

**경계 (동시에 쓰이는 명세와)**
- **F-2041(캐시 먼저 열기)**: 이 명세는 **부팅의 목록 경로** — `boot()` 에서 저장소를 연 뒤부터 `setBootPhase('ready')` 와 그 뒤 목록 맞추기까지, 그리고 `serverStore` 의 `list()`·`listCached()`·본문 받기 모음(3.3)을 가진다. **문서 열기 경로**(`openLoad` effect, `docPath`, 열 때 무엇을 먼저 보여 주나)는 F-2041 몫이다. 겹치는 한 자리는 `serverStore.get(id)` 이다 — 이 명세는 "진행 중인 목록 맞추기가 그 문서 본문을 새로 받는 중이면 기다린다"(3.5) 한 규칙만 더한다. F-2041 이 열기에서 캐시를 먼저 보이기로 정하면 3.5 는 F-2041 이 바꾸고, 그때 3.5 의 A 번호(U5)도 F-2041 이 넘겨받는다
- **F-2019(볼트 가져오기)**: 구현 에이전트가 작업 트리에서 `App.tsx` 를 고치는 중이다(2026-09-26). 이 명세가 인용한 `App.tsx` 줄 번호는 **커밋 `b7701d6` 기준**이다 — 작업 트리 줄 번호와 다를 수 있으니 이름으로 찾는다

## 3. 서버 저장소 `list()` 와 본문 받기

### 3.1 `/api/shared` 동시 시작 — 규칙

- `list()` 는 들어오자마자 `api.getShared()` 를 시작하고, `api.listDocs()` 결과·재조정과 상관없이 마지막에 그 결과를 기다린다
- 실패 처리는 지금과 같다 — 어떤 실패든 공유받은 목록을 빈 배열로 둔다(F-212 2.4). 먼저 시작한 요청이 거부돼도 처리되지 않은 거부(unhandled rejection)가 나지 않게 한다
- `/api/docs` 가 401·네트워크 실패여도 `/api/shared` 결과는 지금처럼 따로 쓴다(지금도 두 요청의 실패는 서로 독립이다)

### 3.2 본문 동시 받기 — 규칙

- 재조정 루프는 **받을 문서 id 목록만 모은다**(지금처럼 보낼 목록에 있는 문서·`delete-all` 로 빠진 문서·캐시 버전이 같은 문서는 뺀다). 모은 뒤 받기를 동시에 최대 `BODY_FETCH_CONCURRENCY` 개로 돌린다
- 받는 순서는 `/api/docs` 응답 순서(서버가 `updatedAt` 내림차순으로 준다) — 최근 문서가 먼저 캐시에 들어간다
- 한 문서가 실패하면(네트워크·404·5xx·그 밖) 그 문서만 건너뛴다. 지금 주석 "다음 기회에 다시 시도한다" 와 같다. 나머지는 계속 받는다
- `list()` 는 모든 받기가 끝나거나 실패한 뒤 캐시를 읽어 돌려준다 — 반환 계약은 그대로다

```ts
// src/storage/serverStore.ts — 계약
export const BODY_FETCH_CONCURRENCY = 6
```

### 3.3 본문 받기 모음 — 같은 문서를 두 번 받지 않는다

부팅의 뒤 맞추기(4장) 동안 금고 열림(`App.tsx` `e2ee?.status` effect), 검색 인덱스, 다른 탭 신호(`resyncFromStore`)가 `list()` 를 또 부를 수 있다. 캐시 먼저 셸이 되면 이 겹침이 흔해진다

- 서버 저장소 안에 "지금 받고 있는 본문" 모음을 둔다. 키는 **문서 id + 서버 버전**(`/api/docs` 요약의 `version`)
- 같은 키로 받기가 진행 중이면 새로 요청하지 않고 그 결과를 같이 기다린다. 버전이 다르면(그 사이 서버가 또 바뀜) 따로 받는다
- 받기가 끝나면(성공·실패 모두) 모음에서 뺀다

### 3.4 캐시 쓰기 직전 다시 보기 — 내 편집을 덮지 않는다

지금 코드는 루프 **앞에서** 보낼 목록을 한 번 읽어 `pendingDocIds` 를 만들고, 본문을 받은 뒤 그대로 `cache.putDoc` 한다. 본문을 받는 사이 사용자가 그 문서를 고치면(캐시에 먼저 쓰고 보낼 목록에 넣는다, F-207 2.3) 받은 서버 본문이 방금 쓴 캐시를 덮는다. 캐시 먼저 셸은 사용자가 목록 맞추기 도중에 편집할 수 있게 하므로 이 틈이 커진다

- 받은 본문을 캐시에 쓰기 **직전에** 그 문서의 보낼 목록 항목을 다시 읽는다. 항목(`createDoc`·`updateDoc`·그 밖 `docIdOf` 가 그 id 를 돌려주는 모든 종류)이 생겼으면 쓰지 않는다
- 캐시 행의 `version` 이 루프 앞에서 본 값과 달라졌어도 쓰지 않는다(그 사이 보내기가 끝나 캐시가 더 새 버전을 받았다)
- 이 검사는 `list()` 의 모든 호출에 적용된다(부팅만이 아니다)

### 3.5 `get(id)` — 진행 중인 목록 맞추기를 기다린다

캐시 먼저 셸에서는 셸이 뜬 뒤에도 캐시 본문이 서버보다 낡았을 수 있다. 실시간 경로(F-305)는 본문을 방 Doc 첫 동기화에서 채우므로 상관없지만, `openLoad === 'store'` 경로(금고 문서, `pending`, `fallback`)는 `store.get(id)` 로 캐시 본문을 읽는다(`App.tsx` "문서를 열 때 저장소 본문을 1회 읽어" effect). 지금은 부팅이 본문을 다 받은 뒤 ready 라 이 문제가 없다 — **이 명세가 만드는 틈이므로 이 명세가 막는다**

- `list()` 가 진행 중일 때 `get(id)` 는
  1. 그 `list()` 의 `/api/docs` 요약이 아직 안 왔으면 올 때까지 기다린다. 단 **최대 `GET_WAIT_FOR_LIST_MS`**. 넘으면 기다리지 않고 캐시를 돌려준다(지금 오프라인 동작과 같다)
  2. 요약이 왔고 그 id 가 3.2 의 받을 목록에 있으면, 동시 상한과 상관없이 **그 문서 받기를 곧바로 시작**하고(3.3 모음에 이미 있으면 그것을) 기다린 뒤 캐시를 읽는다
  3. 받을 목록에 없으면 곧바로 캐시를 읽는다
- 진행 중인 `list()` 가 없으면 지금과 같다(캐시에 있으면 캐시, 없으면 서버)

```ts
// src/storage/serverStore.ts — 계약
export const GET_WAIT_FOR_LIST_MS = 3_000
```

3,000ms 인 까닭: 측정 조건의 요청 지연(300ms)의 10배. 이보다 오래 걸리는 연결이면 사용자는 서버 본문보다 캐시 본문이라도 먼저 보는 편이 낫다 — 오프라인 부팅이 이미 캐시 본문으로 연다(F-207 2.6). 11장 Q4

### 3.6 `listCached()` — 계약

```ts
// src/storage/serverStore.ts — ServerStore 타입에 더한다
listCached(): Promise<{ docs: Doc[]; folders: Folder[] }>
```

- 네트워크를 쓰지 않는다. `cache.getDocs(userId)`·`cache.getFolders(userId)` 를 읽어 `list()`·`listFolders()` 가 캐시에서 돌려주는 것과 **같은 모양**으로 돌려준다(문서는 `role: 'owner'`, `updatedAt` 내림차순, 폴더는 `toFolder`). 공유받은 문서는 없다(캐시하지 않는다, F-212 2.4)
- 보낼 목록 개수 표시(`refreshPending`)는 부르지 않는다 — 읽기만 한다
- `withE2ee`(`src/e2ee/e2eeStore.ts`)는 안쪽 저장소에 `listCached` 가 있으면 문서를 `decode` 로 풀어 내보낸다. `refreshDocFromServer` 를 감싸는 자리(`if (serverInner.refreshDocFromServer)`)와 같은 방식. 폴더는 그대로 넘긴다(`listFolders` 도 그대로 넘긴다)
- `Store` 공용 타입(`src/types.ts`)은 넓히지 않는다. `idb`·`memory` 저장소는 `list()` 자체가 로컬이라 필요 없다

### 3.7 쓰기 한도·관문과의 관계 (확인함)

- `worker/writeGate.ts` `isWriteRoute` 는 `GET` 이면 곧바로 `false` 다. `WRITE_LIMITER`(분당 120, `wrangler.jsonc`)와 하루 한도는 **읽기에 걸리지 않는다**. 이 명세가 늘리는 것은 `GET` 동시성뿐이라 429 를 새로 부르지 않는다
- 요청 **수**는 바뀌지 않는다(측정: 본문 요청 20 → 20, 54 → 54). D1 읽기 양도 같다
- `docsApi.getDoc` 는 429 를 따로 가르지 않는다 — 만약 읽기에 429 가 오면 `other` 로 떨어져 3.2 대로 그 문서만 건너뛰고 다음 `list()` 때 다시 받는다
- 보낼 목록(outbox) 보내기는 지금처럼 한 번에 하나씩이다. 이 명세는 보내기 순서를 건드리지 않는다

## 4. 부팅 — 캐시 먼저 셸

### 4.1 캐시 먼저 셸을 쓰는 조건 — `canShowCachedShell`

```ts
// src/app/bootList.ts — 계약
export function canShowCachedShell(input: {
  storeKind: 'idb' | 'memory' | 'server'
  accountState: 'in' | 'out' | 'offline'
  hash: HashRoute            // parseHash(location.hash) 결과
  cachedDocIds: ReadonlySet<string>
}): boolean
```

아래를 **모두** 만족할 때만 `true`

| 조건 | 까닭 |
| --- | --- |
| `storeKind === 'server'` 이고 `accountState === 'in'` | `idb` 는 `list()` 가 이미 로컬이다. `offline` 은 지금도 `list()` 가 곧바로 네트워크 실패로 캐시를 돌려준다 |
| `cachedDocIds.size > 0` | 캐시가 비었으면 새 기기·첫 로그인이다 — 서버 목록 없이 안내 문서 판단(4.4)을 할 수 없다 |
| 해시가 `share`(`#/s/…`) 가 아니다 | 공유 링크 화면은 `openSharedFragment(fragment, metaList)` 에 목록을 넘긴다 — 지금 목록 그대로 넘기려면 서버 목록이 필요하다 |
| 해시가 `doc` 이면 그 id 가 `cachedDocIds` 에 있다 | 없으면 다른 기기에서 만든 문서이거나 공유받은 문서다. 캐시로 먼저 판단하면 `문서를 찾을 수 없습니다.` 를 잘못 띄운다 |
| 해시가 `map` 이고 `docId` 가 있으면 그 id 가 `cachedDocIds` 에 있다 | 같은 까닭(지도 중심 문서, F-292 6.1) |

`none`·`help`·`shares`·문서 id 없는 `map` 은 캐시 먼저로 간다. `md.startScreen === 'last'` 의 `md.lastDocId` 는 조건에 넣지 않는다 — 이 브라우저에서 연 문서라 캐시에 있고, 없으면 지금도 `resolveInitialDoc` 가 알림 없이 다른 문서로 넘어간다

`false` 면 **지금 순서 그대로**(3장 병렬화만 적용) 기다린 뒤 ready 한다

### 4.2 순서 — 규칙

`boot()` 에서 `migrateLocalIfNeeded` 뒤, 지금 `listFolders()`·`list()` 를 부르는 자리에서 갈린다

1. `appStore.listCached()`(3.6, `withE2ee` 를 거친 것)로 캐시 문서·폴더를 읽는다
2. `canShowCachedShell` 이 참이면
   - 캐시 폴더·문서(본문 뺀 것)로 `setFolders`·`setDocs`, 지금 1703~1770행이 하는 처음 화면 고르기(해시·`md.startScreen`)를 **캐시 목록으로** 한 뒤 `setBootPhase('ready')`
   - 첨부 GC 예약(`scheduleAttachmentGc`)은 지금처럼 한다 — 그 자체가 나중에 `list()` 를 부른다
   - 그 다음 **뒤 맞추기**: `Promise.all([appStore.listFolders(), appStore.list()])` 를 시작하고, 끝나면 4.3 규칙으로 반영한다. 뒤 맞추기 시작 때 캐시 목록의 id 집합을 **스냅샷**으로 잡아 둔다
3. 거짓이면 지금 순서(안내 문서 판단 포함) 그대로

ready 전에 네트워크를 기다리는 것은 1번(`/api/me`)뿐이다. 측정 시제품 B 에서 471~505ms(그 중 300ms 가 `/api/me` 지연)

### 4.3 뒤 맞추기 결과 반영 — `mergeBootList`

기존 `resyncFromStore`(다른 탭 신호, F-296 7.2)가 같은 일을 한다 — 폴더 통째 교체, 문서 목록 교체(`keepLiveTitle`), 열린 문서가 사라졌으면 `deletedElsewhereId`, 금고 여부가 바뀌었으면 `restartDocSession`. 뒤 맞추기도 이 규칙을 따르되 **두 가지를 다르게** 한다

```ts
// src/app/bootList.ts — 계약
// DocMeta 는 App.tsx 지역 타입이라 id·updatedAt 만 요구하는 제네릭으로 둔다
export function mergeBootList<T extends { id: string; updatedAt: number }>(input: {
  snapshotIds: ReadonlySet<string>   // 4.2 에서 캐시 목록으로 셸을 띄울 때의 문서 id
  current: readonly T[]              // 반영 시점의 docs state
  result: readonly T[]               // 뒤 맞추기 list() 결과(본문 뺀 것, keepLiveTitle 적용 전)
}): { docs: T[]; removedIds: string[] }
```

- **빼는 것은 "스냅샷에 있었는데 결과에 없는" id 뿐이다.** 스냅샷 뒤 이 탭에서 생긴 문서(새 문서·가져오기·충돌 사본)는 결과에 없어도 남긴다. `resyncFromStore` 는 결과에 없는 것을 다 빼므로 그대로 쓰면 방금 만든 문서가 사라지고, 그 문서가 열려 있으면 삭제 알림이 잘못 뜬다
- 결과에 있는 문서는 결과 값으로 바꾸고(제목은 이후 `keepLiveTitle` 를 거친다), `current` 에만 있는 스냅샷 밖 문서는 그대로 두고, `updatedAt` 내림차순으로 정렬한다
- `removedIds` 에 지금 열린 문서가 있으면 `setDeletedElsewhereId` — 문구는 6장
- 금고 여부가 바뀐 열린 문서는 `resyncFromStore` 와 같은 조건으로 `restartDocSession`
- **늦게 시작한 목록이 먼저 반영됐으면 버린다.** 뒤 맞추기가 도는 동안 금고 열림 effect(`e2ee?.status`) 가 `list()` 를 다시 불러 먼저 반영할 수 있다. 그 결과는 금고 키가 있을 때 `decode` 한 것이고 뒤 맞추기 결과는 키가 없을 때 한 것일 수 있어, 늦게 도착한 뒤 맞추기가 제목을 잠긴 모양으로 되돌린다. 목록 반영마다 **시작 순번**을 붙이고, 이미 반영된 것보다 먼저 시작한 결과는 반영하지 않는다(버린 결과의 삭제 판단은 나중 결과가 대신한다). 순번 비교는 `mergeBootList` 밖 App 쪽 규칙이며 B3 가 순수 함수로 확인할 수 있게 `bootList.ts` 에 비교 함수를 함께 둔다(이름은 구현이 정한다)

### 4.4 첫 실행 안내 문서

- 캐시 먼저 길에서는 안내 문서 판단(F-111 3.1, F-207 2.6 "서버 문서가 0개이고 …")을 **하지 않는다**. 캐시에 문서가 있다는 것은 이 브라우저에서 이 계정으로 서버 목록을 받은 적이 있다는 뜻이라 "첫 실행" 이 아니다
- 달라지는 경우 하나: 다른 기기에서 문서를 모두 지운 뒤 이 브라우저를 열고, 이 브라우저의 `md.firstRunDone` 이 비어 있으면 지금은 안내 문서를 만들지만 이 명세 뒤에는 만들지 않는다(빈 상태 S-2 가 뜬다). 11장 Q7

### 4.5 공유받은 문서

- 캐시 먼저 길의 셸에는 공유받은 문서가 없다. 뒤 맞추기가 끝나면 생긴다(`/api/shared` 는 3.1 대로 `/api/docs` 와 동시에 나가므로 ≈ 1왕복 뒤)
- 해시가 공유받은 문서를 가리키면 4.1 에서 캐시에 없으므로 기다리는 길로 간다 — 지금과 같다

### 4.6 금고 문서

- 부팅 시점엔 금고 키가 없다(`useE2ee` 는 ready 뒤에 시작한다). 캐시 먼저 길도 `withE2ee` 를 거친 `listCached()` 를 쓰므로 금고 문서는 지금 부팅과 같이 잠긴 모양(`e2ee: 'locked'`, 제목 빈 글자)으로 먼저 보인다
- ready 가 앞당겨지므로 `useE2ee` 도 뒤 맞추기와 동시에 돈다. 금고가 열리며 부르는 `list()` 와 뒤 맞추기의 겹침은 3.3(본문 모음)과 4.3(늦게 시작한 것 버림)이 처리한다

### 4.7 오류

- 뒤 맞추기의 `list()` 가 네트워크로 실패하면 지금처럼 캐시를 돌려주고 `syncState.online = false` 가 된다 — 결과(=캐시)를 4.3 대로 반영한다. 새 알림은 없다
- `listCached()`·뒤 맞추기가 예외를 던지면(IndexedDB 오류 등) 셸은 캐시 목록 그대로 두고 `console.error('boot_resync_failed', err)` 한 줄만 남긴다. 사용자에게 새 알림은 띄우지 않는다 — 저장소 쓰기 오류는 이미 기존 알림 경로가 따로 있다
- `listCached()` 가 던지면 캐시 먼저를 포기하고 지금 순서로 간다

### 4.8 `/api/me` 와 `/api/docs`·`/api/shared` 의 의존 관계 (확인함)

## 8. 수용 기준 — e2e (`e2e/bootList.spec.js`)

### 8.1 `fakeServer` 조종 함수 — 계약

```js
// e2e/fixtures/fakeServer.js 반환 객체에 더한다
setLatency(ms)      // 이후 모든 /api/** 응답을 ms 만큼 늦춘다. 0 이면 끈다
```

## 11. 열린 질문

### Q1 캐시 먼저 셸을 이번에 같이 하나 — **사람 결정 필요**

- **기본: 한다(4장).** 까닭: 측정에서 지금 부팅의 대부분은 본문 받기이고(0.2), 병렬화만으로는 바뀐 문서 20개일 때 7,310 → 2,002ms 에 그친다. 캐시 먼저 셸은 505ms. 캐시(`md-remote`)는 F-207 부터 문서 전체를 들고 있고 오프라인 부팅이 이미 그것으로 연다
- 다른 안 (a) **병렬화만(3장만)**: 4장·`bootList.ts`·A1~A7 이 빠지고, 3.5 도 필요 없어진다(부팅이 본문을 다 받은 뒤 ready). 변경이 `serverStore.ts` 한 파일로 줄고 위험이 작다. 대신 새로고침 체감은 "본문 수 ÷ 6 × 왕복" 만큼 남는다
- 다른 안 (b) 캐시 먼저 + 뒤 맞추기 중 표시(사이드바 위 얇은 진행 표시 등): 새 UI 상태와 문구가 생겨 `ia.md`·`design.md` 가 바뀐다. 기본은 표시 없음

### Q2 `/api/me` 를 기다리지 않고 목록 요청을 앞질러 보내나

- **기본: 안 한다.** 까닭: 저장소 선택·캐시 사용자 id·차단 멈춤이 `/api/me` 에 걸린다(4.8). 캐시 먼저 길에서는 ready 전에 목록 요청이 필요 없으므로 이득이 없다. 기다리는 길(캐시 없음·해시가 캐시 밖)에서만 한 왕복을 줄인다 — **측정하지 않았다**
- 다른 안: `md.account` 저장값이 있으면 `/api/me` 와 동시에 `/api/docs`·`/api/folders`·`/api/shared` 를 보내고, `/api/me` 결과의 id 가 같을 때만 그 응답을 저장소에 넘긴다. `openStore`·`createServerStore` 에 "먼저 받은 응답" 입력이 생기고, 다르면 버리는 규칙과 그 테스트가 늘어난다. 캐시 먼저 셸에서 `/api/me` 조차 기다리지 않는 안은 저장소를 바꿔야 할 때 새로고침이 필요해 F-207 2.6 "한 번만 고른다" 를 어긴다 — 권하지 않는다

### Q3 본문 동시 개수

- **기본: 6.** 측정(0.2) 4개 2,341 / 6개 2,002 / 8개 1,774ms(바뀐 문서 20개). 6 은 Chrome 의 HTTP/1.1 호스트당 연결 수와 같아 로컬 `vite preview`·`wrangler dev`(HTTP/1.1)에서도 줄 서지 않는다 — 이 연결 수는 일반 지식이고 이번에 확인하지 않았다. 운영(`rawdoc.app`)이 HTTP/2 로 붙는지도 확인하지 않았다
- 다른 안 8: 측정상 −230ms. 요청 수가 같아 한도에는 영향이 없지만, 한 사용자가 D1 에 한꺼번에 거는 읽기가 늘어난다. 상수 하나라 나중에 바꾸기 쉽다

### Q4 `get()` 이 목록을 기다리는 상한

- **기본: 3,000ms**(3.5). 넘으면 캐시 본문
- 다른 안 "상한 없음": 느린 연결에서 금고·`fallback` 문서 열기가 목록 요약이 올 때까지 멈춘다. 다른 안 "기다리지 않음": 3.5 가 없어져 셸 직후 연 금고·`fallback` 문서가 낡은 캐시 본문으로 열리고, 그 상태로 편집하면 저장 때 409 → 충돌 사본(F-207 2.4)이 생긴다

### Q5 셸 직후 서버에만 있는 문서로 해시를 바꿀 때

- **기본: 막지 않는다.** 뒤 맞추기 전 ≈ 1왕복 동안 `문서를 찾을 수 없습니다.` 가 잘못 뜰 수 있다. 사용자가 그 사이에 주소창을 직접 고치거나 다른 기기의 링크를 붙여 넣는 경우만 해당한다
- 다른 안: `handleHashChange` 가 뒤 맞추기가 진행 중이면 그것을 기다린 뒤 판단한다. `App.tsx` 해시 처리 effect 가 이 명세 소유에 들어오고 F-2041(열기 경로)과 겹친다

### Q6 서버에 여러 문서를 한 번에 받는 API

- **기본: 더하지 않는다.** 사용자 결정 범위가 "부팅 API 병렬화" 이고, 서버 라우트·`worker/docs.ts`·CLI 계약(`/v1/`)·rate limit 판단이 함께 바뀐다
- 다른 안: `GET /api/docs?ids=…` 또는 `POST /api/docs/batch`(읽기지만 `POST` 면 `isWriteRoute` 가 쓰기로 셈 — `GET` 이어야 한다). 바뀐 문서 20개가 한 왕복이 된다. 캐시 먼저 셸이면 본문은 이미 ready 뒤라 체감 이득이 작다 — Q1 을 (a) 로 정할 때만 다시 볼 만하다

### Q7 캐시 먼저 길에서 첫 실행 안내 문서

- **기본: 판단하지 않는다(4.4).** 달라지는 경우는 "다른 기기에서 전부 지움 + 이 브라우저 `md.firstRunDone` 빈 값" 하나뿐이고, 그때 빈 상태 S-2 가 뜬다
- 다른 안: 뒤 맞추기 결과가 0개이고 `md.firstRunDone` 이 비었으면 그때 안내 문서를 만든다. ready 뒤에 문서가 생겨 사용자가 이미 누른 `새 문서` 와 순서가 엇갈릴 수 있다
