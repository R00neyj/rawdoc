## 2. 무엇이 문제인가

`ia.md` 3.9 2번은 모드를 바꿔도 스크롤 위치가 유지된다고 못박고 있다. 실제로는 두 가지가 어긋난다.

1. **보기 → 편집 복귀가 문서 맨 위로 간다.** 게다가 갈 때마다 값이 달라 사용자 눈에는 "위로 갈 때도 있고 아래로 갈 때도 있다" 로 보인다
2. **보기 화면이 늘 문서 맨 위에서 시작한다.** 편집 화면 어디를 보고 있었든 상관없다

편집 ↔ 원문은 멀쩡하다 (3.2 실측 B).

## 4. 원인 (코드와 라이브러리 소스로 확정)

### 4.1 보기 → 편집 복귀가 맨 위로 가는 이유

`src/app/App.tsx` 2453~2458행은 동기 함수다.

```ts
function changeViewMode(mode: string) {
  const v = mode as 'live' | 'raw' | 'view'
  setViewMode(v)                      // React 상태 — 이 줄에서 DOM 이 바뀌지 않는다
  setPref('md.viewMode', v)
  editorRef.current?.setViewMode(v)   // 여기서 DOM 은 아직 "이전 렌더" 그대로다
}
```

React 19 는 이벤트 핸들러 안의 `setState` 를 모아 핸들러가 끝난 뒤에 커밋한다. 그래서 세 번째 줄이 도는 시점의 화면은 **바뀌기 전 모드**다.

- 편집 → 보기: `.editor-slot` 이 아직 보이므로 `setViewMode` 안의 `view.scrollSnapshot()`(`createEditor.ts` 481행)이 제대로 찍히고 바로 적용된다. 문제 없음
- 보기 → 편집: `.editor-slot` 이 아직 `hidden`(2671행) 이라 `display: none` 이고 `scrollDOM.clientHeight === 0`, `scrollTop === 0` 이다

숨겨진 상태에서 찍은 스냅샷이 어떻게 되는지는 라이브러리 소스로 확인했다.

| 위치 | 내용 |
| --- | --- |
| `index.js` 8676~8680행 | `scrollSnapshot()` = `scrollIntoView.of(new ScrollTarget(cursor(ref.from), 'start', 'start', ref.top - scrollTop, scrollLeft, true))`, `ref = viewState.scrollAnchorAt(scrollTop)` |
| `index.js` 6646~6648행 | `scrollAnchorAt(off)` = `lineBlockAtHeight(off + 8)` — `scrollTop` 이 0 이면 **문서 첫 줄**이 나온다 |
| `index.js` 6379~6381행 | `editorHeight = view.scrollDOM.clientHeight` — 숨겨져 있으면 0 |
| `index.js` 8219~8222행 | `if (this.viewState.editorHeight) { if (scrollTarget) { docView.scrollIntoView(scrollTarget); scrollTarget = null } }` — **높이가 0 이면 소비하지 않고 남겨 둔다** |
| `index.js` 7994행 | 다음 `update()` 가 `viewState.scrollTarget` 을 그대로 이어받는다 |
| `index.js` 3429~3435행 | `isSnapshot` 이면 `scrollDOM.scrollTop = viewState.lineBlockAt(head).top - yMargin` |

즉 **문서 맨 위를 가리키는 스냅샷이 보류로 남아 있다가, React 가 `hidden` 을 뗀 뒤 첫 measure 에서 적용된다.** 적용값이 정확히 0 이 아니라 144 인 것은 그 뒤 8227~8241행의 스크롤 앵커 보정이 한 번 더 도는 탓이고, 어느 쪽이든 "문서 맨 위" 라는 결과는 같다.

### 4.2 `scrollSnapshot` 효과를 나중에 dispatch 해도 되는가 (지시 1의 확인 항목)

**된다.** `scrollIntoView` 는 `StateEffect.define({ map: (t, ch) => t.map(ch) })`(`index.js` 1357행)로 만든 평범한 상태 효과이고, 값인 `ScrollTarget`(1332~1356행)은 `range`·`y`·`x`·`yMargin`·`xMargin`·`isSnapshot` 만 들고 있다. 시간이나 뷰를 붙잡지 않는다. 적용부(3429~3433행)가 `viewState.lineBlockAt(head)` 를 **적용 시점에** 다시 읽으므로 그 사이 높이가 바뀌어도 알아서 따라간다. 라이브러리 문서 주석(8664~8670행)도 "The effect should be used with a document identical to the one it was created for … You can map the effect to account for changes" 라고만 제한한다 — 모드 전환은 문서를 바꾸지 않으므로 이 제한에 걸리지 않는다.

**그럼에도 이 명세는 효과를 보관하지 않는다.** 이유는 6.1 에 적는다. 문제는 "나중에 dispatch 해도 되는가" 가 아니라 "**보이지 않을 때 찍으면 안 된다**" 였다.

### 4.3 보기 화면이 늘 맨 위인 이유

`App.tsx` 2693~2706행이 `<Viewer key={currentDocId}>` 를 `viewMode === 'view'` 일 때만 그린다. 모드를 바꿀 때마다 마운트·언마운트되므로 `scrollTop` 은 언제나 0 에서 시작한다. 그리고 편집기 위치를 보기 위치로 옮길 근거가 되는 원문 줄 정보가 `renderMarkdown` 출력에 **제목(h1~h3)밖에 없다**(3.3 실측). 제목이 없는 문서는 아예 맞출 수가 없다.

## 5. 설계 결정

### 5.1 기준값은 "**화면 맨 위에 보이는 원문 줄**" 한 숫자다 (지시 1)

CM6 `scrollSnapshot` 효과를 보관했다가 나중에 dispatch 하는 길은 쓰지 않는다.

| 근거 | |
| --- | --- |
| 말이 이미 정해져 있다 | `ia.md` 3.9 2번과 `F-147` 2장·A2 가 쓰는 말이 "스크롤 위치(보이는 첫 줄)" 다. 사람이 판정할 수 있는 단위이고 그대로 수용 기준이 된다 |
| 양방향이라 숫자여야 한다 | 보기 → 편집 방향의 출발지는 HTML 뿐이다. CM6 효과를 만들 재료가 없다. 한 방향만 효과, 한 방향만 숫자로 쓰면 규칙이 둘이 된다 |
| 잃는 게 없다 | `scrollSnapshot()` 이 속으로 하는 일이 바로 "맨 위 줄의 문서 위치 + 잘린 양" 이다(4.2 표). 같은 것을 우리가 계산할 뿐이다 |
| 숨김 문제를 구조적으로 피한다 | 숫자는 "읽을 수 있을 때만 읽는다" 가 명시적이다. 효과는 찍히는 것 자체를 막아야 하는데 그게 5.3 의 가드다 |

**기준값 = 분수 1-based 원문 줄 번호 하나.** 정수부는 줄 번호, 소수부는 그 줄(또는 그 줄이 속한 블록) 안에서 위로 얼마나 잘렸는지의 비율이다. 예: `641.78` = 641번째 줄이 자기 높이의 78% 만큼 위로 잘린 채 화면 맨 위에 걸쳐 있다. 3.4 에서 확인했듯 잘린 양이 63px까지 가므로 소수부가 필요하다.

### 5.2 언제 찍고 언제 되돌리는가 (지시 2)

**찍는 자리 — `App.tsx` `changeViewMode` 의 맨 앞.** 4.1 에서 확인한 대로 이 자리의 DOM 은 아직 "떠나는 화면" 이다. 편집·원문에서 떠나면 편집기에서, 보기에서 떠나면 `viewerRef` 가 가리키는 `.viewer` 에서 읽는다. 둘 다 대칭이고, `useLayoutEffect` 정리 함수(cleanup)를 쓸 필요가 없다.

**되돌리는 자리 — `App.tsx` 의 새 `useLayoutEffect`, 의존성 `[viewMode, viewerHtml, currentDocId]`.**

- `useLayoutEffect` 여야 한다. 같은 커밋에서 `.editor-slot` 의 `hidden` 이 이미 떨어져 있고, 페인트 전이라 사용자 눈에 한 프레임의 튐이 보이지 않는다. passive `useEffect` 는 페인트 뒤라 문서 맨 위가 한 번 보였다 사라진다
- 선언 위치는 1100~1104행의 `setBreadcrumb` layout effect 바로 **뒤**. 그래야 줄 번호·테마·들여쓰기 재구성이 모두 끝난 높이로 맞춘다

**되돌린 뒤 rAF 2회 실측 보정 — 필요하다. 양쪽 다 한다.**
편집 쪽은 `scrollToHeading`(`createEditor.ts` 583~596행)이 이미 같은 이유로 그렇게 한다. 화면 밖 줄 높이는 추정값이라(3.1 의 42,926 ↔ 40,270) 한 번에 맞지 않는다. 보기 쪽도 같은 모양으로 1회 보정한다 — 폰트 적용·CSS 레이아웃 확정이 한 프레임 뒤에 오는 경우를 흡수한다.

전체 순서:

```
클릭
 └ changeViewMode
    1. 기준값 읽기 (아직 옛 화면)         ← 5.1
    2. 보기로 가면 viewerHtml 을 여기서 만든다 ← 5.2a
    3. setViewMode / setPref
    4. editorRef.setViewMode(v)          ← 5.3 가드가 걸린 채로 돈다
 └ React 커밋 (hidden 이 붙거나 떨어진다)
 └ useLayoutEffect 복원
    5. 보기면 scrollViewerToAnchor, 아니면 handle.scrollToAnchor
    6. rAF ×2 뒤 실측 보정 1회
```

**5.2a — 보기로 갈 때 변환을 `changeViewMode` 안에서 한다.** 지금은 1048~1054행의 passive effect 가 변환하므로, 복원 layout effect 가 도는 시점의 `.viewer` 안에는 **편집 전 옛 HTML**(또는 빈 문자열)이 들어 있다. 그 DOM 으로 좌표를 재면 틀린다. `changeViewMode` 에서 `setViewerHtml(renderMarkdown(getText('lf'), { resolveWikiLink, sourceLines: true }))` 를 먼저 부르면 커밋 시점에 최신 HTML 이 들어 있다. 1048~1054행 effect 는 **그대로 둔다**(보기 모드에서 문서를 열 때가 그 effect 의 몫이다) — 같은 문자열을 다시 만들어 `setViewerHtml` 에 넣으면 React 가 값이 같아 다시 그리지 않는다. 비용은 전환마다 변환 1회 추가, 5,000줄에서 25.5ms(3.6). 덤으로 "전환 직후 한 프레임 동안 편집 전 HTML 이 보이던" 기존 문제도 사라진다.

### 5.3 숨겨진 동안에는 `scrollSnapshot()` 을 찍지 않는다

`createEditor.ts` 의 `setViewMode`·`setLineNumbers`·`setIndent` 는 셋 다 `view.scrollSnapshot()` 을 쓴다. 보기 모드에서는 편집기가 `hidden` 이라 셋 다 4.1 의 "보류된 쓰레기 스크롤 목표" 를 만든다. `setLineNumbers`·`setIndent` 도 보기 모드에서 설정 대화상자를 열면 실제로 닿는 경로다.

공통 헬퍼 하나를 만들어 셋 다 거치게 한다.

```ts
// 숨겨져 있으면(.editor-slot hidden → display:none → clientHeight 0) 스냅샷을 찍지 않는다.
// 뷰포트 높이 0 에서 찍힌 스냅샷은 문서 맨 위를 가리키고(@codemirror/view dist/index.js 6646행),
// CM6 가 그것을 소비하지 못해 보류했다가(8219행) 다시 보일 때 적용해 버린다 (F-295 4.1)
function scrollSnapshotIfVisible(view: EditorView): StateEffect<unknown>[] {
  return view.scrollDOM.clientHeight > 0 ? [view.scrollSnapshot()] : []
}
```

세 메서드의 `effects` 배열에 `scroll` 대신 `...scrollSnapshotIfVisible(view)` 를 펼쳐 넣는다. `setTheme`(491~499행)은 원래 스냅샷을 안 쓰므로 건드리지 않는다.

### 5.4 원문(raw) 모드는 범위 밖이다 (지시 5)

3.2 실측에서 편집 ↔ 원문 왕복이 화면 맨 위 줄을 그대로 지켰다. 이 경로는 같은 `EditorView` 를 `Compartment.reconfigure` 로 바꿀 뿐이고 `.editor-slot` 이 `hidden` 이 되는 일이 없어(2671행 조건은 `viewMode === 'view'`) 5.3 가드에도 걸리지 않는다. **고치지 않는다.** 대신 회귀를 막으려고 A6 를 둔다.

원문 ↔ 보기는 편집 ↔ 보기와 완전히 같은 경로다. 따로 다루지 않는다.

### 5.5 늦게 바뀌는 높이는 어디까지 책임지나 (지시 6)

**책임 경계: 되돌린 직후 + rAF 2회 뒤 실측 보정 1회까지.** 그 뒤 이미지·mermaid 가 그려져 높이가 늘어 위치가 어긋나는 것은 고치지 않는다.

| 근거 | |
| --- | --- |
| 신호가 없다 | `Viewer.tsx` 68~148행의 첨부 이미지·mermaid 채우기는 각자 비동기 `Promise` 이고 "전부 끝났다" 를 밖으로 알리지 않는다. 알리게 고치면 `Viewer.tsx`(F-123·F-158·F-258 소유)를 열어야 한다 |
| 늦은 보정이 더 나쁘다 | 사용자는 전환 직후 바로 스크롤·읽기를 시작한다. 그때 화면이 저절로 움직이면 스크롤을 빼앗는 것이고, 이건 F-171 이 정확히 반대 방향으로 고쳤던 종류의 문제다 |
| 대부분의 문서에 영향이 없다 | 이미지·다이어그램이 많고 **동시에** 아주 긴 문서에서만 눈에 띈다 |

대안은 12장 Q1.

### 5.6 문서를 바꾸면 기준값을 버린다 (지시 7)

기준값은 `{ docId, anchor }` 로 보관하고, 복원할 때 `docId !== currentDocId` 면 **쓰지 않고 버린다.** 그러면 이미 정해져 있는 규칙들과 부딪히지 않는다.

- `F-244` 3.2 "스크롤 위치는 들어올 때마다 맨 위"(도움말 S-7) — 도움말은 `currentDocId === null` 이라 항상 버려진다
- `App.tsx` 1321행(`createNewDoc`)·1452행(`openWikiLinkTarget`)·1901행(`importSharedDoc`)이 부르는 `changeViewMode('live')` — 셋 다 곧 다른 문서로 간다. 복원이 옛 문서 편집기에 먼저 걸려도 그 편집기는 바로 언마운트되고, 새 문서 편집기는 기준값을 못 받는다
- 공유 화면(S-4)이 떠 있으면 `.content-area` 자체가 `hidden`(2670행) 이라 읽기·쓰기 모두 높이 0 에서 막힌다 (6.3 의 `null` 규칙)

### 5.7 같은 모드를 다시 누르면 아무 일도 하지 않는다

`changeViewMode` 첫 줄에 `if (v === viewMode) return` 을 둔다. 없으면 기준값만 저장되고 복원 effect 는 `viewMode` 가 안 바뀌어 돌지 않아, 오래된 기준값이 다음 진짜 전환 때 쓰인다.

## 6. 순수 함수 — `src/lib/scrollAnchor.ts` (신규)

**테스트 환경이 `node` 라 DOM 이 없다.** 그래서 계산은 전부 여기로 빼고 좌표 읽기만 7장·8장에 남긴다. `import` 문이 하나도 없는 파일이고, `editor` 와 `app` 이 둘 다 이 파일을 쓴다 (`architecture.md` 1장 의존 방향 `editor → lib` / `viewer → lib` / `app → …` 을 지킨다).

```ts
// 화면 맨 위에 보이는 원문 줄. 정수부 = 1-based 줄 번호, 소수부 = 그 블록 안에서 위로 잘린 비율
export type ScrollAnchor = number

// 원문 줄 번호가 붙은 블록 하나. top·bottom 은 스크롤러 안쪽 좌표(scrollTop 과 같은 단위)
export type LineBlock = { line: number; top: number; bottom: number }

export function anchorInBlock(startLine: number, endLine: number, ratio: number): ScrollAnchor
export function ratioInBlock(startLine: number, endLine: number, anchor: ScrollAnchor): number
export function anchorAtTop(blocks: LineBlock[], top: number): ScrollAnchor | null
export function topForAnchor(blocks: LineBlock[], anchor: ScrollAnchor): number | null
```

### 6.1 `anchorInBlock(startLine, endLine, ratio)`

`startLine + clamp01(ratio) * max(1, endLine - startLine)`. `endLine` 은 **열린 끝**(그 블록이 끝난 다음 줄)이다. `endLine <= startLine` 이면 `endLine = startLine + 1` 로 본다.

### 6.2 `ratioInBlock(startLine, endLine, anchor)`

`anchorInBlock` 의 역. `clamp01((anchor - startLine) / max(1, endLine - startLine))`.

### 6.3 `anchorAtTop(blocks, top)` — 화면 위 끝 y → 기준값

`blocks` 는 `line` 오름차순이라고 가정한다(부르는 쪽이 보장).

| 경우 | 결과 |
| --- | --- |
| `blocks` 가 비었다 | `null` |
| `top < blocks[0].top` (제목·경로 영역, 프론트매터 표 위) | `blocks[0].line` |
| 그 밖 | `top` 이하인 마지막 블록 `i` 를 찾아 `anchorInBlock(blocks[i].line, endLineOf(i), (top - blocks[i].top) / height)` |

- `endLineOf(i)` = `blocks[i+1]?.line ?? blocks[i].line + 1`
- `height` = `max(1, (blocks[i+1]?.top ?? blocks[i].bottom) - blocks[i].top)` — 다음 블록의 위 끝까지를 이 블록의 몫으로 본다(블록 사이 여백도 이 블록에 속한다고 본다). 마지막 블록만 자기 `bottom` 을 쓴다

### 6.4 `topForAnchor(blocks, anchor)` — 기준값 → 화면 위 끝 y

`anchorAtTop` 의 역.

| 경우 | 결과 |
| --- | --- |
| `blocks` 가 비었다 | `null` |
| `anchor < blocks[0].line` (프론트매터·앞머리 빈 줄) | `0` — **화면 맨 위**. `blocks[0].top` 이 아니다. 문서 앞머리를 보고 있었으면 앞머리가 보여야 한다 |
| 그 밖 | `anchor` 이하인 마지막 블록 `i` 에 대해 `blocks[i].top + ratioInBlock(blocks[i].line, endLineOf(i), anchor) * height` |

`endLineOf`·`height` 는 6.3 과 같다.

### 6.5 반올림 규칙 (지시 3)

- **줄 번호가 정확히 안 맞을 때는 아래(더 작은 줄)로 붙인다.** 6.3·6.4 모두 "그 값 **이하**인 마지막 블록" 을 고른다. 화면 맨 위에 걸친 블록이 기준이라는 뜻이고, 목록·표 한가운데를 보고 있으면 그 목록·표의 시작이 기준 블록이 된다
- **블록 안에서는 줄 번호에 선형 비례해 보간한다.** 100줄짜리 코드블록 한가운데를 보고 있으면 반대편 화면에서도 그 코드블록 한가운데가 나온다. 보간을 안 하면 코드블록 맨 위로 튀어 한 화면 이상 어긋난다 (12장 Q2)
- 양방향 모두 같은 규칙이다. 3.5 에서 왕복 오차 0.011줄을 확인했다

## 7. 보기 화면 좌표 — `src/app/viewerScroll.ts` (신규)

DOM 을 만지므로 `lib/` 가 아니라 `app/` 이다(`outlinePosition.ts` 와 같은 자리·같은 이유). 전역 `document` 를 읽지 않고 넘겨받은 요소만 본다.

```ts
import { anchorAtTop, topForAnchor, type LineBlock, type ScrollAnchor } from '../lib/scrollAnchor'

type Rect = { top: number; bottom: number }
type Scroller = { getBoundingClientRect(): Rect; scrollTop: number; clientHeight: number
                  querySelectorAll(sel: string): Iterable<{ getBoundingClientRect(): Rect; getAttribute(n: string): string | null }>
                  scrollTo(opts: { top: number; behavior: ScrollBehavior }): void }

export function readViewerBlocks(root: Scroller | null): LineBlock[]
export function readViewerAnchor(root: Scroller | null): ScrollAnchor | null
export function scrollViewerToAnchor(root: Scroller | null, anchor: ScrollAnchor): void
```

- `readViewerBlocks`: `root.querySelectorAll('[data-source-line]')` 를 돌며 `line = Number(getAttribute('data-source-line'))`, `top = rect.top - rootTop + root.scrollTop`, `bottom` 도 같은 식. `rootTop = root.getBoundingClientRect().top`. `Number.isFinite(line)` 이 아닌 것은 버리고 `line` 오름차순으로 정렬한다(최상위 블록은 DOM 순서가 곧 줄 순서지만, 인용 안 제목처럼 같은 줄을 가리키는 요소가 섞일 수 있어 정렬해 둔다)
- `readViewerAnchor`: `root` 가 `null` 이거나 `clientHeight === 0` 이면 `null`. 그 밖은 `anchorAtTop(readViewerBlocks(root), root.scrollTop)`
- `scrollViewerToAnchor`: `root` 가 `null` 이거나 `clientHeight === 0` 이면 아무것도 안 한다. `topForAnchor` 결과가 `null` 이면 아무것도 안 한다. 그 밖은 **`root.scrollTo({ top: Math.max(0, y), behavior: 'instant' })`**
  - `scrollTop` 대입을 쓰지 않는다 — 3.3 실측대로 `.viewer` 가 `scroll-behavior: smooth` 라 대입은 애니메이션이 되고 즉시 반영되지 않는다

## 8. 편집기 핸들 — `src/editor/createEditor.ts` 에 메서드 2개 추가

`EditorHandle` 은 `ReturnType<typeof createEditor>`(`Editor.tsx` 15행)라 `Editor.tsx` 를 고칠 필요가 없다. `scrollToHeading`(583~596행) 바로 옆에 둔다.

### 8.1 `getScrollAnchor(): ScrollAnchor | null`

```ts
getScrollAnchor() {
  if (view.scrollDOM.clientHeight === 0) return null            // 숨겨져 있으면 읽지 않는다 (4.1)
  const doc = view.state.doc
  const padTop = view.documentPadding.top
  const top = view.scrollDOM.scrollTop
  const block = view.lineBlockAtHeight(top - padTop)            // 인자는 documentTop 기준 (index.d.ts 910~916행)
  const startLine = doc.lineAt(block.from).number
  const endLine = Math.min(doc.lineAt(block.to).number + 1, doc.lines + 1)
  const ratio = block.height > 0 ? (top - padTop - block.top) / block.height : 0
  return anchorInBlock(startLine, endLine, ratio)
}
```

- `lineBlockAtHeight` 의 인자가 `documentTop`(첫 줄의 위, 여백 위가 아니다) 기준이라 `padTop` 을 뺀다. `Outline.tsx` 96~99행이 반대 방향으로 같은 보정(`+ padTop`)을 쓰고 있다
- 한 `lineBlock` 이 원문 여러 줄을 덮을 수 있다(라이브 프리뷰의 표·이미지 위젯). 그래서 `block.to` 로 끝 줄을 따로 구한다

### 8.1a 문서 맨 위 sentinel (2026-09-21 구현 중 발견, 사람 승인 받음)

문서 맨 위에는 CM6 쪽에 제목 위젯(block widget, `from=0`)이, 보기 화면 쪽에 실제 `h1` 이 있다. 8.1 공식을 그대로 쓰면 **"제목이 아직 보이는 상태"** 와 **"첫 최상위 블록이 정확히 맨 위에 온 상태"** 가 둘 다 `anchor≈1` 로 나와 구별되지 않는다. `getBoundingClientRect` 실측으로 확인했다.

- `scrollTop <= 0` 일 때만 `anchor = 0` 을 sentinel 로 쓴다. `getScrollAnchor`·`scrollToAnchor`(`createEditor.ts`)·`readViewerAnchor`(`viewerScroll.ts`) 세 곳에 든다
- 순수 함수(`src/lib/scrollAnchor.ts`)는 건드리지 않는다 — sentinel 은 DOM 을 읽는 자리에서만 판정한다
- A4 가 이 경우를 검증한다

### 8.2 `scrollToAnchor(anchor: ScrollAnchor)`

```ts
scrollToAnchor(anchor) {
  if (view.scrollDOM.clientHeight === 0) return
  const n = Math.max(1, Math.min(Math.floor(anchor), view.state.doc.lines))
  const pos = view.state.doc.line(n).from
  // 1차 — 그 줄이 보이도록 뷰포트를 옮겨, 그 둘레의 진짜 줄 높이가 측정되게 한다
  view.dispatch({ effects: EditorView.scrollIntoView(pos, { y: 'start', yMargin: 0 }) })
  // 2차 — 그려진 뒤(rAF 2회) 실측으로 보정한다. scrollToHeading(583~596행)과 같은 방식
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      if (destroyed || view.scrollDOM.clientHeight === 0) return
      const doc = view.state.doc
      const block = view.lineBlockAt(pos)
      const startLine = doc.lineAt(block.from).number
      const endLine = Math.min(doc.lineAt(block.to).number + 1, doc.lines + 1)
      const want = block.top + view.documentPadding.top + ratioInBlock(startLine, endLine, anchor) * block.height
      if (Math.abs(view.scrollDOM.scrollTop - want) > 0.5) view.scrollDOM.scrollTop = want
    })

```

- 보정식은 8.1 의 **정확한 역함수**다. `scrollToHeading` 이 쓰는 `coordsAtPos` 방식은 제목 줄 위 여백만큼 차이가 나므로 쓰지 않는다. 그래도 A5 가 안 맞으면 `coordsAtPos` 방식으로 바꿔 보고 결과를 보고한다
- `EditorView.scrollIntoView` 는 대상 위치가 뷰포트에 들어오도록 CM6 가 뷰포트를 넓혀 주는 효과가 있다(`index.js` 6443~6450행). 1차 없이 2차만 하면 `lineBlockAt(pos)` 가 추정값이라 어긋난다
- `.cm-scroller` 에는 `scroll-behavior: smooth` 가 없다(`app.css` 확인). 대입으로 충분하다

## 9. `data-source-line` 을 최상위 블록까지 (지시 3·4)

### 9.1 속성 이름은 기존 것을 그대로 쓴다

`renderMarkdown.ts` 330~344행이 이미 `h1`~`h3` 에 `data-source-line`(1-based, 프론트매터 줄 수 포함)을 붙이고 있고 `outlinePosition.ts` 19행이 그것으로 요소를 찾는다(F-144 3.4). **새 이름(`data-line`)을 만들지 않고 이 속성을 넓힌다.**

### 9.2 옵션으로 켠다. 기본은 꺼져 있다 (지시 4)

```ts
export function renderMarkdown(text: string, options: { resolveWikiLink?: ResolveWikiLink; sourceLines?: boolean } = {}): string
```

`env.sourceLines` 로 내려보낸다(`resolveWikiLink`·`lineOffset` 과 같은 방식, 532~540행).

**호출부 전부와 각각의 선택:**

| # | 호출부 | 쓰임 | `sourceLines` |
| --- | --- | --- | --- |
| 1 | `src/app/App.tsx` 1052행 | 보기 모드 화면 | **`true`** (F-144 목차 + F-295 스크롤) |
| 2 | `src/app/App.tsx` 1541행 | 인쇄·PDF (`printDoc`) | `false`(기본) |
| 3 | `src/viewer/toHtmlDoc.ts` 70행 | HTML 파일 내보내기 + 서식 있는 복사 (`exportDoc.ts` 경유) | `false`(기본) |
| 4 | `src/app/HelpPage.tsx` 11행 | 도움말 S-7 | `false`(기본) |

| 6 | `src/app/PublicView.tsx` 196행 | 공개 보기 S-5 | `false`(기본) |

기본을 끈 이유는 취향이 아니라 **깨지는 것이 있기 때문**이다. `toHtmlDoc.ts` 가 `renderMarkdown` 출력을 정규식으로 다시 뜯는다.

`parseMarkdownTokens`(525~527행, F-278 평문 변환기가 쓴다)는 토큰의 `type`·`content`·`meta` 만 읽으므로 속성이 더 붙어도 결과가 안 바뀐다. 그래도 `env` 를 안 넘기면 옵션은 꺼진 상태다.

### 9.3 어느 토큰에 붙이나

`md.core.ruler.push('source_lines', …)` 로 **코어 규칙 맨 끝**에 단다. `callout`·`image_block`(`before('inline', …)`)·`wikilink`·`table_br`(`after('inline', …)`)·`task_lists`(`push`)가 토큰을 자르고 붙이는 일이 모두 끝난 뒤여야 한다.

`env.sourceLines` 가 참일 때만 돌고, 다음 조건을 **모두** 만족하는 토큰에 `attrSet('data-source-line', String(env.lineOffset ?? 0) + token.map[0] + 1)` 을 한다.

- `token.block === true`
- `token.nesting >= 0` (여는 태그와 단독 태그. 닫는 태그 제외)
- `token.level === 0` (**최상위 블록만.** 목록 안 문단, 표 안 칸, 인용 안 문단은 안 붙인다)
- `token.map` 이 있다
- `token.attrGet('data-source-line') === null` (330~344행이 이미 붙인 제목을 덮어쓰지 않는다)

해당하는 것: `paragraph_open`(p) · `heading_open`(h1~h6 — **h4~h6 은 이 규칙이 처음 붙인다**) · `blockquote_open` · `bullet_list_open` · `ordered_list_open` · `table_open` · `hr` · `fence` · `code_block` · `html_block`.

**최상위만 하는 이유**: (1) 최상위 블록만으로도 문서 전체가 빈틈없이 나뉘고 블록 안은 6.5 의 보간이 메운다, (2) 목록 항목마다 붙이면 같은 줄을 가리키는 요소가 늘어 9.4 의 중복 문제가 커진다, (3) HTML 이 커진다.

**두 곳은 렌더러가 속성을 무시하므로 따로 손댄다.**

| 대상 | 지금 | 옵션이 켜졌을 때 |
| --- | --- | --- |
| 이미지 블록 (`renderImageBlockHtml`, 154~161행. `html_block` 이라 `token.content` 가 그대로 나간다) | `<div class="md-image md-image--{정렬}"…>` | `imageBlockRule`(164~189행)이 `state.env` 로 줄 번호를 구해 넘기고, `renderImageBlockHtml` 이 `class` 바로 뒤에 ` data-source-line="N"` 을 넣는다 |
| mermaid (`fence` 렌더러, 321~327행) | `<div class="md-mermaid" data-mermaid-source="…">` | `class` 바로 뒤에 ` data-source-line="N"` 을 넣는다 |

**알려진 오차**: markdown-it 의 기본 `fence` 렌더러는 속성을 `<code>` 에 붙이고(`markdown-it.mjs` 805~830행) `code_block` 은 `<pre>` 에 붙인다(801~803행). 그래서 코드블록의 기준점이 `<pre>` 의 안쪽 여백(16px)만큼 아래다. 긴 코드블록에서 보간 비율이 그만큼 밀리지만 400px짜리 블록에서 4% 수준이라 받아들인다. 렌더러를 더 손대 `<pre>` 로 옮기지 않는다 — 9.2 의 "출력을 그대로 둔다" 원칙과 부딪힌다.

### 9.4 목차가 제목을 잘못 찾지 않게 한다 (회귀 방어)

옵션이 켜지면 같은 줄을 가리키는 요소가 둘 생길 수 있다. 예: `> # 제목` 은 최상위 `blockquote_open` 과 그 안 `heading_open` 이 둘 다 같은 줄이다. 지금 `outlinePosition.ts` 19행은

```ts
return container.querySelector(`[data-source-line="${lineOf(handle, from)}"]`)
```

라 DOM 에서 먼저 나오는 `<blockquote>` 를 집는다. 선택자를 좁힌다.

```ts
const n = lineOf(handle, from)
return container.querySelector(`h1[data-source-line="${n}"], h2[data-source-line="${n}"], h3[data-source-line="${n}"]`)
```

`h1`~`h3` 만 목차 대상이다(`Outline.tsx` 15행 `RULE_LENGTH` 에 1·2·3 만 있다). 공개 보기(S-5)는 옵션이 꺼져 있어 원래도 제목만 붙지만 같은 선택자로 동작한다.

## 10. 수용 기준

동작 기준은 `e2e/viewScroll.spec.js`(신규)에서 `F-295 A{n}` 이름으로 자동 판정한다. **스크롤 픽셀 값을 박지 않는다.** 판정은 전부 "화면 맨 위에 보이는 것이 무엇인가" 로 한다.

### 10.1 e2e 공통

문서는 `## 제목 N` + 빈 줄 + `본문 N …` 을 N = 0…399 로 이어 붙인 것(`importMarkdown` 으로 넣는다). 화면 맨 위 요소의 글자에서 `제목 (\d+)` 또는 `본문 (\d+)` 로 **구역 번호 N** 을 뽑아 비교한다.

```js
// 편집·원문: .cm-scroller 위 끝을 지나는 첫 .cm-line

//            (.print-root 도 .viewer 클래스를 쓴다 — F-279 4.2. 반드시 .content-area 로 좁힌다)
async function topSection(page, where) { … }   // → 숫자 N
```

**허용 오차는 `|N_before - N_after| <= 1`** — 제목/본문 한 칸까지는 같은 자리로 본다. 3.5 시뮬레이션에서는 오차 0 이 나왔지만, 폰트 렌더링·블록 경계 반올림으로 한 칸이 밀릴 수 있어 여유를 둔다.
