# F-250 새로고침 뒤 60초 동안 자기 문서를 못 고치는 문제

작성일: 2026-09-18
상태: 사용자 승인 (2026-09-18 배포 확인 중 "새로고침 하면 이전 세션기록 때문에 바로 수정불가능함 / 60초 그냥 멍때려야되는데")
근거: `specs/features/F-213.md` 2.2(편집 잠금, 세션 id, 60초), CLAUDE.md 불변조건(저장소 식별자에 제품명을 쓰지 않는다)

## 1. 범위

### 문제
문서를 편집하다 새로고침하면 **최대 60초 동안 읽기 전용**이 된다. 직전 세션이 잡아 둔 잠금이 남아 있고, 새로 뜬 페이지는 그것을 자기 것으로 알아보지 못한다.

F-213 3장은 세션 id 를 이렇게 정했다:

> 세션 id: 창(탭)마다 클라이언트가 `crypto.randomUUID()` 로 만든다. 같은 사람의 다른 창도 다른 세션이다

그런데 `src/storage/docsApi.ts` 42행은 **모듈이 평가될 때마다**, 즉 페이지 로드마다 새로 만든다:

```ts
export const lockSessionId: string =
  typeof crypto !== 'undefined' && crypto.randomUUID ? crypto.randomUUID() : `${Date.now()}-${Math.random()}`
```

새로고침은 같은 창(탭)이지 새 창이 아니다. 그러므로 지금 동작은 명세가 정한 "창마다 하나" 를 지키지 못한 것이고, 서버의 잡기 조건(`expires_at < ? OR session_id = ?`)에서 두 조건 모두 어긋나 `423 locked` 이 된다.

`pagehide` 에서 `unlockDoc(keepalive: true)` 로 풀어 주기는 하지만 확실하지 않다 — 새 페이지의 잠금 요청이 먼저 도착할 수 있고, 브라우저가 keepalive 요청을 버릴 수도 있다. 그래서 재현율이 들쭉날쭉하다.

### 한다
- 세션 id 를 **창(탭)마다 하나**로 고친다 — 같은 탭에서 새로고침하면 같은 id 를 쓴다. `sessionStorage` 가 정확히 그 수명이다
- 그러면 서버 잡기 조건의 `session_id = ?` 가 맞아 **새로고침 직후 바로 잠금을 되잡는다**
- `sessionStorage` 를 못 쓰는 환경(사생활 보호 모드 등에서 접근이 막히는 경우)에서는 지금처럼 새 id 를 만들어 동작은 유지한다
- 저장 키에 제품명을 쓰지 않는다(CLAUDE.md 불변조건)

### 하지 않는다
- 잠금 시간(60초)·연장 주기 변경
- "같은 사용자면 세션이 달라도 빼앗기" — F-213 3장이 "같은 사람의 다른 창도 다른 세션" 이라고 못박았다. 다른 탭끼리는 지금처럼 서로 막는다
- `pagehide` 의 풀어 주기 제거 — 그대로 둔다(빨리 풀리면 좋다)
- 서버 `worker/locks.ts` 의 조건부 쓰기 변경 — 서버는 맞다. 클라이언트가 자기 세션 id 를 잃어버리는 것이 문제다
- 실시간 공동 편집(M3) 관련 작업

## 3. 요구사항

### 3.1 세션 id
- `sessionStorage` 에 저장한 값이 있으면 그것을 쓰고, 없으면 새로 만들어 저장한 뒤 쓴다
- 키는 제품명을 쓰지 않는다 — 기존 키 관례를 따라 `md.lockSession` 으로 한다(`md.lastDocId` 와 같은 접두사)
- `sessionStorage` 접근이 던지면(사생활 보호 모드 등) 잡아서 무시하고 메모리 값(지금 동작)으로 간다. 페이지가 죽지 않는다
- 값은 지금처럼 `crypto.randomUUID()`, 없으면 `${Date.now()}-${Math.random()}`
- `lockSessionId` 는 지금처럼 모듈 상수로 노출해 부르는 쪽을 바꾸지 않는다
