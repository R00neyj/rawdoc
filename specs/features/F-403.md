| 파일 | 변경 |

- **`src/e2ee/base64.ts` 는 F-400 6장 파일 목록에 없던 것을 더했다.** base64 는 F-405(저장소 한 겹)·F-406(첨부)이 암호 함수 없이도 쓸 수 있어 따로 둔다. 디렉터리는 F-400 이 정한 `src/e2ee/` 그대로다
- **의존**: 이 명세의 네 파일(`src/e2ee/` 셋 + `src/lib/e2eeLimits.ts`)은 서로와 전역 `crypto`·`TextEncoder`·`TextDecoder` 만 쓴다. `src/app`·`src/storage`·`src/editor`·`worker/`·`node:*`·`Buffer` 를 import·사용하지 않는다(브라우저에 `Buffer` 가 없다). `crypto → base64, recoveryCode, ../lib/e2eeLimits`, `recoveryCode`·`base64`·`e2eeLimits` 는 아무것도 import 하지 않는다. `e2ee → lib` 한 방향이다(`lib` 는 `e2ee` 를 import 하지 않는다)
- **`src/lib/e2eeLimits.ts` 는 worker 도 import 한다**(architecture.md 6장 "Worker 는 `src/lib/**` 순수 함수와 `src/types.ts` 만 import" 규칙 안). 그래서 이 파일은 DOM 타입을 쓰지 않는다 — `TextEncoder`·`String.prototype.normalize` 만(`worker/validate.ts` `utf8ByteLength` 가 이미 worker 에서 `TextEncoder` 를 쓴다). `worker/tsconfig.json` `include` 에 이 파일을 더하는 것은 **import 하는 쪽인 F-401** 이 한다
- **새 의존성 없음.** WebCrypto(PBKDF2·HKDF·AES-KW·AES-GCM)만 (F-400 Q1)
- 코드 식별자에 `vault` 를 쓰지 않는다(F-400 3.1). 제품명 문자열 없음(불변조건). 이 명세의 파일은 저장소 식별자를 만들지 않는다
- 이 명세만으로는 화면이 바뀌지 않는다 — F-404 부터 import 한다. 빌드 결과에 들어가지 않는 것이 정상이다

## 2. 범위

### 한다
- 금고 키 묶음(F-400 2.3) 만들기·읽기·쓰기, 암호로 열기, 복구 코드로 열기, 반복 수 올려 다시 감싸기, 암호 바꾸기, 복구 코드로 암호 다시 정하기
- 문서 키(DEK) 만들기·풀기·다른 금고 키로 다시 감싸기(F-408 이관용)
- 제목·본문 봉투 암호화·복호화, 첨부 봉투 암호화·복호화·머리의 감싼 키만 바꾸기
- 복구 코드 표기·읽기, base64, 크기·길이 상수와 판정

### 하지 않는다
- 키를 메모리에 들고 있기·자동 잠금·탭 전파(F-404), 저장소·API 호출(F-404·F-405), 화면 문구(F-404)
- 문서 저장 크기 초과 알림(F-405 — 판정 함수만 여기서)
- 서버 쪽 검사(F-401 — 서버는 봉투를 풀지 않는다)
- 금고 키(MK) 교체(F-400 1.3)
- 서버로 보내는 간격 `E2EE_SERVER_SAVE_INTERVAL_MS`(F-400 3.4) — 크기 상수가 아니라 저장 동작이라 F-405 가 둔다

## 3. 바이트 배치 (계약)

모든 base64 는 표준 알파벳(`A–Z a–z 0–9 + /`)과 `=` 패딩이다(F-400 2.3). 여러 바이트 정수는 쓰지 않는다 — 반복 수는 JSON 의 숫자다

### 3.1 제목·본문 봉투 — 평문 + 29 B

| 위치(바이트) | 길이 | 내용 |
| --- | --- | --- |
| 0 | 1 | 버전 `0x01` |
| 1–12 | 12 | IV(암호화할 때마다 `crypto.getRandomValues` 로 새로) |
| 13 – 끝−16 | 평문 UTF-8 길이 | AES-GCM 256 암호문 |
| 끝 16 B | 16 | GCM 태그(WebCrypto `encrypt` 가 암호문 뒤에 붙여 돌려주는 그대로) |
| **합** | **평문 + 1 + 12 + 16 = 평문 + 29** | 저장은 base64 문자열 — 길이 `4 × ⌈(평문+29)/3⌉` |

- AAD(추가 인증 데이터): UTF-8 `"{docId}:title"` / `"{docId}:content"` (F-400 3.2). 봉투에 들어가지 않고 풀 때 다시 만든다
- 평문은 `TextEncoder` 로 만든 UTF-8. 짝 없는 서로게이트는 U+FFFD 가 된다(c13) — 지금 `fetch` 몸통·`utf8ByteLength` 와 같은 동작이다
- 빈 평문도 봉투가 된다 — 29 B, base64 40자(10장 V6)
- 태그 길이는 128비트(WebCrypto 기본). `tagLength` 를 따로 주지 않는다

### 3.2 감싼 문서 키 — 41 B, base64 56자

| 위치 | 길이 | 내용 |
| --- | --- | --- |
| 0 | 1 | 버전 `0x01` |
| 1–40 | 40 | AES-KW(MK, DEK 원시 32 B) — RFC 3394 는 32 B 를 40 B 로 감싼다 |
| **합** | **41 B** | base64 `4 × ⌈41/3⌉ = 56`자, 끝 `=` 하나. `docs.e2ee_key` 에 들어간다 |

### 3.3 첨부 봉투 — 평문 + 69 B

| 위치 | 길이 | 내용 |
| --- | --- | --- |
| 0 | 1 | 버전 `0x01` |
| 1–40 | 40 | AES-KW(MK, 첨부 DEK) — **자체 버전 바이트가 없다**(봉투 0번이 전체 버전) |
| 41–52 | 12 | IV |
| 53 – 끝−16 | 평문 길이 | AES-GCM 암호문 |
| 끝 16 B | 16 | 태그 |
| **합** | **평문 + 1 + 40 + 12 + 16 = 평문 + 69** | 바이너리 그대로 R2 (F-400 3.2). base64 로 바꾸지 않는다 |

- AAD: UTF-8 `"att:{attachmentId}"`, `attachmentId` 는 확장자 없는 소문자 16진 16자(`extractAttachmentRefs` 가 뽑는 값)
- 첨부마다 새 DEK. 같은 이미지를 두 번 올려도 봉투가 다르다

### 3.4 키 묶음 — JSON (F-400 2.3 의 타입 그대로)

| 필드 | 값 | 바이트 |
| --- | --- | --- |
| `v` | `1` | — |
| `kdf.name` / `kdf.hash` | `'PBKDF2'` / `'SHA-256'` | — |
| `kdf.iterations` | 정수 1 ~ 10,000,000 | — |
| `kdf.salt` | base64 | 16 B → 24자 |
| `wrappedByPassword` | base64, AES-KW(KEK_p, MK) | 40 B → 56자. **버전 바이트 없음** — 묶음의 `v` 가 버전이다 |
| `recovery.salt` | base64 | 16 B → 24자 |
| `recovery.wrapped` | base64, AES-KW(KEK_r, MK) | 40 B → 56자 |
| `createdAt` | 밀리초 epoch 정수 | — |

- 직렬화는 위 순서의 `JSON.stringify` 한 줄(공백 없음). 길이 321~323자(c11)
- 반복 수 상한 10,000,000 의 이유: 서버가 묶음을 준다 — 터무니없는 반복 수(예: 2³¹)로 탭을 몇 분 묶어 두지 못하게. 10,000,000 은 Node 에서 1.34초(c8). 하한 1 — 반복 수를 낮춘 묶음은 암호를 모르면 만들 수 없어(AES-KW 무결성) 보안상 하한이 필요 없고, 테스트가 1,000회를 쓴다

### 3.5 키 유도 (F-400 2.1 을 WebCrypto 인자로)

| 키 | 만드는 법 | 알고리즘·용도 | `extractable` |
| --- | --- | --- | --- |
| KEK_p | 암호를 `normalize('NFC')` 한 UTF-8 → `importKey('raw', …, 'PBKDF2')` → `deriveKey({ name: 'PBKDF2', hash: 'SHA-256', salt: kdf.salt, iterations: kdf.iterations })` | `{ name: 'AES-KW', length: 256 }`, `['wrapKey','unwrapKey']` | false |
| KEK_r | 복구 코드 20 B → `importKey('raw', …, 'HKDF')` → `deriveKey({ name: 'HKDF', hash: 'SHA-256', salt: recovery.salt, info: UTF-8 "e2ee-recovery-v1" })` | 같음 | false |
| MK | 무작위 256비트 | `AES-KW`, `['wrapKey','unwrapKey']` | **돌려주는 것은 false**. 다시 감쌀 때만 함수 안에서 true 로 한 번 풀고 버린다 |
| DEK | 무작위 256비트 | `AES-GCM`, `['encrypt','decrypt']` | 돌려주는 것은 false. 다시 감쌀 때(`rewrap*`)만 함수 안에서 true |

- 이 표의 문자열 `"e2ee-recovery-v1"` 과 AAD 형식이 바뀌면 이미 만든 금고가 열리지 않는다 — 10장 벡터가 그것을 고정한다
- GCM IV 는 무작위 96비트. 문서 하나의 DEK 로 암호화하는 횟수는 기기 캐시 쓰기(입력 700ms 멈춤마다)가 가장 잦다 — 그 간격으로 쉬지 않고 써도 NIST SP 800-38D 의 무작위 IV 한 키당 2³² 번에 닿는 데 약 95년이다(0.7초 × 2³²). DEK 를 주기적으로 바꾸는 장치는 두지 않는다

| 디코딩 **표 조회**(글자 4개 → 바이트 3개, 표에 없는 글자에서 멈춤) | **2.2ms** | **11.8ms** | **1.7ms** | **채택** |
| 디코딩 기본 `Uint8Array.fromBase64` | 0.2ms | 1.0ms | 없음 | 안 씀 |
| (참고) 전체를 정규식 `^(?:[A-Za-z0-9+/]{4})*…$` 로 먼저 검사 | 5.3ms | 28.1ms | 5.2ms | 안 씀 — 디코딩보다 느리다. 검사는 디코딩 중에 한다 |

- 네 방식 모두 결과가 같았다(`btoa` 결과 = 표 조회 결과 = 기본 `toBase64` 결과, 998,720자)
- **F-400 3.2 마지막 줄("기본 `toBase64` 가 있으면 그것, 없으면 `btoa` 묶음")과 다르다.** 두 갈래를 두면 Node 단위 테스트가 브라우저 갈래를 못 탄다. 한 갈래 표 조회는 가장 느린 조건(4배 감속)에서도 7.1·11.8ms 라 기본 API 로 얻을 이득이 작다 — 11장 Q1
- `tsconfig.json` `lib` 는 바꾸지 않는다

### 4.2 계약

```ts
export function bytesToBase64(bytes: Uint8Array): string
export function base64ToBytes(text: string): Uint8Array<ArrayBuffer> | null
```

### 4.3 규칙

- 인코딩은 RFC 4648 4장 표준 알파벳, `=` 패딩. 0 B → `''`
- 디코딩은 **엄격**: 길이가 4의 배수, 모든 글자가 알파벳, `=` 는 끝의 1개 또는 2개만, 마지막 묶음의 쓰지 않는 비트가 0(정규형)이 아니면 `null`. 공백·줄바꿈·base64url(`-` `_`)도 `null`. `''` → 길이 0 배열
- 이유: 저장된 값과 다시 인코딩한 값이 늘 같게(한 바이트열에 문자열 하나). 서버(F-401)가 금고 제목을 `[A-Za-z0-9+/=]` 로만 거르므로 느슨한 입력을 받을 이유가 없다
- 결과는 `Uint8Array<ArrayBuffer>` — WebCrypto 인자(`BufferSource`)로 바로 넘길 수 있게(`cliSeal.ts` 와 같은 형)

## 5. 암호 함수 — `src/e2ee/crypto.ts`

### 5.1 오류 (계약)

```ts
export type E2eeErrorCode =
  | 'wrong-password'        // AES-KW 로 MK 를 풀지 못함 (F-400 2.1, c2). 빈 암호 포함
  | 'wrong-recovery-code'   // 복구 코드 형식은 맞으나 MK 를 풀지 못함
  | 'bad-recovery-code'     // 복구 코드가 6.2 규칙으로 읽히지 않음 — 32자가 아니거나 알파벳 밖 글자
  | 'password-too-short'    // 새 암호가 7.3 규칙 미달 (만들기·바꾸기·다시 정하기에서만)
  | 'bad-bundle'            // 키 묶음 JSON·필드·길이가 3.4 와 다름
  | 'bad-envelope'          // 봉투·감싼 키의 base64·길이가 3장과 다름, 풀린 평문이 UTF-8 이 아님
  | 'unsupported-version'   // 묶음 v ≠ 1, 봉투·감싼 키 0번 바이트 ≠ 0x01
  | 'decrypt-failed'        // 형식은 맞으나 GCM 인증·AES-KW 풀기 실패 — 키가 다르거나, AAD(문서 id·필드·첨부 id)가 다르거나, 바뀐 바이트
  | 'bad-argument'          // 호출자 실수: 빈 docId, 16진 16자가 아닌 attachmentId, 20 B 가 아닌 복구 바이트

export class E2eeError extends Error {
  readonly code: E2eeErrorCode
}
```

- 이 파일의 비동기 함수는 실패를 **`E2eeError` 로만** 거부한다. WebCrypto 가 던진 `DOMException` 을 그대로 흘리지 않는다 — c3·c5 처럼 이름이 런타임마다 달라서다
- 판정 순서: 입력 형식(base64·길이·버전) → WebCrypto. 그래서 `wrong-password` 는 "형식은 맞는 묶음을 이 암호로 못 풀었다" 만 뜻한다. 묶음이 서버에서 망가진 경우(형식은 맞고 바이트만 바뀐 경우)도 `wrong-password` 로 보이는데, AES-KW 는 둘을 가를 수 없다 — 받아들인다
- `message` 는 사람이 읽을 한국어가 아니어도 된다(화면 문구는 F-404 가 `code` 로 고른다)

### 5.3 함수별 규칙

| 함수 | 규칙 | 오류 |
| --- | --- | --- |
| `parseKeyBundle` | UTF-8 길이 > `E2EE_BUNDLE_MAX_BYTES`(4,096)면 거절. JSON 이 객체가 아니거나 3.4 표의 필드가 하나라도 없거나 형이 다르면 거절. `salt` 는 디코딩해 16 B, `wrapped*` 는 40 B 여야 한다(c3 — 풀기 전에 걸러야 런타임마다 같은 오류가 난다). `iterations` 는 3.4 범위의 정수. **모르는 필드는 버린다** — 돌려주는 객체는 3.4 의 필드만 | `v` 가 1 이 아닌 숫자면 `unsupported-version`, 나머지는 `bad-bundle` |
| `serializeKeyBundle` | 3.4 순서의 `JSON.stringify`. `parseKeyBundle(serializeKeyBundle(b))` 가 `b` 와 같다 | — |
| `createKeyBundle` | 7.3 암호 검사 → 소금 둘(16 B)·복구 코드 20 B·MK 를 새로 만든다 → KEK_p·KEK_r 로 MK 를 감싼다 → 복구 코드는 6장 표기로 돌려준다. `createdAt` 은 `options.now ?? Date.now()`. 돌려주는 `masterKey` 는 `extractable: false` | `password-too-short` |
| `openWithPassword` | NFC 로 바꾼 암호가 빈 문자열이면 유도하지 않고 바로 `wrong-password`(c16). 묶음의 반복 수·소금으로 KEK_p → MK 풀기(`extractable: false`). **묶음 반복 수 < `E2EE_PBKDF2_ITERATIONS` 이면** 같은 함수 안에서 MK 를 `extractable: true` 로 한 번 더 풀어 새 소금·현재 반복 수로 감싼 `upgradedBundle` 을 돌려준다(`recovery`·`createdAt` 은 그대로). 아니면 `upgradedBundle: null`. 저장은 호출자(F-404)가 한다 — F-400 2.2 "열기에 성공한 직후" | `wrong-password` |
| `openWithRecoveryCode` | 6.2 로 읽기 → HKDF 로 KEK_r → MK 풀기(`extractable: false`). 반복 수와 무관하다 | `bad-recovery-code`, `wrong-recovery-code` |
| `changePassword` | 7.3 새 암호 검사 → 옛 암호로 MK 를 `extractable: true` 로 풀기 → 새 소금·`options.iterations ?? E2EE_PBKDF2_ITERATIONS` 로 감싼다. `recovery`·`createdAt` 은 그대로. PBKDF2 두 번(이 PC 약 160ms, c8) | `password-too-short`(먼저 검사, 유도하지 않는다), `wrong-password` |
| `resetWithRecoveryCode` | 7.3 새 암호 검사 → 복구 코드로 MK 를 `extractable: true` 로 풀기 → 새 KEK_p **와 새 복구 코드·새 복구 소금**으로 둘 다 다시 감싼다(F-400 2.4·Q4). `createdAt` 은 그대로. 돌려주는 `masterKey` 는 `extractable: false`, `recoveryCode` 는 새 코드 | `password-too-short`, `bad-recovery-code`, `wrong-recovery-code` |
| `createDocKey` | 새 DEK → MK 로 감싸 3.2 형식 base64. 돌려주는 `docKey` 는 `extractable: false`(c6) | — |
| `openDocKey` | base64 → 41 B·0번 `0x01` 확인 → MK 로 풀기 | `bad-envelope`, `unsupported-version`, `decrypt-failed` |
| `rewrapDocKey` | `from` 으로 DEK 를 `extractable: true` 로 풀어 `to` 로 감싼 3.2 형식. DEK 값은 그대로(본문 봉투를 다시 만들 필요가 없다 — F-400 2.1 이유 1) | `openDocKey` 와 같음 |
| `encryptDocField` | 3.1. `docId` 가 빈 문자열이면 거절. 크기는 **검사하지 않는다** — 판정은 호출자가 7장 함수로 먼저 한다(F-400 3.3 "암호화 전에"). 같은 평문도 부를 때마다 다른 봉투 | `bad-argument` |
| `decryptDocField` | base64 → 29 B 이상·0번 `0x01` 확인 → GCM 풀기 → `TextDecoder('utf-8', { fatal: true })` | `bad-argument`, `bad-envelope`, `unsupported-version`, `decrypt-failed` |
| `encryptAttachment` | 3.3. 첨부마다 새 DEK. `attachmentId` 가 `/^[0-9a-f]{16}$/` 이 아니면 거절 | `bad-argument` |
| `decryptAttachment` | 69 B 이상·0번 `0x01` → 1–40 을 MK 로 풀기 → 41–52 IV, 53– GCM | `bad-argument`, `bad-envelope`, `unsupported-version`, `decrypt-failed` |
| `rewrapAttachment` | 1–40 만 `from` → `to` 로 바꾼 새 배열. 0번과 41 이후 바이트는 **한 바이트도 바꾸지 않는다**(F-400 4.4 "머리의 감싼 키만 바꿔") | `bad-envelope`, `unsupported-version`, `decrypt-failed` |

- **MK 를 `extractable: true` 로 여는 곳은 `openWithPassword`(올릴 때만)·`changePassword`·`resetWithRecoveryCode` 셋, DEK 는 `rewrapDocKey`·`rewrapAttachment`·`createDocKey`·`encryptAttachment` 넷뿐이다.** 그 키는 함수 밖으로 나가지 않는다(F-400 2.1). 새로 만든 키를 `extractable: false` 로 돌려주는 방법(감싼 것을 다시 풀기 등)은 구현이 고른다 — 테스트는 돌려받은 키의 `extractable` 만 본다
- 무작위 값은 모두 `crypto.getRandomValues`·`crypto.subtle.generateKey` 로. 난수를 넣는 인자는 두지 않는다 — 고정 출력 검사는 10장의 **복호화 방향** 벡터로 한다(만드는 쪽은 왕복·구조로)
- `docId` 는 형식을 보지 않는다(지금 id 는 `crypto.randomUUID()`). AAD 는 `":title"`·`":content"` 가 끝에 붙으므로 어떤 id 로도 두 필드가 겹치지 않는다

## 6. 복구 코드 — `src/e2ee/recoveryCode.ts`

### 6.1 표기

```ts
export const RECOVERY_CODE_BYTES = 20
export function encodeRecoveryCode(bytes: Uint8Array): string          // 20 B 가 아니면 RangeError
export function parseRecoveryCode(input: string): Uint8Array<ArrayBuffer> | null
```

- 20 B = 160비트 → 5비트씩 **32자**, 남는 비트 없음. 비트 순서는 앞 바이트의 높은 비트부터(RFC 4648 base32 와 같은 순서, 알파벳만 다르다)
- 알파벳(Crockford): `0123456789ABCDEFGHJKMNPQRSTVWXYZ` — `I L O U` 없음
- 표기: 4자씩 8묶음을 `-` 로 이은 **39자**, 대문자. 예 `000G-40R4-0M30-E209-185G-R38E-1W81-24GK`(c14)
- **검사 글자를 붙이지 않는다**(11장 Q3). 틀린 코드는 HKDF → AES-KW 풀기 실패로 `wrong-recovery-code` 가 된다

### 6.2 읽기 규칙 — 이 순서로

1. `normalize('NFKC')` — 한글 입력기가 만든 전각 `０`·`Ｇ` 를 반각으로
2. 대문자로
3. 모든 공백(`\s` — 줄바꿈·탭·U+00A0·U+3000 포함)과 `-`·U+2010~U+2015(하이픈·대시류)·U+2212(빼기) 를 지운다. 문서 편집기가 `-` 를 대시로 바꿔 붙여 넣는 경우 때문이다
4. `O` → `0`, `I`·`L` → `1`
5. 정확히 32자이고 모두 알파벳이면 20 B, 아니면 `null`. `U` 는 알파벳 밖이라 `null`

- 묶음 경계는 보지 않는다 — `000G40R4…` 처럼 이어 써도, 묶음이 어긋나도 32자면 된다
- `parseRecoveryCode` 는 순수 함수다. 난수·WebCrypto 를 쓰지 않는다. 20 B 난수는 `crypto.ts` 가 만든다

### 7.2 판정 함수 (계약)


- `isPlainContentTooLarge` 가 받는 것은 **저장되는 문자열**(`fromEditorText` 로 `lineEnding` 을 이은 것, F-400 3.2). CRLF 문서는 줄마다 1 B 씩 크다 — 호출자(F-405)가 저장할 문자열로 부른다
- 제목은 판정 함수가 없다: 평문 500자(UTF-16) 이하면 UTF-8 은 최대 1,500 B(c13 — BMP 한 단위 최대 3 B, 서로게이트 두 단위 4 B, 짝 없는 서로게이트 3 B)라 봉투 base64 는 늘 2,040자 이하다. 기존 500자 검사로 충분하다

### 7.3 암호 길이 규칙

- `password.normalize('NFC')` 의 **코드 포인트 수**(`[...s].length`) ≥ 10. 앞뒤 공백도 센다(자르지 않는다 — 자르면 입력한 바이트와 유도에 쓰는 바이트가 달라진다)
- 글자 종류 규칙 없음(F-400 Q3)
- 이 함수는 D-8 화면(F-404)과 5.3 의 세 함수가 같이 쓴다 — 화면 검사와 코어 검사가 어긋나지 않게

### 결정됨 (2026-09-25 main)

**Q1. base64 를 한 경로(표 조회)로 — 결정(2026-09-25 main): 한 경로. F-400 3.2 마지막 줄과 다르다**

## 13. 확인한 것과 가정

### 13.1 코드를 읽거나 돌려 확인한 것
- 머리 표 c1~c16
- 테스트 환경은 `node`(`vite.config.ts` `test.environment`), Node v24.12.0 에 전역 `crypto.subtle.wrapKey`·`deriveKey` 가 있다. `cliSeal.test.ts` 가 같은 조건에서 이미 돈다
- `Uint8Array.prototype.toBase64`·`Uint8Array.fromBase64` 는 Node 24.12 에 없고(`typeof` = `undefined`) Chrome 153 에 있다. TS 6.0.3 은 `lib.esnext.typedarrays.d.ts` 에만 타입이 있고 이 저장소 `lib` 는 `ES2023`
- 첨부 id 는 `extractAttachmentRefs` 기준 소문자 16진 16자. 문서 id 는 `crypto.randomUUID()`
- `review-diff.mjs` 의 `HEX_RE`(`#` + 3·6·8자리 16진)는 `#` 없는 16진 문자열을 잡지 않고 `*.test.ts` 는 면제. 제품명 검사는 `brand.config.ts` 의 `name`·`shortName`(`Rawdoc`) 대소문자 그대로 `includes`
- `grep -rn "e2ee"` 로 기존 코드·테스트에 겹치는 이름이 없다

### 13.2 가정으로 남긴 것
- **NIST SP 800-38D 의 "무작위 96비트 IV 는 한 키로 2³² 번까지"** 는 기억에 기댄 수치다 — 이번에 원문을 열지 않았다. 3.5 의 "약 95년" 은 그 수치와 700ms 간격의 곱이다
- **Chrome 외 브라우저(Firefox·Safari)** 에서 벡터가 풀리는지 돌려 보지 않았다. 쓰는 것은 모두 WebCrypto 표준 알고리즘(PBKDF2·HKDF·AES-KW·AES-GCM)이라 같을 것으로 본다. 틀린 암호의 오류 이름이 달라도 5.1 이 WebCrypto 오류를 모두 감싸므로 코드는 영향을 받지 않는다
- 느린 PC 의 PBKDF2 시간은 재지 못했다(F-400 m2 와 같은 한계)
- 표 조회 base64 의 4배 감속 수치는 CDP `setCPUThrottlingRate` 흉내다. 실제 느린 PC 값이 아니다
- RFC 3394 AES-KW 가 32 B 를 40 B 로 감싼다는 것은 c1·c6 에서 길이로 확인했다(규격 원문은 열지 않았다)
