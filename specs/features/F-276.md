```ts
  throw new Error(`content/${GUIDES_INDEX_PATH}: 사용법 목록은 빌드가 만듭니다 — 글은 content/guides/{slug}.md 로 두세요`)
}

// 목록은 content/guides/*.md 의 프론트매터로 만든다. 주소 매핑이 없는 파일(잘못된 slug)은 건너뛴다 — 아래 루프의 가드 G2 가 그 파일에서 빌드를 실패시킨다
const guideEntries = fileEntries.flatMap(([relPath, raw]) => {
  if (!relPath.startsWith('guides/')) return []
  const url = contentUrl(relPath)
  return url === null ? [] : [guideEntry(url, raw)]
})

// 가상 글 둘은 맨 뒤에 붙인다 — content/ 글의 가드 에러가 먼저 나와야 사람이 자기가 고친 파일을 본다 (F-274.md 3.3)
const mdEntries: [string, string][] = [
  ...fileEntries,
  [GUIDES_INDEX_PATH, guidesIndexContent(guideEntries)],
  [HELP_CONTENT_PATH, helpContent()],
]
```

- 아래 `for` 반복문·가드·렌더·`sitemap`·링크 목록 검사는 **그대로 둔다**
- 두 가상 글 사이 순서는 결과에 영향이 없다 — `sitemap.xml` 은 `site/build.ts:100` 에서 주소 오름차순으로 정렬되고, `out` 은 키가 다르다
- `/guides` 의 `lastmod` 는 **빌드 시각**이다. 목록 글에 `date`·`updated` 를 넣지 않기 때문이다(`site/build.ts:83` 의 기본 경로, F-274 Q1 과 같은 결정)

### 3.5 목록에 무엇을 보여주고 어떻게 정렬하나

**보여주는 것: 제목 + 한 줄 설명.** 날짜는 보여주지 않는다.

- 제목은 글의 프론트매터 `title`, 설명은 `summary` 다. 둘 다 이미 `<title>`·`og:description` 에 쓰이는 값이라 따로 관리할 것이 늘지 않는다
- `summary` 가 없으면 제목만 낸다(구분선 `—` 도 붙이지 않는다)
- **날짜를 보여주지 않는 이유**: 사용법 글은 시사가 아니라 방법이다. 날짜가 보이면 반년 뒤에 "낡은 글" 로 읽힌다. 글이 실제로 언제 고쳐졌는지는 `sitemap.xml` 의 `lastmod` 로 검색엔진에만 넘긴다

**정렬: `date` 내림차순(최신 먼저), `date` 가 없으면 맨 뒤, 같으면 주소 오름차순.**

- F-272 6.1 표가 `date` 를 "글 목록 정렬(F-276)" 로 미리 예약해 뒀다. 그 예약을 그대로 쓴다
- 주소 비교는 `localeCompare` 없이 `<`/`>` 문자열 비교다. 빌드마다 결과가 같아야 하고, ICU 설정에 기대지 않는다(`site/build.ts:100` 의 `sort()` 와 같은 방식)
- 3편이 같은 날짜(`2026-09-21`)라 실제 순서는 주소순이 된다 — `markdown-portability`, `wiki-links`, `zettelkasten`. **읽는 순서는 3.6 의 안내 문장이 정한다**(정렬을 위해 제목·주소를 비틀지 않는다)

### 4.1 자리와 순서

`src/app/Sidebar.tsx:1006~1024` 의 아래 묶음에 넣는다. 순서는 **`앱 설치`(조건부) → `도움말` → `사용법` → `설정`** 이다.

- `도움말` 을 앞에 둔다 — 앱 안에서 바로 열리는 화면이고(S-7, `#/help`), `사용법` 은 창을 떠난다. 떠나는 항목을 뒤에 둔다
- `설정` 은 맨 아래 그대로다(`specs/ia.md` 2장 78행 "항상 표시. 사이드바 맨 아래")

- 로그인 여부·저장소 종류와 무관하게 **항상 보인다**. 공개 보기 화면(S-5)에는 사이드바 자체가 없으므로 영향이 없다

### 4.2 앵커냐 버튼이냐 — 코드로 확인하고 정한다

**`<a href="/guides" target="_blank" rel="noopener noreferrer">` 로 한다.** 버튼 + `window.open` 은 쓰지 않는다.

| 항목 | 앵커 | 버튼 + `window.open` |
| --- | --- | --- |
| 가운데 클릭·`Ctrl`+클릭·오른쪽 메뉴 `새 탭에서 열기` | 된다 | 안 된다 |
| 상태 표시줄에 주소가 보인다 | 보인다 | 안 보인다 |
| 팝업 차단 | 사용자 동작이라 막히지 않는다 | 같다 |
| 스크린 리더 | `link` 역할 | `button` 역할(이동인데 버튼으로 읽힌다) |
| 코드 | `Sidebar.tsx` 두 컴포넌트에 `href` 분기 + CSS 두 줄 (4.3·4.5) | 콜백이 필요 없어 `App.tsx` 는 안 건드린다는 점은 같다 |

앱 안을 가로채는 코드가 이 링크를 먹지 않는다는 것도 확인했다.

- `src/app/App.tsx:1402~1404` `handleAppShellClick` 은 `[data-go-home]` 만 본다 — 다른 클릭에 손대지 않는다
- 링크 가로채기(F-129, `src/editor/preview/…`)와 위키링크 클릭(`src/editor/preview/wikiLinks.ts:220~244`)은 **CM6 편집 영역 안**에서만 동작한다. 사이드바는 대상이 아니다
- `/guides` 는 `vite.config.ts:217` 의 `navigateFallbackDenylist` 에 이미 들어 있어(2.1) 서비스 워커가 앱 `index.html` 로 가로채지 않는다

### 4.3 `SidebarButton`·`RailButton` 에 `href` 더하기

기존 컴포넌트를 건드려야 하는지 코드로 확인했다 — **건드려야 한다.** 둘 다 `<button>` 을 직접 그린다(`src/app/Sidebar.tsx:440~458`·`468~476`). 새 컴포넌트를 두 개 더 만들면 같은 마크업이 네 벌이 되므로, **각 컴포넌트 안에서 `href` 유무로 갈라 그린다**.

```tsx
type RailButtonProps = { /* 지금 그대로 */ href?: string }
type SidebarButtonProps = { /* 지금 그대로 */ href?: string }
```

- `href` 를 주면 `onClick`·`ariaDisabled`·`buttonRef`·`ariaExpanded` 는 주지 않는다. 사이트로 나가는 링크 하나만 쓰는 통로다
- 새 탭 속성은 컴포넌트가 붙인다 — `target="_blank" rel="noopener noreferrer"`. 부르는 쪽이 고를 수 없다

펼친 사이드바가 내는 마크업:

```html
<a class="sidebar-btn" href="/guides" target="_blank" rel="noopener noreferrer">
  <svg class="sidebar-btn-icon" …></svg>
  <span class="sidebar-btn-label">사용법</span>
  <svg class="sidebar-btn-ext" …></svg>
</a>
```

접힌 레일이 내는 마크업:

```html
<span class="icon-btn-wrap rail-btn-wrap">
  <a class="icon-btn rail-btn" href="/guides" target="_blank" rel="noopener noreferrer" aria-label="사용법">
    <svg …></svg>
  </a>
  <span class="icon-tooltip icon-tooltip--side" aria-hidden="true">사용법</span>
</span>
```

- 주소는 `src/lib/siteChrome.ts` 가 내보내는 `GUIDES_PATH` 를 쓴다. `SITE_NAV` 와 사이드바가 같은 상수를 본다(5장). `src/lib/siteChrome.ts` 의 다른 export(`SITE_CHROME_CSS` 약 1.4KB)는 부수효과 없는 상수라 앱 번들에서 트리셰이킹된다
- `.sidebar-btn-ext` 는 `IconExternalLink`(`open_in_new`, `src/app/icons.tsx:132`)를 `size={14}` 로 그린 것이고 `aria-hidden` 이다 — 새 탭이라는 **눈에 보이는 표시**다. 레일에는 자리가 없어 넣지 않는다
- 툴팁 문구는 `사용법` 이다. `RailButton` 의 `IconTooltip text={label}` 그대로이므로 **툴팁 = `aria-label`** 규칙(F-142 3.2)이 지켜진다

### 4.6 접근성

- 보이는 글자 `사용법` = 접근성 이름 `사용법`. 레일도 같다(`aria-label`)
- **새 탭 안내를 접근성 이름에 넣지 않는다.** 넣으면 레일 툴팁 문구와 `aria-label` 이 달라져 F-142 3.2 를 깬다. 새 탭은 `.sidebar-btn-ext` 아이콘으로 눈에 보이게만 알린다 — 12장 Q2 에 다른 선택지를 적었다
- `rel="noopener noreferrer"` 를 붙인다. 같은 출처라도 `window.opener` 를 넘기지 않는다
- 탭 순서는 DOM 순서 그대로다. `도움말` 다음, `설정` 앞

### 4.7 글에서 앱으로 되돌아오기 — 새로 두지 않는다

````markdown
# 위키링크로 문서 잇기

문서가 스무 개를 넘어가면 폴더만으로는 버티기 어렵습니다. 어디에 뒀는지 기억나지 않는 문서가 생기고, 서로 관련 있는 문서가 다른 폴더에 흩어집니다. 위키링크는 폴더 대신 **문서끼리 직접 잇는** 방법입니다.

## 쓰는 법

본문에 대괄호 두 개로 문서 제목을 감쌉니다.

```
[[회의록]]
```

`[[` 를 치면 지금 있는 문서 제목이 목록으로 뜹니다. 몇 글자만 더 치면 목록이 좁혀지고, 골라 넣으면 닫는 괄호까지 채워집니다.

보이는 글자를 따로 정하려면 세로 막대 뒤에 씁니다.

```
[[회의록|지난주 회의에서 정한 것]]
```

## 눌러서 이동하기

`편집` 모드와 `보기` 모드 어느 쪽에서나 위키링크를 누르면 그 문서가 열립니다.

그 자리에서 글자를 고치고 싶을 때는 `Ctrl`(`Cmd`)을 누른 채 누릅니다. 문서를 열지 않고 커서만 그 자리로 갑니다. 커서가 이미 그 링크에 닿아 있을 때도 열리지 않습니다 — 기호가 드러나 편집 중인 상태로 보기 때문입니다.

## 아직 없는 문서로 잇기

가장 쓸모 있는 쓰임은 **아직 없는 문서**를 가리키는 것입니다.

> [!note] 먼저 잇고 나중에 씁니다
> 없는 제목을 적어 두면 그 링크는 점선 밑줄이 그어진 흐린 글자로 보입니다. 눌렀을 때 그 제목으로 빈 문서가 만들어지고 곧바로 제목 칸에 커서가 놓입니다. 새 문서는 지금 보고 있는 문서와 같은 폴더에 생깁니다.

쓰던 흐름을 끊고 새 문서를 만들러 가지 않아도 됩니다. "여기서 이어질 글" 을 제목으로 적어 두었다가 나중에 그 자리를 채우면 됩니다.

## 제목이 곧 주소입니다

위키링크는 파일 경로가 아니라 **문서 제목**으로 상대를 찾습니다. 찾는 순서는 이렇습니다.

1. 제목이 정확히 같은 문서
2. 없으면 대소문자만 다른 문서
3. 그래도 여럿이면 가장 최근에 고친 문서

그래서 제목을 바꾸면 그 문서를 가리키던 링크는 대상을 잃습니다. 제목을 바꾸기 전에 `Ctrl+Shift+F` 로 옛 제목을 찾아 함께 고쳐 두는 편이 안전합니다.

같은 제목을 두 문서에 붙이지 않는 것도 같은 이유입니다. 제목이 겹치면 링크가 어느 쪽으로 갈지 사람이 알기 어렵습니다.

## 이어진 문서를 함께 공유하기

위키링크가 들어 있는 문서를 공유하면 이어진 문서까지 함께 공개할지 고를 수 있습니다. 상단바 `공유` 에서 `읽기 전용 링크 복사…` 를 누르면 `함께 공유할 문서` 목록이 뜹니다. 고르지 않은 문서로 가는 링크는 받는 사람 화면에서 눌리지 않는 보통 글자로 보입니다.

## 정리

- `[[문서 제목]]` 으로 잇고, `[[` 뒤에 뜨는 목록에서 고릅니다
- 없는 제목을 누르면 그 제목으로 새 문서가 생깁니다
- `Ctrl`(`Cmd`)을 누른 채 누르면 열지 않고 커서만 옮깁니다
- 제목을 바꿀 때는 그 제목을 가리키던 링크도 함께 고칩니다
````

````markdown
# 제텔카스텐으로 메모 쌓기

제텔카스텐(Zettelkasten)은 독일 사회학자 니클라스 루만이 쓰던 메모 상자입니다. 규칙은 단순합니다 — **쪽지 한 장에 생각 하나만 적고, 쪽지끼리 번호로 잇는다.** 미리 분류하지 않고 잇기만 해도, 나중에 하나를 꺼내면 이어진 것이 딸려 나옵니다.

종이 상자에서 번호가 하던 일을 여기서는 위키링크가 합니다. 아래는 그 방식을 이 앱에서 쓰는 방법입니다.

## 1. 한 문서에 한 생각

문서를 길게 쓰지 않습니다. 한 문서에는 나중에 혼자 꺼내 써도 말이 되는 생각 하나만 둡니다. 길어야 화면 한 쪽입니다.

회의록처럼 사건을 적는 문서와, 거기서 건져 낸 생각을 적는 문서를 나누면 편합니다. 사건은 시간이 지나면 다시 볼 일이 없지만 생각은 계속 불려 나옵니다.

## 2. 제목을 문장으로 씁니다

`회의`·`메모3` 같은 제목은 나중에 찾지 못합니다. 위키링크가 제목으로 상대를 찾기 때문에, 제목은 그 문서의 주소이면서 요약이기도 합니다.

- 아쉬운 제목: `독서 메모`
- 나은 제목: `옮겨 적기만 하면 기억에 남지 않는다`

주장을 문장으로 적어 두면 다른 문서에서 불러 쓸 때 문장이 그대로 읽힙니다. `이 주장은 [[옮겨 적기만 하면 기억에 남지 않는다]] 와 이어진다` 처럼 씁니다.

## 3. 쓰면서 잇습니다

새 생각을 적다가 관련 있는 문서가 떠오르면 그 자리에서 `[[` 를 치고 목록에서 고릅니다. 아직 없는 문서라면 제목만 적어 두었다가 나중에 눌러서 만듭니다.

이을 때는 **왜 이었는지**를 한 줄 덧붙입니다. 링크만 있으면 반년 뒤에 그 줄이 왜 거기 있는지 알 수 없습니다.

```
이 방법은 [[옮겨 적기만 하면 기억에 남지 않는다]] 의 반대편에 있다 —
옮겨 적는 대신 자기 말로 바꿔 적게 만든다.
```

## 4. 속성으로 묶습니다

문서 맨 위에 `---` 두 줄 사이를 두면 속성이 됩니다.

```
---
title: 옮겨 적기만 하면 기억에 남지 않는다
tags:
  - 읽기
  - 기억
---
```

`Ctrl+Shift+F` 로 검색을 열고 `tags:읽기` 라고 치면 그 속성을 가진 문서만 남습니다. 값까지 정확히 같아야 걸리고, `tags:` 까지만 치면 그 속성이 있는 문서가 모두 나옵니다. 조건을 여러 개 쓰면 모두 만족하는 문서만 남고, 보통 낱말을 섞어 치면 제목·본문에서 함께 찾습니다.

속성은 폴더와 달리 한 문서에 여러 개를 붙일 수 있습니다. 그래서 분류를 미리 정하지 않아도 됩니다.

## 5. 입구 문서를 하나 만들어 고정합니다

쌓기만 하면 어디부터 봐야 할지 알 수 없습니다. 주제마다 **입구 문서**를 하나 두고 그 안에 위키링크만 늘어놓습니다.

```
# 읽기와 기억

- [[옮겨 적기만 하면 기억에 남지 않는다]]
- [[요약은 이해한 뒤에만 가능하다]]
```

이 문서를 `⋯` 메뉴에서 `상단 고정` 해 두면 사이드바 맨 위 `고정됨` 묶음에 남습니다. 돌아올 자리가 생깁니다.

## 6. 폴더는 적게 씁니다

폴더는 두 단계까지 만들 수 있지만, 제텔카스텐에서는 많이 쓰지 않습니다. 한 문서는 폴더 하나에만 들어갈 수 있어서, 폴더를 세밀하게 나눌수록 "어디에 넣지" 를 고민하는 시간이 늘어납니다.

폴더는 성격이 아주 다른 묶음(예: `일`·`개인`)에만 쓰고, 주제는 위키링크와 속성으로 다루는 편이 손이 덜 갑니다.

## 7. 하루 흐름

1. 떠오른 것을 새 문서에 한 생각씩 적습니다
2. 제목을 문장으로 고쳐 씁니다
3. 관련 있는 문서를 `[[` 로 잇고, 이은 이유를 한 줄 적습니다
4. 주제 입구 문서에 새 문서를 한 줄 더합니다

이 네 단계만 반복하면 됩니다. 분류는 나중에 필요해질 때 속성으로 붙이면 됩니다.
````

````markdown
# 한 번 쓴 글을 다른 도구로 옮기기

글을 쌓기 전에 확인해야 할 것이 하나 있습니다. **여기서 나갈 수 있는가.** 편집기가 자기 형식으로 글을 가두면, 도구를 바꾸는 순간 쓴 것이 반쯤 망가집니다.

이 앱은 처음부터 마크다운 원문을 그대로 들고 있습니다. `##` 을 쳐도 기호가 사라지지 않고, 문서 안에 들어 있는 것이 곧 파일에 들어갈 것입니다.

## 내보낸 파일은 입력한 그대로입니다

상단바 내보내기 메뉴에서 `.md` 를 고르면 지금 문서의 원문이 그대로 파일이 됩니다. 앱이 붙이는 서식도, 떼는 기호도 없습니다.

줄바꿈 형식도 그대로입니다. 윈도우에서 만든 파일(CRLF)을 가져와 고친 뒤 다시 내보내면 여전히 CRLF 입니다. 리눅스·맥에서 만든 파일(LF)은 LF 로 나갑니다. 형식이 바뀌면 git 에서 파일 전체가 바뀐 것처럼 보이기 때문에 일부러 기억해 둡니다.

## 이미지가 있으면 zip 으로 나갑니다

붙여넣은 이미지가 있는 문서는 `.md` 대신 zip 으로 받습니다. 안에는 이렇게 들어 있습니다.

```
문서 제목.md
attachments/0123456789abcdef.png
```

본문의 이미지 자리에는 표준 HTML 이 들어 있습니다.

```
<div align="center">
  <img src="attachments/0123456789abcdef.png" width="320">
</div>
```

경로가 `attachments/…` 상대 경로라서, zip 을 통째로 풀면 `.md` 와 이미지가 나란히 놓입니다. 마크다운 안 HTML 을 그리는 도구라면 이미지가 그대로 보입니다.

## 전부 한 번에 꺼내기

문서 하나가 아니라 통째로 옮길 때는 `설정` 의 `데이터` 에서 `전체 내보내기` 를 누릅니다. 폴더 하나만 꺼낼 때는 사이드바 폴더 `⋯` 메뉴의 `폴더 내보내기` 입니다.

받은 zip 안에는 사이드바에서 보던 폴더 구조가 그대로 들어 있고, 폴더마다 자기 `attachments/` 가 붙습니다. 맨 위에는 `manifest.json` 이 하나 있습니다 — 폴더·문서 목록과 만든 날짜가 적힌 파일이고, 다시 가져올 때 씁니다. 다른 도구는 이 파일을 몰라도 되니 무시하면 됩니다.

## 다른 도구에서 열 때

| 도구 | 그대로 되는 것 | 알아 둘 것 |
| --- | --- | --- |
| GitHub | 제목·목록·표·코드블록·체크박스, 이미지 HTML | `[[제목]]` 은 링크가 아니라 글자로 보입니다 |
| VS Code | 마크다운 미리보기에서 대부분 그대로 | 위키링크는 확장을 깔아야 동작합니다 |
| Obsidian | `[[제목]]`·`[[제목\|별칭]]` 문법이 같습니다 | 이미지는 `attachments/` 폴더째 옮겨야 보입니다 |

문서 맨 위 속성(`---` 사이의 `title:` 같은 줄)은 YAML 프론트매터 그대로라, 이를 읽는 도구에서 속성으로 잡힙니다. 읽지 못하는 도구에서는 본문 맨 앞 몇 줄로 보일 뿐 내용이 깨지지는 않습니다.

## 다시 가져오기

내보낸 zip 은 그대로 되돌릴 수 있습니다. `설정` 의 `데이터` 에서 `가져오기…` 를 누르고 zip 을 고르면 무엇이 들어올지 먼저 보여 줍니다. `.md` 파일 하나만 들일 때는 사이드바 `가져오기` 를 씁니다.

## 마크다운이 아닌 형식으로

같은 내보내기 메뉴에 네 가지가 더 있습니다.

- `.txt (평문)` — 기호를 뗀 글자만 남깁니다. 기호를 모르는 사람에게 보낼 때 씁니다
- `HTML 파일` — 서식이 들어간 한 파일입니다
- `PDF (A4 인쇄)` — 인쇄 창을 엽니다. `Ctrl+P` 와 같습니다
- `서식 있는 복사` — 굵게·목록 같은 서식을 살린 채 다른 편집기에 붙여넣습니다

## 정리

- `.md` 로 내보낸 파일은 입력한 바이트와 같고 줄바꿈 형식도 유지됩니다
- 이미지가 있으면 zip 이고, 안에서 `attachments/` 상대 경로로 이어져 있습니다
- 전체·폴더 내보내기는 폴더 구조를 그대로 담고 다시 가져올 수 있습니다
- 위키링크는 Obsidian 에서 그대로 동작하고, GitHub 에서는 글자로 보입니다
````
