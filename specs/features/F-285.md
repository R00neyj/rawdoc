## 3. 내보내는 것 (전체 목록)

```ts
// ── 상수 ────────────────────────────────────────────────
export const SNIPPET_BEFORE = 30   // 발췌: 첫 매치 앞 글자 수 (F-284 4.3)
export const SNIPPET_AFTER = 70    // 발췌: 첫 매치 뒤 글자 수
export const RESULT_LIMIT = 200    // 결과 상한 (F-284 4.3)

// ── 정규화 ──────────────────────────────────────────────
export function normalizeForSearch(text: string): string
export function foldCase(text: string): string

// ── 쿼리 파싱 ────────────────────────────────────────────
export type QueryFilter = { key: string; value: string }
export type ParsedQuery = {
  raw: string            // 받은 문자열 그대로 (정규화 전). 표시·디버그용
  terms: string[]        // 본문 검색어. NFC + foldCase 를 마친 값, 중복 제거, 입력 순서
  filters: QueryFilter[] // key·value 모두 NFC + foldCase + trim 을 마친 값, 중복 제거
  isEmpty: boolean       // terms 와 filters 가 둘 다 비었다
}
export function parseSearchQuery(raw: string): ParsedQuery

// ── 매칭 ────────────────────────────────────────────────
export type SearchProperty = { key: string; value: string | string[] }
export type SearchDocInput = {
  id: string
  title: string                                  // NFC 정규화된 제목
  body: string                                   // 프론트매터를 뗀 뒤 NFC 정규화된 본문. 공유받은 문서는 ''
  properties: readonly SearchProperty[] | null   // NFC 정규화된 parseSimpleProperties 결과. 규칙 밖이면 null
  updatedAt: number
}
export type DocMatch = {
  titleMatched: boolean  // 검색어 전부가 제목에 있다 → 정렬 앞 묶음 (7.3)
  bodyHit: number        // 본문 첫 매치 위치(코드유닛). 없으면 -1
}
export function matchDoc(doc: SearchDocInput, query: ParsedQuery): DocMatch | null
export function matchesFilters(
  properties: readonly SearchProperty[] | null,
  filters: readonly QueryFilter[],
): boolean
export function hasPropertyKey(properties: readonly SearchProperty[] | null, key: string): boolean

// ── 검색 실행 ────────────────────────────────────────────
export type SearchHit = DocMatch & { id: string }
export type SearchOutcome = {
  hits: SearchHit[]            // 정렬·상한을 적용한 결과
  total: number                // 상한 적용 전 매치 수
  truncated: boolean           // total > limit
  unreadableProperties: number // 필터가 있을 때, properties 가 null 이라 필터에서 빠진 문서 수 (F-284 4.4)
  missingFilterKeys: string[]  // 어느 문서에도 없는 필터 키 (F-284 3.5)
}
export function searchDocs(
  docs: readonly SearchDocInput[],
  query: ParsedQuery,
  options?: { limit?: number },
): SearchOutcome

// ── 발췌·강조 ────────────────────────────────────────────
export type SnippetPart = { text: string; hit: boolean }
export function highlightParts(source: string, query: ParsedQuery): SnippetPart[]
export function buildSnippet(source: string, query: ParsedQuery): SnippetPart[]
```

## 4. 쿼리 파싱

### 4.1 토큰 나누기

한 글자씩 훑는 스캐너 하나다. 정규식으로 쪼개지 않는다 — 따옴표 상태를 들고 있어야 한다

| 규칙 | 내용 |
| --- | --- |
| 구분자 | `/\s/` 에 맞는 글자(공백·탭·줄바꿈·NBSP `U+00A0`·전각 공백 `U+3000` 포함) |
| 큰따옴표 `"` | **어디에 있든 따옴표 모드를 토글**하고, 토큰 글자에는 남지 않는다. 따옴표 모드 안에서는 구분자가 글자로 취급된다 |
| 작은따옴표 `'` | 보통 글자다 (F-284 3.1 — 한국어 본문에 그대로 쓰인다) |
| 닫히지 않은 `"` | 입력 끝까지 한 토큰 |
| 토큰 시작이 `"` 였는지 | 기억한다(`quotedAtStart`). **이 토큰은 언제나 본문 검색어**가 된다 (4.2 의 탈출구) |
| 빈 토큰 | 버린다. `""` 는 토큰 0개 |

### 4.2 `key:value` 판별

`quotedAtStart` 가 아닌 토큰만 후보다. 첫 `:` 앞을 키, 뒤 전부를 값으로 본다

| 조건 | 결과 |
| --- | --- |
| 첫 `:` 위치가 0 이거나 `:` 가 없다 | 본문 검색어 |
| 키가 `/^[A-Za-z0-9가-힣_-]+$/` 에 안 맞는다 | 본문 검색어 (토큰 전체가 검색어) |
| 값이 `//` 로 시작한다 | 본문 검색어 (URL 오인 방지, F-284 3.2) |
| 그 밖 | 필터 `{ key, value }` |

- 키·값 모두 `foldCase` 를 거치고, 값은 `trim()` 까지 한다. 키는 정규식상 공백이 못 들어가므로 `trim()` 이 불필요하지만 같은 경로를 쓴다
- **같은 `(key, value)` 쌍이 두 번 나오면 하나만 남긴다.** 서로 다른 값이면 둘 다 남고 AND 로 걸린다 (F-284 3.2 "같은 키를 여러 번 써도 AND")
- 본문 검색어도 **같은 값이면 하나만 남긴다** (AND 라 결과가 같고, 훑는 횟수만 준다)

### 4.3 경계 사례 — 입력 → 파싱 결과 (전부 실행해 확인함)

아래 표는 이 명세를 쓰며 만든 프로토타입을 실제로 돌려 얻은 값이다. 단위 테스트가 이 표를 그대로 옮긴다

| 입력 | `terms` | `filters` | 비고 |
| --- | --- | --- | --- |
| `tag:일기 회고` | `['회고']` | `[{tag, 일기}]` | 기본형 |
| `"주간 회고"` | `['주간 회고']` | `[]` | 붙은 구절 |
| `"주간 회고` (닫는 따옴표 없음) | `['주간 회고']` | `[]` | 끝까지 한 토큰 |
| `""` | `[]` | `[]` | 빈 토큰은 버린다 |
| `"" 회고` | `['회고']` | `[]` | |
| `(공백만)` / `(빈 문자열)` | `[]` | `[]` | `isEmpty === true` |
| `tag:` | `[]` | `[{tag, ''}]` | **존재 검사** (F-284 3.2) |
| `tag:""` | `[]` | `[{tag, ''}]` | 위와 같다 |
| `tag:  ` (값이 공백뿐) | `[]` | `[{tag, ''}]` | 값이 `trim()` 으로 빈다 |
| `tag:"주간 회고"` | `[]` | `[{tag, 주간 회고}]` | 값에 공백을 넣는 **인정되는 표기** |
| `"tag:일기"` | `['tag:일기']` | `[]` | 필터를 본문 검색어로 쓰는 탈출구 |
| `"tag:주간 회고"` | `['tag:주간 회고']` | `[]` | **개요 3.2 와 어긋남 → 11장 M1** |
| `a:b:c` | `[]` | `[{a, b:c}]` | 값은 첫 콜론 뒤 전부 |
| `time:10:30` | `[]` | `[{time, 10:30}]` | |
| `:foo` | `[':foo']` | `[]` | 키가 비었다 |
| `my.key:1` | `['my.key:1']` | `[]` | 키에 `.` 은 허용 밖 |
| `http://a.com` | `['http://a.com']` | `[]` | 값이 `//` 로 시작 |
| `https://a.com/b` | `['https://a.com/b']` | `[]` | 위와 같다 |
| `Tag:Diary` | `[]` | `[{tag, diary}]` | 대소문자 구분 안 함 |
| `-x:1` / `x-y_z:1` | `[]` | `[{-x, 1}]` / `[{x-y_z, 1}]` | `-`·`_` 는 키에 허용 |
| `tag: 일기` (콜론 뒤 공백) | `['일기']` | `[{tag, ''}]` | **공백은 언제나 구분자.** `tag` 존재 검사 + 본문 검색어 `일기` 로 갈라진다 |
| `tag:일기" 회고` (값 뒤 따옴표) | `[]` | `[{tag, 일기 회고}]` | 따옴표가 뒤를 전부 삼킨다 |
| `a"b c"d` | `['ab cd']` | `[]` | 따옴표는 글자에서 빠지고 앞뒤가 이어 붙는다 |
| `tag:일기 tag:일기` | `[]` | `[{tag, 일기}]` | 중복 제거 |
| `회고 회고` | `['회고']` | `[]` | 중복 제거 |

- **검색어 개수에 상한을 두지 않는다.** 매칭이 문서 하나마다 첫 실패에서 끊기고(7.2), 10개 검색어가 1개와 사실상 같은 시간이 드는 것을 실측했다 (9장). 상한을 두면 "왜 뒷 단어가 무시되나" 를 설명할 길이 없다

### 4.4 알려진 제약 (개요에서 이어받은 것)

- 프론트매터 키에 공백이 있으면(`my key: v`) 쿼리로 칠 방법이 없다 (F-284 3.3). 따옴표로도 안 된다 — 따옴표는 토큰 경계만 바꾸고 키 정규식(4.2)은 그대로 적용된다
- 키에 한글·ASCII 영숫자·`_`·`-` 밖의 글자가 있으면(`café:`, `日付:`) 필터가 되지 않는다. 개요 3.2 가 정한 글자 집합 그대로다

## 5. 정규화 — 어디서 몇 번 하나

**`.normalize('NFC')` 를 직접 부르는 곳은 `normalizeForSearch` 함수 본문 한 줄뿐이다.** 다른 곳에서 `.normalize(` 를 쓰지 않는다

| 쪽 | 부르는 곳 | 횟수 |
| --- | --- | --- |
| 검색어 | `parseSearchQuery` 맨 앞에서 **입력 문자열 전체에 1회**. 토큰으로 쪼갠 뒤에는 다시 부르지 않는다 | 검색 1회당 1번 |
| 문서 | **이 모듈이 부르지 않는다.** F-286 이 인덱스를 만들 때 제목·본문·속성 키·값마다 1회 | 문서가 인덱스에 들어갈 때 1번 |

- 토큰을 쪼갠 뒤 다시 정규화하지 않아도 되는 근거: **NFC 문자열의 부분 문자열은 NFC 다.** 쪼개는 자리가 공백·`"`·`:`(전부 결합 문자가 아니다)라 앞뒤 글자의 조합을 끊지 않는다
- `matchDoc`·`searchDocs`·`buildSnippet`·`highlightParts` 는 **입력이 이미 NFC 라고 믿는다.** 방어적으로 다시 정규화하면 검색 한 번에 본문 전체를 또 훑게 된다(5,000개에 20~190ms, F-284 5.1 실측). 타입 주석(3장 `SearchDocInput`)과 파일 머리 주석에 이 전제를 적는다
- **원문은 정규화하지 않는다.** 이 모듈은 저장소·`EditorState` 를 모른다 (F-284 5.4, `CLAUDE.md` 불변조건)

### 5.1 `foldCase` — 길이를 보존하는 소문자화

```ts
export function foldCase(text: string): string
```

- 먼저 `text.toLowerCase()` 를 하고, **길이가 같으면 그대로 돌려준다**(거의 모든 경우, 빠른 길)
- 길이가 달라졌으면 코드포인트마다 소문자로 바꾸되 **길이가 늘어나는 글자는 원래 글자를 그대로 둔다**. 결과는 언제나 `foldCase(s).length === s.length`
- **왜 필요한가:** `'İ'`(U+0130) 의 `toLowerCase()` 는 `'i̇'`(U+0069 U+0307) 로 **1코드유닛 → 2코드유닛**이 된다. 이 PC 의 Node v24.12.0 에서 직접 확인했다. 소문자 사본에서 찾은 위치를 원래 대소문자 문자열에 그대로 쓰는 것이 발췌(8장)의 전제인데, 길이가 달라지면 그 위치가 어긋나 발췌가 엉뚱한 곳에서 잘린다
- 그리스어 종성 시그마(`'ΑΣ'.toLowerCase()` → `'ας'`)는 길이가 같아 문제가 없다 — 같은 실행에서 확인했다
- 로캘 독립이어야 하므로 `toLocaleLowerCase` 를 쓰지 않는다 (F-284 4.2)
- 대가: `İ` 가 든 문서에서만 느린 길로 간다. 실측 9.2

## 6. 속성 매칭

### 6.1 입력 모양 — `parseSimpleProperties` 의 출력 그대로

`src/lib/frontmatter.ts` 85~116행을 읽어 확인한 것:

| 프론트매터 | `parseSimpleProperties` 결과 |
| --- | --- |
| `tag: 일기` | `{ key: 'tag', value: '일기' }` — 값은 `trim()` + 감싼 따옴표 한 쌍 제거(`stripQuotes`, 76~83행) |
| `tags:` + 들여쓴 `  - a` `  - b` | `{ key: 'tags', value: ['a', 'b'] }` — **배열.** 원소도 `stripQuotes` 를 거친다 |
| `tags: [a, b]` | `{ key: 'tags', value: '[a, b]' }` — **문자열.** 배열로 안 읽힌다 → 6.3 |
| `tag:` | `{ key: 'tag', value: '' }` |
| 같은 키가 두 줄 | 항목이 **둘** 생긴다 (겹쳐 쓰지 않는다) |
| 중첩 맵·블록 스칼라 등 규칙 밖 | 전체가 `null` |

- 키는 `match[1].trim()` 이라 공백이 들어 있을 수 있다(`my key`). 그래서 매칭 때도 키에 `trim()` 을 한 번 더 건다 — 비교 결과는 같고 방어만 는다

### 6.2 매칭 규칙

| 항목 | 규칙 |
| --- | --- |
| `properties === null` | 필터가 하나라도 있으면 **그 문서는 빠진다**(`false`). 본문 검색에는 정상 참여 (F-284 3.3) |
| 필터가 0개 | 언제나 `true` (`properties` 가 `null` 이어도) |
| 키 비교 | `foldCase(key).trim() === filter.key`. **완전일치**, 대소문자 구분 안 함 |
| 같은 키 항목 여럿 | **하나라도 맞으면 맞음**(OR) |
| 값이 빈 필터(`tag:`) | 그 키를 가진 항목이 있으면 맞음 (존재 검사) |
| 값 비교 | `foldCase(후보).trim() === filter.value`. **완전일치** (F-284 3.2 Q6) — 부분일치가 아니다 |
| 배열 값 | **원소 중 하나라도** 완전일치하면 맞음 |
| 필터 여러 개 | **전부 AND** (F-284 3.2 Q7) |

### 6.3 인라인 배열 보정 (F-284 3.4 = 승인된 기본값)

값이 **문자열**일 때만 적용한다. `trim()` 한 값이 `[` 로 시작하고 `]` 로 끝나며 길이가 2 이상이면:

1. 대괄호 안을 `,` 로 쪼갠다
2. 조각마다 `trim()` → 감싼 따옴표(`"` 또는 `'`) 한 쌍 제거 → `foldCase`
3. **쪼갠 원소들과 `foldCase(원본 문자열).trim()` 을 모두 후보로 본다**

3번이 개요 3.4 에 더하는 결정이다. 개요 8장 Q2 가 걱정한 "값에 쉼표가 든 문자열을 배열로 오인" 을 이것으로 막는다 — 원본 문자열도 후보에 남으므로 `note: [1, 2]` 는 `note:1` 에도 `note:"[1, 2]"` 에도 걸린다. 후보를 늘리기만 하므로 개요 결정과 충돌하지 않는다 (둘 다 실행해 확인했다)

- 대괄호 안이 비면(`tags: []`) 원소 후보가 없다. 키 존재 검사(`tags:`)에는 여전히 걸린다
- 따옴표 제거는 `frontmatter.ts` 76~83행의 `stripQuotes` 와 같은 규칙이다. **그 함수를 import 하지 않고 같은 6줄을 이 파일에 둔다** — `stripQuotes` 는 export 되어 있지 않고, F-284 3.3 이 `frontmatter.ts` 를 고치지 말라고 정했다. 이 모듈이 import 0개를 유지하는 값이기도 하다. 주석에 원본 위치를 적는다
- 배열 값(블록 목록)의 원소에는 이 보정을 적용하지 않는다 — 이미 배열이다

### 6.4 `hasPropertyKey`

`missingFilterKeys`(F-284 3.5 `'tagg' 속성을 가진 문서가 없습니다`)를 만들려면 "그 키를 가진 문서가 하나라도 있나" 를 알아야 한다. `searchDocs` 가 문서를 훑는 **같은 루프 안에서** 아직 못 찾은 키만 검사하고, 한 번 찾은 키는 다시 검사하지 않는다

## 7. 본문 매칭·정렬

### 7.1 대상

`SearchDocInput` 의 `title` 과 `body` 둘뿐이다. `body` 는 F-286 이 프론트매터를 떼고 넣는다(F-284 4.1 — YAML 원문은 본문 검색 대상이 아니다). 공유받은 문서는 `body === ''` 라 제목만 걸린다 (F-284 5.2)

### 7.2 규칙

```
matchDoc(doc, query):
  query.isEmpty            → null
  필터 불일치               → null
  terms 가 0개(필터만)      → { titleMatched: false, bodyHit: -1 }
  term 마다:
    제목에도 본문에도 없으면 → null   (첫 실패에서 끊는다)
  → { titleMatched, bodyHit }
```

| 항목 | 규칙 |
| --- | --- |
| 비교 문자열 | `foldCase(title)`, `foldCase(body)` 를 문서마다 **매 검색 때 한 번** 만든다 (F-284 5.1 — 소문자 사본을 인덱스에 담지 않는다) |
| 한 검색어의 판정 | `제목.includes(term) || 본문.includes(term)` — **제목과 본문을 합친 것 기준** |
| 여러 검색어 | **전부 맞아야 한다(AND).** 검색어마다 제목/본문 중 아무 쪽에서나 맞으면 된다 — 한 검색어는 제목에서, 다른 검색어는 본문에서 맞아도 결과다 |
| `titleMatched` | **검색어 전부가 제목에 있을 때만** `true`. 정렬 묶음(7.3)을 가른다. 검색어가 0개면 `false` |
| `bodyHit` | 검색어들의 본문 첫 매치 위치 중 **가장 작은 값**. 본문에 아무 검색어도 없으면 `-1` |
| 최소 길이 | 1글자부터 (F-284 4.2) |
| 정규식 | 쓰지 않는다. `String.prototype.indexOf`·`includes` 만 |

### 7.3 정렬·상한 (`searchDocs`)

1. `query.isEmpty` 면 곧바로 `{ hits: [], total: 0, truncated: false, unreadableProperties: 0, missingFilterKeys: [] }`. **문서를 훑지 않는다** — 안 그러면 빈 쿼리에 모든 문서가 걸린다
2. 문서를 받은 순서대로 훑으며 `matchDoc`, 동시에 `unreadableProperties`(필터가 있을 때 `properties === null` 인 문서 수)와 키 존재 여부를 센다
3. 정렬: `titleMatched === true` 묶음이 먼저, 각 묶음 안은 `updatedAt` **내림차순** (F-284 4.3)
4. `total` 은 자르기 전 개수, `hits` 는 `options.limit ?? RESULT_LIMIT`(=200) 개까지, `truncated = total > limit`
5. `unreadableProperties` 는 **필터가 0개면 언제나 0** 이다 — 필터가 없으면 속성을 못 읽어도 빠지는 문서가 없다

- `updatedAt` 이 같은 두 문서의 앞뒤는 정하지 않는다(`Array.prototype.sort` 는 안정 정렬이라 받은 순서가 유지된다). 테스트에서 같은 `updatedAt` 을 쓰지 않는다

## 8. 발췌·강조

### 8.1 조각 배열

```ts
export type SnippetPart = { text: string; hit: boolean }
```

React 가 조각마다 `<span>` 을 그린다. `dangerouslySetInnerHTML` 을 쓰지 않는다 (F-284 4.3). 자르는 기준은 **F-286 이 정규화해 넣은 문자열**이고 원문 좌표로 되돌리지 않는다 (F-284 4.2)

### 8.2 `highlightParts(source, query)` — 자르지 않는다 (제목용)

- `source` 전체를 매치 조각과 나머지로 나눈다
- 매치 범위 계산: 검색어마다 **모든 등장 위치**를 `foldCase(source)` 에서 찾고, 시작 위치로 정렬한 뒤 **겹치거나 맞닿은 범위를 하나로 합친다**(`start <= 앞 범위의 end`). 검색어 `회고`·`고록` 이 `회고록` 에서 각각 [0,2)·[1,3) 으로 겹치면 `[{회고록, hit}]` 하나가 된다
- 공백 접기(8.4)를 적용한다
- `source === ''` 면 `[]`

### 8.3 `buildSnippet(source, query)` — 창을 잘라낸다 (본문용)

| 단계 | 규칙 |
| --- | --- |
| 1. 기준 위치 | 검색어들의 **첫 매치 중 가장 앞선 것**. 위치가 같으면 `query.terms` 에서 앞선 검색어 |
| 2. 창 | `start = max(0, 첫매치시작 - 30)`, `end = min(길이, 첫매치끝 + 70)`. 단위는 **코드유닛** |
| 3. 검색어가 0개이거나 본문에 매치가 없을 때 | `start = 0`, `end = min(길이, 100)` — 필터만 있는 검색(`tag:일기`)에서도 본문 앞부분을 보여준다 |
| 4. 서로게이트 쌍 보호 | `start` 가 하위 서로게이트(`U+DC00~U+DFFF`) 자리면 1 줄이고, `end - 1` 이 상위 서로게이트(`U+D800~U+DBFF`)이며 `end < 길이` 면 1 줄인다. 이모지가 반으로 잘려 `�` 가 되는 것을 막는다 |
| 5. 강조 | 창 **안에서** 8.2 와 같은 방식으로 모든 매치를 표시한다. **창은 1개**(문서당 발췌 1개, F-284 4.3)이고 창 안의 매치 수는 세지 않는다 |
| 6. 공백 접기 | 8.4 |
| 7. 말줄임 | `start > 0` 이면 맨 앞에, `end < 길이` 면 맨 뒤에 `…`(U+2026). **`hit: false` 인 이웃 조각의 글자에 붙이고**, 이웃이 `hit: true` 면 `{ text: '…', hit: false }` 조각을 새로 넣는다 |
| 8. 빈 본문 | `source === ''` → `[]`. 접은 결과가 비어도 `[]` |

### 8.4 공백 접기

| # | 규칙 |
| --- | --- |
| 1 | `/\s/` 에 맞는 글자의 연속(줄바꿈 포함)은 공백 하나로 접는다 |
| 2 | 조각 경계를 넘는 연속도 **하나로** 접는다 (조각마다 따로 접지 않는다) |
| 3 | 접힌 공백 하나는 **`hit: false` 쪽 조각에 붙인다.** 강조 표시에 공백이 끼면 안 된다. 양쪽이 모두 `hit: true` 인 경우는 없다 — 맞닿은 매치 범위는 8.2 에서 이미 합쳐진다 |
| 4 | 발췌 전체의 맨 앞·맨 뒤 공백은 뗀다 (말줄임을 붙이기 전에) |
| 5 | 접은 뒤 빈 문자열이 된 조각은 버린다 |

확인한 결과(프로토타입 실행):

| 입력 | 결과 |
| --- | --- |
| `highlightParts('주간  회고 정리', q('회고'))` | `[{'주간 ',false},{'회고',true},{' 정리',false}]` — 공백이 hit 밖에 있다 |
| `highlightParts('주간\n회고\n정리', q('회고'))` | 위와 같다 |
| `highlightParts('회고록', q('회고 고록'))` | `[{'회고록',true}]` — 겹친 범위 합침 |
| `highlightParts('회고록', q('회고 록'))` | `[{'회고록',true}]` — 맞닿은 범위 합침 |
| `buildSnippet('짧은 회고', q('회고'))` | `[{'짧은 ',false},{'회고',true}]` — 말줄임 없음 |
| `buildSnippet('회고' + 'x'*200, q('회고'))` | `[{'회고',true},{' xxx…69개…x…',false}]` — 앞에는 말줄임이 없고 뒤에만 있다 |
| `buildSnippet(본문, q('tag:일기'))` | 검색어가 없으므로 본문 앞 100자, `hit` 조각 없음 |
| `buildSnippet('x'+'😀'*20+'회고'+'😀'*60, q('회고'))` | 앞뒤 `…`, 고아 서로게이트·`�` 없음 |

## 9. 성능 (이 PC, Node v24.12.0 에서 직접 쟀다)

스크래치패드에 3~8장 규칙을 그대로 구현한 프로토타입과 합성 문서 생성기를 만들어 쟀다. 문서 규모는 F-284 5.1 의 가정(문서 평균 4.2천자)을 따랐다. **5회 실행의 중앙값**

### 9.1 실측값

| 항목 | 문서 1,000개 (4.2M자) | 문서 5,000개 (21.0M자) |
| --- | --- | --- |
| (a) `parseSearchQuery` 1회 (`tag:일기 "주간 회고" 메모`) | 0.04ms | 0.00ms |
| (a) `parseSearchQuery` 1,000회 | 2.58ms | 1.50ms |
| (b) `searchDocs` — 검색어 1개 (593 / 2,964건 매치) | 9.68ms | 41.08ms |
| (b) `searchDocs` — 검색어 3개 | 9.52ms | 42.06ms |
| (b) `searchDocs` — 검색어 10개 | 9.53ms | 42.79ms |
| (b) `searchDocs` — **어느 문서에도 없는 검색어 1개** | 10.57ms | 56.40ms |
| (b) `searchDocs` — 필터만 (`tags:일기`) | 0.75ms | 1.42ms |
| (b) `searchDocs` — 필터 + 본문 검색어 | 3.31ms | 15.30ms |
| 참고: `foldCase(본문)` 전부만 | 7.82ms | 38.21ms |
| 참고: `toLowerCase(본문)` 전부만 | 7.85ms | 39.56ms |
| (c) `buildSnippet` 200개 (검색어 1개) | 2.92ms | 2.38ms |
| (c) `buildSnippet` 200개 (검색어 10개) | 4.09ms | 4.30ms |

읽는 법:

- **키 입력 한 번당 전체 비용 = (a) + (b) + (c).** 최악(5,000개, 매치 없는 검색어)이 약 **61ms** 로 디바운스 150ms(F-284 5.1) 안에 들어간다
- **검색어 개수는 거의 영향이 없다.** 문서마다 첫 실패에서 끊고(7.2), 시간의 대부분이 소문자화이기 때문이다 — `foldCase` 만으로 매칭 시간의 **93%**(1,000개 7.82/9.68·5,000개 38.21/41.08)다. 4.3 에서 검색어 개수 상한을 두지 않기로 한 근거다
- **매치가 없는 검색어가 가장 느리다.** 본문을 끝까지 훑어야 없다고 말할 수 있다
- **필터가 있으면 빨라진다.** 필터에서 떨어진 문서는 소문자화를 하지 않는다(1/3만 통과하는 합성 데이터에서 41ms → 15ms)
- **발췌는 문서 수와 무관**하다. 상한 200개 × 창 100자뿐이다
- **쿼리 파싱은 잴 필요가 없는 수준**이다(1회 0.002ms 안팎)
- `foldCase` 의 빠른 길이 `toLowerCase` 와 같은 값이다 — 길이 검사 한 번은 공짜다

### 9.2 `foldCase` 느린 길

| 본문 4.2천자 1개 | 시간 |
| --- | --- |
| 빠른 길(보통 본문) | 0.004ms |
| 느린 길(`İ` U+0130 이 든 본문) | 0.119ms |

- 30배지만, **`İ` 가 든 문서에서만** 돈다. 계정의 문서 1,000개가 전부 그런 문서라는 최악에도 119ms 다. 터키어 본문이 아니면 사실상 일어나지 않는다
- 브라우저에서는 재지 않았다. **저장소 읽기를 포함한 브라우저 실측은 F-286 의 게이트**다 (F-284 5.1)

### 9.3 메모리

이 모듈은 문서를 들고 있지 않는다. 검색 한 번에 `foldCase` 사본 **문서 하나 분량**(≤ 수십 KB)이 잠깐 생겼다 사라진다. 인덱스 메모리는 F-286 몫이다
