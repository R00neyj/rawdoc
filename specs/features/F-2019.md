**직접 재거나 돌린 것** (2026-09-23, 이 PC, Node v24.13.0·Chrome. 다른 세션이 같이 돌아 편차가 크다. 스크립트는 스크래치패드에만 있다)
- (a) **Playwright 폴더 선택.** 이 저장소 Playwright 1.63.0 + Chrome 채널로 `hidden` 이고 **속성(`input.webkitdirectory = true`)으로 켠** 파일 입력에 디렉터리를 `setInputFiles` 하면 된다. 받은 `File` 네 개의 `webkitRelativePath` 는 `내 볼트/루트.md`·`내 볼트/위키/개념/a.md`·`내 볼트/attachments/그림.png`·`내 볼트/.obsidian/app.json` — **첫 조각이 고른 폴더 이름, 점 폴더 안 파일도 온다, 빈 폴더는 오지 않는다.** `webkitdirectory` 가 없는 입력에 디렉터리를 주면 `File input does not support directories` 로 던진다
- (b) **합성 끌어놓기.** `new DataTransfer()` 에 `File` 을 넣어 `drop` 을 보내면 `item.kind === 'file'` 이고 `item.webkitGetAsEntry()` 는 **`null`** 이다. 그래서 기존 `F-145` e2e(합성 드롭)는 `null` 을 "파일" 로 보는 한 바뀌지 않고, 폴더 끌어놓기는 e2e 로 만들 수 없다(개요 4.1 그대로 사람 확인)
- (c) **markdown-it 문단 경계.** 이 저장소 `markdown-it`(`html: false`, 보기 모드와 같은 설정)에서 F-156 블록 3줄 바로 앞이나 뒤에 빈 줄 없이 글 줄이 붙으면 그 문단은 **4줄**이 되어 `parseImageBlock`(정확히 3줄)이 실패한다. 목록 항목 바로 뒤도 4줄(느슨한 이어짐). 제목 줄 바로 뒤와 앞뒤에 빈 줄이 있을 때만 3줄. 개요 4.4 의 "그 줄을 블록으로 바꾼다" 에 빈 줄 규칙이 필요한 근거(5.3)
- (d) **1차 훑기 비용.** fflate 로 만든 zip(`.md` 2,000개 + PNG 크기의 무작위 바이트 200개 × 500KB, 100MB)을 64KB 조각으로 `Unzip` 에 밀어 넣었다. `.md` 만 읽기 1.4~2.4초, `.md` + 이미지 전부 읽고 SHA-256 까지 1.9~3.6초(세 번씩, 무압축·압축 두 종류). 데이터 디스크립터 zip 은 건너뛰는 항목도 끝을 찾으려 훑어야 해 차이가 편차 안에 든다. SHA-256 자체는 `crypto.subtle.digest` 로 100MB 에 66~188ms. 6.2 의 근거
- (e) **임베드 찾기 비용.** 5.1 규칙을 옮긴 시제품으로 문서 5,000개(1,690만 글자, 임베드 3만 개)를 훑는 데 242~481ms. 넣을 폴더를 바꿀 때마다 다시 훑으면 안 된다는 근거(7.4)

## 사용자가 이미 정한 것 (바꾸지 않는다)

F-2016 1~5장·8장 "기본값으로 정한 것" 과 16장 답 전부. 이 명세에 닿는 것만 다시 적는다

1. **다시 가져오기 = 경로로 맞춰 덮기**(전제 2). 넣을 폴더 안에서 `폴더 경로 + 파일명` 이 같은 문서를 갱신하고 id·공개 링크를 유지한다. 덮기 전 사본은 F-282 규칙
2. **입구: zip + 폴더 선택 + 폴더 끌어놓기**(전제 3)
3. **이미지는 가져올 때 이 앱 형식으로 변환**(전제 4). 파일은 첨부로. 왕복하면 이미지 파일명이 바뀌는 대가를 받아들였다
4. **`manifest.json` 없는 zip 은 전부 볼트 가져오기**(개요 Q3, 사용자가 기본값 선택). F-282 3.7 을 대체한다
5. **볼트에 없는 문서는 그대로 둔다, 본문이 같으면 건너뛴다**(개요 Q4·Q5)
6. **줄 가운데 이미지는 바꾸지 않는다**(개요 Q9), **넣을 폴더를 기억하지 않는다**(Q12), **`옵시디언 볼트` 라는 말**(Q13)
7. 새 의존성 없음. 저장소 인터페이스(`Store`)를 바꾸지 않는다(개요 6.1)
8. **구현 순서는 F-2018 → F-2020 → F-2019**(사용자 2026-09-23, 17장 Q10 — 개요 6.1 의 원래 차례 F-2019 → F-2020 을 뒤집음)
9. **볼트 이미지의 첨부 id 는 내용 해시(SHA-256 앞 16자)**(사용자 2026-09-23, 17장 Q1 — 개요 4.4 의 "새 id" 를 대체)

## 2. 범위

### 한다

- 입구 셋 — `manifest.json` 없는 zip(설정 `가져오기…`, F-282 입구 그대로), 폴더 선택(설정 `폴더 가져오기…`), 폴더 끌어놓기(창 전체)
- 미리보기에 `넣을 폴더` 선택, 기본값 규칙, 바꾸면 요약이 곧바로 바뀜
- 경로로 맞춰 새로·갱신·건너뜀, 볼트에 없는 문서 그대로
- 이미지 임베드(`![[그림.png]]`·`![](그림.png)`)를 F-156 블록으로, 파일은 첨부로
- 이미 이 앱 형식인 블록(`attachments/{16hex}.{ext}`)의 첨부 들이기
- **앱 안에서 다른 문서로 풀리거나 안 풀리게 될 위키링크만** 앱 형태로 되돌리기, F-2020 이 붙인 별칭 접기(7.8 — F-2020 13장 Q2 를 받음)
- 볼트 이름 끝 `-vault` 떼기(4.4 — F-2020 13장 Q7 을 받음)

### 하지 않는다

- `manifest.json` 있는 zip — F-282 3.6 그대로(개요 4.7)
- 이미지가 아닌 임베드·`#태그`·각주·`aliases`·마크다운식 내부 링크·`.canvas`(개요 4.5). 앱에서 볼트와 같은 문서로 풀리는 위키링크는 손대지 않는다 — 해석은 F-2018
- 볼트에서 옮기거나 지운 파일 알아내기(개요 Q4), 넣을 폴더 기억하기(Q12)
- **어느 문서도 쓰지 않는 이미지 파일** 들이기 — F-282 3.7 과 같다(세지도 않는다). 옵시디언으로 되내보내면 그 파일은 없다(17장 Q8)
- 옵시디언 내보내기 — F-2020

## 3. 흐름

1. 입구에서 볼트 원천을 얻는다(4장). 시작 전에 `await saver.flush()`(F-282 3.1 과 같은 이유)
2. **1차 훑기**(6장) — `.md` 본문과 이미지 해시를 모은다. zip 은 이때 `manifest.json` 도 본다 — 있고 `detectZipKind` 가 `workspace` 면 F-282 3.6 으로, `rejected` 면 F-282 거부 알림으로 끝
3. 저장소에서 `store.list()`(본문·`createdAt` 이 든 전체 문서)·`store.listFolders()`·`store.listAttachments()` 를 한 번 읽는다
4. 넣을 폴더 기본값(7.1)으로 계획(7장 — 경로 맞추기·링크 되돌리기·이미지 블록·판정)을 세워 미리보기를 연다
5. 넣을 폴더를 바꾸면 3 의 목록과 1 의 훑은 결과로 계획을 다시 세운다 — 순수 함수, 저장소·zip 을 다시 읽지 않는다
6. `가져오기` → 적용(9장): 넣을 새 폴더 → 폴더 → 이미지(2차 훑기) → 문서
7. 끝나면 F-282 3.9 의 알림·결과 단계, 목록 새로 읽기, 열린 문서 재마운트. **넣을 폴더와 그 조상을 사이드바에서 펼친다**(17장 Q4)

## 4. 입구

### 4.1 zip

- 설정 `데이터` 탭 `가져오기…` 와 파일 입력 `input[data-import="zip"]` 은 F-282 그대로
- 1차 훑기의 `want` 를 넓힌다: `manifest.json`, `.md`·`.markdown`, 이미지 확장자(6.1). F-282 가 `manifest.json`·`.md` 만 읽던 것에 이미지를 더한다 — 머리 (d) 로 추가 시간이 편차 안임을 확인했다. `manifest.json` 이 zip 맨 앞(F-281 `exportWorkspace` 가 첫 항목으로 넣는다)이어도 이미지 읽기를 끄지 않는다 — 볼트 안에 우연히 같은 이름 파일이 있으면 해시가 비어 다시 훑어야 한다
- 볼트 이름: F-282 3.7 의 공통 최상위 벗기기로 벗긴 디렉터리 이름. 벗기지 않았으면 zip 파일 이름에서 끝 `.zip`(대소문자 무시)을 뗀 것, 없으면 파일 이름 전체. NFC 로 바꾼다. 그다음 4.4 의 `-vault` 떼기
- 미리보기 대화상자의 파일 이름 줄은 F-282 그대로 zip 파일 이름

### 4.2 폴더 선택

- 설정 `데이터` 탭에 `폴더 가져오기…`(10.1). 누르면 **설정을 닫고**(F-282 3.1 과 같은 이유) 숨은 입력을 누른다
- 입력: `<input type="file" data-import="folder" hidden>`. `webkitdirectory` 는 React 19 JSX 타입에 없으므로 **ref 콜백에서 `el.webkitdirectory = true` 로 켠다**(`lib.dom.d.ts` 의 `HTMLInputElement.webkitdirectory: boolean`). `multiple`·`accept` 는 두지 않는다
- 받은 `File` 마다 경로 = `webkitRelativePath`. 첫 조각이 볼트 이름(NFC, 그다음 4.4), 모든 경로에서 첫 조각을 벗긴다. 조각이 하나뿐인 경로는 버린다(생기지 않지만 방어)
- 파일이 0개면(빈 폴더) 아무것도 하지 않는다 — 폴더 이름조차 알 수 없다. 입력 값은 F-282 처럼 비워 같은 폴더를 연달아 고를 수 있게
- 미리보기 파일 이름 줄 = 고른 폴더 이름(4.4 로 떼기 전)

### 4.3 폴더 끌어놓기 (F-145 창 전체 끌어놓기 확장)

**판정** — `drop` 이벤트 안에서 **동기로** `dataTransfer.items` 중 `kind === 'file'` 인 것마다 `webkitGetAsEntry()` 를 부른다(이벤트가 끝나면 목록에 닿을 수 없다). 결과는 `classifyDroppedEntries` 로:

| 항목 | 결과 |
| --- | --- |
| 디렉터리 0개 | `none` — 지금 F-145 흐름 그대로. **`null` 은 파일로 센다**(머리 (b) — 합성 드롭은 전부 `null`) |
| 디렉터리 1개, 다른 항목 0개 | `folder` — 그 디렉터리로 볼트 가져오기 |
| 디렉터리 2개 이상, 또는 디렉터리 1개 이상 + 파일 1개 이상 | `too-many` — 알림(`info`) `폴더는 한 번에 하나만 가져올 수 있습니다.` 아무것도 들이지 않는다 |

- 막는 때: 지금 `.md` 끌어놓기가 막히는 때와 같다 — `imageDropBlockedRef`(대화상자·공유 화면·지도 등)면 판정 전에 돌아가고, 메모리 저장소(`dropBlockedRef` 가 참인 나머지 경우)면 `folder`·`too-many` 둘 다 **조용히** 무시한다(`.md` 가 그렇듯)
- 편집 영역 위에 놓아도 된다 — `dropFileGuard`(`createEditor.ts`)가 외부 파일 끌기를 CM6 기본 삽입에서 막고 버블시키고, `imageInsert` 의 `drop` 은 이미지 확장자 파일이 없으면 손대지 않는다. 폴더와 이미지 파일을 섞어 편집 영역에 놓으면 `imageInsert` 가 이미지만 넣고 전파를 막는다 — 지금 동작이고 바꾸지 않는다
- 덮개: 지금처럼 이미지만 끌 때가 아니면 뜬다(디렉터리 항목은 `type` 이 비어 `isImageOnlyDrag` 가 거짓). 문구만 `여기에 놓아 .md 파일·폴더 가져오기`

**읽기** — `readDroppedDirectory(루트 디렉터리 항목)`:

- `createReader().readEntries` 는 한 번에 일부만 줄 수 있다 — **빈 배열이 올 때까지** 같은 리더로 다시 부른다
- 하위 디렉터리는 재귀로 읽는다. **이름이 `.` 으로 시작하거나 `__MACOSX` 인 디렉터리는 들어가지 않는다** — `.git` 에 파일이 수만 개 있어도 읽지 않게. 어차피 `isNoiseEntry` 가 버릴 것들이다
- 파일 항목은 `file()` 로 `File` 을 얻는다. 경로 = 항목 `fullPath` 에서 맨 앞 `/` 를 뗀 것 — 첫 조각이 루트 디렉터리 이름이라 4.2 의 `webkitRelativePath` 와 같은 모양이 된다
- 어느 단계든 오류 콜백이 불리면 전체를 거부한다 → 알림(`error`) `가져오지 못했습니다.`(F-282 문구)
- 그 뒤는 4.2 와 같다(첫 조각 = 볼트 이름, 파일 이름 줄 = 놓은 폴더 이름)

```ts
// src/app/fileDrop.ts (F-2019)
export type DropClass = { kind: 'none' } | { kind: 'folder'; entry: FileSystemDirectoryEntry } | { kind: 'too-many' }
export function classifyDroppedEntries(entries: ReadonlyArray<FileSystemEntry | null>): DropClass
export function readDroppedDirectory(root: FileSystemDirectoryEntry): Promise<Array<{ path: string; file: File }>>
```

- 두 함수는 DOM 전역을 쓰지 않는다 — 단위 테스트는 같은 모양의 가짜 객체(`isFile`·`isDirectory`·`name`·`fullPath`·`createReader`·`file`)를 넣는다

### 4.4 볼트 이름 끝 `-vault` 떼기 (세 입구 공통)

- 4.1~4.3 으로 정한 볼트 이름이 정확히 `-vault`(소문자, F-2020 이 붙이는 글자)로 끝나고 뗀 나머지가 비지 않으면 뗀다. `교안-vault.zip`·풀어 놓은 `교안-vault/` → `교안`. 그래서 F-2020 폴더 내보내기를 되가져올 때 넣을 폴더 기본값(7.1)이 원래 폴더 `교안` 을 찾는다(F-2020 13장 Q7 기본값)
- 전체 내보내기 `2026-09-23-vault` 는 `2026-09-23` 이 되고, 그런 폴더가 없으니 기본값은 `새 폴더 "2026-09-23"` 이다 — 전체 볼트는 사용자가 `최상위` 를 고른다(개요 4.2 그대로)
- 대소문자가 다른 `-Vault`·`-VAULT` 는 떼지 않는다 — F-2020 이 만들지 않는 이름이고, 사용자가 직접 지은 이름일 수 있다
- 미리보기 파일 이름 줄(zip 은 파일 이름, 폴더는 볼트 이름)은 뗀 뒤의 볼트 이름이 아니라 **원래 이름**을 보인다 — 무엇을 골랐는지 알아보게. `새 폴더 "{볼트 이름}"` 선택지는 뗀 이름

### 5.1 찾기 — `findVaultEmbeds`

**보지 않는 곳**

- 프론트매터 — `findFrontmatter`(`src/lib/frontmatter.ts`)가 준 범위
- 펜스 코드블록 — 줄 앞 공백 0~3칸 뒤 `` ` `` 또는 `~` 3개 이상으로 열고, 같은 글자가 연 길이 이상이고 뒤에 공백만 있는 줄로 닫는다(`comments.ts` 의 펜스 판정과 같은 규칙). 닫히지 않으면 문서 끝까지
- 인라인 코드 — 한 줄 안에서 같은 길이의 백틱 묶음 사이. 줄을 넘는 인라인 코드는 보지 않는다(드묾, 넘어가면 그 안 임베드도 찾아진다)
- 들여쓴 코드블록은 따로 가리지 않는다 — 그 안 임베드는 줄 앞 공백이 있어 바꾸지 않고(5.2) 세기만 한다

**찾는 모양**

| 모양 | `syntax` | `target` | `caption` · `width` |
| --- | --- | --- | --- |
| `![[그림.png]]` | `wiki` | `[[` 와 첫 `\|` 사이(없으면 `]]` 까지), 앞뒤 공백 제거 | 없음 |
| `![[그림.png\|300]]`, `![[그림.png\|300x200]]` | `wiki` | 같음 | `width` 300 (높이는 버린다) |
| `![[그림.png\|설명]]` | `wiki` | 같음 | `caption` `설명` |
| `![[그림.png\|설명\|300]]` | `wiki` | 같음 | 마지막 조각이 크기 모양이면 `width`, 그 앞 조각들을 `\|` 로 다시 이은 것이 `caption` (17장 Q5) |
| `![설명](그림.png)`, `![설명](그림.png "제목")` | `markdown` | 괄호 안 경로, 제목 문자열은 버린다 | `caption` `설명`(비면 없음). `[설명\|300]` 이면 위 표와 같은 규칙으로 나눈다 |
| `![](<그림 1.png>)` | `markdown` | `<` `>` 를 벗긴 것 | 없음 |
| `![](a%20b.png)` | `markdown` | `%XX` 를 푼 것(`decodeURIComponent`, 실패하면 원래 글자) | 없음 |

- 크기 모양은 `^\d+(x\d+)?$`. 폭이 **1~9999** 일 때만 `width` 로 쓴다 — F-156 `parseImageBlock` 의 `WIDTH_RE` 가 4자리까지만 받기 때문이다. 0 이나 10000 이상은 크기가 없는 것으로 본다(글자는 버린다)
- `target` 이 스킴(`^[A-Za-z][A-Za-z0-9+.-]*:` — `https:`·`data:`·`file:` 등)이나 `//` 로 시작하는 `markdown` 임베드는 **결과에 넣지 않는다**(바꾸지도 세지도 않는다, 개요 4.4)
- `kind`: `target` 의 마지막 조각이 `.png` `.jpg` `.jpeg` `.gif` `.webp` `.svg` `.bmp` `.avif`(대소문자 무시)로 끝나면 `image`, 아니면 `other`(`![[노트]]`·`![[x.pdf]]`·`![[노트#헤딩]]`)
- `standalone`: 임베드가 줄 첫 칸에서 시작하고, 그 줄에 다른 임베드가 없고, 임베드 뒤에 공백·탭만 있다. 줄 앞 공백·`>`·목록 기호가 있으면 거짓

### 5.2 바꾸는 조건

`kind === 'image' && standalone` 이고 파일을 찾았고(7.3) 첨부로 넣을 수 있을 때(6.2·9.3)만 그 줄을 블록 3줄로 바꾼다. 나머지는 원문 그대로 두고 경고 `원문 그대로 둔 이미지·임베드 {N}개` 에 **한 번씩** 센다(같은 임베드가 두 번 나오면 두 번)

| 경우 | 센다 |
| --- | --- |
| `kind === 'other'` | 예 |
| `image` 인데 `standalone` 이 아님(문단 가운데·목록·인용·콜아웃 안·한 줄에 둘 이상) | 예 |
| 파일을 볼트에서 못 찾음 | 예 |
| 확장자가 `.svg`·`.bmp`·`.avif` | 예 |
| 확장자는 PNG·JPEG·GIF·WebP 인데 내용이 아님, 5MB 초과 | 예 + 결과 실패 목록(9.3) |
| 적용 때 올리기 실패·저장 공간 초과 | 미리보기에서는 알 수 없다 — 실패 목록·F-282 공간 알림만 |

### 5.3 블록으로 바꾸기 — `embedsToImageBlocks`

- 바꿀 임베드마다 그 **줄 전체**를 `buildImageBlock({ id, ext, alt, width, align })` 3줄로 바꾼다
- **빈 줄 규칙** — 바꾼 블록 바로 위 줄이 있고 빈 줄(공백·탭만)이 아니면 사이에 빈 줄 하나를 넣는다. 바로 아래 줄도 같다. 바꾼 블록 둘이 원래 이웃한 줄이었으면 사이에 빈 줄 **하나만**. 이유: 머리 (c) — 붙어 있으면 보기 모드(markdown-it 문단)와 편집 모드(CM6 `HTMLBlock` 이 빈 줄까지 이어짐) 둘 다 블록으로 읽지 않는다. `computeImagePlacement`(`imageInsert.ts`)가 붙여넣기 블록 앞뒤에 빈 줄을 두는 것과 같은 이유
- 원래 앞뒤가 빈 줄인 임베드(옵시디언이 붙여 넣은 이미지, F-2020 이 블록을 되돌린 줄)는 줄 수가 3줄로 늘 뿐 빈 줄이 더해지지 않는다 — 5.4 왕복이 바이트까지 같아지는 전제
- 바꾸지 않는 임베드와 나머지 글자는 한 글자도 바꾸지 않는다

- width 없는 블록은 편집기(`imageWidget.ts` 가 `box.style.width` 를 비움)와 `image.css`(`width: fit-content; max-width: 100%`)에서 원래 크기까지만 보인다 — 코드로 확인했다. 모양은 사람 확인 H-b

## 6. 1차 훑기 — `scanVault`

### 6.1 무엇을 읽는가

- 경로 정규화·잡음·`..`·공통 최상위 벗기기는 F-282 3.7 규칙 그대로(`isNoiseEntry` 를 내보내 같이 쓴다). 폴더 입구는 4.2 의 첫 조각 벗기기만 하고 공통 최상위 벗기기를 **더 하지 않는다** — 고른 폴더가 볼트 루트다
- 경로는 논리용으로 **NFC** 로 바꿔 쓰고, 2차 훑기에서 항목을 찾을 원래 이름도 함께 둔다
- 바이트를 읽는 것(`vaultWantsBytes`): `.md`·`.markdown`, `.png` `.jpg` `.jpeg` `.gif` `.webp`(대소문자 무시). `.svg`·`.bmp`·`.avif` 는 바꾸지 않으므로 이름만
- 문서: `decodeMarkdown` — UTF-8 이 아니면 F-282 처럼 계획에는 `create` 로 넣고 적용 때 실패 목록 `{제목} — 이 문서는 UTF-8 로 읽을 수 없어 가져오지 못했습니다`. 문서 본문은 메모리에 둔다(F-282 미리보기도 이미 그렇다). 임베드 목록(5.1)과 이미지 참조(7.3)를 **여기서 한 번** 구한다(머리 (e))
- 제목: 파일 이름에서 `.md`·`.markdown` 을 뗀 것, 비면 `제목 없는 문서`(F-282 `titleFromPath`), NFC. 폴더 이름: 경로 조각, NFC. 본문은 정규화하지 않는다(개요 4.3)
- 이미지: 바이트는 해시·형식·크기만 보고 버린다. 메모리에는 한 번에 한 장
- 그 밖의 파일(`.pdf`·`.canvas`·`.txt` 등, 이미지 확장자 제외)은 세어 경고 `.md 가 아니라 건너뛴 파일 {N}개`(F-282 문구). 이미지 확장자 파일은 쓰이든 안 쓰이든 세지 않는다(F-282 의 `attachments/` 파일과 같은 취급)
- 파일 읽기가 실패하면(폴더 입구에서 그 사이 지워진 파일 등) 문서는 적용 때 실패 목록 `{제목} — 가져오지 못했습니다`, 이미지는 "내용이 아님" 과 같게(5.2 표)

### 6.2 이미지 식별

| 파일 | 첨부 id | ext |
| --- | --- | --- |
| 이름이 `^[0-9a-f]{16}\.(png\|jpg\|gif\|webp)$` 이고 `inspectImageBytes` 의 `ext` 가 이름의 확장자와 같음 | 이름의 16진수(개요 4.4 — F-2020 으로 내보낸 이미지가 같은 첨부로 돌아오는 길) | 이름의 확장자 |
| 그 밖에 `inspectImageBytes` 가 알아본 것 | **내용 해시** — 파일 바이트의 SHA-256 앞 8바이트를 소문자 16진수 16자로 (17장 Q1) | 7.5·9.3 이 정한다 |
| 알아보지 못함 또는 5,242,880 바이트 초과(`MAX_ATTACHMENT_BYTES`) | 없음 — 이 파일을 가리키는 임베드는 원문 그대로(5.2) | — |

- 해시 함수는 인자로 받는다(기본 `crypto.subtle.digest('SHA-256', …)`). Node 24 테스트 환경에 `crypto.subtle` 이 있다(머리 (d) 에서 돌렸다)
- 내용이 같은 파일은 이름이 달라도 한 첨부가 된다 — 개요 4.4 "같은 파일을 여러 문서가 쓰면 한 번만 올린다" 를 이름이 다를 때까지 넓힌 것
- 해시 충돌(서로 다른 이미지가 같은 앞 8바이트, 2⁻⁶⁴ 안팎)은 막지 않는다. `putAttachment({ id })` 는 있는 id 를 덮지 않으므로 먼저 들어온 그림이 보인다

### 7.1 넣을 폴더

```ts

export function defaultVaultTarget(scan: VaultScan, folders: readonly Folder[]): VaultTarget
// value: 'new' | 'top' | `folder:${id}`, label: 10.2 문구
```

- 기본값: `parentId === null` 이고 이름을 NFC 로 바꾼 것이 볼트 이름과 **정확히 같은**(대소문자 구분) 폴더가 **하나**면 그 폴더, 없거나 둘 이상이면 `new`(개요 4.2)
- 선택지 순서: `new`, `top`, 그다음 `flattenFolderTree(folders)` 순서(폴더로 이동 대화상자와 같은 순서)의 모든 폴더. 라벨의 경로는 `folderPathMap`(`searchIndex.ts`, `상위 / 하위`)
- `new` 는 적용 때 최상위에 볼트 이름으로 만든다. 계획에서는 "기존 트리가 빈 폴더" 로 본다 — 모든 문서가 `create`

### 7.2 기존 트리 — 넣을 폴더 T 아래 내 문서

- 대상: `role` 이 `owner` 이거나 없는 문서(개요 4.3). T 가 폴더면 `descendantFolderIds(folders, T)`(T 자신 포함)에 든 폴더의 문서, `top` 이면 내 문서 전부. T 밖 문서는 이름이 같아도 건드리지 않는다. 이 고르기는 `selectExportScope(docs, folders, 범위)`(8.2) 그대로다 — 범위는 T 가 폴더면 `{ kind: 'folder', folderId: T }`, `top` 이면 `{ kind: 'all' }`
- 각 폴더·문서가 **지금 옵시디언으로 내보내진다면 받을 경로**를 `planExportPaths(고른 docs, 고른 folders, rootFolderId, { fileName: toObsidianFileName, folderName: toObsidianFolderName })`(8.2)로 구한다. 경로는 T 기준 상대 경로다. F-2020 의 zip 경로와 **같은 함수의 같은 결과**라야 왕복이 맞는다

### 7.3 볼트 안 파일 찾기 (넣을 폴더와 무관 — 1차 훑기 때 한 번)

| 임베드 | 찾는 순서 |
| --- | --- |
| `wiki` | F-2018 해석기를 **볼트 파일로** 만든다 — 볼트 디렉터리마다 가상 폴더(id = NFC 디렉터리 경로, 이름 = 마지막 조각, 부모 = 윗 디렉터리 경로, 루트는 `null`), 이미지 확장자 파일마다 가상 문서(id = NFC 파일 경로, 제목 = 확장자까지 든 파일 이름, 폴더 = 든 디렉터리). 문서 목록 순서는 NFC 경로의 코드 단위 오름차순(= 해석기 4단계 "목록 앞" 이 경로순). `resolve(target, 임베드를 가진 문서의 디렉터리)` — 이름만이면 볼트 전체, `하위/그림.png` 면 끝 맞추기, 여럿이면 가까운 폴더(개요 4.4 가 3.2·3.3 에 맡긴 것을 해석기 그대로) |
| `markdown` | 앞 `/` 가 없으면 ① 문서 디렉터리 기준 상대 경로(`./`·`../` 를 풀고, 루트를 벗어나면 이 단계 없음) → ② 볼트 루트 기준 → ③ 같은 파일 이름(대소문자 무시)이 볼트에 **하나뿐**이면 그것. 앞 `/` 가 있으면 떼고 ② → ③. 각 단계에서 NFC 경로 정확 일치, 없으면 대소문자 무시 일치 |
| 원문의 `attachments/{16hex}.{ext}` 참조(F-156 블록 등, `extractAttachmentRefs` 가 잡는 것) | ① 문서 디렉터리의 `attachments/{id}.{ext}`(F-282 3.7) → ② 볼트 루트 `attachments/{id}.{ext}`. 찾으면 그 id 로 들인다. 볼트에도 없고 `store.listAttachments()` 에도 없으면 경고 `가져오지 못한 이미지 참조 {N}개`(F-282 문구). 원문은 바꾸지 않는다 |

- 해석기는 `src/lib/wikiResolve.ts` 의 `createWikiResolver` 를 import 해 쓴다. 가상 문서의 `.md` 떼기 단계는 이미지 이름에 걸리지 않는다

### 7.4 경로 맞추기 — 규칙

T 를 볼트 루트로 놓고 볼트 디렉터리를 **위에서 아래로** 걸으며 맞춘다. 비교는 전부 `키 = NFC 로 바꾼 뒤 toLowerCase()`(F-281 이름 충돌이 이미 `toLowerCase` 로 대소문자를 무시한다, F-2018 4.5 가 `toLowerCase` 를 고른 이유와 같다)

**폴더** — 볼트 디렉터리 D(부모가 이미 기존 폴더 P 에 맞은 것)마다, P 의 자식 폴더 중

1. 옵시디언 내보내기 이름(7.2 경로의 마지막 조각)의 키가 D 이름의 키와 같은 것
2. 없으면 폴더 이름 그대로의 키가 같은 것 (17장 Q3)
3. 없으면 새로 만든다 — 이름은 D 이름(NFC). 그 아래 디렉터리는 전부 새로 만든다

**문서** — 맞은 폴더(또는 T) 안에서, 볼트 문서 파일 이름에서 `.md`·`.markdown` 을 뗀 줄기의 키가

1. 기존 문서의 옵시디언 내보내기 파일 이름(`.md` 를 뗀 것)의 키와 같은 것
2. 없으면 기존 문서 제목 그대로(앞뒤 공백 제거)의 키와 같은 것 (17장 Q3)

- 한 디렉터리 안에서는 볼트 항목을 NFC 경로 오름차순으로 놓고, **1 단계를 모두 끝낸 뒤** 남은 것에 2 단계를 한다. 기존 폴더·문서 하나는 한 번만 맞는다(먼저 맞은 볼트 항목이 가진다)
- 2 단계가 필요한 이유: 옵시디언 이름 함수는 `# ^ [ ]` 를 `_` 로 바꾸고 100자에서 자른다(8.1). 볼트 파일 이름이 `C# 정리.md` 이거나 100자를 넘으면 처음 가져와 만든 문서(제목 `C# 정리`)의 내보내기 이름이 `C_ 정리.md` 라 1 단계로는 영영 안 맞아 **다시 가져올 때마다 같은 문서가 새로 생긴다.** 옵시디언 밖 도구(LLM 등)는 이런 이름을 파일 시스템이 허락하는 한 만든다
- **문서가 하나도 없는 볼트 디렉터리는 폴더를 만들지 않는다**(F-282 3.7 과 같음). 맞추기에서도 건너뛴다

### 7.5 이미지 블록 값

맞은 기존 문서가 있으면 그 원문의 `listImageBlocks` 결과로 **첨부 id → 첫 블록**의 표를 만든다

| 속성 | 값 |
| --- | --- |
| `id` | 6.2 |
| `ext` | 저장소에 그 id 가 있으면(`store.listAttachments()`) 그 `ext` → 없고 이어받을 블록이 있으면 그 블록의 `ext` → 둘 다 없으면 적용 때 정한다(9.3) |
| `align` | 이어받을 블록의 `align`, 없으면 `left` |
| `alt` | 임베드 `caption` → 없으면 이어받을 블록의 `alt` → 없으면 파일 이름에서 확장자를 뗀 것. 이스케이프·100자는 `buildImageBlock` 이 한다 |
| `width` | 임베드 `width`(없으면 없음). 이어받지 않는다 — F-2020 이 블록의 `width` 를 `\|{width}` 로 내보내므로 볼트 쪽이 맞는 값이다 |

- `ext` 두 번째 칸이 필요한 이유: 서버 저장소 `listAttachments` 는 캐시만 읽는다(`serverStore.ts`). 다른 기기에서 들여 서버에만 있는 첨부는 목록에 없지만, 그 첨부를 쓰는 문서 원문은 캐시에 있어 블록으로 알 수 있다. 이어받을 블록으로 `ext` 를 안 첨부는 **있는 것으로 보고 올리지 않는다**

### 7.6 문서마다 판정

맞은 문서는 변환한 원문을 만든다: `toEditorText(볼트 원문)` → 링크 되돌리기(7.8)와 블록 바꾸기(5.3)를 원문 위치로 한 번에 → `fromEditorText(…, 기존 문서 lineEnding)`. 두 편집은 겹치지 않는다 — 바꾸는 임베드 줄에는 그 임베드 하나뿐이다(5.1 `standalone`). `ext` 를 적용 때 정해야 하는 임베드가 하나라도 있으면 "같음" 이 될 수 없다(그 id 를 쓰는 블록이 기존 원문에 없다는 뜻이므로)

| 경우 | 판정 |
| --- | --- |
| 맞음, 변환한 원문이 기존 `content` 와 같음, 이름 바꾸기 없음 | `skip` — 사본 없음, 이미지 안 올림 |
| 맞음, 원문이 다름 | `update` — F-282 3.9 사본 → `store.update(id, { content })`. `lineEnding` 은 바꾸지 않는다 |
| 맞음, 제목과 볼트 줄기가 **NFC 로는 다르고 키로는 같음**(대소문자만 다름) | 제목을 볼트 줄기(NFC)로 바꾼다 — 원문이 같아도 `update`(사본 포함, 17장 Q6). `왜?` ↔ `왜_` 처럼 키도 다르면 바꾸지 않는다 |
| 안 맞음 | `create` — 맞은(또는 새로 만들) 폴더 안, `lineEnding` 은 `decodeMarkdown` 판정 |
| T 아래 내 문서인데 어느 볼트 문서에도 안 맞음 | 그대로. 경고 `볼트에 없어 그대로 둔 문서 {N}개` |

- `counts`: `created`·`updated`·`skipped` 는 위 판정 수, `images` 는 **올릴** 첨부 수(서로 다른 id). `skip` 문서만 쓰는 이미지는 올리지 않는다
- 넣을 폴더를 바꾸면 7.2·7.4~7.6·7.8 만 다시 한다. 7.3 과 임베드·링크 목록은 1차 훑기의 것을 쓴다

### 7.8 링크 되돌리기 (F-2020 13장 Q2 를 받음)

**왜** — F-2020 5.4 는 볼트에서 제 문서로 안 풀릴 링크를 고쳐 내보낸다: `[[왜?]]` → `[[왜_|왜?]]`(파일 이름이 `왜_.md`), 같은 이름이 둘이면 `[[회의록]]` → `[[교안/회의록|회의록]]`. 그대로 되가져오면 앱에는 `왜_` 라는 제목이 없어(7.6 은 기존 제목을 `왜_` 로 바꾸지 않는다) **링크가 끊기고** 누르면 `왜_` 새 문서가 생긴다. 경로만 붙은 링크는 앱에서도 풀리지만 원문이 달라 문서마다 한 번 `update` 된다. 이 절은 **앱에서 볼트와 다른 문서로 풀리거나 안 풀리는 링크만** 앱 형태로 되돌리고, F-2020 이 붙인 모양의 별칭을 접는다. 둘 다 F-2020 이 고친 링크를 첫 왕복에서 원래 바이트로 돌려놓는다

**링크 찾기** — `scanWikiLinks`(F-2020 5.2 계약, 8.3)를 LF 원문에 돌린다. 내보낼 때 고친 것과 **같은 판정**(프론트매터·펜스·인라인 코드 제외, 표 줄은 `inTable`)이라 되돌릴 때도 같은 링크 집합을 본다. 1차 훑기 때 문서마다 한 번

**해석기 둘**

| 해석기 | 만드는 법 |
| --- | --- |
| 볼트 해석기 (1차 훑기 때 한 번) | F-2018 `createWikiResolver` 에 볼트 문서마다 가상 문서(id = NFC 경로, 제목 = NFC 줄기, 폴더 = 든 디렉터리)와 7.3 의 가상 폴더. 문서 순서는 NFC 경로 오름차순. 옵시디언이 같은 이름 파일을 어떻게 고르는지 모르므로(개요 G1) 앱 규칙(가까운 폴더)으로 푼다 — F-2020 이 고친 링크는 볼트 안에서 하나로 풀리게 만든 것이라 어느 규칙이든 결과가 같다 |
| 가져온 뒤 앱 해석기 (계획마다) | `store.list()` 문서 **전부**(공유받은 문서 포함 — 앱 편집기와 같은 풀, F-2018 8.1·F-2020 Q3)에 계획을 입힌 것: 7.6 의 제목 바꾸기를 반영하고, `create` 문서는 자리 id `vault:{NFC 경로}`·볼트 제목·계획된 폴더로 더한다. 폴더는 기존 폴더 + 새로 만들 폴더(자리 id `vaultdir:{NFC 디렉터리 경로}`). 순서는 `create`·`update` 문서(NFC 경로순 — 가져오면 가장 최근이 된다) 다음 나머지(`store.list()` 순서). 자리 id 는 원문에 나타나지 않는다 |

**링크마다** — 볼트 문서 S 의 링크 L(`target` 이 비지 않은 것. `[[#헤딩]]` 은 그대로). S 의 볼트 디렉터리와 S 가 들어갈 앱 폴더(맞은 폴더·새 폴더 자리·T·최상위)를 원본으로 쓴다

1. V = 볼트 해석기로 `resolve(L.target, S 볼트 디렉터리)`. 없으면 그대로(볼트 밖이나 옵시디언에서도 끊긴 링크)
2. D = V 에 대응하는 앱 문서 — 7.4 로 맞은 기존 문서, 아니면 V 의 `create` 자리
3. F = `shortestWikiTarget(앱 해석기, D, S 앱 폴더)`. 앱 해석기로 `resolve(F, S 앱 폴더)` 가 D 가 아니면 그대로(앱에서 D 를 가리킬 글자가 없다 — 제목에 `|`·`#` 이 든 문서 등, F-2018 4.8)
4. H = L 의 `targetFrom`~`targetTo` 원문 조각에서 첫 `#` 부터 끝까지(없으면 빈 글자). N = F + H
5. **별칭 접기** — L 에 별칭 A 가 있고 표 줄이 아니며 A 의 앞뒤 공백을 뗀 것이 N 과 같으면, `[[`·`]]` 사이를 N 으로 바꾼다(별칭을 없앤다). F-2020 5.4 6단계가 붙인 별칭이 이 모양이다
6. 앱 해석기로 `resolve(L.target, S 앱 폴더)` 가 D 면 그대로
7. **되돌리기** — `targetFrom`~`targetTo` 를 N 으로 바꾼다. L 에 별칭이 없고 표 줄이 아니면 `]]` 앞에 `|{원래 보이던 글자}`(F-2018 3.2 — 원문 조각의 앞뒤 공백을 뗀 것)를 넣는다. F-2020 5.4 의 5·6단계를 거꾸로 한 것과 같은 모양이다

| --- | --- | --- |
| `[[왜_\|왜?]]` (최상위) | 최상위 문서 `왜?`(볼트 `왜_.md` 와 맞음) | `[[왜?]]` — 5 |

| `[[회의록 (2)\|회의록]]` (최상위) | 최상위에 `회의록` 둘 — F-2020 이 늦게 만든 쪽을 `회의록 (2).md` 로 내보냈다(F-281 3.2), 앱 해석은 그 쪽 | `[[회의록]]` — 5. `shortestWikiTarget` 은 제목만으로 D 가 풀리면 제목을 준다(`wikiResolve.ts` `shortestWikiTarget` 첫 줄) |
| 위와 같은데 앱 해석이 다른 `회의록` | — | 그대로 — 3. 앱에서 D 를 가리킬 글자가 없다(같은 폴더 같은 제목, F-2018 4.8). 앱에서는 끊긴 채 남는다 |
| `[[없는 글]]`, `[[#결정]]`, `` `[[왜_]]` `` | — | 그대로 |

- 접기(5)는 사용자가 옵시디언에서 직접 쓴 `[[교안/회의록|회의록]]`·`[[a|a]]` 도 접는다 — 앱에서 같은 문서로 풀리고 보이는 글자도 같으므로 뜻이 바뀌지 않는다. 다시 내보내면 F-2020 이 필요할 때 경로를 다시 붙인다(17장 Q9)
- 되돌리기(7)는 앱에서 **틀리게 풀릴** 링크만 고친다 — 개요 Q6 "필요할 때만 고친다" 를 가져오기 쪽에 같은 뜻으로 옮긴 것이다
- 비용: 링크 하나에 `resolve` 가 볼트 해석기 1번, 앱 해석기 (폴더 깊이 + 2)번 안팎이다. F-2018 4.6 이 잰 해석기 비용(문서 5,000·링크 5만 지도 조건 15~64 ms)에서 몇 배 안쪽으로 **추정**한다 — 직접 재지 않았다(18.2 G-f). 넣을 폴더를 바꿀 때마다 다시 한다

## 9. 적용 — `applyVaultImport`

### 9.1 순서

1. `new` 면 최상위에 볼트 이름 폴더를 만든다. 실패하면 T = 최상위로 두고 실패 목록 `{볼트 이름} — 폴더를 만들지 못했습니다`(F-282 형식)
2. 새 폴더들 — 부모 먼저. 실패하면 그 폴더에 들어갈 문서·하위 폴더는 **가장 가까운 성공한 조상**(없으면 T)으로 간다. 실패 목록 한 줄(F-282 형식)
3. 이미지 — **2차 훑기**로 올릴 이미지 항목만 읽는다(zip 은 `readZipEntries` 의 `want`, 폴더는 `filesAsEntries`). 개요 4.4 "폴더 → 이미지 → 문서" 순서의 이유 그대로 — 문서 원문에 저장소가 준 `ext` 를 적어야 한다
4. 문서 — `create` 다음 `update`, 각각 NFC 경로 순. 원문은 1차 훑기의 메모리 본문에 계획의 링크 편집(7.8)과 3 의 결과로 정한 블록을 넣어 **다시** 만든다. `update` 는 다시 만든 원문이 기존과 같아지면(올리기 실패로 임베드가 원문으로 남아 우연히 같아지는 경우) 쓰지 않고 `skip` 으로 센다

- 진행 `total` = 올릴 이미지 수 + `create` + `update`. 폴더는 세지 않는다(F-282 와 같음)
- 취소는 항목 사이에서만(F-282 3.9). 멈추면 이미 올린 이미지는 남는다(쓰는 문서가 없는 첨부 — F-282 와 같음)

### 9.2 문서 쓰기

- `create`: `store.create({ title, content, lineEnding, folderId })`. id·시각은 저장소가 정한다(`pinnedAt` 없음)
- `update`: F-282 3.9 그대로 — 사본(`truncatedCopyTitle`, 같은 폴더, 기존 `content`·`lineEnding`) 먼저, 실패하면 갱신하지 않고 `{제목} — 사본을 만들지 못해 갱신하지 않았습니다`. 그다음 `store.update(id, { content })`, 이름 바꾸기면 `title` 도
- 1MB(`store.kind === 'server'`)·잠금·열린 문서 재마운트는 F-282 3.9~3.10 그대로. 재마운트 판정은 `update` 된 id 에 지금 문서가 들었는지

### 9.3 이미지 올리기

| 경우 | 동작 |
| --- | --- |
| 16진수 이름 파일(6.2 첫 행) | `putAttachment({ id, ext: 이름의 ext, blob: 원래 바이트, … })`. 인코딩하지 않는다 |
| 내용 해시 id, `store.kind === 'server'`, 형식이 PNG·JPEG | 인자로 받은 `encode`(App 은 `toWebp`)로 바꾼다. 결과가 원래 blob 과 다르면 `ext: 'webp'`·`mime: 'image/webp'`, 같으면 원래 형식. 그다음 `putAttachment({ id, … })` — id 를 주면 서버 저장소가 자체 WebP 변환을 건너뛰므로(`serverStore.putAttachment` 의 `givenId`) 여기서 한다. 전제 4 의 "`{id}.webp` 로 바뀜" 이 그대로 지켜진다 |
| 내용 해시 id, 그 밖(로컬 저장소·GIF·WebP) | 인코딩 없이 `putAttachment({ id, … })`. 로컬 저장소가 F-282 로 들일 때와 같다 |

- **쓰는 `ext` 는 `putAttachment` 가 돌려준 값**이다 — 그 id 가 이미 있으면 저장소가 기존 것을 돌려준다(F-282 3.11)
- 크기·형식은 1차 훑기에서 걸렀다. 실패(던짐)하면 그 파일을 쓰는 임베드는 원문 그대로, 실패 목록 `{파일 이름} — 이미지를 넣지 못해 원문 그대로 두었습니다`. `{파일 이름}` 자리에는 볼트 안 경로(NFC)를 쓴다 — 이름이 같은 파일이 여러 폴더에 흔해서
- 1차 훑기에서 걸러진 파일(5.2 표 "내용이 아님, 5MB 초과")을 가리키는 바꿀 수 있던 임베드도 같은 줄을 파일마다 한 번 실패 목록에 넣는다 — 미리보기 경고에는 이미 세었다
- 저장 공간 초과(`quota_exceeded`)는 F-282 3.10 그대로 — 남은 이미지를 더 시도하지 않고, 그 이미지들을 쓰는 임베드는 원문 그대로, 알림 `이미지 저장 공간(300MB)이 가득 차 이미지 {N}개를 넣지 못했습니다.`

```ts
export function applyVaultImport(input: {
  plan: VaultPlan
  scan: VaultScan
  entries: AsyncIterable<VaultEntry>          // 2차 훑기. want 는 호출부가 vaultUploadNames(plan) 으로
  store: ApplyStore                            // importWorkspace.ts 의 그것
  encode?: (blob: Blob) => Promise<Blob>
  isCancelled?: () => boolean
  onProgress?: (p: { done: number; total: number }) => void
}): Promise<ApplyResult & { targetFolderId: string | null; skippedCount: number }>
export function vaultUploadNames(plan: VaultPlan): ReadonlySet<string>   // 2차 훑기에서 읽을 원래 항목 이름
```

## 12. `App.tsx` 배선

- 상태·참조: 볼트 미리보기에 필요한 것(훑은 결과, 원천 — zip `File` 또는 `{ path, file }` 목록, 1차 훑기 때 읽은 `docs`·`folders`·`attachments`, 지금 넣을 폴더)을 F-282 의 `importFileRef`·`importPlanRef` 곁에 둔다. `ImportDialogState` 모양은 10.2

## 17. 열린 질문 / 사람 결정 필요

### Q1. 볼트 이미지의 첨부 id — **답: 내용 해시(SHA-256 앞 16자) (사용자 2026-09-23).** 기본값 채택. 개요 4.4 는 같은 날 고쳐졌다 (6.2·9.3)

- (결정 전 기록) 개요 4.4 는 "그 밖의 이름은 새 id 로 올린다" 로 적었다. 그대로면 볼트 쪽 이미지 이름(`Pasted image ….png`)이 가져올 때마다 새 무작위 id 가 되어, **옵시디언에서 계속 쓰고 이 앱으로 주기적으로 다시 가져오는** 쓰임(사용자 메모 "옵시디언에서 만든 LLM 위키 공유용")에서
  - 이미지가 든 문서는 본문이 안 바뀌어도 변환 결과의 id 가 달라 **매번 `update` + `(가져오기 전)` 사본**이 생긴다 — 개요 4.3 "건너뜀" 과 Q5 "사본이 쌓이지 않게" 가 막으려던 일
  - 같은 이미지를 매번 **다시 올린다** — 계정 300MB 를 가져오기 횟수만큼 쓴다
  - 개요 5.4 의 "한 번에 수렴" 은 이 앱 → 옵시디언 → 이 앱 왕복(F-2020 이 `{id}.{ext}` 이름으로 내보냄)에만 맞고, 옵시디언이 원본인 경우는 다루지 않았다
- 기본값: 이미지 바이트의 해시를 id 로 쓴다. 같은 그림은 언제 가져와도 같은 id → `putAttachment({ id })` 가 기존 것을 돌려주고 변환 결과가 바이트까지 같아 `skip`(U16). 이름이 다른 같은 그림도 한 첨부. 서버 저장소는 id 를 주면 WebP 변환을 건너뛰므로 가져오기가 `toWebp` 를 직접 불러 전제 4 의 "`{id}.webp` 로 바뀜" 을 지킨다(9.3)
- 대가: 1차 훑기에서 이미지를 모두 읽어 해시한다(머리 (d) — 100MB 에서 편차 안), 해시 충돌은 막지 않는다(2⁻⁶⁴)
- 다른 쪽 — **개요 원문(새 무작위 id)**: `scanVault` 가 해시하지 않고, 16진수 이름이 아닌 이미지는 적용 때 `putAttachment` 에 id 없이 넣는다(서버가 WebP 로 바꾼다). 7.6 에서 16진수 이름이 아닌 이미지가 든 문서는 늘 `update`, `counts.images` 는 그런 이미지 전부. U8 의 해시 행·U16 이 빠지고 H-d 는 "다시 가져오면 이미지 든 문서가 매번 갱신된다" 는 알려진 한계로 바뀐다. 개요 16장 갱신 대상 첫 줄이 없어진다

### 18.1 코드를 읽거나 돌려 확인한 것

- F-282 미리보기는 이미 `.md` 본문을 1차 훑기에서 읽어 둔다(`App.tsx` `previewImportZip` 의 `want`) — 개요 4.4 그대로
- `applyImportPlan` 은 문서와 첨부를 **zip 항목 순서대로** 섞어 처리한다(F-282 3.9 는 "문서 → 첨부" 로 적었다). 볼트는 이미지가 먼저여야 해 따로 둔다(9.1)
- `store.list()` 는 본문·`createdAt` 이 든 `Doc` 을 준다(`idbStore`·`serverStore` — 서버는 캐시 본문). App 의 `docs` 상태(`DocMeta`)에는 `createdAt` 이 없어 이름 충돌 순서(F-281 3.2)를 못 구한다 — 3장 3 에서 새로 읽는 이유
- `serverStore.putAttachment` 는 `id` 를 주면 캐시에 있을 때 기존 것을 돌려주고, 없으면 **변환 없이** 넣는다. `listAttachments` 는 캐시만 읽는다. `idbStore.putAttachment({ id })` 도 있으면 기존 것
- `toWebp` 는 더 커지면 원래 blob 을 돌려준다 — 9.3 의 "같으면 원래 형식" 판정 근거
- `buildImageBlock` 은 `width` 가 필수이고, `parseImageBlock` 은 width 없는 블록을 받는다. `setImageBlockAttrs` 의 `?? 1` 은 테스트에서만 불린다
- 편집기 블록 판정은 CM6 `HTMLBlock` → `parseImageBlock`, 보기는 `html: false` 문단 → `parseImageBlock`. 앞뒤 빈 줄이 필요하다(머리 (c))
- `DataTransferItem.webkitGetAsEntry`·`File.webkitRelativePath`·`FileSystemDirectoryReader.readEntries`·`HTMLInputElement.webkitdirectory` 는 TS DOM 타입에 있다. Playwright 1.63.0 폴더 선택·합성 드롭의 `null` 은 직접 돌렸다(머리 (a)·(b))
- `planWorkspaceExport` 의 범위·이름 규칙은 `buildFolderPaths`·`buildDocPaths`·`resolveSiblingNames` 셋이 전부이고 이름 함수 두 곳(`toFolderName`·`toFileName`)만 바꾸면 된다 — 8.2
- F-2018 의 App.tsx 변경 구역(`git diff`)과 이 명세 구역은 줄이 겹치지 않는다 — 12장. F-2018 은 `d1063ab` 로 커밋됐고 `wikiResolve.ts` export 이름이 명세 `94fee58` 과 같다(`git show HEAD:src/lib/wikiResolve.ts`). `shortestWikiTarget` 은 제목만으로 그 문서가 풀리면 제목을 준다 — 7.8 별칭 접기가 첫 왕복에 맞는 근거
- `specs/features/F-2020.md` 전문을 읽었다 — 3.1·3.2·5.2 계약을 8장에 옮겼고, 13장 Q1(순서)·Q2(링크)·Q7(`-vault`)을 17장 Q10·Q9·Q11 로 받았다. F-2020 이 전제한 "`obsidianImage.ts` 는 `src/lib/` 에 있고 markdown-it 을 import 하지 않는다" 와 맞춘다(1장)
- `e2e/importWorkspace.spec.js` 의 `getByRole('button', { name: '가져오기…' })` 다섯 곳(100·150·207·235·265행 — `grep` 으로)과 Playwright `name` 기본 부분 일치(`playwright-core/types/types.d.ts` 의 `exact` 설명: "By default, matching is case-insensitive and searches for a substring") — 14장 회귀의 근거
- 1차 훑기·임베드 찾기 비용 — 머리 (d)·(e)
