# F-3019 Worker 를 D1 근처에서 실행 — placement 지역 힌트

작성일: 2026-10-07
상태: 승인 (2026-10-07, 상시 지시(결정 없음 → 승인)로 승인). 서버 설정만(`wrangler.jsonc`). 형제 명세 F-2133(캐시 없을 때 부팅이 본문 다운로드를 기다리지 않음)·F-2134(`/api/me` 전에 캐시 셸) 와 파일이 겹치지 않아 순서와 무관하게 배포할 수 있다. 효과 판정은 배포 뒤 측정이라 수용 기준 대부분이 사람(main) 확인이다
구현 담당: `feature-implementer`

## 정해진 것 (사용자 결정, 바꾸지 않는다)

1. 느린 부팅의 서버 쪽 원인은 "KT 회선 요청이 미국 colo 에서 Worker 를 돌리고, D1 질의마다 홍콩까지 왕복" 이다. Worker placement 로 Worker 를 D1 근처에서 돌린다
2. 클라이언트 부팅 순서(F-2133·F-2134)는 이 명세가 다루지 않는다

## 1. 파일 소유

| 파일 | 바뀌는 것 |
| --- | --- |
| `wrangler.jsonc` | 최상위에 `"placement": { "region": "gcp:asia-east2" }` 한 항목. 다른 키는 그대로 |
| `tests/worker/placement.test.ts` | 새 파일. P1 |

- **주석·끝 쉼표를 넣지 않는다.** `tests/worker/authServer.test.ts` U12 와 `tests/worker/writeGate.test.ts` G10 이 원문을 그대로 `JSON.parse` 한다(F-2026 머리말 g)
- `worker/worker-configuration.d.ts` 는 다시 만들 필요 없다(확인 i)

## 2. 결정 — `mode: "smart"` 가 아니라 `region` 힌트

```jsonc
"placement": { "region": "gcp:asia-east2" }
```

- **smart 를 쓰지 않는 이유**: 문서(Placement, "Enable Smart Placement")에 "Smart Placement only considers locations where the Worker has previously run" 이고 "requires consistent traffic … from multiple locations" 다. KT 요청은 미국 colo 에서만 돈다(확인 a). 하루 D1 읽기 3,654건 규모라 `INSUFFICIENT_INVOCATIONS` 로 남거나, 옮겨도 HKG 를 고른다는 보장이 없다
- **region 이 맞는 이유**: 문서 표 "Region — Single back-end service in a known cloud region". 뒤쪽은 복제 없는 D1 주 DB 하나(확인 b·c)이고, R2 도 APAC 이다(확인 d). Cloudflare 가 그 클라우드 지역에 지연이 가장 낮은 자기 데이터센터에서 Worker 를 돌린다
- **값**: `gcp:asia-east2` 는 GCP 홍콩 지역이다. `aws:ap-east-1`·`azure:eastasia` 도 홍콩이고 셋 다 계정 목록에 있다(확인 e) — 어느 것이든 같은 HKG 근처를 겨눈다. 문서 예시 형식(`gcp:…`)을 따라 GCP 를 고른다
- `host`·`hostname` 은 쓰지 않는다 — D1 은 찌를 주소가 없고, 문서가 "experimental" 이라 한다
- D1 위치가 바뀌면(확인 b 의 `served_by_colo` 가 HKG 가 아니게 되면) 이 값을 다시 고른다

예상 [추정]: 요청 하나에 미국 colo ↔ HKG 왕복이 **한 번** 붙고, 대신 D1 질의마다의 왕복(≈0.2s)이 몇 ms 로 준다. 질의 1번인 `/api/health` 는 비슷하고, 질의가 3번 이상인 `GET /api/docs/{id}`·`/api/me`·목록은 그만큼 빨라진다.

## 3. 영향 범위

placement 는 **fetch 핸들러 실행 위치만** 바꾼다(문서 "Review limitations"). 정적 자산은 늘 사용자 근처에서 나가지만, Worker 안에서 `env.ASSETS.fetch` 로 부르면 Worker 가 도는 곳에서 나간다.

| 대상 | 무엇이 바뀌나 | 나빠지나 |
| --- | --- | --- |
| `/api/*`·`/v1/*`·`/pub/*`·`/p/*` | Worker 가 HKG 근처에서 돈다. D1·R2(APAC) 왕복이 짧아진다 | 좋아진다. D1 을 1번만 부르는 경로는 비슷 |
| `/ws/doc/:id` 입구 | `resolveDocSocket` 의 세션·문서·사용량 판정이 HKG 근처에서 돈다 | 연결 수립은 빨라진다 |
| `DocRoom` DO 자체 | DO 는 처음 `get` 한 곳 근처에 만들어지고 옮겨지지 않는다(DO 문서 "Data location"). **이미 있는 방**은 지금까지 Worker 가 돈 미국 colo 근처에 있을 것이다 [추정, 확인 못 함]. 배포 뒤 **처음 열리는 방**은 HKG 근처에 생긴다 | 기존 방은 업그레이드 요청이 HKG → 미국 방으로 한 번 더 건넌다. 이어지는 소켓 프레임이 Worker 위치를 거치는지는 문서에 없다 — **확인 못 함**. 거친다면 기존 방의 입력 반영이 늦어질 수 있다 → A8 과 6장 되돌림 조건으로 본다. 새 방은 DO → D1 스냅숏 쓰기가 빨라진다 |
| Worker → DO RPC (`notifyRevalidate`·`writeText`, `worker/docRoomRpc.ts`) | 부르는 쪽 위치만 바뀐다. DO 위치는 위 행 그대로 | 위 행과 같다 |
| `env.ASSETS.fetch` (`/` 앱 셸, `/?app=1`, `/p/*` 없는 링크) | HKG 근처에서 나간다 | 왕복 하나가 붙는다(≈0.2s [추정]). 설치된 PWA 는 `/` 탐색을 서비스 워커 precache 로 받아(`vite.config.ts` `navigateFallback: 'index.html'`) 재방문에는 영향 없음 |
| `/`(랜딩)·`/welcome` 렌더 | D1 없이 Worker 가 그린다 | 왕복 하나가 붙는다(≈0.2s [추정]). 받아들인다 — 6장 기록 대상 |
| `/login` | 쿠키가 있으면 세션 판정(D1)이 빨라지고, 없으면 위 행과 같다 | 쿠키 없을 때만 조금 |
| `run_worker_first` 밖 정적 자산(`/assets/*`·사이트 페이지·`/manifest.webmanifest`·`/sw.js`) | Worker 를 거치지 않는다 | 바뀌지 않는다 |
| Cron (`scheduled`, `0 18 * * *`·`*/10 * * * *`) | fetch 핸들러가 아니라 placement 대상이 아니다 | 바뀌지 않는다 |
| `WRITE_LIMITER` (F-2026, `worker/writeGate.ts`·`worker/cspReport.ts`) | 카운터는 **Worker 가 도는 위치별**이다(Rate Limiting 문서 "Locality"). 지금은 KT 요청이 SEA·LAX·ATL·DFW·PDX 로 흩어져 위치마다 따로 센다. 배포 뒤에는 한 위치에 모인다 | 나빠지지 않는다. 사용자 한 명의 분당 120 이 실제로 120 에 가까워진다 — F-2026 의도에 더 맞다 |
| 외부 호출(GitHub API, OAuth 토큰 교환, 웹 푸시 전송) | 출발점이 HKG 근처로 바뀐다 | GitHub API 가 미국에 있다면 호출마다 조금 늘 수 있다 [추정, 재지 않음]. 그 경로도 D1 을 부르므로 받아들인다 |

배제한 대안 — Worker 를 둘로 나눠(가장자리 Worker + placement 붙인 뒤쪽 Worker, 서비스 바인딩) 랜딩·자산 경로를 사용자 근처에 두는 구성: 라우팅·인증 코드를 옮기는 구조 변경이라 이 명세 범위 밖이다. 6장 측정에서 랜딩 지연이 문제로 드러나면 따로 명세한다.

## 6. 유지·되돌림

**되돌리는 조건** (하나라도): 배포 30분 뒤에도 A2 또는 A3 미달 / A7 에서 기존 문서 실시간 반영이 눈에 띄게 느려짐 / A4 가 0.6s 를 넘음. A5 가 전보다 0.3s 넘게 늘었으면 되돌리지 않고 기록해 Worker 분리 명세(3장 끝)를 제안한다.

**되돌리는 법**

1. `wrangler.jsonc` 의 값을 `"placement": { "mode": "off" }` 로 바꾸고, P1 기대값도 같이 바꿔 한 커밋(제목 `Worker placement 끄기 (F-3019)`) → `deploy` 스킬로 배포. 키를 지우지 않고 `off` 를 적는 이유: 키가 없을 때 wrangler 가 원격 설정을 끄는지 남겨 두는지 확인하지 못했다 [추정]. `off` 는 스키마(확인 g)가 받는 명시 값이다
2. 급하면 먼저 대시보드 Workers & Pages → `md-editor-web` → Settings → Placement 를 Default 로 바꾼다(즉시). 다음 배포가 `wrangler.jsonc` 값을 다시 올리므로 1번 커밋을 반드시 뒤따라 한다
3. 확인: A1 의 `cf-placement` 머리가 사라지고 `/cdn-cgi/trace` colo 와 tail 위치가 다시 미국이다

배포 중 HKG 근처에 새로 생긴 `DocRoom` 은 되돌려도 그 자리에 남는다. 지우지 않는다(4장).

## 7. 기존 테스트 회귀

`grep wrangler.jsonc` 로 `tests/`·`scripts/`·`e2e/` 를 봤다. 원문을 읽는 곳은 `tests/worker/authServer.test.ts` U12(`vars`·`secrets`·`compatibility_flags`), `tests/worker/writeGate.test.ts` G10(`ratelimits`), `tests/worker/purgeJobs.test.ts`(`triggers.crons`) 셋이고 모두 다른 키만 본다. **깨지는 테스트 없음** — 단, 주석을 넣으면 U12·G10 이 `JSON.parse` 에서 깨진다(1장).
