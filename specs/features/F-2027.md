## 2. 범위

### 한다

- DO 실시간 경로의 D1 스냅숏 한 번마다 **문서 소유자**의 하루 카운터 +1, 누계 바이트 증감을 같은 batch 에서 (F-2024 2.5, 3.3 표 "`DocRoomCore.snapshot`" 행)
- 소유자가 하루 5,000 에 닿으면 그 방의 D1 스냅숏을 60초에 한 번으로 — 미룬 것은 DO 알람이 쓴다
- `/v1` PUT 실시간 경로의 두 flush(F-308 6장 3번·9번)는 느린 저장을 건너뛰고 쓴다
- 소유자가 막혔으면 스냅숏을 D1 에 쓰지 않는다. 편집은 DO SQLite 에 남는다

### 하지 않는다

- DO idle 경로(`writeIdle` → `updateDocRow`) — F-2025 가 이미 센다. 두 번 세지 않는다(F-2024 2.5 첫 줄)
- 실시간 경로의 총량 413 — 결정 7
- 느린 저장·막힘을 편집자 화면에 알리기 — F-2024 Q6. 새 UI 문자열 없음
- `/ws` 연결 거절·재검증에서 막힌 소유자 닫기(4403) — F-2028(`access.ts`·`docSocket.ts`)
- `/v1` PUT 을 보낸 사람의 카운터 — Worker 관문(F-2026)이 보낸 사람을 **읽기만** 한다. 실시간 경로의 쓰기는 소유자에게 센다(F-2025 Q2 와 같은 방향, 7.3)

## 3. 지금 — 스냅숏 주기와 D1 행 (측정 a·m)

### 3.1 스냅숏이 일어나는 때 (F-304 6.2, 코드 그대로)

| 때 | 간격 |
| --- | --- |
| 편집 뒤 조용해지면 | 마지막 업데이트 뒤 5,000ms (`FLUSH_DEBOUNCE_MS`) |
| 편집이 계속되면 | 첫 미저장 업데이트 뒤 최대 30,000ms (`FLUSH_MAX_WAIT_MS`) |
| 마지막 연결이 닫히면 | 곧바로 (`roomEmptied`) |
| D1 쓰기 실패 뒤 | 5초 뒤, 최대 3번 (`SNAPSHOT_RETRY_*`) |
| 불러왔더니 D1 이 뒤처져 있으면 | 불러온 뒤 5,000ms (`LOAD_FLUSH_DELAY_MS`) |
| `/v1` PUT 실시간 경로 | 요청마다 flush(선)·flush(후) (F-308 6장) |

- flush 는 본문·제목이 D1 값(`base`)과 같으면 D1 에 쓰지 않는다(`snapshot` 첫 판정). 그래서 스냅숏 수 = "바뀐 것이 있는 flush" 수다
- 방 하나의 스냅숏 빈도는 **편집 간격**이 정한다(측정 m): 쉬지 않고 치면 **분당 2**(30초 maxWait), 5초보다 살짝 긴 간격으로 한 글자씩 치면 **분당 12**(최대). 사람이 여럿이어도 방 하나의 박자는 하나다

### 3.2 D1 행 — 전후 (측정 a·b·c·d·g)

| 스냅숏 한 번 | 지금 | F-2027 뒤 |
| --- | --- | --- |
| 버전 맞음 | 쓰기 2 · 읽기 1 | 쓰기 **3** · 읽기 **3** (2+1 / 1+2) |
| 버전 틀림 → 흡수 → 한 번 더 | (0 + 읽기 1) + 불러오기 1 + (2 · 1) | (1 · 3) + 1 + (3 · 3) — 카운터 +2 |
| 소유자가 막힌 것을 아는 방의 스냅숏 | — | 쓰기 0 · 읽기 1 (`SELECT blocked_at`, 5.3) |
| 느린 저장으로 건너뛴 스냅숏 | — | 0 |
| 불러오기(`load`·`catchUp`·`absorb` 의 읽기) | 읽기 1 | 읽기 1 (`owner_id` 열만 늘어남, 측정 g) |

- 흔한 스냅숏의 쓰기는 **1.5배**(2 → 3) — F-2024 2.4 표 "DO 스냅숏 2 → 3" 과 같다. 읽기는 +2(사용량 줄 1 + `RETURNING` 1). 읽기는 D1 무료 하루 500만 행이라 쓰기(10만 행)보다 여유가 크다
- **보통의 편집**: 8시간 쉬지 않고 치면 분당 2 × 480분 = 960번 → 지금 1,920행, 뒤 2,880행. 카운터 960 — 한도 5,000 에 닿지 않는다
- **방 하나의 최악(한도가 없을 때)**: 분당 12 × 1,440분 = 17,280번 → 지금 34,560행(D1 하루 쓰기 10만 행의 35%)
- **방 하나의 최악(F-2027 뒤, 소유자 카운터가 0 에서 시작)**: 분당 12 로 5,000번까지 416.7분 → 남은 1,023.3분은 분당 1 → 약 6,023번 × 3행 = **약 18,070행(18%)**. F-2024 2.4 의 "한도에 닿은 한 사람 15,000~20,000행" 과 같은 크기다
- 방이 여러 개면 느린 저장이 방마다 분당 1 이라 더 쓸 수 있다 — F-2024 Q5 그대로(방 10개 × 1,440 × 3 = 43,200행)
- **원격 D1 의 행 계산이 로컬과 같다는 것은 확인하지 않았다.** D1 `RETURNING` 이 원격 batch 에서 같은 모양으로 돌아오는지도 확인하지 않았다(10장 ①)

## 4. 스냅숏 사용량 줄

### 4.1 계약 — `worker/usage.ts`

```ts
// 스냅숏 한 번 = 소유자 하루 +1, 누계 += deltaBytes (앞 문장이 1행을 바꿨을 때만). 문서 수는 바꾸지 않는다
export function snapshotUsageStatement(db: D1Database, ownerId: string, now: number, deltaBytes: number): D1PreparedStatement
```

문장(계약 — 테스트가 글자까지 본다): F-2025 5.1 "하루 + 누계" 문장 **그대로** 뒤에 ` RETURNING ` + `USAGE_COLUMNS`

```sql
UPDATE users SET write_count = CASE WHEN write_day = ?1 THEN write_count + 1 ELSE 1 END, write_day = ?1, content_bytes = content_bytes + CASE WHEN changes() = 1 THEN ?2 ELSE 0 END, doc_count = doc_count + CASE WHEN changes() = 1 THEN ?3 ELSE 0 END WHERE id = ?4 RETURNING write_day, write_count, content_bytes, doc_count, blocked_at, warned_at
```

- 바인딩 `[utcDay(now), deltaBytes, 0, ownerId]`
- 새 문장을 만들지 않고 F-2025 문장에 `RETURNING` 만 붙이는 이유: 증감 규칙(`changes()` 로 앞 문장 결과를 봄, F-2024 3.2 1번)과 날짜 바꿈 규칙이 한 벌로 남는다. `docUsageStatements` 를 그대로 쓰지 못하는 이유는 준비된 문장에 `RETURNING` 을 덧붙일 수 없어서다
- `RETURNING` 열은 `USAGE_COLUMNS` 여섯 개 전부 — `rowToUsage`·`isDailyLimitReached`(F-2025 4.1)를 그대로 쓰려고. 열 셋과 읽기 행이 같다(측정 e)

### 4.2 batch — 자리와 순서

- 스냅숏의 D1 쓰기는 `batch([스냅숏 문장, snapshotUsageStatement(…)])` 하나다. 스냅숏 문장(`UPDATE_SQL`)의 글자·바인딩은 **바꾸지 않는다**(F-304 A9·F-308 A13 이 그 문장을 본다)
- 판정은 batch 결과 **첫 문장**의 `meta.changes === 1`(지금 `run()` 결과와 같은 뜻). 둘째 결과의 `results[0]` 이 사용량 행이다
- 둘째 결과에 행이 없으면(사용자 행이 없음 — 지금은 생길 수 없다) **판정하지 않는다**: 느린 저장·막힘 둘 다 끈 채로 둔다. 던지지 않는다
- batch 가 던지면 둘 다 되돌려진다(측정 l). 지금처럼 `flushOnce` 의 `catch` → `'retry'`. 카운터는 오르지 않는다

### 4.3 누구에게 세나 — 소유자, 불러올 때 읽은 `owner_id`

- 불러오기 문장을 `SELECT title, content, line_ending, version, owner_id FROM docs WHERE id = ?` 로 바꾼다(계약 — 가짜 D1 이 이 글자로 분기한다). `load`·`catchUp`·`absorb` 가 모두 이 문장이라 소유자 id 를 **추가 읽기 없이** 안다(측정 g). 소유자는 바뀌지 않는다(`SET owner_id` 없음)
- 연결의 `userId` 를 쓰지 않는 이유: 소유자가 연결돼 있지 않은 방(편집 초대받은 사람만), 연결이 0 인 방(`roomEmptied`·알람·`/v1` PUT)이 흔하다
- 소유자를 부분 질의로 찾는 안(측정 f)은 스냅숏마다 읽기 1 이 더 든다 — 쓰지 않는다
- **여러 사람이 동시에 편집해도 스냅숏 한 번 = 소유자 +1** 이다. 편집자 각자의 카운터는 이 경로로 오르지 않는다. 결과: 편집 초대받은 사람이 많이 치면 **소유자**의 하루 몫이 줄고, 5,000 에 닿으면 소유자 본인의 `/api` 쓰기도 관문(F-2026)에서 429 가 된다 — 결정 4 가 받아들인 모양이다(12장에 적는다)

### 4.4 누계 증감 — D1 행의 바이트에서 (F-2024 3.2 끝 "F-2027 이 정한다" 의 답)

- **규칙: 증감 = 이번에 쓰는 본문(`fromEditorText(지금 본문, base.lineEnding)`)의 UTF-8 바이트 − `base` 가 가리키는 D1 행 본문의 UTF-8 바이트.** 뒤쪽 값을 `base` 에 숫자 하나로 들고 다닌다
  - `load`·`absorb`(`catchUp` 포함)가 D1 행을 읽을 때: 그 행 `content` 의 `utf8ByteLength`
  - 스냅숏이 1행을 바꿨을 때: 방금 쓴 본문의 바이트(스냅숏이 1MB 판정 때 이미 잰 값)
- 정확한 이유: 조건부 `UPDATE … AND version = base.version` 이 바꾸는 행은 **바로 그 `version` 의 행**이고, 그 행은 이 DO 가 읽었거나 썼다. `version` 이 다르면 `changes()` 가 0 이라 증감이 들어가지 않는다(측정 d)
- `base.content` 에서 거꾸로 계산(`fromEditorText(base.content, base.lineEnding)`)하지 않는 이유: D1 행이 섞인 줄바꿈이나 홀로 쓴 `\r` 이면 `toEditorText` → `fromEditorText` 가 원래 바이트로 돌아오지 않는다(F-2024 3.2 끝). 그러면 그 방의 첫 스냅숏마다 몇 바이트씩 어긋난다
- 비용: 불러오기·흡수마다 D1 본문 한 번 `TextEncoder` — 1MB 에 1.49ms(F-308 머리말 측정 (a), node 값)

## 5. 느린 저장과 막힘 — 규칙

### 5.1 DO 가 들고 있는 것 (메모리, 인스턴스마다)

| 이름(설명용 — 구현 재량) | 뜻 | 처음 값 |
| --- | --- | --- |
| 소유자 id | 4.3 | 불러오기에서 |
| D1 행 바이트 | 4.4 | 불러오기에서 |
| 느린 날 | 소유자가 하루 한도에 닿은 것을 안 UTC 날짜. 없으면 느리지 않음 | 없음 |
| 막힘 | 소유자가 막힌 것을 앎 | 거짓 |
| 마지막 batch 시각 | 스냅숏 batch 가 **돌아온**(1행이든 0행이든) 마지막 시각 ms | 없음 |
| 걸어 둔 알람 시각 | 이 인스턴스가 `setAlarm` 한 시각 | 없음 |

- 저장하지 않는다(DO SQLite·D1 에 새 열·행 없음). DO 가 쫓겨나면 잊는다 — 다음 스냅숏 한 번이 다시 알려 준다(F-2024 2.5 "쫓겨날 때마다 한 번 더 쓰는 셈이라 받아들인다")

### 5.2 스냅숏 한 번의 순서

`snapshot` 이 부를 때마다 위에서부터. 1·2 는 지금 그대로다

| # | 판정 | 하는 일 |
| --- | --- | --- |
| 1 | 본문·제목이 `base` 와 같음 | 끝 (D1 없음) — 지금 그대로 |
| 2 | 본문이 1MB 초과 | `too-large` — 지금 그대로. **막힘·느린 저장보다 앞**이라 편집자 경고가 늦어지지 않는다 |
| 3 | **막힘 문** — 막힘이 참 | `SELECT blocked_at FROM users WHERE id = ?`(소유자) 한 번. 아직 막혔으면 **D1 에 쓰지 않고 끝**(재시도·알람 없음). 풀렸으면(`NULL` 또는 행 없음) 막힘을 거짓으로 하고 4번으로 |
| 4 | **느린 문** — 이번 flush 가 강제(5.4)·알람(5.5)이 아니고, 느린 날 = 오늘(UTC, `utcDay(Date.now())`), 마지막 batch 시각이 있고, 지금 − 마지막 batch 시각 < **60,000ms** | **D1 에 쓰지 않고 끝.** 알람을 `마지막 batch 시각 + 60,000` 에 건다 — 걸어 둔 알람 시각이 없거나 이미 지났을 때만(같은 창 안에서 `setAlarm` 을 되풀이하지 않는다). 재시도는 걸지 않는다 |
| 5 | batch (4.2) | 돌아오면 곧바로 마지막 batch 시각 = 지금. 사용량 행이 있으면: `blocked_at` 이 `NULL` 이 아니면 막힘 참. `isDailyLimitReached(rowToUsage(행), 지금)` 이면 느린 날 = 오늘, 아니면 느린 날 없음 |
| 6 | 첫 문장 1행 | `base`(D1 행 바이트 포함)를 새 값으로 — 지금 그대로 |
| 7 | 첫 문장 0행 | 지금처럼 D1 한 줄을 읽어 흡수한 뒤 5번을 **한 번 더**(3·4 번 문은 다시 보지 않는다 — 한 스냅숏 안의 두 번째 시도다). 단, 5번에서 막힘이 참이 됐으면 두 번째 시도를 하지 않고 끝 |

- 3·4 번에서 끝난 스냅숏은 `SnapshotResult` 로 `'ok'` 다(재시도 대상이 아니다). 그 flush 의 SQLite 추가(`persistPending`)는 스냅숏 **앞**에 이미 끝나 있다(F-304 6.2 순서) — **편집은 버려지지 않는다**(결정 4)
- 4번의 기준 시각은 "마지막 batch" 다(마지막 **성공**이 아님). 0행으로 끝난 batch 도 카운터를 +1 했으므로(측정 d) D1 쓰기 몫을 쓴 것으로 본다
- 던진 batch(D1 오류)는 되돌려져 카운터가 안 올랐으므로 마지막 batch 시각을 바꾸지 않는다. 그 재시도(5초 뒤)도 4번 문을 지난다 — 60초가 안 지났으면 건너뛰고 알람에 맡긴다
- 5번의 판정 기준은 F-2026 관문과 같은 함수(`isDailyLimitReached`: 오늘 `write_count >= 5000`)다. 그래서 **5,000번째 쓰기가 끝난 뒤부터** 느리다 — 관문도 5,000 에서 429 를 낸다

### 5.3 막힌 소유자 — `blocked_at` 을 어디서 읽나

| 때 | 읽는 곳 | 추가 D1 읽기 |
| --- | --- | --- |
| 스냅숏마다 | 사용량 줄의 `RETURNING blocked_at` (4.1) | **0** — 사용량 줄이 어차피 돌려주는 행 |
| 막힌 것을 안 뒤의 스냅숏 | `SELECT blocked_at FROM users WHERE id = ?` (5.2 3번) | 1 (측정 i) — 풀렸는지 보려고. 이때 쓰기는 0 |
| 불러오기 | 읽지 않는다 | 0 |

- 결과: 운영자가 막은 **뒤 첫 스냅숏 한 번은 D1 에 들어간다**(`RETURNING` 으로 알게 되는 그 쓰기, 측정 j). 그다음부터 멈춘다. 새는 양은 **DO 인스턴스마다 최대 한 번**이다 — 쫓겨났다 깨면 또 한 번이지만, F-2028 뒤에는 막힌 소유자 문서의 `/ws` 연결이 4403 으로 거절되고(새 연결), 열린 연결도 다음 재검증(최대 60초)에서 닫혀(F-2024 4.2) 방을 다시 깨울 사람이 없다
- 불러오기에서 `JOIN users` 로 미리 읽는 안(측정 h)은 새는 한 번을 **깨어날 때만** 막고(한창 편집 중에 막힌 경우는 그대로 샌다), 깨어날 때마다 읽기 +1 이다. 스냅숏마다 먼저 읽는 안은 11장 Q2
- 막힘이 참인 동안 알람을 걸지 않는다. 풀린 뒤 D1 에 가는 길: ① 편집이 이어지면 다음 flush 의 3번이 풀린 것을 읽고 쓴다 ② 방이 비고 DO 가 쫓겨났으면 다음 깨어남의 `load` 가 "SQLite 가 D1 보다 앞섬"을 보고 5초 뒤 flush(지금 `loadFlushTimer`)
- `writeText` 의 flush(5.4)도 막힘 문(3번)을 지난다 — 예외가 아니다. 그래서 막힌 소유자 문서의 `/v1` PUT 이 Worker 관문(F-2028)을 지나 DO 에 닿으면(막은 순간과 겹친 경우) flush(후)가 쓰지 못해 F-308 6장 10번 `unavailable`(503)이 된다. 편집은 `Y.Doc`·SQLite 에 이미 있다 — F-308 6.7 과 같은 모양

### 5.4 `writeText` flush 는 느린 문을 건너뛴다 (F-2024 기본값 15)

- 범위: `writeLive`(F-308 6장)가 부르는 **두 flush** — 3번 flush(선)과 9번 flush(후). `writeIdle` 은 flush 가 없다(F-2025 `updateDocRow` 가 센다)
- 이유
  1. flush(후) 가 D1 에 못 쓰면 F-308 6장 10번이 `unavailable`(503)을 돌려준다 — 한도를 넘은 소유자의 문서에 편집 초대받은 사람이 `/v1` PUT 을 하면 관문(보낸 사람 카운터)은 지나고 DO 에서 늘 503 이 된다(F-2024 2.5)
  2. flush(선) 도 건너뛰면 D1 에 못 나간 편집을 먼저 쓰는 F-308 7.1 이 깨진다 — `base.version` 이 낡은 채 5번 비교를 지나, "PUT 이 200 이면 문서가 정확히 X" 계약이 무너진다
  3. 사람이 친 명령 하나라 60초 규칙의 목적(자동 저장이 쉬지 않고 쓰는 것)과 다르다. 분당 120 은 관문이 막는다
- 비용: PUT 한 번에 스냅숏 최대 2번 = 소유자 카운터 최대 +2. flush(선)은 못 나간 편집이 있을 때만 쓴다(1번 판정)
- **합쳐지는 flush**: 강제 요청이 들어왔을 때 다른 flush 가 돌고 있으면 지금처럼 "끝난 뒤 한 번 더"(F-304 6.2)가 되는데, 그 **뒤이은 한 번이 강제**여야 한다. 강제 표시는 다음 한 번의 실행에 실리고 그 실행이 가져가면 지워진다. 일반 flush 가 강제 flush 에 합쳐져도 손해가 없다(강제가 더 넓다)
- 강제 flush 가 쓴 batch 도 마지막 batch 시각을 바꾼다 — 그 뒤 자동 저장은 다시 60초를 센다

### 5.5 DO 알람

- 알람은 **느린 문(5.2 4번)이 D1 쓰기를 미뤘을 때만** 건다. 편집이 없거나 전부 D1 에 나갔으면 걸지 않는다
- 알람이 울리면 partyserver 가 초기화(`onStart` → `onLoad` → `core.load()`)를 거친 뒤 `onAlarm()` 을 부른다(`partyserver/dist/index.js` `alarm`). `DocRoom.onAlarm` 은 `core.alarm()` 만 부른다(F-304 5.3 "규칙은 전부 core")
- `core.alarm()`: 걸어 둔 알람 시각을 지우고, 사라진 방·불러오지 않은 방이면 아무것도 하지 않는다. 그 밖이면 **알람 flush** 하나 — 5.2 4번의 60초 검사만 건너뛰고 나머지(막힘 문 포함)는 그대로. 알람은 `마지막 batch + 60,000` 에만 걸리므로 알람 flush 가 60초 규칙을 어기지 않는다. 60초 검사를 건너뛰는 이유: 알람이 예정 시각보다 몇 ms 일찍 불리면 4번이 또 건너뛰고 같은 시각에 알람을 다시 걸어 헛돈다(일찍 불릴 수 있는지는 확인하지 않았다 — 막으려고 둔다)
- 알람이 울렸는데 느린 날이 지났거나(자정) 한도 밑으로 내려왔으면: 그 flush 는 평소처럼 쓴다. 쓸 것이 없으면 D1 호출 0
- **알람이 `setTimeout` 이 아닌 이유**: 방이 비고 DO 가 쫓겨나도 알람은 남아 DO 를 깨운다. `setTimeout` 은 인스턴스와 함께 사라져, 느린 저장 중에 방이 비면 그 편집이 다음 누군가 열 때까지 D1 에 안 나간다
- `roomEmptied`(마지막 연결이 닫힘)는 따로 다루지 않는다 — flush 가 5.2 를 지나므로 느린 저장 중이면 60초 안에서는 쓰지 않고 알람에 맡긴다(F-2024 2.5 "곧바로 쓰면 연결·끊기를 되풀이해 60초를 우회할 수 있다")
- 알람 한 번이 깨우는 비용: DO 가 잠들어 있었으면 불러오기(F-304 5.2) + D1 스냅숏 1번. 방마다 60초에 최대 1번이고, 편집자가 붙어 있는 방은 어차피 깨어 있다
- `setAlarm` 이 던지면 `console.warn` 한 줄 뒤 계속한다(편집은 SQLite 에 있다). 걸어 둔 알람 시각은 비워 둬서 다음 flush 가 다시 건다
- **`purgeRoom`(문서 삭제)은 알람을 지운다**(`deleteAlarm`) — `storage.deleteAll()` 이 알람도 지우는지 확인하지 못했다. 남아 울리면 초기화의 `load` 가 D1 줄이 없는 것을 보고 사라진 방 처리(`roomGone` → `store.clear()`)를 한 번 더 할 뿐이라 해롭지는 않지만, 지운 문서의 DO 를 헛되이 깨운다

### 5.6 되돌아가는 조건 (느린 저장이 풀릴 때)

| 조건 | 판정 자리 | 결과 |
| --- | --- | --- |
| UTC 날짜가 바뀜 | 5.2 4번이 매번 `utcDay(Date.now())` 와 느린 날을 견준다 | 곧바로 풀림. 다음 flush 가 쓰고, 사용량 줄이 `write_day` 를 오늘로·`write_count` 1 로(측정 k) |
| 스냅숏 결과가 한도 밑 | 5.2 5번 | 풀림. 카운터는 하루 안에서 줄지 않으므로 운영자가 `users` 를 직접 고쳤을 때만 일어난다 |
| DO 가 쫓겨남 | — | 잊음. 다음 스냅숏이 곧바로 쓰고(마지막 batch 시각 없음) 결과로 다시 느려진다 |

- `writeText` 의 강제 flush 는 느린 날을 바꾸지 않는다 — 결과 행이 한도 이상이면 느린 날은 그대로다

### 5.7 로그 (운영 확인용 — 화면 문자열이 아니다)

| 때 | `console.warn` 문자열 |
| --- | --- |
| 느린 날이 없다가 생김 | `docRoom: owner over daily write limit, slow snapshots ({docId})` |
| 막힘이 거짓이다가 참이 됨 | `docRoom: owner blocked, snapshots paused ({docId})` |

- 상태가 **바뀔 때 한 번씩**만 — 스냅숏마다 찍지 않는다. 사용자 id·이메일은 싣지 않는다(문서 id 만)
- 10장 사람 확인이 `wrangler tail` 에서 이 줄을 본다

## 6. 계약 변경 (코드 모양)

```ts
// worker/docRoomCore.ts
export const SLOW_SNAPSHOT_MS = 60_000

export interface DocRoomHost<C extends RoomConnection = RoomConnection> {
  // …지금 멤버 그대로…
  // DO 알람을 at(ms) 에 건다. 이미 걸린 알람은 바뀐다 (5.5)
  setAlarm(at: number): Promise<void>
}

// DocRoomCore — 새 공개 메서드
alarm(): Promise<void>
```

- `docRoom.ts` 배선: 호스트 `setAlarm` = `ctx.storage.setAlarm(at)`, `onAlarm()` 은 `await this.core.alarm()`, `purgeRoom` 은 `deleteAll` **앞**에 `ctx.storage.deleteAlarm()`
- `flush()`·`roomEmptied()`·`writeText()`·`revalidateConnections()`·`purge()` 의 공개 모양은 그대로다. 강제·알람 표시는 core 안에서만 오간다
- 불러오기 문장(4.3)과 막힘 확인 문장 `SELECT blocked_at FROM users WHERE id = ?` 는 `docRoomCore.ts` 안 상수다(계약 — 가짜 D1 이 글자로 분기)
- `UPDATE_SQL`(스냅숏 문장)·`ACCESS_ROW_SQL`·`FULL_ROW_SQL` 은 바꾸지 않는다

## 7. 누가 얼마나 세이나 — 정리

### 7.1 하루 카운터의 단위

| 일 | 소유자 카운터 | 편집자(보낸 사람) 카운터 |
| --- | --- | --- |
| 실시간 편집의 스냅숏 batch 한 번(1행이든 0행이든) | +1 | 0 |
| 버전이 틀려 흡수 후 다시 쓴 스냅숏 | +2 | 0 |
| 바뀐 것 없는 flush, 1MB 초과로 멈춘 flush, 느린 저장·막힘으로 건너뛴 스냅숏 | 0 | 0 |
| D1 오류로 던진 batch | 0 (되돌려짐) | 0 |
| `/v1` PUT 실시간 경로 | flush(선) 이 썼으면 +1, flush(후) +1 | 0 (Worker 가 D1 에 쓰지 않는다) |

- "쓰기 한 번 = D1 batch 한 번" 이라는 F-2024 1.2 규칙을 DO 에도 그대로 쓴다. 키 입력·편집자 수·Yjs 업데이트 수와 상관없다

### 7.2 한도를 넘은 소유자의 방에서 보이는 것

- 편집자 화면: 달라지는 것 없음(Q6). 실시간 편집·다른 편집자와의 동기화는 그대로다(DO 가 중계한다)
- D1 스냅숏을 읽는 경로 — 공유 링크(`/pub`·`/p`), `/v1` GET, `/api` 목록·문서 GET — 가 최대 60초 낡는다(지금은 최대 30초)
- 소유자 본인의 `/api`·`/v1` 쓰기는 관문(F-2026)에서 429 `scope: "day"`(F-2024 2.1 ③)

### 7.3 남는 구멍 (막지 않는다 — 기록만)

- F-2024 Q5 방 여러 개(3.2 끝)
- 편집 초대받은 사람이 남의 문서에 `/v1` PUT 을 되풀이하면 실시간 경로는 소유자에게만 센다(F-2025 Q2 의 구멍이 실시간 경로에도 있음). 분당 120(관문)이 상한이다

### Q1. 스냅숏 사용량 문장을 어디에 두나 — **기본값: `worker/usage.ts` 에 함수 하나(4.1)** (확인 권장)

### Q2. 막힌 소유자를 언제 알아채나 — **기본값: 스냅숏 결과의 `RETURNING blocked_at`, 안 뒤로는 스냅숏마다 한 줄 읽어 풀렸는지 확인(5.3)**

### Q3. 누계 증감의 기준 — **기본값: `base` 가 가리키는 D1 행의 실제 바이트(4.4)**

- 이유: 정확하다. 추가 D1 읽기 0, 불러오기·흡수마다 `TextEncoder` 한 번(1MB 1.5ms)
- 다른 안(`fromEditorText(base.content, base.lineEnding)` 에서 계산): 상태가 하나 줄지만 섞인 줄바꿈 문서의 첫 스냅숏마다 몇 바이트 어긋나고, 그 어긋남은 `admin-recount` 전까지 쌓인다(F-2024 3.2 끝)

### Q4. `writeText` 예외의 범위 — **기본값: flush(선)·flush(후) 둘 다(5.4)**

- F-2024 2.5 는 "`writeText` 가 부르는 flush" 라고만 적었다. flush(후)만 예외로 두면 5.4 이유 2(F-308 7.1)가 깨진다
- 다른 안(flush(후)만): PUT 한 번의 카운터가 최대 +1 로 준다. 대신 느린 저장 중인 방에서는 CLI 가 아직 D1 에 안 나간 편집을 모른 채 쓰게 되어, 겹치지 않으면 두 편집이 합쳐진 문서로 200 이 된다 — F-223 "200 이면 문서가 정확히 X" 와 어긋난다

### Q5. 알람 flush 가 60초 검사를 건너뛸 것인가 — **기본값: 건너뛴다(5.5)**

- 이유: 알람은 `마지막 batch + 60초` 에만 걸리므로 규칙을 어기지 않고, 일찍 불린 알람이 헛도는 것을 막는다
- 다른 안(검사함): 알람이 예정보다 일찍 불리면 알람을 다시 걸고 한 번 더 깨운다. 알람이 늦게만 불린다면 차이 없음

### Q6. 문서 삭제 때 알람을 지울 것인가 — **기본값: 지운다(5.5)**

- `deleteAll` 이 알람을 지우는지 확인하지 못해서 둔다. 지우지 않아도 해롭지는 않고 DO 를 한 번 헛되이 깨울 뿐이다. 다른 안이면 `docRoom.ts` 변경이 `onAlarm` 한 줄로 준다
