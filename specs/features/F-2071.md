### 2.2 판정 갈래 — 무엇이 `decideHashNav` 로 가고 무엇이 훅에 남나

`handleHashChange` 는 **동기 판정**(해시·경로를 읽고 ref 값과 견주어 갈래를 고른다)과 **비동기 실행**(`await beforeLeaveDoc()` 뒤 화면 플래그 setter·문서 목록 조회·주소 쓰기)으로 나뉜다.

- 동기 판정 → `decideHashNav`(순수). `parseHash(location.hash)`, 두 공개 경로 가드, `shares`·`help` 의 "이미 열려 있으면 무시", 지도의 "같은 중심이면 무시", 문서의 "같은 문서이고 화면이 없으면 무시(스레드면 대상만 잡기)"
- 비동기 실행 → 훅에 그대로. **특히 `docsRef.current` 조회 두 곳(지도 `anchorId`, 문서 있음/없음)은 `await beforeLeaveDoc()` 뒤에 읽으므로 `decideHashNav` 로 옮기지 않는다** — 옮기면 목록을 읽는 시점이 flush 앞으로 당겨진다(11장 Q5)

## 5. 시그니처 (계약)

### 5.1 `src/app/hashNav.ts`

```ts
import type { HashRoute } from './hashRoute'

export type PublicRoute = { type: 'public'; token: string } | { type: 'publicFolder'; token: string; docId?: string } | null

export function toPublicRoute(route: HashRoute): PublicRoute

export type HashNavInput = {
  hash: string
  pathname: string
  currentDocId: string | null
  sharedDoc: object | null
  sharesOpen: boolean
  helpOpen: boolean
  mapRoute: { centerDocId: string | null } | null
}

export type HashNav =
  | { kind: 'ignore' }
  | { kind: 'share'; fragment: string }
  | { kind: 'shares' }
  | { kind: 'help' }
  | { kind: 'map'; centerDocId: string | null }
  | { kind: 'thread'; docId: string; threadId: string }
  | { kind: 'open'; home: boolean; docId: string | null; threadId: string | null }

export function decideHashNav(input: HashNavInput): HashNav
```

**`decideHashNav` 규칙 — 위에서 아래로 처음 맞는 것 하나.** 순서가 곧 결정이다(지금 `handleHashChange` 의 `if` 순서와 같다). `parsed = parseHash(hash)`.

1. `parsed.type` 이 `public`·`publicFolder` → `ignore`
2. `toPublicRoute(parsePathRoute(pathname))` 가 `null` 이 아님 → `ignore` (해시가 무엇이든)
3. `share` → `{ kind: 'share', fragment }` (`sharedDoc` 이 있어도 — "매번 새로 연다")
4. `shares` → `sharesOpen` 이면 `ignore`, 아니면 `shares` (`helpOpen` 은 보지 않는다)
5. `help` → `helpOpen` 이면 `ignore`, 아니면 `help` (`sharesOpen` 은 보지 않는다)
6. `map` → `center = parsed.docId ?? null`. `mapRoute` 가 있고 `(mapRoute.centerDocId ?? null) === center` 면 `ignore`, 아니면 `{ kind: 'map', centerDocId: center }`. 중심 id 가 목록에 있는지는 **보지 않는다**(2.2)
7. 나머지: `docId` = `doc` 이면 그 id 아니면 `null`, `threadId` = `doc` 이면 `threadId ?? null` 아니면 `null`. `docId === currentDocId` 이고 `sharedDoc`·`sharesOpen`·`helpOpen`·`mapRoute` 가 모두 거짓이면 — `docId` 와 `threadId` 가 둘 다 있으면 `{ kind: 'thread', docId, threadId }`, 아니면 `ignore`
8. 그 밖 → `{ kind: 'open', home: parsed.type === 'home', docId, threadId }`

- `hashchange` 핸들러 안 가드 두 줄의 주석(``// 공개 링크(#/p/…)는 위 handlePublicHashChange 가 …``·``// 경로형 공개 링크(/p/…)도 같다 — …``)과 문서 비교 앞 주석(``// 해시가 문서 경로·문서 없음으로 바뀌면 …``)·스레드 주석(``// 알림함 링크를 눌렀는데 …``)은 해당 규칙 줄 위로 **글자 그대로** 옮긴다(관찰 5)
- 머리 한 줄 주석: `// 해시 이동 판정 — hashchange 가 어느 갈래로 갈지 정하는 순수 함수와 공개 보기 경로 (F-2071, ia.md 3.10)`
- React·DOM·`location`·`history` 를 읽지 않는다. import 는 `./hashRoute` 의 `parseHash`·`parsePathRoute`·`type HashRoute` 뿐이다(테스트 환경 `node`)
- `sharedDoc` 을 `object | null` 로 받는 이유: `ShareDoc` 타입을 이 순수 모듈에 끌어오지 않으려는 것이다(`useGlobalShortcuts` 의 `sharedDocRef: RefObject<object | null>` 선례). 규칙 7 은 지금처럼 거짓 여부만 본다

- 이유: 셋 다 `history.replaceState`·`pushState` 를 부른다. F-2059 2.1 "판정은 순수 함수로, `window` 호출은 훅에 남긴다" 에 따라 순수 모듈 `hashNav.ts` 에 넣지 않는다. `.ts` 파일이라 `react-refresh/only-export-components` 대상도 아니다(ESLint `reactRefresh.configs.vite` 는 `.jsx`·`.tsx` 만 본다 — 규칙 설정 읽기, 실행 확인 아님)
- 다른 쪽(`hashNav.ts`): import 출처가 하나로 준다. 대신 순수 모듈이 `location`·`history` 를 부르는 함수를 갖게 된다(호출만 안 하면 `node` 테스트는 돈다)
- 다른 쪽(`hashRoute.ts`, `formatHash` 옆): 가장 자연스러운 자리지만 다른 명세 소유이고 머리 주석이 "순수 함수" 다. 이 조각 소유 표가 커진다

### Q3. `useFolderActions`·`useImportFlow` 가 옵션 대신 직접 import 하게 하나 — **기본값: 옵션 그대로 (두 파일 고치지 않음)**

- 이유: 옮기기만 한다(전제 3). 옵션을 빼면 두 훅의 옵션 타입·호출 줄·`useFolderActions.test.ts`(`replaceHashUrl: vi.fn()` 으로 주소 쓰기를 가짜로 넣는다)가 바뀌어, 이 조각 소유 표에 앞 조각 파일 셋이 들어온다
- 다른 쪽(직접 import): App 호출 줄에서 이름 둘이 빠지고 훅이 모듈 함수를 바로 부른다. 대신 `useFolderActions.test.ts` 가 `history` 없는 `node` 에서 진짜 `replaceHashUrl` 을 부르게 되어 가짜를 넣을 방법(모듈 목)을 새로 정해야 한다

### Q4. `decideHashNav` 출력에 화면 플래그 변화를 데이터로 싣나 — **기본값: 갈래(`kind`)와 값만. setter 는 훅 본문에 글자 그대로 (5.1·5.2)**

- 이유: 갈래마다 setter 순서와 범위가 다르다(6장). 플래그를 데이터로 실으면 훅이 그 데이터를 해석해 setter 를 부르는 모양이 되어, 모든 setter 줄이 빨강·초록이 된다(F-2059 3.6 "옮기기" 판정이 무너진다). D1 차이는 본문을 바이트 그대로 옮기는 것으로 보존되고 A5 가 그것을 본다
- 다른 쪽(`leave: { sharedDoc, sharesOpen, helpOpen, mapRoute }` 를 싣는다): 6장의 ✗ 가 단위 테스트로 고정된다. 대신 훅 본문이 새로 쓰여 "옮기기" 가 아니게 되고, `anchorId`·문서 있음 판정은 await 뒤라 어차피 순수 함수 밖에 남는다

### Q5. await 뒤 목록 조회(지도 `anchorId`, 문서 있음/없음)를 `decideHashNav` 로 넣나 — **기본값: 넣지 않는다 (2.2)**

- 이유: 지금 두 조회는 `await beforeLeaveDoc()`(편집 flush) **뒤**의 `docsRef.current` 를 읽는다. 순수 함수는 핸들러 첫머리에서 불리므로, 넣으면 목록을 읽는 시점이 flush 앞으로 당겨진다
- 다른 쪽(넣는다): 단위 테스트가 "없는 문서 → 첫 문서 + 알림" 까지 덮는다. 대신 flush 도중 다른 탭 삭제 등으로 목록이 바뀌면 결과가 달라질 수 있다 — 동작 변화다

### Q6. `sharesOpenRef`·`helpOpenRef` 를 훅으로 옮기나 — **기본값: App 에 둔다 (3장)**

- 이유: 대입이 최신값 effect ③ 이다(F-2059 3.2). 읽는 곳은 이 훅뿐이지만, 옮기면 훅 안에 인자 없는 effect 가 새로 생기고 대입 시점이 ③ 에서 훅 자리로 옮겨진다
- 다른 쪽(옮긴다): App 이 약 4줄(선언 2 + 주석 2) 더 준다. 같은 커밋에 읽는 effect 가 없어 동작은 같다. 대신 effect ③ 에서 두 줄이 빠지고 훅이 `sharesOpen`·`helpOpen` 값을 옵션으로 더 받는다

### Q7. e2e 묶음에 `homeScreen`·`notifications`·`fileDrop` F-145 A6 을 더하나 — **기본값: 더한다 (8장)**

- 이유: `open`(인식 못 한 해시·없는 문서·스레드)·`thread`·`share` 갈래를 hashchange 로 타는 테스트가 이 셋에만 있다. 6장 행에서 빼는 것이 아니라 더하는 것이다(F-2066 Q2·F-2067 Q5·F-2068 Q7 과 같은 판단)
- 다른 쪽(6장 행 그대로): 이 갈래들을 묶음 안에서 아무것도 보지 않는다. `verify:full` 이 결국 돌리지만 실패 원인을 좁히기 어렵다

### 관찰 (이 조각은 고치지 않는다 — F-2059 7장 성격, 판정은 사용자)

1. **도움말 → 공유 관리 → 뒤로 가기에서 공유 관리가 남을 수 있다.** `shares` 갈래는 `helpOpen` 을 끄지 않고 `help` 갈래는 `helpOpenRef` 가 참이면 무시한다. 도움말 화면에서 계정 메뉴 `공유 관리`(`location.hash = '#/shares'`)로 가면 `sharesOpen`·`helpOpen` 이 둘 다 참이 되고(렌더는 `sharesOpen` 우선), 뒤로 가기로 `#/help` 가 되어도 무시되어 주소는 `#/help`, 화면은 공유 관리로 남는다. 거꾸로 공유 관리 → 도움말(`openHelp` 는 `sharesOpen` 을 끈다)은 문제없다. 코드를 읽어 판단했고 실행해 보지 않았다(도움말 화면에서 계정 메뉴가 보이는지 미확인)
2. **`share` 갈래는 `sharesOpen`·`helpOpen` 을 끄지 않는다.** 공유 보기(`sharedDoc`)가 가장 앞이라 그동안은 안 보이지만, `closeSharedDoc`(`setSharedDoc(null)` + replace)으로 닫으면 밑에 남은 공유 관리·도움말 화면이 드러날 수 있다(코드 읽기)
3. **지도 중심 id 가 목록에 없으면** `anchorId` 는 `null` 이 되지만 주소는 `#/map/{그 id}` 로 남는다(replace 없음)
4. **홈(문서 없음, 화면 없음)에서 인식 못 한 해시는 무시된다** — 규칙 7 이 `null === null` 로 `ignore` 를 낸다(U20). 주소가 `#abc` 그대로 남고 알림도 없다. 문서를 연 상태에서는 "첫 문서 + `문서를 찾을 수 없습니다.`"(F-232 리뷰 A4)로 가므로 두 경우가 다르다
5. 옮기는 주석 ``// 공개 링크(#/p/…)는 위 handlePublicHashChange 가 …`` 의 "위" 는 App 안 위치를 가리킨다. `hashNav.ts` 로 가면 가리키는 대상이 다른 파일이 된다. F-2059 3.6 "주석은 그대로" 에 따라 고치지 않는다
6. `toPublicRoute(parsePathRoute(location.pathname)) ?? toPublicRoute(parseHash(location.hash))` 가 `publicRoute` 초기값과 `handlePublicHashChange` 에 두 벌 있다. 모양이 같아도 합치지 않는다(F-2059 1.1)
7. **경계 — 뒤 조각과 대조 필요.** F-2074(부팅)가 옮길 부팅 effect 는 `replaceHashUrl`·`parseHash` 를 쓴다. 이 조각 뒤 `replaceHashUrl` 은 `useHashRouting.ts` 에서 온다 — F-2074 명세가 옵션으로 받을지 import 할지 정한다. F-2072(편집기 연동)는 `focusEditorRef` 를 App 에 남긴다는 이 조각의 전제와 부딪치지 않는지 본다
