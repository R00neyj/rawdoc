## 2. 범위

### 한다

- `Y.Doc` 과 `ySync` 사이에 **공유 `Y.Doc`**(원격 쪽) 하나를 더 두고, 원격 업데이트를 편집기 `Y.Doc` 으로 넘기는 자리에 **IME 게이트**를 건다 (3·4장)
- 조합 중 보류, `compositionend` 뒤 한 번에 적용 + `forceRecalc`, 초점을 잃었거나 브라우저가 조합이 아니라고 알린 "끝난 조합" 처리 (5장)
- 표 칸 편집 중 원격이 **그 칸**을 건드리면 편집 세션을 끝낸다 (6장)
- 원격 연결 훅 `window.__yProviderFactory` 와 포트 `YLinkPort` — e2e 와 개발용 연결이 같은 입구를 쓴다 (8장)
- 개발 빌드 전용 두 탭 연결(`?ysync`)과 사람 확인 절차 (9장·13.4)

### 하지 않는다

- provider·WebSocket·awareness·원격 커서·경로 판정(F-301 8장)·재연결·영속 — F-304~F-307. **개발용 두 탭 연결은 운영 경로가 아니다**
- 제목 `Y.Text` — F-305(F-302 2장). 개발용 연결에서도 제목은 지금처럼 저장 → `docs-changed` 로만 따라간다
- `Y.Doc` 수명을 `createEditor` 밖으로 꺼내기 — F-302 Q6 그대로 F-305 가 정한다
- 운영 빌드에서 사용자에게 보이는 변화. **훅이 없으면 중계 자체가 생기지 않고 F-302 와 한 바이트도 다르지 않게 돈다**(4.2)

## 3. 게이트를 거는 방식 — 결론: (b) 중계 `Y.Doc`

### 3.1 `y-codemirror.next` 0.3.6 에 훅이 있는가 — **없다** (U4 답)

- `y-sync.js` `YSyncPluginValue` 생성자가 `ytext.observe(this._observer)` 를 직접 건다. observer 는 `tr.origin !== this.conf` 인 **모든** 트랜잭션을 곧바로 `view.dispatch({ changes, annotations: [ySyncAnnotation.of(conf)] })` 로 옮긴다. 거를 인자·콜백이 없다
- `YSyncConfig` 가 받는 것은 `ytext`·`awareness` 둘뿐이다
- 공개 export 는 `yCollab`·`ySync`·`ySyncFacet`·`YSyncConfig`·`ySyncAnnotation`·`yRemoteSelections`·`yRemoteSelectionsTheme`·`YRange`·`yUndoManagerKeymap` 이고 `package.json` `exports` 는 `.` 하나다(F-302 4.5 와 같은 확인). `yUndoManager` 플러그인은 `yCollab` 을 거쳐야만 얻고, `yCollab` 은 항상 `ySync` 를 같이 넣는다

### 3.2 세 안 비교

## 4. 중계 구조

### 4.1 두 Doc 과 흐름

```
원격(개발 연결·e2e 훅, F-305 이후 provider)
        │ applyRemote            ▲ onLocalUpdate
        ▼                        │
   공유 Y.Doc  ── 원본(truth) ────┘
        │ ▲
 게이트 │ │ 편집기에서 나온 update 는 같은 틱에 그대로
(5장)   ▼ │
   편집기 Y.Doc (F-302 의 binding.ydoc, UndoManager 가 여기 붙는다)
        │ ySync (F-302 그대로)
        ▼
   EditorState
```

| 방향 | 언제 | origin |
| --- | --- | --- |
| 편집기 → 공유 | 편집기 Doc 의 `update` 이벤트마다, **원인이 중계가 아니면 전부**(로컬 입력·되돌리기·다시 실행). 같은 호출 안에서 동기로 | 공유 Doc 쪽 origin = 중계 상수 `RELAY_FROM_EDITOR` |
| 공유 → 편집기 | 공유 Doc 의 `update` 이벤트 중 origin 이 `RELAY_FROM_EDITOR` 가 아닌 것(= 원격·입양). 게이트가 열려 있으면 곧바로, 닫혀 있으면 비울 때 | 편집기 Doc 쪽 origin = 중계 상수 `RELAY_FROM_SHARED` |
| 공유 → 원격 | 공유 Doc `update` 중 origin 이 `RELAY_FROM_EDITOR` 인 것만 `onLocalUpdate` 구독자에게 | — |

- 편집기 → 공유가 **같은 틱에 동기**로 가므로, 게이트가 열려 있는 동안 두 Doc 의 상태 벡터는 모든 트랜잭션 경계에서 같다(실측 M1 마지막 판정). 편집기 Doc 은 늘 공유 Doc 의 부분집합이다 — 공유 Doc 이 편집기에서 온 업데이트의 의존 구조를 기다리는 일이 없다
- **공유 Doc 에서는 입양의 지우기(8.3) 말고 로컬 쓰기를 하지 않는다.** 모든 로컬 입력은 편집기 Doc 에서 `ySync` 를 거쳐 생긴다. 공유 Doc 은 제 clientID 로 구조를 만들지 않으므로 yjs `cleanupTransactions` 의 "Changed the client-id…" 분기에 걸리지 않는다
- 공유 Doc 은 옵션 없이 만든다(`gc: true`). 시작 상태는 편집기 Doc 전체 상태를 한 번 넣은 것(씨앗 포함)

### 4.2 중계는 연결이 붙을 때만 만든다

- 공유 Doc·중계·게이트는 **`connectRemote` 가 훅을 찾았을 때만** 만든다(8.2). 훅이 없으면(운영의 모든 경우, F-302 e2e, 랜딩 데모) 편집기 Doc 에 리스너 하나 붙지 않고 F-302 와 같다
- 근거: 실측 (c) — 원격이 없는 문서에 메모리 두 배·키 입력당 인코딩을 물릴 이유가 없다. 두 경로가 아니라 "붙으면 켜진다" 한 경로다. F-305 에서 서버 문서는 전부 provider 가 붙으므로 그때는 늘 켜진다. 다른 안은 15장 Q4

### 4.3 비우기가 `forceRecalc` 를 스스로 보낸다

- 보류분을 편집기 Doc 에 넣은 **직후** 게이트가 주 뷰에 `forceRecalc` 를 dispatch 한다. 순서가 계약이다 — 적용이 먼저, 재계산 신호가 나중(F-301 5.2)
- `compositionCatchup`(주 뷰)·칸의 `compositionend` 처리기(`tableWidget.ts` `startEdit`)가 같은 `setTimeout(0)` 대에 보내는 기존 `forceRecalc` 와 **순서를 맞추지 않는다.** 기존 것이 먼저 가도 뒤따르는 "적용 → forceRecalc" 가 다시 맞추고, 뒤에 가도 내용이 같다(`createEditor.ts` `focusRelay` 주석의 "여기서 다시 보내도 내용엔 영향 없다" 와 같은 성질). 그래서 `composition.ts` 에 훅을 넣지 않는다
- 게이트가 곧바로 넘긴 원격(조합 중이 아닐 때)에는 `forceRecalc` 를 보내지 않는다. 조합 중이 아니면 여섯 보류 지점이 보통 트랜잭션처럼 다시 계산한다

### 4.4 `createEditor` 조립

- 옵션 `docId?: string` 을 더한다. `Editor` 가 prop 으로 받아 넘기고, `App` 은 `currentDocId` 를 준다. 랜딩 데모(`src/welcome/demo.ts`)는 넘기지 않는다 → 연결이 붙지 않는다
- 뷰를 만든 **뒤** `connectRemote({ view, editorDoc: binding.ydoc, docId })` 를 부른다. 뷰가 있어야 조합 상태를 읽을 수 있고, 원격 도착은 전부 뒤의 작업(메시지·타이머·`page.evaluate`)이라 `EditorState.create` 와 뷰 생성 사이에 끼어들 틈이 없다
- `destroy()` 순서: 기존 정리 → `remote?.destroy()`(연결 `destroy`, DOM 리스너·타이머 해제, 공유 Doc `destroy`) → `view.destroy()` → `binding.destroy()`
- **`EditorHandle` 은 바뀌지 않는다.** 공유 Doc 을 handle 로 내보내지 않는다(F-302 Q6 과 같은 이유)

### 4.5 불변조건과의 관계 — 문구 수정이 필요하다

지금 `CLAUDE.md` 문장 "The one source of truth for an open document is the `Y.Text` in its `Y.Doc`" 은 Doc 이 하나라고 가정한다. 이 명세 뒤로는 연결이 붙은 문서에 Doc 이 둘이다

- **원본은 공유 Doc 의 `Y.Text`** 다. provider·영속(F-305·F-306)이 붙는 곳이고, 원격이 가장 먼저 도착하는 곳이다
- 편집기 Doc 은 **게이트 뒤의 Yjs 복제본**이다. 손으로 맞추는 사본이 아니라 Yjs 업데이트로만 따라가고, 차이는 "아직 넘기지 않은 원격" 뿐이며 게이트가 열리면 사라진다
- 연결이 없으면 편집기 Doc 하나가 원본이다(지금과 같다)

문구 제안은 14장, 승인 여부는 15장 Q1

## 5. 보류·비우기 규칙

### 5.1 "조합 중" 판정

`조합 중` = **주 뷰의 `view.compositionStarted`** 또는 **활성 칸 하위 뷰의 `compositionStarted`**(`isCellCompositionStarted(mainView)`, 6.1)

- `composing` 이 아니라 `compositionStarted` 를 본다. `@codemirror/view` 6.43.11 에서 `composing` 은 `inputState.composing > 0`(조합 뒤 첫 변경부터), `compositionStarted` 는 `>= 0`(`compositionstart` 직후부터)이다. `composition.ts` 머리 주석이 적은 "조합 진입 직후 첫 update 1건은 보류를 타지 않고 통과" 틈에 원격이 커서 줄을 다시 그리면 IME 가 조합 기준점을 잃을 수 있어 그 틈까지 막는다
- 데스크톱 Chrome 은 DOM 조합 이벤트를 쓴다 — CM6 가 EditContext 를 쓰는 조건은 `window.EditContext && browser.android` 뿐이다

### 5.2 원격 업데이트 하나가 공유 Doc 에 도착했을 때

| 지금 상태 | 동작 |
| --- | --- |
| 이미 보류 중 | 계속 보류. 따로 쌓지 않는다 — 공유 Doc 이 이미 담고 있다 |
| 보류 중 아님, `조합 중` | 보류 시작. 점검 타이머(5.4)를 건다 |
| 보류 중 아님, `조합 중` 아님 | 곧바로 편집기 Doc 에 넣는다(`RELAY_FROM_SHARED`). `forceRecalc` 없음 |

- 표 칸 편집 중(조합 아님)이어도 곧바로 넣는다 — 칸 쪽 처리는 6장
- 개발 플래그 `nogate`(9.1)가 켜져 있으면 표 첫 두 행을 건너뛰고 늘 곧바로 넣는다(사람 확인 H0 용)

### 5.3 비우기

**비우기** = 공유 Doc 의 상태를 편집기 Doc 의 상태 벡터 기준 차분으로 뽑아 편집기 Doc 에 **한 번의 `applyUpdate`**(= Yjs 트랜잭션 1개 = `ySync` 가 만드는 CM6 트랜잭션 1개)로 넣고, 이어서 `forceRecalc` 를 dispatch 한다(4.3)

- 상태 벡터 차분을 고른 이유: 보류한 update 를 목록으로 들고 있을 필요가 없고(공유 Doc 이 이미 들고 있다), 순서·중복을 따질 일이 없다. 실측 (c) 에서 목록 합치기보다 느린 경우(삭제 기록이 큰 문서 5.59ms 대 3.69ms)가 있지만 비우기는 단어 경계마다 한 번이라 둘 다 문턱 아래다
- **조합 중에는 비우지 않는다.** 아래 5.4 의 "끝난 조합" 만 예외이고, 그것은 브라우저 쪽에서 조합이 이미 없다는 신호가 있을 때다

| 비우기를 시도하는 때 | 조건 | 동작 |
| --- | --- | --- |
| `compositionend` 가 주 뷰 `view.dom` 에 닿은 뒤 한 틱(`setTimeout(0)`). 칸 하위 뷰의 `compositionend` 도 버블로 여기 닿는다 — 리스너는 `view.dom` 에 캡처로 단다 | 보류 중이고 `조합 중` 이 아니다 | 비우기 |
| 같은 때 | 여전히 `조합 중`(한글은 음절이 끝나자마자 다음 음절 조합이 시작될 수 있다) | 아무것도 안 한다. 다음 `compositionend` 에서 다시 본다 |
| 점검 타이머(5.4) | 5.4 표 | 5.4 표 |
| `view.dom` 에 캡처로 단 `keydown` 이 `isComposing === false` 이고 `keyCode !== 229` 인데 보류 중이고 `조합 중` 이 참 | 브라우저는 조합이 아니라고 말하는데 CM6 표시만 남은 상태(끝난 조합) | 한 틱 뒤 **강제 비우기**(조합 판정을 보지 않고 비우기) |

### 5.4 끝난 조합과 점검 타이머 — F-301 "200개 또는 2초" 를 바꾼다

- 보류를 시작하면 `REMOTE_HOLD_CHECK_MS`(2,000ms) 타이머를 건다. 울리면:

| 상황 | 동작 |
| --- | --- |
| 이미 비었다 | 타이머를 끝낸다 |
| `조합 중` 아님(비우기 기회를 놓친 경우) | 비우기 |
| `조합 중` 이고 **살아 있다** — 조합 중인 뷰의 DOM 에 포커스가 있고(`view.dom.contains(document.activeElement)`), `document.hasFocus()` 가 참이고, `document.visibilityState === 'visible'` | 비우지 않는다. 타이머를 다시 건다 |
| `조합 중` 인데 살아 있지 않다(창·탭을 떠남) | **강제 비우기** |

- **살아 있는 조합 중에는 시간이 얼마나 지나도 비우지 않는다.** 불변조건 "Never apply remote updates during IME composition" 에 예외를 만들지 않기 위해서다. 대가: 사용자가 한 음절을 조합해 둔 채 포커스를 두고 가만히 있으면, 그동안 온 원격은 그 사람 화면에 안 보인다. 원격분은 이미 공유 Doc 에 있고(원본에 반영됨) 그 사람이 무엇이든 치거나 클릭하면 조합이 끝나 곧바로 보이므로 잃는 것이 없다
- **개수 상한을 두지 않는다.** 보류분은 목록이 아니라 공유 Doc 안에 있으므로 개수가 늘어도 따로 커지는 메모리가 없고, 200건을 한 번에 비우는 데 0.11ms(실측 (c))다. F-301 5.2 의 "200개" 가 막으려던 것이 여기서는 생기지 않는다
- F-301 5.2 "2초" 는 "2초마다 조합이 살아 있는지 본다" 로 바뀐다. H6(조합 도중 창 전환)의 기대도 이것에 맞춘다(13.4)
- 조합을 억지로 끝내는 동작(포커스를 뺐다 돌려주기 등)은 하지 않는다. 끝난 조합일 때만 강제로 비우므로 깰 조합이 없다

## 6. 표 칸

### 6.1 칸 조합 판정

`tableWidget.ts` 에 `isCellCompositionStarted(mainView): boolean` 을 더한다. 활성 칸 세션이 있고 그 하위 뷰의 `compositionStarted` 가 참이면 true. 기존 `isCellComposing`(`composing` 기준, `blocks.ts` 가 씀)은 그대로 둔다

### 6.2 결정 — 칸 편집 중(조합 아님) 원격은 곧바로 넣고, 그 원격이 **편집 중인 칸**을 건드렸으면 세션을 끝낸다

F-301 5.3 은 "그 **표** 범위를 건드리면 보류, 3초 넘으면 `endEdit` 뒤 적용" 이었다. 코드를 읽어 보니 표 범위 전체를 막을 필요가 없고, 막으면 H3 이 깨진다

코드에서 확인한 것:

- **같은 표 다른 칸의 원격은 칸 세션을 해치지 않는다.** 원격 트랜잭션도 `blocks.ts` `blockPreview` 의 StateField 를 지나며 `trackActiveEditRange` 가 활성 칸 범위를 옮긴다. 표 원문이 바뀌면 새 `TableWidget` 이 `eq` 에서 다르다고 나오고 CM6 가 `updateDOM` 을 부른다. `sameShape` 가 참이면 **활성 칸만 빼고** 나머지 칸 글자를 고쳐 쓰고 `active.widget` 을 새 위젯으로 바꾼다 — 하위 에디터는 그대로다. 표 밖 원격이면 표 원문이 그대로라 `eq` 가 참이고 DOM 을 건드리지 않는다
- **위험한 것은 같은 칸이다.** `pushCellEdit` 는 칸 입력마다 칸 전체를 `{ from, to, insert }` 로 갈아 끼운다. 원격이 같은 칸에 글자를 넣은 뒤 내가 한 글자를 더 치면 그 원격 글자가 지워진다 — 조용한 유실이다
- **행·열 수가 바뀌는 원격**은 `updateDOM` 의 "구조 바뀜" 분기에서 `endEdit(deferDispatch)` → 세션이 끝난다(튕김). 조합이 아니면 칸 값은 입력마다 이미 주 문서에 들어가 있어 잃는 것이 없다

그래서:

| 칸 세션 중 원격 | 동작 |
| --- | --- |
| 조합 중 | 5장대로 보류(`조합 중` 에 칸 조합이 들어 있다) |
| 조합 아님, 활성 칸 범위를 안 건드림 | 곧바로 적용. 세션 유지. 같은 표 다른 칸이면 그 칸 글자가 바로 바뀐다 |
| 조합 아님, 활성 칸 범위를 건드림 | 곧바로 적용한 뒤 **세션을 끝낸다**. 칸은 합쳐진 원문으로 다시 그려진다 |
| 조합 아님, 행·열 수를 바꿈 | 지금 코드대로 세션이 끝난다(튕김). 바꾸지 않는다 |

- "건드림" 판정: `trackActiveEditRange(mainView, tr)` 안에서, `tr` 에 `ySyncAnnotation` 이 붙어 있고 **옮기기 전** 칸 범위에 대해 `tr.changes.touchesRange(from, to)` 가 `false` 가 아니면(`@codemirror/state` `ChangeDesc.touchesRange` — 양 끝 포함) 표시한다. 칸 범위가 `null`(아직 없는 채움 칸)이면 `lineStart` 가 든 줄 전체를 범위로 본다
- 세션 종료는 StateField 갱신 도중이라 바로 할 수 없다 — **마이크로태스크**에서, 그때도 같은 세션이 살아 있으면 `endEdit(mainView)`(보통 경로)를 부른다. 조합이 아니므로 `pushCellEdit` 가 다시 불리지 않고 원격 글자를 덮지 않는다
- `ySyncAnnotation` 은 되돌리기 결과에도 붙지만, 칸 세션 중의 되돌리기는 `cellKeydown` 이 먼저 `endEdit` 를 부르므로 세션이 없다. 칸 안 브라우저 메뉴 되돌리기는 `TableWidget.ignoreEvent` 가 true 라 주 뷰의 `beforeinput` 처리기에 닿지 않는다
- F-301 5.3 과의 차이와 되돌리는 경우의 영향은 15장 Q2(사람 결정 필요)

### 6.3 칸의 마이크로태스크 쓰기와 Yjs 트랜잭션 경계 — 어긋나지 않는다 (F-301 5.1 위험 3 결론)

- 칸 입력은 **동기**다. 칸 하위 뷰의 `updateListener` → `pushCellEdit` → `mainView.dispatch` 가 같은 호출 안에서 돌고, 주 뷰 트랜잭션 하나가 `ySync` 의 Yjs 트랜잭션 하나가 된다
- 마이크로태스크로 미루는 쓰기는 `endEdit({ deferDispatch: true })` 하나뿐이고, 그것은 뷰 갱신 도중(`TableWidget.updateDOM`·`destroy`) 불릴 때 **칸이 조합 중이었던** 경우에만 생긴다
- 원격 적용은 전부 매크로태스크(BroadcastChannel 메시지, WebSocket 메시지, 게이트 타이머, `page.evaluate`)에서 시작한다. 마이크로태스크는 지금 작업이 끝나자마자 돌므로 **미룬 쓰기와 그 원인이 된 갱신 사이에 원격이 끼어들 수 없다**
- 끼어든다 해도 `trackPendingWrites` 가 `blockPreview` StateField 에서 문서가 바뀐 모든 트랜잭션(원격 포함)마다 미룬 범위를 옮긴다
- 게이트가 칸 조합 중 원격을 막으므로, 원격 트랜잭션이 "조합 중 칸 + 구조 바뀜" 으로 미룬 쓰기를 일으키는 경로 자체가 없다

## 7. 저장·`getText` — F-302 13장 Q1 다시 정함: **`EditorState` 그대로**

보류 중에는 편집기 쪽(화면·`EditorState`)이 공유 Doc(원본)보다 늦다. 벌어지는 폭은 "조합 한 단어" 또는 "끝난 조합이면 최대 2초"(5.4)다

| 읽는 곳 | 읽는 것 | 이유 |
| --- | --- | --- |
| `getText`(저장 `useDocSaver`, 공유 `getShareDoc`, 인쇄, 보기 모드 변환, `새 문서로 저장`, `jumpToHeading`) | **`EditorState`**(지금 그대로) | `jumpToHeading` 이 `getText('lf')` 로 줄 번호를 찾아 `view.state.doc.line(n)` 에 넣는다. 원본을 읽게 하면 보류 중 줄 수가 달라 엉뚱한 줄로 가거나 `RangeError` 가 난다. 읽는 곳을 하나로 두는 F-302 의 이유가 그대로 남는다 |
| 통계·목차·검색 | `EditorState` | 화면에 보이는 것과 같아야 한다 |

**F-303 시점에 실제로 달라지는 것:**

- **운영: 없다.** 원격이 없어 보류가 생기지 않는다
- **개발용 두 탭 연결**: 두 탭이 같은 IndexedDB 문서를 저장한다(9.4). 보류 중인 탭이 저장하면 다른 탭의 최신 편집이 빠진 본문이 잠깐 저장될 수 있다. 그러나 비우기는 `docChanged` 트랜잭션이라 `App` 의 `handleDocChange` → `notifyChange` 가 다시 저장을 예약한다 — 700ms 뒤 합쳐진 본문으로 덮인다. 개발용이라 이 틈을 받아들인다
- **F-305 이후**: 연결된 서버 문서는 본문을 `useDocSaver` 로 저장하지 않고 DO 가 쓴다(F-301 8.1). "저장이 원본보다 늦다" 는 문제가 운영 경로에 생기지 않는다. 내보내기·공유가 보류분을 빼고 나가는 것은 화면에 보이는 대로 나가는 것이라 받아들인다. 다른 안은 15장 Q5

## 8. 원격 연결 훅과 포트

### 8.1 계약

F-301 10.2 의 `window.__yProviderFactory` 이름을 그대로 쓰고, 그 인자 모양을 여기서 정한다. e2e(운영 빌드)와 개발용 연결(개발 빌드)이 **같은 입구**를 쓴다

```ts
// src/editor/remoteGate.ts
export const REMOTE_HOLD_CHECK_MS = 2000

export type YLinkPort = {
  docId: string
  encodeState(): Uint8Array                    // 공유 Doc 전체 상태
  applyRemote(update: Uint8Array): void        // 공유 Doc 에 원격으로 넣는다 — 게이트를 거쳐 편집기로
  adopt(state: Uint8Array): boolean            // 8.3
  onLocalUpdate(listener: (update: Uint8Array) => void): () => void  // 편집기에서 나온 업데이트, 구독 해제 함수를 돌려준다
  holding(): boolean                           // 보류 중인가 (테스트·진단용)
  sharedText(): string                         // 공유 Doc 본문 (테스트·진단용)
}

export type YProviderFactory = (port: YLinkPort) => { destroy(): void }

declare global {
  interface Window { __yProviderFactory?: YProviderFactory }
}
```

- `createRemoteGate(editorDoc, options)` 는 뷰 없이 도는 부분(두 Doc·중계·보류·비우기·입양·포트)이고, `connectRemote({ view, editorDoc, docId })` 는 뷰·DOM 배선(5.1 판정, `compositionend`·`keydown` 리스너, 5.4 의 포커스 판정, 비운 뒤 `forceRecalc`)과 훅 호출이다. **node 단위 테스트가 `createRemoteGate` 를 뷰 없이 돌릴 수 있어야 한다** — 조합 판정·살아 있음 판정·비운 뒤 콜백·`nogate` 는 옵션으로 넣는다. 옵션의 모양은 구현이 정한다
- `connectRemote` 는 `docId` 가 있고 `window.__yProviderFactory` 가 함수일 때만 공유 Doc 을 만들고 팩토리를 부른다. 아니면 `null` 을 돌려주고 아무것도 만들지 않는다(4.2)
- 팩토리가 던지면 `console.error` 를 찍고 중계를 걷어 연결 없이 계속한다
- `applyRemote`·`adopt` 는 `destroy` 뒤에 불려도 던지지 않고 무시한다
- 이 입구가 운영 빌드에 남는 것은 F-301 10.2 가 정했다("분기가 없으면 e2e 를 못 쓴다"). F-305 가 진짜 provider 를 붙일 때 이 모양을 넓힐 수 있다(예: 공유 Doc 을 넘기기) — 그때 F-305 가 정한다

### 8.2 origin 상수

`RELAY_FROM_EDITOR`·`RELAY_FROM_SHARED`·`REMOTE`(`applyRemote`·`adopt` 가 공유 Doc 에 쓰는 origin) 세 개를 모듈 안 객체 상수로 둔다. 문자열이 아니라 객체라 다른 모듈의 origin 과 우연히 같을 수 없다. `Y.UndoManager` 의 `trackedOrigins` 에 들지 않는다

### 8.3 입양 `adopt` — 씨앗 두 벌 막기

F-302 3.1 대로 에디터마다 저장소 본문을 씨앗으로 심는다. 같은 문서를 연 두 탭(또는 두 e2e 페이지)을 이으면 **씨앗이 서로 다른 clientID 라 본문이 두 벌**이 된다(실측 M5 대조군). 늦게 연 쪽이 제 씨앗을 버리고 먼저 연 쪽 상태를 받는다

- `adopt(state)`: 이 공유 Doc 에 편집기에서 온 업데이트가 **씨앗 뒤로 한 번도 없었으면**, 공유 Doc 에서 한 트랜잭션(origin `REMOTE`) 안에 `Y.Text` 전체를 지우고 `state` 를 넣은 뒤 true. 로컬 편집이 이미 있었으면 지우지 않고 `state` 만 합친 뒤 false(본문이 두 벌이 될 수 있다 — 개발 연결이 경고를 찍는다, 9.3)
- 그 트랜잭션은 보통 원격처럼 게이트를 지나 편집기로 간다. 편집기 쪽 `UndoManager` 는 추적하지 않는다 — 입양을 Ctrl+Z 로 되돌릴 수 없다
- 입양한 쪽은 곧바로 **자기 전체 상태(`encodeState`)를 상대에게 보내야 한다.** 버린 씨앗 구조(GC 됨)를 상대가 모르면, 그 뒤 이쪽 편집기 clientID 로 만든 업데이트를 상대가 "앞 clock 이 빠졌다" 며 대기에 묶는다. 실측 M5 에서 전체 상태를 보낸 뒤 편집이 대기 없이 도착했다
- 운영 provider(F-305)는 입양을 쓰지 않는다 — 거기서는 브라우저가 씨앗을 심지 않는다(F-302 3.4). 입양은 "브라우저가 심은 Doc 을 잇는" 개발·테스트 연결을 위한 것이다

## 9. 개발용 두 탭 연결

### 9.1 켜는 방법 — 쿼리 `?ysync`

```ts
// src/editor/devSyncFlag.ts
export const DEV_YSYNC: boolean         // import.meta.env.DEV 이고 location.search 에 ysync 가 있다
export const DEV_YSYNC_NOGATE: boolean  // DEV_YSYNC 이고 그 값이 nogate 다
```

- 주소: `http://localhost:5173/?ysync#/d/{문서 id}`. 게이트를 끄고 비교하려면 `?ysync=nogate`
- 두 상수의 첫 항이 `import.meta.env.DEV` 라 운영 빌드에서 `false` 로 접힌다(실측 (d) — 다른 모듈에서 가져온 상수로도 접혔다)
- `src/main.tsx`: `DEV_YSYNC` 이면 `import('./app/yDevLink')` 를 불러 `installDevLink()` 한 **뒤** 앱을 그린다(첫 에디터가 만들어지기 전에 훅이 있어야 한다). 불러오기에 실패하면 `console.error` 를 찍고 연결 없이 그린다. 아니면 지금처럼 곧바로 그린다. **최상위 `await` 를 쓰지 않는다** — 운영 대상 문법 검사에 걸릴 수 있다
- `installDevLink()` 는 `window.__yProviderFactory` 에 개발 연결 팩토리를 넣는다
- 쿼리를 고른 이유: 탭마다 따로 켜지고, 저장되지 않아 잊고 켜 둘 일이 없고, `prefs.ts` 허용 키를 늘리지 않는다. 사이드바 `새 탭에서 열기` 는 `window.open(formatHash(id), '_blank', 'noopener')` — 해시만 적은 상대 주소라 지금 주소의 경로·쿼리를 그대로 이어받아 `?ysync` 가 따라간다. 다른 안은 15장 Q7

### 9.2 채널과 메시지

- 채널 이름 **`md-ydev`**(제품명 없음 — `md-tabs` 와 같은 규칙). F-296·F-297 의 `md-tabs` 와 **따로** 연다 — 수명(개발 전용, 에디터마다)이 다르다
- 연결(= 팩토리 호출) 하나마다 채널 객체 하나, `destroy` 에 닫는다. StrictMode 이중 마운트로 잠깐 둘이 생겨도 `linkId` 가 달라 섞이지 않는다

```ts
// src/app/yDevLink.ts
export const DEV_LINK_CHANNEL = 'md-ydev'

export type DevLinkMessage =
  | { kind: 'hello'; docId: string; linkId: string; openedAt: number; synced: boolean }
  | { kind: 'state'; docId: string; linkId: string; openedAt: number; to: string | null; update: Uint8Array }
  | { kind: 'update'; docId: string; linkId: string; update: Uint8Array }
```

- `linkId` 는 `newTabId()`(`src/lib/tabChannel.ts`), `openedAt` 은 연결 시각 `Date.now()`. `Uint8Array` 는 구조화 복제로 그대로 간다
- `docId` 가 내 것과 다르거나 `linkId` 가 내 것인 메시지는 전부 무시한다
- `state` 는 보낸 쪽이 `synced` 일 때만 나간다(아래 규칙)

### 9.3 규칙 — 순수 리듀서 `reduceDevLink`

`reduceDevLink` 는 상태와 사건(연결됨·대기 타이머·메시지·로컬 업데이트)을 받아 새 상태와 할 일(보내기·입양·원격 넣기·타이머 걸기·콘솔 찍기) 목록을 돌려주는 **순수 함수**다. `BroadcastChannel`·Yjs 를 모른다. 구동부가 할 일을 실행한다. F-296 `reduceClaim` 과 같은 모양. 이름만 계약이고 상태·사건·할 일의 모양은 구현이 정한다

| 사건 | 조건 | 할 일 |
| --- | --- | --- |
| 연결됨 | — | `synced = false`, `hello` 보내기, `CLAIM_WAIT_MS`(150ms, `src/lib/tabChannel.ts`) 대기 타이머 |
| 남의 `hello` | 나는 `synced` | `state { to: 보낸 쪽, update: encodeState() }` |
| 남의 `hello` | 나는 아직 아님 | 보낸 쪽을 "경쟁자"(`openedAt`, `linkId`)로 적어 둔다 |
| 대기 타이머 | 아직 아님, 적어 둔 경쟁자 중 나보다 먼저인 쪽이 있다(`claimWins(경쟁자, 나)` — `src/app/tabSync.ts`, `since` 자리에 `openedAt`, `tabId` 자리에 `linkId`) | 적어 둔 것을 비우고 `hello` 를 다시 보내고 타이머를 다시 건다 |
| 대기 타이머 | 아직 아님, 그런 경쟁자 없음 | `synced = true`, 콘솔 `[ysync] 연결됨 · 먼저 연 탭` |
| `state`(`to` 가 나 또는 `null`) | 나는 아직 아님 | `adopt(update)`. `synced = true`. 결과가 true 면 콘솔 `[ysync] 연결됨 · 다른 탭의 내용을 받음`, false 면 `console.warn` `[ysync] 이 탭에서 먼저 편집해 본문이 두 벌이 될 수 있습니다`. 이어서 `state { to: null, update: encodeState() }` 와 `hello { synced: true }` 를 보낸다(셋째 탭이 있으면 그 응답으로 빠진 것을 채운다) |
| `state` | 나는 `synced` | `applyRemote(update)` |
| `update` | 나는 `synced` | `applyRemote(update)` |
| `update` | 아직 아님 | 무시(곧 올 `state` 가 담고 있다 — 같은 보낸 쪽의 메시지는 순서대로 온다) |
| 로컬 업데이트(`onLocalUpdate`) | `synced` | `update` 보내기 |
| 로컬 업데이트 | 아직 아님 | 보내지 않는다(입양 뒤 보내는 전체 상태에 들어간다) |

- 동시에 연 두 탭: 둘 다 서로를 경쟁자로 적고, 늦은 쪽은 타이머에서 `hello` 를 다시 보내고, 먼저 쪽은 `synced` 가 된 뒤 그 `hello` 에 `state` 로 답한다 → **정확히 한 쪽만 입양한다.** 둘 다 제 씨앗으로 `synced` 가 되면 서로 모르는 구조를 기다리며 조용히 갈라지므로 이 규칙이 필요하다
- 보장 범위: 두 탭은 위 규칙으로 맞는다. 셋 이상은 입양 뒤 `hello` 재전송으로 채우는 최선 노력이다. 사람 확인은 두 창으로 한다
- `nogate` 로 켜졌으면 연결 때 콘솔 `[ysync] 게이트 끔 (nogate)` 를 한 번 찍는다

### 9.4 두 탭이 같은 로컬 문서를 편집할 수 있게 — F-296 편집권을 끈다

지금 같은 로컬 문서를 두 탭에서 열면 나중 탭이 `다른 탭에서 편집 중입니다. 읽기만 할 수 있습니다.` 로 읽기 전용이 된다(F-296 6.4). 개발용 연결에서는 둘 다 편집해야 한다

- `App.tsx` `claimDocId` 에 `!DEV_YSYNC` 조건을 더한다 → 편집권 질의를 안 하고 `claimReadOnly` 가 늘 false, `useDocSaver` 의 `blocked` 도 안 켜진다. 운영에서는 `false` 로 접혀 지금과 같다
- 두 탭 모두 같은 IndexedDB 문서를 저장한다(7장의 틈). 저장마다 `docs-changed` 가 가고 받는 탭은 목록만 다시 읽는다(F-296 7.2 — 열린 본문을 건드리지 않는다). 충돌이 아니다
- `npm run dev` 에는 Worker 가 없어 서버 문서를 쓸 수 없다 — **로그아웃 상태 로컬 문서만** 대상이다. F-213 잠금·경로 판정(F-301 8장)과 만나지 않는다
- `<Editor docId={currentDocId}>` — 공유 화면·지도가 떠 있는 동안에도 편집 영역은 숨김으로 살아 있으므로 연결도 살아 있다

### 9.5 운영 빌드에 안 실리는 것을 확인하는 법 (A27)

`npm run build` 뒤 `dist/assets` 에서

- `md-ydev`, `ysync`(소문자, 대소문자 구분) 가 **0건**. `y-codemirror.next` 의 식별자는 `ySync`(대문자 S)라 겹치지 않는다
- 파일 이름에 `yDevLink` 가 든 청크가 없다
- `__yProviderFactory` 는 **있다**(e2e 입구)
- 빌드 전후 청크 파일 수가 같다(A28)

**게이트 (F-301 5.5 이어받음)**: H1~H7 이 통과로 확인되기 전에는 **F-305(클라이언트 연결)의 결과물을 `deploy` 로 올리지 않는다.** 사용자가 "초대 편집자 전원에게 바로 연다" 를 골랐으므로 단계적 노출로 위험을 줄일 수 없고, 사람 확인이 유일한 방벽이다. F-303 자체는 운영에서 보이는 변화가 없어 이 게이트와 무관하게 배포해도 된다
