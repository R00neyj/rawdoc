## 2. 범위

### 한다

- 사이드바 `지도` 버튼 → 전체 화면 지도 (전제 1)
- **현재 문서 중심**(기본, 1~3단계)과 **전체 보기** 전환 (전제 2)
- 노드 클릭 → 그 문서를 열고 지도를 닫는다. Ctrl(⌘)+클릭 → 그 노드를 중심으로 다시 그린다
- **끊긴 링크**를 다른 모양의 노드로 그리고, 누르면 F-131 의 "그 제목으로 새 문서" 흐름을 그대로 탄다 (전제 3)
- 확대·이동(휠·끌기)과 `맞춤`(전체가 보이게)
- 그래프를 읽을 수 없는 사람을 위한 **`목록` 대체 표시** (7.4)
- 빈 상태 세 가지와 안내 문구 (6.5)

### 하지 않는다

- **링크 관계를 저장하지 않는다.** 메모리 인덱스만 쓴다. IndexedDB·D1 에 그래프 테이블을 만들지 않는다 (F-284 5.1 과 같은 결정)
- **원문을 바꾸지 않는다.** 지도는 읽기만 한다. 노드를 끌어 옮겨도 문서가 바뀌지 않고, 옮긴 위치를 저장하지도 않는다
- 폴더·태그·프론트매터 속성으로 묶어 색칠하기, 노드 필터, 검색창
- 마크다운 링크(`[글자](주소)`)·외부 링크·첨부 이미지를 그래프에 넣기. **위키링크(`[[…]]`)만**이다
- 방향 화살표 (9장 Q6)
- 배치가 움직이는 애니메이션 (9장 Q10). 계산을 끝낸 좌표를 한 번 그린다
- 지도에서 문서 만들기·이름 바꾸기·삭제. 끊긴 링크로 새 문서를 만드는 것만 예외이고, 그것도 F-131 흐름을 부를 뿐이다
- 공개 보기(F-210·F-211)·공유 화면(F-130)·랜딩(F-271)의 지도
- 단축키. 진입은 사이드바 버튼과 주소뿐이다 (6.4)
- 웹 워커, Barnes-Hut 근사 (5.4 상한 안에서는 필요 없다 — 필요해지면 명세를 먼저 고친다)

## 3. 링크 관계를 어디서 뽑는가 (`src/lib/wikiGraph.ts`)

### 3.1 지금 있는 코드로는 부족하다 — 확인한 사실

→ **문서 전체 문자열에서 링크 목록을 주는 순수 함수가 없다. 새로 만든다.**

### 3.2 새로 만들 함수

```ts
// 문서 원문 한 덩어리에서 위키링크 대상 제목을 순서대로 뽑는다
export function extractWikiTargets(content: string): string[]
```

- **입력**: 문서 원문 그대로(CRLF·LF 섞여도 된다). **출력**: 대상 제목 문자열 배열(중복 포함, 등장 순서)
- DOM·CM6·markdown-it·React·저장소를 import 하지 않는다. `lib/wikiLink.ts` 의 `findWikiLinks` 와 `lib/frontmatter.ts` 의 `findFrontmatter` 만 쓴다
- **제외 규칙은 F-131 2장·F-137 을 그대로 따른다.** 판정 수단만 구문 트리에서 줄 스캐너로 바꾼다

| 제외 | 판정 방법 |
| --- | --- |
| 프론트매터 | `findFrontmatter(content)` 가 준 범위 뒤부터 훑는다 (F-137 3.1) |
| 펜스 코드블록 | 줄 시작이 공백 0~3칸 + `` ``` `` 또는 `~~~` 이면 펜스 토글. 닫는 펜스는 같은 문자·같은 길이 이상 |
| 인라인 코드 | 줄 안에서 같은 개수의 백틱 쌍 사이를 공백으로 덮은 뒤 `findWikiLinks` 를 부른다 (위치가 어긋나지 않게 같은 길이로 덮는다) |
| 표 칸 | 어떤 줄이 `|` 를 담고 **바로 다음 줄이 구분 줄**(`| --- | :--: |` 모양)이면 그 줄부터 빈 줄 전까지를 표로 보고 건너뛴다 |
| `![[…]]` · 빈 대상 · `#` 뒤 | `findWikiLinks` 가 이미 한다 |

- **표 판정은 근사다.** CM6 구문 트리·markdown-it 은 GFM 표를 정확히 읽지만 줄 스캐너는 그렇지 않다. 실측(5.1)에서 합성 문서 30개를 두 방식으로 대조해 **30/30 같은 결과**가 나오는 것을 확인했고, 어긋날 수 있는 경우(목록 안 들여쓴 표, 표 뒤 빈 줄 없이 이어지는 문단)는 알려진 제약으로 남긴다
- **틀려도 원문은 바뀌지 않는다.** 표 안 링크를 잘못 세면 지도에 선이 하나 더 생길 뿐이고, 편집 화면 표시(F-131·F-137)는 지금 그대로 구문 트리로 판정한다. 두 곳의 판정이 다를 수 있음을 인정하고 지도 쪽을 관대한 쪽으로 둔다

```ts
export type WikiGraph = {
  nodes: { id: string; title: string; missing: boolean; degree: number }[]
  edges: { from: number; to: number }[]        // nodes 배열의 인덱스
  unreadable: string[]                          // 본문을 읽지 못한 문서 id (5.2)
}
// docs 는 store.list() 결과 그대로 — updatedAt 내림차순
export function buildWikiGraph(docs: { id: string; title: string; content: string; role?: string }[]): WikiGraph

export function subgraphAround(graph: WikiGraph, centerIndex: number, depth: number, cap: number):

```

### 3.3 제목 → 문서 매칭 — `resolveWikiTarget` 과 같은 결과를 내되 O(1) 로

`resolveWikiTarget(target, docs)` 를 링크마다 부르면 `링크 수 × 문서 수` 가 된다(링크 1만 개 × 문서 1,000개 = 1천만 회). 대신 **맵 두 개를 한 번 만든다**

1. `exact: Map<제목.trim(), 문서 인덱스>` — `docs` 순서(= `updatedAt` 내림차순)로 넣되 **이미 있으면 덮지 않는다**
2. `lower: Map<제목.trim().toLocaleLowerCase('ko'), 문서 인덱스>` — 같은 규칙
3. 조회: `exact.get(t) ?? lower.get(t.toLocaleLowerCase('ko')) ?? null`
4. 제목이 빈 문서는 두 맵에 넣지 않는다

- 이 순서가 F-131 2.1 의 세 규칙(정확 일치 → 대소문자 무시 → 여러 개면 목록 앞)과 **같은 답**을 낸다. `resolveWikiTarget` 이 `candidates.find(...)` 로 목록 앞에서부터 찾기 때문이다
- **단위 테스트로 대조한다** (A2): 같은 입력에 대해 두 방식의 결과가 같은지 본다. `wikiLink.ts` 는 고치지 않는다 — F-131 소유이고 편집·보기 모드가 쓴다

### 3.4 노드와 간선

- **노드**: 문서마다 1개(`id` = 문서 id, `missing: false`) + **끊긴 링크 대상마다 1개**(`id` = `missing:{정규화한 제목}`, `missing: true`). 끊긴 대상의 묶음 기준은 `trim()` 후 `toLocaleLowerCase('ko')` — `[[회의록]]` 과 `[[회의록 ]]` 은 같은 노드
- **간선**: `문서 → 대상 노드`. **같은 쌍이 여러 번 나오면 간선 하나로 합친다**(굵기를 바꾸지 않는다). 자기 자신을 가리키는 링크(`[[자기 제목]]`)는 간선으로 만들지 않는다 — 그리면 점 위에 점만 찍힌다
- **방향은 데이터에 남기되 그림에는 쓰지 않는다** (9장 Q6). `edges` 의 `from`·`to` 순서가 방향이고, 목록 대체 표시(7.4)가 이 방향으로 `나가는 링크`·`들어오는 링크` 를 나눈다
- `degree` = 들어오고 나가는 간선 수의 합(합쳐진 뒤 기준). 노드 크기와 상한 자르기(5.4)에 쓴다

### 3.5 부분 그래프 — 현재 문서 중심

- `subgraphAround(graph, centerIndex, depth, cap)`
  - 너비 우선으로 중심에서 `depth` 단계까지. **이웃은 방향을 가리지 않는다** — 내가 가리킨 문서와 나를 가리킨 문서(백링크)를 모두 이웃으로 본다. 이것이 지도를 보는 목적이다
  - 한 단계를 통째로 더했을 때 노드 수가 `cap` 을 넘으면 **그 단계를 더하지 않고** 멈추고 `truncated: true`. 단계 중간에서 자르지 않는다 — 잘린 모습이 매번 달라 보이면 읽을 수 없다
  - 중심이 끊긴 링크 노드일 수도 있다 (Ctrl+클릭으로 중심을 옮긴 경우)

## 4. 배치 — 힘 기반(force-directed) 직접 구현 (`src/lib/graphLayout.ts`)

```ts
export type LayoutOptions = { iterations?: number; width?: number; height?: number }
export function layoutGraph(nodeCount: number, edges: Int32Array | number[], options?: LayoutOptions):
  { x: Float64Array; y: Float64Array }
```

- **Fruchterman-Reingold(1991) 방식**을 쓴다. `k = √(넓이 / 노드 수)`, 반발력 `k²/d`, 인력 `d²/k`, 매 단계 변위를 **온도 `t` 로 제한하고 `t` 를 선형으로 냉각**한다
- **초기 배치는 난수가 아니라 황금각 나선**이다. 같은 입력이면 항상 같은 좌표가 나온다 — 그래야 단위 테스트가 되고 화면이 새로고침마다 달라지지 않는다
- 기본 `iterations = 150`. 5.1 실측에서 30~50회면 간선 길이 분포가 이미 안정되고 100회 이상에서는 변화가 없었다. 150회는 여유분이다
- DOM 을 모른다. 좌표만 돌려준다. 화면에 맞추는 일(중심 이동·배율)은 `MapGraph.tsx` 가 한다

> **"힘 기반 배치는 수십 줄로 쓸 수 있다" 는 조건부로만 참이다.** 처음에 속도를 누적하고 감쇠(0.85)하는 흔한 방식으로 짜서 재 보니 **반복 600회까지도 수렴하지 않았다**(노드 300개에서 간선 길이 표준편차가 78 → 1,172 → 871 로 널뛰었다). 변위를 온도로 제한하는 FR 방식으로 바꾸자 30회에서 이미 표준편차 78, 겹친 노드 0쌍으로 안정됐다. **어떤 수십 줄이냐가 결과를 가른다** — 그래서 알고리즘을 이 명세에 못 박는다 (5.1 "수렴 확인")

### 5.2 공유받은 문서 — 본문이 비어 있다

F-284 5.2 가 코드로 확인한 사실을 그대로 이어받는다: `src/storage/serverStore.ts` 의 `list()` 는 `api.getShared()` 결과를 **`content: ''` 로 채워** 돌려주고 캐시에 넣지 않는다

| 경우 | 지도에서 |
| --- | --- |
| 내 문서 | 노드 + 나가는 링크 + 들어오는 링크 전부 |
| **공유받은 문서** | **노드로는 넣는다. 나가는 링크만 없다** — 본문이 없어서 읽을 수 없다. 들어오는 링크(내 문서가 그 제목을 가리킨 것)는 제목 매칭이라 정상으로 잡힌다 |
| 로그인하지 않음 | IndexedDB `md-docs` 전부. 공백 없음 |

- 공유받은 문서 노드는 **다른 모양**으로 그린다(7.2) — 선이 한쪽만 있는 것이 데이터 부족 때문이지 실제로 링크가 없어서가 아님을 보여야 한다
- 결과 아래 안내: `공유받은 문서 {N}개는 나가는 링크를 읽지 못했습니다`
- 공유받은 문서 본문까지 읽으려면 문서마다 `api.getDoc` 요청이 한 건씩 나가고 F-207 캐시 정책을 바꿔야 한다 → 하지 않는다 (9장 Q5). F-284 Q4 와 같은 판단이다
- `buildWikiGraph` 는 `content` 가 빈 문자열인 문서의 id 를 `unreadable` 에 담아 돌려준다. 화면이 그 개수로 안내 문구를 만든다

### 5.3 인덱스와 재사용 — F-284 5.3 을 그대로 따른다

- 자리: `src/app/mapIndex.ts` 의 **모듈 수준 `Map<docId, { updatedAt, title, targets: string[] }>`**. React 상태가 아니다
- 만드는 시점: 지도를 열 때. `store.list()` + `store.listFolders()` 는 부르지 않는다(폴더를 안 쓴다)
- **바뀐 문서만 다시 만든다.** 판정 키는 `updatedAt` 과 `title` 둘 다, `>` 가 아니라 `!==`. `list()` 결과에 없는 id 는 지운다
- **로그인·로그아웃·계정 전환이면 통째로 버린다.** 인덱스를 만든 저장소 표시(`store.kind` + 계정 id)를 같이 두고 다르면 새로 만든다
- IndexedDB 에 영속시키지 않는다
- **메모리는 작다.** 담는 것이 대상 제목 문자열뿐이라 문서 1,000개 × 링크 10개 × 10자 ≈ 0.2MB 다. F-284 검색 인덱스(정규화한 본문 전체, 5,000개에 40MB 규모)와는 차원이 다르다
- **검색 인덱스(F-286 `searchIndex.ts`)와 합치지 않는다.** 지도를 열 때 검색용 본문 사본까지 메모리에 올릴 이유가 없다. `store.list()` 호출과 변경 판정 규칙만 같은 방식을 쓴다. 합칠지는 둘 다 구현된 뒤에 본다 (9장 Q7)
- **저장되지 않은 입력**: 지도를 열기 전에 `saver.flush()` 를 먼저 부른다(`beforeLeaveDoc()`). 안 그러면 방금 친 `[[링크]]` 가 지도에 없다

### 5.4 경계 — 몇 개까지 전부 그리는가

| 항목 | 값 | 근거 |
| --- | --- | --- |
| **한 화면에 그리는 노드 상한** | **500개** | 5.1(b) 실측. 500개 150회 반복 = 105ms. 800개면 266ms, 1,000개면 539ms 로 눈에 띄게 걸린다 |
| 전체 보기에서 노드가 상한을 넘으면 | **`degree` 큰 순으로 500개만** 그리고 안내. 같은 `degree` 면 `updatedAt` 최신순 | 연결이 많은 문서가 지도에서 쓸모가 크다. 자르는 기준이 예측 가능해야 한다 |
| 현재 문서 중심에서 넘으면 | 그 **단계를 통째로 더하지 않고** 멈추고 안내 (3.5) | 단계 중간에서 자르면 모습이 매번 달라진다 |
| 링크를 뽑는 대상 문서 수 | **상한 없음** | 5.1(a). 5,000개에 약 1초이고, 5.3 재사용으로 두 번째부터는 바뀐 문서만 낸다 |
| 배치 반복 횟수 | 150회 고정 | 5.1(c). 30~50회면 이미 수렴한다 |

**견디는 규모: 문서 5,000개까지 읽고, 한 번에 노드 500개까지 그린다.** 그 위로 가려면 (1) 노드 상한을 올리기 전에 Barnes-Hut 근사(사원 트리)로 반발력을 O(n log n) 으로 바꾸거나 (2) 웹 워커로 배치를 옮긴다. 둘 다 2장 "하지 않는다" 에 있으므로 **명세를 먼저 고치고 사람 승인을 받는다**

**게이트 — 구현할 때 판정한다**

- **잰다**: `scripts/measure.mjs` 로 문서 1,000개를 넣은 상태에서 사이드바 `지도` 를 누른 뒤 (a) 지도 화면 틀이 보이기까지 (b) 그래프가 그려지기까지
- **목표**: (a) **100ms 이내** (b) **1,000ms 이내**
- **이 두 숫자는 이 프로젝트에서 실측해 정한 값이 아니다.** 응답 시간에 대해 널리 쓰이는 통념(0.1초 = 즉각 반응, 1초 = 생각의 흐름이 안 끊기는 한계. Miller 1968 / Nielsen 1993 의 구분으로 알려져 있다)을 근거로 잡았고, F-284 5.1 이 쓴 것과 같은 기준이다. **통념이라는 점을 밝혀 둔다**
- **넘으면**: 순서대로 (1) 5.3 재사용 확인 → (2) 노드 상한을 300 으로 낮춤 → (3) 반복 횟수를 50 으로 낮춤 → (4) 인덱스 만들기를 청크로 쪼갬. (4) 까지 안 되면 설계를 재검토한다

## 6. 화면과 조작

### 6.1 라우팅 — 편집기를 언마운트하지 않는다

| 해시 | 뜻 |
| --- | --- |
| `#/map/{docId}` | 그 문서를 중심으로 한 지도 (기본) |
| `#/map` | 전체 보기 |

- `hashRoute.ts` 에 `{ type: 'map'; docId?: string }` 를 더한다. `#/map` 은 정확히 그 값만, `#/map/{id}` 는 `/` 를 담지 않는 한 조각만 인정한다. **`#/map` 검사를 `#/m…` 계열 다른 라우트보다 먼저 두지 않는다** — 지금 `#/shares` 를 `#/s/{조각}` **뒤**에 검사하는 것과 같은 이유다(`hashRoute.ts` 19행 주석)
- **`currentDocId` 를 비우지 않는다.** 도움말(F-244)·공유 관리(F-243)는 `currentDocId = null` 로 두지만, 지도는 **공유 화면(`sharedDoc`, F-138 3.2)과 같은 방식**을 쓴다: `currentDocId` 를 유지한 채 편집 영역 `<div className="content-area">` 에 `hidden` 을 주고 그 옆에 지도를 그린다
  - 이유 1 — **현재 문서 중심이 기본**인데 `currentDocId` 를 비우면 중심이 사라진다
  - 이유 2 — F-138 3.2 가 기록한 회귀: 편집 영역을 언마운트했다가 같은 문서로 돌아오면 `EditorView` 가 새로 만들어져 그 사이 저장된 편집을 옛 `openDoc.content` 로 덮어쓴다. 지도를 닫고 돌아오는 흐름이 정확히 그 경로다
  - 대가 — `App.tsx` 의 해시 처리기가 `map` 라우트에서 **문서를 열지도 닫지도 않고 곧바로 빠져나가야** 한다(`sharesOpenRef`·`helpOpenRef` 와 같은 방식의 `mapRouteRef`)
- 열기: `await beforeLeaveDoc()` → `setSharedDoc(null)` → `setSharesOpen(false)` → `setHelpOpen(false)` → `setMapRoute({ docId: currentDocId })` → 해시 **push** → `closeSidebarIfNarrow()`
- 전체 ↔ 현재 전환은 해시 **replace** 다. 전환할 때마다 뒤로 가기 기록이 쌓이면 지도를 빠져나가기 어렵다
- 닫기: 지도를 열 때의 문서로 돌아간다(`#/d/{docId}`, replace). 열 때 문서가 없었으면(홈·빈 상태) `goHome()`
- 브라우저 뒤로 가기도 자연스럽게 동작한다(해시 이동이라 그대로)
- **화면 분할(F-262)과 동시에 켜지지 않는다.** F-262 1장이 이미 "전용 화면으로 이동하면 분할이 꺼진다" 로 정해 두었다. 지도도 그 규칙에 들어가는 전용 화면이다 — F-262 를 고치지 않는다. 지도를 열면 분할이 꺼지고, 닫으면 왼쪽 문서만 남는다 (9장 Q9)

## 7. 그리는 방법

### 7.1 SVG 를 쓴다. Canvas 를 쓰지 않는다

| | SVG | Canvas |
| --- | --- | --- |
| 노드 500 + 간선 1,000 일 때 요소 수 | 약 1,600개(원 500 + 선 1,000 + 이름표 ≤80 + 틀) | 0 |
| 확대·이동 | `<g transform>` 하나만 바꾼다 — **DOM 을 다시 만들지 않는다** | 매 프레임 전부 다시 그린다 |
| 호버·클릭 판정 | 브라우저가 한다 | 좌표로 직접 찾아야 한다 |
| 툴팁·포커스 표시 | 기존 CSS·토큰 그대로 | 직접 그려야 한다 |
| 테마 전환(F-141) | CSS 변수가 그대로 먹는다 | 다시 그려야 한다 |

- **배치를 애니메이션하지 않기 때문에**(2장) SVG 의 약점인 "매 프레임 DOM 갱신"이 아예 없다. 좌표를 한 번 계산해 한 번 그리고, 그 뒤로는 `<g>` 의 `transform` 만 바뀐다
- **노드 상한 500 이 곧 SVG 의 상한이다** (5.4). 상한을 올리게 되면 그때 Canvas 를 다시 본다
- **브라우저에서 재지 않았다.** 위 비교는 코드 구조에서 따진 것이고, 요소 1,600개의 실제 그리는 시간은 5.4 게이트에서 측정한다

### 7.2 노드·선 (`map.css` — 색 hex 금지)

| 대상 | 모양 |
| --- | --- |
| 있는 문서 노드 | 채운 원. 반지름 `4 + min(degree, 16) × 0.5` px (4~12px). 색 `--accent` |
| **중심 문서** | 같은 원 + 바깥 링 2px. 색 `--accent`, 링은 `color-mix(in srgb, var(--accent) 40%, transparent)` |
| **끊긴 링크 노드** | **속이 빈 원**(채움 없음) + 1px 점선 테두리 `--muted`. 반지름 4px 고정 |
| **공유받은 문서 노드** | 있는 문서와 같은 원, 테두리 1px `--ink-2` |
| 간선 | 1px 선, `--rule`. 중심 노드에 닿는 선은 `color-mix(in srgb, var(--ink) 30%, transparent)` |
| 이름표 | 노드 오른쪽 6px, 11px `--ink-2`, `--font-sans`. **노드 60개 이하면 전부, 넘으면 `degree` 상위 60개만**. 나머지는 호버·포커스 때 툴팁 |
| 호버 | 노드 반지름 +2px, 이어진 간선 `--accent`. 전환은 `--transition-fast`·`--ease-out` (`specs/design.md` 4장) |
| 바탕 | 메인 열과 같은 `--panel` (F-143 3.8 "편집 영역 색 구분 제거" 와 같게) |

- **새 색 토큰을 만들지 않는다.** 전부 기존 토큰과 `color-mix()` 파생이다 (`specs/design.md` 3.2). 그래서 `specs/design.md` 는 고치지 않는다
- 위 수치(반지름·굵기·글자 크기)는 **시각값이라 e2e 로 고정하지 않는다.** `CLAUDE.md` "개발 방식" — 서브픽셀로 흔들린다. 사람 확인으로 넘긴다

### 7.3 접근성 — 무엇을 포기하는지 밝힌다

- **SVG 안 개별 노드에 포커스를 주지 않는다.** 노드가 500개면 Tab 순회가 500번이 되어 오히려 못 쓴다. SVG 전체를 `role="img"` + `aria-label="문서 {N}개, 연결 {M}개의 지도"` 로 두고 `tabindex="-1"` 로 뺀다
- **대신 같은 데이터를 목록으로 제공한다** (7.4). 키보드·스크린리더 사용자는 `목록` 세그먼트를 쓴다. 이것이 대안이다
- 조작 요소(세그먼트·`맞춤`·`닫기`)는 전부 키보드로 닿고 `:focus-visible` 표시를 갖는다 (`specs/product.md` 6장 접근성)
- 확대·이동은 키보드로 하지 않는다. `맞춤` 만 있으면 전체를 볼 수 있다

### 7.4 목록 대체 표시

세그먼트 `목록` 을 누르면 같은 부분 그래프를 목록으로 본다

| 묶음 | 내용 |
| --- | --- |
| `나가는 링크 ({N})` | 중심 문서가 가리킨 문서. 제목 · 폴더 경로 |
| `들어오는 링크 ({N})` | 중심 문서를 가리킨 문서 |
| `끊긴 링크 ({N})` | 중심 문서가 가리켰지만 없는 제목. 누르면 새 문서 (6.4) |

- 전체 보기에서는 묶음 대신 `연결이 많은 순` 한 줄 목록 — 제목 · 연결 수
- 항목은 평범한 `<button>` 이라 Tab 으로 닿는다. 동작은 6.4 표와 같다
- 이 화면은 `--content-max` 폭을 쓴다 (글이라 읽기 폭이 있는 게 낫다)

## 9. 열린 질문 / 사람 결정 필요

### Q1. 레이아웃 라이브러리를 쓸 것인가 — **기본값: 쓰지 않는다 (직접 구현)**

| 방식 | 새 의존성 | 속도 (노드 1,000, 300회/tick) | 손이 가는 곳 | 판단 |
| --- | --- | --- | --- | --- |
| **직접 구현 (FR, 4장)** | **0** | **913ms** (150회면 539ms) | 알고리즘 40~60줄. 상수 조정이 필요하다 | **기본값** |
| `d3-force` | **`package.json` 에 1개 추가** | 1,153ms (2,000개부터는 d3 가 2배 빠르다) | 시뮬레이션 수명 관리. 좌표가 객체 배열이라 테스트가 조금 번거롭다 | 안 쓴다 |
| `mermaid` 안에 든 것 재사용 | — | — | **불가능** | 안 쓴다 |
| `cytoscape` / `elkjs` | 1개 이상 | 재지 않음 | 그래프 편집·계층 배치까지 딸려 온다. 이번 요구(점과 선)에 과하다 | 안 쓴다 |

- **`node_modules` 를 확인했다.** `d3`·`d3-force`·`cytoscape`·`cytoscape-fcose`·`elkjs` 가 **이미 디스크에 있다 — 전부 `mermaid` 의 전이 의존성이다.** `package.json` 의 직접 의존성이 아니다. `src/` 에서 `import 'd3-force'` 를 쓰면 호이스팅에 기대는 것이고, mermaid 가 판올림하면 조용히 깨진다. 쓰려면 직접 의존성으로 올려야 하고 그건 **새 의존성 추가**다 (`CLAUDE.md`: 명세에 적힌 것만 설치)
- mermaid 는 `src/lib/mermaidRender.ts` 2행에서 **정적 import** 라 이미 번들에 들어 있다. 그래도 그 안의 d3 에 손을 뻗는 것은 위와 같은 이유로 하지 않는다
- **속도는 5.1(d) 에서 실제로 쟀다.** 상한 500 안에서는 직접 구현이 3배 빠르다
- **사람 결정 필요.** 기본값대로 직접 구현으로 갈지, `d3-force` 를 직접 의존성으로 올릴지

### Q2. 노드 상한 500 으로 둘 것인가 — **기본값: 500** (5.4)

500개 150회 = 105ms(Node 실측). 300 으로 낮추면 38ms 로 더 빠르지만 전체 보기가 자주 잘린다. 800 으로 올리면 266ms 로 여는 게 눈에 띄게 늦어진다

### Q3. SVG 로 그릴 것인가 — **기본값: SVG** (7.1)

배치를 애니메이션하지 않아 SVG 의 약점이 없다. **브라우저에서 재지 않았다** — 5.4 게이트에서 확인하고 넘으면 다시 본다

### Q4. 그래프 노드를 키보드로 순회하게 할 것인가 — **기본값: 하지 않는다. 대신 `목록` 대체 표시** (7.3)

노드 500개에 Tab 순회를 붙이면 쓸 수 없다. 같은 데이터를 목록으로 주는 쪽을 고른다

### Q5. 공유받은 문서의 나가는 링크를 읽을 것인가 — **기본값: 이번엔 안 읽는다** (5.2)

읽으려면 문서마다 `api.getDoc` 요청이 나가고 F-207 캐시 정책을 바꿔야 한다. F-284 Q4 와 같은 판단이다

### Q6. 방향 화살표를 그릴 것인가 — **기본값: 그리지 않는다** (3.4)

화살표를 그리면 노드 500개에서 요소가 2배가 되고 작은 배율에서는 보이지도 않는다. 방향은 목록 대체 표시(7.4)의 `나가는`/`들어오는` 묶음으로 본다

### Q7. 검색 인덱스(F-286)와 지도 인덱스를 합칠 것인가 — **기본값: 따로 둔다** (5.3)

담는 것이 다르다(본문 전체 vs 대상 제목만). 둘 다 구현된 뒤에 다시 본다

### Q8. 노드 클릭을 "열기" 로 둘 것인가 — **기본값: 클릭 = 열고 지도 닫기, Ctrl+클릭 = 중심 이동** (6.4)

사용자 전제("노드 클릭 → 그 문서로 이동")를 그대로 따르고, 중심 이동은 수정 키로 뺐다. F-129·F-131 이 쓰는 관례와 같다

### Q9. 화면 분할(F-262)과 동시에 켜질 수 있나 — **기본값: 없다. 지도로 가면 분할이 꺼진다** (6.1)

### Q10. 배치가 움직이는 애니메이션을 넣을 것인가 — **기본값: 넣지 않는다** (2장)

계산을 끝낸 좌표를 한 번 그린다. 움직이면 매 프레임 SVG 를 갱신해야 하고(7.1), `prefers-reduced-motion` 처리도 따로 필요하다
