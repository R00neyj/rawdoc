### 2.3 인스턴스를 언제·몇 번 만드나

- `getAuth(env)` 는 isolate 모듈 변수에 **`env` 객체를 열쇠로** 인스턴스를 하나 둔다(`WeakMap<Env, Auth>` 모양). 같은 `env` 면 다시 쓰고, 다른 `env` 면 새로 만든다
  - 이유: 로컬 workerd 에서는 요청 사이 `env` 가 같은 객체다(측정 h) — 한 isolate 에 한 번. 테스트는 테스트마다 새 `env` 를 만들므로 서로 섞이지 않는다. 모듈 변수 하나만 두면 테스트 사이에 옛 DB 가 남는다
  - **운영에서 `env` 가 요청마다 다른 객체면 요청마다 만든다**(측정 f 로 약 11ms). 운영은 확인하지 못했다 — 14장 ⑬ 의 CPU 관측이 이것도 드러낸다
- 모듈 최상위에서 만들지 **않는다**. `cloudflare:workers` 의 `env` 도 쓰지 않는다 — `worker/v1.test.ts` `freshWorker` 가 node 에서 `worker/index.ts` 를 불러오고, 거기엔 `cloudflare:workers` 가 없다(F-2032 2.2)
- `better-auth` 는 **정적 import** 한다. 동적 `import()` 는 쓰지 않는다 — 12장 Q1
- `getAuth` 를 부르는 곳(= 인스턴스가 생길 수 있는 경로)은 아래뿐이다. 이 목록 밖에서 부르지 않는다

| 경로 | 부르는 곳 |
| --- | --- |
| `/api/*` 중 사용자 판정이 필요한 라우트, `/ws/doc/:id` | `auth.ts` `getUser` 의 세션 분기(3.2 3번) |
| `GET /api/me` | `auth.ts` 연장 조회(3.3) |
| `GET /login`, `GET /api/login` | `getUser`(세션이 있으면 바로 돌려보내려고) |
| `POST /api/login` | `signInSocial` |
| `GET /api/auth/callback/google`·`/github`, `POST /api/auth/sign-out` | better-auth `handler` |

- **만들지 않는 경로**: `/v1/*`(`getUser` 첫 분기가 토큰만), `/pub/*`, `/p/*`, `/`, `/welcome`, 정적 자산, `OPTIONS`·405·404 로 끝나는 요청, `Origin` 관문 403, `/api/health`, `scheduled`(3.7 정리는 D1 문장 두 개라 인스턴스가 필요 없다), 개발 우회(3.2 2번)
- 판정: 10.1 U30 — **비밀이 없는 `env`** 로 위 "만들지 않는 경로" 에 요청해서 500 이 나지 않으면 `getAuth` 를 부르지 않은 것이다(`getAuth` 는 비밀이 없으면 던진다)

### 2.4 설정 검사 (F-2032 4.1)

- `getAuth` 는 인스턴스를 만들기 **전에** `env.BETTER_AUTH_SECRET` 이 문자열이고 길이가 `AUTH_SECRET_MIN_LENGTH` 이상인지 본다. 아니면 `AuthConfigError` 를 던지고 만들지 않는다 — better-auth 는 비밀이 없거나 짧아도 경고만 하고 만든다(측정 r)
- `env.BETTER_AUTH_URL` 이 `new URL()` 로 읽히지 않아도 `AuthConfigError`
- 오류 메시지는 비밀 값을 담지 않는다(이름과 "없음/짧음" 만)
- `AuthConfigError` 가 사용자에게 어떻게 보이는지는 3.2·7장

### 3.3 `/api/me` 의 연장 — `getUserRefreshing`

- `GET /api/me` **만** 이 함수를 쓴다. `GET /v1/me` 는 지금처럼 `handleMe` → `getUser`(토큰) — `/v1/me` 에서 better-auth 를 부르지 않는다
- 순서: 개발 우회면 `{ user, setCookies: [] }`. 아니면 `getAuth(env)` → `auth.api.getSession({ headers: request.headers, returnHeaders: true })`(`disableRefresh` 없음). `setCookies` = 돌려받은 헤더의 `getSetCookie()` 전부 — 연장이면 세션 쿠키 한 줄(측정: `Max-Age=2592000`), 만료 세션이면 쿠키 지우는 줄들, 그 밖 빈 배열
- `index.ts` 의 `/api/me` 핸들러는 200·401 **두 응답 모두**에 `setCookies` 를 `Set-Cookie` 로 싣는다 — 만료된 세션의 401 에도 쿠키 지우는 줄이 실려야 브라우저가 죽은 쿠키를 버린다
- 몸통·상태는 지금과 같다: `200 {"id","email"}` / `401 {"error":"unauthenticated"}`. `getSession` 이 던지면 401(3.2 3번과 같은 규칙), `AuthConfigError` 면 500

## 5. `worker/origin.ts` — 로컬 인증 모드와 `Origin` 관문

### 5.1 계약

```ts
// worker/origin.ts
export function isLocalAuthMode(env: Env): boolean        // BETTER_AUTH_URL 이 http: 이고 호스트가 localhost 또는 127.0.0.1
export function isDevBypass(env: Env): boolean            // isLocalAuthMode && DEV_AUTH_EMAIL 이 '@example.com' 으로 끝남(소문자 비교)

```

- `isLocalAuthMode`: `BETTER_AUTH_URL` 이 없거나 `new URL()` 로 읽히지 않으면 `false`. 포트는 보지 않는다(에이전트 슬롯 8791~ 도 같은 `.dev.vars` 로 우회가 켜진다 — `BETTER_AUTH_URL` 은 8790 을 가리켜도 된다)
- `isAllowedOrigin` 규칙은 지금 `docSocket.ts` 것 그대로이고, 조건만 "`isDevBypass`" → "`isLocalAuthMode`" 로 바뀐다(F-2032 2.6 셋째 줄): `Origin` 없음 → `false` / `new URL(SITE_URL).origin` 과 같음 → `true` / 로컬 인증 모드가 아니면 `false` / 요청 주소의 출처와 같음 → `true` / `http:` 이고 호스트가 `localhost`·`127.0.0.1` → `true` / 그 밖 `false`

### 5.2 운영에서 우회가 켜지지 않는 조건

우회는 **세 조건이 모두** 참일 때만 켜진다. 운영에서는 첫째부터 거짓이다

| 조건 | 운영 값 | 어디서 오나 |
| --- | --- | --- |
| `BETTER_AUTH_URL` 이 `http:` + `localhost`/`127.0.0.1` | `https://rawdoc.app` | `wrangler.jsonc` `vars` — 커밋된 값 한 곳. 비밀 목록(`secrets.required`)에 넣지 않는다 |
| `DEV_AUTH_EMAIL` 이 있음 | `""` | `wrangler.jsonc` `vars` 의 빈 문자열(8.1). 비밀로 넣지 않는다 |
| `DEV_AUTH_EMAIL` 이 `@example.com` 으로 끝남 | — | 예약 도메인이라 실제 사람의 주소가 아니다(지금 규칙 그대로) |

- 이 조건은 **`wrangler.jsonc` 계약 테스트**(10.1 U12)가 지킨다: `vars.BETTER_AUTH_URL === 'https://rawdoc.app'`, `vars.DEV_AUTH_EMAIL === ''`, `secrets.required` 에 `BETTER_AUTH_URL`·`DEV_AUTH_EMAIL` 이 **없다**. 누가 운영 값을 로컬 값으로 커밋하면 CI 가 떨어진다
- 요청 주소가 `http:` 인지를 넷째 조건으로 두지 않는다 — 운영에서 `http://rawdoc.app` 요청이 Worker 에 오는지는 zone 의 "Always Use HTTPS" 설정에 달려 있어(확인하지 않았다) 보장이 되지 않는다. 로컬은 `wrangler dev` 가 `http://rawdoc.app` 로 바꿔 쓰므로(측정 k) 넷째 조건이 참이지만 운영을 가르지 못한다

### 5.3 왜 `auth.ts` 가 아니라 `origin.ts` 인가 — F-2032 2.6 과 다르다

- F-2032 2.6 은 "이 판정 함수 하나를 `auth.ts` 에서 내보내고 `docSocket.ts` 의 복사본을 지운다" 였다. 그대로 하면 **`docSocket.test.ts` 가 깨진다**: 그 파일의 `vi.mock('./auth', () => ({ getUser: vi.fn() }))` 팩토리는 `getUser` 하나만 돌려주므로, `docSocket.ts`(또는 `origin.ts`)가 `auth.ts` 에서 판정 함수를 가져오면 `undefined` 를 부른다. 다른 8개 테스트의 팩토리도 `getUser`·`requireUser` 만이다
- 그래서 판정 함수를 mock 되지 않는 `origin.ts` 에 두고, `auth.ts`(우회)와 `docSocket.ts`(`/ws` 출처)와 `index.ts`(관문)가 **같은 함수 하나**를 가져다 쓴다. "판정은 한 곳" 이라는 개요의 뜻은 그대로다 — 갱신 대상(13장)

### 5.4 관문 규칙 (F-2032 4.2)

- `index.ts` 가 `/api/` 로 시작하는 요청에서 **라우트 표를 찾기 전에**: `needsOriginCheck(method)` 이고 `!isAllowedOrigin(request.headers.get('Origin'), request, env)` 면 403 `{"error":"forbidden_origin"}`. 핸들러·D1·better-auth 에 닿지 않는다
- `/v1/*`·`/pub/*`·`/ws/*`·`/login` 은 이 관문을 지나지 않는다(`/ws` 는 `docSocket.ts` 가 같은 `isAllowedOrigin` 을 따로 부른다 — 지금 그대로)
- 앱의 비`GET` 요청은 모두 같은 출처 `fetch` 라 `Origin` 을 싣는다(F-2032 4.2). F-2034 의 `logout()` 도 같다(F-2034 3.1 — `credentials: 'same-origin'`). `/login` 의 폼 제출도 브라우저가 `Origin` 을 싣는다

## 6. `/login` 페이지 — `worker/loginPage.ts`

### 6.1 계약


`loginReturn` 규칙(F-2032 3.2):

| 입력 `raw` (디코드된 `return` 값) | `hash` | `successUrl` | `failureUrl` |
| --- | --- | --- | --- |
| `#/` 로 시작하고 길이 ≤ 512 (UTF-16 코드 단위) | `raw` | `/` + `raw` | `/login?return=` + `encodeURIComponent(raw)` |
| `null`, 빈 문자열, `#/` 로 시작하지 않음, 513 이상 | `''` | `/?app=1` | `/login` |

- `GET /api/login`·`GET /login`·`POST /api/login` 셋이 이 함수만 쓴다. `failureUrl` 은 `POST /api/login` 이 better-auth 에 `errorCallbackURL` 로 넘기고, better-auth 가 뒤에 `&error=…`(또는 `?error=…`)를 붙인다(측정 o)

### 6.2 오류 코드 → 문구 (F-2032 3.4 표를 코드로)

| `error` | 문구 |
| --- | --- |
| `email_not_verified`, `account_not_linked`, `email_not_found` | `이메일 주소가 인증되지 않은 계정이라 로그인하지 못했습니다. Google 또는 GitHub 계정 설정에서 이메일을 인증한 뒤 다시 시도해 주세요.` |

| `state_mismatch`, `state_not_found`, `state_invalid`, `state_security_mismatch` | `로그인 시간이 지났거나 다른 창에서 시작한 로그인입니다. 다시 시도해 주세요.` |
| 그 밖 모두(`LOGIN_ERROR_FALLBACK`) | `로그인하지 못했습니다. 잠시 뒤 다시 시도해 주세요.` |

- `error` 가 없거나 빈 문자열이면 오류 줄을 그리지 않는다. 있으면 표에 없는 값도 마지막 줄 — `error` 값 자체는 **화면에 한 글자도 넣지 않는다**
- 이 명세가 쓰는 우리 쪽 코드(`bad_request`·`provider_unavailable`·`internal_server_error`, 7.3)는 모두 마지막 줄로 간다

### 6.3 HTML — 틀과 색

- 문서 하나: `<!doctype html>`, `<html lang="ko">`, `<meta charset="UTF-8">`, viewport, `<meta name="robots" content="noindex">`, `<title>로그인 · {brand.name}</title>`, `<link rel="icon" href="{brand.icon}">`, `<style>` 하나, `<body>` 에 `renderSiteHeader({ brandName, brandIcon, appCta: 'link' })` → `<main class="login">` → `renderSiteFooter({ brandName })`
- **`<script` 가 한 글자도 없다**(F-272 규칙, F-2032 3.3)
- `<style>` 은 `PAGE_TOKENS_CSS`(아래) + `SITE_CHROME_CSS` + 이 페이지 규칙. 색은 토큰 변수·`brand.accent`·`color-mix()` 로만 — **이 파일에 색 hex 를 새로 적지 않는다**(로고 SVG 는 6.4 예외, `providerLogos.ts` 에 있다)
- **`PAGE_TOKENS_CSS` — `worker/pageTokens.ts` (신규)**: 지금 `worker/welcomePage.ts` `renderWelcomePage` 의 `<style>` 안 `:root { color-scheme: light; --accent: …; --paper: #faf8f4; … --page: 1060px; }` 블록을 **글자 그대로** 옮긴 문자열 상수. `welcomePage.ts` 는 그 자리에 `${PAGE_TOKENS_CSS}` 를 끼운다. `renderWelcomePage()` 의 응답 본문은 옮기기 전과 **바이트가 같아야 한다**(10.1 U25)
  - 이유: `SITE_CHROME_CSS` 는 `var(--ink)`·`var(--font-display)` 등을 **쓰기만** 하고 정의하지 않는다. Worker 는 해시가 붙은 앱 CSS 이름을 모르므로(F-2032 3.3) 랜딩과 같은 변수 정의가 필요하다. 셋째 사본을 만들지 않으려고 옮긴다 — 다른 안은 12장 Q4
  - 이 블록의 hex 는 지금도 `tokens.css` 값의 사본이다(불변조건과 어긋나 있는 기존 상태 — 15장). 이 명세는 사본 수를 늘리지도 줄이지도 않는다

`<main class="login">` 안 순서와 클래스(계약 — 단위 테스트가 이 이름으로 찾는다):

| 순서 | 요소 | 내용 |

| 3 | `<p class="login-error" role="alert">` (오류가 있을 때만) | 6.2 문구 |
| 4 | `<form class="login-form" method="post" action="/api/login">` | 아래 5~7 |

| 6 | `<button class="login-provider" type="submit" name="provider" value="google">` | `<svg aria-hidden="true" …>`(GOOGLE_LOGO_SVG) + `<span>Google로 계속</span>` |

### 6.4 `worker/providerLogos.ts`

- 값은 **사람이 받아 준 SVG 파일 내용 그대로**(경로·색·`viewBox` 를 고치지 않는다). 파일 머리 주석에 받은 URL 과 날짜, "CLAUDE.md Invariants 의 제공자 로고 예외 — 이 파일 밖에 색 값을 옮기지 않는다" 를 적는다
- `loginPage.ts` 가 넣을 때 `<svg` 여는 태그에 `aria-hidden="true"`·`width="20"`·`height="20"`·`focusable="false"` 를 **덧붙인다**(원본 속성은 지우지 않는다. 같은 이름 속성이 원본에 있으면 원본 값을 둔다)
- **사람이 SVG 를 아직 주지 않았으면**: 구현은 두 상수를 빈 문자열로 두고, `loginPage.ts` 는 빈 상수면 `<svg>` 를 넣지 않는다(버튼은 글자만). 보고에 "로고 미반영" 을 적는다. 로고를 추측해 그리거나 다른 곳에서 가져오지 않는다
- `src/`·`public/` 은 이 파일을 쓰지 않는다 — 서비스 워커 precache 에 들어가지 않는다(F-2032 3.3.1)

## 7. `worker/index.ts` — 라우팅

### 7.1 순서

`fetch` 안에서 위에서부터:

1. `/ws/` — 지금 그대로(`docSocket.ts` 가 `origin.ts` 를 쓰는 것만 바뀜)
2. `/api/`·`/pub/`·`/v1/` 가 아닌 경로 — 지금 분기에 **`/login` 한 줄**을 `/welcome` 앞에 더한다(7.2)
3. 여기부터 `try` 안(지금 `try` 그대로):
   1. 경로가 `/api/` 로 시작하면 **`Origin` 관문**(5.4)
   2. 경로가 `/api/auth/` 로 시작하면 **허용 목록**(7.4) — 라우트 표를 보지 않고 여기서 끝난다
   3. 라우트 표 — 새 줄: `{ GET /api/login → handleLogin }`(바뀜), `{ POST /api/login → handleLoginStart }`(새), `{ GET /api/me → handleApiMe }`(새, 3.3). `{ GET /v1/me → handleMe }` 는 그대로
4. `scheduled` — `cleanupServerAttachments` 와 `cleanupExpiredAuth` 를 각각 `ctx.waitUntil`(2.6)

### 7.2 `GET /login` (F-2032 3.1 둘째 줄)

- 메서드: `GET`·`HEAD` 만. 그 밖은 405 `{"error":"method_not_allowed"}`
- `loginReturn(url.searchParams.get('return'))`
- `getUser` 가 사용자를 돌려주면 `302 Location: successUrl`, `Cache-Control: no-store`
- `getUser` 가 `null` 이거나 **던지면**(설정 오류 포함) 로그인 페이지 200. 던졌으면 `console.error`. 이유: 페이지는 better-auth 없이 그릴 수 있고, 버튼을 누르면 `POST /api/login` 이 오류 줄로 돌려보낸다(7.3) — 빈 500 화면보다 낫다
- `error` 는 `url.searchParams.get('error')` 를 `loginErrorMessage` 에 넘긴다

### 7.3 `GET /api/login` · `POST /api/login`

`GET /api/login` (`handleLogin`, 지금 함수를 바꿈):

- `loginReturn(return)` → `getUser` 가 사용자면 `302 successUrl`, 아니면 `302 /login` + (`hash` 가 있으면 `?return=` + `encodeURIComponent(hash)`). 둘 다 `Cache-Control: no-store`
- 지금의 "사용자가 없으면 401 JSON" 은 없어진다. `getUser` 가 던지면(설정 오류) 라우트 `catch` → 500(지금 규칙)
- 빈 `return` 의 성공 주소가 지금 `/` 에서 `/?app=1` 로 바뀐다(F-2032 3.2). 랜딩의 `로그인` 버튼(`welcomePage.ts` `data-cta="login"` → `/api/login?return=`)은 로그인 뒤 랜딩이 아니라 앱으로 간다

`POST /api/login` (`handleLoginStart`, 새):

| # | 검사 | 실패하면 (전부 `303`, `Cache-Control: no-store`) |
| --- | --- | --- |
| 0 | `Origin` 관문(5.4) — 7.1 3-1 에서 이미 지났다 | 403 JSON (관문) |
| 1 | `Content-Length` 가 있고 4,096 이하, `Content-Type` 이 `application/x-www-form-urlencoded` 로 시작 | `/login?error=bad_request` (`return` 을 못 읽었으므로 없이) |
| 2 | `request.formData()` 에서 `return`·`provider` 를 읽는다. 읽기가 던지면 | 1번과 같다 |
| 3 | `loginReturn(return)` | — (늘 성공) |
| 4 | `provider` 가 `google`·`github` 가 아니면 | `failureUrl` 에 `error=bad_request` |
| 5 | 그 제공자의 `*_CLIENT_ID`·`*_CLIENT_SECRET` 중 하나라도 비었으면 | `failureUrl` 에 `error=provider_unavailable` + `console.error('oauth provider not configured', provider)` |
| 6 | `getAuth(env)` → `auth.api.signInSocial({ body: { provider, callbackURL: successUrl, errorCallbackURL: failureUrl }, headers: new Headers(), returnHeaders: true })` | 던지면(설정 오류 포함) `failureUrl` 에 `error=internal_server_error` + `console.error` |
| 7 | 성공 | `303 Location: {응답 url}`, 돌려받은 `Set-Cookie` 전부(`oauth_state`) |

- "`failureUrl` 에 `error=…`" 는 `failureUrl` 에 `?` 가 없으면 `?error=`, 있으면 `&error=` 를 붙인다는 뜻이다
- 6번에 **빈 `Headers`** 를 넘기는 이유: 요청의 `Origin` 은 5.4 가 이미 봤고, F-2032 측정(`signInSocial` 서버 호출, 쓰기 0)이 빈 헤더로 돌았다. 요청 헤더를 넘기면 로컬에서 바뀐 `Origin`(측정 k)이 better-auth 의 출처 검사에 한 번 더 걸린다
- 이미 로그인한 사람이 눌러도 막지 않는다 — 새 OAuth 가 시작되고 콜백이 세션을 하나 더 만든다

### 7.4 `/api/auth/*` 허용 목록 (F-2032 3.1)

| 메서드 · 경로 | 처리 |
| --- | --- |
| `GET /api/auth/callback/google` | `getAuth(env).handler(request)` 그대로 |
| `GET /api/auth/callback/github` | 같음 |
| `POST /api/auth/sign-out` | 같음 (F-2034 2장 응답 표 — 200 `{"success":true}`) |
| 그 밖 모든 메서드·경로 | 404 `{"error":"not_found"}`. better-auth 에 넘기지 않고 `getAuth` 도 부르지 않는다 |

- 경로 비교는 정확히 같음(뒤 `/`·대소문자 차이 불허). `POST /api/auth/callback/*` 도 404 — Google·GitHub 는 `GET` 으로 돌아온다
- better-auth 응답(상태·헤더·몸통)을 바꾸지 않고 그대로 돌려준다. `handler` 가 던지면 라우트 `catch` → 500

### 8.1 `wrangler.jsonc`

| 키 | 바뀐 뒤 |
| --- | --- |
| `compatibility_flags` | `["nodejs_compat"]` (새 키. F-2032 2.2) |

- 지금 로컬 `.dev.vars` 의 `ACCESS_AUD=`·`ACCESS_TEAM_DOMAIN=` 은 이름이 사라져 무시된다(측정 i). 지워도 되고 남아도 해가 없다 — 11장 3번
- `routes`·`d1_databases`·`r2_buckets`·`durable_objects`·`migrations`·`triggers`·`assets` 의 다른 키는 그대로

### 8.2 `worker/worker-configuration.d.ts`

- `npm run cf:types` 로만 다시 만든다. `secrets.required` 가 있어 `.dev.vars` 를 뒤지지 않으므로 두 PC 에서 같은 파일이 나와야 한다(F-2032 2.6). 결과에 `BETTER_AUTH_URL`·`DEV_AUTH_EMAIL`(리터럴)과 비밀 다섯이 있고 `ACCESS_*` 가 없어야 한다
- `nodejs_compat` 로 `node:*` 타입이 늘 수 있다 — 생긴 대로 커밋하고 `npm run typecheck:worker` 가 통과하면 된다
