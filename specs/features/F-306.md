  - 읽은 것: 적용 시간은 **압축본(문서 크기)이 지배**하고 행 수에는 거의 안 는다. 행 수는 읽기에만 선형으로 붙는다(1MB 에서 200행 → 500행 +2ms, 4배 감속 200행 → 1,000행 +11ms). 압축은 느린 PC 에서 1MB 에 **45ms 안팎 메인 스레드를 막는다** — 치는 도중이면 3프레임쯤 끊긴다
- (c) **Playwright `context.setOffline`** — `navigator.onLine` 이 `false`/`true` 로 바뀌고 `offline`·`online` 이벤트가 실제로 온다. **`page.route` 처리기는 오프라인에서도 불려 응답을 준다**(`fetch('/api/x')` → 200). 그래서 e2e 는 요청 실패를 fakeServer 의 `setOffline` 으로 따로 만든다(19.2)
- (d) **`y-indexeddb` 9.0.12 소스에서 확인한 것**: 문서 하나가 IndexedDB **데이터베이스 하나**다(`new IndexeddbPersistence(name, doc)` 가 `name` 이라는 DB 를 연다, 스토어 `updates`·`custom`). 열 때 `fetchUpdates` 의 `beforeApplyUpdatesCallback` 이 **지금 Doc 전체 상태를 한 행 더 쓴다**. `update` 마다 자동 증가 키로 한 행, 500행(`PREFERRED_TRIM_SIZE`) 이 넘으면 1,000ms 디바운스 뒤 압축. 압축은 읽은 **모든 행**을 지운다. 사용자 구분·"안 보낸 편집" 표시는 없다. 마지막 publish 2023-11-02(npm `time.modified`, 2026-09-24 다시 확인)
- (e) **`y-partyserver` 동기화 순서(소스 읽기, 실측 아님)**: 서버 `onConnect` 가 연결 직후 sync step 1 을 먼저 보낸다(`dist/server/index.js`). 브라우저는 그 step 1 에 **내가 가진 것 중 서버에 없는 것(step 2)** 으로 곧바로 답하고, 서버가 내 step 1 에 답한 step 2 를 받을 때 `synced` 가 된다(`dist/provider/index.js` `messageHandlers[0]`). 웹소켓은 순서를 지키므로 **`synced` 가 올 때 내 밀린 편집은 이미 `ws.send` 로 넘어갔다.** 서버가 받았다는 확인(ack)은 없다

## 3. outbox 와 본문 충돌 사본 — 무엇이 걷히고 무엇이 남나

### 3.1 걷히는 것

- **오프라인에서 연 서버 문서가 더는 outbox 로 본문을 쓰지 않는다.** F-305 는 오프라인 열기를 `fallback`/`offline`(잠금 + `store.update` → outbox `updateDoc{content}`)으로 보냈다(F-305 4.1 4번). 이 명세는 그 줄을 없앤다 — 이 브라우저에 기록이 있으면 실시간 세션을 오프라인으로 시작하고(`md-yjs` 에 쌓임), 없으면 읽기 전용(5장)
- 실시간 세션(`realtime`)은 F-305 부터 이미 본문 PUT·제목 PUT 을 보내지 않는다(F-305 10.1). 이 명세 뒤로 **실시간 세션에서 연결이 끊겨도, 새로고침해도, 오프라인으로 다시 열어도** 본문은 outbox 를 지나지 않는다

### 3.2 남는 것 (22장 Q1)

- outbox 항목 `updateDoc{ title?, content? }`, 409 충돌 사본(`handleConflict`), 423 잠금 사본은 **코드에서 지우지 않는다.** 쓰는 곳이 둘 남기 때문이다
  - `pending` 세션(outbox 에 이 문서의 `createDoc`·`updateDoc` 이 남음, F-305 4.1 3번) — 방금 만든 새 문서 포함
  - `fallback` 세션(한 번도 연결하지 못함 — F-301 8.1 표 "기존 PUT + outbox (폴백)", F-305 Q2)
- F-301 2.2 6번 "outbox 에서 `updateDoc{content}` 를 뺀다" 와 8.1 표 "폴백은 기존 PUT + outbox" 는 승인된 개요 안에서 서로 부딪친다. 이 명세는 8.1 을 따르고, 6번은 "실시간 경로에서 뺀다" 로 읽는다. 폴백 자체를 걷는 F-309 가 남은 둘을 지운다
- 가져오기(`confirmImport`)는 지금처럼 `store.update` 로 쓴다(F-305 10.1). 열린 실시간 문서가 아니어도, 마지막 `list()` 뒤 DO 가 D1 을 쓴 문서면 `baseVersion` 이 낡아 409 → 충돌 사본이 생길 수 있다. F-305 부터 있던 모양이고 이 명세가 바꾸지 않는다(15장 L5)

### 3.3 이미 쌓인 사용자 outbox — 잃지 않기

- **바꿀 것이 없다.** 옮기기(마이그레이션) 코드도 없다. 근거:
  1. outbox 항목 모양(`OutboxItem`)·DB `md-remote` 버전(2)을 바꾸지 않는다 — 옛 항목을 읽는 코드가 그대로다
  2. `createServerStore` 가 부팅 때 `refreshPending(); kickSend()` 로 **어느 문서를 열든 상관없이** 쌓인 항목을 보낸다(`serverStore.ts` 끝부분). `sendOne` 의 `updateDoc` 처리·409 사본·423 사본·413·404 규칙이 그대로다
  3. 보내기 전에 그 문서를 열면 `hasPendingChanges` 가 참이라 `pending` 경로다(F-305 4.1 3번) — 캐시 본문으로 열고 PUT 으로 쓴다. 다 보낸 뒤 다음 열기부터 실시간
  4. 보낸 PUT 이 D1 에 들어가면 DO 가 흡수한다(F-304 7.2)
- 지금 배포본(F-305 전) 사용자가 오프라인에서 쌓아 둔 `updateDoc{content}` 는 이 배포 뒤 첫 부팅에서 위 2번으로 나간다. `version` 이 어긋나 있으면 지금처럼 충돌 사본이 된다 — **사본이 생기는 것이지 잃는 것이 아니다**

## 4. `md-yjs` — `src/storage/yjsStore.ts`

### 4.1 스키마

- DB 이름 **`md-yjs`**, 버전 1. 제품명을 쓰지 않는다(불변조건). `md-docs`·`md-remote` 와 같은 규칙
- 스토어 `updates` — 행 하나 = Yjs 업데이트 하나

```ts
// keyPath 'key', autoIncrement. 색인 'byDoc' = ['userId', 'docId']
type YjsUpdateRow = { key: number; userId: string; docId: string; update: Uint8Array }
```

- 스토어 `meta` — 문서당 한 행

```ts
// keyPath ['userId', 'docId']. 색인 'byUser' = 'userId'
type YjsMetaRow = {
  userId: string
  docId: string
  unsyncedLocal: boolean   // 연결이 live 가 아닐 때 내 편집이 들어왔고 그 뒤 아직 synced 를 못 봤다 (7.2)
  lastOpenedAt: number     // 세션이 붙은 시각(ms). 나이 정리(4.6)가 본다
}
```

- 키를 F-301 3.6 의 `[userId, docId, seq]` 에서 자동 증가 `key` + 색인으로 바꾼 이유: 같은 브라우저의 두 탭이 같은 문서를 열면 각자 방 Doc 과 각자 seq 를 가진다(`disableBc`, F-305 6.2). 탭마다 seq 를 세면 키가 겹쳐 **남의 행을 덮는다**. 자동 증가 키는 겹치지 않는다
- 사용자 구분: 모든 읽기·쓰기가 `userId` 로 거른다. 로그아웃해도 지우지 않는다(`md-remote` 와 같은 규칙, F-207 2.1)

### 4.2 계약

```ts

export const COMPACT_ROWS = 500
export const COMPACT_IDLE_MS = 2_000
export const RETAIN_MS = 30 * 24 * 60 * 60 * 1000
export const YJS_LOAD_ORIGIN: object              // 불러오기 트랜잭션의 origin

export type YjsStore = {
  hasState(docId: string): Promise<boolean>        // 이 사용자·문서의 updates 행이 하나라도 있는가
  attach(docId: string, doc: Y.Doc, options?: YjsAttachOptions): Promise<YjsAttachment>
  unsyncedDocIds(): Promise<string[]>              // meta.unsyncedLocal 이 참인 문서
  removeDoc(docId: string): Promise<void>          // updates·meta 둘 다
  collectGarbage(now: number): Promise<void>       // 4.6
}

  setTimeout?: (fn: () => void, ms: number) => unknown
  clearTimeout?: (handle: unknown) => void
}

export type YjsAttachment = {
  readonly loadedRows: number          // 불러와 적용한 행 수. 0 이면 이 문서 기록이 없었다
  readonly unsyncedLocal: boolean      // 불러온 meta 값(없으면 false)

```

- `src/storage` 에 두는 이유: IndexedDB 입출력이고 `architecture.md` 1장 의존 방향(`app → storage → lib`)에 맞다. `yjs` 와 `idb` 만 import 한다. `window`·`navigator` 를 읽지 않는다 — node 단위 테스트가 `fake-indexeddb/auto` 로 전부 돌린다(`serverStore.test.ts` 와 같은 방식)

### 4.3 붙이기 (`attach`)

1. 이 사용자·문서의 `updates` 행을 `byDoc` 색인으로 전부 읽는다(키 오름차순)
2. 읽은 행을 **한 `Y.transact`(origin `YJS_LOAD_ORIGIN`) 안에서 행마다 `Y.applyUpdate`** 로 적용한다. 행을 `mergeUpdates` 로 먼저 합치지 않는다 — F-304 실측 (b) 에서 합친 뒤 적용이 더 느렸다
3. 읽은 키를 "이 세션이 아는 키" 에 넣는다. `meta` 를 읽어 `unsyncedLocal` 을 돌려주고 `lastOpenedAt` 을 지금으로 쓴다(`meta` 가 없으면 `unsyncedLocal: false` 로 만든다)
4. 그 뒤 `doc` 의 `update` 를 듣는다 — origin 이 `YJS_LOAD_ORIGIN` 이 아닌 **모든** 업데이트(내 편집 중계·provider 가 받은 원격·첫 동기화 step 2 전부)를 한 행씩 `put` 한다. 돌려받은 키를 "아는 키" 에 넣는다
   - 원격분도 담는 이유: 재연결 없이 새로고침·오프라인 열기를 해도 받았던 원격 편집이 남아야 한다(F-301 3.6)
   - 한 업데이트 = 한 트랜잭션. 합쳐 쓰지 않는다 — 완료 중앙값 0.2ms(측정 b)라 모을 이유가 없고, 모으면 그만큼 창 닫기 때 잃는 구간이 생긴다
- **이것은 "파생 값을 열린 Doc 에 되쓰기" 가 아니다.** `md-yjs` 는 `Y.Doc` 자신의 업데이트 기록이다 — 본문 문자열(D1 `content`·캐시 본문)이 아니다. F-301 3.6 이 승인한 순서("`md-yjs` 를 먼저 적용하고 그다음 provider 를 붙인다") 그대로다. 캐시 본문(`md-remote` `docs.content`)은 어떤 경우에도 방 Doc 에 들어가지 않는다

### 4.4 압축 — 임계값 실측으로 정함 (F-301 3.6 의 200행을 바꾼다, U11 답)

- **"아는 키" 가 `COMPACT_ROWS`(500) 이상이 되면 압축을 예약한다. 예약된 압축은 마지막 업데이트 뒤 `COMPACT_IDLE_MS`(2,000ms) 동안 새 업데이트가 없을 때 돈다** — 업데이트가 올 때마다 2초를 다시 센다. 불러오기 직후 아는 키가 500 이상이어도 같은 규칙으로 예약한다
- 압축 = `Y.encodeStateAsUpdate(doc)` 를 새 행 하나로 넣고 **이 세션이 아는 키만** 지우는 것을 **한 readwrite 트랜잭션**으로. 그 뒤 아는 키 = 새 행 키 + 그사이 들어와 아직 키를 못 받은 append 들
  - 아는 키만 지우는 이유: 같은 브라우저 다른 탭이 같은 문서에 쓴 행은 이 탭의 Doc 에 없을 수 있다(오프라인 두 탭). 지우면 그 탭의 편집이 영속에서 사라진다. 남겨 두면 다음 불러오기 때 한 번 더 적용될 뿐이다(Yjs 적용은 멱등)
- `detach` 때 예약된 압축은 버린다(다음 불러오기가 다시 예약한다)
- 근거(측정 b)
  - 압축은 느린 PC 에서 1MB 문서에 메인 스레드 42.7~45.9ms. 치는 도중이면 끊겨 보인다 → **입력이 2초 멈췄을 때만** 돈다. F-301 3.6 이 적어 둔 "압축이 입력을 눈에 띄게 끊으면 미룬다" 를 실측이 확인했다. `requestIdleCallback` 대신 2초 조용함을 쓰는 이유: 입력 중에도 idle 틈이 생겨 콜백이 치는 사이에 불릴 수 있고, 주입한 타이머로 node 테스트가 된다
  - 불러오기 적용 시간은 압축본(문서 크기)이 지배한다 — 1MB 에서 200행 4.1~5.1ms, 500행 4.7~6.6ms, 1,000행 5.5~8.5ms. 행 수는 읽기만 는다(200 → 500행 +2ms, 이 PC). 그래서 200행이 아니라 500행으로 올려 **1MB 문서를 약 500타마다 한 번만 다시 쓴다**(200행이면 2.5배 자주 1MB 를 쓴다)
  - 바이트 조건은 두지 않는다. 큰 붙여넣기도 행 하나이고, 불러오기 비용은 행 크기가 아니라 문서 크기를 따른다
  - `y-indexeddb` 의 500행(측정 d)과 같은 값이 된 것은 우연이다 — 위 두 줄이 근거다

### 4.5 실패

- `openYjsStore` 가 실패하면(IndexedDB 를 못 여는 브라우저·권한) `null`. 앱은 영속이 없는 F-305 동작 그대로다: `hasLocalState` 는 늘 거짓, N5 는 휘발 문구(11.2 N5′)
- `attach` 의 읽기가 실패하면 던진다 → 부르는 쪽(6.4)은 그 세션을 "기록 없음" 으로 다시 판정한다
- `put`·압축 트랜잭션이 한 번이라도 실패하면(`QuotaExceededError` 포함) `broken = true`, 그 세션은 더 쓰지 않는다(듣기를 뗀다). 앱은 그 세션의 N5 를 휘발 문구로 띄운다. `console.error` 한 번

### 4.6 정리

- **문서가 사라졌다고 확인되면 곧바로 지운다**: 실시간 세션이나 밀린 편집 러너(8장)가 `4404`(`not-found`·`deleted`)를 받았을 때 `removeDoc`
- **나이 정리**: 부팅 뒤 한 번, 첨부 GC 와 같은 예약(`scheduleAttachmentGc` 의 idle 방식)으로 `collectGarbage(Date.now())`. 이 사용자의 `meta` 중 `unsyncedLocal` 이 거짓이고 `lastOpenedAt` 이 `RETAIN_MS`(30일)보다 오래된 문서를 `removeDoc` 한다
  - 안 보낸 편집이 있는 문서는 나이로 지우지 않는다 — 사용자 데이터다
  - 지워도 잃는 것은 "그 문서를 오프라인에서 편집 가능하게 여는 것" 과 다음 열기의 대역폭뿐이다(서버가 원본)
- 사용자가 문서를 지울 때(`store.remove`) 따로 지우지 않는다 — 다음 열기·러너의 `4404` 또는 30일 정리가 치운다. 지운 문서는 목록에 없어 열 수 없다

## 5. 경로 판정 — F-305 4.1 에 더함 (`src/app/docPath.ts`)

### 5.1 계약

```ts
export type DocPathKind = 'local' | 'view' | 'pending' | 'realtime' | 'fallback' | 'offline-view'

export type DocPathInput = {
  storeKind: 'idb' | 'memory' | 'server'
  shareLinkScreen: boolean
  role: 'owner' | 'edit' | 'view' | undefined
  forbidden: boolean
  hasPendingChanges: boolean
  online: boolean
  hasLocalState: boolean        // 새로. yjsStore.hasState(docId). 영속이 없으면 false
}

export type InitialDocPath =
  | { kind: 'local' | 'view' | 'pending' | 'offline-view' }
  | { kind: 'realtime'; resume: boolean; startOffline: boolean }

export function decideDocPath(input: DocPathInput): InitialDocPath
```

규칙 — **위에서부터 처음 맞는 것** (1~3 은 F-305 그대로)

| 순서 | 조건 | 결과 |
| --- | --- | --- |
| 1 | `storeKind !== 'server'` 또는 `shareLinkScreen` | `local` |
| 2 | `role === 'view'` 또는 `forbidden` | `view` |
| 3 | `hasPendingChanges` | `pending` |
| 4 | `!online` 이고 `!hasLocalState` | **`offline-view`** (F-305 의 `fallback`/`offline` 을 대신한다) |
| 5 | 그 밖 | `realtime`, `resume = hasLocalState`, `startOffline = !online` |

- `decideDocPath` 는 더 이상 `fallback` 을 돌려주지 않는다. `fallback` 은 제어기가 정한다(6장). `FallbackReason` 의 `'offline'` 은 남는다 — 비재개 세션에서 첫 동기화 전 `offline` 이벤트가 오면 제어기가 `fallback`/`offline` 을 낸다(F-305 7.3). **App 은 그 경우를 폴백(잠금 + PUT)이 아니라 `offline-view` 로 연다**(9.1)
- App 의 판정 effect 는 `hasPendingChanges` 와 `hasState` 를 **함께** 기다린다(`Promise.all`). `hasState` 가 실패하면 `false`

### 5.2 `offline-view` 세션

- 본문: `store.get(docId)` 캐시 본문으로 편집기를 띄운다(지금 `view` 경로와 같은 방식 — 편집기 Doc 을 그 문자열로 심는 비실시간 경로). 방 Doc 을 만들지 않는다. **캐시 본문이 방 Doc·`md-yjs` 로 들어가는 길은 없다**(불변조건)
- 읽기 전용(`isReadOnlyDoc` 에 더한다), 제목도 읽기 전용. 본문 PUT(`useDocSaver`)·잠금(`useDocLock`) 없음 — F-305 10.1 표의 `view` 줄과 같다
- 알림 띠 N7(11.2). 상태바 `.statusbar-save` 는 저장소 표시 그대로 — 오프라인이면 `syncSuffix` 가 이미 ` · 오프라인` 을 붙인다(F-207 2.5). `.statusbar-live` 없음
- **`window` `online` 이벤트가 오면 그 문서 열기 세션을 새로 시작한다** — 경로를 다시 판정(대개 `realtime`, 기록이 없으므로 `resume: false`)하고 N7 을 걷는다(22장 Q5). F-305 3장 "한 세션의 경로는 바뀌지 않는다" 의 예외다. 그 규칙은 한 세션에 두 저장 경로가 섞여 이중 쓰기가 되는 것을 막으려는 것인데, `offline-view` 는 아무것도 쓰지 않으므로 이중 쓰기가 없다. 새 세션은 첫 동기화까지 편집기를 내리고(F-305 5.1) 방 Doc 으로 다시 띄운다 — 스크롤 위치는 지키지 않는다
- 캐시 본문조차 없으면(캐시에 없는 공유 문서 등) 지금 `store.get` 이 `null` 일 때의 흐름 그대로(편집기 없음) + N7

## 6. 연결 제어기 — 재개 가능 세션 (`src/app/liveDoc.ts`, F-305 7장에 더함)

### 6.1 계약에 더하는 것


- 비재개(`resumable: false`)는 **F-305 와 한 글자도 다르지 않다**. `ready` 는 `everSynced` 와 같은 값이다

### 6.2 재개 가능 세션의 단계

- `startOffline`: `start()` 는 소켓을 열지 않는다. 곧바로 `phase: 'reconnecting'`, `ready: true`. 첫 동기화 시간 제한(F-305 7.5)을 걸지 않는다. N5 타이머(`DISCONNECT_NOTICE_MS`)는 건다. `wake()` 가 첫 시도를 연다
- 온라인 시작: F-305 와 같이 `connecting`, `ready: false`, 첫 동기화 시간 제한을 건다. 첫 `synced` → `live`, `ready: true`, `everSynced: true`
- **폴백하지 않는다.** F-305 에서 `fallback` 이 되던 세 경우가 재개 가능 세션에서는 `reconnecting` + `ready: true` 가 된다(22장 Q2)

### 6.3 닫기 분류 — F-305 7.2 표에 열 하나를 더함

| 닫기 | 비재개, 첫 동기화 전 (F-305) | **재개 가능, `ready` 전** | `ready` 뒤 (동기화 뒤 포함) |
| --- | --- | --- | --- |
| `4401` | `fallback` / `signed-out` | `stopped` / `signed-out`, `ready: true` | `stopped` / `signed-out` |
| `4403` | `stopped` / `forbidden` | `stopped` / `forbidden`, `ready: false` | `stopped` / `revoked` |
| `4404` | `stopped` / `not-found` | `stopped` / `not-found`, `ready: true` | `stopped` / `deleted` |
| 그 밖, 열린 적 없음 | `fallback` / `unreachable` | `reconnecting`, `ready: true`, 백오프 | `reconnecting`, 백오프 |
| 그 밖, 열린 적 있음 | 백오프(시간 제한 안에서) | 백오프(시간 제한 안에서) | `reconnecting`, 백오프 |
| 첫 동기화 시간 제한(F-305 7.5) | `fallback` / `timeout` | `reconnecting`, `ready: true`, 백오프 | 해당 없음 |
| `goOffline()` | `fallback` / `offline` | `reconnecting`, `ready: true`, 대기 타이머 없음 | `live` 면 `reconnecting` (F-305) |

- "`ready` 뒤" 열은 `everSynced` 가 거짓이어도 쓴다 — 오프라인에서 로컬 기록으로 편집하다가 붙은 첫 연결이 `4403` 이면 "권한을 뺏김"(`revoked`, N2 + `새 문서로 저장`)이 맞다. `forbidden`(보기로 다시 열기)으로 가면 화면의 로컬 편집이 사라진다
- `4403` 을 `ready` 전에 받으면 F-305 와 같이 보기로 연다(`ready: false` 라 방 Doc 으로 편집기를 띄우지 않는다). 로컬 기록에 안 보낸 편집이 있었으면 그것은 보이지 않는다(15장 L3)
- `4404` 는 앞뒤 모두 `md-yjs` 기록을 지운다(4.6). 지우기 전에 편집기는 방 Doc(로컬 기록)으로 떠 있으므로 `새 문서로 저장` 이 로컬 편집까지 건진다
- 재개 가능 세션의 `reconnecting` 은 F-305 7.3 백오프·`wake`·N5 타이머를 그대로 쓴다

### 6.4 `useLiveDoc` 에서의 순서 (F-307 뒤)

1. 빈 방 Doc 을 만든다
2. 영속이 있으면 `attach(docId, roomDoc)` 를 **기다린다**. 판정기(7장)를 만든다
3. 그 뒤에 제어기를 만들고 `start()` 한다 — `ready` 가 불러오기보다 먼저 참이 되는 일이 없다(빈 방 Doc 으로 편집기가 뜨면 안 된다)
4. `attach` 가 던지면 영속 없이 진행하되, 그 세션이 `resume: true` 로 판정됐었다면 **그 문서 열기 세션을 다시 판정**한다(`hasLocalState: false` 로) — 오프라인이면 `offline-view`, 온라인이면 비재개 `realtime`
5. 세션이 끝나면(문서 전환·`null`) `detach` → 판정기 `destroy` → 제어기 `destroy` → 방 Doc `destroy` 순. `detach` 가 먼저라 방 Doc `destroy` 가 빈 업데이트를 쓰지 않는다
- `useLiveDoc` 의 인자는 문서 id 에 `{ store: YjsStore | null; resume: boolean; startOffline: boolean }` 를 더한다. 돌려주는 `LiveDocSession` 에 `merged: number`(병합 알림을 띄울 때마다 1 씩 는다, 7.3)와 `persistBroken: boolean` 을 더한다. F-307 이 더한 `awareness` 는 그대로

## 7. 병합 알림 판정 — `src/app/liveMerge.ts` (F-301 3.7 결론)

### 7.1 계약

```ts
export type MergeTracker = {
  setLive(live: boolean): boolean     // 제어기 단계가 live 로 바뀔 때 true 를 넘긴다. 돌려준 값이 true 면 병합 알림(N8)
  unsyncedLocal(): boolean
  destroy(): void
}

export function createMergeTracker(doc: Y.Doc, options: {
  initialUnsynced: boolean                         // attach 가 돌려준 meta 값
  isLocalOrigin: (origin: unknown) => boolean      // remoteGate 의 isEditorRelay
  isLoadOrigin: (origin: unknown) => boolean       // origin === YJS_LOAD_ORIGIN
  onUnsyncedChange: (value: boolean) => void       // attachment.setUnsyncedLocal 로 잇는다
}): MergeTracker
```

- `remoteGate.ts` 에 더하는 export: `isEditorRelay(origin: unknown): boolean` — `origin === RELAY_FROM_EDITOR`. 편집기 Doc 의 내 편집(본문·제목 `LOCAL_TITLE` 포함)은 게이트가 이 origin 으로 방 Doc 에 넣는다(F-303 8.2, `onEditorUpdate`). 상수 자체는 export 하지 않는다 — 다른 모듈이 그 origin 으로 쓰면 게이트 중계 규칙이 깨진다

### 7.2 규칙

- **안 보낸 내 편집(`unsyncedLocal`)**: 시작값은 `initialUnsynced`. 방 Doc 에 `isLocalOrigin` 인 업데이트가 **live 가 아닐 때** 들어오면 참. live 로 바뀌는 순간(= `synced`) 거짓. 값이 바뀔 때마다 `onUnsyncedChange`
  - `synced` 에서 거짓으로 내리는 근거: 측정 (e) — `synced` 가 올 때 내 밀린 편집은 이미 `ws.send` 로 넘어갔다. 서버 확인은 없다. 그 뒤 소켓이 죽어 못 갔더라도 편집은 `md-yjs` 에 남아 **그 문서를 이 브라우저에서 다음에 열 때** 다시 간다(Yjs 동기화는 상태 기반이라 매번 빠진 것을 다시 보낸다). 러너(8장)만 못 집는다(15장 L4)
  - live 인 동안의 내 편집은 표시하지 않는다 — 그 자리에서 곧바로 서버로 간다
- **서버 쪽 본문 변경(`remoteChanged`)**: 방 Doc 의 `content` `Y.Text` 가 `isLocalOrigin` 도 `isLoadOrigin` 도 아닌 트랜잭션으로 **live 가 아닐 때** 바뀌면 참. 이 구간에 원격 변경이 들어오는 길은 다시 붙는 소켓의 step 2 와 그사이 중계뿐이다
  - `title` 만 바뀐 것은 세지 않는다 — F-301 3.7 "서버에서 받은 업데이트가 본문을 바꿨을 때"
- **`setLive(true)` 가 true 를 돌려주는 조건**: 그 순간 `unsyncedLocal` 과 `remoteChanged` 가 **둘 다 참**. 돌려준 뒤 둘 다 거짓으로
  - 한쪽만 바뀌었으면 알리지 않는다(F-301 3.7 — 합쳐진 게 아니라 올라간 것)
  - 첫 열기(기록 없음): `unsyncedLocal` 이 거짓이라 step 2 로 본문이 채워져도 알리지 않는다
  - 오프라인에서 고치고 창을 닫았다가 온라인에서 다시 열기: `initialUnsynced` 가 참 → 첫 `synced` 의 step 2 가 본문을 바꿨으면 알린다. 이것도 "재연결 직후" 로 본다
- `setLive(false)` 는 아무것도 지우지 않는다

### 7.3 앱

- `useLiveDoc` 가 제어기 스냅샷을 들을 때 `phase === 'live'` 로 바뀌는 순간 `setLive(true)`, 그 밖으로 바뀌면 `setLive(false)`. `true` 가 돌아오면 `merged` 를 1 올린다
- App 은 `merged` 가 오를 때마다 N8 을 띄운다(`info`). N5 가 떠 있으면 같은 순간 걷히므로(F-305 11.2) 순서는 N5 걷기 → N8

## 8. 밀린 편집 러너 — `src/app/yjsFlush.ts`

### 8.1 왜 필요한가

- 지금(F-305 전 배포본)은 오프라인 편집이 outbox 에 들어가 **어느 문서를 열든 부팅 때 나간다**(3.3). `md-yjs` 편집은 그 문서의 방 Doc 이 붙어야만 나간다. 오프라인에서 X 를 고치고 창을 닫은 뒤, 다음에 X 를 열지 않으면 **X 의 편집은 이 브라우저 밖으로 영영 안 나간다** — 다른 사람도, 다른 기기의 나도 못 본다. `md.startScreen` 기본값이 `home` 이라(`architecture.md` 4장) 다시 열 때 X 가 자동으로 열리지도 않는다
- 이 러너가 outbox 의 "부팅 때 전부 보냄" 성질을 `md-yjs` 에 옮긴다(22장 Q3)

### 8.2 계약과 규칙

```ts
export const FLUSH_SESSION_TIMEOUT_MS = 30_000
export type FlushOutcome = 'synced' | 'gone' | 'forbidden' | 'signed-out' | 'failed'
export function flushUnsyncedDocs(deps: FlushDeps): Promise<Map<string, FlushOutcome>>
```

- `FlushDeps` 의 모양은 구현이 정한다. 주입받는 것: `YjsStore`, "지금 편집기에 열린 문서 id 인가" 판정, 제어기를 만드는 함수(`createLiveDocController` + `openLiveSocket`), 타이머. `window` 를 읽지 않는다 — node 단위 테스트가 가짜 제어기로 돈다
- 대상: `unsyncedDocIds()`. **한 번에 한 문서씩** 차례로
- 지금 열린 문서면 건너뛴다(그 세션이 스스로 올린다)
- 한 문서: 새 `Y.Doc` → `attach` → 판정기(7장, `initialUnsynced` 는 meta 값) → 제어기(`resumable: true`, `startOffline: false`, `keepaliveMs: null`) `start()`
  - `live` → `synced`(판정기가 `unsyncedLocal` 을 내린다). **병합 알림은 띄우지 않는다**(22장 Q10)
  - `stopped`/`not-found`·`deleted` → `gone`, `removeDoc`
  - `stopped`/`forbidden`·`revoked` → `forbidden`. 기록은 남긴다(15장 L6)
  - `stopped`/`signed-out` → `signed-out`. **남은 문서를 모두 건너뛰고 러너를 끝낸다**
  - `reconnecting`(열리지 않고 닫힘 등) 또는 `FLUSH_SESSION_TIMEOUT_MS` 초과 → `failed`. 기록·표시 남김
  - 끝나면 `detach` → 판정기 `destroy` → 제어기 `destroy` → Doc `destroy`
- 언제 도는가(App)
  - 부팅이 끝나고(`bootPhase === 'ready'`) 저장소가 `server` 이고 `navigator.onLine` 이면 한 번. `scheduleAttachmentGc` 와 같은 idle 예약으로
  - `window` `online` 이벤트마다 한 번
  - 이미 돌고 있으면 새로 시작하지 않는다(한 페이지에 러너 하나)
- 비용: 대상 문서마다 Worker 요청 1 + DO 연결 1(잠들었으면 `onLoad` 1). 대상은 "끊긴 동안 고친 문서" 뿐이라 드물다

## 9. 앱 연결 (`App.tsx`, F-307 뒤)

### 9.1 문서 열기

- 판정 effect: `hasPendingChanges`·`hasState` 를 함께 기다려 `decideDocPath` 에 `hasLocalState` 를 넘긴다. `realtime` 이면 `resume`·`startOffline` 을 세션에 둔다
- 제어기가 `fallback`/`offline` 을 내면(비재개, 첫 동기화 전 `offline`) 경로를 `offline-view` 로(5.2). `unreachable`·`timeout`·`signed-out` 은 F-305 그대로 `fallback`
- **편집기 마운트 조건을 `everSynced` 에서 `ready` 로 바꾼다** — F-305 "첫 synced 블록"(방 Doc 본문으로 `openDoc`·제목·글자 수를 맞춤)과 `liveRoomDoc`(사이드바 `updatedAt`·편집기 `live` 옵션)가 `ready` 를 본다. 비재개 세션은 `ready === everSynced` 라 동작이 같다
- `stopped`/`not-found`(재개 가능, `ready: true`)는 방 Doc 으로 편집기를 띄운 뒤 읽기 전용 + N3. F-305 의 `notFoundBeforeSync`(캐시 본문을 읽기 전용으로) 흐름은 비재개일 때만
- 읽기 전용 판정(`isReadOnlyDoc`)에 `offline-view` 를 더한다

### 9.2 `md-yjs` 열기

- 저장소가 `server` 로 정해지면 `openYjsStore(store.userId)` 를 한 번 연다. 페이지 수명 동안 하나. 로그인·로그아웃은 페이지 이동이라 다시 열 일이 없다(F-207 2.6)
- `ServerStore` 에 `readonly userId: string` 을 더한다 — 오프라인 부팅(`account.state === 'offline'`)에서는 App 이 계정 id 를 모르고 `openStore` 가 `md.account` 에서 읽는다(`openStore.ts`). `withTabBroadcast` 가 저장소를 펼쳐 감싸므로 평범한 필드는 그대로 지나간다
- 부팅 뒤 idle 에 `collectGarbage`(4.6), 이어서 러너(8장)

### 9.3 PUT·잠금·캐시 본문

| 경로 | 본문 PUT | 잠금 | 캐시 본문(`md-remote`) | `md-yjs` |
| --- | --- | --- | --- | --- |
| `realtime`(재개 포함) | 없음 | 없음 | 안 씀 | 불러오고 쓴다 |
| `offline-view` | 없음 | 없음 | 읽기만 | 안 씀 |
| `pending`·`fallback` | F-305 그대로 | F-305 그대로 | F-305 그대로 | 안 씀 |
| `local`·`view` | F-305 그대로 | F-305 그대로 | F-305 그대로 | 안 씀 |

- **캐시 본문을 실시간 세션에서 파생하지 않는다**(F-305 20장 인계 — 22장 Q8). 캐시 본문은 "서버 스냅샷의 거울" 로 둔다 — 다음 `list()` 가 `version` 이 다른 문서를 다시 받아 맞춘다(F-207 2.2). 실시간 문서의 로컬 진실은 `md-yjs` 다
  - 파생하지 않는 이유: 캐시 문서 행은 `version`(폴백 PUT 의 `baseVersion`)과 본문을 한 행에 든다. 앱이 본문만 고쳐 쓰면 `version` 과 본문이 서로 다른 시점의 값이 되고, 그 문서가 나중에 폴백으로 열리면 낡은 `version` + 새 본문으로 PUT 한다. `serverStore` 밖에서 캐시 행을 쓰는 두 번째 필자도 생긴다
  - 대가: 오프라인 동안 검색·지도·`offline-view` 가 보는 본문은 마지막 `list()` 시점이다(15장 L2). 첨부 GC 는 이것 때문에 거르개가 필요하다(10장)

## 10. 첨부 GC 거르개 — 이 명세가 만드는 회귀를 막는다

- 첨부 GC(F-156 2.7)는 서버 저장소일 때 **캐시 본문**의 참조를 본다(`App.tsx` `gcStore`, F-207 2.5). F-305 까지는 오프라인 편집이 `store.update` 로 캐시 본문에 들어갔다. 이 명세 뒤로 오프라인 편집은 `md-yjs` 에만 있다 → 오프라인에서 붙여 넣은 이미지(캐시 `attachments` 에 `uploaded: false`, outbox `upload` 대기)가 어떤 캐시 본문에도 없게 된다. 오프라인이 24시간을 넘긴 채 부팅하면 GC 가 그 blob 을 지우고, 뒤이은 `upload` 는 캐시에 blob 이 없어 항목을 버린다(`sendOne` `upload`) — **이미지가 영영 사라진다**
- 막는 법: `serverStore.listAttachments()` 항목에 `uploaded`(캐시 행 값)를 싣고, App 의 서버용 `gcStore.listAttachments` 가 **`uploaded === false` 인 것을 빼고** 넘긴다. 아직 안 올린 첨부는 GC 대상이 아니다. 올린 첨부는 캐시에서 지워져도 서버에서 다시 받는다(`getAttachment`)
- `AttachmentMeta` 에 `uploaded?: boolean` — idb·memory 저장소는 채우지 않는다(`undefined` 는 거르지 않는다)

## 12. 창 닫기 경고 — 두지 않는다 (22장 Q7)
