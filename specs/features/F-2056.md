## 3. 결론 — 개요가 "여기서 정한다" 고 넘긴 다섯 가지

### 3.1 TTL 값과 기준 시각 — **10분, 탭마다 메모리(`serverStore` 인스턴스)**

- `LIST_FRESH_TTL_MS = 600_000`. 근거: 같은 앱이 이미 "화면이 다시 보일 때 `/api/me` 재확인" 에 10분(`ACCOUNT_RECHECK_MS`)을 쓴다 — 다른 기기에서 생긴 변화를 따라잡는 주기로 사용자에게 한 번 받아들여진 값이다. 다른 값의 효과는 13장 Q1
- **기준 시각 = 이 `serverStore` 인스턴스에서 `/api/docs` 를 성공적으로 읽은 `list()` 가 끝난 시각**(`handlers.now`, 기본 `Date.now`). 누가 부른 `list()` 든 센다 — 부팅 뒤 맞추기, 검색이 부른 뒤 새로 읽기, 가져오기 뒤 목록 등. `/api/docs` 가 실패한(오프라인·5xx·401) `list()` 는 시각을 바꾸지 않는다 — 캐시가 서버와 맞춰진 것이 아니기 때문이다
- **탭 사이에 공유하지 않는다.** 까닭:
  - 공유 목록(3.2)이 탭 메모리에만 있다. 시각만 탭 사이에 나누면, 탭 A 가 계속 먼저 새로 읽는 동안 탭 B 는 서버를 한 번도 안 불러 **B 의 공유 목록이 B 를 새로 고칠 때까지 낡는다**(새로 초대받은 문서가 B 에 안 뜬다)
  - 새 저장 키가 필요 없다(localStorage·IndexedDB 스키마 불변). 단위 테스트가 `now` 주입만으로 된다
  - 대가: 탭이 k 개면 TTL 당 새로 읽기가 최대 k 번. 탭 둘 기준 차이는 13장 Q1 표
- 새로 고침(페이지 재시작)하면 시각은 없어진다(`null` = 낡음) — 부팅이 어차피 서버 목록을 읽어 곧 채운다

### 3.2 서버를 안 부르는 resync 의 삭제 판정과 공유 목록 — **캐시 삭제로 충분, 공유는 마지막 서버 값**

- **다른 탭에서 지운 문서**: 다른 탭의 `remove()`·`removeFolder(delete-all)` 는 `md-remote` 캐시 행을 지운 **뒤** resolve 하고, `withTabBroadcast` 는 resolve **뒤** 신호를 보낸다(확인함). 같은 출처의 탭은 같은 `md-remote` 를 본다. 그러므로 신호를 받은 탭의 `listCached()` 에는 그 문서가 이미 없다 → `mergeResyncList` 가 스냅샷에 있던 그 id 를 `removedIds` 로 낸다 → 열린 문서면 지금처럼 `deletedElsewhereSourceRef = 'tab'` + `setDeletedElsewhereId`. **판정 규칙은 바뀌지 않고 입력만 캐시로 바뀐다**
- **공유 목록(리뷰 A3 의 `sharedListed`)**: 마지막으로 끝난 `list()` 의 `/api/shared` 결과를 `serverStore` 가 들고 있다(`lastSharedList()`, 4.2). resync 결과 = 캐시 소유 문서 ∪ 그 공유 목록. `sharedListed` = `lastSharedList() !== null`. 마지막 `/api/shared` 가 실패했으면 `null` → `sharedListed: false` → `mergeResyncList` 가 지금처럼 **공유 문서를 지우지 않는다**. 다른 탭은 공유 문서 집합을 바꿀 수 없다(초대·해제는 다른 사람·다른 기기 몫) — 그래서 마지막 서버 값이면 충분하다
- **같은 id 가 캐시와 공유 목록에 둘 다 있을 때**: 공유받은 edit 문서를 `pending`·`fallback` 경로로 처음 편집하면 `update()` 가 그 문서를 캐시에 넣는다(`update` 의 "첫 편집을 보내려면 … 지금 캐시한다"). 그러면 `listCached()` 가 그것을 `role: 'owner'` 로 돌려준다. 합칠 때 **공유 목록 쪽이 이긴다**(캐시 행을 버린다) — 역할·소유자 표시가 뒤집히지 않게(5.3 `combineCachedList`)
- **다른 기기가 지운 문서**: 서버를 부를 때만 안다. TTL 밖 뒤 새로 읽기(서버 `resyncFromStore`)가 찾으면, 그 열린 문서의 알림은 **`이 문서가 다른 곳에서 삭제되었습니다. …`**(F-2042 6장 문구, `'bootMerge'` 갈래)로 띄운다 — 서버가 알려준 삭제는 다른 탭이라고 단정할 수 없다. 탭 신호 경로에서 캐시로 찾은 삭제는 지금 문구(`… 다른 탭에서 삭제되었습니다. …`) 그대로
- 한계(받아들임): 다른 탭이 **자기 서버 `list()`** 로 다른 기기 삭제를 캐시에서 지운 직후 이 탭이 캐시 resync 를 하면, 이 탭은 그것을 "다른 탭에서 삭제" 로 적는다. 열린 문서가 그 문서일 때만 문구가 어긋나고, 읽기 전용·`새 문서로 저장` 동작은 같다

### 3.3 금고(`e2eeStore`) 목록 — **캐시는 봉투, 감싼 `listCached` 가 푼다. 잠기면 잠긴 모양**

- `md-remote` 의 금고 문서 행은 **봉투**(제목·본문 암호문 + `e2eeKey` + `attachmentRefs`)다 — `withE2ee.create`·`update` 가 봉투를 안쪽 저장소에 넘기고 `serverStore` 는 받은 그대로 캐시에 쓴다
- 앱이 부르는 `store.listCached()` 는 `withE2ee` 가 감싼 것이다(펼침으로 `withTabBroadcast` 결과에도 있다). 행마다 `decode`: MK 있음 → 평문 + `e2ee: 'open'`, MK 없음 → `title: ''`·`content: ''`·`e2ee: 'locked'`·`attachmentRefs` 유지(F-2042 U7 이 이미 판정). **`list()` 가 주는 모양과 같다** — 그래서 검색(`lockedCount`, F-409 3.1)·지도(`lockedCount`)·사이드바(`잠긴 문서`)가 바뀌지 않는다
- 공유 목록에는 금고 문서가 없다(금고 문서는 링크·초대가 막힌다, F-409 E9) — `lastSharedList()` 는 `decode` 가 필요 없다
- 잠그기·열기 동안: `SearchDialog`·`MapPage` 는 `e2eeOpen` 이 바뀌면 인덱스·그래프를 버리고 다시 읽는다(F-409 3.5·3.6). 다시 읽을 때 목록 소스(5.5)가 `listCached()` 를 새로 읽으므로 새 MK 상태로 `decode` 된다. 금고 열림/잠김 때의 사이드바 목록 다시 읽기(`e2ee?.status` 효과)는 이 명세가 건드리지 않는다(서버 목록 그대로)

### 3.4 검색·지도의 본문이 낡는 경우 — **실시간 편집은 캐시를 거치지 않는다** (코드로 확인, 개요에 없던 것)

- 실시간 경로(`realtime`)는 `store.update` 를 부르지 않는다(자동 저장이 꺼진다, F-305 4장·10장). `md-remote` 의 그 문서 본문은 **DO 가 D1 에 스냅숏을 쓴 뒤(조용해지면 5초, 최대 30초) 다음 서버 `list()` 가 버전 차이로 본문을 새로 받을 때만** 바뀐다. 클라이언트가 실시간 본문을 캐시에 쓰는 길은 없다(grep 확인)
- 그래서 캐시만 읽으면 **이 탭에서 방금 실시간으로 쓴 글이 검색·지도에 TTL 동안 안 보인다.** 지금은 검색을 열 때마다 서버 `list()` 를 부르므로 스냅숏 뒤(≥5초)면 보인다 — 받아들인 대가(사용자 결정 4, "다른 기기의 변경")를 넘어서는 퇴행이다
- **이 명세의 해법 (이 탭)**: 탭은 자기가 본 실시간 변경을 안다 — 방 Doc 효과가 이미 `SAVE_DEBOUNCE_MS` 뒤 사이드바 `updatedAt` 을 지금으로 올린다. 그 자리에서 **문서 id → 마지막 실시간 변경 시각**을 메모리 `Map` 에 적는다(6.3). 검색·지도를 열 때 그 시각 중 하나라도 `lastServerListAt()` 보다 늦으면(`hasLiveChangesSince`, 5.2) **지금처럼 서버 목록을 기다린 뒤** 캐시를 읽는다(5.5). 내 편집·상대 편집 둘 다 센다 — 둘 다 이 탭 캐시 본문을 낡게 한다
  - 이 경우 D1 절감은 없다(지금과 같은 1회). 실시간으로 편집하던 사용자가 검색할 때의 결과는 지금과 같게 지킨다. 그 밖의 경우(읽기만, 로컬·pending 편집, 탭 신호)는 절감한다
  - 서버 목록이 스냅숏보다 먼저 끝나면(편집 뒤 5초 안에 검색) 본문은 여전히 옛 것이다 — **지금과 같은 한계**다
- **다른 탭의 실시간 편집**: 탭 A 가 실시간으로 쓴 본문은 A 도 캐시에 쓰지 않으므로 탭 B 의 캐시에 없고, 실시간 경로는 탭 신호도 보내지 않는다. **사용자 전제 4 가 이 경우에는 성립하지 않는다.** 이 명세 기본값은 받아들인다(B 의 검색·지도에 TTL 만큼 늦게 보인다) — 13장 **Q2 사람 결정 필요**. 지금도 B 의 사이드바 제목·시각은 A 의 실시간 편집을 모른다(탭 신호 없음)

### 3.5 부팅 GC 가 다시 쓸 "부팅 목록 결과"와 진행 중 합치기 키

- **부팅 목록 결과** = `boot()` 가 사이드바에 쓰려고 이미 부른 `appStore.list()` 의 결과(캐시 없는 길: 그 `list` 값, 캐시 먼저 셸 길: 뒤 맞추기의 `appStore.list()` 약속). **수명은 첫 GC 한 번**: GC 가 그 값을 한 번 읽고 끝나면 버린다. 다른 곳(검색·지도·resync)은 이 값을 쓰지 않는다(그들은 캐시 소스를 쓴다). 시간 제한을 두지 않는다 — GC 는 부팅 직후 한 번이고, 24시간 유예(`GRACE_MS`)가 그 사이 생긴 첨부를 지킨다
  - 캐시 먼저 셸 길의 순서가 바뀐다: 지금은 셸 직후 `scheduleGc()` 를 부르고 GC 가 따로 `list()` 를 부른다. 뒤에는 **뒤 맞추기 `list()` 가 끝난 뒤** 그 결과로 idle GC 를 예약한다. 뒤 맞추기가 던지면(오류) 이 페이지에서는 GC 를 하지 않는다 — 다음 부팅에 한다
  - GC 에 넘기는 값은 `withE2ee` 로 푼 앱 층 문서다(날 저장소 행이 아니다). 금고 문서는 잠겼으면 `content: ''` + `attachmentRefs`, 열렸으면 평문 + `attachmentRefs` 라 `cleanupUnusedAttachments` 의 "본문 참조 ∪ `attachmentRefs`"(F-406 G1)가 그대로 맞다. 지금의 `e2eeKey` → 참조 글자 바꾸기는 필요 없어진다(푼 문서에는 `e2eeKey` 가 없다). 참조 집합은 지금과 같거나 크다(열린 금고 문서는 본문 참조가 더해진다 — 둘은 같은 id 다) → **지울 것이 늘지 않는다**
  - `idb` 저장소(로그아웃)도 같은 규칙으로 부팅 결과를 쓴다 — D1 과 무관하지만 규칙을 하나로 둔다. `memory` 는 지금처럼 GC 를 건너뛴다
- **진행 중 합치기의 키 = "쓰기 세대"**. `serverStore` 가 정수 하나를 들고, 캐시의 문서·폴더 행을 바꾸는 공개 메서드가 **불리는 순간**(끝나기를 기다리지 않고) 1 올린다: `create`·`update`·`remove`·`moveDoc`·`setPinned`·`createFolder`·`renameFolder`·`moveFolder`·`removeFolder`·`setDocE2ee`·`setFolderE2ee`·`importLocal`·`importLocalE2ee`·`refreshDocFromServer`. `list()` 가 불렸을 때 진행 중인 `list()` 가 있고 **그것이 시작할 때의 세대와 지금 세대가 같으면** 그 약속을 같이 기다린다. 다르면 새로 시작한다(4.1)
  - 왜 "같은 틱" 이나 "시간 창" 이 아닌가: 합류한 호출이 받는 결과는 진행 중인 호출이 **끝에** 읽은 캐시다. 합류자가 그 전에 한 쓰기는 대부분 들어가지만, 진행 중인 호출이 캐시를 이미 읽고 `/api/shared` 만 기다리는 순간이면 빠진다 — 가져오기·폴더 삭제 뒤 `list()` 로 사이드바를 통째로 바꾸는 호출이 방금 만든 문서를 잃는다. 세대가 다르면 합류하지 않으므로 이 경우가 생기지 않는다
  - 계정(`userId`)은 키에 넣지 않는다 — 저장소 인스턴스가 사용자 하나에 하나다(F-207 2.6, 부팅 때 한 번)
  - 합치는 것은 `list()` 뿐이다. `listFolders()` 는 합치지 않는다(사용자 결정 2 범위. ①②③ 이 캐시 폴더를 쓰므로 남는 `/api/folders` 는 부팅·드문 경로뿐)

## 4. 저장소 계약 (`src/storage/serverStore.ts`)

```ts
// ServerStore 타입에 더한다. 둘 다 this 를 쓰지 않는다 — withE2ee·withTabBroadcast 가 펼쳐 넘긴다
lastSharedList(): Doc[] | null     // 마지막으로 끝난 list() 의 /api/shared 결과(content ''). 한 번도 없거나 그 요청이 실패했으면 null
lastServerListAt(): number | null  // /api/docs 를 성공적으로 읽은 마지막 list() 가 끝난 시각(handlers.now). 없으면 null
```

### 4.1 `list()` 진행 중 합치기 — 규칙

- 3.5 의 쓰기 세대로 판정한다. 합류한 호출도 진행 중인 호출과 **같은 결과**를 받되, **호출마다 새 배열**을 받는다(`Doc` 객체는 같아도 된다 — 지금 부르는 곳은 결과를 고치지 않고 `map`·`sort` 사본을 만든다)
- 진행 중인 호출이 던지면(비 `ApiError` — 지금도 `list()` 가 던지는 유일한 경우) 합류자도 같은 오류를 받는다. 성공·실패 모두 끝나면 진행 중 자리를 비운다 — **결과를 보관하지 않는다**(끝난 뒤의 호출은 늘 새로 요청한다. 결과 재사용은 앱 층 3.5·5장 몫)
- 부수 효과(`lastListSharedOk`·`lastSharedList`·`knownSharedIds`·`lastServerListAt`·`patchState`)는 한 번만 일어난다
- 기존 `activeListSessions`(`get()` 이 진행 중인 목록을 기다리는 F-2042 3.5)·본문 받기 모음(3.3)은 그대로다

### 4.2 `lastSharedList()`·`lastServerListAt()` — 규칙

- `lastSharedList`: `lastListSharedOk` 를 적는 **같은 자리**에서 같이 적는다. `lastListSharedOk()` 는 남기고, 늘 `lastSharedList() !== null` 과 같다. 돌려줄 때 배열 사본
- `lastServerListAt`: `/api/docs` 요약이 성공한 `list()` 가 본문 받기·캐시 읽기까지 끝낸 뒤 `now()` 를 적는다. 요약이 실패한 `list()` 는 건드리지 않는다

## 5. 순수 모듈 `src/app/cachedList.ts` (새 파일)

React·DOM·IndexedDB 를 import 하지 않는다. `Doc`·`Folder`·`Store` 타입만 `../types` 에서 가져온다. 테스트 환경 `node` 에서 가짜 함수로 전부 판정한다

```ts
export const LIST_FRESH_TTL_MS = 600_000

export function isListStale(input: { lastServerListAt: number | null; now: number; ttlMs?: number }): boolean
export function hasLiveChangesSince(changedAt: ReadonlyMap<string, number>, since: number | null): boolean
export function combineCachedList<T extends { id: string; updatedAt: number }>(input: {
  cached: readonly T[]
  shared: readonly T[] | null
}): { docs: T[]; sharedListed: boolean }

export type ListRefresher = {
  run(): Promise<void>      // 진행 중이면 그 약속, 아니면 새로 시작
  maybeRefresh(): void      // isStale() 이 참이고 진행 중이 아닐 때만 run(). 기다리지 않는다
}
export function createListRefresher(deps: { refresh: () => Promise<void>; isStale: () => boolean }): ListRefresher

export function createCachedListSource(deps: {
  listCached: () => Promise<{ docs: Doc[]; folders: Folder[] }>
  lastSharedList: () => Doc[] | null
  hasLiveChanges: () => boolean
  isOnline: () => boolean
  refresher: ListRefresher
}): Pick<Store, 'list' | 'listFolders'>
```

### 5.1 `isListStale`
- `lastServerListAt` 가 `null` 이면 참. `now - lastServerListAt >= ttlMs`(기본 `LIST_FRESH_TTL_MS`)이면 참. 시계가 뒤로 가 `now < lastServerListAt` 이면 거짓

### 5.2 `hasLiveChangesSince`
- `changedAt` 의 값 중 하나라도 `since` 보다 크면(엄격히) 참. `since` 가 `null` 이면 `changedAt` 이 비어 있지 않을 때 참

### 5.3 `combineCachedList`
- `shared` 가 `null` 이면 `docs` = `cached` 를 `updatedAt` 내림차순으로, `sharedListed: false`
- 아니면 `cached` 에서 `shared` 에 있는 id 를 뺀 것 ∪ `shared`, `updatedAt` 내림차순, `sharedListed: true` (3.2 "공유 목록 쪽이 이긴다")
- 입력 배열을 고치지 않는다

### 5.4 `createListRefresher`
- 한 번에 하나: `run()` 이 진행 중이면 새로 부르지 않고 그 약속을 돌려준다. 끝나면(성공·실패) 자리를 비운다
- `refresh()` 가 던져도 `run()` 은 던지지 않는다(삼키고 `console.error('list_refresh_failed', err)`) — 검색·지도 열기가 이것 때문에 실패하지 않게
- 앱은 ①②③ 이 **같은 인스턴스 하나**를 쓴다(6.1) — 탭 신호와 검색 열기가 겹쳐도 서버 목록은 한 번

### 5.5 `createCachedListSource` — 검색·지도에 넘기는 `store`
- `list()`·`listFolders()` 는 **한 번의 읽기 회차**를 나눠 쓴다: 회차가 진행 중이면 둘 다 그 회차를 기다린다(`buildSearchIndex`·`MapPage` 가 둘을 `Promise.all` 로 같은 틱에 부른다 → `listCached()` 한 번). 회차가 끝나면 비운다
- 회차 순서(이 순서가 결정이다):
  1. `hasLiveChanges()` 가 참이고 `isOnline()` 이 참이면 `refresher.run()` 을 **기다린다**(3.4). 거짓이면 `refresher.maybeRefresh()`(TTL 밖일 때만 뒤에서 시작, 기다리지 않는다)
  2. `listCached()` 를 읽는다 — 1 에서 기다렸으면 새로 읽기가 끝난 **뒤**의 캐시다
  3. `combineCachedList({ cached: docs, shared: lastSharedList() })` 의 `docs` 를 `list()` 가, `folders` 를 `listFolders()` 가 돌려준다
- 오프라인이면 1 에서 기다리지 않는다 — 실패할 요청을 기다려 검색을 늦추지 않는다(`오프라인 —` 안내는 `SearchDialog` 가 이미 띄운다, F-288 A7)
- 1 에서 뒤로 돌린 새로 읽기가 끝나도 **열려 있는 검색 인덱스·지도 그래프를 갈아 끼우지 않는다.** 새로 읽기는 캐시·사이드바를 맞추고, 다음 열기가 그것을 읽는다 — 13장 Q3

## 6. `App.tsx` 배선 (다섯 자리, 규칙만)

`store.kind === 'server'` 일 때만 바뀐다. `idb`·`memory` 는 모든 경로가 지금 그대로다(`list()` 가 로컬이라 D1 과 무관)

### 6.1 새로 읽기 한 줄 — `resyncFromStore`
- `resyncFromStore` 에 삭제 문구 갈래 인자 하나를 더한다: 기존 다섯 호출은 지금 문구(`'tab'`), 새로 읽기(5.4 `refresh`)가 부를 때는 `'bootMerge'`(3.2). 나머지 동작(순번 `bootListSeqRef`, `mergeResyncList`, 금고 전환 재시작)은 그대로
- `createListRefresher` 인스턴스 하나를 페이지 수명 동안 둔다. `refresh` = 서버 저장소일 때 `resyncFromStore('bootMerge')`, `isStale` = `isListStale({ lastServerListAt: store.lastServerListAt(), now: Date.now() })`. 최신 `resyncFromStore` 는 ref 로 읽는다 — 인스턴스를 렌더마다 다시 만들지 않는다

### 6.2 탭 신호 받기 — 캐시 resync
- `useTabSync` 의 `onDocsChanged` 는 서버 저장소면 새 함수(캐시 resync), 아니면 지금 `resyncFromStore`
- 캐시 resync 규칙:
  1. 스냅숏 = 지금 `docsRef.current`
  2. `store.listCached()` 를 읽고 `combineCachedList({ cached, shared: store.lastSharedList() })`
  3. 반영은 `resyncFromStore` 의 반영부와 같다: `setFolders(캐시 폴더)`, `keepLiveTitle` + `mergeResyncList({ snapshot, current: prev, result, sharedListed })` 를 `flushSync` 안에서 한 번, 열린 문서가 `removedIds` 에 있으면 `'tab'` 문구로 `setDeletedElsewhereId`, 금고 전환 재시작 조건(F-407 7.4) 그대로
  4. 반영한 뒤 `refresher.maybeRefresh()`
- **순번(`bootListSeqRef`·`lastAppliedListSeqRef`)을 올리지도 비교하지도 않는다.** 까닭: 순번은 "늦게 **시작한** 서버 결과만 반영" 규칙이다. 캐시 resync 가 순번을 올리면, 그보다 먼저 시작해 늦게 끝나는 서버 목록(부팅 뒤 맞추기 등)이 버려져 서버에만 있던 문서가 사이드바에 안 붙는다. 서버 목록의 결과도 끝에 읽은 캐시로 만들어지므로(4장 확인), 나중에 도착한 서버 결과가 캐시 resync 결과보다 낡지 않는다
- 이 경로는 사이드바 state 만 바꾼다. 열린 편집기 본문·`Y.Doc` 은 건드리지 않는다(불변조건, F-296 7.2 와 같다)

### 6.3 실시간 변경 시각 — 기록
- 방 Doc 효과(`liveRoomDoc` 의 `afterTransaction` → `SAVE_DEBOUNCE_MS` 타이머)에서 사이드바 `updatedAt` 을 올리는 **같은 순간**에 `liveChangedAtRef`(`Map<문서 id, 시각>`)에 그 문서 id → 같은 `now` 를 적는다. 조건(첫 동기화 전 따라잡기·댓글만 바뀐 트랜잭션 제외)은 지금 효과의 것을 그대로 따른다
- 지우지 않아도 된다 — 크기는 이 페이지에서 실시간으로 연 문서 수를 넘지 않는다

### 6.4 검색·지도에 넘기는 `store`
- 서버 저장소면 `SearchDialog`·`MapPage` 의 `store` prop 에 `createCachedListSource` 결과를 넘긴다: `listCached` = `store.listCached`, `lastSharedList` = `store.lastSharedList`, `hasLiveChanges` = `hasLiveChangesSince(liveChangedAtRef.current, store.lastServerListAt())`, `isOnline` = `navigator.onLine`, `refresher` = 6.1 의 인스턴스
- **소스 객체는 `store` 가 바뀔 때만 새로 만든다**(`useMemo` 의존 `store` 하나). `buildSearchIndex` 는 `store !== cachedStore` 면 인덱스 캐시를 통째로 버리므로, 렌더마다 새 객체면 F-286 의 재사용이 사라진다. `hasLiveChanges` 등은 ref 를 읽어 최신 값을 본다
- `searchScope`·`beforeIndex`(열기 전 저장 flush)는 그대로 — flush 가 `pending`·`fallback`·금고 편집을 캐시에 쓴 뒤 소스가 캐시를 읽으므로 "저장 안 된 입력도 찾는다"(F-287 A11)가 지켜진다

### 6.5 부팅 GC — `scheduleGc`
- `scheduleGc` 는 부팅 목록 결과(값 또는 약속)를 받는다(3.5). GC 저장소의 `list` 는 그 결과를 돌려준다. 서버면 `listAttachments`·`removeAttachment` 는 지금 그대로(`uploaded !== false` 거르기 포함)
- 캐시 먼저 셸 길: 셸 직후의 `scheduleGc()` 호출을 없애고, 뒤 맞추기의 `appStore.list()` 약속을 넘겨 **그것이 끝난 뒤** idle GC 를 예약한다. 캐시 없는 길: 이미 받은 `list` 를 넘긴다

## 13. 열린 질문

### Q1 TTL 값 — **사람 결정 필요** (기본 10분)

탭 하나가 한 시간 동안 계기(탭 신호·검색·지도)를 계속 받을 때 새로 읽기 **상한** = ⌈60 / TTL⌉ 회. 조사 보고 시나리오(문서 500·폴더 20, 목록 한 번 ≈ 529행, 탭 2)의 "다른 탭 resync + 검색·지도" 는 지금 약 8,500행/시간

| TTL | 탭당 상한(회/시간) | 탭 2 상한(행/시간) | 계기를 고르게 흩었을 때 예상(탭 2) | 다른 기기 변경이 검색·지도에 늦는 최대 |
| --- | --- | --- | --- | --- |
| 5분 | 12 | ≈ 12,700 | ≈ 16회 계기 중 ≈ 11회 → ≈ 5,800 | 5분 + 다음 열기 |
| **10분 (기본)** | 6 | ≈ 6,300 | ≈ 9회 → ≈ 4,800 | 10분 + 다음 열기 |
| 30분 | 2 | ≈ 2,100 | ≈ 4회 → ≈ 2,100 | 30분 + 다음 열기 |

- "예상" 열은 조사 보고의 계기 수(탭 신호 10 + 검색·지도 6)를 한 시간에 고르게 흩어 센 **어림**이다(재지 않았다). 실제 계기는 몰려 오므로 이보다 적을 가능성이 높다. 여기에 부팅 GC 중복 제거(≈ 1,000행/시간, 탭 2)와 이 탭 실시간 변경으로 기다리는 검색(3.4, 줄지 않음)이 더해진다
- 기본 10분 까닭: 같은 앱의 `/api/me` 재확인 간격과 같다. 5분은 계기가 잦은 사용자에게 지금보다 나빠질 수 있다(상한 12,700 > 지금 8,500)
- 30분을 고르면: 상수 하나만 바뀐다. 9장 A6·A7·A10 과 11장 `sessionRestartFlush` 고침의 `fastForward('10:01')` 이 `'30:01'` 로 바뀐다
- 10장 재측정 뒤 값을 다시 정할 수 있다 — 상수 하나라 되돌리기 쉽다

### Q2 다른 탭의 실시간 편집 본문 — **사람 결정 필요** (기본: 받아들인다)

- 사실(3.4): 실시간 편집은 `md-remote` 에도, 탭 신호에도 안 실린다. 그래서 사용자 전제 4("같은 브라우저 다른 탭 변경은 곧바로")가 실시간 본문에는 성립하지 않는다. 지금은 검색·지도를 열 때마다 서버를 부르므로 DO 스냅숏(5~30초) 뒤면 다른 탭의 실시간 편집도 보인다 → 이 명세 기본값은 **그 경우만 TTL 만큼 늦어진다**
- **기본: 받아들인다.** 까닭: ① 새 탭 메시지 종류가 필요하고, 그러면 `tabSync.ts`(`TabMessage`·`reduceClaim` — 새 종류에 `docId` 가 있으면 지금 코드는 편집권 메시지로 떨어진다)·`useTabSync.ts`·`src/storage/lockSession.ts`(메시지 판별, 그 테스트 U8)가 바뀐다. ② 같은 때 F-2057 이 BroadcastChannel 로 "한 탭만 알림 폴링" 을 설계 중이라 탭 메시지 모양을 두 명세가 따로 바꾸면 부딪친다. ③ 지금도 다른 탭의 사이드바 제목·시각은 실시간 편집을 모른다
- 다른 안 — **실시간 변경 힌트 방송**: 6.3 이 시각을 적는 같은 순간 `{ kind: 'live-changed', tabId, docId, at }` 을 보내고, 받은 탭은 자기 `liveChangedAtRef` 에 적는다 → 그 탭의 검색·지도도 3.4 처럼 서버를 기다린다. 바뀌는 것: 1장 소유에 `src/app/tabSync.ts`·`useTabSync.ts`·`src/storage/lockSession.ts`(+ 각 테스트) 추가, `reduceClaim` 이 새 종류를 무시하는 줄, e2e A11(두 탭 실시간 → B 검색이 서버를 기다림) 추가. F-2057 과 메시지 모양을 먼저 맞춰야 한다

### Q3 뒤 새로 읽기가 끝나면 열린 검색 결과를 갈아 끼우나 (기본: 안 한다)

- F-284 5.2 가 원래 적은 "캐시 결과로 먼저 그리고 `list()` 가 끝나면 인덱스를 갈아 끼운다" 를 따를 수도 있다. **기본은 안 한다**: 입력 중 결과가 바뀌면 선택 자리가 0번으로 돌아가고(F-287 결과가 바뀔 때마다 선택 0), 지도는 그래프를 다시 배치해야 해 화면이 튄다. TTL 밖 첫 열기만 낡고 다음 열기가 새것이다
- 갈아 끼우면: 소스가 "새로 읽기 끝남" 을 알리는 구독 하나가 생기고 `SearchDialog.tsx` 가 1장 소유에 들어간다(인덱스를 다시 만든다). 지도는 여전히 안 한다

### Q4 부팅 목록 자체도 TTL 로 건너뛰나 (기본: 안 한다 — 범위 밖)

- 새로 연 탭은 다른 탭이 방금 서버 목록을 읽었어도 뒤 맞추기를 한다(탭 2 부팅 ≈ 2,200행/시간 중 절반). 사용자 결정 1 의 네 곳에 없고, 공유 목록·`lastServerListAt` 이 탭 메모리라(3.1) 새 탭은 공유 목록이 없다. 하려면 공유 목록을 탭 사이에 나눠야 해 저장 키가 생긴다 — 10장 재측정 뒤 목록 ETag 와 같이 본다

### Q5 `listFolders()` 도 합치나 (기본: 안 한다)

- 사용자 결정 2 는 `list()` 만 말한다. 이 명세 뒤 `/api/folders` 가 남는 곳은 부팅·서버 `resyncFromStore`·드문 쓰기 뒤 목록이고 동시에 겹치는 일이 드물다. 합치면 4.1 과 같은 쓰기 세대 규칙을 `listFolders` 에도 둔다 — U 하나 추가

### Q6 캐시 resync 도 `/api/folders` 를 안 부르므로 폴더 삭제가 다른 기기에서 일어나면

- 다른 기기의 폴더 변경은 TTL 밖 뒤 새로 읽기에서 붙는다(문서와 같다). 기본값 그대로 — 따로 정할 것 없음을 적어 둔다
