## 3. 라우트

### 3.1 `GET /api/user-css`

- `requireUser` → `SELECT snippets, rev FROM user_css WHERE user_id = ?` (세션 사용자 id 만)
- 행 없음 → `{ snippets: [], rev: 0 }`. 있음 → 저장된 JSON 을 `snippets` 로, `rev` 그대로. 서버는 자기가 검증해 쓴 값을 다시 검증하지 않는다
- **ETag 는 `"c1-{userId}-{rev}"`**(강한 태그, 행 없음도 `rev` 0). 개요 4.3 의 `"{rev}"` 에 사용자 id 를 더한 것 — 한 브라우저에서 계정을 바꿨을 때 앞 계정의 태그가 새 계정의 같은 `rev` 에 맞아 304 가 나는 것을 서버 쪽에서 막는다(`notificationsEtag` 선례). `c1` 은 모양이 바뀔 때 올릴 판 표시
- `If-None-Match` 판정은 `worker/notifications.ts` 의 `ifNoneMatchHits` 를 import 해 쓴다(그 파일은 고치지 않는다). 맞으면 몸통 없는 304 + `ETag` + `Cache-Control: no-store`. 200 에도 `ETag` 를 붙인다
- 쓰기 관문 밖 — 막힌 계정·하루 한도를 넘긴 계정도 읽는다(`GET /api/e2ee/keys` 와 같다). 하루 카운터를 올리지 않는다

### 3.2 `PUT /api/user-css`

관문(401 → 403 `account_blocked` → 429 day → 429 minute, F-2026)을 지난 뒤, **이 순서로 첫 실패**:

| # | 조건 | 응답 |
| --- | --- | --- |
| 1 | `readJsonLimited(request, USER_CSS_MAX_BODY_BYTES)` 가 `too_large` | 413 `{ error: 'too_large', limit: 262144 }` |
| 2 | JSON 이 아님 / 몸통이 객체가 아님(`null`·배열 포함) | 400 `{ error: 'invalid' }` |
| 3 | `validateUserCssSnippets(body.snippets)` 가 `invalid` | 400 `{ error: 'invalid', field }` — `field` 는 F-2094 5.3 값 그대로(`snippets`, `snippets[3].name` …). 51개 이상도 여기(`snippets`) |
| 4 | 같은 함수가 `too_large` | 413 `{ error: 'too_large', limit: 262144 }` |
| 5 | `baseRev` 가 0 이상 정수가 아님 | 400 `{ error: 'invalid', field: 'baseRev' }` |
| 6 | batch 전 `rev` 사전 검사 실패 (아래) | 409 `{ error: 'conflict', rev: 지금 rev (행 없으면 0) }` — 하루 카운터가 오르지 않는다 |
| 7 | 쓰기 batch 의 첫 문장 `changes !== 1` (동시 쓰기) | 409 `{ error: 'conflict', rev: 다시 읽은 rev ?? 0 }` — 하루 카운터는 이미 +1 |
| — | 성공 | 200 `{ rev: 새 rev }` |

- `limit` 은 상수 `USER_CSS_MAX_TOTAL_BYTES` 에서. 몸통 상한 초과(1)도 같은 몸통을 준다 — 클라이언트가 413 하나로 "256KB 넘음" 문구를 고른다(F-2092 5.8). 제어 문자로 채운 CSS 는 합이 256KiB 안이어도 1에서 413 이 날 수 있다(m1) — 그런 CSS 는 실제로 쓰이지 않아 상한을 키우지 않는다
- **`rev` 규칙은 `handlePutE2eeKeys` 와 같다:** 행이 없고 `baseRev === 0` 이면 `rev = 1` 로 만든다(`ON CONFLICT(user_id) DO NOTHING`). 그 밖에는 지금 `rev === baseRev` 일 때만 `rev + 1` 로 조건부 `UPDATE`. 행이 없는데 `baseRev > 0`, 행이 있는데 `baseRev === 0` 은 둘 다 6번 409
- 저장값은 **검증 결과의 `snippets`**(원소마다 다섯 키만 담은 새 객체)를 `JSON.stringify` 한 것 — 모르는 키를 D1 에 남기지 않는다. 빈 배열도 정상 저장(다 지운 상태)
- 쓰기 batch 는 `[쓰기 문장, dayUsageStatement(env.DB, user.id, now)]`. 사용량 누계(`content_bytes`·`doc_count`)는 건드리지 않는다(F-2092 3.5)
- CSS 원문은 해석·필터링하지 않는다(Q1). `DELETE` 라우트는 두지 않는다 — 비우기는 `snippets: []`, 행 자체는 계정 삭제만 지운다

## 10. 열린 질문

### Q1. 서버가 저장 전에 `filterUserCss`(F-2094 토크나이저)까지 돌릴 것인가 — **기본값: 돌리지 않는다, 모양·크기 검증(`validateUserCssSnippets`)만**

- 까닭: 개요 3.5 "서버는 CSS 를 해석하지 않는다"와 4.1 "원문 저장, 컴파일은 기기마다(검사기 버전이 다를 수 있음)". 서버가 CSS 를 남에게 내주는 길이 없어(정해진 것 3) 서버 필터는 막는 것이 없다. `userCssPolicy.ts` 는 토크나이저를 import 하지 않도록 F-2094 3.3 이 정했다
- 다르게 고르면: `worker/tsconfig.json` 에 `cssTokens.ts`·`userCssFilter.ts` 가 더해지고 요청마다 최대 256KiB 토큰화 비용(F-2094 A15 예산 50ms 는 브라우저 기준, Worker CPU 한도에서 재야 함)이 든다. 빼낸 것이 있을 때 400 으로 거절할지, 걸러 저장할지(원문 보존이 깨진다)를 새로 정해야 하고, 검사기 버전이 오르면 옛 원문이 서버에서 거절되는 길이 생긴다
