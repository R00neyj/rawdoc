### 2.1 이 커밋이 끝난 시점의 상태

1. **노드에 마우스를 올리면 나머지가 180 ms 에 걸쳐 배경으로 가라앉는다.** 호버한 노드와 이웃은 같은 시간 동안 원색으로 떠오르고, 이어진 간선이 `--accent` 로 물든다
2. **마우스를 배경으로 빼면 같은 길이로 되돌아온다.** 되돌아온 그림은 F-2010 이전과 한 픽셀도 다르지 않다 (4.2)
3. **덩어리 위로 마우스를 쓸면 강조만 노드에서 노드로 옮겨 다니고 흐리기 세기는 흔들리지 않는다.** 노드 사이의 빈 곳을 스치고 지나가도 화면이 확 밝아졌다 어두워지지 않는다 (5.3)
4. `prefers-reduced-motion` 이면 지금(F-2010)과 똑같이 즉시다
5. **전환이 끝나면 렌더 루프가 스스로 멈춘다** (7장). 마지막 호버 변화로부터 180 ms 가 지나면 반드시 멈춘다
6. 설정 패널에 새 항목은 없다

**쓸 만한가 — 판단.** 쓸 만하다. F-2010 이 준 그림은 맞았고 사용자가 그것을 보고 요구한 것은 부드러움 하나다. 잃는 것은 "호버 뒤 180 ms 동안 렌더 루프가 돈다" 인데, 11장 실측대로 그 프레임들의 추가 비용이 0.005 ms 대이고 **호버가 노드 사이를 옮겨 다니는 동안에는 전환이 아예 안 돈다** — F-2010 16장 Q6 이 전환을 거절한 이유("마우스를 덩어리 위로 한 번 쓸면 사실상 멈추지 않는 루프가 된다")가 5장의 설계로 없어진다.

### 2.2 다른 소명세와의 경계 — 같은 색 경로를 여는 셋

**지금 다른 에이전트가 `specs/features/F-2008.md`(그룹 색)를 쓰고 있다.** 겹치는 코드 파일은 `MapScene.tsx` 의 색 경로(`applyColors`·`applyDepth`·`writeEdgeColors`) 하나다.

- **그룹 색이 들어오면 전환 대상이 하나 더 는다** — 노드 기본색과 간선 기본색이 그룹마다 달라진다. **이 명세의 장치는 색을 모른다** — 끝 색 둘을 고르는 곳과 계수를 곱하는 곳만 있고, 어떤 색이 기본색인지는 `applyColors()`·`edgeColorAt()` 이 정한다. 그래서 F-2008 이 기본색을 바꾸면 전환은 자동으로 따라간다. **결정은 F-2008 에 맡긴다. 이 명세는 그룹을 모른다**
- **`F-2007`(필터)도 같다.** F-2010 2.2 가 필터 흐리기를 `combineMix` 의 `dimT` 자리에 얹으라고 정해 두었고, 이 명세는 그 자리에 `× focusW` 하나를 곱할 뿐이다. 필터 흐리기에 전환을 줄지는 F-2007 이 정한다 — 필터는 호버와 달리 사용자가 명시적으로 켜는 것이라 같은 답이 아닐 수 있다
- **`F-2012`(카메라 전환)와는 `frame()` 안에서 만난다.** 7.3 이 둘이 동시에 돌 때의 규칙을 정한다

## 4. 무엇을 보간하나 — **계수 하나**다

### 4.1 상태는 숫자 하나다

**`focusW` 하나를 0 ↔ 1 로 움직이고, F-2010 의 계산식에 그 값을 곱한다.** 노드 하나마다의 규칙은 셋이다.

- 현재 문서(`centerIndex`)의 깊이 면제는 **그대로 0** — F-2004 6.2 의 규칙이고 호버와 무관하다
- 그 밖의 노드는 `depthMix(...)` 에 **초점 안이면 `1 - focusW`, 초점 밖이면 1** 을 곱한 값이 깊이 항이다. 곧 초점 노드는 `focusW` 가 1 로 갈수록 깊이 섞기에서 빠져나온다
- 흐리기 항은 **초점 안이면 0, 초점 밖이면 `MAP_HOVER_DIM × focusW`** 다
- 두 항을 `combineMix` 에 넣어 나온 `t` 로 `blendRgb(기본색, --panel, t)` 하는 것은 **F-2010 그대로다**

`focusW = 0` 이면 모든 노드가 `depthMix` 그대로에 흐리기 0 이라 **F-2010 이전(=호버 없음) 화면과 한 픽셀도 다르지 않다.** `focusW = 1` 이면 F-2010 의 식과 글자 그대로 같아진다.

**`combineMix` 가 `Math.max` 가 아니라는 것을 짚어 둔다.** `combineMix(d, m) = d + (1-d)m` 이고 두 인자 각각에 대해 연속·단조다(`mapFocus.ts` 주석의 `1 - t = (1-d)(1-m)`). `Math.max` 라는 말은 F-2010 2.2 가 **F-2007 이 필터 흐리기를 얹을 때** 쓰라고 적어 둔 규칙이고 지금 코드에는 없다. 그래서 계수만 보간해도 중간값이 꺾이거나 되돌아가지 않는다.

### 4.2 계수 보간이 색 직선 보간과 **정확히 같다** — 대수로 풀고 수치로 확인했다

`blendRgb` 는 `t` 에 대해 1차식이고, 위 두 항은 `focusW` 에 대해 1차식이다.

- 초점 밖: `t = d + (1-d)·0.85·focusW` — `focusW` 에 대해 1차
- 초점 안: `t = d·(1 - focusW)` — `focusW` 에 대해 1차

1차식을 1차식에 넣으면 1차식이다. **곧 계수를 선형으로 움직이는 것과 시작 색·끝 색을 sRGB 좌표에서 직선으로 잇는 것이 같은 색을 낸다.**

**2026-09-22 수치 확인** (Node v24.12.0, 화이트 테마 근사 `--panel` 247 / `--ink` 20, `d` 를 0·0.2·0.4·0.65 로, `focusW` 를 0~1 사이 21점으로):

| 확인 | 결과 |
| --- | --- |
| 초점 안 — 계수 보간 대 색 직선 보간의 최대 차이 | **2.84×10⁻¹⁴** (부동소수 반올림) |
| 초점 밖 — 같은 비교 | **2.84×10⁻¹⁴** |
| `focusW = 1`, `d = 0.65` 인 초점 밖 노드의 `t` | **0.9475** — F-2010 5장·U9 의 값 그대로 |
| `focusW = 1` 인 초점 안 노드의 `t` | **0** — F-2010 5장 그대로 |
| `focusW = 0`, `d = 0.65` 의 `t` | **0.65** — 오늘 그대로 |

**그래서 계수를 고른다.** 색을 직접 보간하려면 시작 색을 노드마다 얼려 두어야 하는데, `depthMix` 는 **카메라가 움직일 때마다 프레임마다 바뀐다.** 얼려 두면 전환 중에 카메라를 돌리는 순간(회전 중에도 강조가 유지된다 — F-2010 8.2) 색이 깊이를 안 따라가 어긋난다. **계수는 얼릴 것이 없다.** 덤으로 상태가 `Float32Array(nodeCount)` 가 아니라 숫자 하나다.

### 4.3 간선만은 색 보간이 필요하다 — 끝 색 둘을 `edgeClass` 로 고른다

간선 색은 `--panel`~`--ink` 무채 축 위에만 있지 않다. **`--accent` 가 축 밖이라 흐리기 계수 하나로는 못 쓴다** (F-2010 6.5 표). 그래서 간선은 **`focusW = 0` 일 때의 색과 `focusW = 1` 일 때의 색을 고른 뒤 그 둘을 보간한다.**

두 끝 색은 **F-2010 의 `edgeClass()` 를 두 번 불러** 고른다 — 새 함수를 만들지 않는다.

- **`focusW = 0` 끝**: `edgeClass(from, to, -1, centerIndex)` 가 `MAP_EDGE_CENTER` 면 `--accent`, 아니면 기본 간선 색(`edgeColorAt`). 곧 **호버가 없었을 때의 색**이다
- **`focusW = 1` 끝**: `edgeClass(from, to, focusHover, -1)` 가 `MAP_EDGE_FOCUS` 면 `--accent`, 아니면 기본 간선 색을 85% 흐린 색. 곧 **F-2010 이 정한 호버 중의 색**이다
- 호버가 현재 문서를 이긴다는 F-2010 의 규칙이 그대로 지켜진다 — 둘 다 닿는 간선은 양 끝이 모두 `--accent` 라 전환 중에도 `--accent` 다

**보간은 sRGB 좌표에서 하고 그 뒤에 선형으로 옮긴다.** 노드 쪽 `blendRgb` 가 sRGB 좌표에서 섞고(`design.md` 3.2 의 `color-mix(in srgb, …)` 와 같은 공간), CSS 전환도 sRGB 에서 보간한다. 두 곳이 어긋나면 노드와 간선이 서로 다른 속도로 흐려 보인다. **정점 버퍼에 넣기 직전에 `Color` 를 거쳐 선형으로 바꾸는 것은 F-2010 6.2 의 규칙 그대로다** — 그 순서를 바꾸면 밝고 뿌옇게 뜬다.

- 기본 간선 색 세 가지(기본·흐림·`--accent`)는 지금도 `writeEdgeColors()` 가 루프 앞에서 세 번만 만든다. **그 구조를 그대로 두고 간선마다 둘을 고르는 분기만 바뀐다**

## 5. 호버가 전환 도중에 다른 노드로 옮겨가면 — **이어 간다**

### 5.1 규칙 셋

1. **`focusW` 는 절대 처음부터 다시 시작하지 않는다.** 목표값(0 또는 1)만 바뀌고 현재 값에서 이어 간다
2. **초점 마스크(`nodeFocus`)와 `focusHover` 는 즉시 바뀐다.** 노드 A 에서 B 로 옮기면 강조 자리가 그 프레임에 바뀐다
3. **호버를 놓아도 마스크를 바로 비우지 않는다.** `focusW` 가 0 에 닿는 프레임에 비운다

3번이 중요하다. 마스크를 먼저 비우면 **직전에 초점이던 노드가 깊이 섞기 면제를 한 프레임에 잃어** 되돌아가는 도중에 한 번 툭 어두워진다. 그것은 지금 고치려는 바로 그 증상이다.

> **마스크를 늦게 비워도 색은 안 틀린다.** `focusW = 0` 이면 초점 안·밖의 식이 같은 값을 내므로(4.1) 마스크가 남아 있든 비었든 같은 그림이다. 비우는 것은 뒷정리이고, 비워야 "호버 없음" 의 0 비용 경로로 돌아간다.

### 5.2 목표값을 바꾸는 곳은 `setHover()` 하나다

`setHover()` 는 지금도 **호버한 노드가 실제로 바뀐 프레임에만** 몸통이 돈다. 거기에 더하는 일은 셋이다 — 마스크를 다시 채우고(이미 한다), 노드가 있으면 목표를 1·없으면 0 으로 두고, 전환 기준 시각을 지금으로 맞춘다. `hoverIndex` 와 `refreshLabels()` 와 커서 모양은 **한 줄도 안 바뀐다** — 이름표는 전처럼 즉시 뜨고 즉시 사라진다.

### 5.3 그래서 덩어리 위로 쓸 때 어떻게 보이나 — H289 의 뒤쪽 절반에 대한 답

| 마우스가 하는 일 | `focusW` | 화면 |
| --- | --- | --- |
| 배경 → 노드 | 0 → 1 (180 ms) | 나머지가 서서히 가라앉는다 |
| 노드 A → 노드 B (사이에 배경 없음) | **1 에 머문다. 아무것도 안 움직인다** | 강조 자리만 즉시 옮겨간다. 오늘과 같다 |
| 노드 A → 배경 30 ms → 노드 B | 1 → 0.83 → 1 | **거의 안 보이는 흔들림.** 오늘은 여기서 화면 전체가 밝아졌다 어두워지는 **깜빡임**이 난다 |
| 노드 → 배경(머문다) | 1 → 0 (180 ms) | 서서히 되돌아온다 |

**세 번째 줄이 이 설계의 값이다.** 덩어리 위를 쓸 때 노드와 노드 사이에는 반드시 배경이 끼고, 오늘은 그 몇 프레임마다 흐리기가 통째로 꺼졌다 켜진다. 전환을 넣으면 그 사이에 `focusW` 가 30 ms × (1/180) ≈ 0.17 만큼밖에 못 떨어져 **사실상 안 보인다.**

**노드 → 노드 강조 이동을 전환하지 않는 이유 둘.**

- **덩어리가 어느 것을 가리키는지 흐려진다.** 노드마다 따로 세기를 들고 가면 빠르게 쓸 때 반쯤 밝은 무리가 여러 개 남는다. 호버 초점의 쓸모가 "지금 이 노드가 무엇과 이어져 있나" 하나인데 그 답이 둘 이상 보이면 못 읽는다
- **F-2010 16장 Q6 이 전환을 거절한 근거를 되살린다.** 노드마다 세기를 두면 호버가 바뀔 때마다 전환이 시작돼 **쓰는 내내 렌더 루프가 안 멈춘다.** 지금 설계는 목표가 안 바뀌므로 루프가 한 프레임만 돌고 멈춘다 (7장)
- 반대쪽을 고르면 무엇이 드는지는 17장 Q2, 눈으로 보는 판정은 13.3 H-b

## 6. 길이와 곡선

### 6.1 180 ms — `design.md` 4장의 값을 코드가 이미 쓰고 있다

`design.md` 4장 `전환` 행은 "150~200 ms" 범위와 "색은 `--ease-out`" 을 적어 두었다. **그 범위가 코드에서 실제로 서 있는 값은 하나다.**

| 토큰 | 값 | 쓰이는 곳 (2026-09-22 `grep` 실측) |
| --- | --- | --- |
| `--transition-fast` | **`180ms var(--ease-out)`** | `var(--transition-fast)` 를 직접 쓰는 줄 **20** (`app.css`·`map.css`·`frontmatter.css`·`image.css`·`wikilink.css`) |
| `--transition-colors` | 위 토큰으로 7개 속성을 묶은 것 | `var(--transition-colors)` 를 쓰는 줄 **44** |

**`--transition-colors` 는 `tokens.css` 주석이 "색이 바뀌는 모든 조작 요소·툴팁이 참조하는 공용 전환" 이라고 적은 바로 그 줄이고, 그 길이가 180 ms 다.** 지도 호버도 "호버로 색이 바뀌는 조작 요소" 라 같은 길이를 쓴다. 150 이나 200 을 새로 고르면 **화면의 다른 호버와 지도만 속도가 다르다.** **`map.css` 자체가 이미 그 토큰을 쓴다** — 지도 설정 패널의 여닫기가 180 ms 다(F-2005, 사람 확인 H273). 같은 화면 안에서 패널은 180, 호버는 150 이 될 이유가 없다.

**길이는 토큰이 아니라 `MapScene` 쪽 상수다.** `--transition-fast` 는 `180ms var(--ease-out)` 이라는 **단축 속성**이라 길이만 뽑아 쓰는 토큰이 저장소에 없다. `F-2012` 가 `CAMERA_TWEEN_MS = 240` 을 같은 이유로 상수로 둔 전례를 따른다. 다만 이 값은 단위 테스트가 읽어야 해서 `mapFocus.ts` 에 `MAP_FOCUS_FADE_MS` 로 내보낸다 (9장). **색 hex 와 달리 시간 상수는 불변조건의 대상이 아니다** (`CLAUDE.md` "Invariants" 는 제품 이름 문자열과 색 hex 만 묶는다).

- 다른 값을 고르면 어떻게 되는지는 17장 Q1. 느낌 판정은 13.3 H-a

### 6.2 곡선은 `--ease-out`

`design.md` 4장이 "색·바탕·테두리·그림자·투명도는 `--ease-out`" 이라고 못 박았고 `--ease-spring`·`--ease-pop` 은 y 가 1 을 넘어 **색이 목표를 지나쳤다 돌아온다** — 흐리기 85% 를 넘어서면 배경보다 더 옅어졌다 돌아오는 그림이 된다. 쓸 이유가 없다.

### 6.3 `--ease-out` 을 푸는 것은 **F-2012 가 만든 함수를 그대로 부른다**

`F-2012` 5.2 가 이미 같은 문제를 풀었다 — 제어점을 JS 에 적으면 `tokens.css` 와 두 벌이 되고, `1-(1-t)³` 같은 닫힌 식으로 대신하면 곡선이 달라진다(F-2012 실측: 500 px 이동에서 최대 18.0 px 어긋남). 그래서 **토큰을 프로브로 읽어 3차 베지어를 푸는 함수 둘을 `src/lib/mapCamera.ts` 에 만든다.**

| F-2012 가 만드는 것 | 이 명세가 쓰는 법 |
| --- | --- |
| `parseCubicBezier(text)` | **그대로 부른다.** 모자란 것이 없다 |
| `easeAt(curve, t)` | **그대로 부른다.** `curve` 가 `null` 이면 선형이라는 계약까지 그대로 쓴다 |
| `buildScene()` 안의 `easeCurve` 상수(`--ease-out` 을 `.map-probe` 에서 한 번 읽어 푼 것) | **그 변수를 그대로 읽는다. 프로브를 두 번 읽지 않는다** |
| `tweenPose` | 안 쓴다 — 카메라 자세용이다 |

- **`easeCurve` 를 나눠 쓰는 것이 옳은 이유**: 같은 토큰을 같은 프로브에서 두 번 읽을 이유가 없고, 둘 중 하나만 고치는 사고가 안 난다. `buildScene()` 안의 같은 스코프이고 `frame()` 은 `buildScene()` 이 끝난 뒤에만 도므로 선언 순서 문제도 없다
- **이 명세가 덧붙이는 것은 진행도를 움직이는 `stepFade()` 하나뿐이다** (9장). F-2012 의 트윈 상태(`beginTween`·`stepTween`·`cancelTween`)는 카메라 자세 전용이라 재사용할 수 있는 모양이 아니다 — 시작 자세를 얼리고 `OrbitControls` 의 감쇠를 끄고 `selfDriven` 을 세우는 것이 전부 카메라 얘기다
- **F-2012 의 코드를 옮기지 않는다.** `mapCamera.ts` 는 F-2012 소유로 두고 **부르기만** 한다 (1.1)

### 6.4 `prefers-reduced-motion` 이면 즉시

`MapScene` 의 `buildScene()` 은 이미 `reduced` 플래그를 들고 있다(`window.matchMedia('(prefers-reduced-motion: reduce)')`). **`reduced` 면 `setHover()` 가 목표값을 세우는 대신 `focusW` 를 목표값으로 바로 밀어 놓는다.** 그러면 전환 단계가 아예 안 돌고 F-2010 과 글자 그대로 같은 동작이 된다.

- **`tokens.css` 의 `@media (prefers-reduced-motion: reduce)` 블록은 안 건드린다.** 거기 있는 `--transition-fast: 0ms` 는 CSS 전환용이고, 캔버스 안은 CSS 가 못 닿는다
- 값은 `buildScene()` 때 한 번 읽는다. 지도를 열어 둔 채 OS 설정을 바꾸는 경우는 F-2002 이후 전부 같은 취급이다

## 7. 루프 수명 — 반드시 멈춘다

### 7.1 지금 루프

`frame()` 은 맨 앞에서 `dirty` 를 내리고, 맨 끝에서 **`layout.isSettled() && !dirty`** 면 `renderer.setAnimationLoop(null)` 로 스스로 멈춘다. `requestDraw()` 는 `dirty` 를 세우고 꺼져 있으면 다시 켠다. `setHover()` 는 이미 `requestDraw()` 를 부른다.

### 7.2 전환은 `dirty` 하나로 이어 간다 — 새 표시가 필요 없다

- **시작**: `setHover()` 가 목표를 바꾸고 `requestDraw()` 를 부른다 (지금도 부른다)
- **이어 감**: `frame()` 안의 전환 단계가 `focusW` 를 옮기고 **아직 목표에 못 닿았으면** `dirty` 를 세운다. `frame()` 맨 앞의 `dirty = false` 보다 뒤라 그 프레임 끝의 정지 판정을 통과하지 못한다
- **멈춤**: 목표에 닿은 프레임에서는 `dirty` 를 **안 세운다.** 그 프레임이 끝 색을 그리고, 배치가 멈춰 있으면 그대로 루프가 꺼진다. **끝나는 자리가 결정적이다**
- **시각은 `performance.now()` 로 잰다.** F-2012 6.2 와 같은 이유다 — `frame()` 이 인자를 안 받고, 받게 바꾸면 그 하나 때문에 시그니처가 바뀐다
- **영영 안 꺼지는 경우가 없다.** 진행도는 실시간 기반이라 180 ms 가 지나면 반드시 목표에 닿는다. 탭이 백그라운드로 가 rAF 가 멈추면 전환도 멈췄다가, 돌아오면 경과가 이미 180 ms 를 넘어 **한 프레임에 끝난다**
- **`dispose()` 에 새 줄이 없다.** 타이머를 안 쓰고 `dispose()` 가 이미 `setAnimationLoop(null)` 을 부른다

### 7.3 카메라 전환(F-2012)과 동시에 돌 때 — 누가 루프를 붙잡고 있나

**`dirty` 는 "누구든 한 프레임 더 원한다" 는 OR 다.** 내리는 곳은 `frame()` 맨 앞 한 곳뿐이고, 세우는 쪽은 서로를 모른다.

- 카메라 전환은 `stepTween()` 이 세우고, 호버 전환은 이 명세의 단계가 세운다. **둘 중 하나라도 진행 중이면 루프가 돈다. 둘 다 끝난 프레임에 멈춘다**
- **둘 사이에 우선순위를 두지 않는다.** 겹치는 상태가 없다 — 카메라 전환은 `controls.target`·`camera.position` 을 쓰고, 호버 전환은 인스턴스 색과 정점 색 버퍼를 쓴다
- **순서는 정한다. 호버 전환 단계는 카메라 분기 뒤, `writeEdgeColors()` 앞이다.** 간선 색과 노드 색이 **그 프레임의 `focusW`** 로 써져야 한 프레임 늦지 않는다
- **카메라 전환이 취소돼도(사용자가 손을 대면, F-2012 7.2) 호버 전환은 안 끊긴다.** 회전을 시작하면 호버 갱신이 얼지만(8.1) 진행 중인 전환은 그대로 끝나는 것이 맞다

## 8. 회전·메뉴·경계

### 8.1 회전을 시작하는 순간 전환이 진행 중이면 — **그대로 끝까지 간다**

F-2004 7.6 이 `onPointerMove` 에서 버튼이 눌려 있으면 호버를 갱신하지 않게 해 두었고(F-2010 8.2 가 그 줄을 그대로 둔다고 못 박았다), **이 명세도 그 줄을 안 건드린다.** 곧 회전을 시작해도 **목표값이 안 바뀌므로** 전환은 하던 대로 목표까지 간다.

- **얼리면 더 나쁘다.** 회전은 몇 초씩 이어지는데 그동안 화면이 반쯤 흐려진 채 멈춰 있게 된다. 어느 쪽 끝도 아닌 그림이 오래 남는 것이 제일 읽기 나쁘다
- **회전 중에는 어차피 매 프레임이 그려지므로**(`OrbitControls` 의 `change` → `requestDraw`) 전환이 늦어지지도 않는다
- 캔버스 밖까지 끌고 나갔다 놓으면 그때 `pointerleave` 가 와서 `setHover(null)` 이 불리고 되돌아가는 전환이 시작된다 — F-2010 8.1 이 소스로 확인한 동작 그대로다

### 8.2 나머지 경계

| 상황 | 어떻게 되나 |
| --- | --- |
| 노드 메뉴가 떠 있는 동안 | 호버 갱신이 멈추는 것은 지금과 같다. 진행 중이던 전환은 끝까지 간다 |
| 터치 | 호버가 없어 전환도 없다. 지금과 같다 |
| 전환 중에 문서가 열림(노드 클릭) | 지도가 언마운트되고 `dispose()` 가 루프를 끈다. 정리할 타이머가 없다 |
| 전환 중에 그래프가 바뀜(문서 추가·삭제) | 장면을 다시 지으므로 `focusW` 가 0 인 새 장면으로 시작한다 |
| 전환 중에 테마가 바뀜 | `applyColors()` 가 기본색을 다시 읽고 `edgeColorDirty` 를 세운다. 다음 프레임이 새 기본색에 같은 `focusW` 를 곱한다 — 어긋나는 데가 없다 |
| 전환 중에 `선 두께` 를 끔 | 위와 같다. 기본 간선 색이 바뀌고 전환은 이어진다 |
| 노드 0개·간선 0개 | `applyDepth()`·`writeEdgeColors()` 가 지금도 곧바로 돌아온다. 전환 단계는 돌지만 보이는 것이 없고 180 ms 뒤 멈춘다 |
| 노드 1개(첫 실행 `사용법`) | 호버하면 그 노드만 초점이고 흐릴 대상이 없다. 전환은 돌되 화면이 거의 안 바뀐다 |

**접근성.** 새 조작·새 포커스 대상·새 문구가 0개다. 캔버스의 `aria-label`(문서 수·연결 수)은 안 바뀐다 — 전환은 보이는 것에만 있다. `prefers-reduced-motion` 은 6.4 로 덮인다.

## 9. `src/lib/mapFocus.ts` 에 더하는 계약

테스트 환경이 `node` 라 three 도 DOM 도 import 하지 않는 순수 모듈이어야 단위 테스트가 된다 — F-2010 3장이 이 파일을 만든 이유 그대로다. **새 파일을 만들지 않는다.** 호버 초점의 값과 판단이 이미 여기에 모여 있다.

```ts
/** 호버 초점이 들어오고 나가는 데 걸리는 시간. design.md 4장 `전환` 의 150~200ms 안이고
 *  tokens.css `--transition-fast`(180ms)와 같은 값이다 (F-2013 6.1) */
export const MAP_FOCUS_FADE_MS = 180

/** 선형 진행도 p(0~1)를 target 쪽으로 dtMs 만큼 옮긴다. 곡선은 호출부가 easeAt 으로 따로 씌운다 */
export function stepFade(p: number, target: 0 | 1, dtMs: number, durationMs: number): number
```

**`stepFade` 의 규칙.**

- 돌려주는 값은 언제나 `[0, 1]` 안이고, `target` 을 지나치지 않는다 — 넘으면 `target` 으로 자른다
- `dtMs` 가 유한수가 아니거나 0 이하면 `p` 를 그대로 돌려준다. **되돌리지 않는다** — 첫 프레임의 시각 차가 0 일 수 있다
- `durationMs` 가 유한수가 아니거나 0 이하면 **`target` 을 바로 돌려준다.** `MAP_FOCUS_FADE_MS` 를 0 으로 바꾸는 것만으로 전환이 꺼진다
- `p` 가 유한수가 아니면 `target` 을 돌려준다 — 망가진 상태에서 벗어나는 쪽이 안전하다
- **곡선을 여기서 씌우지 않는 것이 핵심이다.** 진행도를 선형으로 들고 있어야 목표가 뒤집혔을 때 **같은 곡선을 거꾸로 되짚어** 값이 튀지 않는다. 곡선을 씌운 값을 상태로 들면 방향이 바뀔 때마다 기울기가 어긋난다 (5.1 의 "이어 간다")

**내보내는 것은 위 둘이 전부다.** `MAP_HOVER_DIM`·`MAP_EDGE_*`·`fillNodeFocus`·`edgeClass`·`combineMix` 는 한 글자도 안 고친다.

## 10. `src/app/MapScene.tsx` 에서 바뀌는 곳

**F-2012 가 `frame()` 의 카메라 분기를 통째로 갈아 끼우므로 그 뒤에 얹는다** (17장 Q5). 아래는 `db167f1` 의 작업 트리 기준이고, 가리키는 것은 전부 함수 이름이다.

| 어디 | 무엇 |
| --- | --- |
| import | `mapFocus` 에서 `MAP_FOCUS_FADE_MS`·`stepFade` 를 더 가져온다. `mapCamera` 에서 `easeAt` 을 가져온다 (F-2012 가 만든다) |

| `setHover()` | 마스크를 채우는 지금 줄 뒤에 **목표값과 기준 시각을 세우는 두 줄.** `reduced` 면 `focusW` 를 목표로 바로 민다 (6.4). `hoverIndex`·`refreshLabels()`·커서 줄은 그대로다 |

| `applyDepth()` | 깊이 항과 흐리기 항 두 줄이 `focusW` 를 곱하는 모양으로 바뀐다 (4.1). 나머지는 그대로다 |

| `frame()` | 카메라 분기 뒤·`writeEdgeColors()` 앞에 전환 단계 한 줄 (7.3) |

**늘지 않는 것도 못 박는다.**

- **`useEffect` 도 리스너도 지금 그대로다.** 전환은 prop 이 아니라 호버에만 달려 있다
- **`dispose()` 에 새 줄이 없다** (7.2)
- **`readTheme()` 이 읽는 토큰이 여섯 그대로다.** 곡선은 F-2012 의 `easeCurve` 를 나눠 쓴다 (6.3)
- **`refreshLabels()`·`placeLabels()`·`hitAt()`·`applyColors()` 의 몸통은 한 줄도 안 바뀐다**

## 11. 비용 — 직접 쟀다

### 11.1 전환이 도는 동안 프레임마다 더 드는 일

**2026-09-22 실측** (Node v24.12.0, 이 PC. 워밍업 뒤 5회 중 중앙값, 한 번 = 전체 배열 한 바퀴).

| 무엇 | 오늘 | 전환판 | 차이 |
| --- | --- | --- | --- |
| `writeEdgeColors()` 산술, 간선 **2,000** | 0.00992 ms | **0.01546 ms** | +0.0055 ms |
| `applyDepth()` 색 계산, 노드 **1,000** | 0.00316 ms | **0.00363 ms** | +0.0005 ms |

- **간선 쪽이 커 보이는 것은 `edgeClass` 를 두 번 부르고 채널마다 보간을 하기 때문**이고, 그래도 **간선 2,000개에 0.0055 ms** 다
- **F-2010 10장이 같은 루프를 설치된 Chrome 에서 잰 값이 0.0075 ms** 였다(GPU 업로드 표시까지 포함). Node 에서 잰 배율 1.56 을 그대로 적용하면 브라우저 기대값은 **0.0117 ms** 다. 이 명세가 그 값을 브라우저에서 다시 재지는 않았다 — 구현할 때 G6 와 함께 확인한다 (14장)
- **노드 쪽이 싼 이유**: `applyDepth()` 는 오늘도 프레임마다 전체를 돈다. 더하는 것은 곱셈 두 번이다

### 11.2 진짜 비용은 **깨어 있는 프레임 수**다

전환이 없으면 호버 한 번에 한두 프레임만 그린다. 전환이 있으면 180 ms 동안 계속 그린다.

**2026-09-22 실측** (설치된 Chrome, 1600×900, 문서 24개·연결 48개의 실제 빌드. `WebGL2RenderingContext.prototype.drawElementsInstanced` 를 가로채 프레임 시각을 기록):

| 무엇 | `prefers-reduced-motion` | 기본 |
| --- | --- | --- |
| 지도를 열고 배치가 멈출 때까지 | **352 ms · 2 프레임** | **2,395 ms · 301 프레임** |
| **호버 한 번(배경 → 노드) 뒤에 그려진 프레임** | **2 프레임 · 마지막 그리기까지 10 ms** | **2 프레임 · 마지막 그리기까지 3 ms** |

- **오늘의 기준선이 2 프레임이다.** 전환을 넣으면 180 ms 동안 60 Hz 에서 약 11 프레임, 144 Hz 에서 약 26 프레임이 된다. 13.2 의 e2e 문턱이 이 간격 위에 선다
- **전환 한 번이 쓰는 총 시간은 배치를 한 번 도는 것보다 훨씬 작다.** 위 표대로 지도를 여는 데만 301 프레임을 이미 그린다
- **덩어리 위를 쓸 때는 전환이 아예 안 돈다** (5.3). 목표값이 안 바뀌므로 `focusW` 가 1 에 머물고, `frame()` 은 지금처럼 호버가 바뀐 그 한 프레임만 돈다
- **최악의 경우는 사용자가 노드 경계를 계속 들락거리는 것**이고, 그때도 마지막 호버 변화로부터 180 ms 뒤에는 반드시 멈춘다 (7.2)

### 13.2 e2e — `e2e/map.spec.js` 뒤에 `F-2013 A1~A5`

**전환을 보는 탐침은 "렌더러가 몇 프레임을 더 그렸나" 다.** 캔버스 픽셀은 `preserveDrawingBuffer` 가 없어 페이지 안에서 못 읽고(F-2010 12.2 가 확인), Playwright 스크린샷은 한 장에 수십 ms 가 걸려 180 ms 안을 못 쪼갠다. 대신 **그리기가 여러 프레임에 걸쳐 이어졌다가 멈춘다**는 것은 정확히 측정된다.

```js
// 드로우 콜을 가로채 프레임 시각을 모은다. three 는 InstancedMesh 하나를 drawElementsInstanced 로
// 그리므로 호출 한 번이 곧 한 프레임이다 (F-2013 13.2). 제품 코드에는 아무 고리도 넣지 않는다
async function trackFrames(page) {
```

## 17. 열린 질문 / 사람 결정 필요

**사람이 꼭 볼 것은 Q1 하나다.** 나머지 넷은 코드·실측으로 기본값이 서 있고, 다른 쪽을 골랐을 때 무엇이 달라지는지 적었다.

### Q1. 전환 길이 — **기본: 180 ms** (사람 결정 필요)

**사용자 지시는 "`design.md` 4장의 150~200 ms 를 따르되 150 과 200 중 하나를 근거를 대고 고르라" 였다. 근거를 대고 그 사이의 180 을 고른 것이라 사람이 한 번 봐야 한다.**

- 180 을 고른 이유는 **그 값이 이미 저장소에 있기 때문**이다. `--transition-fast: 180ms var(--ease-out)` 이 직접 20줄, `--transition-colors` 를 거쳐 44줄에서 쓰이고 **`map.css` 도 그중 하나다**. `tokens.css` 주석이 그 줄을 "색이 바뀌는 모든 조작 요소·툴팁이 참조하는 공용 전환" 이라고 부른다. **지도 호버만 다른 속도로 도는 것이 규칙을 따르는 것보다 낫다고 볼 근거를 못 찾았다**
- **150 을 고르면**: 앱의 다른 호버보다 지도만 30 ms 빠르다. 덩어리 위를 쓸 때 반응이 조금 더 붙어 보이고, 노드 사이 틈을 스칠 때의 흔들림이 0.17 → 0.20 으로 조금 커진다 (5.3). 상수 하나만 바뀐다
- **200 을 고르면**: 부드러움이 가장 크고 `design.md` 범위의 위 끝이다. 대신 루프가 깨어 있는 시간이 11% 늘고, 호버 강조는 마우스를 따라 즉각 읽혀야 한다는 F-2010 8.1 의 판단과 가장 멀다
- **어느 쪽을 골라도 코드 변경은 `MAP_FOCUS_FADE_MS` 한 줄이고 U16 의 범위 검사가 셋 다 통과한다.** e2e 문턱(A1 의 100 ms 하한)도 셋 다 여유가 있다

### Q2. 노드 → 노드 이동도 전환할까 — **기본: 안 한다**

5장. 지금 설계는 **세기 하나를 전역으로** 들고 마스크만 즉시 바꾼다. 그래서 목표값이 안 바뀌는 사이(= 덩어리 위를 쓰는 내내) 전환이 아예 안 돌고, F-2010 16장 Q6 이 전환을 거절한 근거가 사라진다.

**다른 쪽을 고르면**: 노드마다(그리고 간선마다) 세기를 따로 들어야 한다 — `Float32Array(nodeCount)` 와 간선 쪽 상태가 생기고, `stepFade` 가 배열을 도는 함수가 된다. 얻는 것은 A 의 이웃이 서서히 꺼지고 B 의 이웃이 서서히 켜지는 그림이고, 잃는 것 셋이다: (1) **호버가 바뀔 때마다 전환이 시작돼 쓰는 내내 루프가 안 멈춘다** — 11.2 의 "전환이 아예 안 돈다" 가 "쉬지 않고 돈다" 로 뒤집힌다, (2) 빠르게 쓸 때 반쯤 밝은 무리가 여러 개 남아 **어느 노드를 가리키는지 흐려진다**, (3) 비용이 프레임당 0.0055 ms 에서 노드·간선 배열을 도는 값으로 는다. **먼저 기본값으로 만들고 H-b 로 눈으로 본 뒤, 그래도 필요하면 별도 번호로 간다.**

### Q3. 이름표도 같이 흐려질까 — **기본: 안 한다**

3장. `.map-label` 에는 지금 `transition` 이 한 줄도 없고, React 가 붙였다 떼며 `[hidden]` 이 `display: none` 이라 CSS 전환이 안 걸린다. 넣으려면 전환이 끝날 때까지 DOM 을 남겨 두고 `refreshLabels()` 와 `place()` 를 손봐야 하는데 **F-2010 사용자 결정 1 이 이름표를 건드리지 말라고 못 박았다.**

**다른 쪽을 고르면**: `MapLabels.tsx`(F-2004 소유)와 `map.css` 가 소유표에 들어오고, 이름표가 사라지는 시점이 호버 해제보다 180 ms 늦어진다. **그러면 `F-2004 A1~A9`·`F-2010 A2·A4` 가 `.map-label:not([hidden])` 개수를 곧바로 세고 있어 깨진다** — 기존 e2e 를 고쳐야 한다. 이름표만 늦게 남는 것이 오히려 어색한지는 H-c 가 본다.

### Q4. 전환 길이를 설정으로 뺄까 — **기본: 안 뺀다**

`md.mapView` 에 축을 더하면 `mapPrefs.ts`(F-2005 소유)·패널·저장 검증이 전부 는다. 180 ms 는 앱 전체가 이미 쓰는 값이고, 움직임을 줄이고 싶은 사람에게는 `prefers-reduced-motion` 이라는 표준 통로가 있다 (6.4). **다른 쪽을 고르면** `표시` 묶음에 슬라이더가 하나 늘고 F-2005 소유 파일을 열어야 한다 — 이 명세의 범위를 넘는다. F-2012 16장 Q4 가 카메라 전환 길이에 대해 내린 결론과 같다.

### Q5. `F-2012` 보다 먼저 구현할 수 있나 — **기본: 못 한다. 뒤에 온다**

이유 둘이다. (1) `parseCubicBezier`·`easeAt` 이 F-2012 가 만드는 것이고, 여기서 따로 만들면 **같은 베지어 풀이가 두 벌이 된다** — `CLAUDE.md` 가 경계하는 "두 벌은 갈라진다" 그대로다. (2) F-2012 가 `frame()` 의 카메라 분기를 통째로 갈아 끼우므로 이 명세가 먼저 그 함수에 줄을 넣으면 충돌한다.

**정말 먼저 가야 한다면**: 곡선 없이 **선형**으로 먼저 넣을 수 있다. `easeAt` 자리에 항등을 쓰면 되고 `stepFade` 는 그대로다. 그러면 `design.md` 4장의 "색은 `--ease-out`" 을 어기므로 **F-2012 가 들어온 뒤 한 줄을 되돌리는 후속 작업이 반드시 남는다.** 그 빚을 지느니 순서를 지키는 편이 낫다.
