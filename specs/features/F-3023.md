## 3. 보내기
### 3.1 `trashDoc`
판정: `getDocAccess` 없음 → `not_found` · `!allowE2ee` 이고 금고 → `e2ee_doc` · 소유자 아님 → `forbidden`. 그다음 batch 하나: `UPDATE docs SET deleted_at, deleted_by, deleted_path WHERE id AND owner_id AND deleted_at IS NULL` + `dayUsageStatement`. 0행(끼어든 보내기)이면 `not_found`. 일반 문서면 `notifyTrashed(env, ctx, [id])`. 사용량 누계·초대·링크·묶음·댓글·GitHub 행은 건드리지 않는다(F-3021 결정 3·4)
### 3.2 `trashFolder` (`contents=delete-all` 의 뜻)
- 판정: `getOwnedFolder` 없음 → `not_found` · `!allowE2ee` 이고 `folderSubtreeHasE2ee` → `e2ee_folder`(아무것도 안 바꿈)
- batch 하나: ① 하위 폴더(대상 포함) 안의 **살아 있는** 문서를 한 문장으로 보내기 — 폴더마다 `deleted_path` 가 달라 `[폴더 id, 경로]` JSON 하나를 바인딩해 `json_each` 로 고른다 ② 지운 폴더의 링크·초대·요청(`targetShareCleanupStatements('folder', …)` 지금 그대로) ③ `folder_id` 가 지운 폴더인 **알림만**(문서 쪽 알림·댓글은 남김) ④ `DELETE FROM folders` ⑤ `dayUsageStatement`. 바인딩은 문장당 100 미만
- 이미 휴지통이던 문서는 그대로(경로·시각 유지, 복원 때 최상위). 그 뒤 보낸 일반 문서를 `updated_at` 내림차순으로 `notifyTrashed`(앞 20개, 나머지는 방의 다음 D1 확인 — F-3021 Q1 승인)
- 결과 `{ ok, id, parentId: 대상의 parent_id, docs: 이번에 보낸 수, folders: 지운 폴더 수(대상 포함) }`
### 3.3 `closeTrashed()` (DocRoomCore)
이미 `gone` 이면 끝. 불러온 방이면 `runFlush` 를 **느린 날 우회·점검 생략**으로 한 번(마지막 편집을 휴지통 행에 — `UPDATE_SQL` 은 휴지통 행에도 쓴다), 그다음 `roomTrashed()`. 불러오지 않은 방(hibernation)은 메모리에 미저장 편집이 없으니 곧바로 `roomTrashed()`. 저장소·알람은 지우지 않는다(F-3021 5장)
### 3.4 `src/lib/trash.ts` 추가 — `trashPathOf(folders: FolderLike[], folderId: string | null): string | null`(뿌리→잎 이름을 `'/'` 로, 없는 폴더·`null` 이면 `null`), `trashPurgeAt(deletedAt: number): number`(+ `TRASH_RETENTION_DAYS` 일 ms)
`trashActorForMcp`: 제어 문자(`\p{Cc}`) 제거 → trim → **코드 포인트 40개**에서 자름. 비면 `'mcp:'`(화면은 `연결된 앱에서 지움`, F-2145)

## 4. 라우트 (`/api` 만, 소유자 본인만, `isWriteRoute` 그대로 — 셋 쓰기·GET 아님)
| 라우트 | 성공 | 규칙 |
| --- | --- | --- |
| `GET /api/trash` | 200 `TrashItem[]` | 내 휴지통 전부, `deletedAt` 내림차순(같으면 id). 금고 행은 `title: ''`·`e2ee: true`. `purgeAt = trashPurgeAt(deletedAt)` |
| `POST /api/trash/:id/restore` | 200 `{ id, folderId }` | `folder_id` 폴더가 있고 내 것이고 금고 여부가 문서와 같으면 그대로, 아니면 `null`. `deleted_*` 비움 + `dayUsageStatement` 한 batch, 조건 `deleted_at IS NOT NULL`. `updated_at`·`version` 그대로 |
| `DELETE /api/trash/:id` | 204 | 휴지통 행 확인 뒤 `deleteDocRows`(금고 문서도 — F-2145 의 금고 초기화가 쓴다) |
| `DELETE /api/trash` | 200 `{ docs }` | `purgeTrashStatements`(범위: 내 휴지통 전부, 하루 +1) batch 하나, `docs` = `docs` DELETE 의 changes. 0개여도 200·하루 +1. 뒤에 `runPurgeJobs(PURGE_CALLS_ON_DELETE)` 를 조용히 |
- 휴지통에 없는 id(살아 있음·남의 것·없음)는 404 `not_found`. 401 은 `requireUser` 그대로
- `purgeTrashStatements(db, ownerId, scope, now, countWrite)`: 문서 집합을 **하위 질의 하나**로 모든 문장이 같이 써서 문서 수와 무관하게 **16문장**(사용량 1·댓글 4·링크·초대·요청 6·`purge_jobs` room 1(일반 문서만)·묶음·GitHub 3·`docs` 1). 범위 둘: 내 휴지통 전부 / 만료분(`deleted_at < 기준`, `deleted_at, id` 순 99개). `countWrite` 거짓이면 사용량 문장이 하루 쓰기를 올리지 않는다. 한 batch 라 하위 질의는 모든 문장에서 같은 행을 본다

## 5. 30일 만료 — `expireTrash(env, now)`
기준 `now − TRASH_RETENTION_DAYS 일`. 가장 오래된 만료 행의 소유자 한 명을 `SELECT` 1번 → 없으면 끝, 있으면 그 소유자의 만료분 99개까지 `purgeTrashStatements(countWrite: false)`. `scheduled` 10분 갈래는 `waitUntil` 하나 안에서 `expireTrash` → `runPurgeJobs(PURGE_CALLS_ON_CRON)` 차례(만료가 던져도 로그 뒤 비우기는 돈다 — 방금 넣은 room 작업을 같은 호출이 비운다). **예산**: 무료 호출당 50(F-2038 m5, D1 은 batch 안 문장마다 셈) ≥ 만료 17 + 비우기 D1 4 + 방·R2 호출 → `PURGE_CALLS_ON_CRON = 29`. 몰리면 늦어진다(F-3021 3장, 받아들임)
