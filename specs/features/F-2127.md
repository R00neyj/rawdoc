# F-2127 이미지 원문을 표준 마크다운으로

작성일: 2026-10-04
상태: 승인(2026-10-04, 열린 질문 3개 모두 기본값 — 상시 지시 "결정할 것이 없으면 바로 구현"에 따른 승인). 2026-10-04 grill 에서 사용자 승인한 방향(아래 "정해진 것")을 소명세로 옮긴 것. GitHub 연동 개요 F-3013(동시 작성 중)이 이 문법과 6장 확장 지점을 전제로 한다. 열린 질문 3개(9장) — 모두 기본값이 있다

## 정해진 것 (사용자 2026-10-04, 바꾸지 않는다)

1. 새로 넣는 이미지는 `![alt|center|300](attachments/{id}.{ext})` 한 줄. 정렬은 alt 뒤 `|left|center|right`, 너비는 `|N`(옵시디언 너비 표기). `left` 가 기본이라 왼쪽이면 정렬 조각을 적지 않는다
2. 정렬 버튼·끌어 크기 조절·삭제(F-157·F-218)는 새 문법에서도 그대로 — 바꾸면 alt 의 `|` 조각만 고친다
3. 기존 `<div align><img>` 3줄 블록은 이주하지 않는다. 두 문법 모두 그림으로 그린다
4. 화면 모양은 지금 이미지 블록과 같다
5. GitHub 에서 정렬·너비가 무시되고 원래 크기·왼쪽으로 보이는 것을 받아들인다
6. 사용자가 친 `![]()` 는 바이트를 바꾸지 않는다. 정렬·너비 조작을 할 때만 alt 를 고친다

## 2. 문법 — `src/lib/imageMarkdown.ts`

```ts
export type ParsedImageLine = {
  alt: string          // 정렬·너비 조각을 뗀 나머지. 원문 글자 그대로(역슬래시 이스케이프를 풀지 않는다)
  align: ImageAlign    // 조각이 없으면 'left'
  width: number | null
  url: string          // 괄호 안 주소. <> 는 벗기고 %XX 는 풀지 않는다
}
export type ImageTarget = { id: string; ext: ImageExt }
export type ResolveImagePath = (path: string) => ImageTarget | null
export function parseImageLine(text: string): ParsedImageLine | null
export function imageLineTarget(parsed: ParsedImageLine, resolveImagePath?: ResolveImagePath): ImageTarget | null
export function buildImageLine(p: { id: string; ext: ImageExt; alt: string; width?: number | null; align?: ImageAlign }): string
export function imageLineAlignChange(lineText: string, lineFrom: number, align: ImageAlign): CodeMirrorChange | null
export function imageLineWidthChange(lineText: string, lineFrom: number, width: number): CodeMirrorChange | null
```

### 2.1 한 줄 해석 `parseImageLine`
- 입력은 문단 글자 하나. 앞뒤 공백·탭을 떼고 **줄바꿈이 없어야** 한다
- 모양: `![` alt `](` 주소 [공백 + `"제목"`] `)` 가 글자 전체. alt 에 `[` `]` 줄바꿈이 없다. 주소는 `<…>`(안에 `<` `>` 없음) 또는 공백·괄호 없는 글자 1자 이상. 제목은 있어도 되고 해석에 쓰지 않는다(원문에 남는다). 그 밖은 `null`
- **alt 의 `|` 조각** — `alt.split('|')` 를 뒤에서부터 본다
  1. 조각이 2개 이상이고 마지막 조각(앞뒤 공백 무시)이 `^\d{1,4}(x\d{1,4})?$` 이고 앞 수가 1 이상이면 `width` = 앞 수, 그 조각을 뗀다 (`x` 뒤 높이는 버린다 — F-2019 5.1 과 같음)
  2. 남은 조각이 2개 이상이고 마지막 조각(앞뒤 공백 무시)이 정확히 `left` `center` `right`(소문자)면 `align`, 그 조각을 뗀다
  3. 남은 조각을 `|` 로 다시 이은 것이 `alt`

| alt 원문 | alt | align | width |
| --- | --- | --- | --- |
| `그림\|300` | `그림` | left | 300 |
| `그림\|center\|300` | `그림` | center | 300 |
| `\|center` | (빈 글자) | center | null |
| `a\|b\|c` | `a\|b\|c` | left | null |
| `300`·`center` (조각 하나) | 그 글자 | left | null |
| `가격\|100` | `가격` | left | 100 |
| `a\|300\|center` | `a\|300` | center | null |
| `그림 \| center \| 300x200` | `그림 ` | center | 300 |

- **사용자 문장과 구별하지 않는다.** alt 끝이 `|숫자`·`|정렬어` 면 문장이어도 조각으로 읽는다 — 옵시디언 너비 표기와 같은 읽기를 택했고, 이스케이프 문법(`\|`)은 두지 않는다. 그런 alt 는 드물고, 화면에 alt 가 보이는 것은 그림이 깨질 때뿐이다(정해진 것 5)
- 옵시디언이 `![a|center|300](x.png)` 를 어떻게 읽는지는 **확인하지 못했다**(옵시디언을 돌릴 수 없었다). F-2019 는 `|300` 을 너비로 읽는 것을 가정 G 로 두었고(F-2016 9.2), `|center` 를 정렬로 읽는 것은 옵시디언 본체가 아니라 일부 테마의 alt 선택자 관례로 알고 있으나 이것도 확인하지 않았다

### 2.2 무엇을 그리나 `imageLineTarget`
| `url` | 결과 |
| --- | --- |
| 정확히 `attachments/{16hex}.{png\|jpg\|gif\|webp}` (`imageBlock.ts` `SRC_RE` 와 같은 규칙) | 그 `{id, ext}` |
| 스킴(`^[A-Za-z][A-Za-z0-9+.-]*:` — `https:`·`data:`·`file:`)이나 `//` 로 시작 | `null` — 그리지 않는다. 외부 요청 금지(product.md 4.5 "외부 URL 이미지 문법은 원문·링크로만", F-123 3.2) 그대로. 추적 픽셀·오프라인 모양 차이도 같은 이유 |
| 그 밖(상대 경로 `./img/a.png`, `/a.png`, `../x.png`, `./attachments/…`) | `resolveImagePath?.(url) ?? null`. 이 명세 안에서는 넘기는 곳이 없어 늘 `null` |

### 2.3 만들기 `buildImageLine`
- 결과 `![{alt}{|align}{|width}](attachments/{id}.{ext})`. `align` 이 없거나 `left` 면 조각 없음, `width` 가 없거나 `null` 이면 조각 없음, 있으면 `Math.max(1, Math.round)`
- alt 정리: 줄바꿈 → 공백, `\` `[` `]` `|` → 공백, 연속 공백 하나로, 앞뒤 공백 제거, 100자에서 자름(F-156 2.1 의 100자). 만든 줄은 늘 `parseImageLine` 으로 같은 값이 돌아온다(단위 A1)

### 2.4 조각 고치기 (정해진 것 2·6)
- 바꾸는 범위는 alt 안 조각뿐이고 트랜잭션 1개(`userEvent: 'input.image'`, F-157 2.3 그대로). 주소·제목·alt 글자는 그대로
- `imageLineAlignChange`: 정렬 조각이 있으면 그 조각 글자(둘레 공백 포함)를 새 값으로, 새 값이 `left` 면 앞 `|` 와 조각을 지운다. 없으면 `|{align}` 를 너비 조각 앞(없으면 `]` 앞)에 넣는다. 해석 실패·값이 같으면 `null`
- `imageLineWidthChange`: 너비 조각이 있으면 그 조각 글자를 `{N}` 으로(높이 `x…` 도 함께 사라진다), 없으면 `|{N}` 을 `]` 앞에 넣는다. 해석 실패·값이 같으면 `null`

### 4.2 위젯 (`imageWidget.ts`)
- `ImageWidget` 은 해석 결과를 `ParsedImageBlock` 모양(`align`·`id`·`ext`·`src`(=`url`)·`alt`·`width`)으로 받고, 원문 모양 `form: 'html' | 'markdown'` 을 함께 받는다. `eq` 비교에 `form` 을 더한다

## 5. 보기·공유·내보내기·가져오기

### 5.1 보기 (`renderMarkdown.ts` `imageBlockRule`)
- level 0 문단의 `inline.content` 가 `parseImageBlock` 에 맞지 않으면 `parseImageLine` → `imageLineTarget(parsed, options.resolveImagePath)` 를 본다. 첨부가 나오면 **옛 블록과 같은** `html_block` 토큰(같은 `renderImageBlockHtml` 출력, `meta` = 4.2 의 `ParsedImageBlock` 모양, `map`·`data-source-line` 그대로)으로 바꾼다

- `findVaultEmbeds`: 대상이 정확히 `attachments/{16hex}.{ext}` 인 마크다운 임베드는 **결과에 넣지 않는다**(외부 주소와 같은 취급). 이미 이 앱 형식이라 바꾸면 alt 조각이 캡션으로 섞여 깨진다(`a|center|300` → 캡션 `a|center`). 파일은 지금 `attachmentRefs` 경로(F-2019 7.3 셋째 줄)가 올린다
- `listImageBlocks`: 이미지 줄(줄 첫 칸 `![`, `parseImageLine` 과 2.2 첨부 규칙에 맞고, 다음 줄이 빈 줄·문서 끝)도 문서 순서로 넣고 각 항목에 `form` 을 단다
- `EmbedBlock` 에 `form` 을 더하고 `embedsToImageBlocks` 는 `form === 'markdown'` 이면 `buildImageLine` 한 줄, 아니면 지금 3줄. 앞뒤 빈 줄 규칙(F-2019 5.3)은 같다
- `importVault.ts`: 이어받을 기존 이미지가 있으면 그 `form` 을, 없으면 `'html'`(9장 Q3)
- 결과: 새 문법으로 넣은 이미지가 `내보내기 → 손대지 않고 되가져오기` 에서 같은 바이트로 돌아와 `skip`(F-2016 5.4). 원문이 2.3 정규형이 아니면(공백 낀 조각, 명시 `|left`, 제목, `300x200`) 처음 한 번 `update`

## 6. F-3013 에 넘기는 확장 지점

- 연결: `createEditor({ resolveImagePath })` → `livePreview` → `buildBlocks` 매개변수, `renderMarkdown(text, { resolveImagePath })`. 이 명세에서는 아무도 넘기지 않는다. 동기 함수이고 문서 하나에 묶인 값을 F-3013 이 만든다
- 받는 글자: 2.2 셋째 줄(외부·`attachments/` 형식이 아닌 것)의 `url` 원문. `%XX` 풀기·`./` 정리는 F-3013 몫
- **F-3013 이 정해야 할 것** (이 명세는 손대지 않음)
  1. 경로로 푼 첨부는 원문에 `attachments/{id}` 글자가 없다 → 5.2 표의 정리 4곳이 그 첨부를 **24시간 뒤 지운다**. 내보내기 zip·공개 보기 권한(`worker/attachments.ts` → 404)·금고 옮기기도 그 첨부를 모른다
  2. 대응표가 늦게 도착해도 편집기는 다시 그리지 않는다 — `blocks` StateField 는 문서·선택·포커스 변화에만 다시 계산한다. 다시 그리는 effect 는 F-3013 이 더한다
  3. Worker 프록시로 보이는 그림은 지금 `ImageTarget`(첨부만)에 자리가 없다. 갈래를 더하면 그리는 세 곳(`imageWidget.ts` 불러오기, `renderMarkdown` 출력, `Viewer` 채우기)을 F-3013 이 고친다 — `renderMarkdown` 은 지금 `src` 를 출력하지 않는다(F-158 2.1)

### Q1. 줄에 혼자인 최상위 이미지만 그리는가 — **기본값: 그렇다**
- 이유: 지금 블록과 같은 자리 규칙(F-157 2.1)이라 위젯·방향키·IME 경로를 새로 만들지 않는다. 붙여넣기는 늘 혼자인 줄을 만든다
- 다르게 하면: 문장 안 인라인 그림은 인라인 replace 위젯이 필요하다 — 커서가 위젯을 건너뛰는 규칙, `lineWrapping` 줄 높이, 조합 중 보류를 새로 설계해야 하고 4.2 의 손잡이·버튼이 줄 안에 들어간다. 목록·인용 안만 더 허용하면 4.1 의 `isInsideListOrQuote` 거르기와 5.1 의 level 0 조건을 푼다(F-2019 의 standalone 규칙과도 맞춰야 한다)

### Q2. 새로 넣는 이미지 정렬을 지금처럼 `center` 로 두는가 — **기본값: `center`**
- 이유: 화면 모양을 지금과 같게(정해진 것 4), 사용자 예시도 `|center|300`
- 다르게 하면(`left`): 넣은 줄이 `![이미지|200](…)` 로 짧아지고 GitHub 모양과 같아진다. 3.1·3.2 의 `align` 값, 7장 회귀 기대값, E1 첫 원문이 바뀐다

### Q3. 볼트 가져오기가 새로 바꾸는 임베드를 어느 모양으로 쓰는가 — **기본값: 지금처럼 3줄 블록**
- 이유: 사용자가 정한 범위는 붙여넣기·끌어놓기·파일 고르기다. 지금 F-2019 단위 테스트(`obsidianImage.test.ts` `embedsToImageBlocks` 7개, `importVault.test.ts` alt 이어받기)가 그대로 남는다
- 다르게 하면(새 문법): 옵시디언에서 온 문서가 원래 모양(`![[a.png|300]]` → `![a|300](attachments/…)`)에 더 가깝고 옵시디언·GitHub 에서도 그림이 보인다. 5.3 마지막 줄 기본값을 `'markdown'` 으로, 위 테스트 8개 기대값과 `content/guides/obsidian-vault.md` "이미지는 이렇게 바뀝니다" 를 고친다
