## 2. 지금 코드가 세 응답을 어떻게 다루나 (확인한 것)

F-2024 5.1 끝 문단("지금 배포된 웹은 세 응답을 잘못 다룬다")을 코드로 다시 확인했다. 모두 **outbox 항목을 지운다**

| 응답 | 어느 함수 | 지금 분류 | `sendOne` 이 하는 일 | 결과 |
| --- | --- | --- | --- | --- |
| 429 (모든 쓰기) | `docsApi` 쓰기 함수 9개 | `classifyStatus` 가 401·5xx 만 보므로 `other` | "id_taken·invalid·other" 갈래 — `cache.removeOutbox` + `동기화하지 못했습니다.` | **항목 사라짐** |
| 413 `doc_quota_exceeded` | `createDoc`·`updateDoc` | `too_large` (상태 코드만 본다) | `removeOutbox` + `문서가 너무 커서 서버에 저장하지 못했습니다(1MB 초과).` | **항목 사라짐**, 틀린 문구 |
| 403 `account_blocked` | `updateDoc` | `forbidden` | `removeOutboxForDoc` + `removeOutbox` + `onForbidden` + `이 문서를 편집할 권한이 없어졌습니다.` | **그 문서 대기 편집 전부 사라짐** |
| 403 `account_blocked` | `createDoc`·`moveDocFolder`·`setPinned`·`removeDoc`·폴더 셋 | 403 갈래가 없어 `other` | `removeOutbox` + `동기화하지 못했습니다.` | **항목 사라짐** |
| 429·403 | `uploadAttachment` | `other` | "server_error·other" 갈래 — `return false`(회차만 멈춤) | 항목은 남는다. 30초마다 다시 보낸다 |

- 항목이 사라진 뒤에도 캐시 본문은 남지만, 다음 `list()` 재조정이 "서버에 없고 outbox 에도 없는" 캐시 문서를 지운다(`serverStore.ts` `list` 의 `deleteDocsNotIn(userId, keepIds)`). 그래서 **만들기(`createDoc`)가 사라지면 그 문서는 다음 목록 갱신 때 이 브라우저에서도 사라진다**. 지금 코드의 가장 큰 구멍이다
- 한 번 더 확인한 함정: 앞 항목을 건너뛰고 **같은 문서의 뒤 항목**을 보내면 서버가 404 를 줄 수 있다(만들기가 아직 안 된 문서에 PUT·이동·고정). `sendOne` 의 `not_found` 갈래는 `cache.deleteDoc` + `removeOutboxForDoc` 이다 — **로컬 문서가 지워진다.** 4.3 의 "같은 문서 뒤 항목도 건너뛴다" 는 이것 때문이다

## 3. 계약

### 3.1 `src/storage/docsApi.ts`

```ts
export type ApiErrorKind =
  | 'network' | 'unauthorized' | 'not_found' | 'too_large' | 'conflict' | 'locked'
  | 'id_taken' | 'invalid' | 'forbidden' | 'server_error' | 'other'
  | 'rate_limited'          // 429 (F-2030)
  | 'doc_quota_exceeded'    // 413 { error: 'doc_quota_exceeded' } (F-2030)
  | 'account_blocked'       // 403 { error: 'account_blocked' } (F-2030)

export class ApiError extends Error {
  // 기존 필드 그대로 (kind, status, doc, email, expiresAt)
  scope?: 'minute' | 'day'      // rate_limited
  retryAfter?: number           // rate_limited — 초, 1 ~ 86400
  limit?: number                // rate_limited·doc_quota_exceeded — 몸통 값 그대로
  used?: number                 // doc_quota_exceeded
  resource?: 'bytes' | 'docs'   // doc_quota_exceeded
}
```

분류 규칙 — **쓰기 함수 전부**(`createDoc`·`updateDoc`·`lockDoc`·`moveDocFolder`·`setPinned`·`removeDoc`·`createFolder`·`updateFolder`·`removeFolder`·`putGrant`·`deleteGrant`)가 기존 상태별 갈래 **앞에서** 아래를 먼저 본다. `unlockDoc` 은 오류를 버리는 함수라 그대로 둔다. `GET` 함수는 서버가 세지 않으므로(F-2024 1.2) 고치지 않는다

| 응답 | 결과 |
| --- | --- |
| 429 | `rate_limited`. `scope` = 몸통 `scope` 가 `'day'` 면 `'day'`, 그 밖(몸통 없음·JSON 아님·다른 값) 전부 `'minute'`. `retryAfter` = `parseRetryAfter(헤더 Retry-After, 몸통 retryAfter)`(3.5). `limit` = 몸통 `limit` 이 양의 정수일 때만 |
| 413, 몸통 `error === 'doc_quota_exceeded'` | `doc_quota_exceeded`. `resource` = 몸통 값이 `'docs'` 면 `'docs'`, 그 밖 `'bytes'`. `used`·`limit` = 몸통 값이 0 이상의 유한수일 때만 |
| 413, 그 밖(몸통 없음·`too_large`·JSON 아님) | 지금처럼 `too_large` |
| 403, 몸통 `error === 'account_blocked'` | `account_blocked` |
| 403, 그 밖 | 지금 갈래 그대로 — `updateDoc`·`lockDoc` 은 `forbidden`, 나머지는 `other` |

- WAF 규칙(F-2024 9장 Q1 대안)이 돌려주는 429 는 몸통이 우리 모양이 아니다 — 그래서 "몸통 없는 429 = `minute`" 이다(F-2024 5.1 L1 행)
- 403 은 몸통을 읽어야 가를 수 있다. 몸통 읽기가 실패하면 "그 밖" 이다

규칙:

- `parseRetryAfter`: 헤더가 `^\d+$` 인 양의 정수면 그 값, 아니면 몸통 값이 양의 유한수면 올림한 값, 둘 다 아니면 **60**. 결과는 1 이상 86,400 이하로 자른다(하루 한도의 `retryAfter` 는 최대 86,400 — F-2024 3.4 "다음 UTC 자정까지 남은 초, 올림"). HTTP 날짜 형식 `Retry-After` 는 받지 않는다 — 우리 서버·WAF 모두 초를 보낸다고 가정한다(12장 가정 목록)
- `nextUtcMidnight`: `nowMs` 보다 **큰** 가장 가까운 UTC 자정. 정확히 자정이면 다음 날 자정

- `formatMegabytes`: 지금 `AccountMenu.tsx` `formatUsage` 규칙 그대로 — 1,048,576 바이트 = 1MB, 10MB 미만은 소수 1자리, 이상은 반올림 정수. 104,857,600 → `100MB`
- `formatCount`: `toLocaleString('ko-KR')`
- 문구는 6.1 표. `limit` 이 양의 정수가 아니면(서버 몸통이 계약과 다름) 괄호·숫자를 뺀 대체 문구를 쓴다(6.1 "대체")
- L2 의 `{시각}` 은 **브라우저 시계로 계산한 다음 UTC 자정**이다(F-2024 5.1 "다음 UTC 자정을 브라우저 현지 시각으로"). 서버 `retryAfter` 로 더하지 않는 이유: 서버 값은 올림이라 표시가 `오전 9:01` 이 될 수 있다. 보내기를 다시 여는 시각은 `retryAfter` 를 따른다(4.2) — 표시와 실제가 1초 안쪽으로 다를 수 있고 받아들인다
- `planAccountNotices` 는 5.3 표를 그대로 옮긴 판정이다

## 4. outbox 동작 (F-207 2.3 에 더함)

### 4.1 보장 — 로컬 편집은 사라지지 않는다

**429·413 `doc_quota_exceeded`·403 `account_blocked` 어느 것을 받아도 `serverStore` 는 outbox 항목을 지우지 않고, 캐시 문서·첨부를 지우지 않는다.** 항목은 IndexedDB `md-remote` 에 남아 새로고침·브라우저를 다시 연 뒤에도 그대로이고, 제한이 풀리면(시간이 지나거나 공간을 비우거나 차단이 풀리면) 원래 순서대로 나간다. 건너뛴 항목 때문에 같은 문서의 뒤 항목이 404 를 받아 캐시 문서가 지워지는 일(2장 끝)도 없다 — 같은 문서의 뒤 항목은 함께 건너뛴다(4.3). 실시간 경로의 편집은 outbox 를 지나지 않고 DO·`md-yjs` 에 있다(F-306 3장) — 서버 하루 한도는 DO 를 느리게 할 뿐 편집을 버리지 않고(F-2024 결정 4), 차단된 방의 `4403` 은 `md-yjs` 기록을 지우지 않는다(`yjsFlush.ts` `flushOne` 은 결과가 `gone` 일 때만 `removeDoc`)

- 이 보장이 지키지 **못하는** 것: 사용자가 브라우저 데이터를 지우면 사라진다(지금과 같다). 기존 413 `too_large`(1MB 초과)는 지금처럼 항목을 버린다(바꾸지 않는다 — 다시 보내도 늘 실패한다)

### 4.2 429 — 전체를 멈추고 기다린다

- `rate_limited` 를 받으면 이번 회차를 멈추고(그 항목은 그대로 맨 앞), **`now + retryAfter × 1000` 까지 outbox 전체를 보내지 않는다.** 이 시각을 "보내기 재개 시각" 이라 한다
- 재개 시각 전에는 어떤 계기로도 보내지 않는다 — 30초 재시도(`RETRY_INTERVAL_MS`), `online` 이벤트, 새 쓰기(`enqueue*`·`create`·`remove` 등이 부르는 `kickSend`) 모두. 새 쓰기는 캐시·outbox 에 지금처럼 들어간다
- 재개 시각에 한 번 보내기를 시작한다(브라우저에서만 타이머를 건다 — 지금 `setInterval` 이 `typeof window !== 'undefined'` 일 때만 걸리는 것과 같다). 탭이 잠들어 타이머가 늦으면 30초 재시도가 이어받는다
- 첨부 올리기(`upload`)의 `rate_limited` 도 같다 — 분당·하루 몫은 사용자 하나에 하나다(F-2024 2.2)
- 알림: `scope` 가 `minute` 이면 L1, `day` 면 L2. **멈출 때마다 한 번**(같은 멈춤 동안 다시 띄우지 않는다)
- 하루 한도로 멈춘 뒤 새로고침하면 부팅 때 한 번 보내 429 를 다시 받는다 — 요청 1개, L2 한 번. 멈춤을 저장해 두지 않는다(로컬 저장 키를 늘리지 않는다)

### 4.3 413 `doc_quota_exceeded` — 그 항목을 30초 붙잡고 나머지를 보낸다

- 받은 항목을 **`now + QUOTA_HOLD_MS`(30초)까지 붙잡는다.** 붙잡힌 항목은 지우지 않고 회차마다 건너뛴다
- `resource` 가 `docs` 면(문서 수) 받은 항목 하나가 아니라 **그 시각까지 outbox 의 모든 `createDoc` 항목**을 붙잡는다 — 수가 줄지 않는 한 어느 만들기도 성공하지 못하기 때문이다
- **같은 문서의 뒤 항목도 건너뛴다.** outbox 순서에서 붙잡힌 항목보다 **뒤에 있고** `docIdOf` 가 같은 항목(`updateDoc`·`moveDoc`·`setPinned`·`removeDoc`)은 그 회차에 보내지 않는다. 이유는 2장 끝(만들기 전에 PUT → 404 → 캐시 문서 삭제). 붙잡힌 항목보다 **앞에** 있는 것은 이미 나갔거나 먼저 나간다
  - 사용자가 붙잡힌 문서를 지우면 `remove()` 가 그 문서의 대기 항목을 지우고(`removeOutboxForDoc`, 보내는 중인 것 제외) `removeDoc` 을 새로 넣는다. 그 `removeDoc` 앞에는 붙잡힌 항목이 없으므로 바로 나간다 — 공간을 비우는 삭제가 막히지 않는다
- 나머지 항목(다른 문서, 폴더, 삭제, 줄이는 편집, 첨부)은 계속 보낸다(F-2024 5.1 "앞 항목에서 멈추면 공간을 비우는 삭제가 뒤에 막혀 영영 못 나간다")
- 30초가 지나면 붙잡기가 풀려 다음 회차(30초 재시도·새 쓰기·`online`)에 다시 보낸다. 다시 413 이면 다시 30초. 붙잡힌 문서 하나당 최대 분당 2요청이다 — 폴백 편집 중 입력 저장마다 PUT 이 나가(`SAVE_DEBOUNCE_MS` 간격) 분당 한도를 먹는 것을 막는 것이 30초의 이유다
- 알림 L3(`bytes`)·L4(`docs`): 그 자원으로 **붙잡힌 항목이 하나도 없던 상태에서** 첫 413 을 받을 때 한 번. 붙잡힌 항목이 남아 있는 동안 다시 받은 413 은 알리지 않는다. 붙잡힌 항목이 모두 나가거나(성공) outbox 에서 없어지면(사용자가 지움) 다음 413 에서 다시 알린다
- 붙잡힌 항목이 있는 문서는 `hasPendingChanges` 가 참이라 실시간으로 붙지 않고 `pending` 경로로 열린다(F-305 4.2) — 지금 동작 그대로다. 만들기가 붙잡힌 새 문서도 이 브라우저에서 편집을 이어갈 수 있다

### 4.4 403 `account_blocked` — 멈추고, 누구의 차단인지 확인한다

서버는 **내 계정이 막혔을 때**와 **남의 문서 소유자가 막혔을 때**(내가 편집 권한으로 그 문서에 쓸 때) 같은 403 `account_blocked` 를 준다(F-2024 4.2 표 "그 문서에 쓰는 요청도 403"). 몸통으로는 둘을 가를 수 없다. 그래서:

1. 받으면 그 항목을 두고 이번 회차를 멈춘다. **차단 멈춤** 상태가 되어 `setAccountBlocked(false)` 가 불릴 때까지 아무것도 보내지 않는다(30초 재시도·`online`·새 쓰기 모두). 받은 항목의 `docId`(없으면 없음)를 기억한다. `onAccountBlocked()` 를 부른다
2. App 이 `/api/me` 를 다시 읽는다(5.1 ③)
   - `blocked: true` → 내 계정이 막혔다. App 이 `setAccountBlocked(true)` 를 부르고 L5(5.3). 차단 멈춤이 이어진다
   - `blocked: false` → 남의 문서 소유자가 막혔다. App 이 `setAccountBlocked(false)` 를 부른다. `serverStore` 는 기억한 `docId` 를 **이 페이지 동안 건너뛸 문서**로 옮기고, 그 문서에 `onForbidden(docId)`(지금 403 강등과 같은 읽기 전용, F-212 2.4)와 error 알림 `이 문서를 편집할 권한이 없어졌습니다.`(지금 문구 그대로)를 보낸 뒤 보내기를 다시 시작한다. **항목은 지우지 않는다** — 지금 403 `forbidden` 갈래와 다른 점이다. 새로고침하면 다시 한 번 보내 같은 확인을 거친다(12장 Q1)
   - `/api/me` 를 못 읽으면(오프라인·5xx) 차단 멈춤을 유지한다. 다음 `online` 이벤트·화면 복귀(5.1)에서 다시 읽는다
3. `setAccountBlocked(true)` 는 App 이 **부팅·다시 읽기에서 먼저 알게 된 경우**에도 부른다 — 그러면 첫 요청을 보내 403 을 받는 일 없이 처음부터 멈춰 있다
4. `setAccountBlocked(false)` 가 차단 멈춤 중이 아닐 때 불리면 아무것도 하지 않는다

- 차단 멈춤 중에도 `pending` 수(상태바 ` · 동기화 대기 {N}`)는 지금처럼 보인다. 새 상태바 문구는 없다(F-2024 5.1)

### 4.5 한 회차 안에서의 선택 — 정리

회차는 outbox 를 순서대로 훑으며, 보낼 수 있는 **첫 항목**을 하나씩 보낸다. 지금 코드는 늘 `entries[0]` 을 보내는데(`kickSend`), 붙잡힌 항목(4.3)과 건너뛸 문서(4.4)가 생기므로 "건너뛸 항목이 아닌 첫 항목" 으로 바뀐다. 건너뛰는 조건은 셋이다 — ① 붙잡힌 항목(시각 전), ② 붙잡힌 항목 뒤의 같은 문서 항목, ③ 이 페이지 동안 건너뛸 문서(4.4)의 항목. 보낼 항목이 없으면 회차가 끝난다. 429 멈춤·차단 멈춤 중에는 회차를 시작하지 않는다

### 4.6 outbox 밖의 쓰기 — 바꾸지 않는다

| 쓰기 | 지금 | 이 명세 |
| --- | --- | --- |
| 잠금 잡기·연장(`lockDoc`) | 오류는 `locked` 만 본다(`useDocLock.ts`) — 나머지는 무시하고 편집 허용 | 그대로. 새 `kind` 셋도 무시된다. 폴백 편집 자체는 outbox 로 가므로 4.2~4.4 를 따른다 |
| 공유 링크(`linkApi`·`shareSetApi`), 초대(`putGrant`·`deleteGrant`), API 토큰(`apiTokensApi`) | 사람이 누른 한 번의 요청. 실패하면 각 대화상자의 기존 실패 문구 | 그대로. 데이터가 사라지지 않고, 막힌 계정은 이미 L5 를 본다. 전용 문구는 12장 "하지 않는 것" |
| 실시간 편집(WebSocket) | 분당·하루 관문을 지나지 않는다(업그레이드는 `GET` — F-2024 1.2) | 그대로. 하루 초과는 DO 느린 저장(알리지 않음, F-2024 Q6), 차단은 `4403`(5.4) |

## 5. 계정 상태 `blocked`·`warned`

### 5.1 `/api/me` 를 읽는 때

| # | 계기 | 지금 | 이 명세 |
| --- | --- | --- | --- |
| ① | 부팅 | 있다(`App` `boot` 의 `fetchAccount`) | 그대로. 결과의 `blocked`·`warned` 를 반영(5.2) |
| ② | `online` 이벤트 | 있다(`App` 의 `online` → `fetchAccount`) | 그대로 |

| ④ | 실시간 세션이 `4403` 으로 멈춤 — 내 소유 문서(`role` 이 없거나 `owner`)일 때 | 없다 | **곧바로 읽는다**(5.4) |
| ⑤ | 화면이 다시 보임(`visibilitychange` → `visible`) | 없다 | 마지막으로 **성공한** 읽기에서 `ACCOUNT_RECHECK_MS`(10분)가 지났을 때만 읽는다 |

- ⑤ 의 이유: 운영자가 `admin-warn`·`admin-block`·`admin-unblock` 을 한 뒤, 탭을 며칠 열어 두는 사람에게도 알림이 닿게 하려고(F-2024 4.4 "사용자가 앱을 열어 L7 을 봐야 한다"). 10분으로 둔 이유: `/api/me` 는 쓰기 관문을 지나지 않는 `GET` 이고 D1 읽기 2행(세션·사용자, F-2032 2.5)이다. 탭을 오가는 사람이 분마다 전환해도 한 시간 6번이다. 주기적 타이머는 두지 않는다 — 안 보는 탭이 계속 읽을 이유가 없다
- 같은 순간 둘 이상의 계기가 겹치면 읽기는 **하나만** 진행한다(진행 중이면 새 계기는 그 결과를 기다린다)
- 읽기 결과가 `out`(401)이면 지금처럼 `setAccount` 로 반영한다 — 이 명세가 바꾸지 않는다. `offline` 이면 `blocked`·`warned` 를 **바꾸지 않는다**(모르는 것을 "안 막힘" 으로 덮지 않는다)

### 5.2 App 에 반영하는 것

- App 은 `accountBlocked`·`accountWarned` 두 값을 가진다. `in` 결과가 오면 그 값으로 바꾼다. `onAccountBlocked` 는 값을 바꾸지 않고 읽기 ③ 만 부른다
- `accountBlocked` 가 바뀔 때마다 서버 저장소면 `setAccountBlocked(accountBlocked)` 를 부른다
- **읽기 전용**: 서버 저장소이고 `accountBlocked` 이면 모든 문서(내 것·공유받은 것)의 편집기와 본문 맨 위 제목이 읽기 전용이다 — `isReadOnlyDoc` 조건에 더한다. 서버가 어차피 모든 쓰기를 403 으로 막으므로(F-2024 4.2) 편집을 받아 outbox 에 쌓아 봤자 나가지 못한다. 내보내기(`.md 내보내기`·zip·옵시디언 볼트·인쇄)는 막지 않는다(결정 10)
- **경로 판정**: `accountBlocked` 이면 `decideDocPath` 의 입력 `forbidden` 을 참으로 넘긴다 — 두 자리 모두(`App` 의 렌더 중 빠른 판정, outbox·기록 확인 뒤 판정). 그러면 문서가 소켓을 열지 않고 곧장 `view` 로 열린다. 소켓을 열어 `4403` 을 받는 왕복과 N1 이 생기지 않는다
- 이미 열린 실시간 세션은 `accountBlocked` 가 참이 된 순간 편집기가 읽기 전용이 되고, 서버 재검증이 `4403` 으로 닫을 때(F-2024 4.2 — 편집이 이어지면 최대 약 90초, F-2028) 멈춘다(5.4)
- **차단이 풀릴 때**(`true` → `false`): outbox 가 다시 나가고(4.4), 읽기 전용 조건에서 빠진다. 그 사이 소켓 `4403` 으로 `forbiddenDocIds` 에 들어간 문서는 이 페이지 동안 읽기 전용으로 남는다 — 지금 `forbiddenDocIds` 가 "이번 세션 동안" 규칙이다(F-212 2.4). 새로고침하면 풀린다. 풀림을 알리는 새 알림은 두지 않는다 — L5 만 걷는다(5.3)

### 5.3 L5·L7 을 띄우고 걷는 규칙 (`planAccountNotices`)

`prev` 는 이 페이지에서 직전에 반영한 값(부팅 전이면 `null`), `next` 는 새 `in` 결과다

| 경우 | 하는 일 |
| --- | --- |
| `next.blocked` 이고 `prev` 가 `null` 이거나 `prev.blocked` 가 거짓 | **L5 를 띄운다** |
| `next.blocked` 이고 `prev.blocked` 도 참 | 아무것도 안 한다(이미 띄웠고, 사용자가 닫았으면 다시 띄우지 않는다) |
| `next.blocked` 가 거짓이고 `prev.blocked` 가 참 | L5 가 아직 떠 있으면 걷는다 |
| `next.warned` 이고 `next.blocked` 가 거짓이고 이 페이지에서 L7 을 아직 안 띄움 | **L7 을 띄운다** — "앱을 열 때마다 한 번"(F-2024 5.1). 새로고침하면 다시 한 번 |
| `next.warned` 가 거짓이고 L7 이 떠 있음 | 걷는다 |
| `next.blocked` 가 참이고 L7 이 떠 있음 | 걷는다(L5 가 대신한다) |

- 떠 있는지는 `showNotice` 가 돌려준 id 로 판단한다(`dismissNotice(id)` — 다른 알림이 자리를 차지했으면 건드리지 않는다, F-305 11.2 와 같은 방식)
- 부팅 때 `blocked` 와 `warned` 가 모두 참이면 L5 만 뜬다(F-2024 5.1 L7 조건 "`blocked` 가 아님")

### 5.4 실시간 `4403` 과의 관계 (N1·N2)

- 소켓이 `4403` 으로 닫히면 `liveDoc.ts` 가 첫 동기화 전이면 `forbidden`(N1), 뒤면 `revoked`(N2)로 멈춘다 — 그대로 둔다. 막힌 계정 본인도, 남의 막힌 문서를 연 사람도 `4403` 을 받는다(F-2024 4.2 표 "실시간 연결")
- App 은 멈춘 세션이 **내 소유 문서**이면:
  - 이미 `accountBlocked` 가 참이면 N1·N2 를 띄우지 않고 **L5 를 띄운다**(이미 닫았어도 다시). N2 의 `새 문서로 저장` 버튼은 막힌 계정에서 쓸모가 없다(만들기도 403)
  - 아니면 N1·N2 를 지금처럼 띄우고 5.1 ④ 로 `/api/me` 를 읽는다. 결과가 `blocked: true` 면 5.3 대로 L5 — error 가 warn(N2)·info(N1)를 대체한다(`pushNotice`)
- 공유받은 문서(`role` 이 `edit`·`view`)의 `4403` 은 지금처럼 N1·N2 만 — 막힌 쪽이 소유자일 수 있지만 내 계정 문제가 아니다

## 6. 알림 L1~L5·L7

### 6.1 문구 (F-2024 5.1 그대로, 채운 예)

| # | 언제 | 종류 | 문구 | 버튼 | 누가 띄우나 |
| --- | --- | --- | --- | --- | --- |
| L1 | outbox 429 `minute`(또는 몸통 없는 429)로 멈출 때 한 번 | info | `요청이 많아 잠시 쉬었다가 이어서 저장합니다.` | — | `serverStore` → `onNotice` |
| L2 | outbox 429 `day` 로 멈출 때 한 번 | error | `오늘 저장 한도(하루 {limit}번)를 넘었습니다. {시각}부터 다시 저장됩니다. 그때까지 바뀐 내용은 이 브라우저에 보관됩니다.` — 예: `하루 5,000번`, `오전 9:00부터` | — | `serverStore` → `onNotice` |
| L3 | outbox 413 `doc_quota_exceeded` `bytes` (4.3 규칙으로 한 번) | error | `계정의 문서 저장 공간({limit})이 가득 찼습니다. 문서를 지우거나 줄이면 다시 저장됩니다.` — 예: `(100MB)` | — | `serverStore` → `onNotice` |
| L4 | outbox 413 `doc_quota_exceeded` `docs` (4.3 규칙으로 한 번) | error | `문서가 {limit}개에 이르러 새 문서를 서버에 저장하지 못했습니다. 문서를 지우면 다시 저장됩니다.` — 예: `10,000개` | — | `serverStore` → `onNotice` |
| L5 | 5.3·5.4 | error | `이 계정은 운영자가 쓰기를 막았습니다. 문서 읽기와 내보내기만 할 수 있습니다.` | — | App |
| L7 | 5.3 | warn | `운영자가 이 계정의 사용 방식에 주의를 보냈습니다. 이용약관 제7조(금지 행위)를 확인해 주세요. 계속되면 쓰기가 막힐 수 있습니다.` | — | App |

- 채우는 값: L2 `{limit}` = `formatCount(limit)`, `{시각}` = `formatResetTime(nextUtcMidnight(now))`. L3 `{limit}` = `formatMegabytes(limit)`. L4 `{limit}` = `formatCount(limit)`. 숫자를 코드에 적지 않는다(F-2024 5.1)
- **대체**(몸통 `limit` 이 양의 정수가 아닐 때): L2 `오늘 저장 한도를 넘었습니다. {시각}부터 다시 저장됩니다. 그때까지 바뀐 내용은 이 브라우저에 보관됩니다.` / L3 `계정의 문서 저장 공간이 가득 찼습니다. 문서를 지우거나 줄이면 다시 저장됩니다.` / L4 `문서 수가 한도에 이르러 새 문서를 서버에 저장하지 못했습니다. 문서를 지우면 다시 저장됩니다.`
- L6(가입 마감)은 `/login` 서버 페이지 몫이라 이 명세 밖이다(F-2028)
- L7 의 "제7조" 는 `content/legal/terms.md` 의 `## 제7조 (금지 행위)` 와 맞다(확인). 약관 조 번호가 바뀌면 이 문구도 바꾼다(11장)

### 6.2 기존 알림과의 우선순위

`pushNotice` 규칙을 **바꾸지 않는다** — "새 알림이 대체한다. 단 지금이 error·update·warn 이면 info 는 대체하지 못한다". 그 결과:

| 지금 떠 있는 것 | L1(info) 가 오면 | L2~L5(error) 가 오면 | L7(warn) 이 오면 |
| --- | --- | --- | --- |
| 없음·info | L1 | 새 것 | L7 |
| error (N3·N4·N6, 저장 실패 등) | **안 바뀜** | 새 것 | L7 |
| warn (N2·N5·N7, 충돌 사본 등) | **안 바뀜** | 새 것 | L7 |
| update (`새 버전이 있습니다.`) | **안 바뀜** | 새 것 | L7 |

- L1 은 4초 뒤 스스로 걷힌다(지금 info 규칙). 다른 알림이 떠 있으면 L1 은 보이지 않는다 — 쉬었다 다시 저장하는 것은 저절로 되므로 사용자가 못 봐도 잃는 것이 없다
- L7 이 `새 버전` 알림을 밀어낼 수 있다 — 지금 규칙 그대로다(warn 은 update 를 대체한다). 부팅 때 L7 은 `/api/me` 직후라 서비스 워커 갱신 알림보다 대개 먼저 뜬다. 뒤에 온 `새 버전` 알림이 L7 을 밀어낸다 — 받아들인다
- 막힌 계정에서는 N1(5.2 경로 판정으로 생기지 않는다)·N2(5.4 로 L5 로 바뀐다)·N5·N7(실시간·`offline-view` 세션이 생기지 않는다 — `decideDocPath` 는 `forbidden` 을 오프라인 판정보다 먼저 본다)이 L5 를 밀어내지 않는다

## 7. 계정 메뉴 문서 줄

- 이미지 줄(`.account-menu-usage`) **바로 아래**에 한 줄. 메뉴를 열 때 이미 받는 `GET /api/usage` 응답(`AccountMenu` 의 `fetchUsage`)의 `docs` 로 그린다 — 새 요청 없음
- 요소: `<li className="account-menu-usage-docs" role="none">`, 90% 이상이면 클래스 `account-menu-usage-docs account-menu-usage-danger`
- 문구: `문서 {bytes} / {bytesLimit} · {count}개` — `{bytes}`·`{bytesLimit}` 은 `formatMegabytes`, `{count}` 는 `formatCount`. 예: `bytes` 12,582,912·`bytesLimit` 104,857,600·`count` 1,234 → `문서 12MB / 100MB · 1,234개`. 문서 수 한도(`countLimit`)는 문구에 넣지 않는다(F-2024 5.1 문구 모양)
- 90% 판정: `bytes / bytesLimit >= 0.9` **또는** `count / countLimit >= 0.9`
- 그리지 않는 때: `docs` 가 없거나, 네 값 중 하나라도 유한수가 아니거나, `bytesLimit`·`countLimit` 이 0 이하. 이미지 줄도 없을 때(`fetchUsage` 실패)는 당연히 없다
- **이미지 줄의 클래스·글자는 그대로**다. 새 줄에 `account-menu-usage` 클래스를 달지 않는 이유: `e2e/imageQuota.spec.js` 가 `page.locator('.account-menu-usage')` 로 `toHaveText('이미지 120MB / 300MB')` 를 본다 — 두 요소가 걸리면 strict 위반으로 깨진다
- `AccountMenu` 의 `formatUsage` 는 `usageLimits.ts` `formatMegabytes` 로 바꾼다(같은 규칙 두 벌을 두지 않는다). 이미지 줄의 출력은 한 글자도 바뀌지 않아야 한다 — `imageQuota.spec.js` 가 판정한다
- 하루 쓰기 수(`writes`)는 그리지 않는다(F-2024 9장 기본값 11)
- CSS: `.account-menu-usage` 규칙(글씨 12px·`--muted`·안쪽 여백)의 선택자 목록에 `.account-menu-usage-docs` 를 더한다. 새 색·새 값은 없다

## 8. 도움말 한도 문단 (`src/app/helpDoc.ts`)

`## 저장` 절(지금 "입력을 멈추면 자동으로 저장됩니다. …" 한 문단) **끝에 새 문단 하나**를 더한다. 문장(계약 — 사이트 `/help` 에도 그대로 나간다):

```text
로그인한 계정은 문서 본문을 모두 합쳐 100MB, 문서 10,000개까지 서버에 저장할 수 있습니다. 저장·이동·삭제처럼 서버에 쓰는 일은 계정마다 하루 5,000번까지이고, 한국 시간 오전 9시(UTC 자정)에 다시 셉니다. 한도에 닿아도 편집한 내용은 이 브라우저에 남아 있다가, 공간을 비우거나 시간이 지나면 서버로 올라갑니다.
```

- `## 이미지` 절의 300MB 문장은 그대로 둔다
- **새 `##` 제목을 만들지 않는다.** 그래서 앱 도움말 목차(`helpOutline`)와 사이트 `/help` 목차(F-2036 이 만드는 오른쪽 목차 — `##`·`###` 제목에서 뽑는다)는 **바뀌지 않는다.** `helpDoc.test.ts` 의 절 순서(G1), `helpOutline.test.ts`, `e2e/help.spec.js` 의 묶음 순서도 그대로 통과한다. 새 절 `## 한도` 를 두면 목차에 한 줄이 생기고 F-2036 의 사이트 목차 e2e 가 제목 수를 세는 경우 영향을 받는다 — 12장 Q3
- 이 문서는 사이트 `/help` 의 원본이다(F-274, `site/helpPage.ts`). 문장이 바뀌면 다음 사이트 빌드에서 `/help` 본문도 바뀐다. 이미지·mermaid 문법을 쓰지 않으므로 빌드 제약(`helpDoc.ts` 머리 주석)에 걸리지 않는다
- 숫자를 여기서는 문장에 적는다 — 도움말은 정적 문서이고 이미 `300MB`·`20MB` 를 적고 있다. 한도가 바뀌면 이 문단을 함께 고친다(11장)

## 12. 열린 질문

### Q1. 남의 막힌 문서에 쓴 편집(403 `account_blocked`, 내 계정은 안 막힘) — **기본값: 항목을 남기고 이 페이지 동안 그 문서만 건너뛴다, 문구는 기존 `이 문서를 편집할 권한이 없어졌습니다.`** (4.4)

- F-2024 는 이 경우를 따로 다루지 않았다 — 5.1 은 "403 `account_blocked` → 보내기를 멈춘다" 로 내 계정 차단만 가정했다. 몸통으로 둘을 가를 수 없어 `/api/me` 로 확인한다
- 기본값의 이유: 결정 10 은 막힌 소유자의 문서를 "쓰기 차단" 이라 했을 뿐 편집자의 로컬 편집을 버리라고 하지 않았다. 4.1 보장과 맞추려면 남긴다. 문구를 새로 만들지 않는 이유: 사용자에게 보이는 결과(이 문서를 더는 저장하지 못함)가 권한 회수와 같고, 새 문자열은 `ia.md` 표를 늘린다
- **다른 안 — 지금 403 `forbidden` 처럼 그 문서 대기 편집을 버린다**: 코드가 줄고(차단 멈춤 뒤 확인 → 기존 `forbidden` 갈래 재사용), `동기화 대기 {N}` 가 영영 남지 않는다. 대신 소유자가 풀려도 그 편집은 돌아오지 않는다. U14·4.4 2번이 바뀐다
- **다른 안 — 전용 문구** `이 문서의 소유자 계정이 막혀 서버에 저장하지 못했습니다. 편집은 이 브라우저에 남아 있습니다.`: 원인이 정확하다. `ia.md` 4.2 에 한 줄, `usageLimits.ts` 상수 하나가 는다

### Q2. 막힌 계정에서 새 문서·새 폴더·이름 바꾸기·이동·삭제 — **기본값: 막지 않는다(로컬에 적용, outbox 에서 기다림)** (5.2)

- 편집기·제목만 읽기 전용이다. 사이드바 조작은 지금처럼 캐시에 먼저 쓰고 outbox 에 쌓여 차단이 풀리면 나간다 — 잃는 것이 없다
- 이유: 막힌 계정은 드물고(운영자가 직접 막는다), 사이드바·팔레트·가져오기·끌어놓기 등 만들기 진입점이 열 곳 가까이라 모두 막으려면 이 명세의 파일이 크게 는다. 새 문서는 만들어져도 편집기가 읽기 전용이라 빈 문서로 남는다 — 어색하지만 L5 가 이유를 말한다
- **다른 안 — 만들기·옮기기·삭제 진입점을 모두 비활성**: 화면이 L5 문구와 맞는다. `Sidebar.tsx`·`SidebarHead.tsx`·`ContextMenu`·`paletteCommands.ts`·가져오기·끌어놓기 판정이 소유 표에 더해지고 각 e2e 가 는다

### Q3. 도움말에 새 `## 한도` 절을 둘까 — **기본값: 두지 않는다, `## 저장` 끝에 문단 하나** (8장)

- 이유: 사용자가 한도를 궁금해하는 때는 "저장이 왜 안 되지" 일 때라 `저장` 절 안이 자연스럽다. 목차가 바뀌지 않아 F-2036(사이트 목차, 구현 중)과 부딪치지 않는다
- **다른 안 — `## 한도` 절 신설(`## 저장` 과 `## 이미지` 사이), 이미지 300MB 문장도 옮김**: 한 곳에서 모든 한도를 본다. 앱 목차·사이트 `/help` 목차에 한 줄이 생긴다. `helpDoc.test.ts` G1 목록·F-257 2장 표·(F-2036 이 `/help` 목차 항목 수를 센다면) 그 테스트를 함께 고친다

### 기본값으로 정한 것 (승인 시 확정)

1. 429 는 outbox 전체를 `Retry-After`(없으면 60초, 1~86,400 로 자름) 동안 멈춘다. 새 쓰기·30초 재시도·`online` 모두 그 전에는 보내지 않는다 — 4.2
2. 413 `doc_quota_exceeded` 는 그 항목(문서 수면 모든 `createDoc`)을 30초 붙잡고 같은 문서 뒤 항목도 건너뛴다 — 4.3
3. 403 `account_blocked` 는 차단 멈춤 + `/api/me` 확인 — 4.4
4. `/api/me` 는 부팅·`online`·403·내 문서 `4403`·10분 넘은 화면 복귀에서 읽는다. 주기 타이머 없음 — 5.1
5. 막힌 계정은 모든 서버 문서가 읽기 전용이고 `view` 경로로 곧장 연다 — 5.2
6. L5 는 막힘으로 바뀔 때 한 번, L7 은 페이지마다 한 번. 풀리면 걷는다 — 5.3
7. `pushNotice` 규칙은 바꾸지 않는다 — 6.2
8. 알림 문구·표기 함수는 `src/lib/usageLimits.ts` 한 곳 — 3.5
9. `md.account` 에는 `{ id, email }` 만 — 3.4
10. 계정 메뉴 문서 줄은 새 클래스, 90% 는 두 비율 중 하나 — 7장

### 가정으로 남긴 것 (확인하지 않았다)

- 서버가 429 에 **초 단위** `Retry-After` 를 싣는다 — F-2024 3.4 계약이 그렇고, WAF 대안의 헤더 모양은 확인하지 않았다(F-2024 9장 Q1 "조건식에 … 확인 못 함"). 날짜 형식이 오면 60초로 떨어진다
