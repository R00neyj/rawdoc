## 2. 전체 그림 (한 문단씩)

- **열려 있는 동안**: 로컬 문서의 댓글은 F-505 가 만든 그대로 편집기 `Y.Doc` 의 `comments` `Y.Map` 에 있다. 이 명세는 화면을 바꾸지 않는다
- **저장**: 본문이 저장될 때와 댓글이 바뀔 때, 편집기 상태 한 시점에서 본문 글과 기록(`CommentRecord[]`)을 함께 만들어 `store.update(id, { content?, comments })` 한 번으로 보낸다. `idbStore` 는 `docs` 행과 `comments` 행을 **한 IndexedDB 트랜잭션**에 쓴다. 기록의 위치 힌트는 그 순간 본문의 LF 글자 위치라 저장된 본문과 늘 맞는다
- **다시 열기**: 로컬 문서 편집기가 마운트되면 기록을 읽어 `restoreCommentEntries` 로 새 `Y.Doc` 에 다시 심고, **그 뒤에** F-504 표시를 붙인다. 자리를 못 찾은 첫 댓글은 앵커 없는 고아가 되어 레일 맨 아래로 간다(F-500 2.3)
- **로그인 이관**: F-208 이 로컬 문서를 outbox `createDoc` 으로 넣을 때 그 문서의 기록이 있으면 **바로 뒤에** `importComments` 를 넣는다. outbox 가 순서대로 보내므로 서버에 문서가 먼저 생긴다. 응답마다 버릴지 다시 보낼지는 7.2 표. 로컬 기록은 이관이 성공해도 실패해도 지우지 않는다(F-208 "로컬 `md-docs` 는 지우지 않는다")

## 3. 계약

### 3.1 저장소 — `md-docs` 스토어 `comments` 와 `Store` 에 더하는 것

```ts
// src/storage/idbStore.ts — md-docs 버전 6 스토어 'comments', keyPath 'docId'. 문서 하나에 행 하나
export type LocalCommentsRow = { docId: string; v: 1; records: CommentRecord[]; updatedAt: number }

// src/types.ts — Store
update(id: string, patch: { title?: string; content?: string; attachmentRefs?: string[]; comments?: CommentRecord[] }): Promise<Doc>
// 기록이 없으면 []. 행이 있는데 검사(parseCommentRecords, v === 1)를 통과하지 못하면 던진다 — Error('comments_row_invalid')
getCommentRecords?(docId: string): Promise<CommentRecord[]>
// 로그인 이관용. 검사를 통과한 행만 docId → 기록. 통과 못 한 행은 빼고 console.error('local_comments_row_invalid', docId)
listCommentRecords?(): Promise<Map<string, CommentRecord[]>>
```

- 스토어 이름 `comments`·키 `docId`·읽기 이름 `getCommentRecords` 는 **F-509 4.2 가 제안한 것 그대로**다. F-509 는 이 셋과 "금고 행에는 기록을 쓰지 않는다"(5.1 넷째 줄)를 쓴다
- 스토어 이름에 제품명이 없다(불변조건). 한 번 정하면 바꾸지 않는다 — 사용자 기록이 영구히 남는 자리다
- `idb`·`memory` 저장소만 두 메서드를 채운다. `server` 저장소는 채우지 않는다(서버 문서의 댓글은 방 Doc·`md-yjs` 에 있다, F-500 2.1)
- `withE2ee` 는 `...inner` 로, `withTabBroadcast` 는 `...store` 로, App 의 `setStore` 는 `...broadcastStore` 로 새 메서드를 넘긴다(코드 확인). 읽기라 탭 신호를 보내지 않는다
- `comments` 필드의 뜻: **없으면 기록 행을 건드리지 않는다. `[]` 면 행을 지운다. 1개 이상이면 행을 통째로 바꾼다**

### 3.2 `src/app/useDocSaver.ts`

```ts
useDocSaver({
  /* 기존 인자 그대로 */
  getComments?: () => CommentRecord[] | null,   // null = 이번 저장에서 기록 행을 건드리지 않는다
}): { status; notifyChange: () => void; notifyCommentsChange: () => void; flush: () => Promise<boolean> }
```

- 더러움 표지를 둘로 나눈다 — 본문(`notifyChange`)과 댓글(`notifyCommentsChange`)
- `notifyCommentsChange`: 막힘(`blocked`)이면 아무것도 안 한다. 아니면 댓글 표지를 켜고 상태를 `dirty` 로 두고 **기다리지 않고 곧바로** 저장을 돌린다(F-500 4.5 "700ms 기다리지 않는다"). 진행 중인 저장이 있으면 그 저장의 되풀이가 이어받는다(지금 `runSave` 의 `while` 과 같은 방식)
- 저장 한 번의 패치 — 규칙:
  - 본문 표지가 켜졌으면 `content`
  - `getComments()` 가 `null` 이 아니고 (본문 표지 또는 댓글 표지가 켜졌으면) `comments` — **본문만 바뀐 저장에도 기록을 다시 쓴다.** 위치 힌트가 저장된 본문과 늘 맞아야 하기 때문이다(F-500 4.5 "위치 힌트가 늘 정확하다"). 비용은 m1·m6 — 1MB·500 최악에서 기록 만들기 1.2ms + 트랜잭션 +1.8ms
  - 둘 다 없으면 저장하지 않는다
- `getText` 와 `getComments` 는 **같은 동기 구간에서 잇달아** 부른다(사이에 `await` 없음). 그래야 본문과 기록이 같은 편집기 상태에서 나온다
- 실패·문서 전환·`flush` 는 지금 규칙 그대로. 문서가 바뀌면 두 표지를 모두 버린다

## 4. `md-docs` 버전 6 — 업그레이드 경로

- `upgradeMdDocs` 에 `oldVersion < 6` 갈래 하나: `comments` 스토어를 keyPath `docId` 로 만든다. 색인 없음(키 하나로만 찾고, 이관은 `getAll` 한 번)
- **기존 사용자**: 버전 5 DB 를 가진 브라우저가 새 빌드를 열면 `openDB(…, 6)` 의 `upgrade` 가 이 갈래만 돈다. 기존 스토어·행은 그대로다. 메타 행 `schema` 의 `version` 은 지금처럼 `DB_VERSION` 으로 다시 쓴다(`upgradeMdDocs` 끝 줄)
- **옛 창이 열려 있을 때**: 지금의 F-136 3.3 흐름 그대로다 — 새 창은 부팅 화면에 `다른 창에서 이 앱이 열려 있습니다. 그 창을 닫거나 새로 고치면 계속됩니다.`, 옛 창은 대기 중 저장을 끝내고 연결을 닫은 뒤 `새 버전이 다른 창에서 열렸습니다. 이 창을 새로 고쳐 주세요.`. 이 명세가 새로 할 일은 없다(F-404 가 버전 5 로 올릴 때와 같다)
- 로그인 사용자도 `md-docs` 를 연다 — 로그인 이관의 `readLocal`(`createIdbStore()`)과 금고 행 함수(`openE2eeDb`)가 같은 `DB_VERSION`·`upgradeMdDocs` 를 쓴다. 두 길 모두 저절로 버전 6 이 된다
- 버전을 낮춰 여는 코드: `src/**` 에는 없다(모두 `DB_VERSION` 상수). e2e 는 `indexedDB.open('md-docs')`(버전 없음) 또는 `bootSkeleton.spec.js` 의 `open('md-docs', 1)`(다른 창 흉내 — 6 에서도 똑같이 막는다)이다. `scripts/measure.mjs` `seedDocs` 는 `open('md-docs', 4)` 인데 **버전 5 때부터 이미** 앱이 먼저 연 DB 보다 낮은 버전이라 `VersionError` 가 날 것으로 본다(코드 읽기로 판단, 돌려 보지 않았다 — 14장)

## 5. 쓰기 — 본문과 같은 트랜잭션

### 5.1 저장소 쪽 규칙 (`idbStore.update`, `memoryStore.update`, `serverStore.update`)

- `idbStore.update(id, patch)`:
  - 패치에 `comments` 가 있으면 트랜잭션 범위를 `docs` + `comments` 로, 없으면 지금처럼 `docs` 만
  - 같은 트랜잭션에서 `docs` 행을 읽는다. 없으면 **아무것도 쓰지 않고** 지금처럼 던진다
  - 본문 필드(`title`·`content`·`attachmentRefs`) 중 하나라도 있으면 지금처럼 행을 고치고 `updatedAt` 을 지금 시각으로. **본문 필드가 하나도 없으면(`comments` 만) `docs` 행을 쓰지 않고 `updatedAt` 도 그대로** — 사이드바 순서가 댓글로 흔들리지 않는다(서버 문서의 F-500 3.3 "댓글은 `updated_at` 을 올리지 않는다" 와 같게. 15장 Q2). 돌려주는 `Doc` 은 읽은 행 그대로
  - **읽은 행에 `e2eeKey` 가 있으면 `comments` 를 무시한다**(행을 쓰지도 지우지도 않는다) — F-509 4.2 "금고 행에는 기록을 쓰지 않는다". 금고 문서에는 기록이 살 자리가 없다(F-500 4.7), 그리고 기록에는 본문의 평문 인용이 있다(F-509 2.3)
  - 그 밖이면 3.1 끝의 뜻대로 행을 바꾸거나 지운다. 행의 `updatedAt` 은 지금 시각
  - 쓸 때 기록을 검사하지 않는다 — 검사는 읽을 때(m5). 쓸 때 검사해 던지면 본문 저장까지 막히기 때문이다. 쓰는 쪽(`buildLocalCommentRecords`)이 늘 검사를 통과하는 기록만 만든다(U18)
- `memoryStore.update`: 같은 규칙을 문서 `Map` 옆의 기록 `Map` 으로. 넣고 꺼낼 때 배열을 복사한다(문서 `clone` 과 같은 이유). 메모리 저장소에는 금고 문서가 없다
- `serverStore.update`: 패치의 `comments` 를 **버린다** — 캐시 행에도 outbox `updateDoc` 패치에도 싣지 않는다. 서버 문서는 이 길로 기록을 보낼 일이 없지만(App 이 로컬 경로에서만 `getComments` 를 넘긴다), 실수로 실리면 서버가 모르는 키로 400 을 돌려줘 본문 저장까지 버려지기 때문이다(`sendOne` 의 `invalid` 갈래)

### 5.2 언제 무엇을 쓰나

| 무엇이 바뀌었나 | 패치 | `docs` 행 | 기록 행 |
| --- | --- | --- | --- |
| 본문만 (댓글 있음) | `content` + `comments` | 고침, `updatedAt` 오름 | 새 위치 힌트로 통째로 바꿈 |
| 본문만 (댓글 없음) | `content` + `comments: []` | 고침 | 없으면 그대로 없음 |
| 댓글만 (달기·답글·해결·다시 열기·삭제) | `comments` | **안 씀** | 바꿈. 마지막 스레드를 지웠으면 행을 지움 |
| 둘 다 (700ms 안에 댓글도 바뀜) | `content` + `comments` | 고침 | 바꿈 |
| 되살리기 직후 | 없음 | — | — (되살리기 origin 은 저장을 부르지 않는다) |
| 되살리기 실패·전 | `content` 만 | 고침 | **건드리지 않음** (`getComments` 가 `null`) |

- 기록의 위치는 CM 이 편집 트랜잭션마다 매핑해 둔 범위(`handle.comments.ranges()`)를 쓴다. `RelativePosition` 을 저장 때마다 모두 풀면 1MB·항목 4,000개 문서에서 310ms(개요 c4)라 700ms 마다 멈춘다
- 기록 텍스트는 편집기 본문 LF(`handle.getText('lf')`)다. 저장되는 본문은 `lineEnding` 으로 바꾼 것(`getText(lineEnding)`)이지만, 다시 열 때 `createYBinding` 이 `toEditorText` 로 LF 로 되돌리고 서버 DO 도 같은 `toEditorText`(`src/lib/lineEnding.ts`, `worker/docRoomCore.ts` 가 import)를 쓰므로 위치가 그대로 맞는다
- 조합 중: 댓글 입력은 레일의 `textarea` 라 편집기 조합과 겹치지 않는다(F-505 8.3). 본문 저장이 조합 중에 도는 것은 지금과 같다 — `ranges()` 는 CM 필드를 읽기만 하므로 조합을 건드리지 않는다. 이 명세는 조합 중 미루는 재계산을 새로 두지 않는다
- 변화 알리기: 훅이 `handle.comments.map` 을 `observe` 해서 origin 이 `LOCAL_COMMENT_RESTORE_ORIGIN` 이 아닌 트랜잭션마다 `localComments.onChange()` 를 부른다. 되살리기를 마친 로컬 마운트에서만 관찰한다

## 6. 다시 열기 — 되살리기와 고아

### 6.1 순서 (로컬 경로 마운트마다)

1. 편집기가 마운트되고(`currentDocId`·`editorRemountNonce` 가 바뀔 때마다) 접근이 `write` 또는 `read` 이고 경로가 `local` 이면, `localComments.load(docId)` 를 부른다
2. 결과가 오면 — 그 사이 마운트가 바뀌었으면 버린다 — `restoreLocalComments(handle.comments, records)`
3. **그 뒤에** `handle.comments.attach(...)` (F-505 3장). 그래서 F-504 의 첫 풀기(`start`)가 되살린 항목을 함께 보고, F-505 의 "처음 열림"(첫 `onLayout` 의 열린 스레드 수, 5.1)과 해시 이동 판정 시점("local 경로면 첫 `onLayout`", 7.6)이 되살린 댓글을 본다
4. 되살리기를 마쳤다는 표지를 그 마운트에 둔다 — 이때부터 `localCommentRecords()` 가 `null` 이 아니고 `map` 관찰(5.2 끝)이 켜진다
- 읽기는 m6 기준 1ms 안팎이라 레일은 F-505 5.5 의 `불러오는 중…` 을 거의 보이지 않는다
- 로컬이 아닌 경로(실시간·view 등)는 이 순서를 거치지 않는다 — F-505 그대로 곧바로 붙인다

### 6.2 자리를 못 찾으면 (고아)

- `reanchor`(F-501 4.2): ① 저장된 `anchorFrom` 자리에서 인용문이 시작하면 거기 ② 아니면 인용문이 나오는 곳 중 앞뒤 32자가 가장 많이 맞는 곳, 같으면 힌트에 가까운 곳(후보 최대 1,000) ③ 없으면 고아
- 보통은 ①에서 끝난다 — 기록과 본문을 같은 트랜잭션으로 썼기 때문이다(m3: 500개 0.5ms). 힌트가 어긋나는 경우는 셋이다: 되살리기에 실패한 마운트에서 본문만 저장했을 때(5.2 표 끝 줄), 가져오기가 열린 로컬 문서의 본문을 덮어썼을 때(8장), 다른 코드가 본문만 바꿨을 때. 그때는 ②가 찾는다(m4: 1MB 되풀이 글 500개 223ms — 마운트 때 한 번)
- 고아는 **지우지 않는다**(F-500 2.3). 앵커 `null`·인용문 그대로 레일 맨 아래 `본문이 지워진 댓글` 묶음에 간다(F-505 5.4). 알림을 띄우지 않는다 — 묶음이 보인다
- 고아 기록은 다음 저장에서 `anchorFrom: null` 로 쓰이고, 그 뒤로는 다시 찾지 않는다(F-501 4.2 "고아 기록은 찾지 않음"). 같은 세션 안의 `Ctrl+Z` 되살리기(F-504 5.4)는 되므로, 되돌린 뒤 저장되면 다시 앵커가 있는 기록이 된다. **세션을 넘어서는 되돌리기가 없다** — 앵커 글을 지운 채 탭을 닫으면 그 댓글은 고아로 남는다(알려진 한계, 13장 사람 확인 아님)

### 6.3 읽기 실패

- `load` 가 던지면(`comments_row_invalid` 또는 IndexedDB 오류) 그 마운트 동안: 기록을 **덮어쓰지 않는다**(`localCommentRecords()` 가 `null` — 본문만 저장), 접근을 `read` 로 낮춘다(달기·답글·해결·삭제 없음 — 새로 단 댓글이 옛 기록을 지우는 것을 막는다), 오류 알림 한 번(9장 L1), `console.error('local_comments_read_failed', docId, err)`. 다음 마운트에서 다시 읽는다
- 이유: 읽지 못한 기록을 빈 것으로 보고 저장하면 `comments: []` 가 행을 지운다. 실패는 드물지만(같은 DB 가 이미 열려 있다) 되돌릴 수 없는 손실이다

### 6.4 다시 마운트되는 때

코드에서 로컬 문서 편집기가 새로 마운트되는 자리는 다음이다(`<Editor key={currentDocId:editorRemountNonce}>`). 모두 6.1 을 다시 돈다

| 자리 | 본문 출처 | 기록 |
| --- | --- | --- |
| 문서 열기·전환 | `store.get` (전환 전에 `beforeLeaveDoc` 이 대기 저장을 끝낸다) | 새로 읽음 — 마지막 저장과 같은 트랜잭션의 값 |
| 다른 탭에서 편집권을 되찾음 `handleClaimRegained` | `store.get` | 새로 읽음 — 편집권 탭이 마지막으로 쓴 값 |
| 가져오기 덮어쓰기 뒤(두 곳) | `store.get` — 가져온 본문 | 새로 읽음 — 가져오기는 `comments` 를 싣지 않아 옛 기록이 남고 새 본문에 `reanchor` 된다(8장) |

- 보기 모드 전환은 다시 마운트하지 않는다(`changeViewMode` 가 `handle.setViewMode` 만 부른다 — 코드 확인. 개요 c11 의 "모드 전환 다시 마운트" 는 지금 코드와 다르다, 14장)
- 편집권이 없는 탭(`claimReadOnly`)은 접근이 `read` 이고 저장이 막혀 있다. 기록은 마운트 때 한 번 읽은 값이고, 다른 탭의 새 댓글은 편집권을 되찾을 때 다시 마운트하며 보인다 — 본문과 같은 규칙(F-296)

## 7. 로그인 이관

### 7.1 넣는 순서 (F-208 2.2 확장)

1. App 의 `readLocal` 이 `createIdbStore()` 로 폴더·문서와 함께 `listCommentRecords()` 를 읽어 `LocalSnapshot.comments` 로 넘긴다. 이 셋은 한 트랜잭션이 아니다 — 이관은 부팅 때 저장소를 열기 전이라 로컬 문서를 쓰는 탭이 없다(로그인 상태의 앱은 `md-docs` 문서에 쓰지 않는다)
2. `migrateLocalIfNeeded` 의 안내 문서 빼기: **손대지 않은 안내 문서라도 기록이 1개 이상이면 옮긴다.** 댓글은 사용자가 쓴 것이다(15장 Q5)
3. `serverStore.importLocal({ folders, docs, comments })`: 지금처럼 문서마다 캐시에 쓰고 `createDoc` 을 넣은 **직후**, 그 문서의 기록이 1개 이상이면 `{ type: 'importComments', docId, records }` 를 넣는다. 캐시에 이미 있어 건너뛴 문서·금고 문서(지금도 건너뜀)·기록이 0개인 문서는 넣지 않는다
4. 알림·`md.localMigrated`·목록 새로고침은 지금 그대로(F-208 2.2 4~5번). 알림 문구의 `{N}` 은 문서 수 그대로 — 댓글 수를 세지 않는다

### 7.2 보내기와 응답 (`sendOne`)

- `importComments` 항목은 `importDocComments(docId, { records })` 를 부른다
- `createDoc` 보다 뒤 키라 같은 회차에서 문서가 먼저 만들어진다. `createDoc` 이 붙잡히면(413 `docs`·금고 간격 등) `findSendable` 이 같은 문서의 뒤 항목인 이 항목도 붙잡는다. `createDoc` 이 네트워크·5xx 로 멈추면 이 항목도 그 회차에 가지 않는다
- 응답 처리 — **공통 갈래(네트워크·5xx·401·429·`account_blocked`) 는 지금 `catch` 의 앞부분이 그대로 처리하고**, 그 바로 뒤, 금고 갈래(`handleE2eeApiError`)와 일반 `not_found` 갈래보다 **앞에** `importComments` 갈래를 둔다:

| 응답 | 처리 | 알림 | 이유 |
| --- | --- | --- | --- |
| 200 | 항목 지움, 계속 | 없음 | — |
| 409 `comments_exist` | 항목 지움, 계속 | 없음 | 방에 이미 댓글이 있다 — 개요 4.6 "outbox 는 그 항목을 조용히 버린다" |
| 409 `e2ee_doc` | 항목 지움, 계속 | 없음 | 그 사이 금고로 옮겨졌다. 금고 문서는 댓글 없음 |
| 404 `not_found` | **그 항목만** 지움(캐시 문서·같은 문서의 다른 항목은 그대로), 계속 | 없음 | 문서가 없거나(다른 기기에서 지움) 접근이 없다. 캐시 정리는 다음 `list()` 가 한다 — 댓글 이관 실패로 문서 캐시를 지우지 않는다(15장 Q6) |
| 403 `forbidden` | 항목 지움, 계속 | 없음 | 소유자가 아니다 — 다른 계정으로 로그인해 같은 id 로 다시 옮길 때(F-208 2.1 "다른 계정이면 다시 옮긴다")의 `createDoc` 409 `id_taken` 뒤에 온다. 그 경우 `createDoc` 쪽이 이미 알림을 띄운다 |
| 400 `invalid` / 413 / 409 그 밖 / `other` | 항목 지움, 계속. `console.error('comments_import_dropped', docId, kind)` | 없음 | 다시 보내도 같은 답이다. 사용자가 할 수 있는 것이 없다 — 로컬 기록은 남는다 |
| 5xx(503 `unavailable` 포함)·네트워크 | 지금 공통 갈래 — 이번 회차 멈춤, 항목 남김. 30초마다(`RETRY_INTERVAL_MS`)·`online` 때 다시 | 없음 | 방을 못 깨웠다(F-503 6.4) |
| 429 | 지금 공통 갈래 — 재개 시각까지 멈춤 | 지금 L1·L2 | — |
| 401 | 지금 공통 갈래 — `signedOut` | 지금 그대로 | — |
| 403 `account_blocked` | 지금 공통 갈래 — 차단 멈춤 | 지금 그대로 | — |

- F-503 8.3 의 제안(200·409·404·400·413 → 버림, 503·네트워크 → 다시)과 같고, 403 두 갈래와 404 에서 캐시를 건드리지 않는 점을 더했다
- 응답의 `imported`·`orphaned` 는 쓰지 않는다(화면에 보이지 않는다). 서버에서는 작성자·해결한 사람이 이관한 사용자가 되고 `mentions` 는 `[]` 라 알림이 생기지 않는다(F-503 5장, O14)

### 7.3 이관이 끝나기 전에 그 문서를 열면

- `hasPendingChanges(docId)` 가 `importComments` 항목도 센다 → 경로가 `pending`(F-305 4.1 3번)이라 실시간으로 붙지 않는다. `pending` 경로는 지금처럼 캐시 본문을 띄우고 PUT 으로 저장하며, 댓글은 C8(F-505 4장 `unavailable`)
- 이유: 이관 전에 실시간으로 붙어 누군가(나 포함) 댓글을 하나 달면 방이 비지 않아 `comments_exist` 로 로컬 댓글 전부가 옮겨지지 않는다. 기다리는 쪽이 잃는 것이 없다(15장 Q1)
- 이관이 끝난 뒤 다시 열면(문서 전환·새로고침) 실시간 경로가 되고, 방 Doc 에 이관된 댓글이 보인다
- `pending` 경로의 본문 `updateDoc` 은 `importComments` 보다 뒤 키다(`importLocal` 이 `createDoc` 바로 뒤에 넣었다). 그래서 서버는 이관 때 `createDoc` 본문 그대로를 보고 `reanchor` ①단계에서 끝난다(F-503 5장 끝)

### 7.4 로컬 기록을 지우는 때 — 이관은 지우지 않는다

- **이관이 성공해도, 버려져도(409·404·400 등), 대기 중이어도 로컬 기록은 그대로다.** F-208 2.2 "로컬 `md-docs` 는 지우지 않는다. 로그아웃하면 옮기기 전 로컬 문서가 그대로 보인다" — 로그아웃하면 로컬 문서가 댓글과 함께 보인다
- 그래서 "부분 실패 때 언제 지우나" 는 생기지 않는다. 버려진 이관은 다시 시도하지 않는다 — `md.localMigrated` 가 이미 그 계정 id 다(F-208 2.1). 로컬 기록이 남아 있으므로 사용자가 잃는 것은 없다
- 로그아웃 뒤 로컬 문서에 단 댓글은 같은 계정으로 다시 로그인해도 올라가지 않는다 — 본문과 같은 F-208 규칙
- 기록이 지워지는 때는 8장 표의 넷뿐이다

## 15. 열린 질문 — 모두 기본값 있음

### Q1. 이관을 기다리는 문서를 실시간으로 붙이지 않는다 — **기본값: 붙이지 않는다(`hasPendingChanges` 가 `importComments` 를 셈, 7.3)** · 사람이 한 번 보기를 권함

- 이유: 이관 전에 방에 댓글이 하나라도 생기면 `comments_exist` 로 로컬 댓글 전부가 버려진다(방이 비었을 때만 받는다 — 사용자 결정 2). 기다리면 잃는 것이 없다. 보통은 로그인 직후 몇 초 안에 끝난다
- 대가: `importComments` 가 5xx 로 계속 실패하면(예: DO RPC 인자 크기 — F-503 H3 가 의심한 것, 확인하지 않음) 그 문서는 그 동안 `pending` 경로(캐시 본문·PUT 저장·잠금, 댓글 C8)에 머문다. `createDoc` 이 계속 실패할 때와 같은 모양이다. outbox 에는 지금 어느 항목에도 다시 시도 횟수 한도가 없다
- 다른 안(세지 않음): 곧바로 실시간으로 붙는다. `hasPendingChanges` 한 줄과 U16 앞 절반이 빠진다. 대신 그 사이 댓글을 달면 이관이 409 로 조용히 버려진다(로컬 기록은 남는다)

### Q2. 댓글만 바뀐 저장은 `updatedAt` 을 올리지 않는다 — **기본값: 올리지 않는다(5.1)**

- 이유: 서버 문서는 댓글이 `docs.updated_at` 을 올리지 않는다(F-500 3.3, F-505 11.1 사이드바 규칙). 로컬도 같아야 로그인 전후로 사이드바 순서 규칙이 같다
- 다른 안(올림): `idbStore.update` 가 늘 행을 다시 쓴다(지금 코드 그대로). U3·E2 의 기대가 뒤집히고, 댓글을 달면 그 문서가 사이드바 맨 위로 간다

### Q3. 파일 목록이 개요와 다르다 — **기본값: 1장 표대로**

- 더한 것: `memoryStore.ts`(+test) — `Store` 계약이 같아야 한다(architecture.md 2장 "`memoryStore` 와 `idbStore` 는 같은 모양"). `types.ts` — `Store` 타입. `App.tsx` — 저장 훅·댓글 훅·이관 `readLocal` 을 잇는 자리가 App 뿐이다. 테스트 파일 넷
- 다른 안: 메모리 저장소는 기록을 안 남긴다(두 메서드를 채우지 않음). 파일 둘이 빠지고, IndexedDB 를 못 쓰는 브라우저에서는 문서를 바꿨다 돌아오면 댓글이 사라진다(본문은 남는데)

### Q4. 기록을 읽지 못하면 그 마운트는 읽기만 — **기본값: 읽기만 + 알림 L1(6.3)**

- 이유: 빈 것으로 보고 쓰면 행을 지운다 — 되돌릴 수 없다
- 다른 안(빈 것으로 계속): 알림·접근 낮추기가 빠지고, 읽기 실패 뒤 첫 저장이 옛 기록을 지운다

### Q5. 손대지 않은 안내 문서라도 댓글이 있으면 옮긴다 — **기본값: 옮긴다(7.1 2번)**

- 이유: F-208 이 안내 문서를 빼는 까닭은 "기기마다 새 id 로 만들어져 계정에 쌓인다" 인데, 댓글을 단 안내 문서는 사용자가 쓴 것을 담고 있다. 본문 비교만으로는 댓글을 보지 못한다
- 다른 안(지금 규칙 그대로): `migrateLocal.ts` 한 줄과 U22 둘째 칸이 빠진다. 그 댓글은 로컬에만 남는다

### Q6. 이관 404 는 그 항목만 지운다 — **기본값: 그 항목만(7.2)**

- 이유: 지금 outbox 의 일반 `not_found` 갈래는 캐시 문서와 그 문서의 outbox 항목을 모두 지운다. 댓글 이관 하나의 답으로 문서 캐시를 지우는 것은 이 항목의 책임 밖이고, 문서가 정말 없으면 다음 `list()` 가 맞춘다
- 다른 안(일반 갈래 그대로): 새 갈래가 404 를 다루지 않는다. U13 의 "404 뒤에도 캐시 행이 남는다" 가 뒤집힌다

### Q7. 전체 내보내기(zip)·옵시디언 내보내기에 댓글을 넣지 않는다 — **기본값: 넣지 않는다(8장)**

- 이유: F-500 사용자 결정 9 "`.md` 내보내기 바이트는 절대 댓글을 포함하지 않는다" 와 1.1 "전체 내보내기·옵시디언 내보내기는 `Y.Text` 에서만" 이 이미 정했다. 이 명세는 그 결과(백업을 다른 기기로 옮기면 로컬 댓글이 없다)를 적을 뿐이다
- 다른 안(별도 파일로 싣기): 새 명세가 필요하다 — zip 안 댓글 파일 형식, 가져오기의 되살리기, F-2020·F-282 계약 변경
