## 3. `/help` 를 빌드에 어떻게 끼워 넣나 — 개요가 미룬 결정 1

`buildSite` 는 `content: Record<상대경로, 원문>` 하나만 받는다(`site/build.ts:9~13`). `/help` 만 원본이 `content/` 밖이라 이 구조에 들어갈 자리가 없다. 세 가지를 비교했다.

### 3.1 방법 비교

| # | 방법 | F-272 에서 바뀌는 것 | 판정 |
| --- | --- | --- | --- |
| (a) | `vite.config.ts` 의 `sitePlugin` 이 `helpDoc` 를 읽어 `content['help.md']` 로 주입 | `vite.config.ts` 62~66행 + `runnerImport` 한 번 더(F-272 3.4 "빌드마다 한 번만"). **플러그인이 "파일 입출력만" 한다는 F-272 3.2 규칙을 깬다** — 프론트매터 조립이 `vite.config.ts` 로 들어온다 | 안 쓴다 |
| (b) | **`site/build.ts` 가 `HELP_DOC_CONTENT` 를 직접 읽어 글 목록에 더한다** | `site/build.ts` 두 줄 + 새 모듈 하나. `SiteInput`·플러그인·`vite.config.ts`·`wrangler.jsonc` **무변경** | **쓴다** |
| (c) | `SiteInput` 에 `help: string` 같은 입력을 더한다 | `site/build.ts` 의 공개 타입 + `vite.config.ts:80` 의 `const input: SiteInput = { content, appCssHref, builtAt }` 가 함께 바뀐다. 결국 (a) 와 같은 자리를 건드린다 | 안 쓴다 |

(b) 를 고르는 근거:

- **의존 방향이 이미 허용된다.** `specs/architecture.md:69` — `site → src` 는 한 방향이고 `site/render.ts:3` 이 이미 `src/viewer/renderMarkdown` 을, `site/build.ts:5~7` 이 `src/lib/siteChrome`·`src/lib/siteMeta`·`brand.config` 를 import 한다

- 글 하나가 `content/` 밖에 있다는 사실이 `site/` 안쪽에만 머문다. 빌드 파이프라인(가드 → 주소 매핑 → 렌더 → sitemap)은 다른 글과 **완전히 같은 길**을 탄다

### 3.2 `site/helpPage.ts` (신규)

```ts
// 도움말은 content/ 에 글 파일이 없다 — 앱과 같은 원본(src/app/helpDoc.ts)에 프론트매터만 붙여 글 하나처럼 넘긴다 (F-274.md 3장)
import { HELP_DOC_TITLE, HELP_DOC_CONTENT } from '../src/app/helpDoc'

export const HELP_CONTENT_PATH = 'help.md'

const HELP_SUMMARY = '앱 사용법과 마크다운 문법을 한 페이지에 모았습니다.'

export function helpContent(): string {
  return `---\ntitle: ${HELP_DOC_TITLE}\nsummary: ${HELP_SUMMARY}\n---\n${HELP_DOC_CONTENT}`
}
```

- `title` 은 `HELP_DOC_TITLE`(`'도움말'`)을 그대로 쓴다 — 제목도 한 원본이다
- `summary` 는 `<meta name="description">`·`og:description` 이 된다(`site/render.ts:36`). **제품명을 쓰지 않는다** — `CLAUDE.md` 불변조건이고, `src/app/helpDoc.test.ts:132` 도 원문에 제품명이 없음을 이미 검사한다
- `date`·`updated` 는 **넣지 않는다.** `sitemap.xml` 의 `lastmod` 는 `site/build.ts:77` 이 빌드 시각으로 채운다 (10장 Q1)
- **닫는 `---` 뒤에 빈 줄을 두지 않는다.** 두면 `textAfterFrontmatter` 가 앞에 `\n` 을 남겨 본문 HTML 의 `data-source-line` 이 1씩 밀리고, 앱과 바이트가 달라진다. 2026-09-21 실측:

```
"---\ntitle: 도움말\n---\n"    -> body "# 도움말\n\n## 이 "  앱 HTML 과 identical: true
"---\ntitle: 도움말\n---\n\n"  -> body "\n# 도움말\n\n## 이"  앱 HTML 과 identical: false (data-source-line 만 다름)
```

### 3.3 `site/build.ts` 변경

`buildSite` 안, `mdEntries` 를 만드는 자리(69행) 하나만 바꾼다.

```ts
const fileEntries = Object.entries(input.content).filter(([relPath]) => relPath.endsWith('.md'))
if (fileEntries.some(([relPath]) => relPath === HELP_CONTENT_PATH)) {
  throw new Error(`content/${HELP_CONTENT_PATH}: 도움말은 src/app/helpDoc.ts 가 원본입니다 — content/ 에 두지 않습니다`)
}
const mdEntries: [string, string][] = [...fileEntries, [HELP_CONTENT_PATH, helpContent()]]
```

- 아래 `for` 반복문·가드·렌더·`sitemap`·링크 목록 검사는 **그대로 둔다**. 도움말도 `checkContentFile` → `contentUrl` → `renderSitePage` 를 똑같이 탄다
- 중복 검사를 두는 이유: `contentUrl('help.md')` 가 `/help` 를 돌려주게 되면 누군가 `content/help.md` 를 만들어도 가드 G2 를 통과한다. 그러면 `out['help.html']` 이 조용히 덮어써지고 `sitemap.xml` 에 `/help` 가 두 번 들어간다. **에러로 막는다**
- 도움말을 **맨 뒤에** 붙인다. `content/` 글이 가드에 걸리면 그 에러가 먼저 나와야 사람이 자기가 고친 파일을 본다
- `sitemap.xml` 은 `site/build.ts:94` 에서 주소 오름차순으로 정렬되므로 순서 영향이 없다

### 3.4 `site/pages.ts` 변경

`contentUrl` 에 한 줄 더한다.

```ts
// 도움말만 content/ 에 파일이 없다 — site/build.ts 가 src/app/helpDoc.ts 로 만들어 넣는다 (F-274.md 3장)
if (relPath === 'help.md') return '/help'
```

`urlToFile('/help')` 는 지금 코드가 그대로 `'help.html'` 을 낸다(`site/pages.ts:18~21`, 문자열 규칙). 고칠 것 없다.

### 3.5 성능

2026-09-21 실측(Node 24.12, Vite 7.3.6, 20회 평균): `renderSitePage` 로 도움말 한 장을 만드는 데 **1.37ms**, 결과 HTML **11,499바이트**. `runnerImport` 는 이미 빌드마다 한 번 돌고 있고 이번에 늘지 않는다. 빌드 시간에 실질적 영향이 없다.

### 4.2 가드에 예외를 두지 않고 글을 고친다

**그 캡션은 지금 앱 도움말에서도 잘못 그려지고 있다.** 2026-09-21 `renderMarkdown(HELP_DOC_CONTENT)` 실행 결과:

```html
표준 문법 <a href="%EC%A3%BC%EC%86%8C" target="_blank" rel="noopener noreferrer">이미지: 설명</a>으로 직접 쓴 외부 이미지는 …
```

`![설명](주소)` 를 글자로 보여 주려던 자리가 `/주소` 로 가는 **죽은 링크**가 됐다(F-123 이미지 → 링크 치환 규칙이 그대로 먹었다). 가드가 걸린 것이 아니라 가드가 버그를 찾아낸 쪽이다. 그래서 가드에 예외를 두지 않고 문장을 고친다.

`src/app/helpDoc.ts:69~71` 의 `caption` 을 **이 문장으로 교체한다**:

```
붙여넣기·끌어넣기로 넣은 이미지만 이렇게 보입니다. 주소를 직접 적는 표준 이미지 문법은 오프라인에서도 항상 보이도록 이미지 대신 `이미지: 설명` 링크로 바뀝니다.
```

- **인라인 코드로 감싸는 것만으로는 안 된다.** 가드는 원문 검사다(F-272 9장, `site/guard.ts:1` 주석). `` `![설명](주소)` `` 도 `IMAGE_SYNTAX_RE` 에 그대로 걸린다. 문자열 자체를 없애야 한다
- 고친 문장으로 2026-09-21 재실측: `checkContentFile` 이 `{ title: '도움말' }` 을 돌려주고(통과), 렌더 결과에 `<code>이미지: 설명</code>` 이 나오며 `%EC%A3%BC%EC%86%8C` 링크가 사라진다
- 이 문장은 앱 `#/help`·`내 문서로 복사` 결과에도 똑같이 반영된다. 한 원본이라 그렇게 되는 것이 맞다
- 기존 설명이 담던 정보("표준 문법으로 직접 쓴 외부 이미지는 링크로 바뀐다")는 그대로 남는다. 잃는 것은 문법 기호 예시 하나뿐이고, 그 예시는 애초에 링크로 뭉개져 보이지 않았다

### 4.3 가드가 앞으로 하는 일

도움말 항목이 `checkContentFile` 을 타므로, 나중에 누가 `helpDoc.ts` 에 mermaid 펜스·이미지 문법·`{{…}}` 를 넣으면 **`npm run build` 가 실패한다.** 그 실패를 빌드보다 먼저 보게 하려고 같은 검사를 단위 테스트로도 둔다(A3, `site/helpPage.test.ts`).

- 이 검사는 `site/helpPage.test.ts` 에 둔다. `src/app/helpDoc.test.ts` 에 두면 `src/` 가 `site/` 를 import 하게 되어 의존 방향(`specs/architecture.md:69`)을 어긴다
- `src/app/helpDoc.ts` 맨 위 주석에 "이 문서는 공개 사이트 `/help` 로도 나간다 — 이미지·mermaid 문법을 쓰면 빌드가 실패한다 (F-274)" 한 줄을 더한다

## 5. 앱 `#/help` 와 사이트 `/help` — 어디까지 같은가 (개요가 미룬 결정 3)

"내용이 한 원본" 이 실제로 성립하는지 **두 경로의 HTML 을 만들어 비교했다**(2026-09-21).

- 앱: `src/app/HelpPage.tsx:11` `renderMarkdown(HELP_DOC_CONTENT)`
- 사이트: `site/render.ts:86` `renderMarkdown(textAfterFrontmatter(raw, frontmatter))`

결과: **두 문자열이 바이트까지 같다**(3.2 의 프론트매터 형식을 쓸 때). 닫는 `---` 뒤에 빈 줄을 두면 `data-source-line` 숫자만 1씩 밀리고 나머지는 같다.

같은 렌더러를 쓰므로 렌더 결과가 갈릴 여지는 없고, 갈리는 곳은 **렌더 뒤에 앱이 DOM 을 더 만지는 부분**뿐이다.

| 항목 | 앱 `#/help` | 사이트 `/help` | 이번 결정 |
| --- | --- | --- | --- |
| 본문 HTML | `renderMarkdown` 결과 | 같은 문자열 | **같게 못박는다** — A2 가 바이트 비교 |
| 위키링크 `[[문서 제목]]` | `HelpPage` 가 `env.resolveWikiLink` 를 넘기지 않아 `<span class="wikilink wikilink--plain">` — **앱에서도 눌리지 않는다** | 같다 | 같다. 손대지 않는다 |
| 체크박스 `- [ ]` | `<input type="checkbox" disabled>` 2개 | 같다 | 같다 |

| 오른쪽 목차 | 있다 (F-249 `Outline`) | 있다 (F-2036, 스크립트 없는 늘 펼친 목록) | **모양만 같게** — F-2036 이 `.outline-item` 모양을 빌려 쓴다. 제목 id 는 사이트 빌드가 붙인다(2026-09-24 사용자) |

**경계 한 줄 요약: 마크다운 원문과 그 렌더 결과까지는 같고, 렌더 뒤 자바스크립트가 더하는 것(코드 복사 버튼·목차·테마·앱 버튼)부터는 다르다.**

`#/help` 가 사이트 `/help` 와 같은 내용이어서 색인이 겹치는지도 확인했다 — 겹치지 않는다. 앱 도움말은 해시 경로라 크롤러가 보는 주소는 `/` 이고, 쿠키·localStorage 가 없는 크롤러는 `/` 에서 랜딩을 받는다(F-270 2장, `wrangler.jsonc:17` `run_worker_first` 에 `/`). 색인되는 도움말 주소는 `/help` 하나다.
