  - 지금 `dist/assets` 의 큰 청크: `createEditor-*.js` 1,694,316 B, `index-*.js` 644,370 B. `App.tsx` 가 `../editor/Editor` 를 정적으로 import 하므로 두 청크 모두 시작 때 받는다 — 새 코드가 어느 청크에 들어가든 시작 비용은 같다
- (b) **WebSocket 을 받지 않는 서버에 붙으면** — `vite preview`(e2e 가 쓰는 것)에 `new WebSocket('/ws/doc/x')`: `open` 없이 `error` → `close 1006` 이 **약 9ms** 에 온다. 기존 fakeServer e2e 는 모두 이 경로를 탄다(18장)
- (c) **Playwright `routeWebSocket`** — 페이지 이동 **전에** 등록해야 처리기가 불린다(이동 뒤 등록하면 안 불렸다)
  - 처리기에서 곧바로 `close({ code: 4401, reason: 'unauthenticated' })`: 페이지는 `open` 없이 `close 4401 unauthenticated`, `wasClean true`
  - 처리기가 먼저 메시지를 보낸 뒤 닫으면: 페이지는 `open` → 메시지 → `close 4403 revoked`
  - 이진 `Buffer` 는 양방향으로 그대로 오간다
- (d) **`YProvider` + Node 가짜 sync 서버**(`yjs` + `y-protocols/sync` + `lib0`)
  - `connect: false` 로 만들고 `awareness.setLocalState(null)` 뒤 `connect()`: 상태 `connecting` → `connected` 6ms, `synced` 12ms, 서버의 `content`·`title` 을 받음
  - URL: `ws://localhost:4591/ws/doc/{id}?_pk={10자}` (`prefix` + `protocol: 'ws'`)
  - `disableBc: true` 면 `bcconnected` false
  - `setLocalState(null)` 을 연결 전에 부르면 awareness 메시지를 한 통도 보내지 않았다
  - 로컬 삽입이 서버 Doc 에 닿음
- (e) **`YProvider` 내장 재연결의 실제 모양**
  - 서버가 받아 준 뒤 20ms 만에 `1013` 으로 닫기를 되풀이: **2초에 15번, 간격 약 141ms 로 쉬지 않음.** 열릴 때마다 `wsUnsuccessfulReconnects` 가 0 으로 돌아가 백오프가 자라지 않는다
  - 열리기 전에 `1011` 로 닫기: 간격 217·411·804·1,611ms(상한 2,500)
  - `4403` 으로 닫아도 처리기가 없으면 다시 연결한다. `connection-close` 처리기 안에서 `disconnect()` 를 부르면 1.5초 동안 재연결 0번
- (f) **`YProvider` 소스에서 확인한 것**(`dist/provider/index.js`): `synced` 는 sync step 2 를 받을 때. 이벤트 `connection-close`(CloseEvent, provider)·`connection-error`·`status`(`connecting`|`connected`|`disconnected`)·`custom-message`(`__YPS:` 접두 떼고). `__YPS:` 없는 문자열 메시지는 무시한다(`pong` 포함). `sendMessage` 는 `__YPS:` 를 붙이므로 날 `ping` 은 `provider.ws.send` 로만 보낼 수 있다. 메시지 시간 제한(죽은 연결 감지)이 없다. awareness 기본값은 `new Awareness(doc)` 이고 주기 타이머를 끈다. `window` `unload` 처리기를 단다. `destroy()` 는 끊고 처리기를 뗀다. `connect()` 는 비동기(`params` 풀이). `WebSocketPolyfill` 옵션이 있다
- (g) **타입** — 스크래치패드 tsconfig(`moduleResolution: bundler`, TS 6)에서 `import YProvider from 'y-partyserver/provider'` 와 `p.ws`·`p.on(...)`·`p.awareness.setLocalState(null)` 가 타입 검사를 통과(`TSC_OK`)

## 3. 전체 흐름

```
문서 열기 (currentDocId 바뀜)
 └ decideDocPath ─┬ local/view/pending ── 지금과 같음 (store.get → 편집기)
                  ├ fallback(offline) ─── 지금과 같음 + 상태바 `.statusbar-live`
                  └ realtime ─ useLiveDoc: 빈 방 Doc + YProvider 연결
                       │  상태바 `불러오는 중…`, 편집기 없음
                       ├ synced ─────────── 방 Doc 상태로 편집기 마운트, 편집 가능, PUT·잠금 없음
                       │    ├ 끊김(그 밖의 코드) → `연결 끊김 · 다시 연결 중` → 백오프 재연결 → synced
                       │    └ 4401/4403/4404 → 멈춤, 읽기 전용 + 알림 (폴백하지 않는다, F-301 8.2)
                       ├ 연결 전 닫힘 / 10초 시간 제한 / offline → fallback: store.get → 편집기, 잠금 + PUT
                       ├ 4401 → fallback (로그인 필요 표시는 기존 signedOut 흐름)
                       ├ 4403 → 보기로 열기 (forbiddenDocIds)
                       └ 4404 → 캐시 본문을 읽기 전용으로 + 알림
```

- 한 번 정한 경로는 **그 문서 열기 세션**(같은 `currentDocId` 가 유지되는 동안, 새로고침 전까지) 동안 바뀌지 않는다. 폴백 세션이 나중에 실시간으로 올라가지 않고, 실시간 세션이 폴백으로 내려가지 않는다(F-301 8.1·8.2)
- 편집기 다시 마운트(`editorRemountNonce`)는 세션을 새로 시작하지 않는다. 실시간 경로에서 다시 마운트하면 같은 방 Doc 의 지금 상태로 새 편집기 Doc 을 만든다(9.1)

## 5. 첫 동기화와 그동안 화면 — F-301 3.3 결론

### 5.1 편집기를 첫 동기화 전에 띄우지 않는다 (22장 Q1)

- 실시간 경로면 App 은 **`openDoc` 을 첫 `synced` 뒤에야 채운다.** 그 전에는 편집기가 마운트되지 않는다(`.cm-content` 가 없다)
- 그동안: 편집 영역 자리는 빈 채(스켈레톤 없음), 상태바 `.statusbar-save` 는 `불러오는 중…`(`ia.md` 6장에 이미 있는 문구, 11.1). 사이드바·상단바는 평소대로 쓸 수 있다. 제목은 편집기 안 위젯이라 이때 안 보인다
- F-301 3.3 은 "첫 동기화까지 에디터는 읽기 전용" 이었다. 읽기 전용 편집기를 먼저 띄우지 않는 이유:
  1. **무엇을 보여 줄지가 없다.** F-304 11.3 1번 때문에 방 Doc 은 비어서 시작해야 한다. 캐시 본문을 보여 주려면 따로 읽기 전용 편집기를 띄우고 동기화 뒤 방 Doc 으로 **다시 마운트**해야 한다 — 스크롤·포커스가 튀고, 캐시와 서버가 다르면 본문이 바뀌어 보인다
  2. **기존 e2e 와 부딪친다.** 기존 서버 e2e 는 문서를 열자마자 `.cm-content` 를 눌러 친다. Playwright 는 요소가 생길 때까지 기다리지만 읽기 전용 편집기에는 곧바로 입력을 보낸다 — 그 입력이 사라진다. 편집기가 없으면 Playwright 가 기다려 준다
  3. 첫 동기화는 로컬에서 12ms(측정 d). 배포 환경 값은 모른다(21장) — U12 를 사람 확인으로 잰다(19.4 H5)

### 5.2 실시간 경로의 열기 순서

1. `useLiveDoc` 가 빈 `Y.Doc`(이하 **방 Doc**)을 만들고 제어기를 시작한다(7장). 문서 열기 effect 는 이 경로에서 `store.get` 으로 `openDoc` 을 채우지 않는다
2. 첫 `synced` 가 오면 App 은 한 렌더 안에서:
   - `openDoc = { id, content: 방 Doc 의 content 문자열, lineEnding: 사이드바 메타(docs 의 그 문서)의 lineEnding }` — `lineEnding` 은 내보내기용이고 D1 에 쓰는 것은 DO 가 D1 값으로 정한다(F-304 7.1)
   - 사이드바 메타의 제목을 방 Doc 의 `title` 로 맞춘다
   - 글자·단어 수를 방 Doc 의 본문으로 계산한다
   - `Editor` 에 `live={{ roomDoc, onRemoteTitle }}` 를 넘긴다
3. 편집기는 방 Doc 상태로 편집기 Doc 을 만들고 게이트를 세운다(9.1·9.2). 이 뒤로는 F-303 과 같다 — 방 Doc 이 공유 Doc 이다
4. 5.1 동안 사용자가 다른 문서로 옮기면 세션을 버린다(방 Doc·제어기 `destroy`). 늦게 온 `synced` 는 무시된다

### 5.3 방 Doc 에는 브라우저가 한 글자도 심지 않는다 (F-304 11.3 1번)

- 방 Doc 은 빈 채 `YProvider` 에 붙는다. 편집기 Doc 은 방 Doc 이 **서버 상태를 받은 뒤** 그 상태를 그대로 옮겨 만든다 — 편집기 Doc 이 방 Doc 에 없는 구조를 갖는 일이 없다
- F-304 11.3 1번은 "편집기 `Y.Doc` 을 비운 채 만들고" 라고 적었다. 이 명세는 편집기 Doc 을 방 Doc 에서 **복제**해 만든다. 목적(씨앗이 두 벌 되지 않음)은 같고, 편집기 Doc 을 비운 채 게이트를 세우면 첫 동기화 전 편집을 막을 방법이 따로 필요해서다(20장 F-304 11.3 갱신)

### 6.2 규칙

- **시도 한 번 = `YProvider` 하나.** 옵션: `connect: false`, `prefix: DOC_SOCKET_PREFIX + docId`, `protocol` 은 `secure` 에 따라 `'wss'`/`'ws'`, `disableBc: true`(22장 Q4), `WebSocketPolyfill` 은 주어졌을 때만. 만든 직후 `awareness.setLocalState(null)` 을 부르고 그다음 `connect()`
  - awareness 를 끄는 이유: 서버는 awareness 한 통마다 DO 를 깨운다(F-304 11.3 7번). F-305 단독으로는 끈다. F-307 부터 `useLiveDoc` 가 늘 awareness 를 넘긴다(F-307 5.1). 연결 전에 끄면 한 통도 나가지 않는다(측정 d)
  - `disableBc: true`: `BroadcastChannel` 로 탭끼리 주고받는 길은 F-303 게이트를 지나지 않는 두 번째 입구다(F-304 11.3 6번). 같은 브라우저의 두 탭도 각자 WebSocket 으로 붙는다
- `connection-close` 가 오면 **곧바로** `provider.destroy()` 와 `awareness.destroy()` 를 부르고 `onClose(code, reason, opened)` 를 한 번 부른다. `opened` 는 이 시도에서 `status: connected` 를 본 적이 있는가다
  - 내장 재연결을 쓰지 않는 이유: 받아 준 뒤 닫히는 경우 약 141ms 간격으로 끝없이 다시 붙는다(측정 e). F-301 9.2 의 1초~30초 지터 백오프는 제어기가 한다(7.3)
  - `connection-error` 는 무시한다 — 뒤따르는 `connection-close` 로 처리한다
- `synced` 이벤트가 `true` 로 오면 `onSynced`. 한 시도에서 여러 번 와도(재동기화) 처음 한 번만 부른다
- `custom-message` → `onCustom`. `provider.ws` 의 날 `message` 이벤트에서 문자열이 정확히 `SOCKET_PONG` 이면 `onPong`(`YProvider` 는 `__YPS:` 없는 문자열을 무시하므로 따로 들어야 한다 — 측정 f)
- 같은 방 Doc 에 새 시도마다 새 `YProvider` 를 붙인다. 이전 provider 는 이미 `destroy` 되어 방 Doc 에서 처리기가 떨어져 있다. 재연결 때 sync step 1·2 가 두 쪽 상태를 맞춘다 — 방 Doc 에는 서버에서 온 구조와 이 브라우저의 편집만 있으므로 두 벌이 되지 않는다
- `awareness` 를 주면(F-307): 그 인스턴스를 `YProvider` 옵션 `awareness` 로 넘기고, `setLocalState(null)` 도 `destroy` 도 하지 않는다 — 주인은 넘긴 쪽이고 재연결 시도마다 같은 인스턴스를 넘긴다. 안 주면 위 규칙(끄고, 닫힐 때 `destroy`). F-307 입력 계약 ①(`specs/features/F-307.md` "입력 계약")은 awareness 를 `connectRemote`·`YLinkPort` 로 provider 팩토리에 넘기는 배선을 가정했지만, 이 명세에서 provider 는 편집기가 아니라 `useLiveDoc`(App 층)가 만들고 포트를 거치지 않는다(9.2). awareness 는 방 Doc 과 같이 `useLiveDoc` 가 들고 편집기에 `live` 옵션으로 내려보내는 모양이 맞는다 — F-307 이 정한다(20장)
- 이 파일만 `y-partyserver/provider` 를 import 한다. `src/storage` 에 두는 이유: 네트워크 입출력이고 `architecture.md` 1장 의존 방향(`app → storage → lib`)에 맞다. `docRoomProtocol` 을 `src/lib` 에서 읽는다

### 7.2 닫기 분류 — **코드가 먼저**, 그다음 첫 동기화 전후

**F-306 갱신(2026-09-24)**: 아래 표는 `resumable`(영속 기록이 있어 재개 가능한 세션)이 거짓인 지금까지의 세션 그대로다. `resumable` 이 참인 세션은 "폴백" 이 되는 자리가 전부 `reconnecting` + `ready: true` 로 바뀐다 — 재개 가능 세션은 폴백하지 않는다(F-306 6.2·6.3). 새 열이 더해진 표는 F-306 6.3 에 있다

| 닫기 | 첫 동기화 전(`everSynced` 거짓) | 첫 동기화 뒤 |
| --- | --- | --- |
| `4401` | `fallback` / `signed-out` | `stopped` / `signed-out` |
| `4403` (reason 무관) | `stopped` / `forbidden` | `stopped` / `revoked` |
| `4404` (reason 무관) | `stopped` / `not-found` | `stopped` / `deleted` |
| 그 밖, 이 시도에서 **열린 적 없음** | `fallback` / `unreachable` **곧바로** (22장 Q2) | `reconnecting`, 백오프 |
| 그 밖, 열린 적 있음(`1011`·`1013`·`1006` 등) | 백오프 재시도(첫 동기화 시간 제한 안에서) | `reconnecting`, 백오프 |
| pong 시간 제한(7.4) | 해당 없음(연결 전에는 ping 안 함) | `reconnecting`, 백오프 |

- reason 문자열(`forbidden`/`revoked`, `not_found`/`deleted`)로 가르지 않는다 — 같은 코드의 뜻은 "첫 동기화 전이냐 뒤냐" 로 이미 갈리고, 서버가 reason 을 바꿔도 클라이언트가 깨지지 않는다
- 배포 환경에서 Worker 의 거절(F-304 4.2)은 101 뒤 닫으므로 브라우저가 `open` 을 먼저 볼 수 있다. 로컬 `routeWebSocket` 은 `open` 없이 닫았다(측정 c). **어느 쪽이든 44xx 는 코드로 갈리므로 결과가 같다**
- `stopped`·`fallback` 은 끝 단계다. 소켓을 닫고 모든 타이머를 멈추고 다시 시도하지 않는다
- 첫 동기화 뒤에는 **어떤 경우에도 폴백하지 않는다**(F-301 8.2 — 실시간으로 편집한 세션이 PUT 으로 내려가면 DO 와 D1 이 갈린다)

### 7.3 재연결 백오프 (F-301 9.2)

- 실패 횟수 `n`(마지막 `synced` 이후 닫힌 횟수, 1부터): 대기 = `min(RECONNECT_BASE_MS × 2^(n−1), RECONNECT_MAX_MS) × (1 − RECONNECT_JITTER + 2 × RECONNECT_JITTER × random())`
  - `random()` 이 0.5 일 때 1,000 → 2,000 → 4,000 → 8,000 → 16,000 → 30,000 → 30,000 …ms
- `synced` 를 받으면 `n = 0`
- `wake()`(온라인 복귀·창이 다시 보임): `reconnecting` 이고 대기 중이면 **곧바로** 시도하고 `n` 은 그대로 둔다. `live` 면 ping 을 한 번 보낸다(7.4). `connecting` 에서 대기 중이면 곧바로 시도
- `goOffline()`: `live` 면 소켓을 닫고 `reconnecting` 으로(대기 타이머는 걸지 않는다 — `wake` 가 깨운다). 첫 동기화 전이면 `fallback` / `offline`
- 지터가 필요한 이유: 배포나 DO 재시작으로 여러 사람이 한꺼번에 끊기면 같은 박자로 몰려 붙는다

### 7.4 keepalive 와 죽은 연결

- `live` 인 동안 `keepaliveMs` 마다 `ping()`. `null` 이면 주기 ping 은 없다(`wake` 의 한 번짜리 ping 은 남는다)
- ping 을 보낸 뒤 `PONG_TIMEOUT_MS` 안에 `onPong` 이 없으면 소켓을 닫고 "열린 적 있음, 그 밖의 코드" 로 처리한다(7.2)
- `YProvider` 에는 메시지 시간 제한이 없다(측정 f) — 노트북 덮개를 닫았다 연 경우처럼 TCP 가 조용히 죽으면 ping 없이는 알 수 없다
- 서버는 `ping` 을 DO 를 깨우지 않고 런타임이 `pong` 으로 답한다(`worker/docRoom.ts` `setWebSocketAutoResponse`). 요금에 잡히는지는 H363 이 판정한다(13장)

### 7.5 첫 동기화 시간 제한

- `start()` 부터 `FIRST_SYNC_TIMEOUT_MS` 가 지나도 `synced` 가 없으면:
  - 지금 열린 소켓이 없다(대기 중이거나 연결 중) → `fallback` / `timeout`
  - 열린 소켓이 있다(서버가 받아 줬고 상태를 보내는 중 — 큰 문서) → `FIRST_SYNC_HARD_TIMEOUT_MS` 까지 기다린다. 그때도 없으면 `fallback` / `timeout`
- 두 단계인 이유: 1MB 문서의 첫 상태는 1MB 가 넘는 메시지 하나다(F-304 6.3 압축본 1,003,059~1,006,007 B). 느린 회선에서 10초로 자르면 받고 있던 동기화를 버리고 폴백한다
- `useLiveDoc` 가 붙이는 이벤트: `window` `online` → `wake()`, `offline` → `goOffline()`, `document` `visibilitychange` 가 `visible` 이 되면 → `wake()`. 세션이 끝나면 떼고 `destroy()`

- **폴백으로 들어가는 것은 첫 동기화 전뿐**이다. 폴백에서 실시간으로 돌아오는 길은 "그 문서를 다시 열기"(다른 문서로 갔다 오기·새로고침)뿐이다(3장). 폴백 세션 도중 몰래 실시간으로 올리지 않는 이유: 폴백은 잠금을 잡고 PUT 으로 쓰는 중이고, 그 사이 올라간 D1 값은 DO 가 흡수해야 한다(F-304 7.2) — 한 세션에 두 길이 섞이면 어느 쪽 본문이 화면에 있는지 설명할 수 없다
- 폴백에서 편집기를 여는 본문: 이 페이지에서 **그 문서를 실시간으로 연 적이 있으면** `refreshDocFromServer` 를 먼저 부르고, 실패하면 `store.get` 캐시. 연 적이 없으면 지금처럼 `store.get`. 이유: 실시간 세션은 IndexedDB 캐시 본문을 고치지 않으므로(불변조건 — 캐시는 `Y.Text` 의 한 방향 파생이고, 이 명세는 파생을 새로 쓰지 않는다) 같은 페이지에서 다시 열 때 캐시가 낡았을 수 있고, 낡은 `version` 으로 PUT 하면 409 충돌 사본이 생긴다. 처음 여는 문서는 부팅 때 `list()` 가 `version` 이 다르면 다시 받아 둔다(`serverStore.ts` `list`)
- `새 문서로 저장`: 지금 `saveAsNewDocAfterDeletedElsewhere` 가 하는 일(편집기 본문 + 사이드바 메타 제목으로 `store.create`, 새 문서 열기, 알림 걷기)을 네 경우 모두에 쓴다. 이름은 구현이 정한다. 새 문서는 outbox 에 `createDoc` 이 있으므로 그 세션은 `pending` 경로다. 로그인이 풀린 상태(`4401`)에서도 캐시·outbox 에 남아 로그인 뒤 올라간다(`serverStore.ts` outbox 처리 `unauthorized` → 항목을 지우지 않음)
- 읽기 전용으로 내릴 때: App 의 읽기 전용 판정(`isReadOnlyDoc`)에 "실시간 세션이 `stopped`" 를 더한다. 편집기 `setReadOnly(true)`·`setTitleReadOnly(true)` 가 지금 흐름으로 불린다. 방 Doc 은 더 이상 어디에도 붙지 않는다

### 9.2 바깥 공유 Doc 으로 게이트 세우기 (`remoteGate.ts`, F-303 8.1 에 더함)

### 9.3 제목 (`liveTitle.ts`, `docTitle.ts`, `createEditor.ts`)

```ts
// src/editor/liveTitle.ts
export const LOCAL_TITLE: object                        // 이 브라우저가 제목을 쓰는 트랜잭션의 origin
export function writeTitle(doc: Y.Doc, value: string): boolean      // 바뀐 것이 있으면 true

  onRemoteTitle: (title: string) => void

```

- 제목은 방 Doc 의 `Y_TITLE_NAME`(`'title'`) `Y.Text` 다(F-304 11.1). **편집기 Doc** 의 같은 이름 `Y.Text` 에 쓰고, 게이트가 방 Doc 으로 중계한다 — 공유 Doc 에는 채택 말고 로컬 쓰기를 하지 않는다는 F-303 4.1 을 지킨다
- `writeTitle`: 지금 `Y.Text` 값과 `value` 의 차이를 `diffText`(`src/lib/textRebase.ts`)로 구해 **바뀐 구간만** 한 트랜잭션(origin `LOCAL_TITLE`)으로 지우고 넣는다. 같으면 아무것도 안 한다. 통째로 지우고 넣지 않는 이유: 한 글자 칠 때마다 업데이트가 제목 길이만큼 커지고, 동시에 친 상대 글자를 모두 지운다
- 결과는 **입력하는 쪽 기준 마지막 값이 이긴다**(22장 Q5): 포커스를 가진 사람이 다음 글자를 치면 그때의 textarea 값과 `Y.Text` 차이를 쓰므로, 그 사이 들어온 상대 편집 중 겹치는 부분이 지워진다
- `UndoManager` 는 `content` 만 추적한다(F-302). 제목 쓰기는 본문 되돌리기에 섞이지 않는다
- `observeTitle`: 편집기 Doc 의 `title` 이 origin `LOCAL_TITLE` 이 아닌 트랜잭션으로 바뀌면 새 값으로 `onRemote` 를 부른다. 원격 제목은 게이트를 지나 편집기 Doc 에 들어오므로 **IME 조합 중에는 보류되고 조합이 끝날 때 함께 들어온다**(불변조건)
- App: 실시간 경로에서 `commitTitle(value)` 는 `store.update` 대신 `writeLiveTitle(value)` 를 부르고 사이드바 메타 제목을 바꾼다. `handleTitleCommit` 의 빈 제목 → `제목 없는 문서` 규칙은 그대로다. `onRemoteTitle` 은 사이드바 메타 제목을 바꾼다(편집기의 `title` prop 이 바뀌어 `setTitle` 이 지금 흐름으로 불린다)
- `docTitle.ts`: 제목 textarea 가 포커스를 가진 동안에는 지금처럼 값을 바꾸지 않는다(`TitleWidget.updateDOM`). **blur 된 뒤에는 필드의 현재 제목과 textarea 값이 다르면 필드 값을 보여 준다.** 지금은 포커스 중에 원격 제목이 와서 필드가 바뀌면, blur 뒤에도 `eq` 가 같아 `updateDOM` 이 다시 불리지 않고 옛 값이 남는다
- 제목 길이: DO 가 D1 에 쓸 때 `MAX_TITLE_CHARS`(500)로 자른다(`docRoomCore.ts`). 클라이언트는 자르지 않는다

## 10. 저장 경로 — PUT 이 멈추고 다시 도는 곳

### 10.1 경로별 표

| 경로 | 본문 자동 저장(`useDocSaver`) | 제목 | 편집 잠금(`useDocLock`) | 캐시 본문 |
| --- | --- | --- | --- | --- |
| `local`·`view`·`pending` | 지금 그대로 | 지금 그대로(`store.update`) | 지금 그대로 | 지금 그대로 |
| `realtime`, 첫 동기화 전 | `blocked` | 편집기 없음 | **끔** | 안 씀 |
| `realtime`, 동기화 뒤(`live`·`reconnecting`·`stopped`) | `blocked` | Yjs(9.3). `stopped` 면 읽기 전용 | **끔** | 안 씀 |
| `fallback` | 지금 그대로 | 지금 그대로 | 지금 그대로 | 지금 그대로 |

- `useDocSaver` 의 `blocked` 에 "실시간 경로" 를 더한다. 멈추는 순간은 경로가 `realtime` 으로 정해질 때, 다시 도는 순간은 **다음 문서 열기 세션이 `realtime` 이 아닐 때**다. 한 세션 안에서 PUT 이 다시 켜지는 일은 없다
- `useDocLock` 은 인자를 바꾸지 않는다. App 이 `docId` 를 넘기는 조건에 "경로가 `pending` 또는 `fallback`" 을 더한다(그 밖이면 `null` → 적용 안 됨). 경로가 아직 정해지지 않은 동안(5.1)에도 `null` — 폴백으로 정해진 뒤 잠금을 잡는다
- 실시간 세션에서 PUT 을 보내면 안 되는 이유: DO 가 D1 을 쓰면서 `version` 이 오른다(F-304 8장). 브라우저의 `baseVersion` 은 낡아 409 → 충돌 사본이 생긴다. 제목만 보내도 `handleUpdateDoc` 이 `baseVersion` 을 본다
- 사이드바 정렬: 실시간 세션에서 방 Doc 이 바뀌면(내 편집·상대 편집) 700ms 뒤 사이드바 메타의 `updatedAt` 을 지금 시각으로 바꾼다(마지막 변경 기준 한 번). D1 `updated_at` 은 DO 가 5~30초 박자로 쓴다(F-304 6.2)
- 가져오기(F-282 `confirmImport`)가 열린 실시간 문서를 갱신 대상으로 가지면: 가져오기는 지금처럼 `store.update` 로 D1 에 쓴다. 뒤이은 "열린 문서 다시 마운트" 는 실시간 경로에서 **건너뛴다** — 편집기는 방 Doc 에서 만들어지므로 다시 마운트해도 가져온 본문이 안 보이고, 가져온 본문은 DO 가 흡수(F-304 7.2 — 다음 flush 의 조건부 쓰기 실패 또는 다음 새 연결)할 때 방 Doc 으로 들어와 화면에 온다. 15장 한계

### 10.2 폴백 세션

- F-213·F-207 흐름을 **한 줄도 바꾸지 않는다.** 잠금 알림 띠·423/409 충돌 사본·`syncSuffix` 가 그대로다
- 폴백 세션과 실시간 세션이 같은 문서에 섞이면(A 는 폴백, B 는 실시간): A 의 PUT 은 D1 에 들어가고 DO 가 흡수해 B 화면에 퍼진다(F-304 7.2). 겹치면 DO 가 이기고 A 는 다음 PUT 에서 409 → 충돌 사본(F-304 18장 Q4). B 가 잠금을 잡지 않으므로 A 는 잠금을 늘 얻는다 — **A 는 B 가 있다는 것을 모른다.** F-301 8.3 이 받아들인 모양이다(15장)

```ts
live?: LiveStatus | null     // 실시간 경로일 때만. 폴백·그 밖이면 null
fallback?: boolean           // 폴백 경로일 때 true

export type LiveStatus = 'connecting' | 'live' | 'reconnecting' | 'signed-out' | 'revoked' | 'gone'
```

실시간 경로 — `.statusbar-save` 한 칸을 이것으로 채운다(저장 상태 글자 대신. `syncSuffix` 는 붙이지 않는다)

| `LiveStatus` | 제어기 상태 | `.statusbar-save` 글자 | 점 클래스 |
| --- | --- | --- | --- |
| `connecting` | `connecting` | `불러오는 중…` | `statusbar-save-dot--dirty` |
| `live` | `live` | `저장됨` | `statusbar-save-dot--saved` |
| `reconnecting` | `reconnecting` | `연결 끊김 · 다시 연결 중` | `statusbar-save-dot--error` |
| `signed-out` | `stopped`/`signed-out` | `다시 로그인 필요` | `statusbar-save-dot--error` |
| `revoked` | `stopped`/`forbidden`·`revoked` | `편집 권한이 없습니다` | `statusbar-save-dot--error` |
| `gone` | `stopped`/`not-found`·`deleted` | `저장되지 않음` | `statusbar-save-dot--error` |

- `live` 에서 `저장됨` 인 뜻: 편집이 DO 에 닿았다(DO 가 5~30초 안에 SQLite·D1 에 쓴다, F-304 6.2). 전송 확인(ack)은 없다 — `y-protocols` sync 에 없다(22장 Q7)
- 편집기가 없는 `connecting` 동안에도 상태바는 보인다. 지금은 편집기 자리와 함께 그려지므로 편집기 없이 상태바만 그리는 분기가 필요하다(구현이 정한다)

폴백 경로 — `.statusbar-save` 는 **지금 그대로**(저장 상태 + `syncSuffix`). 그 옆에 형제 요소 하나를 더한다

```html
<span class="statusbar-live">실시간 연결 실패 · 한 명씩 편집</span>
```

- 따로 두는 이유: 기존 e2e 가 `.statusbar-save` 를 `toHaveText('저장됨')` 으로 **정확히** 본다(`e2e/helpers.js` `waitSaved`, `serverStore.spec.js`, `docLock.spec.js`, `serverImage.spec.js`). 기존 서버 e2e 는 전부 폴백 경로를 타므로(18장) 같은 칸에 붙이면 전부 깨진다
- 문구는 F-301 8.3 그대로. 이유(`unreachable`·`timeout`·`offline`·`signed-out`)와 상관없이 같다. 오프라인·로그인 필요는 `syncSuffix` 가 이미 따로 알린다
- `pending`·`view`·`local` 경로에는 `.statusbar-live` 가 없다

## 12. `/v1` PUT 임시 423 — F-301 7장 결론 (F-308 에서 뺐다)

### 12.1 판정 자리와 순서

```ts
// worker/docs.ts — 다섯째 인자(선택)를 더한다. /api 경로는 넘기지 않는다
export async function handleUpdateDoc(
  request: Request, env: Env, ctx: ExecutionContext, params: Record<string, string>,
  options?: { refuseWhileLive?: boolean },
): Promise<Response>
```

- `handleUpdateDocV1` 만 `refuseWhileLive: true` 로 부른다. 순서: 본문 검사(400·413) → 접근(404·403) → D1 잠금(423, 지금 그대로) → **실시간 편집자(423, 새로)** → `version`(409) → 쓰기
- 새 단계: `liveEditorOf(env, docId)` 가 이메일을 돌려주면 `423` `{"error":"locked","email":"<그 이메일>"}`. `expiresAt` 은 싣지 않는다(DO 연결에는 만료 시각이 없다). 게시된 CLI 는 `email` 만 읽어 `브라우저에서 편집 중인 문서라 고칠 수 없습니다 ({email}). 편집을 마친 뒤 다시 시도하세요.` 를 낸다(`cli/src/output.ts` `locked`) — CLI 를 고치지 않는다
- 이 자리인 이유: `handleUpdateDocV1` 앞에서 따로 막으면 D1 에서 문서·권한을 한 번 더 읽고, 400·413·404 보다 423 이 먼저 나가 CLI 오류 순서가 `/api` 와 달라진다. 권한 없는 사람에게 "누가 편집 중" 을 알려 주지 않는 것도 이 순서가 지킨다
- `/api` PUT(폴백 세션)은 막지 않는다 — 폴백과 실시간이 섞이는 경우는 흡수(F-304 7.2)가 다룬다(10.2). 막으면 폴백 사용자는 실시간 사용자가 있는 한 저장을 못 한다
- **F-308 에서 뺐다**(`/v1` 이 DO 경유가 되면 필요 없다)

## 13. keepalive — H362·H363 에 따라 갈리는 매개변수

- 코드의 기본값은 `KEEPALIVE_INTERVAL_MS = 20_000`(7.1). **이 값은 H362·H363 결과가 나온 뒤 아래 규칙으로 확정하고, 확정 전에는 `deploy` 로 올리지 않는다**(F-304 15.4 게이트)
- 판정 규칙 — 위에서부터

| # | H363(20초 ping 30분, DO Duration) | H362(ping 없이 30분) | 결정 |
| --- | --- | --- | --- |
| K1 | `pong` 이 20초마다 오고, 대시보드 DO Duration 이 깨어 있었을 때 값(한 시간 450 GB-s)의 **10% 이하** | 무엇이든 | `20_000` 그대로 |
| K2 | Duration 이 10% 를 넘는다(ping 이 DO 를 깨우거나 요금에 잡힘) | "30분 유지" | `null`(주기 ping 끔). 죽은 연결은 `wake` 의 한 번짜리 ping 과 끊김 재연결로만 잡는다 |
| K3 | Duration 이 10% 를 넘는다 | T분에 끊김, T ≥ 10 | `null`. 끊기면 7.3 재연결 — 한 번마다 DO 가 깨어 `onLoad` 를 돈다. T 를 적어 둔다 |
| K4 | Duration 이 10% 를 넘는다 | T분에 끊김, T < 10 | **사람 결정 필요** — 재연결 비용(시간당 60/T 번 깨어남 × 편집자 수)과 ping 비용을 견준다. 결정 전 배포 금지 |

- 10% 를 문턱으로 둔 이유: H363 문장은 "한참 못 미침" 이다. 판정을 사람이 다시 하지 않게 숫자로 박는다. 10% 이하면 편집자 한 명이 하루 종일 붙어 있어도 깨어 있는 비용의 1/10 이다
- `pong` 이 안 오면(`auto-response` 가 안 돔) K1 이 아니다 — K2~K4 로 가고, 그 경우 7.4 의 pong 시간 제한이 연결을 계속 끊으므로 **반드시 `null`**
- 확정 값은 `liveDoc.ts` 상수 한 줄과 이 표의 결과 기록으로 남긴다(메인이 `human-checks.md` 에 적는다)

### 19.2 e2e (`e2e/liveDoc.spec.js`, fakeServer + fakeDocRoom)

`e2e/fixtures/fakeDocRoom.js` — `context.routeWebSocket('**/ws/doc/*', …)` 로 Node 쪽 가짜 방을 돌린다. **페이지 이동 전에 설치한다**(측정 c). 한 테스트 안의 여러 context 가 같은 방 상태를 나눠 쓴다

- 방마다 Node `Y.Doc` 하나(`content`·`title` 을 준 값으로 씨앗). 들어온 sync·update 를 적용하고 **보낸 쪽 포함 모두에게** 되돌린다(F-304 11.2), `ping` 에는 `pong`
- 제어: 방 본문·제목 읽기, 연결 수·연결 시도 수 세기, 들어온 연결을 곧바로 닫기(`open` 없음)·먼저 메시지를 보낸 뒤 닫기(`open` 있음), 지금 연결을 코드·reason 으로 닫기, 커스텀 메시지 보내기(`__YPS:` 붙여), sync step 2 보내기를 멈췄다 풀기
- import: `yjs`(직접 의존), `y-protocols/sync`·`lib0/encoding`·`lib0/decoding`(**직접 의존이 아님** — `y-partyserver`·`yjs` 의 의존으로 최상위에 있다, `npm ls`). `package.json` 을 바꾸지 않는다(22장 Q9)

## 21. 확인 못 한 것 (단정하지 않음)

- **배포 환경의 첫 동기화 시간.** 로컬 12ms(측정 d)는 같은 PC 안이다. Cloudflare 에서 DO 깨어남(`onLoad`)·D1 읽기·지역 왕복이 더해진다 — 19.4 H5
- **Cloudflare WebSocket 메시지 크기 상한.** 1MB 문서의 첫 상태는 약 1,003,059 B 한 메시지다. Cloudflare 문서 값은 확인하지 않았다 — 19.3 L3·19.4 H6
- **배포 환경에서 Worker 거절(101 뒤 44xx 닫기) 때 브라우저가 `open` 을 먼저 보는지.** 로컬 `routeWebSocket` 은 안 봤다. 7.2 는 어느 쪽이든 같게 설계했다
- **`auto-response` ping 이 요금에 잡히는지** — H363
- **`npm run dev`(vite 개발 서버, 5173)에서 `/ws/doc/:id` 업그레이드가 어떻게 끝나는지.** 개발 서버의 HMR 이 같은 포트에서 WebSocket 을 받는다. 확인하지 않았다(5173 은 사용자 개발 서버라 쓰지 않았다). 개발 서버는 보통 idb 저장소라 4.1 1번으로 연결하지 않을 것으로 읽었다
- **우리 코드의 번들 크기** — 라이브러리만 쟀다(14.2)
