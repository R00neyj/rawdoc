## 3. 먼저 정리해야 하는 것 — `unreadableProperties` 가 무엇을 세는가

### 3.1 코드가 하는 일

`searchDocs`(`docSearch.ts` 233~234행):

```
for (const doc of docs) {
  if (query.filters.length > 0 && doc.properties === null) unreadableProperties++
```

그리고 `properties === null` 이 되는 경로는 **둘**이다 (`searchIndex.ts` 79~82행):

| 경로 | `properties` | `frontmatterUnreadable` |
| --- | --- | --- |
| 프론트매터가 **아예 없다**(`findFrontmatter` 가 `null`) | `null` | `false` |
| 프론트매터는 있는데 `parseSimpleProperties` 가 못 읽었다(중첩 맵·블록 스칼라 등, F-284 3.3) | `null` | `true` |
| 공유받은 문서(본문을 `''` 로 넣는다) | `null` | `false` |

즉 **`unreadableProperties` = 필터가 걸린 검색에서 "속성이 없어서든 못 읽어서든 필터 판정에서 탈락한 문서 수"** 다. 실측(7.2): 프론트매터 없는 문서 90개 + `tag` 가진 문서 10개인 저장소에서 `tag:일기` 를 치면 **90** 이 나온다

### 3.2 그래서 정하는 것

- **N 의 출처는 `SearchOutcome.unreadableProperties` 그대로** — 사용자 결정(전제 1)이고, "필터에서 빠진 수" 로는 이 값이 맞다
- **문장은 고친다**: `속성을 읽지 못한 문서 {N}개는 필터에서 빠졌습니다` → **`속성이 없거나 읽지 못한 문서 {N}개는 필터에서 빠졌습니다`**
  - 고치지 않으면 프론트매터를 한 번도 쓴 적 없는 문서 전부를 "읽지 못한" 으로 말하게 된다. 보통의 저장소에서는 그게 거의 모든 문서라 **필터를 쓸 때마다 사실이 아닌 문장이 뜬다**
  - `frontmatterUnreadableCount`(진짜 못 읽은 수)로 바꾸는 쪽은 사용자 결정과 어긋난다 → 쓰지 않는다. 두 수를 함께 적는 안도 버린다(한 줄에 숫자가 둘이면 읽히지 않는다)
- 이것은 **F-284 4.4 가 승인받은 문장을 바꾸는 것**이라 1.1 갱신 대상과 13장 Q1 에 올린다. **사람 결정 필요**

- **안내를 전부 검색창 바로 아래로 모은다.** F-284 는 같은 문구의 자리를 2.2·3.3·4.4·5.2 에서 서로 다르게 적었다(1.1). 근거: (1) 이 문구들은 **결과를 설명하는 것이 아니라 검색 범위·해석을 설명**한다. 결과가 0개일 때도 보여야 하는데 결과 아래에 두면 상태 문구와 위아래로 겹쳐 읽힌다. (2) 결과 목록은 `max-height: 50vh; overflow-y: auto`(`app.css` 1401행)라 그 아래에 둔 글은 스크롤을 내려야 보인다
- **꼬리 줄에는 결과 수만** 남긴다. 결과가 있을 때만 뜨므로 위 문제가 없다
- 해석 줄과 안내 줄은 **같은 묶음(`.search-notes`)** 안의 형제 `<p>` 다. 묶음 자체는 그릴 줄이 하나도 없으면 아예 그리지 않는다(빈 여백이 남지 않게)

### 4.2 안내 줄은 몇 개까지 동시에 뜨는가 — **최대 3**

| 줄 | 조건 | 같이 뜰 수 없는 줄 |
| --- | --- | --- |
| 해석 줄 | 필터 ≥ 1 | — |
| `목록을 새로 읽는 중…` | 인덱스가 아직 없다 | **`속성이…`·`공유받은…`** — 둘 다 인덱스·결과가 있어야 계산된다 |
| `오프라인 —` | 서버 저장소 + `online === false` | **`공유받은…`** — 오프라인이면 `api.getShared()` 가 실패해 `shared = []` 이고 `sharedCount === 0` 이 된다 (`serverStore.ts` 553~570행) |
| `속성이 없거나 읽지 못한 문서 {N}개…` | 필터 ≥ 1 이고 `unreadableProperties > 0` | `목록을…` |
| `공유받은 문서 {N}개…` | `sharedCount > 0` 이고 검색어 ≥ 1 | `목록을…`, `오프라인 —` |

- 가장 붐비는 조합은 `해석 줄 + 오프라인 + 속성이…` 또는 `해석 줄 + 속성이… + 공유받은…` 으로 **3줄**이다
- 줄 수를 줄이려고 `…` 로 접거나 "더 보기" 를 두지 않는다. 3줄은 `wide`(520px)에서 세 줄이면 약 54px 이고, 결과 목록이 `50vh` 로 잘려 있어 대화상자가 화면을 넘지 않는다 (정확한 높이는 11장 사람 확인)

### 4.3 꼬리 줄

- 결과가 **1개 이상일 때만** 그린다. 0개면 상태 문구(`찾는 문서가 없습니다` 등)가 그 뜻을 이미 말한다
- 스크롤 영역(`.search-results`) **바깥**에 둔다 — 200행을 끝까지 내려야 결과 수를 보는 일이 없게

### 5.1 `formatQuerySummary`

```ts
/** 쿼리 해석 줄. 필터가 하나도 없으면 null */
export function formatQuerySummary(query: ParsedQuery): string | null
```

| 규칙 | 값 |
| --- | --- |
| `query.filters.length === 0` | `null` — 검색어만 친 흔한 경우에 줄이 늘지 않게 |
| 필터 조각 | `` `${key}=${value}` ``. 값이 빈 필터(`tag:`, 존재 검사)는 **`${key}=(모두)`** (13장 Q2) |
| 필터 여러 개 | `, ` 로 잇는다 → `필터 tag=일기, mood=좋음` |
| 검색어가 있으면 | ` · 검색어 ` + 각 검색어를 `"…"` 로 감싸 공백으로 이어 붙인다 → `· 검색어 "회고" "주간"` |
| 검색어가 없으면 | 그 부분을 통째로 뺀다 → `필터 tag=일기` |
| 전체 | `필터 tag=일기 · 검색어 "회고"` (F-284 4.4 의 예와 글자까지 같다) |

- **`ParsedQuery.filters`·`terms` 는 이미 `foldCase()`(소문자화)를 거친 값이다**(`docSearch.ts` 97~98·107행). 그래서 `Tag:Diary` 를 치면 해석 줄에 `필터 tag=diary` 로 보인다. **이것을 되돌리지 않는다** — 해석 줄은 "앱이 어떻게 읽었는지" 를 보여 주는 줄이고, 대소문자를 구분하지 않는다는 규칙(F-284 3.2)이 여기서 그대로 드러나는 편이 낫다. 한글은 애초에 차이가 없다
- 중복 토큰은 `parseSearchQuery` 가 이미 지웠다(`seenTerms`·`seenFilters`, `docSearch.ts` 91~92행) — 여기서 다시 지우지 않는다

### 5.2 `buildSearchNotes`

```ts
/** 해석 줄 아래 안내 줄들. 화면에 그릴 순서 그대로. 없으면 빈 배열 */
export function buildSearchNotes(input: {
  query: ParsedQuery
  outcome: SearchOutcome | null
  sharedCount: number
  offline: boolean
  loading: boolean
}): string[]
```

순서와 조건 (**이 순서를 바꾸지 않는다**):

| # | 조건 | 문구 |
| --- | --- | --- |
| 1 | `loading` | `목록을 새로 읽는 중…` |
| 2 | `offline` | `오프라인 — 이 기기에 저장된 문서에서 찾습니다` |
| 3 | `outcome !== null && outcome.unreadableProperties > 0` | `속성이 없거나 읽지 못한 문서 {N}개는 필터에서 빠졌습니다` |
| 4 | `sharedCount > 0 && query.terms.length > 0` | `공유받은 문서 {N}개는 제목만 찾았습니다` |

- 순서 근거: **지금 무슨 일이 일어나는 중인지(1) → 어떤 범위를 보고 있는지(2) → 무엇이 빠졌는지(3·4)**
- 3번에 `query.filters.length > 0` 조건을 따로 걸지 않는다. `searchDocs` 가 **필터가 없으면 `unreadableProperties` 를 아예 0 으로 둔다**(`docSearch.ts` 234행, 7.2 에서 실측). 조건을 두 곳에 두면 한쪽이 바뀔 때 어긋난다
- 4번에 `query.terms.length > 0` 을 거는 이유: 필터만 있는 쿼리에서는 공유받은 문서가 **제목으로도 안 걸린다**(본문이 `''` 라 `properties` 가 `null` → `matchesFilters` 가 `false`, `docSearch.ts` 172행). 그때 "제목만 찾았습니다" 는 거짓이고, 그 문서들은 이미 3번 줄에 세어져 있다
- `{N}` 은 `toLocaleString('ko-KR')` 로 천 단위 쉼표를 넣는다 (선례: `StatusBar.tsx` 41행)

### 5.3 `formatResultCount`

```ts
/** 결과 꼬리 줄. 결과가 0개거나 아직 모르면 null */
export function formatResultCount(outcome: SearchOutcome | null, rowCount: number): string | null
```

| 조건 | 값 |
| --- | --- |
| `outcome === null \|\| rowCount === 0` | `null` |
| `outcome.truncated === false` | `결과 {outcome.total}개` |
| `outcome.truncated === true` | `결과 {outcome.total}개 — 앞 {rowCount}개만 보입니다` |

- **총계를 적는다.** `searchDocs` 가 자르기 전에 센 값이 `outcome.total` 로 이미 나와 있다(`docSearch.ts` 251행, 7.1 실측). F-284 4.3 의 `결과가 많습니다 — 앞 200개만 보입니다` 는 개수를 모른다는 전제로 쓴 문장이라 고친다 (13장 Q3)
- 뒤 숫자는 상수 `200` 이 아니라 **`rowCount`(실제로 그린 행 수)** 를 쓴다. `buildResultRows` 가 인덱스에 없는 id 를 건너뛸 수 있어(방어, `searchResults.ts` 48행) `hits.length` 와 어긋날 수 있다. 화면에 보이는 수를 말해야 한다
- `RESULT_LIMIT` 을 import 하되 문구에는 넣지 않는다 — 9장 U27 이 `RESULT_LIMIT` 로 기대값을 만든다(상수가 바뀌면 테스트가 따라온다)
- 두 값 모두 `toLocaleString('ko-KR')`


우선순위 (위에서부터 먼저 걸리는 것 하나만):

| # | 조건 | 문구 | 누가 정한 것 |
| --- | --- | --- | --- |
| 1 | `failed` | `문서를 읽지 못했습니다` | F-287 6장 |
| 2 | `query.isEmpty` | `검색어를 입력하세요` | F-284 3.5 |
| 3 | `outcome === null` | `null` — **빈 영역**. "없다" 가 아니라 "아직 모른다" | F-287 4.3 |
| 4 | `outcome.missingFilterKeys.length > 0` | `'tagg' 속성을 가진 문서가 없습니다` | F-284 3.5 — **이번에 새로 만드는 것** |
| 5 | `rowCount === 0` | `찾는 문서가 없습니다` | F-284 3.5 |
| 6 | 그 밖 | `null` | |

- 1번이 2번보다 앞인 것은 지금 코드의 동작과 같다(`SearchDialog.tsx` 123행이 마지막에 덮어쓴다). 읽기 실패는 검색어 유무와 무관하게 알려야 한다
- 4번이 5번보다 앞: `'tagg' 속성을 가진 문서가 없습니다` 는 **왜** 없는지까지 말하므로 더 구체적이다
- 4번이 참이면 5번은 언제나 참이다 — `missingFilterKeys` 에 키가 남았다는 것은 그 키를 가진 문서가 하나도 없다는 뜻이고, 필터는 전부 AND 라 결과가 0이 된다 (`docSearch.ts` 236~240행·167~174행. 7.2 에서 실측: `missingFilterKeys ['tagg']`, `hits 0`)
- 키가 여럿 빠졌으면 `, ` 로 잇는다 → `'tagg', 'moodd' 속성을 가진 문서가 없습니다`. 실측에서 배열 순서는 쿼리에 쓴 순서다
- 따옴표는 F-284 3.5 가 쓴 **곧은 작은따옴표 `'`** 를 그대로 쓴다
- **키는 있는데 값이 안 맞는 경우**는 `missingFilterKeys` 가 빈 배열이라 5번 `찾는 문서가 없습니다` 로 떨어진다. F-284 3.5 표의 2행과 정확히 같다 (7.2 실측으로 확인)

## 7. 확인한 것 (직접 읽고 돌려 본 값)

방법: Node v24.12.0 의 타입 지우기(`--experimental-strip-types` 기본 켜짐)로 `src/lib/docSearch.ts`·`src/app/searchResults.ts` 를 **스크래치패드에 복사해 import 경로만 고쳐** 돌렸다(원본은 확장자 없는 import 라 Node 가 그대로는 못 읽는다). 원본 파일은 건드리지 않았다

### 7.1 결과 상한 200 — 어디서 자르고, 총계를 아는가

| 확인 | 결과 |
| --- | --- |
| 상수 | `docSearch.ts` 6행 `export const RESULT_LIMIT = 200` |
| 어디서 자르나 | `searchDocs` 228행 `const limit = options?.limit ?? RESULT_LIMIT`, 252~254행 `matched.slice(0, limit)` |
| `SearchDialog` 가 넘기나 | **안 넘긴다** — `SearchDialog.tsx` 92행 `searchDocs(index.entries, parsed)`. 기본값 200 이 그대로 걸린다 |
| **총계를 아는가** | **안다.** 251행 `const total = matched.length` 는 **자르기 전** 값이고 `truncated = total > limit` 과 함께 나온다 |
| 실측 (합성 문서, 전부 매치되는 검색어) | 500개 → `hits 200 / total 500 / truncated true`, 1,000개 → `hits 200 / total 1000`, 5,000개 → `hits 200 / total 5000` |

→ **F-288 은 자르는 일을 하지 않는다. 문구만 만들고, 총계를 적을 수 있다**

### 7.2 `unreadableProperties`·`missingFilterKeys` 가 실제로 세는 것

합성 문서 100개(10개만 `tag: 일기` 속성, 90개는 속성 없음):

| 쿼리 | `hits` | `unreadableProperties` | `missingFilterKeys` |
| --- | --- | --- | --- |
| `tag:일기` | 10 | **90** | `[]` |
| `tagg:일기` (없는 키) | 0 | 90 | `['tagg']` |
| `tag:회고` (키는 있고 값이 안 맞음) | 0 | 0 * | `[]` |
| `회고` (필터 없음) | — | **0** | `[]` |
| `tagg:1 moodd:2` (없는 키 2개) | 0 | — | `['tagg', 'moodd']` — 쿼리 순서 |

\* 이 줄만 속성을 가진 문서 1개짜리 별도 표본으로 쟀다

→ 3장의 결론(문장을 고쳐야 한다)과 5.2·5.4 의 조건이 전부 이 값에서 나왔다

### 7.3 문구 계산 비용

| 문서 수 | `searchDocs` | `buildResultRows`(200행) |
| --- | --- | --- |
| 500 | 3.3ms | 9.4ms (첫 회, JIT 예열 포함) |
| 1,000 | 3.6ms | 4.3ms |
| 5,000 | 29.7ms | 4.1ms |

- **F-288 이 더하는 네 함수는 전부 O(필터 수 + 검색어 수 + 1)** 이다. 문서 수와 무관하고 위 표에 잴 만한 값을 더하지 않는다. 디바운스 150ms 예산(F-284 5.1)에 영향이 없다
- 그래서 이 명세에는 **성능 게이트를 두지 않는다.** F-287 A17 이 잰 대화상자 열림 시간에도 영향이 없다(안내 줄은 인덱스가 온 뒤에 계산된다)

검색어가 없으면 `buildSnippet` 이 413~415행 경로로 가 **본문 앞 100자 + `…`** 를 강조 없이 돌려준다 (실측: 조각 1개, 101자, 끝이 `…`). **F-288 이 바꾸지 않는다** — 필터만으로 찾을 때 문서 첫머리를 보여 주는 것이 맞고, 바꾸려면 F-285 를 고쳐야 한다(1장 금지)
