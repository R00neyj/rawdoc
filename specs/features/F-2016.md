### 1.1 F-277 5장의 예외

F-277 5장은 "Notion·HackMD 등 다른 서비스 전용 내보내기 형식 해석" 을 하지 않는다고 적었고, F-282 3.7 은 그 결정대로 `![[그림.png]]` 를 원문 그대로 두었다. **이 개요는 옵시디언 하나만 예외로 연다.** Notion·HackMD 는 여전히 범위 밖이다. 이유: 이 앱의 편집 방식(라이브 프리뷰)과 위키링크·콜아웃·주석 문법이 이미 옵시디언을 기준으로 정해졌고(`specs/product.md` 1.1·Q22), 사용자가 지목한 쓰임(옵시디언 LLM 위키 공유)이 그 문법을 그대로 쓴다

### 1.2 불변조건과의 관계

- **"내보내면 친 바이트 그대로"** 는 `.md` 내보내기와 전체·폴더 zip(F-281)에 대한 약속이다. 옵시디언 볼트 내보내기는 `.txt`(F-278)처럼 **변환 내보내기**라 이 약속 밖이다. F-281 zip 바이트는 바꾸지 않는다 — F-2020 의 수용 기준으로 판정한다
- **가져오기의 변환은 사용자가 고른 것이다.** 옵시디언 이미지 문법을 F-156 블록으로 바꾸는 것은 가져올 때 한 번 원문을 만드는 일이고, 그 뒤 편집·저장·내보내기 경로의 원문 보존은 그대로다
- **decoration 은 문서 내용을 바꾸지 않는다** — 헤딩 이동·경로식 링크 표시는 표시와 스크롤만 바꾼다
- **원본은 CM6 `EditorState` 하나** — 가져오기로 열린 문서가 갱신되면 F-282 3.9 처럼 에디터를 다시 마운트한다. 새 규칙 없음
- **제품명·저장소 식별자** — 새 UI 문구의 `옵시디언` 은 다른 제품 이름이라 불변조건 대상이 아니다. 이 개요는 새 localStorage 키·IndexedDB 스토어를 만들지 않는다 (8장 Q12)

## 2. 폴더 깊이 해제 (F-2017)

### 2.1 규칙

- **만들기**: 부모가 최상위(`null`)이거나 **존재하는 폴더**면 된다. 부모가 하위 폴더인지는 보지 않는다
- **옮기기**: 막는 경우는 셋뿐이다 — ① 자기 자신 안으로 ② **자기 자손 안으로**(`descendantFolderIds(folders, id)` 에 대상이 있으면) ③ 대상 폴더가 없음. 자식이 있는 폴더도 다른 폴더 안으로 갈 수 있다
- **지금 순환 검사는 깊이 규칙에 기대고 있다 — 코드로 확인했다.** `canMoveFolder` 가 직접 막는 순환은 `parentId === id`(자기 자신)뿐이다. 손자 안으로 옮기는 순환은 "대상이 하위 폴더면 불가"·"자식 있는 폴더는 다른 폴더 안으로 못 감" 두 깊이 규칙이 우연히 막고 있다. 깊이 규칙을 지우면 ②를 **명시적으로 더하지 않는 한 순환이 생긴다**
- 저장소 세 곳(`idbStore`·`memoryStore`·`serverStore`)과 서버(`worker/folders.ts`)가 **모두 같은 두 함수**(`canCreateFolder`·`canMoveFolder`)를 부른다. 서버는 `worker/folders.ts` 에서 `../src/lib/folderTree` 를 import 한다. 따라서 규칙을 바꾸는 곳은 `src/lib/folderTree.ts` 하나다
- **D1 에는 깊이 제약이 없다** (`migrations/0002_docs.sql` 의 `folders` 는 `parent_id TEXT` 뿐). 마이그레이션이 필요 없다

### 2.3 순환 데이터 방어

2.1 로 새 순환은 못 만든다. 그래도 **이미 저장된 데이터가 순환일 수 있는 경로가 하나 남는다**: `worker/folders.ts` `handleUpdateFolder` 는 폴더 목록을 읽고(`SELECT`) 검사한 뒤 따로 `UPDATE` 한다 — 두 기기가 동시에 A→B, B→A 를 보내면 둘 다 검사를 통과할 수 있다. 가능성은 낮지만 순환이 한 번 저장되면 아래가 멈추거나 사라진다

| 함수 | 순환일 때 지금 | F-2017 에서 |
| --- | --- | --- |
| `ancestorsOfDoc` | `while` 에 방문 기록이 없어 **무한 루프** (확인) | 방문 기록으로 끊는다 |
| `buildTree` | 순환에 든 폴더는 루트에서 닿지 않아 **사이드바에서 사라진다** | 순환에 든 폴더는 최상위로 본다 (없는 부모를 최상위로 보는 지금 규칙과 같은 취급) |
| `descendantFolderIds`·`folderPathMap`·`folderChainRole`·`sortFoldersParentFirst` | 방어 있음 | 그대로 |

- 서버 쪽 읽기-쓰기 사이 경합을 트랜잭션으로 막는 일은 하지 않는다 — 위 방어로 화면이 깨지지 않으면 충분하다

### 2.4 들여쓰기 상한 — **6단계부터 더 들어가지 않는다**

- 트리 행 들여쓰기는 **`--depth` 가 5(= 6번째 단계)에서 멈춘다.** 최대 5 × 14px = 70px. 가이드 선(`.tree-group::before`)도 같은 값으로 멈춘다. 7단계 이하는 6단계와 같은 자리에 그려진다. 각주: F-2017 Q2 가 기본값(4)으로 정해져 가이드 선은 4 에서 멈춘다 (F-2017 5.4, 2026-09-23)
- 근거: 사이드바 최소 폭 200px·기본 300px(`src/app/sidebarWidth.ts` `MIN_SIDEBAR_WIDTH`·`DEFAULT_SIDEBAR_WIDTH`). 한 행 = 들여쓰기 + 토글 22px(`.tree-toggle`) + 간격 6px + 이름 + `⋯` 버튼. 70px 들여쓰기면 기본 폭에서 이름 칸이 150px 안팎, 최소 폭에서 50px 안팎 남는다(대략치 — 이름 칸 폭은 실측하지 않았다, 사람 확인). 옵시디언 LLM 위키는 보통 3~4단계라 6단계까지는 구분이 보인다
- 상한은 **CSS 한 곳**에서 건다 — `--depth` 값을 넘기는 JS 는 그대로 실제 깊이를 넘긴다. 폴더로 이동 대화상자(`.move-doc-list li`)와 공개 폴더 목록도 같은 상한
- 화면 읽기 도구에는 실제 깊이가 그대로 전달된다(`role="tree"` 안 `role="group"` 중첩이 단계를 알린다) — 상한은 보이는 모양만이다
- 다른 값은 8장 Q2

### 2.5 배포 순서

- 서버와 클라이언트가 같은 `folderTree.ts` 를 쓰고 한 번에 배포된다(Worker 정적 자산 + API). 순서 문제는 없다
- 새 버전 전의 PWA 가 남은 기기는 깊은 트리를 받으면 **표시는 된다**(`buildTree` 가 재귀) — 옛 `MoveDocDialog` 가 2단계만 보이고 옛 `canMoveFolder` 가 일부 이동을 막을 뿐이다. 새 버전 알림(F-117)으로 풀린다

## 3. 위키링크 해석 (F-2018)

### 3.1 링크 모양

| 원문 | 대상 | 헤딩 | 비고 |
| --- | --- | --- | --- |
| `[[회의록]]` | 제목 `회의록` | — | 지금과 같다 |
| `[[회의록\|9월 회의]]` | 제목 `회의록` | — | 지금과 같다 |
| `[[교안/1주차]]` | 경로 `교안` + 제목 `1주차` | — | **신규** |
| `[[회의록#결정]]` | 제목 `회의록` | `결정` | 지금은 `#` 뒤를 버린다 → 헤딩으로 쓴다 |
| `[[#결정]]` | **지금 문서** | `결정` | 지금은 링크가 아니다 → 링크가 된다 |
| `[[회의록#^abc123]]` | 제목 `회의록` | — | 옵시디언 블록 참조. `^` 로 시작하는 조각은 버리고 문서만 연다(알림 없음) |
| `[[회의록.md]]` | 제목 `회의록.md` 가 없으면 `회의록` | — | 끝의 `.md`(대소문자 무시)는 제목 일치가 없을 때만 떼고 다시 찾는다 |
| `![[…]]` | — | — | 지금처럼 링크가 아니다 (전제 7) |

`findWikiLinks` 의 결과에 헤딩 칸이 더해진다 — 다른 소명세가 기대는 모양이라 여기서 정한다:

```ts
// src/lib/wikiLink.ts (F-2018)
export type WikiLinkMatch = {
  from: number; to: number
  target: string          // '#' 앞, 앞뒤 공백 제거. [[#헤딩]] 이면 ''
  heading: string | null  // '#' 뒤, 앞뒤 공백 제거. 없거나 '^' 로 시작하면 null
  alias: string | null
  targetFrom: number; targetTo: number
}
```

- `target === '' && heading === null` 이면 지금처럼 링크가 아니다
- `target === ''` 인 결과를 받는 모든 소비자(지도 `extractWikiTargets`, `worker/shareSet.ts`, `ShareMenu`)는 **다른 문서를 가리키지 않는 링크로 보고 건너뛴다** — 지도에 자기 자신 간선·끊긴 링크 노드가 생기지 않게

### 3.2 후보 고르기

대상 문자열을 `/` 로 나눠 마지막 조각을 **제목**, 앞 조각들을 **폴더 경로**로 본다. 순서:

1. **대상 전체와 제목이 같은 문서** — 지금 규칙 그대로(정확 일치 → 대소문자 무시). 제목에 `/` 가 든 기존 문서(`A/B 테스트`)로 건 링크가 그대로 살아야 해서 이것이 먼저다. 옵시디언 파일명에는 `/` 가 못 들어가므로 가져온 볼트와는 충돌하지 않는다
2. 1 에 없고 `/` 가 있으면 **경로식**: 제목이 마지막 조각과 같고(정확 → 대소문자 무시), 그 문서가 든 폴더의 조상 이름을 아래에서부터 읽었을 때 앞 조각들과 **끝이 맞는** 문서. 폴더 이름 비교는 대소문자 무시
3. 둘 다 없고 끝이 `.md` 면 떼고 1·2 를 한 번 더
4. 후보가 여럿이면 3.3

**경로는 "끝이 맞기"로 본다 — 해석 기준점을 두지 않는다.** `[[교안/1주차]]` 는 폴더 경로가 `…/교안` 으로 끝나는 곳의 `1주차` 다. 그래서 볼트를 최상위에 넣었든 `옵시디언/내 볼트` 아래에 넣었든 같은 링크가 같은 문서를 찾는다. 옵시디언의 "가장 짧은 경로" 링크(`[[하위/노트]]`)도 끝 맞추기라야 풀린다 — 옵시디언이 실제로 끝 맞추기로 해석하는지는 **확인하지 못했다**(9장 가정 G2). 옵시디언의 상대 경로(`./`·`../`)와 볼트 루트 고정(`/` 로 시작)은 지원하지 않는다 — 앞의 `/` 는 떼고 끝 맞추기로 본다

- 제목·폴더 이름 비교에 NFC 정규화를 하지 않는다. 대신 **가져올 때 파일·폴더 이름에서 만든 제목·폴더 이름을 NFC 로 바꾼다**(4.3) — macOS 에서 압축한 볼트의 NFD 파일명이 본문의 NFC 링크와 어긋나는 것을 거기서 막는다
- 공유받은 문서(`role` 이 `edit`·`view`)도 지금처럼 후보에 든다. 그 문서의 `folderId` 는 남의 폴더라 내 폴더 목록에 없으므로 3.3 에서 "최상위와 무관한 문서"로 취급된다

### 3.3 가까운 폴더

후보가 여럿이면 링크를 건 문서(원본)의 폴더 기준으로 아래 순서에서 **먼저 걸리는 단계**의 후보를 고른다. 같은 단계 안에서는 지금 규칙대로 **목록 앞(최근 수정)**

| 단계 | 후보 | 예 — 원본 `위키/개념/a` |
| --- | --- | --- |
| 1 | 원본과 **같은 폴더** | `위키/개념/색인` |
| 2 | 원본 폴더의 **조상 폴더**, 가까운 것부터. 최상위(폴더 밖)가 마지막 조상이다 | `위키/색인` → `색인`(최상위) |
| 3 | 나머지 중 원본과의 **공통 조상 폴더가 가장 깊은** 후보 | `위키/인물/색인`(공통 조상 `위키`) 이 `일기/색인`(공통 조상 없음)보다 먼저 |
| 4 | 그래도 여럿 | 목록 앞(최근 수정) |

- 1·2·4 는 사용자 문구("같은 폴더 → 가까운 조상 → 최근 수정") 그대로다. **3 은 이 개요가 더한 것이다** — 없으면 볼트를 폴더 하나에 넣었을 때 볼트 안 `위키/인물/색인` 을 두고 볼트 밖 아무 `색인` 으로 갈 수 있다. 8장 Q1
- 원본이 최상위에 있으면 1 = 최상위, 2 는 없다
- 원본 폴더 안쪽(자손 폴더)의 후보는 2 에 들지 않고 3 에서 가장 깊은 공통 조상(원본 폴더 자신)을 갖는다 — 조상 후보가 있으면 조상이 이긴다
- 옵시디언 자체가 같은 이름 파일을 어떻게 고르는지는 **확인하지 못했다**(가정 G1). 그래서 옵시디언으로 내보낼 때는 모호한 링크에 경로를 붙인다 (5.3)

해석 함수는 여러 소명세·서버가 같이 쓰는 계약이다:

```ts
// src/lib/wikiResolve.ts (F-2018 신규) — 순수, DOM·CM6·저장소를 import 하지 않는다. worker 도 import 한다
export type WikiDocRef = { id: string; title: string; folderId: string | null }
export type WikiFolderRef = { id: string; name: string; parentId: string | null }
export type WikiResolver = {
  resolve(target: string, sourceFolderId: string | null): WikiDocRef | null
}
// docs 는 updatedAt 내림차순 (store.list() 순서)
export function createWikiResolver(docs: WikiDocRef[], folders: WikiFolderRef[]): WikiResolver
```

- `resolveWikiTarget` 은 지우지 않는다. 폴더를 모르는 호출부가 남아 있으면 `createWikiResolver(docs, [])` 와 결과가 같아야 한다(모두 최상위 → 단계 1 → 목록 앞). 기존 `wikiLink.test.ts` 의 규칙 1·2·3 테스트가 그대로 통과하는 것으로 판정한다

- `[[노트#상위#하위]]`(옵시디언 하위 헤딩 사슬)는 **마지막 조각**만 쓴다

- 못 찾으면 문서 처음을 열고 알림(`info`) `"{헤딩}" 제목을 찾지 못해 문서 처음을 엽니다.`
- **해시 주소에 헤딩을 남기지 않는다.** `#/d/{id}` 그대로다. 뒤로 가기로 돌아오면 헤딩 위치가 아니라 문서로 돌아온다. 8장 Q10

### 3.6 없는 문서를 누르면

- 경로식 `[[교안/새 글]]` 은 앞 조각이 **이미 있는 폴더**로 끝 맞추기(3.2)가 되면 그 폴더(여럿이면 3.3 순서)에 제목 `새 글` 로 만든다. 맞는 폴더가 없으면 지금 문서의 폴더에 **대상 전체**(`교안/새 글`)를 제목으로 만든다 — 3.2 의 1단계로 그 링크가 곧바로 풀린다. 폴더를 새로 만들지 않는다

### 3.7 비용 (실측)

해석기가 링크마다 후보를 다 훑으면 느리다. 2026-09-23 이 PC(Node v24.13.0)에서 합성 데이터로 쟀다 — 폴더 깊이 최대 8, 문서 10% 최상위, 문서마다 링크 10개, 링크 10% 가 경로식, **문서 30% 가 제목 4종을 나눠 가진** 심한 경우(제목 하나에 후보 약 375개). 다른 세션이 같이 돌고 있어 편차가 크다

| 구현 | 문서 1,000 / 링크 1만 | 문서 5,000 / 링크 5만 | 문서 10,000 / 링크 10만 |
| --- | --- | --- | --- |
| 지금 규칙(제목 맵 두 개) | — | 4.1~6.5 ms | — |
| 링크마다 후보 전부 훑기 | 98~138 ms | **1,488~3,446 ms** | 4,310~6,019 ms |
| 제목별 "폴더 → 첫 문서"·"조상 폴더 → 그 아래 첫 문서" 표를 미리 만들고 경로식 걸러내기를 기억 | 22~46 ms (중앙값) | 100~215 ms (중앙값) | 256~281 ms (중앙값) |
| 같은 방식, 겹치는 제목이 600종으로 흩어진 경우 | — | 76~142 ms (중앙값) | — |

- **F-2018 은 셋째 줄 방식을 따른다** — 제목마다 후보를 폴더별로 묶은 표와, 조상 폴더마다 "그 아래 가장 최근 후보" 표를 해석기를 만들 때 한 번 만들어 두면, 링크 하나는 원본의 조상 사슬 길이만큼만 본다. 두 번째 줄 방식은 5,000개에서 수 초라 쓰지 않는다
- 해석기는 문서·폴더 목록이 바뀔 때만 다시 만든다(편집기는 입력마다 만들지 않는다)
- 지도 쪽 기준(F-292 G5 "멈출 때까지 3,000 ms")에 5,000개에서 0.1~0.2초가 더해진다. 게이트로 삼지 않고 F-2018 에서 브라우저 지도 열기 시간을 한 번 재어 적는다
- 측정 스크립트는 스크래치패드에만 있다(저장소에 넣지 않았다)
- **F-2018 로 개정** (2026-09-23): 대소문자 접기를 `toLocaleLowerCase('ko')` 가 아니라 `toLowerCase()` 로 확정했다 — 모든 코드 포인트와 문맥 의존 글자열에서 결과가 하나도 다르지 않았고, 제목 5,000개 접기가 90배 빠르다(F-2018 4.5). 비용 기준은 지도 조건 150ms·서버 조건 10ms·편집기 조건 5ms 로 확정, 브라우저 지도 측정은 Node 실물 측정으로 갈음한다(F-2018 4.6)

## 4. 볼트 가져오기 (F-2019)

### 4.1 입구

| 입구 | 어디 | 어떻게 |
| --- | --- | --- |
| zip | 설정 `데이터` 탭 `가져오기…` (F-282 그대로) | `manifest.json` 이 있으면 F-282 3.6 그대로(id 로 맞춤). **없으면 볼트 가져오기** — F-282 3.7 을 대체한다 (4.7, 8장 Q3) |
| 폴더 선택 | 설정 `데이터` 탭에 버튼 `폴더 가져오기…` 추가 | `<input type="file" webkitdirectory hidden>`. React 19 JSX 타입에 `webkitdirectory` 가 없으므로(`node_modules/@types/react` 확인) 속성은 ref 로 켠다. 파일마다 `File.webkitRelativePath` 첫 조각이 고른 폴더 이름이다 |
| 폴더 끌어놓기 | 창 전체 끌어놓기 (F-145) | `DataTransferItem.webkitGetAsEntry()` 가 `isDirectory` 면 `FileSystemDirectoryReader.readEntries` 로 재귀해 읽는다. `readEntries` 는 한 번에 일부만 줄 수 있어 빈 배열이 올 때까지 반복한다. 디렉터리 1개만 놓였을 때만 받는다. 디렉터리 둘 이상이거나 파일과 섞이면 알림 `폴더는 한 번에 하나만 가져올 수 있습니다.` 끌어놓기 덮개 문구는 `여기에 놓아 .md 파일·폴더 가져오기` |

- 세 입구 모두 **같은 계획·적용 코드**를 탄다. zip 은 F-282 의 스트리밍 두 번 읽기(`readZipEntries`), 폴더는 `File` 목록을 그대로 쓴다(디스크에 있어 두 번 읽을 수 있다)
- **볼트 이름**: 폴더 선택·끌어놓기는 그 폴더 이름. zip 은 F-282 3.7 의 "공통 최상위 벗기기" 로 벗긴 디렉터리 이름, 벗기지 않았으면 zip 파일명에서 `.zip` 을 뗀 것
- 잡음 항목(`__MACOSX/`, `.` 으로 시작하는 조각 — `.obsidian/`·`.trash/`·`.git/` — `Thumbs.db`, `desktop.ini`)은 F-282 3.7 `isNoiseEntry` 규칙 그대로 버리고 세지 않는다. `.obsidian/` 무시는 **이미 그 규칙으로 된다**(확인)
- Playwright 1.63 은 `webkitdirectory` 입력에 디렉터리 경로를 `setInputFiles` 할 수 있다(타입 정의 확인) — 폴더 선택은 e2e 로 판정한다. **폴더 끌어놓기는 합성 `DataTransfer` 에 디렉터리 항목을 넣을 수 없어 사람 확인**이다

### 4.2 넣을 폴더

- 미리보기 대화상자에 `넣을 폴더` 선택을 둔다. 선택지: `새 폴더 "{볼트 이름}"`(최상위에 만든다) / `최상위` / 모든 폴더(`상위 / 하위` 경로, 2.4 들여쓰기)
- **기본값**: 최상위에 볼트 이름과 **정확히 같은 이름의 폴더가 하나** 있으면 그 폴더(다시 가져오기), 없거나 둘 이상이면 `새 폴더 "{볼트 이름}"`
- 넣을 폴더를 바꾸면 계획(새로·갱신·건너뜀)을 다시 계산해 요약을 바꾼다 — 순수 함수라 즉시다
- 전체 내보내기(범위 `all`)로 만든 옵시디언 볼트를 되돌려 넣을 때는 사용자가 `최상위` 를 고른다. 고른 것을 기억하지 않는다 (8장 Q12)

### 4.3 경로로 맞춰 덮기 — 정확한 키

넣을 폴더 T 를 볼트 루트로 본다. 볼트 안 `d1/d2/이름.md` 는 T 아래 `d1/d2` 폴더의 문서 하나에 대응한다

**비교는 "그 문서가 지금 옵시디언으로 내보내진다면 받을 이름" 으로 한다**

- T 아래 기존 폴더·문서마다 5.2 의 옵시디언 내보내기 이름 규칙(파일명 치환, 같은 폴더 안 충돌 시 ` (2)`, 최상위 `attachments` 예약)으로 **이름을 계산**하고, 볼트 쪽 이름과 비교한다. 폴더는 조각마다 같은 방식
- 이 한 규칙이 제목과 파일명이 다른 경우를 모두 덮는다: 금지 문자(`왜?` → `왜_.md`), 100자 자르기, 끝 마침표·공백, Windows 예약 이름, 같은 제목 두 문서(`회의록.md`·`회의록 (2).md`, `createdAt` 순서)
- 비교는 **NFC 정규화 + 대소문자 무시**. 내보내기 충돌 규칙이 이미 대소문자를 무시하므로(F-281 3.2) 한 폴더 안에서 둘이 같은 키를 갖는 일이 없다
- 볼트에서 만든 제목(파일명에서 확장자 `.md`·`.markdown` 을 뗀 것)과 폴더 이름은 **NFC 로 바꿔** 저장한다. 문서 본문은 정규화하지 않는다
- **프론트매터 `title` 은 보지 않는다.** 옵시디언은 파일명이 문서 이름이다
- 대상은 **T 아래 내 문서만**(`role` 이 `owner` 이거나 없음). T 밖 문서는 아무리 이름이 같아도 건드리지 않는다

| 경우 | 동작 |
| --- | --- |
| 키가 맞는 문서가 있고, 변환(4.4) 뒤 본문이 기존 본문과 **같음** | `skip` — 사본을 만들지 않는다. 다시 가져올 때마다 `(가져오기 전)` 문서가 쌓이지 않게 |
| 키가 맞는 문서가 있고 본문이 다름 | `update` — F-282 3.9 의 덮기 전 사본(`{제목} (가져오기 전)`)을 먼저 만든다. 제목은 바꾸지 않는다. 단 키가 대소문자만 달라 맞았으면 제목을 볼트 쪽 이름으로 바꾼다 |
| 맞는 문서가 없음 | `create` — 그 경로의 폴더(없으면 만든다) 안에 새 문서 |
| T 아래 있는데 볼트에 없는 문서 | **그대로 둔다.** 지우지도 옮기지도 않는다. 미리보기 경고 `볼트에 없어 그대로 둔 문서 {N}개` (8장 Q4) |
| 볼트에서 파일을 옮김 | 옛 자리 문서는 위 행대로 그대로, 새 자리에 새 문서. 옮김을 알아내지 않는다 |
| 폴더 | 키가 맞는 폴더를 쓴다. 없으면 볼트 조각 이름(NFC)으로 만든다. 문서가 하나도 없는 볼트 폴더는 만들지 않는다(F-282 3.7 과 같음) |

- 알려진 한계: 같은 폴더에 같은 제목 문서가 둘 있고 내보낸 뒤 앞의 것을 지웠으면 ` (2)` 번호가 당겨져 다른 문서와 맞을 수 있다. 덮기 전 사본이 남으므로 내용은 잃지 않는다
- 기존 문서의 `lineEnding` 은 바꾸지 않는다(F-282 3.9 `update` 와 같음). 새 문서는 `decodeMarkdown` 판정을 따른다
- 한도(문서 1MB·이미지 5MB·계정 300MB)·잠금 문서·취소·실패 목록·열린 문서 재마운트는 F-282 3.9~3.10 그대로

### 4.4 이미지 변환

**찾는 모양** (펜스 코드블록·인라인 코드·프론트매터 안은 보지 않는다)

| 원문 | 파일 찾기 |
| --- | --- |
| `![[그림.png]]`, `![[그림.png\|300]]`, `![[그림.png\|300x200]]`, `![[그림.png\|설명]]` | 이름만 있으면 볼트 전체에서 **파일 이름**으로, `하위/그림.png` 처럼 경로가 있으면 3.2 와 같은 끝 맞추기. 여럿이면 3.3 순서(원본 문서 폴더 기준) |
| `![설명](그림.png)`, `![설명](<그림 1.png>)`, `![](a%20b.png)` | 문서 폴더 기준 상대 경로 → 볼트 루트 기준 → 이름이 볼트에 하나뿐이면 그것. `%XX` 는 풀어서 찾는다 |
| `![](https://…)` | 외부 주소 — 바꾸지 않고 세지도 않는다(Q30 대로 링크로만 보인다) |
| 이미 이 앱 형식인 F-156 블록(`attachments/{16hex}.{ext}`) | F-282 3.7 그대로 문서 폴더 기준 `attachments/` 에서 찾아 id 를 유지해 넣는다 |

**바꾸는 조건** — 임베드가 **줄 하나를 혼자 차지하고 줄 앞에 공백이 없을 때만** 그 줄을 F-156 3줄 블록으로 바꾼다. 문단 가운데·목록 안(들여쓴 줄)·한 줄에 여럿이면 원문 그대로 두고 경고에 센다. F-156 블록은 `<div>` 줄이 줄 첫 칸에서 시작해야 해석되므로(`parseImageBlock`) 들여쓴 자리에 넣으면 블록이 되지 않는다. 8장 Q9

**블록 값**

| 속성 | 값 |
| --- | --- |
| `align` | `left` |
| `src` | `attachments/{id}.{ext}` — 저장소가 돌려준 id·ext |
| `alt` | `\|` 뒤가 크기 모양(`^\d+(x\d+)?$`)이 아니면 그 글자, 마크다운 이미지는 `[설명]`, 없으면 파일 이름에서 확장자를 뗀 것. F-156 2.1 의 이스케이프·100자 규칙 |
| `width` | `\|300` → `300`, `\|300x200` → `300`(높이는 버린다 — F-156 블록에 높이가 없다). 없으면 **`width` 속성을 쓰지 않는다** — `image.css` 의 `max-width: 100%` 로 원래 크기까지만 커진다. `buildImageBlock` 은 지금 `width` 가 필수라 선택으로 바꾼다 |

**다시 가져올 때 기존 블록 이어받기** — `update`·`skip` 판정 전에, 키가 맞은 기존 문서에 **같은 첨부 id 의 F-156 블록**이 있으면 그 블록의 `align` 과 `alt` 를 쓴다(볼트 쪽에 `|설명` 이 있으면 그것이 이긴다). `width` 는 볼트 쪽 `|숫자` 를 따른다. 이렇게 해야 5.3 으로 내보냈다가 손대지 않고 되돌린 문서가 **바이트까지 같아져** `skip` 된다

**파일 넣기**

- 형식은 `inspectImageBytes`(`src/lib/imageFile.ts`)가 PNG·JPEG·GIF·WebP 로 알아본 것만. `.jpeg`·대문자 확장자도 내용으로 판정한다. SVG·BMP·AVIF·PDF 는 원문 그대로 + 경고
- 파일 이름이 `{16자리 소문자 16진수}.{png|jpg|gif|webp}` 이고 내용 형식이 확장자와 같으면: 저장소에 그 id 가 **있으면 새로 올리지 않고 그대로 쓴다**, 없으면 **그 id 로 올린다**(`putAttachment({ id })`, F-282 3.11 — 서버 저장소는 이때 WebP 변환을 건너뛴다). 5.3 으로 내보낸 이미지가 되돌아올 때 같은 첨부로 이어지는 길이다. 첨부 키가 `[소유자, id]` 라 남의 첨부와 부딪히지 않는다(F-282 4.1 확인)
- 그 밖의 이름은 **내용 해시 id**(파일 바이트 SHA-256 앞 8바이트를 소문자 16진수 16자로)로 올린다 — 같은 그림은 언제 가져와도 같은 id 라 다시 가져와도 `update`·사본·재업로드가 생기지 않고, 이름이 달라도 내용이 같으면 한 첨부다. id 를 주면 서버 저장소가 WebP 변환을 건너뛰므로 서버 저장소의 PNG·JPEG 는 가져오기가 직접 WebP 로 바꿔 넣는다(F-2019 6.2·9.3) — 전제 4 의 대가 (사용자 2026-09-23 — 원래 "새 id 로 올린다", F-2019 17장 Q1)
- 볼트 안 같은 파일을 여러 문서가 쓰면 **한 번만** 올린다
- 5MB 를 넘거나 형식이 아니면 그 임베드는 원문 그대로, 실패 목록에 파일 이름
- **적용 순서가 F-282 와 다르다**: 폴더 → **이미지** → 문서. 문서 본문에 저장소가 준 id·ext 를 적어야 하므로 이미지를 먼저 올린다. `.md` 본문은 1차 훑기에서 이미 메모리에 있다(`App.tsx` `previewImportZip` 이 지금도 `.md` 본문을 읽어 둔다 — 확인)

### 4.5 바꾸지 않는 것

- 이미지가 아닌 임베드 `![[노트]]`·`![[노트#헤딩]]`·`![[x.pdf]]`·`![[x.canvas]]`·`![[x.mp4]]` — 원문 그대로. 경고에 이미지와 합쳐 센다 (전제 7)
- `#태그`, 각주, `aliases` 프론트매터(옵시디언은 별칭으로도 링크를 푼다 — 이 앱은 풀지 않는다), 마크다운식 내부 링크 `[글](폴더/노트.md)`(일반 링크로 남는다), `.canvas` 파일

### 4.7 F-282 와의 관계

- `manifest.json` 이 있는 zip(이 앱의 전체·폴더 내보내기)은 **바뀌지 않는다.** id 로 맞추는 쪽이 경로보다 정확하다
- `manifest.json` 이 없는 zip 은 볼트 가져오기가 대신한다. F-282 3.7 과 달라지는 점: 넣을 폴더(기본 `새 폴더 "{볼트 이름}"`), 경로 맞춤 갱신, 이미지 변환, 폴더를 합치지 않음(2장). 처음 가져올 때는 새 폴더 안이라 맞는 문서가 없으므로 결과가 "전부 새 문서" 로 F-282 와 같고, 자리가 최상위에서 볼트 이름 폴더 안으로 바뀐다
- F-282 3.7 의 "같은 부모에 이름이 같은 폴더가 있으면 그 폴더에 넣는다" 는 **구현되지 않았다**(`planPlainImport` 는 기존 폴더를 받지 않고, `applyImportPlan` 은 plain 폴더를 늘 새로 만든다 — 확인). 볼트 가져오기의 폴더 키 맞춤(4.3)이 그 약속을 대신 지킨다 (7장 충돌 1)

### 5.1 자리·대상

| 자리 | 항목 | 대상 |
| --- | --- | --- |
| 설정 `데이터` 탭 | 버튼 `옵시디언 볼트로 내보내기` (`전체 내보내기` 옆) | F-281 3.1 과 같다 — 로그인 안 함: 이 브라우저 전부, 로그인: 내 문서만, 로그인 + 오프라인: 막고 `온라인일 때 내보낼 수 있습니다` |

- 상단바 문서 하나 `내보내기` 메뉴에는 넣지 않는다. 문서 하나는 볼트가 아니다
- 시작 전 `await saver.flush()` (F-281 3.1 과 같은 이유)

### 5.2 zip 모양

```
{YYYY-MM-DD}-vault.zip           (폴더는 {toFolderName(폴더 이름)}-vault.zip)
├─ attachments/{id}.{ext}        ← 볼트 전체에서 쓰는 이미지, 한 번씩
├─ {문서}.md
└─ {폴더}/
    ├─ {문서}.md
    └─ {하위 폴더}/…
```

- `manifest.json` 을 넣지 않는다. `.obsidian/` 설정 폴더도 만들지 않는다 — 옵시디언은 폴더를 처음 열 때 스스로 만든다(가정 G4)
- 이미지는 **루트 `attachments/` 한 곳**. 이름이 `{id}.{ext}` 라 볼트 전체에서 겹치지 않으므로 `![[{id}.{ext}]]` 가 어느 폴더 문서에서든 하나로 풀린다 — 옵시디언이 `![[이름]]` 을 볼트 전체에서 이름으로 찾는다는 것은 **확인하지 못했다**(가정 G1, 사람 확인)
- zip 파일명에 제품명을 넣지 않는다(F-277 2.2). `-export.zip`(F-281)과 구분되게 `-vault` 를 붙인다
- 디렉터리·파일 이름은 F-281 경로 계획(`buildFolderPaths`·`buildDocPaths` 의 충돌·예약어 규칙)을 **이름 함수만 바꿔** 그대로 쓴다. 예약어 `attachments` 는 F-281 처럼 모든 디렉터리에서 민다(루트만 필요하지만 규칙을 하나로 둔다)
- 스트리밍 `Zip` + `ZipPassThrough`, 진행·실패 처리, 없는 이미지 알림 `이미지 {N}개를 찾을 수 없어 빼고 내보냈습니다.` 는 F-281 3.3·3.5·3.8 그대로
- **F-281 zip 의 바이트는 한 글자도 바뀌지 않는다** — `exportWorkspace.ts` 에서 경로 계획을 꺼내 쓰더라도 F-281 기존 단위 테스트가 그대로 통과해야 한다

### 5.3 변환 규칙

**이 앱 전용 문법은 이미지 블록 하나뿐이다** — 코드로 훑어 확인했다. 콜아웃(`[!type]`)·`==…==`·`%%…%%`·`<!-- -->`·`$…$`·Mermaid 펜스·프론트매터·`[[제목|별칭]]` 은 옵시디언과 문법이 같다. 제목은 원문 밖(`Doc.title`)에 있어 파일명이 된다

| 무엇 | 규칙 |
| --- | --- |
| F-156 이미지 블록(`parseImageBlock` 이 해석하는 3줄) | 한 줄 `![[{id}.{ext}\|{width}]]`, `width` 가 없으면 `![[{id}.{ext}]]`. `align`·`alt` 는 옵시디언에 해당 문법이 없어 버린다(다시 가져올 때 4.4 로 되살린다) |
| 블록으로 해석되지 않는 `attachments/{id}.{ext}` 참조 | 파일은 넣고 원문은 그대로. 알림에 개수를 붙이지 않는다(F-156 은 해석 안 되는 블록을 원문으로 보이므로 옵시디언에서도 같은 모습이다) |
| 파일명 | `toFileName` 에 더해 **`#` `^` `[` `]` 를 `_` 로**. 옵시디언 링크에서 `#`·`^` 는 헤딩·블록 구분자, `[` `]` 는 링크 괄호라 파일명에 있으면 `[[…]]` 로 가리킬 수 없다. 폴더 이름도 같다 |
| 위키링크 | 아래 |
| 줄바꿈 | 문서 `lineEnding` 그대로(F-281 과 같음). 인코딩 UTF-8, BOM 없음 |

**위키링크 고쳐 쓰기** — 필요할 때만 고친다

1. 각 링크를 3장 해석기로 푼다. 원본 = 그 문서, 후보 = **내보내는 범위 안 문서만**(폴더 내보내기면 그 폴더 밖 문서로 풀리는 링크는 볼트에서 끊기므로 그대로 둔다)
2. 풀리지 않는 링크, `[[#헤딩]]` 은 그대로
3. 풀린 문서 D 의 볼트 안 경로(`.md` 를 뗀 것)를 P, 파일 이름을 N 이라 할 때, 링크의 대상이 이미 **P 의 끝과 맞고**(3.2 끝 맞추기, 대소문자 무시) **그 끝 맞추기로 볼트 안에서 D 하나만 가리키면** 그대로 둔다
4. 아니면 대상을 **P 의 끝 조각 중 볼트 안에서 D 하나만 가리키는 가장 짧은 것**으로 바꾼다(`N` → `상위/N` → …). 헤딩 조각은 그대로 붙인다. 별칭이 없던 링크는 원래 대상 글자를 별칭으로 넣어 보이는 글자를 지킨다 — `[[왜?]]` → `[[왜_|왜?]]`, 같은 이름이 둘이면 `[[회의록]]` → `[[교안/회의록|회의록]]`
5. 고친 링크가 있으면 끝 알림에 개수를 붙인다 (6.4)

- 옵시디언이 같은 이름 파일 중 무엇을 고르는지 확인하지 못했으므로(가정 G1) **이름이 볼트 안에서 하나가 아니면 무조건 경로를 붙인다** — 옵시디언의 규칙이 무엇이든 경로가 붙은 링크는 하나로 풀린다
- 8장 Q6

### 5.4 왕복이 한 번에 수렴한다

- 이미지: 내보내면 `![[{id}.{ext}|{width}]]`, 되가져오면 4.4 가 같은 id 를 재사용하고 기존 블록의 `align`·`alt` 를 이어받아 **원래 블록과 같은 바이트**가 된다 → `skip`
- 위키링크: 5.3 으로 경로가 붙은 링크는 되가져오면 원문이 달라 **처음 한 번 `update`** 된다(사본이 남는다). 그 뒤 다시 내보내면 경로식 링크가 이미 하나로 풀리므로(5.3 의 3) 고치지 않는다 → 두 번째 왕복부터 `skip`
- 서버 저장소에서 새로 넣은 이미지는 WebP 로 바뀐다(전제 4) — 옵시디언에서 새로 붙여 넣은 `Pasted image ….png` 는 되가져오면 `{id}.webp` 가 되고, 그다음 내보내기부터는 그 이름으로 고정된다

4. **`App.tsx` 의 위키링크 풀이는 공유받은 문서까지 후보로 본다**(`docs` 에 `role` 이 `edit`·`view` 인 문서가 섞여 있다). 새 규칙에서도 그대로 두되 3.2 끝의 취급을 따른다 — 버그가 아니라 기록

## 8. 열린 질문 / 사람 결정 필요

### Q1. "가까운 폴더" 에 3단계(공통 조상이 깊은 후보)를 더하는가 — **기본값: 더한다** (3.3)

- 사용자 문구는 "같은 폴더 → 가까운 조상 → 최근 수정" 이다. 그대로면 원본 폴더의 조상 사슬 밖 후보(형제·사촌 폴더)는 모두 "최근 수정" 으로 갈린다
- 더하는 이유: 볼트를 `내 볼트` 폴더 하나에 넣으면 `내 볼트/위키/개념/a` 의 `[[색인]]` 이 볼트 안 `내 볼트/위키/인물/색인` 을 두고 **볼트 밖 아무 `색인`** 으로 갈 수 있다. 3단계가 있으면 볼트 안이 먼저다
- 문구대로 하면: 해석기에서 "조상 폴더 → 그 아래 첫 문서" 표가 빠져 조금 단순해진다. 가져온 볼트가 여러 개거나 같은 이름 문서가 이미 있는 저장소에서 링크가 볼트 밖으로 새는 경우가 생긴다

### Q2. 들여쓰기 상한을 몇 단계로 — **기본값: 6단계부터 멈춤(`--depth` 5, 70px)** (2.4)

- 4단계(42px): 최소 폭에서도 이름이 넉넉하지만 5·6단계가 겹쳐 보여 옵시디언 볼트 구조가 흐려진다
- 8단계(98px): 기본 폭 300px 에서 이름 칸이 120px 안팎으로 준다
- 상한 없음: 깊은 트리에서 이름이 사라진다

### Q3. `manifest.json` 없는 zip 을 모두 볼트 가져오기로 보내는가 — **기본값: 보낸다(F-282 3.7 대체)** (4.7)

- 보내는 이유: 옵시디언 볼트를 압축한 것과 아무 `.md` 묶음을 구분할 방법이 확실하지 않고(`.obsidian/` 이 없는 볼트도 흔하다), 볼트 가져오기가 첫 가져오기에서 F-282 와 같은 결과(전부 새 문서)를 낸다. 달라지는 것은 자리(최상위 → 볼트 이름 폴더 안)와 이미지 변환뿐이다
- 따로 두면: 미리보기에 `옵시디언 볼트로 가져오기` 체크박스를 두고 끄면 F-282 3.7 그대로. 사용자가 한 번 더 판단해야 하고 두 경로를 계속 유지해야 한다

### Q4. 볼트에서 사라진 문서를 어떻게 하나 — **기본값: 그대로 둔다** (4.3)

- 지우자는 안(미리보기에 `볼트에 없는 문서 {N}개 지우기` 체크)을 넣으면 옵시디언 쪽 정리가 이 앱에도 반영된다. 대신 이 앱에서만 새로 쓴 문서를 한 번의 가져오기로 잃을 수 있다 — 되돌리기가 없다(F-282 3.9)
- 옮김 감지(이름이 같고 경로만 다른 파일을 같은 문서로 보기)도 넣지 않는다. 같은 이름 파일이 흔한 볼트(`index.md`)에서 틀리게 이어 붙인다

### Q5. 본문이 같으면 건너뛰는가 — **기본값: 건너뛴다(사본 없음)** (4.3)

- 건너뛰지 않으면 다시 가져올 때마다 모든 문서에 `(가져오기 전)` 사본이 쌓인다. 사실상 결정이 필요 없는 기본값이라 "기본값으로 정한 것" 에도 적었다

### Q6. 옵시디언 내보내기에서 위키링크를 고쳐 쓰는가 — **기본값: 필요할 때만 고친다** (5.3)

- 고치지 않으면: 원문이 덜 바뀌지만 `[[왜?]]`(파일은 `왜_.md`)·같은 이름 문서로 가는 링크가 옵시디언에서 끊기거나 다른 문서로 간다. 끝 알림에 `옵시디언에서 찾지 못할 위키링크 {N}개` 만 적게 된다
- 고치면: 처음 왕복 때 해당 문서가 한 번 `update` 된다(5.4)

### Q7. 옵시디언 파일명에서 `# ^ [ ]` 도 바꾸는가 — **기본값: `_` 로 바꾼다** (5.3)

- 안 바꾸면 `C# 정리.md` 가 되고 `[[C# 정리]]` 는 옵시디언에서 `C` 문서의 ` 정리` 헤딩으로 읽힌다. 이 앱도 `#` 뒤를 헤딩으로 보므로(3.1) 그런 제목은 원래 위키링크로 가리킬 수 없다 — 바꿔도 잃는 링크가 없다

### Q8. 공개 묶음 보기의 해석을 서버가 하는가 — **기본값: 서버가 링크 표를 내려준다** (3.4)

- 지금처럼 묶음 문서 `{id,title}` 안에서 제목만으로 풀면 같은 제목 두 문서가 묶음에 들 때(`index` 가 폴더마다 있는 위키) 엉뚱한 문서로 간다. 폴더 경로를 응답에 넣으면 익명 방문자가 묶음 문서들의 폴더 이름을 보게 된다
- 서버 표 방식의 대가: `GET /pub/docs/:token/set` 이 묶음 문서 본문(최대 50개, F-252 2.2 상한)과 소유자 문서·폴더 목록을 읽는다 — 공유 대화상자의 묶음 미리보기(`handleGetDocShareSet`)가 이미 같은 양을 읽는다

### Q9. 줄 가운데 이미지 임베드를 바꾸는가 — **기본값: 바꾸지 않는다(원문 그대로 + 경고)** (4.4)

- 바꾸면 그 줄을 앞 글·블록 3줄·뒤 글로 쪼개야 해 문단 구조가 바뀐다. 목록 안(들여쓴 줄)은 F-156 블록이 들여쓰기를 허용하지 않아 바꿀 수 없다
- 옵시디언은 붙여 넣은 이미지를 대개 줄 하나에 혼자 넣는다(가정 G6). 실제 볼트에서 얼마나 남는지는 사람 확인

### Q10. 헤딩 이동을 주소에 남기는가 — **기본값: 남기지 않는다** (3.5)

- 남기면(`#/d/{id}#헤딩` 같은 꼴) 해시 주소 해석(`hashRoute.ts`)·공개 주소(`#/p/{토큰}/{문서id}`)까지 바꿔야 하고 헤딩 글자가 주소에 그대로 드러난다. 뒤로 가기로 헤딩 위치에 돌아오는 것만 잃는다

### Q11. 소명세 병렬 — **결론: 병렬 불가, 차례대로** (6.1)

- 사람 결정이 아니라 확인 결과를 알리는 항목이다. 앞당기는 유일한 방법(F-2020 에서 링크 고쳐 쓰기 빼기)은 권하지 않는다

### Q12. 넣을 폴더를 기억하는가 — **기본값: 기억하지 않는다** (4.2)

- 기억하려면 볼트 이름 → 폴더 id 를 localStorage 에 둔다(새 키, 제품명 없는 이름). 전체 볼트를 `최상위` 로 되돌리는 사람은 매번 한 번 고르는 수고가 준다. 볼트 이름과 같은 최상위 폴더 기본값만으로 흔한 경우(폴더 하나에 넣은 볼트)는 이미 맞는다

### Q13. `볼트` 라는 말을 UI 에 쓰는가 — **기본값: `옵시디언 볼트` 로 쓴다** (6.4)

- 사용자가 그릴링에서 `옵시디언 볼트` 항목이라 불렀다. 옵시디언 한국어 화면은 vault 를 `보관함` 으로 옮기는 것으로 알고 있으나 **확인하지 않았다**. `보관함` 으로 바꾸면 6.4 의 문구 다섯 줄이 바뀐다

### 기본값으로 정한 것 (승인 시 확정)

1. 폴더 옮기기는 자기 자신·자기 자손·없는 대상만 막는다 — 2.1
2. 순환 데이터가 들어와도 `ancestorsOfDoc` 이 멈추지 않고 `buildTree` 가 폴더를 잃지 않는다 — 2.3
3. 들여쓰기는 6단계에서 멈추고 문서 제목 위 경로는 접지 않는다 — 2.2·2.4
4. 경로식 링크는 끝 맞추기, 제목 전체 일치가 먼저 — 3.2
5. 가까운 폴더는 같은 폴더 → 조상 → 공통 조상 깊은 순 → 최근 수정 — 3.3
6. 헤딩은 1~6단계, 못 찾으면 문서 처음 + 알림, 주소에 남기지 않음 — 3.5
7. 없는 경로식 링크는 맞는 폴더가 있으면 거기에, 없으면 대상 전체를 제목으로 — 3.6
8. `manifest.json` 없는 zip 은 볼트 가져오기 — 4.7
9. 경로 맞춤 키는 "지금 옵시디언으로 내보내면 받을 이름", NFC·대소문자 무시, 프론트매터 `title` 무시 — 4.3
10. 본문이 같으면 건너뜀, 볼트에 없는 문서는 그대로 — 4.3
11. 이미지는 줄 하나를 혼자 차지할 때만 블록으로, `align="left"`, 크기 없으면 `width` 안 씀, 다시 가져올 때 기존 블록의 `align`·`alt` 이어받기 — 4.4
12. `{16진수}.{ext}` 이름 이미지는 id 를 이어 쓴다 — 4.4
13. 옵시디언 내보내기: 루트 `attachments/`, `-vault.zip`, `# ^ [ ]` 도 `_`, 모호한 링크에만 경로 — 5.2·5.3
14. 공개 묶음 보기는 서버 링크 표 — 3.4
15. 소명세는 차례대로 — 6.1

## 9. 확인한 것과 가정

### 9.1 코드를 읽거나 돌려 확인한 것

- 서버도 폴더 깊이를 검사한다 — `worker/folders.ts` `handleCreateFolder`·`handleUpdateFolder` 가 `src/lib/folderTree` 의 `canCreateFolder`·`canMoveFolder` 를 import 해 부른다. D1 `folders` 표에는 깊이 제약이 없다
- 순환 이동 방지가 깊이 규칙에 기대고 있다 — `canMoveFolder` 의 직접 검사는 `parentId === id` 하나뿐
- 2단계를 가정한 서버 코드 두 곳 — `worker/grants.ts` `handleGetShared`(직속 하위만, `viaFolder` 두 칸)와 `worker/links.ts` `folderTreeIds`(주석 "손자는 없다")
- 깊이와 무관하게 이미 맞는 곳 — `descendantFolderIds`, `folderChainRole`, `exportWorkspace.ts` `buildFolderPaths`, `searchIndex.ts` `folderPathMap`, `mapFilter.ts` `expandFolders`, `removeFolder` 두 방식
- `ancestorsOfDoc` 은 순환 데이터에서 무한 루프 — `while` 에 방문 기록이 없다
- `.obsidian/` 은 F-282 `isNoiseEntry` 가 이미 버린다
- F-282 3.7 의 같은 이름 폴더 재사용은 구현되지 않았다 (7장 충돌 1)
- 이 앱 전용 문법은 F-156 이미지 블록뿐이다 — 주석(`comments.ts`, `%%`·`<!-- -->`), 하이라이트(`highlightSyntax.ts`), 콜아웃(`callout.ts` `[!type]`)은 옵시디언 문법
- 서버 저장소 WebP 변환은 `serverStore.putAttachment` 안에서, `id` 를 주면 건너뛴다. 첨부 키는 `[소유자, id]`
- 편집기 위키링크 표시는 제목 배열(`wikiTitlesField`)만 들고 있어 폴더를 모른다. 목차 `extractHeadings` 는 1~3단계만
- 공개 묶음 보기는 `{id,title}` 만 받는다. 서버 묶음 수집은 문서를 정렬 없이 읽는다
- `webkitGetAsEntry`·`webkitRelativePath`·`webkitdirectory`·`readEntries` 는 TS DOM 타입에 있고, React 19 JSX 타입에 `webkitdirectory` 는 없다. Playwright 1.63.0 은 `webkitdirectory` 입력에 디렉터리를 `setInputFiles` 할 수 있다
- 해석 비용 실측 — 3.7 표 (Node v24.13.0, 합성 데이터, 다른 작업과 함께 돌아 편차가 크다)
