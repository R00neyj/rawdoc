## 1. 범위

### 1.1 하는 것

- 로그인한 사용자가 기기마다 `이 기기에서 푸시 받기` 를 켜면, 그 기기(브라우저 프로필 하나 = 구독 하나)로 **표준 웹 푸시**(RFC 8030 전송 + RFC 8291 암호화 + RFC 8292 VAPID)를 보낸다. 설치한 PWA 든 데스크톱 브라우저 탭이든 같은 경로다
- 보내는 것 넷(사용자 결정 1): 멘션·답글 / 내 문서의 새 댓글 / 공유·초대 받음 / 저장 공간 경고
- 댓글 계열(앞의 둘)은 **문서마다 3분 묶음**, 보내기 직전에 "지금 그 문서를 열어 둠"·"이미 읽음" 을 다시 보고 뺀다(3.4)
- 알림에 **무엇이 왔는지**(누가·어느 문서·발췌)와 **앱 아이콘**이 보이고, 누르면 그 댓글·문서로 간다(2.4, 4.4)
- 로그아웃·세션 만료·계정 삭제·푸시 서비스의 404·410 에서 구독을 치운다(3.7)

### 1.2 이번 범위에서 빼는 것

- 새 버전 알림 푸시(사용자 결정 2)
- 메일 알림(F-500 1.2 그대로)
- 종류별 켜기·끄기, 방해 금지 시간, 기기 목록 화면(사용자 결정 4)
- "앱이 보이면 OS 알림 대신 앱 안에서만" 같은 클라이언트 쪽 억제(10장 Q6)
- 로그인 안 한 로컬 문서(댓글 알림이 원래 없다, F-500 사용자 결정 3)
- 금고(E2EE) 문서에서 생기는 알림 — 생길 길 자체가 없다(3.9)
- 안드로이드 앱(Capacitor)의 FCM 네이티브 알림 — 웹앱 먼저(CLAUDE.md "Direction")
- 10장 Q8 에 적은 "생각 못 한 알림" 후보들(댓글 해결됨, 공유 문서 편집됨 등)

### 1.3 이 개요가 만드는 파일

| 파일 | 변경 |
| --- | --- |
| `specs/features/F-3001.md` | **신규.** 이 파일 하나. 코드·다른 명세는 고치지 않는다 — 하위 명세별 파일은 6장, 고칠 문서는 9장 |

## 2. 데이터 모델

### 2.1 구독 표 — D1 `push_subscriptions` (계약)

마이그레이션 `migrations/0017_push_subscriptions.sql`(지금 마지막이 `0016_shared_indexes.sql`. F-3003 을 쓸 때 다음 빈 번호). 이름을 바꾸면 F-3003~F-3008 이 어긋난다:

```sql
CREATE TABLE push_subscriptions (    -- 기기(브라우저 프로필) 하나 = 행 하나
  id TEXT PRIMARY KEY,               -- crypto.randomUUID()
  user_id TEXT NOT NULL,             -- users.id. 외래 키를 걸지 않는다 (purge_jobs 와 같은 이유)
  session_id TEXT,                   -- auth_sessions.id. NULL = 로컬 개발 우회 사용자
  endpoint TEXT NOT NULL UNIQUE,     -- 허용한 푸시 서비스의 https 주소, 최대 1,024자 (3.8)
  p256dh TEXT NOT NULL,              -- 받는 쪽 공개 키, base64url 65 B
  auth TEXT NOT NULL,                -- 인증 비밀, base64url 16 B
  created_at INTEGER NOT NULL,       -- ms
  last_ok_at INTEGER,                -- 마지막으로 2xx 를 받은 때. 하루에 한 번만 고쳐 쓴다
  fail_count INTEGER NOT NULL DEFAULT 0   -- 이어진 4xx(404·410·429 제외) 수. 3 이면 지운다
);
CREATE INDEX push_subscriptions_user ON push_subscriptions(user_id);
```

- **`endpoint` 가 기기의 정체다.** 같은 브라우저가 다른 계정으로 다시 켜면 그 행이 새 계정·새 세션으로 **옮겨 간다**(upsert). 한 기기는 한 계정의 푸시만 받는다
- **세션에 묶는다.** 보낼 때 `auth_sessions` 에 그 세션이 살아 있는지(`expires_at` > 지금) 함께 본다(3.8). 그래서 로그아웃(세션 행 삭제)·세션 만료(30일 동안 안 씀, p12) 뒤에는 **클라이언트가 아무것도 안 해도** 그 기기로 안 간다. 세션 연장은 id 를 바꾸지 않는다(p12)
- 계정당 최대 **5개**(`PUSH_SUBSCRIPTIONS_PER_USER_MAX`). 6번째를 넣으면 `last_ok_at`(없으면 `created_at`)이 가장 오래된 것을 같은 batch 에서 지운다. 5 인 이유는 3.5 의 Worker CPU(기기 5개 × 0.68 ms ≈ 3.4 ms, p2)
- 기기 이름(`user_agent`)은 두지 않는다 — 기기 목록 화면이 없다(1.2). 나중에 목록을 만들면 열 하나를 더한다
- 표 이름·열에 제품명이 없다(불변조건)

### 2.2 알림 표 — `notifications` 바꾸기 (계약, **10장 Q1 기본값 기준**)

마이그레이션 `migrations/0018_notifications_push.sql`. SQLite 는 `CHECK` 를 `ALTER` 로 못 바꾸므로(p10) **표를 새로 만들어 옮긴다**(새 표 → `INSERT … SELECT` → 옛 표 `DROP` → 이름 바꾸기 → 색인 셋 다시 만들기: `notifications_recipient_order`, `notifications_doc`, `UNIQUE`). 달라지는 것 둘:

| 열 | 전 | 후 |
| --- | --- | --- |
| `kind` | `CHECK (kind IN ('mention','reply'))` | `CHECK (kind IN ('mention','reply','comment'))` — `comment` = 내 문서에 남이 단 새 댓글·답글 |
| `push_due_at` | 없음 | **`INTEGER`**, NULL 허용. "이 행을 푸시로 보낼 차례가 되는 때(ms)". **NULL = 보낼 것 없음**(받는 사람에게 구독이 없었음 / 이미 처리함 / 읽음) |

- `push_due_at` 에 **색인을 걸지 않는다.** 보낼 것을 찾을 때는 이미 있는 `notifications_doc(doc_id)` 로 그 문서 행만 걷고 `push_due_at IS NOT NULL` 로 거른다. 이유: D1 무료 한도는 쓰기(10만/일)가 읽기(500만/일)보다 50배 빡빡하다(p5). 부분 색인을 걸면 넣을 때·처리할 때 행마다 쓰기가 1~2행 더 든다 — 3.1 의 계산에서 1만 명일 때 쓰기가 약 9% → 약 18% 로 는다
- `comment` 종류의 행 모양은 `mention`·`reply` 와 같다(`comment_id`·`thread_id`·`actor_email`·`doc_title`·`excerpt`). 새 열이 필요 없다
- 공유·초대는 알림함 행도 만든다(F-3012, 2026-10-01 번복 — 공유 목록 10분 TTL 때문에 `공유받음` 이 바로 안 보임). 저장 공간 경고는 푸시만 — 계정 메뉴 사용량 줄이 90% 에서 빨개진다(F-221 2.5, F-2030 7장)

### 2.3 저장 공간 경고 표시 — `users.push_quota_at` (계약)

마이그레이션 `migrations/0019_push_quota.sql`: `ALTER TABLE users ADD COLUMN push_quota_at INTEGER;` — 마지막으로 저장 공간 경고 푸시를 **보내기로 정한** 때(ms). NULL = 아직 없음. 7일 안에는 다시 보내지 않는다(3.6)

### 2.4 푸시 본문 — 서버 → 서비스 워커 (계약, `src/lib/pushPayload.ts`)

```ts
// 암호화 전 평문 JSON. 서비스 워커는 이 모양만 믿고 문구를 만들지 않는다
type PushPayload = {
  v: 1
  title: string   // 알림 제목 (5.1)
  body: string    // 알림 본문 (5.1)
  tag: string     // 'doc:{docId}' | 'share:{targetId}' | 'quota' | 'test'
  url: string     // 누르면 열 곳. 반드시 '/' 로 시작하는 같은 출처 경로 ('/#/d/{docId}/c/{threadId}' 등)
}
```

- **문구는 서버가 만든다**(`src/lib/pushText.ts`, 순수 함수 — Worker 가 import 한다). 서비스 워커는 모양 검사 뒤 `showNotification` 만 한다. 이유: 문구를 한 곳에 두고 node 단위 테스트로 고정한다. 서비스 워커는 e2e 로도 못 본다(p14)
- 평문은 **최대 3,000 B**(`PUSH_PAYLOAD_MAX_BYTES`). 레코드 크기 4,096 에서 머리 86 B·태그 16 B·구분 1 B 를 빼면 3,993 B 까지 되지만 여유를 둔다. 넘을 것 같으면 `body` 를 자른다(제목·발췌 상한이 있어 보통 700 B 안팎, p2)
- `tag` 가 같은 알림은 OS 가 **바꿔 끼운다** — 같은 문서의 새 묶음은 알림이 쌓이지 않고 하나로 갱신된다. `renotify` 는 쓰지 않는다(기본 거짓 — 바꿔 끼울 때 다시 울리지 않는다)
- 아이콘 `/icons/icon-192.png`, 배지 `/icons/badge-96.png`(**신규** — 투명 바탕 단색 `#` 기호, `scripts/make-icons.py` 가 만든다. p7). 제품명은 본문·제목에 넣지 않는다 — 데스크톱은 출처(`rawdoc.app`)를, 안드로이드 설치 앱은 매니페스트 이름을 OS 가 머리에 붙인다

**N 명일 때 하루 추정 — 가정을 분리해 적는다**

가정(**재지 않았다.** 서비스 사용량이 없어 이 수치는 계산 모형이다): 하루 활성 30%, 활성 1명이 하루 새 댓글·답글 3개, 댓글 하나가 알림 행 1.2개(멘션·답글·주인 `comment`), 푸시를 켠 사람 40%·평균 기기 1.5개, 묶음 하나에 행 1.5개, 문서 알람 하나에 받는 사람 1.2명, 지금 열어 둠·이미 읽음으로 빠지는 것 30%, 공유는 사람당 하루 0.05번. 계산은 스크래치패드 `f511/budget.mjs`(부분 색인 없는 2.2 기준으로 고쳐 적음)

| N | 알림 행/일 | 푸시 대상 행 | 문서 알람(DO 요청) | 실제 푸시(기기 기준 fetch) | Worker 요청(구독 다시 알리기) | D1 쓰기(푸시 몫) | D1 읽기(푸시 몫) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | 108 | 43 | 24 (**무료 한도의 0.02%**) | 33 | 17 (0.02%) | 약 93 (0.09%) | 약 870 (0.02%) |
| 1,000 | 1,080 | 432 | 240 (0.24%) | 332 | 171 (0.17%) | 약 940 (0.9%) | 약 8,700 (0.17%) |
| 10,000 | 10,800 | 4,320 | 2,400 (2.4%) | 3,324 | 1,714 (1.7%) | 약 9,400 (**9.4%**) | 약 86,000 (1.7%) |

- D1 쓰기(푸시 몫) = 처리한 알림 행(1행씩, 색인 없음) + 구독 `last_ok_at`(하루 한 번 이하) + 다시 알리기. D1 읽기(푸시 몫) = 알람마다 문서 알림 행(가정 30행) + 6
- **`comment` 종류를 알림함에 넣는 비용은 따로다**(푸시를 켜지 않은 사람에게도 생긴다): 새 댓글 중 주인이 아닌 사람이 단 것(가정 40%)마다 행 하나 × 쓰기 5행(p10). 100명 약 180(0.18%), 1,000명 약 1,800(1.8%), **1만 명 약 18,000(18%)**. Q1 에서 이것을 고른다
- **DO 시간**: 알람이 빈 방을 깨우면 방 Doc 을 불러온다(p9). 한 번 0.2초·128MB 로 잡으면 1만 명 2,400번 ≈ 61 GB-s(13,000 의 0.5%). 불러오기 시간은 **재지 않았다**
- **CPU**: 알람 하나 평균 기기 1.4대 → 암호화 약 1 ms + 방 불러오기. DO 는 호출당 30초라 넉넉하다. **Worker 쪽(공유·저장 공간 경고) 10 ms 가 빡빡한 자리다** — 기기 5대 3.4 ms + 요청 자체. 3.5
- **결론**: 푸시 몫은 1만 명에서도 각 한도의 10% 안쪽이다. 다만 1만 명이면 **기존 기능(편집 소켓 메시지·스냅숏)이 먼저 무료 한도를 넘을 가능성이 크다** — 그 기준선은 재지 않았다(`scripts/admin-usage.mjs` 로 원격 사용량을 보면 알 수 있다). `product.md` Q42 "무료 플랜으로 시작, 넘치면 그때 유료" 그대로다

**한도를 넘으면**

| 무엇이 막힘 | 푸시는 | 알림함은 |
| --- | --- | --- |
| D1 하루 쓰기·읽기 초과(질의가 오류) | 알람의 질의가 실패 → **10분 뒤 한 번만 다시**, 그래도 실패면 포기(행은 `push_due_at` 이 남는다 → 매일 Cron 이 1일 넘은 것을 NULL 로, 3.7) | 스냅숏 batch 자체가 실패 — 지금 동작 그대로(F-502) |
| DO 하루 요청 초과 | 알람이 돌지 못한다 → 그 묶음은 사라진다(`PUSH_STALE_MS` 로 늦게 가지도 않는다) | 방 연결부터 안 된다 — 지금 동작 |
| 알람 한 번의 하위 요청 50 | 40개만 보내고 1초 뒤 알람을 다시 걸어 나머지 | 영향 없음 |
| Worker CPU 10 ms 초과(공유·저장 공간 경고) | 응답은 이미 나갔다(푸시는 `waitUntil`). 그 푸시만 잃는다 | 영향 없음 |
| 푸시 서비스 429·5xx | 그 기기는 이번 묶음을 건너뛴다. **다시 보내지 않는다** | 영향 없음 |

- **알림함이 원본, 푸시는 최선을 다하는 사본이다.** 푸시를 잃어도 앱을 열면 알림함에 있다. 그래서 재시도를 한 번(10분)으로 묶는다

| --- | --- | --- | --- |
| **A. 문서 방(`DocRoom`) 알람** | 댓글 알림 행을 넣은 스냅숏이 "가장 이른 `push_due_at`" 을 받아 그 시각에 방 알람을 건다. 알람이 그 문서의 대기 행을 모아 보낸다 | 묶음 하나 = DO 요청 1. "지금 열어 둠" 을 **그 방의 연결로 바로** 안다(p8). 댓글이 생기는 곳이 바로 이 방이다. 빈 방을 깨우면 방 Doc 을 불러온다(p9) | **채택 — 댓글 계열** |
| B. 받는 사람별 새 DO(가칭 받은편지 DO) | 모든 알림을 받는 사람의 DO 로 RPC → 그 DO 가 알람으로 모아 보낸다 | 새 DO 클래스(마이그레이션 태그 v2). 알림 하나 = RPC 1 + 알람 1, "열어 둠" 은 다시 `DocRoom` 에 RPC → 묶음 하나에 DO 요청 약 3. 1만 명이면 약 7,200/일(A 의 3배) | 안 씀 |
| C. Cron Trigger(매분) | D1 대기 표를 매분 훑어 보낸다 | Cron CPU **10 ms/호출**(p5) — 암호화만으로 기기 15대 남짓(0.68 ms × 15 ≈ 10 ms)에 닿는다. 하루 1,440번 깨어난다. Cron 계정당 5개 중 하나 더 | 안 씀 |
| D. Queues | 대기열 소비자가 보낸다 | 무료 10,000 연산/일 = 메시지 약 3,300개(p5) — 1만 명 추정의 푸시 대상 행 4,320 이면 넘는다. 새 바인딩도 는다 | 안 씀 |

- **결론**: 댓글 계열(멘션·답글·`comment`)은 **A**. **공유·초대와 저장 공간 경고는 묶지 않는다** — 그 일이 생긴 요청(초대 `PUT`, 첨부 올리기, 문서 만들기) 또는 스냅숏 안에서 곧바로 `waitUntil` 로 보낸다(3.5·3.6). 둘 다 드물고(공유는 초대 한 번에 한 번, 경고는 7일에 한 번) 문서 방이 없는 것(폴더 초대, 계정 사용량)도 있다
- **3분인 이유**: 댓글이 D1 에 닿기까지 이미 5~30초(스냅숏, F-502), 앱 안 알림함은 60초마다 가져온다(F-507) — 앱을 쓰는 사람은 푸시보다 먼저 앱에서 본다. 3분이면 대화처럼 오가는 답글이 한 알림으로 묶이고, 그 사이 문서를 열면(F-510 읽음) 푸시가 빠진다. 1분이면 묶임이 적고, 5분이면 "왜 늦게 오지" 가 된다(10장 Q3)
- **알람 하나를 나눠 쓴다**: `DocRoomCore` 의 알람은 F-2027 느린 저장이 이미 쓴다(p9). 규칙 — 알람을 걸 때는 **지금 걸린 알람과 새 시각 중 이른 쪽**으로 건다(지금 `scheduleAlarm` 은 이미 미래 알람이 있으면 무시한다 → 바꾼다). 알람이 울리면 ① 미룬 스냅숏이 있으면 지금처럼 쓰고 ② 푸시가 켜져 있으면 3.4 의 보내기를 돈 뒤 ③ 남은 일(다음 느린 저장·다음 푸시 묶음)의 가장 이른 시각으로 다시 건다
- **VAPID 비밀 값이 없으면 푸시 경로 전체가 꺼진다** — 스냅숏의 추가 문장·알람의 D1 질의가 0이다. 그래서 기존 `docRoomCore.test.ts` 의 F-2027 알람 테스트가 그대로 통과한다(7장)

### 3.4 댓글 계열 푸시 흐름

1. **종류 정하기**(F-3005, `notificationTargets` 확장): 새 항목마다 받는 사람을 지금 규칙(멘션 > 답글, 작성자 자신 제외)으로 정한 뒤, **문서 주인**이 작성자가 아니고 아직 그 항목의 행이 없으면 `comment` 행을 하나 더한다. 한 항목에서 한 사람은 행 하나다(멘션 > 답글 > `comment`). 주인 이메일은 이미 읽는 접근 집합(`docPeople`)에 있다. 첫 댓글·답글 모두 `comment` 대상이다(사용자 결정 1 "내 문서의 새 댓글")
2. **넣을 때**: 알림 행 `INSERT` 가 받는 사람마다 "구독이 하나라도 있나"(`users.email` → `push_subscriptions.user_id`)를 `EXISTS` 로 보고, 있으면 `push_due_at = 지금 + PUSH_BATCH_MS`, 없으면 NULL. 같은 batch 끝에 `SELECT MIN(push_due_at) FROM notifications WHERE doc_id = ?`(알림 행을 넣은 batch 에만, 푸시가 켜졌을 때만). 결과가 있으면 그 시각으로 알람(3.3 규칙)
3. **알람 — 보내기**(F-3006): ① 그 문서의 `push_due_at IS NOT NULL` 행을 전부 읽는다(**아직 창이 안 끝난 뒤쪽 행까지** — 창 안에 생긴 것은 한 묶음이다. 한 번에 최대 200행) ② 받는 사람별로 묶는다 ③ 빼기: `read_at` 이 있는 행(이미 읽음 — 사용자 결정 3), **받는 사람이 지금 이 방에 있으면 그 사람 전부**(아래 "열어 둠"), 가장 오래된 행이 `PUSH_STALE_MS` 보다 오래된 묶음, 문서가 금고가 됐거나 없어진 경우(`DOC_WRITABLE` 과 같은 조건) ④ 남은 받는 사람의 살아 있는 구독(세션이 살아 있는 것, 2.1)을 읽고 사람마다 **푸시 하나**(5.1 문구)를 기기마다 보낸다 ⑤ 한 batch 로: 읽은 행 **모두** `push_due_at = NULL`(보냈든 뺐든 — 한 행은 한 번만 다룬다), 404·410 구독 지우기, 4xx 실패 수 올리기(3이면 지우기), 2xx 구독은 `last_ok_at` 이 하루보다 오래됐을 때만 고쳐 쓰기
4. **"지금 열어 둠" 판정**(사용자 결정 3): 그 방의 연결 중 연결 상태 `email`(소문자)이 받는 사람이고, **마지막 ping 자동 응답 시각**(`getWebSocketAutoResponseTimestamp`) 또는 연결 시각이 `PUSH_PRESENCE_FRESH_MS`(90초) 안인 것이 하나라도 있으면 "열어 둠". 연결 시각은 연결 상태에 새 필드로 적는다(hibernation 을 넘긴다). **숨은 탭도 열어 둠이다**(사용자 문장 "열어 두고 있으면". 10장 Q4). 휴대폰이 잠겨 페이지가 얼면 ping 이 멈춰 90초 뒤부터 "안 열어 둠" 이 된다
5. **읽음이 푸시를 끈다**: `POST /api/notifications/read`(F-503·F-510)가 `read_at` 을 채울 때 같은 문장에서 `push_due_at = NULL` 도 한다 — 더 쓰는 행이 없다(같은 행)
6. 댓글을 지우면 그 알림 행이 지워지므로(F-502) 푸시도 사라진다. 문서를 금고로 옮기거나 지우면 알림 행이 지워진다(F-502 3.7) — 푸시도 없다

### 3.5 공유·초대 받음

- **언제**: `PUT /api/{docs|folders}/:id/grants/:email`(`handlePutGrant`)이 **새 초대 행을 만들었을 때만**(역할만 바꾼 경우는 아님). 판정은 `INSERT … ON CONFLICT … RETURNING created_at` 이 이번 요청의 `now` 와 같은지로 한다 — 충돌이면 옛 `created_at` 이 돌아온다. 한 문장 더 들지 않는다
- **누구에게**: 초대받은 이메일의 계정(있으면)의 살아 있는 구독. 아직 가입 안 한 사람은 계정이 없어 보낼 곳이 없다
- **겹침 막기**: 같은 주인이 같은 사람에게 **10분 안에** 만든 초대가 이번 것 말고 또 있으면 보내지 않는다(`grants` 에서 `owner_id`·`grantee_email`·`created_at` 로 센다 — 행 쓰기 없음). 여러 문서를 한꺼번에 초대할 때 푸시가 쏟아지지 않게, 초대를 넣었다 뺐다 하며 남의 휴대폰을 울리지 못하게
- **어디서 보내나**: 그 요청의 `ctx.waitUntil`. Worker CPU 10 ms 안에 기기 5대(약 3.4 ms, p2)를 넣어야 한다 — **요청 자체의 CPU 는 재지 않았다**. 배포 뒤 대시보드에서 초대 요청 CPU 를 보는 것을 사람 확인에 넣는다. 넘치면 그 푸시만 잃는다(3.1)
- 알림함 행은 같은 판정으로 같은 batch 에서(F-3012). 10분 겹침 막기는 푸시에만
- 금고 문서·폴더는 초대가 409 라(`checkOwnedTarget`) 푸시도 없다

### 3.6 저장 공간 경고

- **기준**(F-221 2.5·F-2030 7장과 같다): 이미지 `used / ATTACHMENT_QUOTA_BYTES ≥ 0.9`, 문서 바이트 `content_bytes / DOC_BYTES_QUOTA ≥ 0.9`, 문서 수 `doc_count / DOC_COUNT_QUOTA ≥ 0.9` 중 하나. 판정은 순수 함수(`src/lib/pushText.ts` 옆 또는 `worker/usage.ts`)
- **어디서 알아채나** — 값이 이미 손에 있는 곳만(질의를 더 하지 않으려고):
  - 첨부 올리기: 한도 검사가 이미 `SUM(size)` 를 읽는다(`worker/attachments.ts`). 올린 뒤 값 = 읽은 합 + 새 크기
  - 문서 만들기(`/api`·`/v1`): `checkDocCreate` 가 쓰는 사용량 + 늘어난 값
  - DO 스냅숏: 사용량 줄이 `RETURNING` 으로 돌려주는 행(`judgeUsage` 가 이미 읽는다)
- **되풀이 막기**: 기준을 넘었으면 `UPDATE users SET push_quota_at = ?now WHERE id = ? AND (push_quota_at IS NULL OR push_quota_at < ?now − 7일)` 을 한 번. **바뀐 행이 1일 때만** 보낸다 — 여러 요청이 동시에 넘어도 한 번. 7일마다 한 번까지(80% 로 내려갔다 올라오는 되돌림 판정은 두지 않는다 — 지우는 경로마다 판정을 넣어야 해서)
- **본인이 올리는 중이어도 보낸다**(10장 Q7). 받는 사람은 **소유자**다 — 공유 문서에 남이 쓴 본문도 소유자 누계라(F-2024), 남이 내 공간을 채울 때 알게 된다
- 보내는 곳: Worker 는 `waitUntil`, DO 는 스냅숏 뒤 곧바로

### 3.8 보내기와 실패 처리

- **허용 목록**(SSRF 막기 — `endpoint` 는 클라이언트가 준 주소다): `https:` 이고 호스트가 `fcm.googleapis.com`(Chrome·안드로이드·삼성 인터넷 등), `updates.push.services.mozilla.com`(Firefox), `web.push.apple.com`(Safari·iOS), `*.notify.windows.com`(Edge) 중 하나. **이 목록은 일반 지식에서 왔고 이번에 브라우저마다 확인하지 않았다** — F-3003 이 착수 때 각 브라우저 문서로 다시 확인한다. 목록 밖은 등록 때 400 `unsupported_push_service`, 보낼 때도 다시 걸러낸다
- 요청 머리: `TTL: 86400`, `Content-Encoding: aes128gcm`, `Urgency: normal`, `Authorization: vapid t={JWT}, k={공개 키}`, 문서 묶음은 `Topic: {문서 id 에서 - 를 뺀 32자}`(RFC 8030 — 기기가 꺼져 있는 동안 같은 문서의 옛 푸시를 푸시 서비스가 새것으로 바꾼다. 32자·base64url 문자 조건을 UUID 16진수가 만족한다)
- VAPID `sub` 는 **`BETTER_AUTH_URL` 값(`https://…`)** 을 쓴다 — RFC 8292 는 `mailto:` 또는 `https:` 를 받는다. 제품명·주소 문자열을 코드에 새로 쓰지 않는다(불변조건)
- **응답 분류**: 2xx 성공 / 404·410 구독 없음 → 지움 / 429·5xx 일시 실패 → 이번만 건너뜀 / 그 밖 4xx → 실패 수 +1 / 네트워크 오류 → 일시 실패
- VAPID 키는 **비밀 값 하나** `VAPID_PRIVATE_JWK`(P-256 JWK. `d`·`x`·`y` 를 모두 담아 공개 키를 따로 두지 않는다). **`secrets.required` 에 넣지 않는다** — 없으면 푸시만 꺼지고(503·경로 전체 0) 배포는 막히지 않는다. 그래서 `wrangler.jsonc` 계약 테스트(F-2033 U12)가 그대로다(7장). 읽기는 `readVar`(이름 목록에 더한다)
- 키를 바꾸면 모든 구독이 VAPID 불일치(401·403)로 3번 뒤 지워지고, 기기는 다음 다시 알리기(4.3, 최대 7일)에 새 키로 다시 구독한다

### 3.9 금고(E2EE)와 알림 본문

- **금고 문서에서는 푸시가 생길 길이 없다**: 댓글이 없다(F-500 사용자 결정 8), 알림 행 `INSERT` 가 금고면 0행(`DOC_WRITABLE`, p10), 초대가 409(`checkOwnedTarget`), 금고로 옮기면 그 문서 알림 행을 지운다(F-502). 알람이 보내기 직전에도 `e2ee_key IS NULL` 을 다시 본다(3.4 ③). 저장 공간 경고는 계정 숫자만 담는다
- 그래서 "서버가 금고 제목을 모른다" 는 문제는 생기지 않는다. **앞으로 금고 문서에서 알림이 생기게 바꾸는 명세는 제목·발췌 대신 `금고 문서` 같은 고정 문구를 써야 한다** — 서버가 가진 금고 제목은 암호문이다(F-400)
- 일반 문서: 본문은 RFC 8291 로 **기기 키에 맞춰 암호화**되어 푸시 서비스(Google·Apple·Mozilla·Microsoft)는 내용을 못 본다 — 보는 것은 주소·크기·시각이다. 대신 **잠금 화면에 제목·발췌가 보인다**(10장 Q5). 개인정보 처리방침에 적는다(9장)

## 4. 클라이언트

### 4.1 서비스 워커 — `generateSW` 유지 + `importScripts`

| 안 | 하는 것 | 판정 |
| --- | --- | --- |
| **A. `workbox.importScripts: ['/push-sw.js']`** | 지금 만든 서비스 워커가 첫 줄에서 우리 스크립트 하나를 불러온다. 그 스크립트는 `push`·`notificationclick` 처리기만 둔다 | **채택** — 오프라인·갱신(F-116·F-117) 설정을 한 줄도 안 바꾼다 |
| B. `injectManifest` 로 바꾸기 | 서비스 워커를 직접 짠다 | 안 씀 — precache·`navigateFallbackDenylist`(15개)·fonts 런타임 캐시·`cleanupOutdatedCaches`·`prompt` 갱신 메시지를 다시 짜야 한다. 오프라인 앱 전체가 흔들린다 |

- `push-sw.js` 는 **고전 스크립트**여야 한다(`importScripts` 는 ES 모듈을 못 부른다). 원본 `src/pwa/pushSw.ts`(처리기만, 짧게)를 앱 빌드 뒤 **한 파일 IIFE** 로 따로 묶어 `dist/push-sw.js` 에 둔다 — 방법은 `vite.config.ts` 의 작은 플러그인(`sitePlugin` 처럼 `closeBundle` 에서 Vite `build` API, 새 의존성 없음). 앱 번들의 `rollupOptions.input` 에 넣지 않는다(공유 청크가 생기면 `import` 문이 끼어 고전 스크립트가 깨진다)
- 순수 규칙은 `src/lib/pushPayload.ts`(본문 모양 검사, 누를 때 열 주소 정하기)에 두고 node 단위 테스트로 판정한다. 서비스 워커 글루는 e2e 로도 못 본다(p14) → 사람 확인
- **`push` 처리기 규칙**: 본문을 풀어 모양이 맞으면 그 `title`·`body`·`tag`·`data.url` 로, 틀리면 `새 알림`(본문 없음, 주소 `/`)으로 **반드시 하나를 띄운다** — Chrome 은 푸시를 받고 알림을 안 띄우면 "백그라운드에서 업데이트됨" 류 기본 알림을 대신 띄울 수 있다고 알려져 있다(확인 안 함). 그래서 "앱이 보이면 OS 알림을 건너뛴다" 는 두지 않는다(10장 Q6)
- `/push-sw.js` 는 `/assets/` 밖이라 1년 immutable 머리가 붙지 않는다. `importScripts` 로 부른 스크립트는 브라우저가 서비스 워커 갱신 확인 때 바이트를 비교한다 — 바뀌면 새 서비스 워커가 대기하고 F-117 `새 버전` 알림이 뜬다(지금과 같다)
- 서비스 워커는 `devOptions.enabled: false` 라 `npm run dev` 에서 돌지 않는다. 사람 확인은 `npm run build` + `vite preview` 또는 배포 주소에서

### 4.2 설정 화면과 환경 차이 (반드시 결론 5, 사용자 결정 4)

- **자리**: 설정 `계정` 탭(p13), `계정 삭제…` 위에 묶음 `알림`. 로그인이 있어야 하는 기능이라 로그인일 때만 보이는 탭에 둔다(10장 Q9)
- 스위치 `이 기기에서 푸시 받기`(`role="switch"`), 기본 꺼짐. 켜져 있으면 아래에 `테스트 알림 보내기` 버튼
- **환경 판정 — 순수 함수 하나**(`src/app/pushClient.ts`, 입력: 서비스 워커·`PushManager`·`Notification` 유무, iOS 여부, 설치 앱으로 실행 중인지, 알림 권한, 온라인, 서버 키 상태)가 아래 상태 중 하나를 돌려준다. 위에서부터 먼저 맞는 것:

| 상태 | 조건 | 스위치 | 아래 줄 문구 |
| --- | --- | --- | --- |
| `ios-browser` | iOS·iPadOS 이고 설치 앱으로 실행 중이 아님 | 비활성 | `iPhone·iPad에서는 홈 화면에 추가한 앱에서만 푸시를 받을 수 있습니다.` |
| `unsupported` | 서비스 워커·`PushManager`·`Notification` 중 하나라도 없음 | 비활성 | `이 브라우저는 푸시 알림을 지원하지 않습니다.` |
| `denied` | `Notification.permission === 'denied'` | 비활성 | `이 사이트의 알림이 브라우저에서 차단되어 있습니다. 브라우저 설정에서 허용한 뒤 다시 켜 주세요.` |
| `offline` | 오프라인 | 비활성(지금 값 유지) | `온라인일 때 바꿀 수 있습니다.` |
| `unavailable` | `GET /api/push/key` 가 503 | 비활성 | `지금은 푸시 알림을 켤 수 없습니다.` |
| `ready` | 그 밖 | 활성 | 설명(5.2) |

- iOS 판정: UA 에 `iPhone`·`iPad`·`iPod`, 또는 `Macintosh` 이면서 `maxTouchPoints > 1`(iPadOS 데스크톱 UA). 설치 앱 판정: `navigator.standalone === true` 또는 `display-mode: standalone` 미디어 쿼리. iOS 는 16.4 이상, **홈 화면에 추가한 앱에서만** 웹 푸시가 되고(일반 지식, 확인 안 함) 그 밖의 iOS 탭에는 `PushManager` 가 없다 — 그래서 `ios-browser` 가 `unsupported` 보다 앞이다
- **데스크톱**: Chrome·Edge·Firefox·Safari(macOS) 탭에서 된다. 브라우저가 꺼져 있으면 받지 못한다 — 도움말에 한 줄(5.2)
- **안드로이드**: 설치 앱이든 Chrome 탭이든 같다. 휴대폰 설정에서 Chrome(또는 설치 앱)의 알림이 꺼져 있으면 권한이 `granted` 여도 안 보인다 — 도움말에 한 줄
- **켜기 흐름**(스위치 누름 = 사용자 동작 안에서): 권한이 `default` 면 `Notification.requestPermission()` → `granted` 가 아니면 꺼진 채로 `알림 권한을 받지 못해 켜지 않았습니다.`(info) → `GET /api/push/key` → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` → `PUT /api/push/subscription` → 성공이면 켜짐. 중간 실패면 꺼진 채로 `푸시를 켜지 못했습니다. 잠시 뒤 다시 시도하세요.`(error). **권한은 켤 때만 묻는다**(사용자 결정 4) — 부팅·로그인 때 묻지 않는다
- **끄기 흐름**: `DELETE /api/push/subscription` → `subscription.unsubscribe()` → 꺼짐. `DELETE` 가 실패하면 꺼지지 않고 error(서버가 계속 보내기 때문)
- **이 기기 설정 키**(architecture.md 4장에 더함): `md.push` = 켠 계정의 사용자 id(없으면 꺼짐), `md.pushSyncedAt` = 마지막으로 서버에 알린 때(ms). 사용자 id 를 적는 이유: 같은 기기에서 다른 계정으로 로그인하면 **저절로 켜지지 않게**(그 계정에는 꺼짐으로 보인다. `md.localMigrated` 와 같은 방식)

### 4.3 구독 다시 알리기

- 부팅 뒤(로그인, `md.push` 가 지금 사용자, 권한 `granted`, 온라인) 한 번, 브라우저 구독을 읽어:
  1. 없으면 `GET /api/push/key` → 새로 구독 → `PUT`
  2. 있고 `md.pushSyncedAt` 이 7일 안이면 아무것도 하지 않는다(Worker 요청 0)
  3. 있고 7일이 지났으면 `GET /api/push/key` → 구독의 `options.applicationServerKey` 와 다르면 해지 → 새로 구독 → `PUT`, 같으면 같은 구독을 `PUT`(서버가 치운 행을 되살린다 — 세션이 바뀐 경우 포함)
- 권한이 `denied` 로 바뀌어 있으면 `md.push` 를 지우고 서버에 `DELETE` 한 번
- 그래서 기기 하나가 평소 쓰는 요청은 7일에 둘이다(3.1)

### 4.4 알림을 눌렀을 때

- `notificationclick`: 알림을 닫고, 이 출처의 창이 있으면 **가장 최근에 포커스된 창**에 포커스 → 그 창에 `{ type: 'push-open', url }` 메시지. 앱은 받으면 `url` 의 해시로 옮긴다(`#/d/{docId}/c/{threadId}` 는 F-505 가 이미 푼다). 창이 없으면 `clients.openWindow(url)` — 설치 앱은 범위(`scope: '/'`) 안이라 앱 창으로 열린다
- `url` 은 `/` 로 시작하는 같은 출처 경로만 따른다. 아니면 `/` 로(서비스 워커도 다시 검사 — `src/lib/pushPayload.ts`)
- 열린 문서가 되면 F-510 규칙대로 그 문서의 알림이 읽음이 된다 — 서비스 워커가 따로 읽음 요청을 보내지 않는다

### 4.5 알림함에 `comment` 종류 (Q1 기본값)

- 새 클라이언트는 `GET /api/notifications?kinds=mention,reply,comment` 로 부른다. **`kinds` 가 없으면 서버는 지금처럼 `mention`·`reply` 만** 목록·안 읽은 수에 넣는다 — 옛 클라이언트(설치된 PWA 가 새로고침 전)가 p11 로 알림함 전체를 잃지 않게. `kinds` 는 알려진 종류의 부분 집합만, 그 밖은 400 `{ error: 'invalid', field: 'kinds' }`
- ETag(F-2057): `kinds` 가 없으면 지금 모양 그대로(`n1-…`), 있으면 끝에 종류를 붙인다 — 같은 리비전이라도 응답 모양이 다르므로
- 알림함 문구(5.1) 한 줄, 사이드바 점(F-510)은 `docId` 로 묶으므로 저절로 따라온다

### 5.1 푸시 알림 (ia.md 6장 형식. 하위 명세가 이 값을 기본으로 쓴다)

`{보낸 사람}` = 이메일(알림함과 같다, F-500 5.1). `{문서 제목}` = 알림 행의 `doc_title` 을 40자(코드 포인트)로 자르고 넘으면 `…`, 비었으면 `제목 없는 문서`(지금 `formatNotificationTitle` — `src/lib` 로 옮겨 서버·클라이언트가 같이 쓴다, p16). `{발췌}` = 줄바꿈을 공백으로, 80자에서 자르고 `…`

### Q1. 새 종류를 알림함에도 넣나 — **사람 결정 필요. 기본값: `comment`(내 문서의 새 댓글)만 알림함에도, 공유·저장 공간 경고는 푸시만 (공유는 2026-10-01 F-3012 로 알림함에도 넣음)**

- 기본값의 이유: `comment` 는 멘션·답글과 모양이 같아(문서·댓글·보낸 사람·발췌) 알림함·사이드바 점(F-510)·"이미 읽음" 판정(`read_at`)을 그대로 쓴다. F-510 을 요청할 때의 사용자 문장("남이 댓글 달면 사이드바 문서 리스트에 알림 있어야") 과도 맞는다. 공유는 사이드바 `공유받음` 이, 저장 공간은 계정 메뉴 빨간 줄이 이미 앱 안 자리다. 두 종류는 댓글 id·스레드 id 가 없어 표 모양을 더 바꿔야 한다
- 비용: `comment` 행은 **푸시를 안 켠 사람에게도** 생긴다 — 1만 명 가정에서 D1 쓰기 약 18%(3.1). 알림함이 시끄러워질 수 있다
- **`comment` 도 넣지 않으면**: 2.2 의 `kind` 변경이 없어 표 다시 만들기가 `ALTER TABLE … ADD COLUMN push_due_at` 한 줄로 준다. 대신 `comment` 푸시의 대기·"이미 읽음" 을 둘 곳이 따로 필요하다(새 표 하나, 읽음은 "그 문서를 연 적 있나" 를 알 길이 없어 "열어 둠" 판정만 남는다). F-3005 가 새 표 명세로, F-2111 은 없어진다
- **공유도 넣으면(F-3012 로 넣음, 이 줄이 예고한 열·NULL 허용이 0021)**: `notifications` 에 대상 종류(문서·폴더)를 담을 열과 `comment_id`·`thread_id` NULL 허용이 필요하다 — `0018` 이 더 커지고, 알림함 항목 모양(`NotificationItem`)·이동 규칙(폴더는 이동할 곳이 없다)을 새로 정해야 한다

### Q2. iOS — **사람 결정 필요. 기본값: iOS 전용 작업 없이 표준 경로만, 안내 문구 하나**

- `product.md` 8장이 "iOS, Safari 대응" 을 범위 밖에 둔다. 한편 사용자는 iOS 차이를 물었다
- 기본값: 웹 푸시는 표준이라 iOS 16.4+ 홈 화면 앱에서는 **같은 코드로** 된다(가정 — 실제 기기로 확인하지 않았다). 이 개요가 iOS 를 위해 더하는 것은 4.2 의 `ios-browser` 판정과 문구 하나뿐이다. iOS 에서 안 되는 것이 나와도 고치지 않는다(8장 그대로)
- 다른 안: iOS 를 이 개요의 지원 대상으로 올린다 → 8장 문장을 고치고, 사람 확인 ⑤ 를 통과 기준으로 삼고, Safari 의 알림 조건(푸시마다 알림을 반드시 띄우기, 권한은 사용자 동작 안에서만)을 수용 기준에 넣는다. 작업량은 크게 늘지 않지만 "범위 밖" 원칙의 예외가 된다

### Q3. 묶음 창 3분 — **기본값: 3분**

- 이유는 3.3. **1분이면**: 대화가 이어질 때 알림이 더 잦다(같은 `tag` 라 쌓이지는 않는다). 문서 알람이 늘어 1만 명 DO 요청이 약 2배. **5분이면**: 알림함(최대 약 2분, ia.md 3.34)보다 한참 늦어 "푸시가 늦다" 로 보인다

### Q4. 숨은 탭도 "열어 둠" 인가 — **기본값: 그렇다(소켓이 살아 있으면)**

- 사용자 문장 "지금 열어 두고 있으면" 을 그대로 읽었다. 데스크톱에서 문서를 뒤 탭에 열어 둔 채 다른 일을 하면 그 문서의 푸시는 오지 않는다(앱 안 알림함·점은 생긴다)
- 다른 안: "보이는 탭만 열어 둠" — 클라이언트가 보임 상태를 방에 알려야 한다(awareness 나 명령 메시지에 필드 하나, F-307·F-503 계약 변경). 연결 상태에 적고 3.4 4번 판정이 그것을 본다

### Q5. 잠금 화면의 발췌 — **기본값: 넣는다(80자)**

- 멘션을 받았을 때 무슨 말인지 보여야 한다는 사용자 불만("무슨내용인지 안나옴")이 이 개요의 출발점이다
- 다른 안: 발췌 없이 `"{문서 제목}"` 만. 5.1 본문 칸이 바뀌고 개인정보 처리방침 문장이 줄어든다. 기기 쪽에서 "잠금 화면에 내용 숨기기" 를 켜는 것으로도 가릴 수 있다

### Q6. 앱이 보일 때 OS 알림을 건너뛰나 — **기본값: 건너뛰지 않는다(늘 띄운다)**

- 이유: 푸시를 받고 알림을 안 띄우면 Chrome 이 기본 알림을 대신 띄우거나, Safari 가 구독을 거둘 수 있다고 알려져 있다(둘 다 확인 안 함). 서버가 이미 "그 문서를 열어 둠" 을 뺀다(3.4) — 다른 문서를 보는 중에 오는 알림은 받는 편이 맞다
- 다른 안: 서비스 워커가 보이는 창이 있으면 알림 대신 창에 메시지 → 앱이 알림함을 새로 고침. 브라우저마다 동작을 확인해야 하고(F-3004 가 complex 로 커진다) iOS 는 제외해야 한다

### Q7. 올리는 본인에게도 저장 공간 경고 푸시 — **기본값: 보낸다(7일에 한 번)**

- 서버는 그 사람이 지금 앱을 보고 있는지 모른다(문서 방 밖의 일이다). 한 번 울리고 7일 조용하다
- 다른 안: 이미지 올리기·문서 만들기처럼 **본인이 한 요청**에서 넘었으면 푸시 대신 그 응답에 표시를 실어 앱이 알림 띠로 알린다 — 새 응답 필드와 띠 문구가 는다(화면 명세 하나 더). 남이 공유 문서에 써서 넘긴 경우(스냅숏)만 푸시

### Q8. 사용자가 물은 "생각 못 한 알림" — **기본값: 이번에는 더하지 않는다**

### Q10. `테스트 알림 보내기` — **기본값: 둔다**
