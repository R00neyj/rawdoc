### 4.5 3.5 공개 보기 조기 반환 · 3.8 훅 호출 자리

- **호출 자리 = Ⓒ(최신값 effect ④)가 있던 자리다.** effect ③ 닫는 줄 다음 빈 줄 뒤, `// ----- 탭이 숨겨지거나 닫힐 때 최선 시도로 저장 …` 절 앞이다. 탐침 App 기준 ≈2452 이다

- 훅 안 순서: 구조 분해 → Ⓐ(상태·ref, 원래 상대 순서) → Ⓑ effect → ④ → 끌어놓기 effect → Ⓓ 함수들 → Ⓔ `handleImageFiles` → `return`. 훅 안 effect 순서 "OS 열기 → ④ → 끌어놓기" 는 지금 App 안 순서와 같다

- 조기 반환 `if (publicRoute) {`(탐침 App ≈3668)보다 위다. 공개 보기 렌더에서도 훅이 불리고 effect 세 개가 지금처럼 돈다. 훅은 조기 반환 아래 값을 받지 않는다. 판정은 `publicView.spec.js` 다

### 5.2 `src/app/importResult.ts` — 다시 마운트 판정

```ts
import type { DocPathKind } from './docPath'

export type RemountGateInput = {
  openBeforeId: string
  updatedIds: ReadonlySet<string>
  currentDocId: string | null
  docPath: { docId: string | null; path: DocPathKind | null }
}

export function shouldRemountAfterImport(input: RemountGateInput): boolean
export function canRemountWithFresh<T extends { id: string; e2ee?: 'locked' | 'open' }>(fresh: T | null, currentDocId: string | null): fresh is T
```

- **두 함수로 가르는 이유:** 지금 조건은 두 단계다. 첫 단계는 `store.get` **앞**에서 `currentDocIdRef.current`·`docPathRef.current` 를 읽고, 둘째 단계는 `await store.get` **뒤**에 `currentDocIdRef.current` 를 다시 읽는다. 한 함수로 합치면 `store.get` 을 늘 부르게 되거나 둘째 읽기 시점이 바뀐다. 개요 4장의 네 갈래 중 실시간·폴백·다른 문서는 `shouldRemountAfterImport` 에, 잠긴 금고는 `canRemountWithFresh` 에 든다
- `shouldRemountAfterImport` 규칙: `updatedIds` 에 `openBeforeId` 가 있고, `openBeforeId === currentDocId` 이고, `docPath` 가 `{ docId: openBeforeId, path: 'realtime' }` 이 **아닐** 때만 참이다. 실시간이어도 `docPath.docId` 가 다른 문서면 참이다(지금 식 그대로)
- `canRemountWithFresh` 규칙: `fresh` 가 있고, `fresh.id === currentDocId` 이고, `fresh.e2ee !== 'locked'` 일 때만 참이다. 타입 술어라 호출 자리에서 `fresh` 가 좁혀진다
- **호출 자리 모양(두 곳 똑같이):** 지금의 5줄 `if (` 조건이 한 줄이 된다: `if (openBeforeId && shouldRemountAfterImport({ openBeforeId, updatedIds, currentDocId: currentDocIdRef.current, docPath: docPathRef.current })) {`. 안쪽 `if (fresh && fresh.id === currentDocIdRef.current && fresh.e2ee !== 'locked') {` 는 `if (canRemountWithFresh(fresh, currentDocIdRef.current)) {` 가 된다. `openBeforeId &&` 를 호출 자리에 남기는 이유는 두 가지다. `store.get(openBeforeId)` 앞에서 `string` 으로 좁혀야 한다(탐침 `TS2345`). 그리고 첫 판정이 거짓이면 ref 를 읽지 않는 순서가 그대로 유지된다
- 두 조건식이 글자 그대로 같은지 확인했다. `confirmVaultImport`(≈3425~3437)와 `confirmImport`(≈3515~3527)의 `if (` 5줄과 안쪽 `if` 1줄이 바이트 단위로 같다(탐침 스크립트가 두 곳 모두 정확히 일치하는 것을 셌다). 다른 것은 `confirmImport` 위의 이유 주석 두 줄뿐이다. 이 주석은 그대로 둔다
- 머리 한 줄 주석: `// 가져오기 뒤 열린 편집기를 다시 마운트할지 — confirmImport·confirmVaultImport 가 함께 쓴다 (F-2068, F-282 3.9, F-305 10.1)`
- React·DOM·저장소를 import 하지 않는다(테스트 환경 `node`)

### 7.2 특성 e2e — `e2e/appSplit.spec.js` (F-2059 5.2)

**옮기기 전 코드에서 먼저 통과**해야 한다(빨강 확인 대상이 아니다). 구현자는 옮기기 전에 한 번, 옮긴 뒤에 한 번 돌려 둘 다 초록인지 보고한다. **옮기기 전에 실패하면 멈추고 보고한다.** 테스트를 동작에 맞춰 고치지 않는다. 기대값은 코드를 읽어 정했고 명세를 쓸 때 돌려 보지 못했다(근거 "하지 못한 것"). 선택자 수준의 오류(strict mode 위반 등)로 빨가면 선택자만 좁혀도 되지만, 기대 **값**이 다르면 멈춘다.

## 11. 열린 질문 (모두 기본값 — 기본값대로)

### Q1. 한 조각으로 하나, a/b 로 나누나 — **기본값: 한 조각**

- 이유
  - 세 effect 와 함수들이 ref 로 서로 물려 있다. 끌어놓기 effect 는 `runImportFilesRef`·`previewImportFolderRef` 를, OS 열기 effect 는 `openOrImportLaunchedFilesRef` 를 읽는다. 셋 다 ④ 가 대입한다. 끌어놓기만 떼면 이 ref 들의 선언·대입·읽기가 두 훅에 갈라진다(F-2059 3.2 위반). 피하려면 한 훅이 다른 훅의 ref 를 반환해 넘겨야 한다
  - 탐침에서 한 번에 옮긴 결과가 ESLint·`tsc` 0 이었고, 옮기기 아닌 줄은 빨강 19·초록 104 뿐이었다. 옮긴 618줄 중 604줄이 이동색이다
  - `CLAUDE.md` "Never split one F across several commits"
- 다른 쪽(a: 가져오기·OS 열기, b: 끌어놓기·이미지): 커밋마다 diff 가 약 절반이 된다. 대신 a 가 `runImportFilesRef`·`previewImportFolderRef` 를 반환하고 b 가 옵션으로 받는 틀이 새로 생긴다. 번호 하나를 두 커밋으로 나누는 것은 `CLAUDE.md` 규칙의 예외가 되어 사용자 승인이 필요하다

### Q2. 훅 호출 자리 — **기본값: Ⓒ(최신값 effect ④) 자리 (4.5)**

- 이유: 훅 안 effect 셋 중 둘(④·끌어놓기)의 실행 자리가 그대로이고, 움직이는 OS 열기 effect 는 순서에 기대지 않는다(4.5 근거)
- 다른 쪽(Ⓓ, 가져오기 절 자리 ≈3158 — F-2059 3.8 "가장 큰 절 자리"): 함수 본문 위치는 그대로다. 하지만 effect 셋이 모두 ≈2631~3147 의 effect(탭 숨김 flush, 금고 옮기기, `useSharesPage` 등)를 건너 내려간다. 끌어놓기 `keydown` 리스너도 그 사이 리스너보다 늦게 등록된다
- 다른 쪽(Ⓑ, ≈2157): ④·끌어놓기 effect 가 `useGlobalShortcuts` 리스너보다 **먼저** 등록된다. `keydown` 리스너 등록 순서가 바뀐다

### Q3. 끌어놓기 차단 ref(`dropBlockedRef`·`imageDropBlockedRef`)를 훅으로 옮기나 — **기본값: App 에 둔다 (2.2)**

- 이유: 대입 식이 다른 구역 상태 9개와 `store.kind` 를 읽는다. 옮기면 그 9개가 이 훅의 옵션이 되고, 훅 안에 인자 없는 새 effect 가 생기며, effect ③ 에서 7줄이 빠진다. `readOnlyDocRef` 는 팔레트(`runPaletteEditorCommand`)도 읽어 어차피 못 옮긴다
- 다른 쪽(옮긴다): App 줄이 몇 줄 더 준다(선언 4줄 + ③ 안 7줄 − 옵션 줄, 추정). 대신 이 훅이 설정·검색·삭제·이동·팔레트·공유 화면 상태를 알게 되고, 새 effect 가 대입 시점을 ③ 에서 훅 자리로 옮긴다. 같은 커밋에 읽는 effect 가 없어 동작은 같다

### Q4. 다시 마운트 판정 모양 — **기본값: 두 함수 + 호출 자리의 `openBeforeId &&` (5.2)**

- 이유: 지금 조건은 `store.get` 앞과 뒤 두 단계다. 두 함수로 가르면 두 읽기 시점이 그대로다. `openBeforeId &&` 를 호출 자리에 두어 `string` 으로 좁힌다(탐침 `TS2345`)
- 다른 쪽(`shouldRemountAfterImport` 가 id 를 돌려준다, 예: `remountTargetAfterImport(…): string | null`): 좁히기 문제는 없어진다. 대신 개요 4장이 정한 이름·불리언 모양과 어긋나고, 호출 자리에 `const` 한 줄이 더 생긴다
- 다른 쪽(한 함수가 `fresh` 까지 받는다): `store.get` 을 늘 먼저 불러야 한다 — 부르는 횟수가 바뀌므로 "옮기기만" 을 어긴다

### Q5. D1 표의 `runImportFiles`·`openOrImportLaunchedFiles` 를 옮기나 — **기본값: 옮긴다**

- 확인한 충돌: 개요 2.2 는 "문서 이동 함수들(`selectDoc`·…·`copyHelpToDoc` 등) — 7장 D1 판정이 끝나기 전에는 옮기지 않는다" 이고, D1 표에 이 두 함수가 있다. 한편 개요 5.4·6장은 "가져오기(md·zip·볼트·OS 열기)" 를 F-2068 로 정했다. 사용자 프롬프트도 `openOrImportLaunchedFiles` 를 옮길 목록에 넣었다
- 이유: `runImportFiles` 는 input·끌어놓기·OS 열기·`openOrImportLaunchedFiles` 가 모두 부르는 구역의 중심이다. App 에 남기면 훅이 이것을 옵션으로 받아야 하고, OS 열기 effect·④ 도 App 에 남아야 해서(ref 가 갈라진다) 조각이 반쪽이 된다. D1 차이는 줄 그대로 옮겨지므로 `useImportFlow.ts` 에서 똑같이 보인다. 개요 7장 머리의 "고치는 시점은 옮기는 조각 커밋 뒤, 옮긴 자리에서" 와도 맞는다
- 다른 쪽(두 함수를 App 에 둔다): 개요 2.2 를 글자 그대로 지킨다. 대신 옵션에 `runImportFiles` 가 더해지고, ④ 와 OS 열기 effect 가 App 에 남으며, `runImportFilesRef`·`openOrImportLaunchedFilesRef` 가 App·훅에 갈라진다. 줄 감소도 약 130 줄어든다(두 함수 약 100줄 + OS 열기 effect·④ 16줄 + ref 선언 6줄을 더한 추정, 탐침 아님)

### 관찰 (이 조각은 고치지 않는다 — F-2059 7장 성격, 판정은 사용자)

1. **끌어놓기 차단 조건에 가져오기 대화상자가 없다.** `dropBlockedRef`·`imageDropBlockedRef` 식(effect ③)은 설정·검색·삭제·이동·일괄 삭제·공유 보기·공유 관리·지도·팔레트를 보지만 `importState` 는 보지 않는다. 그래서 미리보기·진행 대화상자가 떠 있는 동안 창에 폴더를 놓으면 `previewImportFolder` 가 `importVaultContextRef` 를 새것으로 바꾸고, 떠 있던 미리보기 대신 새 볼트를 가져올 수 있다. 진행 중에 `.md` 를 놓으면 `runImportFiles` 가 함께 돈다. 코드를 읽어 판단한 것이고 실행해 보지는 않았다(모달 `<dialog>` 위 드롭 이벤트가 `window` 까지 오는지 미확인)
