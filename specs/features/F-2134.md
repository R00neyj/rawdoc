## 3. 부팅 순서

### 3.1 앞질러 열 수 있나 — `canStartBeforeAccount` (입출력 없음)

```ts
// src/app/bootList.ts — 계약
export function canStartBeforeAccount(input: {
  storedAccountId: string | null   // storedAccount()?.id ?? null
  localMigratedId: string          // getPref('md.localMigrated', '')
  hash: HashRoute                  // parseHash(location.hash)
}): boolean
```

모두 만족할 때만 `true`: `storedAccountId` 가 있다 / `localMigratedId === storedAccountId`(아니면 로컬 이관이 남았다 — 이관은 확인된 계정에만 한다, R5) / `hash.type` 이 `share` 가 아니다(F-2042 4.1 과 같은 까닭). 공개 보기(`public`·`publicFolder`)는 `runBoot` 이 이보다 먼저 돌려보낸다(지금 그대로)

### 3.2 규칙

1. 공개 보기 판정 뒤 `fetchAccount()` 를 **시작만** 한다. 이 약속 하나를 끝까지 쓴다(`/api/me` 는 부팅에 한 번)
2. `canStartBeforeAccount` 가 거짓이면 그 약속을 기다린 뒤 지금 순서 그대로 간다
3. 참이면 `openStore({ account: { state: 'in', id: 저장 id }, holdUntilConfirmed: true, … })` 로 연다. `openYjsStore`·`withE2ee`·`withTabBroadcast`·`setStore` 는 지금처럼. `migrateLocalIfNeeded` 는 부르지 않는다(3.1 로 할 일이 없다)
4. `listCached()` 후 `canShowCachedShell({ storeKind: 'server', accountState: 'in', … })` (F-2042 4.1, 앞질러 연 저장소는 `in` 으로 본다)
   - **참** → `setAccountPending(true)`, 캐시 폴더·문서로 `finishBootRouting`(ready). `runBoot` 은 여기서 돌아오고 4장 답 처리는 뒤에서 이어진다. 스냅샷 id 집합은 셸을 띄울 때 잡는다(F-2042 4.3)
   - **거짓**(캐시가 비었거나 해시 문서가 캐시에 없음) → 스켈레톤인 채 답을 기다린다. 4.1 이 `confirm` 이면 `confirmAccount()` 뒤 지금의 기다리는 길(F-2133 모양)로, `reload` 면 새로 고친다
5. `ACCOUNT_CONFIRM_WAIT_MS` 타이머는 4번 참일 때만 건다. 기다리는 길에는 지금처럼 시간 제한이 없다

```ts
// src/app/bootList.ts — 계약
export const ACCOUNT_CONFIRM_WAIT_MS = 5_000
```

5,000ms 인 까닭: 측정에서 D1 두 번을 차례로 읽는 `GET /api/docs/{id}` 의 Worker wallTime 이 1~4초였다(F-3019 이전, 미국 colo → HKG D1). `/api/me` 도 세션·사용자 두 행을 읽는다. 그보다 길면 문서가 열리지 않는 시간이 사용자를 막는다. 타이머가 먼저 울려도 잃는 것은 없다 — D5

## 4. `/api/me` 답에 따라

### 4.1 판정 — `judgeEarlyAccount`

```ts
// src/app/bootList.ts — 계약
export type EarlyAccountVerdict = 'confirm' | 'reload' | 'stuck'
export function judgeEarlyAccount(input: {
  earlyId: string                  // 앞질러 연 저장소의 사용자 id
  result: AccountState             // fetchAccount() 결과
  storedIdAfter: string | null     // 답을 받은 뒤 storedAccount()?.id ?? null
}): EarlyAccountVerdict
```

| 답 | 판정 | 화면·저장 |
| --- | --- | --- |
| `in`, `id === earlyId` | `confirm` | `applyAccountFlags(result)` → `blocked` 면 `setAccountBlocked(true)` → `confirmAccount()` → `setAccountPending(false)` → 뒤 맞추기 시작. **이 순서가 계약이다** — 막힌 계정은 멈춤이 풀리는 순간에도 회차를 시작하지 않고(F-2030 4.4 3번), `accountBlocked` 와 `accountPending=false` 가 같은 렌더에 들어가 경로 판정이 처음부터 `view` 로 간다 |
| `offline` | `confirm` | `applyAccountFlags(result)` → `confirmAccount()` → `setAccountPending(false)` → 뒤 맞추기. 지금 오프라인 부팅이 고르는 저장소와 같고(R4) 그 뒤 동작도 같다 |
| `in`, 다른 id, `storedIdAfter === result.id` | `reload` | `await beforeLeaveDoc()` 뒤 `location.reload()`. `fetchAccount` 가 이미 새 id 를 썼으므로 다음 부팅은 새 사용자로 앞질러 열거나(그 캐시가 있으면) 기다린다 |
| `out`, `storedIdAfter === null` | `reload` | 같음. `md.account` 가 지워져 다음 부팅은 기다리는 길 → 로그아웃 상태(IndexedDB) |
| 그 밖(`md.account` 쓰기·지우기가 먹지 않음) | `stuck` | 새로 고치면 같은 판정이 되풀이된다. 새로 고치지 않고 멈춤을 유지한 채 `console.error('boot_account_stuck')` 한 줄. 새 알림 없음 |

- 판정이 `reload` 여도 그 사이 쓰기는 사라지지 않는다 — 앞질러 연 사용자의 `md-remote` outbox·`md-yjs` 에 남고(F-207 2.1 "로그아웃해도 지우지 않는다") 그 사용자가 다시 로그인한 부팅에서 나간다
- 뒤 맞추기의 목록 반영 순번(`bootListSeqRef`)은 셸을 띄울 때가 아니라 **뒤 맞추기를 실제로 시작할 때** 받는다

### 4.2 타이머가 먼저 울리면

- `setAccountPending(false)` 만 한다. 멈춤(5장)과 뒤 맞추기는 답을 기다린다
- 뒤에 온 답은 4.1 그대로 처리한다. `blocked` 가 늦게 오면 이미 열린 실시간 세션은 F-2030 5.4(4403 → L5)로 정리된다

## 5. 서버 저장소 — 확인 전 멈춤

```ts
// src/storage/serverStore.ts — ServerStoreHandlers 에 더한다
holdUntilConfirmed?: boolean   // true 면 confirmAccount() 전까지 서버 요청을 보내지 않는다 (F-2134)
// ServerStore 에 더한다
confirmAccount(): void          // 멈춤을 풀고 outbox 회차를 한 번 시작한다. 두 번째부터는 아무것도 하지 않는다
```

`OpenStoreHandlers` 는 `holdUntilConfirmed` 를 그대로 넘긴다. 값이 없거나 `false` 면 지금과 같다

멈춤 동안:
- 쓰기(`create`·`update`·`remove`·폴더·첨부 등)는 지금처럼 캐시·outbox 에 곧바로 쓰고 resolve 한다. `syncState.pending` 도 지금처럼 센다
- outbox 회차를 시작하지 않는다 — 새 쓰기·30초 재시도·`online` 이벤트 모두
- `docsApi`·`attachmentsApi` 를 부르는 **모든 자리**(`list`·`listStaged`·`listFolders`·캐시에 없는 `get`·`refreshDocFromServer`·캐시에 없는 `getAttachment`·첨부 크기 사전 검사·금고 전환 등)는 `confirmAccount()` 까지 기다린 뒤 보낸다. 서버를 부르지 않는 읽기(`listCached`·`hasPendingChanges`·캐시에 있는 `get`)는 기다리지 않는다
- `setAccountBlocked(true)` 가 `confirmAccount()` 보다 먼저 불렸으면 풀린 뒤에도 회차를 시작하지 않는다(F-2030 4.4 그대로)

## 6. App 연결

```ts
// src/app/App.tsx — 계약
const [accountPending, setAccountPending] = useState(false)
const sessionPhase: 'booting' | 'ready' = accountPending ? 'booting' : bootPhase
```

- `sessionPhase` 를 `bootPhase` 대신 넘기는 곳은 셋뿐이다: `useDocSession`, `useE2ee`, `startFlushRunner` effect. 나머지(스켈레톤 걷기·`aria-busy`·해시 라우팅·탭 신호·팔레트 등)는 `bootPhase` 그대로 — 셸은 곧바로 쓸 수 있다
- 확인 전 계정 메뉴·설정은 `account` 처음 값(`offline`)대로 저장 이메일과 `오프라인` 표시를 보인다(R9). 새 상태·문구를 더하지 않는다
- 확인 전에 연 문서는 편집기가 비어 있다가 확인(또는 타이머) 뒤 열린다. 새 표시 없음

## 12. 기본값으로 정한 것 (사람 결정 없음)

1. **문서 세션을 확인 뒤로 미룬다(D4).** 다른 안 "곧바로 연다" 는 실시간 문서가 한 왕복 빨리 열리지만, 세션 만료 때 4401 알림이 뜬 직후 새로고침되고, 다른 사용자 쿠키면 저장 id 의 `md-yjs` 편집이 그 사용자로 방에 올라갈 수 있다. 지금도 문서는 `/api/me` 뒤에 열리므로 이 명세로 늦어지는 것은 없다
2. **확인 전 쓰기는 막지 않고 보낼 목록에서 붙잡는다(D3).** 다른 안 "셸을 읽기 전용으로" 는 만들기 진입점이 열 곳 가까이라(F-2030 Q2 와 같은 사정) 파일이 크게 늘고, 붙잡아도 잃는 것이 없다
3. **어긋나면 새로고침(D2).** 다른 안 "한 페이지 안에서 저장소 바꾸기" 는 F-207 2.6 을 어기고 열린 세션·금고·탭 신호를 모두 다시 세워야 한다
4. **멈춤은 시간으로 풀지 않는다(D5).** `/api/me` 가 끝내 답하지 않으면 그 페이지의 쓰기는 오프라인처럼 쌓인다(상태바 `동기화 대기 {N}`)
5. **`fetchAccount` 에 시간 제한(AbortController)을 두지 않는다.** 두면 느린 답이 `offline` 이 되어 `confirm` 으로 멈춤이 풀린다 — 4번과 어긋난다. 기다리는 길의 무응답은 지금처럼 스켈레톤으로 남는다
6. 남는 위험(가정): 타이머가 울린 뒤에 다른 사용자 답이 오면, 그 사이 금고 열쇠 묶음 캐시(R8)가 쿠키 주인의 것으로 덮였을 수 있다. 다음 온라인 부팅에서 다시 받아 덮어 고쳐진다. `/api/me` 가 5초 넘게 늦고 쿠키가 저장 id 와 다른 두 조건이 겹칠 때만 생긴다
