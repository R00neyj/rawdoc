## 3. 저장소에서 무엇이 오는가 (코드로 확인한 결과)

### 3.1 `list()` 가 본문을 담아 준다 — 문서마다 `get()` 을 부르지 않는다

| 저장소 | `list()` 구현 | `content` |
| --- | --- | --- |
| `memoryStore` | 56~58행 `[...docs.values()].map(normalizeDoc)` | **있다** (원본 그대로) |
| `idbStore` | 116~119행 `db.getAll('docs')` | **있다** (레코드 전체) |
| `serverStore` — 내 문서 | 496~549행. 서버 요약과 캐시의 `version` 이 다른 문서만 `api.getDoc` 으로 채운 뒤 `cache.getDocs(userId)` 전체를 돌려준다 | **있다** |
| `serverStore` — 공유받은 문서 | 551~570행. `api.getShared()` 결과를 `content: ''` 로 채운다 | **없다(`''`)** — 일부러 캐시하지 않는다(F-207) |

**결론: `buildSearchIndex` 는 `store.get(id)` 를 한 번도 부르지 않는다.** `store.list()` 와 `store.listFolders()` 두 번이 전부다. F-284 5.2 의 "캐시 공백 보완"은 `serverStore.list()` 가 이미 안에서 하고 있고(빠진 본문을 `api.getDoc` 으로 채운다), 그 비용은 이 모듈이 아니라 저장소 쪽에서 난다

- 그래서 인자 타입을 **`Pick<Store, 'list' | 'listFolders'>`** 로 좁힌다. 이 모듈이 저장소에서 무엇을 쓰는지가 타입에 그대로 드러나고, 단위 테스트가 두 함수만 가진 스텁을 넘길 수 있다 (7장 A10·A15·A16·A23)
- `App.tsx` 의 `docs` 상태는 `stripContent`(115행)를 거쳐 **본문이 없다.** 인덱스는 그것을 쓰지 않고 `store.list()` 를 직접 부른다

- **지도(F-292 개정판)도 이 인덱스를 함께 쓴다.** 필터(6.4)와 그룹(6.5)이 `parseSearchQuery` + `matchDoc` + `searchIndex` 를 그대로 재사용하기로 정해져서, `buildSearchIndex` 가 이미 읽어 둔 문서 배열을 받을 수 있게 **`docs?: Doc[]`·`folders?: Folder[]` 선택 인자 둘**을 갖게 된다 (F-2007 실제 구현, `folders?` 는 폴더 경로를 함께 넘기려고 더해졌다). 소비자가 하나 늘 뿐 이 장의 결론은 바뀌지 않는다

### 3.3 공유받은 문서 판정 — `role === 'edit' || role === 'view'`

`Doc.role` 은 **서버 저장소에서만 채운다**(`src/types.ts` 14~15행 주석). `idbStore`·`memoryStore` 는 이 필드를 아예 만들지 않아 `undefined` 다

- F-284 4.3 은 "`Doc.role` 이 `owner` 가 아님"으로 적었는데, 그대로 구현하면 **로그인하지 않은 사용자의 모든 문서가 공유받은 문서로 잡힌다**(`undefined !== 'owner'`). 1.1 갱신 대상에 올렸다
- 이 명세의 규칙: `entry.shared = (doc.role === 'edit' || doc.role === 'view')`. `undefined`·`'owner'` 는 내 문서다
- `shared` 인 문서는 **본문을 아예 읽지 않는다.** `serverStore` 가 이미 `''` 를 주지만, 나중에 F-207 캐시 정책이 바뀌어 본문이 들어와도 인덱스는 넣지 않는다 (F-284 5.2, 8장 Q4 가 별도 명세로 미뤘다)
- 본문을 안 읽으므로 공유받은 문서는 **`key:value` 필터에 절대 걸리지 않는다.** `properties` 가 `null` 이다. 그 사실을 사용자에게 알리는 문구(`공유받은 문서 {N}개는 제목만 찾았습니다`)는 F-288 이 `sharedCount` 를 받아 쓴다

### 3.4 계정이 바뀌는 곳 — 무엇과 무엇을 비교해 아는가

| 확인한 것 | 코드 |
| --- | --- |
| `Store` 는 계정 id 를 **내보내지 않는다.** `kind`(`'idb'|'memory'|'server'`)만 있다 | `src/types.ts` 51~52행 |
| 계정 id 를 아는 곳은 `openStore({ account })` 를 부르는 `App` 이다. `openStore` 가 `account.state === 'in'` 이면 `createServerStore(account.id, …)` 를 만든다 | `src/storage/openStore.ts` 35~41행 |
| 저장소는 **부팅 때 한 번만** 연다. `bootedRef` 가 막고, `openStore`·`setStore` 호출은 파일 전체에서 575·606행 한 쌍뿐이다 | `src/app/App.tsx` 554~606행 |
| 로그인·로그아웃은 `location.href = loginUrl(...)` / `logoutUrl()` — **전체 페이지 이동**이다. 모듈 수준 상태가 통째로 사라진다 | `src/app/AccountMenu.tsx` 74·80행 |
| 같은 페이지 안에서 `store` 가 바뀌는 경우는 **부팅 임시 `memoryStore` → 실제 저장소** 교체 하나뿐이다 | `src/app/App.tsx` 196~197행, 606행 |

**결론: "계정이 바뀌면 통째로 버린다"를 런타임에 판정할 일은 실제로 거의 없다.** 그래도 두 가지를 둔다 — 잘못 남았을 때의 대가가 "남의 계정 문서 발췌가 보인다"라서 싸게 막을 수 있으면 막는다

1. **범위 문자열(`scope`)**: 호출하는 쪽이 준다. `searchScope(store.kind, accountId)` = `` `${kind}:${accountId ?? 'local'}` ``. 예 `server:u_8f21`, `idb:local`, `memory:local`. 캐시에 만들 때의 `scope` 를 같이 두고 다르면 `Map.clear()`
2. **`store` 인스턴스 동일성**: 마지막으로 인덱스를 만든 `store` 객체 참조를 두고 `!==` 이면 역시 `Map.clear()`. 위 표의 "부팅 임시 `memoryStore` → 실제 저장소" 가 `memory:local` → `memory:local` 로 같은 `scope` 를 낼 수 있는 유일한 경로다(IndexedDB 를 못 쓰는 브라우저)

- `accountId` 를 이 모듈이 직접 읽지 않는다. `localStorage` 를 읽으면 테스트 환경(`node`)에서 못 돌고, `app → storage` 방향도 흐려진다. **`searchScope` 는 인자만 받는 순수 함수**다
- 대가: 옛 `store` 참조를 하나 붙잡고 있어 그 저장소의 클로저(캐시·리스너)가 GC 되지 않는다. 버릴 때 `null` 로 되돌린다

### 3.5 재사용 키 — `updatedAt` 만으로 안전한가 (직접 읽고 답한다)

**질문: 본문만 바뀌고 `updatedAt` 이 안 바뀌는 경로가 있는가?**

| 경로 | `updatedAt` | 본문·제목 | 판정 |
| --- | --- | --- | --- |
| `idbStore.update` → `applyPatch`(30~37행) | `Date.now()` | 바뀐다 | 안전 |
| `memoryStore.update`(112~117행) | `Date.now()` | 바뀐다 | 안전 |
| `serverStore.update`(640~645행) | `Date.now()` | 바뀐다 | 안전 |
| `serverStore` 가 보낸 뒤 서버 응답을 캐시에 덮기(246~249행) | 서버 `now`(`worker/docs.ts` 242·245행) | 같은 내용 | 값이 달라져 **한 번 더** 다시 만든다. 맞기는 하다 |
| 다른 기기에서 고친 것 → `list()` 가 `api.getDoc` 으로 채움(538~543행) | 서버 `updated_at` | 바뀐다 | 안전 |
| 409 충돌로 서버 문서를 캐시에 덮기(213~216행) | 서버 값 | 바뀐다 | 안전 |
| `refreshDocFromServer`(587~595행, F-213) | 서버 값 | 바뀐다 | 안전 |
| `moveDoc`(`idbStore` 172~199행, `memoryStore` 127~141행, `serverStore` 664~680행) | **안 바뀐다** | **안 바뀐다** | 안전 — 본문 인덱스는 그대로여도 맞다. 단 `folderId`·`folderPath` 는 갱신해야 한다 (4.4) |
| `setPinned`(`idbStore` 203~215행 등) | **안 바뀐다** | 안 바뀐다 | 안전 |
| `create`(가져오기 F-282 가 `updatedAt` 을 그대로 준다) | 주어진 값 | 새 문서 | 안전 — 이미 있는 id 면 던진다(덮지 않는다) |
| `importWorkspace.ts` 692행 `store.update(id, { title, content })` | `Date.now()` | 바뀐다 | 안전 |

**남는 구멍은 하나다 — 같은 밀리초 안에 같은 문서를 두 번 쓰는 경우.** `Date.now()` 는 밀리초라 두 번째 쓰기가 같은 값을 낼 수 있다. 자동 저장이 700ms 디바운스(`useDocSaver.ts`)라 실제로 일어나기 어렵지만, `flush()` 를 명시로 부르는 경로(문서 전환·내보내기)가 겹치면 이론상 가능하다

**대처: 변경 키에 `content.length` 를 더한다.**

```
changeKey(doc) = `${doc.updatedAt}\u0000${doc.content.length}\u0000${doc.title}`
```

- `content.length` 는 자바스크립트에서 **O(1)** 이다(문자열이 길이를 들고 있다). 비용이 사실상 0 이다
- `title` 은 F-284 5.3 이 정한 안전장치를 그대로 둔 것이다. `updatedAt` 은 `>` 가 아니라 **`!==`** 로 본다 — 기기 시계가 어긋나 서버 값이 캐시보다 과거일 수 있다(F-284 5.3)
- 구분자는 `\u0000`. 제목에 들어갈 수 없는 글자라 `updatedAt`·길이·제목 경계가 섞이지 않는다
- 그래도 남는 구멍: 같은 밀리초 + 같은 길이 + 같은 제목인데 내용만 다른 경우. 해시를 뜨면 막히지만 문서 전체를 다시 훑어야 해서 재사용의 이득이 사라진다. **막지 않는다** (8장 Q1)
- 공유받은 문서는 `content` 가 항상 `''` 라 길이가 0 으로 고정된다. `updatedAt`+`title` 로만 판정되고, 본문을 안 쓰므로 그것으로 충분하다

## 4. 인덱스 만들기

### 4.1 내보내는 타입

```ts
import type { Doc, Folder, Store } from '../types'

// 이 모듈이 저장소에서 쓰는 것은 이 둘뿐이다 (3.1)
export type SearchSource = Pick<Store, 'list' | 'listFolders'>

// parseSimpleProperties 결과를 NFC 정규화한 것. 대소문자는 그대로 둔다 (4.3)
// F-285 의 SearchProperty 와 모양이 같다 — 두 모듈이 각자 선언하고 구조적으로 맞춘다 (8장 Q2)
export type SearchProperty = { key: string; value: string | string[] }

export type SearchIndexEntry = {
  id: string
  /** NFC 정규화한 제목. 제목 매칭과 결과 행 표시에 같이 쓴다 */
  title: string
  /** 프론트매터를 뗀 뒤 NFC 정규화한 본문. 공유받은 문서는 '' (3.3) */
  body: string
  /** 프론트매터가 없거나 파서가 못 읽었으면 null (4.3) */
  properties: SearchProperty[] | null
  /** 프론트매터는 있는데 parseSimpleProperties 가 null 을 돌려준 문서. 안내 문구용 (F-284 4.4) */
  frontmatterUnreadable: boolean
  folderId: string | null
  /** '상위 / 하위'. 폴더 밖이거나 없는 폴더를 가리키면 '' (4.4) */
  folderPath: string
  updatedAt: number
  /** role 이 'edit'|'view' 인 문서 — 본문을 넣지 않았다 (3.3) */
  shared: boolean
}

export type SearchIndex = {
  scope: string
  /** store.list() 순서 그대로 (updatedAt 내림차순). 정렬은 F-285·F-287 몫 */
  entries: SearchIndexEntry[]
  /** frontmatterUnreadable 인 문서 수 (F-284 4.4 안내 문구) */
  frontmatterUnreadableCount: number
  /** shared 인 문서 수 (F-284 4.4 안내 문구) */
  sharedCount: number
  /** 이번 호출에서 본문을 새로 만든 문서 수 — 계측·테스트용 (7장) */
  rebuiltCount: number
  /** 이번 호출에서 캐시를 재사용한 문서 수 */
  reusedCount: number
}
```

export function searchScope(kind: Store['kind'], accountId: string | null): string

- `../storage/*` 도 import 하지 않는다 — `store` 를 인자로 받는다

### 4.3 문서 하나를 항목으로 만드는 순서

```
1. shared = (doc.role === 'edit' || doc.role === 'view')
2. raw = shared ? '' : doc.content
3. fm = raw ? findFrontmatter(raw) : null
4. body = fm ? textAfterFrontmatter(raw, fm) : raw           // 원문 좌표로 자른다
5. parsed = fm ? parseSimpleProperties(raw.slice(fm.contentFrom, fm.contentTo)) : null
6. properties = parsed ? parsed.map(NFC 정규화) : null
   frontmatterUnreadable = (fm !== null && parsed === null)
7. title = doc.title.normalize('NFC')
   entryBody = body.normalize('NFC')
8. folderPath = folderPaths.get(doc.folderId) ?? ''
```

**순서가 중요하다 — 자른 뒤에 정규화한다.** `findFrontmatter` 가 돌려주는 `to`·`contentFrom`·`contentTo` 는 **원문 좌표**다. 먼저 `normalize('NFC')` 를 하면 NFD→NFC 로 글자 수가 절반 가까이 줄어(F-284 4.2, 6.1 실측에서 39.0M자 → 21.0M자) 그 좌표가 전부 어긋난다. 자를 때는 원문 좌표로, 잘라 낸 조각만 정규화한다

- **`properties` 의 키·값은 NFC 정규화만 하고 소문자화하지 않는다.** F-284 3.2 의 "대소문자를 구분하지 않는다"는 **비교하는 쪽**(F-285)에서 `toLowerCase()` 로 처리한다. 인덱스가 소문자 사본을 들고 있으면 메모리가 늘고(F-284 5.1) 화면에 원래 대소문자를 보여줄 수 없다
- `parseSimpleProperties` 의 값은 `string` 이거나 `string[]`(블록 목록)이다. 배열이면 항목마다 정규화한다
- **`tags: [a, b]` 인라인 배열 보정(F-284 3.4)은 여기서 하지 않는다.** 그건 쿼리 쪽 매칭 규칙이라 F-285 몫이다 — 인덱스는 파서가 준 문자열 `'[a, b]'` 를 정규화해서 그대로 담는다
- `properties === null` 과 `frontmatterUnreadable === true` 는 다르다. 프론트매터가 아예 없는 문서(대부분)는 `properties: null, frontmatterUnreadable: false` 다. 이 둘을 안 나누면 F-284 4.4 의 `속성을 읽지 못한 문서 {N}개` 가 프론트매터 없는 문서까지 세어 항상 전체 수가 된다

### 4.4 폴더 경로

`folderPathMap(folders)` 이 폴더마다 `상위 / 하위` 문자열을 미리 만들어 `Map<folderId, string>` 으로 돌려준다. 문서마다 트리를 거슬러 올라가지 않는다 — 문서 5,000개 × 폴더 20개를 매번 훑는 초기 구현은 5,000개에서 약 290ms 를 더 썼다(6.1 각주)

| 경우 | 결과 | 근거 |
| --- | --- | --- |
| 최상위 폴더 안 문서 | `폴더이름` | |
| 하위 폴더 안 문서 | `상위 / 하위` (구분자는 공백·슬래시·공백) | F-284 4.3 |
| 폴더 밖 문서 (`folderId === null`) | `''` | |
| 없는 폴더를 가리키는 문서 | `''` | `buildTree` 가 끊긴 `folderId` 를 최상위로 보는 것과 같은 규칙 (`folderTree.ts` 33~34행) |
| 부모가 없는 폴더 | 그 폴더 이름만 | 위와 같은 규칙 |
| 순환 참조(있을 수 없지만 데이터가 깨졌을 때) | 본 폴더를 다시 만나면 멈춘다 | `serverStore.sortFoldersParentFirst`(64~78행)가 쓰는 방어와 같다 |

- **폴더 이름은 정규화하지 않는다.** 경로는 표시용이고 검색 대상이 아니다 (F-284 4.1 "폴더 이름 ×"). 8장 Q4
- `folderTree.ts` 에는 경로 문자열을 만드는 함수가 없다(`ancestorsOfDoc` 는 id 배열을 준다). **`folderTree.ts` 를 고치지 않고** `searchIndex.ts` 안에 둔다 — 지금 쓰는 곳이 하나뿐이라 공용 `lib` 으로 뽑을 근거가 없다

## 5. 재사용

### 5.1 어디에 두나

`src/app/searchIndex.ts` 의 **모듈 수준 `Map<string, SearchIndexEntry>`** 와 `scope`·`store` 를 담는 모듈 변수. React 상태가 아니다 — 대화상자를 닫아 컴포넌트가 사라져도 남아야 재사용이 되고, 이 값이 바뀐다고 화면을 다시 그릴 일이 없다 (F-284 5.3)

IndexedDB 에 영속시키지 않는다. 새로고침하면 사라지고 다시 만든다

### 5.2 `buildSearchIndex` 절차

```
1. scope 또는 store 인스턴스가 지난번과 다르면 Map.clear() (3.4)
2. const [docs, folders] = await Promise.all([store.list(), store.listFolders()])
3. const folderPaths = folderPathMap(folders)
4. 문서마다:
     key = changeKey(doc)
     hit = cache.get(doc.id)
     if (hit && hit.__key === key)   → 재사용. 메타만 새 값으로 바꾼 사본을 만든다 (5.3)
     else                            → makeIndexEntry(doc, folderPaths)
     캐시에 넣고 entries 에 밀어 넣는다
5. list() 에 없던 id 를 Map 에서 지운다
6. scope·store 를 모듈 변수에 기록한다
7. SearchIndex 를 돌려준다
```

- 2번은 **`Promise.all` 로 나란히** 부른다. `serverStore` 에서는 둘 다 네트워크가 걸려 있어 차례로 부르면 시간이 두 배가 된다
- `__key` 는 항목에 함께 담는 비공개 필드다. 별도 `Map` 을 하나 더 두지 않는다. 타입에는 `SearchIndexEntry & { __key: string }` 를 모듈 안에서만 쓴다
- **`store.list()` 가 reject 하면 잡지 않는다.** 예외를 그대로 올리고 **캐시는 건드리지 않는다**(1번의 `clear()` 는 이미 지났을 수 있지만, 그건 범위가 바뀌어 버려야 할 때뿐이다). 어떤 화면을 보일지는 F-287·F-288 이 정한다 (F-284 4.4 `오프라인 —`)
  - `serverStore.list()` 는 네트워크 오류를 스스로 삼키고 캐시 결과를 돌려주므로(501~506행) 실제로 여기서 던지는 것은 IndexedDB 가 깨졌을 때다
  - 삭제(5번)가 맨 뒤에 있어 중간에 실패해도 인덱스가 반쯤 지워지지 않는다

### 5.3 재사용할 때 메타를 새로 읽는다

F-284 5.3 이 "폴더 경로·고정·`role` 은 인덱스 캐시가 아니라 매번 `list()` 결과에서 읽는다"로 정했다. `moveDoc`·`setPinned` 가 `updatedAt` 을 안 바꾸기 때문이다 (3.5)

- **비싼 부분**(`title`·`body`·`properties`·`frontmatterUnreadable`)만 재사용한다
- **싼 부분**(`folderId`·`folderPath`·`updatedAt`·`shared`)은 이번 `list()` 결과로 매번 덮는다
- 덮을 때 **기존 객체를 고치지 않고 사본을 만든다**(`{ ...hit, folderId, folderPath, updatedAt, shared, __key }`). 앞서 돌려준 `SearchIndex` 를 React 가 쥐고 있을 수 있어 제자리 수정은 조용한 버그가 된다. 비용은 문서마다 작은 객체 하나 — 5,000개에서 재사용만 도는 경우가 2.7~3.9ms 다 (6.1)

### 5.4 모듈 수준 `Map` 의 위험과 대처

| 위험 | 대처 |
| --- | --- |
| **테스트 사이에 상태가 남는다.** Vitest 는 파일마다 모듈을 새로 읽지만 한 파일 안 테스트끼리는 같은 모듈을 쓴다 | **`resetSearchIndexCache()` 를 내보낸다.** `searchIndex.test.ts` 가 `beforeEach` 에서 부른다. A22 가 이것 자체를 판정한다 |
| **캐시 상태를 밖에서 볼 수 없어 재사용을 테스트할 수 없다** | `SearchIndex.rebuiltCount`·`reusedCount` 와 `searchIndexCacheSize()` 를 내보낸다. 내부 `Map` 자체는 내보내지 않는다 |
| **같은 페이지에서 계정을 바꿔 로그인하면 남의 문서가 남는다** | 실제로는 로그인·로그아웃이 전체 페이지 이동이라 모듈이 새로 읽힌다(3.4). 그래도 `scope`+`store` 동일성 검사를 둔다 |
| **대화상자를 닫아도 메모리를 잡고 있다** | 의도한 대가다 (F-284 5.3). 실측 규모는 6.3 — 문서 1,000개 약 17MB, 5,000개 약 53MB. 상한을 두지 않는다 (8장 Q3) |
| **탭이 여러 개면 탭마다 인덱스가 따로 생긴다** | 그대로 둔다. 탭 사이 공유 장치(BroadcastChannel 등)를 만들지 않는다 |

## 6. 실측 (이 PC, 2026-09-21)

**추정이 아니다. 아래 숫자는 전부 직접 재서 적은 것이다.** 두 가지를 쟀다 — (1) Node 에서 문자열 처리만, (2) 실제 브라우저에서 IndexedDB 읽기까지 포함해서

### 6.1 Node — 인덱스 만들기·재사용 (Node v24.12.0)

`src/lib/frontmatter.ts` 를 **그대로 import 해서**(Node 24 타입 스트리핑) 4.3 절차를 돌린 스크래치패드 스크립트. 합성 문서는 CRLF, 프론트매터 7줄(`title`·`tags` 블록 목록·`author`·`date`) + 한글 본문. 문자열은 `JSON.parse(JSON.stringify(...))` 로 평탄화해 IndexedDB 구조화 복제와 같은 모양으로 맞췄다. 3회 실행

| 문서 수 | 총 글자 | **처음 만들기** | **1개만 바뀜** | 하나도 안 바뀜 |
| --- | --- | --- | --- | --- |
| 100 | 0.22M자 | 1.9~2.3ms | 0.1ms | 0.1ms |
| 1,000 | 4.28M자 | 9.9~13.7ms | 0.9~1.8ms | 0.6~1.6ms |
| 5,000 | 21.4M자 | 51.3~54.1ms | 4.4~5.3ms | 2.7~3.9ms |

원문이 **전부 NFD** 일 때 (최악):

| 문서 수 | 총 글자 | 처음 만들기 | 1개만 바뀜 |
| --- | --- | --- | --- |
| 1,000 | 7.80M자 | 36.3~37.2ms | 1.1~1.2ms |
| 5,000 | 39.0M자 | 154~161ms | 5.7~6.2ms |

단계 분해 (5,000개·21.4M자·NFC 원문, 2회):

| 단계 | 시간 |
| --- | --- |
| `findFrontmatter` × 5,000 | 3.1ms |
| `textAfterFrontmatter`(= `slice`) × 5,000 | 0.6ms |
| `parseSimpleProperties` × 5,000 | 15.8ms |
| `normalize('NFC')` 본문 × 5,000 | 27.5ms |
| 합 | **약 47ms** |

- **재사용이 인덱스 만들기를 10배 이상 줄인다.** 5,000개에서 52ms → 4.5ms
- 각주: 폴더 경로를 문서마다 트리를 거슬러 계산한 첫 구현은 5,000개에서 **343ms** 였다. `folderPathMap` 으로 한 번만 만들게 고쳐 51ms 가 됐다 (4.4)
- 각주2: 합성 문서를 평탄화하지 않으면 `findFrontmatter` 가 5,000개에서 **323ms** 로 나온다. 생성기의 문자열 이어붙이기가 만든 V8 rope 를 첫 `indexOf` 가 평탄화하는 비용이고, **인덱스 비용이 아니다.** 실제 앱의 `content` 는 IndexedDB 가 준 평탄한 문자열이다. F-284 5.1 표의 수치도 같은 함정을 탔을 수 있다

### 6.2 브라우저 — 저장소 읽기까지 포함 (F-284 6장 게이트 (b))

`scripts/measure.mjs --eval` 로 **실제 Chromium(HeadlessChrome 153) 안에서** 잰 것이다. `md-docs` IndexedDB `docs` 스토어에 합성 문서를 직접 넣고, `getAll` → 인덱스 만들기 → 검색 1회를 3라운드 돌린 뒤 넣은 문서를 지웠다. 본문 4.2천자, 프론트매터 6줄

| 문서 수 | **`list()`(= `getAll`)** | **인덱스 만들기** | **합 (게이트 (b))** | 검색 1회(`toLowerCase`+`indexOf`) |
| --- | --- | --- | --- | --- |
| 1,000 | 60.0 / 60.6 / 65.4ms | 5.9 / 5.9 / 6.8ms | **65.9 / 66.5 / 72.2ms** | 5.4~8.4ms |
| 5,000 | 268 / 321 / 381ms | 37.4 / 45.4 / 46.5ms | **305 / 368 / 427ms** | 44.7~56.1ms |

**판정: 게이트 (b) 통과.** 문서 1,000개에서 인덱스가 준비되기까지 **66~72ms** — F-284 가 정한 1,000ms 의 1/14 이다. 5,000개에서도 305~427ms 로 상한 안이다

- **F-284 가 "안 잰 것"으로 남긴 것 중 가장 큰 항목이 IndexedDB 읽기였는데, 실제로 가장 컸다.** 인덱스 만들기의 **9~10배**다. 그래서 재사용(5장)으로 줄일 수 있는 것은 전체의 10% 뿐이다 — 재사용의 진짜 이득은 5,000개 규모에서 45ms → 5ms 로 내려가는 쪽이고, `list()` 자체는 매번 낸다(F-284 5.3 이 그렇게 정했다. 캐시 공백 보완이 거기 달려 있다)
- **안 잰 것**: `serverStore.list()` 의 네트워크(캐시가 비어 있으면 문서마다 `api.getDoc` 한 건씩), React 가 결과 200행을 그리는 시간, 게이트 (a) "검색창이 보이기까지". 셋 다 대화상자가 있어야 잴 수 있어 **F-287 로 넘긴다** (1.1 갱신 대상)
- 재현 방법: 이 명세 본문의 절차를 `scripts/measure.mjs --eval` 에 넣어 돌린 것이다. 셸을 거치며 따옴표가 깨져서 표현식을 base64 로 감싸 넘겼다. 반복이 필요해지면 `scripts/` 에 문서 씨 뿌리기 도구를 두자고 제안한다 (8장 Q5)

### 6.3 메모리 (Node, `--expose-gc`, 3회 GC 후 `heapUsed`)

| 문서 수 | 총 글자 | 문서만 | 문서 + 인덱스 | **인덱스만(문서 참조를 끊은 뒤)** |
| --- | --- | --- | --- | --- |
| 1,000 | 4.25M자 | 15.7MB | 16.7MB | **16.6MB** |
| 5,000 | 21.3M자 | 48.8MB | 53.2MB | **53.2MB** |

- **`normalize('NFC')` 는 이미 NFC 인 문자열에 같은 객체를 돌려준다 — 5,000/5,000 전부 `===` 로 확인했다.** 그래서 잘라 낸 본문은 V8 의 sliced string 이고 원문 `content` 를 계속 붙잡는다

  - 잘라 낸 조각을 새 문자열로 떼어 내 봤지만(`(' ' + s).slice(1)`) 5,000개에서 53.2MB → 52.7MB 로 차이가 없었다. 프론트매터가 문서의 2% 뿐이라 떼어 낼 게 없다. **하지 않는다**

### Q1. 변경 판정 키에 `content.length` 를 더할 것인가 — **기본값: 더한다**

F-284 8장 항목 11 은 `updatedAt`+`title` 로 정했다. 여기에 `content.length` 를 더하자는 제안이다

| | 더한다(기본값) | F-284 문구 그대로 |
| --- | --- | --- |
| 비용 | 0. `String.length` 는 O(1) | 0 |
| 막는 것 | 같은 밀리초에 같은 문서를 두 번 써서 `updatedAt` 이 겹치는 경우 (3.5) | 못 막는다 |
| 남는 구멍 | 같은 밀리초 + 같은 길이 + 같은 제목 | 같은 밀리초 |

- 다른 쪽을 고르면: 3.5 표의 "남는 구멍" 이 그만큼 넓어진다. 증상은 **편집한 내용이 검색에 안 잡히는 것**이고, 탭을 새로 고치기 전까지 낫지 않는다. 대신 F-284 승인 문구와 한 글자도 어긋나지 않는다

### Q2. F-285 의 매칭 함수 입력 타입과 맞는가 — **확인함. 이름을 F-285 에 맞췄다**

F-285(`src/lib/docSearch.ts`)를 같은 시각에 다른 에이전트가 썼다. **이 명세를 다 쓴 뒤 `specs/features/F-285.md` 3장을 읽어 대조했다.** F-285 가 정한 매칭 입력은:

```ts
// specs/features/F-285.md 3장
export type SearchProperty = { key: string; value: string | string[] }
export type SearchDocInput = {
  id: string
  title: string
  body: string
  properties: readonly SearchProperty[] | null
  updatedAt: number
}
```

| 항목 | F-285 | F-286 | 맞나 |
| --- | --- | --- | --- |
| `id` `title` `body` `updatedAt` | 있다 | 있다 | ○ |
| 속성 필드 이름 | `properties` | 처음엔 `props` 였다 → **`properties` 로 고쳤다** | ○ |
| 속성 모양 | `{key, value: string \| string[]}[] \| null` | 같다 | ○ |
| NFC 전제 | "입력이 이미 NFC 라고 믿는다"(F-285 5장) | 인덱스가 정규화해서 넣는다 (4.3) | ○ |
| 소문자화 | `foldCase` 를 **F-285 가** 비교 때 한다 | 인덱스는 원래 대소문자를 둔다 (4.3) | ○ |
| `readonly` | 매개변수가 `readonly` | 인덱스는 보통 배열 | ○ (`T[]` 는 `readonly T[]` 에 넘어간다) |
| 인덱스에만 있는 필드 | 모름 | `frontmatterUnreadable` `folderId` `folderPath` `shared` | ○ 구조적 부분집합이라 남는 필드는 무시된다 |

- **`src/lib/docSearch.ts` 는 `src/app/searchIndex.ts` 를 import 할 수 없다**(`lib → app` 은 역방향, `specs/architecture.md` 1장). 그래서 두 타입을 **각자 선언하고 구조적으로만** 맞춘다. `SearchIndexEntry[]` 를 `searchDocs(docs: readonly SearchDocInput[], …)` 에 그대로 넘길 수 있다
- **남은 한 곳 — 안내 문구의 셈이 두 군데다.** F-285 의 `SearchOutcome.unreadableProperties` 는 "필터가 있을 때 `properties` 가 `null` 이라 빠진 문서 수"(프론트매터가 **아예 없는** 문서도 포함)이고, F-286 의 `frontmatterUnreadableCount` 는 "프론트매터는 있는데 파서가 못 읽은 문서 수"다. **둘은 다른 수다.** F-284 4.4 의 문구 `속성을 읽지 못한 문서 {N}개는 필터에서 빠졌습니다` 에 어느 쪽을 넣을지는 **F-288 이 정한다**
  - 기본값 제안: **F-285 의 `unreadableProperties`** 를 쓴다 — 문구가 "필터에서 빠졌습니다" 라 실제로 빠진 수를 말하는 게 맞다. 그러면 `frontmatterUnreadableCount` 는 계측·디버그로만 남는다
  - 반대로 F-286 의 수를 쓰면 "프론트매터가 없어서 안 나온 문서" 를 사용자가 알 수 없다
- 이름이 더 어긋나면 **고치는 쪽은 F-286 이다** — 인덱스는 만들기만 하고 의미를 정하지 않으므로 이름을 양보하는 게 싸다

### Q3. 인덱스 항목 수 상한을 둘 것인가 — **기본값: 두지 않는다**

문서 5,000개에 약 53MB(6.3), 만드는 데 브라우저에서 305~427ms(6.2). F-284 5.1 이 "견디는 규모: 문서 5,000개 / 2천만 자"로 이미 선을 그었다

- 상한이 필요해지면 그때 F-284 5.1 의 재검토 순서(청크 → 웹 워커 → 저장하는 역색인)를 따른다. **웹 워커·역색인은 F-284 5.4 "하지 않는 것" 이라 명세를 먼저 고치고 사람 승인을 받는다**

### Q4. 폴더 이름을 NFC 정규화할 것인가 — **기본값: 하지 않는다**

폴더 경로는 결과 행에 **보여주기만** 하고 검색 대상이 아니다 (F-284 4.1 "폴더 이름 ×")
