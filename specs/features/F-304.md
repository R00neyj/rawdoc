## 2. 범위

### 한다

- 문서마다 DO 하나(`DocRoom`, `getByName(docId)`), `y-partyserver` 의 `YServer` 상속, **hibernation 켬** (5장)
- `/ws/doc/:id` — Worker 가 Origin·로그인·권한(edit 이상)을 보고 DO 로 넘긴다. 거절은 닫기 코드로 (4장)

- D1 에서 `Y.Doc` 으로 씨앗 심기(본문 + 제목), D1 에 외부 쓰기가 있었으면 흡수 (7장)
- D1 파생 스냅샷, `version` 단조 증가, 문서 크기 초과 경고 (8장)
- 권한 회수·문서 삭제 때 소켓 닫기 (9장)
- 자동 응답 ping, 타이머 최소화 등 DO 를 깨우지 않는 규칙 (10장)
- 클라이언트 쪽 계약 파일 `src/lib/docRoomProtocol.ts` 와 F-305 에 넘길 것 정리 (11장)

### 하지 않는다

- **클라이언트 연결** — `YProvider`, 경로 판정, 폴백, 재연결, 첫 동기화 전 읽기 전용, 연결 상태 표시: F-305

- awareness 로 무엇을 보낼지(F-307). 서버는 `y-partyserver` 기본 중계만 한다
- 브라우저 오프라인 영속(F-306), 잠금 제거(F-309)
- `/api/ws-ticket`(4.4 2안) — **구현하지 않고 명세만 둔다.** 15.4 S1 이 실패하면 그대로 구현한다

## 3. 전체 흐름

```
브라우저 WebSocket ──► Worker /ws/doc/:id ──(검사 통과)──► DocRoom DO (문서당 1개, hibernation)
   (F-305)              Origin·로그인·권한                   Y.Doc: content, title
                        실패 → 101 + 즉시 닫기(44xx)          │ 깨어날 때: DO SQLite 로그 + D1 한 줄 읽기
```

- D1 → `Y.Doc` 방향은 **씨앗 심기(7.1)와 외부 쓰기 흡수(7.2)** 두 경우뿐이다. 흡수는 F-301 3.3 "그 뒤로 D1 → `Y.Doc` 방향은 다시 일어나지 않는다" 에 대한 예외이고 이유는 7.2

## 4. `/ws/doc/:id` — 연결 경로와 인증

### 4.1 Worker 판정 순서

`worker/index.ts` 는 `/ws/` 로 시작하는 경로를 지금의 JSON API 분기보다 **앞에서** 받아 `handleDocSocket` 으로 넘긴다. `/ws/doc/:id` 가 아닌 `/ws/*` 는 `errorResponse('not_found', 404)`

`resolveDocSocket(request, env, docId)` 는 아래 순서로 보고 첫 실패에서 멈춘다

| # | 검사 | 실패하면 |
| --- | --- | --- |
| 1 | `GET` 이고 `Upgrade` 헤더가 대소문자 무시 `websocket` | HTTP `426 {"error":"upgrade_required"}` |
| 2 | Origin 허용(4.5) | HTTP `403 {"error":"forbidden_origin"}` |
| 3 | `isValidUuid(docId)` (`worker/validate.ts`) | HTTP `404 {"error":"not_found"}` |
| 4 | `getUser(request, env)` 가 사용자를 돌려준다 | 닫기 `4401` `unauthenticated` |
| 5 | `getDocAccess(env, docId, user, 'id, owner_id, folder_id, version')` 가 있다 | 닫기 `4404` `not_found` |
| 6 | `roleAtLeast(role, 'edit')` | 닫기 `4403` `forbidden` |
| 7 | 통과 | DO 로 넘긴다 |

- 5번의 열 목록에 `content` 를 넣지 않는다. `getDocAccess` 기본값 `*` 는 본문(최대 1MB)까지 읽는다
- 1~3 은 우리 클라이언트가 만들 수 없는 요청이라 HTTP 로 거절한다. 4~6 은 우리 클라이언트가 실제로 만나는 경우라 닫기 코드로 거절한다(4.2)
- 넘기기: 들어온 요청을 복제해 헤더 `X-WS-*` 로 시작하는 것을 **전부 지우고** 아래 넷을 새로 넣은 뒤 `env.DOC_ROOM.getByName(docId).fetch(요청)`. 그 호출이 던지면 닫기 `1013` `unavailable`

```ts
// worker/docSocket.ts — Worker 와 DocRoom 사이 계약
export const DOC_ROOM_HEADERS = {
  userId: 'X-WS-User-Id',
  email: 'X-WS-User-Email',
  role: 'X-WS-Role',          // 'owner' | 'edit'
  docVersion: 'X-WS-Doc-Version', // 5번에서 읽은 D1 version
} as const
```

- 비용: 연결 한 번 = Worker 요청 1건 + D1 질의(사용자 확인 2, 권한 판정 1~3). DO 는 7번에서만 부른다 — 거절된 요청은 DO 를 깨우지 않는다

### 4.2 거절을 HTTP 상태가 아니라 닫기 코드로 — F-301 4.5 와 다르다 (18장 Q1)

F-301 4.5 는 "업그레이드하지 않고 HTTP 403, 남의 문서면 404" 였다. **그렇게 하면 F-301 9.2 의 "인증 실패면 재시도를 멈추고 `다시 로그인 필요` / `편집 권한이 없습니다`" 를 클라이언트가 구현할 수 없다**

- 브라우저 `WebSocket` 에는 HTTP 상태를 읽을 속성이 없다. 멤버는 `binaryType`·`bufferedAmount`·`extensions`·`protocol`·`readyState`·`url` 과 이벤트뿐이고, `CloseEvent` 는 `code`·`reason`·`wasClean` 만 준다(`node_modules/typescript/lib/lib.dom.d.ts`). 업그레이드가 HTTP 4xx 로 끝나면 `error` 다음 `close` 가 `1006` 으로 오고 401·403·404·서버 장애가 구분되지 않는다 — F-301 4.2 가 Access 302 를 두고 든 이유와 같다
- 그래서 Worker 가 **업그레이드를 받아들이고(101) 곧바로 앱 닫기 코드로 닫는다.** `WebSocketPair` 를 만들어 서버 쪽을 `accept()` 하고 `close(code, reason)` 한 뒤 클라이언트 쪽을 101 응답에 싣는다. `partyserver` 0.5.10 `Server.fetch` 의 `catch` 가 세션 설정 실패를 똑같이 처리한다(`pair[1].accept(); … pair[1].close(1011, …)`)
- 거절에는 DO 가 끼지 않는다. Worker 요청 1건으로 끝난다

닫기 코드 표 — 계약은 11.1 의 `SOCKET_CLOSE`

| 코드 | reason | 언제 | F-305 가 할 일(제안) |
| --- | --- | --- | --- |
| `4401` | `unauthenticated` | 로그인 안 됨·만료 | 재시도 멈춤, `다시 로그인 필요` |
| `4403` | `forbidden` | 연결 시점에 보기 권한뿐 | 재시도 멈춤, `편집 권한이 없습니다` |
| `4403` | `revoked` | 연결 중 권한이 빠짐(9장) | 읽기 전용 + 알림 |
| `4404` | `not_found` | 문서가 없거나 접근 권한이 전혀 없음 | 재시도 멈춤 |
| `4404` | `deleted` | 연결 중 문서가 지워짐(9.4) | 재시도 멈춤 |
| `1013` | `unavailable` | Worker 가 DO 를 부르지 못함, DO 가 불러오기에 실패(5.3) | 재시도 |
| `1011` | — | `partyserver` 가 세션 설정 중 예외로 닫음 | 재시도 |

- `YProvider` 는 닫히면 **코드와 상관없이** 다시 연결한다(`dist/provider/index.js` `close` 처리기 → `setTimeout(_reconnectWS, min(2^n × 100, maxBackoffTime))`, `maxBackoffTime` 기본 2,500ms). 44xx 에서 멈추는 것은 F-305 가 `connection-close` 이벤트를 받아 `disconnect()` 를 불러야 한다

### 4.3 인증 1안 — `CF_Authorization` 쿠키 (기본)

- `/ws/*` 는 지금 Access 밖이다(직접 확인 (f)). Access 가 끼지 않으니 `Cf-Access-Jwt-Assertion` 헤더는 오지 않고, 브라우저가 보내는 같은 출처 쿠키만 온다
- `worker/auth.ts` `getUser` 는 `/v1/` 이 아닌 경로에서 헤더가 없으면 `CF_Authorization` 쿠키를 읽어 JWT 를 서명·`iss`·`aud`·`exp`·`email` 까지 검증한다. **`/ws/` 를 위해 `auth.ts` 를 고칠 것이 없다**
- 로컬 `dev:worker` 는 `DEV_AUTH_EMAIL` 우회(`@example.com` 이고 `ACCESS_AUD` 가 비었을 때)가 경로와 상관없이 먼저 걸리므로 **쿠키가 실리는지는 로컬에서 판정할 수 없다**
- **확인 못 함 — 배포본에서 사람이 확인(15.4 S1)**: 브라우저가 `wss://rawdoc.app/ws/doc/…` 업그레이드에 `CF_Authorization` 을 싣는지. 같은 출처라 `SameSite` 는 문제가 아니고, 남는 변수는 그 쿠키의 `Path`·`Domain` 이다. Access 가 같은 응답에서 준 `CF_AppSession` 은 `Path=/` 였다(직접 확인 (f)). `CF_Authorization` 은 로그인 뒤 `/cdn-cgi/access/authorized` 에서 설정돼 로그인 없이는 볼 수 없었다
- 쿠키는 연결 시점에만 본다. 연결된 뒤 JWT `exp` 가 지나도 끊지 않는다(F-301 4.5 "권한은 연결 시점에만" 과 같은 선). 재연결 때 만료면 4401

### 4.4 인증 2안 — 티켓 (S1 이 실패하면 이대로 구현한다)

F-301 4.4 를 구현할 수 있는 수준으로 적는다. **전환 조건: 15.4 S1 에서 로그인한 창의 연결이 `4401` 로 닫힌다.** 그러면 F-305 명세를 쓰기 전에 이 절만 구현하는 작업을 따로 돌린다(1안 코드는 그대로 두고 2안을 더한다)

- `GET /api/ws-ticket?doc={id}` — Access 안 경로라 로그인은 Access 가 보장한다. `requireUser` → `getDocAccess`(열은 4.1 과 같이) → 없으면 404, edit 미만이면 403 → `200 {"ticket":"…","expiresAt":ms}`
- 티켓 = `base64url(JSON {d: docId, u: userId, e: email, x: 만료 ms})` + `.` + `base64url(HMAC-SHA256(비밀, 앞부분))`. 수명 **60,000ms**. 비밀은 Worker secret `WS_TICKET_SECRET`(배포 전 `npx wrangler secret put WS_TICKET_SECRET`, 로컬은 `.dev.vars`)
- `/ws/doc/:id?t={ticket}` — 4.1 의 4번에서 `getUser` 가 사용자를 못 찾으면 `t` 를 본다. 서명·만료·`d === docId` 가 맞으면 `{ id: u, email: e }` 를 사용자로 삼고 5번부터 그대로 간다(권한은 티켓 발급 뒤 바뀌었을 수 있으므로 다시 본다)
- **한 번만 쓰기는 강제하지 않는다.** 강제하려면 발급·사용마다 저장소 쓰기가 한 번씩 는다. 티켓은 문서 하나·사용자 하나·60초로 묶이고, 이 Worker 는 요청 URL 을 로그로 남기지 않으며(`wrangler.jsonc` 에 `observability` 없음), 브라우저 방문 기록에 WebSocket 주소는 남지 않는다
- 클라이언트: `YProvider` 옵션 `params` 에 비동기 함수를 주면 **연결·재연결마다 다시 불린다**(`dist/provider/index.js` `YProvider.connect`·`_reconnectWS` → `#resolveParams`). `params: async () => ({ t: await 티켓받기(docId) })` 로 끝난다. 티켓 요청이 Access 302 로 실패하면 지금 API 호출과 같은 경로로 `signedOut` 을 알 수 있다
- 파일: `worker/wsTicket.ts`(+test) 신규, `worker/index.ts` 라우트 한 줄, `worker/docSocket.ts` 4번 분기, `.dev.vars`(커밋 안 됨)

### 4.5 Origin 검사

브라우저는 WebSocket 업그레이드에 `Origin` 을 반드시 싣고, 다른 사이트의 페이지도 `wss://rawdoc.app/…` 로 연결을 열 수 있다(쿠키가 실리면 남의 문서를 읽고 쓴다). 쿠키 인증(1안)에서는 Origin 검사가 유일한 방어라 반드시 둔다

- 허용: `Origin` 이 `new URL(SITE_URL).origin`(`src/lib/siteMeta.ts`, 지금 `https://rawdoc.app`)과 같다
- 로컬 개발 우회: `auth.ts` 의 `DEV_AUTH_EMAIL` 우회와 **같은 조건**(`DEV_AUTH_EMAIL` 이 `@example.com` 으로 끝나고 `ACCESS_AUD` 가 비었다)일 때만, 호스트가 `localhost`·`127.0.0.1` 인 `http:` Origin 을 포트와 상관없이 허용한다. `request.url` 의 출처와 비교하지 않는 이유: `auth.ts` 주석대로 `wrangler dev` 는 커스텀 도메인 routes 가 있으면 호스트를 바꾼다
- `Origin` 이 없으면 거절한다(브라우저가 아닌 스크립트는 `/v1` 을 쓴다)
- 제품명·도메인 문자열을 새로 적지 않는다 — `SITE_URL` 에서 읽는다

## 5. DocRoom DO — hibernation 과 깨어남 비용 (F-301 9.4·12.1 U2 결론)

### 5.1 hibernation 을 켜는 법 — 소스로 확정

- **`partyserver` 의 `Server` 에 정적 속성 `options = { hibernate: true }`** 를 둔다. 기본값은 `{ hibernate: false }` 이고 `YServer` 는 이 값을 정하지 않는다(`partyserver` `dist/index.js` `resolveServerOptions` 가 프로토타입 사슬에서 처음 만나는 `hibernate` 를 쓴다. README "Hibernation" 절도 같다)
- 켜면 `HibernatingConnectionManager` 가 `ctx.acceptWebSocket(ws, tags)` 로 받고, 연결별 상태는 `serializeAttachment` 에 싣고, 이벤트는 DO 의 `webSocketMessage`·`webSocketClose`·`webSocketError` 로 온다. 끄면 `ws.accept()` + `addEventListener` 라 DO 를 메모리에 붙잡는다 — F-301 9.3 이 금지한 쪽
- `partyserver` README: 서버 클래스에 `webSocketMessage`·`webSocketClose`·`webSocketError`·`alarm` 을 **직접 구현하지 않는다**. 라이브러리가 그 자리에서 생명주기 메서드를 부른다

### 5.2 깨어날 때마다 `onLoad` 를 다시 도는가 — **그렇다**

- 깨어나면 생성자가 다시 돌아 `#status = "zero"` 이고 `document = new WSSharedDoc()` 도 새로 만든다(클래스 필드). 다음 이벤트가 `#ensureInitialized()` → `blockConcurrencyWhile(onStart)` → `YServer.onStart` → `await this.onLoad()` 를 부른다. **깨어날 때마다 전체 상태를 다시 읽는다**
- 이것을 부르는 입구: 새 연결(`fetch`), `webSocketMessage`, `webSocketClose`, `webSocketError`, `alarm`. **부르지 않는 입구**: 우리가 정의한 RPC 메서드(`partyserver` `getServerByName` 주석: "User-defined RPC methods don't otherwise pass through `Server.fetch()`"), 그리고 런타임이 처리하는 자동 응답(10.2)
- `onStart` 가 끝나면 `YServer` 는 **붙어 있는 모든 연결에 sync step 1 을 보낸다** → 연결마다 클라이언트 답장 1통. 깨어남 한 번 = 연결 수만큼의 수신 메시지
- 연결이 닫히는 것만으로도(`webSocketClose`) 깨어나 전체를 다시 읽고 awareness 를 지운다. 피할 수 없고 받아들인다
- **깨어남 비용(실측 (b), node)**: 1MB 문서 압축본 5.7~5.9ms, 100행 쌓인 1MB 8.1ms, 100KB 압축본 1.1ms. 여기에 DO SQLite 읽기와 D1 한 줄 읽기(7장)가 더해진다. 6.3 의 압축 임계값은 이 값을 기준으로 정했다
- awareness 는 메모리에만 있어서 **깨어난 뒤에는 비어 있다**. 새로 붙은 사람은 다른 사람이 커서를 움직일 때까지 그 사람을 모른다 — F-307 이 다룬다(16장)

### 5.3 껍데기 `worker/docRoom.ts` 가 하는 일

규칙은 전부 `docRoomCore.ts` 에 두고, 이 파일은 `YServer` 생명주기를 core 로 잇는다

| 자리 | 하는 일 |
| --- | --- |
| 정적 `options` | `{ hibernate: true }` |
| 정적 `callbackOptions` | `{ debounceWait: FLUSH_DEBOUNCE_MS, debounceMaxWait: FLUSH_MAX_WAIT_MS }` (6.2) |
| 생성자 | `super` 뒤 `ctx.setWebSocketAutoResponse(new WebSocketRequestResponsePair(SOCKET_PING, SOCKET_PONG))` (10.2) |
| `onLoad()` | core 불러오기(7장). 결과 Doc 을 돌려주지 않고 `this.document` 에 직접 넣는다 — 돌려주면 `YServer.onStart` 가 `encodeStateAsUpdate` → `applyUpdate` 로 한 번 더 복사한다. **실패하면** 로그를 남기고, `stack` 을 `unavailable` 로 덮은 오류를 던진다 — `partyserver` `Server.fetch` 의 `catch` 가 `err.stack` 을 그대로 소켓에 보내기 때문이다(`specs/architecture.md` 6장 "오류 본문에 내부 정보 없음"). 던지면 `#status` 가 `zero` 로 돌아가 다음 이벤트가 다시 불러온다 |
| `onSave()` | core flush (6.2) |
| `onConnect(conn, ctx)` | `ctx.request` 헤더(4.1)로 연결 상태를 정하고 core 에 알린 뒤 `super.onConnect`. 헤더가 없으면 `4401` 로 닫는다. 자세한 순서는 7.2 |
| `onClose(…)` | `super.onClose`(awareness 정리) 뒤, 열린 연결이 하나도 안 남았으면 core flush 를 **곧바로** 기다린다 (6.2) |
| `onCustomMessage` | 아무것도 안 한다(기본 구현은 `console.warn`). 클라이언트 → 서버 커스텀 메시지는 F-304 에 없다 |
| `isReadOnly` | `false`. 보기 권한은 Worker 가 이미 거절한다 |
| RPC `revalidateConnections(email?)`, `purgeRoom()` | 9장 |

- 연결 상태(`connection.setState`)는 `{ userId: string; email: string; role: 'owner' | 'edit' }`. `y-partyserver` 가 같은 상태에 awareness id 목록 키 `__ypsAwarenessIds` 를 `setState(prev => ({ ...prev, … }))` 로 섞어 넣으므로 우리도 **앞 상태를 펼쳐 섞는다**. 상태는 첨부(attachment)로 hibernation 을 넘어 산다
- DO 이름 = 문서 id. `partyserver` 는 이름 기반 주소(`idFromName`/`getByName`)만 지원하고 `this.name` 을 `ctx.id.name` 에서 읽는다(`Server.fetch` 의 오류 문구)

## 6. DO SQLite 영속 (F-301 3.4 결론)

### 6.1 형식

```sql
-- worker/yStore.ts 가 없으면 만든다. 이름에 제품명 없음 (불변조건)
CREATE TABLE IF NOT EXISTS ydoc_updates (
  seq  INTEGER NOT NULL,
  part INTEGER NOT NULL,
  data BLOB    NOT NULL,
  PRIMARY KEY (seq, part)
);
CREATE TABLE IF NOT EXISTS ydoc_meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

- 한 `seq` = Yjs 업데이트 하나. 그 바이트가 `YSTORE_PART_BYTES`(**1,500,000**)를 넘으면 `part` 0,1,2… 로 쪼개 같은 `seq` 로 쓴다. 불러올 때 `seq`·`part` 순으로 이어 붙여 원래 바이트로 되돌린 뒤 적용한다
  - F-301 3.4 는 "압축 결과만 청크로" 였지만 **모든 쓰기를 쪼갤 수 있어야 한다** — 클라이언트 한 번의 붙여넣기가 2MB 를 넘으면 그 업데이트 하나가 행 상한(DO SQLite 문자열·BLOB 행 2MB, F-301 3.4 인용)을 넘는다
  - 1,500,000 을 고른 이유: 1MB 문서의 압축본이 1,003,059~1,029,512 B(실측 (b))라 한 행에 들어가고, 2MB 가 2,000,000 인지 2,097,152 인지와 상관없이 여유가 남는다
- `ydoc_meta` 키: `schema`(`'1'`), `d1_version`(DO 가 마지막으로 맞춘 D1 `version`, 7장), `base_seq`(압축본 또는 씨앗의 `seq`)
- 불러올 때는 행마다 `applyUpdate` 하되 **한 Yjs 트랜잭션 안에서** 한다. 모든 행을 `mergeUpdates` 로 합친 뒤 한 번에 넣지 않는다 — 실측 (b) 에서 합치는 쪽이 2~5배 느렸다
- DO 는 `ctx.storage.sql` 을 쓴다. SQL API 는 SQLite 백엔드 DO 에만 있어 **`new_sqlite_classes` 로 만든다**(12.1). F-301 12.1 U7 "무료 플랜에서 필수인가" 는 이 명세에서는 따질 필요가 없어졌다 — SQL 을 쓰는 한 SQLite 백엔드여야 한다. "SQL API 가 SQLite 백엔드 전용" 은 Cloudflare 문서 서술이고 이번에 다시 열어 보지 않았다. 틀렸다면 배포가 아니라 첫 연결에서 `sql` 호출이 실패해 드러난다(15.3 L4)

### 6.2 flush — 저장 한 번의 단위

**flush** = 지난 flush 뒤 `document` 에 들어온 업데이트(원인 무관, 서버가 넣은 흡수 포함)를 `mergeUpdates` 로 **한 `seq`** 에 추가 → 압축 조건이면 압축(6.3) → D1 스냅샷(8장) → 권한 주기 점검(9.2). 순서가 계약이다 — SQLite 가 먼저라 D1 쓰기가 실패해도 Yjs 원본은 남는다

| flush 가 일어나는 때 | 값 |
| --- | --- |
| 편집 뒤 조용해지면 | 마지막 업데이트 뒤 `FLUSH_DEBOUNCE_MS` = **5,000ms** |
| 편집이 계속되면 | 첫 미저장 업데이트 뒤 최대 `FLUSH_MAX_WAIT_MS` = **30,000ms** |
| 마지막 연결이 닫히면 | **곧바로** |
| D1 쓰기 실패 뒤 | 8.4 의 재시도 |
| 불러왔더니 D1 이 Yjs 보다 뒤처져 있으면 | 불러온 뒤 5,000ms 에 한 번 (7.2) |

- 앞 두 줄은 `y-partyserver` 의 `callbackOptions`(lodash `debounce`, `maxWait`)로 건다. `y-partyserver` 기본값 2,000/10,000ms 를 쓰지 않고 **SQLite 추가와 D1 스냅샷을 같은 박자 하나로** 묶는다 — 박자가 둘이면 타이머가 둘이고, DO 는 타이머가 걸려 있는 동안 잠들지 않는다(10장)
- "마지막 연결이 닫히면 곧바로" 는 `y-partyserver` 2.2.0 에 없다. README 는 "`onSave` is called … when the room is emptied" 라고 쓰지만 `dist/server/index.js` `onClose` 는 awareness 만 지운다. 걸린 타이머가 있는 채로 DO 가 내려가면 그 사이 편집은 클라이언트에만 남는데, 탭을 닫고 나간 경우에는 클라이언트도 없다
- flush 는 겹쳐 돌지 않는다. 도는 중에 또 불리면 끝난 뒤 한 번 더 돈다
- 5,000/30,000 을 고른 이유는 10.3
- **내구성**: DO 가 flush 전에 죽으면(배포·장애) 그 사이 편집은 DO 메모리에서 사라지지만 붙어 있던 클라이언트가 재연결 때 sync step 2 로 다시 보낸다(`YServer.onConnect` 가 sync step 1 을 먼저 보내고, 클라이언트는 서버에 없는 것을 전부 답장한다). 잃는 것은 "flush 전 + 클라이언트도 사라짐" 뿐이고, 그중 탭 닫기는 위 "곧바로" 가 막는다

### 6.3 압축 임계값 — 실측으로 정함 (F-301 3.4 의 200행·1MB 를 바꾼다)

**마지막 압축(또는 씨앗) 뒤 쌓인 `seq` 가 `COMPACT_ROWS` = 100 개 이상이거나, 쌓인 바이트 합이 `COMPACT_BYTES` = 524,288(512KiB) 이상이면** 그 flush 에서 압축한다. 압축 = `encodeStateAsUpdate(document)` 를 새 `seq` 하나로 쓰고 그 앞 행을 전부 지운 뒤 `base_seq` 를 바꾸는 것을 **한 트랜잭션**(`ctx.storage.transactionSync`)으로

근거(실측 (a)(b)):

- 한 flush 의 행은 보통 200 B 안팎이다(10타 묶음 중앙값 185~196 B). 100행이면 20KB 쯤이라 **바이트 조건은 큰 붙여넣기·지우기에서만 걸린다**
- 깨어남 비용은 행 수에 비례해 는다. 1MB 문서: 압축본 5.7ms → 100행 8.1ms → 200행 9.7ms → 500행 12.6ms. 100KB: 압축본 1.1ms → 200행 3.9ms → 1,000행 15.0ms. 100행이면 압축본보다 1MB 에서 +2.4ms 안쪽이다
- 임계값을 낮춰도 쓰기 행 수는 거의 늘지 않는다. 모든 행은 한 번 쓰이고 압축 때 한 번 지워지므로 추가 1행당 **약 2행**(쓰기 1 + 나중 지우기 1)이고, 압축본 행(`part` 수)만 임계값에 반비례한다
- 압축 CPU: 1MB 5.0~7.0ms, 100KB 0.7~1.65ms. 최대 박자(5초마다 flush)에서도 100행은 8분 20초에 한 번이다
- 512KiB: 깨어날 때 압축본 위에 다시 적용하는 업데이트를 반 MB 안쪽으로 묶는다. 적용 비용은 대략 1MB 에 5ms 대(실측 (b) 압축본 적용 값)

### 6.4 DO SQLite 쓰기 행 수

flush 한 번 = 추가 1행(쪼개지면 `part` 수) + `ydoc_meta` `d1_version` 1행(D1 을 썼을 때만) + 압축 몫(평균 약 1행). **flush 당 약 3행**. 편집 1시간당 최대 720번 flush(5초마다)면 2,160행, 계속 치면(30초마다) 360행. 무료 하루 100,000행(F-301 9.3) 기준 최악 박자로도 문서-시간 46시간

## 7. 씨앗 심기와 외부 쓰기 흡수

### 7.1 불러오기 (`onLoad`, 깨어날 때마다)

`blockConcurrencyWhile` 안이라 이게 끝나기 전에는 어떤 연결도 받지 않는다(`partyserver` `Server.fetch` 는 `#ensureInitialized` 뒤에 `accept` 한다)

1. 표를 만든다(없으면). `ydoc_updates` 를 읽어 `document` 에 적용한다(6.1)
2. D1 에서 한 줄 읽는다: `SELECT title, content, line_ending, version FROM docs WHERE id = ?`(id = `this.name`)
3. 그 줄이 없으면 **사라진 방**이다: DO 저장소를 비우고(9.4 와 같은 비우기) 씨앗을 심지 않는다. 이후 연결은 `4404` `deleted` 로 닫는다(Worker 검사와 DO 사이에 지워진 경우)
4. `ydoc_updates` 가 비었으면 **씨앗 심기**: 한 트랜잭션에서 `content` 에 `toEditorText(D1 content)`(`src/lib/lineEnding.ts` — `\r\n`·`\r` → `\n`), `title` 에 D1 `title` 을 넣는다. 그 상태를 **곧바로** 첫 `seq` 로 쓰고 `base_seq`·`d1_version` 을 적는다. D1 에는 쓰지 않는다
5. 비어 있지 않고 `d1_version` 이 D1 `version` 과 같으면: 아무것도 넣지 않는다
6. 다르면 **외부 쓰기 흡수**(7.2)

- 4번에서 씨앗을 flush 박자에 맡기지 않고 **곧바로** 쓰는 이유: 씨앗을 받은 클라이언트가 있는 채로 DO 가 flush 전에 내려가면, 다음 깨어남이 다른 clientID 로 씨앗을 다시 심고, 첫 씨앗을 가진 클라이언트가 그것을 되돌려 보내 **본문이 두 벌이 된다**(F-303 실측 M5 대조군과 같은 현상)
- 씨앗은 서버 Doc 의 clientID 로 들어간다. 깨어날 때마다 서버 Doc 의 clientID 는 새로 정해지지만, 서버가 스스로 만드는 구조는 씨앗과 흡수(7.2)뿐이다
- 불러온 뒤 core 는 메모리에 **기준점** `base = { content: toEditorText(D1 content), title: D1 title, version: D1 version, lineEnding: D1 line_ending }` 을 둔다. 기준점은 "D1 이 지금 무엇을 들고 있는가" 이고 8장 스냅샷과 7.3 흡수가 쓴다. 5번 경우에 `document` 본문·제목이 기준점과 다르면(앞서 D1 쓰기가 실패했거나 크기 초과였던 경우) 5,000ms 뒤 flush 를 한 번 건다(6.2)
- 제목이 `MAX_TITLE_CHARS`(500)를 넘는 경우는 D1 에 없다(`isValidTitle`). 씨앗은 그대로 넣는다

### 7.2 외부 쓰기 흡수 — F-301 3.3 "D1 → `Y.Doc` 은 한 번뿐" 의 예외

**왜 필요한가.** F-301 8.1 은 "한 번도 WebSocket 에 연결하지 못한 세션은 폴백 PUT" 을 남기고, F-308 전까지 `/v1` PUT 도 D1 을 직접 쓴다. DO 가 이미 상태를 가진 문서에 그런 쓰기가 들어온 뒤 다음 연결이 오면, 흡수가 없으면 DO 는 낡은 Yjs 를 내보내고 다음 flush 가 D1 을 덮어 **그 쓰기가 조용히 사라진다.** F-304 배포 뒤 F-305 까지는 모든 저장이 PUT 이므로, 누구든 한 번 `/ws` 로 연결한 문서(15.4 S1 의 확인 연결 포함)는 이 경로를 반드시 탄다

흡수가 일어나는 곳과 판정:

| 곳 | 외부 쓰기가 있었다는 신호 | 기준점(base) |
| --- | --- | --- |
| 불러오기(7.1 6번) | `d1_version` ≠ D1 `version` | **모른다** — 현재 `document` 를 기준으로 본다 |
| 새 연결(`onConnect`) | 헤더 `X-WS-Doc-Version` ≠ `base.version` | 메모리의 `base` |
| flush 의 조건부 쓰기 실패(8.2) | `UPDATE … WHERE version = base.version` 이 0행 | 메모리의 `base` |

- 새 연결 쪽이 필요한 이유: 연결이 다 나가도 DO 는 곧바로 잠들지 않고 메모리에 남는다. 그 사이 PUT 이 D1 을 바꾸고 새 연결이 오면 `onLoad` 는 다시 돌지 않는다(5.2). Worker 가 이미 읽은 `version`(4.1 5번)을 헤더로 넘기므로 **같으면 D1 을 다시 읽지 않는다**
- 흡수 = D1 한 줄을 다시 읽고(`version` 이 다르다고 나온 경우만) 7.3 규칙으로 `document` 에 바꾸기를 얹은 뒤 `base` 를 그 D1 값으로 옮긴다. 불러오기 중이면 그 바꾸기를 곧바로 한 `seq` 로 쓰고 `d1_version` 을 적는다(7.1 4번과 같은 이유). 그 밖에서는 보통 업데이트처럼 흘러 연결된 클라이언트에 퍼지고 다음 flush 가 쓴다
- 새 연결 쪽은 흡수가 끝난 **뒤에** `super.onConnect`(sync step 1)를 부른다 — 새 클라이언트가 처음부터 흡수된 본문을 받는다
- 흡수 트랜잭션의 origin 은 core 안의 객체 상수 하나다. 클라이언트와 공유하지 않는다
- **알려진 손실(받아들인다)**: 불러오기 쪽은 기준점을 몰라 "현재 `document` = 기준" 으로 보고 D1 쪽 값으로 바꾼다. DO 에 D1 로 못 나간 편집(앞선 D1 쓰기 실패·크기 초과)이 있었고 **그 사이** 누군가 D1 을 외부에서 썼다면, 그 두 편집이 겹치는 범위에서 DO 쪽 편집이 D1 값으로 바뀐다. D1 쓰기가 실패한 채 DO 가 잠드는 경우와 외부 쓰기가 겹쳐야 생긴다

### 7.3 바꾸기를 얹는 규칙 — `worker/textRebase.ts`

```ts
export type TextEdit = { from: number; to: number; insert: string }
export function diffText(a: string, b: string): TextEdit | null
export function rebaseExternal(base: string, external: string, current: string): TextEdit | null | 'conflict'
```

- `diffText`: 앞뒤 공통 부분을 잘라 가운데만 바꾸는 편집 하나(F-301 7장 2번 "글자 단위 최소 diff 를 요구하지 않는다" 와 같은 수준). 같으면 `null`. **UTF-16 서로게이트 쌍을 가르지 않는다** — 경계가 쌍 가운데에 떨어지면 쌍 밖으로 넓힌다. Yjs 는 문자열을 UTF-8 로 인코딩하므로 홀로 남은 서로게이트는 `U+FFFD` 로 깨진다. F-308 이 같은 함수를 쓴다
- `rebaseExternal`: 외부 편집 E = `diffText(base, external)`, 내부 편집 I = `diffText(base, current)`
  - E 가 `null` → `null`
  - I 가 `null`(DO 쪽 변화 없음) → E 그대로
  - E 가 I 보다 앞(`E.to <= I.from`) → E 그대로. 둘 다 같은 자리 삽입이면 이 경우로 친다 — 외부 삽입이 앞에 온다
  - E 가 I 보다 뒤(`E.from >= I.to`) → E 를 `I.insert.length - (I.to - I.from)` 만큼 민다
  - 겹침 → `'conflict'`
- `'conflict'` 면 **DO 쪽이 이긴다**: 외부 편집을 얹지 않고 `base` 만 D1 값으로 옮긴다 → 다음 스냅샷이 D1 을 DO 본문으로 덮는다. `console.warn` 에 문서 id 를 남긴다. 다른 안은 18장 Q4
  - 잃는 것: 폴백 PUT 사용자의 그 편집. 그 사용자는 다음 저장에서 `baseVersion` 이 낡아 `409` → 충돌 사본(F-207)을 받으므로 **다음에 한 번이라도 저장하면** 본문이 사본으로 남는다
- `document` 에 얹을 때는 `content` 에 `delete(from, to - from)` + `insert(from, insert)` 를 한 트랜잭션으로. 제목(`title`)도 같은 규칙을 따로 적용한다
- 1MB 에서 차이 찾기 3.5ms(실측 (c))

## 8. D1 파생 스냅샷·`version`·크기 초과 (F-301 3.5 결론)

### 8.1 쓰는 값

- `content` = `fromEditorText(document 의 content, base.lineEnding)` — CRLF 문서는 CRLF 로 되돌린다. **원문 바이트 보존이 지금 저장 경로(`getText(lineEnding)`)와 같다.** 섞인 줄바꿈 문서가 한 번 쓰이면 한 가지로 통일되는 것도 지금 저장과 같다(F-302 3.5)
- `title` = `document` 의 `title`, 500자(`MAX_TITLE_CHARS`)를 넘으면 앞 500자
- `version` = `base.version + 1`, `updated_at` = 지금 ms
- `line_ending`·`owner_id`·`folder_id`·`pinned_at` 은 건드리지 않는다

### 8.2 쓰기 규칙

1. `document` 의 본문(LF)·제목이 `base.content`·`base.title` 과 같으면 **쓰지 않는다**(Yjs 에는 변화가 있어도 글자가 같은 경우, 흡수 직후 등)
2. 8.1 의 `content` 를 UTF-8 로 잰 값이 `MAX_CONTENT_BYTES`(1,000,000, `worker/validate.ts` `isContentTooLarge` 와 같은 판정)를 넘으면 **쓰지 않는다** → 8.3
3. `UPDATE docs SET title = ?, content = ?, version = ?, updated_at = ? WHERE id = ? AND version = ?`(마지막 값 = `base.version`). `owner_id` 조건은 두지 않는다 — DO 는 누구 대신 쓰는지 모른다
4. 1행 바뀜 → `base` 를 방금 쓴 값으로, `d1_version` 메타를 새 `version` 으로
5. 0행 → D1 한 줄을 다시 읽는다. 줄이 없으면 9.4 의 사라진 방 처리. 있으면 7.2 흡수 후 `base.version` 기준으로 3번을 **한 번만** 다시 한다. 또 0행이면 8.4 재시도

- **`version` 은 단조 증가한다.** DO 는 항상 "읽은 값 + 1" 을 "읽은 값일 때만" 쓰고, `PUT /api/docs/:id` 도 같은 조건부 쓰기다(`worker/docs.ts` `handleUpdateDoc`). 둘이 섞여도 값이 내려가거나 같은 값이 두 번 나오지 않는다
- **F-304 단계에서 DO 와 PUT 이 같은 문서를 동시에 쓰는 일은 없다.** 앱은 `/ws` 에 붙지 않는다. 예외는 사람이 콘솔로 연 확인 연결(15.4 S1)인데, 그 연결로 편집하지 않으면 1번에서 멈춰 D1 에 쓰지 않는다. F-305 이후 폴백·`/v1` 과 섞이는 경우는 7.2·3~5번이 받는다
- `PUT /api/docs/:id` 의 409 판정은 그대로 둔다(F-301 3.5)

### 8.3 크기 초과 경고

- 2번에서 멈추면 방 상태 `tooLarge` 를 켠다. **꺼져 있다가 켜질 때만** 연결 전원에 `{"type":"too-large","limit":1000000,"bytes":N}` 를 보낸다(`broadcastCustomMessage` — `__YPS:` 앞붙이는 `y-partyserver` 가 한다). 켜진 채 다시 넘으면 보내지 않는다
- 켜져 있는 동안 새로 붙는 연결에는 `onConnect` 에서 그 연결에만 같은 메시지를 보낸다
- 줄어서 3번이 성공하면 끄고 `{"type":"size-ok"}` 를 전원에 보낸다
- 넘은 동안 D1 은 마지막으로 쓴 값에 머문다 — 공유 링크·`.md` 내보내기·`/v1` 읽기가 그 값을 본다. 편집은 계속되고 Yjs 원본은 DO 에 남는다(F-301 3.5 결정 그대로). 제목도 같이 멈춘다(18장 Q6)
- 클라이언트 알림 문구는 F-301 3.5 `문서가 1MB 를 넘어 서버에 저장되지 않습니다. 내용을 줄이거나 문서를 나눠 주세요` — F-305 가 띄운다
- **확인 못 함**: 1MB 가까운 문서의 첫 동기화 메시지가 Cloudflare 의 WebSocket 메시지 크기 상한 안에 드는지. 1MB 텍스트의 압축본이 1,003,059~1,029,512 B 라 상한이 1MiB(1,048,576)라면 경계에 붙는다. 로컬은 15.3 L11 로 재고, 배포본 상한은 F-305 에서 실제 클라이언트로 잰다

### 8.4 실패와 재시도

- D1 호출이 던지거나 5번에서 또 0행이면 `SNAPSHOT_RETRY_MS` = **5,000ms** 뒤 스냅샷만 다시 한다. 연속 `SNAPSHOT_RETRY_MAX` = **3번**까지. 넘으면 멈추고 `console.error`. 기준점이 그대로라 다음 편집의 flush 가 다시 쓴다. 성공하면 횟수를 0 으로
- 재시도 타이머가 걸린 동안은 DO 가 잠들지 않는다. 최대 15초

### 8.5 D1 쓰기 행 수

스냅샷 한 번 = `docs` 1행 + `docs_owner_updated` 인덱스 갱신(`updated_at` 이 바뀐다, `migrations/0002_docs.sql`). D1 이 인덱스 갱신을 행 몇 개로 세는지는 확인하지 않았다 — 보수적으로 **3행**으로 잡는다. 편집 1시간당 최대 720번(5초마다) = 2,160행, 계속 치면 120번 = 360행. 무료 하루 100,000행(F-301 9.3). 지금 F-213 잠금 연장이 **편집 창 하나당** 시간당 약 180행(F-213 2.5)을 쓰고 있어 비교 대상이다 — 스냅샷은 창 수와 무관하고 편집이 있을 때만 쓴다

## 9. 권한 회수와 문서 삭제 (F-301 4.5 결론)

### 9.1 무엇을 누가 알리나

| 일 | 처리 | 지연 |
| --- | --- | --- |
| 문서 초대 삭제 `DELETE /api/docs/:id/grants/:email` | `grants.ts` 가 응답을 만든 뒤 `notifyRevalidate(env, ctx, docId, email)` | 즉시 |
| 문서 초대를 `view` 로 `PUT /api/docs/:id/grants/:email` | 같음. `edit` 로 올리는 PUT 은 알리지 않는다 | 즉시 |
| 문서 삭제 `DELETE /api/docs/:id` | `docs.ts` 가 `notifyPurge(env, ctx, docId)` | 즉시 |
| 폴더 초대 삭제·낮추기, 문서·폴더 이동(상속 권한이 바뀜), 폴더째 삭제 | **알리지 않는다.** 9.2 주기 점검과 7.1 3번·8.2 5번이 잡는다 | 편집이 있으면 최대 약 90초 (18장 Q2) |

### 9.2 주기 점검 — flush 에 얹는다

- flush 가 돌 때 마지막 점검에서 `REVALIDATE_INTERVAL_MS` = **60,000ms** 이상 지났으면 연결마다 권한을 다시 본다(9.3 `revalidateConnections` 와 같은 판정, 이메일 거르지 않음). 깨어난 뒤 첫 flush 는 늘 점검한다
- **점검만을 위한 타이머를 두지 않는다.** flush 는 누군가 편집할 때만 돈다 — 회수당한 사람이든 남이든 편집하면 30초(flush 최대 대기) + 60초 안에 닫힌다. 아무도 편집하지 않으면 새로 흘러가는 내용이 없어 연결이 남아 있어도 드러나는 것이 없다
- 폴더 초대를 즉시 알리지 않는 이유: 폴더 아래 문서가 몇 개든 문서마다 DO 를 불러야 하고(연결이 없어도 DO 인스턴스가 만들어진다), 어느 DO 에 연결이 있는지 Worker 가 알 방법이 지금은 없다

### 9.3 `revalidateConnections(email?)` 와 알림 도우미

```ts
// worker/docRoom.ts — DocRoom 의 RPC (Worker 가 getByName(docId) 스텁으로 부른다)
revalidateConnections(email?: string): Promise<void>
purgeRoom(): Promise<void>

// worker/docRoomRpc.ts
export function notifyRevalidate(env: Env, ctx: ExecutionContext | undefined, docId: string, email: string): Promise<void>
export function notifyPurge(env: Env, ctx: ExecutionContext | undefined, docId: string): Promise<void>
```

- `revalidateConnections`: D1 에서 `SELECT id, owner_id, folder_id FROM docs WHERE id = ?` 한 번. 없으면 9.4 사라진 방. 있으면 열린 연결마다(`email` 이 주어지면 그 이메일만) 연결 상태의 `{ userId, email }` 로 `resolveDocAccess`(`worker/access.ts`) → 결과가 없거나 `edit` 미만이면 `4403` `revoked` 로 닫는다
- **RPC 는 `onLoad` 를 부르지 않는다**(5.2). 연결 목록은 `ctx.getWebSockets()` 에서 오므로 초기화 없이 읽힌다. 연결이 없는 문서라면 DO 인스턴스가 생겼다 사라질 뿐 저장소에 아무것도 쓰지 않는다
- 서버가 닫으면 클라이언트가 닫기 프레임을 돌려보내고 그 `webSocketClose` 가 DO 를 깨워 한 번 불러온다(5.2) — 회수 한 번의 비용으로 받아들인다
- 도우미 규칙: `env.DOC_ROOM` 이 없으면(기존 단위 테스트의 가짜 `env`) 아무것도 안 하고 끝난다. `ctx.waitUntil` 이 함수면 거기에 맡기고, 아니면(`{} as ExecutionContext`) 기다린다. RPC 가 던지면 `console.error` 만 찍고 삼킨다 — **원래 응답(204·200)은 알림 성공과 무관하게 그대로 나간다.** `apiTokens.ts` 의 `if (ctx) ctx.waitUntil(update) else await update` 와 같은 모양
- `grants.ts` 의 export 래퍼는 지금 `_c` 로 `ctx` 를 버린다. 문서 쪽 두 래퍼(`handlePutDocGrant`·`handleDeleteDocGrant`)가 `ctx` 를 넘기게 고친다

### 9.4 문서 삭제 — `purgeRoom()` 과 사라진 방

- `purgeRoom`: 열린 연결 전부를 `4404` `deleted` 로 닫고 → `ctx.storage.deleteAll()` → `ctx.abort('purged')` 로 메모리의 `document`·상태를 버린다. `abort` 가 없으면 메모리에 남은 인스턴스가 같은 id 로 다시 만든 문서(F-207 outbox 의 `createDoc` 는 같은 id 로 재시도한다)에 옛 본문을 내줄 수 있다
- **확인 못 함**: `ctx.abort()` 가 RPC 를 부른 쪽에 어떤 오류로 돌아가는지. 도우미가 삼키므로 결과는 같다. 15.3 L12 에서 본다
- 불러오기(7.1 3번)·스냅샷(8.2 5번)·점검(9.3)에서 D1 줄이 없다고 나오면 같은 처리를 한다(**사라진 방**) — 연결 `4404` `deleted`, 저장소 비우기, 이후 flush 는 아무것도 안 한다
- 폴더째 삭제(`folders.ts` 의 `DELETE FROM docs WHERE … folder_id IN (…)`)는 알리지 않는다(9.1). 연결이 있는 문서는 위 경로로 닫히고, 연결이 없는 문서의 DO 저장소는 **남는다**. 문서당 크기는 그 문서의 Yjs 상태(1MB 문서 약 1MB)이고 계정 전체 무료 5GB(F-301 9.3) — 지금 규모에서 문제 되지 않는다고 보고 18장 Q5 에 둔다

## 10. 쿼터 — DO 를 깨우지 않는 규칙

### 10.1 기준 수치 (F-301 9.3 표에서 계산)

- Duration 무료 하루 13,000 GB-s ÷ DO 1개 0.125 GB = **DO 가 깨어 있는 시간 합계 하루 104,000초(28.9시간)**. 문서 하나를 한 시간 내내 편집하면 450 GB-s(3.5%)
- Requests 무료 하루 100,000건, 수신 WebSocket 메시지 20통 = 1건. 한 사람이 초당 5타로 1시간 치면 18,000통 = 900건
- 이 계산은 공식 수치에 대입한 것이고 대시보드로 확인한 값이 아니다 — 15.4 S5 와 F-301 9.3 O1~O4

### 10.2 규칙

| # | 규칙 | 값 · 근거 |
| --- | --- | --- |
| R1 | hibernation 켬 | `static options = { hibernate: true }` (5.1) |
| R2 | ping 은 DO 를 깨우지 않고 런타임이 답한다 | 생성자에서 `setWebSocketAutoResponse(new WebSocketRequestResponsePair('ping', 'pong'))`. 들어온 메시지가 요청 문자열과 정확히 같을 때만 자동 응답한다(Cloudflare 문서 서술 — 이번에 다시 열어 보지 않았다. 로컬 L6 이 확인한다). `YProvider` 는 문자열 메시지 중 `__YPS:` 로 시작하지 않는 것을 버리므로 `pong` 이 클라이언트 동작에 끼지 않는다(`dist/provider/index.js` `message` 처리기). **`YProvider` 는 ping 을 보내지 않는다**(소스에 없다) — 보낼지·간격은 15.4 S4 결과로 F-305 가 정한다 |
| R3 | 저장 박자는 하나 | SQLite 추가와 D1 스냅샷을 5,000ms / 30,000ms 한 박자로 (6.2) |
| R4 | 방이 비면 곧바로 저장 | 마지막 연결이 닫히면 flush 를 기다렸다 끝낸다 — 타이머를 남기지 않는다 (6.2) |
| R5 | 상시 타이머 없음 | `setInterval` 없음. 서버 awareness 점검 타이머는 `y-partyserver` `WSSharedDoc` 생성자가 이미 끈다(`clearInterval(this.awareness._checkInterval)`). 남는 타이머는 flush 디바운스·D1 재시도(최대 15초)·불러온 뒤 한 번(7.1)뿐 |
| R6 | 권한 점검은 flush 에 얹는다 | 따로 깨우지 않는다 (9.2) |
| R7 | RPC 는 불러오기를 하지 않는다 | `revalidateConnections`·`purgeRoom` 은 `onLoad` 없이 끝난다 (5.2) |
| R8 | 거절은 DO 에 닿지 않는다 | Worker 가 닫는다 (4.2) |
| R9 | 연결마다 D1 본문을 읽지 않는다 | Worker 는 `version` 까지만 읽고, DO 는 그 값이 다를 때만 본문을 읽는다 (4.1, 7.2) |

- 편집이 끝난 뒤 DO 가 깨어 있는 꼬리 = flush 디바운스 5초 + 런타임이 잠들기 전 기다리는 시간. 뒤쪽은 Cloudflare 문서에 약 10초로 적혀 있다고 알고 있으나 **이번에 확인하지 않았다.** 합쳐 15초면 한 번에 1.9 GB-s
- 클라이언트가 할 일(awareness 를 얼마나 자주 보낼지, ping 간격)은 11.3

### 10.3 5,000 / 30,000ms 를 고른 이유 (F-301 3.5 값을 쿼터 관점에서 다시 봄)

| 디바운스 | D1 최대 쓰기(편집 1시간) | 편집 뒤 꼬리(Duration) | D1 이 낡는 최대 시간 |
| --- | --- | --- | --- |
| 2,000ms(`y-partyserver` 기본) | 1,800번 | 짧다 | 10초(최대 대기 10,000ms) |
| **5,000ms** | **720번** | 5초 + 런타임 | **30초** |
| 30,000ms | 120번 | 30초 + 런타임 — 편집 묶음 하나마다 +25초 × 0.125 GB = +3.1 GB-s | 30초 이상 |

- 5,000ms 가 두 한도를 동시에 여유 있게 둔다: D1 최악 2,160행/시간(8.5)이면 하루 46 문서-시간, Duration 꼬리는 묶음당 수 GB-s
- 30초로 늘리면 D1 쓰기는 줄지만 묶음마다 DO 가 25초 더 깨어 있고, 공유 링크·내보내기가 최대 30초 넘게 낡는다(F-301 3.5 "최대 5초 낡을 수 있다" 는 디바운스 5초 기준이고, 편집이 계속되면 최대 대기 30초까지 낡는다 — 16장에서 문구를 고친다)

## 11. 클라이언트에 넘기는 계약 (F-305~F-307)

### 11.1 `src/lib/docRoomProtocol.ts`

```ts
export const Y_CONTENT_NAME = 'content'   // src/editor/yBinding.ts Y_TEXT_NAME 과 같아야 한다 (A25)
export const Y_TITLE_NAME = 'title'
export const DOC_SOCKET_PREFIX = '/ws/doc/'   // + 문서 id
export const SOCKET_PING = 'ping'
export const SOCKET_PONG = 'pong'
export const SOCKET_CLOSE = {
  unauthenticated: 4401,
  forbidden: 4403,
  notFound: 4404,
  unavailable: 1013,
} as const
export type SocketCloseReason = 'unauthenticated' | 'forbidden' | 'revoked' | 'not_found' | 'deleted' | 'unavailable'
export type DocRoomMessage =
  | { type: 'too-large'; limit: number; bytes: number }
  | { type: 'size-ok' }
export function encodeDocRoomMessage(message: DocRoomMessage): string   // JSON 한 줄
export function parseDocRoomMessage(text: string): DocRoomMessage | null // 모양이 다르면 null
```

- 이름은 전부 **저장소 식별자에 준한다**(DO SQLite 안 `Y.Doc` 루트 이름) — 제품명과 무관하게 고정
- `too-large`·`size-ok` 는 `__YPS:` 뒤 문자열로 온다. `YProvider` 는 `custom-message` 이벤트로 앞붙이를 뗀 문자열을 준다(`dist/provider/index.js`)

### 11.2 프로토콜 — 표준 `y-partyserver` 그대로

- 이진 메시지: `y-protocols` sync(step1·step2·update) + awareness. 서버는 받은 업데이트를 **보낸 사람을 포함한** 전원에게 되돌려 보낸다(`YServer.onStart` 의 `document.on('update')` 가 `getConnections()` 전부에 보낸다) — 보낸 쪽에는 이미 있는 구조라 Yjs 가 무시한다. 송신 메시지는 과금이 없다(F-301 9.3)
- 문자열: `__YPS:` + `DocRoomMessage` JSON, 그리고 `ping`/`pong`
- 연결 순서: 서버 `onConnect` 가 sync step 1 을 먼저 보내고, 클라이언트는 열리자마자 자기 sync step 1 을 보낸다. **클라이언트는 서버 step 1 에 대한 답장(step 2)으로 서버에 없는 자기 구조를 전부 보낸다** — 서버 상태(step 2)를 받기 전에

### 11.3 F-305~F-307 이 지켜야 하는 것

1. **`YProvider` 에 붙이는 `Y.Doc` 에는 브라우저가 심은 씨앗이 한 글자도 없어야 한다.** 11.2 마지막 줄 때문에, 씨앗이 든 Doc 을 붙이면 서버 상태를 받기 전에 씨앗이 올라가 **본문이 두 벌**이 된다. 서버는 이를 알아챌 수 없다(씨앗도 보통 삽입이다)
   - F-303 8.3 입양(`adopt`)은 이 순서를 막지 못한다 — 입양은 "상대 상태를 먼저 받고 내 것을 나중에 보낸다" 는 순서에 기대는데, `y-protocols` sync 는 그 순서를 보장하지 않는다. **입양은 F-303 대로 개발·테스트 연결 전용**으로 남는다
   - 그러므로 F-305 는 연결할 서버 문서의 편집기 `Y.Doc` 을 **비운 채** 만들고(F-302 3.4 "provider 에 붙는 `Y.Doc` 은 브라우저가 심지 않는다", F-301 3.3 "첫 동기화까지 읽기 전용") 공유 Doc 도 빈 채로 시작해야 한다. 지금 F-303 4.1 "공유 Doc 시작 상태 = 편집기 Doc 전체 상태(씨앗 포함)" 는 편집기 Doc 이 비어 있으면 그대로 성립한다
   - F-306 이 브라우저에 영속하는 Doc 은 서버에서 받은 구조 + 내 편집이라 이 규칙에 걸리지 않는다
2. `YLinkPort`(F-303 8.1)로는 `YProvider` 에 바로 붙일 수 없다 — `YProvider` 는 `Y.Doc` 을 받고 그 Doc 의 `update` 를 스스로 듣는다. F-303 8.1 이 예고한 대로 **공유 Doc 을 넘기도록 포트를 넓히는 쪽**을 권한다. 공유 Doc 에 붙이면 `YProvider` 는 origin 이 자기가 아닌 업데이트(편집기에서 온 `RELAY_FROM_EDITOR`)를 보내고, 자기가 받은 것은 origin 자신으로 넣어 되돌려 보내지 않으며, 게이트는 F-303 그대로 선다
3. 닫기 코드 4401·4403·4404 에서는 `disconnect()` 로 자동 재연결을 멈춘다(4.2)
4. `YProvider` 옵션: `prefix` 를 주면 URL 이 정확히 그 경로가 된다(`isPrefixedUrl` — 방 이름을 뒤에 붙이지 않는다). `prefix: DOC_SOCKET_PREFIX + docId`. 쿼리에 `_pk`(연결 id, `nanoid(10)`)가 붙고 서버는 그것을 연결 id 로 쓴다
5. `YProvider` 재연결 간격은 `min(2^n × 100ms, maxBackoffTime)`, 기본 상한 **2,500ms**, 지터 없음(소스). F-301 9.2 의 "1s → … 최대 30s, 지터" 를 원하면 F-305 가 감싸야 한다. README 는 옵션 이름을 `maxBackoffTimeout` 으로 적었지만 코드는 `maxBackoffTime` 이다 — F-301 12.1 U3 의 답
6. `YProvider` 는 브라우저에서 **같은 문서를 연 탭끼리 `BroadcastChannel` 로도 동기화**한다(`disableBc` 기본값 = `typeof window === "undefined"` → 브라우저에서는 켜짐, 채널 이름은 WebSocket URL). F-303 게이트를 지나지 않는 두 번째 입구라 F-305 가 끌지(`disableBc: true`) 정해야 한다
7. awareness: 서버는 awareness 메시지 한 통마다 DO 를 깨운다. `YProvider` 는 awareness 갱신 주기 타이머를 끈다(`clearInterval(awareness._checkInterval)`)라 커서가 멈추면 메시지가 없다. **F-307 은 커서 이동 awareness 를 조여 보내야 한다**(간격은 F-307 이 정한다). hibernation 뒤 서버 awareness 는 비어 있다(5.2)
8. `/v1` PUT 임시 규칙(F-301 7장, F-305): F-304 의 흡수(7.2)로 **DO 가 잠든 동안의** `/v1` 쓰기는 사라지지 않는다. 연결 중 겹치는 쓰기는 7.3 `'conflict'` 로 DO 가 이기므로 "활성 연결이면 423" 임시 규칙은 여전히 필요하다. 연결 수를 묻는 RPC 는 F-305 가 `DocRoom` 에 더한다(F-304 는 만들지 않는다)

- 바인딩 이름 `DOC_ROOM`·클래스 이름 `DocRoom`·태그 `v1` 은 계약이다. DO 클래스 이름은 저장소에 묶여 바꾸려면 `renamed_classes` 마이그레이션이 필요하다 — 제품명을 넣지 않는다
- `DocRoom` 은 `worker/index.ts` 에서 export 해야 한다(Wrangler 는 main 모듈의 export 에서 클래스를 찾는다). 그다음 `npm run cf:types` → `Env` 에 `DOC_ROOM: DurableObjectNamespace<…DocRoom>`

### 12.2 마이그레이션

- **D1 원격 마이그레이션: 없다.** `migrations/` 에 파일을 더하지 않는다. `CLAUDE.md` "Remote D1 migrations are not automated" 절차가 이번에는 필요 없다
- **DO 마이그레이션**(`wrangler.jsonc` `migrations`)은 `wrangler deploy` 가 적용한다 — Workers Builds 의 `npx wrangler deploy` 도 같다(`specs/architecture.md` 6장). 손으로 할 것 없음
- **되돌릴 때 주의 (확인 못 함)**: 배포 뒤 이 커밋을 `git revert` 만 하면 `DocRoom` export 와 `migrations` 가 함께 빠진다. Wrangler 는 이미 적용된 DO 클래스가 사라지는 배포를 `deleted_classes` 마이그레이션 없이 거절한다고 알고 있으나 이번에 확인하지 않았다. 되돌려야 하면 `run_worker_first` 의 `/ws/*` 와 `index.ts` 의 분기만 빼고 클래스·바인딩·마이그레이션은 남기는 쪽이 안전하다

### 12.3 의존성

- `npm install y-partyserver@^2.2.0 partyserver@^0.5.10`. `npm` 이 peer `@cloudflare/workers-types` 를 잠금 파일에 넣는다(실측 (e)). **`package.json` 에 적지 않고 `tsconfig` 에서 참조하지 않는다** — 워커 타입은 `worker-configuration.d.ts` 가 `declare module 'cloudflare:workers'` 로 준다. `partyserver` 의 `.d.ts` 는 `cloudflare:workers` 를 import 한다
- **(2026-09-23 구현 중 확인·사용자 결정)** 저장소에서는 `ERESOLVE` 로 실패한다 — `y-partyserver` 2.2.0 peer 는 `@cloudflare/workers-types` v4 만, `wrangler` 4.131.1 peerOptional 은 v5 만 받는다(실측 (e) 는 wrangler 없는 폴더라 안 드러났다). **`package.json` 에 `"overrides": { "@cloudflare/workers-types": "^5.20260911.1" }` 를 더해 푼다**(`.npmrc legacy-peer-deps` 는 저장소 전체 peer 검사를 꺼서 기각). 플래그 없는 `npm ci` 가 통과한다. `y-partyserver` 가 v5 를 받는 판을 내면 이 항목을 지운다
- 같이 들어오는 것: `y-protocols`, `lodash.debounce`, `nanoid` 5(저장소에 이미 있는 `nanoid` 3.3.18 과 별개로 중첩 설치), `lib0`(이미 있음). 앱 번들에는 들어가지 않는다(15.2 B3)
- 워커 번들 증가 예상: gzip 약 +30~60 KiB(실측 (d)). 지금 29.54 KiB. 무료 플랜 스크립트 크기 상한과는 거리가 멀다

### 12.4 배포해도 사용자에게 보이는 변화가 없어야 한다

- 앱 번들 무변화: `src/` 기존 파일을 고치지 않고, 새 `src/lib/docRoomProtocol.ts` 는 앱이 import 하지 않는다 → `npm run build` 결과 `dist/assets` 파일 이름(내용 해시)이 전부 같다(15.2 B3). 그러면 서비스 워커 precache 도 같다
- 서비스 워커(`vite.config.ts` `navigateFallbackDenylist`)에 `/ws/` 를 더하지 않는다: 서비스 워커는 WebSocket 연결을 가로채지 않고, `navigateFallback` 은 페이지 이동에만 걸린다. 더하면 `sw.js` 가 바뀌어 위 기준이 깨진다
- 워커 쪽 기존 경로는 그대로다. 바뀌는 것은 `/ws/*` 하나 — 지금은 정적 404 페이지, 배포 뒤에는 426·403·404 JSON 또는 WebSocket
- 체인지로그: 사용자에게 보이는 변화가 없다. F-304 만 올릴 때는 `CLAUDE.md` 배포 절대로 `--no-verify` 로 push 하거나, 사용자에게 보이는 다른 변경과 함께 올린다
- 올리기 전 `npm run verify:full`(`CLAUDE.md` 배포). 올리기 전후로 사용자에게 알린다

### 15.4 배포 후 사람 확인 (메인이 `specs/human-checks.md` 에 옮긴다. 번호는 메인이 매긴다)

**게이트**: S1 결과가 있어야 F-305 명세를 쓴다(인증 방식이 갈린다). S4·S5 결과가 있어야 F-305 를 `deploy` 로 올린다(F-305 가 ping 을 보낼지·hibernation 이 실제로 도는지)

확인용 콘솔 코드(rawdoc.app 에서 서버 문서를 연 탭의 개발자 도구 콘솔):

```js
const id = location.hash.split('/')[2] // 주소가 `#/d/{id}` 일 때 (`src/app/hashRoute.ts`)
const ws = new WebSocket(`wss://${location.host}/ws/doc/${id}`)
ws.onmessage = (e) => console.log('msg', typeof e.data === 'string' ? e.data : e.data.size ?? e.data.byteLength)
ws.onclose = (e) => console.log('close', e.code, e.reason, new Date().toLocaleTimeString())
```
