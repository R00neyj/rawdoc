## 2. 범위

### 한다

- 경로식 `[[폴더/문서]]`, 같은 제목이면 가까운 폴더, 끝 `.md` 떼기 — 편집기·보기·인쇄·공유 메뉴·지도·서버 묶음 수집·공개 묶음·공개 폴더가 **같은 함수**로
- `[[문서#헤딩]]`·`[[#헤딩]]` 으로 그 제목까지 스크롤 — 편집·원문·보기 모드, 공개 묶음·공개 폴더 화면
- 편집기 자동완성: 같은 제목이 여럿이면 폴더 경로를 보이고, 고른 문서로 풀리는 가장 짧은 형태를 넣는다
- 없는 경로식 링크를 누르면 맞는 폴더가 있을 때 그 안에 새 문서
- `GET /pub/docs/:token/set` 에 문서별 링크 표

### 하지 않는다

- 임베드 `![[…]]`, `#태그`, 블록 참조 이동(`#^id` 는 문서만 연다), 별칭 프론트매터 `aliases`, 제목을 바꿀 때 링크 고치기(F-131 Q26 그대로 미결)
- 헤딩을 해시 주소에 남기기(사용자 결정 2). 뒤로 가기는 문서로 돌아오고 제목 위치로는 돌아오지 않는다
- 인용·목록·콜아웃 **안의** 제목으로 이동 (7.1)
- 해시 공유 `#/s/…`(F-130)·초대 공유 보기(F-212 `SharedView`)·링크 하나짜리 공개 문서의 위키링크 — 지금처럼 `wikilink--plain` (11.1)
- 검색에서 위키링크 해석, 목차(F-144)의 단계 확대

## 3. 링크 모양 — `findWikiLinks`

### 3.1 계약

개요 3.1 의 모양 그대로다. `heading` 만 규칙을 더 좁혔다

```ts
// src/lib/wikiLink.ts (F-2018)
export type WikiLinkMatch = {
  from: number; to: number
  target: string          // 첫 '#' 앞, 앞뒤 공백 제거. [[#헤딩]] 이면 ''
  heading: string | null  // 마지막 '#' 뒤, 앞뒤 공백 제거. 없거나 비었거나 '^' 로 시작하면 null
  alias: string | null
  targetFrom: number; targetTo: number   // '|' 앞 원문 조각('#' 뒤 포함) — 지금과 같다
}
```

| 원문 | `target` | `heading` | 링크인가 |
| --- | --- | --- | --- |
| `[[회의록]]` | `회의록` | `null` | 예 |
| `[[회의록#결정]]` | `회의록` | `결정` | 예 |
| `[[회의록# 결정 ]]` | `회의록` | `결정` | 예 |
| `[[노트#상위#하위]]` | `노트` | `하위` | 예 — 옵시디언 하위 헤딩 사슬은 마지막 조각만 (개요 3.5) |
| `[[#결정]]` | `''` | `결정` | **예 (신규)** |
| `[[회의록#^abc123]]` | `회의록` | `null` | 예 — 블록 참조는 문서만 연다, 알림 없음 |
| `[[회의록#]]` | `회의록` | `null` | 예 |
| `[[#^abc]]`, `[[#]]`, `[[ # ]]` | `''` | `null` | **아니다** — `target === '' && heading === null` |
| `[[C# 정리]]` | `C` | `정리` | 예 — 지금도 대상은 `C` 다. 옵시디언 내보내기가 파일명의 `#` 을 `_` 로 바꾸는 이유(F-2016 Q7) |

- 정규식 `WIKILINK_RE`·`![[…]]` 제외·한 줄 안 규칙은 그대로다
- `target === ''` 을 받는 소비자 전부는 **다른 문서를 가리키지 않는 링크**로 보고 해석하지 않는다 — `extractWikiTargets`(지도, 9.1)는 아예 뽑지 않고, `collectWikiSet`·`buildWikiLinkTable`(서버, 10장)·`ShareMenu`(8.4)는 건너뛴다

### 3.2 보이는 글자 — 한 규칙

**별칭이 있으면 별칭, 없으면 `targetFrom`~`targetTo` 원문 조각의 앞뒤 공백을 뗀 것.** `[[회의록#결정]]` 은 `회의록#결정`, `[[#결정]]` 은 `#결정` 이다

- 편집기는 이미 이렇게 그린다(`wikiLinksOnLine` 의 `visibleFrom`·`visibleTo` 가 원문 조각 그대로). F-131 2장 표도 `[[회의록#결정]]` 의 보이는 글자를 `회의록#결정` 으로 적었다
- 지금 **보기 모드**(`wikiLinkTokens` 의 `alias ?? target`)와 **표 칸**(`cellInline.ts` 의 `alias ?? target`)은 `#` 뒤를 버려 `회의록` 만 보인다. `[[#결정]]` 은 그 규칙으로는 빈 글자가 되므로 두 곳을 위 규칙에 맞춘다. 영향: 보기 모드·인쇄·HTML 내보내기·`.txt` 내보내기(F-278, `toPlainText` 가 토큰 안 글자를 쓴다)에서 `[[문서#헤딩]]` 이 `문서#헤딩` 으로 보인다. 17장 Q1

### 4.2 폴더 사슬 — 해석 전부가 기대는 정의

문서의 자리를 "그 문서가 든 폴더부터 위로 올라가는 폴더 id 목록 + 최상위에 닿았는가" 로 본다

| 경우 | 사슬 | 최상위에 닿음 |
| --- | --- | --- |
| `folderId === null` | 빈 목록 | 예 |
| `folderId` 가 폴더 목록에 없음 (공유받은 문서 — 남의 폴더) | `[folderId]` 한 칸 | **아니다** — 개요 3.2 "최상위와 무관한 문서" |
| 폴더를 따라 올라가다 `parentId === null` | 지나온 폴더들 | 예 |
| 올라가다 부모가 목록에 없음 | 지나온 폴더들 | 예 |
| 올라가다 **순환에 든 폴더**를 만남 | 지나온 폴더들(그 폴더까지) | 예 — 순환에 든 폴더는 최상위에 있는 것으로 본다 |

- 폴더의 부모 판정은 **F-2017 3.3 "화면 부모" 표와 같다** — 없는 부모·순환에 든 폴더는 최상위, 순환으로 들어가는 사슬에 있지만 자신은 순환 밖인 폴더는 저장된 부모. 예: C→A, A↔B 면 C 안 문서의 사슬은 `[C, A]` 이고 최상위에 닿는다. 사이드바에 보이는 자리와 해석 결과가 어긋나지 않게 하려는 것이다. F-2017 의 `folderAncestors`(저장된 사슬, 권한용)와는 다르다. `folderTree.ts` 에 그 판정이 내보내져 있으면 import 하고(worker 도 `folderTree.ts` 를 import 한다), 없으면 같은 규칙을 이 파일에서 계산한다. **어느 쪽이든 멈추지 않는 일이 없어야 한다**
- 문서의 `folderId` 가 목록에 없는 경우와 폴더의 `parentId` 가 목록에 없는 경우를 다르게 다루는 이유: 앞의 것은 공유받은 문서(내 트리 밖)이고, 뒤의 것은 내 트리 안의 어긋난 데이터다. 뒤의 것은 사이드바가 보여 주는 자리를 따른다

### 4.3 후보 고르기 (개요 3.2 를 정확히)

`target` 을 앞뒤 공백 없이 받는다. 비었으면 `null`

1. **제목 전체 일치.** 제목(앞뒤 공백 제거)이 `target` 과 같은 문서들. 없으면 대소문자를 접어(4.5) 같은 문서들. 제목이 빈 문서는 후보가 아니다. 찾으면 4.4 로 하나 고른다
2. **경로식.** 1 에 후보가 없고 `target` 에 `/` 가 있으면: 맨 앞 `/` 들을 떼고 `/` 로 나눠 조각마다 앞뒤 공백을 뗀다. **빈 조각이 하나라도 있으면 이 단계는 없다**(`[[a//b]]`, `[[a/]]`). 마지막 조각이 제목, 앞 조각들이 폴더 경로다
   - 제목이 마지막 조각과 같은(정확 → 없으면 대소문자 접기) 문서 중, **그 문서의 폴더 사슬 이름을 아래에서부터 읽었을 때 폴더 경로의 끝과 맞는** 문서. 폴더 이름은 앞뒤 공백을 떼고 대소문자를 접어 비교한다. 사슬 길이가 폴더 경로보다 짧으면 안 맞는다. 목록에 없는 폴더(공유받은 문서)는 이름을 모르므로 안 맞는다
   - 정확 일치 제목에서 경로가 맞는 문서가 있으면 그들만, 없을 때만 대소문자 접은 제목에서 찾는다
3. **끝 `.md`.** 1·2 모두 없고 `target` 이 `.md` 로 끝나면(대소문자 무시) 그 세 글자를 떼고 앞뒤 공백을 지운 값(비지 않으면)으로 1·2 를 **한 번만** 다시 한다
4. 없으면 `null`

- 1 이 2 보다 먼저인 이유는 개요 그대로다 — 제목에 `/` 가 든 기존 문서(`A/B 테스트`)로 건 링크가 살아야 한다
- 없음(`null`)인지 아닌지는 **원본 폴더와 무관하다.** 원본은 후보가 여럿일 때 고르는 데만 쓴다. `ShareMenu`(8.4)가 원본 없이 판정하는 근거다
- NFC 정규화는 하지 않는다(개요 3.2 — 가져올 때 F-2019 가 맞춘다)

### 4.4 가까운 폴더 (개요 3.3 을 정확히)

후보가 하나면 그것. 여럿이면 원본의 폴더 사슬(4.2)로 아래 단계를 차례로 보고, **처음 걸리는 단계에서 목록 앞(최근 수정)** 후보를 고른다

| 단계 | 걸리는 후보 |
| --- | --- |
| 1·2 | 원본 사슬을 아래(원본 폴더 자신)부터 위로 올라가며, 그 폴더에 **바로** 든 후보가 있으면 그것. 원본 사슬이 최상위에 닿았으면 마지막으로 최상위(`folderId === null`) 후보 |
| 3 | 원본 사슬을 다시 아래부터 올라가며, 그 폴더의 **자손 어디든** 든 후보(후보 사슬에 그 폴더가 있는 후보)가 있으면 그것 — 먼저 걸리는 폴더가 가장 깊은 공통 조상이다 |
| 4 | 목록 맨 앞 후보 |

- 원본이 공유받은 문서(사슬 `[남의 폴더]`, 최상위 안 닿음)면 1 은 같은 남의 폴더에 든 후보, 2·3 은 없다 → 4
- 원본이 최상위 문서면 1 = 최상위 후보, 2·3 은 없다
- 원본 폴더 **안쪽**(자손 폴더)의 후보는 3 에서 원본 폴더를 공통 조상으로 갖는다 — 원본의 조상 폴더(2)에 후보가 있으면 조상이 이긴다(개요 3.3 그대로)
- **최상위도 2 의 마지막 조상이다.** 그래서 최상위에 같은 제목 문서가 있으면 3 단계 후보(볼트 안 사촌 폴더)보다 먼저 걸린다 — 17장 Q2

### 4.5 대소문자 접기 — `toLowerCase()`

- 지금 코드(`resolveWikiTarget`·`buildTitleMaps`)는 `toLocaleLowerCase('ko')` 를 쓴다. 해석기는 **`toLowerCase()`** 를 쓴다
- 결과가 같다 — 이 PC V8 에서 모든 코드 포인트와 문맥 의존 글자열로 확인했다(머리 (a)). 로케일별 대소문자 규칙은 리투아니아어·터키어·아제르바이잔어에만 있다(Unicode SpecialCasing — 이것은 알려진 사실이고 이 세션에서 V8 밖 엔진으로 돌려 보지 않았다, 18.2 G-a)
- 이유: 90배 차이가 서버 CPU 에 그대로 걸린다(4.6 의 "지금 방식" 줄). 다른 파일의 `toLocaleLowerCase('ko')`(지도 끊긴 링크 키 등)는 결과가 같으므로 이 명세에서 고치지 않는다

### 4.6 비용 — 실측과 기준

머리 (b) 의 합성 데이터. "만들기" 는 `createWikiResolver` 만, "지도" 는 만들기 + 모든 문서의 링크 전부 해석, "서버" 는 만들기 + 문서 51개 × 링크 10개(묶음 상한 50 + 시작 문서), "편집기" 는 만들기 + 링크 50개(보이는 범위). 두 번 잰 중앙값(괄호는 최소~최대)

| 조건 | 만들기 | 지도 | 서버 | 편집기 |
| --- | --- | --- | --- | --- |
| 문서 1,000 / 링크 1만, `toLowerCase` | 0.3~0.6 ms | 4.4~10.5 ms | 0.5~0.8 ms | 0.3~0.4 ms |
| 문서 5,000 / 링크 5만, `toLowerCase` | 0.9~2.0 ms | **15.0~63.5 ms** (13.5~120.8) | **3.2~3.8 ms** (2.2~4.3) | **1.5~2.5 ms** (1.1~5.8) |
| 같은 조건, 겹치는 제목 600종 | 1.2~2.1 ms | 18.0~50.1 ms | 1.5~2.7 ms | 1.1~1.7 ms |
| 문서 10,000 / 링크 10만, `toLowerCase` | 1.6~3.2 ms | 38.3~80.0 ms | 4.0~5.5 ms | 2.5~3.4 ms |
| 문서 5,000, 같은 시제품을 `toLocaleLowerCase('ko')` 로 | 14.7 ms | 195.5 ms | 21.6 ms | 10.8 ms |
| 문서 5,000, 서버 조건을 **지금 방식**(링크마다 전체 선형 탐색 + `toLocaleLowerCase('ko')`) | — | — | **693.9~755.8 ms** | — |

- 시제품은 **제목 표만 만들 때 만들고, 제목 키별 "폴더 → 그 폴더에 바로 든 첫 후보"·"폴더 → 그 자손 어디든 첫 후보" 표는 그 키가 처음 물릴 때 만들어 기억하는** 방식이다. 전부 미리 만드는 쪽과 지도 전체 시간이 같은 자릿수였고(5,000개 16.9~41.3 ms) 만들기는 게으른 쪽이 1.5~2배 빨랐다. 구현이 다른 방식을 골라도 아래 기준만 지키면 된다
- **기준(구현자가 실물 함수로 재어 보고, 15.1 U17)**: 문서 5,000·링크 5만 겹침 심한 조건에서 지도 조건 중앙값 **150 ms 이하**, 서버 조건 **10 ms 이하**, 편집기 조건 **5 ms 이하**
- **지도 열기 시간**(개요 3.7 이 F-2018 에 미룬 것): 해석이 더하는 시간은 문서 5,000개에서 0.02~0.06 초로, F-292 G5 의 "멈출 때까지 3,000 ms" 에 견줘 1~2% 다. 5,000개를 브라우저에 심는 측정 도구가 없어 **브라우저 측정은 하지 않고 위 Node 실물 측정으로 갈음한다**
- **지금 서버 묶음 수집이 이미 무겁다**는 것을 함께 확인했다 — 마지막 줄. 이 명세로 해석기를 쓰면 줄어든다

### 4.7 없는 경로식 링크의 새 문서 자리 — `findLinkFolder`

개요 3.6. `resolve` 가 `null` 인 대상에만 쓴다

- 4.3 의 2 와 같은 방식으로 나눴을 때 폴더 경로가 있고(빈 조각 없음), **폴더 사슬 이름을 아래에서부터 읽어 그 경로의 끝과 맞는 폴더**(그 폴더 자신이 경로 마지막 조각)가 있으면 `{ folderId: 그 폴더, title: 마지막 조각 }`
- 여럿이면 각 폴더를 "그 폴더에 든 문서" 로 보고 4.4 단계 1~3 을 그대로 쓴다. 단계 4(같은 단계 안)의 순서는 `folders` 배열 순서
- 없으면 `null` — 호출부는 지금처럼 **대상 전체**를 제목으로 `newDocFolderId()` 자리에 만든다(F-131 5장). 그 뒤 3.2 1단계(제목 전체 일치)로 링크가 곧바로 풀린다
- 폴더를 새로 만들지 않는다. 끝 `.md` 는 떼지 않는다(떼는 것은 찾기에만 쓴다) — `[[새 글.md]]` 는 제목 `새 글.md` 로 만든다

### 4.8 가장 짧은 형태 — `shortestWikiTarget`

- 문서 제목(앞뒤 공백 제거), 그다음 `{가장 가까운 폴더}/{제목}`, `{두 칸 위}/{가까운 폴더}/{제목}` … 순으로 `folderNames` 끝 조각을 하나씩 늘려 가며, **`resolve(형태, 원본)` 이 그 문서 자체를 돌려주는 첫 형태**
- 어느 형태로도 그 문서가 안 풀리면(폴더를 모르는 공유받은 문서, 이름에 `/` 가 든 폴더, 다른 문서가 제목 전체 일치로 가로챔) **제목** — 지금 자동완성이 넣는 값과 같다
- 제목에 `|`·`[`·`]`·`#` 이 든 문서는 어떤 형태로도 가리킬 수 없다. 지금처럼 제목을 넣는다(이 명세에서 막지 않는다)

### 4.9 지금 규칙과 같은 경우

모든 문서가 최상위(`folderId: null`)이고 `folders` 가 비었을 때, `createWikiResolver(docs, []).resolve(t, null)` 은 **끝 `.md` 떼기(4.3 의 3)가 걸리는 경우를 빼면** `resolveWikiTarget(t, docs)` 와 같은 문서를 돌려준다. `wikiLink.test.ts` 의 규칙 1·2·3 입력을 그대로 넣어 판정한다(15.1 U3). 개요 3.3 끝의 "결과가 같아야 한다" 에 `.md` 예외를 적은 것이다

### 5.2 다시 만드는 때와 비용

- `App` 이 `docs`·`folders` 가 바뀔 때만 해석기를 새로 만든다(`useMemo`). **입력마다 만들지 않는다**

- 순서만 바뀌어도 다시 만든다 — "최근 수정" 이 같은 단계 안 순서를 정하므로 순서가 결과를 바꿀 수 있다
- 비용: 만들기 0.3~2.0 ms(문서 1,000~5,000, 4.6), 그 뒤 편집기가 보이는 범위의 위키링크 표시를 다시 계산한다 — 지금 `setWikiTitles` 가 일으키는 것과 같은 재계산이다
- 문맥 객체는 `resolver` 나 `sourceFolderId` 가 바뀔 때만 새로 만든다. 문서를 다른 폴더로 옮기면 `docs` 가 바뀌어 둘 다 새로 온다
- 전달 시점은 지금 `setWikiTitles` 효과와 같다 — `openDoc.id !== currentDocId` 인 동안(문서 전환 중)은 보내지 않는다

## 7. 헤딩 찾기와 이동

### 7.1 찾기 함수 — `src/viewer/headingTarget.ts`

```ts
// src/viewer/headingTarget.ts (F-2018 신규) — markdown-it(renderMarkdown 의 그 인스턴스). DOM 없음, 테스트 환경 node
export type DocHeading = { level: 1 | 2 | 3 | 4 | 5 | 6; text: string; raw: string; line: number }
export function listDocHeadings(markdown: string): DocHeading[]
export function findHeadingLine(markdown: string, wanted: string): number | null
```

- **개요 3.5 는 "원문에서 펜스·프론트매터를 건너뛰는 새 순수 함수(`src/lib/`)" 로 적었다. 원문을 직접 훑지 않고 `renderMarkdown` 의 `parseMarkdownTokens` 를 쓴다.** 이유: 보기 모드에서 스크롤할 요소를 `data-source-line` 으로 찾는데(7.3), 그 줄 번호는 markdown-it 이 만든다. 따로 훑는 함수는 `- item\n---`(markdown-it: 목록 + 가로줄, 머리 (c))을 제목으로 잡는 식으로 어긋나 "편집기에선 찾고 보기에선 요소가 없는" 틈이 생긴다. `src/lib/` 은 markdown-it 을 import 하지 않는 자리(`wikiLink.ts`·`callout.ts`·`frontmatter.ts` 머리 주석)라 `toPlainText.ts`·`toHtmlDoc.ts` 처럼 `src/viewer/` 에 둔다
- 대상: markdown-it 이 만든 `heading_open` 중 **본문 최상위(`level === 0`)** 인 것 — ATX·Setext 1~6단계. 펜스·들여쓴 코드·표·HTML 은 markdown-it 이 이미 제목으로 보지 않는다. 인용·목록·콜아웃 안 제목(`level` 1 이상)은 대상이 아니다 — 보기 결과에서 최상위 블록만 `data-source-line` 을 갖기 때문이다(F-295 U13·U14)
- 프론트매터: `renderMarkdown` 과 **같은 방식**으로 떼고 그 줄 수를 더한다. 그래서 `line` 은 보기 결과의 `data-source-line` 값과 같다(1부터)
- `text`: 제목 인라인 토큰의 자식 중 글자(`text`)·인라인 코드(`code_inline`)의 내용을 이어 붙이고, 줄바꿈(`softbreak`)은 공백 하나로, 앞뒤 공백을 뗀 것 — 보기 모드에 보이는 글자다(위키링크는 보이는 글자, 강조 기호는 빠짐)
- `raw`: 제목 인라인 토큰의 원문(`content`) 앞뒤 공백 뗀 것

### 7.2 비교 — 세 단계

`findHeadingLine(원문, 링크의 heading)` 은 제목을 문서 순서로 놓고 **앞 단계에서 하나라도 맞으면 그 단계에서 문서 순서로 첫 제목**의 `line`

1. `text` 가 `heading` 과 정확히 같다
2. 대소문자를 접어(`toLowerCase`) 같다
3. 양쪽에서 `# ^ : | [ ] %` 를 지우고 연속 공백을 하나로 접고 앞뒤 공백을 뗀 뒤 대소문자를 접어, `heading` 이 `text` 와 같거나 **`raw`** 와 같다

- 3단계는 옵시디언이 헤딩 링크를 만들 때 이 글자들을 뺀다는 가정(F-2016 G3)을 따른 것이다. **확인하지 못했다** — 사람 확인 H1. 틀려도 1·2 단계는 그대로 동작한다
- 3단계에 `raw` 를 넣은 이유: `## **중요** 결정` 을 옵시디언이 `[[노트#**중요** 결정]]` 처럼 원문 그대로 링크한다면 `text`(`중요 결정`)로는 안 맞는다. 옵시디언이 어느 쪽을 쓰는지도 G3 와 같이 확인하지 못했다
- 제목이 없거나 아무 단계에서도 안 맞으면 `null`

### 7.3 이동 — 화면별

| 화면 | 이동 |
| --- | --- |
| 편집·원문 모드 | 커서를 그 줄 처음으로 옮기고, F-144 `scrollToHeading(pos)` 와 같은 방식(맨 위 16px 여백, rAF 두 번 뒤 보정)으로 스크롤한다. 커서를 옮기는 이유는 17장 Q3 |
| 보기 모드(앱) | 보기 결과 안의 `h1~h6[data-source-line="{line}"]` 요소를 찾아 목차가 보기 모드에서 하는 것(`Outline.tsx` `selectHeading`, 요소 위가 스크롤 영역 위에서 `SELECT_MARGIN` 16px 아래)과 같게 스크롤한다. 앱 보기 모드는 이미 `sourceLines: true` 로 그려 h4~h6 도 줄 번호를 갖는다(F-295 U13) |
| 공개 묶음·공개 폴더 | 보기 모드와 같다. **`DocPane` 의 `renderMarkdown` 에 `sourceLines: true` 를 켠다** — 지금은 꺼져 있어 h4~h6 에 줄 번호가 없다. 켜도 공개 화면의 다른 동작(목차는 h1~h3 선택자만 씀)은 바뀌지 않는다 |

- 요소 찾기 선택자는 계약이다: `h1[data-source-line="{n}"], h2[…], h3[…], h4[…], h5[…], h6[…]`. `outlinePosition.ts` 에 줄 번호로 찾는 함수를 더한다(기존 `findViewerHeadingEl` 은 목차용 h1~h3 그대로)
- 찾았는지는 **원문으로 판정한다**(`findHeadingLine`). 보기 결과가 아직 그 문서로 안 그려졌으면 그려진 뒤 스크롤한다. 원문으로 찾았는데 요소가 끝내 없으면(그럴 일은 없어야 한다) 아무것도 하지 않는다 — 알림을 내지 않는다
- 편집 모드의 원문은 에디터 원문(`getText('lf')`), 보기·공개 화면은 그 화면이 그린 원문이다

### 7.4 못 찾으면

- 문서 처음으로 스크롤하고 알림(`info`) `"{헤딩}" 제목을 찾지 못해 문서 처음을 엽니다.` — `{헤딩}` 은 링크의 `heading` 그대로. 편집 모드면 커서도 문서 처음(지금 문서 열기와 같다)
- **지금 문서 링크 `[[#없는 제목]]` 도 같다** — 문서 처음으로 가고 같은 알림. 17장 Q4
- 알림은 앱 알림 띠(`showNotice`, 4초 뒤 사라짐)다. 공개 화면에는 알림 띠가 없으므로 `PublicView` 가 `NoticeBar` 를 그린다(11.3)

### 7.5 주소·기록

- 다른 문서로 가면 지금처럼 `#/d/{id}`(공개는 `#/p/{토큰}/{id}`·`#/p/f/{토큰}/{id}`)를 push 한다. **헤딩은 주소에 넣지 않는다**
- 같은 문서 안 이동(`[[#결정]]`, 또는 풀린 문서가 지금 문서)은 기록을 **추가하지 않는다** — 주소가 그대로다

## 8. 앱 흐름 — `App.tsx`

### 8.1 해석기와 편집기 문맥

- `docs`(DocMeta, `updatedAt` 내림차순)와 `folders` 로 해석기를 만든다. 문서 참조는 `{ id, title, folderId }` 만 쓴다. 공유받은 문서(`role` 이 `edit`·`view`)도 지금처럼 후보에 든다(개요 7장 충돌 4)
- 편집기 문맥 = `{ resolver, sourceFolderId: currentDoc?.folderId ?? null }` (5.1·5.2)

### 8.2 `resolveWikiHref` (보기 모드·인쇄)

- 대상이 `''` 이면 `#/d/{지금 문서 id}`
- 아니면 `resolve(대상, 지금 문서의 folderId)` → `#/d/{id}` 또는 `null`

### 8.3 `openWikiLinkTarget(target, heading)`

차례대로 처음 맞는 것 하나

1. `target === ''` → 지금 문서에서 헤딩 이동(7.3·7.4)
2. `resolve(target, 지금 문서의 folderId)` 가 **지금 문서**이고 앱이 문서 화면이면(지도·공유 화면·도움말·공유 관리가 떠 있지 않음) → 1 과 같다. 헤딩이 없으면 아무것도 하지 않는다(지금 `selectDoc` 이 같은 문서면 돌아가는 것과 같다)
3. 풀린 문서가 있으면 → 지금처럼 `selectDoc(id)`. 헤딩이 있으면 **그 문서가 열린 뒤** 이동한다 — 기다리는 방식은 F-294 검색어 넘기기(`pendingEditorSearch`: 대상 문서 id 를 기억해 두고 새 에디터가 만들어진 뒤 한 번 적용)와 같다. 보기 모드면 보기 결과가 그 문서로 그려진 뒤다
4. 없으면 새 문서(F-131 5장). **헤딩은 버린다**(개요 3.6). `findLinkFolder(target, 원본)` 이 자리를 주면 그 폴더에 그 제목, 아니면 지금처럼 대상 전체를 제목으로 `newDocFolderId()` 에. 만든 문서의 조상 폴더를 사이드바에서 펼친다(지금 `addOpenFolders(ancestorsOfDoc(…))` 그대로)

- 지도의 끊긴 링크 노드는 `onOpenWikiLink(node.title)` 로 4 에 온다 — 원본은 지도 뒤에 열려 있던 문서다. 끊긴 링크인지는 원본과 무관하므로(4.3) 결과가 어긋나지 않는다
- 3 에서 문서를 여는 흐름(`selectDoc`)은 편집기에 포커스를 주고 커서를 문서 처음에 둔다(`focusEditorRef`). 헤딩 이동은 그 뒤에 커서를 제목 줄로 옮긴다

### 8.4 `ShareMenu` 판정

- `TopBar` 를 거쳐 `wikiDocs` 대신 **해석기**를 받는다(prop 이름 `wikiResolver`)
- 메뉴를 열 때 공유할 문서 원문의 위키링크 중 `target !== ''` 이고 `resolve(target, null) !== null` 인 것이 하나라도 있으면 `읽기 전용 링크 복사…` — 있음/없음은 원본과 무관하므로(4.3) 원본을 넘기지 않는다. 경로식 링크만 있는 문서도 이제 `…` 가 붙는다(지금은 `[[교안/1주차]]` 가 제목 전체 일치에 실패해 안 붙는다)
- 판정은 여전히 로컬이고, 실제 묶음은 서버 미리보기(10.4)가 정한다 — 서버는 소유자 문서만 보므로 공유받은 문서로만 풀리는 링크는 `…` 가 붙어도 대화상자가 비어 있을 수 있다(지금도 같다)

## 9. 지도

### 9.1 `wikiGraph.ts`

```ts
export type WikiGraphEntry = { id: string; title: string; targets: string[]; unreadable?: boolean; folderId?: string | null }
export function buildWikiGraphFromEntries(entries: WikiGraphEntry[], folders?: readonly WikiFolderRef[]): WikiGraph
```

- 간선의 대상 = `createWikiResolver(entries 의 {id,title,folderId}, folders).resolve(target, 그 항목의 folderId)`. `folderId` 가 없으면 `null`, `folders` 가 없으면 `[]` — 둘 다 없으면 지금 규칙(정확 → 대소문자 → 먼저 나온 것)과 같다(4.9). 그래서 **`wikiGraph.test.ts` 는 바뀌지 않고 통과한다**(개요 6.2 는 바뀐다고 적었지만 선택 인자로 두어 피했다)
- 끊긴 링크 노드 키(대상 문자열 소문자)·자기 자신 간선 없음·중복 간선 없음·`degree` 는 그대로
- `extractWikiTargets` 는 `target === ''`(`[[#헤딩]]`)을 뽑지 않는다
- `buildWikiGraph(docs)` 는 모양 그대로, 문서에 `folderId` 가 있으면 넘긴다

### 9.2 `mapIndex.ts`

- `MapIndexEntry` 에 `folderId: string | null` 을 더한다. **캐시하지 않는다** — `changeKey` 는 `updatedAt`·제목만 보는데 `moveDoc` 은 `updatedAt` 을 바꾸지 않는다(`idbStore.ts` `moveDoc` 주석, 확인). 캐시된 항목의 `targets` 는 재사용하고 `folderId` 는 매번 새 목록의 값을 쓴다(검색 인덱스 `searchIndex.ts` 가 `folderPath` 를 매번 덮는 것과 같다)

### 9.3 `MapPage.tsx`

- `load()` 가 이미 `store.listFolders()` 를 읽는다(F-2007 5.2). 항목에 `folderId` 를 싣고 그 폴더 목록을 `buildWikiGraphFromEntries` 에 넘긴다 — 이 한 곳만 고친다

## 10. 서버

### 10.1 `collectWikiSet` — 묶음 미리보기

```ts
export function collectWikiSet(rootId: string, loadDoc: LoadDoc, allDocs: WikiDocRef[], folders: WikiFolderRef[],
  opts?: CollectWikiSetOptions): CollectWikiSetResult
```

- 해석기를 한 번 만들고, 방문하는 문서마다 **그 문서의 `folderId`(`allDocs` 에서)** 를 원본으로 `resolve`. `target === ''` 은 건너뛴다
- 너비 우선·방문 표시·상한 5단계 50개·`truncated`·시작 문서 제외는 그대로(F-252 2.2)
- 개요 6.2 의 "폴더 목록 인자·`folderId`" 모양이다

### 10.2 `buildWikiLinkTable` — 공개 묶음 링크 표 (순수)

```ts
// worker/shareSet.ts (F-2018)
export function buildWikiLinkTable(content: string, sourceFolderId: string | null, resolver: WikiResolver,
  allowedIds: ReadonlySet<string>): Record<string, string>
```

- `content` 의 각 줄에서 `findWikiLinks`, `target` 이 `''` 이 아니고 `resolve(target, sourceFolderId)` 가 `allowedIds` 안 문서면 `표[target] = 그 id`
- **키는 `findWikiLinks` 가 준 `target` 문자열 그대로**다 — 클라이언트가 같은 원문에 같은 함수를 돌려 같은 키로 찾는다
- **`content` 는 `stripComments` 를 거친 값이어야 한다.** 주석(`%%…%%`·`<!-- -->`) 안 위키링크 대상 글자가 표의 키로 익명 방문자에게 새면 안 된다. 방문자가 받는 본문도 같은 `stripComments` 를 거친다(F-210 2.3)
- 표는 **자기 속성**으로만 만든다 — `[[__proto__]]`·`[[constructor]]` 같은 대상이 프로토타입을 바꾸거나 잘못 걸리지 않게. 클라이언트도 자기 속성인지 보고 읽는다(11.1)
- 묶음 밖 문서로 풀리는 대상·못 푸는 대상은 표에 없다 — 묶음 밖 문서 id 가 새지 않는다

### 10.3 `GET /pub/docs/:token/set` 응답

```json
{ "docs": [ { "id": "시작 문서 id", "title": "…", "links": { "1주차": "문서 id", "과제/1주차": "문서 id" } } ] }
```

- 문서 순서(시작 문서 맨 앞, 삭제된 문서 빠짐)·헤더·404 규칙은 F-252 2.5 그대로. **`links` 를 더할 뿐 기존 필드를 바꾸지 않는다** — 옛 클라이언트(새 버전 알림 전의 PWA)는 `links` 를 무시하고 지금처럼 제목으로 푼다
- **폴더 이름·폴더 id·다른 문서 목록은 응답에 넣지 않는다**(사용자 결정 3)
- 묶음 문서가 **1개**면 모든 문서의 `links` 는 `{}` 이고 소유자 전체 문서·폴더를 읽지 않는다 — 클라이언트는 문서 1개면 위키링크를 `--plain` 으로 그려 표를 쓰지 않는다(F-252 4.4)
- 2개 이상이면: 묶음 문서의 본문을 읽고, 소유자(`share_links.owner_id`) 문서 `{ id, title, folder_id }` 를 **`updated_at` 내림차순**으로, 소유자 폴더 `{ id, name, parent_id }` 를 읽어 해석기를 만들고, 묶음 문서마다 `buildWikiLinkTable(stripComments(본문), 그 문서의 folder_id, 해석기, 묶음 id 집합)`
- D1 질의: 소유자 문서는 `docs_owner_updated` 인덱스, 폴더는 `folders_owner` 인덱스를 탄다(`migrations/0002_docs.sql`). 쓰기는 없다(`/pub` 은 읽기만, F-210 2.3)
- 발급 뒤 문서를 옮기거나 같은 제목 문서가 새로 생겨 링크가 **묶음 밖 문서로 풀리게 되면 그 링크는 `--missing`** 으로 보인다 — 서버가 조회 시점의 소유자 전체로 해석하기 때문이다(사용자 결정 3). 묶음에 든 문서는 바뀌지 않는다(F-252 0장 "발급 시점 고정" 그대로)
- `publicDoc.ts` 의 `PublicSetDoc` 에 `links?: Record<string, string>` 을 더한다(선택 — 11.1 의 되돌림 규칙 때문)

### 10.4 `handleGetDocShareSet` — 미리보기 정렬

- 소유자 문서를 `SELECT … ORDER BY updated_at DESC` 로 읽고(개요 7장 충돌 3 — 지금은 정렬이 없어 같은 제목이면 D1 이 준 순서의 첫 문서가 뽑힌다), `folder_id` 와 소유자 폴더도 읽어 10.1 에 넘긴다
- 응답 모양(F-252 2.3)은 그대로다

### 10.5 CPU

- 해석 자체는 문서 5,000개에서 1.5~3.8 ms(4.6 서버 조건, Node). 여기에 D1 행 읽기·`findWikiLinks`·`stripComments` 가 더해진다
- Workers 무료 플랜(Q42)은 요청당 CPU 시간 한도가 있다(Cloudflare 문서상 10ms — 이 세션에서 확인하지 않았다, 18.2 G-b). 지금 `handleGetDocShareSet` 는 같은 규모에서 선형 탐색 + `toLocaleLowerCase('ko')` 로 수백 ms 가 나온다(4.6 마지막 줄) — 이 명세가 그 경로를 줄인다. 배포 뒤 큰 계정의 CPU 시간은 사람 확인 H6

### Q1. 보기 화면에서 `[[회의록#결정]]` 을 `회의록#결정` 으로 보이는가 — **기본값: 그렇다 (원문 조각 그대로)** (3.2) · 사람 결정

### Q2. 최상위의 같은 제목 문서가 볼트 안 사촌 문서를 이긴다 — **기본값: 승인된 순서 그대로** (4.4) · 사람 확인

- 개요 3.3 표는 최상위를 2단계의 "마지막 조상" 으로 두고 3단계(공통 조상이 깊은 후보)를 그 뒤에 두었다. 그래서 볼트를 `내 볼트` 폴더에 넣고 `내 볼트/위키/개념/a` 에서 `[[색인]]` 을 걸면, **최상위에 `색인` 이 있을 때** `내 볼트/위키/인물/색인` 이 아니라 최상위 `색인` 으로 간다. 개요 Q1 의 근거 문장("볼트 밖 아무 `색인` 으로 갈 수 있다 → 3단계가 있으면 볼트 안이 먼저")은 **최상위 밖의** 볼트 밖 후보에만 맞는다. 사용자는 Q1 을 골랐지만 이 경우를 따로 보지 않았다
- 다른 쪽 — **최상위를 3단계 뒤로**(2단계는 폴더 조상만, 최상위는 "공통 조상 깊이 0" 으로 3단계 끝에): 위 예에서 볼트 안이 이긴다. 원본이 최상위 문서일 때(1 = 최상위)는 결과가 같다. 사용자 문구 "같은 폴더 → 가까운 조상 → …" 에서 "최상위도 조상" 이라는 해석만 바뀐다. U6 의 한 단언과 4.4 표 한 줄이 바뀐다

### Q3. 편집 모드에서 헤딩으로 가면 커서도 옮기는가 — **기본값: 제목 줄 처음으로 옮긴다** (7.3)

- 이유: 다른 문서로 가면 `selectDoc` 이 커서를 문서 처음에 두고 포커스를 준다(`focusEditorRef`). 스크롤만 하면 바로 쳤을 때 글자가 문서 처음에 들어가며 화면이 맨 위로 튄다
- 다른 쪽 — 목차(F-144)처럼 **스크롤만**: 제목 줄의 `##` 기호가 드러나지 않는다. 대신 위 튐이 생긴다

### Q4. `[[#없는 제목]]` 도 문서 처음으로 가는가 — **기본값: 간다, 같은 알림** (7.4)

- 이유: 개요가 정한 문구 하나("문서 처음을 엽니다")가 거짓이 되지 않게
- 다른 쪽 — 제자리에 두고 다른 알림 `"{헤딩}" 제목을 찾지 못했습니다.`: 읽던 자리를 잃지 않는다. 문구가 하나 늘고 `ia.md` 에 적을 것이 는다

### Q5. 공개 화면에서도 헤딩 못 찾음 알림을 보이는가 — **기본값: 보인다, `NoticeBar` 재사용** (11.3)

- 다른 쪽 — 공개 화면은 조용히 문서 처음: `PublicView` 에 알림 상태를 두지 않아도 된다. 방문자는 왜 처음으로 왔는지 모른다

### Q6. 헤딩 찾기를 markdown-it 으로 — **기본값: `src/viewer/headingTarget.ts`, 최상위 제목만** (7.1)

- 개요 3.5 의 "원문을 훑는 `src/lib/` 함수" 를 바꾼 것이다. 이유는 7.1(보기 결과 줄 번호와 어긋나지 않게, 확인한 반례 `- item\n---`)
- 다른 쪽 — 원문 훑기: 인용 안 제목도 잡을 수 있지만 보기 화면에서 요소를 못 찾는 경우가 생겨 "찾았다고 판정했는데 안 움직임" 이 된다. `level` 과 무관하게 모든 제목을 잡고 싶으면 `heading_open` 규칙이 h4~h6 에도 줄 번호를 붙여야 해 F-144 A1 "h4 이하에는 붙이지 않는다" 가 뒤집힌다

### Q7. 링크 하나짜리 공개 문서의 `[[#결정]]` — **기본값: 지금처럼 `--plain`** (11.1)

- 이유: 그 화면은 위키링크 해석을 아예 주지 않는다(F-252 4.4, C6). `[[#…]]` 만 살리려면 `renderMarkdown` 이 "다른 문서 링크는 plain, 지금 문서 링크만 a" 인 세 번째 모드를 가져야 한다

### Q8. `/set` 응답에 `links` 가 없을 때 — **기본값: 지금 규칙(묶음 안 제목)으로 되돌림** (11.1)

### 18.1 코드를 읽거나 돌려 확인한 것

- worker 가 `src/lib` 를 이미 import 한다 — `worker/shareSet.ts` 가 `../src/lib/wikiLink` 를, `worker/links.ts` 가 `../src/lib/comments` 를 import 한다. `wikiResolve.ts` 도 같은 길로 쓸 수 있다
