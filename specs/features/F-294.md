## 2. 범위

### 2.1 한다

- 검색 결과에서 문서를 열 때 **본문에 실제로 있는 검색어 하나**를 골라 (4.1) 그 문서의 CM6 찾기 패널에 넣는다 (4.2)
- 패널을 열고, 매치를 강조하고, **첫 매치로 선택을 옮긴다**. 포커스는 본문으로 되돌린다 (4.4)
- 넣을 것이 없는 경우(필터만 친 검색·제목만 맞은 문서·공유받은 문서·보기 모드)에는 **아무 일도 하지 않는다** (4.2)
- 문서가 실제로 화면에 실린 뒤에 적용한다 (4.3 — 타이밍이 이 명세의 핵심)

### 2.2 하지 않는다

- **검색어 여러 개를 동시에 강조하기.** CM `SearchQuery.search` 는 문자열 하나다. 정규식 `a|b` 로 우회하지 않는다 — 이유는 3.2·13장 Q1
- **발췌(`SnippetPart`)·`bodyHit` 의 좌표를 에디터로 넘기기.** 그 값은 NFC 로 정규화하고 프론트매터를 뗀 문자열 기준이라 원문 좌표가 아니다 (F-284 4.2, F-287 4.6). 검색어 **문자열**만 넘기고 위치는 CM6 가 원문에서 다시 찾는다
- 보기 모드(`Viewer`, 렌더된 HTML) 안 하이라이트 — 새 기능이고 F-284 5.4 범위 밖이다 (13장 Q6)
- 검색 패널 UI·문구·스타일 바꾸기 — F-261 것을 그대로 쓴다
- 대화상자를 열어 둔 채 문서를 바꿔 가며 보는 흐름, 매치 개수 표시, 결과 간 이동 — F-284 5.4
- `Ctrl+F`(`App.tsx` 955~966행)·`Mod-h`(F-261) 동작 바꾸기
- 큰 문서에서 `findNext` 를 건너뛰는 상한 두기 (7.2, 13장 Q9)

## 3. 코드에서 확인한 것 (이 설계가 여기서 나왔다)

### 3.1 패널이 열려 있어야만 매치가 강조된다

`@codemirror/search/dist/index.js` 819~821행:

```js
highlight({ query, panel }) {
    if (!panel || !query.spec.valid)
        return Decoration.none;
```

- `searchState` 에 검색어만 넣고 패널을 안 열면 `.cm-searchMatch` 가 **하나도 안 그려진다**. 그래서 사용자 전제 1(패널을 연다)이 곧 구현 방법이다
- `query.spec.valid` 는 `!!search && (!regexp || validRegExp(search))`(565행)다 — 빈 문자열이면 무효라 역시 아무것도 안 그려진다

### 3.2 CM6 문자열 검색은 NFKD 정규화를 스스로 한다 — 정규식으로 바꾸면 그것을 잃는다

| 확인 | 결과 |
| --- | --- |
| `SearchCursor` | 5~6행 `basicNormalize = x => x.normalize("NFKD")`, 47~48행에서 **질의와 문서 양쪽에** 적용한다 |
| 대소문자 | 617~623행 `stringCursor` 가 `spec.caseSensitive ? undefined : x => x.toLowerCase()` 를 정규화 함수로 넘긴다 |
| `RegExpCursor` | 694~700행 `regexpCursor` 는 `new RegExpCursor(state.doc, spec.search, { ignoreCase: !spec.caseSensitive })` — **정규화를 하지 않는다.** 원문 줄에 정규식을 그대로 돌린다 |

- 실측(7.1)에서 **NFD 로 저장된 한글 본문 × NFC 검색어**가 문자열 검색으로는 걸리고, 이것이 `regexp: true` 로 `a|b` 를 만드는 안을 버린 **가장 큰 이유**다. F-284 4.2 가 NFC 정규화에 공들인 것을 정규식 경로가 되돌린다
- 부수 효과: 검색어를 `foldCase()`(소문자·NFC)한 값 그대로 넣어도 된다. CM 이 다시 `NFKD` + `toLowerCase` 를 하므로 **원문 대소문자와 어긋나지 않는다** (4.2)

### 3.3 `openSearchPanel` → `setSearchQuery` → `findNext` 순서

| 함수 | 확인한 동작 |
| --- | --- |
| `openSearchPanel`(1009~1027행) | 패널이 없으면 `togglePanel.of(true)` + `setSearchQuery.of(defaultQuery(...))` 를 **한 트랜잭션**으로 보낸다. **이미 열려 있으면 `defaultQuery(view.state, 지금 질의)` 로 덮어쓴다** — `defaultQuery`(982~996행)는 **선택 영역 글자**를 검색어로 쓴다. 그래서 우리 검색어는 반드시 **그 뒤 별도 dispatch** 로 넣어야 한다 |
| | 실제 DOM 에서는 검색 입력에 `focus()`·`select()` 를 한다. `SearchPanel.mount()` 도 `searchField.select()` 를 부른다 → **포커스가 패널로 간다.** 4.4 가 본문에 다시 포커스를 주는 이유다 |
| `setSearchQuery`(772행 정의, 780~783행 반영) | 상태 필드만 바꾼다. **선택·스크롤을 움직이지 않는다.** 패널 `update`(1160행대)가 입력 칸 값을 같이 바꾼다 |
| `findNext`(850~861행) | `selection.main.to` 뒤 첫 매치로 선택을 옮기고, 없으면 문서 처음부터 다시 찾는다(순환). 매치가 없으면 `false` 를 돌려주고 **선택을 건드리지 않는다**. 스크롤(`scrollToMatch`)·스크린리더 안내(`announceMatch`)가 딸려 온다 |
| `searchKeymap`(1040~1059행) | `Mod-f`·`F3`·`Mod-g`(다음)·`Shift-F3`·`Shift-Mod-g`(이전)·`Escape`(닫기, `scope: "editor search-panel"`). **패널이 열려 있으면 이 키들이 본문 포커스에서 바로 먹는다** — 전제 1 이 말한 "공짜로 따라오는 것" |
| 패널 DOM 위치 | `@codemirror/view` 11119~11122행 — `.cm-panels` 를 `view.dom`(= `.cm-editor`) 의 첫 자식으로 넣는다. 그래서 "포커스가 `.cm-editor` 안" 만으로는 본문인지 패널 입력인지 구분되지 않는다. 수용 기준은 `.cm-content` 로 잡는다 |

### 3.4 새 문서의 `EditorView` 는 `#/d/{id}` 이동 직후에 없다

- `selectDoc`(1352~1365행)은 `currentDocId` 만 바꾼다. 본문은 **그 뒤 effect**(1004~1020행)가 `store.get(id)` 로 비동기로 읽어 `setOpenDoc` 한다
- 렌더는 `openDoc?.id === currentDocId` 일 때만 `<Editor key={`${currentDocId}:${editorRemountNonce}`}>` 를 그린다(2670~2674행). 즉 문서를 바꾸면 **이전 에디터가 먼저 언마운트되고**(`editorRef.current === null`), 본문이 도착한 뒤에야 새 뷰가 생긴다
- `Editor.tsx` 62~101행: 뷰 생성·`autoFocus`·`useImperativeHandle` 이 전부 **layout effect** 다
- **그래서 `await selectDoc(id)` 바로 뒤에 `editorRef.current` 를 쓰면 대개 `null` 이다.** 지금 `openDocFromSearch` 의 `setTimeout(() => editorRef.current?.focus(), 0)`(2163~2166행)이 실제로 포커스를 주는 게 아니라 `autoFocus` 가 주고 있는 이유가 이것이다
- 올바른 자리는 **`[openDoc, currentDocId]` 에 걸린 App 의 passive effect** 다. 같은 파일 1115~1124행이 이미 그 자리에서 "자식의 layout effect 뒤에 돈다"는 전제로 포커스 플래그를 소비하고 있다 — 그 옆에 붙인다 (4.3)

## 4. 동작

### 4.1 무엇을 넣는가 — 본문에 실제로 있는 검색어 하나

`parseSearchQuery` 를 실제로 돌려 확인한 값(7.1):

| 입력 | `terms` | `filters` |
| --- | --- | --- |
| `회고 주간` | `['회고','주간']` | `[]` |
| `tag:일기 회고` | `['회고']` | `[{key:'tag',value:'일기'}]` |
| `tag:일기` | `[]` | `[{key:'tag',value:'일기'}]` |
| `"주간 회고"` | `['주간 회고']` | `[]` |
| `Hello World` | `['hello','world']` (소문자) | `[]` |

규칙:

1. **`query.terms` 를 앞에서부터 보며, 그 문서의 `SearchIndexEntry.body` 에 들어 있는 첫 검색어를 고른다**
2. 하나도 없으면 `null` → **패널을 열지 않는다**
3. 비교는 `foldCase(body).includes(term)`. `terms` 는 이미 `foldCase`(NFC + 소문자)를 거쳤고(`docSearch.ts` 107행) `entry.body` 는 NFC 다(`searchIndex.ts` 14행) — 대화상자가 매치를 판정한 것과 **같은 방식·같은 데이터**다 (`docSearch.ts` 190~198행 `matchDoc`)

| 경우 | 고르는 값 | 왜 |
| --- | --- | --- |
| `회고 주간`, 본문에 둘 다 | `회고` | 사용자가 먼저 친 것 |
| `회고 주간`, `회고`는 제목에만·`주간`은 본문에 | `주간` | **첫 검색어로 못을 박으면 매치 0 인 패널이 뜬다.** 검색 조건은 AND 라 그 문서는 어쨌든 두 검색어를 다 갖고 있지만, 한쪽은 제목에만 있을 수 있다 |
| `tag:일기` (필터만) | `null` | 넣을 것이 없다 (13장 Q2) |
| `특이제목` 이 제목에만 | `null` | 본문에 없다. 열면 "매치 0" 만 보인다 (13장 Q4) |
| 공유받은 문서 | `null` | `entry.body` 가 `''` 다 (`searchIndex.ts` 14·20행, F-284 5.2) |

- 여러 검색어를 한 번에 강조하지 않는다 — 3.2·13장 Q1
- 본문에는 있는데 CM 이 못 찾는 경우는 실질적으로 없다. `entry.body` 는 **프론트매터를 뗀** 것이고 CM 은 프론트매터까지 포함한 원문 전체를 보므로, 인덱스가 찾은 것은 원문에도 있다. 반대로 CM 이 **더 많이** 찾을 수는 있다(프론트매터 안 글자, NFKD 로만 같아지는 글자)

### 4.2 CM `SearchQuery` 에 넣는 값

```ts
new SearchQuery({ search: term, caseSensitive: false, literal: true })
```

| 필드 | 값 | 근거 |
| --- | --- | --- |
| `search` | `foldCase` 를 거친 검색어 그대로(소문자·NFC) | CM 이 다시 `NFKD`+`toLowerCase` 하므로 매치 결과가 같다 (3.2). 원문 대소문자를 따로 들고 다니지 않는다 — 그러려면 F-285 토크나이저를 다시 짜야 한다 (13장 Q3) |
| `caseSensitive` | `false` | 대화상자 검색이 대소문자를 구분하지 않는다 (F-284 4.2). 기본값과 같지만 **명시한다** |
| `literal` | **`true`** | 기본값(false)이면 CM 이 검색어의 `\n`·`\t`·`\\` 를 실제 제어 문자로 바꾼다(`unquote`, 575행). `parseSearchQuery('a\\nb')` 는 `['a\\nb']` 로 백슬래시를 그대로 둔다(7.1 실측) — 안 맞추면 대화상자가 찾은 것과 다른 것을 찾는다 |
| `regexp` | 기본값 `false` | 3.2 |
| `wholeWord` | 기본값 `false` | 한국어는 조사가 붙어 단어 경계로 자르면 안 걸린다 (F-284 4.2) |
| `replace` | 기본값 `''` | **부수 효과: 패널에 쳐 둔 바꾸기 문자열이 지워진다.** 문서를 바꿔 열면 어차피 패널이 새로 만들어지므로(4.5), 같은 문서를 검색 결과로 다시 열 때만 생기는 일이다. 받아들인다 |

- 사용자가 패널에서 **대소문자 구분·정규식·단어 단위**를 켜 뒀더라도 이 값으로 덮어쓴다. 검색어를 새로 넣는 것이므로 옵션도 대화상자 규칙에 맞추는 쪽이 일관된다

### 4.3 여는 순서와 타이밍

```

  onOpenDoc(id, term)

App.openDocFromSearch(id, term)
  setSearchOpen(false)
  setPendingEditorSearch(term && viewMode !== 'view' ? { docId: id, term } : null)   // ← 문서 전환 전에 예약한다

  if (viewMode !== 'view') setTimeout(() => editorRef.current?.focus(), 0)            // F-287 4.6 그대로 둔다

    if (!pendingEditorSearch) return
    if (currentDocId !== pendingEditorSearch.docId) return   // 아직 그 문서가 아니다

```

| 물음 | 답 | 근거 |
| --- | --- | --- |
| 어디서 기다리는가 | **`openDoc?.id === currentDocId` 가 될 때까지.** 그 조건이 참인 렌더에서만 `<Editor>` 가 그려지고(2670행), 뷰는 그 자식의 layout effect 에서 만들어진다 | 3.4 |
| 이 effect 가 뷰 생성보다 늦게 도는가 | **그렇다.** 자식의 layout effect 는 같은 커밋의 부모 passive effect 보다 먼저 돈다. 같은 파일 1115~1124행이 이미 그 전제로 쓰여 있다 | 3.4 |
| 왜 `ref` 가 아니라 state 인가 | 이 값이 바뀌면 effect 가 다시 돌아야 한다. `ref` 면 `openDoc` 이 이미 맞는 상태(같은 문서를 다시 열 때)에서 아무 일도 일어나지 않는다. **호출마다 새 객체**라 같은 문서·같은 검색어여도 다시 돈다 | |
| 이미 열려 있는 문서를 고르면 | `selectDoc` 이 1354행에서 곧바로 return 하지만, `setPendingEditorSearch` 가 렌더를 일으키고 effect 조건이 이미 참이라 **바로 적용된다** | |
| `await selectDoc` 앞에서 예약하는 이유 | 뒤에 두면 `beforeLeaveDoc()`(저장 flush) 왕복이 끝날 때까지 예약이 안 되고, 그 사이 `openDoc` 이 먼저 도착하면 effect 가 한 번 헛돈다 | |
| 적용 못 한 예약이 남으면 | 아무 일도 하지 않는다. 다음 "결과로 열기" 가 덮어쓴다. 타임아웃을 두지 않는다 | |
| 부팅 중 | 검색 대화상자 자체가 `bootPhase !== 'ready'` 면 안 열린다 (`openSearch`, 2149~2153행) | |

### 4.4 `showSearchMatches` 가 하는 일 (순서 고정)

1. `openSearchPanel(view)` — **패널을 먼저 연다.** 없으면 강조가 안 그려진다 (3.1)
2. `view.dispatch({ effects: setSearchQuery.of(new SearchQuery({...})) })` — **별도 dispatch 여야 한다.** 같은 트랜잭션에 넣으면 `openSearchPanel` 이 만든 `defaultQuery`(선택 영역 글자)와 순서 싸움이 난다 (3.3)
3. `findNext(view)` — 첫 매치로 선택을 옮기고 그 자리로 스크롤한다. 커서는 새 뷰에서 0이므로(`Editor.tsx` 91행 `setCursorToStart()`) 사실상 **문서 첫 매치**다. 같은 문서를 다시 열면 커서 뒤 첫 매치이고 끝에 닿으면 처음으로 돌아간다 (CM 기본)
4. `view.focus()` — **포커스를 본문으로 되돌린다**

| 물음 | 답 |
| --- | --- |
| 왜 4번이 필요한가 | `openSearchPanel` 과 `SearchPanel.mount()` 가 패널 입력에 `focus()`·`select()` 를 한다(3.3). 그대로 두면 **문서를 열었는데 캐럿이 찾기 칸에 있다.** 게다가 `createEditor.ts` 의 `searchMoreToggle` 이 패널 DOM 을 다시 묶으면서 입력을 옮겨(`append`) 포커스가 아예 떠 버릴 수도 있다 |
| 회귀 | `e2e/docSearch.spec.js` 133·148행(F-287 A8·A9)이 `.cm-content` 포커스를 단언한다. 4번이 없으면 **두 테스트가 깨진다** (10장) |
| 첫 매치가 선택된 채로 두는 것이 위험하지 않은가 | 그 상태에서 글자를 치면 매치가 대체된다 — 어느 편집기의 찾기와도 같은 동작이고 `Ctrl+Z` 로 되돌아간다. 선택을 접어 캐럿만 두면 `.cm-searchMatch-selected` 링(현재 매치 표시)이 사라져 "어디를 찾았는지" 가 약해진다 (13장 Q7) |
| 매치가 없으면 | `findNext` 가 `false` 를 돌려주고 선택을 안 건드린다. 4.1 의 사전 판정 때문에 실제로는 거의 없다. `showSearchMatches` 는 그 값을 돌려주기만 한다(단위 테스트용) |
| 검색어가 빈 문자열이면 | 아무것도 하지 않고 `false`. 패널도 안 연다 |

### 4.5 모드별 동작과 패널이 닫히는 때

| 상황 | 동작 | 근거 |
| --- | --- | --- |
| 편집(live)·원문(raw) 모드 | 연다 | `search({ top: true })` 가 `previewCompartment` 밖이라 모드와 무관하다 (`createEditor.ts` 388~389행, F-261 2.1) |
| 읽기 전용 문서(F-212 `view` 권한) | **연다.** 찾기는 되고 **바꾸기 줄이 아예 안 그려진다** | `SearchPanel` 생성자가 `...view.state.readOnly ? [] : [바꾸기 입력·버튼]` 으로 만든다(1120행대). 추가 코드 없음 |
| 보기(view) 모드 | **열지 않는다** | 그 모드에서는 `.editor-slot` 이 `hidden` 이고 화면에는 `Viewer` 가 있다(`App.tsx` 2669·2691행). 에디터는 마운트돼 있어 뷰는 존재하지만, 안 보이는 곳에 패널을 열고 포커스를 옮기는 일이 된다. 13장 Q6 |
| 다른 문서를 연다 | **저절로 닫힌다.** 추가 코드 없음 | `<Editor key={`${currentDocId}:${nonce}`}>`(2672행) — 문서가 바뀌면 `EditorView` 가 새로 만들어지고 `searchState` 도 처음부터 시작한다 |
| 같은 문서를 검색 결과로 다시 연다 | 패널은 열린 채 **검색어만 새 값으로 바뀐다** | `setSearchQuery` → `SearchPanel.update` 가 입력 값을 갈아 끼운다 (3.3) |
| 사용자가 `Esc`·`닫기` 로 닫았다 | 닫힌 채 있는다. 다시 여는 것은 다음 "결과로 열기" 와 `Ctrl+F`·`Ctrl+H` 뿐 | `searchKeymap` 의 `Escape`(scope `editor search-panel`)라 본문 포커스에서 바로 닫힌다 |
| 검색 대화상자를 다시 연다(`Ctrl+Shift+F`) | 패널에 아무 일도 하지 않는다 | 대화상자는 CM6 를 모른다 |
| 편집 ↔ 원문 전환 | 패널 유지 | `setViewMode` 는 `previewCompartment`·`attributesCompartment` 만 reconfigure 한다 (`createEditor.ts` 479~489행) |
| 보기 모드로 갔다 돌아온다 | 패널이 그대로 다시 보인다 | 에디터를 언마운트하지 않고 `hidden` 으로만 숨긴다 |

### 4.6 좁은 화면(≤600px)

- 패널은 **자리를 차지하지 않는다.** `searchPanel.css` 가 `.cm-panel.cm-search` 를 `position: absolute; top: 10px; right: 10px; max-width: min(300px, calc(100% - 20px))` 로 편집 영역 오른쪽 위에 띄운다. `.cm-panels` 도 `position: static; background: transparent` 로 눌러 놨다
- 따라서 **줄바꿈·가로 스크롤·레이아웃 밀림이 생기지 않는다.** 폭이 좁으면 카드가 `100% - 20px` 로 줄어든다
- 남는 문제: **첫 매치가 문서 맨 윗줄이면 카드에 가릴 수 있다.** `findNext` 의 기본 `scrollToMatch` 는 떠 있는 카드를 모르기 때문이다. 이번에 `search()` 설정을 바꾸지 않는다(F-261 소유) → 11장 사람 확인
- 휴대폰에는 키보드가 없어 `F3` 로 다음 매치를 못 가지만, 패널의 `다음 찾기` 아이콘 버튼이 있다 (F-261)

## 5. 함수 시그니처

### 5.1 `src/app/searchResults.ts` 에 이어 쓴다 (순수 함수)

```ts
/** 에디터 찾기 패널에 넣을 검색어 하나. 본문에 들어 있는 첫 검색어, 없으면 null (F-294 4.1) */
export function pickEditorSearchTerm(body: string, query: ParsedQuery): string | null
```

| 규칙 | 값 |
| --- | --- |
| `query.terms.length === 0` | `null` |
| `body === ''` | `null` |
| 그 밖 | `foldCase(body)` 를 한 번만 만들고, `terms` 를 순서대로 `includes` 로 본다. 처음 걸리는 것을 돌려준다. 하나도 없으면 `null` |

- `foldCase` 는 `../lib/docSearch` 에서 가져다 쓴다(이미 export 되어 있다). **`docSearch.ts` 를 고치지 않는다**
- 새 파일을 만들지 않는 이유: 입력이 `SearchIndexEntry.body` + `ParsedQuery` 로 같은 파일의 다른 함수들과 똑같다 (F-288 5장과 같은 판단)
- 테스트 환경이 `node` 라 DOM 이 없다 — 판정은 전부 이 함수가 한다

### 5.2 `src/editor/showSearchMatches.ts` (신규)

```ts
import { findNext, openSearchPanel, SearchQuery, setSearchQuery } from '@codemirror/search'
import type { EditorView } from '@codemirror/view'

/** 찾기 패널을 열고 검색어를 넣어 매치를 강조한 뒤 첫 매치로 옮긴다. 포커스는 본문으로 되돌린다.
 *  매치를 찾았으면 true (F-294 4.4) */

```

| Q1 | 검색어가 여러 개일 때 CM 에 무엇을 넣나 | **본문에 있는 첫 검색어 하나** (4.1) | (a) `regexp: true` 로 `a\|b` 를 만들면 둘 다 강조되지만, **`RegExpCursor` 는 NFKD 정규화를 하지 않아**(3.2 실측) NFD 로 저장된 한글 문서에서 강조가 통째로 사라진다. 게다가 정규식 특수문자(`. * + ?
