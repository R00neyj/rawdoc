## 3. 글에 무엇을 적는가

다음 사람이 배포 때마다 같은 판단을 다시 하지 않도록 **기준을 문장으로 못박는다.** `CLAUDE.md` 가 5장 문장으로 이 절을 가리킨다.

### 3.1 적는 것 / 적지 않는 것

**적는다** — 사용자가 앱·공유 화면·사이트에서 **눈으로 확인할 수 있는 변화**

- 새로 쓸 수 있게 된 기능
- 화면 구성·조작 방식이 바뀐 것 (버튼이 옮겨졌다, 대화상자가 탭으로 나뉘었다)
- 사용자가 실제로 겪을 수 있었던 오작동을 고친 것

**적지 않는다**

- 명세·문서·규칙·에이전트 정의 작업
- 테스트·빌드·배포·검증 도구, 알려진 실패 기록
- 타입 이전·리팩토링처럼 화면에 나타나지 않는 내부 정리
- 배포되기 전에 같은 날 다시 뒤집힌 중간 단계 (결과만 한 줄로 적는다)
- 1~2px 간격·색 미세 조정처럼 나란히 놓고 봐야 보이는 변화
- 구현되지 않은 명세 (승인만 받은 기능은 적지 않는다)

**판단이 갈리면 적지 않는다.** 빠진 항목은 다음 배포에 얹을 수 있지만, 없는 기능이 적히면 바로 거짓말이 된다(F-270 4장 "없는 기능을 쓰지 않는다").

### 3.2 어떻게 쓰는가

- **커밋 제목을 그대로 옮기지 않는다.** `F-xxx`·파일 이름·CSS 선택자·`e2e`·`회귀`·`토큰`·`위젯` 같은 내부 말을 빼고, **무엇을 할 수 있게 됐는지**로 다시 쓴다
  - 나쁨: `F-233 상단바 서식 탭바 추가`
  - 좋음: `상단바에 서식 버튼 줄이 생겼습니다 — 굵게·제목·목록·표·링크를 눌러 넣습니다`
- 한 기능이 초안·후속·수정 여러 커밋으로 나뉘어 있으면 **한 줄로 합친다**
- 한 항목은 한 문장, `~습니다` 체(`specs/ia.md` 6장). 마침표를 찍는다
- 단축키는 `Ctrl+H` 처럼 인라인 코드로 감싼다
- 제품명은 글이므로 본문에 써도 된다(F-270 3장 예외). 다만 **이 글에서는 쓰지 않는다** — 쓸 자리가 없고, 안 쓰면 이름이 바뀌어도 글을 고칠 일이 없다

### 3.3 묶는 단위와 날짜 — 버전 번호는 매기지 않는다

- 묶음 제목은 `## YYYY-MM-DD` 하나뿐이다. **최신이 맨 위**
- **시맨틱 버전을 매기지 않는다.** 확인한 것: `package.json` 의 `"version"` 은 초기 커밋 `c9696c5` 이후 한 번도 바뀌지 않은 `0.0.0` 이고(`git log -L '/"version"/,+1:package.json'` 결과가 초기 커밋 한 건), 태그는 하나도 없다(`git tag` 빈 출력). 버전을 새로 도입하려면 올리는 규칙·올리는 사람·올리는 시점을 따로 정해야 하는데, 이 글의 목적(사용자가 무엇이 바뀌었는지 안다)에 필요하지 않다
- **날짜는 배포한 날**이다. 지난 배포 지점은 git 에 남아 있지 않다 — `deploy` 브랜치는 `push --force` 로 덮어써서 마지막 배포 한 지점만 남는다(2026-09-21 확인: `origin/deploy` = `6b12e49`, 2026-09-20). 그래서 **과거분(4장)은 변화가 저장소에 들어온 날짜로 묶었고**, 앞으로는 5장 절차대로 배포하는 날에 맞춘다
- 날짜에 적을 것이 하나도 없으면 그 묶음을 만들지 않는다

## 5. 배포 절차 항목 제안 (`CLAUDE.md`)

개요 4장이 "`CLAUDE.md` 배포 절차에 넣는 것은 F-273 승인 때 사람이 정한다" 로 남긴 항목이다. **이 명세는 문장만 제안하고 `CLAUDE.md` 를 고치지 않는다**(1.1 갱신 대상).

넣을 자리: `CLAUDE.md` "Deployment (2026-09-15)" 절의 **첫 항목**, `To deploy, push a main commit…` 바로 위. `CLAUDE.md` 는 영어가 원본이므로 영어로 적는다.

```markdown
- **Before deploying, add the day's changelog entry.** In `content/changelog.md`, put a `## YYYY-MM-DD` group at the top and write one line per user-visible change since the last deploy — what a user can now do, not what changed in the code. Leave out specs, tests, tooling, and refactors; the full inclusion and wording rules are `specs/features/F-273.md` ch. 3. Set the frontmatter `updated:` to the same date. Commit it on its own (subject `체인지로그 {날짜} 항목`) and deploy a SHA that includes it — an entry added after the push does not reach the site until the next deploy. If nothing user-visible shipped, add no group.
```

- `체인지로그 {날짜} 항목` 은 `CLAUDE.md` "Commit granularity" 의 셋째 단위("One change outside any spec")에 해당한다. 명세 구현 커밋에 끼워 넣지 않는다 — 한 커밋에 F 번호와 체인지로그가 섞이면 되돌리기가 엉킨다
- 배포 뒤에 적으면 그 글은 **다음 배포까지 사이트에 나오지 않는다.** 글이 저장소 `.md` 라 배포와 함께만 나간다(F-270 3장)
- 자동 검사는 두지 않는다. "배포하는 커밋에 체인지로그 변경이 들어 있는지" 를 기계로 보려면 배포 지점을 기록해야 하는데, 지금은 `deploy` force push 라 그 기록이 없다(3.3). 규칙 한 줄로 둔다
