# F-271 루트 랜딩과 첫 방문 판정

작성일: 2026-09-20
상태: 사람 승인 전. `specs/features/F-270.md`(설계 개요, 2026-09-20 사람 승인) 6장 로드맵의 첫 항목이고, 그 **2장 "첫 방문 판정" 전부**가 이 명세의 범위다. 개요의 결정은 바꾸지 않고 구현 단위로 풀어 쓴다
근거: `F-239`(랜딩을 워커가 완결된 HTML 로 돌려주는 이유 §2, 히어로 편집기 데모 §2.1), `worker/index.ts` 176~185행(정적 자산 폴백 앞 분기), `wrangler.jsonc` `assets.run_worker_first`, `vite.config.ts` `workbox.navigateFallback`·`navigateFallbackDenylist`, `src/app/prefs.ts`(localStorage 접근 단일 통로), `worker/auth.ts` 42~44행(`readCookie` 기존 구현), `worker/index.ts` 99~106행(`/api/login?return=`), Cloudflare 문서 "Static assets → run_worker_first"(패턴은 `/` 또는 `!/` 로 시작, `*` 글롭, 배열이면 `Sec-Fetch-Mode: navigate` 자동 판정은 꺼진다)

## 1. 범위

### 한다

- `GET /` 를 워커가 먼저 받아 **랜딩 HTML** 또는 **앱(`index.html`)** 중 하나를 돌려준다. 판정은 쿠키 `md_app` 하나로 한다
- 랜딩 HTML 안에서 조기 판정(localStorage 3개 키·앱 해시)을 하고, `로그인 없이 사용`·`로그인` 을 누르면 두 값을 쓴다
- 앱이 켜질 때 두 값이 없으면 쓴다
- `/welcome` 을 `301` 로 `/` 에 보낸다
- `run_worker_first`·서비스 워커 제외 목록을 그에 맞게 고친다

### 하지 않는다 (F-270 3~5장, 다음 명세들)

- `/guides`·`/changelog`·`/help`·`/privacy`·`/terms`·`sitemap.xml`·`robots.txt`, 공통 머리·꼬리, `404` 페이지, `content/` 빌드 단계 — 전부 F-272 이후
- 랜딩의 카피·섹션 구성·편집기 데모를 새로 설계하지 않는다. F-239 로 이미 배포된 내용을 그대로 옮기고, 이 명세가 바꾸는 것은 **주소·판정·CTA 동작**뿐이다
- 앱 사용자에게 랜딩을 다시 보여주는 기능(재방문 링크)을 두지 않는다 (F-270 2장)
- 분석·추적 스크립트, 쿠키 동의 배너 (F-270 5장)

## 2. 주소와 응답

| 요청 | 조건 | 응답 |
| --- | --- | --- |
| `GET /` | `Cookie` 에 `md_app=1` 있음 | `env.ASSETS.fetch(request)` — 앱 `index.html` |
| `GET /` | 없음 | 랜딩 HTML `200`, `content-type: text/html; charset=utf-8` |
| `GET /?app=1` | 쿠키 상관없이 | `env.ASSETS.fetch` — 앱 `index.html`. 쿠키를 저장하지 못하는 브라우저의 탈출구 (2.3) |
| `GET /welcome` | 항상 | `301`, `Location: /` |
| `/api/*`·`/pub/*`·`/v1/*`·`/p/*`·그 밖의 경로 | — | **지금 그대로.** 이 명세가 건드리지 않는다 |

### 2.1 워커 분기

`worker/index.ts` 의 정적 자산 폴백 분기(현재 176~185행, `/p/` 다음·`env.ASSETS.fetch` 앞)에 두 줄을 더한다. 순서는 `/p/` → `/welcome` → `/` → 폴백이다.

판정과 응답 만들기는 `worker/rootRoute.ts`(신규) 의 순수 함수로 빼서 단위 테스트한다 — `worker/index.ts` 자체는 D1·R2 바인딩 타입에 묶여 있어 테스트에서 통째로 불러오지 않는다(기존 `publicPage.ts`·`welcomePage.ts` 와 같은 방식).

```
rootTarget(request): 'app' | 'landing'      // Cookie 헤더만 본다
welcomeRedirect(): Response                  // 301, Location: /
withRootHeaders(response): Response          // 2.2 헤더를 덧붙인 새 Response
```

- `rootTarget` 은 `Cookie` 헤더와 **질의 문자열 `app=1`** 둘을 본다. 둘 중 하나라도 맞으면 `app` 이다 (2.3)
- 쿠키 읽기는 `src/lib/appEntry.ts`(신규, 3장) 의 `hasAppCookie(cookieHeader)` 를 쓴다. 워커는 `src/lib/**` 순수 함수만 import 한다(`specs/architecture.md` 6장)
- `env.ASSETS.fetch` 는 `run_worker_first` 를 다시 타지 않으므로 자기 자신을 부르는 되돌이가 생기지 않는다(F-238·F-239 에서 쓰던 그대로)

### 2.2 캐시 헤더

같은 주소 `/` 가 쿠키에 따라 두 가지 응답을 준다. 중간 캐시·브라우저가 엉뚱한 쪽을 다시 쓰지 않게 랜딩·앱 두 응답 모두에 붙인다.

- `Cache-Control: private, no-store`
- `Vary: Cookie`

`env.ASSETS.fetch` 가 돌려준 응답은 헤더가 잠겨 있으므로 `new Response(res.body, res)` 로 다시 만들어 붙인다. 정적 자산(`/assets/*`·`/icons/*`)은 이 경로를 타지 않으므로 캐시 그대로다.

`X-Robots-Tag` 는 붙이지 않는다 — 랜딩은 색인 대상이다(F-239 §3.1 과 같은 이유).

### 2.3 탈출구 `?app=1` (2026-09-20 사용자 결정)

쿠키를 저장하지 못하는 브라우저(쿠키 차단, 일부 확장·기업 정책)는 랜딩에서 두 값을 써도 서버가 쿠키를 못 봐서 계속 랜딩을 받는다. 4.2 의 1회 가드가 무한 왕복은 막지만 그 사람은 앱에 못 들어간다. 그래서 **질의 문자열로 판정을 건너뛰는 길을 하나 둔다**

- `GET /?app=1` 은 쿠키가 없어도 앱을 준다. 워커 분기(2.1)에서 쿠키 확인과 OR 로 묶는다
- 랜딩은 **4.2 의 가드에 걸렸을 때만** 이 링크를 보여준다. 평소에는 화면에 없다 — 정상 흐름을 흐리지 않는다
- 안내 문구(`specs/ia.md` 6장 갱신 대상): `이 브라우저는 쿠키를 저장하지 못합니다. 아래 주소를 즐겨찾기에 두고 쓰세요` + `앱으로 바로 가기` 링크(`/?app=1`)
- `?app=1` 은 값을 쓰지 않는다. 쿠키가 안 써지는 브라우저라 써도 소용이 없고, 다음에도 같은 주소로 들어와야 한다
- 앱은 이 질의 문자열을 읽지 않는다. 해시 라우팅(`#/d/…`)과 섞이지 않는다
- 색인 영향: 랜딩에만 조건부로 나타나는 링크라 크롤러는 보지 못한다. `?app=1` 응답에는 `X-Robots-Tag: noindex` 를 붙여 중복 색인을 막는다

### 2.4 `wrangler.jsonc`

```
"run_worker_first": ["/api/*", "/pub/*", "/v1/*", "/p/*", "/welcome", "/"]
```

- `"/"` 는 루트 한 경로만 매칭한다. `"/*"` 가 아니므로 `/assets/index-*.js`·`/icons/*`·`/manifest.webmanifest` 같은 정적 자산과 F-272 가 더할 사이트 경로는 영향을 받지 않는다. 배열 형태는 이미 쓰고 있어 `Sec-Fetch-Mode: navigate` 자동 판정 여부도 달라지지 않는다
- 없는 경로는 여전히 워커의 `env.ASSETS.fetch` → `not_found_handling: single-page-application` 으로 앱을 준다. F-272 에서 사이트 접두사와 `404` 를 다룬다
- `/` 가 워커를 타므로 루트 진입마다 워커 요청이 하나 는다. 무료 플랜 요청 수 상한 안이고, 랜딩은 DB·R2 를 건드리지 않는다

## 3. 두 값

| 이름 | 위치 | 값 | 쓰는 곳 |
| --- | --- | --- | --- |
| `md.landingDone` | localStorage | `1` | 랜딩(조기 판정·CTA), 앱 부팅 |
| `md_app` | 쿠키 | `1` | 같음 |

원본은 localStorage, 서버가 보는 사본이 쿠키다(F-270 2장). 이름에 제품명을 쓰지 않는다(`CLAUDE.md` 불변조건 — 저장소 식별자 고정).

### 3.1 쿠키 속성

`Path=/; Max-Age=31536000; SameSite=Lax` + **`Secure` 는 `location.protocol === 'https:'` 일 때만** 붙인다.

- 이유: 로컬 확인은 `npm run dev:worker`(http://localhost:8790)·e2e preview(http://localhost:4317) 이고, LAN IP(`http://192.168.x.x`)로 여는 경우도 있다. `Secure` 쿠키는 브라우저가 https 가 아닌 출처에서 저장하지 않는다(Chrome 은 localhost 를 예외로 두지만 LAN IP 는 아니다). 운영(`https://rawdoc.app`)에서는 언제나 `Secure` 가 붙는다
- `HttpOnly` 는 쓸 수 없다 — JS 가 써야 한다
- 만드는 곳은 `src/lib/appEntry.ts` 의 `buildAppCookie({ secure })` 한 군데다. 랜딩 인라인 스크립트도 이 파일의 상수를 템플릿으로 받아 쓴다

### 3.2 `src/lib/appEntry.ts` (신규, 순수)

```
APP_COOKIE = 'md_app'              // 쿠키 이름
APP_COOKIE_VALUE = '1'
LANDING_DONE_KEY = 'md.landingDone'
EARLY_APP_KEYS = ['md.landingDone', 'md.firstRunDone', 'md.account']   // 조기 판정용 (F-111, F-205)
buildAppCookie({ secure }): string  // 'md_app=1; Path=/; Max-Age=31536000; SameSite=Lax[; Secure]'
hasAppCookie(cookieHeader): boolean // 'a=1; md_app=1' → true, 'md_appx=1' 같은 접두 일치는 false
```

앱·워커·랜딩 세 곳이 이 한 파일을 본다. 키 문자열을 다른 파일에 다시 적지 않는다.

## 4. 랜딩 HTML (`worker/welcomePage.ts`)

파일 이름과 데모 자산 이름(`src/welcome/demo.ts`, `assets/welcome-demo.js`)은 **그대로 둔다** — 내부 이름이고 제품명과 무관하며, 자산 이름을 바꾸면 서비스 워커 precache·워커가 적는 경로까지 같이 흔들린다. 주석과 문서 문구만 "랜딩(`/`)" 으로 고친다.

### 4.1 메타

- `og:url`·`<link rel="canonical">` 을 `https://rawdoc.app/` 로 바꾼다(지금은 `/welcome`)
- `<title>`·`description`·`og:image`·`theme-color` 는 그대로. 값은 계속 `brand.config.ts` 에서만 읽는다

### 4.2 조기 판정 인라인 스크립트 (`<head>` 맨 위)

랜딩 본문이 그려지기 전에 판정해 깜빡임을 줄인다. `<head>` 안, 스타일보다 앞에 둔다.

1. `EARLY_APP_KEYS` 중 하나라도 localStorage 에 값이 있으면 → 두 값을 쓰고 앱으로
2. 주소에 앱 해시(`location.hash` 가 `#/` 로 시작)가 있으면 → 두 값을 쓰고 앱으로. 공유받은 앱 주소(`#/d/…`·`#/s/…`·`#/p/…`·`#/help` 등)가 랜딩에 막히지 않게 한다
3. 둘 다 아니면 아무것도 하지 않고 랜딩을 보여준다

"앱으로" 는 `location.reload()` 다. 서버가 쿠키를 보고 앱을 준다.

- 개요 2장은 `location.replace('/')` 라고 적었지만, 해시가 붙은 주소에서 같은 주소로 `replace` 하면 브라우저가 재요청 없이 해시 이동만 할 수 있어 앱이 뜨지 않는다. `reload()` 는 해시를 지키면서 다시 요청한다 — 결과는 개요와 같다
- localStorage 접근은 `try/catch` 로 감싼다(시크릿 창·차단). 랜딩은 워커가 돌려주는 단일 HTML 이라 `prefs.ts` 를 쓸 수 없다
- **되돌이 방지**: 판정을 통과해 `reload()` 하기 전에 `sessionStorage['md.landingReloaded'] = '1'` 을 쓰고, 이 값이 이미 있으면 다시 `reload()` 하지 않는다. 쿠키가 아예 차단된 브라우저에서 랜딩 ↔ 새로고침 무한 왕복을 막는다. 그 브라우저는 랜딩에 머무르고, 이때만 `?app=1` 탈출구 안내를 보여준다 (2.3)

### 4.3 CTA 두 개

히어로와 하단 CTA 를 F-270 2장의 이름으로 맞춘다.

| 버튼 | 동작 |
| --- | --- |
| `로그인 없이 사용` (주 버튼, `<a href="/">`) | 클릭 → `preventDefault` → 두 값 쓰기 → `location.reload()` |
| `로그인` (보조, `<a href="/api/login?return=">`) | 클릭 → `preventDefault` → 두 값 쓰기 → `location.href = '/api/login?return='`. 기존 로그인 흐름(Access → `handleLogin` 이 `302` 로 `/`)을 탄다. 그때는 쿠키가 있으므로 앱이 열린다 |

- 두 버튼 모두 `<a href>` 를 그대로 둔다 — 자바스크립트가 꺼진 브라우저·크롤러에게도 링크로 보인다. 다만 JS 가 꺼져 있으면 값을 쓸 수 없어 `/` 가 랜딩을 다시 준다(알려진 제약, 이번에 대응하지 않는다)
- 값 쓰기는 4.2 와 같은 함수 하나를 쓴다
- 하단 CTA 는 `로그인 없이 사용` 하나만 둔다. `설치도 로그인도 없이 시작합니다` 같은 보조 문구는 지금 문구를 유지한다

## 5. 앱 부팅 쓰기

`src/main.tsx` 에서 `createRoot(...).render(...)` **앞에** 한 번 부른다(서체·테마 반영 줄 옆). 서비스 워커로 앱을 받은 기존 사용자·설치한 PWA 도 다음 요청부터 서버 판정이 맞게 된다.

- `src/app/markAppEntry.ts`(신규): 두 값이 **없을 때만** 쓴다. localStorage 는 `setPref('md.landingDone', '1')`, 쿠키는 `document.cookie = buildAppCookie({ secure: location.protocol === 'https:' })`
- `src/app/prefs.ts` 의 `PrefMap`·`ALLOWED_KEYS` 에 `md.landingDone: '1'` 을 더한다. localStorage 접근은 전부 `prefs.ts` 를 거친다는 규칙을 지킨다
- 앱 코드 어디서도 이 값을 읽지 않는다. 쓰기만 한다

## 6. 서비스 워커 (`vite.config.ts`)

`workbox.navigateFallbackDenylist` 에서:

- `/^\/welcome$/` 은 **그대로 둔다** — 서비스 워커가 `index.html` 로 가로채면 워커의 `301` 이 안 나간다
- `/` 는 넣지 않는다. 서비스 워커가 있는 브라우저는 `/` 를 캐시된 `index.html` 로 받아 워커 판정 없이 바로 앱이다 — F-270 2장이 의도한 동작이다
- 나머지(`/api/`·`/pub/`·`/v1/`·`/cdn-cgi/`)는 그대로

`navigateFallback: 'index.html'`, `start_url`·`scope`·`file_handlers`(`/`)도 그대로다.

## 9. 테스트 방법

### 9.1 판정 로직은 단위 테스트

쿠키 분기·`301`·헤더·쿠키 문자열은 `worker/rootRoute.test.ts`·`src/lib/appEntry.test.ts` 로 잡는다. 이쪽이 이 명세의 본체다.

### 9.2 랜딩 동작 e2e 의 제약

`npm run test:e2e` 는 `vite preview` 가 `dist` 를 정적으로 주는 서버다 — **워커가 없어서 `/` 는 언제나 앱 `index.html`** 이다. 그래서 랜딩 동작은 Playwright 가 랜딩 HTML 을 `/` 에 한 번만 물려서(`page.route(url, handler, { times: 1 })`) 판정한다. 같은 방식이 `e2e/account.spec.js` 에서 `/api/me` 응답을 대신 주는 데 이미 쓰이고 있다.

- 랜딩 HTML 은 테스트가 `renderWelcomePage()` 를 직접 불러 `await res.text()` 로 얻는다. 원본이 하나라 문구가 어긋나지 않는다
- `times: 1` 이라 `location.reload()` 뒤에는 preview 의 앱이 뜬다 — 운영에서 쿠키를 보고 앱을 주는 것과 같은 결과를 확인할 수 있다
- Playwright 설정이 `serviceWorkers: 'block'` 이라 서비스 워커가 끼어들지 않는다
- `@playwright/test` 가 테스트에서 `worker/welcomePage.ts`(TS)를 import 해 주는지 **구현 첫 단계에서 확인**한다. 안 되면 A5~A8 을 사람 확인으로 내리고 그 사실을 보고한다 — 이를 위해 새 의존성을 넣지 않는다
- 워커 자체를 띄우는 e2e(예: `wrangler dev` 를 두 번째 webServer 로)는 이번에 만들지 않는다

### 9.3 워커 실제 응답

`npm run dev:worker`(8790) 를 띄우고 `curl` 로 본다. 구현 에이전트가 직접 확인할 수 있다(A9).
