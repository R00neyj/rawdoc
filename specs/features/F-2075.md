## 3. 계약

### 3.1 마이그레이션

파일 이름 `migrations/00NN_notifications_recipient_order.sql`(번호는 1장). 내용:

```sql
-- F-2075 받는 사람별 최근순 색인 (specs/features/F-2075.md 3.1). id 까지 넣어 300번째 행 찾기·목록이 정렬 없이 색인만 걷는다
CREATE INDEX notifications_recipient_order ON notifications(recipient_email, created_at DESC, id DESC);
DROP INDEX notifications_recipient;
```

- 색인 이름 `notifications_recipient_order` 는 계약이다 — A5 가 계획 문자열에서 찾는다
- **만들기가 지우기보다 먼저다.** 파일 안에서 중간에 멈춰도 색인 없는 순간이 없다
- 옛 색인 `notifications_recipient(recipient_email, created_at DESC)` 는 새 색인의 앞부분이라, 그것을 타던 문장 전부가 새 색인을 탄다(머리 k). 남겨 두면 알림 한 행 넣을 때마다 쓰기가 1 는다(머리 g) — 그래서 지운다
- `notifications_doc` 은 그대로
- `IF NOT EXISTS` 를 쓰지 않는다 — 기존 마이그레이션과 같은 모양
- **배포 순서는 어느 쪽이어도 안전하다.** 옛 코드 + 새 색인: 옛 `TRIM` 도 새 색인을 타 오히려 준다(머리 k). 새 코드 + 옛 색인: 새 문장이 옛 색인으로 돈다(머리 c — 색인 효과만 빠진다). 그래도 `deploy` 스킬의 "새 마이그레이션은 배포 전에 `d1 migrations apply --remote`" 규칙대로 마이그레이션을 먼저 적용한다
- 한 번 드는 비용: 원격 알림 행 수 × 약 1 쓰기, × 약 2 읽기(머리 h). 배포 전 메인이 원격에서 `SELECT COUNT(*) FROM notifications` 로 한 번 보고 배포 보고에 적는다

### 3.2 알림 넣기 batch 의 정리 문장 — `TRIM_NOTIFICATIONS_SQL`

바인딩은 지금과 같다 — `?1` = 받는 사람 이메일 JSON 배열(`notificationStatements` 가 `new Set` 으로 겹침을 뺀 것). batch 안 자리(넣기 문장들 바로 뒤)와 문장 수(1)도 같다.

```sql
WITH cut(r, i) AS MATERIALIZED (
  SELECT value, (SELECT id FROM notifications WHERE recipient_email = value
                 ORDER BY created_at DESC, id DESC LIMIT 1 OFFSET 299)
  FROM json_each(?1))
DELETE FROM notifications WHERE rowid IN (
  SELECT n.rowid FROM cut
  JOIN notifications t ON t.id = cut.i
  JOIN notifications n ON n.recipient_email = cut.r AND n.created_at <= t.created_at
  WHERE (n.created_at, n.id) < (t.created_at, t.id))
```

- `299` 는 코드에서 `NOTIFICATIONS_PER_RECIPIENT_MAX - 1` 로 만든다. 숫자를 글자로 쓰지 않는다
- 모양의 까닭(각각 실측):
  - **`cut` 을 `MATERIALIZED` 로** — 받는 사람마다 기준 행 찾기를 한 번만 한다. 지금 문장이 비싼 까닭(머리 b)이 이 찾기를 행마다 되풀이하는 것이다
  - **기준 행은 `id` 하나만 찾고 `t` 로 다시 붙인다** — `created_at`·`id` 를 부질의 둘로 찾으면 300번째까지 두 번 걷는다(머리 m, 2배)
  - **`n.created_at <= t.created_at`** — 색인 범위로 지울 후보만 걷게 한다. 행 값 비교만 두면 판정은 같지만 이 조건이 범위 검색을 보장한다(계획 `SEARCH n USING COVERING INDEX notifications_recipient_order (recipient_email=? AND created_at<?)`)
  - **`rowid IN`** — `notifications` 는 rowid 표다(`0012` 에 `WITHOUT ROWID` 없음). 지울 행을 정수 키로 바로 찾는다
- 창 함수·받는 사람마다 문장 하나는 쓰지 않는다(3.4)

### 3.3 매일 정리의 넘침 문장 — `OVERFLOW_SQL`

`cut` 의 출처만 다르고 `DELETE` 부분은 3.2 와 **같은 조각**이다.

```sql
WITH cut(r, i) AS MATERIALIZED (
  SELECT o.recipient_email, (…3.2 와 같은 부질의, recipient_email = o.recipient_email…)
  FROM notifications o GROUP BY o.recipient_email HAVING COUNT(*) > 300)
DELETE FROM notifications WHERE rowid IN (…3.2 와 같은…)
```

- "300개를 넘는 받는 사람만 고른다"(F-502 10장 4번)는 그대로 — 평소(넘는 사람 없음) 비용은 표 전체 한 번 훑기로 지금과 같다(머리 e)
- 조각 나눔 규칙: "300번째 행 id 부질의(받는 사람 식을 받는다)" 와 "`cut` 뒤의 `DELETE` 꼬리" 를 `worker/commentRows.ts` 에 한 번만 두고 `commentGc.ts` 가 가져다 쓴다. 지금 `TRIM_NOTIFICATIONS_WHERE` 를 나누는 것과 같은 방향이다. 내보내는 이름은 구현자가 정하되 `OFFSET` 이 든 SQL 글자는 `commentRows.ts` 한 곳에만 있다(A7)
- `cleanupComments` 의 batch 문장 수·자리·돌려주는 객체 모양은 그대로

## 4. 같은 결과인가 — 따진 것

**한 받는 사람 e 안에서.** `id` 는 기본키라 `(created_at DESC, id DESC)` 는 e 의 행들에 **동점 없는 전체 순서**를 준다. 그래서 "최근 300개" 는 모호함 없이 정해진 집합이다.
- 지금 문장: e 의 행 x 를 지우는 조건 = x 가 그 순서의 앞 300개에 없다
- 새 문장: e 의 행이 300개 미만이면 `OFFSET 299` 가 행을 못 찾아 `cut.i` 가 NULL → `t` 가 붙지 않아 지울 것 없음(지금 문장도 전부 앞 300개 안이라 지울 것 없음). 300개 이상이면 `t` = 그 순서의 300번째 행. 순서가 `(created_at DESC, id DESC)` 이므로 "x 가 t 보다 뒤" ⇔ `(x.created_at, x.id) < (t.created_at, t.id)` (오름 비교, 둘 다 BINARY 비교 — 지금 `ORDER BY` 와 같은 비교). 앞 300개 = t 와 그 앞 → 지우는 것 = t 보다 뒤 = 앞 300개 밖. 같다
- **동점 `created_at`**: 같은 시각 행들은 `id` 로 갈린다. 행 값 비교의 둘째 자리가 정확히 그 가름이다. `n.created_at <= t.created_at` 은 행 값 비교가 참인 행을 하나도 빼지 않는 느슨한 조건이라 결과에 영향이 없다(범위 검색용)
- 넣기 batch 안의 새 행도 똑같이 다룬다 — 넣기 문장 뒤에 도는 것은 지금과 같다(같은 스냅숏의 `now` 로 넣은 행끼리 동점이면 `id` 로 가른다. 지금도 같다)

**받는 사람 여럿.** `cut` 은 받는 사람마다 한 행이고, `n` 은 `n.recipient_email = cut.r` 로 그 받는 사람의 행만, `t` 도 그 받는 사람의 300번째 행이다. 받는 사람끼리 섞이지 않는다 — 지금 문장의 `n.recipient_email = notifications.recipient_email` 과 같다. JSON 에 없는 받는 사람은 `cut` 에 없어 건드리지 않는다(지금도 `recipient_email IN (…json_each…)`). JSON 에 같은 이메일이 두 번 있으면 `n` 이 두 번 나오지만 `rowid IN` 이 한 번으로 만든다(지금 코드는 `new Set` 으로 이미 겹침을 뺀다).

**매일 정리.** `cut` 이 "300개 넘는 받는 사람 전부" 로 바뀔 뿐 판정은 같다. 지금 문장도 같은 조건으로 고른 받는 사람에게 같은 판정을 한다.

**경계 하나(확인함).** `id TEXT PRIMARY KEY` 인 rowid 표는 SQLite 에서 `id` 가 NULL 인 행을 받아들인다. 그런 행이 있으면 지금 문장(`NOT IN` 에 NULL)과 새 문장이 다르게 돈다. 알림 행을 넣는 곳은 `INSERT_NOTIFICATIONS_SQL` 하나이고, 그 `id` 는 `notificationStatements` 가 `crypto.randomUUID()` 로 모든 행에 채운다 — NULL 행은 생기지 않는다. 테스트 픽스처도 모두 `id` 를 준다.

**실측.** 머리 i — 무작위 300회와 동점 세 경우 전부 같음.

## 7. F-2057 과의 관계

- **F-2057 ① (넣기 뒤 리비전 올리기)** 은 `TRIM` **뒤**에 붙는 별도 문장이고 `?1` 에 `TRIM` 과 같은 받는 사람 JSON 을 쓴다. 이 명세는 `TRIM` 의 바인딩(`?1` 하나, 같은 JSON)과 자리·문장 수를 바꾸지 않으므로 ① 의 모양·바인딩·F-2057 U6 이 그대로 맞다. 결과도 서로 바꾸지 않는다 — ① 은 `users` 만 쓰고, `TRIM` 은 `notifications` 만 지운다
- **F-2057 ⑦ (매일 정리)** 은 `OLD_NOTIFICATIONS_SQL`·`ORPHAN_NOTIFICATIONS_SQL` 앞에 리비전 문장을 넣어 batch 결과 자리가 밀린다. 이 명세는 `OVERFLOW_SQL` 글자만 바꾸므로 그 자리 맞춤과 부딪히지 않는다. ⑦ 이 `OVERFLOW_SQL` 앞에 리비전 문장을 두지 않는 까닭 둘 중 "비싸다"(m13) 는 이 명세 뒤 사라지지만, "평소 0행인 안전망이라 필요 없다" 는 그대로라 F-2057 결정은 바꾸지 않는다(10장에 적어 둠)
- **순서**: 기본은 F-2057 뒤. 마이그레이션 번호는 F-2057 이 `0014`, 이 명세가 그 다음. 순서가 뒤집히면 이 명세가 `0014`, F-2057 이 `0015`(F-2057 1장 규칙이 이미 그 경우를 적어 둠). 코드는 어느 순서든 뒤에 오는 쪽이 앞 커밋 위에서 자기 줄만 고친다
- **F-2058** 도 마이그레이션을 더한다 — 셋 모두 "구현 순서대로 다음 번호" 규칙이라 충돌하지 않는다

### 12.1 코드를 읽거나 돌려 확인한 것
- 머리 a~m 전부
- 알림 300개 정리 문장은 `commentRows.ts` `TRIM_NOTIFICATIONS_SQL`(넣기 batch)과 `commentGc.ts` `OVERFLOW_SQL`(매일) 둘뿐이고, 조건 조각 `TRIM_NOTIFICATIONS_WHERE` 를 가져다 쓰는 곳은 `commentGc.ts` 하나다(`grep -rn "TRIM_NOTIFICATIONS\|OVERFLOW_SQL" worker`)
- `notificationStatements` 는 받는 사람을 `new Set` 으로 겹침 없이 만들고 `TRIM` 을 넣기 조각들 **뒤** 한 문장으로 둔다
- 알림 행의 `id` 는 모두 `crypto.randomUUID()` — NULL 이 생기는 길이 없다(4장 경계)
- `notifications` 는 rowid 표(`0012` 에 `WITHOUT ROWID` 없음)
- `openTestDb()` 는 `migrations/*.sql` 을 번호 순서로 전부 실행하고, `account.test.ts` 만 `'0012'` 까지로 자른다
- `LIST_SQL`·`UNREAD_SQL`·`READ_ALL_SQL`·`READ_IDS_SQL` 은 `recipient_email = ?` 로 시작해 새 색인 앞부분을 쓴다(머리 k, node:sqlite 계획)

### 12.2 가정으로 남긴 것
- **원격 D1 이 로컬 workerd 와 같은 행 수를 센다** — F-2057·F-2058 과 같은 가정. 다르면 5장 수치가 바뀌지만 제곱 → 1차로 바뀌는 방향은 계획(A5)으로 고정된다
- **D1 원격이 `AS MATERIALIZED` 를 받는다** — 로컬 workerd 에서만 확인. 로컬 D1 은 `sqlite_version()` 을 막아 판을 못 봤다(F-502 s6). 원격이 받지 않으면 첫 스냅숏에서 문장이 실패해 알림 넣기 batch 전체가 되돌려진다 — 배포 뒤 첫 멘션 하나로 드러난다. 배포 보고에 "멘션 하나 보내 알림함에 뜨는지" 를 메인이 확인한다
- **`wrangler d1 migrations apply` 가 한 파일을 한 덩어리로 적용한다** — 확인하지 않았다. 그래서 3.1 이 만들기를 지우기보다 먼저 둔다(중간에 멈춰도 색인이 둘이거나 새것 하나)
- 원격 알림 행 수는 모른다 — 색인 만들기 한 번의 쓰기 수는 배포 전 3.1 의 `COUNT(*)` 로 확인
- 5.1 의 "한 시간에 스냅숏 5번" 은 F-2057 5장의 가정을 그대로 쓴 것이다

### 12.3 기존 명세·코드와 부딪힌 것
- 과제 설명의 `worker/notifications.ts` 의 `TRIM_NOTIFICATIONS_SQL`·`notificationStatements` 는 실제로는 `worker/commentRows.ts` 에 있다. `notifications.ts` 에는 목록·읽음 문장만 있다 — 이 명세는 `notifications.ts` 를 고치지 않는다
- F-502 10장 4번 "표 전체에 상관 부질의를 돌리지 않는다" 는 넘는 사람만 고른다는 뜻으로 지켜졌지만, 고른 사람의 행마다 상관 부질의가 돌아 305행일 때 186,226 을 읽었다(머리 e). 이 명세가 그 부분을 없앤다
