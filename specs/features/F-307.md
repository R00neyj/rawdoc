## 입력 계약 — F-305 에게서 받는 것 (F-305 `2ca7a41` 에 맞춤)

F-305 에서 provider 는 편집기가 아니라 **App 층 `useLiveDoc`** 가 만든다. 연결 시도 한 번 = `openLiveSocket` 한 번 = `YProvider` 하나이고, 방 Doc(= F-303 의 공유 Doc)은 `useLiveDoc` 가 들고 편집기에는 `createEditor` 옵션 `live: { roomDoc, onRemoteTitle }` 로 내려간다(F-305 6.2·9.2·9.3). F-307 은 이 위에 셋을 얹는다

| # | 무엇 | 어디서 | F-305 상태 |
| --- | --- | --- | --- |
| ① | **awareness 하나를 방 Doc 과 같이 만들고, 매 연결 시도에 같은 인스턴스를 `LiveSocketOptions.awareness` 로 넘기고, 편집기에는 `live.awareness` 로 내린다** | `useLiveDoc.ts`(만들기·넘기기), `createEditor.ts`(받기) — 5.1 | 자리만 비워 둠(F-305 6.1 `awareness?: Awareness` — "F-305 는 넘기지 않는다"). 받았을 때 `liveSocket` 이 `setLocalState(null)`·`destroy` 를 안 하는 규칙은 F-305 6.2 끝에 **이미 있다** |
| ② | **provider 는 내 clientID 의 변화만 서버로 보낸다** — 받은 원격 상태를 되돌려 보내지 않는다 | `liveSocket.ts` — 4.4 | **없다.** F-307 이 `liveSocket.ts` 를 "F-305 뒤" 로 소유 표에 올려 직접 더한다 |

- `YLinkPort`·`connectRemote` 팩토리·`window.__yProviderFactory` 를 거쳐 awareness 를 넘기는 배선은 쓰지 않는다. 그 길(`?ysync` 개발 연결, `e2e/remoteGate.spec.js`)에는 awareness 가 없고 원격 커서·아바타도 없다(2장)

## 3. awareness 에 싣는 것

### 3.1 모양 — 클라이언트는 커서만, 신원은 서버가 찍는다

```ts
// src/lib/docRoomProtocol.ts 에 더한다 — 서버·클라이언트 공용 계약
export const AWARENESS_STATE_MAX_BYTES = 512

export type RelativePositionJSON = Record<string, unknown>   // yjs relativePositionToJSON 결과
export type PeerCursor = { anchor: RelativePositionJSON; head: RelativePositionJSON }

// 클라이언트가 자기 awareness 에 넣는 것
export type ClientAwarenessState = { cursor?: PeerCursor | null }

// 서버가 도장을 찍어 다른 연결에 내보내는 것
export type PeerState = { user: { id: string; email: string }; cursor: PeerCursor | null }
```

- 클라이언트는 **`cursor` 만** 싣는다. 이름·이메일·색을 싣지 않는다
- 서버(`DocRoom`)가 연결 상태 `{ userId, email }`(F-304 5.3 — Worker 가 `X-WS-User-*` 헤더로 넘긴 값)으로 **`user` 를 덮어쓰고, `cursor` 말고 다른 키를 버린다**(4.1). 그래서
  - 신원을 꾸밀 수 없다. 편집 권한자가 남의 이메일로 커서를 띄우는 길이 막힌다 — `y-protocols` `modifyAwarenessUpdate` 주석이 적은 쓰임새 그대로다
  - 앱이 계정 정보를 에디터로 넘길 필요가 없다. `createEditor` 는 계정을 모른다
- 색은 **싣지 않는다.** 받는 쪽이 `user.id` 로 계산한다(3.3). 모든 클라이언트가 같은 함수를 쓰므로 같은 사람은 어느 창에서 봐도 같은 색이다(F-301 6.1)
- 512 B 를 고른 이유: 실측 (d) 커서 상태가 168 B 이고, clientID·clock 이 10자리씩이어도 상대 위치 하나는 약 80 B 다. 3배 여유를 두고 그보다 큰 상태는 서버가 버린다(4.1)
- F-301 6.2 "awareness 로 보내는 값은 이메일과 색 인덱스, 선택 범위뿐" 을 이 절로 바꾼다 — 이메일은 서버가 찍고, 색 인덱스는 싣지 않는다(13장)

### 3.2 이름 — 이메일에서 만든다

`users` 표에는 `id`·`email` 뿐이다(`worker/auth.ts` `findOrCreateUser`). 표시 이름이 없으므로 이메일에서 만든다

| 자리 | 무엇 | 예 |
| --- | --- | --- |
| 아바타 글자 | 이메일 로컬 부분(마지막 `@` 앞)의 **첫 코드 포인트**를 `toUpperCase()` | `yjw1555@gmail.com` → `Y`, `홍길동@example.com` → `홍` |
| 원격 커서 라벨 | 이메일 로컬 부분. 24 코드 포인트를 넘으면 앞 24개 + `…` | `yjw1555`, `abcdefghijklmnopqrstuvwx…` |
| 아바타 툴팁·접근성 이름 | 이메일 전체 | `yjw1555@gmail.com` |

- `@` 가 없으면 문자열 전체가 로컬 부분이다
- 코드 포인트 단위로 자른다(`Array.from`) — 이모지 같은 서로게이트 쌍이 반으로 잘리지 않는다

**개인정보 판단**: 같은 문서의 편집자끼리는 서로의 **이메일 전체**를 본다(툴팁). 지금은 초대받은 사람이 다른 초대자 목록을 볼 수 없으므로(`worker/grants.ts` — 초대 목록은 소유자 전용) 이것은 새로 드러나는 정보다. 그래도 F-301 6.2 가 승인한 대로 간다 — 소유자가 같은 문서에 부른 사람들이고, 같은 사람의 이메일이 두 도메인에서 로컬 부분만 같을 때 가를 수단이 이메일뿐이다. 로컬 부분만 보이는 쪽은 15장 Q3

### 3.3 색 — `--people-1`~`--people-7`

```css
/* src/styles/tokens.css — 새 hex 없음. --map-group-* 와 같은 별칭 방식 (design.md 3.3) */
--people-1: var(--callout-note);
--people-2: var(--callout-tip);
--people-3: var(--callout-success);
--people-4: var(--callout-question);
--people-5: var(--callout-warning);
--people-6: var(--callout-danger);

```

```ts
// src/lib/peers.ts
export const PEOPLE_COLORS = 7
export function peerColorIndex(userId: string): number   // 1..PEOPLE_COLORS
```

- 규칙: `userId` 문자열의 `charCodeAt` 값들에 **FNV-1a 32비트**(시작값 `0x811c9dc5`, 곱 `0x01000193`, 부호 없는 32비트)를 돌리고 `% 7 + 1`. 이 규칙이 곧 계약이다 — 바꾸면 모든 사람의 색이 바뀐다. 시험값: `''` → 3, `'a'` → 6(FNV-1a `'a'` = `0xe40c292c` = 3,826,002,220), `'00000000-0000-4000-8000-000000000000'` → 3
- 해시 입력은 이메일이 아니라 `users.id`(UUID)다 — 무작위 값이라 고르게 퍼진다(실측 (e) 칸마다 ±1.6% 안쪽)
- `--callout-quote`(`--ink-2`, 회색)는 넣지 않는다 — 본문 글자와 구별되지 않는다. 그래서 7색이다
- 테마: `--callout-*` 는 다크에서 다시 정의돼 있어(`tokens.css` `:root[data-theme='dark']`) 별칭이 따라 바뀐다. 대비는 `tokens.test.ts` 가 `--callout-*` 를 세 테마에서 이미 검사한다
- **겹침**: 3명이면 38.8% 확률로 두 사람이 같은 색이다(실측 (e)). 라벨·아바타 글자·툴팁으로 가른다. 겹치지 않게 방 안에서 다시 고르는 안은 15장 Q2
- 쓰는 곳은 `data-people="{1..7}"` 속성 하나로 정한다. CSS 가 속성값을 `--people-N` 으로 잇는다(6.6·7.2). 인라인 `style` 에 색을 적지 않는다

## 4. 서버 — 도장·소유·되돌림 버리기·나간 사람 지우기

`y-partyserver` 기본 중계만으로는 세 가지가 틀린다(읽은 코드):

1. **신원을 꾸밀 수 있다** — `handleMessage` 는 받은 awareness 바이트를 검사 없이 모든 연결에 되돌린다
2. **provider 가 받은 원격 상태를 서버로 되돌려 보낸다** — `_awarenessUpdateHandler` 는 `change` 의 `added`·`updated`·`removed` 전부를 origin 과 무관하게 보낸다. 원격 적용도 `change` 를 낸다(실측 (f)). 커서 한 번 움직일 때 서버가 받는 메시지가 접속자 수 N 배가 된다
3. **hibernation 뒤 나간 사람이 남는다** — 깨어나면 서버 awareness 가 비어 있고(F-304 5.2), `onClose` 의 `removeAwarenessStates` 는 없는 상태를 지우지 못해 아무것도 보내지 않는다. 클라이언트 쪽 30초 만료 타이머는 provider 가 껐다(`clearInterval(awareness._checkInterval)`). **그래서 남은 사람 화면에 나간 사람의 아바타·커서가 새로고침·재연결 전까지 남는다.** 탭을 닫을 때는 provider 의 `unload` 처리기가 지우기를 보내지만, 절전·네트워크 끊김·브라우저 종료로는 오지 않는다

### 4.1 들어온 awareness 메시지 처리

`DocRoom` 은 첫 varUint 가 awareness(1)인 이진 메시지를 `YServer` 에 넘기지 않고 직접 처리한다. 나머지(sync, `__YPS:` 문자열)는 지금처럼 넘긴다. 항목(clientID, clock, state)마다:

| 조건 | 처리 |
| --- | --- |
| clock 이 이 방에 기록된 그 clientID 의 clock 보다 크다, 또는 기록이 없다 | 받는다 |
| clock 이 기록과 같고 `state === null` 이고 보낸 연결이 그 clientID 의 주인이다 | 받는다 — `disconnectBc` 는 clock 을 올리지 않고 `null` 을 보낸다(읽은 코드). `y-protocols` 도 이 경우를 지우기로 친다 |
| 그 밖(clock 이 기록 이하) | **버린다** — 되돌림(2번)이거나 늦게 온 것이다 |
| 받은 `state` 가 `null` 이 아니고, JSON 이 `AWARENESS_STATE_MAX_BYTES` 를 넘는다 | 버린다 |
| 받은 `state` 가 `null` 이 아니다 | `{ user: { id: 연결의 userId, email: 연결의 email }, cursor }` 로 바꾼다. `cursor` 는 `anchor`·`head` 가 둘 다 객체인 객체일 때만 남기고 아니면 `null` |

- 받은 항목만으로 새 awareness 업데이트를 만들어 **서버 awareness 에 적용하고(origin = 그 연결) 모든 연결에 보낸다.** 받은 항목이 없으면 아무것도 보내지 않는다
- 서버 awareness 에 적용하는 이유: `onConnect` 가 새 연결에 서버 awareness 전체를 보낸다(`YServer.onConnect`) — 깨어 있는 동안에는 새 사람이 곧바로 모두를 본다
- CPU: 도장 한 번 0.0047ms(실측 (d), node)

### 4.2 clientID 소유와 clock 기록 — 연결 상태에 둔다

- 연결마다 그 연결이 가진 clientID 와 마지막으로 받은 clock 을 **연결 상태(`connection.setState`)의 `awarenessClocks` 키**에 둔다. 연결 상태는 첨부로 hibernation 을 넘어 산다(F-304 5.3). 앞 상태를 펼쳐 섞는다 — `{ userId, email, role }`·`__ypsAwarenessIds` 를 지우지 않는다
- "기록된 clock" = 열린 연결 중 그 clientID 를 가진 연결의 `awarenessClocks` 값
- **주인은 그 clientID 를 마지막으로 받아 준 연결이다.** 다른 연결이 가지고 있던 id 를 받아 주면 옛 연결의 기록에서 지운다. 이유: 같은 탭이 끊겼다 다시 붙으면 같은 공유 Doc 이라 clientID 가 같다. 서버가 옛 연결의 끊김을 새 연결보다 늦게 알 수 있고, "처음 가진 연결이 주인" 이면 새 연결의 상태가 옛 연결이 닫힐 때까지 버려진다
- 대가: 편집 권한자가 남의 clientID 에 더 큰 clock 을 보내 그 사람 커서를 가져갈 수 있다. 도장은 보낸 사람 것으로 찍히므로 **신원은 못 꾸민다.** 편집 권한자는 본문을 통째로 지울 수도 있는 사람이라 이 정도는 받아들인다
- `state === null` 을 받아 주면 그 clientID 를 주인 연결의 기록에서 뺀다

### 4.3 연결이 닫힐 때 — `onClose`

- `super.onClose`(awareness 정리만 한다 — 읽은 코드) **대신**: 닫힌 연결의 `awarenessClocks` 에 남은 clientID 마다 `(clientID, 기록된 clock, state = null)` 항목을 만들어 서버 awareness 에서 지우고 **남은 연결 모두에게 보낸다.** 받는 쪽 `y-protocols` 는 clock 이 같고 `null` 이면 지운다
- 서버 awareness 에 그 상태가 없어도(깨어난 직후) 보낸다 — 이것이 3번 문제의 답이다. 기록이 첨부에 있으므로 hibernation 과 상관없다
- 다른 연결이 이미 가져간 clientID 는 닫힌 연결의 기록에 없으므로 지우지 않는다(4.2)
- 보통 나가기(문서 옮기기·세션 끝·오프라인 — F-305 제어기가 `LiveSocket.close()` 를 부름)에서는 이보다 먼저 클라이언트가 지운다: `provider.destroy()` → `disconnect()` → `disconnectBc()` 가 내 clientID `null`(clock 그대로)을 아직 열린 소켓으로 보내고 그다음 닫는다(읽은 코드). **그래서 awareness 를 받은 `LiveSocket.close()` 는 `provider.destroy()` 로 닫아야 한다** — F-305 구현이 `provider.ws.close()` 처럼 소켓만 닫으면 F-307 이 `liveSocket.ts` 에서 바꾼다(12.1 A8 ⑤). 서버는 4.1 둘째 줄로 받아 방송하고 기록에서 뺀다 → `onClose` 때 지울 것이 없다. 4.3 의 서버 지우기는 그 한 통이 오지 않는 경우(소켓이 먼저 끊김·탭 강제 종료·절전)를 위한 것이다
- 나머지(열린 연결이 없으면 곧바로 flush, F-304 6.2)는 지금 그대로
- 비용: 연결이 닫히면 어차피 DO 가 깨어난다(F-304 5.2). 보내는 메시지는 과금이 없다(F-301 9.3). 새 비용 0

### 4.4 되돌림 — 클라이언트에서 막고 서버에서 한 번 더 막는다

- **클라이언트(입력 계약 ②, `src/storage/liveSocket.ts`)**: awareness 를 받은 시도에서 provider 는 `change` 에 내 clientID 가 있을 때만, **내 clientID 하나만** 실어 보낸다. 원격 적용·연결 끊김 정리(origin = provider)로 난 `change` 는 보내지 않는다. 연결 `open` 때 provider 가 내 상태를 따로 보내는 한 통(읽은 코드)은 그대로 둔다
  - 되는 길이 있음을 읽은 코드로 확인했다: provider 가 `awareness.on('change', this._awarenessUpdateHandler)` 로 단 처리기는 `index.d.ts` 에 공개 필드로 있고, `destroy()` 는 **그 필드에 든 함수**를 뗀다. 그래서 생성 직후 원래 처리기를 떼고, 바뀐 id 목록에서 내 clientID 만 남겨 원래 처리기에 넘기는 거르개를 달고 그 필드에 넣으면 `destroy` 가 거르개를 뗀다. 새 import(`lib0` 등)가 필요 없다. 방법은 구현이 정한다 — 결과가 12.1 A8 을 지나면 된다
  - awareness 를 받지 않은 시도(F-305 그대로)는 바뀌지 않는다
- **서버(4.1 셋째 줄)**: clock 이 오르지 않은 항목은 버린다. 클라이언트가 되돌려 보내도 관계 없는 사람의 소유가 옮겨 가지 않는다
- 클라이언트 쪽을 안 막으면 요청 수가 N 배다(5.4). 서버 쪽만으로는 요청 수가 줄지 않는다 — 받은 메시지는 버려도 이미 센다
- 남는 틈(받아들인다): 클라이언트가 되돌려 보낸 옛 상태가, 그 주인이 닫혀 기록이 사라진 **직후** 서버에 닿으면 "기록 없음" 으로 받아진다. 클라이언트 쪽을 막으면 생기지 않는다

### 4.5 BroadcastChannel 은 꺼져 있어야 한다 (입력 계약 ③ — F-305 가 정함)

F-305 6.2 가 `disableBc: true` 로 정했다(22장 Q4 기본값, 이유는 IME 게이트를 지나지 않는 두 번째 입구). F-307 도 같은 값이 필요하다 — 켜져 있으면 같은 브라우저 두 탭이 awareness 를 BroadcastChannel 로 먼저 주고받는다. 그 상태는 **서버 도장이 없다.** 서버를 거친 같은 clock 의 도장 찍힌 상태는 뒤에 와서 `currClock < clock` 이 거짓이라 버려진다(`applyAwarenessUpdate`). 그러면 같은 브라우저 탭끼리 서로의 커서를 영영 못 그린다(3.1 — `user` 없는 상태는 안 그린다). F-307 은 이 값을 바꾸지 않는다. 누가 나중에 `false` 로 바꾸면 12.2 A32 가 깨진다

## 5. 보내기 규칙과 쿼터

### 5.1 배선

```ts
// src/app/useLiveDoc.ts — 돌려주는 값에 한 필드 (F-305 는 반환 모양을 계약으로 적지 않았다. 필드 이름이 계약)
awareness: Awareness | null        // 실시간 세션(방 Doc 이 있는 동안)만. 방 Doc 과 수명이 같다

// src/editor/createEditor.ts — F-305 의 live 옵션에 한 필드
live?: {
  roomDoc: Y.Doc
  awareness: Awareness             // F-307
  onRemoteTitle: (title: string) => void
}

// src/editor/remoteCursors.ts
export const CURSOR_SEND_MS = 250
export const CURSOR_LABEL_MS = 1500
export function remoteCursors(): Extension
export function attachRemoteCursors(view: EditorView, source: { awareness: Awareness; ytext: Y.Text }): () => void

// src/app/usePeers.ts
export function usePeers(awareness: Awareness | null): Peer[]
```

- **만들기(`useLiveDoc`)**: 방 Doc 을 만드는 **같은 자리에서** `new Awareness(roomDoc)` 하나를 만들고 곧바로 `_checkInterval` 을 끈다. `y-protocols` 생성자는 3초 `setInterval` 을 걸어 30초 넘은 원격 상태를 지운다. `YProvider` 생성자가 시도마다 끄지만(읽은 코드) 첫 시도 전·시도 사이에도 "원격 상태는 명시적 지우기로만 사라진다" 는 규칙이 되게 한다. 생성자가 넣는 첫 내 상태 `{}` 는 그대로 둔다 — `open` 때 이것이 나가 커서 없이도 아바타가 뜬다(5.2)
- **넘기기**: 제어기(`createLiveDocController`)에 주는 `openSocket` 을 감싸 매 시도의 `LiveSocketOptions` 에 같은 `awareness` 를 넣는다. `liveDoc.ts` 는 바꾸지 않는다. `liveSocket` 은 받은 인스턴스를 `YProvider` 옵션으로 넘기고 끄지도 버리지도 않는다(F-305 6.2 끝)
- **버리기**: 방 Doc 이 `destroy` 되면 `Awareness` 도 따라 버려진다(`y-protocols` 생성자의 `doc.on('destroy')` — 읽은 코드). `useLiveDoc` 가 따로 부를 것이 없다. 순서상 소켓이 먼저 닫혀 내 `null` 한 통이 이미 나간 뒤다(4.3 끝)
- **편집기(`createEditor`)**: `live` 가 있으면 F-305 의 `connectRemote({ …, sharedDoc })` 뒤에 `attachRemoteCursors(view, { awareness: live.awareness, ytext: 편집기 Y.Text })` 를 부르고, `destroy` 에서 게이트보다 **먼저** 뗀다. 편집기를 다시 마운트(`editorRemountNonce`)하면 새 편집기가 같은 awareness 에 다시 붙는다
- **아바타(`usePeers`)**: awareness `change` 를 듣고 `nextPeerList(prev, awareness.getStates(), awareness.clientID)` 로 목록을 만든다. `null` 이면 빈 배열. 목록이 값으로 같으면 이전 배열을 그대로 돌려줘 다시 그리지 않는다. 아바타가 편집기가 아니라 App 층 awareness 에서 나오므로 편집기 다시 마운트·첫 동기화 전(편집기 없음)에도 목록이 흔들리지 않는다
- `remoteCursors()` 는 연결과 상관없이 늘 확장 목록에 있다(`Prec.low`). 붙은 소스가 없으면 장식이 비어 있고 아무 일도 안 한다 — 로컬·폴백·`?ysync` 경로는 그대로다. 붙일 때 `Compartment` 재구성을 쓰지 않는다(재구성은 `blockPreview` StateField 를 새로 만들 수 있다 — `CLAUDE.md` 배포 절 F-156 A7 기록)
- 상대 위치는 **편집기 `Y.Text`** 로 만들고 편집기 `Y.Doc` 에 대해 푼다 — 화면(`EditorState`)과 같은 쪽이다. 편집기 Doc 은 방 Doc 에서 복제되고(F-305 5.3) item id 는 게이트 중계로 방 Doc·서버·상대에 그대로 간다(F-303 4.1). awareness 는 방 Doc 에 매여 있지만 커서 값은 JSON 이라 어느 Doc 으로 만들었는지와 상관없다

### 5.2 내 커서를 언제 보내나

"접속자" = 내 것이 아닌 clientID 중 `readPeerState` 가 `null` 이 아닌 상태(도장 있음)를 가진 것

| 상황 | 보내나 |
| --- | --- |
| **접속자가 0명** | **안 보낸다.** 마지막 커서는 플러그인 안에만 둔다 |
| 접속자가 있고, 주 뷰에 포커스가 있고(`view.hasFocus && document.hasFocus()`), 선택의 상대 위치가 지난번 보낸 것과 다르다 | 보낸다 — 250ms 조이기(5.3) |
| 포커스가 없다(제목 입력, 표 칸 하위 편집기, 사이드바 등) | 보내지 않는다. 마지막 보낸 값이 남는다 |
| 상대 위치가 같다 — 타이핑·Backspace·Enter·한글 조합(실측 (a)) | 보내지 않는다 |
| 접속자가 새로 보였다(5.3) | 내 상태를 **한 번 다시** 보낸다 — 포커스가 있으면 지금 커서, 없으면 마지막으로 보낸 커서(없으면 `null`). 포커스와 상관없이 보낸다: 새 사람이 나를 알아야 한다 |
| 편집기를 붙인 직후(`attachRemoteCursors`) | 그때 이미 있는 접속자를 "새로 보였다" 로 친다 — 위 줄과 같다 |

- 접속자 0명일 때 안 보내는 이유: 볼 사람이 없는 메시지가 DO 를 깨운다(F-304 5.2 — 깨어날 때마다 `onLoad` 로 DO SQLite 와 D1 한 줄을 다시 읽는다). 혼자 문서를 읽으며 여기저기 누르는 흔한 경우가 awareness 로는 DO 를 한 번도 안 깨운다
- 연결 직후 한 번은 보낸다 — provider 가 `open` 에서 내 상태(처음엔 `{}`)를 보낸다(읽은 코드). 서버가 도장을 찍어 퍼뜨리므로 **커서 없이도 아바타가 뜬다.** 재연결 시도마다 같은 awareness 가 넘어가므로(5.1) 다시 붙을 때도 마지막 커서가 담긴 한 통이 나간다
- 첫 동기화 전(F-305 5.1 — 편집기가 아직 없다)에는 보내는 쪽(`remoteCursors`)이 없다. 그 사이 새 접속자가 보여도 다시 보내기가 없고, 편집기가 붙는 순간(위 표 끝 줄) 보낸다. 로컬 첫 동기화 12ms(F-305 측정 d)라 틈은 짧다
- 포커스를 잃어도 커서를 지우지 않는다(`y-remote-selections` 와 같다). 지우면 포커스가 오갈 때마다 메시지가 난다
- 조합 중에도 보낼 수 있다 — 보내기는 네트워크만 쓰고 편집기 DOM 을 건드리지 않는다. 실제로는 조합이 상대 위치를 안 바꿔(실측 (a)) 거의 안 나간다

### 5.3 조이기와 다시 보내기

- **조이기**: 250ms 에 최대 한 번. 앞 가장자리(첫 변화는 곧바로)와 뒤 가장자리(창 안의 마지막 값은 창이 끝날 때) 둘 다. 내 커서의 마지막 위치는 반드시 나간다
- **다시 보내기**: 접속자 목록에 **없던 clientID 가 생기면**(원격 상태가 없다가 생김) 지금 커서로 내 상태를 보낸다. 커서가 지난번과 같아도 **clock 을 하나 올려** 보낸다 — 서버는 clock 이 안 오른 항목을 되돌림으로 보고 버린다(4.1). `setLocalState` 는 같은 값이면 `change` 를 안 내서 provider 가 안 보낸다(실측 (f)) — 구현이 clock 을 올리고 `change` 가 나게 한다. 방법은 구현이 정한다
- 다시 보내기도 조이기를 탄다 — 250ms 안에 여러 명이 보여도 최대 2통
- **왜 필요한가(F-304 11.3 7번)**: DO 가 잠들었다 깨면 서버 awareness 가 비어 있어 새로 붙은 사람은 먼저 있던 사람을 모른다. 새 사람의 `open` 상태가 퍼지는 순간 먼저 있던 사람들이 다시 보내 새 사람이 모두를 본다. 서버가 깨어 있었다면 `onConnect` 로 이미 받았으므로 다시 보내기는 중복이다 — 한 사람당 최대 2통이라 받아들인다
- 이 규칙은 연쇄되지 않는다: 다시 보낸 상태를 받은 쪽에서 그 clientID 는 이미 있으므로 "새로 생김" 이 아니다
- 시계·타이머를 주입받는 순수 제어기로 뽑는다(`src/app/usePresence.ts` `createPresenceController` 와 같은 방식). 입력: 접속자 수, 포커스, 새 상대 위치, 강제 여부. 출력: 보낼 값. node 단위 테스트가 가짜 타이머로 본다(12.1 A6)

### 5.4 쿼터 계산

기준(F-301 9.3): Requests 하루 100,000건, 들어오는 WebSocket 메시지 20통 = 1건, 나가는 메시지 과금 없음. Duration 하루 13,000 GB-s, DO 1개 0.125 GB. 아래는 공식 수치에 대입한 계산이고 대시보드로 확인한 값이 아니다

| 경우 | 들어오는 메시지 | 요청 |
| --- | --- | --- |
| 혼자 연결 1번 | 1통(연결 때 내 상태) | 0.05건 |
| 혼자 1시간 읽고 누르기 | 0통 | 0건 — DO 를 awareness 로 깨우지 않는다 |
| 커서를 쉬지 않고 움직임(최악, 250ms 조이기) | 초당 4통 → 시간당 14,400통 | **시간당 720건**(하루 한도의 0.72%) |
| 참고: 초당 5타 1시간 타이핑(F-304 10.1) | 18,000통 | 900건 |
| 타이핑 중 | 커서 메시지 0통(실측 (a)) | 0건 |
| 한 사람이 들어옴(방에 N명이 됨) | 새 사람 1 + 먼저 있던 N−1명 × 최대 2 | 1 + 2(N−1) 통 — 5명이면 9통 |
| 한 사람이 나감 | 0~1통(provider 의 지우기). 서버의 지우기 방송은 나가는 쪽이라 0 | ≤ 0.05건 |
| **입력 계약 ② 가 없을 때** | 커서 한 번에 N통(되돌림) | 3명이면 최악 시간당 2,160건 — ② 가 필요한 이유 |

- Duration: 함께 편집하는 동안에는 문서 업데이트로 어차피 깨어 있다. 커서만 오가는 경우(둘이 같이 읽기)에는 메시지마다 잠든 DO 를 깨울 수 있어 최대 그 세션 길이만큼 깨어 있다 — 1시간이면 450 GB-s(하루 3.5%). 혼자면 0
- 상시 타이머·주기적 생존 신호(heartbeat)는 **두지 않는다.** 15초마다 보내면 DO 가 사실상 잠들지 못한다(F-304 10.2 — 잠들기 전 대기 약 10초, 확인 못 함). 나간 사람은 4.3 이 지운다
- 250ms 를 고른 이유: 텍스트 커서는 뜻이 중요하지 움직임의 부드러움은 중요하지 않다. 최악 박자가 타이핑 최악(900건/시간)보다 낮다. 500ms 로 늘리면 최악이 360건/시간이 되고 상대 화면의 커서가 최대 0.5초 늦는다 — 상수 하나만 바뀐다

| --- | --- | --- |
| awareness 를 받는 곳 | `ySyncFacet` — `yCollab(ytext, awareness)` 를 만들 때 넣어야 한다. 지금 `yBinding.ts` 는 `null` 이고, awareness 는 연결이 붙은 뒤에야 생긴다. 나중에 넣으려면 `ySync`·`yUndoManager` 가 든 확장을 재구성해야 한다 | `attachRemoteCursors` 로 나중에 붙인다 |
| 내 커서 보내기 | **모든 view update 마다** 상대 위치를 만들고 다르면 곧바로 `setLocalStateField` — 조이기·혼자 판정 없음 | 5.2·5.3 |
| 원격 커서 다시 풀기 | 모든 view update 마다 전원. 실측 (c) 로 큰 문서 키 한 번에 약 12ms | 6.3 — 그 사람 awareness 가 바뀔 때만 |
| 조합 중 | awareness `change` 마다 `view.dispatch`, update 마다 장식 전체를 새로 만든다 | 6.2 — 얼린다 |
| 모양 | `fontFamily: 'serif'`, 흰 글자, hex 기본값 `#30bced` | 토큰만(6.5) |

위 `YRemoteCaretWidget`·장식 구성은 참고로 삼되 코드를 복사하지 않는다(규칙이 다르다)

### 6.2 IME 조합 중 — 얼린다

`조합 중` 은 F-303 5.1 과 같다: `view.compositionStarted || isCellCompositionStarted(view)`

| 때 | 동작 |
| --- | --- |
| 원격 awareness `change`(내 clientID 가 아닌 것이 바뀜), `조합 중` 아님 | 그 사람들을 다시 풀고(6.3) 장식 갱신을 dispatch 한다 |
| 같은 때, `조합 중` | **dispatch 하지 않는다.** "밀림" 표시만 남긴다 |
| 조합 중 view update(내가 치는 글자) | 장식을 **다시 만들지 않고** 트랜잭션의 변경으로 옮기기(map)만 한다. 위젯은 같은 것으로 남는다(6.4 `eq`) — CM6 는 옮겨진 장식을 바뀐 범위로 보지 않는다 |
| `forceRecalc` 가 든 update(`isForced` — 주 뷰 `compositionend` 뒤 `compositionCatchup`, 칸 `compositionend` 뒤 `tableWidget`, 게이트 비우기 뒤 `afterFlush` 가 보낸다) | "밀림" 이면 전원을 다시 푼다. **이것이 불변조건 "조합이 끝나면 밀린 재계산을 따라잡는다" 를 지키는 자리다** |
| "밀림" 인데 `조합 중` 이 `REMOTE_HOLD_CHECK_MS`(2,000ms, F-303) 넘게 이어짐 | 2초마다 본다. 조합이 살아 있으면(`compositionAlive` — 포커스·`document.hasFocus()`·보임, F-303 5.4) 계속 기다린다. 살아 있지 않으면 다시 푼다 — 살아 있지 않은 조합은 깰 IME 세션이 없다 |

- 조합 중 편집기 DOM 에 생기는 변화는 **내 글자 입력이 원래 만드는 것뿐**이다. 원격 awareness 때문에 생기는 DOM 변화는 0이다(12.2 A26 이 MutationObserver 로 잰다)
- 원격 **문서** 업데이트는 F-303 게이트가 조합 중 막는다. 그 사이 원격 커서가 아직 안 들어온 글자를 가리키면 풀기가 `null` 을 돌려 그 커서는 안 그린다 — 게이트가 비우며 보내는 `forceRecalc` 에서 다시 풀려 나타난다
- 라벨이 1.5초 뒤 사라지는 것도 JS 타이머로 DOM 을 고치지 않는다(6.4) — 조합 중 사라져도 DOM 변화가 없다

### 6.3 푸는 때와 옮기는 때

- **다시 푸는 때**: 그 사람의 awareness 상태가 바뀌었을 때(6.2 첫 줄), "밀림" 이 풀릴 때, 연결을 붙인 직후. 그 밖의 문서 변경(내 입력, 원격 입력)에는 **옮기기만** 한다
- 옮기기로 충분한 근거: 커서 위젯을 `side: 1` 로 두면 그 자리에 누가 글자를 넣을 때 위젯이 넣은 글 뒤로 간다. 상대 위치(`assoc` 0 — 오른쪽 글자에 붙음)를 다시 풀어도 같은 자리다. 원격 사용자가 자기 커서 자리에 타이핑하면 그 사람의 상대 위치는 안 바뀌고(실측 (a)) 우리 쪽 위젯은 옮기기로 따라간다
- 선택이 앞으로(anchor < head) 가면 머리 위젯은 `side: -1` 이다(선택 밖에 내 커서가 그려지게 — `y-remote-selections` 와 같다). 이때 머리 자리에 누가 글자를 넣으면 옮기기와 다시 풀기 결과가 한 글자 어긋날 수 있다. 다음 awareness 변화에서 맞춰진다 — 받아들인다
- 푸는 중 예외가 나거나 결과가 `null` 이거나 다른 타입을 가리키면 그 사람 커서만 안 그린다

### 6.4 장식

| 요소 | 모양 | 계약 |
| --- | --- | --- |
| 선택 | mark 장식 하나(시작~끝). 여러 줄이어도 줄 장식을 쓰지 않는다 — 코드블록 줄 장식(`fenceLinePreview`) 등과 `attributes` 가 섞이지 않게. 빈 줄은 칠해지지 않는다 | class `cm-remote-selection`, `data-people` |
| 커서 | 머리 자리 위젯. `ignoreEvent()` 참, `aria-hidden="true"`(라벨 글자가 스크린 리더에 본문으로 읽히지 않게) | class `cm-remote-caret`, `data-people`, `data-peer-client="{clientID}"` |
| 라벨 | 커서 위젯 안. 3.2 라벨 글자 | class `cm-remote-caret-label` |

- 위젯 동등(`eq`): 같은 clientID·색·라벨·**이동 번호**면 같다. 이동 번호는 그 사람 커서를 다시 풀어 **위치가 달라졌을 때만** 오른다. 그래서 옮기기로는 DOM 이 새로 안 생기고, 그 사람이 움직이면 새로 생긴다
- 라벨 보이기: 위젯 DOM 이 새로 생기면 라벨이 보이고 `CURSOR_LABEL_MS`(1,500ms) 뒤 CSS 애니메이션으로 사라진다(사라짐 150ms `--ease-out`). 커서에 마우스를 올리면 보인다(`:hover`). 움직임 줄이기면 서서히 사라지지 않고 1,500ms 에 바로 사라진다
- 내 clientID 는 그리지 않는다. 같은 사람의 **다른 탭**은 그린다 — 다른 자리에 있는 다른 커서다
- `Prec.low`: 우리 mark 가 라이브 프리뷰 요소(굵게·코드 등)를 쪼개지 않고 그 안쪽에 들어가게 하려는 것이다. 위젯이 가려진 범위에서 빠지는 것은 순서와 무관하다(실측 (b))

### 6.5 표 칸·블록 위젯과 공존 (F-301 12.1 U6 결론)

- **블록 위젯(표·코드블록·이미지·수식·Mermaid·프론트매터)으로 그려진 범위 안, 그리고 끝 자리의 원격 커서·선택은 편집 모드에서 안 보인다.** 인라인으로 숨긴 기호(`**` 등) 안도 같다. 실측 (b) — 가리는 `replace` 장식이 있으면 그 안의 점 장식은 우선순위와 무관하게 빠진다. F-301 6.2 가 대비책으로 적은 "위젯 안에서는 원격 커서를 그리지 않는다" 가 따로 짤 것 없이 성립한다
- 그 사람은 아바타에는 그대로 남는다. **원문 모드**에서는 위젯이 없어 보인다
- 표 칸 하위 `EditorView`(F-125)에는 원격 커서를 그리지 않는다. 칸을 편집하는 동안 내 커서는 보내지 않는다(주 뷰에 포커스가 없다 — 5.2)
- 표 칸 조합 중에도 주 뷰 장식을 얼린다(6.2 `조합 중` 에 칸 조합이 들어 있다). 주 뷰 장식은 표 범위 밖이라 칸 DOM 과 닿지 않지만, 규칙을 하나로 둔다

### 6.6 모양 (값은 사람 확인 12.4 P5 후 확정)

## 7. 상단바 아바타

### 7.1 자리와 개수

- 자리: 상단바 `.topbar-spacer` 뒤, 보기 모드 토글(`.view-mode-seg`) 앞(`specs/ia.md` 8장 "보기 토글 왼쪽")
- **접속자가 없으면 요소 자체가 없다.** 빈 자리·자리 표시를 두지 않는다(`specs/ia.md` 8장 원칙). 그래서 연결이 없는 문서(로컬 문서, 보기 권한, 폴백, 오프라인)에서는 상단바가 지금과 한 픽셀도 다르지 않다

```ts
// src/lib/peers.ts
export type Peer = { userId: string; email: string; color: number }   // color = peerColorIndex(userId)
export const PEER_AVATARS_MAX = 4
export const PEER_AVATARS_MAX_NARROW = 1
export const PEER_LABEL_MAX_CHARS = 24

export function readPeerState(raw: unknown): PeerState | null
export function nextPeerList(prev: readonly Peer[], states: ReadonlyMap<number, unknown>, ownClientId: number): Peer[]
export function visiblePeers(peers: readonly Peer[], selfUserId: string | null, max: number): { shown: Peer[]; hidden: Peer[] }
export function peerInitial(email: string): string
export function peerLabel(email: string): string
```

| 규칙 | 값 |
| --- | --- |
| 한 사람 = 한 아바타 | `user.id` 로 묶는다. 같은 사람의 탭 여러 개도 하나 |
| 나 | 내 `account.id` 와 같은 사람은 뺀다(내 다른 탭 포함) |
| 순서 | 이 연결에서 **처음 보인 순서**. 누가 커서를 움직여도 순서가 바뀌지 않는다. 나갔다 다시 오면 맨 뒤 |
| 개수 | 넓은 창 최대 4개, 5명째부터 `+N`(N = 나머지 수). 좁은 창(`narrow`, 1024px 미만) 최대 1개 + `+N` |
| 바뀜 알림 | `nextPeerList` 는 목록이 **값으로 같으면 `prev` 를 그대로 돌려준다.** `usePeers` 는 참조가 바뀔 때만 상태를 바꾼다 — 커서 이동으로는 `App` 이 다시 그려지지 않는다 |

- 5명 이상에서 4 + `+N` 인 이유: F-301 6.2 "겹쳐서 최대 4개, 넘으면 `+N`" 을 글자 그대로 읽었다
- 좁은 창에서 1개인 이유: 360px 폭 휴대폰에서 상단바에 사이드바 머리 묶음·보기 모드 3칸·공유·내보내기·계정이 이미 있다. 넘치는지는 사람 확인 P6

### 7.4 `App` 배선

- `const peers = usePeers(useLiveDoc 이 돌려준 awareness)` 한 줄. F-305 가 `Editor` 에 넘기는 `live` 에 같은 `awareness` 를 넣는다
- `<TopBar peers={…} selfUserId={account.state === 'in' ? account.id : null}>`. **공유 화면(S-4)·지도(S-8)가 떠 있는 동안은 빈 배열을 넘긴다** — 그동안 편집 영역은 숨긴 채 살아 있어(`App.tsx` `.content-area hidden`) 연결도 살아 있지만, 지금 보고 있는 것은 그 문서가 아니다
- 문서를 바꾸면 F-305 세션이 끝나 `awareness` 가 `null` 이 되고 `usePeers` 가 빈 배열을 돌려준다
- 보기 모드(`Viewer`)에서는 에디터가 숨긴 채 살아 있다 — 아바타는 보이고 원격 커서는 안 보인다
- 첫 동기화 전(`불러오는 중…`, 편집기 없음)에도 연결이 열리면 아바타는 뜬다. 원격 커서는 편집기가 뜬 뒤부터다
