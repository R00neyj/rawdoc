## 2. 범위

### 한다

- `d3-force-3d@^3.0.6` 을 `dependencies` 에 넣는다 (F-292 3.2 표)
- 우리가 실제로 부르는 것만 담은 앰비언트 타입 선언 (4장)
- `WikiGraph` 모양의 그래프 → 3차원 힘 시뮬레이션 (5.3)
- 0~1 정규값 ↔ 힘 파라미터 **양방향** 매핑과 축별 곡선 (5.1·5.2)

- 노드 고정·해제 (`fx`·`fy`·`fz`) (5.3)
- `prefers-reduced-motion` 용 **프레임 예산 안에서 tick 돌리기** — 시계를 주입받는 순수한 루프 (7장)
- 렌더러가 바로 쓸 수 있는 `Float32Array` 좌표 읽기와 경계구 (5.3)

### 하지 않는다

- `three` 도입, 캔버스, 렌더링, 카메라, `requestAnimationFrame` — 전부 F-2002·F-2003
- 노드 크기·색·이름표 판정 — F-2004 (`mapNodeStyle.ts`)
- 슬라이더 UI·설정 저장 — F-2005·F-2006 (`MapPanel.tsx`·`mapPrefs.ts`)
- 필터·그룹 매칭 — F-2007·F-2008 (`mapFilter.ts`)
- 노드 상한 2,000 자르기 — **이미 있는 `truncateGraphByDegree`**(`src/lib/wikiGraph.ts` 256~275행)가 한다. 이 모듈은 이미 잘린 그래프를 받는다
- `forceCollide`·`forceRadial` — 어느 슬라이더도 이것을 몰지 않는다 (11장 갱신 대상)
- e2e 테스트 — 화면이 바뀌지 않는다 (9장)

## 3. `d3-force-3d@3.0.6` 의 실제 API — 소스를 받아 확인했다

F-292 3.2 는 README 를 인용해 "`d3-force` 와 드롭인 호환"이라 적었다. **그것은 검증되지 않은 전제였다.** 아래는 `https://unpkg.com/d3-force-3d@3.0.6/src/*.js` 를 내려받아 읽고, 스크래치패드에 설치해 돌려 확인한 것이다. **행 번호는 그 소스의 행이다.**

### 3.2 난수 — `randomSource` 를 쓸 필요가 없다. **기본이 이미 결정적이다**

- 초기 좌표는 난수가 아니라 **황금각·Markov 무리수 두 각으로 만든 구면 분포**다 (`simulation.js` 19~21·86~99행). 1판 `graphLayout.ts` 의 황금각 나선과 같은 발상이다
- 시뮬레이션 안의 유일한 난수는 `random = lcg()` (`simulation.js` 36행)이고, `lcg.js` 는 **씨앗 `s = 1` 로 고정된 선형 합동 생성기**다. `Math.random` 이 아니다
- 이 난수는 완전히 겹친 두 노드를 떼어놓을 때(`jiggle`)만 쓰인다 (`manyBody.js` 85~87·101~103행, `link.js` 37~39행)
- **실측**: 같은 그래프(노드 60·간선 54)로 시뮬레이션을 두 번 만들어 각각 300 tick 을 돌린 좌표 배열이 **JSON 문자열까지 완전히 같았다**. 첫 노드 좌표 `420.094045, 77.789959, -402.226147`
- **결론: `randomSource()` 를 부르지 않는다.** 대신 단위 테스트가 결정성을 직접 검사한다 (A7). 노드·간선 배열의 **순서**가 같아야 한다는 전제가 붙고, 그 순서는 `buildWikiGraphFromEntries` → `truncateGraphByDegree` 가 이미 결정적으로 정해 준다

### 3.3 **`forceSimulation()` 은 만들자마자 스스로 돈다** — 반드시 `stop()` 한다

`simulation.js` 34행이 `stepper = timer(step)` 이다. `d3-timer` 의 `timer()` 는 만드는 즉시 예약된다.

**실측**: `forceSimulation(nodes, 3)` 을 만들고 아무것도 하지 않은 채 50 ms 를 기다리자 `alpha` 가 `1 → 0.9549925860214359` 로 떨어졌다.

- 이것은 두 군데에서 문제가 된다. (1) 브라우저에서 three 의 rAF 루프와 d3 자체 타이머가 **따로 도는 이중 루프**가 된다 (2) 테스트 환경이 `node` 라 vitest 가 도는 내내 타이머가 살아 남아 상태를 바꾼다
- **그래서 `createMapLayout` 은 시뮬레이션을 만든 직후 `stop()` 을 부른다.** 이 모듈 밖에서는 `stop()` 을 부를 일이 없고, **`restart()` 는 영영 부르지 않는다** — tick 은 언제나 호출자(F-2002 의 rAF)가 민다
- 4장의 앰비언트 선언에 **`restart` 를 아예 넣지 않아** 타입 수준에서 못 부르게 막는다
- 검증: `stop()` 을 부른 뒤 `tick(1)` 을 300번 손으로 밀었더니 `alpha` 가 정확히 300 tick 째에 `alphaMin` 아래로 내려갔다. 계산값과 정확히 같으므로 **타이머가 끼어든 tick 이 하나도 없다**

### 3.4 **`forceCenter().strength()` 는 그래프를 뭉치게 하지 않는다** — F-292 6.7 을 고쳐야 한다

`center.js` 8~26행을 읽으면 이것은 힘이 아니다. `alpha` 인자를 받지도, 속도(`vx`·`vy`·`vz`)를 건드리지도 않는다. **무게중심을 구해 모든 노드를 `(무게중심 − 목표) × strength` 만큼 통째로 평행이동할 뿐**이다. 노드 사이 거리는 조금도 바뀌지 않는다.

**실측** (노드 300, 3D, 반발 −800 / 링크 거리 120 / 링크 장력 0.02, 300 tick):

| `forceCenter().strength(s)` | 평균 반경 | 최대 반경 | 무게중심의 원점 거리 |
| --- | --- | --- | --- |
| 0 | 2513.7 | 4936.5 | 91.050 |
| 0.05 (F-292 기본값) | 2486.4 | 4891.9 | 0.039 |
| 0.3 | 2515.3 | 4929.2 | 0.003 |
| 1 | 2476.5 | 4912.2 | 0.001 |

슬라이더를 0 에서 1 까지 끌어도 **모양이 −1.5% 바뀐다.** 화면에서는 아무 일도 일어나지 않는다. 바뀌는 것은 "덩어리가 원점으로 돌아오는 속도"뿐이다.

**대신 `forceX(0)`·`forceY(0)`·`forceZ(0)` 의 `strength` 가 진짜 중심 인력이다.** 같은 조건, `forceCenter` 는 1 로 고정:

| `forceX/Y/Z(0).strength(s)` | 평균 반경 | 최대 반경 |
| --- | --- | --- |
| 0 | 2489.5 | 4943.3 |
| 0.02 | 1507.6 | 2398.4 |
| 0.05 | 1068.4 | 1452.0 |
| 0.2 | 566.5 | 727.5 |
| 0.5 | 366.4 | 451.9 |

**이 명세의 결정**: `중심 장력` 슬라이더는 `forceX/forceY/forceZ(0).strength(s)` 셋을 함께 민다. `forceCenter(0, 0, 0).strength(1)` 은 **사용자가 못 만지는 고정 값**으로 남겨, 덩어리가 늘 원점에 있게 한다(카메라가 그것을 전제한다). F-292 6.7 표의 `중심 장력` 행을 이렇게 고친다 (11장).

- `forceX/Y/Z` 의 기본 강도는 `constant(0.1)` 이다(`x.js` 4행). **반드시 명시적으로 `strength()` 를 준다**
- 힘이 셋 늘지만 각각 O(n) 이라 비용이 없다. 오히려 **빨라졌다** — 노드 2,000·300 tick 에서 `forceX/Y/Z` 없이 5,013 ms, 있을 때 4,034 ms. 덩어리가 조여들면 옥트리가 얕아진다
- `s = 0` 일 때도 세 힘을 등록해 둔 채 강도만 0 으로 둔다. 힘을 넣었다 뺐다 하지 않는다

### 3.5 3D 는 2D 의 **2.3~2.7배**다 — F-292 4.1 의 "대략 1.5배" 추정을 실측이 뒤집었다

같은 라이브러리·같은 그래프에서 `numDimensions` 만 바꿔 쟀다 (3회 중앙값, 300 tick).

| 노드 | 2D tick | 3D tick | 배율 |
| --- | --- | --- | --- |
| 500 | 1.34 ms | 3.06 ms | 2.29x |
| 1,000 | 3.23 ms | 7.37 ms | 2.28x |
| 2,000 | 7.74 ms | 21.11 ms | 2.73x |

8장에 실제 수치를, 11장에 F-292 4.1 을 고칠 자리를 적었다.

### 3.6 예외와 경계 — 돌려서 확인했다

| 입력 | 결과 |
| --- | --- |
| 노드 0개 | 예외 없음. `forceCenter` 가 `0/0` 을 만들지만 노드 순회가 돌지 않아 `NaN` 이 새지 않는다 |
| 노드 1개, 간선 0개 | 예외 없음, 좌표 유한 |
| 자기 자신을 가리키는 간선 (`{source: 0, target: 0}`) | **예외 없음**, 좌표 유한 |
| **노드 수를 넘는 인덱스** (`{source: 0, target: 99}` 인데 노드가 5개) | **`Error: node not found: 99` 를 던진다** (`link.js` 8~12행) |
| 힘을 갈아끼운 뒤 `alpha(0.3)` + 300 tick | 정상 동작, 좌표 전부 유한 |

- **마지막 줄 때문에 `createMapLayout` 은 간선을 반드시 거른다.** `from`·`to` 가 정수가 아니거나 범위 밖이거나 `from === to` 면 버린다. 1판 `graphLayout.ts` 77행이 이미 같은 방어를 하고 있다 — 그 규칙을 그대로 옮긴다
- 거른 뒤의 간선 배열을 **공개한다** (`MapLayout.edges`). 렌더러가 `graph.edges` 를 그대로 쓰면 간선 인덱스가 어긋나기 때문이다

## 4. `src/types/d3-force-3d.d.ts` — 그대로 옮겨 쓸 수 있는 전문

**3장에서 소스로 확인한 것만 담았다. 짐작으로 넣은 줄이 하나도 없다.** 우리가 부르지 않는 메서드는 일부러 뺐다 — 특히 `restart`·`nodes`·`randomSource`·`on`·`find`·`velocityDecay` 는 **3.3 의 결정("타이머를 절대 돌리지 않는다")을 타입으로 강제하려고** 뺀 것이다. 나중에 정말 필요한 소명세가 한 줄씩 더한다.

```ts
// npm 에 @types/d3-force-3d 가 없다 (npm view 404, 2026-09-21). d3-force-3d@3.0.6 의
// 소스(src/simulation.js·manyBody.js·link.js·center.js·x.js)를 읽고 우리가 부르는 것만 선언한다.
// (specs/features/F-2001.md 4장, F-292 3.2)
//
// 일부러 뺀 것 — restart()·nodes()·randomSource()·on()·find()·velocityDecay()·forceCollide·forceRadial.
// restart() 는 d3 자체 타이머를 되살려 rAF 루프와 이중으로 돌기 때문에 타입 수준에서 막는다 (F-2001 3.3)
declare module 'd3-force-3d' {
  export interface ForceNode {
    index?: number
    x?: number
    y?: number
    z?: number
    vx?: number
    vy?: number
    vz?: number
    fx?: number | null
    fy?: number | null
    fz?: number | null
  }

  // initialize() 가 끝나면 source·target 은 노드 객체로 바뀐다 (link.js 66~67행)
  export interface ForceLinkDatum<N extends ForceNode> {
    source: N | string | number
    target: N | string | number
    index?: number
  }

  export interface Force<N extends ForceNode> {
    (alpha: number): void
    initialize?(nodes: N[], random: () => number, nDim: number): void
  }

  export interface Simulation<N extends ForceNode> {
    /** 타이머와 무관하게 iterations 번 돈다. 이벤트를 쏘지 않는다 (simulation.js 49~77행) */
    tick(iterations?: number): this
    /** 만들자마자 도는 d3-timer 를 멈춘다 (simulation.js 34행) */
    stop(): this
    alpha(): number
    alpha(alpha: number): this
    alphaMin(): number
    alphaTarget(): number
    alphaTarget(target: number): this
    force(name: string, force: Force<N> | null): this
  }

  /** center.js — 힘이 아니라 무게중심 평행이동이다. x()·y()·z() 도 있지만 쓰지 않는다 */
  export interface ForceCenter<N extends ForceNode> extends Force<N> {
    strength(strength: number): this
  }

  /** manyBody.js — distanceMin()·distanceMax()·theta() 도 있지만 기본값을 쓴다 */
  export interface ForceManyBody<N extends ForceNode> extends Force<N> {
    strength(strength: number): this
  }

  /** link.js — id()·iterations() 도 있지만 기본값(d => d.index, 1)을 쓴다 */
  export interface ForceLink<N extends ForceNode, L extends ForceLinkDatum<N>> extends Force<N> {
    strength(strength: number): this
    distance(distance: number): this
  }

  /** x.js·y.js·z.js — 목표 좌표는 생성 인자로 주고 strength 만 조절한다 */
  export interface ForcePosition<N extends ForceNode> extends Force<N> {
    strength(strength: number): this
  }

  /** numDimensions 는 최상위 함수가 아니다. 두 번째 인자로 준다 (1~3 으로 잘린다) */
  export function forceSimulation<N extends ForceNode>(nodes?: N[], numDimensions?: number): Simulation<N>
  export function forceCenter<N extends ForceNode>(x?: number, y?: number, z?: number): ForceCenter<N>
  export function forceManyBody<N extends ForceNode>(): ForceManyBody<N>
  export function forceLink<N extends ForceNode, L extends ForceLinkDatum<N> = ForceLinkDatum<N>>(
    links?: L[],
  ): ForceLink<N, L>
  export function forceX<N extends ForceNode>(x?: number): ForcePosition<N>
  export function forceY<N extends ForceNode>(y?: number): ForcePosition<N>
  export function forceZ<N extends ForceNode>(z?: number): ForcePosition<N>
}
```

**주의 두 가지.**

1. `forceLink`·`forceManyBody`·`forceX/Y/Z` 는 **호출부에서 타입 인자를 명시한다** — `forceManyBody<MapSimNode>()`, `forceLink<MapSimNode, MapD3Link>(links)`. 인자가 없거나 링크 배열만으로는 `N` 을 추론할 자리가 없어 `strict` 에서 걸린다
2. 이 파일은 `declare module` 블록 하나뿐이고 **최상위에 `import`·`export` 문을 두지 않는다.** 그래야 앰비언트 선언으로 잡힌다. `tsconfig.json` 의 `include: ["src", …]` 가 알아서 읽는다

### 5.1 힘 축과 매핑

```ts
/** 장력 슬라이더 4축 (F-292 6.7) */
export type MapForceAxis = 'center' | 'repel' | 'linkStrength' | 'linkDistance'

/** 축별 0~1 정규값. 저장값도 슬라이더 값도 이 모양이다 */
export type MapForceNorms = Record<MapForceAxis, number>

/** 축별 실제 힘 파라미터 */
export type MapForceValues = Record<MapForceAxis, number>

export type MapForceCurve = 'linear' | 'log' | 'pow2'

export type MapForceAxisSpec = {
  readonly min: number
  readonly max: number
  readonly curve: MapForceCurve
  /** F-292 6.7 의 "출발 기본값" — 실제 단위다 */
  readonly start: number
}

export const MAP_FORCE_AXES: Readonly<Record<MapForceAxis, MapForceAxisSpec>>

/** MAP_FORCE_AXES[axis].start 를 forceValueToNorm 으로 되돌린 값 */
export const MAP_FORCE_DEFAULT_NORMS: Readonly<MapForceNorms>

/** 0~1 → 실제 파라미터. 범위 밖은 자르고, 유한수가 아니면 그 축의 start 를 돌려준다 */
export function normToForceValue(axis: MapForceAxis, norm: number): number

/** 실제 파라미터 → 0~1. normToForceValue 의 역함수 */
export function forceValueToNorm(axis: MapForceAxis, value: number): number

/** 저장값·부분값·쓰레기값을 받아 온전한 MapForceNorms 로. 모르는 키는 버린다 */
export function resolveForceNorms(input?: Partial<Record<string, unknown>> | null): MapForceNorms

/** 네 축을 한 번에 실제 파라미터로 */
export function toForceValues(norms: MapForceNorms): MapForceValues
```

**축 정의표 — 이 숫자가 `MAP_FORCE_AXES` 의 내용이다.**

| 축 | 화면 이름 | 미는 힘 | `min` | `max` | `curve` | `start` | 기본 정규값 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `center` | `중심 장력` | `forceX(0)`·`forceY(0)`·`forceZ(0)` 의 `strength(s)` | 0 | 1 | `pow2` | 0.05 | **0.22360679774997896** |
| `repel` | `반발력` | `forceManyBody().strength(-v)` | 50 | 3000 | `log` | 800 | **0.6771752303951257** |
| `linkStrength` | `링크 장력` | `forceLink().strength(v)` | 0.001 | 0.1 | `log` | 0.02 | **0.6505149978319905** |
| `linkDistance` | `링크 거리` | `forceLink().distance(v)` | 30 | 500 | `linear` | 120 | **0.19148936170212766** |

**곡선 공식** (`t` 는 `[0,1]` 로 자른 정규값, `v` 는 `[min,max]` 로 자른 실제값):

| `curve` | `normToForceValue` | `forceValueToNorm` |
| --- | --- | --- |
| `linear` | `min + (max − min) · t` | `(v − min) / (max − min)` |
| `log` | `min · (max / min)^t` | `ln(v / min) / ln(max / min)` |
| `pow2` | `min + (max − min) · t²` | `√((v − min) / (max − min))` |

- `log` 는 `min > 0` 일 때만 쓴다. `repel`·`linkStrength` 둘 다 그렇다
- **부동소수 왕복은 정확하지 않다.** `linkStrength` 를 실제로 왕복시키면 `0.02 → 0.6505149978319905 → 0.019999999999999993` 이 나온다. 테스트는 `toBeCloseTo`(절대오차 1e-12)로 본다 (A4)
- **양방향이 필요한 이유**: 저장값도 슬라이더도 0~1 인데 **기본값은 F-292 6.7 이 실제 단위(0.05·800·0.02·120)로 정했다.** 그 기본값을 정규값으로 옮기려면 역함수가 있어야 하고, F-2006 이 범위를 바꿀 때 기본값을 손으로 다시 계산하지 않게 하려면 `MAP_FORCE_DEFAULT_NORMS` 를 상수 리터럴이 아니라 **`start` 에서 계산해** 둬야 한다

### 5.2 왜 축마다 곡선이 다른가 — 재서 정했다

노드 300개짜리 같은 그래프를 슬라이더 0 / 0.25 / 0.5 / 0.75 / 1 에 대해 300 tick 씩 돌려, 그 결과 모양이 **슬라이더를 따라 고르게 변하는지**를 봤다. 고르지 않으면 슬라이더의 한쪽 끝이 죽는다.

**`repel` 50~3000 — 평균 반경**

| | 0 | 0.25 | 0.5 | 0.75 | 1 |
| --- | --- | --- | --- | --- | --- |
| 선형 | 589 | 2453 | 3497 | 4726 | 5687 |
| 로그 | 576 | 961 | 1678 | 2974 | 5535 |

구간별 배율이 선형은 **4.16 / 1.43 / 1.35 / 1.20**, 로그는 **1.67 / 1.75 / 1.77 / 1.86** 이다. 선형이면 슬라이더 앞 25%가 변화의 대부분을 먹고 뒤쪽 75%는 거의 죽는다. → **로그**

**`linkStrength` 0.001~0.1 — 평균 간선 길이**

| | 0 | 0.25 | 0.5 | 0.75 | 1 |
| --- | --- | --- | --- | --- | --- |
| 선형 | 4352 | 1413 | 904 | 722 | 628 |
| 로그 | 4352 | 3754 | 2512 | 1228 | 628 |

선형 배율 **3.08 / 1.56 / 1.25 / 1.15**, 로그 **1.16 / 1.49 / 2.05 / 1.96**. → **로그**

**`center` 0~1 — 평균 반경** (3.4 의 `forceX/Y/Z` 기준)

| 슬라이더 | 0 | 0.1 | 0.25 | 0.5 | 0.75 | 1 |
| --- | --- | --- | --- | --- | --- | --- |
| 선형 (`s = t`) | 2461 | 787 | 509 | 367 | 296 | 259 |
| `pow2` (`s = t²`) | 2461 | 1866 | 971 | 509 | 342 | 259 |

선형이면 슬라이더 앞 10%가 변화의 3.1배를 먹는다. 로그는 **`s = 0` 을 만들 수 없어**(`min` 이 0 이다) 쓸 수 없다. → **`pow2`**

**`linkDistance` 30~500 — 평균 반경**

| | 0 | 0.25 | 0.5 | 0.75 | 1 |
| --- | --- | --- | --- | --- | --- |
| 선형 | 2449 | 2463 | 2481 | 2495 | 2514 |
| 로그 | 2449 | 2454 | 2462 | 2478 | 2514 |

**둘 다 사실상 변화가 없다 (+2.7%).** 기본 반발력(−800)에서 실제 간선 길이가 1,400 안팎이라 목표 거리 30~500 은 통째로 묻힌다. 곡선을 무엇으로 고르든 차이가 없으므로 **가장 단순한 `linear`** 로 둔다.

- **이 사실은 F-2006 이 알아야 한다** — `링크 거리` 슬라이더는 지금 기본값 조합에서 화면을 거의 바꾸지 않는다. 범위를 키우든(예: 30~3000) `링크 장력` 과 함께 조정하든 **F-2006 이 손으로 정할 일**이다 (12장 Q4)
- **곡선은 여기서 정한 것을 F-2006 이 그대로 쓴다.** F-2006 이 바꾸는 것은 `min`·`max`·`start` 다

### 5.3 시뮬레이션

```ts
/** WikiGraph 를 그대로 넘길 수 있는 구조적 부분집합 (wikiGraph.ts 의 WikiGraph 와 호환) */
export type MapLayoutGraph = {
  readonly nodes: readonly { readonly id: string }[]
  readonly edges: readonly { readonly from: number; readonly to: number }[]
}

/** 시뮬레이션이 들고 있는 노드. 좌표를 직접 읽어도 된다 (복사 없음) */
export type MapSimNode = {
  readonly id: string
  index: number
  x: number
  y: number
  z: number
  vx: number
  vy: number
  vz: number
  fx: number | null
  fy: number | null
  fz: number | null
}

export type MapLayoutOptions = {
  /** 처음 힘 값. 빠진 축은 MAP_FORCE_DEFAULT_NORMS */
  norms?: Partial<MapForceNorms>
  /** 문서 id → 시작 좌표. 문서 목록이 바뀌어 그래프를 다시 만들 때 전부 튀지 않게 한다 */
  seed?: ReadonlyMap<string, readonly [number, number, number]>
}

export type MapLayoutBounds = {
  /** 경계 상자의 가운데 */
  center: [number, number, number]
  /** 그 가운데에서 가장 먼 노드까지의 거리. 노드가 없으면 0 */
  radius: number
}

export type MapLayout = {
  readonly nodes: readonly MapSimNode[]
  /** 거르고 남은 간선. 렌더러는 graph.edges 가 아니라 이것을 쓴다 (3.6) */
  readonly edges: readonly { readonly from: number; readonly to: number }[]

  setForces(norms: Partial<MapForceNorms>): void
  tick(count?: number): void
  runTickBudget(budgetMs: number, now?: () => number): number
  alpha(): number
  isSettled(): boolean
  reheat(alpha?: number): void
  setAlphaTarget(target: number): void
  fixNode(index: number, x: number, y: number, z: number): void
  releaseNode(index: number): void
  readPositions(out?: Float32Array): Float32Array
  readEdgePositions(out?: Float32Array): Float32Array
  bounds(): MapLayoutBounds
  snapshotPositions(): Map<string, [number, number, number]>
  destroy(): void
}

export function createMapLayout(graph: MapLayoutGraph, options?: MapLayoutOptions): MapLayout
```

**각 멤버가 정확히 무엇을 하나.**

| 멤버 | 하는 일 |
| --- | --- |
| `nodes` | `graph.nodes` 와 **같은 순서·같은 길이**. `index` 는 배열 첨자와 같다 |
| `edges` | 3.6 의 규칙으로 거른 간선. `graph.edges` 의 부분집합이고 원래 순서를 지킨다. **`from`·`to` 는 `nodes` 의 첨자다** |
| `setForces(norms)` | 넘긴 축만 갈아끼운다. 힘 객체를 **새로 만들지 않고** `.strength()`·`.distance()` 로 제자리에서 바꾼다. **`alpha` 를 건드리지 않는다** — 재가열은 호출자가 `reheat()` 로 따로 한다 (12장 Q1) |
| `tick(count = 1)` | `simulation.tick(count)` 그대로. **정지 여부를 보지 않는다** — 그 판정은 호출자가 `isSettled()` 로 한다 |
| `runTickBudget(budgetMs, now)` | 7장. 실제로 돈 tick 수를 돌려준다 |
| `alpha()` | 현재 `alpha` |
| `isSettled()` | `alpha() < simulation.alphaMin()` (= 기본 0.001) |
| `reheat(alpha = 0.3)` | `simulation.alpha(alpha)`. **`restart()` 를 부르지 않는다** (3.3). 슬라이더 조작·문서 목록 변경이 부른다 |
| `setAlphaTarget(target)` | `simulation.alphaTarget(target)`. 끌기 시작에 `0.3`, 놓을 때 `0`. `alpha` 가 `target` 으로 수렴하므로 **끄는 동안은 영영 `isSettled()` 가 되지 않는다** (`simulation.js` 55행) |
| `fixNode(i, x, y, z)` | `node.fx/fy/fz` 를 넣는다. 다음 tick 부터 좌표가 그 값으로 못 박히고 속도가 0 이 된다 |
| `releaseNode(i)` | `fx/fy/fz` 를 `null` 로. **재가열은 하지 않는다** — 호출자가 `reheat()` 를 이어 부른다 (F-292 5장) |
| `readPositions(out?)` | 길이 `nodes.length * 3` 의 `Float32Array` 에 `x,y,z` 를 차례로 채워 돌려준다. `out` 의 길이가 맞으면 **그 배열을 그대로 채워 돌려준다**(프레임마다 새로 만들지 않게). 길이가 안 맞거나 안 주면 새로 만든다 |
| `readEdgePositions(out?)` | 길이 `edges.length * 6`. 간선마다 `from` 의 `x,y,z` 그다음 `to` 의 `x,y,z`. `THREE.LineSegments` 가 바로 먹는 모양이다. `out` 규칙은 위와 같다 |
| `bounds()` | 경계 상자의 가운데와, 그 가운데에서 가장 먼 노드까지의 거리. 노드 0개면 `{ center: [0,0,0], radius: 0 }`. `맞춤` 버튼(F-2003)이 쓴다 |
| `snapshotPositions()` | `문서 id → [x,y,z]`. 다음 `createMapLayout` 의 `seed` 로 넘기면 자리가 이어진다 |
| `destroy()` | `simulation.stop()` 을 한 번 더 부르고 내부 플래그를 세운다. 그 뒤 `tick`·`runTickBudget`·`reheat`·`setForces`·`fixNode`·`releaseNode` 는 **조용히 아무 일도 하지 않는다**(예외를 던지지 않는다). `readPositions`·`bounds` 는 마지막 좌표를 그대로 돌려준다 |

**`createMapLayout` 이 하는 일, 순서대로.**

1. `graph.nodes` 를 `MapSimNode` 배열로 만든다. `seed` 에 그 `id` 가 있으면 `x`·`y`·`z` 에 넣고, 없으면 **넣지 않는다** — 그래야 `initializeNodes()` 가 3.2 의 결정적 구면 분포로 채운다
2. `graph.edges` 를 3.6 규칙으로 거른다. 남은 것으로 `MapD3Link = { source: number; target: number }` 배열을 만든다 (`source`·`target` 은 노드 첨자, `forceLink` 의 기본 `id` 접근자 `d => d.index` 와 맞는다)
3. `forceSimulation<MapSimNode>(nodes, 3)` → **곧바로 `.stop()`** (3.3)
4. 힘 다섯을 등록한다. 이름은 `'link'`·`'charge'`·`'center'`·`'x'`·`'y'`·`'z'` (여섯)
   - `'center'` = `forceCenter(0, 0, 0).strength(1)` — **사용자가 못 만지는 고정 값** (3.4)
   - `'charge'` = `forceManyBody().strength(-values.repel)`
   - `'link'` = `forceLink(d3Links).distance(values.linkDistance).strength(values.linkStrength)`
   - `'x'`·`'y'`·`'z'` = `forceX(0)`·`forceY(0)`·`forceZ(0)` 각각 `.strength(values.center)`
5. `MapLayout` 을 만들어 돌려준다. **`tick` 을 한 번도 돌리지 않는다** — 첫 tick 은 호출자의 몫이다

## 6. 구현 규칙

- **DOM·React·`three`·저장소를 import 하지 않는다.** import 는 `d3-force-3d` 하나뿐이다. 테스트 환경이 `node` 라 이 규칙이 곧 테스트 가능성이다 (`vite.config.ts` 227행)
- `verbatimModuleSyntax: true` 이므로 타입만 쓰는 import 는 `import type` 이다
- 간선 거르기는 1판 `graphLayout.ts` 77행의 조건을 그대로 옮긴다 — `Number.isInteger` 가 아니거나 `from === to` 이거나 `from < 0 || to < 0 || from >= nodes.length || to >= nodes.length` 면 버린다
- `setForces` 는 힘 객체를 새로 만들지 않고 제자리에서 바꾼다. `forceLink.strength()`·`.distance()` 는 `initializeStrength()`·`initializeDistance()` 만 다시 돌아 `link.source`/`target` 이 이미 노드 객체로 바뀐 상태를 깨지 않는다 (`link.js` 115~121행)
- `MAP_FORCE_DEFAULT_NORMS` 는 **리터럴로 적지 않는다.** `MAP_FORCE_AXES[axis].start` 를 `forceValueToNorm` 에 넣어 모듈 로드 시점에 계산하고 `Object.freeze` 한다. 5.1 표의 숫자는 그 계산 결과이고, 테스트가 그 값을 못 박는다 (A4)
- `resolveForceNorms` 규칙: 입력이 `null`·`undefined`·객체가 아니면 전부 기본값. 축별로 `typeof !== 'number'` 이거나 `Number.isFinite` 가 아니면 그 축만 기본값, 유한수면 `[0, 1]` 로 자른다. 결과 객체에는 **네 축만** 담는다(모르는 키는 버린다)

## 7. `prefers-reduced-motion` — 예산 안에서 tick 돌리기

F-292 4.2: 배치가 움직이는 모습을 보여 주지 않고 최종 위치로 바로 보이되, 한 프레임에 300 tick 을 몰아 돌리면 화면이 멈추므로 **프레임마다 8 ms 예산 안에서 tick 을 돈다.**

`requestAnimationFrame` 은 F-2002 의 몫이고, **한 프레임 몫의 루프만** 이 모듈이 갖는다.

```ts
runTickBudget(budgetMs: number, now: () => number = () => performance.now()): number
```

동작을 정확히:

1. 이미 `isSettled()` 이거나 `destroy()` 된 뒤면 **0 을 돌려주고 아무것도 하지 않는다**
2. `const start = now()`
3. `do { tick(1); n++ } while (!isSettled() && now() - start < budgetMs)`
4. `n` 을 돌려준다

- **반드시 최소 1 tick 을 돈다.** `budgetMs` 가 0 이나 음수여도 그렇다. 안 그러면 노드가 많을 때 영영 진행이 없다
- **실제로 노드 2,000 에서는 한 프레임에 1 tick 밖에 못 돈다** (8장 실측: tick 당 13.8~21 ms > 8 ms). 그래서 이 보장이 꼭 필요하다
- `now` 를 인자로 받는 이유는 **테스트를 결정적으로 만들기 위해서**다. 단위 테스트는 호출할 때마다 일정하게 증가하는 가짜 시계를 넘긴다 (A15). `performance.now` 는 Node 20+ 에 전역으로 있다
- 실제 걸리는 시간 (8장 [U5], 3D, 기본값):

| 노드 | 프레임 수 | 프레임당 평균 tick | 16.7 ms 프레임 기준 체감 |
| --- | --- | --- | --- |
| 50 | 4 | 75.00 | 0.07 s |
| 200 | 28 | 10.71 | 0.47 s |
| 500 | 99 | 3.03 | 1.65 s |
| 1,000 | 168 | 1.79 | 2.81 s |
| 2,000 | 300 | 1.00 | **5.01 s** |

현재 사용자 데이터 규모(문서 수십 개)면 0.1초 안이다. **2,000 노드에서 `배치를 계산하는 중…` 이 5초 걸린다는 사실은 F-2002 가 G5 게이트에서 판단할 근거다** (8장).
