## 근거 (2026-10-12 HEAD, 이름으로 찾는다)
- `src/app/notificationsApi.ts` `isNotificationItem`: `share` 가 아니면 댓글 키 10개를 정확히 요구하고, 하나라도 틀리면 `readNotificationsResponse` 가 응답 전체를 버린다. `fetchNotifications` 는 `INBOX_NOTIFICATION_KINDS` 전부를 부른다 → **이 명세가 그 상수에 새 종류를 넣으면 지금 클라이언트의 알림함이 통째로 빈다.** F-3012 4장과 같은 이유로 서버만 먼저 받고, 클라이언트 켜기는 F-2136
- `worker/notifications.ts` `readKinds`: 64자 상한 — `mention,reply,comment,share,access_request` 는 42자
- `worker/commentGc.ts` `ORPHAN_WHERE` = `(kind <> 'share' AND NO_DOC) OR (kind = 'share' AND NO_INVITE)` — 그대로 두면 폴더 대상 `access_request` 행(`doc_id` NULL)이 매일 지워진다
- `src/lib/pushPayload.ts` `TAG_RE` 는 `doc:`·`share:` 만 받는다. 이미 깔린 서비스 워커는 모르는 태그를 `새 알림` 으로 바꿔 그린다

## 2. 알림함 행
- **언제**: F-4005 만들기가 **새 대기 행**을 넣을 때(201 — 쿨다운 뒤 새 id 포함). 같은 batch, `WHERE EXISTS (SELECT 1 FROM access_requests WHERE id = ? AND status = 'pending')` 로 건다
- **모양**: `id` = 요청 id, `recipient_email` = 소유자 `users.email`(같은 `INSERT … SELECT` 에서), `kind = 'access_request'`, 대상에 따라 `doc_id`/`folder_id`, `actor_email` = 요청자 이메일, `doc_title` = 대상 제목·폴더 이름, `excerpt` = `''`, `role` = 요청 권한, `push_due_at` NULL
- 소유자 `notif_rev` +1, `TRIM_NOTIFICATIONS_SQL`(300개) — F-3012 3.1 과 같은 셋
- **권한만 바꾼 200**: `UPDATE notifications SET role = ? WHERE id = ? AND kind = 'access_request'` + 소유자 `notif_rev` +1. 읽음 상태·`created_at` 은 그대로, 새 푸시 없음
- 지우기는 F-4005 `accessRequestDeleteStatements`·F-4006 4장이 이미 한다. 문서·폴더 삭제의 기존 `doc_id`·`folder_id` 조건도 같이 잡는다

## 3. 푸시
- `pushInBackground(env, ctx, 'access_request', …)`, 새 대기 행일 때만. 겹침 막기(F-3007 3.2 모양): `SELECT 1 FROM access_requests WHERE owner_id = ?1 AND status = 'pending' AND created_at > ?2 AND created_at <= ?3 AND id <> ?4 LIMIT 1` (`?2 = now − PUSH_SHARE_DEDUPE_MS`) → 있으면 끝. 없으면 `pushToEmail(db, auth, 소유자 이메일, accessRequestPushPayload(…), now)`
- 계약:
```ts
export function accessRequestPushPayload(r: PushShare): PushPayload
// 문서: title `${actorEmail}님이 문서 ${보기|편집} 권한을 요청했습니다`, body `"${formatNotificationTitle(name)}"`
// 폴더: title `${actorEmail}님이 폴더 ${보기|편집} 권한을 요청했습니다`, body `"${formatFolderName(name)}"`
// tag `share:${targetId}`, url '/#/shares'
```
- `tag` 를 새로 만들지 않는 이유: 근거 4번째 — 깔린 서비스 워커가 그대로 그린다. 소유자는 자기 문서의 `share:` 초대 푸시를 받을 일이 없어 겹치지 않는다. 같은 대상에 둘째 요청은 OS 가 바꿔 끼운다(알림함 행은 둘)

## 4. 목록 API — `worker/notifications.ts`
- 받는 종류 `LIST_KINDS = [...INBOX_NOTIFICATION_KINDS, 'access_request']`(파일 안 상수). `readKinds` 검사·정규화 순서·ETag 꼬리가 이것을 쓴다 — 기존 조합의 꼬리는 글자까지 같다(새 종류가 끝)
- `toItem`: `access_request` 는 `share` 와 같은 9키 모양(`kind` 만 다름). 응답 타입은 파일 안에서 `InboxNotificationItem | AccessRequestNotificationItem`
- `kinds` 없음 기본값(`mention`·`reply`)은 그대로. `unread` 는 요청한 종류만 센다 → 지금 클라이언트 배지 변화 없음
