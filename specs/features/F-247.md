# F-247 삭제한 폴더·문서가 서버 목록으로 되살아나는 문제

작성일: 2026-09-18
상태: 사용자 승인 (2026-09-18 배포 확인 중 보고 — "폴더 2뎁스 아래 있는건 삭제 안되는듯" → 되묻자 "(나) 상위 폴더를 `전부 삭제` 했는데 그 안 하위 폴더나 문서가 남음")
근거: `specs/features/F-207.md` 2.2(서버 목록으로 캐시 맞추기), 2.3(캐시에 먼저 쓰고 즉시 resolve), `F-242.md` 3.1(`delete-all`), `F-126.md` 4장(폴더 2단계)

## 1. 범위

### 문제

`전부 삭제`(F-242 `delete-all`) 로 상위 폴더를 지우면 **그 안의 하위 폴더와 문서가 화면에 다시 나타난다.** 지워진 것은 상위 폴더 하나뿐이다.

원인은 `src/storage/serverStore.ts` 의 서버→캐시 재조정이다. `list()`·`listFolders()` 는 둘 다 이렇게 맞춘다:

```ts
const pendingFolderIds = new Set(outbox.map(folderIdOf).filter(Boolean))
const serverIds = new Set(serverFolders.map((f) => f.id))
await cache.deleteFoldersNotIn(userId, new Set([...serverIds, ...pendingFolderIds]))
for (const folder of serverFolders) {
  if (pendingFolderIds.has(folder.id)) continue
  await cache.putFolder(userId, folder)   // ← 되살아나는 지점
}
```

`removeFolder('delete-all')` 은 캐시에서 상위·하위 폴더와 그 문서를 모두 지우고, 각각의 outbox 항목도 지운 뒤 **outbox 에는 상위 폴더 하나만** 넣는다(서버가 하위까지 지워 주므로). 그래서 재조정 시점에

- pending 집합 = `{상위 폴더 id}`
- 서버 목록 = 아직 상위·하위 폴더가 다 있다(DELETE 를 아직 못 보냈거나 응답 전)

→ 하위 폴더와 그 문서는 pending 이 아니므로 `putFolder`·`putDoc` 으로 캐시에 다시 들어가고, `App.confirmDelete` 가 그 캐시를 읽어 화면에 올린다.

`move-up` 도 같은 뿌리의 문제가 있다. 하위 항목의 `parentId` 를 캐시에서 위로 올려 놓았는데, 재조정이 서버의 옛 `parentId`(지워질 폴더를 가리킴)로 덮는다. 부모가 없는 하위 폴더가 되어 트리에서 사라진다.

이어서 나는 오류도 같은 원인이다:

```
Uncaught (in promise) Error: 폴더를 찾을 수 없음: 0036617d-…
    at Object.removeFolder
```

되살아난 폴더가 outbox 가 빠진 뒤 재조정으로 캐시에서 사라지는데 React 상태에는 남아 있어, 그 행의 `삭제` 를 누르면 캐시에 없는 id 로 `removeFolder` 가 불린다.

### 한다
- 보낼 목록(outbox)에 아직 안 보낸 삭제가 있으면 **그 삭제가 지운 것을 서버 목록이 되살리지 못하게** 한다 — 폴더·문서 둘 다
- `move-up` 으로 위로 올린 `parentId` 도 서버의 옛 값으로 덮이지 않게 한다
- 캐시에 없는 폴더를 지우려 할 때 예외를 던지지 않는다(이미 지워진 것으로 보고 조용히 끝낸다)
- 회귀 테스트를 남긴다 — 이 되살아남은 단위 테스트로 잡을 수 있다(가짜 api + 가짜 캐시)

### 하지 않는다
- 서버 쪽 `DELETE /api/folders/:id` 동작 변경 — 서버는 맞다(`worker/folders.ts` 가 하위까지 지운다). 문제는 클라이언트 재조정이다
- 오프라인 큐 구조를 새로 설계하기 — 지금 outbox 를 그대로 쓴다
- F-242 의 삭제 방식 선택(위로 옮기기/전부 삭제) UI 변경
- 폴더 깊이 제한(2단계) 변경

## 3. 요구사항

### 3.1 안 보낸 삭제를 재조정에서 존중한다

`list()`·`listFolders()` 의 재조정이 다음을 지킨다:

- outbox 에 `{type:'removeFolder', folderId, mode:'delete-all'}` 가 있으면, **서버 목록에서 그 폴더의 자손인 폴더와 그 폴더들에 속한 문서를 캐시에 다시 넣지 않는다.** 자손 판정은 `descendantFolderIds`(`src/lib/folderTree.ts`)를 **서버 목록** 기준으로 한다 — 캐시에서는 이미 지워져 자손을 알 수 없다
- outbox 에 `{type:'removeFolder', folderId, mode:'move-up'}` 가 있으면, 그 폴더를 부모로 가리키는 서버 행의 `parentId` 를 그대로 쓰지 않는다. 캐시에 이미 위로 올려 둔 값이 있으면 캐시 값을 유지한다
- 위 두 경우 모두 `deleteFoldersNotIn`·`deleteDocsNotIn` 이 "서버에 있으니 남겨 둘 것" 으로 오해해 되살리지 않도록, 남길 집합 계산과 다시 넣기 판정을 같은 규칙으로 맞춘다

구현 방식은 위 규칙을 만족하는 것이면 된다. 판단이 필요하면 "안 보낸 삭제가 하나라도 있으면 그 하위 트리만 재조정에서 제외" 를 기본으로 본다 — outbox 가 빈 다음 재조정에서 정상 상태로 수렴하면 된다.

### 3.2 없는 폴더 삭제
- `removeFolder(id)` 가 캐시에서 폴더를 못 찾으면 예외를 던지지 않고 아무 일도 하지 않고 끝낸다 — 이미 지워진 것이다
- 서버에만 남아 있을 가능성을 대비해 outbox 에 `removeFolder` 를 넣는 것까지는 하지 않는다(중복 DELETE 는 404 로 끝나 의미가 없다)

### 3.3 불변조건 유지
- 캐시에 먼저 쓰고 즉시 resolve 하는 성질(F-207 2.3)은 그대로다. 이 명세는 **서버 목록이 로컬 삭제를 덮지 않게** 하는 것뿐이다
- 온라인·오프라인 상태 갱신(`patchState`) 동작은 바꾸지 않는다
