- (b) **봉인 왕복 — Node.** 6.2 형식(ECDH → HKDF-SHA256 → AES-256-GCM)을 두 곡선으로 다섯 번씩 돌렸다. X25519: 키 생성 첫 회 6.43 ms, 그 뒤 0.18~0.27 ms, 봉인 0.65 ms, 공개키 **43자**(32바이트), 46자 토큰의 `sealed` **142자**. P-256: 키 생성 0.20~0.80 ms, 공개키 87자(65바이트), `sealed` 186자. 두 곡선 다 `sealed` 한 글자를 바꾸면 풀기 실패, 다른 키 쌍의 개인키로도 실패, 원문 일치
- (c) **Chrome ↔ Node 상호 운용.** `https://seal.test/` 를 `page.route` 로 채워 보안 컨텍스트(`isSecureContext === true`)를 만들고, Node 가 만든 CLI 공개키로 **Chrome 이 봉인 → Node 가 풀기**: X25519·P-256 둘 다 원문 일치. 13.1 U2 의 고정 벡터는 Node 가 봉인하고 **Node 와 Chrome 이 각각 JWK 개인키로 풀어** 둘 다 일치했다
- (d) **오류 이름.** X25519 `importKey('raw', 31바이트)` → Node·Chrome 둘 다 `DataError`. 모르는 알고리즘 이름 `importKey` → Node `NotSupportedError`. 8.1 의 `unsupported` 판정 근거
- (e) **브라우저 지원** — MDN `browser-compat-data` `api/SubtleCrypto.json`(main, 2026-09-24 받음). `X25519`(generateKey·importKey·exportKey·deriveBits·deriveKey): **Chrome·Edge 133, Firefox 130, Safari 17, Node 16.17.0**. P-256 **압축 점** 가져오기: Chrome ≤80, **Firefox 146, Safari 미지원**(이 PC Node 24·Chrome 153 에서는 됐다 — BCD 의 Node 값 `false` 와 다르다). P-256 raw(비압축) ECDH: Chrome 37, Firefox 34, Safari 7
- (f) **Node 22 의 X25519 경고.** `nodejs/node` v22.0.0 `lib/internal/crypto/cfrg.js` `cfrgGenerateKey` 첫 줄이 `emitExperimentalWarning`. `CHANGELOG_V22.md` 22.13.0(2025-01-07) "Graduate WebCryptoAPI Ed25519 and X25519 algorithms as stable … will no longer emit an ExperimentalWarning". v22.13.0 `cfrg.js` 에는 `emitExperimentalWarning` 이 0개. 즉 **Node 22.0~22.12 에서는 `login` 때 표준 오류에 경고 한 줄**이 나온다(15장 Q5)
- (g) **Chrome Local Network Access(LNA).** 공식 글 "New permission prompt for Local Network Access"(developer.chrome.com, 2025-06-09, 2025-09-29 갱신 "launching in Chrome 142"): 공개 사이트 → 로컬·**루프백(127.0.0.0/8)** 요청에 권한 창. 대상은 "`fetch()` API, subresource loading, and subframe navigation". WICG 명세 초안(`wicg.github.io/local-network-access`) 주석: "Chromium only applies LNA restrictions to iframe navigations currently. It may be worth expanding this to include main-frame navigations". → 메인이 제안한 (나) `fetch` 로 키 가져오기는 **권한 창 대상이 맞다**. 지금 콜백인 최상위 이동은 **현재는 대상 밖**이다(F-2021 16.2 의 가정 하나가 문서로 뒷받침된다. 브라우저에서 실제로 돌려 본 것은 아니다)
- (h) **Access 첫 단계는 긴 주소를 자르지 않는다.** 쿠키 없이 `curl` 로 `https://rawdoc.app/api/login?return=` + v1 해시 449자를 인코딩한 값(주소 전체 497자)을 GET → 302, `Location` 이 Access 팀 로그인 주소로 **2,456자**, 그 안 `redirect_url` 479자가 원래 `return` 을 끝(host)까지 담았다. 일회용 코드 입력 **뒤** 단계는 로그인이 필요해 확인하지 못했다
- (i) **npx 가 새 판을 받는지** — npm 11.7.0 번들 `libnpmexec/lib/index.js` `missingFromTree` 와 `npm-package-arg`. `npa('rawdoc')` 는 `type: 'range'`, `rawSpec: '*'`. 그래서 **로컬 프로젝트나 전역(`npm i -g`)에 `rawdoc` 이 있으면 그 판을 그대로 쓴다**(`spec.rawSpec === '*'` 이면 바로 그 노드). 없으면 npx 캐시를 보는데 이름만 준 경우(`npxByNameOnly`)는 `preferOnline: true` 로 최신 매니페스트를 받아 `resolved` 가 다르면 새로 설치한다 — **`npx -y rawdoc` 만 쓰던 사람은 0.2.0 을 저절로 받는다.** `rawdoc@latest` 는 `type: 'tag'` 라 전역 설치가 있어도 최신을 받는다. 사용자 컴퓨터의 npm 판은 다를 수 있다

### 한다
- 인증 화면 주소 새 형식 **v2** — 길이 102자(이 PC)·최대 107자(`https://rawdoc.app`, 5자리 포트, host 20자)

## 5. 새 주소 v2

### 5.1 형식

```
{origin}/?app=1#/cli-login/{port}/{host}/{publicKey}
```

예(측정 (a), 102자):

```
https://rawdoc.app/?app=1#/cli-login/54321/DESKTOP-BB5D3D9/LU2MWmx7Dt_VWEhOf5eRhXMOh3kAcyAGjjkjHx8kPh0
```

- 접두사 `#/cli-login/` 과 `?app=1` 은 그대로다 — `src/main.tsx` 분기와 `rootTarget` 첫 방문 우회(F-2021 6.1·6.2)를 건드리지 않는다
- **`state` 를 뺀다.** 이유: `state` 와 공개키는 늘 같은 주소에 함께 실려 있다. 주소를 본 사람은 둘 다 알고, 못 본 사람은 둘 다 모른다. 공개키가 로그인마다 새로 만든 32바이트이므로 `state` 가 막던 것(가짜 콜백·로그인 CSRF)을 공개키가 그대로 막는다. 콜백의 `state` 자리에는 공개키 문자열을 돌려준다(6.3)
- **순서가 `host` 다음 `publicKey` 인 이유**: 마지막 조각이 길이 고정(43자)이면 끝이 잘린 주소는 반드시 검사에 걸린다. host 를 마지막에 두면 host 가 반쯤 잘린 주소가 통과해 이름이 잘린 토큰이 만들어진다

### 5.2 조각 규칙 (하나라도 어기면 `invalid`)

| 조각 | v2 규칙 | v1 규칙(그대로, F-2021 6.1) |
| --- | --- | --- |
| 조각 개수 | 3 | 4 |
| `port` | 10진 정수 1024~65535 | 같음 |
| `host` | `^[A-Za-z0-9-]{1,20}$` | `^[A-Za-z0-9.-]{1,34}$` |
| `state` | 없음 | `^[A-Za-z0-9_-]{22}$` |
| `publicKey` | `^[A-Za-z0-9_-]{43}$` 이고 X25519 `importKey('raw')` 성공 | `^[A-Za-z0-9_-]{300,800}$` 이고 RSA-OAEP SHA-256 `importKey('spki')` 성공 |

- 판 구분은 조각 개수 하나로 한다. **끝이 잘린 v1 주소가 v2 로 잘못 읽히지 않는다**: 조각이 3개가 된 v1 주소의 두 번째 조각은 22자 `state` 인데 v2 host 상한은 20자라 걸린다(13.1 U3 에 넣었다)
- `importKey` 검사는 비동기라 해석 함수 밖이다(8.1). F-2021 6.1 표에 있던 v1 `importKey` 검사는 지금 구현에 없었다(`CliLoginPage` 는 `승인` 때 처음 가져온다) — 이번에 v1·v2 둘 다 첫 화면에서 한다

### 5.3 CLI 쪽 host — `sanitizeCliHost` 새 규칙
`os.hostname()` 값을 → 첫 `.` 앞까지만 → `[A-Za-z0-9-]` 밖 문자는 `-` 로 → 앞 20자 → 비면 `unknown`
- 첫 `.` 에서 자르는 이유: macOS 의 `이름.local`, Linux 의 FQDN(`host.example.com`)에서 뒤는 알아보는 데 도움이 안 되고 길이만 먹는다
- 20자인 이유: 5.2 의 v1/v2 구분(22자 `state` 와 겹치지 않음) + 최대 길이 107자. Windows 컴퓨터 이름은 NetBIOS 15자가 흔하다(이 PC 15자)
- 토큰 이름 `CLI · {host}` 는 그대로(`cliTokenName`). 최대 26자

## 6. 봉인 v2

### 6.1 무엇이 어디에
- CLI: 로그인마다 X25519 키 쌍. 개인키 `extractable: false`, 프로세스 메모리에만. 공개키 raw 32바이트 → base64url(패딩 없음) 43자 → 주소
- 화면: 봉인할 때마다 **일회용** X25519 키 쌍을 만들고, 그 공개키를 `sealed` 앞에 붙인다. 화면 개인키는 봉인 뒤 버린다
- 방문 기록에 남는 것은 두 공개키와 암호문뿐이다 — 개인키가 둘 다 없어 기록만으로는 못 푼다(F-2021 5.3 의 목적 그대로)

### 6.2 바이트 형식 — 계약 (웹과 CLI 가 따로 게시되므로 한 바이트도 바꾸지 않는다)

```
shared  = X25519(화면 개인키, CLI 공개키)                         // deriveBits 256비트
aesKey  = HKDF-SHA256(ikm = shared, salt = 빈 바이트열,
                      info = ASCII "cli-seal-v2" ‖ 화면 공개키 raw(32) ‖ CLI 공개키 raw(32)), 256비트
sealed  = base64url( 화면 공개키 raw(32) ‖ iv(12, 무작위) ‖ AES-256-GCM(aesKey, iv, UTF-8(토큰)) )   // 태그 16바이트 포함, AAD 없음
```

- 46자 토큰이면 32 + 12 + 46 + 16 = 106바이트 → **142자**(측정 (b))
- `info` 에 두 공개키를 넣는 이유: 키 유도를 이 한 쌍에 묶는다(ECIES 의 일반적인 결합). 문자열 `cli-seal-v2` 는 다른 용도의 HKDF 와 섞이지 않게 하는 꼬리표다. 제품명을 넣지 않는다(불변조건)
- 푸는 쪽 규칙: 바이트가 32 + 12 + 17 = 61 미만이면 실패. 풀린 값이 `^rd_[A-Za-z0-9_-]{43}$` 가 아니면 "풀지 못함"(F-2021 5.3 그대로)

### 6.3 콜백
- 주소는 지금 그대로 `cliCallbackUrl` 로 만든다: `http://127.0.0.1:{port}/callback?state=…&sealed=…` / `…&error=denied`
- v2 의 `state` 값은 **주소에 실렸던 CLI 공개키 43자**(`callbackStateOf`). CLI 는 자기 공개키와 상수 시간 비교를 한다 — `classifyCallback` 은 길이가 다른 값도 이미 다룬다
- 콜백 주소 길이는 사람이 볼 일이 없어 줄이지 않는다(v2 약 230자)

### 6.4 `src/lib/cliSeal.ts` 계약

```ts
// v1 (F-2021) — 이름·동작 그대로. 새 웹이 0.1.0 CLI 의 주소를 받을 때 쓴다
export function generateSealKeyPair(): Promise<{ publicKey: string; privateKey: CryptoKey }>
export function sealToken(publicKey: string, token: string): Promise<string>
export function openSealedToken(privateKey: CryptoKey, sealed: string): Promise<string>
// v2 (F-2023)
export function generateSealKeyPairV2(): Promise<{ publicKey: string; privateKey: CryptoKey }>   // publicKey 43자
export function sealTokenV2(publicKey: string, token: string): Promise<string>
export function openSealedTokenV2(privateKey: CryptoKey, publicKey: string, sealed: string): Promise<string>  // publicKey 는 HKDF info 에 필요
export function checkSealPublicKey(version: 1 | 2, publicKey: string): Promise<'ok' | 'unsupported' | 'invalid'>
```

- `checkSealPublicKey`: 그 판의 `importKey` 가 성공하면 `ok`, `NotSupportedError` 면 `unsupported`, 그 밖의 실패(`DataError`, base64url 해독 실패)는 `invalid`(측정 (d))
- 단위 테스트(환경 `node`)에서 `unsupported` 를 만들 수 있어야 한다. `NotSupportedError` 를 던지는 가짜 `subtle` 을 넣는 방법은 구현자가 정한다(선택 인자든 모듈 안 주입이든)
- `Buffer` 를 쓰지 않는다(브라우저·Node 공용 — F-2021 5.3). base64url 도우미는 이미 파일 안에 있다

## 7. 호환

### 7.1 조합표

| CLI \ 웹 | 지금 웹(F-2021) | 새 웹(F-2023) |
| --- | --- | --- |
| 0.1.0 (v1 주소) | 동작 | **동작** — v1 을 계속 받는다 |
| 0.2.0 (v2 주소) | `잘못된 로그인 주소입니다…` — 깨진다 | 동작 |

- 깨지는 칸은 하나다. 그래서 **웹을 먼저 배포하고 CLI 를 게시한다**(7.3). 웹이 먼저면 어느 시점에도 깨지지 않는다
- 0.1.0 이 한동안 남는다: 전역·로컬 설치는 스스로 올라가지 않는다(측정 (i)). `npx -y rawdoc …` 만 쓰는 사람은 게시 뒤 다음 실행에서 0.2.0 을 받는다

### 7.2 새 웹이 옛 CLI 에 하는 것
- **정상 v1 주소**: 아무 말 없이 지금처럼 승인한다. "업데이트하세요" 를 보이지 않는다 — 동작하는 흐름을 막거나 끼어들 이유가 없다
- **잘린 v1 주소**(`isLegacyCliLoginHash`): 잘림 문구에 업데이트 명령 한 줄을 더한다(8.2). 옛 CLI 사용자가 잘림을 겪는 바로 그 자리이기 때문
- v1 받기를 끝내는 시점은 정하지 않는다(15장 Q4). 남겨 두는 비용은 `cliSeal.ts` 의 RSA 함수 세 개와 해석 분기 하나다

### 7.3 게시 순서 (F-2021 10.3·CLAUDE.md "Deployment" CLI publish 에 더하는 것)
1. F-2023 구현이 든 웹을 배포하고 반영을 확인한다
2. **게시 전 확인**: 저장소 루트에서 `npm run build:cli` → `node cli/dist/rawdoc.js login --no-browser --force` → 찍힌 v2 주소를 브라우저로 열어 `rawdoc.app` 이 **승인 화면**을 보이는지 본다 → `취소` → 터미널에 `브라우저에서 로그인을 취소했습니다.`(종료 1). 이게 되면 운영 웹이 v2 를 안다
3. `cli/` 에서 `npm pack --dry-run` → `npm publish` → `npm view rawdoc version` 이 `0.2.0` → 태그 `cli-v0.2.0`
4. `content/changelog.md` 한 줄(F-273): 사용자에게 보이는 변화 — 예 `터미널 로그인 주소가 짧아져 링크를 눌러도 잘리지 않습니다.`
- 순서를 어겨 0.2.0 이 먼저 나가면: 웹 배포 전까지 새 CLI 의 `login` 이 실패한다. 우회는 `login --with-token`(F-2021 5.5). 웹을 배포하면 저절로 풀린다

### 7.4 버전 `0.2.0`
F-2021 10.1 은 명령·옵션·종료 코드·`--json` 이 깨질 때만 minor 로 올린다. 이번에 그것들은 그대로지만, **로그인이 새 웹을 요구한다**(7.1 의 깨지는 칸 — `--server` 로 옛 커밋의 개발 서버를 쓰는 경우도 같다). 서버와의 호환이 깨지는 변경이라 minor 로 본다. 메인 지시와 같다

## 9. CLI 변경
- `runLoginCommand`(`cli/src/main.ts`): `generateSealKeyPairV2` 로 키를 만들고, `state` 를 만들지 않고, `buildCliLoginUrl(origin, { port, host: sanitizeCliHost(hostname), publicKey })` 로 주소를 만든다. 안내 문구(`브라우저에서 로그인을 승인하세요. 브라우저가 열리지 않으면 이 주소를 여세요:`)와 주소를 따로 한 줄에 찍는 것은 그대로
- `startCallbackServer`(`cli/src/login.ts`): 기대하는 `state` 는 자기 공개키 문자열, 풀기는 `openSealedTokenV2(privateKey, publicKey, sealed)`. 인자 모양은 구현자가 정한다(공개키를 받아 `expectedState` 를 겸해도 된다). `classifyCallback` 과 5.2 판정표(F-2021)는 그대로
- `generateLoginState` 와 그 테스트는 지운다 — 쓰는 곳이 없어진다
- 번들이 v1 RSA 함수를 끌고 오는지는 따지지 않는다(트리 셰이킹 결과는 B1 에서 크기만 적는다)
- Node 22.0~22.12 의 `ExperimentalWarning` 한 줄(측정 (f))은 막지 않는다 — 표준 오류라 `--json` 표준 출력을 깨지 않고, `login` 에서만 한 번 나온다(15장 Q5)

## 15. 열린 질문 / 사람 결정

### Q1. 키 교환 곡선 — 기본값 **X25519** (사람 결정 필요)
- 기본값 이유: 주소 102자(최대 107자)로 120칸 터미널 한 줄에 들어간다. 3장 후보 A(터미널 줄바꿈)가 원인이라면 한 줄에 들어가는 것이 핵심이다
- 대가: Chrome·Edge 133(2025-02), Firefox 130, Safari 17 미만은 승인할 수 없다(측정 (e)). 그 경우 `unsupported` 화면이 업데이트나 `--with-token` 을 안내한다
- 다른 쪽 **P-256**(메인 제안 (가)): 주소 146자(최대 151자). 사용자 목표 "120~160" 안이지만 120칸 터미널에서 두 줄이다. 브라우저 하한 걱정이 없다. 바뀌는 것: 6.2 의 곡선 이름과 바이트 수(화면 공개키 65, `sealed` 186자), 5.2 키 규칙 `{87}`, U2 고정 벡터 새로 만들기, `unsupported` 상태·E5·S6 삭제, 5.3 host 상한은 20 유지(v1/v2 구분 근거가 같다)

### Q2. `state` 를 뺀다 — 기본값 **뺀다**
- 이유: 5.1. 23자를 아낀다
- 다른 쪽(남긴다): 주소 125자. 콜백·CLI 판정이 지금과 같은 모양으로 남는다. 보안상 얻는 것은 없다

### Q3. host 를 주소에 남긴다 — 기본값 **남기되 첫 `.` 앞, 20자**
- 이유: 토큰 목록에서 어느 컴퓨터 토큰인지 알아보는 유일한 단서다. 토큰 이름을 나중에 바꾸는 API 가 없어(`worker/index.ts` 의 `/api/tokens` 는 GET·POST·DELETE 뿐) CLI 가 콜백 뒤에 이름을 붙일 수 없다
- 다른 쪽 ①(뺀다): 주소 86자. 토큰 이름이 `CLI · {날짜}` 같은 것이 되고 승인 화면의 토큰 이름 줄이 기기를 말하지 못한다
- 다른 쪽 ②(CLI 가 이름을 붙인다): 서버에 토큰 이름 바꾸기 라우트가 필요하다 — `worker/apiTokens.ts`·`worker/index.ts` 소유가 늘고 F-304·F-305 와 겹친다. 메인 제안이었지만 서버 변경 0 인 이번 범위를 넘는다

### Q4. v1(RSA) 주소 받기를 언제 끝내나 — 기본값 **정하지 않는다**
- 이유: 남기는 비용이 작고(7.2), 전역 설치 0.1.0 이 언제 사라질지 알 수 없다(측정 (i))
- 다른 쪽(지금 끊는다): v1 주소에 "업데이트하세요" 만 보이고 RSA 코드를 지운다. 0.1.0 전역 설치 사용자는 `npx -y rawdoc@latest login` 을 해야 로그인된다. F-2021 E1~E3·E6~E8 은 v2 로 옮기거나 지운다

### Q5. Node 22.0~22.12 의 경고 — 기본값 **그대로 둔다**(`engines` `>=22` 유지)
- 이유: 표준 오류 한 줄, `login` 때만. 22 LTS 사용자는 대부분 22.13 이상이다(22.13.0 = 2025-01-07)
- 다른 쪽: `engines` 와 시작 검사를 `>=22.13` 으로(시작 검사 문구 `Node.js 22.13 이상이 필요합니다 …`). `cli/src/main.ts` 의 버전 검사와 `cli/package.json`·README 가 바뀐다

### 기본값으로 정한 것 (승인 범위 안)
- 콜백 `state` 에 공개키를 돌려준다(6.3), `info` 꼬리표 `cli-seal-v2`, 문구(8.2), 게시 전 확인 절차(7.3-2), 버전 `0.2.0`(7.4), 정상 v1 주소에는 업데이트 안내를 하지 않는다(7.2)
