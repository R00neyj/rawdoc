## 2. 전체 그림 (한 문단씩)

- **붙이기**: 편집기가 마운트되고 이 경로가 댓글을 볼 수 있으면(4장 `read`·`write`) `useDocComments` 가 `handle.comments.attach({ onActivate, onLayout })` 를 부른다. 경로가 바뀌어 볼 수 없게 되거나 편집기가 내려가면 뗀다. 붙이지 않은 경로에서는 편집기에 댓글 표시가 없다(F-504 3.1)
- **읽기**: 스레드 목록은 훅이 `handle.comments.map` 을 관찰해 `groupCommentThreads` 로 만든다. 카드 위치는 F-504 가 보내는 `CommentLayout`(스크롤 콘텐츠 좌표)을 받아 `layoutRailCards` 로 겹침을 푼다. **`CommentLayout` 에 없는 스레드는 그리지 않는다**(F-504 4.4 — 한 프레임 늦게 온다)
- **쓰기**: 경로가 `write` 면 쓰기 수단(`CommentWriter`)은 직접 쓰기 — 편집기 `Y.Doc` 에 트랜잭션 하나. 그 뒤는 본문과 같은 길(로컬은 편집기 Doc 에 남고, 실시간은 게이트 → 방 Doc → provider·`md-yjs`). F-506 은 같은 모양의 명령 쓰기 수단을 더한다
- **보이기**: 메인 열이 968px 이상이면 오른쪽 레일, 미만이면 아래 판. 상단바 `댓글` 버튼이 연다·닫는다. 활성 스레드는 하나이고 F-505 가 가진다 — `handle.comments.setActive` 로 편집기에 알린다
- **이동**: 카드 → `reveal`(편집 영역 가운데로, 커서 그대로). 앵커·거터 → `onActivate` → 활성 + 레일(또는 판)에서 그 카드. 주소 `#/d/{id}/c/{tid}` → 문서를 열고 댓글이 준비되면 카드 이동과 같게

- `commentAccess` 판정 — 위에서부터 처음 맞는 줄 (4장 표와 같은 내용):
  1. `sharedScreen` 이거나 `e2ee` → `none`
  2. `docPath === null` → `loading`
  3. `docPath === 'local'` → `readOnly` 면 `read`, 아니면 `write`(actor `{ kind: 'local', canEdit: true }`, author `{ id: null, email: null }`)
  4. `docPath === 'realtime'` 이고 `role !== 'view'` 이고 `account` 가 있고 막히지 않음 → `readOnly` 면 `read`, 아니면 `write`(actor `{ kind: 'server', userId: account.id, role: role ?? 'owner', blocked: false }`, author `{ id: account.id, email: account.email }`)
  5. 그 밖(`view`·`pending`·`fallback`·`offline-view`, 그리고 F-506 전의 `realtime` + view) → `unavailable`
- `layoutRailCards` 규칙(경계값이 결정이라 짧은 의사코드로 적는다): 활성이 없으면 위에서부터 `top[i] = max(anchorTop[i], minTop, 앞 카드 아랫변 + gap)`. 활성 카드 `k` 가 있으면 `top[k] = max(anchorTop[k], minTop)` 로 고정하고, `k` 뒤는 같은 식으로 아래로 밀고, `k` 앞은 `top[i] = min(anchorTop[i], 뒤 카드 윗변 − gap − height[i])` 로 위로 민다. 그 결과 맨 앞 카드가 `minTop` 보다 위로 나가면 **맨 앞부터 활성 없음 식을 한 번 더** 돌린다(활성 카드도 밀린다 — 문서 맨 위를 넘는 카드는 스크롤로 닿을 수 없어서다). 비용 r1
- 입력 카드(새 댓글, 7.1)는 `id` 가 `'draft'` 인 항목으로 `anchorTop` 순서 자리에 끼우고 **활성으로 넘긴다** — 입력하는 동안 입력 카드가 제자리에 있고 다른 카드가 비킨다
- `commentRailMode(w)`: `w >= COMMENT_RAIL_MIN_MAIN` 이면 `'rail'`
- `initialCommentRailOpen(pref, n)`: `pref === 'open'` → 참, `'closed'` → 거짓, `null` → `n >= 1`
- `formatCommentTime(at, now)`: 차이 60초 미만(미래 시각 포함) `방금 전`, 60분 미만 `{n}분 전`, 24시간 미만 `{n}시간 전`, 같은 해 `{M}월 {D}일`, 다른 해 `{YYYY}. {M}. {D}.`(F-500 5.1). 해·월·일은 브라우저 현지 시각. 내림(`floor`)

### 3.2 `src/app/useDocComments.ts` — 쓰기 수단과 쓰기 함수

```ts
import type * as Y from 'yjs'
import type { CommentAuthor, CommentThread } from '../lib/docComments'
import type { CommentDraft } from '../editor/commentMarks'

export type CommentWriteFailure =
  | 'empty' | 'too_long'                 // 본문 (C2)
  | 'doc_full' | 'thread_full'           // 한도 (C3)
  | 'gone'                               // 후보 범위가 지워짐 (C10)
  | 'not_found'                          // 대상 댓글이 없음 (C9)
  | 'invalid'                            // 모양 검사 실패 (C11)
  | 'forbidden' | 'rate_limited' | 'offline'   // 명령 경로 전용 — F-506 (C6·C5·C4)
export type CommentWriteResult = { ok: true; id: string } | { ok: false; reason: CommentWriteFailure }

export type CommentWriter = {
  add(input: { draft: CommentDraft; body: string; mentions: string[] }): Promise<CommentWriteResult>
  reply(input: { parent: string; body: string; mentions: string[] }): Promise<CommentWriteResult>
  resolve(threadId: string, resolved: boolean): Promise<CommentWriteResult>
  remove(id: string): Promise<CommentWriteResult>
}

// React 없이 도는 쓰기 — 편집기 Y.Doc 에 트랜잭션 하나씩. U9~U16 이 부른다
type WriteTarget = { doc: Y.Doc; map: Y.Map<unknown>; author: CommentAuthor; now: () => number; newId: () => string }
export function writeNewThread(t: WriteTarget, input: { draft: CommentDraft; body: string; mentions: string[] }): CommentWriteResult
export function writeReply(t: WriteTarget, input: { parent: string; body: string; mentions: string[] }): CommentWriteResult
export function writeResolved(t: WriteTarget, threadId: string, resolved: boolean): CommentWriteResult
export function writeDelete(t: WriteTarget, id: string): CommentWriteResult
export function createDirectCommentWriter(t: WriteTarget): CommentWriter   // 위 넷을 Promise.resolve 로 감싼다
```

- **쓰기 수단이 Promise 인 이유**: F-506 의 명령 경로는 ack 를 기다린다(`보내는 중…`). 화면은 처음부터 모든 쓰기를 기다리는 것으로 다룬다 — F-506 이 컴포넌트를 고치지 않고 쓰기 수단만 바꿔 끼우게
- 공통 규칙: 본문은 `normalizeCommentBody` 뒤 `checkCommentBody`(`empty_body` → `empty`, `body_too_long` → `too_long`). 한도는 `groupCommentThreads(map.entries())` 로 센 스레드에 `checkCommentCapacity`. 쓰기 직전 만든 `CommentEntry` 를 `validateCommentEntry` 로 한 번 더 보고, 실패면 쓰지 않고 `invalid`. **실패면 `Y.Doc` 에 아무것도 쓰지 않는다**
- `writeNewThread`: 항목 `{ v: 1, parent: null, anchor: draft.anchor, quote: draft.quote, body, mentions, author, createdAt: now(), resolved: null }` 을 새 id(`crypto.randomUUID()`, 테스트는 `newId` 로 바꿈)로 한 트랜잭션에 넣는다. 후보 확정(`takeDraft`)은 부르는 쪽(훅)이 먼저 하고, `takeDraft()` 가 `null` 이면 이 함수를 부르지 않고 `gone`
- `writeReply`: 부모가 없거나 부모가 답글이면 `not_found`. 답글 항목(`anchor: null`, `quote: ''`)을 넣고, **부모가 해결 상태면 같은 트랜잭션에서 부모의 `resolved` 를 `null` 로**(F-500 4.4 2번)
- `writeResolved`: 첫 댓글이 없으면 `not_found`. 값은 JSON 한 덩어리라 항목 전체를 `resolved` 만 바꾼 새 객체로 다시 쓴다 — `{ by: author, at: now() }` 또는 `null`
- `writeDelete`: 없는 id 면 `not_found`. 첫 댓글이면 그 답글 전부와 함께, 답글이면 그것만 — **한 트랜잭션**. 권한(2.4)은 화면이 `commentAllowed` 로 메뉴를 숨겨 먼저 막고, 이 함수는 권한을 다시 보지 않는다(서버 문서는 DO 가 사후 검사, F-500 3.2)
- 트랜잭션 origin 은 F-505 의 모듈 상수 객체 하나(`COMMENT_WRITE_ORIGIN`). 게이트 `onEditorUpdate` 는 origin 을 가리지 않고 방 Doc 으로 넘긴다(코드 확인). 편집기 `Y.UndoManager` 는 `content` 만 추적하므로 되돌리기 대상이 아니다(F-500 1.2)
- 멘션: F-505 는 늘 `mentions: []` 로 쓴다 — 후보 고르기는 F-507(`finalizeMentions(body, picked)`), 로컬 문서는 늘 `[]`(F-500 2.1)

훅 `useDocComments`(모양은 구현이 정한다)가 할 일은 11장 표와 5~8장 규칙이 정한다. 훅은 `App.tsx` 에 하나이고, 카드 컴포넌트는 스레드 id 를 React `key` 로 쓴다(F-504 4.4 — 입력칸 조합 중 레일이 움직여도 입력 요소를 다시 만들지 않게)

## 5. 레일 — 넓은 창 (반드시 결론 1)

### 5.1 열고 닫기·자리

- **자리**: `.content-area` 안, `.editor-slot` 바로 뒤의 형제 요소(폭 `COMMENT_RAIL_WIDTH`, 줄어들지 않음). DOM 순서는 `.editor-slot` → `.comment-rail` → `Outline` — Tab 순서가 편집기 → 레일 → 목차 버튼 → 상태바가 된다(F-500 4.9)
- **본문 폭**: 레일이 있는 동안 본문(거터 포함) 최대 폭 = `min(800px, 편집기 칸 폭 − COMMENT_CONTENT_SIDE_GAP)`. 편집기 칸 폭 = 메인 열 − 280 이라 개요 4.3 의 `min(800px, 메인 열 − 280 − 48)` 과 같다. 메인 열 968px 에서 640px — 그보다 좁아지기 전에 판으로 바뀐다. 구현은 `.content-area` 에 레일 열림 표지를 두고 그 안에서 `--content-max` 를 다시 정하는 방식을 권한다(`.cm-scroller` 가운데 정렬 식이 `--content-max` 를 쓴다, F-143 3.8). 수치는 e2e 로 고정하지 않는다
- **보이는 조건(모두)**: 편집기가 보임(`showEditor`, 공유 화면·지도·도움말 아님) · 접근이 `none` 이 아님 · 보기 모드가 `편집`·`원문` · `commentRailMode(메인 열 폭) === 'rail'` · 레일 열림 상태가 참
- **레일 열림 상태**: 편집기가 마운트될 때마다(문서 전환·다시 마운트) `initialCommentRailOpen(md.commentRail, 열린 스레드 수)` 로 정한다 — 열린 스레드 수는 붙인 뒤 첫 `onLayout` 때의 값. 붙이지 않는 경로(`unavailable`·`loading`)는 그 순간 0 으로 센다. 그 뒤 상단바·팔레트로 여닫으면 값을 바꾸고 `md.commentRail` 에 쓴다. 자동으로 열 때(7장 앵커·달기·해시)는 값만 참으로 바꾸고 쓰지 않는다
- **메인 열 폭**: `.content-area` 의 `clientWidth` 를 `ResizeObserver` 로 잰다(`Outline` 의 여백 판정과 같은 방식)
- **목차**: 레일이 보이는 동안 `Outline` 에 `buttonOnly`. 목차 버튼(`.outline-popup`, 편집 영역 오른쪽 위)은 레일 왼쪽으로 비킨다 — `.content-area` 레일 열림 표지 아래에서 `right` 를 레일 폭만큼 더한다

### 5.2 카드 정렬

- **입력**: F-504 `onLayout` 의 `anchored`(문서 위치순, `top` 은 스크롤 콘텐츠 좌표) 중 보일 것 — 열린 스레드 전부, `해결된 댓글 보기` 가 켜져 있으면 해결된 것도. 카드 높이는 카드마다 `ResizeObserver` 로 잰 테두리 상자 높이(r2: 500개 다시 재기 0.2ms). 입력 카드(7.1)가 있으면 3.1 끝 규칙대로 끼운다
- **계산**: `layoutRailCards(cards, activeId, COMMENT_CARD_GAP, 0)` 하나. 활성 카드는 앵커 높이에 고정되고 나머지가 위아래로 비킨다(개요 4.3). 비용 r1 — 500개 0.005ms
- **다시 계산하는 때**: `onLayout` 이 올 때(F-504 가 프레임당 최대 한 번, 같은 값이면 안 보냄), 카드 높이가 바뀔 때(활성 펼침·답글 추가·창 폭), 활성이 바뀔 때, `해결된 댓글 보기` 를 바꿀 때, 입력 카드가 열리고 닫힐 때. 같은 프레임의 여러 까닭은 한 번으로 묶는다(`requestAnimationFrame` 하나)
- **처음 재기 전**: 높이를 아직 모르는 카드는 `visibility: hidden` 으로 두고 첫 계산 뒤 보인다 — 맨 위에 쌓였다가 튀는 것을 막는다
- **React 렌더와 위치 분리**: 카드 컴포넌트는 스레드 내용·활성·펼침·권한이 같으면 다시 그리지 않는다(메모). 위치는 카드 요소의 `transform` 한 속성만 바뀐다. 이유: `onLayout` 은 입력 중 한 글자마다 올 수 있다(F-504 4.4) — 500개를 한 글자마다 다시 그리지 않게. **React 렌더 비용은 재지 않았다**(r2 는 평범한 DOM) — H7
- 고아·해결된 고아는 이 정렬에 들지 않는다(5.4)

### 5.3 스크롤 따라가기

- 카드들은 트랙 요소 하나 안에 있고, 트랙의 세로 이동 = `−scrollDOM.scrollTop`. `handle.view.scrollDOM` 의 `scroll`(passive)에서 **곧바로** 트랙의 `transform` 을 쓴다 — React 상태를 거치지 않는다. React 가 렌더 때 이 `transform` 을 덮어쓰지 않게 트랙의 `style` 에 넣지 않는다
- 맞춤 조건(판정 E5·H1): 밀리지 않은 카드의 윗변 화면 y = 그 앵커 시작 줄 윗변의 화면 y. 레일 머리 줄(5.5)은 카드 영역 위에 따로 있고, 카드 영역은 레일 윗변에서 머리 줄 높이만큼 내려온 곳부터 잘린다 — 트랙 이동에 그 높이를 빼서 맞춘다(구현이 정한다)
- 카드 영역은 `overflow: hidden` 이고 **스스로 스크롤하지 않는다.** 카드에 포커스가 가면 브라우저가 이 영역을 스크롤할 수 있어서, 이 영역의 `scroll` 에서 `scrollTop` 을 0 으로 되돌린다. 포커스 이동으로 카드를 보이게 하는 것은 7.5(포커스 = 활성 + `reveal`)가 맡는다

### 5.4 고아 묶음

- 레일 맨 아래에 붙은 접는 묶음 `.comment-orphans`. 머리 `본문이 지워진 댓글 {N}` (N 은 보이는 고아 수), 누르면 펼치고 접는다. **처음 접힘.** 펼치면 레일 높이의 50% 까지 위로 자라고 그 안에서 스크롤한다. 스크롤 따라가기(5.3)와 무관하다
- 이유: 개요 4.3 "고아 묶음은 맨 아래" 를 트랙 끝에 두면 짧은 문서에서 편집기를 끝까지 내려도 닿지 않는다 — 트랙은 편집기 스크롤 범위만큼만 움직인다
- 고아 카드: 달 때의 `quote` 를 취소선(`<del>`)으로 보이고 그 아래 `댓글을 단 부분이 지워졌습니다.`. `본문으로 이동` 이 없다(누르면 활성만). 답글·해결·삭제는 된다(개요 2.3)
- 해결된 고아는 `해결된 댓글 보기` 가 켜져 있을 때만(개요 2.3). 보이는 고아가 0 이면 묶음이 없다
- 활성 스레드가 고아면 묶음을 펼치고 그 카드가 보이게 **묶음 목록 요소의 `scrollTop` 만** 바꾼다(`scrollIntoView` 는 `overflow: hidden` 조상인 `.content-area` 까지 스크롤할 수 있어 쓰지 않는다 — `Outline` 의 `scrollTo` 와 같은 이유)

### 5.5 머리 줄·빈 상태

- 머리 줄: 제목 `댓글` + 체크 `해결된 댓글 보기`. 닫기 버튼은 없다(상단바 `댓글` 이 닫는다)
- 몸통 — 위에서부터 처음 맞는 것 하나: 접근 `loading` 또는 붙인 뒤 첫 `onLayout` 전 → `불러오는 중…` / `unavailable` → C8 / 스레드 0개 → `write` 면 `이 문서에 댓글이 없습니다. 본문을 선택하고 댓글을 달아 보세요.`, `read` 면 `이 문서에 댓글이 없습니다.` / 열린 스레드 0개이고 해결 보기 꺼짐 → `열린 댓글이 없습니다.` / 그 밖 → 카드
- 입력 카드가 열려 있으면 빈 상태 문구 대신 입력 카드가 보인다

### 5.6 레일 여분 — 카드가 문서 끝을 넘을 때

- 마지막 카드 아랫변이 편집기 스크롤 높이를 넘으면(문서 끝 가까이 댓글이 몰림) 그 카드들은 편집기를 끝까지 내려도 보이지 않는다. 문서 아래 여백은 `--doc-pad-bottom`(50dvh)뿐이다
- 규칙: 넘는 만큼(+ `COMMENT_CARD_GAP`) 편집기 본문 아래 여백을 늘린다. 이름 `--comment-rail-extra`(px, 기본 0)를 `.content-area` 에 두고 `.cm-content` 아래 패딩이 `--doc-pad-bottom` 에 이 값을 더한다. 비교할 높이는 **지금 여분을 뺀** 스크롤 높이다(여분이 여분을 부르는 고리를 막는다). 레일이 닫히면 0
- 장식이 아니라 CSS 패딩이라 문서 내용은 바뀌지 않는다. CM 은 `.cm-content` 의 패딩 변화를 스스로 재지 않지만(`ResizeObserver` 는 `scrollDOM` 만, r 아님 — 코드 확인) 아래 여백만 바뀌므로 다음 측정까지 틀어지는 것은 문서 끝 아래 빈 공간뿐이다
- 16장 Q4 — 두지 않는 안

## 6. 판 — 좁은 창 (반드시 결론 2)

- **전환 기준**: `commentRailMode(메인 열 폭)` — 968px 미만이면 판. 창 폭이 아니라 메인 열 폭이다(넓은 창에서 사이드바가 300px 이면 창 1268px 미만에서 판). 사이드바가 겹쳐 열리는 창(1024px 미만, I2)은 메인 열 = 창 폭이다
- **전환 때**: 레일 ↔ 판을 바꿔도 활성 스레드·입력 중인 새 댓글·답글 글자는 남는다(훅 상태). 레일이 열린 채 좁아지면 판은 **닫힌 채** 시작한다 — 판은 화면 60% 를 덮어서 자동으로 뜨지 않는다. 판이 열린 채 넓어지면 레일 열림 상태를 참으로 두고(저장하지 않음) 판을 닫는다
- **모양**: 창 아래에 붙은 `.comment-sheet`, 높이 창 높이의 60%(`COMMENT_SHEET_HEIGHT`), 머리 `댓글` + 체크 `해결된 댓글 보기` + 버튼 `닫기`. 몸통은 5.5 와 같은 상태 문구, 아니면 문서 위치순 카드 목록(`CommentLayout.anchored` 순서) → 고아 묶음(펼친 채). 입력 카드는 목록 맨 위. 판 안에서 스크롤한다. 정렬(5.2)·스크롤 따라가기(5.3)·여분(5.6)은 쓰지 않는다
- **열기**: 상단바 `댓글`·팔레트 `댓글 열기`, 앵커·거터 누르기(`onActivate`), `댓글 달기`, 해시 이동. 열면 포커스를 판 안으로 — 입력 카드가 있으면 그 `textarea`, 아니면 활성 카드, 둘 다 없으면 머리 `닫기`
- **닫기**: `닫기` 버튼, 판 안에 포커스가 있을 때 `Esc`(입력칸 `Esc` 는 7.1·7.2 가 먼저 — `Esc` 한 번은 한 가지만 한다), 판 바깥 `pointerdown`. 바깥 누르기 중 **앵커(`.cm-comment-anchor`)·거터 표시(`.cm-comment-gutter-marker`)·상단바 `댓글` 버튼**은 닫지 않는다 — 누르자마자 다시 여는 깜빡임을 막는다. 닫으면 포커스를 편집기로(`handle.focus()`)
- **카드 누르기**: 판을 닫고 `reveal` — 판이 편집 영역 아래 60% 를 가리므로 열린 채로는 앵커가 판 밑에 있을 수 있다
- 모달이 아니다(`<dialog>` 가 아니다). 그래서 `Ctrl+P` 처리기의 `dialog[open]` 검사에 걸리지 않는다
- 떠 있는 `댓글 달기` 버튼(7.1)은 판 모드에서 선택 바로 아래, 편집 영역 오른쪽 끝에 뜬다(개요 4.3)

## 7. 흐름

### 7.1 달기 (개요 4.4 1번)

1. **시작**: 떠 있는 버튼·우클릭 `댓글 달기`·팔레트 `comment.add`·`Ctrl+Alt+M`. 모두 같은 함수 하나로 간다
2. 막는 순서: 접근이 `write` 가 아님 → 아무것도 안 함(우클릭은 이미 비활성, 단축키는 4장 표) → 보기 모드 → 아무것도 안 함 → 문서 한도(`checkCommentCapacity(threads, null) === 'doc_full'`) → C3 첫 문구(error), 입력 카드를 열지 않음 → `handle.comments.beginDraft()` 가 `null` → C1(info)
3. **입력 카드 열기**: 넓은 창은 레일 열림 상태를 참(저장 안 함), 입력 카드를 후보 범위 시작 줄 높이에(5.2), 좁은 창은 판을 열고 맨 위에. 포커스를 입력칸으로. 후보 장식(`cm-comment-anchor-draft`)은 F-504 가 칠한다
4. **입력 카드 높이 기준**: 연 순간 `beginDraft` 가 돌려준 범위의 시작 줄 윗변을 F-504 4.4 와 같은 좌표계(`view.documentTop` 기준 스크롤 콘텐츠 좌표)로 잰 값. 그 뒤 위쪽 본문이 바뀌어도(원격 편집) 다시 재지 않는다 — 보낼 때의 범위는 매핑된 후보(`takeDraft`)라 맞다. 16장 Q5
5. **입력 카드가 열린 채 다시 시작**하면 입력한 글은 두고 후보만 새 선택으로 바꾼다(`beginDraft` 가 후보를 바꾼다, F-504 3.4). 새 선택이 비었으면 C1 이고 옛 후보가 남는다
6. **보내기**: `Ctrl+Enter` 또는 `댓글 달기` 버튼. 본문 검사(3.2) → `takeDraft()` → `null` 이면 입력 카드에 C10, 글은 남긴다(보내기 버튼 비활성, 5번으로 다시 고르면 풀린다) → 쓰기 수단 `add` → 성공이면 입력 카드를 닫고 새 스레드를 활성으로(카드는 다음 `onLayout` 에 나타난다 — F-504 4.4), 포커스를 편집기로. 실패면 글을 남기고 3.2 의 문구
7. **버리기**: `Esc`(입력칸) 또는 `취소` → `clearDraft()`, 입력 카드 닫기, 포커스를 편집기로
8. **입력 카드의 버튼 상태**: 앞뒤 공백을 뺀 길이 0 이면 `댓글 달기` 비활성. 1,000 초과면 비활성 + 입력칸 아래 C2. 글자 수 `{n}/1000` 은 길이가 900 이상일 때만 보인다(`COMMENT_BODY_COUNTER_FROM`). 길이는 `normalizeCommentBody` 뒤 UTF-16 길이(서버와 같은 셈)
9. **문서를 떠나면**(문서 전환·편집기 다시 마운트) 입력 중인 새 댓글은 버린다 — 후보 범위가 그 편집기에만 있다
10. **떠 있는 버튼**이 보이는 조건(모두): 접근 `write`, 보기 모드 `편집`·`원문`, 주 편집기의 주 선택이 비어 있지 않음(표 칸 하위 편집기 선택은 아님), 조합 중 아님, 입력 카드가 닫혀 있음. 자리: 넓은 창은 레일 트랙 안 선택 시작 줄 높이(카드 위에 겹쳐 뜬다), 좁은 창은 6장 끝. 버튼의 `mousedown` 은 기본 동작을 막아 편집기 선택·포커스를 뺏지 않는다. 툴팁 `댓글 달기 (Ctrl+Alt+M)`, 아이콘 `IconAddComment`

### 7.2 답글 (개요 4.4 2번)

- 답글 입력칸은 **활성 카드에만** 보인다(비활성 카드를 짧게 두기 위해). 접근 `write` 일 때만
- 자리 표시 `답글을 입력하세요.`, 버튼 `답글`. `Ctrl+Enter` 보내기, `Esc` 는 입력칸을 비우고 포커스를 그 카드로
- 한도: 스레드 100개(`thread_full`)·문서 500개(`doc_full`)면 버튼 비활성 + 입력칸 아래 C3 해당 문구. 본문 규칙은 7.1 의 8번과 같다
- 해결된 스레드에 답글 → 같은 트랜잭션에서 다시 열림(3.2 `writeReply`). 해결 보기가 꺼져 있어도 그 카드는 다시 열려 제자리에 남는다

### 7.3 해결·다시 열기 (개요 4.4 3번)

- 카드 머리 버튼 `해결`(열린 스레드) / `다시 열기`(해결된 스레드). 접근 `write` 일 때만. 누구나(개요 2.4)
- 해결하면: 해결 보기가 꺼져 있으면 카드가 사라지고, 편집기 장식·거터가 없어진다(F-504). 활성이던 스레드면 활성을 끈다
- 해결된 카드: 흐리게, 머리 아래 `{이메일}님이 해결함`(로컬·작성자 `id: null` 은 `해결함`)

### 7.4 삭제 (개요 4.4 4번)

- 카드 머리 `⋯`(`aria-label="댓글 메뉴"`) → `삭제`. 답글마다 `⋯`(`aria-label="답글 메뉴"`) → `삭제`. `commentAllowed(actor, 'delete', 항목)` 이 거짓이면 그 `⋯` 가 없다(메뉴 항목이 `삭제` 하나뿐이라). 메뉴 모양·키보드는 사이드바 `⋯` 메뉴(`FolderMenu.tsx`)와 같게
- D-11 확인(앱 `Dialog`): 제목 `댓글 삭제`, 본문 — 첫 댓글이고 답글 N ≥ 1 이면 `이 댓글과 답글 {N}개를 지웁니다. 되돌릴 수 없습니다.`, 그 밖 `이 댓글을 지웁니다. 되돌릴 수 없습니다.`, 버튼 `취소`(처음 포커스)·`삭제`. `삭제` → `writeDelete`. 활성 스레드를 지웠으면 활성을 끈다

### 7.5 이동·활성 (개요 4.4 5번)

| 무엇을 | 활성 | 편집기 스크롤 | 레일·판 |
| --- | --- | --- | --- |

- "앵커 밖 누르기로 끔": F-504 는 앵커 밖 클릭을 알리지 않는다(F-504 4.2). F-505 가 `view.contentDOM` 의 `pointerdown` 에서 대상의 조상에 `.cm-comment-anchor` 가 없으면 활성을 끈다. 앵커를 눌렀으면 뒤이은 `click` 에서 F-504 가 `onActivate` 를 부른다

- 비활성 카드: 첫 댓글 본문 4줄까지(넘으면 자름), 답글은 `답글 {N}개` 한 줄. 활성 카드: 전부 + 답글 입력칸. 본문은 평문이고 줄바꿈만 살린다(개요 1.2)

### 7.6 주소로 이동 (개요 4.4 6번)

- **받는 곳 둘**: 부팅 `boot()` 의 해시 처리, `handleHashChange`. 둘 다 `parsedHash.type === 'doc'` 이고 `threadId` 가 있으면 **대기 대상** `{ docId, threadId }` 을 잡는다. 주소는 지금처럼 `replaceHashUrl(docId)` 로 `#/d/{docId}` 가 된다(뒤로 가기 기록을 늘리지 않는다) — 부팅은 이미 그렇게 하고, `handleHashChange` 는 대상을 잡은 뒤 `replaceHashUrl` 을 한 번 부른다
- `handleHashChange` 의 "같은 문서면 그냥 돌아간다" 분기: `threadId` 가 있으면 돌아가기 전에 대상을 잡는다(알림을 눌렀는데 이미 그 문서를 보고 있는 경우, F-507)
- 문서를 못 찾으면(지금의 `문서를 찾을 수 없습니다.`) 대상을 버린다
- **판정 시점**: 대상 문서가 열린 편집기에 붙은 뒤 **댓글이 준비됐을 때** — 접근이 `local` 경로면 첫 `onLayout`, `realtime` 이면 첫 `onLayout` 이면서 `liveSnapshot.everSynced` 가 참(F-2041 뒤에는 재개 세션이 서버 동기화 전에 편집기를 띄우므로 `ready` 가 아니라 `everSynced` 로 본다). 그때:
  1. `threadId` 가 답글 id 면 그 부모로 바꾼다
  2. `anchored` 에 있으면: 해결된 스레드면 `해결된 댓글 보기` 를 켠다 → 보기 모드면 `편집` 으로 → 레일 열림(저장 안 함)·판 열기 → 활성 → `reveal`
  3. `orphans` 에 있으면: 레일(판)을 열고 활성, 고아 묶음을 펼쳐 그 카드로(5.4)
  4. 없으면: C9(info)
- 접근이 `none`(금고) → C9. `unavailable` → 대상을 버리고 레일(판)을 연다(C8 이 보인다). 대상 문서에서 다른 문서로 떠나면 대상을 버린다. 오프라인으로 연 재개 세션은 `everSynced` 가 될 때까지 기다린다

## 8. 키보드·접근성·IME (개요 4.9)

### 8.1 `Ctrl+Alt+M`

- App 의 창 `keydown` 처리기 하나(Ctrl+P·Ctrl+Shift+F 와 같은 자리). 편집기 키맵에 넣지 않는다 — `createEditor.ts` 를 고치지 않고, 편집기 밖 포커스(C7 알림)도 같은 자리에서 다룬다
- 조건: `(ctrlKey || metaKey) && altKey && !shiftKey` 이고 **`e.code === 'KeyM'`**. `e.key` 를 보지 않는 이유: 맥에서 Option 을 누르면 `e.key` 가 `µ` 같은 다른 글자가 된다(이 PC 에서 맥은 확인하지 않았다)
- 부팅 중·`dialog[open]` 이 있으면 무시. `e.isComposing` 이거나 주 편집기가 조합 중이면 무시(F-109 `guardComposing` 과 같게, 개요 4.4 1번)
- 포커스가 주 편집기(표 칸 하위 편집기 포함, `view.dom.contains(activeElement)`) 안이면 4장 표의 `Ctrl+Alt+M` 칸대로. 칸 안이면 `beginDraft` 가 `null` 이라 C1. 금고 문서는 포커스 위치와 무관하게 C7(info). 그 밖(편집기 밖)은 무시
- 처리했으면 `preventDefault`
- CM 기본 키맵들에 `m` 키 바인딩이 없다(`@codemirror/commands` dist 확인, 개요 c10). Windows Chrome 에서 브라우저·OS 가 먼저 먹는지, AltGr 배열에서 글자가 들어가는지는 확인하지 않았다 — H4

### 8.2 포커스·읽기 이름

- 레일 `<aside aria-label="댓글">`, 판 `role="dialog" aria-modal="false" aria-label="댓글"`, 카드 `<article tabindex="0">` 이고 머리 줄(작성자·시각)을 `aria-labelledby` 로 잇는다. 활성 카드 `aria-current="true"` 와 `data-active="true"`
- 포커스 순서: 편집기 → (Esc 다음 Tab, I3) 레일 머리 체크 → 카드들(문서 위치순, 각 카드 안 버튼·입력칸) → 고아 묶음 → 목차 버튼 → 상태바
- 카드에 포커스가 있을 때(입력칸 밖) `Esc` → 편집기로 포커스(`handle.focus()`), 활성은 그대로
- 앵커·거터 표시는 키보드 길이 없다 — 레일이 그 길이다(F-504 4.2·4.3)
- 떠 있는 버튼은 선택이 있을 때 Tab 순서에 들지 않는다(`tabindex="-1"`) — 키보드 길은 `Ctrl+Alt+M`·우클릭 메뉴 키·팔레트다

### 8.3 IME

- 입력 카드·답글 입력칸은 보통 `textarea` 라 편집기 조합과 무관하다. 조합 중 `Ctrl+Enter`·`Esc` 는 무시한다(`e.isComposing`) — 조합 확정 `Enter` 가 보내기로 오인되지 않게
- 레일이 움직여도 입력 요소를 다시 만들지 않는다 — 카드 `key` 는 스레드 id, 입력 카드 `key` 는 고정 문자열(F-504 4.4)
- 원격 댓글은 편집기 조합 중 게이트가 붙잡는다(F-500 4.2, 불변조건). F-505 가 새로 미루는 재계산은 없다 — 조합 끝 따라잡기는 F-504 가 한다

## 16. 열린 질문 / 사람 결정 필요

### Q1. 팔레트 id `comment.toggleRail` → `comment.toggle-rail` — **사람 결정 필요(승인된 개요 5.2 의 계약 id 와 다름). 기본값: `comment.toggle-rail`**

- 기존 `paletteCommands.test.ts` U3 는 모든 id 가 `/^[a-z][a-z0-9]*(\.[a-z-]+)+$/` 에 맞는지 본다 — `comment.toggleRail` 은 대문자 때문에 실패한다(r5). 이 규칙은 F-404 11장 Q3 에서 숫자를 허용하며 다듬은 것이다
- 다른 안: U3 정규식에 대문자를 허용하도록 고친다. 그러면 id 는 개요 그대로지만 영역.동작 규칙("소문자·하이픈")이 무너진다. 이 id 를 부르는 다른 코드·명세는 없다(F-507 은 `notifications.open`)

### Q2. 금고 문서의 우클릭 `댓글 달기` — **사람 결정 필요(개요 안의 두 문장이 다름). 기본값: 항목이 없다**

- 개요 4.7 은 금고 문서에서 우클릭 `댓글 달기` 가 "**없다**", 5.2 는 "댓글을 달 수 없으면 비활성(**금고면 C7 설명**)" 이다. 지금 우클릭 메뉴 항목(`MenuItemNode`)에는 설명 칸이 없다
- 기본값의 이유: 사용자 결정 8 "금고 문서는 댓글 없음" 에 더 가깝고, 설명 칸을 새로 만들지 않아도 된다. C7 은 금고 문서에서 `Ctrl+Alt+M` 을 눌렀을 때 알림으로 쓴다(8.1)
- 다른 안(비활성 + 설명): `MenuItemNode` 에 선택 `description` 을 더하고 `ContextMenu.tsx` 가 그것을 보여야 한다 — 소유 파일 하나(`ContextMenu.tsx`)가 늘고 F-170 메뉴 모양이 바뀐다

### Q3. 파일 목록이 개요와 다름 — **기본값: 1장 표대로**
