# F-2113 편집 모드 프론트매터 값 칸 편집

작성일: 2026-10-01
상태: 승인(2026-10-01) — 열린 질문 Q1·Q2 는 모두 기본값 추천이라 갈림길이 없어 "갈림길 없으면 바로 구현" 상시 지시(2026-09-21)로 승인함. 사용자 원문(2026-10-01) "yaml 프론트메터 라이브 프리뷰에서 수정 가능하게 / 단 추가나 제목이 아니라 우측 값만 수정할 수 있게 하면 될듯". **F-155 2.2(위젯 편집 불가)를 개정한다.** CM6 하위 view + IME 게이트를 건드려 작은 명세 상한(250행) 가까이 쓴다
구현 담당: `complex-implementer` (CM6 내부 + IME)

## 정해진 것 (사용자 결정, 바꾸지 않는다)

1. 값 칸을 클릭하면 그 자리에서 편집한다(F-125 방식). 키 칸은 편집 불가(지금처럼 커서 보정). 호버 힌트 `원문 모드에서 편집` 은 없앤다
2. 편집 범위: 한 줄 `키: 값` 스칼라 + 목록 항목(`키:` 아래 `  - a`)을 **항목마다 칸 하나**. 항목·키 추가·삭제·순서 변경, 키 이름 수정은 하지 않는다. 해석 불가(`parseSimpleProperties` 가 null)는 지금처럼 `<pre>` 읽기 전용
3. 편집 중 칸에는 콜론(또는 `- `) 뒤 원문 전부(따옴표·줄끝 `# 메모` 포함)를 보인다. 비편집 표시는 지금처럼 따옴표를 벗긴 값. 본문에는 바뀐 구간만 쓴다. 따옴표 재부여·이스케이프 규칙은 없다. 개행은 공백 1개로 접는다(F-125 2.2 `singleLineFilter` 와 같은 규칙)
4. 프론트매터 전용 병렬 구현 — `tableWidget.ts` 는 고치지 않는다(공용 추출 없음). IME 게이트에는 편입한다(CLAUDE.md 불변식)

## 근거 (직접 읽거나 돌린 것, HEAD `eedf1d7`)

## 2. 화면

### 2.1 표 모양
- 행은 지금처럼 키 하나에 `<tr>` 하나, `th` = 키. 보기 모드 표(F-133 3.3)와 행·키가 같다
- `td` 안에 편집 단위마다 `div.md-frontmatter-value` 를 둔다. 스칼라는 1개, 목록 키는 항목 수만큼 세로로 쌓는다(`, ` 로 잇지 않는다). rowspan 은 쓰지 않는다 — 행 수가 보기 모드와 같아야 짝수 행 규칙·F-155 A2 비교가 그대로 맞는다
- 비편집 글자 = `stripQuotes(구간 원문.trim())` (= 파서 값). 스칼라 문서의 `td` 글자는 지금과 같다
- 목록 키 행에서 키 줄 자체의 값(`a: b` 뒤에 항목이 오는 경우의 `b`)은 파서처럼 버린다 — 보이지 않고 편집 칸도 아니다
- 해석 불가 `<pre>`, 빈 프론트매터·닫는 줄 뒤 줄 없음 예외(F-155 2.1)는 그대로
- `.md-frontmatter-widget-hint` 요소·CSS 삭제. 모양(값 칸 커서·편집 중 칸 테두리·항목 사이 간격)은 사람 확인

```text
div.md-frontmatter-value[data-cell="{i}"]   i = frontmatterValueRanges 결과의 0부터 번호(문서 순서)
div.md-frontmatter-value.md-frontmatter-value-editing   편집 중(하위 view 가 이 div 안에 붙는다)
```

### 2.2 접근성 문자열
하위 view `contentDOM` 의 `aria-label`. 위젯 `aria-label="문서 속성"` 은 그대로

| 상황 | 문자열 |
| --- | --- |
| 스칼라 칸 | `{키} 값` |
| 목록 항목 칸 | `{키} 항목 {n}` (n 은 1부터) |

## 3. 순수 함수 (`src/lib/frontmatter.ts`)

### 3.1 값 위치

```ts
export type FrontmatterValueRange = { key: string; kind: 'scalar' | 'listItem'; from: number; to: number }
export function frontmatterValueRanges(text: string): FrontmatterValueRange[]
```

- `text` 는 문서 앞부분(최소 닫는 줄까지). 프론트매터가 항상 0 에서 시작하므로 `from`·`to` 는 **문서 절대 offset**
- `findFrontmatter` 가 null 이거나 `parseSimpleProperties(내용)` 가 null 이면 `[]`
- 줄 나누기·건너뛰기는 `parseSimpleProperties` 와 똑같다(`/\r\n|\r|\n/`, 빈 줄·`#` 주석 줄 건너뜀, 들여쓴 줄은 직전 키의 항목)
- 스칼라: `from` = 첫 콜론 뒤 `[ \t]*` 를 건너뛴 위치. 목록 항목: `from` = `-` 뒤 `[ \t]+` 를 건너뛴 위치
- `to` = 그 줄 내용 끝(줄 종결자 `\r\n`·`\n`·`\r` 앞). **줄끝 공백은 포함**한다(원문 전부를 보인다는 결정 3)
- 키 줄은 뒤에 항목이 하나라도 붙으면 목록 머리 — 그 줄은 칸이 아니고 항목들이 칸이다. 붙는 항목이 없으면 값이 비어 있어도(`키:`) 스칼라 칸(`from === to`)
- `key` 는 파서와 같은 `match[1].trim()`
- 결과 순서 = 문서 순서 = `data-cell` 번호

| 입력(문서) | 결과 `[key, kind, 원문 구간]` |
| --- | --- |
| `---\na: 1\n---\n본문` | `[a, scalar, "1"]` (7–8) |
| `---\nb: "x y" # 메모\n---\nx` | `[b, scalar, "\"x y\" # 메모"]` |
| `---\ntags:\n  - one\n  - 'two'\n---\nx` | `[tags, listItem, "one"]`, `[tags, listItem, "'two'"]` |
| `---\nc:\n---\nx` | `[c, scalar, ""]` (`from === to` = 줄 끝) |
| `---\nk:\t  v  \n---\nx` | `[k, scalar, "v  "]` |
| `---\nurl: http://x:1\n---\nx` | `[url, scalar, "http://x:1"]` |
| `---\na: b\n  - c\n---\nx` | `[a, listItem, "c"]` 하나 |
| `---\r\na: 1\r\ntags:\r\n  - x\r\n---\r\n본문` | `[a, scalar, "1"]` (8–9), `[tags, listItem, "x"]` (22–23) — `\r` 미포함 |
| `---\n  - x\n---\nx`, `---\nparent:\n  child: 1\n---\nx`, `---\na: \|\n  t\n---\nx`, `# 제목` | `[]` |

(offset 은 스크래치 시제품으로 확인한 값)

### 3.2 쓰기 구간

```ts
export function frontmatterValueWrite(
  current: string, from: number, next: string, charBefore: string,
): { change: { from: number; to: number; insert: string } | null; range: { from: number; to: number } }
```

- `current` 는 지금 세션 구간 원문, `charBefore` 는 `from` 바로 앞 한 글자(문서 시작이면 `''`)
- 콜론 바로 뒤 빈 값(`current === ''` 이고 `charBefore === ':'`)에 빈 문자열 아닌 값을 처음 쓸 때만 앞에 공백 1개를 붙여 넣는다 — `키:값` 은 YAML 에서 키가 아니게 되므로. 이 경우 `range.from = from + 1`. 이 밖의 공백·따옴표는 손대지 않는다(`a:b` 처럼 원래 붙어 있던 값은 그대로 둔다)
- 그 밖에는 `diffText(current, next)` 로 바뀐 구간만(표 칸 `cellWriteChange` 와 같은 원리). 같으면 `change: null`
- `range` = 쓴 뒤 세션이 들 구간 `{ from(+1), from(+1) + next.length }`

## 4. 편집 세션 (`frontmatterEdit.ts`)

규칙은 F-125 2.2·F-135 3.2~3.4·F-138 3.5·F-303 6장의 표 칸 세션 그대로이고, 아래는 다른 점과 꼭 지킬 점만 적는다.

### 4.1 외부 계약

```ts
export function isFrontmatterComposing(mainView: EditorView | null | undefined): boolean          // 활성 칸 하위 view.composing
export function isFrontmatterCompositionStarted(mainView: EditorView | null | undefined): boolean // 하위 view.compositionStarted
export function trackFrontmatterEdit(mainView: EditorView | null | undefined, tr: Transaction): void // 활성 범위·미룬 쓰기 범위를 tr 로 옮김
```

세션은 주 `EditorView` 하나당 하나(`WeakMap`). 동시에 표 칸 세션과 둘 다 열리지 않는다 — 각자의 blur 가 끝낸다.

### 4.2 시작
- 진입은 `div.md-frontmatter-value` 의 `mousedown` 하나(`preventDefault`·`stopPropagation`). 키 칸·표 여백·`<pre>` 는 지금 wrap `mousedown`(커서 보정) 그대로
- `mainView.state.readOnly` 면 시작하지 않고 키 칸과 같은 동작(리뷰 E1 선례)
- 칸 구간은 **시작 시점의 주 문서**에서 `frontmatterValueRanges` 로 다시 계산해 `data-cell` 번호로 고른다(위젯 인스턴스는 조합 중 낡을 수 있다, F-135 3.2). 번호가 범위를 벗어나면 시작하지 않는다
- 하위 view 초기 문서 = 구간 원문 그대로(따옴표·주석 포함), 커서는 클릭 지점이 아니라 **끝**. 확장: 개행 접기 필터, 아래 키 처리, `blur`·`compositionend` 핸들러, `aria-label`(2.2)
- 이미 같은 칸이 활성이면 포커스만

### 4.3 쓰기
- 하위 view `docChanged` 마다 `frontmatterValueWrite(구간 원문, from, 새 값, 앞 글자)` → `change` 가 있으면 주 view 에 `{ changes, userEvent: 'input.frontmatter' }` 로 dispatch, 세션 범위 = 결과 `range`
- `input.frontmatter` 는 `JOINABLE_USER_EVENT` 밖이라 표 칸처럼 변경마다 되돌리기 한 단계다(열린 질문 Q1)
- 조합 중 쓴 적이 있으면 `pendingRecalc` 표시(F-135 3.4)

### 4.4 범위 추적과 원격
- `trackFrontmatterEdit` 는 `frontmatter.ts` StateField `update` 가 `docChanged` 마다 **조합 보류 여부와 무관하게** 부른다(`blocks.ts` 의 `trackActiveEditRange` 호출과 같은 자리 규칙)
- 범위 옮기기는 `mapCellRange` 규칙(from 은 왼쪽, to 는 오른쪽으로 붙음)
- `ySyncAnnotation` 트랜잭션이 옮기기 **전** 구간을 건드리면(`touchesRange` 가 false 아님, 양 끝 포함) 마이크로태스크로 세션을 끝낸다(F-303 6.2). 원격 글자와 내 글자가 모두 남는다
- 트랜잭션 전후 `state.readOnly` 가 false → true 로 바뀌면 같은 방식으로 세션을 끝낸다(편집 잠금 상실 등 — `readOnlyChangeGuard` 가 이후 쓰기를 버려 칸과 원문이 어긋나므로)

### 4.5 끝내기
- `endEdit({ deferDispatch })` 는 F-138 3.5 그대로: 조합 중이면 마지막 값을 먼저 쓰고(갱신 도중이면 범위를 들고 마이크로태스크로 미룸, 미룬 범위도 `trackFrontmatterEdit` 가 옮기고 무너졌으면 안 씀), `pendingRecalc` 면 `forceRecalc` 를 반드시 보낸다. 하위 view `destroy`, 칸 글자를 위젯 표시 값으로 되돌리고 `md-frontmatter-value-editing` 제거
- 갱신 도중 경로(`updateDOM`·`destroy`)는 `deferDispatch: true`

### 4.6 키 (하위 view `keydown`)
조합 중(`event.isComposing`·`keyCode 229`·`isComposing(하위 view)`)에는 아무것도 가로채지 않는다(F-161 3.2).

| 키 | 동작 |
| --- | --- |
| Enter | 끝내기 → 주 커서를 닫는 줄 다음 줄 시작(`frontmatterWidgetInfo().correctedPos`) → 주 view 포커스 |
| Esc | Enter 와 같다. 이미 쓴 내용은 남는다(표 칸 Esc 와 같음, 되돌리려면 Ctrl+Z) |
| Tab / Shift+Tab | 다음·이전 칸(`data-cell` ±1). 끝·처음이면 아무것도 안 함(키는 삼킴) |
| ↓ / ↑ | 다음·이전 칸. 마지막 칸 ↓ 는 Enter 와 같다. 첫 칸 ↑ 는 아무것도 안 함(위젯 위에 줄이 없다) |
| ←/→, Home/End 등 | 칸 안 이동(가로채지 않음) |
| Mod+Z / Mod+Y / Mod+Shift+Z | 끝내기 → 주 view `undoLocal`/`redoLocal`(조합 가드) → 주 view 포커스 |
| Mod+B/I/K, Alt+Enter | 가로채지 않음(값은 마크다운이 아니다. `<br>` 삽입 없음) |

- 우클릭은 브라우저 기본 메뉴(F-170 칸 메뉴 연결 안 함)

## 5. 위젯·StateField·IME

### 5.1 위젯 (`FrontmatterWidget`)
- `eq` 는 지금 그대로(props JSON). 값 글자가 바뀌면 `updateDOM` 이 불린다
- `updateDOM`: "모양"(raw/표 여부 + 키 순서 + 키마다 칸 수)이 같으면 활성 칸만 빼고 나머지 칸 글자만 갈아 끼우고 true. 다르면 활성 세션이 이 DOM 이면 `endEdit({ deferDispatch: true })` 후 통째로 다시 그리고 true(`TableWidget.updateDOM` 과 같은 구조)
- `destroy(dom)`: 활성 세션이 이 DOM 이면 `endEdit({ deferDispatch: true })`. dom → 주 view 는 `WeakMap` 으로 찾는다(`TableWidget` 의 `wrapView` 와 같은 이유). 편집 모드 → 원문 모드 전환(`previewCompartment` 재구성)도 이 경로로 세션이 끝난다
- 정상 값 입력으로 해석 실패(`<pre>` 폴백)나 칸 구조 변화는 일어나지 않는다(근거의 16,000회 측정). 일어나는 것은 원격·되돌리기 등 다른 변경 때뿐이며, 그때는 위 "모양이 다르면" 경로로 세션이 끝나고 이미 쓴 내용은 남는다. 그래서 따옴표 재부여 같은 보호 규칙은 두지 않는다(결정 3과 모순 없음). 남는 최소 규칙은 3.2 의 콜론 뒤 공백 1개와 개행 접기 둘뿐

### 5.2 StateField (`frontmatter.ts`)
- `update` 첫머리에서 `docChanged` 면 `trackFrontmatterEdit(viewRef.current, tr)`
- `isFrontmatterComposing(viewRef.current)` 이고 `forceRecalc` 가 아니면: `docChanged` 면 deco 를 `map(tr.changes)` 만, 아니면 그대로(같은 위젯 인스턴스가 유지돼 하위 view DOM 이 살아남는다)
- `isForced(tr)` 면 다시 만든다(지금은 무시한다 — 조합 중 보류를 따라잡으려면 필요). 그 밖의 재계산 조건은 지금 그대로
- 주 view 자체의 조합(`isComposing`) 가드는 넣지 않는다 — 주 커서는 위젯 범위에 들어올 수 없어(F-155 2.2) 지금 동작을 바꿀 이유가 없다
- `atomicRanges`·커서 보정 `transactionFilter`·처음 열기 보정·거터 규칙은 그대로

### 5.3 조합 훅 편입
- 하위 view `compositionend` → 다음 틱에 여전히 같은 세션이면 `pendingRecalc = false`, 주 view 에 `forceRecalc`. 이것이 5.2 보류·`blocks.ts` 보류·`remoteGate` 큐의 따라잡기 지점이다(불변식 "조합 종료 시 따라잡기")
- `remoteGate.ts`·`remoteCursors.ts`·`commentMarks.ts` 의 조합 판정: `view.compositionStarted || isCellCompositionStarted(view) || isFrontmatterCompositionStarted(view)`. 셋 다 이 한 항 추가뿐 — 조합 중 원격 업데이트 큐잉·`afterFlush` 의 `forceRecalc` 는 기존 경로를 그대로 탄다(불변식 "조합 중 원격 업데이트 금지", table-cell sub-editor 와 같은 취급)
- `blocks.ts` `blockPreview` 보류 조건: `isComposing || isCellComposing || isFrontmatterComposing`. 위젯이 다른 확장에 있어 엄밀히 필수는 아니지만, 하위 view 조합 중 주 view 의 블록 위젯 재구성(높이 변화로 칸이 밀림)을 표 칸 조합 때와 같게 막는다. 따라잡기는 위 `forceRecalc`
- `lines.ts` 는 표 칸 조합 때도 보류하지 않으므로 고치지 않는다
- `compositionAlive`(`remoteGate.ts`)는 `view.dom.contains(activeElement)` 라 하위 view 포커스도 살아 있음으로 본다 — 변경 없음
