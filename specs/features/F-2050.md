## 2. 범위

### 한다
- 서버 `/v1` 라우트 넷: `DELETE /v1/docs/:id`, `PUT /v1/docs/:id/folder`, `DELETE /v1/folders/:id`, `GET /v1/shared`

## 3. 서버

### 3.1 라우트 (`worker/index.ts` `routes` 에 더하는 줄 — 계약)

| 메서드·경로 | 핸들러 | 성공 응답 |
| --- | --- | --- |
| `DELETE /v1/docs/:id` | `handleDeleteDocV1` | 200 `V1DeletedDoc` |
| `PUT /v1/docs/:id/folder` | `handleMoveDocFolderV1` | 200 `V1DocSummary` |
| `DELETE /v1/folders/:id` | `handleDeleteFolderV1` | 200 `V1DeletedFolder` |
| `GET /v1/shared` | `handleListSharedV1` | 200 `V1SharedDoc[]` |

- **`GET /v1/shared` 로 따로 둔다**(`GET /v1/docs?shared=1` 이 아니다). 이유: ① `/api/shared` 와 같은 모양이라 웹과 짝이 맞는다 ② `GET /v1/docs` 의 응답 모양·계약 테스트(F-2021 U15)를 그대로 둔다 — 쿼리에 따라 원소 모양이 달라지는 라우트를 만들지 않는다 ③ `matchPath` 는 쿼리를 보지 않아 쿼리 분기는 핸들러 안 `if` 가 되고, 모르는 쿼리 값의 처리까지 정해야 한다
- 경로 충돌 없음(`matchPath` 는 세그먼트 수와 글자로 가른다): `/v1/shared` 2개 vs `/v1/docs/:id` 3개, `/v1/docs/:id/folder` 는 `/v1/docs/:id/link` 와 넷째 글자가 다르다. `DELETE /v1/docs/:id` 는 같은 경로의 `GET`·`PUT` 과 메서드로 갈린다 — 지금은 이 조합이 405 이고, 이 명세 뒤 200 이다
- **`DELETE` 가 204 가 아니라 200 + 몸통인 이유**: `rm` 이 지운 문서 제목을, `rmdir` 이 옮기거나 지운 수를 사람에게 알려 준다(5.2). 몸통이 없으면 CLI 가 미리 `GET` 을 한 번 더 해야 하고, 그 사이 값이 달라질 수 있다
- `mv` 가 `V1Doc` 이 아니라 `V1DocSummary`(원문 없음)인 이유: 옮기기 결과에 1MB 까지 가는 원문을 실을 까닭이 없다. `/api` 본체는 `rowToDoc`(원문 포함)을 돌려주므로 `/v1` 쪽에서 `content` 를 뺀다
- 인증·CORS·`OPTIONS` 405 는 기존 `/v1` 과 같다(F-223 2.1). `/v1/` 은 Bearer 만 본다(`worker/auth.ts` `getUser`)

### 3.2 판정 순서 — `DELETE /v1/docs/:id` (계약)

1. `getDocAccess` 가 `null` → **404** `not_found` (없는 문서, 권한이 전혀 없는 남의 문서, **남의 금고 문서** — `resolveDocAccess` 가 금고 비소유자를 `null` 로 본다, F-401 X1)
2. 행이 금고(`e2ee_key` 가 문자열) → **403** `{ error: 'e2ee_doc' }` — 결정 4. `handleGetDocV1`·`handleUpdateDocV1` 과 같은 자리(404 바로 뒤)
3. `role !== 'owner'` → **403** `forbidden` (편집·보기 초대자, F-212 2.2)
4. 지우기 — `/api` `handleDeleteDoc` 과 **같은 문장 한 벌**(사용량 줄 `deleteDocUsageStatement`, `share_link_docs`, `docs`, 댓글 문장) + `notifyPurge`. 편집 잠금·접속자를 보지 않는다(결정 5)
5. 200 `{ id, title }` — `title` 은 1번에서 읽은 행의 값

- 1~3 은 D1 쓰기가 없다. 막힌 계정(403 `account_blocked`)·한도(429)는 핸들러 앞 쓰기 관문이 먼저 거른다(3.6)
- 2번이 3번보다 앞인 이유: 금고 문서에 닿는 비소유자는 1번에서 이미 404 라, 2번에 오는 것은 늘 소유자다. 순서를 바꿔도 결과가 같지만 기존 `/v1` 두 핸들러와 자리를 맞춘다

### 3.3 판정 순서 — `PUT /v1/docs/:id/folder` (계약)

몸통은 `/api` 와 같다: `{ folderId: string | null }`. `null` 이면 맨 위(폴더 없음)

1. 몸통 읽기 실패 → 413 `too_large` / 400 `invalid`. `folderId` 가 `null` 도 UUID 도 아니면 400 `{ error: 'invalid', field: 'folderId' }` — `/api` 와 같은 자리·같은 값
2. `getDocAccess` 가 `null` → **404**
3. 행이 금고 → **403** `{ error: 'e2ee_doc' }` — 결정 9(대상이 금고 문서)
4. `role !== 'owner'` → **403** `forbidden`
5. `folderId` 가 문자열이면 `getOwnedFolder`: 없거나 남의 폴더 → **400** `{ error: 'invalid', field: 'folderId' }`(`/api` 와 같다), 금고 폴더 → **403** `{ error: 'e2ee_folder' }` — 결정 9(목적지가 금고)
6. 쓰기 — `/api` `handleMoveDocFolder` 와 같은 문장 한 벌(`UPDATE docs SET folder_id …` + `dayUsageStatement`)
7. 200 — `rowToDoc` 결과에서 `content` 를 뺀 것(`V1DocSummary` 키 집합)

- **지금 서버가 금고 문서를 금고 밖으로 옮기는 것을 막는가 — 막지 않는다.** `handleMoveDocFolder` 의 폴더 검사는 "목적지가 금고 폴더인데 문서가 일반" 일 때만 409 `e2ee_folder` 다. 금고 문서 → 일반 폴더·맨 위는 200 이고, F-401 3.4 표("금고 문서를 일반 폴더로 옮기는 것은 된다")·D11 이 그렇게 정했다. 웹은 이것을 계속 한다. `/v1` 만 3번에서 막는다
- 일반 문서 → 금고 폴더는 `/api` 에서 409 `e2ee_folder` 지만 `/v1` 은 5번에서 **403** 으로 먼저 끝낸다(결정 9 "전부 403"). 그래서 `/v1` 에서는 이 409 가 나오지 않는다
- "지금 폴더가 금고인 일반 문서" 는 검사하지 않는다 — 금고 폴더 안에는 일반 문서가 없다(F-401 5.2: 만들기 409, 켜기는 일반 자식이 있으면 409, `move-up` 은 금고 부모 아래로 평문을 올리지 않는다). 그런 행이 생긴다면 그것은 F-401 의 버그다
- 같은 폴더로 옮기기(바뀌는 것 없음)도 200 이고 하루 쓰기 1 을 센다 — `/api` 와 같다
- 3.2 와 같은 이유로 쓰기 문장은 복사하지 않는다. 뽑는 함수 이름·모양은 구현 재량이다. `/v1` 핸들러가 `getDocAccess`·`getOwnedFolder` 를 먼저 읽고 본체를 다시 부르는 방식(읽기가 한 번 더 난다)도 된다 — 단, 본체가 다시 판정해도 결과가 달라지지 않아야 한다

### 3.4 판정 순서 — `DELETE /v1/folders/:id` (계약)

질의 `contents` 는 `/api` 와 같다: 없으면 `move-up`, `move-up`·`delete-all` 밖의 값은 400

1. `getOwnedFolder` 가 `null` → **404** (없는 폴더, 남의 폴더 — 초대받은 폴더도. `/api` 와 같다)
2. `contents` 값이 틀림 → **400** `{ error: 'invalid', field: 'contents' }`
3. **금고가 끼면** → **403** `{ error: 'e2ee_folder' }`. "낀다" = 대상 폴더와 그 아래 모든 폴더(`descendantFolderIds`, 대상 포함) 가운데 금고 폴더(`e2ee = 1`)가 하나라도 있거나, 그 폴더들 안에 금고 문서(`e2ee_key IS NOT NULL`)가 하나라도 있으면. `contents` 와 상관없이 같은 규칙(13장 Q1)
4. 지우기 — `/api` 와 같은 코드(3.5)
5. 200 `V1DeletedFolder`

- 3번이 하위 전체를 보는 이유: 일반 폴더 아래 금고 폴더를 만들 수 있고(F-401 5.2 "금고 폴더 아래는 늘 금고" 는 반대 방향만), 금고 문서 하나만 일반 폴더로 옮길 수도 있다(3.3). `delete-all` 이면 그 금고 문서들이 CLI 로 지워지고(결정 4 위반), `move-up` 이면 바로 아래 금고 문서·폴더가 CLI 로 옮겨진다(결정 9 위반). 더 깊은 금고 항목은 `move-up` 에서 움직이지 않지만, 규칙을 하나로 두어 "금고가 든 폴더는 CLI 로 지우지 않는다" 로 읽히게 한다
- 폴더 id 는 100개씩 나눠 묻는다 — `handleDeleteFolder` 의 `BATCH_ID_LIMIT` 과 같은 이유(D1 바인딩 한도)
- `/api` 의 "금고 부모 아래 `move-up` 409 `e2ee_folder`" 분기는 `/v1` 에서 닿지 않는다 — 부모가 금고면 대상도 금고라(F-401 5.2) 3번에서 끝난다

### 3.5 `rmdir` 이 돌려주는 수 — 계산 규칙

`handleDeleteFolder` 의 삭제 부분을 `/api`·`/v1` 이 같이 쓰는 함수로 뽑고, 그 함수가 `{ docs, folders }` 를 돌려준다. `/api` 는 이 값을 버리고 지금처럼 **204** 다(`src/storage/docsApi.ts` `removeFolder` 가 204 를 기대한다 — 모양을 바꾸지 않는다)

| `contents` | `docs` | `folders` |
| --- | --- | --- |
| `move-up` | 대상 폴더 **바로 안**에 있다가 부모로 올라간 문서 수 | 부모로 올라간 **바로 아래** 폴더 수. 지운 대상 폴더는 세지 않는다 |
| `delete-all` | 영구 삭제한 문서 수(하위 전체) | 영구 삭제한 폴더 수 — **대상 폴더 포함** |

- `move-up` 의 두 수는 같은 `batch` 의 `UPDATE docs SET folder_id …`·`UPDATE folders SET parent_id …` 결과 `meta.changes` 다. 미리 `COUNT` 하지 않는다 — 같은 batch 라 셈과 실제 옮김이 어긋나지 않는다. 실제 D1·`worker/testD1.ts` 둘 다 `meta.changes` 를 준다(`testD1.ts` `run()` 이 `result.changes` 를 싣는다)
- `delete-all` 의 두 수는 지금 코드가 이미 모으는 문서 id 목록·폴더 id 목록의 길이다
- 이 수로 CLI 가 `문서 3개는 위 폴더로 옮겼습니다` 를 낼 수 있다(5.2)

### 3.6 쓰기 관문(F-2026)과 하루 쓰기 수 — 확인한 결과

- **관문에 든다.** `worker/writeGate.ts` `isWriteRoute` 는 `GET` 이 아니고 `/v1/` 로 시작하는 라우트 패턴이면 참이다. 새 `DELETE`·`PUT` 셋은 코드 변경 없이 관문을 지난다: 401 → 403 `account_blocked` → 429 `day` → 429 `minute`(바인딩 `WRITE_LIMITER`). `GET /v1/shared` 는 관문 밖이다
- **하루 쓰기 수(`write_count`)는 성공할 때 1 씩 는다** — `/api` 와 같은 문장을 쓰므로: 문서 삭제는 `DELETE_DOC_SQL`, 옮기기와 `move-up` 은 `DAY_ONLY_SQL`(`dayUsageStatement`), `delete-all` 은 `DELETE_FOLDERS_SQL`(대상 폴더가 늘 들어 있어 늘 돈다). 문서 수·바이트 누계도 `/api` 처럼 준다
- 3.2~3.4 의 404·400·403 은 D1 쓰기가 없어 하루 수를 올리지 않는다. 다만 **분당 바인딩은 관문에서 이미 한 번 셌다**(핸들러 앞) — 기존 `/v1` 쓰기와 같다
- 그래서 **종료 코드 8 경로가 새 명령에도 그대로 붙는다.** CLI `client.ts` `handleResponse` 는 경로·메서드를 가리지 않고 429 를 `rate_limited` 로 분류한다(F-2031 7장). 새로 할 일 없음 — 10.2 C6 이 확인한다

### 3.7 공유받은 문서 — 출처와 집합

- **출처는 `worker/grants.ts` `handleGetShared` 하나다.** `handleListSharedV1` 은 그것을 불러 결과를 정렬만 한다(아래). 웹 사이드바의 공유받은 문서도 같은 `GET /api/shared` 에서 온다(`src/storage/docsApi.ts` `getShared` → `serverStore.ts` `fetchShared`). 그래서 **웹 사이드바와 같은 집합**이다
- 드는 것: 문서 단위 초대(`grants` `target_type = 'doc'`) + 폴더 초대(`target_type = 'folder'`)가 걸린 폴더와 그 아래 모든 폴더의 문서(저장된 조상 사슬, F-2017 4.4). 둘 다 있으면 높은 역할. 내 소유 문서는 빠진다
- 들지 않는 것: **공유 링크**(`share_links`, `#/p/…`) — 로그인 없이 누구나 보는 공개 주소이고 계정에 묶이지 않는다. 웹 사이드바에도 나오지 않는다
- **금고 문서는 섞이지 않는다.** `handleGetShared` 의 두 `SELECT` 모두 `AND e2ee_key IS NULL` 이고, 금고 문서·폴더에는 초대 행이 생기지 않는다(F-401 X4, `handlePutGrant` 409). 그래서 X18 식의 "제목 비우고 표지" 처리가 필요 없다. 금고 문서가 생기는 순간 목록에서 빠질 뿐이다
- 원소 모양은 `handleGetShared` 의 `SharedItem` 그대로(4장 `V1SharedDoc`). `role` 은 초대 역할(`edit`·`view`)이고, 소유자가 막혀 쓰기가 막힌 경우(F-2028 4.2)에도 초대 역할 그대로 나온다 — 웹과 같다. 실제로 쓰면 `put` 이 403 `account_blocked` 를 받는다
- **정렬**: `handleGetShared` 는 소유자별로 묶어 돌려준다(전체 `updatedAt` 순이 아니다). `handleListSharedV1` 이 `updatedAt` 내림차순, 같으면 `id` 오름차순으로 다시 늘어놓는다 — `GET /v1/docs` 와 같은 순서라 `ls`·`ls --shared` 가 같게 읽힌다. `/api/shared` 순서는 바꾸지 않는다
- `folderId`·`viaFolder` 는 **소유자 쪽** 폴더다. 받은 사람의 `folders` 목록에 없는 id 라 `ls --shared --folder` 는 뜻이 없다 — 사용법 오류로 막는다(5.1)

### 3.8 소유자 이메일 노출과 개인정보 처리방침 — 확인한 결과

- **맞는다. 갱신할 필요 없다.** `ls --shared` 가 보여 주는 소유자 이메일은 웹이 이미 같은 사람(초대받은 사람)에게 `GET /api/shared` `ownerEmail` 로 보여 주는 값이다. 새로 모으는 정보도, 새 수신자도 없다 — 초대받은 본인이 자기 토큰으로 자기 터미널에 받는다
- `content/legal/privacy.md` 4절 "이메일 주소: … 공유와 초대에서 누가 누구에게 권한을 주었는지 가리기 위해" 가 이 쓰임을 덮는다. 3절 표의 "초대한 사람의 이메일 주소와 권한" 도 그대로다
- 관찰(이 명세 범위 밖): 처리방침에 "초대받은 사람에게 초대한 사람(문서 소유자)의 이메일이 보인다" 가 **명시돼 있지는 않다.** 웹이 2026-09 초부터 이미 그렇게 하므로 이 명세가 만든 차이가 아니다 — 12장에 선택 항목으로만 적는다

## 4. 계약 — `worker/v1Contract.ts` 에 더하는 것

```ts
export type V1SharedDoc = V1DocSummary & {
  role: 'edit' | 'view'
  ownerEmail: string
  viaFolder?: { id: string; name: string } // 폴더 초대로 받았을 때만 — 가장 가까운 초대 폴더
}
export type V1DeletedDoc = { id: string; title: string }
export type V1DeletedFolder = {
  id: string
  contents: 'move-up' | 'delete-all'
  parentId: string | null // 지운 폴더의 부모. move-up 이면 안의 것이 여기로 갔다
  docs: number            // 3.5 표
  folders: number         // 3.5 표
}
```

- `V1SharedDoc` 은 `V1DocSummary` 의 `e2ee?` 를 물려받지만 실제로는 늘 없다(3.7)
- `V1_EXAMPLES` 에 `sharedDoc`·`deletedDoc`·`deletedFolder` 세 값을 더한다. `sharedDoc` 은 `viaFolder` **없는** 모양(키 집합 비교의 기준 — 선택 필드는 10.1 V9 가 따로 본다)
- `PUT /v1/docs/:id/folder` 응답은 기존 `V1DocSummary`(`V1_EXAMPLES.docSummary`)
- `V1Error` 는 고치지 않는다 — `error: string` 이 `e2ee_doc`·`e2ee_folder` 를 이미 담는다
- 서버 핸들러는 이 파일을 import 하지 않는다(F-2021 7.2 규칙 그대로). 양쪽 테스트가 여기에 댄다

## 5. CLI

### 5.1 명령 표 (F-2021 4.2 에 더하고 바꾸는 줄 — 계약)

| 명령 | 인자·옵션 | 부르는 것 | 표준 출력(사람용) |
| --- | --- | --- | --- |
| `ls` | `[--folder <폴더id>]` **또는** `--shared` | `GET /v1/docs` / `GET /v1/shared` | 기존 3열 / `--shared` 면 문서마다 `{id}\t{updatedAt}\t{역할}\t{ownerEmail}\t{title}` |
| `mv <문서id>` | `--folder <폴더id>` 또는 `--root` (정확히 하나) | `PUT /v1/docs/:id/folder` | `{id}` |
| `rm <문서id>` | `--yes` (필수) | `DELETE /v1/docs/:id` | `{id}` |
| `rmdir <폴더id>` | `--yes` (필수) `[--all]` | `DELETE /v1/folders/:id?contents=move-up\|delete-all` | `{id}` |

도움말 순서(`COMMAND_NAMES`): `login`·`logout`·`whoami`·`ls`·`get`·`new`·`put`·`mv`·`rm`·`folders`·`mkdir`·`rmdir`·`upload`·`link`

한 줄 설명(`COMMAND_DESCRIPTIONS`) — 바뀌거나 새로 드는 줄:

| 명령 | 한 줄 설명 |
| --- | --- |
| `ls` | `내 문서 목록 (--shared: 공유받은 문서)` |
| `mv` | `문서를 다른 폴더로 옮깁니다` |
| `rm` | `문서를 영구 삭제합니다 (--yes 필요)` |
| `rmdir` | `폴더를 지웁니다. 안의 것은 위 폴더로 (--all: 모두 영구 삭제, --yes 필요)` |

사용법 오류(종료 2, 요청을 보내지 않는다) — 문구 다음 줄에 기존처럼 `{cli} {명령} --help 를 보세요.`

| 명령 | 조건 | 문구 |
| --- | --- | --- |
| `rm` | 위치 인자가 정확히 1개가 아님 | `문서 id 가 필요합니다.` |
| `rm` | `--yes` 없음 | `문서를 영구 삭제하려면 --yes 를 붙이세요. 되돌릴 수 없습니다.` |
| `mv` | 위치 인자가 정확히 1개가 아님 | `문서 id 가 필요합니다.` |
| `mv` | `--folder`·`--root` 둘 다 없음 또는 둘 다 있음 | `--folder <폴더id> 또는 --root 중 하나가 필요합니다.` |
| `rmdir` | 위치 인자가 정확히 1개가 아님 | `폴더 id 가 필요합니다.` |
| `rmdir` | `--yes` 없음, `--all` 없음 | `폴더를 지우려면 --yes 를 붙이세요. 안의 문서와 폴더는 위 폴더로 옮겨집니다.` |
| `rmdir` | `--yes` 없음, `--all` 있음 | `폴더와 안의 문서·폴더를 모두 영구 삭제하려면 --yes 를 붙이세요. 되돌릴 수 없습니다.` |
| `ls` | `--shared` 와 `--folder` 를 같이 | `--shared 와 --folder 는 함께 쓸 수 없습니다.` |

- 인자 순서 판정은 기존 명령과 같다(`node:util` `parseArgs`, `strict: true`). 모르는 옵션은 기존 문구 `알 수 없는 옵션입니다.`
- 인자 개수 검사가 `--yes` 검사보다 먼저다
- `--yes` 에 짧은 이름(`-y`)을 두지 않는다 — `npx -y` 의 `-y` 와 헷갈려, `npx -y rawdoc rm x` 가 삭제를 승인한 것으로 읽히는 일을 막는다
- `rm`·`rmdir` 은 여러 id 를 받지 않는다(한 번에 하나)

### 5.2 출력 (계약)

**표준 출력**: 표 5.1 의 마지막 열. `--json` 이면 JSON 값 하나를 한 줄로(F-2021 4.4 규칙 그대로):

| 명령 | `--json` 표준 출력 |
| --- | --- |
| `ls --shared` | `V1SharedDoc[]` (서버 응답 그대로) |
| `mv` | `V1DocSummary` |
| `rm` | `V1DeletedDoc` |
| `rmdir` | `V1DeletedFolder` |

**`ls --shared` 사람용 열**
- `{updatedAt}` 은 기존 `isoUtcSeconds`
- `{역할}` 은 `edit` → `편집`, `view` → `보기` (웹 초대 대화상자·공유 관리 화면과 같은 낱말 — `src/app/InviteDialog.tsx`·`SharesPage.tsx` `ROLE_LABEL`)
- `{ownerEmail}`·`{title}` 의 제어 문자는 공백 하나로(`stripControlChars`). `--json` 은 바꾸지 않는다
- 목록이 비면 표준 출력은 비우고 표준 오류 `공유받은 문서가 없습니다.`

**표준 오류 안내** (`--json` 이어도 쓴다 — 기존 `new`·`put` 의 해독 안내와 같다)

| 명령 | 조건 | 문구 |
| --- | --- | --- |
| `rm` | 성공 | `문서를 지웠습니다: {title}` |
| `mv` | 성공 | 없음 |
| `rmdir` | `move-up`, `docs` 와 `folders` 가 둘 다 0 | `폴더를 지웠습니다.` |
| `rmdir` | `move-up`, 하나라도 0 보다 큼 | `폴더를 지웠습니다. {항목}는 {곳}로 옮겼습니다.` |
| `rmdir` | `delete-all` | `폴더 {folders}개와 문서 {docs}개를 영구 삭제했습니다.` |

- `{항목}`: `docs > 0` 이고 `folders > 0` 이면 `문서 {docs}개와 폴더 {folders}개`, 문서만이면 `문서 {docs}개`, 폴더만이면 `폴더 {folders}개`
- `{곳}`: `parentId` 가 `null` 이면 `맨 위`, 아니면 `위 폴더`
  - 예: `폴더를 지웠습니다. 문서 3개는 위 폴더로 옮겼습니다.` / `폴더를 지웠습니다. 문서 2개와 폴더 1개는 맨 위로 옮겼습니다.`
- `{title}` 은 제어 문자를 공백으로. 제목이 빈 문자열이면 `문서를 지웠습니다: ` 뒤가 빈 채로 둔다(금고 문서는 여기까지 오지 않는다)
- 숫자는 천 단위 구분 없이(기존 문구와 같다)
- `delete-all` 의 `{folders}` 는 대상 폴더를 포함한 수라 늘 1 이상이다

### 5.3 `client.ts` 함수 (계약 — 이름과 모양)

| 함수 | 메서드·경로 | 몸통 | 404 일 때 `notFoundId` |
| --- | --- | --- | --- |
| `apiListShared(cfg)` | `GET /v1/shared` | 없음 | — |
| `apiMoveDoc(cfg, id, folderId: string \| null)` | `PUT /v1/docs/{id}/folder` | `{ folderId }` (`--root` 면 `null` 을 **명시**) | 문서 id |
| `apiDeleteDoc(cfg, id)` | `DELETE /v1/docs/{id}` | 없음 | 문서 id |
| `apiDeleteFolder(cfg, id, contents)` | `DELETE /v1/folders/{id}?contents={contents}` | 없음 | 폴더 id |

- id 는 기존처럼 `encodeURIComponent`. `contents` 는 늘 명시한다(`move-up` 도) — 서버 기본값에 기대지 않아 요청만 보고 뜻을 안다
- 다시 시도하지 않는다. 요청 수는 명령마다 1회

### 5.4 `commands.ts` 함수

- 입력은 이미 해석된 값이다(F-2021 4.7): `lsShared(cfg)`, `moveDoc(cfg, { id, folderId: string | null })`, `removeDoc(cfg, id)`, `removeFolder(cfg, { id, all: boolean })`. `--yes` 는 명령 함수까지 오지 않는다 — `args.ts` 가 이미 걸렀다. 나중에 `rawdoc mcp` 가 이 함수를 감쌀 때 확인 절차는 MCP 쪽이 정한다
- 결과는 서버 값 그대로 돌려준다. 안내 문구(5.2)는 `main.ts` 가 결과 값으로 만든다
- 기존 `ls` 함수·출력은 바꾸지 않는다(결정 6)

## 6. 오류와 종료 코드

### 6.1 새 코드 둘 (F-2021 4.5 에 더하는 행 — 계약)

| 종료 | `error` | 언제 | 표준 오류 문구 |
| --- | --- | --- | --- |
| 4 | `e2ee_doc` | 403 또는 409, 몸통 `error: 'e2ee_doc'` | `금고 문서는 명령줄 도구로 다룰 수 없습니다. 웹에서 하세요.` |
| 4 | `e2ee_folder` | 403 또는 409, 몸통 `error: 'e2ee_folder'` | `금고 폴더나 금고 문서가 걸려 있어 명령줄 도구로는 할 수 없습니다. 웹에서 하세요.` |

- 코드 이름은 서버 `error` 문자열과 같다(F-2031 3.4 의 관례)
- **종료 코드는 새로 만들지 않는다 — 4 에 넣는다.** 4 의 뜻("권한 없음·찾을 수 없음·계정 쓰기 막힘")과 같은 부류 — 다시 해도 안 되고 사람이 웹에서 해야 한다. 새 번호를 만들면 기존 스크립트의 "4 = 권한 문제" 분기가 이 경우를 놓친다
- `--json` 오류 줄은 `{ error, status, message }` 뿐이다(새 필드 없음)
- `client.ts` 분류 순서: 403 은 `account_blocked` → `e2ee_doc` → `e2ee_folder` → 그 밖 `forbidden`. 409 는 `e2ee_doc`·`e2ee_folder` 를 먼저 보고, 그 밖은 지금처럼 `conflict`. 나머지 상태는 바꾸지 않는다

### 6.2 새 명령에서 나올 수 있는 결과 (확인용 — 판정 근거는 3장)

| 서버 | `rm` | `mv` | `rmdir` | `ls --shared` | CLI `error` | 종료 |
| --- | --- | --- | --- | --- | --- | --- |
| 200 | 지움 | 옮김 | 지움 | 목록 | — | 0 |
| 400 `invalid` `field: 'folderId'` | — | 폴더 id 가 UUID 가 아님·없는 폴더·남의 폴더 | — | — | `invalid` | 2 |
| 400 `invalid` `field: 'contents'` | — | — | CLI 는 늘 올바른 값을 보내므로 나오지 않음 | — | `invalid` | 2 |
| 401 | 토큰 틀림 | 같음 | 같음 | 같음 | `unauthenticated` | 3 |
| 403 `forbidden` | 초대받은 문서(소유자 아님) | 같음 | — | — | `forbidden` | 4 |
| 403 `account_blocked` | 막힌 계정(관문) | 같음 | 같음 | — | `account_blocked` | 4 |
| 403 `e2ee_doc` | 금고 문서 | 금고 문서 | — | — | `e2ee_doc` | 4 |
| 403 `e2ee_folder` | — | 목적지가 금고 폴더 | 금고가 낌(3.4 3번) | — | `e2ee_folder` | 4 |
| 404 | 없음·권한 없음·남의 금고 | 같음 | 없음·남의 폴더 | — | `not_found` | 4 |
| 429 | 한도(관문) | 같음 | 같음 | (GET 이라 서버 규칙상 없음) | `rate_limited` | 8 |
| 5xx | — | — | — | — | `server_error` | 1 |

- **순환 오류는 없다** — 문서만 옮기므로 폴더 사슬이 바뀌지 않는다(폴더 옮기기는 결정 1 로 뺐다)
- 409 는 새 라우트 넷에서 나오지 않는다(3.3 둘째 점, 3.4 끝)
- `mv` 에서 없는 폴더가 404 가 아니라 400(종료 2)인 이유: `/api` 가 400 `field: 'folderId'` 이고, 이 명세는 본체 판정을 바꾸지 않는다. 문구 `서버가 요청을 거절했습니다: folderId 값이 올바르지 않습니다.` 가 무엇이 틀렸는지는 말해 준다(13장 Q3)
- `forbidden` 문구 `이 문서를 고칠 권한이 없습니다.` 는 `rm`·`mv` 에도 그대로 쓴다(문구 계약, F-2021 4.5)

### 6.3 기존 명령에서 달라지는 것 (0.2.0 → 0.3.0)

6.1 의 분류는 경로를 가리지 않으므로 기존 명령의 금고 응답도 새 코드로 간다. 전부 **잘못 읽히던 응답을 바로잡는** 쪽이다

| 명령 · 상황 | 0.2.0 | 0.3.0 |
| --- | --- | --- |
| `get` 금고 문서 (403 `e2ee_doc`, F-401 X19) | 종료 4 `forbidden` `이 문서를 고칠 권한이 없습니다.` | 종료 4 `e2ee_doc` |
| `put` 금고 문서 (403 `e2ee_doc`, X20) | 종료 4 `forbidden` | 종료 4 `e2ee_doc` |

5. `content/changelog.md` 에 게시한 날 한 줄(12장 제안), `content/guides/cli.md` 갱신(12장) — 웹 배포 한 번 더
